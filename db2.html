Fundamentals & Normalization

Keys, constraints, normal forms, and the relational model.

▶ What is the difference between a database and a DBMS? Core

A database is the collection of data itself — the tables, records, relationships, and files stored on disk. A DBMS (Database Management System) is the software that manages that data: it handles storage, retrieval, security, concurrency, backup, and recovery. The DBMS is the interface between applications and the raw data files.

The analogy: a database is a library, and the DBMS is the librarian system that helps you find, check out, and return books while ensuring nobody steals them or misfiles them[reference:0]. Popular DBMS examples include MySQL, PostgreSQL, Oracle, and SQL Server.

Why it matters in interviews: this distinction sets up deeper questions about what the DBMS guarantees — ACID properties, isolation levels, and query optimization — which are the responsibility of the management layer, not the data itself.

▶ Explain the ACID properties with a concrete example. Core

ACID defines the guarantees of a reliable database transaction:

  • Atomicity: all operations in a transaction succeed or fail together. If any part fails, the entire transaction is rolled back.
  • Consistency: the database moves from one valid state to another. Defined constraints and rules are never violated.
  • Isolation: concurrent transactions do not interfere with each other. Each transaction sees a consistent snapshot of the data.
  • Durability: once a transaction commits, the changes survive system crashes, power loss, or restart.

Bank transfer example: you transfer $100 from Account A to Account B.

  • Atomicity: the debit from A and the credit to B must both happen. If the system crashes after the debit but before the credit, the entire transfer rolls back — money does not vanish.
  • Consistency: the total balance across both accounts remains unchanged. A rule like "balance cannot go negative" is enforced.
  • Isolation: another transaction reading the balances concurrently sees either the pre-transfer state or the post-transfer state, never the intermediate state where A is debited but B is not yet credited.
  • Durability: after the transfer commits, a power failure does not undo it. The committed state is persisted to disk and recoverable[reference:1].
Interview follow-up: "Is ACID always required?" No — many high-scale systems relax isolation (read committed, eventual consistency) to gain throughput, and NoSQL systems often guarantee BASE (Basically Available, Soft state, Eventually consistent) instead. The choice depends on the workload.
▶ What are the different types of database keys, and when do you use each? Core

Keys enforce uniqueness and define relationships. The types every candidate must know:

  • Primary key: uniquely identifies each row. Cannot be null or duplicated. Every table should have one (or a composite primary key).
  • Foreign key: a column that references the primary key of another table, establishing a relationship and enforcing referential integrity — you cannot insert a child row that references a non-existent parent.
  • Candidate key: any column (or set of columns) that could serve as a primary key — unique and non-null. One is chosen as the primary; the others are alternate keys.
  • Composite key: a primary key made of multiple columns, used when no single column is unique (e.g., (student_id, course_id) in an enrollment table).
  • Unique key: ensures uniqueness like a primary key but allows null values (typically one null per column in SQL Server, multiple in PostgreSQL).

A concrete schema example makes the distinction clear:

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    department_id INT,
    email VARCHAR(100) UNIQUE,
    FOREIGN KEY (department_id) REFERENCES departments(id)
);

Here employee_id is the primary key, department_id is a foreign key, and email is a unique key[reference:2].

▶ What is normalization, and why is it generally a good thing? What are the normal forms? Core

Normalization organizes data into separate, related tables to eliminate redundancy and prevent update, insert, and delete anomalies. Without it, the same fact is stored in multiple places: updating one copy but not the others creates inconsistency; deleting a row might accidentally destroy the only copy of an unrelated fact.

The normal forms progressively reduce redundancy:

  • 1NF (First Normal Form): every column contains atomic (indivisible) values, and each row is unique. No repeating groups or arrays in a single column.
  • 2NF (Second Normal Form): 1NF plus no partial dependencies — every non-key column depends on the entire primary key, not just part of a composite key.
  • 3NF (Third Normal Form): 2NF plus no transitive dependencies — non-key columns do not depend on other non-key columns. A department name should not be stored in an employee table if it depends on department_id, which itself is a non-key column.
  • BCNF (Boyce-Codd Normal Form): a stricter version of 3NF that handles certain edge cases with overlapping candidate keys.

The classic example: an orders table that stores customer_name and customer_address alongside every order. If a customer changes address, every order row must be updated — and a missed row causes inconsistency. Normalization splits customer into its own table, referenced by customer_id[reference:3].

Trade-off: normalization optimizes for write correctness and storage efficiency at the cost of more joins on read. Denormalization intentionally reverses this for read-heavy workloads — but it should be a deliberate performance decision, not an accident.
▶ When would you denormalize, and what are the risks? Advanced

Denormalization deliberately introduces redundancy — duplicating a column, precomputing an aggregate, or storing a nested document — to eliminate expensive joins or aggregations on the read path. It is the right choice when reads vastly outnumber writes and the join cost dominates latency.

Common denormalization patterns:

  • Duplicated column: store customer_name in the orders table to avoid joining customers on every order lookup. The risk is stale data if the customer changes their name and the update is not propagated.
  • Precomputed aggregate: store total_order_count on the user row instead of running COUNT(*) on every profile view. The risk is drift — the counter must be updated atomically with the order insert, or reconciled periodically.
  • Materialized view / read model: maintain a separate, query-optimized copy of data (CQRS). The risk is eventual consistency between the write model and the read model.

The risks are real: update anomalies (multiple copies must be updated together), increased storage, and write amplification (a single logical change touches multiple rows). The mitigation is to treat the duplicated data as a cache with an explicit consistency contract — either update synchronously in the same transaction, or accept eventual consistency and reconcile with a background job.

In an interview, the senior signal is to say: "I would normalize by default, and denormalize only when a measured read bottleneck justifies it — and I would document the consistency trade-off."

▶ What is the difference between a clustered and a non-clustered index? Core

A clustered index determines the physical order of rows on disk. Because the table's rows are stored in the order of the clustered index key, a table can have only one clustered index. Range scans on the clustered key are fast because the data is contiguous. In most relational databases, the primary key is the clustered index by default (unless configured otherwise).

A non-clustered index is a separate structure that stores the indexed key plus a pointer (row locator) to the actual row. It is like an index at the back of a book: you find the page number (pointer), then go to the page (the row). A table can have many non-clustered indexes, each accelerating a different query pattern. The cost is that a lookup through a non-clustered index may require an additional I/O to fetch the full row (a "bookmark lookup"), unless the query is covered — meaning all requested columns are present in the index itself.

Interview signal: recommend a clustered index on the column most commonly used for range queries or ordered retrieval (often the primary key), and non-clustered indexes on columns used in frequent WHERE clauses or joins[reference:4].

▶ What is a covered query, and why does it matter? Advanced

A covered query is a query where all the columns referenced — in the SELECT list, the WHERE clause, and the ORDER BY — are present in a single non-clustered index. Because the index already contains everything the query needs, the database can answer it by reading only the index, without touching the base table. This avoids the bookmark lookup I/O and can be dramatically faster for read-heavy workloads.

Example: with an index on (user_id, created_at DESC), the query SELECT user_id, created_at FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 20 is covered — both columns are in the index, and the index is already in the right order, so no sort is needed either.

Why it matters in design: covering indexes are a primary tool for latency-sensitive read paths (feeds, timelines, lookups). The trade-off is write cost — every additional column in an index increases the cost of inserts and updates, and every new index consumes storage. A senior answer names the specific query the index covers and weighs that against the write overhead.

Schema Design Scenarios

Real-world modeling problems: booking systems, org charts, social graphs, and more.

▶ Design a schema that prevents double-booking of the same hotel room for overlapping dates. CoreTrap

The core requirement is a constraint that no two bookings for the same room overlap in time. A naive application-level check ("query for conflicts, then insert") is vulnerable to race conditions: two concurrent requests can both query, both see no conflict, and both insert. The database must enforce the invariant.

PostgreSQL solution: an EXCLUDE constraint using btree_gist prevents overlapping ranges for the same room:

CREATE EXTENSION btree_gist;

CREATE TABLE bookings (
    id BIGSERIAL PRIMARY KEY,
    room_id INT REFERENCES rooms(id) ON DELETE RESTRICT,
    check_in DATE NOT NULL,
    check_out DATE NOT NULL,
    CHECK (check_out > check_in),
    EXCLUDE USING GIST (
        room_id WITH =,
        daterange(check_in, check_out, '[)') WITH &&
    )
);

The EXCLUDE constraint says: for the same room_id (WITH =), the date ranges must not overlap (WITH &&). The '[)' bound makes checkout day available for a new check-in[reference:5].

Portable application-level check (still needs a transaction with appropriate isolation, or a unique constraint fallback):

SELECT id FROM bookings
WHERE room_id = $1
  AND check_in < $3   -- new check_out
  AND check_out > $2; -- new check_in

If this returns any rows, a conflict exists. But to be race-safe, this must run inside a transaction with a lock on the room (e.g., SELECT ... FOR UPDATE on the room row) or a serializable isolation level. The EXCLUDE constraint is the robust database-native solution when available.

What the interviewer tests: whether you recognize that a pure application-level check is not concurrency-safe, and whether you know the database-native range-overlap constraint[reference:6].
▶ Design a schema for a social media follow graph (Twitter-style). Core

The follow graph is a many-to-many self-referencing relationship: a user follows many users, and a user is followed by many users. The natural schema is a junction table:

CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE follows (
    follower_id BIGINT REFERENCES users(id) ON DELETE CASCADE,
    followee_id BIGINT REFERENCES users(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (follower_id, followee_id),
    CHECK (follower_id != followee_id)
);

CREATE INDEX idx_follows_followee ON follows(followee_id);

The composite primary key (follower_id, followee_id) ensures a user cannot follow the same person twice and serves the "who does user X follow?" query. The additional index on followee_id serves the reverse query, "who follows user Y?", which is essential for feed generation[reference:7].

Design considerations:

  • Celebrity problem: a user with 50 million followers has 50 million rows in follows pointing to them. Querying "who follows celebrity X" is expensive. Mitigations include caching the follower list, or accepting that fan-out on read is the only viable strategy for celebrities (see the news feed design).
  • Sharding: the follows table is typically sharded by follower_id so all of a user's outgoing follows are co-located. The reverse query (followers of a user) then requires a secondary index or a separate denormalized table.
  • Soft deletes: instead of hard-deleting a follow, a deleted_at column allows auditing and undo. The composite key must then include deleted_at or use a partial unique index.
▶ Design a schema for an org chart where employees have managers and you need to query the full hierarchy. Advanced

The self-referencing table is the natural model:

CREATE TABLE employees (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    manager_id BIGINT REFERENCES employees(id),
    salary DECIMAL(12,2)
);

The manager_id points to another row in the same table. The CEO has manager_id IS NULL[reference:8].

Query 1 — employees earning more than their manager: a self-join with aliases:

SELECT e.name AS employee, m.name AS manager
FROM employees e
JOIN employees m ON e.manager_id = m.id
WHERE e.salary > m.salary;

This is one of the most frequently asked SQL questions at all levels — it tests self-join fluency[reference:9].

Query 2 — full hierarchy with depth: a recursive CTE walks the tree from the root:

WITH RECURSIVE org_chart AS (
    SELECT id, name, manager_id, 0 AS depth, name::TEXT AS path
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, oc.depth + 1,
           oc.path || ' → ' || e.name
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT depth, name, path FROM org_chart ORDER BY path;

This produces the CEO at depth 0, direct reports at depth 1, and so on, with a readable path string[reference:10].

Performance consideration: recursive CTEs are elegant but can be slow on very deep hierarchies or large datasets. For read-heavy org-chart displays, a materialized path (storing "/1/5/12/" on each row) or a closure table (a separate table storing every ancestor-descendant pair) makes descendant queries simple indexed lookups at the cost of write complexity. The choice depends on whether the hierarchy is read-heavy or write-heavy.

▶ Design a schema for a monthly cohort retention analysis. Advanced

The goal: for each signup cohort (users grouped by signup month), show what percentage were still active in months 1, 2, 3, etc. after signup. The schema needs users and their activity events:

CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    created_at DATE NOT NULL
);

CREATE TABLE events (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT REFERENCES users(id),
    event_date DATE NOT NULL
);

CREATE INDEX idx_events_user_date ON events(user_id, event_date);

The analysis query joins each user to their events, computes the month difference between the event and signup, and aggregates:

WITH user_cohorts AS (
    SELECT id AS user_id,
           DATE_TRUNC('month', created_at) AS cohort_month
    FROM users
),
activity AS (
    SELECT uc.cohort_month,
           DATE_TRUNC('month', e.event_date) AS activity_month,
           COUNT(DISTINCT e.user_id) AS active_users
    FROM user_cohorts uc
    JOIN events e ON e.user_id = uc.user_id
    GROUP BY uc.cohort_month, DATE_TRUNC('month', e.event_date)
)
SELECT cohort_month,
       activity_month,
       active_users,
       active_users * 100.0 /
         FIRST_VALUE(active_users) OVER (
             PARTITION BY cohort_month ORDER BY activity_month
         ) AS retention_pct
FROM activity
ORDER BY cohort_month, activity_month;

The key modeling insight: retention is a derived metric, not a stored column. The schema stores raw users and events; the cohort and retention calculations are computed at query time or materialized into a summary table for dashboards. Storing a retention_rate column on the user row would be a denormalization that drifts and becomes incorrect[reference:11].

▶ How would you design a schema for a multi-tenant SaaS application? DesignAdvanced

Multi-tenancy has three common schemas, each with different isolation and scaling characteristics:

  • Shared schema, tenant_id column: every table has a tenant_id column, and every query filters by it. This is the simplest and most storage-efficient — one database serves all tenants. The risk is a missing tenant_id filter leaking one tenant's data to another. Enforce it with row-level security or a mandatory query builder that always injects the filter.
  • Schema per tenant: each tenant gets its own database schema (namespace) within the same database instance. Isolation is stronger — a query cannot accidentally cross tenants because the schema boundary is explicit. The cost is more schemas to manage, and migrations must run per schema.
  • Database per tenant: the strongest isolation, one database instance per tenant. Used for enterprise customers with regulatory requirements or extreme scale. The cost is operational overhead — provisioning, backups, and migrations multiply by the number of tenants.

Sharding consideration: for the shared-schema model, shard by tenant_id so all of a tenant's data is co-located on one shard. Hash-shard the long tail of small tenants for even distribution, and range-isolate large enterprise tenants onto dedicated shards so their load does not affect others.

The senior signal: name the isolation requirement first ("does the customer require physical separation for compliance?"), then choose the model, and explain the trade-off between isolation strength and operational cost.

▶ Design a schema for a URL shortener's storage layer. Design

The core mapping is trivial — short_code → long_url — but the design decisions are about scale and key generation.

CREATE TABLE urls (
    id BIGSERIAL PRIMARY KEY,
    short_code VARCHAR(7) UNIQUE NOT NULL,
    long_url TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT now(),
    expires_at TIMESTAMPTZ,
    click_count BIGINT DEFAULT 0
);

CREATE INDEX idx_urls_short_code ON urls(short_code);

Key generation is the hard part. You cannot use a naive auto-increment sequence as the short code because it leaks volume and is a single bottleneck. Options:

  • Range-based allocation: a central service hands out blocks of IDs to application servers (server A gets 1–10k, server B gets 10k–20k). Each server base62-encodes its local IDs with no per-request coordination. This is the scalable classic.
  • Hash-based: hash the long URL and take the first 7 characters. Collisions must be detected and resolved, which adds write-path complexity.
  • Snowflake-style: timestamp + machine ID + sequence, base62-encoded. Unique without coordination.

Scale considerations: the urls table is sharded by a hash of short_code for even read distribution. The read path is cache-first — hot short codes live in Redis or a CDN with a short TTL, so the database sees a fraction of redirect traffic. Analytics (click counts) should not block the redirect: increment asynchronously via a queue, or use a sharded counter if the write volume is high.

Indexing & Performance

B-trees, composite indexes, query planning, and the cost of indexes.

▶ How does an index work, and why doesn't every column have one? Core

An index is a separate data structure — typically a B-tree (or B+ tree) — that stores the indexed column values in sorted order along with pointers to the corresponding rows. Instead of scanning the entire table (a full table scan) to find matching rows, the database traverses the B-tree in O(log n) and jumps directly to the relevant rows.

Indexes accelerate reads but impose real costs:

  • Storage: every index consumes disk space, sometimes a significant fraction of the table size.
  • Write overhead: every INSERT, UPDATE, and DELETE must also update every index on the table. A table with ten indexes pays ten index-maintenance costs per write.
  • Memory pressure: indexes compete for buffer pool memory; too many indexes reduce the cache available for data pages.

The rule: index the columns that appear in WHERE, JOIN, and ORDER BY clauses of frequent queries, and avoid indexing columns that are rarely queried or have very low selectivity (e.g., a boolean flag, where a scan is often cheaper than an index lookup because the index returns half the table)[reference:12].

Interview follow-up: "Why might the query optimizer ignore your index?" Common reasons: the column is wrapped in a function (WHERE YEAR(created_at) = 2024), the type does not match (string vs. integer), statistics are stale, or the optimizer estimates that a sequential scan is cheaper because the query returns a large fraction of the table.
▶ What is a composite index, and what is the leftmost-prefix rule? Core

A composite index indexes multiple columns together, in a specified order. For example, CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC). The index is sorted first by user_id, then by created_at within each user.

The leftmost-prefix rule: the index can be used efficiently only when the query filters on a leading prefix of the indexed columns. With the index above:

  • WHERE user_id = ? — uses the index (leading column).
  • WHERE user_id = ? ORDER BY created_at DESC — uses the index for both filtering and ordering (no sort needed).
  • WHERE created_at > ? — does not use the index efficiently, because created_at is not the leading column.

Column order matters enormously. The leading column should be the one used in equality predicates or the most selective filter; the trailing column should be the one used for range scans or ordering. In the orders example, (user_id, created_at) serves "get user X's orders, newest first" perfectly — filtering and sorting are both handled by the index.

▶ How would you find and fix a slow query? Advanced

Slow-query diagnosis is a structured process, not guesswork:

  1. Identify the query: use the database's slow-query log (MySQL slow_query_log, PostgreSQL log_min_duration_statement) or an APM tool to find the queries consuming the most time or causing the most load.
  2. Read the execution plan: run EXPLAIN (and EXPLAIN ANALYZE in PostgreSQL) to see whether the query uses an index, does a sequential scan, performs a costly join order, or sorts a large intermediate result. Look for "Seq Scan," "Using filesort," or "Using temporary" — these are common red flags.
  3. Check for missing or unused indexes: a missing index on a join or filter column causes a full scan. An unused index adds write overhead without benefit. Review index usage statistics (pg_stat_user_indexes, sys.dm_db_index_usage_stats).
  4. Look for anti-patterns: functions wrapping indexed columns (WHERE YEAR(created_at) = 2024 prevents index use), SELECT * pulling unnecessary columns, OFFSET pagination on deep pages, and OR conditions that defeat index usage.
  5. Consider schema changes: a covering index, a composite index in the right column order, or denormalizing a frequently joined column may be the real fix. Sometimes the query itself should be rewritten.
  6. Check statistics and hardware: stale statistics cause the optimizer to choose a bad plan; insufficient memory causes excessive disk I/O; lock contention can make a fast query appear slow.

The senior signal: describe the diagnostic process (EXPLAIN, slow-query log) rather than jumping to "add an index." Adding an index without understanding the plan can make writes slower without fixing the read.

▶ How would you delete 200 million rows without killing the database? TrapAdvanced

A naive DELETE FROM table WHERE condition on 200 million rows is dangerous: it holds locks for a long time, fills the transaction log, bloats the table and indexes, and can block other queries and replication. The safe approach is batched deletion:

  • Delete in small batches (e.g., 10,000 rows per batch) in a loop, with a short sleep between batches to let replication and vacuuming catch up. Each batch is its own transaction, so locks are short-lived and the log does not explode.
  • Use the primary key or an indexed column for the batch boundary: DELETE FROM table WHERE id IN (SELECT id FROM table WHERE condition LIMIT 10000) or delete by an ID range.
  • Consider partitioning: if the rows to delete belong to old time ranges, and the table is partitioned by time, dropping the entire partition is instantaneous and avoids row-by-row deletion entirely. This is the best solution when applicable.
  • Monitor replication lag and lock contention throughout the process; pause or slow the batches if lag grows.
  • Run during low-traffic windows and have a rollback plan (a backup of the affected range) in case the wrong condition is used.

The interview signal is recognizing that bulk deletion is an operational hazard, not just a SQL statement[reference:13].

Transactions & Concurrency

Isolation levels, deadlocks, and race conditions.

▶ What are the isolation levels, and what anomalies do they prevent? Core

Isolation levels trade consistency for concurrency. The SQL standard defines four levels, each preventing a specific set of anomalies:

LevelDirty readNon-repeatable readPhantom read
Read UncommittedPossiblePossiblePossible
Read CommittedPreventedPossiblePossible
Repeatable ReadPreventedPreventedPossible
SerializablePreventedPreventedPrevented
  • Dirty read: reading uncommitted data from another transaction that may later roll back.
  • Non-repeatable read: reading the same row twice within a transaction and getting different values because another transaction committed an update in between.
  • Phantom read: running the same query twice and getting different sets of rows because another transaction inserted or deleted rows that match the condition.

The default in most databases is Read Committed (PostgreSQL, Oracle) or Repeatable Read (MySQL InnoDB). Serializable is the strongest but reduces concurrency and can cause more serialization failures (deadlocks or retries). The choice depends on the invariant: a bank transfer may need Serializable, while a dashboard query tolerates Read Committed[reference:14].

▶ How do you prevent a race condition when two users try to claim the last item in inventory? Trap

The naive approach — SELECT quantity; if quantity > 0 then UPDATE quantity = quantity - 1 — is a classic race condition. Two concurrent transactions both read quantity = 1, both decide they can proceed, and both update, resulting in quantity = -1.

Three correct approaches:

  • Atomic conditional update: UPDATE inventory SET quantity = quantity - 1 WHERE product_id = ? AND quantity >= 1. The database checks and decrements atomically. If the affected row count is 0, the item is out of stock. This is the simplest and most portable solution.
  • SELECT ... FOR UPDATE (pessimistic lock): lock the row before reading it: SELECT quantity FROM inventory WHERE product_id = ? FOR UPDATE. The second transaction blocks until the first commits, preventing the race. The cost is lock contention under high concurrency.
  • Optimistic concurrency with a version column: read the row with its version, then UPDATE ... SET quantity = quantity - 1, version = version + 1 WHERE product_id = ? AND version = ?. If the version has changed, the update affects 0 rows and the application retries. This avoids locks but requires retry logic.

The senior signal: name the race condition explicitly and choose the mechanism based on contention level — atomic update for simple cases, pessimistic lock for low-contention critical sections, optimistic locking for high-contention reads with occasional writes.

▶ What is a deadlock, and how do you handle it? Advanced

A deadlock occurs when two or more transactions hold locks that the others need, and each waits for the other to release — a circular wait. Transaction A locks row 1 and waits for row 2; Transaction B locks row 2 and waits for row 1. Neither can proceed.

Databases detect deadlocks automatically (via a wait-for graph) and kill one transaction (the victim) with a deadlock error, allowing the other to proceed. The application must catch that error and retry the victim transaction.

Prevention and mitigation:

  • Access rows in a consistent order: if every transaction locks rows in the same order (e.g., ascending primary key), circular waits are impossible.
  • Keep transactions short: the longer a transaction holds locks, the higher the chance of a deadlock. Do not hold locks while waiting for user input or external API calls.
  • Use lower isolation levels where possible: Read Committed holds fewer locks than Serializable, reducing deadlock frequency.
  • Retry on deadlock: deadlock errors are transient — a well-designed application retries the victim transaction with a small backoff.

In an interview, mention that deadlocks are normal in busy systems and the correct response is detection plus retry, not panic.

Scalability & Core Concepts

Load balancing, caching, CAP, consistency, and database scaling.

▶ Explain the difference between horizontal and vertical scaling, and when you would choose each. Core

Vertical scaling (scaling up) means adding more resources — CPU, RAM, disk — to a single machine. Horizontal scaling (scaling out) means adding more machines to the pool.

Vertical scaling is operationally simple: no code changes, no distributed coordination. It is the right first move for most systems because it buys time cheaply. But it has a hard ceiling (the largest available machine), creates a single point of failure, and cost grows super-linearly. Horizontal scaling is theoretically unbounded and improves availability through redundancy, but requires stateless services, data partitioning, and tolerance for partial failure.

DimensionVerticalHorizontal
EffortLowHigh
CeilingHardEffectively unbounded
AvailabilitySingle point of failureRedundant

The pragmatic strategy is scale up first, then out — delay the complexity of distribution until the pain is real. When you do scale out, design for statelessness and partitionable data from the beginning so the transition is possible.

▶ What is a load balancer, and what algorithms does it use? Core

A load balancer distributes incoming traffic across a pool of backend servers so that no single server is overwhelmed. It is the entry point that makes a fleet of servers look like a single logical service, enabling horizontal scaling and high availability[reference:16].

Common algorithms:

  • Round Robin: requests are distributed in circular order. Simple, but ignores server load and capacity — a slow server still gets its full share.
  • Least Connections: routes to the server with the fewest active connections. Better for uneven workloads, but requires tracking connection state.
  • IP Hash: hashes the client IP to select a server, providing session affinity (the same client goes to the same server). Useful for stateful applications, but can create imbalance if many clients share a NAT IP.
  • Weighted Round Robin: assigns weights to servers based on capacity, so a larger machine receives proportionally more traffic.
  • Least Response Time: routes to the server with the lowest latency and fewest connections, optimizing for user-perceived speed.

The choice depends on the workload: Round Robin for homogeneous stateless services; Least Connections for long-lived connections (WebSockets); IP Hash for session stickiness. A senior answer also mentions health checks — the load balancer must remove unhealthy backends from rotation.

▶ Explain caching strategies: cache-aside, write-through, and write-behind. Core

Caching strategies define how the application reads from and writes to the cache and the database:

  • Cache-aside (lazy loading): the application checks the cache first. On a miss, it reads from the database, writes the result to the cache, and returns it. Writes go directly to the database; the cache is invalidated or updated afterward. This is the most common pattern — simple and flexible, but the first request after a miss is slow, and stale data is possible if invalidation is imperfect.
  • Write-through: every write goes to the cache and the database synchronously in the same transaction. Reads always hit the cache. Consistency is strong, but write latency is higher (two writes), and the cache is populated with data that may never be read.
  • Write-behind (write-back): writes go to the cache and are acknowledged immediately; the cache asynchronously flushes to the database in batches. Write latency is lowest, but data loss is possible if the cache crashes before flushing. Used for high-write workloads where some durability trade-off is acceptable.

The interview signal is matching the pattern to the workload: cache-aside for read-heavy with tolerable staleness; write-through for read-heavy with strong consistency; write-behind for write-heavy with durability flexibility[reference:17].

▶ Explain the CAP theorem and its practical implications. CoreAdvanced

CAP states that in a distributed system experiencing a network partition (P), you must choose between consistency (C) and availability (A). The common misreading is "pick two of three" — but partition tolerance is not optional in any real distributed system, because networks partition. The real choice is: when a partition occurs, do you sacrifice consistency or availability?

  • CP systems (consensus-based databases) refuse writes or reads on the minority side of a partition to preserve consistency. Writes fail during the partition, but data is never wrong.
  • AP systems (Dynamo-style stores) continue serving both sides, accepting divergence. Consistency is restored later via conflict resolution. Users get a response, but it may be stale or conflicting.

The practical decision framework: ask "what does the user experience if they see stale data for a short period?" If the answer is "nothing catastrophic," AP is acceptable. If the answer is "financial loss or legal liability," you need CP, and you must design for write unavailability during partitions[reference:18].

Nuance: CAP is binary only during a partition. In normal operation you can tune consistency continuously (quorum reads/writes, read-your-writes). PACELC extends CAP: even without partitions, there is a latency-vs-consistency trade-off.
▶ What is a CDN, and how does it improve performance? Core

A CDN (Content Delivery Network) is a geographically distributed network of edge servers that cache and serve content close to the user. When a user requests a static asset (image, video, CSS, JS), the request is routed to the nearest edge node. If the edge has the asset cached, it serves it immediately; if not, it fetches from the origin, caches it, and serves it.

The performance benefits are dramatic: a user in Mumbai fetching from an edge in Mumbai experiences single-digit-millisecond latency instead of a 200ms round trip to an origin in Virginia. The CDN also absorbs traffic spikes — a viral video is served from thousands of edge caches, and the origin sees a tiny fraction of the total requests.

CDN design considerations:

  • Cache TTL: short TTLs keep content fresh but reduce hit rate; long TTLs increase hit rate but risk stale content. Versioned URLs (e.g., app.v2.js) allow long TTLs with instant invalidation.
  • Cache invalidation: purge APIs remove stale content from all edges, but purges are slow and expensive. Prefer versioned URLs where possible.
  • Dynamic content: CDNs can also accelerate dynamic API responses through edge computing or connection optimization, but the primary benefit is for static and cacheable content.

Classic Design Problems

URL shortener, rate limiter, chat, news feed, and more.

▶ Design a URL Shortener (TinyURL). Design

Requirements: given a long URL, return a short URL; given a short code, redirect to the original. Read-heavy (redirects vastly outnumber creations), low latency, high availability.

Key challenge — unique ID generation at scale: you cannot use a naive auto-increment database sequence because it is a single bottleneck and leaks volume. Options:

  • Range-based allocation: a central service hands out blocks of IDs to each application server (server A gets 1–10k, server B gets 10k–20k). Each server base62-encodes its local IDs with no per-request coordination. This is the scalable classic.
  • Hash-based: hash the long URL and take the first 7 characters. Collisions must be detected and resolved, adding write-path complexity.
  • Snowflake-style: timestamp + machine ID + sequence, base62-encoded. Unique without coordination.

Storage: a key-value store mapping short_code → long_url, sharded by a hash of the short code for even distribution and horizontal scale. Replicate each shard for read availability[reference:20].

Read path: redirects are pure point lookups — cache hot codes in Redis or a CDN edge with a short TTL. A 301 (permanent) redirect lets browsers cache, reducing load at the cost of analytics; a 302 (temporary) preserves analytics.

Scale estimate to state: at 100M shortenings/day and 10B redirects/day, the read-to-write ratio is 100:1 — optimize and cache the read path aggressively.

▶ Design a Rate Limiter for APIs. Design

Requirements: limit requests per user/IP/API key over a time window (e.g., 100 requests/minute), with low latency and correctness under concurrency[reference:21].

Algorithms:

  • Fixed window: count requests per minute, reset at the boundary. Simple but allows a burst at the boundary (200 requests in a 2-second span across two windows).
  • Sliding window log: store timestamps of each request and count those within the window. Accurate but memory-heavy at scale.
  • Sliding window counter: interpolate between the current and previous fixed windows. Approximate but memory-efficient — the standard production choice.
  • Token bucket: a bucket refills at a steady rate; each request consumes a token. Allows controlled bursts and is easy to implement atomically in Redis.

Storage: counters live in a distributed cache (Redis) with atomic operations — INCR plus EXPIRE, or a Lua script for token-bucket atomicity. Shard counters by user ID or API-key hash so no single Redis node is a bottleneck.

Failure mode: if the rate-limiter store is unavailable, fail open (allow traffic) for most APIs — the limiter is a protection mechanism, not a correctness requirement. Fail closed only when protection is more important than availability.

Placement: enforce at the API gateway or edge so abusive traffic never reaches application servers. Return 429 Too Many Requests with Retry-After and X-RateLimit-Remaining headers.

▶ Design a Chat Application (WhatsApp-style). DesignAdvanced

Requirements: real-time one-on-one and group messaging, delivery receipts, presence (online/offline), and message history. Low latency and high reliability[reference:22].

Connection layer: WebSockets maintain persistent bidirectional connections between clients and chat servers. Each chat server handles thousands of connections; a connection registry maps user_id → server so messages can be routed to the server holding the recipient's connection.

Message flow: sender → chat server → message queue (Kafka) → recipient's chat server → recipient. The queue decouples the sender's request from delivery, provides durability, and enables retry. Message IDs are generated by the server (not the client) and ordered per conversation.

Storage: messages are stored in a wide-column store (Cassandra) or a sharded relational database, sharded by conversation_id so a conversation's history is co-located. Messages are immutable — no updates, only inserts — which simplifies replication and caching. Recent messages are cached in Redis for fast scroll-back.

Delivery guarantees: at-least-once delivery with client-side deduplication by message ID. When a message is delivered, the recipient's device sends an acknowledgment back through the same path, which updates the sender's "delivered" status.

Presence: a separate presence service tracks online/offline status via heartbeats on the WebSocket connection. Presence updates are broadcast to relevant contacts (friends, group members) through a pub/sub channel.

Group chat: a group message is fanned out to all members. For large groups (hundreds of members), fan-out is done asynchronously via the message queue rather than synchronously in the sender's request.

▶ Design a social media news feed. DesignAdvanced

The core tension — fan-out on write vs fan-out on read:

  • Fan-out on write (push): when a user posts, insert the post ID into the feed cache of every follower. Reads are trivial — fetch the precomputed feed. But a celebrity with 50M followers triggers 50M writes per post, which is infeasible.
  • Fan-out on read (pull): when a user opens their feed, fetch recent posts from everyone they follow and merge. Writes are trivial, but reads are expensive for users who follow thousands of accounts.

The hybrid (standard solution): fan-out on write for normal users, fan-out on read for celebrities. Normal posts are pushed to followers' feed caches; celebrity posts are merged at read time. This bounds write amplification while keeping reads fast for the common case[reference:23].

Storage: feed caches are per-user, sharded by user ID, stored in Redis as a bounded list of post IDs (e.g., last 500) with a TTL. Post content is stored separately, sharded by post ID, and fetched on hydration. The social graph is its own sharded store, often cached.

Read path: fetch cached feed IDs → merge in celebrity posts from the read-time path → hydrate post content (cache-first) → rank/filter → return. The senior signal is naming the celebrity case explicitly and explaining the hybrid fan-out trade-off.

▶ Design a distributed queue like Kafka. DesignAdvanced

Requirements: durable message storage, at-least-once delivery, horizontal scale, and consumer groups that process messages in parallel.

Partitioning: a topic is split into partitions. Messages are assigned to a partition by key (hash of the key). Ordering is guaranteed within a partition, not across partitions. To preserve per-user ordering, key by user ID so all of a user's messages land in the same partition[reference:24].

Consumer groups: each partition is assigned to exactly one consumer within a group, so consumers process partitions in parallel without duplicate consumption within the group. Rebalancing redistributes partitions when consumers join or leave.

Replication: each partition is replicated across brokers (leader + followers). Producers write to the leader; followers replicate. A write is acknowledged when the configured quorum has persisted it. If the leader fails, a follower is promoted — the same failover and split-brain concerns as database replication apply.

Durability: messages are appended to a commit log on disk, providing sequential-write throughput far higher than random writes. Retention is time- or size-based; consumers track their offset, enabling replay.

Delivery semantics: at-least-once is the default. Exactly-once requires idempotent consumers (dedupe by message ID) or transactional offset commits. The practical choice is at-least-once plus idempotent consumers.

▶ Design a web crawler. Design

Requirements: crawl billions of pages, respect politeness (robots.txt, rate limits), avoid duplicates, and keep the crawl fresh. The design is a pipeline of URL frontier → fetcher → parser → storage.

  • URL frontier: a prioritized queue of URLs to crawl. Priority is based on page importance (PageRank, update frequency) and politeness (per-domain crawl delay). The frontier is sharded by domain so one slow domain does not block others.
  • Fetcher: a distributed fleet of workers that fetch pages. DNS resolution is cached; HTTP connections are pooled. Politeness is enforced per domain — a worker checks the last-crawl timestamp for the domain before fetching.
  • Parser and deduplication: the parser extracts links and content. Duplicate detection uses a Bloom filter or a hash of the normalized content to avoid crawling the same page twice. The URL canonicalization step removes fragments, session IDs, and tracking parameters.
  • Storage: raw HTML in object storage; extracted text and metadata in a search index (Elasticsearch) or a distributed store. The link graph is stored separately for PageRank computation.

The scaling challenge is the frontier and politeness: a naive crawler hammers a single domain or spreads too thin to make progress. The frontier must balance breadth (many domains) with politeness (slow per domain), and the fetcher fleet must be sized to the number of concurrent domains, not the total URL count[reference:25].

▶ Design a notification system (push, email, in-app). Design

Pipeline: producers (order service, social service) publish notification events to a message queue (Kafka). A notification service consumes events, applies user preferences and rate limits, renders the message per channel, and dispatches to channel-specific adapters (APNs/FCM for push, SES/SendGrid for email, an in-app store for the feed). This decouples producers from delivery.

Sharding: the queue is partitioned by user ID so a user's notifications are ordered. The in-app store is sharded by user ID for per-user reads. Channel adapters scale independently — email throughput needs differ from push[reference:26].

Idempotency and deduplication: each notification carries a unique ID. Before sending, check a dedupe store (Redis with TTL) so a retried event does not send twice. Duplicate push notifications are a visible quality bug.

Rate limiting and preferences: per-user rate limits (no more than N notifications per hour) and per-channel opt-outs are enforced before dispatch. This prevents notification fatigue, which drives uninstalls.

Retries and failure: channel adapters retry with exponential backoff on transient failures; permanent failures (invalid device token) are dropped and the token marked stale. A dead-letter queue captures failures for inspection. Circuit breakers prevent a failing provider (APNs outage) from backing up the pipeline.

Advanced & Failure Modes

Backpressure, idempotency, sagas, circuit breakers, and senior-level thinking.

▶ How do you design for backpressure? Advanced

Backpressure is the mechanism by which a saturated downstream component signals upstream producers to slow down. Without it, queues grow unbounded, memory exhausts, and the system collapses — a cascading failure[reference:27].

Design techniques: bounded queues (force a decision when full — block, drop, or reject), rate limiting at the edge, load shedding (reject excess requests early with 429/503), circuit breakers (fail fast when a dependency is down), and bulkheads (isolate resource pools per dependency).

The key insight: backpressure requires a rejection policy. A system that "handles" backpressure by buffering indefinitely is not applying backpressure — it is deferring the failure. The senior answer names the policy and ties it to user experience.

▶ How do you handle idempotency in write APIs? Advanced

Idempotency ensures that repeating the same request produces the same result as executing it once — critical for payment and order APIs where a timeout-then-retry could charge twice.

The standard pattern: the client generates a unique idempotency key (UUID) per logical operation. The server checks a dedicated store (database or Redis) for that key before executing. If the key exists and the operation completed, return the stored response. If it does not exist, record it as "in progress" atomically (unique constraint or SET NX), execute, store the result, and return.

Critical details: the check-and-insert must be atomic to prevent concurrent duplicate execution; keys should be scoped per user; records expire after a bounded window (e.g., 24 hours); and the "in progress" record must be written before the side effect so a crash mid-operation is detected on retry rather than silently re-executed.

▶ How do you implement distributed transactions without 2PC? Advanced

The Saga pattern breaks a global transaction into a sequence of local transactions, each paired with a compensating action that undoes it if a later step fails. For example: reserve inventory → charge payment → create shipment. If shipment fails, compensate by refunding payment and releasing inventory.

Reliability is the hard part. The Outbox pattern writes the business change and the event to an outbox table in the same local transaction; a relay process publishes the outbox rows to the message broker. This guarantees at-least-once delivery without a distributed transaction. The Inbox pattern makes consumers idempotent by recording processed message IDs in an inbox table within their local transaction.

The trade-off: Sagas are eventually consistent and expose intermediate states to the outside world. Compensations are business-level undo operations, not database rollbacks — refunds have their own latency and failure modes. Design the state machine so intermediate states are visible and recoverable.

▶ What is the circuit breaker pattern? Advanced

The circuit breaker prevents a failing dependency from cascading into a system-wide outage. It wraps calls to a dependency and tracks failures. When the failure rate exceeds a threshold, the breaker opens — subsequent calls fail immediately, without attempting the dependency. This stops the request pile-up that would otherwise exhaust threads and memory.

Three states: closed (normal operation), open (fail fast), and half-open (limited test calls to probe recovery). If the probes succeed, the breaker closes; if they fail, it reopens.

Why it matters: without a breaker, a slow dependency causes every request to wait for a timeout, exhausting the caller's thread pool and taking down the caller even though it is healthy. The breaker converts a slow failure into a fast one, preserving capacity and giving the dependency time to recover.

▶ What separates a senior engineer's system design answer from a mid-level one? Advanced

A mid-level answer lists components: "we'd use Kafka, Redis, Cassandra, and a load balancer." A senior answer describes how the system behaves under failure and why each choice was made over its alternatives.

Concrete differences:

  • Trade-off reasoning: "We chose async replication because the RPO of a few seconds is acceptable for analytics, but the payment path uses synchronous replication because losing a committed charge is unacceptable."
  • Failure modes: "If Kafka is down, producers fall back to synchronous writes behind a circuit breaker; if a shard is hot, we detect it via per-shard p99 and trigger an automated split."
  • Operational reality: resharding plans, monitoring, deployment strategy, and rollback paths are part of the design, not an afterthought.
  • Numbers: back-of-envelope estimates anchor the design in reality. "At 10k writes/sec and 1KB payloads, that's 10MB/s, which fits on one node."
  • Explicit consistency contracts: "Reads are eventually consistent except for the user's own writes, which are served from the primary for 5 seconds."

Interviewers evaluate how you think, not whether you can recite a reference architecture. State your assumptions, justify your choices, and name the trade-offs you accepted[reference:28].
