Part A — The Broker Layer Building the messaging substrate itself

1

Design a distributed message queue from scratch. Walk through the API, data model, replication, and consumer coordination.

Short Answer

A partitioned, replicated append-only log with producer, broker, and consumer components. Topics split into partitions; each partition has one leader and N-1 followers; producers append; consumers read by offset and commit; a coordinator assigns partitions to consumers and stores offsets. The API is five operations: create_topic, produce, consume, commit, join_group.

Requirements

  • Functional: publish messages to topics; consume in order per partition; multiple independent consumer groups; replay from any offset; retention configurable per topic.
  • Non-functional: 1M messages/s at 1 KB (1 GB/s); p99 produce latency < 10 ms; no loss once acknowledged; 99.99% availability; retain 7 days hot, 1 year warm.

Architecture

  • Producers — batch messages, partition by key hash, send to the leader, handle retries with idempotence.
  • Brokers — store partitions as segmented logs on disk; serve produces and consumes; replicate to followers.
  • Controller — elected broker that manages metadata, leader election, partition assignment (Raft-based in the modern design).
  • Coordinators — one broker per group that manages membership, rebalances, and offset commits.
  • Consumers — pull batches, process, commit offsets; one consumer per partition in the group.
  • Registry / metadata store — the internal topic that holds cluster state and group offsets.

Write path

  1. Producer selects the partition by hashing the key; fetches metadata for the leader.
  2. Batch is compressed and sent to the leader.
  3. Leader appends to its active segment (sequential write, page cache).
  4. Followers fetch from the leader and append to their own logs.
  5. Leader updates the high-water mark when all ISR members have acked.
  6. Producer receives the offset; the ack depends on acks (1 or all).

Read path

  1. Consumer fetches from the assigned partition's leader by offset.
  2. Leader reads from the page cache (recent) or disk (with index lookup).
  3. Consumer processes the batch, then commits the next offset to the coordinator.
  4. On restart or rebalance, the consumer resumes from the committed offset.

Replication and failover

Each partition has a leader and followers. Followers are in the ISR if they are caught up to the leader's high-water mark. acks=all waits for the ISR; min.insync.replicas prevents a write when the ISR shrinks below 2. On leader failure, the controller promotes an ISR follower within seconds; the producer retries, and the idempotent producer deduplicates by sequence number.

Consumer coordination

Groups join via the coordinator, which assigns partitions to consumers (range, round-robin, sticky, cooperative-sticky). Committed offsets are stored in a compacted internal topic, surviving broker failures. Rebalances pause consumption (eager) or move partitions incrementally (cooperative). Static membership (group.instance.id) avoids rebalances on restart.

The scale arithmetic

1M messages/s × 1 KB = 1 GB/s produce; with replication factor 3, 3 GB/s of disk writes across the fleet. A broker with 500 MB/s of disk throughput handles ~170 MB/s of unique produce, so 6 brokers minimum for throughput, and 20–100 partitions (at 10k–50k msg/s per partition). Disk for 7 days at 1 GB/s with 3× replication = 1.8 PB, which needs tiered storage to be economical.

Trade-off

The partitioned-log design gives high throughput and replay at the cost of per-partition ordering (not global), storage (retention), and operational complexity (replication, rebalancing). A destructive queue is simpler but loses replay and multiple consumer groups. The log is the right abstraction when the workloads need fan-out and replay; the queue is right when they do not.

Interview Framing

Say: "It's a partitioned replicated log. Topics split into partitions; each is a segmented log with a leader and followers; producers batch and append; consumers pull by offset and commit to the coordinator; the controller handles metadata and leader election. The API is five operations." That names the abstraction and the components in thirty seconds.

2

Design a pub/sub system like Kafka. Focus on topics, partitions, consumer groups, and delivery guarantees.

Short Answer

A pub/sub system where each topic is partitioned, each partition is a replicated ordered log, and each consumer group independently reads all partitions with per-partition ordering. Delivery is at-least-once by default, exactly-once within Kafka via the transactional API, and at-most-once with acks=0. The system's power is that a single event serves many independent consumers without duplication in storage.

Requirements

  • Functional: topics with configurable partitions; independent consumer groups; replay by offset; retention (time/size); log compaction; producer idempotence and transactions.
  • Non-functional: 1M+ messages/s; p99 produce < 10 ms; strong durability with acks=all; 99.99% availability; multi-region replication.

Topics and partitions

A topic is created with a partition count and replication factor. Partitions are the unit of parallelism and ordering. Messages are assigned to partitions by key hash or round-robin. The key choice decides what is ordered: the same key → the same partition → the same order. The partition count is chosen for the maximum expected consumer parallelism (since a consumer group cannot have more active consumers than partitions).

Consumer groups

A group is a set of consumers that jointly read a topic. Each partition is assigned to exactly one consumer in the group. Multiple groups read the same topic independently, each at its own offset — this is how one event serves billing, inventory, and analytics without duplication in the log. The coordinator manages group membership and assignments; the offsets are stored in a compacted internal topic.

Replication and ISR

Each partition has a leader and N-1 followers. The ISR is the set of followers caught up to the leader's high-water mark. acks=all with min.insync.replicas=2 gives no-loss once acknowledged; unclean leader election is disabled so a lagging replica is never promoted. The controller elects a new leader from the ISR within seconds when the old one fails.

Delivery guarantees

GuaranteeHowCost
At-most-onceacks=0, no retriesLoss
At-least-onceacks=all, retries, consumer commit after processingDuplicates
Exactly-once effects (Kafka-internal)Idempotent producer + transactions + read-committedLatency, coordinator overhead
Exactly-once effects (external)Outbox + idempotent consumer + dedup tableComplexity

The transactional API

An idempotent producer assigns a sequence number per partition; the broker dedups retries. A transactional producer with a transactional.id writes to multiple partitions atomically and commits the consumer's offsets in the same transaction. Read-committed consumers see only committed writes. This gives exactly-once effects within Kafka, at the cost of transaction coordinator overhead and read-committed latency.

Retention and compaction

Retention is time-based (retention.ms) or size-based (retention.bytes). Compaction (cleanup.policy=compact) keeps the latest value per key — the mechanism behind changelogs, event sourcing, and CDC. Tiered storage moves old segments to object storage, making long retention affordable.

Failure modes

FailureBehaviour
Leader crashISR follower promoted; producer retries with idempotence
ISR shrink to 1Writes rejected if min.insync.replicas=2; partition unavailable until a replica returns
Consumer crashRebalance; new consumer resumes from committed offset; duplicates handled by idempotency

Schema mismatchSchema registry rejects incompatible schema; producer retries or fails
Trade-off

Kafka's power comes from the log abstraction: everything is a partition, everything is an offset, and multiple groups read independently. The cost is that per-partition ordering is the only ordering, the partition count is a one-way decision, and the operational complexity is real. The alternatives (Pulsar, Kinesis) make different trade-offs, but Kafka's ecosystem is the reason it remains the default.

Part B — User-Facing Systems Notifications, chat, and collaboration

3

Design a notification system for 100 million daily active users across push, email, SMS, and in-app channels.

Short Answer

A fan-out pipeline with a policy layer: business events enter a queue, an orchestrator resolves the audience, checks preferences and rate caps, renders the template, and dispatches per channel through dedicated adapters. Each channel has its own queue and provider connection. Priority tiers isolate transactional from promotional, and the DLP/push provider is the bottleneck at 100M scale.

Requirements and arithmetic

  • Scale: 100M DAU × 10 notifications/day = 1B/day ≈ 11,600/s average.
  • Bursts: 50M campaign in 30 min ≈ 28,000/s; breaking-news to 20M in 5 min ≈ 67,000/s.
  • Latency: OTP and fraud alerts < 1 s to provider; transactional < 5 s; promotional minutes to hours.
  • Guarantees: critical messages escalate if not acknowledged; promotional are best-effort.

Architecture

ComponentRole
Event ingestionServices publish notification events to a queue (or a synchronous API for OTPs)
OrchestratorResolves audience, checks preferences and rate limits, selects channels, renders templates
Preference servicePer-user, per-channel, per-category opt-ins (Redis-cached); consent audit log
Rate limiterPer-user, per-category token buckets (Redis); promotional only
Template serviceVersioned templates per type/channel/locale; deterministic render
Channel adaptersAPNs, FCM, SES, Twilio, in-app inbox; separate queues and connections
Delivery trackerSent/delivered/opened/failed per notification per channel; token invalidation
SchedulerFuture-dated sends; quiet-hours defers; timezone-aware

Priority isolation

Critical (OTP, fraud) and transactional (order, booking) have dedicated queues, workers, and provider connections, with reserved capacity. Promotional has its own queue with hard rate caps. A shared queue with a priority field still has head-of-line blocking because the workers and dependencies are shared.

The notification flow

  1. Business event → queue (or synchronous API for OTPs).
  2. Audience resolution: single user, segment, or all-users; chunks of 10k for segments.
  3. For each recipient: preference check, rate-limit check, quiet-hours check, channel selection.
  4. Render template; validate against schema; fail loudly if invalid.
  5. Enqueue to the channel's queue; the channel adapter sends to the provider with retries.
  6. Record the delivery receipt; invalidate tokens on 410/UNREGISTERED.
  7. Escalation for critical: if not acknowledged within 30 s, SMS; then email; then voice.

The provider bottleneck at 100M

APNs supports a few thousand requests/s per connection; FCM has per-project quotas; SES has sending reputation limits. The 100M-scale design needs multiple provider accounts/connections and topic-based push (one publish to a provider topic reaches all subscribed devices) for broadcast. The recovery from a provider outage is a controlled ramp, not a full queue drain.

Failure modes

FailureHandling

Trade-off

Separate queues and reserved capacity give strong isolation but cost infrastructure and reduce promotional throughput. A single queue with priorities is simpler but does not isolate. For a system where OTP latency is a business requirement, the isolation is worth the cost.

4

Design a chat application like WhatsApp. Cover WebSocket, message storage, presence, and offline delivery.

Short Answer

Three planes: connection (WebSocket gateways + registry), storage (sharded message log keyed by (conversation_id, seq)), and delivery (fan-out workers route to the recipient's gateway or push). Presence is a heartbeat-plus-TTL store. Offline delivery is just a cursor read from the log on reconnect. Group chat uses write fan-out for small groups, read fan-out for large channels.

Requirements

  • Functional: 1-on-1 and group chat; message history; read receipts; presence; typing indicators; media; multi-device sync; E2E encryption for direct messages.
  • Non-functional: 50M concurrent connections; 100k messages/s; sub-second delivery; no loss; eventual consistency across devices.

The message flow

  1. Sender's client → WebSocket gateway → chat service.
  2. Chat service checks membership, checks dedup, assigns seq (atomic per conversation).
  3. Writes message; updates sender's user_conversations index; acks sender with seq.
  4. Fan-out worker: look up each recipient in the registry.
  5. Online: RPC to the gateway, which writes the frame to the socket.
  6. Offline: push notification; client fetches from the log on reconnect.

Ordering and deduplication

Per-conversation seq assigned by the chat service (single-writer per conversation via consistent hashing, or storage-layer atomic counter). The client buffers out-of-order messages and displays from the contiguous prefix. Duplicates are dropped by seq; retried sends are deduplicated by client_uuid.

Offline and multi-device

Each device has its own last_seen_seq per conversation. On reconnect, the client sends its cursors and fetches the deltas, paginated and rate-limited. Read state (last_read_seq) is per-user and synced across devices via the same WebSocket. Sent messages from one device fan out to the user's other devices as normal messages.

Group chat

Write fan-out for groups ≤ 1,000 (one row per member's inbox or per conversation). Read fan-out for larger groups: the message is stored once, and members fetch from the log. The threshold is where per-message write cost exceeds per-read fetch cost.

Presence

Heartbeat every 20–30 s, TTL 60–90 s. Multi-device uses a connection count. Flapping is handled by hysteresis (two missed heartbeats before offline). For large groups, presence is aggregated ("N online") or scoped to visible members. "Last seen" is often a better fit than live presence on mobile.

E2E encryption

Signal protocol: identity keypair, signed prekey, one-time prekeys; X3DH handshake; Double Ratchet for forward secrecy. Group messages use sender keys distributed pairwise, or MLS for large groups. The server is a public-key directory and ciphertext router; it never sees plaintext. This breaks server-side search, moderation, and backup — the design must scope E2E to direct messages and leave channels unencrypted if search is required.

Interview Framing

Say: "Three planes — connection, storage, delivery. The message log keyed by conversation is the source of truth; WebSocket is the fast path; push is a hint; offline is a cursor read. Group chat uses write fan-out for small groups and read fan-out for large ones." That names the architecture and the fan-out threshold in one answer.

5

Design a real-time collaboration platform (like Google Docs or Figma). How does messaging enable collaborative editing?

Short Answer

Collaboration is a message-passing problem: each client sends operations (edits) to a server, which orders and broadcasts them to all participants. The correctness depends on a convergence strategy — OT (operational transformation) with a central server or CRDTs (conflict-free replicated data types) with peer-to-peer or server-relayed operations. The transport is a WebSocket, the persistence is an operation log or a CRDT document, and presence/cursors ride on the same connection.

Requirements

  • Functional: multiple users edit the same document concurrently; all see a converging state; presence (who is here); cursors (where everyone is); undo/redo per user; offline editing with reconciliation.
  • Non-functional: sub-100 ms round-trip edit visibility; no data loss; convergence within seconds; 100 concurrent editors per document; millions of documents.

The convergence strategies

StrategyHowTrade-off
OT (Operational Transformation) Central server orders operations; transforms concurrent ops against each other Central authority (server required); transformation matrices are complex
CRDT (Conflict-free Replicated Data Types) Operations are commutative; replicas converge without central ordering Metadata overhead (tombstones, IDs); harder to enforce invariants
Lock-based One user edits at a time (lock) No real-time collaboration; only for coarse-grained

Architecture (server-based OT or CRDT relay)

ComponentRole
WebSocket gatewaysHold connections; forward client ops to the document service; broadcast server ops
Document serviceOne per document (or sharded by document_id); orders ops, applies them, broadcasts
Operation logDurable append-only log of ops (per document); the source of truth
Document stateMaterialized current state (from replaying the log, with snapshots)
Presence/cursor serviceEphemeral state for who is here and where the cursor is

The edit flow

  1. Client applies the edit locally (optimistic) and sends the operation to the server.
  2. Server assigns a sequence number; transforms the op against any concurrent ops (OT) or applies it to the CRDT state.
  3. Server appends to the op log; broadcasts the transformed op to all other clients.
  4. Clients apply the remote op to their local state; OT clients transform their pending ops against the remote; CRDT clients merge.
  5. Server acks the sender with the sequence number; the client reconciles.

Document routing

Each document is assigned to a "document actor" — a single service instance that serializes operations for that document. This is a single-writer per document, which makes ordering trivial and avoids the transformation matrix complexity. The actor is stateless apart from the in-memory CRDT/OT state; on crash, it resumes from the op log. Consistent hashing on document_id routes the client's WebSocket to the actor.

For very large documents or many concurrent editors, the actor becomes a bottleneck. The mitigation is sub-document actors (per page, per block, per section), each with its own ordering and a merge layer at the document level. The merge is the hard part; most systems accept the single-actor limit up to a few hundred editors.

Offline editing

A client that loses connection continues editing locally, accumulating ops. On reconnect, it sends the ops to the server, which transforms them (OT) or merges them (CRDT) against the ops the client missed. OT requires the server to know the client's base version; CRDT handles it natively. The local state is reconciled when the server's response arrives.

Persistence and snapshots

The op log is the source of truth; the materialized state is derived. Every N ops, a snapshot of the current state is stored, so loading a document is "load the latest snapshot, replay the ops after it". The snapshot is the cache; the log is the truth. This is event sourcing applied to documents.

Presence and cursors

Presence (who is editing) and cursors (where each user's selection is) are ephemeral — they do not need to be persisted. They use the same WebSocket, with a higher message rate and lower durability. The document actor broadcasts cursor updates to all participants; the client renders them as colored carets. On disconnect, the presence is removed via heartbeat timeout.

Permissions and history

Every op carries the author's identity. The actor checks the author's permission (can edit this document, this range) before applying. The op log is the history: version history is a replay from a snapshot, undo/redo is per-user op reversal (or a client-side history that re-applies the inverse).

Failure modes

FailureHandling
Document actor crashResume from the op log; clients reconnect and replay their pending ops
Client offlineLocal ops queue; merge on reconnect (OT/CRDT)
Concurrent editsOT transformation / CRDT merge; convergence guaranteed
Stale snapshotReplay from the snapshot + ops; the actor verifies the version
Slow clientBroadcast may queue; the client's per-connection buffer is bounded; a very slow client is disconnected
Op log corruptionSnapshot + replay from a known-good op; the log is replicated
Trade-off

OT gives exact transformation with low metadata, at the cost of a central ordering authority and complex transformation code. CRDT gives peer-to-peer convergence with no central ordering, at the cost of metadata (tombstones, IDs) and difficulty enforcing invariants. Most products choose OT for text (Google Docs) and CRDTs for JSON/rich data (Figma uses a CRDT-like model).

Design an event-driven order processing pipeline. How do you guarantee exactly-once processing for payments?

Short Answer

The order service writes the order and outbox in one transaction; a relay publishes to Kafka keyed by order_id. Payment is synchronous (the user needs the result); inventory, shipping, and notification are async consumers. Exactly-once effects come from the outbox (DB-queue), the provider's idempotency key (external call), and consumer dedup tables (event processing). The saga compensates on inventory failure.

Requirements

  • Functional: accept order; charge card; reserve stock; ship; notify; cancel and refund if any step fails.
  • Non-functional: no double charge; no lost order; consistent ledger; audit trail; per-order ordering.

Pipeline

StepComponentConsistencyMechanism

3. Publish OrderPlacedOutbox relayAt-least-onceRelay reads outbox, publishes, marks published

5. Create shipmentShipping serviceIdempotent consumerDedup by order_id
6. NotifyNotification serviceAt-most-once okIdempotency key; duplicate notifications acceptable but minimized
7. Update read modelOrder view consumerEventualRead model lags; rebuildable from log
8. Compensate on failureSaga (choreography or orchestration)Compensating actionsCancel order, refund, notify

Why payment is synchronous

The user must know whether the charge succeeded before the order is confirmed. A declined card must be visible immediately, not after a delayed event. The payment call is bounded by a timeout (e.g., 3 s); if the provider does not respond, the order is not confirmed (or a "processing" state is shown, and the user is notified when the result arrives).

Exactly-once effects

  • DB-queue: the outbox. The order and the event are in one transaction; the relay publishes; the consumer dedups by event ID.
  • External call: the provider's idempotency key. The payment service sends the same key on retry; the provider returns the original result, not a second charge.
  • Event processing: a dedup table keyed by order_id + event type. The consumer inserts the key and applies the change in one transaction; a redelivery sees the key and skips.

The compensation flow

If inventory fails after payment succeeded, the saga compensates: the order is cancelled, the payment is refunded (with an idempotency key on the refund), and the user is notified. The compensation is choreographed (each service reacts to the failure event) or orchestrated (a central coordinator drives the compensation sequence). The choice depends on the flow's complexity; a linear flow is choreographed; a branching one is orchestrated.

Failure modes

FailureHandling
Payment declinedAPI returns error; order not confirmed; user retries with another method

Trade-off

Exactly-once effects require the outbox, idempotency keys, and dedup tables at every boundary. The complexity is real, but the alternative — a double charge or a lost order — is unacceptable for payments. For non-financial flows, at-least-once with idempotent consumers is sufficient and simpler.

7

Design a webhook delivery system. How do you make webhooks reliable, signed, and retry-safe?

Short Answer

A webhook is an HTTP callback: the producer sends a POST to the subscriber's URL when an event happens. The design is a durable outbox per subscriber, an HMAC signature for authenticity, retries with exponential backoff and a DLQ, per-subscriber rate limits, and idempotency (each delivery carries a unique event ID so the subscriber can dedup). Reliability is achieved by treating the webhook as an at-least-once message, not a fire-and-forget HTTP call.

Requirements

  • Functional: deliver events to subscriber URLs; signature for authenticity; retries on failure; subscriber can pause/resume; delivery log and replay.
  • Non-functional: at-least-once delivery; p99 delivery < 5 s; no lost events; protect against SSRF and malicious subscribers.

Architecture

ComponentRole
Event sourceBusiness service publishes events (via outbox) to a webhook topic
Subscription registryWhich subscribers are subscribed to which events; URL, secret, filters
Fan-outFor each event, resolve the subscribers; enqueue a delivery per subscriber
Delivery queuePer-subscriber queue; rate-limited; ordered within a subscriber
Delivery workerHTTP POST with signature; timeout; classify response; retry or DLQ
Signature serviceHMAC-SHA256 of the payload with the subscriber's secret
DLQPer subscriber; failed after retries; replayable
Delivery logEvery attempt recorded: timestamp, status, latency, response

The delivery flow

  1. Business event → outbox → webhook topic.
  2. Fan-out: look up subscriptions for the event type; enqueue one delivery per subscriber.
  3. Delivery worker: build the payload; compute HMAC with the subscriber's secret; POST to the URL with a timeout (e.g., 10 s).
  4. 2xx → success; log; done.
  5. 4xx (except 429) → permanent failure; DLQ; do not retry.
  6. 5xx, timeout, 429 → retry with backoff (1 s, 5 s, 30 s, 5 min, 30 min); max 8 attempts.
  7. After exhaustion → DLQ; alert; subscriber sees the failure in the dashboard.

Signatures

Each delivery includes an HMAC-SHA256 signature of the payload (or of timestamp + payload), computed with the subscriber's secret. The subscriber verifies the signature before trusting the payload. The timestamp prevents replay: the subscriber rejects deliveries older than 5 minutes. The secret is per subscriber, rotated on a schedule; the subscriber has a grace period with both secrets to rotate.

Idempotency

Each delivery carries a unique event_id. The subscriber should dedup by it — the same event may be delivered twice (retry after a lost ack, or a failed subscription that was later recovered). The subscriber's handler is idempotent: processing the same event twice produces the same state. The delivery system's at-least-once guarantee and the subscriber's idempotency together give exactly-once effects.

Per-subscriber isolation

A slow or broken subscriber must not affect the others. The delivery queue is per subscriber (or partitioned by subscriber); the worker pool is shared but the per-subscriber rate limit prevents one from consuming the whole pool. A subscriber that consistently fails is paused (after a threshold) and notified; the others continue.

Security

  • SSRF prevention: the subscriber's URL is validated (no internal IPs, no metadata endpoints, no file://). The delivery worker has no network access to internal services.
  • Secret management: the subscriber's secret is stored encrypted; the signature service decrypts it at delivery time.
  • Rate limits: per subscriber, to prevent abuse and to protect the egress.
  • Redirects disabled: the delivery worker does not follow redirects (a redirect to an internal service is an SSRF vector).

Trade-off

At-least-once with idempotency is the practical contract for webhooks. Exactly-once delivery is impossible (the subscriber's HTTP response may be lost), so the design pushes idempotency to the subscriber. The alternative — at-most-once — is simpler but loses events when the subscriber is briefly down, which defeats the purpose of a webhook.

8

Design a distributed job scheduler using a message queue. How do you handle priorities, delayed jobs, and worker failures?

Short Answer

A durable job store (the source of truth), a scheduler that promotes due jobs to a queue, worker pools that consume from priority queues, and a result store that records success/failure. Priorities use separate queues per tier; delayed jobs use a time-indexed store and a scheduler tick; worker failures use visibility timeouts and a DLQ, with idempotent job handlers.

Requirements

  • Functional: submit a job with a payload; execute at a scheduled time; priority tiers; retries on failure; cancel a job; view status.
  • Non-functional: 1M jobs/s enqueued; p99 execution latency < 1 s for high priority; no lost jobs; at-least-once execution with idempotent handlers.

Architecture

ComponentRole
Job APISubmit, cancel, get status; validates and stores the job
Job storeDurable DB (Postgres/Cassandra): job_id, payload, priority, run_at, status, attempts, result
SchedulerPeriodic tick (every second) promotes due jobs from the store to the queues
Priority queuesSeparate queues per priority tier (high, default, low); workers pull
Worker poolsConsume from queues; execute the job; update the store; ack
DLQFailed after retries; alert; manual review

The submit flow

  1. Client submits a job: payload, priority, run_at (now or future).
  2. API validates; assigns job_id; writes to the job store with status pending.
  3. If run_at is now, the API immediately promotes it to the priority queue (or the scheduler picks it up within a second).
  4. If run_at is future, the scheduler's tick promotes it when due.

The scheduler tick

Every second, the scheduler queries the job store for jobs with run_at <= now and status = pending, in batches (e.g., 1,000). It updates them to queued and publishes them to the appropriate priority queue. The query uses an index on (status, run_at) and only touches the due range, so the tick is O(due jobs), not O(all jobs).

The scheduler runs in multiple instances with a leader election (or a distributed lock on the tick) to avoid duplicate promotion. The claim is atomic: UPDATE ... SET status = 'queued' WHERE ... RETURNING ensures each job is promoted once.

Priorities

Separate queues per priority tier: high (user-facing, latency-sensitive), default (batch), low (background cleanup). Worker pools are dedicated per tier (or a shared pool with capacity reserved for high). A high- priority job is never behind a low-priority one, because they are in different queues with different workers.

Worker failure and retries

The worker consumes a job, executes it, updates the job store, and acks the queue message. If it crashes before the ack, the message is redelivered (visibility timeout). The worker must be idempotent: check the job store's status (or a dedup table keyed by job_id) before executing. The retry count is incremented on each failure; after N retries (e.g., 3), the job goes to the DLQ with the error recorded.

Delayed jobs at scale

A separate table for future jobs, partitioned by run_at day. The scheduler's tick scans only today's partition; a job scheduled for a future day is not scanned until that day. This keeps the tick bounded even with millions of future jobs. For precision (sub-second), the scheduler ticks more frequently or uses a time wheel in memory for the next few minutes, backed by the durable store.

Job status and results

The job store tracks status: pending → queued → running → succeeded / failed / cancelled. The client polls a status endpoint (or receives a webhook). The result (output) is stored in a result table keyed by job_id; large outputs go to object storage with a reference in the result table.

Trade-off

A DB-backed job store gives durability and queryability at the cost of a database on the critical path; a queue-only design is faster but loses the query and status features. The hybrid — DB for durability and status, queue for execution — is the standard, at the cost of two systems to keep consistent (the store and the queue), which is why the promotion must be idempotent.

Interview Framing

Say: "Durable job store as the source of truth, a scheduler tick that promotes due jobs to priority queues, worker pools that consume and update the store, and a DLQ for the exhausted retries. Priorities are separate queues; delayed jobs are a time-indexed table; worker failure is a visibility timeout plus idempotent handlers." That names the components and the three key mechanisms.
