Part A — Queue Fundamentals What a queue is, what it is not, and how it differs from related primitives

1

Design a distributed message queue from scratch. What are the core components and APIs?

Short Answer

A distributed queue is a partitioned, replicated append-only log with a consumer-coordination layer on top. Producers append to a partition; consumers read from a partition and commit their position; a broker fleet stores and replicates partitions; a coordinator assigns partitions to consumers and tracks offsets. The API is four operations: produce, consume, ack/commit, and subscribe.

The core abstraction: a partitioned log

The fundamental choice that determines everything else is whether the queue is a log (messages stay until retention expires, and consumers track their own position) or a destructive queue (messages are removed on acknowledgement). Log-based queues (Kafka, Pulsar, Kinesis) support replay, multiple independent consumer groups, and high throughput; destructive queues (SQS, RabbitMQ classic queues) are simpler and have bounded storage. The design below assumes the log-based model because it is the one that scales to the workloads interviewers care about.

Components

ComponentResponsibility
ProducersAppend messages to a topic, choosing a partition via a key hash or round robin
BrokersStore partition log segments, serve reads and writes, replicate to followers
Controller / metadata servicePartition assignment to brokers, leader election, cluster state (ZooKeeper or KRaft)
ConsumersRead from assigned partitions, process messages, commit offsets
Group coordinatorAssigns partitions to consumers within a group, handles rebalances, stores committed offsets
Offset storeDurable record of each group's committed position per partition

The API

  • produce(topic, key, value) → (partition, offset) — the broker returns the assigned partition and offset, which the producer can use for acknowledgement tracking.
  • subscribe(group, topic, listener) — the consumer joins a group; the coordinator assigns partitions.
  • consume(partition, from_offset, max_records) → [records] — pull-based read; the consumer advances its position locally after processing.
  • commit(group, partition, offset) — durably record the consumer's position.
  • seek(partition, offset) — reposition for replay or recovery.

Storage model

Each partition is a sequence of immutable segments on disk. A segment is a file of messages plus an index (offset → file position) and a time index. Appends are sequential — the fastest possible disk pattern — and reads are either sequential scans or indexed lookups. Old segments are deleted or compacted according to the retention policy. The sequential write pattern is why a single broker can sustain hundreds of megabytes per second on commodity hardware.

Replication

Each partition has one leader and N-1 followers. The leader accepts writes; followers replicate from the leader's log. A write is acknowledged based on the producer's acks setting: acks=0 means fire-and-forget; acks=1 means the leader wrote it; acks=all means all in-sync replicas wrote it. The ISR (in-sync replica) list defines which followers are caught up enough to be counted. On leader failure, a follower from the ISR is promoted, preserving committed messages.

Consumer coordination

Consumers join a group by sending a join request to the group coordinator. The coordinator assigns each partition to exactly one consumer in the group (for competing consumers) and triggers a rebalance when membership changes. The assignment strategy (range, round-robin, sticky, cooperative-sticky) determines how partitions are distributed and how much shuffling happens on rebalance. Committed offsets are stored in a compacted internal topic (Kafka's __consumer_offsets) so that they survive broker failures and are visible to all consumers in the group.

What makes it distributed

Three things: (1) partitions spread across brokers, so no single broker is a bottleneck; (2) replication across brokers, so a broker failure does not lose data; (3) consumer groups spread across consumers, so processing throughput scales horizontally. The coordinator and the metadata service are the only centralized components, and both are replicated for availability.

The design decisions that matter

  • Partition count — the unit of parallelism, and it can only be increased, never decreased (in Kafka). Too few limits throughput; too many increases overhead and rebalance time.
  • Retention — how long messages stay. Long retention enables replay and multiple consumer groups; it costs disk. Tiered storage (hot on brokers, cold in object storage) is the modern answer.
  • Ack semantics — durability vs latency. acks=all is the default for anything that matters.
  • Compaction vs delete — delete is for event streams; compaction is for changelogs where only the latest value per key matters.
Trade-off

A log-based queue gives replay, multiple consumer groups, and high throughput, at the cost of storage (messages are not deleted on consumption) and operational complexity (partitions, replication, rebalances). A destructive queue is simpler and cheaper for small volumes, but cannot replay and cannot support more than one consumer group without duplicating messages. Most systems that need to scale choose the log.

Interview Framing

Open with: “I'll model this as a partitioned, replicated log. Producers append, consumers read from partitions and commit offsets, and a coordinator assigns partitions to consumers.” That defines the abstraction before the components, which is the order interviewers want.

2

What is the difference between a message queue and a pub/sub system? When would you choose each?

Short Answer

A message queue delivers each message to exactly one consumer — it distributes work. A pub/sub system delivers each message to every subscriber — it broadcasts notifications. Queues scale processing; pub/sub scales fan-out. The choice determines whether adding a consumer increases throughput (queue) or adds a new recipient of every message (pub/sub).

AspectMessage queuePub/sub
DeliveryOne consumer per messageEvery subscriber gets a copy
PurposeWork distribution, load levellingEvent notification, fan-out
Adding a consumerIncreases throughput; competes for messagesIncreases fan-out; receives all future messages
CouplingProducer knows the queue, not the consumerProducer knows the topic, not the subscribers
ReplayUsually no (destructive)Yes in log-based systems; no in classic pub/sub
ExampleSQS, RabbitMQ queue, Redis listSNS, Kafka topics, Google Pub/Sub
Typical useImage resizing, email sending, payment processingOrder events to billing, inventory, analytics

Why the distinction is not academic

Consider an order-placed event that three systems care about: billing, inventory, and analytics. If you put it on a queue with three consumers, each event goes to exactly one of them — billing might receive an event that inventory never sees. That is a data-loss bug, and a subtle one that only manifests as missing data in one subsystem. Publishing to a topic delivers a copy to each subscriber, which is the correct semantics. The primitive must match the intent.

The hybrid: topics with competing consumer groups

Modern systems need both at once. Kafka provides this directly: a topic is divided into partitions; each consumer group receives every message once, distributed across the members of that group. So a topic can serve billing (group 1), inventory (group 2), and analytics (group 3) — each group receives all events, while within a group the work is distributed across many instances. This composition is why Kafka is the dominant model for event-driven architectures: it is a pub/sub system that supports competing consumers within each subscription.

What each is good for

Queues are right when: the work is a task that needs to be done once (send this email, resize this image), the producer does not care who does it, and adding consumers should increase throughput. Pub/sub is right when: an event has multiple independent consumers with different purposes, each needs its own copy, and the producer should not know or care who is listening.

The failure modes

  • Queue misused for broadcast: a new consumer is added and receives only a fraction of the events, because the others are being consumed by the existing consumers. The fix is a topic, not a queue.
  • Pub/sub misused for work distribution: multiple instances of the same service subscribe to the same topic, and each message is processed N times. The fix is a consumer group, where the instances compete for messages instead of each receiving all of them.

What to say in an interview

Name the intent before the technology: “This is a work-distribution problem, so I'll use a queue with competing consumers” or “This is a notification problem, so I'll use a topic with independent consumer groups.” The technology choice follows from the intent, and demonstrating that you know the difference is what the interviewer is listening for.

Common Pitfall

Using SQS and expecting all consumers to receive every message. SQS is a queue — each message is delivered to one consumer. To fan out, you need SNS in front of SQS (one SNS topic, one SQS queue per subscriber), which is the standard AWS pattern. Choosing SQS alone for a broadcast use case loses messages silently.

Explain point-to-point vs publish-subscribe routing models. How do they map to different business use cases?

Short Answer

Point-to-point has one sender and one receiver per message — a message is delivered to exactly one consumer, and consumers compete for messages. Publish-subscribe has one sender and many receivers — each subscriber gets its own copy of every message. Point-to-point is a work queue; pub/sub is an event bus.

Point-to-point in depth

A producer sends a message to a queue. One consumer picks it up, processes it, and acknowledges. If the consumer crashes before acknowledging, the message is returned to the queue and picked up by another consumer. The queue guarantees that each message is processed exactly once (by one consumer), at least once in delivery terms. Consumers are interchangeable — adding one increases throughput because they compete for messages.

Business use cases: order processing where each order is handled by one worker; email sending where each email is sent once; image transcoding where each image is processed once; payment capture where each transaction is charged once. The common thread is that the work is idempotent per unit and the business does not want it done twice.

Publish-subscribe in depth

A producer publishes a message to a topic. Every subscriber of that topic receives its own copy. The producer does not know or care how many subscribers there are. Subscribers can be added without changing the producer, and removing one does not affect the others. The topic is a broadcast channel.

Business use cases: an order-placed event that must reach billing, inventory, analytics, and notifications; a user-registered event that triggers welcome email, onboarding checklist, and CRM record; a payment-completed event that updates the ledger, sends a receipt, and updates the fraud model. The common thread is that multiple independent systems need to react to the same event, each for its own purpose.

The combination in practice

Most real systems use both. An order-placed event is published to a topic; each downstream service subscribes with its own consumer group. Within each service, the group has multiple instances competing for messages. This gives the fan-out of pub/sub at the top level and the throughput scaling of point-to-point at the consumer level. It is the pattern that Kafka was designed for, and it is what most event-driven architectures converge on.

The routing decisions

QuestionPoint-to-pointPub/sub
Who processes the message?Exactly one consumerEvery subscriber
What happens when a consumer is added?More throughput, same messages splitA new recipient of every message
What happens when a consumer is removed?Others pick up the messagesThat subscriber stops receiving
Is replay possible?Usually noYes in log-based systems
Is the producer coupled to consumers?No — just the queueNo — just the topic

The mistake that costs money

The most common routing mistake is using a queue for a pub/sub use case. A team puts an order-placed event on a queue, then adds a second consumer for analytics. Half the events go to billing and half to analytics, and both are wrong. The fix is a topic with two subscriptions, or a topic with two consumer groups. The signal in an interview is whether the candidate asks “does every consumer need to see every message?” before choosing the primitive.

Interview Framing

Say: “This is a fan-out problem — billing, inventory, and analytics all need the event — so it's pub/sub with a consumer group per subscriber. The image-resize work is point-to-point, so it's a queue with competing workers.” Naming both primitives and both use cases in one sentence shows the distinction is internalized.

What is the difference between a message and an event? Why does the distinction matter in system design?

Short Answer

A message (or command) is an instruction to do something — “send this email”, “charge this card”. It is addressed to a specific handler and expects the work to be done. An event is a statement of fact — “order 123 was placed”. It is broadcast, has no expected handler, and may be consumed by zero or many systems. The distinction determines coupling: commands couple the sender to the handler's behaviour; events decouple the producer from everyone who reacts.

AspectCommand / messageEvent
Semantics“Do this”“This happened”
TenseImperativePast tense
RecipientsOne handler (or one service)Zero or many consumers
CouplingSender knows what should happenSender knows only that it happened
Failure handlingIf unhandled, the command is lost — a problemIf unhandled, that is fine — it was informational
NamingSendEmail, ChargeCardOrderPlaced, PaymentCaptured
RoutingQueue (point-to-point)Topic (pub/sub)

Why the distinction matters

Commands create coupling. If a checkout service sends a SendWelcomeEmail command to an email service, the checkout service now knows that welcome emails exist, and adding a second welcome channel means changing the checkout code. If instead the checkout service publishes UserRegistered, the email service can react without checkout knowing it exists, and a new onboarding service can be added without touching checkout. Events decouple; commands couple.

This has a direct design consequence: a system built on events can add consumers over time without changing producers, which is exactly what makes event-driven architecture scalable organisationally. A system built on commands requires every new reaction to be wired in by the producer, which becomes a bottleneck as the number of consumers grows.

The naming test

The easiest way to tell them apart is grammatical. If the name is imperative (“SendEmail”, “ResizeImage”, “ChargeCard”), it is a command. If it is past tense and describes a fact (“OrderPlaced”, “ImageUploaded”, “PaymentCaptured”), it is an event. This is not pedantry — the name reflects the contract, and a mixed-up name usually indicates a mixed-up design.

When commands are correct

Commands are not always wrong. When the sender genuinely needs the work done by a specific service, and the contract is intentional, a command is the right primitive. “ChargeCard” is a command to a specific payment service; it should not be broadcast to everyone. The rule is: use commands when the sender owns the decision and the recipient is known; use events when the sender is announcing a fact and the reactions are open-ended.

The failure-handling difference

A command that is not handled is a bug — the email was never sent, the image was never resized. The system must guarantee delivery and retry until it succeeds (or dead-letter). An event that is not consumed is fine — no one was listening, no harm done. This means commands need stronger delivery guarantees and monitoring than events, which changes the queue configuration: commands typically use a queue with a DLQ and alerting on failures; events typically use a topic with retention and consumer lag monitoring.

The design principle

Prefer events at the boundaries between services, and commands within a service. A service should announce what happened in its domain and let other services decide how to react. This reduces coupling, makes adding new consumers trivial, and is the foundation of event-driven architecture. But not every message should be an event — a direct request for work that the sender owns is a command, and pretending otherwise creates confusion about who is responsible.

Common Pitfall

Calling a command an event to sound modern. SendWelcomeEmail is not an event, no matter what topic it is on. The sender still expects the email to be sent, and the system still needs to guarantee that. The naming confusion leads to the wrong delivery guarantees and the wrong failure handling.

How is a message queue different from Redis Pub/Sub? What are the durability and delivery implications?

Short Answer

Redis Pub/Sub is a fire-and-forget broadcast with no persistence, no acknowledgement, and no delivery guarantee — if no subscriber is connected when a message is published, the message is gone. A message queue persists messages, tracks acknowledgement, and redelivers on failure. Redis Pub/Sub is for ephemeral real-time signals; a queue is for durable work.

AspectRedis Pub/SubMessage queue (SQS, RabbitMQ, Kafka)
PersistenceNone — in memory onlyDurable on disk (or replicated)
Delivery guaranteeAt-most-once (and often zero)At-least-once
Offline subscribersMessages lostMessages retained until consumed or expired
AcknowledgementNoneExplicit ack; redelivery on failure
ReplayNoYes (Kafka, Kinesis)
Consumer groupsNoYes
BackpressureNo — subscribers buffer or dropYes — queue depth grows
Use caseReal-time signals, cache invalidation, presenceWork queues, event streams, task processing

How Redis Pub/Sub works

A publisher sends a message to a channel. Redis immediately forwards it to all currently connected subscribers. There is no storage — the message exists only for the duration of the publish call. If a subscriber is slow, the message is dropped from its buffer. If a subscriber disconnects, it misses everything published while it was gone. This is fine for cache invalidation (the next read will fetch fresh data) and for presence (the next heartbeat will correct it), but catastrophic for work that must not be lost.

Redis Streams as the durable alternative

Redis also offers Streams (XADD, XREAD, XACK, consumer groups), which are a persistent, append-only log with consumer groups and acknowledgement. Streams close much of the durability gap: messages are stored in memory but can be persisted to disk, and consumers can acknowledge and replay. However, Redis Streams are still memory-bound (the dataset must fit in RAM, or you accept eviction), and the durability guarantees are weaker than a disk-based log because Redis persistence (RDB, AOF) has its own trade-offs. For small-to-medium durable queues, Streams are a reasonable choice; for high-volume durable messaging, Kafka or RabbitMQ is better.

The failure scenarios

  • Subscriber offline: Pub/Sub loses the message; a queue retains it.
  • Subscriber slow: Pub/Sub drops from the buffer; a queue grows and applies backpressure.
  • Redis restart: Pub/Sub loses everything in memory; a queue survives (if persisted).
  • Consumer crash: Pub/Sub has no redelivery; a queue redelivers after the visibility timeout.

When Redis Pub/Sub is the right tool

When the message is a hint, not a fact that must be processed. “Cache key X changed” — if a subscriber misses it, the next request recomputes or the cache expires. “User Y is online” — if a subscriber misses it, the next heartbeat corrects it. “A new message arrived on socket Z” — if the socket is disconnected, the client fetches from the log on reconnect. In all these cases, the system has another source of truth and the Pub/Sub message is an optimization. That is exactly when fire-and-forget is acceptable.

The hybrid pattern

Many systems use both: a durable queue for the work that must not be lost, and Redis Pub/Sub for the real-time notification that work has happened. The queue guarantees processing; the Pub/Sub tells connected clients to refresh. This is the standard pattern for chat (Section 1) and for any system with a real-time UI backed by durable storage.

Common Pitfall

Using Redis Pub/Sub as a job queue. The job is published, no worker is connected, and the job is silently lost. This works in development (the worker is always running) and fails in production (during a deploy or a restart). The fix is Redis Streams, or a real queue.

Part B — Delivery, Acknowledgement & Failure What happens when things go wrong, and how the system recovers

6

What happens if a consumer crashes before processing a message? Explain acknowledgements, manual vs auto-ack modes, and redelivery.

Short Answer

If a consumer crashes before acknowledging, the message is not marked as processed, and the broker redelivers it — either to the same consumer when it restarts or to another consumer in the group. The guarantee is at-least-once: the message will be processed eventually, possibly more than once, so consumers must be idempotent. Auto-ack removes the safety net by acknowledging before processing, which trades duplicates for potential loss.

The lifecycle of a message

  1. Producer publishes; broker stores the message and makes it available.
  2. Consumer fetches the message; broker marks it "in flight" (invisible to other consumers).
  3. Consumer processes the message.
  4. Consumer acknowledges; broker marks it "processed" and removes or advances past it.

The failure point is between steps 2 and 4. If the consumer crashes after fetching but before acking, the broker does not know the message was processed — it only knows it was delivered. The message returns to the queue when the in-flight timeout expires (SQS visibility timeout, RabbitMQ unacked message return, Kafka's consumer group rebalance), and is delivered again.

Auto-ack vs manual ack

ModeWhen the ack is sentFailure on crashUse case
Auto-ackOn delivery, before processingMessage lostLoss-tolerant work (metrics, logs)
Manual ack (after process)After the consumer finishesMessage redeliveredAll business-critical work
Manual ack (before process)Before the consumer starts workMessage lost on crashAvoid — same as auto-ack with extra code

The rule is simple: acknowledge after the work is done and durable. If the consumer writes to a database and then acks, a crash between the write and the ack causes a redelivery and a duplicate write — which is why the write must be idempotent. If the consumer acks before writing, a crash loses the message entirely, which is never acceptable for business work.

The visibility timeout

When a consumer fetches a message (SQS, RabbitMQ), the broker hides it from other consumers for a timeout period (SQS default 30 seconds, up to 12 hours). If the consumer acks within the timeout, the message is removed. If it does not, the message becomes visible again and is redelivered. The consumer can extend the timeout with a heartbeat if the work takes longer than expected — but if it forgets, the message is redelivered and processed twice.

The timeout is a trade-off: too short and slow workers cause spurious redeliveries; too long and a crashed consumer holds the message invisibly, delaying recovery. The right value is the p99 processing time plus a margin, and the consumer should extend it for genuinely long jobs.

Idempotency is mandatory

Because redelivery is possible, the consumer must produce the same result whether a message is processed once or five times. Three common patterns:

  • Idempotency key: the message carries a unique ID; the consumer stores processed IDs in a dedup table and skips duplicates.
  • Upsert semantics: writing the same row twice is safe because the write is an upsert, not an insert.
  • Natural idempotency: the operation is inherently repeatable — setting a status to "shipped" is idempotent; incrementing a counter is not.

What redelivery does not solve

Redelivery does not fix a poison message — a message that crashes the consumer every time it is processed. It is redelivered, crashes the consumer again, and loops forever. This is why dead-letter queues exist (Question 8): after N failed deliveries, the message is moved aside so the pipeline can continue.

The ordering interaction

Redelivery can break ordering if a later message is processed while an earlier one is being redelivered. A FIFO queue (SQS FIFO, Kafka partition, RabbitMQ single consumer) avoids this by blocking the partition on the in-flight message — no later message is delivered until the earlier one is acked or times out. The cost is head-of-line blocking: one slow message stalls the partition. This is the fundamental trade-off between ordering and throughput.

Common Pitfall

Acking before the work is durable. The consumer acks, then writes to the database, then crashes before the write commits — the message is gone and the work was never done. The ack must come after the durable write, and the write must be idempotent to handle the redelivery that follows a crash between the write and the ack.

How do consumers know where to read next? Explain offset management, who advances offsets, and what happens if a consumer crashes between processing and committing an offset.

Short Answer

In a log-based queue, each consumer group maintains a committed offset per partition — the position up to which messages have been processed and acknowledged. The consumer advances its local position as it reads, but the committed offset is only updated when it explicitly commits. On crash, the consumer resumes from the last committed offset, which may reprocess messages read but not committed. This is the source of at-least-once delivery in Kafka.

Local position vs committed offset

These are two different things, and the distinction is the key to understanding Kafka's delivery semantics:

  • Local position: the next offset the consumer will read. It advances as the consumer fetches records. It is in memory, per consumer instance.
  • Committed offset: the durable record of what the consumer group has processed. It is stored on the broker (Kafka's __consumer_offsets topic) and is used on restart or rebalance to decide where to resume.

The consumer can read far ahead of its committed offset — that is how batching works. But if it crashes before committing, the next instance resumes from the committed offset and reprocesses everything after it.

When offsets are committed

StrategyWhenFailure consequence
Auto-commit (interval)Every N seconds, automaticallyMessages processed since the last commit are reprocessed
Commit after each recordAfter processing one messageAt-least-once; slow (a commit per message)
Commit after a batchAfter processing N messagesAt-least-once for the whole batch; faster
Commit before processingAfter fetch, before workAt-most-once — messages lost on crash

Auto-commit is the default in many clients and is a common source of surprises: a crash can cause the last few seconds of messages to be reprocessed, or — worse — committed before they were processed if the commit interval fires between fetch and processing. Disabling auto-commit and committing manually after processing is the standard recommendation for any consumer that must not lose messages.

The crash-between-process-and-commit window

The consumer processes message 42, writes the result to the database, then crashes before committing offset 42. When another consumer takes over the partition, it resumes from the last committed offset (41) and reprocesses 42. The database now has the result of 42 twice — unless the write was idempotent. This is why idempotency is not optional: the window between processing and committing is unavoidable in any at-least-once system, and the consumer must be designed for it.

Rebalance interaction

When a consumer joins or leaves a group, a rebalance reassigns partitions. The departing consumer's uncommitted offsets are lost (they were never committed); the new consumer resumes from the last committed offset. If the departing consumer had processed a batch but not committed it, that batch is reprocessed. This is another source of duplicates, and another reason commits should happen promptly after processing.

Offset retention

Committed offsets are stored in a compacted topic with a retention window (Kafka default 7 days). If a consumer group is inactive for longer than the retention, its committed offsets expire and it must reset to earliest or latest. This is usually fine — a group inactive for a week is effectively new — but it is a surprise when a paused consumer resumes and reprocesses everything or skips everything depending on the reset policy.

Seeking and replay

The consumer can seek to any offset, not just forward. This enables replay: reprocessing from a known good offset after a bug fix, or bootstrapping a new consumer group from the beginning. The log retention policy determines how far back the seek can go. Replay is one of the main advantages of a log-based queue over a destructive queue, and it is why the offset is a first-class concept.

Offsets and exactly-once

Kafka's transactional producer and consumer can atomically commit offsets with the output of processing, giving exactly-once semantics within Kafka. Outside Kafka (e.g., writing to an external database), exactly-once requires idempotent writes or a transactional outbox. The offset is the anchor: the commit and the write must be atomic, or the consumer must be idempotent. There is no third option.

Interview Framing

Say: “The committed offset is the source of truth for restart. The consumer reads ahead, processes, then commits; a crash between processing and commit causes reprocessing, so the consumer must be idempotent.” That names the mechanism, the failure, and the mitigation in one sentence.

What is a dead-letter queue (DLQ)? What kinds of messages end up there, and how do you process them?

Short Answer

A DLQ is a separate queue that receives messages that could not be processed after a configured number of retries. It isolates poison messages so they do not block the main pipeline, and it preserves them for inspection and reprocessing. A DLQ without monitoring and a reprocessing plan is just a graveyard — the design is incomplete without those.

What ends up in a DLQ

  • Poison messages: a malformed payload that crashes the consumer every time it is processed. The canonical case — a missing field, an invalid enum, a payload that fails schema validation.
  • Transient failures exhausted: a downstream dependency was down for the entire retry window, and the message was never processed successfully. By the time the dependency recovers, the message is in the DLQ.
  • Business rule rejections: the message references an order that does not exist, or a user who has been deleted. Retrying will never succeed; it belongs in the DLQ for human review.
  • Unprocessable by design: a message type the consumer version does not support, or a schema version it cannot handle. This is a deployment bug, but the message still needs to be preserved.
  • Expired messages: a message whose TTL elapsed before it could be delivered (SQS max retention 14 days, for example). The DLQ captures what would otherwise be silently dropped.

How the DLQ is triggered

The standard mechanism is a retry counter with a maximum. Each delivery attempt increments the counter; after N attempts (typically 3–5), the message is moved to the DLQ instead of being redelivered. In SQS, this is the redrive policy: maxReceiveCount plus a dead-letter queue ARN. In RabbitMQ, it is the x-dead-letter-exchange and x-dead-letter-routing-key arguments on the queue, triggered after N rejections. In Kafka, there is no native DLQ — the consumer must implement it by catching failures and producing to a DLQ topic, or by using a framework that does.

The retry policy

Retries should use exponential backoff with jitter to avoid a retry storm. A typical policy: 3 attempts at 1 second, 10 seconds, and 1 minute. If the failure is transient (a network blip), one of these succeeds. If the failure is permanent (a malformed message), all three fail and the message goes to the DLQ. The policy must distinguish between these cases where possible — a validation error should not be retried at all; a timeout should. Some systems use two queues: a retry queue with a delay and a DLQ for the final failure.

The DLQ is not the end

A DLQ is only useful if someone looks at it. The operational design must include:

  • Alerting: a non-zero DLQ depth is an alert. A growing DLQ depth is a page. The metric is the queue depth over time, not just a threshold.
  • Inspection: a way to look at the messages — a console, a query API, or an export to a table. The messages must carry enough context (original payload, error, attempt count, timestamp) to diagnose the failure.
  • Reprocessing: a mechanism to move messages from the DLQ back to the main queue after a fix. This is a redrive operation: read from DLQ, validate, publish to the original queue (or a repair queue), remove from DLQ. It must be idempotent, because a redrive can be retried.
  • Discarding: a way to permanently delete messages that are truly unprocessable, with an audit record. Not every DLQ message needs to be recovered; some are genuinely garbage.

The ordering interaction

Moving a poison message to a DLQ unblocks the partition, but the messages that were queued behind it have been waiting. In a FIFO queue, this is a head-of-line block that the DLQ resolves — at the cost of delivering the messages out of their original order relative to the removed one. Most systems accept this: a message that cannot be processed is effectively skipped, and the following messages proceed. If the order matters, the DLQ recovery must reinsert the message at the correct position, which is complex and usually not worth it.

What goes in the DLQ message

The original payload, the error message and stack trace, the consumer identity, the attempt count, and the first and last attempt timestamps. Without the error, the DLQ is undebuggable; without the attempt count, you cannot tell whether it failed transiently or permanently. Enriching the message on the way to the DLQ is cheap and pays off during the incident when someone has to look at it.

Common Pitfall

Configuring a DLQ and never monitoring it. Messages accumulate silently, the DLQ grows to millions of entries, and the first sign of trouble is a storage bill or a missed business process. The DLQ depth must be an alert from day one, and someone must own the runbook for inspecting and redriving it.

How do you design a message queue that handles 1 million messages per second while guaranteeing no message loss once acknowledged?

Short Answer

Partition aggressively, batch writes, replicate with acks=all, and exploit sequential disk writes. The throughput comes from parallelism across partitions and brokers; the no-loss guarantee comes from replication and from acknowledging only after the write is durable on the required number of replicas. Getting both at once is what makes the design interesting — batching raises throughput but increases the loss window unless combined with replication.

The throughput budget

1M messages/second at 1 KB each is 1 GB/s of raw data before replication. That is far beyond a single broker's disk — a typical NVMe drive sustains 3–7 GB/s write for sequential I/O, but the replication factor multiplies the write. With replication factor 3, the cluster writes 3 GB/s. The design must spread this across many brokers: 1M messages/s on 10 brokers is 100k messages/s per broker, which is achievable; on 3 brokers it is 333k per broker, which is at the edge of what commodity hardware can do.

Partitioning

Partitions are the unit of parallelism. Each partition is a sequential log with one leader; throughput per partition is bounded by the leader's disk and network. To reach 1M/s, you need enough partitions that the per-partition rate is within its budget. A common rule of thumb is 10–50 MB/s per partition, which at 1 KB messages is 10k–50k messages/s per partition — so 20–100 partitions for 1M/s. In practice, systems over-provision partitions (e.g., 200–500) to allow for consumer scaling and uneven load, at the cost of more open files, more replication traffic, and longer rebalance times.

Batching and compression

Per-message overhead (framing, checksums, network round trips) dominates at high message rates. Batching amortizes it: the producer accumulates messages and sends them as one batch (Kafka's batch.size and linger.ms). Compression (LZ4, zstd) on the batch reduces bytes on the wire and bytes on disk — often 2–5× for typical payloads. The trade-off is latency: a larger batch means waiting longer to fill it, which adds milliseconds to each message's latency. Tuning linger.ms is the lever: 0–5 ms for latency-sensitive, 10–50 ms for throughput-sensitive.

The write path

  1. Producer picks a partition by key hash or round-robin and sends a batch to the partition leader.
  2. Leader appends the batch to its log — a sequential write to the page cache, then flushed to disk.
  3. Followers fetch from the leader and append to their own logs.
  4. When the required number of replicas have acknowledged (ISR size), the leader returns the ack to the producer.

The no-loss guarantee is at step 4: the producer gets an ack only after acks=all replicas have written the batch. If the leader crashes after acking but before followers replicate, the message is lost — so the ack must wait for the replication. This is the durability/latency trade-off in its purest form.

Sequential writes and the page cache

The reason a single broker can handle tens of thousands of messages per second is that appends are sequential. Sequential writes to an SSD (or even an HDD) are 10–100× faster than random writes. The OS page cache absorbs the writes and flushes them in order, which is the kernel's best-case scenario. Kafka's design deliberately avoids random I/O: no per-message index updates on the write path, no B-tree rebalancing, just an append and a periodic index flush. This is what allows a broker to sustain high throughput on commodity hardware.

Replication cost

Replication factor 3 triples the write bandwidth and storage. The follower fetch is a sequential read from the leader's log and a sequential write to the follower's log, so it is also cheap per byte. But the network between brokers must carry 3× the data, and the leader's egress is the bottleneck at high replication factors. The standard topology is replication factor 2 or 3 within a region, with cross-region replication (if needed) as a separate async stream that does not affect the write ack path.

What breaks first

At 1M/s, the likely bottlenecks, in order:

  • Producer-side batching and network: too many small batches, or the producer's network interface saturates.
  • Leader network egress: the leader must send to all followers and to all consumers; this is often the real limit.
  • Disk write bandwidth on the leader: if the appends are not absorbed by the page cache fast enough.
  • Consumer fetch throughput: consumers must be able to keep up; consumer lag grows if they cannot, and the queue depth grows until retention expires.
  • Metadata overhead: with hundreds of partitions, the controller and coordinator become hot; this is usually manageable but is a known scaling limit.

Consumer side

At 1M/s, consumers must also be scaled: consumer groups with enough instances to keep up with the partition count. Each partition is consumed by one consumer in the group, so the consumer count cannot exceed the partition count. This is why partition count is chosen for the consumer parallelism you will need, not just the producer throughput. The rule of thumb: partitions = max(producer parallelism, consumer parallelism).

The no-loss guarantee in practice

No loss once acknowledged requires: acks=all with min.insync.replicas set to at least 2; a producer that retries on failure with idempotence enabled (to avoid duplicates from retries); a consumer that commits offsets only after processing and is idempotent; and an unclean leader election policy set to false so a lagging replica is never promoted. Each of these is a setting, but the design must choose them deliberately rather than accepting defaults.

Trade-off

1M/s with no loss is achievable, but not with default settings. The throughput comes from batching and parallelism; the no-loss guarantee comes from replication and waiting for acks. Tuning for one usually costs the other: larger batches raise throughput and latency; stronger acks raise durability and latency. The design must decide, per topic, which matters more.

How does message persistence work in different brokers (RabbitMQ, Kafka, RocketMQ)? What are the trade-offs of each approach?

Short Answer

Kafka persists to a partitioned append-only log on disk, with sequential writes and periodic index flushes — the fastest pattern for high throughput. RabbitMQ traditionally keeps messages in memory and spills to disk under pressure, optimized for low-latency routing and per-message acknowledgements. RocketMQ uses a single commit log for all topics, with per-queue indexes — a hybrid that trades some write simplicity for more efficient storage sharing.

BrokerPersistence modelStrengthsWeaknesses
Kafka Per-partition append-only log segments; sequential writes; sparse offset index Highest throughput; replay; tiered storage No per-message priority; partition count fixed once chosen; operational complexity
RabbitMQ In-memory queues with disk-backed message store; messages can be persistent or transient Low latency; flexible routing (exchanges, bindings); per-message ack Throughput lower than Kafka; memory pressure at scale; classic queues limit
RocketMQ Single commit log for all topics; per-queue consume-queue indexes Good throughput; ordered messages; transactional messages Less mature ecosystem; operational complexity; fewer managed offerings
SQS Fully managed distributed storage; no user-visible disk Zero operations; scales automatically No replay; limited ordering (FIFO queues only); max message size

Kafka: log segments

Each partition is a directory of segment files. A segment is a .log file of messages, a .index file mapping offset to file position, and a .timeindex mapping timestamp to offset. Appends go to the active segment; when it reaches a size threshold (typically 1 GB), it is closed and a new one is opened. Old segments are deleted or compacted per the retention policy.

Reads are served from the page cache: the OS keeps recently written segments in memory, so consumers read at memory speed until they fall behind. The index is sparse — one entry per ~4 KB of log — so a lookup is a binary search in the index plus a short sequential scan. This is why Kafka's read throughput is close to disk throughput for sequential access.

RabbitMQ: message store and queues

RabbitMQ's model is a message store plus per-queue indexes. A message is written to the store once and referenced by the queues it is routed to. Persistent messages are written to disk; transient messages are kept in memory. Under memory pressure, RabbitMQ pages messages to disk, which is why it can handle bursts that exceed RAM — but the paging is a performance cliff, not a smooth degradation.

The advantage is flexible routing: exchanges (direct, topic, fanout, headers) route messages to queues by binding rules, so a single publish can fan out to many queues with different routing. The cost is that the per-queue index and the in-memory representation limit throughput per queue, and very large queues (millions of messages) degrade performance. RabbitMQ is optimized for many small queues with low latency, not for a few enormous ones.

RocketMQ: commit log plus consume queues

RocketMQ writes all messages to a single commit log — a sequential append across all topics — and maintains per-queue consume indexes that point into the commit log. This is a middle ground: the write path is as fast as Kafka's (single sequential file), but messages from different topics share storage, which is more efficient when there are many small topics. The read path is an index lookup plus a commit-log read, similar to Kafka's segment read but with an extra indirection.

RocketMQ's design also supports features Kafka historically lacked: transactional messages, scheduled messages, and message priorities — which is why it is popular in Chinese e-commerce.

SQS: managed abstraction

SQS hides the storage entirely. Messages are durable (replicated across availability zones), but the user has no visibility into the disk layout, no replay, and no partition control. The trade-off is that operational burden is zero — you get a URL and an API — at the cost of flexibility. For workloads that fit the SQS model (standard queue with at-least-once, or FIFO queue with ordering), it is often the right choice because the operations are someone else's problem.

The common thread

All persistence models optimize for sequential writes, because random writes are the bottleneck at scale. The differences are in how much routing flexibility, per-message control, and replay they expose. Kafka and RocketMQ optimize for throughput and replay; RabbitMQ optimizes for routing and low latency; SQS optimizes for operational simplicity. The right choice depends on which of those matters most for the workload.

Trade-off

Kafka's throughput comes from its rigid model — one log per partition, no per-message priority, no flexible routing. RabbitMQ's flexibility comes from its message store and exchanges, at the cost of throughput and memory pressure. Choosing a broker is choosing which constraint you can live with.

What happens when a broker crashes mid-write? How does replication and leader election recover the message?

Short Answer

The producer's ack has not been sent (if acks=all), so the producer does not consider the write complete. The controller detects the broker failure via heartbeat timeout, promotes an in-sync follower to leader, and the producer retries against the new leader. If the failed broker had acked but not replicated, the message is lost — which is why the ack must wait for replication, and why unclean leader election must be disabled.

The write path and the crash window

A producer sends a batch to the partition leader. The leader appends to its local log, then waits for followers to fetch and acknowledge. The ack to the producer is sent only after the required number of replicas have written (with acks=all and min.insync.replicas=2, at least two). The crash window is between the leader's local write and the follower's acknowledgment:

  • Crash before local write: nothing was persisted. The producer retries; no message is lost or duplicated.
  • Crash after local write, before follower ack: the leader has the message, followers do not. The producer has not received an ack, so it retries. The new leader (a follower) does not have the message, so the retry writes it again — a duplicate if the original write had somehow been visible, but it was not acknowledged, so the producer's retry is the first "successful" write from its perspective.
  • Crash after follower ack, before ack to producer: the message is on the follower, but the producer does not know. The producer retries; the new leader (the follower) already has the message. If the producer is idempotent (Kafka's idempotent producer with sequence numbers), the retry is deduplicated; otherwise, the message is written twice.

The no-loss guarantee depends on the ack being sent only after replication. The no-duplicate guarantee depends on the producer being idempotent. Both must be configured deliberately.

Leader election

The controller (Kafka's KRaft controller, or ZooKeeper in older versions) monitors broker liveness via heartbeats. When a broker misses heartbeats for the session timeout, the controller marks it dead and reassigns its partitions: each partition's leader is moved to a follower from the ISR. The new leader is the first ISR member in a deterministic order, and it starts accepting producer and consumer requests.

The ISR is the key: it is the set of replicas that are caught up to the leader's high-water mark. A replica falls out of the ISR if it falls behind by replica.lag.time.max.ms. Only ISR members are eligible to become leader (unless unclean leader election is enabled), which is what guarantees that no committed message is lost.

Unclean leader election

If all ISR members are unavailable — for example, a rack failure took out the leader and its in-sync follower — the partition has no eligible leader. Kafka can either become unavailable for that partition (the default: unclean.leader.election.enable=false) or promote an out-of-sync replica (true). Promoting an out-of-sync replica makes the partition available but loses the messages that the out-of-sync replica did not have — a data-loss event. For any system with a no-loss requirement, this must be disabled. The trade-off is availability: the partition is unavailable until an ISR member returns.

The producer retry

The producer's retry is what closes the loop. With retries set high (or delivery.timeout.ms governing the total window), the producer keeps retrying until it gets an ack or the timeout expires. The retry goes to the new leader, which may or may not already have the message. The idempotent producer uses sequence numbers per partition to deduplicate: if the new leader has sequence 42 but the producer is retrying 42, the leader recognizes the duplicate and returns the existing offset instead of appending again.

Consumer-side impact

Consumers fetching from the old leader get an error and must refresh metadata to find the new leader. The client library handles this transparently, with a brief pause during the election (typically a few seconds). Consumers that had committed offsets are unaffected — the offsets are stored on the broker and replicated, so the new leader knows the group's position. The consumer resumes from the committed offset; messages between the committed offset and the high-water mark may be reprocessed if they were not committed.

The recovery timeline

  1. Broker crashes; producer's in-flight batch fails.
  2. Heartbeat timeout (typically 10–30 seconds) triggers the controller.
  3. Controller promotes a new leader from the ISR (sub-second).
  4. Producers and consumers refresh metadata and reconnect to the new leader (a few seconds).
  5. Producer retries the unacked batch; the new leader accepts it.
  6. Consumers resume from their committed offsets.

The total disruption is typically 10–60 seconds, dominated by the heartbeat timeout. This is why the session timeout and heartbeat interval must be tuned: too short and a busy but healthy broker is falsely declared dead; too long and failover takes minutes.

Common Pitfall

Setting acks=1 for "performance" and then being surprised when a broker crash loses the last few seconds of messages. The producer was acked before replication, so the ack meant nothing. For any message that matters, acks=all with min.insync.replicas=2 and an idempotent producer is the only configuration that delivers the no-loss guarantee.

How does a consumer group work? How are partitions assigned, and what happens during a rebalance?

Short Answer

A consumer group is a set of consumers that jointly consume a topic, with each partition assigned to exactly one consumer in the group. The group coordinator tracks membership and offsets, assigns partitions, and triggers a rebalance when consumers join or leave. A rebalance pauses consumption, revokes and reassigns partitions, and resumes — which is why minimizing rebalances and using cooperative protocols matters at scale.

The group model

Each consumer in a group subscribes to the same topic(s) and is assigned a subset of partitions. If there are 12 partitions and 4 consumers, each gets 3. If a 5th consumer joins, the group rebalances to 3, 3, 2, 2, 2 — or whatever the assignment strategy produces. The guarantee is that each partition is consumed by exactly one consumer in the group at any time, which preserves per-partition ordering.

Different groups are independent: group A and group B both consume all partitions of the same topic, each with its own assignments and offsets. This is how one topic serves multiple downstream services.

The coordinator

One broker in the cluster is elected as the group coordinator for a given group. It handles join requests, heartbeats, rebalance coordination, and offset commits. The coordinator is chosen by hashing the group ID, so all consumers of a group talk to the same broker. If that broker fails, the group elects a new coordinator and rebalances.

Assignment strategies

StrategyHow it assignsRebalance cost
RangeContiguous ranges per consumer per topicHigh — can shuffle all partitions
Round-robinPartitions distributed one by oneHigh — can shuffle
StickyKeeps existing assignments where possible; moves minimumMedium — fewer moves but still eager
Cooperative stickyIncremental: only reassigns partitions that must moveLow — other partitions keep consuming

Cooperative sticky is the modern default in Kafka clients. The eager protocols (range, round-robin, sticky) revoke all partitions at the start of a rebalance and reassign them at the end — a stop-the-world pause that grows with the number of partitions. Cooperative sticky rebalances incrementally: it computes the target assignment, identifies the partitions that need to move, and revokes only those. The result is shorter pauses and less disruption for large groups.

The rebalance protocol

  1. A consumer joins or leaves, or the coordinator detects a missed heartbeat.
  2. The coordinator bumps the generation number and starts a rebalance.
  3. All consumers pause consumption and rejoin the group (eager) or continue consuming unaffected partitions (cooperative).
  4. The group leader (one consumer, elected by the coordinator) computes the assignment.
  5. The assignment is sent to the coordinator, which distributes it to all consumers.
  6. Consumers start consuming their new partitions from their committed offsets.

The rebalance storm

A rebalance storm happens when rebalances cascade: a consumer takes too long to process a batch, misses its heartbeat, is declared dead, triggers a rebalance; the rebalance redistributes its partitions, the new consumers take longer to catch up, miss their heartbeats, and the cycle repeats. The group makes no progress, and consumer lag grows while the rebalance loop runs. This is a classic production incident.

The mitigations: increase max.poll.interval.ms so a slow batch does not trigger a rebalance; reduce max.poll.records so each batch is smaller; use cooperative sticky to reduce the blast radius; and use static group membership (a group.instance.id per consumer) so a restarting consumer does not trigger a rebalance if it comes back within the session timeout.

Static membership

Introduced in Kafka 2.3, static membership lets a consumer register a stable group.instance.id. When it restarts, the coordinator recognizes it and keeps its partition assignment — no rebalance, as long as the restart completes within the session timeout. This is essential for Kubernetes deployments, where pod restarts are frequent and every rolling update would otherwise cause a rebalance storm.

What consumers see during a rebalance

During an eager rebalance, consumers receive a RevokedPartitions callback, then a LostPartitions if they missed a commit window, then an AssignedPartitions callback when the new assignment arrives. The consumer should commit offsets in the revoke callback (before losing the partitions) so the next owner resumes from the right place. Missing this step causes reprocessing of the in-flight batch.

Scaling and partition count

A consumer group cannot have more active consumers than partitions — extra consumers sit idle. This is why partition count is chosen for the maximum expected consumer parallelism. Adding partitions later increases parallelism but changes key-to-partition mapping, which breaks ordering for keys that move; the standard workaround is to over-provision partitions at creation or to use a partitioner that preserves key ordering across partition additions (e.g., by key, not by hash mod N).

Interview Framing

Say: “One consumer per partition, a coordinator that assigns partitions and tracks offsets, and a cooperative sticky protocol so a rebalance doesn't pause every consumer. I'll use static membership for rolling deploys so pod restarts don't trigger a rebalance storm.” That covers assignment, coordination, and the operational failure mode in one answer.

How do you design backpressure in a message queue? What happens when consumers cannot keep up with producers?

Short Answer

Backpressure is the mechanism that prevents a producer from overwhelming a consumer. In a pull-based queue, it emerges naturally: the consumer fetches only what it can process, and the queue depth grows. In a push-based queue, the broker must limit its delivery rate. Either way, the queue depth (consumer lag) is the signal, and the response is to add consumers, rate-limit producers, or shed load — not to buffer forever.

The three backpressure models

ModelHow it worksBackpressure signalExamples
Pull Consumer fetches N records when ready; broker never pushes unprompted Consumer lag (offset gap) Kafka, Kinesis, SQS (long-poll)
Push with credits Consumer grants the broker a credit (max in-flight); broker sends up to that many Credit exhaustion RabbitMQ consumer prefetch, AMQP flow control
Push (no backpressure) Broker sends as fast as it can; consumer buffers or drops None — buffer overflow Redis Pub/Sub, naive webhooks

Pull-based backpressure

In Kafka, the consumer explicitly fetches records in batches. If it is slow, it simply fetches less often, and the lag grows. The producer is never blocked — it can keep writing until the retention window expires or the disk fills. The system's signal is consumer lag: the difference between the producer's offset and the consumer's committed offset. A growing lag means consumers are not keeping up; a stable lag means the system is in steady state.

The advantage of pull is that the consumer controls its own pace. A slow consumer does not slow down the producer or the other consumers. The disadvantage is that a consumer that is too slow accumulates lag, and if the lag exceeds retention, the messages are deleted before they are processed — a data loss that the system cannot detect unless it monitors lag against retention.

Push with credits

RabbitMQ's consumer prefetch (basic.qos) sets a limit on unacknowledged messages per consumer. The broker sends up to that many and then stops until the consumer acks one. This is credit-based backpressure: the consumer's ack is the credit that allows the next message. A slow consumer simply receives fewer messages, and the queue depth grows on the broker.

The trade-off is that a low prefetch limits throughput even when the consumer is fast, and a high prefetch lets a slow consumer hold many unacked messages, delaying redelivery on crash. The right value depends on the processing time per message and the ack latency.

Queue depth as a signal

Whatever the model, the queue depth is the primary metric. For a queue, it is the number of messages waiting; for a log, it is the consumer lag in messages or time. The metric should be monitored against a threshold: a depth that exceeds the maximum processing capacity within the retention window is a data-loss risk, not just a performance issue. Alerting on the trend (depth growing for N minutes) catches the problem before the threshold is hit.

The three responses

  1. Scale consumers. Add consumer instances to the group, up to the partition count. This is the first response and works if the bottleneck is consumer CPU and the partitions allow more parallelism.
  2. Rate-limit producers. If consumers cannot be scaled (partition limit, downstream bottleneck), slow the producers. This is application-level backpressure: the producer checks a queue-depth signal and blocks or rejects new work when the depth is high. It moves the problem upstream, where it is visible to the producer rather than silently accumulating in the queue.
  3. Shed load. If neither scaling nor rate-limiting is possible, drop messages — the oldest, the newest, or the lowest priority. This is the last resort and must be a deliberate policy, not an accident. A queue that silently drops messages is worse than one that refuses new work.

The downstream bottleneck

The most common reason consumers cannot keep up is that the consumer's downstream dependency (database, API, third-party service) is the bottleneck, not the consumer itself. Adding consumer instances then makes the problem worse: more consumers hammer the same database, increasing contention and latency, and throughput does not improve. The correct response is to identify the downstream bottleneck and either scale it, batch writes to it, or apply backpressure at the consumer level (process less, not more).

The retention interaction

In a log-based queue, backpressure is bounded by retention. If the consumer lag exceeds the retention window, the messages are deleted and the consumer cannot catch up — it has lost data. The retention window must be longer than the maximum expected lag (e.g., a weekend outage). For systems where outages can be long, tiered storage (keeping old messages in object storage) extends the effective retention without paying for broker disk.

The design principle

Backpressure is not a bug to be eliminated; it is a signal that the system is overloaded. The design should make the signal visible (queue depth, lag), respond to it automatically (autoscaling), and have an explicit policy for when the response is insufficient (rate-limit or shed). A system without backpressure is a system that will eventually drop messages without warning.

Common Pitfall

Scaling consumers to fix lag when the bottleneck is the downstream database. More consumers means more concurrent database queries, which increases contention and can reduce throughput. The fix is to batch writes or add backpressure at the consumer, not to add consumers.

Compare Kafka and RabbitMQ. When would you choose one over the other for an internal eventing platform?

Short Answer

Kafka is a partitioned, replayable log optimized for high-throughput event streaming, multiple consumer groups, and long retention. RabbitMQ is a flexible message broker optimized for low-latency routing, complex routing topologies, and per-message acknowledgement. Choose Kafka for event streams and analytics pipelines; choose RabbitMQ for task queues and complex routing.

DimensionKafkaRabbitMQ

When Kafka is the right choice

  • Event streaming: a stream of events that multiple services consume independently, each at its own pace, with its own offset. The order-placed event feeding billing, inventory, and analytics is the canonical case.
  • Replay requirement: bootstrapping a new service from history, or reprocessing after a bug fix. Kafka's log retention makes this trivial; RabbitMQ cannot do it at all.
  • High throughput: hundreds of thousands or millions of messages per second. Kafka's sequential writes and batching handle this; RabbitMQ's in-memory model hits a ceiling.
  • Analytics and CDC: Kafka Connect and the ecosystem make it the default sink for change data capture and stream processing.
  • Log aggregation: collecting logs from many services into a central store.

When RabbitMQ is the right choice

  • Complex routing: messages need to be routed based on headers, patterns, or fan-out to many queues with different bindings. Kafka's topic/partition model is too rigid for this.
  • Task queues: work items that are consumed once, processed, and forgotten. RabbitMQ's per-message ack and prefetch are a natural fit.
  • Low latency: sub-millisecond routing for RPC-style request/reply or low-latency notifications.
  • Priority and per-message control: messages need different priorities, TTLs, or per-message acknowledgement granularity.
  • Simpler operations: a smaller team without dedicated Kafka expertise may find RabbitMQ easier to run.

The overlap

For moderate volumes and simple topologies, both work. A task queue at 5,000 messages per second fits either system; the choice then comes down to operational familiarity, ecosystem, and long-term direction. Kafka's ecosystem advantage is significant if the platform will grow into streaming analytics or CDC; RabbitMQ's routing flexibility is significant if the topology is complex.

What about managed services?

Confluent Cloud (Kafka), Amazon MSK, and CloudAMQP (RabbitMQ) remove the operational burden. For a team without a dedicated platform group, a managed Kafka is often the better choice even if RabbitMQ's model fits slightly better, because the operational cost of self-managed Kafka is high. This is a legitimate consideration in a design interview: the answer is not always the technically optimal broker, but the one the team can run reliably.

The hybrid pattern

Many organisations run both: Kafka for the event backbone (streaming, CDC, analytics) and RabbitMQ for task queues and request/reply. This is not redundancy — the two systems serve different primitives, and using the right one for each avoids the awkward workarounds that come from forcing one system to do both. The cost is two systems to operate, which is acceptable when both have clear, distinct roles.

What the interviewer is listening for

The answer should name the specific properties that drive the choice — replay, routing, throughput, ordering — and map them to the use case. “Kafka because it's popular” is a red flag; “Kafka because we need replay and multiple independent consumer groups, and RabbitMQ can't provide either” is the answer that demonstrates understanding.

Interview Framing

Say: “For the event backbone I'll use Kafka — replay, multiple consumer groups, and high throughput. For the email and image-processing task queues I'll use RabbitMQ — simple work distribution with per-message ack and routing. If the team can only operate one system, I'd consolidate on Kafka with workarounds, and accept the extra complexity for routing.” That names the trade-off and the constraint.
