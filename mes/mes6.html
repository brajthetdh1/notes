Part A — The Semantics What the three guarantees actually mean, and why one is impossible

1

Explain at-most-once, at-least-once, and exactly-once delivery. Which is achievable in practice, and at what cost?

Short Answer

At-most-once means a message may be lost but never duplicated. At-least-once means it is never lost but may be duplicated. Exactly-once means it is neither lost nor duplicated — and it is impossible for end-to-end delivery in an asynchronous distributed system with failures. What is achievable is exactly-once effects: at-least-once delivery plus idempotent processing, which produces the same result as if each message were processed once.

The three semantics precisely

SemanticLossDuplicatesWhen it happens
At-most-once Possible Never Producer sends without ack, or consumer acks before processing
At-least-once Never (if retries exhausted) Possible Producer retries, or consumer acks after processing and crashes before ack
Exactly-once (delivery) Never Never Impossible in the general case

Why exactly-once delivery is impossible

The argument is the Two Generals Problem in another form. A producer sends a message and waits for an acknowledgement. If the ack is lost, the producer does not know whether the message was received. It can retry — which risks a duplicate if the first copy was received — or not retry — which risks a loss if it was not. The consumer faces the mirror problem: it processes a message and sends an ack; if the ack is lost, the broker does not know whether to redeliver. Every protocol adds another ack to confirm the previous ack, and the ambiguity never resolves. There is always a window in which the sender does not know the receiver's state, and any choice in that window is either a possible loss or a possible duplicate.

This is not a limitation of a particular broker. It is a theorem about asynchronous communication with unreliable channels. Kafka's transactional producer achieves something that looks like exactly-once within Kafka, but it does so by making the consumer's state (the offset) part of the same transaction as the output, which is a form of exactly-once effects, not delivery. The message itself could still be delivered twice if a consumer outside the transaction read it.

At-most-once: the cheapest and most dangerous

At-most-once gives up durability for speed and simplicity. The producer fires and forgets (acks=0); the consumer acks before processing. The message may be lost at any of a dozen points: network drop, broker crash, consumer crash after ack. This is acceptable only for data whose loss does not matter — metrics, logs, telemetry, presence heartbeats. It is never acceptable for business events.

At-least-once: the practical default

At-least-once gives up exactly-once for durability. The producer waits for an ack and retries on failure; the consumer processes and then acks, so a crash before the ack causes a redelivery. The message is never lost (as long as retries are allowed and retention has not expired), but it may be delivered twice. Every Kafka, RabbitMQ, SQS, and Pulsar default is at-least-once. The cost is that the consumer must handle duplicates — which means it must be idempotent (Question 3).

Exactly-once effects: the achievable goal

The achievable target is not that the message is delivered once, but that the effect of processing it happens once. The recipe is: at-least-once delivery + idempotent processing = exactly-once effects. Idempotent processing means that applying the same message twice produces the same state as applying it once. Three ways to achieve it:

  • Natural idempotency: the operation is inherently repeatable. Setting a status to "shipped" is idempotent; incrementing a counter is not.
  • Idempotency key: the message carries a unique ID; the consumer stores processed IDs in a dedup table and skips duplicates. This is the general-purpose technique (Question 9).
  • Transactional consume-process-produce: the consumer's output and its offset commit are in one transaction, so a redelivery does not duplicate the output. This is Kafka's transactional API (Volume 3, Question 8), and it gives exactly-once effects within Kafka.

The cost ladder

GuaranteeCostUse case
At-most-onceLowest — no retries, no dedupMetrics, logs, presence
At-least-onceModerate — retries, idempotent consumer, dedup tableMost business events
Exactly-once effects (Kafka-internal)Higher — transactions, coordinator, read-committedPayments, ledger, inventory
Exactly-once effects (external systems)Highest — outbox, idempotent writes, 2PC or sagaCross-system financial workflows

What the interviewer is listening for

When you say "exactly-once", the interviewer will ask "how?". The strong answer is: "Exactly-once delivery is impossible, but exactly-once effects are achievable with at-least-once plus idempotent consumers. For Kafka-internal pipelines I'd use the transactional API; for external writes I'd use an outbox or an idempotency key." That demonstrates you know the difference between the impossible guarantee and the achievable effect, which is the actual distinction that matters.

Interview Framing

Say: "Exactly-once delivery is impossible in an asynchronous system. What we can achieve is exactly-once effects: at-least-once plus idempotent processing, or the Kafka transactional API for Kafka-to-Kafka." That one sentence resolves the entire question.

2

A consumer team reports duplicate order processing. How do you diagnose whether the issue is at-least-once delivery, a retry, or a rebalance? What is the fix?

Short Answer

Duplicates come from three sources: the producer retried a send whose ack was lost, the consumer processed a message but crashed before committing the offset, or a rebalance moved a partition and the new consumer reprocessed an uncommitted batch. Diagnose by looking at the message ID, the offset commits, and the rebalance history — each source leaves a distinct signature. The fix is always idempotent processing; the specific source determines which log lines to look at and which configuration to change.

The three sources, distinguished

SourceSignatureRoot cause
Producer retry Two messages with the same order_id and same client_seq, different kafka_offset, written within seconds Producer sent, ack lost, producer retried, broker appended both (idempotence disabled)
Consumer crash before commit One message, processed twice, with the second processing happening after a consumer restart Consumer processed, wrote the result, crashed before committing the offset; redelivery on restart
Rebalance One message, processed twice, with the second processing happening on a different consumer instance Partition moved; new consumer resumed from last committed offset, reprocessing the in-flight batch

Step 1 — Identify the duplicate pair

The first thing is to find the two rows that represent the same logical order. Look at the business table: two rows with the same order_id and the same content, different primary keys or timestamps. From those rows, extract the message metadata: the message_id (producer-generated), the kafka_offset, the kafka_partition, and the consumer_instance that wrote each row. This metadata should be in the row (every consumer should write the message ID alongside the business data — this is the single most important operational practice for diagnosing duplicates).

Step 2 — Compare the offsets

If the two rows have different Kafka offsets, the duplicate came from the producer: the same logical message was written to Kafka twice, at two different offsets, and each was consumed. This happens when the producer's idempotence is disabled and a send is retried after a lost ack. The fix is to enable idempotence on the producer (enable.idempotence=true), which deduplicates by producer ID and sequence number. If the producer is not Kafka (e.g., SQS), the fix is a dedup key on the send side.

If the two rows have the same offset, the duplicate came from the consumer: the same Kafka record was processed twice. This narrows it to the consumer-crash or rebalance case.

Step 3 — Compare the consumer instances and timing

If the two rows have the same offset and were written by the same consumer instance, with the second write after a restart of that instance, it is the crash-before-commit case. The consumer processed the message, wrote the business row, then crashed before the offset commit. On restart, it resumed from the last committed offset and reprocessed. The log will show a consumer startup event between the two writes.

If the two rows have the same offset and were written by different consumer instances, it is the rebalance case. The partition moved from consumer A to consumer B; A had processed the message but not committed the offset; B resumed from the last committed offset and reprocessed. The log will show a "partitions revoked" event for A and a "partitions assigned" event for B, between the two writes.

Step 4 — The fix, regardless of source

The three sources share a common root: the consumer is not idempotent. The specific fix for each source reduces the frequency of duplicates (producer idempotence, faster commits, cooperative rebalancing), but the correctness fix is always idempotent processing. The consumer must be designed so that processing the same message twice produces the same result. The three patterns:

  • Idempotency key: a dedup table keyed by message_id, checked and written in the same transaction as the business change. The second processing sees the key and skips.
  • Upsert: the business write is an upsert keyed by order_id, so the second processing overwrites the first with identical data. This works if the message contains the full state, not a delta.
  • Natural idempotency: the operation is repeatable — "set status to shipped" is idempotent, "increment shipped_count" is not.

Step 5 — Reduce the frequency

After making the consumer idempotent, reduce the number of duplicates:

  • Producer idempotence: enable.idempotence=true eliminates the producer-retry duplicate entirely.
  • Faster offset commits: commit after every batch, not every N minutes. The smaller the window between processing and commit, the fewer messages are reprocessed on crash.
  • Cooperative sticky rebalancing: the incremental protocol (Volume 3, Question 12) moves only the partitions that need to move, so fewer in-flight batches are lost during a rebalance.
  • Static group membership: a restarting consumer rejoins with the same identity and keeps its partitions, avoiding a rebalance entirely (if it restarts within the session timeout).
  • Longer max.poll.interval.ms: a slow batch does not trigger a spurious rebalance, which reduces the rebalance-induced duplicates.

The diagnostic checklist

  1. Find the duplicate business rows.
  2. Extract message_id, offset, partition, consumer_instance from both.
  3. If offsets differ → producer retry → enable idempotence.
  4. If offsets same and consumer differs → rebalance → check rebalance log, enable cooperative sticky and static membership.
  5. If offsets same and consumer same → crash-before-commit → check consumer restart log, commit more frequently.
  6. In all cases → the consumer must be idempotent, or the fix is incomplete.
Common Pitfall

Not writing the message ID and offset into the business row. Without them, the duplicate rows cannot be traced to a source, and the diagnosis becomes guesswork. Every consumer should write source_message_id and source_offset alongside the business data — it is the single most valuable observability field.

3

What is idempotency in messaging? How do you design an idempotent consumer? What role does an idempotency key play?

Short Answer

Idempotency means that processing the same message twice produces the same state as processing it once. The idempotency key is a unique identifier attached to the message (or derived from its content) that lets the consumer detect and skip duplicates. The three implementations are: natural idempotency (the operation is repeatable), upsert (the write overwrites with the same value), and a dedup table (a record of processed keys checked and written atomically with the business change).

Why idempotency is the central discipline

Every at-least-once system will deliver duplicates. The producer's retry duplicates the send; the consumer's crash before commit duplicates the processing; the rebalance duplicates the in-flight batch. These are not bugs to be fixed — they are the semantics of the system. The only way to build a correct consumer on top of an at-least-once transport is to make the consumer idempotent. This is not optional; it is the contract.

The idempotency key

The idempotency key is a value that uniquely identifies the logical operation, independent of how many times the message is delivered. It must be:

  • Unique per operation: two different orders have different keys; the same order has the same key across retries.
  • Deterministic: the producer generates it once and includes it in every retry of the same message. If the key is generated inside the consumer, it will be different on each delivery and dedup fails.
  • Scoped: the key's namespace is clear — order:123:created is unique to this consumer, even if the same order produces other events.
  • Stored with the effect: the key must be written in the same transaction as the business change, or there is a window where the effect happens but the key is not recorded (and a redelivery duplicates it).

Where the key comes from depends on the source:

SourceKeyNotes
Kafka messagetopic:partition:offset or producer-generated message_idOffset is stable; producer ID is stable across retries if idempotence is enabled
HTTP requestClient-supplied Idempotency-Key headerThe client generates it once and reuses it on retry
CDC eventtable:primary_key:lsnThe log sequence number is unique per change
Business eventevent_type:aggregate_id:versionThe aggregate version increments per change

Implementation 1 — Natural idempotency

The simplest and most robust: the operation is inherently repeatable. Setting a status to "shipped" is idempotent — doing it twice leaves the status as "shipped". Upserting a row by primary key is idempotent — doing it twice leaves the same row. Deleting by key is idempotent — the second delete is a no-op. Whenever the business operation can be expressed as a state assignment or an upsert, it is naturally idempotent and needs no dedup table.

The catch: not every operation is naturally idempotent. "Increment balance by 10" is not — doing it twice gives 20. "Send email" is not — the user gets two emails. "Charge card" is not — the customer is charged twice. These require the other two patterns.

Implementation 2 — Upsert

If the message carries the full state of the entity, the write can be an upsert keyed by the entity ID. Processing the same message twice overwrites with the same state. This is common in CDC and event sourcing, where each event carries the complete new state of the row. It is not sufficient if the event carries a delta (e.g., "increment by 10"), because the second application doubles the delta.

Implementation 3 — Dedup table

The general-purpose solution for non-idempotent operations. A table keyed by the idempotency key, with a record of when it was processed and (optionally) the result. The consumer, in one transaction:

  1. Inserts the key into the dedup table. If it already exists, the transaction aborts and the message is skipped (it was already processed).
  2. Applies the business change.
  3. Commits the transaction.
  4. Commits the Kafka offset.

The atomicity of steps 1 and 2 is what makes it correct: either both the key and the effect are committed, or neither is. If the transaction fails, the key is not recorded, and the redelivery retries from scratch. If it succeeds, the key is recorded, and the redelivery sees it and skips.

The dedup table is covered in detail in Question 9. The key design decisions are: what columns, what TTL, how to handle the dedup table being unavailable, and how to bound its growth.

The transactional outbox connection

The dedup table solves the consumer side. The producer side has a related problem: writing to the database and publishing to the queue are not atomic, so one can succeed and the other fail. The transactional outbox solves it: the business change and the message are written to the outbox table in the same database transaction, and a separate relay publishes from the outbox. The relay is idempotent (it reads by outbox ID), and the consumer's idempotency key (derived from the outbox ID) makes the end-to-end pipeline exactly-once in effect.

What idempotency does not solve

Idempotency makes duplicates harmless, but it does not make them free. Each duplicate still consumes CPU, database I/O, and a dedup table lookup. At high duplicate rates, the cost is real. The design should also reduce the frequency of duplicates — producer idempotence, faster commits, cooperative rebalancing — so the idempotency mechanism is a safety net, not the primary strategy.

Interview Framing

Say: "Every at-least-once consumer must be idempotent. The idempotency key is generated by the producer, carried in the message, and written to a dedup table in the same transaction as the business change. The three implementations are natural idempotency, upsert, and the dedup table, and the choice depends on whether the operation is a state assignment or a delta." That names the mechanism, the key, and the three patterns in one answer.

Part B — Ordering Why it breaks, how to preserve it, and what it costs

4

Why does message ordering break in distributed queues? What are the root causes (partitions, parallel consumers, retries)?

Short Answer

Ordering breaks because the transport optimizes for throughput, not sequence. Four root causes: partitioning scatters one logical stream across shards that are read in parallel; parallel consumers process different partitions at different speeds; retries re-deliver a failed message after later ones have succeeded; and asynchronous fan-out introduces per-recipient queues that drain at different rates. The fix is to confine ordering to the partition and to make the partition key match the ordering requirement.

Root cause 1 — Partitioning

A topic is split into partitions, and each partition is an independent log. The producer assigns each message to a partition by key hash or round-robin. If two messages that should be ordered (e.g., "order created" and "order shipped" for the same order) are assigned to different partitions, no consumer can see them in order — the ordering is lost at write time. The fix is to key by the entity whose order matters: both messages use the same order_id, hash to the same partition, and are ordered within it.

Root cause 2 — Parallel consumers

Even within a partition, the consumer group may have multiple consumers. Each consumer processes its assigned partitions independently, and there is no ordering across partitions. If the order spans two partitions (because the key was wrong), the parallel consumers process them in arbitrary order. Even within one partition, if the consumer processes messages concurrently (thread pool), the effect order can differ from the read order. The fix is one consumer per partition and single-threaded processing within a partition, which caps throughput per partition.

Root cause 3 — Retries

A message fails to process. The consumer retries it. Meanwhile, the consumer moves on to later messages in the same partition. If the retry succeeds eventually, its effect may be applied after the effect of a later message — violating order. This is especially common with retries that use a delay (backoff), because the delayed message is effectively re-queued behind the ones that come after it. The fix is either to block the partition on the failed message (head-of-line blocking, no retry delay) or to accept that the order is best-effort during failure windows.

Root cause 4 — Asynchronous fan-out

Even if the input is ordered, the fan-out to multiple consumers or services may not be. A message is enqueued to multiple downstream queues; each queue has its own consumers, and they drain at different speeds. The downstream services see the messages in different orders. The fix is to route causally related messages to the same downstream partition (by key) so they stay ordered through the fan-out, or to accept that the fan-out is unordered and make the downstream services order-tolerant.

The throughput-ordering trade-off

Ordering scopeMechanismThroughput
No orderingRound-robin, many consumersMaximum
Per-key orderingHash by key, one consumer per partition, single-threadedScales with the number of keys
Global orderingSingle partition, single consumerBounded by one consumer's throughput

The choice is fundamental. Most systems choose per-key ordering because it matches the domain: orders are independent of each other, but events within an order must be ordered. The partition key is the entity ID, and the throughput scales with the number of entities — which is effectively unbounded for a real system.

What breaks at each level

  • Per-key ordering broken: the key is wrong (timestamp instead of entity ID) or the consumer processes concurrently within a partition. The symptom is events for one entity out of order.
  • Global ordering broken: multiple partitions are used, or multiple consumers. The symptom is a global sequence that is not monotonic.
  • Cross-topic ordering broken: two topics feed the same downstream, and the consumer merges them without a sequence number. The fix is a single topic with a combined key, or a merge with a sequence.

The ordering guarantee is only as strong as the weakest link

A Kafka topic with per-key ordering is useless if the producer reads from a database without an order or the consumer writes to a database in parallel. The ordering must be preserved end-to-end: the producer generates the events in order, the partition key keeps them on one partition, the consumer processes them serially, and the downstream write applies them in the same order. Each step can break the chain, and the end-to-end guarantee is the conjunction of all of them.

Common Pitfall

Assuming that because Kafka preserves order within a partition, the system is ordered. The producer's key choice, the consumer's threading, the retry policy, and the downstream write all have to cooperate. A single parallel step breaks the guarantee, and the failure is invisible until an out-of-order event causes a user-visible bug.

5

How do you guarantee per-key ordering in Kafka? What are the costs of strict per-key ordering in throughput and latency?

Short Answer

Set the partition key to the entity ID, so all messages for that entity hash to the same partition; use a consumer group with one consumer per partition; process serially within a partition; and disable the producer's concurrent in-flight batches to the same partition (or enable idempotence, which preserves order). The cost is throughput per partition — bounded by one consumer's processing rate — and latency, because a slow or failed message blocks the partition (head-of-line blocking).

The four settings that preserve order

  1. Partition key = entity ID. The producer hashes the key to pick a partition. All messages for the same key go to the same partition, and within a partition, the broker preserves order.
  2. Producer ordering: set max.in.flight.requests.per.connection=1 (which serializes sends to the broker) or enable enable.idempotence=true (which allows up to 5 in-flight requests but re-orders them by sequence number on the broker, preserving the producer's send order). Idempotence is the modern default: it preserves order without sacrificing the pipelining benefit.
  3. One consumer per partition. A consumer group can have at most one consumer per partition; the group coordinator enforces this. Do not split a partition across consumers.
  4. Serial processing within a partition. The consumer reads a batch and processes it in order, one message at a time. Do not hand the batch to a thread pool that may complete out of order. If concurrent processing is needed, partition further (more keys), not within the partition.

What per-key ordering does not guarantee

  • Order across keys. Messages for user A and user B have no order relative to each other, even if they are causally related. If a message for A triggers a message for B, the cross-key order is not guaranteed.
  • Order across partitions. A topic with 100 partitions has 100 independent order streams. The "global" order is whatever the consumer chooses when it reads multiple partitions.
  • Order across topics. Two topics with the same key are two independent logs; the consumer that merges them must impose order itself.
  • Order across retries. If the consumer retries a failed message while moving on, the retry applies after later messages. Strict ordering requires blocking the partition on the failed message until it succeeds or is dead-lettered.

The cost — throughput

Per-partition throughput is bounded by the single consumer's processing rate. A consumer that processes 1,000 messages/s per partition caps that partition's throughput at 1,000/s. The total topic throughput is the sum across partitions, so the design scales by adding partitions (more keys), not by adding consumers to the same partition. A topic with 10 partitions and 1,000/s per consumer has 10,000/s total; to double it, you need 20 partitions.

The cost is real for high-cardinality keys. If there are only 10 keys, the topic has at most 10 partitions' worth of parallelism — 10,000/s total if each partition does 1,000/s. Adding more consumers does not help because there are no more partitions to assign. The only way to scale further is to change the key to a finer-grained one, which breaks the per-entity order.

The cost — latency and head-of-line blocking

A slow message blocks the partition. If message 42 takes 30 seconds to process, messages 43–100 in the same partition wait. The consumer cannot skip 42 (that breaks order) and cannot process 43 concurrently (that also breaks order). The only options are to wait, to dead-letter 42 (losing it), or to increase the timeout and accept the latency. This head-of-line blocking is the fundamental cost of strict ordering.

For a payment pipeline, this is acceptable: a payment that fails must be resolved before the next one for the same account, because the balance must be correct. For a chat pipeline, it is annoying: a slow image upload blocks the message behind it. The design must match the ordering requirement to the blocking tolerance.

When to relax the ordering

  • Idempotent, commutative operations: if the operations produce the same result in any order (e.g., setting a status, adding to a set), ordering does not matter and the partition can be processed concurrently.
  • Independent keys: if the consumer's operation for user A does not depend on user B, the cross-key order is irrelevant, and per-key ordering is sufficient.
  • Time-window ordering: if the requirement is "order within a 5-second window", the consumer can buffer and reorder by timestamp within the window, allowing parallel processing outside it.

The partition count and ordering interaction

More partitions means more parallelism but also more independent order streams. If the ordering requirement is per-entity, more partitions is fine — each entity is still on one partition. If the requirement is global, partitions must be 1 (single partition), which caps throughput at one consumer's rate. This is the trade-off: per-key ordering scales, global ordering does not.

Trade-off

Strict per-key ordering gives correctness at the cost of throughput (one consumer per partition) and latency (head-of-line blocking). Relaxing the ordering (concurrent processing, no blocking) gives throughput at the cost of correctness. The right answer is per-key ordering with idempotent consumers — the consumer tolerates duplicates and the partition key matches the entity, which gives correctness with throughput bounded by the number of entities, which is effectively unbounded.

Interview Framing

Say: "Partition by the entity ID, one consumer per partition, serial processing, idempotent producer. The throughput is bounded by one consumer per partition, so I'll size partitions for the expected consumer parallelism, and accept head-of-line blocking because the entity's order matters." That covers the mechanism, the cost, and the design decision.

6

How would you guarantee order for messages that belong to the same customer order while allowing unrelated orders to process in parallel?

Short Answer

Partition by order_id. All events for one order hash to the same partition and are ordered within it; different orders hash to different partitions and are processed in parallel. The throughput scales with the number of concurrent orders, not the number of events. The order aggregate is the unit of ordering, and the partition key is the aggregate ID.

The key choice

The fundamental decision is which key to use. Three candidates:

KeyOrdering scopeParallelismUse case
order_idAll events for one order, in orderOne partition per orderOrder lifecycle: created, paid, shipped, delivered
customer_idAll events for one customer's orders, in orderOne partition per customerCross-order consistency (e.g., loyalty points)
global (single partition)All events, globally orderedNoneLedger, audit

The default is order_id because the order is the aggregate: its events are causally related, and different orders are independent. The customer_id key is used when the events span orders and must be ordered relative to each other (e.g., a customer's loyalty points balance must reflect all orders in sequence). The global key is used only when the business requires a single total order across all events, which is rare and expensive.

How the pipeline preserves order

  1. Producer: every event for order 123 is produced with key order_id=123. The producer's partitioner hashes the key and always assigns the same partition.
  2. Broker: the partition is an ordered log. The messages are appended in the order the producer sent them, with monotonic offsets.
  3. Consumer: one consumer in the group is assigned the partition. It reads messages in offset order and processes them serially.
  4. Consumer's downstream: the consumer writes to the order's state store (or emits a downstream event) in the same order. If the downstream is another topic, the same key preserves order; if it is a database, the write is in the same transaction as the offset commit (or idempotent to handle retry).

The partition is the unit of parallelism: 100 orders on 10 partitions means 10 orders per partition, processed in parallel. Adding orders adds parallelism (up to the partition count); adding partitions adds more. The throughput is bounded by the consumer's per-partition rate times the partition count, which is effectively unbounded for a real workload.

What breaks the ordering

  • Different keys for the same order. If "order created" uses order_id and "order shipped" uses shipment_id, they hash to different partitions and the consumer sees them in arbitrary order. Every event for an order must use the same key.
  • Multiple producers without coordination. If two services produce events for the same order, and they use different partitioners or different key formats, the partition assignment diverges. The fix is a single producing service, or a shared key-derivation function.
  • Consumer concurrency within a partition. If the consumer hands the batch to a thread pool, the processing order is not the read order. The consumer must process serially, or the partition must be split into more partitions with finer keys.
  • Retries with delay. If a failed message is retried after a backoff, the retry applies after later messages. The fix is to block the partition on the failed message or to reorder by sequence number at the consumer.

The out-of-order tolerance

Some order events do not require strict order. "Order shipped" and "order delivered" are causally dependent and must be ordered. "Order note added" and "order shipped" are independent and can be in any order. The design can distinguish them: causally dependent events use a key that ensures order; independent events use a separate topic (or a separate partition) with no order requirement. This reduces the ordering cost for the events that do not need it.

What to do when the order is violated

Despite the best design, an out-of-order event can arrive — a producer bug, a consumer retry, a misconfigured key. The consumer should be order-tolerant where possible: if a "shipped" event arrives before a "created" event, the consumer should buffer the "shipped" until the "created" arrives, rather than failing or applying it out of order. This is the same buffer-and-fetch pattern as the chat client (Section 1, Question 12). The buffer is per aggregate, bounded, and flushed when the missing event arrives (or on a timeout).

The schema and versioning interaction

If the order events are versioned (order v1, then v2, then v3), the consumer must apply them in version order. The version number is the ordering key, and the partition key ensures they are on the same partition. A consumer that receives v3 before v2 (due to a bug or a retry) must buffer v3 until v2 arrives, or reject v3 and wait. This is a stricter form of the buffering pattern and is common in event-sourced systems.

Trade-off

Keying by order_id gives per-order ordering at the cost of per-order parallelism. A very large order with thousands of events is processed serially, which may be slow. Keying by (order_id, line_item_id) gives more parallelism but loses order between line items of the same order. The right key depends on which ordering matters to the business, and the answer is usually order_id because the order's total and status must be consistent.

7

What is the difference between global ordering and local (per-partition) ordering? When is global ordering required, and what does it cost?

Short Answer

Local ordering means each partition is ordered internally, but there is no order across partitions. Global ordering means every message in the topic has a single, total order. Global ordering requires a single partition (or a single logical sequencer), which eliminates parallelism and caps throughput at one consumer's rate. It is required only when the business must reason about a single total order — typically the financial ledger or the audit log.

Local ordering

Each partition is an ordered log. A consumer reading one partition sees the messages in the order the producer wrote them. A consumer reading multiple partitions sees them in per-partition order but with arbitrary interleaving. The "local order" is the offset within the partition; there is no offset across partitions.

Local ordering is sufficient for almost every business use case. An order's events are ordered within its partition; the order's state is consistent. A user's events are ordered within their partition; the user's session is consistent. The events for different orders or different users have no meaningful relationship, so their cross-partition order does not matter.

Global ordering

Every message has a position in a single total order. If message A was produced before message B, every consumer sees A before B, regardless of which consumer or which partition. This is a stronger guarantee than local ordering, and it is achieved by:

  • Single partition: the topic has one partition, and all messages are written to it. The offset is the global sequence number. Throughput is capped at one partition's write and read rate.
  • Single sequencer: a component (a database, a log, a coordination service) assigns a monotonic sequence number to every message before it is partitioned. The consumer reorders by sequence number. Throughput is capped at the sequencer's rate, which is often the bottleneck.
  • Lamport clock or hybrid logical clock: each message carries a timestamp-plus-counter that provides a total order (with tiebreakers). The consumer reorders by the clock. Throughput is not capped, but the clock's granularity and the tiebreaker policy determine the ordering strictness.

When global ordering is genuinely required

  • Financial ledger: every debit and credit must be applied in a single total order to compute the balance correctly. Out-of-order application produces a different (wrong) balance.
  • Audit log: the record of who did what and when must be a single sequence, even if the actions came from different services.
  • Distributed lock or leader election: the acquisition and release of the lock are ordered; a global sequence prevents two leaders.
  • Event sourcing with a strict invariant: the aggregate's events must be in a defined order, and if the aggregate spans services, that order must be global.

Most systems that think they need global ordering actually need per-entity ordering. A "global" ledger can be sharded by account, and each account's ledger is locally ordered — which is sufficient, because the balance is per account. The sharded ledger has per-account ordering and no global ordering, and it is correct. Global ordering is needed only when the invariant genuinely spans entities.

The cost

ApproachThroughput ceilingLatencyFailure mode
Single partitionOne consumer's rateLow (no coordination)Partition is a single point of bottleneck
Single sequencerSequencer's rateHigher (extra hop)Sequencer is a SPOF; must be replicated
Lamport / HLCUnboundedLowOrdering is approximate; ties need a tiebreaker

The single partition is the simplest global order, and its cost is the most severe: no parallelism. At 1,000 messages/s per consumer, a single partition is 1,000/s — fine for a small ledger, unusable for a high-volume event stream. The single sequencer scales better (the sequencer can be a replicated service) but adds latency and complexity. The Lamport clock is the most scalable but provides only a partial order (with tiebreakers), which is usually sufficient for audit but not for financial invariants.

The outbox pattern for global order

A common technique for getting global order without a single partition: write the events to a database table with an auto-increment ID (or a sequence), and read them in ID order. The database sequence is the global order, and the consumer reads the table in sequence. The throughput is the database's write rate, which is high (a single table can handle tens of thousands of inserts/s), and the ordering is exact. The cost is that the database is now on the hot path, and the events are not "streamed" in the Kafka sense — they are polled. For many systems, this is the right trade-off: the database is already there, and the global order is exactly what an auto-increment ID provides.

Common Pitfall

Choosing global ordering "to be safe" when per-entity ordering would suffice. Global ordering caps throughput at one partition, which is a hard scaling limit that is difficult to remove later. The per-entity ordering is almost always sufficient, and the rare cases that need global ordering should be designed explicitly, not defaulted into.

Part C — Effects, Dedup & Capstone Making duplicates harmless, and putting it all together

8

How do you achieve exactly-once effects without exactly-once delivery? What patterns make duplicates harmless?

Short Answer

Combine at-least-once delivery with idempotent processing. The delivery may be duplicated, but the effect is applied once. The three patterns are: an idempotency key with a dedup table, an upsert keyed by the entity, and the transactional outbox for cross-system workflows. The Kafka transactional API adds a fourth for Kafka-to-Kafka pipelines. The goal is not to prevent duplicates but to make them harmless.

The equivalence

The equation is: at-least-once delivery + idempotent processing = exactly-once effects. The delivery is not exactly-once — the message may be processed twice — but the effect is, because the second processing produces the same state as the first. This is what "exactly-once" means in practice: the user sees one order, one charge, one email, even though the message was delivered twice.

Pattern 1 — Idempotency key with dedup table

The general-purpose solution. The message carries a unique key; the consumer checks the dedup table, and if the key is present, skips. If not, it processes and records the key in the same transaction as the business change. The atomicity of the check-and-record with the effect is what makes it correct. This is covered in detail in Question 9.

Pattern 2 — Upsert

If the message carries the full state of the entity, the consumer writes it with an upsert keyed by the entity ID. The second processing overwrites with the same state, and the result is identical. This is common for CDC events (each event is the full row state) and for state-sync events (each event is the full entity document). It does not work for delta events (increment by 10), because the second application doubles the delta.

Pattern 3 — Transactional outbox

For the producer side: the business change and the message are written to the outbox table in the same database transaction. A relay reads the outbox and publishes to the queue, deduplicating by outbox ID. The consumer receives the message and processes it idempotently. This gives exactly-once effects across the database-queue boundary, which is the hardest boundary in a distributed system.

The outbox has three advantages: it does not require distributed transactions (the database transaction is local), it is compatible with any queue (the relay can publish to Kafka, RabbitMQ, SQS), and it is durable (the outbox is a database table, backed up like any other). The cost is the relay component and the slight latency between the business commit and the publish.

Pattern 4 — Kafka transactional API

For Kafka-to-Kafka pipelines: the consumer's input offsets, its output messages, and its state-store updates are committed in one transaction. A failure aborts the transaction, the offsets are not advanced, and the processing restarts from the last committed offset. The output is not visible to read-committed consumers until the transaction commits. This is exactly-once effects within Kafka, at the cost of transaction overhead and read-committed latency (Volume 3, Question 8).

Pattern 5 — Natural idempotency

The simplest and most robust: the operation is inherently repeatable. Setting a status is idempotent; adding to a set is idempotent; upserting a row is idempotent. The consumer does not need a dedup table or a transaction — the operation itself is safe to repeat. Whenever the business operation can be expressed as a state assignment rather than a delta, it is naturally idempotent, and the design should prefer this.

Choosing the pattern

Operation typePatternExample
State assignmentNatural idempotencySet order status to "shipped"
Full-state eventUpsertCDC row update
Delta operationDedup tableIncrement balance by 10
External system callIdempotency key + dedupCharge card
DB write + queue publishTransactional outboxOrder created event
Kafka-to-Kafka pipelineKafka transactionsStream processing

What "harmless" means

The goal is not to make the system exactly-once — that is impossible — but to make the duplicates harmless. A duplicate that is skipped by the dedup table costs a lookup and a no-op. A duplicate that is upserted costs an idempotent write. A duplicate that is caught by a transaction costs an aborted transaction. In all cases, the user-visible state is correct: one order, one charge, one email. The system is not exactly-once; it is exactly-once in effect, which is what matters.

Interview Framing

Say: "Exactly-once delivery is impossible, but exactly-once effects are achievable. I'll use natural idempotency where the operation allows it, a dedup table for delta operations, and an outbox for database-queue boundaries. The user sees one effect, even if the message was delivered twice." That names the equivalence and the patterns.

9

Design the dedup table: what columns, what TTL, how do you handle failure, and how do you bound its growth?

Short Answer

The dedup table is keyed by the idempotency key, with a timestamp and optionally the result. The consumer inserts the key and applies the business change in the same transaction; if the insert conflicts, the message is skipped. The TTL must exceed the maximum redelivery window (usually 7–30 days). The table is sharded by key, cleaned up by time-based partition drops, and degraded gracefully when unavailable — fail open for loss-tolerant operations, fail closed for money.

The schema

ColumnTypePurpose
idempotency_keyVARCHAR / UUIDPrimary key; the unique operation ID
processed_atTIMESTAMPWhen the key was recorded; used for TTL and audit
resultJSON / TEXT (optional)The stored result, for returning the same response on retry
consumer_idVARCHAR (optional)Which consumer processed it; for debugging
expires_atTIMESTAMP (optional)Explicit expiry, for partition management

The primary key is the idempotency key. The result column is needed when the consumer must return the same response on retry (e.g., an HTTP API that returns the same body for the same idempotency key). The expires_at column is needed when the table is partitioned by time and partitions are dropped rather than rows deleted.

The transactional insert

The core operation is:

StepSQLIf conflict
1INSERT INTO dedup (key, processed_at) VALUES (?, now())Unique violation → skip the message, commit offset
2Apply the business change (INSERT/UPDATE)Same transaction; if it fails, roll back the dedup insert
3COMMITBoth the key and the effect are durable
4Commit the Kafka offsetAfter the transaction; a crash between 3 and 4 causes redelivery, which is skipped by the key

The critical property is that steps 1 and 2 are in one transaction. If they were separate, a crash between them would leave the key recorded but the effect not applied — a message that is skipped forever. The transaction guarantees both or neither.

The TTL

The key must be retained for longer than the maximum time a message could be redelivered. That window is determined by:

  • Kafka retention: a message can be re-read from the log as long as the log retains it. If retention is 7 days, the key must be retained at least 7 days.
  • Consumer outage: a consumer that is down for days will catch up from its committed offset. The keys for the messages it reprocesses must still be present.
  • Retry policy: the maximum retry window (hours, days) must be less than the TTL.

The standard TTL is 7–30 days. Shorter TTLs risk a redelivery that is not deduplicated (the key expired); longer TTLs increase storage. The TTL should be set from the retention policy plus a margin.

Bounding growth

At 100k messages/s and a 30-day TTL, the table has 260 billion rows — far too large for a single table. The solutions:

  • Partition by time: a partition per day (or per hour). The TTL is enforced by dropping old partitions, which is O(1) instead of a DELETE. This is the standard approach.
  • Shard by key: hash the key to a shard. The table is distributed, and each shard is partitioned by time. This scales horizontally.
  • Short TTL: if the redelivery window is short (e.g., 1 day), the TTL can be 2 days, and the table is 10× smaller.
  • Bloom filter: for very high-volume, loss-tolerant operations, a Bloom filter of recent keys can be used instead of a full table. It is probabilistic (false positives skip a real message), so it is only suitable where a rare skip is acceptable.

Failure modes

FailureBehaviourMitigation
Dedup table unavailableConsumer cannot check or insertFail closed (block) for money; fail open (process anyway) for loss-tolerant; local cache of recent keys
TTL too shortRedelivery after expiry is not deduplicatedTTL > retention + max outage
Transaction too largeSlow inserts, lock contentionPartition by time; batch the offset commit
Key collisionTwo different operations share a key → second is skippedUse a unique, well-scoped key (UUID or aggregate+version)
Duplicate key inserted concurrentlyOne transaction wins, the other failsThe losing transaction retries and sees the key → skip

The fail-open vs fail-closed choice

If the dedup table is unavailable, the consumer cannot check or insert. The choice:

  • Fail closed: the consumer blocks, does not process, and the message is redelivered later. This is safe for money (no duplicate charge) but stops the pipeline during the outage.
  • Fail open: the consumer processes anyway, accepting possible duplicates. This keeps the pipeline running but risks duplicate effects.

The choice is per-operation. Money and inventory fail closed; analytics and notifications fail open. The design should make the choice explicit, not a default.

The audit trail

The dedup table is also the audit trail: it records what was processed and when. For compliance, it is often retained longer than the TTL (the processing record is separate from the dedup record). The design may have two tables: a dedup table with a short TTL and a processed-events table with a long retention. The first is for correctness; the second is for audit.

Common Pitfall

Checking the dedup table in a separate transaction from the business change. A crash between the check and the change leaves the key recorded but the effect not applied — the message is skipped forever. The check and the effect must be in one transaction.

10

Capstone: design a payment processing pipeline that guarantees exactly-once effects end to end.

Short Answer

The pipeline is: payment service writes the intent to its DB and an outbox row in one transaction; a relay publishes the outbox row to Kafka keyed by payment_id; the payment processor consumes the event, calls the payment provider with an idempotency key, and writes the result plus a dedup row in one transaction; the ledger consumes the result and applies the entry with an idempotency key. Every step is idempotent, every external call has an idempotency key, and the ordering is per payment, not global.

The requirements

  • No double charge: the provider must be charged exactly once per payment, even if the pipeline retries.
  • No lost payment: a payment that the user initiated must eventually be charged or explicitly failed.
  • Consistent ledger: the ledger must reflect every successful charge exactly once, and no failed charge.
  • Auditable: every step must be recorded for compliance.
  • Ordered per payment: the charge, the confirmation, and the refund (if any) must be ordered relative to each other.

The pipeline

StepComponentActionIdempotency
1 Payment API Writes payment_intent + outbox_event in one DB transaction Client-supplied Idempotency-Key; unique constraint on (user_id, idem_key)
2 Outbox relay Reads uncommitted outbox rows, publishes to Kafka, marks them published Outbox row ID is the Kafka message key; relay dedups by ID
3 Kafka topic Partitioned by payment_id; per-payment order preserved Producer idempotence enabled
4 Payment processor Consumes payment_intent, calls provider with idempotency_key = payment_id, writes charge_result + dedup row in one transaction Provider idempotency key + dedup table + offset commit after transaction
5 Ledger consumer Consumes charge_result, writes ledger entry, dedups by payment_id Dedup table + natural idempotency (ledger entry keyed by payment_id)
6 Notification Consumes charge_result, sends receipt Idempotency key; at-most-once acceptable for receipt (retry once, then drop)

Why the outbox is essential here

The payment API must write the intent and publish the event. If it writes the intent and then publishes, a crash between them loses the event — the payment is created but never charged. If it publishes and then writes, a crash loses the intent — the payment is charged but not recorded. The outbox solves both: the intent and the event are one transaction, so either both are written or neither. The relay publishes from the outbox, and if it crashes, it retries on restart; the outbox row is still there. The relay is idempotent (publishing the same row twice is harmless, because the consumer dedups).

Why the provider call has an idempotency key

The provider's API may time out — the charge was successful but the response was lost. The processor cannot know whether to retry (risking a double charge) or not (risking a lost charge). The provider's idempotency key solves it: the processor sends the same key on retry, and the provider returns the original result rather than charging twice. This is the only way to make an external, non-transactional call safe to retry.

The key is payment_id (or a deterministic derivation), not a random UUID generated per attempt. A random UUID per attempt defeats the purpose — each attempt looks like a new charge to the provider. The key must be stable across retries.

Why ordering is per payment, not global

Payments are independent of each other. Payment A's charge and payment B's charge have no causal relationship, so their global order is irrelevant. Within a payment, the events (intent, charge, confirmation, refund) must be ordered, and the payment_id partition key ensures that. A global order across all payments would require a single partition and cap throughput at one consumer's rate — unacceptable for a high-volume payment system.

The failure modes and their handling

FailureHandling
Payment API crashes before commitNo intent, no event; the client retries with the same Idempotency-Key
Payment API crashes after commit, before relayOutbox row is durable; relay picks it up on restart
Relay crashes after publish, before marking publishedRelay retries; publishes duplicate; consumer dedups by message ID
Processor crashes before provider callOffset not committed; redelivery; no charge yet
Processor crashes after provider call, before DB writeProvider charged; redelivery; provider idempotency key returns the original result; DB write succeeds
Processor crashes after DB write, before offset commitRedelivery; dedup table sees the key; skip; offset committed
Provider times outProcessor retries with the same idempotency key; provider returns the original result
Ledger consumer crashesRedelivery; dedup by payment_id; ledger entry applied once
Dedup table unavailableProcessor fails closed (blocks) for money; ledger fails closed; pipeline pauses but does not double-charge

The guarantees, stated precisely

  • No double charge: the provider's idempotency key guarantees it, regardless of how many times the processor retries.
  • No lost payment: the outbox guarantees the event is published; the processor retries until the provider responds; the DLQ catches the ones that exhaust retries.
  • Exactly-once ledger: the ledger consumer's dedup table guarantees each charge is applied once, even if the message is delivered twice.
  • Per-payment order: the partition key guarantees the events for one payment are in order.
  • Audit: the outbox, the dedup table, the ledger, and the provider's records together provide a complete audit trail.

What would break it

  • Non-deterministic idempotency key: a random key per retry makes the provider charge twice. The key must be stable across retries.
  • Dedup check outside the business transaction: a crash between them leaves the key recorded but the effect missing.
  • Global ordering requirement: if the business requires a single total order across all payments, the pipeline is capped at one partition. This is almost never needed for payments (per-payment order is sufficient).
  • Relay not idempotent: a relay that publishes the same outbox row twice without the consumer dedup would duplicate the charge. The relay is idempotent by design, and the consumer dedups as a backstop.
  • Provider without idempotency keys: some providers do not support them. The fallback is to query the provider for the payment's status before retrying, which is slower and not always reliable. Providers with idempotency keys are strongly preferred.
Interview Framing

Say: "The outbox makes the DB-queue boundary exactly-once in effect; the provider's idempotency key makes the external call safe to retry; the dedup table makes the consumer's effect idempotent; and the partition key gives per-payment order without a global bottleneck. Each step is idempotent, and the failures are handled by redelivery plus dedup." That names every mechanism and maps it to its boundary.
