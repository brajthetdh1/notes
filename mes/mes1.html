Part A — Core Chat Design The three planes: connection, storage, delivery

1

Design a chat application like WhatsApp or Messenger. Walk through 1-on-1 messaging, group chats, message history, and read receipts.

Short Answer

Model the system as three planes. The connection plane is a fleet of WebSocket gateways holding live client sockets, with a registry mapping user → gateway. The storage plane is a sharded, time-ordered message log keyed by (conversation_id, seq). The delivery plane reads the log, fans out to online recipients via the registry, and pushes offline ones. Read receipts are a per-user watermark stored alongside the conversation.

Connection plane

Every client opens a WebSocket to one of many gateway nodes. The gateway authenticates the user, registers the connection in a distributed registry (Redis or a purpose-built service), and holds the socket in memory. The registry maps user_id → [(gateway_id, connection_id), ...] because a user may have several devices. Gateways are stateless apart from the live sockets, so they can be added or drained freely. Each connection carries a heartbeat every 20–30 seconds; two missed heartbeats and the gateway removes it from the registry and notifies presence.

Storage plane

The unit of storage is the conversation, not the user. Every message is a row keyed by (conversation_id, seq) where seq is a monotonic per-conversation counter assigned at write time. This key choice is the whole design: "last 50 messages" and "messages after seq X" are both single range scans, which is exactly what the UI needs. The table is sharded by conversation_id, so all of a conversation's history lives on one shard. For 1-on-1, conversation_id = hash(min(a,b) || max(a,b)) — deterministic, so both users' clients compute the same value without a lookup. For groups, conversation_id is a random UUID and the member list lives in a separate membership table.

Wide-column stores (Cassandra, ScyllaDB) are the standard choice because they are designed for exactly this access pattern: partition by conversation, cluster by seq, append-only. Media is stored in object storage; the message holds a reference and a thumbnail URL served through a CDN.

Delivery plane

The write path is: client → gateway → chat service → persist → assign seq → ack sender → fan out. The fan-out path reads the recipient list, looks up each online recipient in the registry, and sends the message over that gateway's socket. Recipients with no active socket get a push notification (APNs/FCM) that wakes the app to fetch. The message is already in the log, so the push is only a hint — it carries no delivery guarantee.

Read receipts

Receipts are a per-user, per-conversation watermark: read_seq is the highest seq the user has seen in that conversation. Marking a conversation read is an upsert of that single value, which is cheap. The sender's UI displays "read by N of M" by querying the watermarks of the other members — for 1-on-1 this is a single value; for groups it is a small aggregate. "Delivered" is a separate watermark updated when the recipient's device acknowledges receipt. Both are stored per-user, sharded by conversation_id, and propagated to other devices of the same user via the same fan-out channel.

What the interview cares about

The design hinges on three choices: (1) keying the log by conversation rather than by user, which makes history a single range scan; (2) separating the connection registry from the message store so neither is a bottleneck for the other; (3) treating push as best-effort and the log as the source of truth, which is what makes offline delivery and reconnection work without special cases. Everything else — presence, typing indicators, delivery receipts — hangs off those three.

Trade-off

Keying by conversation is optimal for history but makes "list all my conversations" require a separate per-user index (the user's conversation list, sharded by user_id, with last-message preview and unread count). That denormalized index is a second source of truth that must be updated on every message, usually via the same fan-out pipeline.

Interview Framing

Open with: “Three planes — connection, storage, delivery — and the message log is the source of truth; WebSocket is an optimization on top of it.” That sentence resolves half the follow-up questions before they are asked.

2

Design a real-time messaging platform like Slack or Discord, focusing on channels, threads, presence, and search.

Short Answer

Slack and Discord are chat at a different scale and shape: many channels per workspace, some very large, with threads as sub-conversations, search as a first-class feature, and presence visible across the workspace. The core message log is the same, but fan-out, presence, and search each need their own subsystem, and the group-size distribution drives the fan-out strategy.

Channels, threads, and message model

A workspace contains channels; a channel is a conversation with its own member list. Every message belongs to exactly one channel and is stored in the channel's log keyed by (channel_id, seq). A thread is a sub-conversation attached to a parent message: the parent holds a thread_id, and the thread's messages are stored under that thread_id as their own log. Threads reduce fan-out on the main channel — a reply in a thread notifies only thread participants, not the whole channel — which is exactly why Slack and Discord added them.

Fan-out by channel size

The critical difference from WhatsApp is that channel sizes are wildly skewed. Most channels have a handful of members, but a few have hundreds of thousands. A single fan-out strategy cannot serve both:

  • Small channels (≤ ~1,000): fan-out on write. Each message generates N delivery events; online members get a WebSocket push, offline members get a push notification and a per-user offset.
  • Large channels (10,000+): fan-out on read. The message is stored once; each member's client pulls from its last-read seq when connected. A lightweight "channel updated" signal tells clients to poll, but the message content is never fanned out.
  • Very large servers (Discord's 100k+ member servers): even the "channel updated" signal cannot be per-member. The client's local view is built from the log on connect and kept fresh by a per-channel broadcast that the client subscribes to only for channels it is actively viewing.

Presence

Presence in Slack and Discord is more complex than WhatsApp because it is scoped to a workspace: you see the online status of people in your workspace, not everyone. The design is a per-user presence entry (online, away, offline, last_seen) stored in a sharded, in-memory store with a TTL, plus a per-workspace subscription so a client is pushed presence updates for its workspace members. For a 100k-member Discord server, per-user presence is impossible — Discord shows presence only for friends and for the current channel's members, and aggregates "N online" for the server. The lesson: presence must be scoped to the audience that actually needs it, or it becomes an unbounded fan-out problem.

Search

Search is the feature that most distinguishes Slack from WhatsApp, and it is why Slack is not end-to-end encrypted. Messages are streamed via CDC from the message store into Elasticsearch (or OpenSearch), where they are indexed by workspace, channel, author, and content. The search index is eventually consistent — typically within a second or two — and it is a separate read path that never touches the OLTP store. Search is permission-filtered at query time: the index carries the channel and workspace, and the search service intersects with the user's membership before returning results. Without permission filtering at query time, search would leak private channels.

Mentions and unread

Every channel member has a read_seq watermark; unread count is last_message_seq - read_seq. Mentions (@user, @here, @channel) are extracted at write time and stored in a separate mentions index keyed by user, so a user's mention inbox is a single query regardless of how many channels they are in. This is a denormalization: the mention notification is derived from the message, not computed at read time.

Storage and scale

Slack historically sharded MySQL by workspace (a Vitess-like approach), which aligns the data layout with the natural tenant boundary. Discord uses Cassandra and ScyllaDB for message storage, with a Rust-based data service in front. Both designs share the same principle: the workspace (or server) is the shard boundary, so a single workspace's data stays together and cross-workspace queries are rare. The message log is append-only and partitioned by channel and time, which makes retention and cold storage straightforward.

Trade-off

Search is incompatible with end-to-end encryption. Slack chose search and moderation over E2E for channels; Signal chose E2E and gives up server-side search entirely. A platform that offers both must scope E2E to direct messages and leave channels searchable — which is exactly what most products do.

How do you design a 1-on-1 chat service? What are the key components and data flows?

Short Answer

1-on-1 is a degenerate group with two members and a deterministic conversation ID. Because conversation_id = hash(sorted(a, b)), both users' clients compute the same shard without a lookup, and every message for the pair lands on one shard. The design is then a single-writer message log, a connection registry, and a delivery path that is identical for both directions.

Data model

Table / KeyspaceKeyPurpose
conversationsconversation_idMembers, created_at, last_message_at, per-user read_seq
messages(conversation_id, seq)sender_id, body, created_at, media_ref, client_uuid
user_conversations(user_id, conversation_id)Per-user index: last message preview, unread count
dedup(sender_id, client_uuid)Idempotency: reject retried sends

The messages table is sharded by conversation_id. The user_conversations table is sharded by user_id so "list my chats" is one query. These are two different shards and two different access patterns, which is why the design needs both.

Write flow

  1. Client sends a message with a client-generated client_uuid.
  2. Gateway forwards to the chat service. The service checks membership, then checks the dedup table on (sender_id, client_uuid). If present, it returns the existing message (idempotent).
  3. The service increments the conversation's seq atomically (a lightweight transaction or a per-conversation counter) and writes the message row.
  4. It updates user_conversations for both users: last message preview, unread count, timestamp.
  5. It acks the sender with the assigned seq.
  6. It fans out: look up the recipient's gateway in the registry and send the message over the socket. If the recipient is offline, enqueue a push.

Read flow

Opening the conversation: the client sends last_seen_seq; the server returns messages with seq > last_seen_seq, paginated. Marking read: upsert read_seq for this user; the server publishes a "read updated" event to the other participant's gateway so the sender sees the receipt. Listing chats: query user_conversations by user_id, ordered by last_message_at.

Sequence assignment

The seq must be atomic per conversation. Three options: (1) route all messages for a conversation to a single chat service instance via consistent hashing — simplest, but the service is stateful; (2) use a per-conversation counter row with a lightweight transaction (Cassandra LWT) or an atomic increment (Redis INCR with persistence) — correct but slower; (3) use a hybrid logical clock with a tiebreaker — no coordination, but the "seq" is a composite value the client must understand. Most production systems use option 1 or 2. The choice matters because it determines whether simultaneous sends are serialized by the service or by the storage layer.

Receipts

"Sent" is returned as soon as the row is persisted. "Delivered" is acknowledged when the recipient's device receives the WebSocket frame (or fetches it on reconnect). "Read" is the read_seq watermark. These are three different states, and the UI shows them as separate ticks. All three are stored per-user and propagated to the user's other devices.

Deletion and edit

"Delete for me" removes the row from the local store and records a tombstone in the user's user_conversations index; the message remains in the log for the other user. "Delete for everyone" writes a tombstone message into the log that replaces the body; both clients apply it. Edit is the same mechanism — a new message that references the original seq and carries the new body; clients render the latest edit. The log remains append-only, which preserves the audit trail.

Common Pitfall

Sharding by sender_id or recipient_id instead of by conversation_id. That splits a conversation across two shards and turns every history read into a fan-out. The conversation is the natural unit of both storage and access; shard by it.

Design a group chat system. How does fan-out work when a message is sent to 256 members? What are the bottlenecks?

Short Answer

For 256 members, fan-out on write is entirely feasible: the message is persisted once, then 256 delivery tasks are enqueued and processed in parallel. The bottlenecks are not the fan-out count itself but the lookup cost (256 presence queries), the push volume (256 push API calls for offline users), and the write amplification if you persist per-recipient delivery state. The fix is batching, caching, and storing delivery state as per-user offsets rather than per-message rows.

The write path

  1. Sender's message reaches the chat service.
  2. Assign seq for the conversation, persist the message once.
  3. Update the sender's user_conversations index.
  4. Enqueue a fan-out task with (conversation_id, seq, member_ids).
  5. Ack the sender.

The fan-out happens asynchronously. The sender does not wait for 256 deliveries — that would make the send latency proportional to group size, which is unacceptable. The message is durable the moment it is persisted; delivery to the other 255 is a background concern.

The fan-out worker

The worker reads the member list and partitions members into online and offline. It does this by querying the connection registry in batch — a single MGET on Redis for 256 keys, not 256 individual lookups. For online members, it groups by gateway and sends one RPC per gateway carrying all the messages for that gateway's connections. If the 256 members happen to be spread across 20 gateways, that is 20 RPCs, not 256. For offline members, it enqueues push notifications, which are also batched by provider and by user settings.

Why 256 is easy and 100,000 is not

The cost is O(members). At 256, that is trivially parallelizable across workers and well within a single broker's throughput. At 100,000, the fan-out itself becomes the workload: a single message generates 100,000 delivery events, and a burst of messages in a large channel generates millions of events per second. The standard strategy shifts at scale:

Group sizeStrategyWhy
≤ 1,000Fan-out on writeCheap; each member gets the message immediately
1,000 – 10,000Hybrid: fan-out to online, lazy for offlineOnline users get real-time; offline users fetch on reconnect
10,000+Fan-out on read onlyFan-out cost dominates; store once, let clients pull
Broadcast (100k+)Store once + notification signalNo per-member delivery; clients subscribe to the channel

Ordering in a group

Every message has a seq per conversation, assigned before fan-out. All members receive the same messages in the same order because the seq is the ordering authority. If a delivery is retried, the client deduplicates by seq. If a client is offline and fetches later, it fetches by seq range and merges in order. Ordering in groups is therefore free as long as the seq is assigned once and delivered with the message.

Read receipts in groups

Aggregating "read by 200 of 256" is a high-write operation. The standard approach is to keep per-user read_seq and either (a) compute the aggregate lazily when the sender opens the message details, or (b) periodically fold the per-user watermarks into a counter (e.g., "read by at least 150") to avoid maintaining an exact count. Exact per-member receipts are usually not worth the write cost; showing "read by many" or listing the readers on demand is the pragmatic compromise.

Storage: one row, not 256

The single most important design choice is to store the message once and represent delivery state as per-user last_seen_seq. If you instead write a delivery row per recipient per message, storage grows as O(messages × members) and write amplification is 256× for a 256-member group. Per-user offsets keep storage O(messages) and delivery state O(members), which is the right scaling. The trade-off is that per-message delivery status ("has Bob seen message 42?") is not directly available; it must be derived from Bob's last_seen_seq, which is fine for the UI ("Bob has read up to this point").

Membership changes

Adding a member: the new member's last_seen_seq is initialized to the current last seq, so they see only future messages by default (or the admin grants history access by setting the offset back). Removing a member: their subscription to the channel is removed, and the fan-out worker no longer includes them. Both operations update the member list atomically; a message in flight during a membership change may reach a just-removed member or miss a just-added one, which is acceptable because the message is still in the log and the client can reconcile.

Trade-off

Fan-out on write gives the best read latency but the worst write amplification. Fan-out on read gives the best write scaling but forces every reader to pull from the log, which is expensive for active readers and requires a separate notification channel to tell them there is something to pull. The group-size threshold is the point where the total fan-out cost per message exceeds the total read cost per active member — usually around a few thousand members for chat workloads.

Compare WebSocket, long-polling, and Server-Sent Events (SSE) for real-time chat. Why is WebSocket the default?

Short Answer

WebSocket is a persistent, full-duplex, low-overhead connection: it is the only option that supports bidirectional, low-latency, high-frequency messaging without per-message HTTP overhead. Long-polling is a compatibility fallback that adds a round trip per message. SSE is a one-way server-to-client stream that is simpler than WebSocket but cannot carry client messages on the same channel.

DirectionFull duplexClient-initiated onlyServer → client only
ConnectionOne persistent TCP connectionRepeated HTTP requestsOne persistent HTTP response

LatencySub-10 msOne RTT per message (~50–200 ms)Low for server→client

Why WebSocket wins for chat

Chat is bidirectional and high-frequency. Typing indicators, presence changes, read receipts, and message sends all flow client→server; message deliveries, presence updates, and receipts flow server→client. A transport that can only do one direction needs a second channel, which doubles the connection state and complicates ordering between the two channels. WebSocket solves this with a single connection and minimal framing overhead. At a thousand messages per second per gateway, the difference between 2-byte frames and 800-byte HTTP headers is roughly 800 KB/s versus 200 KB/s — a factor of four in bandwidth, and a much larger factor in CPU spent parsing HTTP.

Where long-polling still makes sense

Long-polling is a fallback, not a primary transport. It is useful when: the client is behind a proxy that blocks WebSocket upgrades (common in some enterprise networks and older mobile carriers), the client is a browser that does not support WebSocket (very rare today), or the system is a low-frequency notification feed where the per-message overhead does not matter. Many chat apps implement WebSocket with long-polling as a fallback negotiated at connect time.

Where SSE makes sense

SSE is ideal for server-push-only scenarios: a stock ticker, a notification feed, a dashboard that only reads. It is simpler than WebSocket (plain HTTP, auto-reconnect built in) and works through proxies. It is the wrong choice for chat because the client also needs to send messages and presence updates, which requires a second HTTP channel and ordering coordination between the two.

What real chat systems actually do

WhatsApp uses a custom protocol derived from XMPP over TCP, not WebSocket — because the app controls both ends and does not need browser compatibility. Messenger uses MQTT over WebSocket. Slack uses WebSocket for both send and receive. Discord uses WebSocket for the gateway and a separate HTTP API for REST operations. The pattern is consistent: a persistent connection for the real-time channel, and either the same connection or a stateless HTTP API for the request/response operations.

The hidden costs of WebSocket

WebSocket is stateful, and that state is expensive. Each connection holds a file descriptor, buffers, and TLS state — roughly 50–100 KB per connection. A gateway with 500,000 connections uses 25–50 GB of memory just for connection state, plus CPU for heartbeats and TLS. Load balancers must be configured for long-lived connections (idle timeouts, connection draining). Deployment is harder: replacing a gateway means migrating or dropping live connections. None of these costs exist for long-polling, which is why some systems still choose it despite the latency.

Interview Framing

Say: “WebSocket for the real-time channel because chat is bidirectional and high-frequency; long-polling as a negotiation fallback for restrictive networks; SSE only if the product were push-only.” That names all three with a clear reason for each.

6

How do you handle WebSocket connection management across millions of concurrent users?

Short Answer

The gateway fleet is the easy part — each node holds 100k–500k sockets and is otherwise stateless. The hard part is the connection registry: a highly available, low-latency map from user to gateway (and from gateway to its connections) that every message-routing decision depends on. Get the registry right and everything else follows; get it wrong and either the registry becomes a bottleneck or it becomes a single point of failure.

The gateway fleet

Gateways are deployed as a horizontally scaled fleet behind an L4 load balancer (which does not need to inspect HTTP). Each gateway accepts WebSocket upgrades, authenticates the user, and stores the connection locally. The number of connections per gateway is bounded by memory and file descriptor limits; 100k–500k is typical. Gateways are stateless apart from the sockets, so they can be drained and replaced without data loss — the client reconnects to another gateway.

The connection registry

The registry must answer two questions fast: "which gateways hold user X's connections?" and "what are all the connections on gateway G?" The first is needed for message routing; the second is needed for gateway shutdown and monitoring. Options:

  • Redis (or a Redis-compatible store): a hash per user, with TTL, plus a set per gateway. Simple, but every message routing decision becomes a Redis lookup — at 1M messages/s, that is a lot of Redis QPS. Usually acceptable with client-side caching of recently-seen users.
  • Purpose-built registry service: a sharded, in-memory service that holds the map, with consistent hashing so each user's entry lives on a specific node. This is what large platforms build when Redis becomes the bottleneck.
  • Consistent hashing on user_id: no registry at all — the routing layer computes gateway = hash(user_id) mod N. This is the simplest design at the cost of requiring rebalancing when the gateway count changes. Used by Discord and others.
  • Hybrid: consistent hashing for the steady state, with a fallback registry for users whose connection is on a non-home gateway during a rebalance.

Connection lifecycle

On connect: the gateway authenticates the token, registers the connection in the registry with a TTL, and sends a "connected" frame to the client. The client starts a heartbeat (ping every 20–30 seconds). On disconnect: the gateway removes the connection, updates presence, and (if it was the last connection for that user) marks the user offline. On heartbeat timeout: the same cleanup runs on a timer. On gateway crash: the TTL expires and the registry entry is removed; the client detects the dead socket and reconnects.

Connection draining during deploys

Replacing a gateway without dropping messages requires a graceful drain. The gateway marks itself as "draining" in the registry, so new connections are no longer routed to it. It sends a "please reconnect" frame to all clients, which reconnect to healthy gateways with jittered backoff. The gateway continues to serve existing connections for a grace period (e.g., 60 seconds) so in-flight messages complete, then closes the remaining sockets and shuts down. The registry removes the gateway. Clients that reconnect before the grace period ends are served by the new gateway and never notice the deploy.

Failure modes

  • Gateway crash: clients reconnect to any healthy gateway; the registry cleans up via TTL. Messages routed to the dead gateway fail and are retried or converted to push.
  • Registry outage: without the registry, the routing layer cannot find recipients. The mitigation is a local cache of recent lookups (with a short TTL) that keeps working for the most active users. Consistent-hash routing avoids the registry entirely in the steady state.
  • Thundering-herd reconnect: a gateway failure causes thousands of clients to reconnect at once, overloading the healthy gateways. Exponential backoff with jitter on the client, and admission control at the load balancer, are the standard mitigations.
  • Connection limit exhaustion: the OS runs out of file descriptors. Monitor ulimit and connection counts; tune somaxconn, tcp_max_syn_backlog, and per-process limits.

Multi-region

In a multi-region deployment, each user's connections are pinned to their home region. The registry is regional, and cross-region message routing goes through a regional bridge (or the message log, which is replicated). This keeps the routing decision local and avoids a global registry, at the cost of a cross-region hop for messages between users in different regions.

Trade-off

Consistent hashing avoids the registry but makes the gateway fleet hard to change size. A registry makes the fleet elastic but adds a lookup per routing decision and a component to keep available. Most large systems use consistent hashing with a registry fallback — the best of both, at the cost of two code paths to maintain.

Mobile operating systems frequently kill background WebSocket connections. How would you design a hybrid architecture to deliver near-real-time updates while respecting battery and background limits?

Short Answer

Use a WebSocket while the app is in the foreground, and a push notification (APNs on iOS, FCM on Android) when it is backgrounded or killed. The message log is the source of truth; the push is only a hint to wake the app and fetch. This is exactly how every major mobile chat app works, and there is no reliable alternative because the OS will not let you keep a background socket alive.

Why background sockets die

iOS suspends apps within seconds of backgrounding; after roughly 30 seconds the app is frozen and its socket is closed. Android is more permissive but Doze mode and OEM battery optimizations aggressively kill background processes. Neither platform lets an app hold a persistent socket indefinitely — the battery cost would be unacceptable and the OS vendors have made it a policy. The only reliable way to wake a backgrounded app is a push notification, delivered by the OS vendor's own persistent service (APNs or FCM).

The architecture

App stateTransportBehaviour
ForegroundWebSocketReal-time messages, presence, typing, receipts
Background (alive)Push (data) + short reconnectPush wakes the app for a brief fetch; socket may be re-established briefly
Background (suspended/killed)Push (visible notification)User taps → app opens → connects → fetches from log
Offline (no network)Local queueClient persists outbound messages; sends on reconnect

Push payloads

There are two kinds of push:

  • Visible notification — the OS shows it; the user taps it to open the app. This is the only guaranteed delivery mechanism for a suspended app, but it is user-visible and can be ignored.
  • Silent / data push — wakes the app briefly to process a payload. On iOS this is heavily throttled and not guaranteed; on Android it is more reliable but still subject to Doze. Silent pushes are useful for opportunistically syncing, not for guaranteed delivery.

The push payload can carry the message content, but in an E2E-encrypted system it carries only a notification hint (and, if the user has opted in, an encrypted preview the device can decrypt). The client fetches the full message from the log on wake.

Battery and data considerations

Frequent pushes drain the battery and consume mobile data. The mitigations: batch notifications ("5 new messages from Alice"), suppress pushes when the app is foregrounded (the WebSocket already delivered), and coalesce pushes for a user who is offline for a long time. iOS limits silent pushes to a few per hour per app; Android's Doze mode batches network access into maintenance windows. The client must be designed for delayed and out-of-order delivery.

Presence implications

"Online" on mobile is unreliable because the OS kills the socket arbitrarily. Most apps show "last seen at HH:MM" instead of a live online indicator, or treat "foreground app with active socket" as online and everything else as offline. The "last seen" value is updated on every clean disconnect and on every push receipt, giving a reasonable approximation without requiring a live socket.

Reconnection on foreground

When the app returns to the foreground, it opens a WebSocket, authenticates, and sends its last_seen_seq per conversation. The server returns all messages after that seq. The client merges them into its local store, updates unread counts, and resumes real-time. The gap between backgrounding and foregrounding may be hours, so the fetch is paginated and the client rate-limits to avoid overwhelming the device on a slow network.

Trade-offs

Push delivery is best-effort and adds 1–10 seconds of latency compared to WebSocket. It costs money at scale (APNs is free but FCM and vendor services can charge). It requires a push token per device, which must be registered with the backend and refreshed. And it exposes metadata to the push provider — which is why E2E-encrypted apps encrypt the payload or send only a "you have a message" hint.

Common Pitfall

Treating a push as the delivery mechanism and not storing the message in the log first. If the push fails or the app does not wake, the message is lost. The log is the source of truth; the push is a wake-up signal and nothing more.

How do you route messages across multiple WebSocket gateway servers without making Redis Pub/Sub a bottleneck?

Short Answer

Redis Pub/Sub broadcasts every message to every gateway, which means each gateway processes every message even though it holds only a fraction of the users. The fix is targeted routing: look up which gateway holds the recipient's connection and send the message only to that gateway. The lookup is the registry from Question 6; the send is a direct RPC, not a broadcast.

Why broadcast does not scale

With 100 gateways and 1 million messages per second, a Redis Pub/Sub broadcast delivers 100 million message copies per second across the fleet. Each gateway deserializes every message, checks whether any of its connections match the recipient, and discards 99.9% of them. The wasted CPU, memory, and network bandwidth dominates the useful work, and Redis's single-threaded publish path becomes the ceiling. The system scales with the number of messages, not with the number of users — the opposite of what you want.

Targeted routing

The chat service knows the recipient's user_id. It looks up the registry to find the gateway(s) holding that user's connections. It sends the message over a direct gRPC call (or an AMQP queue dedicated to that gateway) to those gateways only. Each gateway delivers to its local connection and acks. The total work is proportional to the number of recipients, not to the number of gateways.

The alternatives, ranked

What production systems do

Discord uses a consistent-hash approach: each user's gateway connection is determined by hashing the user_id, so the routing layer computes the destination without a registry lookup. Slack uses a registry-based routing service that maintains the user-to-gateway mapping and sends directly. WhatsApp's architecture is internal and custom but follows the same pattern: a directory of which server holds which user, and targeted message delivery. In all cases, Redis (or a similar store) is used for presence and ephemeral state, not for message routing at scale.

Failure handling

If the registry lookup fails or the target gateway is unreachable, the routing layer has three options: retry the lookup, fall back to a broadcast (slow but reliable), or convert to a push and let the client fetch on reconnect. In practice the fallback is push — the message is in the log, so the client will get it on the next fetch. The routing failure does not lose the message; it only delays its delivery.

Multi-device

A user connected on phone and laptop has two entries in the registry. The routing layer sends the message to both gateways. The fan-out cost is bounded by the device count (typically 1–5), not by the gateway count, so this is not a scaling problem.

Latency

Targeted routing adds a registry lookup (sub-millisecond for a local cache, a few milliseconds for a Redis lookup) and a direct RPC (same datacenter, sub-millisecond). The total added latency is 1–3 ms, which is negligible compared to the WebSocket frame round trip. The broadcast approach has lower per-message latency for the destination gateway (no lookup) but much higher total system cost. The trade-off favors targeted routing at any meaningful scale.

Interview Framing

Say: “I'll use a connection registry mapping user to gateway, and the chat service will route each message directly to the gateways holding the recipient's connections. Redis is for presence and ephemeral state, not for message routing.” That immediately signals you understand the difference between targeted and broadcast delivery.

Part C — Ordering & Delivery Semantics Sequence numbers, simultaneous sends, and exactly-once effects

9

How do you guarantee that messages within a conversation are delivered in order?

Short Answer

Assign a monotonic seq per conversation at write time, store messages keyed by (conversation_id, seq), and deliver in seq order. The client displays by seq and buffers any out-of-order delivery until the gap fills. The hard part is assigning seq atomically when messages can arrive at different service instances concurrently.

Why ordering breaks

  • Concurrent writes to different instances. Two messages for the same conversation processed by two chat-service instances can be persisted in either order unless a single authority serializes them.
  • Fan-out reordering. The delivery pipeline (queue, worker, gateway) may process messages for the same recipient out of order, especially with retries or parallel workers.
  • Network reordering. TCP guarantees order within a connection, but multiple WebSocket connections (multi-device) or a WebSocket + HTTP fetch can deliver the same message through different paths.
  • Clock skew. Ordering by client timestamp is unreliable; two clients' clocks can differ by seconds.

Sequence assignment

The sequence number must be assigned by a single logical authority per conversation. Three viable designs:

  • Single-writer per conversation. Route all messages for a conversation to one chat-service instance via consistent hashing on conversation_id. The instance assigns seq atomically (in-memory counter, or a storage atomic). Simple, but makes the service stateful and requires rebalancing when instances change.
  • Storage-layer counter. A per-conversation counter row incremented with a lightweight transaction (Cassandra LWT) or an atomic Redis INCR with persistence. The returned value is the seq. Correct and durable, but every message pays a coordination round trip.
  • Hybrid logical clock. Each message carries an HLC — a timestamp plus a logical counter that advances on message receipt. The order is (HLC, tiebreaker), where the tiebreaker is a node ID. No coordination, but the "seq" is a composite value and the client must understand it. Rare in chat, common in databases.

Storage and retrieval

With (conversation_id, seq) as the primary key in a wide-column store, "last 50 messages" is a reverse range scan and "messages after seq X" is a forward range scan. Both are O(log N + page size) and independent of total conversation size. Pagination uses keyset pagination on seq, not offset — offset pagination requires scanning from the beginning.

Delivery ordering

Each message carries its seq when fanned out. The recipient's gateway sends it over the WebSocket in whatever order it receives it. The client is responsible for ordering: it maintains a per-conversation sorted buffer and a last_displayed_seq watermark. On receiving a message with seq = last + 1, it appends and advances. On receiving seq > last + 1, it holds the message in the buffer and fetches the gap from the server before displaying. On receiving seq ≤ last, it drops the duplicate. This makes the display deterministic regardless of network order.

Ordering trade-offs

Strict per-conversation ordering limits throughput to one authority per conversation. For most conversations this is irrelevant — chat is low-volume. For very large channels (10k+ messages/s), strict ordering is a bottleneck, and the system must either accept slight reordering within a time window or partition the conversation into sub-streams. Most systems accept that the client's buffer can handle out-of-order delivery, so the server does not need to guarantee strict delivery order — only strict sequence assignment.

Cross-conversation ordering

Not required and not provided. Each conversation is an independent ordering domain. A user's messages in conversation A are not ordered relative to their messages in conversation B; there is no meaningful relationship. The only cross-conversation ordering that matters is the user's user_conversations index (last message per conversation), which uses a separate timestamp and is eventually consistent.

Common Pitfall

Ordering by client timestamp. Two phones with clock skew of 30 seconds will show messages in the wrong order, and a message sent at 10:00:05 on a slow clock can appear before a message sent at 10:00:00 on a fast clock. The server-assigned seq is the only correct ordering authority.

10

How would you preserve conversation order if two participants send a message at exactly the same time?

Short Answer

Both messages reach the server, and whichever gets the lower seq is displayed first. There is no "correct" answer to who was first — only a requirement that all participants agree. The server serializes the two writes through a single authority per conversation, so the order is consistent across all devices, even if it differs from the wall-clock time on either phone.

The race

Alice and Bob both type "hi" and hit send at the same millisecond. Alice's message travels through her gateway, her region's chat service, and its storage layer. Bob's travels through his. The two paths have different lengths and different load, so the messages can be persisted in either order. The server must assign a seq to each, and the order of those assignments is the conversation order — for everyone.

Serialization mechanisms

  • Single-writer per conversation. Consistent hashing on conversation_id routes both messages to the same chat-service instance. That instance processes them in arrival order (a single-threaded queue per conversation) and assigns seq atomically. The first to arrive at the instance wins. This is the cleanest design and what most systems do.
  • Storage-layer atomic counter. A per-conversation counter with a lightweight transaction. Two concurrent increments are serialized by the storage engine; the one that gets 42 wins over the one that gets 43. Correct, but slower.
  • Hybrid logical clock with tiebreaker. Each message carries an HLC (timestamp + logical counter) and a node ID. The order is (HLC, node ID). Both messages might have the same HLC; the node ID breaks the tie deterministically. No coordination, but the client must understand the composite ordering.

What the client sees

Both clients receive both messages with their assigned seq values. They display them sorted by seq, so both devices show the same order. The user perceives no race — one message simply appears before the other, which is indistinguishable from a few milliseconds of network jitter. The important property is consistency across devices: Alice's phone and Bob's phone show the same order, even if that order differs from the phones' local clocks.

The read-receipt race

A related race: both users mark the conversation read at the same time. Each update is a monotonic upsert of read_seq — the higher value wins. If Alice's device writes 42 and Bob's writes 41 concurrently, the server takes 42 (the max). A duplicate or out-of-order read report is a no-op, so the race is harmless. This is an example of designing each field to be commutative or monotonic so that concurrent updates converge without coordination.

Edge case: same gateway, same batch

If both messages arrive at the same gateway in the same batch, the gateway assigns seq values in the order it processes the batch. That order is arbitrary but consistent — both messages get distinct seqs, and the assignment happens before fan-out, so both recipients see the same order. The gateway does not need to coordinate with other gateways because the conversation is pinned to one gateway.

Idempotency interaction

If Alice's message is retried (network timeout), the client_uuid deduplication prevents a second seq from being assigned. The retry returns the original seq. Without idempotency, a retried send could appear twice in the conversation and consume two sequence numbers, breaking the one-message-per-send invariant.

The design principle

Simultaneous sends are not a correctness problem if you accept that the order is determined by the server, not by the users' clocks. The requirement is agreement, not truth. Every participant must see the same order; no participant needs to see the order they privately believe is correct. This is the same principle behind Lamport clocks and consensus in general: define an arbitrary but consistent order, and everyone follows it.

Interview Framing

Say: “There is no ground truth for simultaneous sends; the requirement is consistency, not correctness. I'll serialize per conversation with a single writer and assign seq there, so both devices see the same order regardless of clock skew.” That shows you understand the problem is about agreement, not about time.

11

How do you guarantee a message is never lost — but also never delivered twice?

Short Answer

The message log provides durability: the sender is acked only after the message is replicated. The delivery path provides at-least-once delivery: duplicates are inevitable, so the client deduplicates by seq. Sends are made idempotent with a client_uuid. Together these give exactly-once effects, which is the strongest achievable guarantee — strict exactly-once delivery is impossible in a distributed system.

Durability on the write path

The sender's ack means "persisted", not "delivered". The chat service writes the message to a replicated store (replication factor 2+ within the region, or a quorum) and returns the ack only after the write is durable. If the service crashes after the write but before the ack, the sender retries; the idempotency key ensures the retry is a no-op. If the service crashes before the write, the retry creates the message. Either way, a message that was acked is durable.

At-least-once delivery

After persistence, the message is fanned out. The delivery path can produce duplicates in several ways: the WebSocket send succeeds but the ack is lost (so the gateway retries); the client reconnects and fetches the same message from the log; a push and a WebSocket deliver the same message to the app. Duplicates are a normal part of the system, not a bug.

Client-side deduplication

The client maintains a per-conversation last_seen_seq. On receiving a message:

  • seq ≤ last_seen_seq → duplicate, drop.
  • seq = last_seen_seq + 1 → append, advance watermark.
  • seq > last_seen_seq + 1 → gap; buffer the message, fetch the missing range from the server, merge, then display in order.

The watermark is persisted locally (SQLite, IndexedDB), so it survives app restarts. This makes the client idempotent regardless of how many times a message is delivered.

Idempotent sends

Each message carries a client-generated client_uuid that is stable across retries. The server maintains a dedup table keyed by (sender_id, client_uuid) with a TTL (long enough to cover any plausible retry, e.g., 24 hours). On receiving a send, the server checks the dedup table; if present, it returns the existing seq without writing. This prevents a retried send from producing a second message and a second seq.

Read receipts and delivery receipts

The read_seq and delivered_seq watermarks are monotonic: the server takes the maximum of the incoming value and the stored value. A duplicate or out-of-order receipt update is a no-op. This makes the receipt path naturally idempotent without a separate dedup mechanism.

Push duplicate handling

A message may be delivered via WebSocket, then again via a push-triggered fetch. The client's dedup by seq handles this: the second delivery has a seq that is already in the local store, so it is dropped. The push itself can also be deduplicated if it carries a message_id.

What "exactly-once" really means

In a distributed system, exactly-once delivery to a client is impossible: if the client crashes after processing a message but before acking, the system cannot know whether to redeliver. The achievable guarantee is at-least-once delivery + idempotent processing = exactly-once effects. This is what every serious messaging system actually provides, even when the documentation says "exactly-once". The user-visible effect is that every message appears exactly once in the conversation, which is what matters.

Failure modes and their handling

Common Pitfall

Relying on the WebSocket delivery as the durability guarantee. The WebSocket is a best-effort channel; the message must be persisted before the sender is acked, and the recipient must be able to reconstruct state from the log alone. Otherwise a gateway crash loses messages that were "sent" but never "delivered".

A client uses WebSocket for real-time updates but also polls. How do you merge incoming events into client state so duplicates, out-of-order messages, and reconnects do not corrupt the UI?

Short Answer

The client treats the message log as the source of truth and maintains a single last_seen_seq watermark per conversation. Both the WebSocket pushes and the polling responses are inserted into a sorted buffer keyed by seq; duplicates are dropped, gaps trigger a fetch, and the UI always renders from the buffer. The two channels are just different ways of delivering the same log entries.

Why the client has two channels

The WebSocket is the primary real-time channel, but it can drop: the app is backgrounded, the network changes, the gateway fails, or the connection silently dies without the client noticing. Polling (or a fetch-on-focus request) is the fallback that catches up when the WebSocket was not receiving. A robust client uses both and reconciles them.

Client state

  • messages: a per-conversation sorted list of message objects, keyed by seq.
  • last_seen_seq: the highest contiguous seq the client has processed.
  • last_read_seq: the highest seq the user has read (for unread counts and receipts).
  • pending_fetch: a flag or range indicating a gap is being filled.

All of these are persisted locally so they survive app restarts.

The merge algorithm

Both channels call the same onMessage(seq, message) function:

  1. If seq ≤ last_seen_seq, the message is a duplicate — drop it (but still ack the delivery receipt if applicable).
  2. If seq = last_seen_seq + 1, insert, advance last_seen_seq, and flush any buffered messages that are now contiguous.
  3. If seq > last_seen_seq + 1, insert into a pending buffer and trigger a fetch for (last_seen_seq + 1 .. seq - 1). Do not display the gap-crossing message until the gap is filled.

The UI always renders the contiguous prefix of the buffer, so it never shows a gap or an out-of-order message even if the underlying delivery was reordered.

Fetch-on-gap

The fetch is an HTTP range request: "give me messages with seq > last_seen_seq, up to the gap". The server returns the range, and each message goes through onMessage, which fills the gap and flushes the buffer. Fetch is rate-limited and retried with backoff; if it fails repeatedly, the client shows a "reconnecting" indicator rather than a corrupted conversation.

Fetch-on-reconnect

When the WebSocket reconnects (after a network change or a gateway failure), the client sends last_seen_seq per conversation and fetches everything after it. This is the same range-fetch mechanism, applied to potentially a large gap. The fetch is paginated (e.g., 100 messages per request) and processed incrementally, so the UI updates as pages arrive.

Polling as a fallback

If the WebSocket is not connected (e.g., during a reconnect, or in a network that blocks WebSocket), the client polls at a low frequency (e.g., every 30 seconds) with the same last_seen_seq. The poll response goes through the same merge path, so there is no special handling. Polling is slower but ensures the client eventually catches up.

Concurrency

The client must serialize onMessage calls so that a WebSocket message and a poll response for the same seq do not both insert. The typical implementation uses a single-threaded event loop (JavaScript) or a lock (native) around the merge function. The last_seen_seq check makes duplicate insertion a no-op even if the lock is held briefly.

Reconnect storms

If the WebSocket flaps (connects and disconnects rapidly), the client must not trigger a full fetch on every reconnect. The mitigations: debounce reconnects (wait 1 second after connecting before fetching), exponential backoff on reconnect attempts, and rate-limit fetch requests. The client should only fetch if the gap is non-trivial; a reconnect that missed one message can be handled by the pending-buffer flush, not a full fetch.

Local persistence

Persisting messages and last_seen_seq in IndexedDB (web) or SQLite (mobile) means the client can render instantly on app open (from local data) and fetch only the delta. Without local persistence, every app open is a full conversation load, which is slow and wasteful. The local store is the client's replica of the log; the merge algorithm keeps it in sync with the server.

Interview Framing

Say: “Both WebSocket and polling feed the same merge function keyed by seq. Duplicates are dropped, gaps trigger a range fetch, and the UI renders from the contiguous buffer. The client's local store is a replica of the log, and the watermark is persisted so reconnects only fetch the delta.” That demonstrates you understand the client as a stateful replica, not a dumb display.

Part D — Presence, Sync & Offline Ephemeral state and the reconnection problem

13

Design the presence system for a chat app. How do you track online/offline status at scale? How do you handle flapping and stale presence?

Short Answer

Presence is a heartbeat-plus-TTL store, sharded by user, with a subscription mechanism so each client receives updates about its contacts. Flapping is handled with hysteresis and debouncing; stale entries are cleaned up by TTL expiry and a background sweeper. For large audiences, presence is scoped to friends and mutual servers, not to every user in the system.

The store

Redis (or an equivalent in-memory store) is the standard choice. Each user has a presence key: presence:{user_id} → {status, last_seen, connection_count, device_info} with a TTL of 60–90 seconds. The key is updated on connect, on every heartbeat (every 20–30 seconds), and on disconnect (explicit removal). The TTL guarantees that a crashed process eventually becomes "offline" without an explicit cleanup.

Heartbeat model

The client sends a heartbeat over the WebSocket every 20–30 seconds. The gateway updates the presence key with a refreshed TTL. If the key expires, presence is considered offline. The heartbeat interval is a trade-off: shorter means faster detection of failures but more write load; longer means less load but a longer stale window. The TTL is typically 2–3× the heartbeat interval, so a single missed heartbeat does not cause a false offline.

Flapping and hysteresis

A user on a flaky mobile connection may connect and disconnect repeatedly, generating a storm of presence updates. The mitigation is hysteresis: require N consecutive missed heartbeats (or N seconds without a heartbeat) before marking offline, and require the connection to be stable for a minimum duration before marking online. This smooths out transient disconnects. The cost is a slight delay in marking offline, which is acceptable because users do not expect instant presence transitions.

Multi-device

A user on phone and laptop has two active connections. The presence key tracks connection_count; the user is online if the count is greater than zero. When one device disconnects, the count decrements; only when it reaches zero is the user offline. The decrement must be atomic (Redis DECR or a Lua script) to avoid a race between two devices disconnecting simultaneously.

Subscriptions

For a client to see live presence, it must be notified when a contact's presence changes. The design is a per-user presence channel: when Alice's presence changes, the server publishes to a channel that Bob (a contact) is subscribed to. The subscription list is the user's contact list (or friends list). For a user with 200 contacts, the client subscribes to 200 channels — a lot of subscriptions, but manageable with a pub/sub system that supports many small channels.

Alternative: the server maintains a per-user "presence feed" — when a contact changes, the server pushes the update to the user's gateway connection. This avoids the 200-channel problem but requires the server to know the contact list and to fan out each change to the user's contacts. The right choice depends on the average contact count and the update frequency.

Coarse presence for large audiences

In a workspace or server with 100,000 members, tracking every member's presence is infeasible: 100,000 keys, 100,000 updates per heartbeat interval, and every client would need to know every other client's status. Discord's approach is to show presence only for friends and mutual servers, and to aggregate "N online" for the server. Slack shows presence only for workspace members, not for everyone in every channel. The principle is to scope presence to the audience that actually needs it, and to aggregate when the audience is too large.

Stale presence

TTL handles crashes. Explicit disconnects remove immediately. A background sweeper scans for keys that have expired (Redis handles this automatically, but a sweeper is useful for auditing and for re-publishing "offline" events if the expiry notification was missed). The sweeper also handles the case where a gateway crashed with many connections — the TTLs expire, and the presence updates are generated in a burst; the subscription mechanism must handle a burst without overwhelming clients.

Privacy

Users can disable presence or set themselves to "invisible". This is a per-user preference checked at read time — the presence entry is still maintained internally, but the subscription filter hides it. A user who appears offline but is actively messaging is a valid state (the "invisible" mode used by many apps).

Alternatives to presence

Many apps have moved from live presence to "last seen at HH:MM" because it is easier to compute, less sensitive to flapping, and less privacy-invasive. Last-seen is updated on every clean disconnect and every message, giving a useful approximation without the write load and subscription complexity of live presence. WhatsApp's design is essentially this — "last seen" rather than "online".

Scale numbers

At 100M DAU, presence is ~100M keys in Redis. At ~100 bytes per key, that is ~10 GB, which fits comfortably in a sharded cluster of 10–20 Redis nodes. The heartbeat write rate is 100M / 25 s ≈ 4M writes per second, which is significant but achievable with sharding and pipelining. The subscription fan-out is the harder problem: a single user's presence change must be delivered to potentially hundreds of contacts, so the publish rate is the heartbeat rate times the average contact count, which is much larger than the heartbeat rate itself.

Trade-off

Live presence gives the best UX but the highest write and fan-out cost, and it is unreliable on mobile. Last-seen is cheaper and more privacy-friendly but less immediate. The pragmatic default for a new product is last-seen; add live presence only for the audience that values it (e.g., gamers, customer support agents).

How do you design offline message delivery? What happens when a user comes online after being away for days?

Short Answer

Offline users have a stale last_seen_seq; the message log holds everything they missed. On reconnect, the client fetches everything after last_seen_seq, paginated and rate-limited. Push notifications are sent opportunistically to wake the app, but the log is the actual delivery mechanism. Retention policy determines how far back the fetch can go — messages older than the retention window are unavailable, which is a product decision that must be made explicitly.

Where offline messages live

They live in the normal message log, exactly like messages for online users. There is no separate "offline queue" — the log is the queue. The only difference is that an offline user's last_seen_seq is behind the log's head, so on reconnect they fetch the range they missed. This is the key insight that makes the design simple: offline is a read path, not a special write path.

The reconnect flow

  1. Client connects to a gateway, authenticates.
  2. Client sends its last_seen_seq per conversation (from local persistence).
  3. Server returns the current head seq per conversation and a paginated range of messages after last_seen_seq.
  4. Client merges the fetched messages into its local store, advances last_seen_seq, and repeats until caught up.
  5. Once caught up, the WebSocket delivers new messages in real time.

The catch-up is the same range-fetch mechanism used for gap filling (Question 12). The only difference is the size of the gap, which can be thousands of messages after a multi-day absence.

Pagination and rate limiting

A user offline for a week with 50 active conversations may have thousands of unread messages. Fetching them all at once would overwhelm the device and the server. The client fetches incrementally: the most recent conversations first, the most recent messages within each, with a page size of 50–100. The UI shows conversations as they load, and the user can scroll back for history. The fetch is rate-limited to avoid saturating the client's network or the server's read capacity.

Retention

The message log has a retention window — 30 days is common for chat, indefinite for some products. A user offline longer than the retention window cannot fetch the expired messages; they are gone. This must be a deliberate product decision, communicated to users. The alternative is cold storage (messages older than the retention window are moved to object storage and retrievable on demand), which is more expensive but allows longer retention. Most chat apps choose a compromise: recent history in the hot store, older history in cold storage, with a per-message retrieval cost.

Push during offline

Each new message for an offline user triggers a push notification (subject to batching and user preferences). The push serves two purposes: it alerts the user that there is a message, and it wakes the app to sync in the background if the OS allows. If the user does not open the app, the push has done its job; the message is still in the log for the next reconnect. Pushes are best-effort and should never be treated as the delivery mechanism.

Batching notifications

A user offline for a day with 200 new messages from 10 conversations should not receive 200 pushes. The push service batches: one push per conversation per time window ("Alice: 5 new messages"), or one summary push ("20 new messages"). The batching window is a trade-off between immediacy and notification fatigue. The client fetches the full set on open regardless.

Sync state across devices

Each device has its own last_seen_seq. A user's phone and laptop may be at different points in the conversation. Read state (last_read_seq) is per-user and synced across devices, so unread counts are consistent. The message fetch is per-device, because a device that was off for a week needs the full range while a device that was off for an hour needs a small delta.

Edge cases

  • User deleted messages while offline: the fetch returns tombstones; the client removes the messages from its local store.
  • User was removed from a group while offline: the fetch returns the removal event; the client removes the conversation or shows a "you were removed" notice.
  • Message retention expired mid-offline: the fetch returns only the available range; the client shows a "messages older than 30 days are no longer available" notice.
  • User has no local state (new device): the client starts with a fresh fetch of the conversation list and the most recent messages per conversation, not the full history.
Common Pitfall

Treating offline delivery as a separate queue that must be drained. That leads to a per-user queue that grows unboundedly and must be garbage-collected. The log-as-queue design avoids this entirely: offline users are just readers whose position is behind the head. The retention policy, not a per-user queue, bounds the storage.

How do you handle multi-device sync? How do you manage sync cursors across a user's phone, laptop, and tablet?

Short Answer

Each device maintains its own last_seen_seq per conversation — a per-device cursor into the shared message log. Read state is a separate, per-user, per-conversation watermark that is synced across all devices so unread counts are consistent. Messages sent from one device are fanned out to all of the user's devices like any other message.

Two different sync problems

Multi-device sync conflates two problems that need separate solutions:

  • Message delivery to multiple devices: if Alice sends a message from her phone, her laptop should also see it (as a sent message, not just as history). The server fans out the message to all of Alice's active connections. If a device is offline, it fetches on reconnect.
  • Read state sync: if Alice reads a conversation on her phone, her laptop's unread badge should clear. This requires a separate sync channel for read state, because read state is per-user, not per-device, and it must propagate quickly to be useful.

Per-device message cursors

Each device stores its own last_seen_seq per conversation, persisted locally. On reconnect, the device fetches from its own cursor. A device that was off for a week fetches a week of messages; a device that was off for a minute fetches a minute. There is no need to coordinate cursors between devices — they are independent readers of the same log.

Read state sync

The read state is last_read_seq per conversation per user, stored on the server. It is monotonic — the server takes the maximum of the incoming and stored values, so out-of-order updates are safe. When a device updates the read state, the server:

  1. Upserts the last_read_seq.
  2. Publishes a "read state updated" event to all of the user's active connections.
  3. Each device receives the event and updates its local unread count.

This is a small, separate fan-out channel per user. It rides on the same WebSocket as messages but is a distinct event type. The read state channel is much lower volume than the message channel (one event per read action, not per message), so it is cheap.

Sent message echo

When a device sends a message, the server persists it and fans out to the recipients — and to the sender's other devices. The sending device shows the message immediately (optimistic echo) and then reconciles with the server's ack (which includes the assigned seq). The other devices receive the message via the normal fan-out path and display it as a sent message from Alice. There is no special "sync sent messages" mechanism; the message is just another message in the log.

Deduplication across devices

If Alice sends a message from her phone, the server assigns a client_uuid. The phone shows the message optimistically with that UUID. When the server fans out, the phone receives its own message back; it deduplicates by client_uuid (not by seq, because the phone has not seen the seq yet). The laptop receives the message without the UUID collision, so it treats it as a new message. Both devices display the same message with the same seq, but only the phone had the optimistic duplicate to reconcile.

New device login

A brand-new device has no local state. It does a full sync: fetch the conversation list, the most recent N messages per conversation, and the current read state. It does not fetch the full history — that would be slow and wasteful. Older history is fetched on demand (scroll back). The new device's cursor starts at the current head, so it will receive new messages in real time but will not automatically fetch old history beyond the initial page.

Device removal

When a device is logged out, its connection is closed and its cursor is discarded. It is removed from the fan-out list for the user. Any future messages are not delivered to it. The read state on the server is unchanged; the device simply stops syncing.

Conflict handling

Read state is monotonic (max), so conflicts are resolved by taking the higher value. Sent messages are idempotent by client_uuid, so a retried send from a device does not create a duplicate. Drafts are the one state that is harder — a draft written on the phone and a draft written on the laptop are both valid and cannot be merged automatically. Most apps keep drafts per-device, not synced, to avoid the conflict.

The trade-off

Syncing read state adds a small real-time channel and some server state, but it is necessary for a consistent multi-device experience. Without it, a user sees unread badges on one device after reading on another, which feels broken. The cost is small compared to the message channel, and the benefit is a coherent experience across devices.

Interview Framing

Say: “Each device is an independent reader of the message log with its own cursor. Read state is separate, per-user, and monotonic, synced to all devices over the same WebSocket. Sent messages are just messages — they go through the normal fan-out, including to the sender's other devices.” That separates the two sync problems and shows you understand each one.

Part E — Encryption & Security What E2E encryption makes possible, and what it makes impossible

16

How does end-to-end encryption work in a chat system? How do you share encryption keys between client and server?

Short Answer

The server never has the keys. Each user has a long-term identity keypair and a set of prekeys published to the server. To start a conversation, Alice fetches Bob's prekey bundle, performs a Diffie–Hellman key exchange, and derives a shared secret. Messages are encrypted with per-message keys derived from that secret via a ratchet. The server sees only ciphertext and public keys.

Key material per user

  • Identity keypair — long-term, used to prove identity. Curve25519 in Signal's protocol.
  • Signed prekey — a medium-term keypair, signed by the identity key, used to initiate sessions.
  • One-time prekeys — a pool of keypairs, each used once, consumed when someone initiates a session with this user. They provide forward secrecy for the initial handshake.

The public halves of all of these are uploaded to the server. The private halves stay on the device. The server is a public-key directory, not a participant in the encryption.

Initiating a session

Alice wants to message Bob. She fetches Bob's prekey bundle from the server (identity key, signed prekey, one one-time prekey). She verifies the signature on the signed prekey using Bob's identity key. She then performs the X3DH (Extended Triple Diffie–Hellman) handshake: three DH operations combined into a single shared secret. The server relays the bundle but never sees the shared secret.

The ratchet

The shared secret is used to derive a chain of per-message keys via the Double Ratchet. Each message uses a key derived from the previous one; after sending, the sender's chain advances; after receiving, the receiver's chain advances. A new DH exchange happens periodically (on each round trip) to provide post-compromise security. The result is forward secrecy (past messages cannot be decrypted if the current key is compromised) and break-in recovery (future messages become secure again after a compromise).

Group chat

Group encryption is harder because the same plaintext must be decryptable by all members without a shared long-lived secret that leaks. The two main approaches:

  • Sender keys (Signal): each member generates a sender key — a symmetric key plus a chain key — and distributes it to all other members using pairwise encrypted messages. To send, a member encrypts once with their sender key; all members can decrypt. When membership changes, the sender key must be rotated and redistributed. The advantage is O(1) encryption per message; the cost is O(N) distribution per sender-key rotation.
  • Group key agreement (MLS): the IETF Messaging Layer Security protocol uses a tree-based key agreement to distribute a group key in O(log N) per membership change, with forward secrecy and post-compromise security. This is the modern approach for large groups.

Multi-device

A user's other devices need to decrypt messages sent to them. Signal uses a "sync key" — a pairwise encrypted message from the primary device to each linked device, carrying the keys needed to decrypt the user's own messages. When a new device is linked, it receives the sync key and can then decrypt everything.

What the server sees

  • Public identity keys and prekey bundles (a public directory).
  • Encrypted message payloads (ciphertext).
  • Metadata: who sent to whom, when, message size, delivery status.
  • It does not see plaintext, sender keys, or the shared secret.

Metadata is the limit of E2E encryption. The server knows the conversation graph even if it cannot read the content. Signal's "sealed sender" mitigates this by hiding the sender's identity from the server (the recipient's device can still verify it), but it is complex and not universal.

Backups

If the server cannot read the messages, it cannot back them up in a recoverable form. Two approaches: the user sets a backup password and the device encrypts the backup with a key derived from it (WhatsApp's approach — the server stores ciphertext, the user is responsible for the password); or no cloud backup at all, and losing the device loses the history (Signal's default). The choice is a product decision, but the E2E guarantee requires that the server never holds the decryption key.

The cost

E2E encryption adds CPU cost on the client (DH operations, ratchet updates) and on the server (larger ciphertext payloads, prekey distribution). It adds complexity to multi-device, group management, and backups. It makes search, moderation, and spam detection impossible server-side. And it makes key verification a UX problem — users must verify safety numbers to be sure they are talking to the right person, which almost nobody does. These costs are real, and a product that adopts E2E must accept them.

Trade-off

E2E encryption is a strong privacy property that fundamentally limits what the server can do. The design must decide which data is E2E (direct messages, small groups) and which is not (public channels, searchable content), because applying E2E to everything makes search, moderation, and compliance impossible.

17

What are the implications of end-to-end encryption on server-side fan-out and search? Can the server search encrypted messages?

Short Answer

Fan-out is unaffected — the server routes ciphertext exactly like plaintext, and group fan-out still works because the group key is distributed to members, not to the server. Search is fundamentally broken: the server cannot index what it cannot read. The options are client-side search only, a user-opt-in unencrypted backup, or searchable encryption (rarely deployed). Moderation and spam detection are similarly limited.

Fan-out

The fan-out path does not need to read the message. It reads the recipient list (which is metadata, not encrypted content) and sends the ciphertext to each recipient. For a group, the sender encrypts once with the group key and fans out the ciphertext; each member decrypts with the group key they already have. The server's fan-out cost is identical to the unencrypted case. The only difference is that the payload is larger (encrypted content plus headers), which is a marginal bandwidth cost.

Why server-side search is impossible

Full-text search requires tokenizing the content, building an inverted index, and querying it. All three require plaintext. With E2E encryption, the server has ciphertext; tokenizing and indexing it produces an index of encrypted tokens, which is useless for querying. The server cannot even determine whether a message contains a particular word, because the ciphertext is indistinguishable from random bytes without the key.

The four options

ApproachHow it worksTrade-off
Client-side search Each device decrypts its local store and indexes it locally (SQLite FTS, IndexedDB) Only searches messages the device has; new device has no history; does not scale to full archive
Unencrypted backup Messages are backed up to the server in plaintext (or with a server-held key) for search Breaks the E2E guarantee; the server can read everything; subject to legal requests
User-encrypted backup Backup is encrypted with a user password; the device decrypts for search Search works only on the device after decrypting the backup; requires the password; slow
Searchable encryption Cryptographic scheme that lets the server match encrypted tokens Leaks access patterns; expensive; complex; not widely deployed in messaging

What Signal does

Signal has no server-side search. The client can search its local message store, which contains everything the device has received. A new device starts with no history and no search. Signal explicitly does not offer a cloud backup, so losing the device loses the history. This is a deliberate choice: search is sacrificed for the E2E guarantee.

What WhatsApp does

WhatsApp offers end-to-end encrypted backups with a user-set password. The backup is encrypted with a key derived from the password (and, in newer versions, with a hardware-backed key), stored in the user's cloud storage. Search happens on the device after decrypting the local store, and a restored backup gives the new device the history to search. The trade-off is that a user who forgets the password loses the backup.

What Slack does

Slack is not end-to-end encrypted for channels, precisely because search and compliance are core features. Slack offers enterprise key management (EKM) where the customer holds the key, but Slack still processes plaintext during indexing. This is a different model — the customer controls the key, but the platform is in the trust boundary. It is not E2E in the Signal sense.

Moderation and spam

E2E breaks server-side content moderation. The server cannot scan for abuse, spam, or illegal content. The mitigations: client-side ML (on-device classification, which can be evaded), user reporting (which forwards decrypted messages to the server, with the user's consent), and network-level signals (message frequency, account age). All are weaker than server-side moderation. Platforms that adopt E2E must accept this and design their abuse-prevention strategy accordingly.

Compliance and legal requests

E2E encryption conflicts with legal intercept requirements in many jurisdictions. A platform that cannot decrypt cannot comply with a subpoena for message content. This is a legal and political problem as much as a technical one. Platforms typically respond by (a) providing metadata only, (b) offering a user-opt-in unencrypted mode, or (c) exiting markets with incompatible requirements.

The design principle

E2E encryption is not a feature you add to an existing system; it is a system-level constraint that determines what the system can and cannot do. The design must be scoped: apply E2E to the content where the privacy guarantee is essential (direct messages, small groups) and leave the content where search, moderation, or compliance is essential (public channels, support conversations) unencrypted, with clear user communication about which is which. Applying E2E to everything and then trying to add search later does not work.

Common Pitfall

Adopting E2E encryption for a product that already has server-side search and moderation, without a plan for what happens to those features. The features break, the product team is surprised, and the rollback is awkward. E2E must be designed in from the beginning, with a clear boundary between encrypted and unencrypted content.
