Part A — The Strategy Write vs read fan-out, and the threshold between them

1

Compare fan-out-on-write vs fan-out-on-read for a messaging system. When would you choose each? What are the latency and storage trade-offs?

Short Answer

Fan-out-on-write (push) copies the message to every recipient's inbox at send time — fast reads, expensive writes, storage proportional to recipients × messages. Fan-out-on-read (pull) stores the message once and lets each recipient read it from the shared log — cheap writes, slower reads, storage proportional to messages. The choice is driven by the read-to-write ratio, the recipient count, and whether the recipient is online.

Fan-out on write in detail

Alice sends a message to a 10-member group. The chat service writes the message to each member's inbox — 10 rows in a per-user inbox table, each pointing to the message. When Bob opens the group, he reads his own inbox (one query, sorted by timestamp) and sees the message without any fan-in. This is fast for reads because the work was done at write time.

The cost is storage and write amplification. A 100-member group generates 100 inbox rows per message. At 100 messages per second, that is 10,000 rows/s — manageable. At 10,000 members, it is 1M rows/s — not manageable. The write cost scales linearly with group size, which is the fundamental limitation.

Fan-out on read in detail

Alice sends a message to the same group. The chat service writes it once, to the group's message log. When Bob opens the group, he queries the group's log directly — no per-user inbox. The read is a range query on the group's conversation, which is fast if the log is partitioned by group. This is cheap for writes because the work is done once, regardless of group size.

The cost is on the read path. Bob must know which groups to read, and for a feed he must merge across many groups. A user in 500 groups must query 500 logs (or one fan-in query) to build their timeline. This is the "fan-in" problem — the mirror of write fan-out. It is manageable if the user reads one group at a time (chat) but expensive if the user reads across all groups (a unified inbox or feed).

Why chat usually uses write fan-out for small groups

Chat is read-heavy and read-latency-sensitive. The user opens a conversation and expects the messages instantly. A write fan-out makes the read a single lookup. The write cost is acceptable because chat groups are small (median group size is 3–10). The 10-member group with 100 messages/day generates 1,000 inbox rows per day per member, which is trivial.

Why large channels must use read fan-out

A 10,000-member channel generates 10,000 inbox rows per message. At 10 messages per second (a busy channel), that is 100,000 rows/s — approaching the limit of a single database shard, and growing. At 100,000 members, it is 1M rows/s, which is not achievable on any single-node database. The write fan-out cost dominates, and the only scalable option is read fan-out: store the message once, let each of the 100,000 members read it from the shared log when they open the channel.

The threshold

The transition point depends on the system's write capacity and the read-to-write ratio, but the practical guidance is:

  • ≤ 1,000 members: write fan-out. The write cost is manageable, and the read latency is best.
  • 1,000–10,000 members: hybrid. Fan-out to online members (they get the message instantly); read fan-out for offline members (they fetch on reconnect). This is the chat industry's standard compromise.
  • 10,000+ members: read fan-out. The write cost of per-member fan-out exceeds any reasonable capacity, and the reads can be served from the log.

The offline interaction

Write fan-out has a significant advantage for offline users: the message is already in their inbox, so when they come online they read their inbox and see everything. Read fan-out requires them to fetch from the log on reconnect, which is more work but equivalent from the user's perspective if the fetch is fast. The offline case does not fundamentally change the trade-off, but it does affect the implementation complexity: write fan-out needs a per-user inbox (storage), read fan-out needs a per-user last-seen cursor (cheap).

Trade-off

Write fan-out moves the cost from read time to write time, and from storage to latency. Read fan-out moves it the other way. The right answer is per-group: small groups write fan-out, large groups read fan-out, and a threshold (or a hybrid) in between. A system that uses one strategy for all groups either wastes storage on small groups or collapses on large ones.

Interview Framing

Say: "Fan-out on write for groups under 1,000, fan-out on read for larger. The threshold is where the per-message write cost exceeds the read cost of fetching from the log. I'll use a hybrid in the middle: write fan-out to online members, read fan-out for offline." That names the strategy, the threshold, and the hybrid.

2

A message sent to a 10,000-member channel generates 10,000 delivery events. How do you design this without overwhelming any single server?

Short Answer

Don't fan out at all — use read fan-out. Store the message once in the channel's log, and let members fetch it when they open the channel. For real-time members, send a lightweight notification signal (not the message) to their gateway, and they fetch the message from the log. The per-message work is O(1), not O(members).

Why per-user fan-out fails at 10,000

If the chat service tries to deliver the message to every member individually, it must do 10,000 lookups (registry + gateway) and 10,000 sends. At 1 message/second, that is 10,000 sends/s. At 100 messages/second, it is 1M sends/s. No single chat-service instance can do this; the fan-out worker fleet must scale with the channel's message rate × member count, which is unbounded. The work is fundamentally O(members), and no amount of horizontal scaling makes O(10,000 × 100/s) manageable for every channel.

The second problem is duplicate delivery. If the message is delivered to all 10,000 members, and a member is connected on 2 devices, that is 20,000 deliveries. If the fan-out retries (because a gateway is slow), it is 20,000 more. The system's work is proportional to delivery attempts, not to the message, which is the wrong scaling axis.

The read fan-out design

  1. Store once. The message is written to the channel's log: (channel_id, seq) keyed, sharded by channel_id. One write, one storage location.
  2. Broadcast a signal, not the message. The chat service publishes a lightweight event to the channel's subscribers: "channel X has a new message at seq Y". This is a fan-out of the signal, not the message — the signal is small (a few bytes) and does not need to be stored per-member.
  3. Online members fetch. A member's gateway receives the signal and knows the member's last_seen_seq for that channel. If last_seen_seq < seq, it fetches the message from the log and delivers it to the member. If the member is already up to date, the signal is a no-op.
  4. Offline members fetch on reconnect. A member who was offline does not receive the signal (or receives it as a push notification). On reconnect, they send last_seen_seq and fetch everything after it.

How the signal fan-out scales

The signal fan-out is still O(members) in the naive design — the chat service must notify 10,000 members that there is a new message. But the signal is much cheaper than the message: it is a few bytes, not a full message; it can be coalesced (one signal per member per second, not per message); and it can be delivered via a pub/sub channel that the gateway subscribes to per-member.

Better still: the signal can be a sequence number rather than a per-member delivery. The channel's current seq is a single value that changes on every message. The gateway can poll or subscribe to the channel's "current seq" and compare it with each connected member's last_seen_seq. Members who are behind fetch; members who are caught up do nothing. The per-message fan-out is O(1) (update the channel's seq), and the per-member work is only for members who are actually behind.

The gateway's role

Each gateway holds connections for members. When the channel's seq advances, the gateway needs to know which of its connected members are subscribed to the channel. This is a per-gateway subscription table: channel_id → set of user_ids. When the seq advances, the gateway iterates its subscribers, checks each member's last_seen_seq, and fetches for the ones who are behind. The gateway's work is proportional to its own connected members who subscribe to the channel, not to the channel's total members. Across the fleet, the work is O(members × fraction online), which is much smaller than O(members).

The batching optimization

If 10,000 members are online and all are caught up, the channel receives 100 messages per second, and the gateway processes 100 signals per second per member — 1M signal checks per second. This is a lot of CPU. The optimization: coalesce the signals. Instead of one signal per message, the gateway checks the channel's seq periodically (e.g., every 100 ms) and fetches the delta for each behind member. The per-member fetch is one batch, not 100 individual fetches. The signal rate drops from 100/s to 10/s, and the fetch is more efficient.

The push fallback

For offline members, the signal is a push notification ("New message in channel X"). The push is coalesced (one push per channel per hour, not per message) and the client fetches on open. This is the same pattern as Section 4 (notifications) — the push is a hint, not the message.

What the design actually costs

OperationCostScaling
Write the messageOne row in the channel logO(1) per message
Update channel seqOne counter incrementO(1) per message
Signal online membersPer-gateway subscription checkO(online subscribers) per gateway
Fetch for behind membersOne batch fetch per memberO(behind members)

The per-message cost is O(1) plus O(online subscribers per gateway), which is bounded by the gateway's connection count. A gateway with 500k connections has at most 500k members to check, not 10,000 per channel per message. The total work scales with the fleet's connection count, not with the sum of all channel memberships.

Common Pitfall

Trying to fan out the full message to 10,000 members. The per-message work is O(members), and no horizontal scaling makes it manageable. The fix is not more workers — it is a different strategy: store once, signal, fetch on demand.

3

For very hot groups (10,000+ concurrent users), is per-user fan-out the wrong abstraction? What alternative would you propose?

Short Answer

Yes — per-user fan-out is the wrong abstraction above a few thousand members. The right abstraction is a broadcast channel: the message is written once to a shared log, and clients subscribe to the channel and pull from it. The gateway's job is to serve the channel's log to its connected subscribers, not to deliver individual messages. This is how IRC, Discord's largest servers, and live-streaming chat work.

The abstraction shift

Per-user fan-out models the channel as a set of inboxes, each receiving a copy. The model works for small groups because the inbox count is bounded. For 10,000+ members, the inbox count is the problem: the channel becomes a fan-out engine whose cost is O(members) per message, and the total cost is O(sum of members across all channels) — which is unbounded as the product grows.

Broadcast models the channel as a single log, and members as readers of that log. The cost of a message is O(1) — one write — regardless of member count. The read cost is per-member, but it happens on demand (when the member opens the channel) rather than on every message. This is the same shift as fan-out-on-read, but taken further: the channel itself becomes the unit of delivery, not the member.

The broadcast channel design

ComponentRole
Channel logAppend-only log keyed by (channel_id, seq), sharded by channel_id. One copy of the message.
Channel seqA monotonic counter per channel, incremented on every message. The head of the log.
Subscription registryWhich members are subscribed to which channels. Per-member, per-channel.
Gateway subscription tablePer-gateway: which of its connected members subscribe to which channels.
Channel broadcast topicA pub/sub topic per channel (or per shard of channels) that the gateways subscribe to for "new message" signals.
Client cursorPer-member, per-channel last_seen_seq.

The flow for a new message

  1. The sender's message is written to the channel log (seq N).
  2. The channel's seq is incremented to N.
  3. A signal is published to the channel's broadcast topic: "channel X is at seq N".
  4. Every gateway subscribes to the broadcast topics for channels its members are in. On receiving the signal, the gateway iterates its subscribers to channel X, checks each one's last_seen_seq, and for those behind, fetches the delta from the log and sends it over the socket.
  5. The gateway updates the member's last_seen_seq (or lets the client update it).

Why this is not the same as per-user fan-out

The gateway does not "deliver the message to each member". It serves the channel's log to its subscribers. The distinction matters in three ways:

  • Multiple members share the fetch. If 100 of the gateway's members are in channel X, the gateway fetches the delta once and sends it to all 100. The log read is shared, not per-member.
  • Members who are behind get the whole delta. A member who has been offline for 5 minutes receives all messages since their cursor, not just the newest. The gateway fetches the range once and sends it to the member.
  • The gateway's work scales with its own connections, not the channel's total members. A gateway with 500k connections and 10k of them in channel X does 10k sends, not 10,000,000 sends. The other 990k members are on other gateways (or offline).

The subscription registry

The registry tracks which members are subscribed to which channels. For a 10k-member channel, this is 10k entries. For a user in 100 channels, it is 100 entries. The registry is sharded by user_id for "what channels am I in?" queries and by channel_id for "who is in this channel?" queries. Both are needed: the first for the client's channel list, the second for the gateway's subscription table.

Broadcast topic scaling

If every channel has its own broadcast topic, the number of topics equals the number of channels, which is unbounded. Instead, use a sharded broadcast topic: hash channel_id to a topic partition, and the gateway subscribes to the partitions it needs. The signal is a small message (channel_id, seq), and the gateway's consumer processes it in batches. This is the standard pattern for "notify many subscribers of a change" at scale.

Where per-user fan-out is still right

Small groups — 1-on-1, family groups, project channels — benefit from per-user fan-out because the inbox model is simpler and the read is a single lookup. The threshold is where the per-message write cost exceeds the per-read fetch cost, and it depends on the message rate and member count. For a 10-person group at 10 messages/day, per-user fan-out is 100 writes/day, which is nothing. For a 10,000-person channel at 10 messages/second, per-user fan-out is 100,000 writes/s, which is a different problem entirely.

Discord's and Slack's approach

Discord uses a hybrid: small servers get per-user fan-out (each member has an inbox), and large servers use read fan-out (members fetch from the channel log). The threshold is around a few thousand members. Slack uses read fan-out for all channels and a per-user read model (the "channel list" with unread counts) that is maintained separately. Both systems converge on the same principle: the channel log is the source of truth, and the delivery strategy is chosen per channel based on size.

Trade-off

Broadcast channels are cheaper per message but more complex per read (the client must fetch and merge, and the gateway must serve ranges, not single messages). Small groups are simpler per read but more expensive per message. The right answer is per-channel: small groups use per-user fan-out, large channels use broadcast.

Part B — Group Scale, Storage & History From 3 members to 100,000, and how the history is kept

4

How does group size affect the fan-out design? Contrast a 3-person chat with a 100,000-member broadcast channel.

Short Answer

Every order of magnitude changes the design. A 3-person chat is a per-user inbox with push delivery; a 100,000-member channel is a shared log with pull delivery and a broadcast signal. The fan-out strategy, the storage model, the read path, the presence model, and the notification model all change as the group grows.

3-person chat — the simplest case

Two people talking, or a small family group. The chat is a per-user inbox: each message is written to all participants' inboxes. The inbox is small, the read is a single lookup, and the real-time delivery is a WebSocket push. The presence is live (each participant sees the other's online status). Read receipts are exact ("Alice read at 10:42"). The system can be a single database with no sharding, and it will scale to millions of such conversations because each is independent.

100-person group — the transition begins

A work channel, a large family, a community group. The per-user inbox is still feasible (100 copies per message), but the storage and write cost are noticeable. Presence is still live but expensive (100 users × presence updates). Read receipts become aggregate ("read by 40") because tracking 100 exact receipts per message is too much. Notifications are batched (one push per group per hour, not per message). The design is still write fan-out, but with optimizations for the larger scale.

10,000-member channel — the hybrid threshold

A large community, a public channel, a support forum. Per-user fan-out is now the dominant cost: 10,000 copies per message at any meaningful message rate is infeasible. The design switches to read fan-out for offline members and a signal-plus-fetch for online members. The gateway subscribes to the channel's broadcast topic, and members fetch from the log. Presence is aggregate ("12,000 online") or scoped (only for the user's friends). Read receipts are dropped or aggregate. Notifications are coalesced or dropped entirely for non-mentions.

100,000-member broadcast — the broadcast model

An announcement channel, a live event, a news feed. There is no per-user inbox — the channel's log is the only storage. Members read the log when they open the channel, and the push notification is a single broadcast to all subscribers (via APNs/FCM topic, not per-device). The write is O(1). The read is per-member on demand. Presence is "N watching" or nothing at all. Read receipts are not tracked. The system is essentially a publish-subscribe system with a durable log, not a chat system.

What changes at each transition

  • 3 → 100: batching, aggregate receipts, presence scoping. Storage and write cost become noticeable but are still manageable with a single database.
  • 100 → 10k: the fan-out strategy changes from write to hybrid. The storage model changes from per-user inbox to shared log. Presence becomes aggregate. This is the biggest architectural change.
  • 10k → 100k: the hybrid becomes pure read fan-out. Notifications become broadcast rather than per-member. Presence and receipts are dropped. The system is a broadcast log, not a chat.

The threshold is not just size — it is activity

A 100,000-member channel with 1 message/day is cheap even with per-user fan-out (100,000 writes/day is manageable). A 1,000-member channel with 100 messages/second is expensive (100,000 writes/s is not). The threshold depends on the product of size and activity, not size alone. The design must measure the actual write rate, not just the member count, and choose the strategy based on the total cost.

Mixed systems

A real product has all four sizes simultaneously. The system must support per-user inboxes for small groups and shared logs for large channels, with a routing layer that picks the strategy based on the channel's size. This is more complex than a single strategy, but it is the only way to serve both ends of the spectrum efficiently. The design decision is where to put the threshold and how the two systems share the message store.

Interview Framing

Say: "The strategy changes with group size. Small groups get per-user inboxes with write fan-out; large channels get a shared log with read fan-out. The threshold is where the per-message write cost of fan-out exceeds the per-read fetch cost, typically around 1,000–10,000 members depending on activity." That names the spectrum and the decision criterion.

5

Where do you store group messages? How do you serve history for a large group efficiently?

Short Answer

Store messages in a sharded, time-ordered log keyed by (group_id, seq), partitioned by group_id. Reads are range scans on seq, which is efficient for "last N messages" and "messages after seq X". For a large group, the log is on a wide-column store (Cassandra, ScyllaDB) or a partitioned PostgreSQL table, and the history is served by paginating on seq, not offset. Old history is tiered to cold storage.

The storage model

StoreKeyPurpose
Message log(group_id, seq)The message content, sender, timestamp, media references
Group metadatagroup_idName, created_at, last_message_at, member count
Membership(group_id, user_id)Who is in the group, role, joined_at
Per-user cursor(user_id, group_id)last_seen_seq, last_read_seq
Per-user group list(user_id, group_id)Last message preview, unread count

The message log is the primary store, sharded by group_id so all messages for one group are on one shard. The seq is monotonic per group, assigned by a per-group counter (or a distributed sequence). The key order (group_id, seq) means a range scan on seq returns the messages in order, which is exactly what the read path needs.

The read paths

  • Last N messages (open channel): a reverse range scan on seq, limit N. O(log n + N) where n is the total messages in the group. Fast regardless of group size.
  • Messages after seq X (catch-up): a forward range scan from X. O(log n + delta). Fast if delta is small; for a large delta, paginate in batches.
  • Messages before seq X (scroll back): a reverse range scan ending at X. Paginated.
  • Search (find a message): not on the log — the log is ordered, not indexed. Search uses a separate index (Elasticsearch) fed by CDC.

Pagination

The standard is keyset pagination on seq, not offset pagination. The client sends last_seq and the server returns the next N messages after (or before) it. This is O(N) regardless of how deep into the history the user scrolls, and it is stable (new messages do not shift the page). Offset pagination (LIMIT N OFFSET K) requires scanning K rows, which becomes unusable at deep offsets in a large group.

Sharding a large group's history

A group with millions of messages is a large partition. In a wide-column store, the partition is per group, and a very large group can exceed a single node's capacity. The solutions:

  • Time-based sub-partitions: split the group's log into monthly (or weekly) partitions: (group_id, year_month, seq). The read for "recent messages" touches only the current partition; the read for "old messages" touches the archive partition.
  • Seq-range sub-partitions: split at fixed seq boundaries (e.g., every 1M messages). The read for a specific range touches only the relevant sub-partition.
  • Offload cold history: messages older than 90 days are moved to object storage (Parquet files), and the log retains only recent messages. The read for old history is a different, slower path.

The cold-history path

For very large groups with long history, keeping all messages on the hot store is expensive. The design is tiered:

TierStorageAccessRetention
HotWide-column store (Cassandra)Recent messages, fast0–90 days
WarmObject store (S3), columnar formatOlder messages, slower90 days – 2 years
ColdGlacier / archiveVery old, on demand2+ years

The client's scroll-back reads from hot first, then warm, then cold. The transition is transparent (the server routes by seq range). The cost is the cold-read latency (seconds for Glacier), which is acceptable for very old history that the user rarely accesses.

Media storage

Media (images, videos, files) is not stored in the message log. The message holds a reference (object key, thumbnail URL, dimensions), and the media is in object storage (S3) served through a CDN. The log is small and fast; the media is large and cached. This separation is essential — a message with a 10 MB video would make the log unusable if the video were stored inline.

Deletion and retention

"Delete for me" removes the message from the user's local store and adds a tombstone in the user's cursor; the message remains in the log for other users. "Delete for everyone" writes a tombstone message into the log (replacing the body with a deletion marker), and all clients apply it. Retention (auto-delete after N days) is enforced by dropping old partitions or by a background job that writes tombstones. The log remains append-only; deletes are soft.

What the read path optimizes for

The read path is optimized for the most common query: "the last N messages in this group." This is the query the UI issues when the user opens the channel, and it must be fast regardless of the group's size or history. The (group_id, seq) key and a reverse scan on seq deliver exactly this. Everything else — catch-up, scroll-back, search — is secondary and can be slower.

Common Pitfall

Storing media inline with the message. A group with millions of messages and media inline becomes gigabytes of log data that cannot be cached or efficiently scanned. The media belongs in object storage, and the message holds a reference. This is the single most important storage decision for a messaging system.

6

How do you handle a group member who joins late? Do they get history, and how do you delimit what they should see?

Short Answer

It is a product policy, not a technical limitation. The three common policies are: no history (the joiner sees only messages after joining), full history (they see everything), and bounded history (the last N messages or the last N days). The policy is enforced by the joiner's first_visible_seq, which is set at join time and used to filter all their reads. The log contains everything; the policy determines what each member can see.

The three policies

PolicyBehaviourUse case
No history The joiner sees only messages after their join. Their first_visible_seq is the current seq at join. Slack channels, Discord servers (default), work chat
Full history The joiner sees everything from the beginning. Their first_visible_seq is 0. WhatsApp groups, family chat, small groups where history is expected
Bounded history The joiner sees the last N messages (or the last N days). Their first_visible_seq is the seq at the boundary. Telegram (last N messages for new members), some community platforms

Implementation: first_visible_seq

The membership table records, per member, a first_visible_seq — the lowest seq the member can see. When the member joins, the value is set based on the policy:

  • No history: first_visible_seq = current_seq.
  • Full history: first_visible_seq = 0.
  • Bounded history: first_visible_seq = current_seq - N (or the seq at the day boundary).

Every read is filtered by seq >= first_visible_seq. The query is still a range scan on the log; the filter is applied at the query or the client. This is O(log n + N) regardless of the policy, so there is no performance difference between policies — only a correctness difference.

What "no history" really means

The joiner does not see messages before their join, but they can still see messages after. If the group had 100 messages before they joined and 5 after, they see 5 — the conversation appears to start mid-thread. In practice, the client often shows a "You joined the group" marker at the join seq, so the user understands why the history begins there. The marker is a system message in the log, and the joiner's first_visible_seq is the seq of the marker.

What "full history" requires

The joiner must fetch the group's history from the beginning. For a small group, this is a few hundred messages — fine. For a large group with years of history, the fetch is enormous. The client fetches the most recent N messages (the current screen) and lazily loads older messages as the user scrolls back. The first_visible_seq is 0, so the scroll-back can reach the beginning, but the client does not load it all at once.

The access-control interaction

The first_visible_seq is not just a product policy — it is an access control mechanism. The server must enforce it: a read request with seq < first_visible_seq is rejected or filtered. A client that tries to bypass the policy (by directly querying the log) must be blocked at the server, not just in the UI. This means the read path checks the membership and the first_visible_seq for every request, which is the same check as membership authorization (a member is authorized only for their visible range).

Rejoining and history changes

A member who leaves and rejoins — what do they see? The policy must define this:

  • No history on rejoin: first_visible_seq is reset to the current seq. The member loses their prior history (they cannot see the messages from their first membership).
  • Full history on rejoin: first_visible_seq is reset to 0. The member regains all history, including the messages from before their first join.
  • Preserve prior history: the first_visible_seq is not reset; the member keeps whatever they could see before, plus new messages. This is the most common policy for chat apps — rejoining does not lose history, and does not gain the messages from the gap.

The rejoin policy is a product decision, and it must be specified in the system's contract. The technical implementation is the same: update the first_visible_seq on rejoin according to the policy.

Admin and moderation

Admins and moderators may have different visibility rules: they can see messages that were deleted by users (for moderation), or they can see the full history even in a "no history" group (for compliance). This is a per-role override of first_visible_seq, and it must be audited — every admin view of a restricted message is a privileged access that should be logged.

The deletion interaction

If a message is deleted after a member joins, the member sees the tombstone (the message is replaced with a "deleted" marker), not the original content. The first_visible_seq does not override deletion; deleted messages are not visible to anyone (except admins, if the deletion is soft). This is a separate filter (per-message deletion marker) applied in addition to the seq filter.

What the design must specify

  1. The history policy per group type (no history, full, bounded).
  2. The rejoin policy (reset, preserve, or full).
  3. The admin override policy (what can admins see).
  4. The deletion policy (hard delete, soft delete, tombstone).
  5. The enforcement point (server-side, not client-side).

Each is a product decision, and the technical implementation is the same mechanism (the first_visible_seq filter plus the membership check). The design must specify all five, or the system's behavior is undefined for the cases the product cares about.

Common Pitfall

Enforcing history access only in the UI. A client that directly queries the log bypasses the UI and sees messages it should not. The enforcement must be server-side: the read API filters by first_visible_seq, and there is no API that returns messages outside the visible range for non-admin members.

How do you design a broadcast channel with 100,000+ members, where a single message reaches everyone?

Short Answer

A broadcast channel is a shared log plus a fan-out signal. The message is written once to the channel's log; the channel's seq is incremented; a single signal is published to the channel's broadcast topic; every gateway that has subscribers to the channel fetches the delta for its connected members; offline members receive a coalesced push and fetch on open. The per-message server cost is O(1) plus O(online subscribers per gateway), never O(total members).

The architecture

ComponentRole
Channel logSingle append-only log keyed by (channel_id, seq). One copy of the message.
Channel seqMonotonic counter; incremented on every message.
Broadcast topicPub/sub topic per channel (or sharded); the gateway subscribes to the topics for channels its members are in.
Gateway subscription tablePer-gateway: which connected members subscribe to which channels.
Per-member cursorlast_seen_seq per member per channel.
Push serviceCoalesced push notifications to offline members, per channel per window.

The write path

  1. The sender's message is appended to the channel log; the broker assigns seq N.
  2. The channel's current seq is updated to N (atomic increment).
  3. A single signal is published to the broadcast topic: {channel_id, seq: N}.
  4. The sender receives an ack with seq N.

The write is O(1) plus one signal publish. It is the same cost as a 3-person message, which is the key property: the write cost does not depend on the member count.

The read path (online members)

Every gateway subscribes to the broadcast topic for channels its members are in. On receiving the signal, the gateway:

  1. Looks up its local subscription table for members in channel_id.
  2. For each member, compares their last_seen_seq to the signal's seq.
  3. For members who are behind, fetches the range (last_seen_seq, N] from the log in one batch.
  4. Sends the batch to each behind member over their socket.
  5. Updates the member's last_seen_seq (or lets the client update it on the next request).

The gateway's cost is O(members in this channel who are connected to this gateway and are behind). Across the fleet, the total cost is O(members who are connected and behind), which is bounded by the fleet's total connection count, not by the channel's member count.

The read path (offline members)

Members who are not connected do not receive the signal. The push service sends a coalesced notification ("New in channel X") at a throttled rate (e.g., one push per channel per hour). When the member opens the app, they connect and fetch their delta from the log, using their last_seen_seq. The push is a hint, not the message.

The batching of signals

If the channel receives 100 messages/s, the broadcast topic receives 100 signals/s. Each gateway processes each signal, which is 100 × (subscriptions) work per second. At 100k subscriptions across the fleet, that is 10M subscription checks per second — heavy but manageable with batching. The optimization is to coalesce signals: instead of one signal per message, the channel publishes its current seq periodically (e.g., every 100 ms) and the gateway fetches the delta once per period. The signal rate drops to 10/s, and the fetch is one batch per member per period.

The push broadcast

For 100k offline members, sending 100k individual push notifications is expensive. APNs and FCM both support topic-based push: the device subscribes to a topic (the channel ID), and a single publish to the topic reaches all subscribed devices. The backend sends one request to APNs/FCM, and the provider fans out to the devices. This is dramatically cheaper than per-device push and is the standard for broadcast channels. The limitation is that the topic subscription is managed by the provider (the device must subscribe/unsubscribe), and the payload is the same for all members (no personalization).

The presence and receipts

In a 100k-member channel, live presence is infeasible: 100k presence updates per heartbeat is millions of operations per second. The design shows "N online" as an aggregate (counted by the registry, updated periodically) or nothing at all. Read receipts are dropped entirely — tracking 100k read positions per message is infeasible and not useful (nobody cares if 47,231 people read the message). The channel's UI shows the message, not who read it.

The moderation problem

In a 100k-member channel, moderation is a bottleneck. The messages are visible to everyone, and a bad message reaches 100k people before a moderator can remove it. The design must support: pre-publication review (only approved senders can post), post-publication removal (the message is deleted from the log, and clients see a tombstone), and rate limiting on senders (one message per N seconds). The moderation tools are a first-class part of the design, not an afterthought.

What breaks at 100k

  • The log's shard capacity: a channel with 100k members and years of history is a large partition. It must be sub-partitioned by time, with cold history tiered.
  • The broadcast topic's throughput: one signal per message is 100/s at 100 messages/s, which is fine; 100 signals per second to 100k subscribers (if not sharded) is not. The topic is sharded by channel_id, and the gateway subscribes only to its channels.
  • The gateway's subscription table: a gateway with 500k connections and 100k subscribed to one channel has 100k entries for that channel. The table must be indexed by channel_id for the signal processing, and the iteration must be efficient.
  • The push provider's quota: even topic-based push has limits; a channel with 100k subscribers sending 10 pushes/hour is 1M device deliveries/hour, which is within APNs/FCM's capacity but must be monitored.
Trade-off

Broadcast channels are cheap per message but expensive per read (each member must fetch and merge) and expensive to moderate. Small groups are the opposite. A product that supports both must have two architectures and a routing layer that picks one per channel — the complexity is real, but the alternative (one architecture for all sizes) either wastes resources on small groups or collapses on large ones.

What is the difference between fan-out for feeds and fan-out for chat? Why do they use different strategies?

Short Answer

Chat fan-out is per-conversation: a message goes to one group's members, and the fan-out is bounded by the group size. Feed fan-out is per-user: a post goes to everyone who follows the author, and the fan-out is bounded by the follower count, which can be millions. Chat is usually write fan-out for small groups and read fan-out for large channels; feeds are usually write fan-out for normal users and read fan-out (with a merge) for celebrities.

DimensionChat fan-outFeed fan-out
Unit of fan-outConversation (group)Author's follower set
Bounded byGroup sizeFollower count (can be 100M+)
Who readsGroup membersFollowers of the author
OrderingPer group (seq)Global timeline (reverse chronological or ranked)
Read pathOne group's logMerge across all followed authors
Write fan-out costO(group members)O(followers)
Read fan-out costO(1) per groupO(followed authors) per timeline
Standard strategyWrite for small groups, read for large channelsWrite for normal users, read for celebrities

Chat fan-out

Chat is conversation-centric. The user opens a conversation and reads its messages. The fan-out unit is the conversation: a message goes to the members of one group. The number of recipients is the group size, which is typically small (3–100) and bounded by the product's group limit. The read is a single conversation's log, which is a range scan on seq. The system's total fan-out is the sum over all messages × group sizes, which is manageable because the group sizes are small.

Feed fan-out

Feeds are user-centric. The user opens their timeline and sees posts from everyone they follow. The fan-out unit is the author's follower set: a post goes to all followers. The number of recipients is the author's follower count, which is unbounded (a celebrity has 100M followers). The read is a merge across all followed authors' posts, sorted by time (or ranked). The system's total fan-out is the sum over all posts × follower counts, which is enormous for a social network with celebrities.

Why the strategies diverge

Chat's bounded group size makes write fan-out feasible: 100 writes per message is fine. Feed's unbounded follower count makes write fan-out infeasible: 100M writes per post from a celebrity is not. The feed system handles this with a hybrid:

  • Normal users (few followers): write fan-out. The post is copied to each follower's timeline cache. The read is a single lookup.
  • Celebrities (many followers): read fan-out. The post is stored once, and each follower's timeline is built by merging the celebrity's posts with the other authors' posts at read time. The merge is expensive but bounded by the number of celebrities the user follows (usually a few).
  • The hybrid: the user's timeline is precomputed for the non-celebrities (write fan-out) and merged with the celebrities' posts (read fan-out) at request time. This is the standard "push-pull" feed design (Twitter's original design, Instagram's design).

The ordering difference

Chat is per-conversation ordered: messages within a group are in seq order, and the user sees them in that order. The order across groups is not meaningful. Feed is globally ordered: the user's timeline is a single sequence of posts from many authors, ordered by time (or by a ranking). The merge at read time must impose this order, which is why the read fan-out is more expensive for feeds.

The read latency difference

Chat read latency is low: one range scan on one group's log. Feed read latency is higher: merge N authors' posts, sort, paginate. The write fan-out precomputes the timeline, which makes the read a single lookup — but only for non-celebrities. The celebrity posts are merged at read time, adding latency. The design must balance the two: precompute as much as possible, merge only the unavoidable (celebrities, real-time posts).

Why chat does not have a "celebrity problem" in the same way

Chat has groups, not followers. A celebrity's group has the same size as anyone else's group (the product limits it). A celebrity is not a fan-out problem in chat; they are a content problem (their messages are more read). The "celebrity problem" in chat is a hot group (a group with many members), not a hot author. The design for hot groups is read fan-out (Question 3), which is different from the feed's celebrity handling but follows the same principle: above a threshold, switch to read fan-out.

The unified principle

Both chat and feed choose the fan-out strategy based on the fan-out factor: how many recipients per message. Below a threshold, write fan-out; above, read fan-out. The threshold is different (chat is 1,000 members, feed is maybe 10,000 followers) because the write cost per recipient is different, but the principle is the same. The systems look different because the fan-out factors are different by orders of magnitude, but the design decision is the same.

Interview Framing

Say: "Chat fan-out is per-conversation and bounded by group size, so write fan-out works for most groups. Feed fan-out is per-follower and unbounded, so it uses a hybrid: write fan-out for normal users, read fan-out for celebrities. The principle is the same — switch to read fan-out above the fan-out threshold — but the thresholds differ because the recipient counts differ." That names the principle and its two applications.

How do you handle read receipts and presence in large groups? Where does the per-user approach stop working?

Short Answer

Read receipts and presence are both per-user state that must be aggregated for display. In small groups, exact per-user tracking is feasible. Above a few hundred members, the per-user state is too expensive to maintain and too noisy to display, and the design switches to aggregate counts ("read by 40", "12,000 online") or drops the feature entirely.

Read receipts at each scale

Group sizeReceipt modelStorageDisplay
≤ 50Exact per-userread_seq per (user, group)"Alice and Bob read"
50–500Aggregate countread_count per (message, group)"Read by 47"
500–10kApproximate countSampled or periodic rollup"Read by many"
10k+None—Not displayed

The per-user receipt is a read_seq watermark: the highest seq each member has read. The exact receipt requires storing this per member per group, which is O(members × groups) storage. For a 50-person group it is 50 values; for a 10k-member channel it is 10k values — manageable, but the display ("read by 10,000") is meaningless, and the update rate (10k reads per message) is expensive. The aggregate count avoids the per-member storage: a counter per (message, group) incremented when a member reads. But the counter is a hot row, and incrementing it 10k times per message is a write bottleneck.

The aggregate counter's problem

An aggregate counter per message is a hot row. At 10k reads per message, the counter receives 10k increments per message, which serializes on the row. The standard mitigation is to shard the counter (N sub-counters, each receiving 1/N of the increments) and sum at read time, or to batch the increments (a background job that aggregates the per-user read seqs into a count every minute). The batch approach is more scalable but shows stale counts ("read by 47" may be 30 seconds old), which is acceptable for a receipt.

Where receipts stop being useful

The display of "read by 10,000" is not useful — no user cares about the exact count in a large channel. The feature becomes a waste of resources and a source of noise. The design should drop it above the threshold where it stops being useful, which is usually a few hundred to a few thousand members. The threshold is a product decision, not a technical one, but the technical cost grows linearly with group size, so the drop is also economically motivated.

Presence at each scale

Group sizePresence modelUpdate rateDisplay
≤ 50Live per-userHeartbeat per memberGreen dot per member
50–500Live, scopedHeartbeat per member, but only for open groupGreen dot for visible members
500–10kAggregatePeriodic count"47 online"
10k+Aggregate or nonePeriodic count"12,000 online" or nothing

Presence is more expensive than receipts because it updates continuously (heartbeats), not once (read). A 50-person group with 30-second heartbeats generates 100 presence updates per minute — trivial. A 10k-member channel generates 20,000 updates per minute — 333/s — which is manageable for a single channel but not for many large channels simultaneously. The aggregate model counts online members periodically (e.g., every 30 seconds) and updates a single number, which is O(1) per update instead of O(members).

The scoping technique

For medium groups (50–500), the presence can be scoped to the visible members: only the members currently displayed in the UI have their presence tracked. If the user is looking at the first 20 members, only those 20 are tracked; scrolling reveals more, and presence is fetched for the newly visible ones. This reduces the presence load from O(all members) to O(visible members), which is bounded by the screen size (tens, not hundreds).

The combined cost

Receipts and presence are both per-user state, and their combined cost at scale is significant. A 10k-member channel with live presence and exact receipts would need 10k presence entries (updated every 30s) plus 10k read_seq values (updated per message) — 20k writes per 30s and 10k writes per message. At 100 messages/s, that is 1M reads/s just for receipts, which is a whole database. The aggregate model reduces this to a periodic count and a batched receipt rollup, which is O(1) per update and O(messages) per minute, a 1000× reduction.

What to drop first

When the group grows, drop receipts first. Presence is more valuable (users like knowing who is online) and cheaper to aggregate (a count). Receipts are less valuable at scale (nobody cares if 8,412 people read the message) and more expensive to maintain per-message. The order is: exact receipts → aggregate receipts → drop receipts; live presence → aggregate presence → drop presence.

Common Pitfall

Maintaining exact per-user receipts in a 10k-member channel because "the product asked for it". The cost is 10k writes per message, which is a database bottleneck, and the display is not useful. The product requirement should be challenged: "do you really need to show read by 10,000?" — usually the answer is no, and the aggregate count is what they actually want.

How do you design push notification fan-out for a large group? How is it different from per-user push?

Short Answer

Per-user push sends one request per device to APNs/FCM. Group push uses topic-based push: the device subscribes to a provider topic (the group ID), and the backend sends one request to the topic; the provider fans out to all subscribed devices. This is dramatically cheaper for large groups, at the cost of no per-user personalization and limited delivery tracking.

Per-user push vs topic-based push

DimensionPer-user pushTopic-based push
Request to providerOne per deviceOne per topic
Backend costO(recipients)O(1)
PersonalizationYes (per-user payload)No (same payload for all)
Delivery trackingPer-device (APNs/FCM returns acceptance)Limited (provider handles fan-out)
Subscription managementBackend tracks device tokensDevice subscribes to topic; backend does not track
Best forIndividual notificationsBroadcast messages (channels, announcements)

How topic-based push works

  1. The app, on the device, subscribes to a topic when the user joins a group: FCM.subscribeToTopic("group_123") or the APNs equivalent.
  2. When the group has a new message, the backend sends one request to APNs/FCM with the topic name.
  3. The provider looks up all subscribed devices and delivers the notification to each.
  4. The device receives the notification, opens the app, and fetches the message from the log.

The backend's cost is one API call, regardless of the group size. The provider's fan-out is their problem, and they are built for it. This is the only way to push a message to a 100,000-member channel without sending 100,000 requests.

The limitations

  • No personalization: the payload is the same for all subscribers. If the notification should say "Alice mentioned you" for one user and "New message" for others, topic-based push cannot do it. The workaround is to send a generic push to the topic ("New in channel X") and let the app personalize on open, or to use per-user push for the personalized recipients (the mentioned users) and topic-based push for the rest.
  • No delivery tracking: the provider does not tell the backend which devices received the notification. The backend can track opens (via the app) but not deliveries. This is acceptable for broadcast channels, where delivery is best-effort and the message is in the log regardless.
  • Subscription management is on the device: the device must subscribe and unsubscribe, and the backend does not track the subscription. If the device is reinstalled or the token changes, the subscription is lost. The app must re-subscribe on startup, and the backend must handle a user who is not subscribed (they do not receive the push).
  • Provider topic limits: APNs and FCM have limits on the number of topics per app (usually thousands to tens of thousands). A product with millions of groups cannot subscribe each device to every group it is in; it must limit the number of topic subscriptions per device or use per-user push for small groups.

The hybrid strategy

Most products use both:

  • Large groups (10k+): topic-based push, generic payload ("New in channel X"). The user taps and fetches the message.
  • Small groups (≤ 1k): per-user push, personalized payload ("Alice: hey!"). The cost is O(members), but the group is small, so it is fine.
  • Mentions: per-user push, even in large groups, because the mention is personal. The mentioned user gets a personalized push; the other members get the topic-based generic push.

The coalescing of pushes

A 100k-member channel at 100 messages/s generates 100 pushes/s to the topic. If the provider allows it, that is a lot of notifications to the device. The coalescing is the app's job: the device receives many notifications for the same channel and groups them ("5 new messages in channel X"), or the backend throttles the pushes (one per channel per minute). The throttling must be careful — it delays the notification, which defeats the purpose of push. The standard is to send the first message immediately, then coalesce subsequent ones within a window (e.g., a summary after 60 seconds).

The push as a hint, not the message

As in Section 4, the push is a hint to wake the app and fetch. The message is in the log, and the app fetches it on open. The push payload can carry the message content (for the lock-screen preview) or just a summary ("New message"). The content is limited (APNs payload is 4 KB, FCM is 4 KB), so media and long messages are always fetched.

What breaks at 100k

  • The push provider's rate limits: FCM has per-project limits (e.g., 600k requests/minute). A 100k-member channel with one push per message at 100 messages/s is 10M pushes/minute, which exceeds the limit. The coalescing reduces this, but the design must account for it.
  • The device's notification limit: iOS and Android limit the number of notifications per app; a channel that pushes every message will be muted by the user. The product must coalesce and rate-limit the pushes to avoid being muted.
  • The topic subscription limit: the device cannot subscribe to 1000s of topics; the app must limit the subscriptions and fall back to per-user push for the groups it is not subscribed to.
Trade-off

Topic-based push is cheap but generic and untracked. Per-user push is personalized and tracked but expensive. The right answer is per-group size: small groups per-user, large groups topic-based, mentions per-user regardless. The threshold is where the per-user cost exceeds the topic-based cost, typically a few thousand members.

Interview Framing

Say: "For large groups I'll use topic-based push — one request to APNs/FCM, the provider fans out. For small groups and mentions, per-user push with personalized payloads. The threshold is a few thousand members, and the push is always a hint; the app fetches the message from the log on open." That covers the mechanism, the hybrid, and the source-of-truth principle.
