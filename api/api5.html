Part A — Idempotency Fundamentals Why retries are dangerous, and what makes them safe

1

What is idempotency, and why is it essential in distributed systems?

Short Answer

Idempotency means that executing an operation multiple times has the same effect as executing it once. It is essential because every distributed system operates over a network where the outcome of a request is ambiguous — the server may have processed the request but the response was lost. Without idempotency, retrying after an ambiguous failure causes double charges, duplicate orders, and double emails.

The fundamental ambiguity

Consider a client sending POST /payments to charge $100. The request reaches the server, the server commits the charge, and the server's response is lost in transit. The client sees a timeout. What should the client do?

  • Give up? The payment may or may not have been charged — the customer does not know whether their order went through.
  • Retry? If the first request succeeded, retrying charges the customer twice.

There is no information in the timeout that distinguishes these two cases. This is the two generals problem applied to HTTP: a client cannot know whether a request succeeded just because it did not get a response. Idempotency is the mechanism that resolves this ambiguity — it makes retry safe by making the second execution a no-op.

Three ways to achieve idempotency

  1. Natural idempotency. The operation is inherently idempotent — PUT with a full representation, DELETE of a specific resource, GET. Repeating it produces the same state, no key required.
  2. Idempotency keys. The client generates a unique key per logical operation and sends it with every retry. The server stores the key and returns the cached response for subsequent requests with the same key. This is the mechanism for non-idempotent operations (POST that creates a resource). (Questions 2–7 cover this in depth.)
  3. External deduplication. A downstream system deduplicates — the payment processor rejects a duplicate charge within a window, the queue consumer tracks processed message IDs. This shifts the burden to another system, which must have its own idempotency.

Where idempotency matters most

OperationWhy retry is dangerousSolution
Charge a paymentDouble charges the customerIdempotency key
Create an orderDuplicates the order and shippingIdempotency key
Send an emailDuplicate emails annoy the userIdempotency key or dedup at the email service
Increment a counterDouble-countsMake it a set operation (PUT), or idempotency key
Post a messageDuplicates the messageClient-generated message ID + dedup
Enqueue a jobRuns the job twiceIdempotency key or natural job ID

Where it does not matter: reads, deterministic queries, and operations whose duplicate execution is obviously safe (a DELETE that leaves the resource deleted). For these, retry is already safe, and adding idempotency keys is overhead.

The cost of not having it

The classic incident: a mobile app has a flaky network, a user taps "Pay", the request times out, the app retries automatically, and the user is charged twice. The fix in the app is either to retry safely (with an idempotency key) or not to retry at all (and let the user see the error). The fix in the API is to support idempotency keys so that retries are safe.

Other incidents: duplicate emails that the user receives twice and unsubscribes, duplicate orders that inventory and shipping both process, duplicate events that a downstream system processes and double-counts. Every one of these is a real production bug that a well-designed idempotency layer prevents.

Idempotency is a property of the operation, not the endpoint

An endpoint is not "idempotent" or "not idempotent" as a property — it depends on what the operation does. POST /payments is not idempotent. POST /payments with an idempotency key becomes idempotent. PUT /users/42 is idempotent. PUT /users/42 with a body that includes a "last_login" timestamp is not (each PUT sets a different time). The design decision is about what guarantees to provide, not about labelling the endpoint.

Idempotency vs at-least-once delivery

Message queues deliver at-least-once: a message can be delivered multiple times if the broker does not receive an acknowledgement. The consumer must therefore be idempotent — process the message, record its ID as processed, and ignore duplicates. HTTP clients have the same problem: any retry is an at-least-once delivery, and the receiver must be idempotent. Idempotency is the client-side complement to at-least-once infrastructure.

Interview Framing

Say: "Every network request is ambiguous — the client does not know whether a timeout means the server did not receive it or the response was lost. To make retries safe, either the operation is naturally idempotent (PUT/DELETE), or the client sends an idempotency key and the server deduplicates." That single sentence covers the whole topic.

What is an idempotency key, and how do you design one?

Short Answer

An idempotency key is a client-generated unique identifier for a logical operation. The client generates one per operation and sends it with every retry of that operation. The server records the key, its result, and returns the same result for any subsequent request with that key. The key must be unique per operation, stable across retries, and opaque to the server.

The core properties

PropertyMeaningWhy it matters
Client-generatedThe client creates the key, not the serverA server-generated key cannot be used for retries — the client does not know it until it has a response
Unique per operationEach logical operation (each "click Pay") has its own keyReusing a key for two different operations makes the second a duplicate of the first
Stable across retriesThe same key is used for every retry of the same operationIf the client generates a new key on retry, the server has no way to know it is a retry
Opaque to the serverThe server does not interpret the key; it just comparesLets clients use any format (UUID, ULID, hash) without server changes
Unique enough to avoid collisionTwo clients must not generate the same keyCollision would make one client's request a duplicate of another's

Generating the key

The key must be unique across all clients. The standard choices:

  • UUID v4 — 122 bits of randomness. The default for most APIs. Collision probability is negligible.
  • ULID — 128 bits, time-ordered. Sortable and unique. Useful if you want to query keys by time.
  • UUID v7 — new standard, time-ordered like ULID. Good for index locality.
  • Prefixed tokens — e.g., order_abc123. Human-readable, but must still have enough randomness to avoid collision.

What not to use:

  • User ID + timestamp. Two requests in the same millisecond collide.
  • Request body hash. The same body could legitimately be sent twice for two different operations. More importantly, the hash is not a key — it is a fingerprint that the server might use to detect misuse (see Question 5), but it cannot be the primary deduplication mechanism.
  • Session ID. A session has many operations; using it as the key makes all operations in a session duplicates of each other.
  • Server-assigned ID. The client cannot know it before the first response, so it cannot use it for retries.

Where the key goes

LocationExampleProsCons
Custom headerIdempotency-Key: abc-123Separates metadata from the body; easy to add to all requests via an HTTP interceptorNot visible in the body; requires header inspection
Body field{"idempotency_key": "abc-123", ...}Visible in logs and examplesMixes metadata with data; every schema must include it
Query parameter?idempotency_key=abc-123SimplePollutes the URL; not a resource identifier; not standard

Stripe's convention is the Idempotency-Key header, and it is the de facto standard. Use it. The header is convenient because it can be added by generic HTTP middleware (an interceptor, an SDK) without modifying the request body, and it does not require the body schema to include a metadata field.

Who generates the key, and when

The client generates the key at the moment of intent — when the user clicks "Pay", when the mobile app sends the "create order" request, when the batch job constructs the operation. The same key is then used for every retry of that intent, no matter how many retries occur.

This means the key must be generated in application code, not by the HTTP library (which might generate a fresh UUID per request). The key must be persisted if the operation might outlive the process — a mobile app that is killed and restarted after a failed payment must reuse the same key when the user retries.

What if the client does not send one?

Three options:

  • Reject the request. Return 400 Bad Request with "Idempotency-Key header is required". Strictest, safest for critical endpoints (payments, order creation).
  • Allow, no deduplication. Treat the request as non-idempotent — retries will duplicate. Acceptable for internal APIs where the client team is trusted to implement retries correctly.
  • Generate one server-side. The server generates a key and returns it, but this only helps if the client can use it for retries — which requires the client to have received the first response, so it is too late for the ambiguous case.

For any endpoint where duplicates cause harm, the first option is correct. For everything else, the second is fine. The third is a false comfort — it does not actually solve the problem it claims to.

Common Pitfall

Generating a new key on every retry attempt. This makes every retry a new operation from the server's perspective, which is exactly the bug idempotency was meant to prevent. The key must be generated once per logical operation and reused for all retries. This requires application code to carry the key through its retry loop, which is why it is not just an HTTP concern.

How do you store and check idempotency keys?

Short Answer

Store each key with its response, status, and request fingerprint in a durable store. On receipt, look up the key: if present with a completed response, return it; if present with an in-progress marker, return 409 Conflict (another request is in flight); if absent, process the request and store the result atomically. The store must be transactional or use an atomic set-if-not-exists operation.

The storage schema

ColumnPurpose
idempotency_keyPrimary key — the client's key
request_fingerprintHash of the request body + method + path, to detect misuse (Question 5)
statusin_progress, completed, failed
status_codeThe HTTP status of the original response (for completed)
response_bodyThe response body, so retries get the same result
response_headersAt least the important ones (Content-Type, Location)
created_atWhen the key was first used
expires_atTTL for cleanup (Question 6)

Why store the response, not just a flag

If you only store "this key was used", a retry can be detected but the client does not get the original result — it gets an error ("duplicate request") and has no way to know what the original response was. That defeats the purpose: the whole point is that a retry returns the same result as the original.

Storing the full response is what makes the retry indistinguishable from the original. The client sees the same status code, the same body, the same headers. This is why idempotency keys are sometimes called "response memoization" — they cache the response under the key.

The processing flow

StepActionOn result
1Look up the keyNot found → continue to 2. Found → go to 4.
2Atomically insert a row with status = in_progressInsert succeeded → process. Unique violation → go to 4.
3Process the request, then update the row to completed with the responseSuccess → done. Failure → update to failed (see below).
4Read the existing rowin_progress → return 409. completed → return the stored response. failed → decide based on policy.

The atomic insert in step 2 is the critical part. Two concurrent requests with the same key will race; the unique constraint on idempotency_key ensures only one succeeds in inserting, and the other sees the conflict and goes to step 4. This is the mechanism that prevents double processing (Question 4).

What to do with a failed request

If the request failed (a 500, a network error), should the key be reusable? Two policies:

  • Delete the key on failure. A retry is allowed to reprocess. This is what Stripe does for server errors — the key is released so the client can retry. The risk: the operation may have partially succeeded before the error, and retrying re-does that partial work.
  • Keep the key with the failure response. A retry returns the same error. This is what Stripe does for validation errors (400) — the request is malformed, so retrying the same request will fail the same way. The client must fix the request and use a new key.

The distinction is between transient failures (500, network) and permanent failures (400, 422). For transient, release the key; for permanent, keep it. This is covered in more detail in Question 7.

Storage choices

StoreProsConsBest for
Redis Fast; native TTL; atomic SET NX Not durable by default — a Redis crash loses keys, allowing duplicate processing High-throughput APIs where occasional duplicate is acceptable
Relational DB Durable; transactional; easy to query for audit Slower; requires an index and a cleanup job Payments, orders, anything where duplicates must never happen
DynamoDB / Cassandra Durable, horizontally scalable; TTL built-in Eventual consistency can leak duplicates during failover High-scale APIs with a need for durability
Hybrid Redis for fast lookup, DB for durability More complexity; two failure modes to handle Very high scale where every millisecond matters

For payments and any operation where a duplicate causes harm, use a durable store (database or DynamoDB). Redis is acceptable when the operation is high-volume and a rare duplicate is tolerable — but "tolerable duplicate" is a high bar for anything involving money.

The audit trail

Idempotency keys leave a natural audit trail: every operation, its request, its response, and its timestamp are recorded. This is enormously valuable for debugging "did this payment go through?" and for compliance ("show me every refund request with its outcome"). Store the audit records longer than the operational TTL — the key can expire, but the audit history should not.

Trade-off

Redis gives you speed and TTL but can lose keys on failover, which allows duplicate processing. A database gives durability at the cost of latency and cleanup complexity. For payments, the database is the right choice, and the ~5 ms of extra latency is negligible compared to the cost of a double charge.

How do you handle concurrent requests with the same idempotency key?

Short Answer

Use an atomic operation (unique constraint insert, or Redis SET NX) to ensure only one request claims the key. The first request processes the operation; the second returns 409 Conflict with "another request with the same idempotency key is in progress". Once the first completes, subsequent requests return the stored response. The in-progress state must have a timeout to recover from crashes.

The race condition

Two requests arrive at the server at nearly the same time, both with Idempotency-Key: abc-123. The naive implementation:

  1. Request A looks up the key — not found.
  2. Request B looks up the key — not found.
  3. Request A processes and charges the customer.
  4. Request B processes and charges the customer again.

The key was supposed to prevent this, but both requests saw "not found" and both proceeded. This is a race condition, and it happens constantly in production — the network may deliver two retries within milliseconds of each other, especially if a client is aggressive about retries.

The atomic claim

The fix is that the check-and-claim must be atomic. The two standard mechanisms:

StoreOperationBehaviour
Relational DB INSERT INTO idempotency_keys (key, status, ...) VALUES (..., 'in_progress') Success → this request owns the key. Unique violation → another request already owns it.
Redis SET key "in_progress" NX EX 3600 Returns 1 → this request owns the key. Returns nil → key exists, another request owns it.
DynamoDB PutItem with ConditionExpression: "attribute_not_exists(key)" Succeeds → this request owns the key. ConditionalCheckFailedException → another owns it.

The atomicity is provided by the store, not by the application. The application cannot implement check-then-insert because there is a window between the check and the insert — only the store can make that window zero.

What the second request returns

Once the first request has claimed the key, the second request sees status = in_progress and must decide what to return. The options:

  • 409 Conflict — "a request with this idempotency key is already in progress". The client should retry after a delay. This is the most common.
  • 423 Locked — semantically similar, but less common in REST APIs.
  • 202 Accepted — "your request is being processed, poll for the result". This works if the endpoint is already async, but for a synchronous endpoint, 409 is more honest.
  • Wait and return the result — the server blocks until the first request completes, then returns the same response. Elegant, but requires the second request to wait, which may exceed its timeout. This is what some databases do with row-level locking, but it is hard to implement at the API layer.

409 with a Retry-After header is the standard — it tells the client exactly what to do. The client should wait the indicated time and retry, at which point the first request will have completed and the stored response will be returned.

The stale in-progress problem

If the first request crashes (the server dies mid-processing), the key is stuck in in_progress forever. Every subsequent retry gets 409, and the operation never completes. This is a deadlock.

The fix is a timeout on the in-progress state. The row has an in_progress_at timestamp; if a request finds a key that has been in progress for longer than a threshold (e.g., 60 seconds), it can either:

  • Take over — atomically update the row to a new in-progress state owned by this request, and process. Risk: the original request is still running and may also complete, causing a duplicate.
  • Return 409 with a note — the client should investigate. Safer but not self-healing.
  • Return 500 — the operation is stuck; manual intervention needed. Worst option.

The timeout + takeover approach is what most systems use, with the caveat that the operations must be idempotent at the storage layer (the charge, if it was made, should be detectable). If the operation is a database write, the write's own idempotency (upsert, unique constraint) handles the double-processing risk.

The two-phase design

A more robust approach separates the key claim from the operation:

  1. Claim — atomically insert the key with a short lease (e.g., 30 seconds). If claimed, proceed.
  2. Process — do the work. If it succeeds, update to completed with the response.
  3. Renew the lease — if the work takes longer than the lease, the processor extends it periodically. If it crashes, the lease expires and a retry can take over.
  4. Release — on completion or failure, update the row to a terminal state, releasing the lease.

This is a distributed lock pattern applied to idempotency. It handles crashes gracefully and does not require operations to be naturally idempotent (though having them idempotent is still better).

Common Pitfall

Doing the lookup and the insert as two separate operations without any atomicity. The code looks correct: "if not exists, insert and process". But two concurrent requests both see "not exists" and both proceed. The fix is a single atomic operation (unique constraint, SET NX, conditional put) that guarantees only one request wins.

What happens if a client retries with the same key but a different payload?

Short Answer

This is an error condition. The key is supposed to identify one operation; reusing it with a different payload means either a buggy client or a malicious request. The server should compare a fingerprint of the request to the stored fingerprint and, on mismatch, return 422 Unprocessable Entity with a clear error — and not process the new payload.

Why this happens

  • Buggy retry logic. The client generates a key, sends request A, gets a timeout, then for some reason sends request B (a modified version of A) with the same key. Perhaps the user edited the amount and the retry logic reused the key.
  • Key collision. Two different clients accidentally generate the same key. Unlikely with UUIDs, but possible with low-entropy formats (user ID + counter).
  • Misuse. A client deliberately reuses a key to try to get a "free" operation — e.g., using a past key to avoid paying again. This is a form of replay attack.
  • Copy-paste error. A developer hardcodes a key in a test, and the test runs against production.

The fingerprint check

The server must store a fingerprint of the original request alongside the key. On subsequent requests, it computes the fingerprint of the new request and compares:

ComparisonMeaningResponse
Same key, same fingerprintLegitimate retryReturn stored response
Same key, different fingerprintMisuse422 with an error
Same key, in progressConcurrent request409 (Question 4)
New keyNew operationProcess normally

How to compute the fingerprint

The fingerprint is a hash (SHA-256) of the canonical request: method, path, and a canonicalised body. Canonicalisation matters — a body of {"a": 1, "b": 2} and {"b": 2, "a": 1} is semantically the same, and a client that serialises its JSON differently between retries should not be penalised. The standard approach is:

  1. Sort object keys recursively.
  2. Normalise whitespace.
  3. Normalise number formats (or reject them).
  4. Hash the resulting string.

Alternatively, canonicalise only the semantically important fields and ignore ones that might legitimately differ (like a client-generated timestamp in the body). This is more forgiving but harder to get right. For most APIs, the full-body hash after canonicalisation is fine.

The response format

On a fingerprint mismatch, return a clear error that tells the client what happened:

FieldExample
Status422 Unprocessable Entity
Error codeidempotency_key_reuse
Message"The provided idempotency key has already been used with a different request body."
DetailsThe fingerprint of the original request (a hash, not the body — for security)
Docs linkLink to documentation on idempotency

The error should not reveal the original body — that would leak information to a potentially malicious client. The hash is enough to confirm the mismatch without disclosing the content.

What NOT to do

  • Silently return the cached response. The client asked for something different and got the old answer. This is confusing — the client has no way to know its new request was ignored. Worse, if the new request is a legitimate correction (the user edited the amount), the client will believe its edit took effect when it did not.
  • Silently process the new request. This defeats the entire purpose of idempotency — the key becomes meaningless if it can be reused with a different body.
  • Return 400. This implies a malformed request, which is not the case. The request is well-formed; the key is being misused. 422 is more accurate.
  • Return 409. This implies a conflict with the current state, which is not what happened. 409 is for concurrent in-progress requests; 422 is for semantic errors.

The audit and alerting angle

A fingerprint mismatch is worth alerting on. It usually indicates a client bug, and one client's bug will cause many mismatches. The API should track:

  • Rate of fingerprint mismatches per client (API key, user ID).
  • Any client with a sustained mismatch rate above a threshold — likely a bug to be reported.
  • Suspicious patterns (same key, wildly different payloads — possibly an attack).

This turns the error into an operational signal, which is much more useful than a silent failure.

The "replay attack" dimension

A malicious client might try to reuse a key from a past operation. If the server stores the response with a TTL (Question 6), a key that is past its TTL is treated as new — so a replay after the TTL succeeds as a new operation. This is fine for most cases (the client has to know the key, which requires it to have been the legitimate client). For high-security operations (money transfers), consider storing keys indefinitely or using signed idempotency tokens that the server can verify.

Interview Framing

Say: "Same key + same body = return cached response. Same key + different body = 422, because the client is misusing the key. I'll store a hash of the request body with the key so I can detect the mismatch without storing the body itself." That demonstrates you know the fingerprint mechanism and its purpose.

6

What is the TTL for an idempotency key, and how do you choose it?

Short Answer

TTL should cover the window in which a client might retry. 24 hours is the industry standard (Stripe uses 24h), which is long enough for every reasonable retry pattern and short enough to keep storage bounded. For high-volume, low-stakes operations, 1 hour is fine; for very high-stakes operations (large payments), 7 days.

What TTL is for

Every idempotency key consumes storage — the key, its request fingerprint, its response body, and its metadata. At a million operations per day, that is a million rows per day, and without cleanup the store grows unboundedly. The TTL is the cleanup mechanism: after N hours or days, the key is deleted, and any retry with that key is treated as a new operation.

The two failure modes

TTL too shortTTL too long
A retry after the TTL is treated as a new operation — the duplicate is not prevented. This is exactly the bug idempotency was meant to prevent. Storage grows; the store becomes expensive and slow; cleanup jobs take longer. At high volume, the storage cost dominates.
Example: a 1-hour TTL on a payment API — a customer retries after 2 hours and is charged twice. Example: an indefinite TTL — after a year, the store has 365 million rows and queries are slow.

The TTL must be long enough that a legitimate retry is always within the window, and short enough that the storage cost is acceptable. The right value depends on the client's retry behaviour.

The retry window

How long does a client actually retry? It depends on the operation and the client's design:

Client typeTypical retry windowReason
Mobile app, immediate retrySeconds to minutesThe user is waiting; the app retries a few times with backoff
Server-to-server with SDKMinutes to hoursThe SDK retries with exponential backoff; the process may be long-lived
Batch jobHours to a dayThe job runs nightly and retries failed items
Manual retry after an incidentHours to daysThe operator investigates and retries
Client with a queueUp to a dayItems sit in a retry queue

A 24-hour TTL covers all of these. A 1-hour TTL would miss the batch job and manual retry cases. A 7-day TTL covers the "operator investigates over a long weekend" case, but costs 7× the storage.

Recommended values

OperationTTLWhy
Low-stakes, high-volume (creating a "like", logging an event)1 hourRetries are rare and immediate; storage matters
Standard API operation (create order, send email)24 hoursThe industry default; covers all common retry patterns
Payment, transfer, any money movement7 days or indefiniteThe cost of a duplicate is catastrophic; storage is negligible compared to it
Configuration or deployment operationIndefiniteRedoing a deployment with the same key should never be allowed to re-run

How to expire

StoreMechanism
RedisSET key value EX 86400 — expiry is automatic
DynamoDBTTL attribute (expires_at) — the item is deleted automatically within 48 hours of expiration
PostgreSQLScheduled job (pg_cron or application-level) that runs DELETE FROM idempotency_keys WHERE expires_at < now()
MySQLSame — scheduled job or a partition-based approach where old partitions are dropped

The cleanup must be reliable. If it fails, the store grows unboundedly. The cleanup job should be monitored, and the store's size should be alerted on. For high-volume systems, partition-based expiry (drop partitions older than N days) is more efficient than a delete query.

What happens after the TTL

A retry with an expired key is treated as a new operation. This is the correct behaviour — the TTL says "after this long, we no longer track this operation". The client should ideally never retry after the TTL (its retry policy should give up before that), but if it does, the operation proceeds as new.

For high-stakes operations, the audit trail is separate from the TTL — the key expires, but the record of what happened does not. This allows investigation ("was this charged twice?") without keeping every key forever.

The Stripe 24-hour precedent

Stripe's documentation says: "We'll remember the key for 24 hours. After that, a request using the same idempotency key is treated as a new request." This is the industry standard, and it is a good default for most APIs. The reasoning: 24 hours covers every realistic retry, the storage cost is manageable, and the behaviour is documented so clients can plan.

Trade-off

Long TTLs are safer (fewer duplicates) but cost more storage and make the store slower. Short TTLs are cheaper but risk duplicates for slow retries. The right balance depends on the cost of a duplicate: for a $1 like, 1 hour; for a $1M transfer, indefinite.

7

How do payment APIs (Stripe) implement idempotency?

Short Answer

Stripe's implementation is the reference design: an Idempotency-Key header on POST requests, a per-account namespace, a durable store of key → response, a fingerprint check for misuse, a 24-hour TTL, and a 409 response for concurrent requests. It is worth studying because payments are where idempotency matters most and where the design has been battle-tested at enormous scale.

The Stripe flow

  1. The client generates a unique key (Stripe recommends UUID v4 or a similar scheme) at the moment of intent — when the user clicks "Pay", not when the request is retried.
  2. The client sends POST /v1/charges with the key in the Idempotency-Key header.
  3. The server looks up the key in the per-account namespace. If not found, it processes the charge and stores the response under the key.
  4. If found and completed, the server returns the stored response — the same status code, the same body, the same headers. The client sees an identical result.
  5. If found but in progress (another request with the same key is currently processing), the server returns 409 Conflict with a clear error.
  6. If found but with a different request fingerprint, the server returns 422 with an error.
  7. After 24 hours, the key expires and a new request with the same key is treated as a fresh charge.

The per-account namespace

Stripe's keys are scoped per account (or per API key). This means two different accounts can use the same idempotency key value without conflict — each account has its own namespace. This is important for multi-tenant APIs: the key must be scoped to prevent one tenant from "using up" a key that another tenant wants.

The response caching detail

Stripe stores the entire response — status code, body, and headers. This is what makes a retry truly indistinguishable from the original. The client cannot tell whether it is seeing a fresh response or a cached one, which is exactly the point.

The stored response includes errors: if the original charge failed with 402 Payment Required, retries return the same 402 (not a fresh attempt that might succeed). The exception is server errors (5xx), where the key is released so a retry can reprocess — because a 500 might have been transient.

The error-handling policy

Original responseBehaviour on retryWhy
200 OK (charge succeeded)Return stored 200 with the same charge IDThe charge was made; the client should see it
400 Bad Request (invalid parameters)Return stored 400The request is malformed; retrying the same body will fail the same way
402 Payment Required (card declined)Return stored 402The decline is the outcome; retrying the same card will decline again
409 Conflict (concurrent request)Not stored — the in-progress request will completeThe original request's outcome will be stored
422 (idempotency misuse)Not stored — the key is invalidThe client must use a new key
500 Internal Server ErrorRelease the keyA 500 may be transient; retrying with the same key should be allowed
Network timeout (no response)Release the keySame as 500 — the operation may or may not have happened; retry is allowed

The 500-release policy is the subtle one. If the server crashed after charging but before storing the response, releasing the key allows a retry, which charges again. Stripe accepts this risk — the alternative (keeping the key with a 500) would make legitimate retries impossible after a transient failure. The mitigation is that payment processors are themselves idempotent at the network level, so a duplicate charge can be detected and reversed. For most APIs, releasing on 5xx is the right policy.

The 24-hour TTL

Stripe documents the 24-hour TTL explicitly. This means a client that retries after 24 hours will make a new charge — and is expected to know this. The documentation is the contract: the client must complete its retries within 24 hours, or accept that the key is no longer valid.

What Stripe's design teaches

  • Use the standard header. Idempotency-Key is the de facto convention.
  • Scope keys per tenant. Multi-tenant APIs need a namespace, not a global key space.
  • Store the full response. Not just the outcome, but the status, body, and important headers.
  • Distinguish transient and permanent failures. 5xx releases the key; 4xx keeps it.
  • Document the TTL. Clients need to know how long their keys are valid.
  • Return 409 for concurrent requests. Not a silent retry, not a blocked wait.
  • Reject key misuse with 422. Same key + different body is a client bug, not a retry.
  • Durability matters. A payment API cannot use Redis with default settings — the key store must survive failover.

What is different for non-payment APIs

Most APIs do not need the full Stripe design. A less critical API might:

  • Use Redis instead of a database (accepting rare duplicate processing during failover).
  • Use a shorter TTL (1 hour instead of 24).
  • Not store the full response — just a hash and a status flag, if the client can reconstruct the result.
  • Not distinguish 4xx and 5xx — just delete on failure, always allowing retry.

The Stripe design is the gold standard because payments are the highest-stakes case. For other APIs, the same principles apply at lower cost. The core invariants — atomic claim, stored response, fingerprint check, documented TTL — are non-negotiable.

Common Pitfall

Implementing idempotency keys but not scope-ing them per account. A multi-tenant API where keys are global means tenant A's key abc-123 blocks tenant B's key abc-123, which is a confusing cross-tenant bug. Scope the key to the account (or API key) as part of the primary key.

What are ETags, and how do conditional requests enable optimistic concurrency?

Short Answer

An ETag is an opaque version identifier for a resource. The server includes it in responses (ETag: "v42"), and the client sends it back in conditional requests (If-Match: "v42") to say "only apply my change if the resource is still at this version". If the version has changed, the server returns 412 Precondition Failed — the lost-update problem is prevented without any locking.

The lost-update problem

Two clients read the same user profile (version 1). Client A updates the name to "Alice". Client B updates the email. If both use a plain PUT, client B's write overwrites client A's — the name is silently lost. This is the lost-update problem, and it is the most common data corruption bug in concurrent systems.

Optimistic concurrency solves it by detecting the conflict at write time. The client says "I read version 1, apply my change only if it is still version 1". If the server is at version 2 (because client A already updated), it rejects the write — the client must re-read and retry with the new version.

The ETag mechanism

StepClientServer
1. ReadGET /users/42Returns 200 OK with ETag: "v1" and body
2. Modify locallyChanges the name to "Alice"—
3. Write with preconditionPUT /users/42 with If-Match: "v1"—
4a. SuccessSees 200 OK with new ETag: "v2"ETag matched; update applied; new version
4b. ConflictSees 412 Precondition FailedETag did not match (another client updated); write rejected
5. On conflictRe-reads, merges, retries with the new ETagAccepts the new write if ETag matches

Strong vs weak ETags

TypeSyntaxMeaningUse
StrongETag: "v42"Byte-for-byte identicalUpdates — a byte difference is a real conflict
WeakETag: W/"v42"Semantically equivalent, but possibly byte-differentCaching — a semantically identical response can be reused

For optimistic concurrency, use strong ETags. A weak ETag says "these two responses mean the same thing", which is fine for caching but not for conflict detection — you need to know whether the resource is exactly the version the client saw.

How to generate ETags

  • Content hash. SHA-256 of the response body. Works for any resource, but expensive to compute on every response.
  • Version column. A monotonically increasing integer updated on every write. Cheap, but requires a schema column and a write-time increment.
  • Timestamp. updated_at as an ETag. Simple, but two updates in the same millisecond collide, and clock skew can cause ordering issues.
  • Composite. A hash of the version column plus a schema version — allows distinguishing "the resource changed" from "the schema changed".

The version column is the most practical for high-volume APIs. The content hash is the most correct but the most expensive. The timestamp is the easiest but the least reliable under high write rates.

If-Match vs If-None-Match

HeaderSemanticsUse case
If-MatchApply only if the ETag matchesOptimistic update — "only if unchanged"
If-None-MatchApply only if the ETag does not matchCreate-if-absent (with *), or caching
If-Modified-SinceOnly if modified since a dateCaching — return 304 if unchanged
If-Unmodified-SinceOnly if not modified since a dateWeaker form of If-Match

If-Match: * means "only if the resource exists" — used for create-if-absent semantics.

The 412 vs 409 distinction

When an If-Match precondition fails, the standard response is 412 Precondition Failed. This is distinct from 409 Conflict (used for idempotency key contention and other state conflicts). The 412 specifically means "your precondition was not met" — which is exactly the message the client needs.

The cost of optimistic concurrency

Every write requires a read first (to get the ETag), which is an extra round trip. On high-latency networks, this doubles the cost of an update. The mitigations:

  • Return the ETag in the create response. A client that creates a resource gets the ETag, and can use it for the first update without a read.
  • Let the client supply the ETag from its local cache. If the client has cached the resource with its ETag, it can use it without a network round trip.
  • Accept the cost. For high-stakes updates (payments, inventory), the extra round trip is worth the correctness. For low-stakes updates (user preferences), a plain PUT is fine — the lost-update risk is acceptable.
Trade-off

Optimistic concurrency avoids locks (good for throughput) but requires the client to handle conflicts (412) and retry. Pessimistic concurrency (Question 9) avoids conflicts but serialises access. Choose based on conflict probability: low-conflict resources favour optimistic, high-conflict resources favour pessimistic.

What is the difference between optimistic and pessimistic concurrency in an API?

Short Answer

Optimistic concurrency assumes conflicts are rare: it does not lock, but detects conflicts at write time (ETag/If-Match, version columns) and rejects conflicting writes. Pessimistic concurrency assumes conflicts are common: it locks before modifying, preventing other writers from touching the resource until the lock is released. Optimistic scales better; pessimistic avoids conflict retries.

AspectOptimisticPessimistic
MechanismVersion check at write timeLock acquired before write
Conflict detectionAt write time (412)At lock time (wait or 409)
Client experienceRead, write, retry if conflictLock, write, unlock (or hold lock)
ThroughputHigh — no locks heldLower — locks reduce concurrency
Deadlock riskNoneYes — lock ordering matters
Best forLow-conflict, long-lived operationsHigh-conflict, short-lived operations
ExampleUser profile updateSeat reservation

Optimistic concurrency in detail

The client reads the resource, gets a version (ETag or a version field), modifies locally, and writes with a precondition. If the version has not changed, the write succeeds; if it has, the write fails and the client retries with the new version. The server never holds a lock — it only checks at write time.

This is ideal when conflicts are rare. In a user profile, two people rarely edit the same field at the same millisecond. In a document editor, conflicts are uncommon and can be merged. The cost is that the client must handle the 412 and retry, which is extra code. The benefit is that the server can serve thousands of concurrent reads without any coordination.

Pessimistic concurrency in detail

The client acquires a lock on the resource, does its work, and releases the lock. Other clients that try to acquire the lock either wait (blocking) or get a 409/423 (non-blocking). The server must implement the lock — a row lock in the database (SELECT ... FOR UPDATE), a distributed lock (Redis, etcd), or an explicit lock endpoint.

This is ideal when conflicts are common. In seat reservation, two people trying to book the same seat at the same time is a real scenario; the lock ensures only one succeeds. In inventory, the lock prevents overselling. The cost is that the lock reduces throughput and introduces deadlock risk (if two operations acquire locks in different orders). The benefit is that the client does not have to retry — the lock either succeeds (proceed) or fails (a clear error).

How each appears in an API

PatternOptimisticPessimistic
UpdatePUT /users/42 with If-Match: "v1"POST /seats/42/lock, then PUT /seats/42, then DELETE /seats/42/lock
Conflict response412 Precondition Failed409 Conflict or 423 Locked
RetryClient re-reads and retriesClient waits and retries the lock
Lock lifecycleNoneExplicit acquire and release; auto-expiry on timeout

Pessimistic locking patterns

  • Database row lock. SELECT ... FOR UPDATE — the transaction holds the lock until commit. Simple, but limited to a single database session.
  • Distributed lock. Redis SET NX EX, etcd lease, ZooKeeper ephemeral node. Works across services, but adds a dependency and has its own failure modes (lock expiry, split-brain).
  • Lock endpoint. An explicit POST /resource/lock that returns a lock token, and DELETE /resource/lock to release. More visible in the API, but requires the client to manage the lifecycle.

The lock timeout problem

Every pessimistic lock needs a timeout. If a client acquires a lock and crashes without releasing it, the resource is locked forever. The standard fix is a lease — the lock expires after N seconds unless renewed. The client must renew the lease if the operation takes longer than expected, and must be prepared for the lock being stolen if it fails to renew. This is the fencing token problem (Volume 6 of the distributed systems series) — the classic example is a paused process that resumes after its lock has expired and continues to write.

Choosing between them

  1. How often do conflicts happen? Rare → optimistic. Frequent → pessimistic.
  2. How long does the operation take? Long → optimistic (holding a lock for a long time blocks everyone). Short → pessimistic is fine.
  3. How bad is a conflict? Mergeable (text, tags) → optimistic. Not mergeable (seat, balance) → pessimistic.
  4. Do you have a distributed lock store? No → optimistic is simpler. Yes → pessimistic is possible.

The hybrid pattern

Many systems use optimistic for most operations and pessimistic only for the critical ones. A banking API might use ETags for profile updates and a database row lock for transfers. The choice is per operation, not per API. Documenting which operations use which mechanism is important — the client needs to know whether to expect a 412 (retry) or a 409 (wait).

Common Pitfall

Using optimistic concurrency but not telling the client how to recover from 412. The client sees a 412 and does not know whether to retry (with a new ETag) or give up. The documentation and error message must say: "Re-read the resource to get a fresh ETag, then retry your update."

How do you design retries safely — retryable vs non-retryable errors, backoff, budgets, and circuit breakers?

Short Answer

Retry only on transient errors (5xx, 429, timeouts), never on permanent errors (4xx like 400, 401, 403, 404, 422). Use exponential backoff with jitter, cap the attempts and total duration, enforce a retry budget (retries as a fraction of total requests), and wrap the downstream in a circuit breaker that fails fast when it is unhealthy. And retry only if the operation is idempotent or carries an idempotency key.

Classifying errors

CategoryExamplesRetry?Why
Client errors (400, 401, 403, 404, 422)Bad request, invalid token, forbidden, not foundNoThe request is malformed or unauthorised — retrying will produce the same error
Conflict (409, 412)Version conflict, concurrent requestSometimesRetry after re-reading (412) or after the conflicting operation completes (409)
Rate limiting (429)Too many requestsYesRetry after Retry-After header
Timeout (408, network)Request timeout, connection resetYes, with idempotencyThe request may or may not have been processed; retry with a key
Server errors (500, 502, 503, 504)Internal error, bad gateway, unavailable, timeoutYes, with backoffTransient — the server may recover
Non-idempotent POST without a keyPayment, order creationNoRetry may duplicate the operation

The rule: 4xx means the client is wrong; 5xx means the server is wrong. Retrying a 4xx is usually pointless — the client must fix its request. Retrying a 5xx is often useful — the server may recover. The exceptions are 408 (timeout — retry), 429 (rate limit — retry after delay), and 409/412 (conflict — retry after resolving the conflict).

Exponential backoff with jitter

Retrying immediately hammers a struggling server. The standard is exponential backoff: the wait doubles with each attempt.

AttemptBase backoffWith jitter (random 0–100%)
11s0–1s
22s0–2s
34s0–4s
48s0–8s
516s0–16s
Max60s or a fixed cap0–60s

The jitter is critical. Without jitter, a thousand clients that all fail at the same moment will all retry at exactly 1s, 2s, 4s — a thundering herd that amplifies the problem. With full jitter (random in [0, backoff]), the retries spread out and the load is smoothed. AWS's "exponential backoff and jitter" paper documents this in detail; the practical recommendation is decorrelated jitter, which randomises both the base and the cap.

The retry cap

Retries must be bounded. Two limits:

  • Max attempts — typically 3–5. Beyond that, the failure is probably not transient.
  • Max duration — typically 30 seconds to 2 minutes. Beyond that, the client should give up and report the failure to the user.

A request that takes 10 retries and 5 minutes to fail is worse than one that fails immediately — the user has waited all that time and still sees an error. Fail fast, or escalate to async (Volume 1, Question 13).

The retry budget

A retry budget is a cap on retries as a fraction of total requests. If a service normally has a 2% retry rate, a budget of 10% means retries can be used freely in normal operation but are throttled when a downstream failure causes a spike. Without a budget, a failing service causes every client to retry, which triples the load — a retry storm that turns a local failure into a global outage.

ScenarioRetry rateWith budget (10%)
Normal operation2%All retries allowed
Minor blip8%All retries allowed
Downstream failure50%Retries throttled to 10%; 90% of failures returned to client immediately

The budget is enforced by the client (or by a service-mesh sidecar), tracked over a rolling window (e.g., the last 10 seconds). When the budget is exhausted, further requests fail fast rather than retrying — which reduces load on the struggling service and gives it a chance to recover.

The circuit breaker

The circuit breaker is the next level of protection: after a threshold of failures, it stops sending requests to the failing dependency entirely, for a cool-down period. This is different from a retry budget: a budget limits retries, a circuit breaker stops all traffic to a dependency.

StateBehaviourTransition
ClosedRequests flow normally; failures are countedFailure threshold exceeded → Open
OpenAll requests fail immediately (or go to a fallback)After timeout → Half-Open
Half-OpenA single test request is allowed throughSuccess → Closed. Failure → Open

The circuit breaker converts a slow timeout into a fast failure, which is much better for the client (the user sees an error immediately instead of waiting 30 seconds) and for the dependency (it receives almost no traffic, so it can recover).

Client-side vs server-side retries

Retries can be implemented on either side:

  • Client-side retries. The SDK or application retries. More control per client, but each client team must implement it — and many forget the budget, jitter, or idempotency key.
  • Server-side retries. The gateway or service mesh retries on behalf of the client. Uniform policy, but harder to apply idempotency per operation — the gateway does not know which operations are safe.
  • Both. The gateway retries transient errors uniformly, and the client retries for its own operation semantics. This is common but compounds — a gateway retry of 3 plus a client retry of 3 means 9 attempts, which is usually too many.

The best practice: one layer does the retry. Either the client (with full operation knowledge) or the gateway (with uniform policy), but not both. If both are needed, the client retries only after the gateway has exhausted its retries and returned a definitive error.

Retry and idempotency are intertwined

Every retry is safe only if the operation is idempotent or carries an idempotency key (Questions 1–2). This is why retry design and idempotency design belong together: the retry policy says when to retry, and the idempotency key says why a retry is safe. Without both, retries are a footgun — they turn transient failures into duplicate charges, duplicate orders, and duplicate emails.

Interview Framing

Say: "I'll retry 5xx, 429, and timeouts with exponential backoff and jitter, and never retry 4xx. I'll cap attempts at 3, use a retry budget to prevent retry storms, and wrap the downstream in a circuit breaker. And I'll only retry non-idempotent operations if they carry an idempotency key." That single sentence covers every dimension of the retry policy.
