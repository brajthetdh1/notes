Part A — Algorithms The five classic limiters, and how each behaves under burst

1

Why rate limit? What problem does it actually solve?

Short Answer

Rate limiting protects three things: availability (one client cannot exhaust shared resources), fairness (every client gets a reasonable share), and cost (downstream services, third-party APIs, and compute are bounded). It is not about security in the narrow sense — it is about making the system's capacity predictable under abuse, accident, or runaway clients.

The four reasons to rate limit

  • Protect shared infrastructure. A single client sending 100,000 requests per second can saturate the database, the connection pool, or the CPU — degrading service for everyone. The limiter caps each client's share of the shared resource.
  • Prevent accidental over-use. A misconfigured client (a retry loop with no backoff, a batch job with too much parallelism) can generate traffic that looks like an attack. The limiter turns it into clear 429s that the client can respond to, instead of silent degradation.
  • Bound cost. Every request costs compute, database IO, or a third-party API call. Without a limit, one client's usage can produce an unbounded bill — or exhaust a downstream quota (e.g., a payment provider's per-second limit), which affects all clients.
  • Make abuse expensive. Scrapers, credential stuffing, and enumeration become far less effective when each source is limited to a rate that makes the attack impractically slow. This is the security dimension — not preventing the attack, but making it economically unattractive.

What rate limiting is not

Rate limiting is often confused with adjacent mechanisms. It is not:

  • Authentication. A rate limit applies after authentication. It cannot substitute for verifying identity.
  • Authorization. It does not check whether the caller is allowed to do something — only how often.
  • DDoS protection. A DDoS attack from 100,000 IPs each sending 10 requests per second will not be stopped by per-IP rate limiting. DDoS protection is at the network edge (anycast, scrubbing centres, CDNs). Rate limiting is for authenticated or semi-identified clients.
  • A security boundary. A determined attacker with many accounts can bypass per-user limits. Rate limiting raises the cost; it does not guarantee safety.

The consequences of not rate limiting

ScenarioWithout rate limitingWith rate limiting
A client's retry loop goes haywire Database saturates; all clients see errors; the system looks down The runaway client gets 429s; healthy traffic continues
A scraper enumerates the catalogue The scraper copies the entire dataset in minutes Enumeration takes days; the cost outweighs the value
A batch job re-processes an entire table Third-party API quota is exhausted; the integration breaks for everyone The batch job is throttled; other clients unaffected
A bug creates a tight loop in a mobile app Thousands of users with the bug overwhelm the backend The app's users get 429s and backoff; the rest of the system is safe

Where to rate limit

LayerWhat it protectsTypical limit
CDN / edgeNetwork bandwidth, DDoSVery high per IP (thousands/s)
API gatewayThe API surface, authentication, and routingPer API key: tens to thousands/s
ServiceThe service's own resources (database, dependencies)Per operation: specific to the operation's cost
Third-party clientThe downstream provider's quotaAt or below the provider's limit

The standard architecture: a coarse limit at the gateway (per API key) and a finer limit at the service (per operation, or per tenant). The gateway protects the whole API; the service protects its specific resource.

The fairness dimension

Rate limiting is fundamentally about fairness. A system with no limits is a system where the loudest client wins, and the quietest client suffers. A system with well-designed limits is one where each client gets a share proportional to its tier, the shared infrastructure is protected, and the quiet client is never degraded by the loud one. This framing — fairness, not punishment — is what distinguishes a good rate limiter from a hostile one.

Interview Framing

Say: "Rate limiting is about fairness and protection, not security — it caps each client's share of shared resources and bounds the cost of any one client. DDoS is handled at the edge, not here." That framing shows you understand what the mechanism is actually for.

Compare fixed window, sliding window log, and sliding window counter algorithms.

Short Answer

Fixed window counts requests in a fixed time bucket (e.g., per minute) — simple and cheap, but allows a 2× burst at the boundary. Sliding window log stores each request timestamp and counts the last N — accurate, but memory-heavy. Sliding window counter approximates the sliding window by weighted interpolation of two fixed windows — nearly as accurate as the log at a fraction of the memory.

AlgorithmMemoryAccuracyBurst behaviourBest for
Fixed window O(1) — one counter per key Low — boundary burst allowed Up to 2× the limit at the boundary Simple cases; approximate limits
Sliding window log O(N) — every request timestamp Exact Strict — no boundary burst Low-volume, strict limits (login attempts)
Sliding window counter O(1) — two counters per key High (approximation) Smoothed — no 2× burst High-volume APIs — the pragmatic default

Fixed window

The simplest algorithm. Divide time into fixed buckets (e.g., a minute), and keep one counter per key per bucket. On each request, increment the counter; if it exceeds the limit, reject. When the bucket rolls over, the counter resets.

ProsCons
Trivial to implement and reason aboutThe boundary burst problem
One counter per key, O(1) memoryImprecise limits — actual rate can reach 2×
Cheap to computeDoes not smoothly distribute load

The boundary burst. With a limit of 100 per minute, a client can send 100 requests at 59.999s and 100 more at 60.001s — 200 requests in 2 milliseconds, while technically satisfying "100 per minute". This is fine for approximate limits, and catastrophic for strict ones (e.g., login attempts).

Sliding window log

Store every request's timestamp in a log (usually a sorted set, or a Redis sorted set with timestamp scores). On each request, remove entries older than the window, count what remains, and compare to the limit. Accurate but memory-proportional to the limit — a limit of 10,000 per hour needs up to 10,000 timestamps per key.

ProsCons
Exact — no boundary burstMemory grows with the limit
Handles variable windows easilyEach request needs a write + range delete
Useful for logging rejected requests tooNot scalable to millions of keys at high limits

This is the algorithm of choice for strict, low-volume limits — password attempts, SMS sends, expensive operations. For an API that allows millions of requests per hour, storing a timestamp per request is too much memory.

Sliding window counter (the pragmatic default)

An approximation that is accurate to within a few percent while using O(1) memory. The idea: keep two fixed-window counters — the current window and the previous window. On each request, compute a weighted count based on how far into the current window you are:

StepComputationExample
Current timet45 seconds into a 60-second window
Current window countcurr40 requests
Previous window countprev80 requests
Weight of previous(window_seconds − t) / window_seconds(60 − 45) / 60 = 0.25
Estimated totalcurr + prev × weight40 + 80 × 0.25 = 60
DecisionCompare to the limitIf limit is 100, allow

This estimates the count in the "sliding" window ending at t: the current window's counts, plus a fraction of the previous window's counts proportional to how much of it still lies in the past 60 seconds. It is a linear interpolation, not exact, but the error is small (a few percent) and it is O(1) per key — two counters, one per window.

This is the algorithm used by most production rate limiters (Cloudflare, Redis-backed limiters, Stripe's published design). It gives smooth limits without the boundary burst and without the memory cost of the log.

The burst question

None of these algorithms handle "bursts" gracefully in the way clients actually behave. A client that sends 100 requests over 60 seconds may send them in 10 seconds (a 10x burst) and then be idle. Fixed and sliding windows see "100 in the minute" and allow it; the momentary load spike still hits the backend. This is why token bucket (Question 3) exists — it allows a burst up to the bucket size while enforcing an average rate over time.

The decision

If you need…Use
The simplest possible implementationFixed window
Exact enforcement at low volumeSliding window log
Smooth enforcement at high volumeSliding window counter
Burst allowance with a rate capToken bucket (Question 3)
Common Pitfall

Using fixed windows for security-sensitive limits (login attempts, SMS sends). The 2× boundary burst means an attacker can make twice the allowed attempts per period by timing the request around the boundary — which for a limit of 5 attempts per minute means 10 attempts per minute, enough for a much faster brute-force. Use sliding window log for these.

3

Compare token bucket and leaky bucket.

Short Answer

Token bucket refills a bucket of tokens at a fixed rate and consumes one per request. It allows a burst up to the bucket size, then enforces the rate — good for real client behaviour. Leaky bucket drains a queue at a fixed rate; incoming requests either fill the queue or are rejected — good for smoothing output. Token bucket limits input rate with bursts; leaky bucket shapes output rate.

AlgorithmShapeBurst allowed?Rate enforcedBest for
Token bucket Refill at rate R, up to capacity B; consume 1 per request Yes, up to B Average R, instantaneous up to B API rate limits — bursts are normal client behaviour
Leaky bucket Queue of capacity B; drain at rate R No — output is strictly at R Strict R Smoothing traffic to a downstream (e.g., a third-party API)

Token bucket — the API rate limiter

The metaphor: a bucket holds tokens. Tokens are added at a fixed rate (say, 10 per second) up to a maximum (say, 100). Each request consumes one token. If the bucket is empty, the request is rejected. If the bucket is full, extra tokens are discarded — the rate is capped, not the burst.

StateBehaviour
Bucket full, no recent trafficThe client can burst up to the bucket size (100 requests immediately)
Bucket empty after a burstRequests are rejected until tokens accumulate
Steady traffic at rate RThe bucket stays full; no rejections
Traffic above rate RThe bucket drains; after B tokens, rejections start

This is why token bucket is the default for APIs: real clients are bursty. A mobile app loading a screen sends 10 requests in 200 ms, then nothing for a minute. Fixed and sliding windows would reject the burst (10 in 200 ms violates "10 per minute"), which frustrates the client. Token bucket allows the burst (10 ≤ 100), and the bucket refills over the next minute, ready for the next screen.

Leaky bucket — the output shaper

The metaphor: a bucket with a hole in the bottom. Requests pour in; the bucket drains at a fixed rate (say, 10 per second). If the bucket is full, incoming requests are rejected (or queued, depending on the variant). The output is always at the drain rate — no bursts ever reach the downstream.

This is the right tool when the downstream cannot handle bursts. A third-party API that allows 100 requests per second but rejects bursts above 10 in any 100 ms window needs leaky bucket shaping — the client must present a smooth rate, not a burst.

The two bucket variants

VariantBehaviourUse
Leaky bucket as a queue Requests wait in the queue and are processed at the drain rate; the queue is bounded; overflow is rejected Smoothing with latency tolerance — the client waits
Leaky bucket as a meter The bucket is a counter that drains; requests are rejected when the meter is full Rate limiting without queueing — the client is told to retry later

The queue variant introduces latency (requests wait), which is usually unacceptable for a synchronous API. The meter variant is what most APIs actually use, and it behaves similarly to token bucket with zero burst capacity.

When each is the right answer

  • API rate limiting (per client): token bucket. Bursts are normal; the limit should allow them up to a reasonable size while capping the average.
  • Protecting a downstream that cannot handle bursts: leaky bucket (meter variant). Smooth the rate to exactly what the downstream can handle.
  • Protecting against scraping or enumeration: token bucket with a small bucket. The attacker cannot exploit bursts because the bucket is tiny.
  • Queueing with bounded latency: leaky bucket as a queue, with a max wait time. Useful for batch processing where the client tolerates waiting.

The combined token-bucket-plus-concurrency approach

For high-performance APIs, a token bucket alone is not enough. A client with a bucket of 100 tokens can send 100 concurrent requests, which may overload the backend even though the rate is fine. The complete design combines two limits:

  • Rate limit (token bucket) — caps requests per second per client.
  • Concurrency limit (Question 7) — caps requests in flight per client, so no client can saturate the thread pool.

Both are necessary. The rate limit protects against sustained over-use; the concurrency limit protects against momentary bursts of parallel requests.

Trade-off

Token bucket allows bursts — good for user experience, but a client can briefly exceed the average rate. Leaky bucket strictly limits the rate — good for downstream protection, but rejects the bursts real clients send. Choose based on what you are protecting: the API from the client (token bucket) or the downstream from the API (leaky bucket).

How do you implement a distributed rate limiter without a single point of failure?

Short Answer

Store the counters in a shared, fast, durable store — usually Redis, sometimes a specialized service like Envoy's rate limit or Cloudflare's edge counters. Use atomic operations (INCR, Lua scripts, or token bucket scripts) so concurrent requests see a consistent view. Shard by key to avoid a single hot instance, and accept eventual consistency across shards as the trade-off for scale.

Why distributed is hard

A single-server rate limiter is trivial: a hash map in memory. A distributed limiter has three problems:

  • Shared state. Every instance must see the same counter. Two instances that each allow "50 per second" without sharing state effectively allow 100 — the limit is multiplied by the fleet size.
  • Atomicity. The check-and-decrement must be atomic. A naive "read counter, compare to limit, increment" race allows a burst through if two requests read the same value.
  • Latency. Every request now requires a call to the limiter store, adding a network hop to the hot path. At high volume, that hop is significant.

The Redis approach

Redis is the standard because it is fast, supports atomic operations, and is widely available. Two common patterns:

PatternCommandsProsCons
Fixed window with INCR + EXPIRE INCR key, EXPIRE key window Simple, one round trip if pipelined Fixed window limitations
Token bucket via Lua script A single EVAL that reads, refills, checks, and decrements atomically Atomic; token bucket semantics; one round trip Lua complexity; script maintenance
Sliding window via sorted set ZADD, ZREMRANGEBYSCORE, ZCARD Exact sliding window Memory proportional to limit; multiple commands
Sliding window counter via Lua Two counters, interpolated O(1) memory; smooth Approximate

The Lua script pattern is the standard for token bucket and sliding window counter, because it gives atomicity without a transaction protocol. The script reads the current state, computes the refill, checks the limit, and updates — all in one atomic operation on the Redis server.

The hot key problem

A single Redis instance handling all rate limit keys becomes a hotspot. A popular API key (a public integration used by millions) can hit the same Redis shard with thousands of requests per second, saturating it. The mitigations:

  • Shard by key. Redis Cluster distributes keys across shards; a single key still hits one shard, so a single popular key is still a hotspot.
  • Local approximation with periodic sync. Each instance holds a local token bucket and periodically (every 100 ms) syncs its consumption to Redis. The local limiter allows bursts up to its own capacity; the global limiter corrects over time. This trades exactness for speed.
  • Two-tier limits. A per-instance limit (local, fast) plus a global limit (Redis, authoritative). The local limit prevents any one instance from over-consuming; the global limit enforces the tenant-wide cap.
  • Cache the decision. For the "allow" case, cache the decision for a few milliseconds — if a burst of requests for the same key arrives within 10 ms, use the cached decision instead of re-querying Redis. The cost is that the limit is approximate within that window.

The failure mode question

What happens when the rate limiter store is down? Two policies:

PolicyBehaviourTrade-off
Fail-open Allow all requests when the limiter is unavailable Availability preserved; the system is unprotected during the outage
Fail-closed Reject all requests when the limiter is unavailable Protection preserved; the entire API is down because of the limiter
Fail-degraded Use a local fallback limiter (each instance limits independently, without global coordination) Some protection, some availability — the pragmatic answer

Fail-open is the right default for most APIs: a rate limiter outage should not become an API outage. The risk (temporary over-use) is smaller than the cost (total unavailability). Fail-closed is only right if the limit protects a resource that would be catastrophically damaged by over-use — which is rarely the case for an API.

The local fallback

The best of both worlds: each instance runs its own token bucket locally, and syncs consumption to Redis every 100 ms or so. When Redis is available, the global limit is enforced (within the sync window). When Redis is down, the local limit still caps each instance — so the fleet can over-consume by at most N × local_limit, which is degraded but not catastrophic. This is how most production rate limiters work.

The alternative: dedicated rate limit services

For very high scale or very strict requirements, a dedicated rate limit service — Google's Cloud Armor, Cloudflare's edge rate limiting, Envoy's rate limit service, or a custom gRPC service — is the right design. It scales independently of the API, is optimised for the limiter workload, and centralises the policy. The cost is an extra service to operate.

Common Pitfall

Implementing rate limiting with a non-atomic read-modify-write on Redis (e.g., GET, then SET). Two concurrent requests both read the same counter, both increment to the same value, and the effective limit is doubled. Redis INCR and Lua scripts are atomic; anything built on separate commands is not.

What do you rate limit on — IP, user, tenant, endpoint, or something else?

Short Answer

The key should match the unit of fairness you care about. Per API key for machine clients, per user for authenticated humans, per tenant for a SaaS, per IP for unauthenticated traffic. In practice you layer several: a coarse per-IP limit at the edge (DDoS), a per-API-key limit at the gateway, a per-user limit in the service, and a per-endpoint limit for expensive operations.

The possible keys

KeyWhat it protectsWeaknessUse when
IP address The network; unauthenticated traffic NAT and mobile carriers share IPs; a single IP can represent thousands of users Unauthenticated endpoints (login, signup, public search)
API key The application One key can be shared by an entire tenant — the limit is per application, not per user Machine-to-machine; public APIs
User ID The individual authenticated user Requires authentication; an attacker can create many accounts Authenticated user-facing endpoints
Tenant ID The organisation Does not distinguish noisy users within a tenant SaaS billing, fair-share across customers
Endpoint / operation A specific expensive operation Not an identity — must be combined with an identity key Expensive operations (search, export, report)
Composite key E.g., user × endpoint, tenant × endpoint Combinatorial explosion of counters Per-user limits on each expensive operation

Why IP alone is insufficient

IP-based rate limiting has two well-known problems:

  • NAT and carrier-grade NAT. A thousand users behind one corporate NAT share one IP. A per-IP limit of 100/minute means 100 users get the whole quota and the other 900 get 429s. The limit punishes the whole group for one user's behaviour.
  • Distributed attacks. A botnet with 10,000 IPs each sending 10 requests per minute easily exceeds a per-IP limit without any individual IP triggering it. IP rate limiting is not DDoS protection.

IP is still useful as the outermost layer for unauthenticated endpoints (login, signup, public search), where it is the only identity available. But it is a blunt instrument, and it should not be the primary limiter for authenticated traffic.

Layering the keys

Real APIs use multiple limits at multiple layers:

LayerKeyTypical limitProtects
Edge / CDNIPThousands/minuteNetwork bandwidth; basic DDoS
GatewayAPI keyHundreds–thousands/minuteThe API surface
GatewayTenantPer planFair share across customers
ServiceUserTens–hundreds/minuteIndividual user behaviour
ServiceUser × operationPer operationExpensive operations

A request must pass every layer. A single user can have 100/minute (their user limit) but also be subject to a 1000/minute API key limit shared with their whole company — if the company's collective traffic exceeds that, everyone in the company gets 429s regardless of their individual limit.

The expensive-operation dimension

Some endpoints cost 100× more than others. A simple GET /users/{id} might take 5 ms and hit one database row; a POST /search might take 500 ms and scan millions of rows. Applying the same rate to both means either the simple one is under-limited (wasting capacity) or the expensive one is over-limited (rejecting reasonable use). The answer is per-operation limits:

  • GET /users/{id} — 1000/min per user
  • POST /search — 60/min per user
  • POST /export — 5/hour per user
  • POST /reports — 10/day per user

The limits reflect the cost of the operation, not a single global rate. This is also the foundation of usage-based billing (Question 8) — the meter counts per operation, not just requests.

The multi-dimensional key

For a SaaS API, the most useful limit is often a composite: (tenant_id, endpoint). This gives each tenant a fair share of each operation's capacity. Tenant A cannot exhaust the search quota for tenant B, and a noisy tenant cannot degrade the experience of a quiet one. The composite key is the design that makes multi-tenant fairness work — Question 8 covers the details.

Interview Framing

Say: "I'll layer limits — per-IP at the edge for unauthenticated traffic, per-API-key at the gateway, per-tenant for fair share, per-user for the individual, and per-operation for expensive endpoints. Each layer protects a different resource." That demonstrates the multi-layer design and why no single key is sufficient.

How do you communicate rate limits to clients — headers, 429, and Retry-After?

Short Answer

Return rate limit information in response headers on every request (not just when rejecting), and return 429 Too Many Requests with a Retry-After header when the limit is exceeded. The headers should tell the client the limit, the remaining budget, and when the window resets — so well-behaved clients can self-throttle before they hit the wall.

The standard headers

There are three conventions in the wild, and the industry is slowly converging on the third:

ConventionHeadersNotes
GitHub / Twitter style X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset Widely understood; the Reset is usually a Unix timestamp
IETF draft (RateLimit-*) RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset, RateLimit-Policy Standardised draft; no X- prefix; supports multiple policies
RFC 9331 (combined) RateLimit: limit=100, remaining=50, reset=30 Single header; newer; less tooling support

The IETF draft headers are the future, but the X-RateLimit-* headers are what most tools, clients, and SDKs understand today. Many APIs send both — the standard ones for compatibility, the X- ones for the ecosystem.

What each header means

HeaderMeaningExample
LimitThe maximum requests allowed in the current window100
RemainingHow many requests are left in the window37
ResetSeconds until the window resets (or a Unix timestamp, depending on the convention)23 (seconds) or 1705314600 (timestamp)
PolicyThe limit's scope and window100;w=60 (100 per 60 seconds)

The Remaining header is the most actionable — a client that sees remaining: 5 with reset: 2 can wait 2 seconds and continue, instead of blasting requests and getting rejected. This is the "self-throttling" use case that makes the headers valuable: well-behaved clients stay under the limit without ever hitting a 429.

The 429 response

When the client exceeds the limit, return 429 Too Many Requests with a body that explains the rejection and a Retry-After header:

Header / fieldContent
Status429 Too Many Requests
Retry-AfterSeconds to wait, or an HTTP date: Retry-After: 30
RateLimit-ResetWhen the limit resets (same as on the success response)
Body (RFC 7807){"type": ".../rate-limited", "title": "Too many requests", "detail": "Rate limit of 100/min exceeded. Retry after 30 seconds.", "status": 429}

The Retry-After header is the critical piece. Without it, the client has no idea when to retry and will either give up or retry immediately (making the problem worse). With it, a well-written client can wait exactly as long as needed.

Which convention for Reset

The X-RateLimit-Reset header has two interpretations in the wild:

  • Seconds remaining (a small integer, e.g., 23) — easier to use, but the client's clock is irrelevant.
  • Unix timestamp (e.g., 1705314600) — the client computes reset - now, which is subject to clock skew.

Use seconds remaining. It is unambiguous, immune to clock skew, and what the IETF draft specifies. Document it clearly — the same header with different semantics across APIs is a source of bugs.

Headers on success, not just on failure

A common mistake is returning rate limit headers only on 429. This means the client has no idea what its limit is until it has already exceeded it. Return the headers on every response — success and failure — so a well-behaved client can self-throttle from the first request.

The cost is a few bytes per response, negligible. The benefit is that clients that read the headers can avoid hitting the limit at all, which is better for the client (no 429s, no retry logic) and for the server (no wasted rejection work).

The multi-policy case

A request may be subject to several limits at once — per-user, per-tenant, per-operation. When any is exceeded, return 429 with the headers for the tightest limit (the one that triggered the rejection). The IETF RateLimit-Policy header supports listing multiple policies, but the client's decision should be based on the most restrictive one.

Common Pitfall

Returning 429 without a Retry-After header. The client does not know how long to wait, so it either gives up (bad UX) or retries immediately (worse — it makes the rate limit problem worse). Every 429 must tell the client when to come back.

Interview Framing

Say: "Every response carries RateLimit-Limit, Remaining, and Reset, so well-behaved clients self-throttle. On 429 I add Retry-After so the client knows exactly when to retry." That covers both the success path and the failure path in two sentences.

What is the difference between rate limiting, concurrency limiting, and load shedding?

Short Answer

Rate limiting caps requests per unit time (per client). Concurrency limiting caps requests in flight at any instant (per client or per service). Load shedding rejects requests when the system is overloaded, regardless of who is asking. Rate limiting is a policy on the caller; concurrency limiting protects a resource; load shedding is a last-resort defence of the whole system.

MechanismWhat it capsProtectsBehaviour under load
Rate limiting Requests per second per client Fairness; sustained capacity 429 per client over its limit; others unaffected
Concurrency limiting Requests in flight per client or per service Memory, thread pools, connection pools Queue or 503 when concurrency is at the cap
Load shedding Total load on the system The system itself (from overload) Reject based on priority, endpoint, or random sampling — even for callers under their rate limit

Rate limiting

Requests per second. The classic limiter from Question 2. Protects against sustained over-use by one client and enforces fairness. Applied per API key, per user, per tenant, per operation. It does not protect against a momentary burst of parallel requests — 100 tokens allow 100 concurrent requests in milliseconds, which a rate limit alone cannot prevent.

Concurrency limiting

Requests in flight. Each service has a finite thread pool, connection pool, and memory budget. A concurrency limit — enforced by a semaphore or a queue — ensures that no more than N requests are being processed at once. When N are in flight, the next request waits (bounded queue) or is rejected (503).

The concurrency limit is what protects the actual resource — the database connection pool (10 connections per instance), the thread pool (200 threads), the memory for request bodies (100 MB). A rate limit of 1000 per second means nothing if the service can only handle 50 concurrent requests — the 51st will queue, latency will spike, and the whole service will collapse.

The implementation is a bulkhead pattern: each client or each operation gets a bounded number of concurrent slots. A slow client exhausting its own slots does not affect others — they have their own bulkhead. This is the mechanism that prevents the "one slow dependency takes down the whole service" failure.

Load shedding

When the system is overloaded, something must be rejected, or everything fails. Load shedding decides what to reject, based on priority:

  • Priority. Reject low-priority traffic (analytics, background jobs) first; keep critical traffic (checkout, authentication) flowing.
  • Endpoint. Reject expensive endpoints first; keep cheap ones.
  • Random sampling. Reject a random fraction of requests — simple, fair, and effective at reducing load below capacity.
  • Per-client. Reject the clients that are consuming the most — the ones most likely to be abusive or runaway.

The classic techniques are deadline propagation (if a request has already consumed 80% of its latency budget and is still queued, shed it — the client will time out anyway) and CPU-based shedding (if CPU is above 90%, shed a proportional fraction of requests).

How they compose

LayerMechanismFails with
EdgeRate limit per IP429
GatewayRate limit per API key; concurrency limit per tenant429 / 503
ServiceConcurrency limit per operation; load shedding when CPU high503
DownstreamCircuit breaker; timeout; bulkheadfallback / error

Each layer catches what the others miss. Rate limiting catches the abusive client; concurrency limiting catches the burst that a rate limit allows; load shedding catches the general overload that no per-client limit can prevent (e.g., a sudden 10× surge from all clients at once). Together they form the complete overload protection.

The failure ordering question

Which mechanism should fire first? The answer is: rate limit before concurrency before load shedding. A client should be told "you are over your rate" (429) before being told "the server is busy" (503). Load shedding is the last resort — it should only fire when the system is genuinely near collapse, because it rejects requests that the other mechanisms would have allowed.

Trade-off

Rate limiting is precise but does not protect against bursts. Concurrency limiting protects the resource but adds latency (queueing). Load shedding is a blunt instrument that rejects indiscriminately. Use all three, in that order, with the coarsest at the outside and the finest at the resource boundary.

Part C — Quotas & Abuse Multi-tenant fairness and the bypass problem

How do you design quotas for a multi-tenant SaaS?

Short Answer

A quota is a usage allowance over a billing period — millions of requests per month, storage gigabytes, API calls per tier. It is different from a rate limit (which caps instantaneous rate): quotas are about total consumption, not speed. The design has four parts: a tier model, a metering system, enforcement at multiple windows (per-second, per-day, per-month), and a clear client-facing contract for what happens at overage.

Rate limit vs quota

DimensionRate limitQuota
Time windowSeconds to minutesDay, month, billing period
PurposeProtect against bursts and abusePrice usage; bound total consumption
Response on exceed429 with retry-after429, or overage billing, or feature lockout
ResetContinuously (rolling) or per windowPeriodically (monthly, on billing date)
Measured inRequests/secondRequests, bytes, compute, storage
Configurable byOps/platformProduct/pricing; often customer-self-serve

Both are needed: a tenant on the "Pro" plan might have a quota of 10 million requests per month and a rate limit of 1,000 requests per minute. The quota is about how much; the rate limit is about how fast. Exceeding the rate is temporary (wait and retry); exceeding the quota is persistent (upgrade or wait for the billing period).

The tier model

TierMonthly requestsRate limitOverage
Free10,00010/minHard cap — 429 after quota
Pro1,000,0001,000/min$0.01 per 1,000 extra; no hard cap
EnterpriseCustomNegotiatedNegotiated

The free tier is usually hard-capped (to prevent abuse); the paid tiers allow overage with billing (so the customer's service does not break at the quota boundary); the enterprise tier is custom. This is the standard model, and it aligns with what customers expect.

Metering

Every billable operation must be counted and attributed to a tenant. The meter must be:

  • Accurate. Every billable request is counted exactly once. This is an idempotency problem (Volume 5) — a retried request must not be billed twice, or a client retrying a timeout is charged extra for the retry.
  • Timely. The meter is updated within seconds, so the quota enforcement reflects current usage. A daily batch is too slow — a tenant can exceed its quota by millions of requests before the meter catches up.
  • Durable. The meter is stored in a durable store (database, not just Redis), so a crash does not lose billing data.
  • Attributable. Every count maps to a tenant, an operation, and a timestamp — for billing, for analytics, and for resolving disputes.

The standard implementation is an event stream: every request emits a usage event, which is aggregated into a per-tenant, per-period counter. The aggregation can be real-time (Redis + periodic flush to DB) or near-real-time (a streaming pipeline like Kafka + ClickHouse).

Enforcement at multiple windows

A complete quota system enforces at several windows simultaneously:

WindowEnforced wherePurpose
Per second / minuteRate limiter (Redis, in-memory)Burst and abuse protection
Per dayQuota counter (Redis or DB)Prevent a single day's runaway
Per monthQuota counter (DB)Billing period total
Per featurePer-operation quotaBound use of expensive features

A request must pass all windows. The per-second limit is checked cheaply (in Redis); the per-month limit is checked against a cached counter that is refreshed periodically. The multi-window enforcement prevents both momentary bursts and long-term over-use.

The client-facing contract

The quota must be expressed clearly in the API contract:

  • Response headers — Quota-Limit, Quota-Remaining, Quota-Reset — analogous to rate limit headers.
  • Usage endpoint — GET /usage returns current consumption per feature, the billing period, and the projected end-of-period.
  • Approaching-quota alerts — a webhook or email at 80% and 95% of quota, so the customer can act before the service stops.
  • Overage policy — documented clearly: hard cap (429), soft cap with billing, or grace period. The customer must know what happens when they exceed the quota.

The alerting is critical. A customer that hits the quota unexpectedly sees their service break with no warning. A customer that was told at 80% and 95% has time to upgrade or reduce usage. The alerts convert a customer-service problem into a self-service action.

Fairness across wildly different tenant sizes

A shared-schema SaaS has tenants ranging from 10 requests/day to 10 million. The rate limits and quotas must be tiered so that the large tenant does not exhaust shared capacity while the small tenant gets a reasonable share. The design:

  • Per-tenant rate limits — the "Pro" tier gets 1,000/min, the "Free" tier gets 10/min. The large tenant cannot consume the shared capacity beyond its tier.
  • Per-tenant quotas — the billing period is per tenant, so one tenant's over-use does not consume another's allowance.
  • Shared infrastructure caps — beyond per-tenant limits, the system as a whole has a capacity limit. If the sum of per-tenant limits exceeds the infrastructure, a global fallback limiter (or load shedding) protects the shared resource.
Trade-off

Hard caps are simple and protect infrastructure, but they break customer trust at the quota boundary. Soft caps with overage billing preserve the customer's service but expose them to unexpected costs. The pragmatic answer: soft caps for paid tiers (with alerts), hard caps for free tiers (with upgrade prompts), and clear documentation of the policy for each tier.

Interview Framing

Say: "Quotas are per-tenant, per-billing-period, metered accurately and attributed to the tenant. Rate limits are separate — per minute, per API key. I'll alert the customer at 80% and 95% of quota, and the overage policy is documented per tier." That demonstrates the full lifecycle: metering, enforcement, contract, and alerts.

What is the difference between throttling and rejection, and when do you delay instead of deny?

Short Answer

Rejection refuses the request immediately with a 429 (or 503). Throttling (also called shaping or delay) holds the request and processes it later, within a bounded wait. Rejection is better for synchronous APIs (the client can retry with a known delay); throttling is better for async work (the client tolerates latency) and for protecting a downstream that must see a smooth rate.

AspectRejection (429)Throttling (delay)
Client experienceImmediate error; the client must retrySlower response; no error
Connection holdReleased immediatelyHeld for the wait duration
Server resourcesMinimal — the request is not processedA queue slot and a thread/connection during the wait
Best forSynchronous APIs, high-latency operations, abuse preventionBatch processing, async APIs, downstream smoothing
Latency impactNone (the request fails fast)Adds wait time to the response
Timeout riskLowHigh — a long wait may exceed the client's timeout

Why rejection is the default for synchronous APIs

A synchronous HTTP request has a latency budget (typically 1–30 seconds at the client, with intermediate timeouts at proxies and load balancers). Holding a request for even a few seconds risks exceeding those timeouts: the client times out, retries, and now two copies of the request are in flight. The result is worse than rejection.

Additionally, holding connections consumes server resources. A hundred held requests occupy a hundred connections, a hundred threads, a hundred queue slots — each of which could have served a request that was actually going to be processed. At scale, holding is more expensive than rejecting.

Rejection gives the client control: it gets a clear 429 with Retry-After and can decide whether to wait, back off, or give up. This is the right contract for a synchronous API.

When throttling is the right answer

  • Async APIs. The client has submitted a job and is polling for the result; a small delay in processing is invisible. Throttling the job queue to protect the workers is standard.
  • Batch processing. A batch import that is throttled to 1,000 rows per second protects the database without failing the batch. The batch takes longer but succeeds.
  • Downstream smoothing. When a third-party API rejects bursts, throttling the requests to that API shapes them into a smooth rate. The client experiences a longer wait, not an error.
  • Premium tiers. A VIP client's requests can be queued (throttled) rather than rejected, preserving their experience at the cost of latency. Non-VIP clients are rejected.

The hybrid: bounded wait, then reject

The pragmatic middle ground: hold the request for a bounded wait (say, 100 ms to 1 second), then reject if the rate is still exceeded. This gives a brief smoothing benefit without the risk of long-held connections. The pattern is used for rate limiters where the traffic is bursty but the bursts are short:

  • If a token is available now, process immediately.
  • If not, wait up to N milliseconds for a token to refill.
  • If no token arrives within N, reject with 429 and Retry-After.

This handles the common case (a client sends 110 requests in a second with a limit of 100/second — the first 100 are immediate, the next 10 wait a few milliseconds and then succeed). It avoids the pathological case (a client sends 10,000 requests — most are rejected after the brief wait).

Throttling via async APIs

The cleanest form of throttling is to make the operation async (Volume 1, Question 13). Instead of holding the request, return 202 Accepted with a job ID, and let the client poll or receive a webhook. The server processes the job at its own pace, throttled as needed. The client's HTTP connection is released immediately, and the latency of the wait does not affect any timeout.

This is the standard design for batch operations, exports, and any work that might take more than a few seconds. It gives the server the freedom to throttle without penalty, and the client the clarity of knowing the operation is queued.

Trade-off

Rejection is faster and cheaper but worse for the client. Throttling is slower and more resource-heavy but preserves the client's experience. For sync APIs, default to rejection; for async, default to throttling; for batch or downstream smoothing, throttle. Never throttle a sync request beyond a second — the risk of timeouts outweighs the benefit.

How do you prevent rate-limit bypass and abuse?

Short Answer

Rate limits are only effective if the key cannot be trivially changed. Prevent bypass by rate limiting on multiple keys simultaneously (IP + API key + user + tenant), by limiting account creation (to prevent account farming), by detecting distributed patterns (many IPs, same user agent), and by layering anomaly detection on top of the fixed rules. Rate limits are a floor on abuse cost, not a guarantee of safety.

The common bypass techniques

BypassHow it worksCountermeasure
Account farming Create many accounts; each has its own per-user limit Limit signups per IP/device; require email or phone verification; flag new accounts for elevated scrutiny
API key rotation Create many API keys; each has its own per-key limit Limit keys per tenant; rate limit on tenant, not just key; require approval for new keys
Distributed IPs Send from many IPs (botnet, cloud proxies); each is under the per-IP limit Rate limit on user/tenant as well as IP; detect patterns across IPs
Parameter manipulation Use a different header, endpoint, or query to hit a different counter Rate limit on the operation, not on the URL surface; normalize aliases
Slow drip Send just under the limit, continuously — never triggering a burst detection Rate limit over multiple windows (per second, per day, per month); detect sustained patterns
Client spoofing Fake the user agent, the IP, or the API key Authenticate the key at every layer; use mTLS or signed requests for high-value endpoints
Multi-tenant abuse One attacker creates multiple tenants Rate limit on multiple axes; verify tenant creation with payment or identity

Multiple simultaneous keys

The single most effective countermeasure: rate limit on every dimension at once. A request is rejected if it exceeds any of:

  • Per-IP limit
  • Per-user limit
  • Per-tenant limit
  • Per-API-key limit
  • Per-operation limit

An attacker who farms accounts hits the per-IP limit. An attacker who distributes across IPs hits the per-user limit (if they are using one user) or the signup limit (if they are creating many users). An attacker who rotates API keys hits the per-tenant limit. Each bypass is closed by a different key.

Account creation limits

Account farming is the most common bypass for per-user rate limits. The countermeasures:

  • Per-IP signup limit. Limit signups from a single IP to a small number per day. This alone blocks most automated farming.
  • Email verification. Require a verified email; throwaway domains are blocked or flagged.
  • Phone verification. For high-value endpoints, require a phone number; SMS-based verification is harder to farm than email.
  • CAPTCHA / proof-of-work. For signup and for password reset, add a human-verification challenge.
  • Payment method. Require a credit card on file for accounts that need elevated limits — a real payment method is expensive to farm.
  • Device fingerprinting. Combine IP, user agent, and browser characteristics to detect multiple accounts on the same device.

No single measure is sufficient; the layering makes farming expensive. The goal is not to prevent every fake account but to make the cost of creating one exceed the value of the abuse.

Anomaly detection

Fixed rate limits catch the obvious patterns. Anomaly detection catches the subtle ones:

  • Sudden rate increase. A user whose traffic is normally 10 requests/minute suddenly sends 500 — flag for review or apply a temporary lower limit.
  • Distributed pattern. Many IPs, same user agent, same request signature — likely a botnet or a scraping service.
  • Endpoint targeting. A user who suddenly hits a single expensive endpoint repeatedly — likely scraping or a runaway script.
  • Geographic anomalies. Requests from a country the user has never used the API from — possible compromised account.
  • Repeated 429s. A user who consistently hits the limit — either a buggy client or a deliberate over-user; either way, worth flagging.

Anomaly detection complements fixed limits: the fixed limit catches the known patterns, the anomaly detection catches the unknown ones. The result is a system that is resilient to both naive and sophisticated abuse.

The abuse escalation ladder

Rate limiting should escalate, not just reject:

  1. Warning — return rate limit headers on every request, alert at 80% and 95%.
  2. Throttle — reduce the rate for the specific client (Question 9) before rejecting.
  3. Reject — 429 with Retry-After.
  4. Temporary ban — block the client for minutes or hours after repeated over-use.
  5. Permanent ban — disable the API key or account after egregious abuse; require a human to review.

Each step is more severe; escalation is based on the pattern and persistence of the over-use, not on a single violation. A client that hits the limit once gets a 429; a client that hits it continuously gets throttled; a client that bypasses the limit gets banned.

Rate limiting is not security

The most important point: rate limiting raises the cost of abuse; it does not prevent it. An attacker who is willing to spend enough (compute, accounts, proxies) will bypass any rate limit. The complete defence requires:

  • Rate limiting (this volume).
  • Authentication and authorization (Volume 6).
  • Input validation and injection prevention (Volume 14).
  • Encryption in transit and at rest.
  • Monitoring and anomaly detection.
  • Incident response for active attacks.

Each layer contributes. Rate limiting is one layer in a defence-in-depth strategy, not a substitute for the others.

Common Pitfall

Rate limiting only on the API key. An attacker who creates a new API key (or a new account) gets a fresh limit, bypassing the rate entirely. Always layer: per IP, per user, per tenant, per key — and limit account creation itself.

Interview Framing

Say: "Rate limiting on multiple axes — IP, user, tenant, key, operation — so no single bypass works. Limit account creation so farming is expensive. Layer anomaly detection for patterns the fixed limits miss. And remember: rate limiting raises the cost of abuse; it does not prevent it." That covers the strategy and the limitation in one sentence.
