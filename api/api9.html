Part A — Fundamentals What a gateway is, what it is not, and how it fits

1

What is an API gateway, and what problems does it actually solve?

Short Answer

An API gateway is a reverse proxy that sits at the edge of a microservices architecture and handles the cross-cutting concerns that would otherwise be duplicated across every service: authentication, authorization, rate limiting, routing, request/response transformation, observability, and versioning. It is not a piece of middleware — it is the single entry point for all client traffic, and the place where the public API contract is defined.

The problem it solves

Without a gateway, every microservice implements authentication, rate limiting, logging, and TLS on its own. The result is predictable:

  • Inconsistency. One service validates JWTs correctly, another forgets to check expiry, a third accepts unsigned tokens. Security becomes the weakest link.
  • Duplication. Six services, six rate limiters, each with slightly different configuration. A bug in one is a bug that affects everyone.
  • Coupling. Each service must know how to parse the client's API key, the JWT, the token refresh flow — all infrastructure concerns, not domain concerns.
  • No single view. No place to see "how many requests is the mobile app making?" — each service logs its own slice, and correlating across services is impossible.

The gateway centralises these concerns. A client's request arrives at one place, is authenticated once, is rate-limited once, is logged once, and is routed to the right service. The service sees an authenticated, authorised, rate-limited request with a correlation ID — its only job is to do the domain work.

The cross-cutting concerns a gateway handles

ConcernWhat the gateway doesWhy centralise
AuthenticationVerify API keys, JWTs, OAuth tokens, mTLSOne implementation, one set of secrets, one rotation policy
Authorization (coarse)Check scopes, roles, plansReject unauthorised requests before they reach a service
Rate limitingPer API key, per tenant, per userUniform policy; no service can be overwhelmed
RoutingPath, host, header, or weighted routing to servicesClients see a stable URL; services move internally
TransformationRequest/response rewrite, protocol translation (REST↔gRPC)Services can speak their native protocol
VersioningRoute /v1 to old services, /v2 to newMultiple versions coexist without service changes
ObservabilityAccess logs, metrics, trace propagationOne place to see all client traffic
ResilienceTimeouts, retries, circuit breakers, bulkheadsUniform policy, not per-service
AggregationCombine responses from multiple services (BFF)Reduce round trips for clients
SecurityWAF, IP allowlists, request size limitsBlock malicious traffic before it reaches services

What a gateway is not

  • Not a service mesh. The gateway handles north-south traffic (clients → system); the mesh handles east-west (service → service). They are complementary, not alternatives.
  • Not a load balancer. A load balancer distributes across instances of the same service; a gateway routes between services and applies policy. (The gateway does load-balance, but that is one of its jobs, not its primary purpose.)
  • Not a business logic layer. The moment the gateway has domain rules — "promotions apply only to non-enterprise tenants" — it has become a distributed monolith (Question 10).
  • Not a substitute for service-level authorization. The gateway can do coarse authorization (does this token have the scope?); the service must do fine-grained (does this user own this resource?). Both are required.

When to use a gateway

When the architecture has more than a handful of services, or when the API is public (so the consistency and observability matter). For a small monolith, an ingress controller or a simple reverse proxy is sufficient — a full gateway is over-engineering.

Interview Framing

Say: "The gateway is the single entry point — authentication, rate limiting, routing, and observability all happen there. Services see authenticated, rate-limited requests and focus on domain logic." That demonstrates the centralising purpose in one sentence.

What is the difference between an API gateway, a load balancer, and a service mesh?

Short Answer

A load balancer distributes traffic across instances of one service. An API gateway routes traffic between services and applies edge policy (auth, rate limiting, transformation). A service mesh handles service-to-service traffic with mTLS, retries, and observability. They operate at different layers and are complementary — a complete architecture often uses all three.

LayerWhat it doesTrafficExamples
Load balancer Distributes across instances of the same service; health checks; TLS termination Client → instance AWS ELB, NGINX, HAProxy
API gateway Routes between services; auth, rate limiting, transformation, versioning Client → service Kong, Apigee, AWS API Gateway, Envoy Gateway
Service mesh mTLS, retries, timeouts, circuit breaking, observability per service call Service → service Istio, Linkerd, Consul Connect

The load balancer

The simplest infrastructure layer. It receives traffic on a single address and distributes it across N instances of the same service. Its concerns are capacity and health — is any instance overwhelmed, is any instance unhealthy. It is L4 (TCP/IP) or L7 (HTTP path/host). It does not know about authentication, scopes, or service boundaries.

A gateway often includes load balancing as one of its functions, but the two are conceptually distinct. A standalone load balancer is right when there is only one service (no routing needed) — for example, a load balancer in front of a monolith.

The API gateway

The edge layer for a multi-service architecture. It knows about service boundaries — "route /users to user-service, /orders to order-service" — and applies cross-cutting policy. It is a superset of what a load balancer does; it also authenticates, rate-limits, transforms, and versions.

The gateway is the place where the public API contract is defined. Clients see /v1/users, not user-service-7f3a.internal:8080. This abstraction is what allows services to move, split, merge, or be rewritten without breaking clients.

The service mesh

The internal communication layer. It handles the calls between services — service A calling service B, service B calling the database, service C calling the cache. Its concerns are security (mTLS — every call encrypted and authenticated), reliability (retries, timeouts, circuit breakers, bulkheads), and observability (per-call metrics, trace propagation).

The mesh is not aware of the public API. It sees internal service names and internal traffic, not client requests. Its job is to make internal communication reliable and secure, not to define the API surface.

How they compose

Request pathHandled by
Client → CDNCDN (edge caching, DDoS)
CDN → load balancerLoad balancer (TLS, distribution)
Load balancer → API gatewayGateway (auth, rate limit, routing)
Gateway → service AService mesh sidecar (mTLS, retries)
Service A → service BService mesh (mTLS, retries, circuit breaker)
Service B → databaseService mesh or direct (depending on policy)

Each layer has a single job. The CDN absorbs static content and DDoS; the load balancer distributes TLS connections; the gateway routes and applies edge policy; the mesh secures and stabilises service-to-service communication.

The overlap question

Modern gateways and meshes overlap. Envoy can act as a gateway, a mesh sidecar, and a load balancer. Istio includes a gateway component (Istio Gateway) that uses Envoy as the underlying proxy. Kong can be deployed as an ingress controller in Kubernetes, blurring the line with a load balancer.

The overlap is fine — the technology is converging. What matters is the conceptual model: which layer is responsible for which concern. A request should be authenticated at the gateway, secured with mTLS at the mesh, and load-balanced at both. The technology can be unified; the responsibility boundaries should not be.

When you need which

  • One service, small team: a load balancer (or an ingress controller). No gateway, no mesh.
  • Several services, external clients: a load balancer + a gateway. The mesh is optional if the services are few.
  • Many services, multi-language, compliance requirements: all three. The mesh provides uniform mTLS and observability; the gateway provides the edge; the load balancer distributes.
  • Public API with a small internal team: a gateway (managed, like AWS API Gateway or Kong Cloud) is often enough. A full mesh is over-engineering.
Trade-off

A service mesh gives the strongest security (mTLS by default) and observability, but adds a control plane and per-pod proxies — a real operational cost. A gateway gives the strongest edge policy but does not secure internal traffic. A load balancer is the simplest but does no policy. Use each at its layer; do not use one to do another's job.

Interview Framing

Say: "The load balancer distributes; the gateway authenticates and routes; the mesh secures internal calls with mTLS and provides retries. They operate at different layers — client-to-service, service-to-service, instance-to-instance — and are complementary." That demonstrates the layering and its purpose in one sentence.

What is the difference between north-south and east-west traffic?

Short Answer

North-south traffic enters the system from outside — clients calling the API. It flows vertically through the CDN, load balancer, gateway, and into the services. East-west traffic flows horizontally between services inside the system — order-service calling user-service, payment-service calling the database. The gateway handles north-south; the service mesh handles east-west. The distinction determines the appropriate tooling and security model.

DimensionNorth-southEast-west
DirectionExternal → internalInternal ↔ internal
SourceClients (browsers, mobile, partners)Services within the cluster
IdentityUser (JWT, session, API key)Service (mTLS, SPIFFE)
Threat modelUntrusted clientsTrusted services (but zero-trust assumes the worst)
Rate limitingPer client, per API key, per userPer service, per endpoint
ToolingCDN, load balancer, API gateway, WAFService mesh, sidecars, client libraries
Latency toleranceVariable — client is waitingTight — every millisecond counts in the call chain
Failure handlingRetry, degrade gracefully, show errorCircuit breaker, fallback, timeout

Why the distinction matters

  • Different identity models. North-south traffic is from untrusted clients; identity is user-based (JWT, session). East-west traffic is from services; identity is service-based (mTLS, SPIFFE). Mixing them — accepting user JWTs for internal calls, or requiring mTLS on public endpoints — is a design smell.
  • Different policy. Rate limits for a client are per-user or per-API-key; rate limits between services are per-endpoint or per-service. A gateway that applies client rate limits to internal calls is throttling the wrong thing.
  • Different tooling. North-south uses a CDN, load balancer, and gateway. East-west uses a service mesh or shared client libraries. Using the wrong tool means extra complexity or missing protection.
  • Different threat model. North-south is exposed to the internet — DDoS, injection, botnets. East-west is inside the network, but zero-trust assumes the internal network is untrusted too, which is why mTLS is essential.

The classic pattern

LayerNorth-southEast-west
EdgeCDN + WAF + DDoS—
Load balancingL4/L7 load balancerService mesh sidecar or client LB
API policyAPI gatewayService mesh policy (retries, timeouts)
IdentityJWT, session, API keymTLS, SPIFFE
ObservabilityAccess logs, client metricsPer-call traces, service metrics
Traffic managementCanary, blue-green, versioningWeighted routing, fault injection

The hybrid reality

Some requests span both directions. A user request comes north-south into the gateway, then fans out east-west to several services. The gateway handles the north-south portion; the mesh handles the east-west portion; the correlation ID flows through both, so the whole request can be traced end-to-end.

The mistake: applying north-south policy in the east-west path, or vice versa. For example, requiring user JWTs for internal service calls — which means every service must validate JWTs, duplicating the gateway's job. Or applying per-client rate limits to internal calls, which means a burst from one client can throttle the service's calls to its dependencies.

Where the boundary blurs

The public API is north-south. A service that exposes a public-facing endpoint but also calls other services internally has both. A mobile app calling an API endpoint that the app also uses internally for other purposes crosses the boundary. The design principle: classify the request by its origin (client vs service), not by its destination. A request from a client is north-south regardless of where it ends up; a request from a service is east-west regardless of which service it hits.

Common Pitfall

Putting the service mesh in front of external traffic. A mesh sidecar is designed for east-west, with mTLS and internal-only identity. Exposing it directly to clients means managing client certificates and dealing with all the mesh's assumptions about trusted callers. Use a gateway for north-south; use the mesh for east-west. They serve different purposes.

Interview Framing

Say: "North-south is clients calling in — CDN, load balancer, gateway, user identity, per-client rate limits. East-west is services calling each other — service mesh, mTLS, per-service policies. The boundary is the origin of the request, not the destination." That demonstrates the distinction and its implication in one sentence.

How do you design routing at the gateway — path, host, header, weight?

Short Answer

Routing decides which service handles a request. The four mechanisms: path (URL prefix — /users/*), host (subdomain — users.api.example.com), header (custom header — X-Version: 2), and weight (percentage — 10% to canary). Real gateways combine them, with a priority order and a fallback. The routing rules must be declarative, versioned, and testable — they are part of the API contract.

Path-based routing

The most common mechanism. The URL prefix determines the service:

PathService
/users/*user-service
/orders/*order-service
/payments/*payment-service
/admin/*admin-service (with additional auth)
/*fallback — usually 404 or a default service

The gateway matches the path prefix and forwards to the service. Most gateways support: exact match (/users), prefix match (/users/*), and regex match (/users/[0-9]+) — in that order of preference, from most specific to least.

Trade-off: path routing is simple and visible, but it couples the URL structure to the service boundaries. If user-service is later split into user-service and profile-service, the /users/* rule must be split into /users/* and /profiles/* — a routing change that must be coordinated.

Host-based routing

Different subdomains route to different services (or different versions):

HostService
api.example.comPublic API gateway
admin.example.comAdmin gateway (different auth)
partners.example.comPartner API (different rate limits)

Host routing is useful when different audiences need different policies. The public API and the admin API have different authentication, different rate limits, and different SLAs — keeping them on different hosts keeps the policies cleanly separated.

Header-based routing

A custom header selects the service or version:

HeaderRoutes to
X-API-Version: 2v2 of the service
X-Beta-Feature: new-checkoutA beta deployment
X-Internal-Caller: trueInternal-only endpoints
X-Canary: trueThe canary deployment

Header routing is useful for:

  • Versioning — clients send the version they want, the gateway routes accordingly (Volume 3, Question 2).
  • Beta testing — internal users or opted-in customers get the new version.
  • Debugging — a support engineer can route a specific request to a specific version to reproduce a bug.

The risk: clients can set headers, so a header-based route must be validated. X-Internal-Caller: true from an external client is a privilege escalation if trusted.

Weight-based routing (traffic splitting)

A percentage of traffic goes to each backend:

BackendWeight
orders-v190%
orders-v210%

This is the mechanism for canary deploys (Question 7) and gradual rollouts. The weights are adjusted over time — 10% → 50% → 100% — as confidence in the new version grows. If a problem appears, the weights can be reverted in seconds.

The split must be sticky per user for user-facing features — a user should not flip between v1 and v2 on every request. The gateway can hash a user identifier (from the JWT) to assign the user consistently to one bucket.

Combining mechanisms

Real routing is a priority-ordered set of rules:

PriorityRuleBackend
1X-Canary: true AND path = /orders/*orders-v2-canary
2path = /admin/*admin-service (with strict auth)
3path = /orders/*orders-v1 (with 10% weight to v2)
4path = /users/*user-service
5default404 (or a catch-all service)

The rules are evaluated in order; the first match wins. This is how canary deploys, versioning, and internal-only endpoints coexist.

Routing table as code

The routing table should be:

  • Declarative — expressed as YAML or a resource, not as imperative code.
  • Versioned — in git, with the same review process as application code.
  • Testable — a unit test can verify that /users/42 routes to user-service.
  • Deployable atomically — a routing change is a deployment, with the same rollback story.
  • Observable — every request logs which rule matched, so debugging is possible.

Gateways like Kong, Envoy, and AWS API Gateway support declarative routing. Treating the routing table as code means it can be reviewed, tested, and reverted — which is essential for a table that determines every request's fate.

Common Pitfall

Ordering routing rules incorrectly. A prefix match /* placed before /users/* means every request matches /* first, and /users/* is never reached. The rule order must go from most specific to least. Test the routing table with representative paths to verify the order.

Interview Framing

Say: "Path routing for service boundaries, host routing for different audiences, header routing for version and beta, weight routing for canary. Evaluated in priority order, declarative, in version control." That covers the four mechanisms and the operational discipline in one sentence.

What can request and response transformation at the gateway do, and what should it never do?

Short Answer

Transformation at the gateway can rewrite headers, change the protocol (REST to gRPC), add or remove fields, rename fields to match the public contract, and adapt the response shape for a specific client. It should never implement domain logic, hide business rules, or become the place where API semantics live — that is the path to a distributed monolith (Question 10).

What transformation can do

TypeExampleUse case
Header manipulation Add X-Request-ID, strip X-Internal-*, add Authorization for the backend Correlation, internal auth, hiding implementation details
Protocol translation REST/JSON on the outside, gRPC on the inside Public clients use HTTP; services use the efficient internal protocol
Field renaming Internal user_id becomes public userId Public contract differs from internal schema
Field filtering Remove internal_notes from the response Prevent leaking internal fields (defence in depth, not the only defence)
Field addition Add _links (HATEOAS), add request_id Enrich the response with metadata
Versioning shim Route /v1/users to the new service but translate the response to the v1 shape Migrate internal services without breaking old clients
Content negotiation Accept XML from an old client, return JSON to the modern client Support multiple formats
Compression gzip response bodies Reduce bandwidth (Volume 10)

What transformation should never do

  • Business logic. "Discount applies only if the customer is premium" is not a transformation — it is a domain rule. It belongs in the service, not in the gateway.
  • Aggregation beyond simple composition. Combining user and orders into one response is fine (BFF pattern, Question 6). Computing "the user's lifetime value" from those fields is business logic — it belongs in a service.
  • Authorization decisions. The gateway can do coarse auth (is the token valid? does the scope cover the operation?). Fine-grained auth (does this user own this resource?) requires the service's context.
  • Data consistency logic. Coordinating writes across multiple services is a distributed transaction (Volume 5 of the distributed systems series), not a transformation.
  • Long-running work. The gateway is on the hot path; it must respond in milliseconds. Anything that takes more than a few ms belongs in the service (async).
  • Validation logic beyond structure. The gateway can validate "the body is valid JSON and has a required field" — but "this email is already registered" is a domain rule that requires the database.

The slippery slope

A transformation starts small: rename one field, add one header. Then a client needs a different shape for a different endpoint, so a new rule is added. Then a bug requires a workaround, so another rule. Within six months, the gateway has hundreds of rules, no one understands the whole picture, and every change risks breaking something else. This is how a gateway becomes a distributed monolith.

The guardrails:

  • Every transformation must be justified by the public contract. If the public API does not require the transformation, do not add it.
  • Transformations must be declarative and testable. A rule in YAML with an associated test, not a Lua script buried in a config.
  • Review by the API owner. Someone responsible for the public contract must approve new transformations.
  • Deprecate unused transformations. The same discipline as API versioning — unused rules should be removed.

The BFF exception

The BFF pattern (Question 6) is the one place where substantial transformation is justified. A BFF is explicitly a per-client adapter: it takes the services' generic responses and shapes them for one specific client (mobile, web, partner). The transformation is the BFF's purpose, not a side effect. Even then, the BFF should be a separate service, not the gateway itself — so the gateway remains a thin, uniform layer.

Trade-off

Transformation lets the gateway present a stable public contract even as internal services change. But it also creates a hidden layer of logic that is hard to test, hard to debug, and hard to reason about. The pragmatic rule: transform only what the public contract requires, and always with tests.

Interview Framing

Say: "The gateway can translate protocol, rename fields, and filter internal data — but no business logic, no aggregation that computes derived values, no authorization beyond scopes. If a transformation needs domain context, it belongs in a service." That demonstrates the boundary clearly.

What is the BFF pattern, and when should you use it?

Short Answer

Backend-for-Frontend (BFF) is a pattern where each client type — mobile, web, partner — gets its own thin backend layer that aggregates and shapes the responses from the underlying services for that client. The BFF hides the service complexity from the client, reduces the number of round trips, and lets each client's needs evolve independently. It should be a separate service, not a function of the gateway.

The problem it solves

Without a BFF, a client talks directly to multiple services:

ClientRound trips needed
Web app loading the home screenusers, feed, notifications, recommendations — 4 calls
Mobile app loading the home screen4 calls, but only needs a subset of fields from each
Partner API reading customer data2 calls, but expects a different shape

Each round trip is latency (on mobile, hundreds of milliseconds), each response has fields the client does not need, and each client ends up with its own aggregation code that drifts from the others. The BFF moves the aggregation server-side: one call to the BFF, which fans out to the services in parallel, assembles the response, and returns exactly what that client needs.

The structure

LayerResponsibility
ClientRenders the UI; makes one call to the BFF
BFFAuthenticates the user; fans out to services; aggregates; shapes; returns
ServicesOwn their domain; expose generic APIs

Each BFF is a separate deployment, often owned by the team that owns the client. The mobile BFF is owned by the mobile team, the web BFF by the web team. This ownership is the key benefit — the BFF can evolve at the client's pace, without affecting other clients.

BFF vs API gateway

They are often confused, and sometimes implemented in the same technology. The differences:

AspectAPI GatewayBFF
PurposeCross-cutting concerns (auth, rate limit, routing)Client-specific aggregation and shaping
AudienceAll clientsOne client type
Business logicNoneClient-specific composition — which fields to include, which services to call
OwnershipPlatform / infrastructure teamClient team
DeploymentOne per environmentOne per client per environment
EvolutionSlow, coordinatedFast, independent

The gateway and the BFF can be deployed together (the gateway routes /mobile/* to the mobile BFF, which then routes to services). But they are different concerns — the gateway handles all clients uniformly; the BFF handles one client specifically.

When to use a BFF

  • Multiple heterogeneous clients. Mobile, web, and partner APIs with different needs — each gets its own BFF.
  • Complex aggregation. The home screen requires data from five services — the BFF composes the response in one round trip.
  • Client-specific optimization. Mobile needs minimal payloads; web needs more; partner needs a stable legacy shape.
  • Client teams want autonomy. The client team owns its BFF, deploys at its own pace, and does not need to coordinate with services for every UI change.

When not to use a BFF

  • Single client. If there is only one client, the BFF is just an extra hop. The services can be designed for that client directly.
  • Simple reads. If the client just fetches one resource from one service, no BFF is needed.
  • Small systems. A monolith with a few endpoints does not need a BFF layer; the API itself is the BFF.
  • Replacing proper service design. The BFF is not a fix for a badly decomposed service — if the services are chatty and slow, the BFF will be chatty and slow too.

The pitfalls

  • BFF becomes the new monolith. If the BFF accumulates business logic, it becomes a single point of coupling. The BFF should only compose and shape; the domain logic stays in the services.
  • BFF duplicated across clients. If mobile and web BFFs have identical code, they are the same BFF — share it, or make the clients use the same API.
  • Too many BFFs. One per client version, one per platform, one per region — the combinatorics explode. Consolidate where possible.
  • Synchronous fan-out at the BFF. The BFF calling five services sequentially is slower than the client calling them directly. The BFF must fan out in parallel and merge.

The GraphQL variant

GraphQL is a natural fit for a BFF — the schema defines the client-facing API, the resolvers fan out to services, and the client queries exactly what it needs. A GraphQL BFF gives the client control over field selection and shape, which is the essence of the BFF pattern taken further. The caveat: GraphQL adds complexity (Volume 12–13) and does not remove the need for aggregation logic in the resolvers.

Trade-off

A BFF reduces client round trips and gives each client team autonomy, but adds a deployment per client, a code layer to maintain, and a potential bottleneck if not fanning out in parallel. Use it when the client genuinely needs aggregation and has its own team; skip it when the client can talk to services directly.

Interview Framing

Say: "One BFF per client type — mobile, web, partner — each owned by the client team, each aggregating and shaping the underlying services. It is separate from the gateway; it is the client-specific adapter layer." That demonstrates the pattern, its ownership, and its relationship to the gateway.

How do you implement canary and blue-green deploys at the gateway?

Short Answer

Canary: route a small percentage of traffic (1%, 5%, 10%) to the new version, monitor error rates and latency, and gradually increase the percentage until 100%, or roll back if the canary shows problems. Blue-green: run two identical environments, route 100% of traffic to one (blue), switch 100% to the other (green) when ready, and roll back by switching back. Both rely on the gateway's ability to route and split traffic.

AspectCanaryBlue-green
Traffic splitPercentage-based, gradual100% all-at-once
Rollout timeMinutes to hoursSeconds
RollbackReduce canary weight to 0Switch traffic back to blue
CostCanary fleet is small (5–10% of capacity)Two full environments
RiskCanary traffic is limited; problems affect few usersIf green is broken, all users are affected immediately
Best forMost deploys; catching issues earlyMajor version changes, infrastructure migrations

Canary deployment

The standard pattern:

  1. Deploy the new version alongside the old, with its own service instances but the same database.
  2. Route 1% of traffic to the new version, either by random sampling or by hash of the user ID (sticky, so a user sees one version consistently).
  3. Monitor — error rate, latency p99, throughput, and business metrics (conversion, signups). Compare to the baseline from the old version.
  4. Increase gradually — 1% → 5% → 10% → 50% → 100%, with a pause and evaluation at each step.
  5. Roll back immediately if any metric regresses — set the canary weight to 0.

The critical requirement: the new version must be backward compatible with the old — same database schema, same API contract — because both versions run simultaneously. A schema change that breaks the old version cannot be canary-deployed; it requires an expand-contract migration (Volume 3, Question 4).

The traffic split mechanism

MethodBehaviourTrade-off
Random per-requestEach request has a 5% chance of going to canarySimple; but a user might flip between versions
Sticky per-userUsers in bucket 0–5% go to canary consistentlyConsistent experience; but a bucket is a fixed set of users
Header-basedInternal testers set X-Canary: trueTargeted testing; not representative traffic
GeographicOne region gets the canaryLimits blast radius; but regions differ in load

Sticky per-user is the right default for user-facing services, because it avoids the confusing experience of the same user seeing two different versions. Random per-request is fine for stateless API endpoints where each request is independent.

Blue-green deployment

The pattern:

  1. Two environments — blue (currently serving) and green (idle or on a previous version). Both are full capacity.
  2. Deploy the new version to the idle environment (green).
  3. Test green with smoke tests, canary traffic, or internal users.
  4. Switch the router — 100% of traffic moves to green, atomically.
  5. Monitor — if the new version has problems, switch back to blue.
  6. After confidence, blue becomes the next idle environment for the next deploy.

The critical requirement: the two environments must be isolated — no shared state that would cause issues when switching. A shared database is fine (both versions read the same data), but a shared cache or a shared connection pool is a problem.

The routing mechanism for both

The gateway (or an ingress controller) does the traffic split. The mechanism:

  • Weighted routing — the gateway has a rule that says "90% to orders-v1, 10% to orders-v2".
  • Header routing — X-Canary: true goes to v2.
  • Path routing — /canary/* goes to v2 (for internal testing).

The gateway is the right place for this because it can change the routing without redeploying the services. A canary deploy is a routing change, not a code change.

The observability requirement

Canary deploys only work if you can compare the canary's metrics to the baseline. This requires:

  • Version tagging — every metric is tagged with version: v1 or version: v2, so the comparison is possible.
  • Per-version dashboards — error rate, latency, throughput side by side.
  • Business metrics — conversion, signups, checkouts, not just technical metrics. A canary that is fast but breaks the checkout flow is worse than the baseline.
  • Alerts — automatic alerts if the canary's error rate exceeds the baseline by N%.

Without this observability, canary deploys are guesswork. With it, they are the safest deployment pattern available.

The database compatibility requirement

Both canary and blue-green require that both versions can run against the same database simultaneously. This means:

  • Schema changes must be backward-compatible — adding a column is fine; removing or renaming one requires expand-contract (Volume 3, Question 4).
  • New fields must have defaults — the old version does not set them, so the new version must handle their absence.
  • Data migrations must be idempotent — running them twice is safe, since both versions may trigger them.

Which to choose

  • Canary for most deploys. Gradual, low-risk, catches problems early.
  • Blue-green for infrastructure changes. Migrating to a new database engine, a new cluster, a new cloud — where gradual rollout is not possible.
  • Combined. Deploy to green, canary-test green with 1% of traffic, switch 100% if good. This gives the safety of canary with the atomic switch of blue-green.
Common Pitfall

Canary-deploying a database schema change that the old version cannot handle. The canary version writes a new column; the old version does not know about it; both crash. Canary requires backward-compatible schemas — if the schema is not compatible, use expand-contract first, then canary-deploy the code.

Interview Framing

Say: "Canary is gradual — 1% to 100% with monitoring and immediate rollback. Blue-green is atomic — two environments, switch traffic. Both require backward-compatible schemas, per-version metrics, and the gateway to route." That covers the patterns, their requirements, and the mechanism.

Should authentication be at the gateway, in the service, or both?

Short Answer

Both, with different jobs. The gateway does coarse authentication — validates the token, resolves the identity, rejects invalid requests with 401 before they reach any service. The service does fine-grained authorization — does this user own this resource? — using the identity the gateway forwarded. Defence in depth: the gateway is the first line; the service is the last line.

The case for gateway authentication

  • Uniform policy. Every request is authenticated the same way; no service can forget to validate a token.
  • Performance. Invalid requests are rejected at the edge, before consuming service resources.
  • Key and secret management. The signing keys, the OAuth client secrets, and the rotation policy are in one place.
  • Simplifies services. Each service receives a trusted identity header, not a raw token it must parse.
  • Observability. Authentication failures are logged in one place, making abuse patterns visible.

The case for service-level authorization

  • Resource ownership. "This order belongs to this user" requires the service's data — the gateway cannot know it.
  • Business rules. "Only admins of the tenant can delete" requires the tenant's role model — a service concern.
  • Context. Some authorization decisions need the resource state, not just the identity — the gateway does not have the resource.
  • Defence in depth. If the gateway is misconfigured, the service still enforces. If the service is called internally (bypassing the gateway), it still enforces.

The division of responsibility

ConcernGatewayService
Token signature and expiryYesDefence in depth (verify again if not trusting the gateway)
API key validationYesNo (trust the gateway's forwarded identity)
Identity resolution (user ID, tenant ID)YesUses the forwarded identity
Scope check (read:orders)YesDefence in depth
Role check (is admin)Sometimes (coarse)Yes (fine-grained)

The "trust the gateway" question

A common design: the gateway validates the token and forwards X-User-ID and X-Tenant-ID headers to the service. The service trusts these headers and does not re-validate the token. This is efficient — the service does not need to verify signatures or fetch user data.

The risk: if the service is reachable without going through the gateway (a misconfigured network policy, an internal caller bypassing the gateway, a compromised pod), an attacker can send X-User-ID: admin and the service will trust it. This is a real attack vector in Kubernetes environments where services are reachable within the cluster.

The mitigations:

  • Network isolation. The service accepts traffic only from the gateway (a network policy, a service mesh authorization rule).
  • Signed headers. The gateway signs the identity headers (mTLS or a JWT); the service verifies the signature. Adds complexity but eliminates the "trust the header" risk.
  • Service re-validation. The service verifies the token itself, not trusting the gateway. The most robust, but slower (a signature check or a lookup per request).

The pragmatic middle: network isolation (services only reachable via the gateway) plus periodic re-validation (the service verifies the token on a subset of requests, or on cache miss). This gives performance with defence in depth.

The alternative: no gateway auth

Some architectures put authentication entirely in the services, using a shared library. The library validates the token, resolves the identity, and provides the authorization helpers. The gateway only routes.

This is defensible when: the services are all in the same language (so a shared library is viable), there is no concern about one service forgetting the library, and the team prefers to keep the gateway thin.

The downside: every service must include the library correctly, update it when the auth model changes, and enforce it consistently. The risk of "one service forgot" is real — which is exactly what the gateway design prevents.

The recommendation

For most microservices architectures, the right answer is:

  1. Gateway: coarse auth — validate the token, resolve the identity, reject 401 before the request reaches the service. Forward the identity as a signed header or via mTLS.
  2. Service: fine auth — check scope, role, and resource ownership using the forwarded identity. Never trust client-supplied identity fields.
  3. Defence in depth — the service verifies the token or the signed header, so a gateway-bypass is still caught.
  4. Network isolation — the service cannot be reached from outside the cluster except via the gateway.

This gives the performance benefit of the gateway with the safety of service-level enforcement.

Common Pitfall

Trusting client-supplied identity headers (X-User-ID) without the gateway stripping them. A client can send X-User-ID: admin, the gateway forwards it unchanged, and the service believes the client is an admin. The gateway must strip any incoming X-User-* or X-Internal-* headers and set them itself.

Interview Framing

Say: "Gateway does coarse auth — token validation, identity resolution, 401. Service does fine auth — ownership, roles, business rules. Defence in depth: the service verifies the forwarded identity or the token itself, and network policy prevents bypassing the gateway." That covers the layering in one sentence.

How do you scale a gateway and prevent it from becoming a single point of failure?

Short Answer

Deploy the gateway as a horizontally scaled fleet of stateless instances behind a load balancer or DNS round-robin. Make the gateway stateless (no local session, no local rate limit state — those go to Redis). Deploy across multiple availability zones. Give the gateway its own capacity budget so it can absorb traffic spikes. And add a fallback path — a secondary gateway or a bypass — so a gateway outage does not mean a complete outage.

Why the gateway is a SPOF risk

Every client request goes through the gateway. If the gateway is down, the whole API is down — regardless of how healthy the services are. The gateway is therefore the most critical component to make highly available (Volume 1, Question 7).

The common mistakes:

  • One gateway instance. A single VM, a single container, a single pod — any failure is total.
  • Stateful gateway. Sessions stored in memory, rate-limit counters in memory, caches per-instance — a failure loses state, and load balancing is uneven.
  • Single AZ. All gateway instances in one datacenter — an AZ failure takes them all down.
  • Undersized. The gateway is provisioned at average load, and a spike saturates it — the gateway becomes the bottleneck that the services were designed to avoid.
  • No fallback. The gateway is the only path; there is no secondary or bypass.

Stateless deployment

The gateway should be stateless:

  • No sessions in memory. Sessions are in a shared store (Redis) or encoded in the token (JWT).
  • No rate-limit counters in memory. Counters are in Redis (Volume 7, Question 4), with a local fallback that is conservative (per-instance limit × instance count ≤ global limit).
  • No caches in memory. Response caches are in a shared cache or the CDN.
  • Config loaded from a central store. The routing table, the policies, the secrets — loaded from etcd, Consul, or a config service at startup and updated on change.

Statelessness lets the fleet scale arbitrarily and lets any instance serve any request.

Horizontal scaling

LayerScaling mechanism
DNSMultiple A records or anycast to multiple gateways
External load balancerDistributes across the gateway fleet
Gateway fleetN instances, autoscaled by CPU/connection count
Within the gatewayWorker threads or async I/O (Envoy, NGINX, Kong are event-driven)

The gateway must have headroom — its peak capacity should exceed the services' peak capacity, so the gateway is never the bottleneck. A gateway at 80% CPU is a gateway that will drop requests under a burst.

Multi-AZ deployment

Deploy the gateway fleet across at least two availability zones (preferably three). The external load balancer health-checks each instance and routes around failed AZs. An AZ failure leaves the other AZs serving.

For the highest availability, deploy the gateway in multiple regions with GeoDNS or anycast. A regional failure routes traffic to another region.

The capacity budget

The gateway is on the hot path for every request, so its capacity must be sized for the peak, not the average:

  • Baseline capacity — enough instances to serve average load at 40% CPU.
  • Autoscaling — add instances when CPU exceeds 60%, remove when below 30%.
  • Reserved capacity — a minimum fleet size (e.g., 3 instances) even at low load, so a sudden spike does not outrun the autoscaler.
  • Load shedding — if the gateway reaches its capacity limit, shed low-priority traffic (Volume 7, Question 7) rather than crashing.

The fallback path

Even a highly available gateway can have a bad day — a bad config push, a dependency outage, a DNS issue. The fallback:

  • A secondary gateway in a different region, with the same routing table, reachable via a different DNS name. The client (or a smart DNS service) can switch to it if the primary is unreachable.
  • A static maintenance page served by the CDN, so the client sees "we are doing maintenance" rather than a connection error.
  • A read-only bypass for critical endpoints — a direct path to the services for GET requests, bypassing the gateway's policy, for emergencies.

The fallback should be tested — the same as any other failover mechanism.

The config rollout safety

The gateway is frequently changed — routing rules, rate limits, auth policies. Each change is a potential outage. The safety measures:

  • Config as code, reviewed in PRs, tested with unit tests.
  • Staged rollout — apply the config to a canary gateway instance, verify, then roll out to the fleet.
  • Automatic rollback — if the error rate spikes after a config change, revert automatically.
  • Dry-run mode — some gateways support validating a config change against production traffic without applying it.

The worst gateway outage is a config error — a bad routing rule that drops all traffic, a typo in the auth policy that rejects everyone. The config discipline prevents these.

Common Pitfall

Storing rate-limit counters in the gateway's memory. With N gateway instances, the effective limit is N × the configured limit — a client's requests are spread across instances, each with its own counter. Rate limits must be in a shared store (Redis), not per-instance, or the limit is meaningless.

Interview Framing

Say: "The gateway is stateless, horizontally scaled, multi-AZ, with headroom for bursts, and a secondary path for fallback. Config is code, rolled out gradually, with automatic rollback. The gateway is the most critical component — it must be the most available." That covers the architecture and the operational discipline.

How do you prevent the gateway from becoming a distributed monolith?

Short Answer

A gateway becomes a distributed monolith when it accumulates business logic, per-client branching, and domain rules that should live in services. The symptoms: hundreds of routing rules, transformation scripts that nobody understands, per-endpoint custom logic, and a gateway deployment that requires coordinating every team. The prevention: keep the gateway thin, put business logic in services, use the BFF pattern for client-specific shaping, and treat the gateway as infrastructure — not as an application.

The distributed monolith anti-pattern

A distributed monolith is a system that has the deployment topology of microservices but the coupling of a monolith. In the gateway context, it manifests as:

  • Business logic in the gateway. "If the request is from a premium tenant and the product is on sale, apply the discount" — implemented as a gateway rule, not a service call.
  • Hundreds of per-client rules. "For the mobile v2.3.1 client on iOS 17, transform the response to include..." — the gateway becomes a compatibility layer for every client version.
  • Orchestration. The gateway calls service A, uses the response to call service B, combines the results, and applies conditional logic — this is business process orchestration, not API gateway work.
  • Stateful workflows. The gateway holds state between requests — shopping cart sessions, multi-step wizards, progressive onboarding — which should be in a service.
  • A shared deployment. Every team's change requires a gateway deployment, and the gateway team becomes a bottleneck for every product change.

Each of these is a sign that the gateway is no longer a thin proxy — it is becoming an application that happens to live at the edge.

Why it happens

  • It is easy. A routing rule or a transformation script is faster to write than a new service endpoint.
  • It avoids service changes. A client needs a slightly different response, and the service team is busy — the gateway team adds a transformation.
  • It centralises observability. "We need to log every request with these fields" — the gateway is the place to do it, so the gateway grows.
  • It is invisible. Gateway logic does not go through the same review as service code. A transformation here, a rule there, and suddenly it is 10,000 lines of config.

The prevention

RuleWhy
No business logic. The gateway routes, authenticates, rate-limits, and transforms structurally — nothing more. Business logic requires domain knowledge and tests; the gateway is not the place for it.
BFF for client-specific shaping. If a client needs a different response, it gets a BFF, not a gateway transformation. The BFF is owned by the client team, deployed independently, and can evolve without affecting others.
Thin gateway config. Under a few hundred rules; most requests match a simple prefix. The gateway's value is uniformity; complexity defeats it.
Reviewed by the API owner. Every new rule or transformation requires approval from someone responsible for the public contract. Prevents the slow accumulation of ad-hoc rules.
Tested transformations. Every transformation has a unit test that verifies the input → output. Untested transformations are bugs waiting to happen, and impossible to change safely.
Versioned and deprecated. Old rules are removed, not accumulated. Like API endpoints, gateway rules have a lifecycle.
Separate from the deployment pipeline. The gateway's config is deployed independently of the services — the services can deploy without the gateway, and the gateway without the services. Prevents the gateway from being a coordination point for every service deploy.
Declarative, not imperative. YAML or a declarative DSL, not a general-purpose language like Lua. The declarative form makes the config visible, reviewable, and bounded.

The BFF as the pressure valve

The BFF pattern is the escape hatch for client-specific needs. When a client needs a different response, a different aggregation, or a different shape, the answer is not a gateway rule — it is a BFF. The BFF is a separate service, deployed by the client team, with its own tests and its own life. This keeps the gateway thin and lets the client's complexity live where it belongs.

The BFF is not a panacea — a BFF that accumulates business logic is just a smaller distributed monolith. The BFF's job is composition and shaping, not domain logic. The services still own the domain.

The health check

How do you know the gateway is becoming a distributed monolith? The signals:

  • Rule count growing. More than a few hundred rules is a warning sign; more than a thousand is a problem.
  • Per-client rules. If the routing table has rules that mention client versions, the gateway is becoming a compatibility layer.
  • Deployment frequency rising. If the gateway deploys more often than the services, it is accumulating logic.
  • The gateway team is a bottleneck. If every product change requires a gateway change, the gateway is coupled to every team.
  • Complex config. If a new engineer cannot understand the routing table in a day, it is too complex.

Any of these signals should prompt a review: what is in the gateway that should be in a service?

The refactoring path

If the gateway has already become a distributed monolith, the refactoring:

  1. Extract business logic into services. Identify the gateway rules that contain domain logic, and move that logic into the service that owns the domain.
  2. Extract per-client logic into BFFs. Identify the transformations that serve one client, and move them into a BFF for that client.
  3. Simplify the routing. Reduce the routing table to path-based routing for service boundaries; move everything else into the services.
  4. Retire unused rules. Many gateway rules are no longer needed — the clients that needed them have been updated, the services have changed, the versions have been deprecated.
  5. Establish review. New rules require approval from the API owner.

The refactoring is not trivial — the gateway is on the hot path, and every change carries risk. But the alternative — a gateway that grows unboundedly — is worse: it becomes unmaintainable, the team becomes a bottleneck, and the distributed monolith slowly grinds to a halt.

Trade-off

A thin gateway is simple but requires that every client-specific need be addressed elsewhere — in a BFF or a service. A thick gateway is flexible in the short term but becomes unmaintainable in the long term. The discipline is to keep the gateway thin and pay the cost of proper service design.

Interview Framing

Say: "The gateway is infrastructure — routing, auth, rate limits — nothing more. Client-specific shaping goes in a BFF, owned by the client team. Business logic goes in the service. Every gateway rule needs review, and unused rules are removed." That demonstrates the discipline and its boundaries in one sentence.
