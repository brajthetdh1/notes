Part A — Modeling Resources What is a thing, what is a collection, and where do they live

1

How do you model resources and collections in a REST API?

Short Answer

A resource is a named thing the API exposes — a user, an order, a comment. A collection is a resource that is a set of other resources — /users, /orders. Every resource has a URL, a representation, and a set of methods. Collections hold resources; resources belong to one or more collections; the whole API is a graph of resources linked by URLs.

Resources vs collections — the two fundamental shapes

Every well-designed REST API reduces to these two shapes. A collection is an enumerable set — you can list it, filter it, paginate it. A resource is a single identified item — you can fetch it, update it, delete it. The distinction matters because the semantics differ:

AspectCollectionResource
URL shape/users/users/42
Primary operationGET — list, filtered, paginatedGET — fetch by identifier
CreationPOST — create a new memberRarely created directly
Response typeArray (or paginated envelope)Single object
IdentityImplicit — the set itselfExplicit — via path parameter
DeleteUsually not supported (mass delete)DELETE /users/42

What qualifies as a resource

A candidate is a resource if it has three properties: identity (it can be referenced), state (it has attributes worth exposing), and lifecycle (it can be created, updated, and deleted independently). A user is a resource. A user's name is an attribute of a resource, not a resource. A user's addresses are a resource (they have identity, state, lifecycle) — a sub-collection of the user.

This test rules out things that engineers often wrongly model as resources: search results (not a thing, a query), aggregations (a computation over things), and transient operations (a transfer is an action, not a noun). When the model starts to include non-resources, the API is drifting toward RPC — which is fine if it is a deliberate choice, but is a problem if it is an accidental one.

The domain model vs the API model

The API model is not the domain model. The domain model includes internal entities, invariants, and relationships that clients do not need to see. The API model is a narrow projection of the domain designed around what clients actually need to do. This means:

  • Not every database table is a resource. Some are internal bookkeeping.
  • One API resource can aggregate several tables. A product resource might combine rows from products, prices, inventory.
  • Some domain concepts become attributes, not resources. A product's "on sale" flag is an attribute; its sale events might be a sub-collection if clients need them.
  • The API model changes for client reasons, the domain model for business reasons — keeping them separate lets each evolve.

The three questions that decide resource boundaries

  1. Does the client reference this thing by identifier? If a client asks for /orders/42, orders are a resource. If the client only ever asks for "the current user's orders", orders might be a sub-collection or a filtered view.
  2. Does it have its own lifecycle? Can this thing be created, updated, or deleted independently? If yes, it is likely a resource; if its lifecycle is entirely tied to a parent, it might be an attribute or an embedded object.
  3. Does it have meaningful state on its own? If it has five or more attributes the client cares about, it is probably a resource. If it is a name-value pair, it is probably an attribute.

Sub-collections

A resource can own sub-resources. /users/42/orders is the collection of orders belonging to user 42. This is useful when the sub-resource is genuinely scoped to the parent — an order always belongs to exactly one user, so /users/42/orders is a natural URL. It is a problem when the sub-resource exists independently — an order can be looked up directly by its own ID, so /orders/42 is usually better than /users/7/orders/42.

Collections are not just filters

A common design mistake is to treat every filter as a collection. /users/active is not a collection — it is a filtered view of /users. The correct form is /users?status=active. Collections are defined by the resource type, not by the predicate. Getting this wrong multiplies the URL surface and makes the API harder to consume.

Interview Framing

Say: "I'll model users, orders, and products as resources with their own URLs. Order lines belong to an order, so I'll expose them as a sub-collection under /orders/{id}/lines, not a top-level resource — they don't have an independent lifecycle." That sentence demonstrates the boundary test.

How do you name resources in URLs? Plural vs singular, nouns vs verbs?

Short Answer

Use plural nouns for collections (/users), and plural nouns plus an identifier for a single resource (/users/42). Use nouns, not verbs — the HTTP method supplies the verb. Use lowercase, hyphens between words, and no file extensions. URLs are stable, human-readable identifiers, not sentences.

The naming rules

RuleGoodBad
Plural for collections/users/user
Plural + ID for members/users/42/user/42
Nouns, not verbsPOST /ordersPOST /createOrder
Lowercase/users/42/profile/Users/42/Profile
Hyphens, not underscores/order-items/order_items
No trailing slash/users/42/users/42/
No file extensions/users/42/users/42.json
No deep nesting for unrelated items/orders/42/users/7/orders/42

Why plural

Plural is the convention because it makes the collection the base case. /users is a set; /users/42 is a member. If you started with singular, you would have /user for the collection and /user/42 for the member, which is inconsistent — /user reads like a single resource with no identifier, but it is actually a collection. Plural is more honest about what the URL represents, and it is what every major public API does (Stripe, GitHub, Twilio, Slack).

The one exception people sometimes make is for singletons — a user has one profile, one settings object. Some APIs use /users/42/profile (singular) for such singletons, on the logic that there is only one. This is defensible, but the simpler rule — always plural — is easier to apply consistently and is what most style guides recommend.

Why nouns, not verbs

In REST, the verb is the HTTP method. POST /orders means "create an order in the orders collection". POST /createOrder means "post to an endpoint whose name happens to be a verb". The second is technically functional but abandons the uniform interface — the client cannot generalise because every operation has its own ad-hoc URL. The verb-in-URL pattern also makes it impossible to express the same resource in multiple ways — you cannot list, filter, and search the same "createOrder" resource.

Verbs in URLs are not always wrong — for actions that genuinely have no resource representation, a verb is the right answer (Question 7). But for CRUD operations, the HTTP method already provides the verb, and adding it to the URL is redundant and harmful.

Words with spaces and special characters

Multi-word resource names should use hyphens, not underscores or camelCase. /order-items, not /order_items or /orderItems. Hyphens are the standard across the web, are SEO-friendly, and are unambiguous in URLs. Underscores can be confused with spaces in some rendering contexts; camelCase requires case-sensitive comparisons that some systems mishandle.

Case sensitivity

URL paths are case-sensitive by spec, but many systems (proxies, caches, browsers) treat them case-insensitively. The safest approach is to use lowercase everywhere, so case never matters. If you use camelCase in identifiers, be aware that some clients will normalise them, and some CDNs will treat /users/42 and /Users/42 as different cache entries.

Identifiers in URLs

The identifier in /users/{id} should be stable and public. This is why auto-increment integer IDs are a mixed choice for public APIs — they leak volume and are enumerable. UUIDs are safer but uglier. The common solution is a separate public identifier (a slug, an opaque token, or a UUID) distinct from the internal primary key. Stripe uses prefixed opaque IDs (cus_abc123) which are neither sequential nor guessable.

URLs as stable identifiers

Once a URL is published, it is a contract. Clients bookmark it, hardcode it, log it, and cache it. Changing /users to /people breaks everyone. This is why the naming decision deserves more care than the schema decision — a schema can be versioned, a URL cannot (except by keeping the old one around forever). Choose names carefully, and stick with them.

Common Pitfall

Mixing conventions in the same API. /users next to /order_items next to /Products is a sign that no one designed the API — it just grew. A style guide and a linter (Spectral, OpenAPI Validator) enforce consistency at build time, which is the only reliable way to keep it.

How deep should URL nesting go, and when do you flatten?

Short Answer

Nest only when the sub-resource cannot exist without its parent. One level of nesting is usually fine, two is the maximum, three is a warning sign. When a resource has its own identity and can be looked up independently, flatten it to a top-level collection and use a query parameter to express the relationship.

The two competing URL styles

StyleExampleWhen it fits
Nested/users/42/ordersThe sub-resource is scoped to the parent; there is no meaningful "order" outside a user context
Top-level with filter/orders?userId=42The sub-resource is independent and globally addressable
Both/users/42/orders and /orders/42The client needs both perspectives

The test: can it exist independently?

The simplest test is: does the child resource have its own identifier that is meaningful outside the parent? An order has order_id; it is referenced in shipments, invoices, and payments. It exists independently of the user. A user's address is usually identified only by user and address number — address_id is meaningful only in the user's context. So:

  • Independent identity → top-level. /orders/42, and optionally /users/7/orders as a convenience sub-collection.
  • Dependent identity → nested. /users/42/addresses/3, because the address's identity is scoped to the user.

The problem with deep nesting

Deep nesting looks tidy on a whiteboard but degrades in every operational dimension:

  • URLs become rigid. /users/7/orders/42/lines/3 forces every lookup through every parent. If the client only knows the line ID, it cannot find it without knowing the user and order.
  • Authorization is harder. Each level implies a check — is the user allowed to see this order, and this line within it? Deep nesting makes every authorization a chain of checks, each of which can fail. Flatter URLs make auth a single check.
  • Caching is fragmented. /users/7/orders and /users/8/orders are different cache entries even if they hold the same data. Deep nesting multiplies cache entries with no benefit.
  • Versioning is harder. Changing the parent's URL changes the child's URL. A version bump on users cascades to every nested resource.
  • Refactoring is harder. Splitting a parent into two means rewriting every child URL.

The pragmatic rule

A defensible rule that many public APIs follow:

  1. Top-level collections for every independently addressable resource. /users, /orders, /products.
  2. One level of nesting for sub-collections that are genuinely scoped to the parent. /users/42/addresses, /orders/42/lines.
  3. Never two or more levels. If you find yourself writing /users/42/orders/42/lines/3, stop — the line has a top-level URL and the user linkage is a query parameter.
  4. Accept both forms when the client needs both. /orders/42 and /users/7/orders/42 can both exist and return the same resource, with the second verifying that the order belongs to the user.

Why the "one level" rule works

One level of nesting mirrors the actual data model — most child resources belong to exactly one parent, and the parent is what the client has in hand. Deeper nesting implies a hierarchical relationship that usually does not exist; a line belongs to an order, and an order belongs to a user, but the line does not belong to the user in any meaningful way. Modelling the true structure (one level) and expressing other relationships via filters is both more accurate and more usable.

When nesting is genuinely the right answer

Some resources really do lack independent identity. A settings object, an address, an order line, a permission grant — these exist only in the context of a parent, and their URLs reflect that. For these, nesting is not a compromise, it is the correct model. The question is not "should I nest?", it is "does this thing have identity outside its parent?" — and the answer should be based on the domain, not on aesthetics.

Interview Framing

Say: "Orders have their own ID and are referenced from shipments and payments, so they live at /orders/{id}. Order lines don't have identity outside an order, so they're at /orders/{id}/lines." That demonstrates you are applying the identity test, not a stylistic rule.

What is the difference between PUT, PATCH, and POST for updates?

Short Answer

PUT replaces the resource entirely — the client sends the full representation, and omitted fields are removed or reset. PATCH applies a partial update — the client sends only the fields to change. POST creates a new resource in a collection. Using PUT for partial updates is the most common and most damaging mistake in REST API design.

AspectPUTPATCHPOST
SemanticsReplace entire resourceApply partial modificationCreate new resource
Body containsFull representationOnly the fields to changeFields for the new resource
Omitted fieldsRemoved / reset to defaultLeft unchangedN/A
IdempotentYesNot guaranteedNo
Target URLSpecific resource (/users/42)Specific resource (/users/42)Collection (/users)
Response200 or 204200 or 204201 with Location

PUT — full replacement

PUT means "make the resource at this URL look exactly like this body". It is a replace, not an update. If a user has fields {name, email, phone} and the client PUTs {name: "Alice"}, the result is a user with name: "Alice" and email: null, phone: null — because the body is the complete new state.

This is why PUT is well-suited to idempotent, full-document resources — configuration files, settings documents, and data where the client holds the full representation. It is a poor fit for entities with many fields that the client only partially knows, because every PUT risks wiping fields the client did not include.

PATCH — partial update

PATCH means "apply this change to the resource". A PATCH body of {email: "alice@example.com"} updates only the email; the name and phone remain unchanged. This is what most applications actually want, because clients rarely hold the entire resource — they edit one field on a form and submit the change.

PATCH is not guaranteed idempotent in the HTTP spec, because the patch format could be non-idempotent (e.g., "increment a counter by 1"). In practice, most PATCH bodies are JSON objects that merge into the resource, which is idempotent — applying the same PATCH twice gives the same result. But the spec allows non-idempotent semantics, so retries must be considered carefully. The safest design is to make PATCH idempotent in your API and document it.

The PATCH format problem

PATCH does not specify a body format. The two common ones:

  • JSON Merge Patch (RFC 7396) — a JSON object whose fields are merged into the target. {"email": "new@x.com"} changes email. {"email": null} removes the field. Simple, intuitive, and what most APIs use.
  • JSON Patch (RFC 6902) — a list of operations: [{"op": "replace", "path": "/email", "value": "new@x.com"}]. More powerful (can reorder arrays, test preconditions), but more verbose and rarely needed.

The choice matters because the semantics differ. JSON Merge Patch cannot express "set this field to null" separately from "remove this field". JSON Patch can, at the cost of verbosity. Most APIs should use JSON Merge Patch and document the limitation.

POST — creation, and the "action" escape hatch

POST to a collection creates a new member. The server generates the ID and returns 201 Created with a Location header pointing at the new resource.

POST is also the correct method for operations that are not CRUD — POST /orders/42/cancel, POST /payments. These are actions that create a new resource (the cancellation, the payment) or that change state in ways not expressible as PUT or PATCH. Using POST here is correct because POST is the method of "anything not otherwise specified", and these operations do not fit the replace or partial-update semantics of PUT/PATCH.

The cardinal sin: PUT for partial updates

Many APIs use PUT for partial updates, treating it as "the update method". This breaks the HTTP spec and causes real bugs: a client that PUTs {email: "new"} silently wipes the user's name and phone. This is not a theoretical concern — it is the most common data-loss bug in poorly designed REST APIs. If partial updates are needed (and they almost always are), PATCH is the right method.

If a client genuinely wants to replace the whole resource, PUT is correct. If it wants to change one field, PATCH is correct. The methods are not interchangeable, and treating them as such is a contract violation.

Trade-off

PUT is idempotent and simple to reason about, but requires the client to know the full resource. PATCH is ergonomic but requires the server to interpret a patch format and loses the idempotency guarantee unless you document it. For internal APIs where the client controls both sides, PATCH is almost always the right default; for public APIs, offering both (PUT for full replacement, PATCH for partial) is common.

What is the difference between safe and idempotent HTTP methods?

Short Answer

Safe means the method does not modify server state — reads are safe. Idempotent means the effect of calling it multiple times is the same as calling it once. Safety is about whether it changes anything; idempotency is about whether repeating it changes the outcome. GET, HEAD, OPTIONS, and TRACE are safe. GET, HEAD, OPTIONS, TRACE, PUT, and DELETE are idempotent. POST is neither.

MethodSafeIdempotentChanges state
GETYesYesNo
HEADYesYesNo
OPTIONSYesYesNo
TRACEYesYesNo
PUTNoYesYes — replace
DELETENoYesYes — remove
PATCHNoNot guaranteedYes — partial
POSTNoNoYes — create / action

Safety

A safe method does not change server state. GET, HEAD, OPTIONS, and TRACE are safe. This is why crawlers, prefetchers, and caches can issue them freely — the spec guarantees that a GET never modifies anything.

Violating safety is a real bug: a GET that creates a record, deletes a row, or sends an email is not safe, and any infrastructure that issues GETs speculatively (browsers, CDNs, bots) will cause unintended effects. The classic example is a GET endpoint that decrements an inventory count — a crawler indexing the site inadvertently sells out the stock. Every endpoint that changes state must be POST, PUT, PATCH, or DELETE.

Idempotency

An idempotent method's effect is the same whether called once or ten times. PUT is idempotent because the second PUT sets the resource to the same state as the first. DELETE is idempotent because deleting an already-deleted resource leaves it deleted — the state is the same. GET is idempotent because reading does not change anything.

POST is not idempotent because two POSTs create two resources. A retry of POST /orders after a network timeout may create two orders if the first one actually succeeded but the response was lost. This is the core reason POST requires an idempotency key for safe retries — the key lets the server detect that this is a retry, not a new request.

Why this matters for retries

The whole point of idempotency in HTTP is that a client or proxy can safely retry an idempotent method after a network failure. If a PUT times out, the client can retry — the result is the same. If a DELETE times out, retry — the result is the same. If a POST times out, retrying may duplicate the operation, so the client must either give up or use an idempotency key to make the retry safe.

This is why load balancers and API gateways sometimes retry idempotent methods automatically but never retry POST. The HTTP method is a signal that the retry is safe. Violating the convention breaks the infrastructure's ability to help you.

PATCH's ambiguous status

PATCH is not required to be idempotent by spec, because a patch could contain a non-idempotent operation ("append to list", "increment counter"). In practice, most PATCH bodies — JSON Merge Patch, JSON Patch with only replace operations — are idempotent. The pragmatic recommendation: design your PATCH endpoints to be idempotent when the operation permits, and document it clearly. Do not assume a PATCH is safe to retry unless you know the specific patch semantics.

DELETE and the "already deleted" question

DELETE is idempotent, but there is a subtle debate: what should a DELETE of an already-deleted resource return? Two defensible answers:

  • 404 Not Found — the resource does not exist, so return an error. Idempotent because the second call also returns 404.
  • 204 No Content — the resource is now deleted, which is what the client wanted. Idempotent because the second call also returns 204, and the state is correct.

Both are idempotent. The 404 approach is more informative; the 204 approach is more friendly to idempotent retries. Most modern APIs (Stripe, GitHub) return 404 on the second DELETE of a resource. Choose one and be consistent.

What idempotency does not mean

Idempotency does not mean the response is identical — only that the state is. DELETE /users/42 might return 200 the first time and 404 the second, but the state is "user 42 does not exist" in both cases. This distinction matters when you build retry logic: the retry succeeds if the state is correct, even if the response is different.

Common Pitfall

Treating idempotency as a binary property and assuming every POST needs an idempotency key. A POST that creates a genuinely new resource on every call does not — the client simply must not retry. The ones that need a key are POSTs whose duplicate execution would cause a harmful side effect (charging a card, sending an email, creating an order). Adding a key to every POST is unnecessary overhead.

What is the difference between PUT-as-create and PUT-as-update, and which should you use?

Short Answer

PUT-as-update assumes the resource already exists: a PUT to a known URL replaces its state, and 404 if it does not exist. PUT-as-create allows the client to choose the URL: a PUT to a URL that does not yet exist creates the resource, returning 201; a PUT to an existing URL replaces it, returning 200. Both are valid; which you choose depends on whether the client or the server owns identifier generation.

AspectPUT-as-updatePUT-as-create (upsert)
Who chooses the URLServer (in a prior POST)Client
Behaviour on missing resource404Creates it (201)
Behaviour on existing resourceReplaces (200)Replaces (200)
IdempotentYesYes
Client knows the IDOnly after creationBefore creation
Typical useServer-generated IDsClient-generated IDs, config, snapshots

PUT-as-update

The client creates a resource with POST, gets the ID from the server, and later updates it with PUT. The server controls identity. This is the more common pattern because it lets the server assign collision-free IDs (auto-increment, UUID, Snowflake) and enforce uniqueness without the client needing to know.

This pattern's strength is that it is unambiguous about state: "replace the resource at this URL, or tell me it does not exist". The client cannot accidentally create a resource by trying to update a nonexistent one. For most CRUD APIs, this is the right default.

PUT-as-create (upsert)

The client chooses the URL — usually by generating the identifier — and PUTs the full representation. If the resource exists, it is replaced (200); if not, it is created (201). This is an upsert.

The classic use case is client-side ID generation: a mobile app creates a note while offline, generates a UUID locally, and syncs later. The URL is known before the resource exists. PUT-as-create makes the sync trivially idempotent — the app can retry the PUT as many times as needed without creating duplicates.

Other use cases: configuration documents (PUT /configs/production — set it to this value, whether or not it exists), declarative resources (Kubernetes-style apply), and user-defined paths (a project named my-project lives at /projects/my-project, and the user chooses the name).

The status code distinction

The two behaviours return different status codes:

  • 200 OK — the resource existed and was replaced.
  • 201 Created — the resource did not exist and was created. Include a Location header pointing to the new resource (redundant if the client chose the URL, but good practice).
  • 204 No Content — sometimes used for 200 when the response body is empty.

Clients can use the status code to know whether their PUT created or replaced — useful for logging and metrics, though clients should not depend on it for correctness because a concurrent request could have created the resource between their check and their PUT.

The idempotency argument for PUT-as-create

The strongest argument for PUT-as-create is idempotency without idempotency keys. A POST-based create requires an idempotency key to be retry-safe (Volume 5 will cover this). A PUT-based create is idempotent by definition — the URL identifies the resource, and repeating the PUT is a no-op if the state is already correct. For mobile apps and unreliable networks, this is enormously valuable.

The cost is that the client must generate globally unique IDs. UUIDs are the standard answer; ULIDs or other time-ordered IDs are better for index locality (see the distributed systems series). Auto-increment IDs cannot be used here because the client cannot know the next value.

Which to choose

The decision is fundamentally about who owns identity:

  • Server owns identity → POST to create, PUT to update. The server generates the ID, the client learns it from the POST response, and subsequent updates use it.
  • Client owns identity → PUT-as-create. The client generates the ID, PUTs to the URL, and retries freely.
  • Hybrid — support both: POST for server-generated IDs, PUT with client-supplied ID for client-generated ones. This is what many modern APIs do, at the cost of more surface area.

The "PUT to a URL that does not exist" trap

Some APIs return 404 on PUT-to-nonexistent-resource, which makes the client's life harder — it must check existence before creating, or handle the 404 with a fallback POST. Other APIs return 201 and create the resource, which is friendlier but changes the semantics from "update" to "upsert". The spec allows both; pick one and document it clearly. The most confusing design is a mix — some URLs create, others return 404 — because the client cannot predict the behaviour.

Trade-off

PUT-as-create is idempotent and offline-friendly but requires client-side ID generation and accepts that the client chooses the URL (which is a security consideration — a client-supplied ID could collide with another tenant's). PUT-as-update is simpler for the server but makes retries harder for the client. The right choice depends on whether the client is offline-capable and whether the URLs are client-meaningful.

Part C — Actions, Representations & Anti-patterns Non-CRUD operations, data types, polymorphism, and what to avoid

7

How do you design URLs for actions that don't map cleanly to CRUD?

Short Answer

Most non-CRUD actions fall into three categories: state transitions on an existing resource (cancel, approve, publish), operations that create a new resource (transfer, payment, checkout), and computations (search, estimate). The best practice is to model the action as a sub-resource (POST /orders/42/cancellation) or a new resource (POST /transfers). When that does not work, a verb endpoint (POST /orders/42/cancel) is a defensible escape hatch.

Approach 1 — Model the action as a resource

Many actions are really "create an instance of something". Cancelling an order creates a cancellation. Refunding a payment creates a refund. Sending an email creates a message. These are resources, and POSTing to a collection is the correct REST design:

Instead ofUseResponse
POST /orders/42/cancelPOST /orders/42/cancellations201 with cancellation resource
POST /payments/42/refundPOST /payments/42/refunds201 with refund resource
POST /users/42/send-emailPOST /users/42/emails201 with email resource
POST /invoices/42/approvePOST /invoices/42/approvals201 with approval resource

The advantage is that the action has a resource — it can be queried (GET /orders/42/cancellations lists all attempts), referenced in logs, and given its own state (pending, completed, rejected). The cancellation is not just a method call, it is a thing that happened.

This approach is what Stripe uses for many operations (refunds are resources; payouts are resources) and what many well-designed APIs use for anything with a lifecycle or an audit trail.

Approach 2 — Model the action as a state transition via PATCH

If the action is simply a state field changing (active → cancelled), the cleanest design is a PATCH to the resource:

ActionDesign
Cancel an orderPATCH /orders/42 with {"status": "cancelled"}
Publish a postPATCH /posts/42 with {"status": "published"}
Archive a projectPATCH /projects/42 with {"archived": true}

This is the most RESTful approach and works beautifully when the action maps to a field. The server validates that the transition is legal (you cannot cancel an already-shipped order) and returns 409 if not.

The limitation is that some actions have side effects beyond a field change (a refund is not just a flag, it moves money). For those, Approach 1 or 3 is better.

Approach 3 — Verb endpoints as an escape hatch

Sometimes the action does not fit any of the above. A search is not a resource. A price estimate is not a resource. A PDF generation is not a resource (or, alternatively, it is a job, and jobs are resources). For these, a verb endpoint is defensible:

ActionVerb endpoint
SearchPOST /search (body is the query)
Price estimatePOST /price-estimates (still resource-shaped, but verb-y)
Convert filePOST /convert or POST /conversions

The rule of thumb: if you can model it as a resource, do; if you cannot after honest effort, a verb is better than a contorted resource. But be honest — most "actions" are resources in disguise (a search is a query, a conversion is a job, a refund is a resource) and modelling them as such is better.

What not to do

  • Verb in a top-level URL for a single resource action — POST /cancelOrder is not RESTful and creates a parallel URL structure.
  • Using GET for actions — GET /orders/42/cancel violates safety and will be triggered by crawlers and prefetchers.
  • Using POST on a resource for a state change — POST /orders/42 with a body saying "cancel this" is ambiguous. PATCH or a sub-resource is clearer.
  • One endpoint with an operation parameter — POST /orders with {"operation": "cancel", "id": 42} is RPC hiding in REST clothing; it loses all the benefits of resource-oriented URLs.

Idempotency for action endpoints

Actions require special care about idempotency. Cancelling an already-cancelled order should probably return 200 (idempotent) rather than an error — the state is what the client wanted. Cancelling a shipped order should return 409 (conflict). The decision is domain-specific, but it should be made deliberately, because a client retrying an action after a timeout will hit the already-done case.

For actions that are not idempotent (a refund is a good example — two refunds refund twice), an idempotency key is essential. This is a Volume 5 topic, but the design implication is that action endpoints must be designed with idempotency in mind from the start.

Interview Framing

Say: "Cancelling an order creates a cancellation resource at /orders/{id}/cancellations, because the cancellation has its own lifecycle and audit trail. Publishing a post is a state change, so it's a PATCH setting status: published." That shows you are classifying actions, not applying a single rule.

How do you represent dates, money, enums, and nulls in an API?

Short Answer

Dates: ISO 8601 in UTC, always with timezone information for instants, and date-only where appropriate. Money: integer minor units plus a currency code, never floating point. Enums: string values, versioned when extended, with a fallback for unknown values. Nulls: distinguish absent from null from empty, and prefer omitting absent fields over sending nulls.

Dates and times

The rules that avoid almost every date bug:

  • Instants (a specific moment) — ISO 8601 with UTC offset: "2024-01-15T10:30:00Z". The Z is critical — without it, the timestamp is ambiguous and different clients interpret it in different timezones.
  • Local times (a wall-clock time without a zone) — ISO 8601 without an offset: "2024-01-15T10:30:00". Use only when the time genuinely is local (a meeting scheduled "at 10:30 in New York" is different from "at 10:30 UTC").
  • Dates (no time) — ISO 8601 date format: "2024-01-15". Birthdates, invoice dates, and reporting periods are dates, not timestamps. Converting a date to a timestamp creates false precision and timezone problems.
  • Durations — ISO 8601 duration: "P1D" (1 day), "PT1H30M" (1 hour 30 minutes).

The most common mistake is storing timestamps without a timezone and treating them as UTC. This works until a server is in a non-UTC zone and starts producing timestamps that are off by hours. Always include the timezone, and prefer UTC for instants.

Money

Money must be represented as integer minor units plus a currency code. Never as a floating-point number. Floats cannot represent 0.10 exactly — the classic bug is 0.1 + 0.2 = 0.30000000000000004 — and any rounding in a financial calculation is a bug.

FormatExampleVerdict
Integer minor units + currency{"amount": 1050, "currency": "USD"}Correct — 10.50 USD
String decimal + currency{"amount": "10.50", "currency": "USD"}Acceptable, if parsed carefully
Float + currency{"amount": 10.50, "currency": "USD"}Wrong — precision loss
Formatted string"$10.50"Wrong — cannot be parsed reliably across locales

The currency is mandatory because 1050 is 10.50 USD, or 10.50 EUR, or 1050 JPY — the number alone is meaningless. Use ISO 4217 currency codes (USD, EUR, GBP).

The minor-unit convention differs by currency: USD has 2 decimals (cents), JPY has 0, some currencies have 3. Include this in the documentation or, better, send the currency's exponent alongside the amount.

Enums

Enums should be strings (not integers, not booleans) so they are self-documenting and extensible. {"status": "active"} is far better than {"status": 1}.

The versioning question: what happens when you add a new enum value? Clients that switch on the value will hit the new case. The standard mitigations:

  • Tolerant reader. Document that clients must handle unknown values gracefully — typically by treating them as "unknown" or by ignoring the record. This is what large APIs do (Stripe, GitHub).
  • Versioned enum values. Prefix values with a version (v2_processing) so old clients do not confuse new values with old ones. This is heavier and rarely necessary.
  • Never remove. Only add values. Removing a value is a breaking change.

Nulls

There are three states that JSON conflates: absent (the field was not included), null (the field is present with no value), and empty (the field is present with an empty value — "", [], 0). The distinctions matter:

  • Absent — the client did not ask for it, or the server did not include it. A PATCH that omits a field should not change it.
  • Null — the field exists but has no value. A PATCH that sends {"email": null} means "clear the email".
  • Empty — the field has an empty value (an empty list of tags, an empty string for a middle name). Not the same as null.

Best practice: omit fields that are not applicable rather than sending nulls, and document what null means for each field. For PATCH specifically, the distinction between absent (leave alone) and null (clear) is critical — without it, you cannot express "clear this field" in a JSON Merge Patch.

Booleans in JSON

Use true / false, not "true" or 1 / 0. This is unambiguous and typed correctly. The one trap is optional booleans — a field that can be true, false, or absent is effectively tri-state, and clients must handle the third case. Document it.

Common Pitfall

Returning a local-time timestamp without a timezone offset. It looks correct in development (both client and server in the same timezone) and produces subtly wrong times in production when a user is in a different zone. Always include the offset, always in UTC for instants.

How do you represent polymorphic resources?

Short Answer

When a resource can be one of several types, include a discriminator field that identifies the type, and document the schema for each variant. The two common patterns are tagged unions (a type field alongside variant-specific fields) and sub-resources (each variant has its own URL and schema). Tagged unions are simpler; sub-resources are more discoverable and versionable.

The problem

A payment can be a card payment, a bank transfer, or a wallet payment. Each has different fields — a card has a last-4 and expiry, a bank transfer has an account number and routing code, a wallet has a provider. The API needs to return any of them in a consistent shape, and the client needs to know which fields to expect.

Approach 1 — Tagged union with a discriminator

Every variant includes a type (or kind) field, and the client switches on it to know what other fields to expect:

VariantExample
Card{"type": "card", "last4": "4242", "expiry": "2026-12"}
Bank transfer{"type": "bank_transfer", "account": "1234", "routing": "5678"}
Wallet{"type": "wallet", "provider": "paypal"}

This is what Stripe does (its PaymentMethod has a type and variant-specific objects under it — card, bank_transfer, etc.). It is the simplest pattern, widely understood, and works with any JSON client.

The trade-off is that the schema is not obvious from the API definition — clients must know the mapping from type to fields. OpenAPI's oneOf / anyOf with a discriminator can express this, but code generation support varies.

Approach 2 — Nested variant object

The type-specific fields are nested under a key named after the type:

VariantExample
Card{"type": "card", "card": {"last4": "4242", "expiry": "2026-12"}}
Bank transfer{"type": "bank_transfer", "bank_transfer": {"account": "1234", "routing": "5678"}}
Wallet{"type": "wallet", "wallet": {"provider": "paypal"}}

This is a small variation that has two advantages: the top-level object's shape is uniform (always type plus a variant object), which makes generic processing easier; and the variant object can be absent when the type is unknown, which is graceful. Stripe's modern API actually uses this form.

The trade-off is more nesting, which some clients find awkward.

Approach 3 — Separate sub-resources per variant

Each variant has its own URL and schema:

  • GET /payments/42 returns a base payment with {"type": "card"} and a _links or related object pointing to /payments/42/card.
  • GET /payments/42/card returns the card-specific fields.

This is more HATEOAS-flavoured, more discoverable, and lets each variant have its own permissions. The trade-off is two requests for one object, which is worse for performance and more complex for the client.

This pattern is worth it when the variants are truly different domains (a search result that could be a user, a post, or a product), less worth it when they are minor variations of the same concept.

What to avoid

  • Implicit types. Returning fields that imply a type without a type field. The client is left to guess by which fields are present — brittle and unversionable.
  • Nullable everything. Making every field nullable and letting the client figure out what applies. This loses the schema and defeats type checking.
  • A type field that changes over the resource's lifetime. A payment should not switch from card to bank transfer; if it can, it is really two resources.
  • Enum-of-all-possible-fields. Returning all fields for all variants with nulls for the ones that do not apply. This makes every response huge and makes the schema meaningless.

Versioning polymorphic types

Adding a new variant is backward-compatible (clients ignore unknown types), provided the type field is treated as an enum that can grow. Removing a variant is breaking. Changing a variant's fields is breaking. The same rules as any schema change apply, with the extra complexity that clients may have incomplete handling for new variants.

The tolerant reader pattern is essential here: clients must handle unknown types gracefully (displaying "unsupported" or ignoring the record) rather than crashing or misinterpreting. Document this requirement explicitly — it is the single most important thing consumers need to know about a polymorphic API.

Interview Framing

Say: "Payment methods are polymorphic — a card, a bank transfer, or a wallet. I'll use a tagged union with type and a nested variant object, and document that clients must handle unknown types gracefully so we can add variants without breaking them." That shows you know the pattern, the schema mechanism, and the versioning implication.

What is the RPC-over-REST anti-pattern, and how do you recognise it?

Short Answer

RPC-over-REST is using HTTP transport while ignoring REST semantics — typically a single endpoint (POST /api) with a body containing an operation name and parameters, or a set of verb URLs (/getUser, /createOrder). It works, but it discards the entire benefit of the HTTP ecosystem: caching, conditional requests, meaningful status codes, and discoverability.

The signature of RPC-over-REST

  • One endpoint for everything. POST /api with a body like {"method": "getUser", "params": {"id": 42}}. This is JSON-RPC — it is not wrong, but it is not REST.
  • Verbs in URLs. /getUser, /createOrder, /updateProfile. Every operation has its own URL, and the HTTP method is always POST.
  • POST for reads. Using POST for a read operation to avoid putting data in the URL, or because "the client sends a body anyway". This breaks caching, breaks bookmarks, and breaks the semantics of GET.
  • Status code 200 for everything. Returning 200 with an error object in the body ({"success": false, "error": "..."}) instead of a 4xx or 5xx status. This breaks every monitoring, alerting, and retry system.
  • Operations that do not map to resources. When the API has no clear notion of "resources", but only "operations".
  • The same URL means different things based on a body field. POST /api with {"op": "delete"} versus {"op": "create"} — the URL is not an identifier, it is a dispatcher.

Why it happens

RPC-over-REST is easy to build. You add one endpoint, switch on a method name, and call the right function. It is what a first-pass API looks like when the designer has not spent time on resource modeling. It is also what happens when the API is auto-generated from a service's internal methods, without an intermediate design step.

It is not, in itself, wrong — JSON-RPC is a legitimate protocol. The problem is when it is called "REST" and consumers expect REST semantics. The label promises caching, conditional requests, and status codes that the API does not provide.

The real cost

  • No caching. A cache cannot cache a POST, and cannot distinguish "get user 42" from "get user 43" if both are POST /api with a body. Every request hits the origin, every time.
  • No conditional requests. ETags, If-Match, and If-None-Match are HTTP header mechanisms that assume a GET. Without GET, they do not apply, so optimistic concurrency must be reimplemented in the body.
  • No meaningful status codes. Everything is 200, so monitoring cannot distinguish success from failure. Retry logic cannot distinguish retryable from non-retryable. Load balancers cannot detect health by status code.
  • No browser tooling. You cannot open the URL in a browser, cannot bookmark it, cannot inspect it in the dev tools network panel as a readable request.
  • No discoverability. Clients cannot construct URLs from a base; every operation has its own URL and its own semantics.
  • No standard tooling. Swagger/OpenAPI can document it, but the generated clients are awkward, and the ecosystem of REST tooling (Postman collections, GraphQL-to-REST bridges, CDN rules) does not apply.

The legitimate RPC-over-HTTP design

If you genuinely want RPC, use a proper RPC framework. gRPC is the modern choice, with binary encoding, streaming, and a proper schema. JSON-RPC is the HTTP-native option — one endpoint, a standard envelope, consistent error handling, and batch support. Both are honest about being RPC, and neither pretends to be REST.

The problem is not RPC. The problem is claiming REST while doing RPC, because consumers then expect semantics that are not provided.

When RPC-over-REST is acceptable

There is a narrow case where it makes sense: a small internal API with a single consumer and no caching or observability requirements. For a prototype, or a one-off integration, RPC-over-REST is faster to build than a proper REST API. The moment the API has more than one consumer, or the moment caching matters, the cost outweighs the simplicity.

How to fix it

If you inherit an RPC-over-REST API and want to migrate:

  1. Add resource-oriented endpoints alongside the RPC one. GET /users/42 can coexist with POST /api for a transition period.
  2. Migrate consumers one at a time. The RPC endpoint can be deprecated once all consumers are on the new endpoints.
  3. Extract resources from the operations. Every operation on a "user" implies a user resource. Map the operations to resources and define the CRUD equivalents.
  4. Fix the status codes first. Even within an RPC-over-REST design, return proper 4xx/5xx codes instead of 200-with-an-error-body. This is a small change with a large operational benefit.
Common Pitfall

Building a REST API and then adding a POST /api endpoint "for special cases". It starts as an escape hatch and becomes the primary interface, because it is easier to add an operation there than to model a resource. The result is two APIs — a real one and a shadow one — with no shared semantics. Resist the temptation; if an operation does not fit, model a resource for it (Question 7).
