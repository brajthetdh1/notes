Part A — Pagination The single most consequential decision in a list endpoint

1

What is the difference between offset, cursor, and keyset pagination?

Short Answer

Offset pagination skips N rows and returns the next page — simple, but O(N) and inconsistent when data changes. Cursor pagination encodes the position of the last item seen and asks for "items after this" — consistent and O(1), but cannot jump to page 50. Keyset pagination is the implementation of cursor pagination using an indexed column (usually the primary key or a timestamp), and it is what almost every large list API actually uses underneath.

AspectOffsetCursorKeyset
Parameter?page=5&limit=20 or ?offset=100?cursor=eyJpZCI6MTIzfQ==?after_id=123&limit=20
Complexity per requestO(offset + limit)O(limit)O(limit)
Consistency under writesBreaks — items skip or duplicateStableStable
Jump to page NYesNoNo
Total countEasy (but expensive)HardHard
Best forAdmin dashboards, small datasets, numbered pagesInfinite scroll, feeds, exportsTime-series, activity feeds, any large list

Why offset pagination breaks at scale

An offset query SELECT * FROM orders ORDER BY created_at LIMIT 20 OFFSET 100000 requires the database to find and discard 100,000 rows before returning the next 20. This is O(offset) — it gets linearly slower as the user pages deeper. On a large table, page 5,000 can take seconds while page 1 is instant. The database cannot skip rows it has not scanned; there is no "start at position 100,000" without walking through the first 100,000.

The second problem is that offset pagination is not stable under writes. If an item is inserted between page 1 and page 2, every subsequent page shifts by one, and the user sees one item twice and misses another. In a feed where items are inserted constantly, this is a visible bug — "I saw this post twice" or "this post disappeared".

How cursor pagination fixes it

A cursor encodes the position of the last item on the current page — usually as the sort key of that item, or an opaque token containing it. The next request says "give me items after this one", which the database can answer with an index seek rather than a scan:

StyleRequestSQL
Offset?page=3&limit=20LIMIT 20 OFFSET 40
Keyset?after_id=123&limit=20WHERE id > 123 ORDER BY id LIMIT 20
Composite keyset?after_created=2024-01-15T10:30:00Z&after_id=123WHERE (created_at, id) > ('2024-01-15T10:30:00Z', 123) ORDER BY created_at, id LIMIT 20

The composite form is the one that actually works in production. A single sort key is rarely unique (many items share a timestamp), so the tiebreaker is a unique column — usually the primary key. The sort order must be (created_at, id) with a matching composite index, and the cursor carries both values.

The opaque cursor pattern

Most public APIs do not expose after_id directly — they encode the position into an opaque string:

StyleRequestProsCons
Transparent?after_id=123&after_created=...Debuggable, easy to construct by handExposes internal structure; hard to change
Opaque?cursor=eyJpZCI6MTIzLCJ0IjoxNzA1MzE0MjAwfQ==Internal details hidden; can evolve the encodingHarder to debug; clients must not parse it

Opaque cursors are base64-encoded JSON or a signed token. The client must treat them as a black box — its only job is to pass the cursor from the previous response into the next request. Documenting this as a requirement is critical, because clients that parse cursors will break when the encoding changes.

What about total counts?

Offset pagination makes total counts trivial (one COUNT(*) query) but expensive on large tables. Cursor pagination makes them awkward — there is no cheap way to know how many pages remain. The pragmatic approach: do not return total counts for large lists. Return a has_more boolean, which the server can compute from "did we get more than limit rows". If a total count is genuinely required (search results, reports), compute it once and cache it, or accept the cost of a counted query.

Hybrid: cursor internally, offset externally

Some UIs need numbered pages (admin dashboards, data tables). A design that supports both is possible: the client sends ?cursor=... for "next/previous", and the server still exposes ?page=N which internally translates to a keyset query where possible. This is more complex but gives the UI the page numbers it needs while keeping the backend efficient.

Trade-off

Offset pagination is simple for small datasets but breaks at scale and is inconsistent under writes. Cursor pagination is the right default for any large list, but it cannot support "jump to page 50". Choose based on the UI: numbered pages need offset (or a hybrid), infinite scroll and feeds need cursors.

How do you paginate across shards or distributed data?

Short Answer

Cross-shard pagination is a merge problem: each shard returns its own sorted page, and a merge layer combines them into a single global page. The correct approach is keyset pagination with a global cursor — the cursor encodes the last-seen value of the global sort key, and each shard returns only items after that value. Scatter-gather with offset is the naive approach and it does not work at scale.

Why offset does not work across shards

Consider a feed sharded by user_id, with 10 shards. A request for page 3 (OFFSET 40 LIMIT 20) must ask every shard for "rows 40–60", then merge the 200 total results and return the top 20 by the global sort key. Each shard returns 20 rows, most of which are discarded. For page 50, each shard returns 1,000 rows, most of which are discarded. The fan-out cost grows linearly with depth, and the tail latency is the max of 10 shards. This does not scale.

Keyset pagination across shards

With keyset, the request is ?after_created_at=2024-01-15T10:30:00Z&after_id=123&limit=20. Every shard executes WHERE (created_at, id) > ('2024-01-15T10:30:00Z', 123) ORDER BY created_at, id LIMIT 20. Each shard returns at most 20 rows starting from the cursor. The merge layer combines them, sorts by the same key, and returns the top 20.

This is O(limit) per shard, not O(offset). It is stable under writes (a new item with a newer timestamp goes to the next page, not to page 2). And the merge is a bounded K-way merge of at most shards × limit rows, which is trivial.

The bounded fan-out problem

The merge layer must still contact every shard for every request. With 100 shards, this is 100 RPCs per page — potentially slow and expensive. Mitigations:

  • Co-locate by the query key. If the query is "a user's feed", shard the feed by user_id — then one shard has all the user's items, and no fan-out is needed. This is the best fix: design the shard key so that the dominant query is single-shard.
  • Precompute the merged list. For feeds, fan out on write: when a new item is created, push it into every follower's materialized feed table, which is itself sorted. Then the read is a single shard. This trades write cost for read speed.
  • Parallel fan-out with a deadline. If fan-out is unavoidable, issue all shard requests in parallel and use a deadline — if some shards are slow, return a partial page with a note that results may be incomplete, rather than blocking on the slowest shard.
  • Hierarchical shards. Group shards into "super-shards" with a rollup layer. The merge contacts super-shards, which contact their members. This reduces the number of RPCs but adds a layer.

Consistency across shards

A cross-shard query reads from shards at slightly different points in time. An item written to shard A one second ago may not be visible, while an item written to shard B is. The result is a page that is "almost complete" — a new item appears on the next page fetch, or an item is temporarily missing. For most feeds and lists this is acceptable; for anything requiring a strict global snapshot, a distributed transaction or a version-based read is required.

The "just use a search index" alternative

For queries that need true cross-shard sorting and filtering, the pragmatic answer is often to not query the operational database at all. Stream changes via CDC (Volume 4 of the distributed systems series) into a search index — Elasticsearch, OpenSearch, Typesense, Meilisearch — and query that. The index handles sorting, filtering, and pagination across the entire dataset efficiently, at the cost of eventual consistency (typically a few seconds of lag).

What the cursor must contain

In a cross-shard system, the cursor must be global — it cannot reference a specific shard, because the next page may involve different shards. A global cursor contains the value of the global sort key (created_at, id), possibly encoded as an opaque token. Each shard applies the same predicate, so the merged result is consistent regardless of which shards contributed to which page.

Common Pitfall

Implementing cross-shard pagination with offset and then being surprised that page 50 times out. The fan-out cost is invisible on page 1 and catastrophic on page 100. Keyset pagination is the only design that scales to deep pages, and it must be designed in from the start.

How do you design filtering syntax safely?

Short Answer

Use explicit, whitelisted query parameters for each filterable field, not a free-form expression language. Each filter is documented, typed, and indexed. A general-purpose filter DSL is a security risk (injection, unbounded query cost) and a maintenance burden (you cannot support arbitrary filters efficiently without an index for each).

The three approaches

ApproachExampleWhen to use
Individual query params?status=active&created_after=2024-01-01Known, finite set of filters — the default for most APIs
Structured filter object?filter[status]=active&filter[amount][gte]=100Many fields, consistent operations — some JSON:API-style APIs
Expression language?filter=status eq "active" and amount gt 100Complex Boolean logic, usually behind a search service (OData, FIQL)

Why explicit parameters are the default

An explicit parameter per filter has enormous advantages:

  • It is typed. created_after is a date; the parser knows how to validate it. status is an enum; invalid values can be rejected.
  • It maps to an index. Each supported filter has an index in the database, and only queries that use an indexed filter are allowed. This prevents an unbounded scan.
  • It is documented. Every filter appears in the reference docs with its type and semantics. Clients know exactly what is supported.
  • It is safe. There is no parser to exploit — the parameters are simple strings, and they are bound as SQL parameters, not concatenated.
  • It is versionable. Adding a filter is a non-breaking change; changing one is documented.

The filter DSL danger

A general-purpose filter language is seductive — it looks flexible and powerful — but it breaks the core promise of an API: that every supported operation is efficient and safe. A DSL that accepts any expression will happily accept substring(content, 1, 3) = "abc", which the database cannot answer without a full scan. The result is a query that looks reasonable to the client and destroys the database. Even worse, a badly designed DSL is a SQL injection vector or an unbounded resource exhaustion vector.

If you genuinely need a filter DSL (usually because you are exposing a search product), push it behind a search service (Elasticsearch, Typesense) that is designed for it, and expose only the operations that service can handle efficiently. Do not build a DSL on top of a transactional database.

The naming conventions

OperationConventionExample
Equality?field=value?status=active
Comparison?field_gt=, field_gte=, field_lt=, field_lte=?amount_gte=100
Range?field_min=&field_max= or ?field[gte]=&field[lte]=?created_after=...&created_before=...
Multi-value (OR)Comma-separated or repeated param?status=active,pending
Negation?field_not= or ?field_ne=?status_not=cancelled
Null check?field_is_null=true?deleted_at_is_null=true

The bracket syntax (filter[status]=active) is popular in JSON:API-style APIs because it groups all filters under one namespace and avoids parameter name collisions. The flat syntax (?status=active) is simpler and what most APIs use. Either is fine — pick one and be consistent.

Implicit defaults and safety

Every list endpoint should have mandatory filters when the underlying table is large. "List all orders" without a date filter is a query that returns billions of rows. The safe design is:

  • Default filters. If no date range is given, default to "last 30 days" or "the current tenant's recent orders", not "everything".
  • Required filters. Some endpoints require at least one filter — /orders without ?user_id= is a 400, not a full table scan.
  • Maximum results. Even with filters, a result set can be huge — a hard cap (e.g., the list endpoint returns at most 10,000 items and then a hint to narrow) prevents accidental overload.
  • Index-aware. Document which filters use an index and which are slow. Better: reject filters that would trigger a scan, and tell the client which filters are allowed on this endpoint.

The "filter and page" interaction

Pagination and filtering must be designed together. A cursor pagination scheme assumes a stable sort key; a filter that changes the result set between requests (e.g., a filter on a field that is being updated) makes the cursor unstable. The standard rule: filters must be deterministic — the same filter applied at two points in time must produce a consistent view of history, even if new items have been added. This is usually achieved by combining the filter with the sort key in the cursor, so the position is absolute rather than relative to a changing result set.

Common Pitfall

Exposing a filter on a field that is not indexed. It works in development with 1,000 rows and takes 30 seconds in production with 10 million. Every filter parameter must be backed by an index, and the index must be checked by the query planner — the API should verify that the query plan uses the index before deploying the filter.

How do you design multi-field sorting?

Short Answer

Use a comma-separated list of field names with optional direction prefixes, and whitelist the sortable fields. Every sortable field must be indexed, and every sort must have a unique tiebreaker (usually the primary key) so pagination is stable. Never accept an arbitrary sort expression — it is a performance and injection risk.

The syntax

StyleExampleProsCons
Prefix?sort=-created_at,+nameCompact; widely used (JSON:API)Easy to misread as negation
Suffix?sort=created_at:desc,name:ascExplicitMore verbose
Separate params?sort_by=created_at&sort_dir=descSimpleCannot express multi-field

The prefix convention (-field for descending, no prefix or + for ascending) is the most common. It is compact, easy to parse, and the "minus" reads as "descending" once you know the convention. Document it clearly in the getting-started guide.

Always include a tiebreaker

A sort on created_at alone is not stable — many rows share a timestamp. If pagination uses the sort key as a cursor, a set of rows with equal timestamps has no defined order, and pagination can duplicate or skip them. The fix is to always add the primary key as a final tiebreaker:

RequestActual sort
?sort=-created_atORDER BY created_at DESC, id DESC
?sort=nameORDER BY name ASC, id ASC
?sort=-status,nameORDER BY status DESC, name ASC, id ASC

The tiebreaker is invisible to the client — it is not in the response, it is not in the sort spec. It exists only to guarantee that two rows that are "equal" under the client's sort still have a deterministic order, which makes cursor pagination correct.

Indexes must match the sort

A sort that does not match an index requires the database to sort the entire result set in memory (or on disk). At a million rows, this is a full sort — slow and memory-hungry. The index must be (filter_col, sort_col1, sort_col2, ..., pk) in the exact order the sort will use. If a client can sort by any of five fields, you need at least five indexes, and that is a real cost on write.

The standard mitigation: limit the sortable fields to a small, curated set with known indexes. An API that accepts any field for sorting is an API that forces the database to sort on unindexed columns, which will fail under load. Document the sortable fields, and reject any others.

The composite sort + filter pattern

Most real list endpoints filter and sort. A common query: "orders for user 42, sorted by created_at descending". The index must be (user_id, created_at DESC, id DESC) — the filter column first, then the sort columns in the same direction. This lets the database seek to the user's orders and then walk the index in the sort order, returning LIMIT 20 without sorting.

If the index is (created_at, id) but the query is WHERE user_id = 42 ORDER BY created_at, the database must find all of user 42's orders and then sort them — a potentially large intermediate result. This is why composite indexes must match the query pattern, and why exposing "sort by any field, filter by any field" is expensive.

Collation and case sensitivity

Sorting strings brings the collation problem. "Apple" sorts before "apple" in some collations (ASCII), and after in others (case-insensitive). This is a locale and database setting, but it matters for the client — the API must document the collation used, or the client will see orderings it cannot predict.

The pragmatic answer: use the database's default collation, document it, and if a client needs a specific collation, expose a parameter (?sort=name&collation=ci). Most APIs skip this and accept the default — it is fine for English but occasionally surprising for other languages.

Nulls in sorting

Where do nulls sort? PostgreSQL sorts NULLs last on ASC by default, Oracle sorts them first. MySQL sorts NULLs first on ASC. There is no cross-database standard, and even within a database the behaviour can be configured. The API must document the behaviour (or, better, treat nulls consistently across all sort fields by using NULLS LAST on both directions). Without this, "sorted by last_name" is ambiguous for rows with no last name.

Trade-off

Every sortable field is an index, and every index is a write cost. An API that lets clients sort by any field is an API that pays to maintain an index on every field. Curate the sortable set to what clients actually need (usually 2–5 fields), document it, and reject the rest. The "flexible" design is actually the expensive one.

How do you design field selection and partial responses?

Short Answer

A field selection parameter (?fields=id,name,email) lets the client specify which fields to include, reducing payload size for mobile clients and avoiding the over-fetching that plagues REST. The main design questions are scope (which resources can be shaped), syntax (comma-separated vs nested), and defaults (a "full" representation when no selection is given).

Why field selection matters

A GET /users/42 that returns a 40-field user object is 4 KB. On a mobile client listing 100 users, that is 400 KB, most of which is fields the client does not display. Field selection lets the mobile client request ?fields=id,name,avatar_url and get 400 bytes per user — 40 KB total. This is the same problem GraphQL solves, done within the REST idiom.

The cost is that the field-selection parameter is a new dimension in the API surface: every combination of fields must be supported by the server, and the response shape is not fixed. This complicates caching (the same URL with different fields is a different response), codegen (typed clients must handle optional fields), and contract testing (which shapes are valid?).

The syntax

StyleExampleNotes
Comma-separated?fields=id,name,emailSimple, most common
Bracket-specified?fields[users]=id,name&fields[orders]=id,totalPer-resource-type, JSON:API
Bracket-list?fields[]=id&fields[]=nameSome frameworks prefer this
Nested?fields=id,name,orders(id,total)Field selection on related resources — powerful but complex

The comma-separated form is the pragmatic default. Nested selection is powerful but essentially rebuilds GraphQL's query language inside a query parameter, and it is rarely worth the complexity.

Defaults and mandatory fields

When no fields parameter is given, the API should return the full representation. This is the backward-compatible default that keeps existing clients working. When fields is given, only those fields are returned — plus any "mandatory" fields the API decides are non-negotiable (usually id and type for polymorphic resources).

Mandatory fields exist because some operations require them — a client that fetches a list of IDs to display needs the IDs even if it does not list them in fields. Documenting that id is always returned is important, so clients do not accidentally break their code.

Field selection and the "expand/include" pattern

Field selection is different from expansion. Field selection controls which fields of the current resource to return. Expansion controls which related resources to inline:

ParameterPurposeExample
fields=Which fields of this resource?fields=id,name
expand= / include=Which related resources to inline?expand=customer,items

Expansion replaces the "N+1 problem" of fetching a list and then fetching each item's related resource. A request for 20 orders with ?expand=customer returns each order with its customer inlined, saving 20 round trips. This is the REST equivalent of GraphQL's nested selection, scoped to named relationships rather than arbitrary depth.

The cost of field selection

  • Cache fragmentation. ?fields=id,name and ?fields=id,email are different URLs, so caches store them separately. This increases cache miss rate and storage cost.
  • Type complexity. A typed client must handle a response with optional fields — either by making every field optional (annoying) or by generating a separate type per field set (complex).
  • Contract testing. The contract is now a family of shapes, not a single one. Testing every combination is exponential, so testing must sample.
  • Backend implementation. The server must project the requested fields without returning the full row — which is trivial in a document store, harder in a relational database where "select only these columns" means generating dynamic SQL.

When field selection is worth it

Field selection is worth the complexity when:

  • Payload size is a real problem — mobile clients on metered connections, or list endpoints returning large objects.
  • The resource has many fields that different clients need subsets of.
  • The clients are diverse — mobile wants minimal, web wants more, partners want everything.

It is overkill when the resource is small (5 fields) or all clients need all fields. In that case, just return the full object and save the complexity.

The GraphQL comparison

Field selection is REST's answer to GraphQL's core value proposition. GraphQL does it more elegantly (selection is the query, no separate parameter) and more powerfully (arbitrary depth, nested relationships, fragments). REST field selection is a coarser tool — it cannot express "user.name but order.totals only" — but it addresses the same over-fetching problem with a fraction of the complexity. Choose based on how much of GraphQL's power you actually need.

Common Pitfall

Implementing field selection but forgetting the fields that clients need to construct subsequent requests. If fields=name omits id, the client cannot build /users/{id} for the next request. Mandatory fields (id, type discriminators, links) should always be included regardless of the fields parameter — or the API must document the consequence.

How do you handle partial success in batch operations?

Short Answer

Return a per-item result, not a single status for the whole batch. Each item gets its own success/failure status and, if it failed, its own error code and message. The top-level response is 207 Multi-Status (or 200 with a structured body) indicating that the batch was processed — the individual outcomes are in the array.

The three semantics

SemanticsBehaviourClient sees
All-or-nothingAny failure rolls back the entire batchTop-level error; nothing changed
Best-effort (partial success)Each item succeeds or fails independentlyMixed results; client must handle
Fail-fastStop at the first failure; prior items are committedPartial results; unclear what happened to the rest

Fail-fast is almost never the right choice — it is ambiguous (which items committed?) and forces the client to reconstruct state. The real choice is between all-or-nothing and best-effort, and the right answer depends on the domain.

When all-or-nothing is right

Some operations are only meaningful as a unit. A transfer of $100 from A to B plus a credit of $100 to C plus a debit of $100 from D — if any fails, the whole thing is invalid. Similarly, a batch insert of a shopping cart's line items: if one item is out of stock, the cart is not orderable.

The implementation requires a transaction, which limits the batch size (transaction size limits, lock contention, rollback cost). The response is a single 400 with an error identifying the failing item — but the client gets no information about which items would have succeeded, because none did.

When best-effort is right

Most batch operations are independent: creating 100 users, updating 50 records, deleting 20 items. One failure does not invalidate the others, and forcing the client to fix one bad item to get the other 99 through is user-hostile. Best-effort is the default for bulk imports, list updates, and any operation where items are independent.

The implementation is simpler (each item is its own transaction) and the batch can be larger. The complexity is entirely in the response — the client must inspect each item and decide what to retry.

The response shape

PatternBodyNotes
Array of results [{"status": 201, "id": 1}, {"status": 409, "error": {...}}, {"status": 201, "id": 3}] Simplest; matches the order of the request
Envelope with counts {"succeeded": 98, "failed": 2, "results": [...]} Adds a summary; useful when the client wants a quick check
Correlated by client ID {"id": "a", "status": 201, ...}, {"id": "b", "status": 409, ...} Each item carries a client-provided ID so the client can correlate without relying on order

The correlated form is the most robust — a client that reorders its request or filters the response still knows which item is which. If the client can provide IDs, this is worth it; if not, matching by array index is the standard.

The status code question

What status code should a batch with partial success return?

  • 207 Multi-Status (from WebDAV) — explicitly designed for this case. It signals "the batch was processed; inspect the body". Rarely used outside WebDAV because it is not widely understood.
  • 200 OK — the request was processed successfully (even if some items failed). The body contains the per-item statuses. This is what many APIs do and is defensible: the API call succeeded, the item operations are in the body.
  • 400 / 422 — if any item failed, treat the whole batch as a bad request. This conflicts with best-effort semantics (partial success was expected) and forces the client to look at the body to see which failed.
  • 207 or 200 — the pragmatic answer. Use 200 with a clear body for best-effort batches, and document that per-item failures are in the response.

The one status that is definitely wrong: returning 200 with an error message in the body for the whole batch. That is the RPC-over-REST anti-pattern (Volume 2, Question 10), and it breaks every monitoring and alerting system.

Idempotency in batch operations

A batch operation that partially succeeded must be safe to retry. If the client retries the entire batch, the already-succeeded items will fail with "already exists" or be duplicated. The mitigations:

  • Per-item idempotency keys. Each item carries its own idempotency key, so a retry of an already-processed item is a no-op. This is the standard.
  • Upsert semantics. Each item is an upsert, not an insert — a retry updates the already-existing record instead of failing.
  • Client-side retry only the failed items. The client inspects the response, identifies the failures, and retries only those. This requires the response to be unambiguous about which items failed, which is why the correlated response is worth the complexity.

Batch size limits

Every batch endpoint must have a maximum size — usually 100 or 1,000 items. Without a limit, a client will send 1 million items and the server will exhaust memory. The limit should be documented, enforced with a clear error, and chosen based on the transaction size and typical item size. If a client needs to process more, they use a bulk API (Volume 1, Question 14) that chunks the work.

Common Pitfall

Returning a single status code for a batch and putting per-item details in a nested array that nobody reads. The client sees 200 and assumes everything worked, then later discovers that 5 of 100 items failed. The response shape must make per-item failures impossible to miss — either through a top-level summary ({"succeeded": 95, "failed": 5}) or through a response structure that requires the client to inspect the array.

Should you wrap responses in an envelope? What goes in it?

Short Answer

Use an envelope for collections (where you need pagination metadata) but return bare objects for single resources. The envelope holds the array plus pagination state (next_cursor, has_more, total) and sometimes links or metadata. Wrapping a single resource in {"data": {...}} adds a layer of indirection that most clients do not need.

Three envelope styles

StyleCollectionSingle resourceNotes
Bare [{...}, {...}] {...} Simplest; no place for metadata
Data-wrapped {"data": [...]} {"data": {...}} Always an object at the top level
Metadata-envelope {"data": [...], "meta": {"total": 1000, "cursor": "..."}} {"data": {...}, "meta": {...}} Best for collections; optional for resources

The argument for a bare array on collections

A bare array is the simplest shape — GET /users returns [...]. The advantage is clarity: the response is obviously a list. The disadvantage is that there is nowhere to put pagination metadata. A bare array cannot carry next_cursor — it must go in a Link header (Question 8), which is the HTTP-native way to express pagination.

Bare arrays are defensible when pagination is via Link headers. They are wrong when you want to return counts, cursors, or other metadata, because headers become a dumping ground.

The argument for an envelope

An envelope is future-proof — you can add fields to meta without breaking the response shape. This is why most modern APIs wrap collections:

FieldPurpose
dataThe array of resources
meta.has_moreWhether there is another page (cheaper than total)
meta.next_cursorCursor for the next page; null if last
meta.prev_cursorCursor for the previous page; null on first page
meta.totalTotal count (expensive; omit or make optional)
meta.limitEffective page size (may differ from requested)
links.self, links.next, links.prevURLs for navigation
warningsNon-fatal issues (e.g., "some records could not be loaded")

Should single resources be enveloped?

Wrapping a single resource in {"data": {...}} is a stylistic choice. It gives consistency with the collection form, and it provides a place for metadata about the resource (links, warnings). It also allows the server to return the resource with related links without polluting the resource itself.

The counter-argument is that a single resource is not a list, and forcing a .data access on every client is unnecessary indirection. Many APIs (Stripe, GitHub) return bare objects for single resources and enveloped collections. This is the pragmatic default and is what most clients find easiest.

Error responses must not be enveloped

One rule that is not stylistic: error responses must use a consistent shape, and it should be the same shape everywhere. RFC 7807 (Problem Details for HTTP APIs) is the standard:

FieldPurpose
typeA URI identifying the error type
titleA short human-readable summary
statusThe HTTP status code
detailA human-readable explanation
instanceA URI identifying this specific occurrence

Error envelopes should not be nested inside the success envelope. A 200 with an error in the body is always wrong (Volume 8 covers this in detail). Errors use 4xx/5xx status codes and the RFC 7807 body, and they are not wrapped in {"data": ...} — the top-level object is the problem.

The JSON:API style

JSON:API is a specification that mandates a particular envelope structure — data, included, links, meta, errors — with strict rules about how resources relate. It is more prescriptive than necessary for most APIs, but for teams that want a standard, it removes the ambiguity. Most APIs implement a lighter version: data + meta + links, without JSON:API's full resource linkage.

Trade-off

Envelopes are more future-proof but less ergonomic. Bare responses are simpler but constrain pagination to headers. The pragmatic middle: enveloped collections (where metadata is necessary), bare single resources (where it is not). Consistent error envelopes across everything, regardless of success-shape.

What is the Link header, and how does it express pagination?

Short Answer

The Link header (RFC 8288) carries hypermedia relations in HTTP headers, most commonly pagination links. A paginated response includes Link: <https://api.example.com/users?cursor=abc>; rel="next" so clients can follow it without constructing URLs. It is the HTTP-native alternative to putting next_cursor in a JSON envelope.

The syntax

RelationMeaningExample
selfThe current page</users?page=2>; rel="self"
nextThe next page</users?page=3>; rel="next"
prev / previousThe previous page</users?page=1>; rel="prev"
firstThe first page</users?page=1>; rel="first"
lastThe last page</users?page=100>; rel="last"

A response can include multiple relations in one header, separated by commas:

Header
Link: </users?page=1>; rel="first", </users?page=3>; rel="next", </users?page=1>; rel="prev"

Why the Link header matters

  • It keeps the body simple. A bare array response plus a Link header is the cleanest possible paginated response — no envelope, no metadata, just data and navigation.
  • It is HTTP-native. Clients that understand HTTP (browsers, crawlers, HTTP libraries) know what Link means. It is not a bespoke convention.
  • It supports discovery. A client does not need to know the URL structure — it follows the next link. This means the API can change its pagination URL format without breaking clients, as long as the header is updated.
  • It works with both offset and cursor. The URL inside the Link header can be ?page=3 (offset) or ?cursor=abc (cursor) — the client does not need to know.

The GitHub API precedent

GitHub's REST API is the most prominent example of Link-header pagination:

Response
HTTP/1.1 200 OK
Link: <https://api.github.com/user/repos?page=3>; rel="next", <https://api.github.com/user/repos?page=1>; rel="first"
[{...}, {...}, ...]

Clients parse the Link header for the rel="next" entry and follow it. If it is absent, there is no next page. This is elegant and works — the body is a clean array, and pagination information is in the headers where HTTP clients expect it.

When to prefer Link vs an envelope

Prefer Link headerPrefer envelope
Bare array responses are acceptableYou need has_more or total in the body
You want HTTP-native semanticsYou want a consistent JSON shape for all responses
You want to keep the body cleanYou want the metadata to be visible in dev tools without reading headers
Clients use a library that parses LinkClients are hand-written and would rather not parse headers

The trade-off

The Link header is more "HTTP-correct", but it is also less visible. A developer looking at the response in a browser dev tools network panel sees the body immediately and the headers only after clicking. A next_cursor in the body is visible at a glance. This is a real usability difference, and it is why many modern APIs use envelopes rather than headers, even though the header is technically more elegant.

The pragmatic answer: use both. Return a bare array with a Link header for HTTP-native clients, and also include a small envelope with next_cursor for convenience. Or just pick one and be consistent — the difference is not large enough to justify the complexity of dual formats.

Link headers beyond pagination

RFC 8288 defines the Link header for any hypermedia relation, not just pagination. It can also express:

  • rel="deprecation" — pointing to a deprecation notice (Volume 3, Question 3).
  • rel="describedby" — pointing to documentation or schema.
  • rel="author", rel="license" — metadata about the resource.
  • rel="preload" — hinting at a resource that will be needed (related to performance).

This makes the Link header a general-purpose hypermedia mechanism, of which pagination is the most common use case. Using it for deprecation and documentation is good practice — it makes the API self-describing at the HTTP layer.

Common Pitfall

Hardcoding the pagination URL structure in clients. A client that reads response.headers['Link'] and follows rel="next" is future-proof; a client that constructs ?page=N+1 itself will break when the URL structure changes. The whole point of the Link header is that clients do not need to construct URLs — use it that way.

How do you design a search endpoint?

Short Answer

A search endpoint is fundamentally different from a list endpoint: it has a query (free-text), often spans multiple entity types, and needs relevance ranking rather than a fixed sort. It should be a separate endpoint (GET /search?q=...) backed by a search engine (Elasticsearch, OpenSearch, Typesense, Meilisearch), not by the transactional database.

Why search is a separate concern

A list endpoint (GET /users?status=active) is a filter over a single resource type, backed by indexed columns in the operational database. A search endpoint (GET /search?q=alice) is a relevance-ranked match across many fields — name, email, bio, posts, comments — and often across multiple entity types. The operational database cannot answer this efficiently:

  • Full-text matching requires an inverted index. SQL's LIKE '%alice%' cannot use a standard B-tree index and forces a full scan.
  • Relevance ranking is not SQL's strength. Even with tsvector (PostgreSQL full-text search), ranking and highlighting are rudimentary.
  • Cross-entity search spans multiple tables, each with its own join graph — the query becomes a monster that no one wants to maintain.
  • Fuzzy matching, stemming, synonyms, typo tolerance — these are the domain of a search engine, and they matter enormously for user experience.

The standard architecture

  1. Operational database is the source of truth (PostgreSQL, MySQL).
  2. CDC (Change Data Capture) streams changes to a message queue (Kafka).
  3. Indexer consumes the stream and updates the search index (Elasticsearch).
  4. Search endpoint queries the index and returns results, with a reference back to the source-of-truth IDs.
  5. Hydration — the endpoint either returns the search-index document directly (if it contains enough data) or fetches the full resource from the database by ID.

This decouples search from the operational database entirely — search load does not affect transactional performance, and the search index can be rebuilt from the source of truth at any time.

The endpoint design

ParameterPurposeExample
qThe free-text query?q=vintage+camera
typeFilter to one or more entity types?type=product,article
filtersStructured filters (facets)?brand=canon&price_max=500
sortRelevance (default), price, date?sort=price_asc
cursor / pagePagination?cursor=...
limitPage size?limit=20
highlightWhether to include highlighted snippets?highlight=true

The response shape

FieldPurpose
resultsArray of results, each with an id, type, score, and either a full document or a reference
highlightSnippets with <em> or <mark> tags around matched terms
facetsCounts per filter value (e.g., {"brand": {"canon": 42, "nikon": 37}})
meta.totalTotal count of matches (search engines often provide this cheaply)
meta.took_msHow long the search took, for debugging
meta.corrected_querySpelling-corrected version of the query, if different

The facets are what make search useful for e-commerce and content platforms — they let the client display "filter by brand: Canon (42), Nikon (37)" without a separate aggregation query.

Ranking and relevance

A search endpoint must return results in relevance order by default, not by ID or date. The engine's relevance score (BM25, TF-IDF, or a learned ranking model) determines the order. Clients should not need to specify a sort to get good results — the default is "best match first".

Relevance is often tunable per field — a match in the title should rank higher than a match in the body. The engine supports field boosting (title^3, body^1), and the API should expose this to the client only if the client genuinely needs to control it (usually it does not — the backend sets the boost).

Pagination in search

Search results are typically paginated with offset (the search engine handles it), but for very deep pages, the same scale problem applies — the engine must score millions of documents to return page 500. Elasticsearch's search_after is the equivalent of cursor pagination, using the sort key and document ID as a cursor. For most search UIs, offset up to a few hundred pages is fine; beyond that, the UI should encourage refinement (narrower query, additional filters) rather than deep paging.

What not to do

  • Search in the operational database with LIKE '%term%'. It cannot use an index, scans the whole table, and will time out.
  • Return unranked results. Users expect "best match first"; a search that returns results in insertion order is broken.
  • Search across everything without type filtering. A search for "apple" returns the fruit, the company, and the user's contact named Apple — the client needs to filter by type.
  • Expose the search engine's query DSL directly. Elasticsearch's query DSL is powerful and dangerous — it can be used to run expensive queries. The API should expose a curated query interface, not the raw DSL.
  • Return the raw search-engine response. The engine's response contains internal metadata that clients do not need and should not depend on. Normalise it to a stable schema.
Interview Framing

Say: "Search is a separate endpoint backed by Elasticsearch, fed by CDC from the operational database. It returns ranked results with highlights and facets, and the operational database is never queried with LIKE." That demonstrates you understand the separation of concerns and the data-flow architecture.

How do you prevent unbounded queries and query abuse?

Short Answer

Layer four defences: mandatory filters or defaults (no unfiltered queries on large tables), hard result caps (reject requests for more than N items), query complexity limits (reject filters, sorts, or expansions that would be expensive), and server-side timeouts (a query that runs longer than T is killed). Each layer protects against a different attack; together they bound the worst case.

The threat model

Unbounded queries come from three sources:

  • Accidental. A client that forgets a filter, or a UI that fetches "all orders" with no date range. This is the most common cause.
  • Careless. A client that calls GET /users?limit=1000000 because it wants to "cache everything". This works once and then kills the database.
  • Malicious. An attacker that deliberately crafts expensive queries to overload the system (an OWASP API4:2023 "Unrestricted Resource Consumption" attack).

The same defences help with all three. The problem is that a query is not obviously expensive — it looks like any other request. The API must decide, on the server side, whether a request is safe before executing it.

Defence 1 — Mandatory filters

On a large table, no query is allowed to run without a filter that uses an index. The API enforces this:

EndpointRequired filterBehaviour without it
GET /orders?user_id= or ?date_from=400 with an error naming the required filter
GET /events?from=Default to last 24 hours (with a warning header)
GET /users?org_id= (in a multi-tenant app)Tenant is derived from the auth token; no explicit filter needed

The error message should tell the client exactly which filter to add — this converts a 400 into a fixable problem rather than a mystery.

Defence 2 — Hard result caps

Every list endpoint has a maximum page size (typically 100, sometimes 1,000). A request for more returns 400 with a clear error, or (more forgiving) is silently capped with a warning:

Client requestServer behaviour
?limit=50Returns 50 items
?limit=500400: "limit must be between 1 and 100"
?limit=500 (with capping)Returns 100 items, header Warning: 199 - "limit capped at 100"
No limitDefault of 20 or 50

The 400 approach is stricter and forces clients to be honest about their intent. The capping approach is friendlier but hides the problem. Either is defensible; the 400 is better for internal APIs, the capping for public ones (where clients might not read errors).

Defence 3 — Query complexity limits

The cost of a query depends not just on limit but on what the query does. A query that joins five tables, sorts by an unindexed column, and filters with a wildcard is expensive regardless of the limit. The API should estimate the cost before executing:

  • Whitelist filters. Only filters backed by an index are accepted. The set of accepted filters is small and documented.
  • Whitelist sorts. Same — only sorts with indexes. Sorting by an unindexed column returns 400 with a clear error.
  • Limit expansions. If the endpoint supports ?expand=customer,items, cap the number of expansions (e.g., 3) and the depth (no nested expansions).
  • Limit filter combinations. Some combinations are expensive even if each filter is indexed — "sort by date, filter by tag" may be a cross-index query. Cap the number of filters or reject combinations that are known to be slow.
  • Cost function. Compute a cost estimate (number of filters × expansion factor × limit) and reject requests above a threshold. This is what GraphQL's query complexity analysis does — the same idea applies to REST.

Defence 4 — Server-side timeouts

No query should be allowed to run unbounded. The database should have a statement_timeout (or the equivalent), and the API should have a request-level timeout that kills the query and returns 504 (Gateway Timeout) or 503. The client then knows the query was too expensive and can refine it. Without a timeout, one bad query holds a database connection for minutes, and a few of them exhaust the connection pool.

The timeout should be tuned to the endpoint: a search query might be allowed 2 seconds, a list endpoint 500 ms, a report endpoint 30 seconds. Documented timeouts are part of the API contract — a client that needs more than the timeout must use an async endpoint (Volume 1, Question 13).

The layered defence in practice

LayerProtects againstExample
Mandatory filtersAccidental full-table scansGET /orders requires user_id
Result capsMemory and bandwidth abuselimit max 100
Filter/sort whitelistsUnindexed scansOnly filters with indexes are accepted
Cost limitsExpensive combinationsMax 3 filters, no nested expansions
TimeoutsAny runaway querystatement_timeout = 500ms
Rate limitingRepeated abusive requestsVolume 7 covers this in detail

Each layer catches what the others miss. Mandatory filters catch the obvious case; whitelists catch the subtle case; timeouts catch the case nobody anticipated. There is no single defence that is sufficient, which is why the layers are complementary.

Common Pitfall

Relying on the client to add LIMIT. A client that does not is the client that crashes the database. The LIMIT must be enforced by the server, and the server must also cap the total cost of the query — not just the row count. A LIMIT 100 query that joins six tables and sorts by an unindexed column is still expensive.

The ethical dimension

Unbounded queries are not just a technical problem — they are a fairness problem. One client sending a million-row query can degrade service for every other client. Enforcing limits is not hostile to clients; it is protective of the shared resource. The API should communicate this clearly — the docs should state the limits, the errors should explain why the request was rejected, and the limits should be generous enough that no reasonable client hits them.
