Part A — The Foundation Why gRPC is fast, and the schema that makes it work

1

What is gRPC, and why is it faster than REST/JSON?

Short Answer

gRPC is an RPC framework from Google that uses Protocol Buffers for binary serialization and HTTP/2 for transport. It is faster than REST/JSON because binary payloads are 3–10× smaller than JSON, HTTP/2 multiplexes many concurrent streams over one connection without head-of-line blocking at the HTTP layer, and Protobuf decoding is significantly cheaper than JSON parsing. It also generates strongly-typed clients from a .proto file, so schema drift is impossible.

The three performance reasons

ReasonMechanismTypical gain
Binary serialization Protobuf encodes fields as tag-value pairs with length-prefixed varints 3–10× smaller payload than JSON
Faster decoding Length-prefixed binary format with generated decoders; no string parsing 5–10× faster deserialization
HTTP/2 multiplexing Many concurrent streams on one TCP connection; no HTTP-level HOL blocking Eliminates connection setup; 2–5× throughput improvement

Payload size — the concrete comparison

FormatExample payloadSize
JSON {"id": 42, "name": "Alice", "active": true} ~44 bytes
Protobuf Field 1 (id) = 42, Field 2 (name) = "Alice", Field 3 (active) = true ~12 bytes
Protobuf with int64 ID Field 1 = 42 (varint, 1 byte), Field 2 = "Alice" (5 bytes), Field 3 = true (2 bytes) ~8 bytes

The savings come from three things: field names are not sent (only field numbers), integers are variable-length (small values take fewer bytes), and there is no whitespace or punctuation. For a large list of small objects, the compression ratio is dramatic.

HTTP/2 — why the transport matters

HTTP/1.1 serializes requests on a connection: the next request waits for the previous response. The workaround is multiple connections (browsers use 6 per host), but that is expensive and still caps concurrency.

HTTP/2 introduces streams: many requests can be in flight on one connection, interleaved and prioritized. For gRPC, this means thousands of concurrent RPCs share one TCP connection — no handshake per call, no connection pool exhaustion, no per-request overhead.

HTTP/2 also has header compression (HPACK), which matters for gRPC because every call carries metadata (content-type, grpc-timeout, authorization, trace headers). Without HPACK, the header overhead would dominate for small messages.

Code generation and schema

The .proto file is the source of truth. It defines services, methods, and message types. protoc generates:

  • Client stubs — typed methods for calling the service.
  • Server interfaces — the methods to implement.
  • Message classes — typed data classes for the payloads.

Because both sides generate from the same schema, field renames, type mismatches, and missing fields are compile-time errors, not runtime bugs. This is a significant advantage over REST, where the contract is documentation that must be tested separately.

What gRPC gives beyond speed

  • Streaming — unary, server-streaming, client-streaming, and bidirectional-streaming RPCs are first-class.
  • Deadlines and cancellation — every call carries a deadline; the framework propagates it and cancels work when exceeded.
  • Rich error model — google.rpc.Status with error codes, messages, and structured details.
  • Interceptors — middleware for auth, logging, tracing, retries.
  • Reflection — servers can describe their own schema at runtime (useful for tooling).

What gRPC costs

  • Browser support is limited — gRPC-Web requires a proxy and does not support bidirectional streaming. For browser clients, REST or GraphQL is usually easier.
  • Debugging is harder — binary payloads are opaque; you need grpcurl and the .proto file. curl and browser dev tools do not work.
  • Caching is harder — HTTP caching (ETag, Cache-Control) does not apply to gRPC. If you need CDN caching, you need a REST layer.
  • Schema changes are visible — adding a field is backward-compatible, but removing one or changing its type requires a new field number; a discipline many teams get wrong.
  • Operational complexity — load balancers must support HTTP/2; some firewalls block it; the tooling ecosystem is smaller than HTTP/JSON.
Interview Framing

Say: "gRPC is binary Protobuf over HTTP/2. Smaller payloads, faster decoding, multiplexed connections, and typed schemas. Best for internal service-to-service — the public API stays REST or GraphQL." That covers the mechanism and the placement in the architecture.

How do Protocol Buffers work, and what are the compatibility rules?

Short Answer

Protobuf encodes messages as a sequence of tag-value pairs: the tag is (field_number << 3) | wire_type, and the value depends on the field's type. Compatibility is defined by field numbers — adding a field with a new number is backward-compatible; changing a field's number or type breaks compatibility; removing a field requires reserving its number so it is never reused.

The wire format

Wire typeUsed forEncoding
0 (Varint)int32, int64, uint32, uint64, sint32, sint64, bool, enumVariable-length integer
1 (64-bit)fixed64, sfixed64, double8 bytes, little-endian
2 (Length-delimited)string, bytes, embedded messages, packed repeatedLength varint, then bytes
5 (32-bit)fixed32, sfixed32, float4 bytes, little-endian

Example: {"id": 42, "name": "Alice"} with the schema {int32 id = 1; string name = 2;} encodes as:

BytesMeaning
0x08Tag: field 1, wire type 0 (varint)
0x2AVarint value 42
0x12Tag: field 2, wire type 2 (length-delimited)
0x05Length: 5 bytes
0x41 0x6C 0x69 0x63 0x65"Alice"

Total: 9 bytes. The JSON equivalent is 27 bytes. The savings are from removing field names, punctuation, and — for small integers — the fixed 4-byte representation JSON uses implicitly.

Field numbers, not names

The wire format uses field numbers, not field names. Renaming a field in the .proto file is a no-op on the wire — the bytes are identical. This is why Protobuf is so flexible for schema evolution: the field name is a code-level concern, not a wire-level one.

But it also means that once a field number is used, it can never be reused for a different field. If field 3 used to be user_id and is removed, adding a new field with number 3 breaks every old client and every persisted message — the field 3 will be decoded as the new field's type, producing garbage.

The compatibility rules

ChangeCompatible?Notes
Add a field (new number)YesOld clients ignore it; new clients decode it if present
Remove a fieldYes (with reserve)Reserve the number and name so it is never reused
Rename a fieldYesWire format uses numbers, not names
Change a field's numberNoWire format depends on the number
Change int32 to int64Yes (usually)Both varints; values > 2³² may be truncated by old clients
Change int32 to stringNoWire type changes (varint → length-delimited)
Change a singular field to repeatedNo (usually)Different encoding; some cases work, but risky
Add a new enum valueYesOld clients must handle unknown values
Remove an enum valueNoOld clients may still send it
Change a required field to optionalYes (proto3)proto3 has no required; proto2 semantics differ

Reserved fields

When removing a field, reserve its number and name so a future developer cannot reuse them:

SyntaxMeaning
reserved 3, 5, 7;Reserve specific field numbers
reserved 9 to 11;Reserve a range of numbers
reserved "old_field_name";Reserve a field name

Reserving a field number prevents a future developer from accidentally reusing it. Without this, a seemingly harmless addition (a new field with number 3) breaks every old client, every persisted message, and every stored event — a silent, catastrophic bug.

proto2 vs proto3

Aspectproto2proto3
Required fieldsSupported (required)Not supported
Optional fieldsSupported (optional)Implicit; added back in proto3 v3.15 for presence
PresenceExplicit — you can distinguish absent from defaultImplicit by default; must use optional to distinguish
Default valuesExplicitImplicit — 0, "", false, empty list
Syntaxsyntax = "proto2";syntax = "proto3";

proto3 is the current default and the recommended choice. The lack of required is deliberate — required fields are a compatibility hazard (removing the requirement is a breaking change). The optional keyword was added back to proto3 to support explicit presence, which is needed for distinguishing "absent" from "default".

The schema registry and buf

For organizations with many services, a schema registry is essential: a central store of .proto files, with versioning and validation. buf is the standard tool — it lints the schema, checks for breaking changes (compared to a baseline), and publishes the generated code.

buf commandWhat it does
buf lintEnforces naming and style conventions
buf breakingFails if the schema introduces a breaking change
buf generateGenerates code from the schema
buf pushPublishes to the BSR (Buf Schema Registry)

The breaking-change check is the Protobuf equivalent of contract testing (Volume 3, Question 9) — it fails CI when a change would break existing clients.

Common Pitfall

Reusing a field number after removing a field. The new field appears compatible (it uses a number that is "free"), but old clients decode the bytes as the old field's type — corrupting the data. The fix: reserve the number when removing the field, and enforce it with buf breaking.

Interview Framing

Say: "Protobuf uses field numbers, not names, on the wire. Adding a field is compatible; removing one requires reserving the number. Changing a field's number or type breaks compatibility. buf breaking enforces this in CI." That covers the format, the rules, and the discipline.

What are the four RPC types in gRPC, and when do you use each?

Short Answer

gRPC defines four RPC types: unary (one request, one response — the classic RPC), server-streaming (one request, many responses — the server pushes a stream), client-streaming (many requests, one response — the client uploads a stream), and bidirectional streaming (many requests, many responses — both sides stream concurrently). The choice depends on the data flow pattern: is the payload small, or is it a stream that should not be buffered?

TypeRequestResponseUse case
Unary One message One message Classic request/response — get user, create order
Server streaming One message Stream of messages Server pushes data — logs, events, progress updates, large result sets
Client streaming Stream of messages One message Client uploads data — batch uploads, telemetry, file chunks
Bidirectional streaming Stream of messages Stream of messages Chat, real-time collaboration, interactive protocols

Unary — the classic RPC

The most common type, equivalent to REST's request/response. The client sends one message, waits, and receives one message. The schema:

Proto
 
service UserService {
  rpc GetUser(GetUserRequest) returns (User);
  rpc CreateUser(CreateUserRequest) returns (User);
}

Use unary when: the request and response are both small, the operation completes in a bounded time, and there is no need to stream. This is the default — 90% of gRPC calls are unary.

Server streaming

The client sends one request; the server sends a stream of responses. The client reads them as they arrive. The schema:

Proto
 
service OrderService {
  rpc WatchOrders(WatchRequest) returns (stream OrderEvent);
  rpc ListOrders(ListRequest) returns (stream Order);
}

Use server streaming when:

  • Pushing real-time events — the server sends new orders as they are created, the client processes them incrementally.
  • Large result sets — instead of returning a million rows in one response (which the client must buffer), the server streams them one by one; the client processes each and does not hold the whole list in memory.
  • Progress updates — a long-running operation streams its progress (0%, 10%, ..., 100%).

Client streaming

The client sends a stream of messages; the server processes them and sends one response. The schema:

Proto
 
service UploadService {
  rpc UploadFile(stream FileChunk) returns (UploadResult);
  rpc SendTelemetry(stream Metric) returns (Ack);
}

Use client streaming when:

  • Uploading data — a large file is sent in chunks; the server assembles them and returns the result.
  • Batching data — the client sends 10,000 records in a stream, the server inserts them in bulk, returns a summary.
  • Real-time input — a device sends sensor readings continuously, the server aggregates them and responds with a summary on stream end.

Bidirectional streaming

Both sides send streams concurrently. The client and server exchange messages freely. The schema:

Proto
 
service ChatService {
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}
service EditorService {
  rpc Collaborate(stream Edit) returns (stream Edit);
}

Use bidirectional streaming when:

  • Real-time chat — the client sends messages and receives others, both streams open simultaneously.
  • Collaborative editing — both sides send edits and receive the other's edits.
  • Interactive protocols — a protocol with back-and-forth (a game, a live control interface, a trading system).
  • Server push with client input — the server streams data, the client streams acknowledgements or commands on the same connection.

The performance characteristics

TypeLatencyThroughputMemory
UnaryLow per callLimited by connection concurrencyConstant
Server streamingLow first byte; streamed as availableHigh — one connection, many messagesConstant on both sides (streaming)
Client streamingOne response at endHigh — upload over one connectionConstant on client; server buffers or processes incrementally
BidirectionalLowest — no round-trip waitHighestConstant if processing incrementally

When NOT to use streaming

  • If the response is small — a unary call is simpler and faster to code.
  • If the client cannot process incrementally — a client that needs the whole list to render a page gains nothing from streaming.
  • If the client is a browser — gRPC-Web supports only unary and server streaming; client and bidirectional streaming require WebSocket, which is a different protocol.
  • If the stream can be unbounded — a stream that never ends (a live event feed) requires the client to handle reconnection and gap-filling (like subscriptions).

The flow control mechanism

All streaming RPCs use HTTP/2 flow control — the receiver tells the sender how many bytes/streams it can handle. This is backpressure at the transport layer: a slow client causes the server to pause sending until the client catches up. The application does not need to implement flow control; the transport does it.

But application-level backpressure is still the application's responsibility — if the server produces data faster than the client can process it, the transport flow control will pause the server, but the server's buffers may grow. The application should have its own buffer limits and its own backpressure signals.

Trade-off

Streaming is more powerful but more complex: connection lifetime, flow control, error handling, partial failures, client reconnection. For most APIs, unary is the right default — use streaming only when the data flow genuinely requires it (large payloads, real-time push, bidirectional protocols).

Interview Framing

Say: "Unary for classic request/response, server-streaming for push and large result sets, client-streaming for uploads, bidirectional for chat and collaboration. Streaming for large payloads and real-time; unary otherwise." That covers the four types and the choice.

How do interceptors work in gRPC, and what middleware should every service have?

Short Answer

An interceptor is gRPC's middleware — a hook that wraps the RPC handler, allowing cross-cutting concerns (auth, logging, tracing, retries, metrics) to be implemented once and applied to every call. There are two kinds: client interceptors (run on the calling side) and server interceptors (run on the receiving side). Both have access to the metadata (headers) and the request/response, and can short-circuit the call.

The interceptor chain

SideDirectionExample
Client interceptor Runs before the request goes out Attach the auth token, add trace headers, measure latency, retry on failure
Server interceptor Runs before the handler Validate the token, log the request, start a trace span, enforce rate limits

Interceptors compose: multiple interceptors form a chain, each wrapping the next. The order matters — an auth interceptor should run before a logging interceptor (so the log includes the authenticated user), and a recovery interceptor should run outermost (so it catches panics from any inner interceptor).

The essential server interceptors

InterceptorPurpose
Recovery Catches panics; returns a structured error instead of crashing the server
Request ID Generates (or propagates) a unique ID per request; adds it to logs and traces
Logging Logs the method, duration, status, and relevant metadata
Tracing Starts a span for the RPC; propagates the trace context
Authentication Validates the token (from metadata); resolves the identity
Authorization Checks the identity has permission for the method
Rate limiting Checks per-client limits; returns RESOURCE_EXHAUSTED if exceeded
Metrics Records latency histograms, error counts, in-flight requests
Deadline enforcement Propagates the deadline to downstream calls; cancels if exceeded

The essential client interceptors

InterceptorPurpose
Auth Attaches the token to every request
Trace propagation Injects the trace context into the metadata (W3C traceparent)
Deadline Sets a default deadline; propagates the remaining time
Retry Retries on transient errors with backoff (Volume 5, Question 10)
Circuit breaker Stops calling a failing service; fails fast
Metrics Records latency and errors for the client

The metadata — gRPC's headers

Interceptors communicate via metadata — the gRPC equivalent of HTTP headers. Metadata is a set of key-value pairs, sent with every call. The standard use cases:

Metadata keyPurpose
authorizationBearer token or other credentials
grpc-timeoutThe deadline (set by the gRPC framework)
x-request-idCorrelation ID
traceparentW3C trace context
x-b3-traceidZipkin B3 trace context
user-agentClient identity

Metadata keys are case-insensitive, and custom keys should be lowercase with hyphens (matching HTTP conventions). Binary metadata is also supported (with the -bin suffix), for cases where the value is not a UTF-8 string.

The interceptor implementation

Server interceptor (Go-style pseudocode)
 
func LoggingInterceptor(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
  start := time.Now()
  resp, err := handler(ctx, req)
  duration := time.Since(start)
  log.Infof("method=%s duration=%v error=%v", info.FullMethod, duration, err)
  return resp, err
}

The interceptor receives the context, the request, the method info, and the handler. It can inspect and modify the context and request, call the handler, and inspect and modify the response and error.

The interceptor chain ordering

The order matters because interceptors can short-circuit. The standard order (outermost to innermost):

  1. Recovery — catches panics from everything inside.
  2. Request ID — generates the correlation ID used by all subsequent log lines.
  3. Metrics — records latency for every request, including auth failures.
  4. Tracing — starts a span that covers the whole request.
  5. Logging — logs the request; will include the correlation ID.
  6. Authentication — validates the token; if it fails, the request never reaches the handler.
  7. Authorization — checks the identity's permissions.
  8. Rate limiting — checks the client's quota.
  9. Handler — the actual RPC method.

This ordering means: a panicked handler is caught; every request has a correlation ID; every request is measured and traced; auth failures are logged and metered; the handler only runs for authenticated, authorized, rate-limited requests.

Where interceptors do not apply

Interceptors run per-RPC, not per-stream-message. For streaming RPCs, a unary interceptor sees the stream's creation and completion, but not each message. Streaming interceptors are more complex — they wrap the stream itself, allowing per-message observation, but this is less commonly used.

Interceptors also do not run for the gRPC connection setup (the HTTP/2 handshake) — that is a transport concern, handled by TLS and connection-level auth (mTLS).

Common Pitfall

Placing the auth interceptor inside the logging interceptor. The log will contain every request, but the authenticated identity is not available in the log — because the logging interceptor runs before auth has resolved it. The fix: auth before logging, or have the log read the identity from the context after auth.

Interview Framing

Say: "Interceptors are the middleware — recovery, tracing, logging, auth, rate limiting — applied as a chain. The order matters: recovery outermost, auth before the handler. Metadata is how interceptors communicate the request context." That covers the mechanism and the essential interceptors.

How do deadlines and cancellation work in gRPC?

Short Answer

Every gRPC call carries a deadline — an absolute time by which the call must complete. The client sets it; the framework propagates it to the server and to any downstream calls the server makes. If the deadline is exceeded, the call is cancelled (both sides stop working) and the client receives DEADLINE_EXCEEDED. Cancellation is the mechanism: a client can cancel an in-flight call, and the cancellation propagates through the chain.

Why deadlines matter

Without deadlines, a slow call can hold resources indefinitely. The server thread blocks, the connection holds, the client waits — and eventually someone gives up. Deadlines bound this worst case, and propagation ensures that a deadline set at the edge limits the whole call chain, not just the first hop.

Without deadlinesWith deadlines
A slow dependency stalls the whole chain The deadline limits the chain — if downstream is slow, the whole call fails fast
Threads and connections held indefinitely Resources are released when the deadline fires
Client waits forever, retries, retries again Client gets a clear DEADLINE_EXCEEDED, can decide to retry or give up

Setting a deadline

LanguageHow to set
Goctx, cancel := context.WithTimeout(ctx, 5*time.Second)
Javastub.withDeadlineAfter(5, TimeUnit.SECONDS)
Pythonstub.GetUser(request, timeout=5)
Node.jsclient.getUser(request, {deadline: Date.now() + 5000})

The deadline is usually set at the top — the API gateway or the client — and propagated. Each layer passes the remaining time to the next, so the deadline is consistent across the chain. A service that receives a call with 4 seconds remaining should not make a downstream call with a 30-second deadline — the downstream should get a deadline within the remaining 4 seconds (or less, to leave time for the response to propagate).

Propagation — the key mechanism

The deadline is carried in the grpc-timeout metadata header, set by the client. The server reads it, and its context has the same deadline. When the server makes downstream calls, it passes the remaining time. This is why a deadline set at the edge bounds the whole call chain, no matter how many hops it takes.

HopDeadlineRemaining
Client10 seconds from now10s
Service ASame absolute time~9.5s (after network)
Service A → Service BSame absolute time, minus a small buffer~9s
Service B → Service CSame absolute time, minus a small buffer~8.5s
Service C → DatabaseSame absolute time, minus a small buffer~8s

Each hop reserves a small buffer (say, 100ms) so that the response can propagate back before the deadline fires. Without the buffer, service B's response might arrive at service A after service A has already cancelled — wasted work.

Cancellation

Cancellation is the client's mechanism to stop an in-flight call. It can be explicit (the client calls cancel() on the context) or implicit (the deadline fires). The cancellation propagates:

  1. Client cancels the call.
  2. The server's context is cancelled.
  3. The server's handler sees the cancellation (via ctx.Done() or an exception).
  4. Any downstream calls the server made are also cancelled (if the server propagated the context).
  5. The server returns early — no response is sent.

The cancellation saves work: a server that sees its context cancelled should stop processing, release resources, and return immediately. This is particularly important for streaming RPCs — a client that disconnects should not leave the server streaming forever.

The cancellation discipline

The server-side code must check for cancellation:

  • Long-running loops — check ctx.Done() at the top of each iteration.
  • Database queries — pass the context to the query; the database client will cancel the query if the context is cancelled.
  • External calls — pass the context; the gRPC client will cancel the call if the context is cancelled.
  • Streaming handlers — check the context between messages; if cancelled, return early.

A server that ignores cancellation continues to consume resources for a request nobody is waiting for. This is a resource leak, and it accumulates — the dead requests pile up until the server is overwhelmed.

The status code on deadline

When a deadline fires, the client receives DEADLINE_EXCEEDED (gRPC status code 4). This is distinct from CANCELLED (status code 1, when the client explicitly cancelled) and from UNAVAILABLE (status code 14, when the server is unreachable).

Status codeMeaningClient action
CANCELLEDThe caller cancelledDo not retry — the cancellation was intentional
DEADLINE_EXCEEDEDThe deadline passedRetry with a longer deadline, or give up
UNAVAILABLEThe server is unreachable or overloadedRetry with backoff

The "retry amplification" problem

A client with a short deadline retries aggressively. The server sees many retries, all with short deadlines. The server is now processing the same request multiple times. The fix: retries must be budgeted (Volume 5, Question 10) and the deadline must be long enough to allow the retries — a 100ms deadline with three retries gives the server a 100ms window per attempt, which may be too short for any attempt to succeed.

Common Pitfall

Setting a deadline only at the client, without propagating it. The client gives up after 5 seconds, but the server continues processing — because it never saw a deadline. The fix: propagate the context (which carries the deadline) to every downstream call; do not create a fresh context with a new deadline in the middle of the chain.

Interview Framing

Say: "Every call has a deadline that propagates through the chain — a 10-second deadline at the edge limits every hop. The server checks the context for cancellation, stops work when it fires, and returns DEADLINE_EXCEEDED. Without propagation, the server keeps working on a request nobody is waiting for." That covers the mechanism and the discipline.

How does error handling work in gRPC — status codes and google.rpc.Status?

Short Answer

gRPC has its own status code set (16 codes, distinct from HTTP), carried in trailers or headers. The basic codes (OK, NOT_FOUND, INVALID_ARGUMENT, etc.) cover the common cases. For richer errors, gRPC uses google.rpc.Status — a message with a code, a message, and a list of Any-encoded details. The details carry structured error information (validation failures, retry guidance, error codes) that the client can parse.

The 16 gRPC status codes

CodeNumberMeaningHTTP analogue
OK0Success200
CANCELLED1The call was cancelled499 (client closed)
UNKNOWN2Unknown error500
INVALID_ARGUMENT3Invalid input400
DEADLINE_EXCEEDED4The deadline was exceeded504

The basic error response

The simplest error response is a status code and a message:

Conceptual response
 
status: NOT_FOUND
message: "User 42 not found"

The client can check status and display message. This is fine for simple cases, but the message is a human-readable string — the client cannot parse it reliably. For machine-readable error classification, use the details.

google.rpc.Status — the structured error

FieldTypePurpose
codeint32The gRPC status code (e.g., 5 for NOT_FOUND)

detailsrepeated AnyStructured error details (see below)

The details is a list of Any-encoded messages — each is a protobuf message of a specific type, serialized with its type URL. This lets the server send rich structured errors that the client can decode if it knows the type.

The standard detail types

TypePurpose
BadRequest Validation failures — a list of FieldViolation (field path + description)

RetryInfo How long to wait before retrying (the equivalent of Retry-After)
QuotaFailure Which quota was exceeded and by how much
PreconditionFailure Which precondition failed — for state conflicts

A structured error example

Error response
 
status:
  code: INVALID_ARGUMENT (3)
  message: "Validation failed"
  details:
    - type: "type.googleapis.com/google.rpc.BadRequest"
      value:
        field_violations:
          - field: "email"
            description: "must be a valid email address"
          - field: "age"
            description: "must be greater than 0"
    - type: "type.googleapis.com/google.rpc.ErrorInfo"
      value:
        reason: "INVALID_EMAIL_FORMAT"
        domain: "api.example.com"
        metadata:
          email: "foo"
    - type: "type.googleapis.com/google.rpc.Help"
      value:
        links:
          - description: "Email validation rules"
            url: "https://docs.example.com/validation/email"

This gives the client everything it needs: the field names and messages (for form display), the machine-readable reason (for conditional logic), the metadata (for debugging), and the documentation link (for the developer).

Why this matters

The google.rpc.Status model is the gRPC equivalent of RFC 7807 (Volume 8, Question 5). It solves the same problem: a structured error that both a machine and a human can understand, with extensibility for domain-specific details.

Without it, an error is a code and a string — the client can display the string but cannot act on it. With it, the client can distinguish "retry this" from "fix the input" from "contact support" without parsing the string.

The error code mapping

The gRPC codes map cleanly to HTTP codes, which is important when a REST gateway wraps a gRPC service (Question 7). The grpc-gateway does this mapping automatically:

How do you use gRPC from a browser? gRPC-Web and grpc-gateway?

Short Answer

Browsers cannot speak native gRPC — they cannot access HTTP/2 trailers, which gRPC requires for status. Two solutions: gRPC-Web (a protocol adaptation that encodes status in trailers-as-headers, supported by all modern browsers via a proxy) and grpc-gateway (a reverse proxy that translates REST/JSON to gRPC, so the browser speaks REST). gRPC-Web is better for gRPC-native clients that happen to run in a browser; grpc-gateway is better when the browser needs a normal HTTP API.

Why browsers cannot speak native gRPC

gRPC depends on HTTP/2 features that browsers do not expose to JavaScript:

  • Trailers — gRPC sends the status in HTTP trailers (after the body); browsers do not expose trailers to fetch/XHR.
  • Streaming request bodies — gRPC can stream from client to server; browsers cannot (the full body is sent at once).
  • Fine-grained flow control — gRPC uses HTTP/2 flow control per stream; browsers do not expose this.
  • Binary framing — gRPC messages are length-prefixed binary frames; JavaScript would need a custom parser.

gRPC-Web — the protocol adaptation

gRPC-Web is a variant of gRPC that works over HTTP/1.1 and HTTP/2 by moving status information into headers (which browsers expose) and constraining streaming to server-push only. The browser uses a gRPC-Web client (a JavaScript library); a proxy on the server side (Envoy, grpc-web-proxy) translates gRPC-Web to gRPC.

FeaturegRPCgRPC-Web

Server streamingYesYes
Client streamingYesNo
Bidirectional streamingYesNo
Status locationTrailersHeaders
ProtocolHTTP/2HTTP/1.1 or HTTP/2
Browser supportNo (needs proxy)Yes (with proxy)

The gRPC-Web architecture:

ComponentResponsibility
BrowserUses gRPC-Web client library; sends gRPC-Web requests
gRPC-Web proxy (Envoy)Translates gRPC-Web to gRPC; forwards to the backend
gRPC serverSpeaks native gRPC; handles the request as usual

The proxy is the trade-off — an extra hop, an extra component to operate. For teams already running Envoy (from a service mesh), the proxy is already there; for others, it is additional infrastructure.

grpc-gateway — REST to gRPC translation

grpc-gateway is a different approach: it exposes the gRPC service as a REST API, so the browser speaks normal HTTP/JSON. The gateway is generated from the .proto file, with annotations specifying the REST mappings:

Proto annotation
 
service UserService {
  rpc GetUser(GetUserRequest) returns (User) {
    option (google.api.http) = {
      get: "/v1/users/{id}"
    };
  }
}

The gateway generates a Go (or other language) server that translates GET /v1/users/42 into GetUser{id: 42}, calls the gRPC service, and translates the response back to JSON. The browser sees a normal REST API; the backend speaks gRPC.

AdvantageTrade-off

Which to choose

Bidirectional streaming in a browserNot possible with gRPC-Web — use WebSocket

The hybrid architecture

In practice, many systems use both: the public REST API is exposed via grpc-gateway (for browsers and third parties); the internal services speak native gRPC to each other; the mobile apps use native gRPC (which is faster and more battery-efficient than REST/JSON).

ClientProtocol

The alternative: don't use gRPC for the browser

Sometimes the simplest answer is: don't expose gRPC to browsers at all. Build a REST API for the browser (or GraphQL), and use gRPC only for service-to-service. This avoids the proxy, the two-API maintenance, and the gRPC-Web limitations. The cost: two API surfaces (REST for external, gRPC for internal), but the two are documented separately, and the trade-off is accepted.

Common Pitfall

Assuming gRPC-Web supports bidirectional streaming. It does not — only unary and server-streaming. A browser app that needs bidirectional (chat, collaboration) must use WebSocket, not gRPC-Web.

Interview Framing

Say: "Browsers cannot speak native gRPC. Two options: gRPC-Web with a proxy for gRPC-native clients in a browser, or grpc-gateway for a REST API over the gRPC service. For most cases, a REST API for the browser and gRPC for internal is simpler." That covers the two mechanisms and the pragmatic answer.

How does load balancing work for gRPC, and why is it different from HTTP?

Short Answer

gRPC uses HTTP/2 with long-lived connections, so per-request load balancing at an L4 proxy does not work — the client holds one connection to one backend, and all requests go there. The solutions are: client-side load balancing (the client knows the backends and picks per-request), L7 proxies that understand HTTP/2 (Envoy, Linkerd), and service mesh sidecars (which handle the load balancing transparently). The problem is fundamentally different from HTTP/1.1, where each request is a new connection.

Why gRPC breaks L4 load balancers

An L4 load balancer (AWS NLB, IPVS) routes based on the connection's IP/port. With HTTP/1.1, each request is a separate connection (or a small pool), so the L4 balancer distributes them across backends. With gRPC, the client opens one connection and multiplexes all requests over it — the L4 balancer sees one connection and routes it to one backend. Every request goes to that backend.

Consequences:

  • Uneven distribution — one backend gets all the client's traffic.
  • No failover — if the backend dies, the client's connection breaks, and the client must reconnect (potentially to the same dead backend).
  • Hot spots — a client with high traffic concentrates on one backend.

Client-side load balancing

The client knows the list of backends and picks one per request (or per call). The client uses a load balancing policy:

PolicyBehaviour
Round-robinCycle through backends per RPC
Pick-firstUse the first healthy backend; fail over on error
Least-requestPick the backend with the fewest in-flight requests
Consistent hashHash the request key to pick the backend (for affinity)

The client must discover the backends — via DNS, a service registry (Consul, etcd), or the Kubernetes API. The discovery is usually handled by the gRPC client library's resolver, which watches the registry and updates the backend list when it changes.

The advantages: accurate per-request distribution, low latency (no extra hop), no central load balancer to bottleneck. The cost: every client must implement the load balancing logic (usually via the gRPC library — it is built-in), and the discovery must be correct.

L7 proxy load balancing

An L7 proxy (Envoy, NGINX with HTTP/2 support) understands HTTP/2 and can route per-stream, not per- connection. The client opens one connection to the proxy; the proxy opens connections to each backend and routes each RPC to the appropriate backend.

AspectL4 LBL7 proxy
Routing unitConnectionStream (request)
HTTP/2 supportPass-through (connection)Native
gRPC load balancingBroken (all to one backend)Works — per-RPC distribution
Extra hopNoYes (proxy)
LatencyMinimalSmall overhead (1–3 ms)

Envoy is the standard for gRPC load balancing — it is HTTP/2-native, supports per-stream routing, and integrates with service discovery. NGINX with grpc_pass works too, but is less capable for advanced routing.

Service mesh sidecars

In a service mesh (Istio, Linkerd), each service has a sidecar proxy. The client sends gRPC to its sidecar; the sidecar discovers the destination's sidecars and load-balances per-request. From the application's perspective, it is calling a single endpoint; the mesh handles the distribution.

The mesh gives:

  • Transparent load balancing — the application does not implement it.
  • mTLS — every call is encrypted and authenticated.
  • Retries, timeouts, circuit breakers — uniform policy.
  • Observability — metrics and traces per call.

The cost: the sidecar adds a hop and resource overhead; the mesh is a control plane to operate. For organizations with many services, the operational cost is amortized; for small deployments, it is over-engineering.

The Kubernetes special case

Kubernetes Services (ClusterIP) use kube-proxy at L4 — the gRPC load balancing problem is inherent. The workarounds:

  • Headless service + client-side LB — the service returns the pod IPs; the client load balances.
  • L7 ingress — an Ingress controller (Envoy, Traefik, NGINX) that handles HTTP/2.
  • Service mesh — Istio, Linkerd, Consul Connect.

The default Kubernetes Service is not suitable for gRPC without one of these. This surprises teams new to gRPC on Kubernetes — the connections all go to one pod.

The health check integration

gRPC has a standard health checking protocol (the grpc.health.v1.Health service). The load balancer (client or proxy) can query it to determine whether a backend is healthy:

ServicePurpose
CheckQuery the health of a specific service
WatchSubscribe to health changes

The client-side balancer uses this to remove unhealthy backends from rotation. The server must implement the health service (the gRPC library provides the boilerplate) and wire it to the actual health status (database connectivity, dependency health).

Common Pitfall

Deploying gRPC behind a default Kubernetes Service (ClusterIP) without client-side load balancing or an L7 ingress. All requests go to one pod — the other pods idle, and the hot pod saturates. The fix: headless service + client LB, or an L7 proxy, or a service mesh.

Interview Framing

Say: "gRPC uses HTTP/2 with long-lived connections, so an L4 load balancer routes the whole connection to one backend. The solutions are client-side LB with service discovery, an L7 proxy like Envoy, or a service mesh. On Kubernetes, the default Service is not enough — use a headless service or an L7 ingress." That covers the problem and the solutions.

How do you observe and debug a gRPC service in production?

Short Answer

gRPC observability uses the same three pillars as any service: metrics (per-RPC latency, error rate, in-flight count, message sizes), tracing (spans across the call chain, with the trace context propagated in metadata), and logging (structured logs with the correlation ID and method). The additional gRPC-specific tools: channelz (per-connection and per-channel stats), grpcurl (a command-line client), reflection (the schema over the wire), and the health service.

The standard gRPC metrics

MetricLabelsPurpose
grpc_server_started_totalmethod, serviceRPCs started
grpc_server_handled_totalmethod, codeRPCs completed, by status code
grpc_server_handling_secondsmethod, codeLatency histogram
grpc_server_msg_received_totalmethodMessages received (streaming)
grpc_server_msg_sent_totalmethodMessages sent (streaming)
grpc_client_started_totalmethod, targetClient calls started
grpc_client_handled_totalmethod, code, targetClient calls completed
grpc_client_roundtrip_secondsmethod, code, targetClient round-trip latency

These are the standard metrics from the OpenTelemetry gRPC instrumentation. The code label is critical — it distinguishes success from each error status. A high rate of UNAVAILABLE is a different problem from a high rate of INVALID_ARGUMENT.

Tracing with context propagation

The trace context is carried in metadata (W3C traceparent header or the legacy B3 headers). The client interceptor injects it; the server interceptor extracts it and starts a child span. For streaming RPCs, the span covers the whole stream; each message may have its own span (for detailed tracing).

SpanWhat it shows
Client span (unary)Request sent, response received, duration
Server span (unary)Request received, handler duration, response sent
Stream spanThe whole stream's lifetime
Message span (optional)Per-message send/receive

Structured logging

Every log line includes:

FieldContent
trace_idThe distributed trace ID
span_idThe current span

status_codeThe gRPC status
duration_msThe RPC duration
request_idThe correlation ID
client_idThe authenticated identity
error_messageThe error (if any)

grpcurl — the command-line client

grpcurl is the gRPC equivalent of curl. It speaks gRPC, uses reflection to discover the schema (or takes a .proto file), and prints the response:

CommandWhat it does
grpcurl -plaintext localhost:50051 listList all services
grpcurl -plaintext localhost:50051 list users.UserServiceList methods of a service
grpcurl -plaintext -d '{"id": 42}' localhost:50051 users.UserService/GetUserCall a method
grpcurl -plaintext -d @ localhost:50051 users.UserService/ChatBidirectional streaming (reads from stdin)

grpcurl requires the schema — either via reflection (the server exposes it) or a .proto file (with -proto). In production, reflection is often disabled for security; the .proto file is used instead.

Reflection — the schema over the wire

gRPC reflection is a service (the grpc.reflection.v1alpha.ServerReflection service) that lets a client query the server's schema at runtime. It enables:

  • grpcurl without a .proto file — the tool discovers the schema.
  • Documentation tools — generate API docs from the live schema.
  • Debugging — a developer can explore the schema without the source code.

But reflection is also an information disclosure risk — an attacker can enumerate every method, message, and field. In production, reflection should be disabled (or restricted to internal networks).

channelz — the connection inspector

channelz is a gRPC-specific diagnostic service that exposes per-channel, per-connection, and per-server stats. It is the equivalent of "show me the connection state" for gRPC:

Channelz queryWhat it reveals
List serversAll servers on this process, with stats
List channelsAll channels (client connections), with state (CONNECTING, READY, TRANSIENT_FAILURE)
Describe a channelTarget, state, sub-channels, calls started/succeeded/failed
Describe a socketThe underlying TCP socket (addresses, bytes, options)

channelz is useful for debugging connection issues — a channel stuck in TRANSIENT_FAILURE means the client cannot connect to any backend. It is exposed as a gRPC service or via a web UI (usually only in development/staging).

The health service

The standard grpc.health.v1.Health service reports the health of the server. The Kubernetes liveness and readiness probes can call it (via a grpc_health_probe binary). The service returns SERVING, NOT_SERVING, or UNKNOWN per service.

Wiring the health service to the actual dependencies (database, cache, downstream services) gives the load balancer an accurate signal — a backend that cannot reach its database reports NOT_SERVING and is removed from rotation.

The streaming-specific observability

For streaming RPCs, the standard metrics capture the stream's lifetime, but not the per-message behavior. Additional metrics:

  • Messages per stream — a stream that sends 1 message vs 10,000 is very different.
  • Stream duration — a long-lived stream (chat) vs a short one (upload) has different expectations.
  • Flow control stalls — the stream paused waiting for the peer to consume.
  • Client cancellations — the client disconnected before the stream ended.
Common Pitfall

Enabling reflection in production without authentication. The schema is exposed to anyone who can reach the server — including attackers. The fix: disable reflection in production, or restrict it to internal networks / authenticated users.

Interview Framing

Say: "The three pillars — metrics with the status code label, trace context in metadata, structured logs with method and trace ID. Plus grpcurl for debugging, channelz for connection state, and the health service for readiness. Reflection off in production." That covers the stack.

gRPC vs REST vs GraphQL — when does each actually win?

Short Answer

gRPC wins for internal service-to-service — performance, typed contracts, streaming, and code generation across languages. REST wins for public APIs — universal tooling, HTTP caching, and zero learning curve. GraphQL wins for client-driven product surfaces with heterogeneous clients — flexible queries and rapid frontend iteration. Most large systems use all three at different layers.

DimensiongRPCRESTGraphQL
Wire formatProtobuf (binary)JSON (text)JSON (text)
TransportHTTP/2HTTP/1.1 or 2HTTP (usually POST)
Contract.proto (typed, codegen)OpenAPI (documentation)SDL (typed, codegen)
Browser nativeNo (needs proxy)YesYes
StreamingNative, four typesSSE, WebSocketSubscriptions
HTTP cachingNoNativeHard (persisted queries help)
Payload sizeSmallestLargestMedium
Learning curveMediumLowHigh
ToolingProtoc, grpcurl, reflectionUniversal (curl, Postman)Apollo, GraphiQL
Best forInternal service-to-servicePublic APIs, CRUD, browsersClient-driven apps, aggregation

Where gRPC wins

  • Internal microservices — performance, typed contracts, and code generation across languages. The .proto file is the contract; buf breaking enforces compatibility.
  • Streaming — server-streaming for large result sets, client-streaming for uploads, bidirectional for real-time protocols. REST requires separate SSE/WebSocket infrastructure; GraphQL subscriptions are less flexible.
  • Low-latency services — a 3–5× serialization speedup matters when a service handles 100,000 RPCs per second.
  • Polyglot environments — Go, Java, Python, C++, Rust — codegen generates consistent clients in every language.
  • Mobile clients — native gRPC on Android and iOS; smaller payloads, less battery consumption.

Where REST wins

  • Public APIs — Stripe, GitHub, Twilio. Universal: every developer, every tool, every client.
  • HTTP caching — a CDN caches GET requests natively. No extra configuration.
  • Browser clients — no proxy needed; fetch/XHR works.
  • Simple CRUD — a handful of resources, one client, straightforward shapes. gRPC's complexity is not justified.
  • File uploads and downloads — multipart forms and binary streaming work naturally.
  • Service-to-service for simpler cases — REST over HTTP with JSON is fine for moderate-volume internal APIs; gRPC's benefits are smaller when the volume is not extreme.

Where GraphQL wins

  • Multiple heterogeneous clients — mobile, web, partner apps each need different shapes; GraphQL lets each query its shape from one schema.
  • Rapid frontend iteration — the frontend adds a field to the query without a backend change, decoupling release cadences.
  • Complex data models — deeply nested data is one query in GraphQL, several in REST.
  • Aggregation over services — one GraphQL gateway over many microservices.
  • Real-time UI — subscriptions integrated into the same schema.

The standard architecture

LayerProtocolWhy
External public APIRESTUniversal, cacheable, simple
Web/mobile client → BFFGraphQLFlexibility, one round trip
BFF → servicesgRPCPerformance, typed, streaming
Service → servicegRPCPerformance, typed contracts
Service → service (async)Message queueDecoupling, buffering (Volume 11)
Mobile native clientsgRPCPayload size, battery

The pattern: REST for public and browser; gRPC for internal; GraphQL for the client's aggregation. Each is used where its strengths dominate.

The migration considerations

From → ToWhen it makes sense
REST → gRPC (internal) The internal API is high-volume, has streaming needs, or spans many languages
REST → GraphQL The frontend iterates faster than the backend, or the client set is heterogeneous and growing
gRPC → REST (public surface) When the API needs to be consumable by browsers and third parties without a proxy
GraphQL → REST (public surface) When the query language is a barrier for partners, or when caching is the dominant requirement

The honest assessment

Each protocol is a tool with a real cost. gRPC requires Protobuf discipline, buf breaking, load-balancing configuration, and a proxy for browsers. REST requires careful API design, versioning, and documentation. GraphQL requires schema design, DataLoader, complexity limits, and a client cache.

The mistake is choosing based on trend. The right choice is: which protocol makes the application's data flow simplest, given the client's needs and the team's expertise? A team that knows REST well and has a simple product should build REST. A team that needs streaming and has polyglot services should build gRPC. A team with heterogeneous clients iterating fast should build GraphQL.

Most mature systems converge on a mix — REST at the edge, gRPC inside, GraphQL where the client's needs demand it. The boundary is the client: if the client is a browser and the data is simple, REST; if the client is a product surface with varied needs, GraphQL; if the client is a service, gRPC.

Trade-off

gRPC trades ecosystem for performance and typing. REST trades performance for universality. GraphQL trades server complexity for client flexibility. The right answer is driven by the audience — internal services, public developers, or the product frontend — not by which is "best".

Interview Framing

Say: "gRPC for internal service-to-service — performance, streaming, typed. REST for public APIs — universal, cacheable, simple. GraphQL for client-driven product surfaces — flexible queries. Most systems use all three at different layers." That demonstrates judgment and the standard architecture in one sentence.
