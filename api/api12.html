Part A — Schema & Execution Designing the graph, and the N+1 trap that follows

1

How do you design a GraphQL schema that survives a real product?

Short Answer

A GraphQL schema is the API contract — it defines every type, field, and operation the client can perform. Good schema design is client-oriented but not client-driven: design for the queries the clients actually make, but keep the schema coherent and evolvable rather than accreting fields per request. The three principles: types represent domain concepts, mutations represent actions, and every field has clear semantics and a clear owner.

The three roots

RootPurposeRules
Query Read operations — the entry points for fetching data No side effects; every field should be safe to call from any client, any time
Mutation Write operations — the entry points for changing data Serial execution (top-level mutations in a single request run in order); return the changed resource so the client can update its cache
Subscription Real-time operations — server-push of events Long-lived; the client subscribes to specific events and receives updates

Types represent concepts, not tables

The most common schema mistake: mirroring the database schema in GraphQL. The database has users and user_profiles and user_settings; the GraphQL schema should have User with fields that span all three tables. The client does not know about the split; the resolvers stitch them together.

DatabaseGraphQL
users tableUser type
user_profiles tableUser.profile field (returns a Profile type)
user_settings tableUser.settings field (returns a Settings type)
orders table with user_idUser.orders field (returns a list of Order)

The schema represents what clients need to know; the database is an implementation detail. This is why GraphQL can be a stable interface over a changing persistence layer — the resolvers do the mapping.

Nullability — the hardest decision

Every field in GraphQL is nullable by default; you add ! to make it non-null. This choice has real consequences:

FieldClient effect
name: String (nullable)The client must handle null — null checks everywhere
name: String! (non-null)The client can rely on the value; but if the resolver fails, the error propagates up to the nearest nullable parent

The non-null field is a promise, and breaking it — a resolver that returns null for a non-null field — causes the error to bubble up. If User.name is String! and the resolver returns null, the entire User becomes null, and if the query fetches a list of users, the entire list fails. This is the "null propagation" behavior that frustrates teams new to GraphQL.

The pragmatic rule: mark as non-null only what is truly guaranteed — an ID, a required field that the domain enforces. For everything else, nullable is safer, and the client's types reflect the actual reality.

Mutations — actions with payloads

A mutation that returns only true or void is useless to a GraphQL client — the client's cache cannot update without the resulting data. Every mutation should return the resource it affected:

Bad mutationBetter mutation
updateUser(id: ID!, name: String!): Boolean!updateUser(input: UpdateUserInput!): UpdateUserPayload!
Returns true or falseReturns the updated user, plus any errors

The payload pattern: a mutation returns a wrapper type with the changed data and per-field errors. This lets the client update its cache in one round trip and handle partial failures.

Input types and the schema contract

Mutations take an input type rather than many arguments. This is more evolvable — adding a new field to the input type is non-breaking; adding an argument to a mutation requires changing every caller.

Anti-patternBetter
createOrder(userId: ID!, items: [ItemInput!]!, promo: String, notes: String)createOrder(input: CreateOrderInput!): CreateOrderPayload!

The interface and union types

GraphQL supports interfaces and unions, which allow polymorphic types:

ConstructWhen to use
InterfaceMultiple types share common fields — Node interface with id, User and Post both implement it
UnionOne field returns different types with no common fields — search(query): [User | Post | Comment]

Use them sparingly — every polymorphic type complicates the client's query and the schema evolution. But for genuinely polymorphic domains (search results, feed items, notifications), they are the right abstraction.

Schema evolution

GraphQL has no version in the URL. Evolution is additive:

  • Add new fields and types — non-breaking.
  • Deprecate old fields with @deprecated — the field still works; clients are warned to migrate.
  • Remove fields only after a deprecation window and confirming no client queries them (requires field usage tracking, Volume 3 Question 8).
  • Change a field's type or arguments — breaking; add a new field instead.
Interview Framing

Say: "Types represent domain concepts, not tables. Mutations return a payload with the changed resource. Nullability is a deliberate choice, not a default. Evolution is additive with @deprecated, not versioned URLs." That covers the schema discipline in one sentence.

What is the N+1 problem, and how does DataLoader solve it?

Short Answer

The N+1 problem: a query fetches N items (one query), then for each item, the client's fields trigger a separate lookup (N queries) — N+1 total. In GraphQL, this happens naturally because every field is resolved independently. DataLoader solves it by batching the N lookups into one query per field, using a per-request cache and a batching window.

The problem in concrete form

Query
 
query {
  posts(first: 100) {
    id
    title
    author {
      name
    }
  }
}

Without batching:

  1. 1 query for the 100 posts.
  2. For each post, a query to fetch its author — 100 queries.
  3. Total: 101 queries.

At 5 ms per query, that is ~505 ms of database time for a single GraphQL request. At scale, this destroys the database — the query count is proportional to the list size, and the list size is controlled by the client.

Why it happens in GraphQL

The resolver architecture makes N+1 natural. Each field has its own resolver, and each resolver runs independently — the author resolver on Post fires once per post, with no awareness that 100 siblings are also requesting authors. In REST, the endpoint is designed as one query that returns the full shape; in GraphQL, the shape is composed at query time, so the resolver cannot assume it is the only consumer.

DataLoader — the batching layer

DataLoader is a small utility that batches individual key lookups into a single query, per tick of the event loop. The pattern:

StepWhat happens
1The resolver calls authorLoader.load(post.authorId) — it does not query yet; it registers the key
2All 100 resolver calls happen in the same event-loop tick
3At the end of the tick, DataLoader has 100 unique author IDs
4It calls the batch function once: batchLoadAuthors([...100 ids])
5The batch function runs a single database query: SELECT * FROM authors WHERE id IN (...)
6The 100 resolvers each receive their author

Total queries: 2 (posts + authors). The pattern is general — any field that does a per-item lookup can be batched this way.

The per-request cache

DataLoader also caches within a single request. If the same author is requested twice (because two posts share an author, or a fragment queries it twice), the second request is served from the cache — no additional batch call. This matters because a single GraphQL query often needs the same entity from multiple paths.

The cache is per-request, not global — the loader is created fresh for each GraphQL request, so a stale cache does not leak between clients. A global cache would require invalidation; a per-request cache is simpler and correct by construction.

Batching depth — the deeper problem

A single DataLoader solves one level. A query that fetches posts → author → company → address has four levels of N+1:

LevelWithout DataLoaderWith DataLoader per level
Posts11
AuthorsN1 (batch)
CompaniesN × M1 (batch)
AddressesN × M × K1 (batch)
Total1 + N + NM + NMK4

Every field that does per-item lookup needs its own DataLoader. This is the discipline that separates a working GraphQL server from one that melts the database.

Where else N+1 happens

  • Database queries — the classic case; covered above.
  • HTTP calls — fetching user data from an external service, once per item.
  • Cache lookups — 100 cache gets for 100 items; a multi-get could do it in one call.
  • File reads — fetching metadata from a file system, once per file.

DataLoader works for all of them, because the batch function is user-supplied — it can call the database, an HTTP API, or a cache.

The alternatives

ApproachProsCons
DataLoader Per-field batching; works with any backend Requires discipline — one loader per field
Join in the resolver Single query, no N+1 Requires the parent to know its children's needs — breaks the resolver model
Look-ahead / selection set The resolver inspects the query to decide what to fetch Couples the resolver to the query AST; complex
GraphQL-to-SQL (Hasura, PostGraphile) Generates SQL from the query; no N+1 by design Limited to SQL-backed domains; less flexible

DataLoader is the standard for application-built GraphQL servers. GraphQL-to-SQL tools solve it differently, by construction, at the cost of flexibility.

Common Pitfall

Creating a new DataLoader instance per resolver call instead of per request. If each resolver creates its own loader, there is no batching — each loader sees one key and issues one query. The loader must be created once per request and passed through the context to all resolvers.

Interview Framing

Say: "N+1 is fundamental to GraphQL — every field is resolved independently. DataLoader batches the lookups per field, per request. Every field that does a per-item lookup needs its own DataLoader, created per request." That covers the problem and its solution.

How do you protect a GraphQL endpoint from expensive or malicious queries?

Short Answer

GraphQL's flexibility is its vulnerability — a client can craft a query that traverses the schema deeply, requests enormous lists, or hits the most expensive resolvers, all in one request. The defenses: depth limits, complexity limits (a cost score per query), pagination limits (maximum page size), timeouts, and persisted queries (only pre-approved queries are executed). The combination makes the worst case predictable.

The attack vectors

AttackHow it worksDefense
Deep nesting A query that traverses the graph 20 levels deep — each level triggers a resolver Depth limit (10 is typical)
Wide fan-out A query that requests 1000 items, each with 10 fields, each triggering a resolver Pagination limit + complexity score
Expensive fields A field that runs a slow query, called 1000 times in one request Complexity score that weights the field heavily
Alias abuse The same field with 1000 different aliases — the resolver runs 1000 times Complexity score counts aliases; or limit the number of fields
Fragments and cycles A recursive fragment that expands exponentially Disable fragment cycles; or depth limit
Introspection Query the entire schema in production Disable introspection in production (or restrict to authenticated users)

Depth limiting

A depth limit rejects queries whose nested-field depth exceeds a threshold. Ten levels is a common default — the typical legitimate query is 3–5 levels deep. The implementation walks the query AST and counts the depth:

DepthExample
1{ user { name } }
2{ user { posts { title } } }
3{ user { posts { author { name } } } }
10Likely legitimate — a complex query
20+Likely attack or a badly-designed client

Depth limiting is cheap and catches the obvious attacks. It does not catch wide fan-out — a shallow query that requests 1000 items is still expensive.

Complexity scoring

A complexity score assigns a cost to each field and rejects queries whose total cost exceeds a budget. The score approximates the actual work:

Field typeCost
Scalar field (name, id)1
Object field (one lookup)5
List field (lookup + multiply by page size)10 × first
Expensive field (search, aggregation)50 or custom
Mutation (write)20

A query's cost is the sum of its fields' costs, multiplied at each level. A budget of 1000 means a query requesting 100 posts with their authors costs 100 × 10 × 5 = 5000 — rejected. The client must reduce the page size or narrow the query.

Pagination limits

Every list field must enforce a maximum page size:

FieldLimit
posts(first: Int!)Maximum first: 100; reject > 100
search(query: String!, limit: Int)Maximum limit: 50
orders(first: Int!)Maximum first: 200

The limit is enforced by the resolver, not just documented. A client that requests first: 10000 gets an error, not 10,000 rows.

Alias abuse prevention

GraphQL allows aliases — a: user(id: 1) { name } b: user(id: 2) { name } — which are legitimate but can be abused:

AliasMeaning
u1: user(id: 1) { name }A legitimate batch — fetch 3 users in one query
u1: user(id: 1) ... u1000: user(id: 1000)Abuse — 1000 lookups in one query

The complexity score must include aliases — the query above has 1000 fields and a cost of 1000 × 5 = 5000, which exceeds the budget. Alternatively, limit the number of top-level fields.

Timeout and resource limits

  • Per-query timeout — the entire GraphQL request must complete within, say, 10 seconds. A query that exceeds this is killed (the resolvers see a cancelled context).
  • Per-resolver timeout — each resolver has its own timeout; a slow resolver does not block the whole query indefinitely.
  • Memory limits — the container's memory limit, plus a hard cap on the response size.
  • Concurrency limits — per-client, limit concurrent requests.

Persisted queries — the strongest defense

Instead of accepting arbitrary queries, the server accepts only pre-approved queries identified by a hash:

Without persisted queriesWith persisted queries
Client sends the full query in the request bodyClient sends a hash: {"sha256Hash": "abc123..."}
Server parses and executes whatever is sentServer looks up the hash; if it knows the query, executes it; if not, rejects
Attack surface: any query the schema allowsAttack surface: only the queries in the approved list

The approved queries are the ones the client actually uses — registered at build time, or learned during a warm-up phase. Attackers cannot send arbitrary queries because the server rejects unknown hashes. This eliminates complexity attacks entirely — the approved queries are known to be safe.

The trade-off: the client cannot execute ad-hoc queries (which is fine for production apps, annoying for debugging). The workaround is a development mode where arbitrary queries are allowed, and production mode where they are not.

Introspection in production

Introspection lets a client query the schema itself — useful for development, dangerous in production (an attacker learns every field, every mutation, every type). The default: disable introspection in production, or restrict it to authenticated users.

Most GraphQL servers support this out of the box. It is a one-line config; forgetting it is a common security oversight.

The layered defense

LayerCatches
Depth limitDeeply nested queries
Complexity scoreWide fan-out, expensive fields, alias abuse
Pagination limitsOversized lists
TimeoutsAny query that exceeds the budget
Persisted queriesAny query not on the approved list
Rate limitingRepeated expensive queries (Volume 7)
Introspection offSchema enumeration

Each layer catches what the previous misses. Persisted queries are the strongest single defense — they make arbitrary queries impossible — but require the client to be built with the approved query set.

Common Pitfall

Implementing a depth limit without a complexity limit. A query like { posts(first: 10000) { title } } is only 2 levels deep — the depth limit allows it — but requests 10,000 rows in one query. Depth limits catch nesting, not fan-out; both are needed.

Interview Framing

Say: "Depth limit for nesting, complexity score for fan-out and expensive fields, page-size limits for lists, timeouts for anything that slips through, and persisted queries as the strongest defense. Disable introspection in production." That covers the layered defense in one sentence.

How do you cache GraphQL responses?

Short Answer

HTTP caching does not work for GraphQL — every request is POST /graphql with a body, so the URL does not identify the response. The four approaches: client-side normalized cache (Apollo Client, Relay) — the dominant pattern; server-side per-field cache — cache individual resolver results; persisted queries + GET — turn the query into a GET with a cacheable URL; CDN caching of persisted queries — the edge caches the whole response for a known query + variables.

Why HTTP caching fails

HTTP caching is based on the URL: the same URL returns the same response (within its freshness). GraphQL uses one URL (/graphql) and varies the meaning by the request body — the query string. The cache cannot distinguish "query for user 1" from "query for user 2" because the URL is identical.

The consequences:

  • A CDN cannot cache GraphQL responses by default — the URL is not the cache key.
  • Browsers cannot cache — the same URL means different queries.
  • Conditional requests (ETag, If-None-Match) do not help — the client is not asking about a resource; it is composing a query.

Client-side normalized cache

Apollo Client and Relay maintain a normalized cache on the client — a local store keyed by entity (User:1, Post:42) that the client populates from query results and reads from for subsequent queries. When a query asks for user 1, and the client already has user 1, no request is sent — the data comes from the cache.

FeatureBehaviour
NormalizationEach entity is stored once, keyed by __typename + id
Query resolutionThe client checks if it has all the fields; if yes, no request
Mutation updatesMutations return the changed entity; the cache updates automatically
Partial cacheA query needing fields the cache has plus fields it does not sends a request only for the missing

The client cache is the primary GraphQL caching mechanism — it eliminates many network requests and makes the UI feel instant. It requires:

  • Stable IDs — every entity must have an id (or a __typename + key combination) so the cache can normalize.
  • Mutations that return the changed entity — so the cache can update.
  • Consistent field naming — so a field queried in one place matches the field queried in another.

Server-side per-field caching

Cache individual resolver results rather than whole responses. The pattern:

FieldCache strategy
User.profileRedis cache keyed by user ID, TTL 5 min
Post.likeCountRedis counter, TTL 30 sec
Product.priceRedis cache keyed by product ID, invalidated on write
Search.resultsRedis cache keyed by query hash, TTL 1 min

This caches at the resolver level, not the response level — the query is still executed, but the expensive resolvers are served from cache. It does not eliminate the network round trip to the GraphQL server, but it does eliminate the expensive downstream calls (database queries, API calls).

DataLoader's per-request cache is a form of this — it caches for the duration of one request. To cache across requests, the resolver needs a longer-lived cache (Redis, Memcached).

Persisted queries + GET

If every query the client uses is registered (persisted, Question 3), it can be addressed by hash in a GET request:

Without persistedWith persisted
 
POST /graphql
{"query": "query { user(id: 1) { name } }"}
 
GET /graphql?hash=abc123&variables={"id":1}
Not cacheable (POST + body)Cacheable (GET + URL with hash and variables)

The GET URL is unique per query + variables combination. A CDN can cache it, keyed by the full URL. For a query that many users request with the same variables (a public page, a shared resource), the CDN serves the cached response — the GraphQL server is not even hit.

The limitation: the cache key includes the variables. A query with user-specific variables (user: 42) is unique per user; the CDN does not help. But a query for public data (the trending feed, the product catalogue) is cached for everyone.

CDN caching of persisted queries

The full pattern:

  1. Queries are persisted at build time; the client knows only the hashes.
  2. The client sends GET /graphql?hash=abc&variables={...}.
  3. The CDN receives the request; the URL is the cache key.
  4. If cached and fresh, the CDN serves it — the GraphQL server is not hit.
  5. If not cached, the CDN forwards to the GraphQL server, which executes the query and returns the response; the CDN caches it with a TTL.

This gives GraphQL the CDN caching that REST has natively. It requires the query to be:

  • Public — the same response for any user with the same variables.
  • Idempotent — GET, not POST; no mutations.
  • Cacheable — the response's freshness is acceptable.

What about mutations and private data?

Mutations are POST and cannot be cached. Private data (per-user) has a cache key per user, which fragments the CDN cache; usually, private data is not cached at the CDN, only in the client cache and the resolver cache.

The layered design:

LayerCaches
Client normalized cacheEntities across queries; eliminates many network requests
CDN (persisted queries)Whole responses for public, cacheable queries
Resolver cache (Redis)Expensive field results; shared across requests
DataLoader (per request)Duplicate lookups within one request

Each layer catches what the one above misses. The client cache is the biggest win — most queries are served without a network call; the CDN is the second; the resolver cache is the third; DataLoader is the last.

Common Pitfall

Assuming GraphQL cannot be cached. It cannot be cached by URL (the default HTTP mechanism), but it can be cached at every layer above HTTP — the client, the CDN (with persisted queries), and the resolver. The choice is architectural, not a limitation of GraphQL.

Interview Framing

Say: "The client normalized cache is the primary — it eliminates most network requests. For public data, persisted queries + GET make the CDN cacheable. For expensive resolvers, Redis at the resolver level. DataLoader handles within-request duplication." That covers the four layers.

What are persisted queries, and how do they enable CDN caching?

Short Answer

A persisted query replaces the full query string with a hash. The client sends {"sha256": "abc123...", "variables": {...}}; the server looks up the hash in a registered list and executes the corresponding query. The benefits: smaller request bodies, no arbitrary queries (security, Question 3), and — critically — the query can be a GET with the hash in the URL, making it cacheable by a CDN.

The problem it solves

GraphQL requests are POSTs with the query in the body. The URL is always /graphql. This breaks HTTP caching: a CDN cannot distinguish one query from another because the URL is the same.

Persisted queries flip the model: the query is a named resource with a hash, and the hash goes in the URL. Now the CDN can cache by URL.

How it works

StepAction
1. RegisterAt build time, the client extracts all queries and mutations, hashes them, and uploads the map to the server
2. StoreThe server stores the hash → query map in a persistent store
3. Client requestThe client sends GET /graphql?sha=abc123&variables={...}
4. Server lookupThe server looks up the hash; if found, executes the query; if not, rejects
5. CDN cacheFor public, cacheable queries, the CDN caches the response by the full URL (hash + variables)

The request format

Before persistence
 
POST /graphql HTTP/1.1
Content-Type: application/json

{
  "query": "query GetProduct($id: ID!) { product(id: $id) { name price } }",
  "variables": {"id": "42"}
}
After persistence
 
GET /graphql?sha=abc123&variables=%7B%22id%22%3A%2242%22%7D HTTP/1.1

# Or with a header:
GET /graphql HTTP/1.1
X-APQ-Sha: abc123
X-APQ-Variables: eyJpZCI6IjQyIn0=

The GET form puts the hash and variables in the URL. The URL is unique per query + variables, so the CDN can cache it exactly like a REST URL.

The variants

VariantMechanism
APQ (Automatic Persisted Queries) Apollo's pattern: the client sends the hash first; if the server does not know it, the client sends the full query and the server stores it. Zero build-time setup, but the first request is not cached.
Trusted documents The query set is uploaded to the server at build time; only those queries are accepted. Strictest; best for security.
Signed persisted queries The hash is signed with a key; the server verifies the signature. Prevents tampering with the query map.

The choice depends on the goal: APQ for convenience (automatic, minimal setup), trusted documents for security (only known queries), signed for high-security environments (verify the source of the query).

The CDN cache key

The cache key must include:

ComponentWhy
The query hashDifferent queries return different data
The variablesproduct(id: 42) and product(id: 43) are different responses
Auth context (if any)Different users may see different data — but if the query is public, no auth is needed
Accept-Language (if the response varies)Localisation

The full URL (/graphql?sha=abc&variables={...}) is the natural cache key — every component is in the URL. The CDN hashes it as usual.

When the CDN caches

Persisted queries enable caching, but the server decides whether to cache:

QueryCacheable?
Public product catalogueYes — same for all users
User's own ordersNo — per-user, would need per-user cache key
Trending posts (updated every minute)Yes with short TTL (e.g., 60 sec)
Real-time stock quotesNo — too volatile
Search results (query varies)Cacheable per query + variables; high cardinality

The server sets Cache-Control on the response; the CDN respects it. A query that returns per-user data sets private, no-store — the CDN does not cache it. A query that returns public data sets public, max-age=60 — the CDN caches it for 60 seconds.

The client-side persistence

For the client to use persisted queries, its build process must:

  1. Extract every query string in the codebase.
  2. Hash each (SHA-256).
  3. Generate a map from hash → query.
  4. Upload the map to the server (trusted documents), or ship the hash to the client for APQ.
  5. Replace the query in the client code with the hash.

Apollo, Relay, GraphQL Codegen, and other tools support this out of the box. The setup is not trivial (build pipeline changes), but the payoff — security, smaller requests, CDN caching — is substantial.

What does not cache

Persisted queries enable caching, but not everything is cacheable:

  • Mutations — POST, state-changing, never cached.
  • Per-user queries — cache key would include the user, fragmenting the cache to a per-user partition, with no benefit over not caching.
  • Queries with sensitive data — the response contains PII; caching it at the CDN is a data leak risk.
  • Queries with no stable variables — a query that includes a timestamp or random ID in the variables is a cache miss every time.

The comprehensive pattern

The production GraphQL CDN setup:

  1. Extract and hash all queries at build time (trusted documents).
  2. The client sends GET requests with the hash + variables in the URL.
  3. The CDN's cache key is the full URL.
  4. The server sets Cache-Control per query — public for shared, private for per-user.
  5. The CDN caches the public ones; the private ones bypass the cache.
  6. For uncached or private requests, the GraphQL server executes normally.

This gives GraphQL the CDN benefit of REST, without losing the flexibility of GraphQL for interactive clients.

Common Pitfall

Using persisted queries but not setting Cache-Control headers. The CDN sees a GET with a unique URL but has no instruction to cache it — it may apply a heuristic or not cache at all. The server must explicitly set Cache-Control: public, max-age=60, s-maxage=300 (or similar) for the CDN to cache.

Interview Framing

Say: "Persisted queries turn a POST with a body into a GET with a hash — the URL becomes unique per query + variables, so the CDN can cache it. The server sets Cache-Control per query, and private data uses no-store." That covers the mechanism and the caching policy.

How do you do per-field authorization in GraphQL?

Short Answer

GraphQL authorization happens at two levels: operation-level (can this user run this query or mutation?) and field-level (can this user see this field on this object?). Field-level is where GraphQL is subtle — a single query can traverse many objects, and each field may have different requirements. The mechanisms: resolver-level checks, middleware/directives, and field-level policies.

Why field-level authorization is hard in GraphQL

In REST, an endpoint is one resource; if you can call it, you can see what it returns. In GraphQL, a query can request any field on any reachable object. The User type has email (visible to the user), salary (visible to HR), phone (visible to the user and their team). The same query fetches all three; the server must decide per-field, per-user, per-object.

FieldWho can see it
User.nameAnyone
User.emailThe user, their org admins
User.phoneThe user, their team
User.salaryHR only
User.socialSecurityNumberThe user only

A single query for a team's users can traverse all of these. The server must filter the fields per requesting user and per target user — a matrix of permissions.

Level 1 — Operation-level authorization

Before any resolver runs, check: is this user allowed to run this operation? This is the analogue of REST's "is this endpoint authorized". The check:

  • Parse the operation. Is it a query, mutation, or subscription?
  • Look at the root fields. A listAllUsers mutation is admin-only; a me query is any authenticated user.
  • Check role/scope. Does the user have the required role or scope?
  • Reject 403. If not allowed, return an error before any resolver.

Level 2 — Field-level authorization

Inside the resolver, after fetching the data, check whether the user may see each field. Three patterns:

PatternHow it worksProsCons
Resolver-level check Each field's resolver checks the user's permission before returning the value Explicit; clear at the field level Duplicated across resolvers; easy to forget one
Directive @auth(requires: HR) on the field; the directive enforces it before the resolver runs Declarative; visible in the schema Requires a directive implementation
Middleware A wrapper around every resolver checks permissions based on a policy map Centralised policy; hard to bypass Policy map must stay in sync with the schema

The directive pattern

A custom directive on the schema declares the permission requirement:

Schema
 
type User {
  id: ID!
  name: String!
  email: String! @auth(requires: SELF_OR_ADMIN)
  salary: Int @auth(requires: HR)
  ssn: String @auth(requires: SELF)
}

The directive implementation intercepts the resolver, checks the user's permissions against the requirement and the current object, and either returns the value or null (or an error). The advantage is that the policy is visible in the schema — a reviewer can see which fields are restricted.

The policy middleware

A wrapper around all resolvers, checking a centralised policy map:

Map
 
{
  "User.email": "self_or_admin",
  "User.salary": "hr",
  "User.ssn": "self",
  "Order.paymentMethod": "owner",
  "Order.refundStatus": "admin"
}

The middleware uses the resolver's path (e.g., User.email) to look up the policy and enforce it. The advantage is that all policies are in one place — easy to audit, easy to review, easy to change without touching every resolver.

Object-level authorization (BOLA)

Field-level is one dimension; object-level is the other. Even if a user can see User.salary in general, they cannot see it for another user's salary. The check is per-object:

  • If the requesting user is the target user — allow (self-access).
  • If the requesting user is the target user's manager — allow (for some fields).
  • If the requesting user is an admin — allow (for some fields, with audit).
  • Otherwise — return null (not the field, not the object, not an error).

The return-null choice: for a restricted field, returning null (with the field present in the schema) tells the client "you cannot see this" without leaking whether the data exists. Returning an error tells the client "this exists but you cannot see it", which is information disclosure (the pattern of 404 vs 403 from Volume 6). For GraphQL, null is usually the right answer for field-level restrictions — the object is still returned, the field is just missing.

The N+1 of authorization

Authorization can be expensive — checking the user's role for each object may require a database lookup. The pattern mirrors DataLoader:

  • Cache the user's roles/permissions — load once per request, not per field.
  • Batch the object-level checks — if the query fetches 100 users and each needs an ownership check, batch the checks into one query.
  • DataLoader for permissions — same batching discipline as for data.

The "silent filter" pattern

For list fields (e.g., User.salary for a list of users), field-level authorization is not enough — some items are visible to this user, some are not. The pattern:

  • Filter the list at the resolver — the resolver fetches only the items the user can see, not all items then filters in memory.
  • The filter is in the query — WHERE owner_id = current_user, not WHERE 1=1 then filter in code (which is the BOLA bug from Volume 6).
  • For nested fields, the field-level check applies per item — the item is present, the field is null for items the user cannot see.

The testing discipline

Authorization bugs in GraphQL are subtle — they only appear when the attacker queries the restricted field. The defense: a test suite that, for every restricted field, verifies that:

  • The field is visible to the allowed user.
  • The field is null (or absent) for the disallowed user.
  • The field is null (or absent) for the disallowed object.
  • Attempting to query the field for a disallowed object does not leak its existence.

Without this test suite, the schema is a maze of fields, and one missing check is a data leak.

Common Pitfall

Checking authorization at the resolver's top level but not for nested fields. A query that fetches user { posts { author { salary } } } — the top-level user is authorized, but author.salary is a different user, and it must be checked independently. The nested check is where BOLA happens.

Interview Framing

Say: "Two levels — operation-level (can you run this query?) and field-level (can you see this field on this object?). Field-level uses a directive or middleware that declares the requirement in the schema. Lists are filtered at the resolver, not in memory. Every restricted field gets a test." That covers the layers and the discipline.

How do you handle errors in GraphQL?

Short Answer

GraphQL has two error categories: transport errors (invalid JSON, server crash, auth failure — HTTP status like 400 or 401) and GraphQL errors (errors in execution — the query is valid, but a resolver failed or a validation rule was violated; the HTTP status is often still 200, with errors in the errors array). The data and errors fields can both be present — partial success is normal.

The response shape

A GraphQL response always has the same structure:

FieldContent
dataThe requested data; null if the operation failed entirely
errorsAn array of errors; absent if no errors occurred
extensionsOptional metadata — tracing, cost, cache hints

The three cases

CasedataerrorsHTTP status
Full success Populated Absent 200
Partial success Populated with null for the failing fields Present, with paths to the failing fields 200 (typically)
Complete failure null Present 200 or 4xx/5xx, depending on the failure class

This is fundamentally different from REST, where a response is either a success (2xx) or an error (4xx/5xx). In GraphQL, a single response can contain both successes and failures for different fields.

Transport errors vs GraphQL errors

The distinction matters because the client's handling differs:

TypeHTTP statusClient action
Transport errors 4xx or 5xx Retry, refresh auth, show error — standard HTTP handling
GraphQL errors — validation 200 with errors The query is malformed; the client has a bug
GraphQL errors — resolver 200 with errors The resolver failed; the client handles per-path

The HTTP status is often 200 even when errors exist — because the request itself succeeded (the server received and parsed it), and the errors are at the data level. Some GraphQL servers return 400 for validation errors and 500 for any resolver error; others return 200 for all GraphQL errors. The choice is a design decision, documented for the client.

The error object

FieldContent
messageHuman-readable — for logs and debugging
locationsWhere in the query the error occurred (line, column)
pathThe path to the failing field (["user", "posts", 0, "title"])
extensionsCustom metadata — error code, category, retryable flag, documentation URL

The path is critical — it tells the client which field failed, so the client can render partial UI (show the successful fields, mark the failed ones). Without the path, the client does not know which part of the response is missing.

The extensions field — the machine-readable part

The extensions.code is the machine-readable error code (Volume 8, Question 6 applied to GraphQL):

Extensions
 
{
  "message": "User not found",
  "path": ["user"],
  "extensions": {
    "code": "USER_NOT_FOUND",
    "retryable": false,
    "documentation": "https://api.example.com/errors/user-not-found"
  }
}

The client switches on extensions.code — the same pattern as REST's error code. The message is for humans; the code is for machines.

Partial success — the "errors do not null the response" rule

A common confusion: when a field's resolver fails, the entire response does not become null. Instead:

  • If the field is nullable, that field becomes null in the data; the error is recorded.
  • If the field is non-null, the error bubbles up to the nearest nullable parent; that parent becomes null.
  • If the whole query is non-null at the root (rare), the entire response is null.

This is why nullability is so consequential (Question 1): a non-null field whose resolver fails takes down its parent, and if that parent is a list element, the whole element becomes null. A single bad resolver can make half the response null.

The discipline: use nullable fields for anything that can fail, so a failure is contained to one field. Reserve non-null for guaranteed fields (an ID, a required domain value).

Where errors should come from

SourceError type
Syntax errors (invalid query)Validation error, 400
Unknown fieldsValidation error, 400
Type mismatchesValidation error, 400
Authentication missing/invalidUNAUTHENTICATED, 401
Authorization deniedFORBIDDEN, 403
Resource not foundNOT_FOUND, 200 with null + error
Validation of input (business rules)BAD_USER_INPUT, 200 with error
Resolver throwsINTERNAL_SERVER_ERROR, 200 with error
TimeoutTIMEOUT, 200 or 504

Mutation errors — the payload pattern

For mutations, the errors array is coarse — it does not tell the client which input field was invalid. The payload pattern wraps the result:

Mutation response
 
mutation {
  createUser(input: {email: "bad"}) {
    user { id }
    errors {
      field
      code
      message
    }
  }
}

The response has the created user (null if failed) and a per-field errors array. This is GraphQL's equivalent of the validation error response from Volume 8, Question 7 — the client can map each error to the corresponding form field.

Common Pitfall

Returning data: null for any error. In GraphQL, a failure in one field should make only that field null (if nullable) — the successful fields are still in data. Returning null for the whole response throws away the successful work and forces the client to re-request.

Interview Framing

Say: "GraphQL errors are in the errors array with a path to the failing field and a machine-readable code in extensions. Partial success is normal — the successful fields are in data, the failing ones are null with a recorded error. Mutations use a payload pattern with per-field errors." That covers the model and the mutations.

How do GraphQL subscriptions work, and when do you use them?

Short Answer

A subscription is a long-lived operation — the client subscribes to an event (subscription { orderUpdated(id: 42) { status } }), and the server pushes updates as the event occurs. The transport is WebSocket (or SSE). The implementation: the client subscribes with the server, the server registers the subscription, and the resolver publishes messages from a pub/sub system (Redis, Kafka) when the event fires.

The subscription model

PhaseWhat happens
SubscribeClient sends subscription { orderUpdated(id: 42) { status } }
RegisterThe server records the subscription and the client's connection
Event firesThe business logic publishes order.42.updated to the pub/sub system
ResolveThe subscription resolver receives the event, resolves the requested fields, and pushes to the client
RepeatEvery event matching the subscription triggers a push
UnsubscribeClient closes the connection or sends an unsubscribe message

The transport

TransportProsCons
WebSocket (graphql-ws protocol) Bidirectional; supports queries, mutations, and subscriptions over one connection Stateful connections; scaling requires sticky routing or a pub/sub layer
SSE Simpler; works over HTTP/2 with automatic reconnection Unidirectional; the client uses HTTP for queries/mutations

WebSocket is the dominant choice for GraphQL subscriptions because it carries the full GraphQL protocol over one connection. SSE is sometimes used for the subscription stream specifically, with queries and mutations over HTTP.

The pub/sub architecture

The subscription resolver is not the source of truth — it is the delivery mechanism. The source is the business logic that publishes events:

ComponentRole
Business logic Publishes an event when something happens (order.updated)
Pub/sub system (Redis, Kafka, NATS) Delivers the event to subscribers — the bridge between business logic and GraphQL servers
Subscription resolver Subscribes to the topic on behalf of the client; transforms events into the GraphQL shape
GraphQL server Holds the client connections; pushes the resolved data

In a multi-server deployment (multiple GraphQL servers behind a load balancer), a client's connection may be on server A, but the event fires on server B. The pub/sub system is what connects them — server B publishes, the pub/sub delivers to all servers (or the relevant ones), and server A pushes to the client. Redis pub/sub is the standard for this; Kafka for high-volume or durable delivery.

Subscription scaling

ChallengeSolution
Many concurrent connections Stateless transport (SSE over HTTP/2), or connection-aware load balancing (sticky sessions)
Server holds connections Horizontal scale; each server handles a subset of connections
Events fan out to many clients Pub/sub system distributes the event; each server pushes to its own connected clients
Server restart drops connections Client auto-reconnect (with subscription replay if the protocol supports it)
Subscription for one entity gets 1M subscribers Fan-out per server; each server pushes to its subset

When to use subscriptions

Use caseGood fit?
Chat messagesYes
Live notificationsYes
Real-time collaborative editingYes (though CRDTs handle conflicts)
Live dashboardsYes, if the update rate is manageable
Stock pricesYes (with throttling)
Long-polling scenariosSubscriptions are better than polling
Once-per-day email confirmationNo — a webhook or email is simpler
Order status pagePolling is fine; subscriptions are overkill
Admin dashboards updated on demandPolling with cache is simpler

The alternative: polling

Subscriptions are complex to build and operate. The alternative — polling the query at an interval — is often sufficient:

  • Polling — the client queries every N seconds; simpler, no stateful connection, works with any client. Worse for high-frequency updates (wasted queries on no change) and for large user bases (the server handles N requests per client per interval).
  • Subscriptions — the server pushes only when there is a change; more efficient for high-frequency, but requires WebSocket infrastructure and a pub/sub system.

The rule: if the update frequency is high or the user base is large, subscriptions are worth the complexity. If the update frequency is low (order status, once-a-minute dashboard), polling is simpler and sufficient.

Authentication in subscriptions

The connection must be authenticated — a WebSocket handshake carries the token, and the server validates it before accepting the subscription. If the token expires during the subscription, the server may close the connection (requiring the client to reconnect with a fresh token) or continue (accepting the token's permissions for the lifetime of the subscription). The first is safer; the second is more convenient.

The "lost updates" problem

If the connection drops, the client misses any events that occurred during the gap. On reconnect, the client must reconcile — fetch the current state, or query for events since the last seen timestamp. Subscriptions do not guarantee delivery; the client must handle the gap with a query on reconnect.

Common Pitfall

Using subscriptions for everything — including low-frequency events that polling handles fine. The subscription infrastructure (WebSocket servers, pub/sub, connection management) is expensive to build and operate. Use it only for the events where it is genuinely better than polling.

Interview Framing

Say: "Subscriptions are WebSocket-based — the client subscribes, the server registers, events are published through Redis pub/sub to all servers, each server pushes to its connected clients. On disconnect, the client reconciles with a query." That covers the model and the failure handling.

How do you design pagination in GraphQL — offsets, cursors, and connections?

Short Answer

GraphQL uses the Relay Connection pattern: a list is wrapped in a connection type with edges (each edge has a node and a cursor) and pageInfo (hasNextPage, hasPreviousPage, startCursor, endCursor). The client pages with after / before cursors — keyset pagination, the same design as REST cursor pagination (Volume 4, Question 1).

Why cursors, not offsets

Offsets are simpler but break under writes — page 2 shifts when items are inserted before it. Cursors are stable because they reference the last item seen, not a position. In GraphQL, cursors are the standard because they fit the pattern of "give me the next N after this point".

The Connection structure

TypeFields
UserConnection edges: [UserEdge!]!, pageInfo: PageInfo!, totalCount: Int
UserEdge node: User!, cursor: String!
PageInfo hasNextPage: Boolean!, hasPreviousPage: Boolean!, startCursor: String, endCursor: String

The connection type wraps the list with the metadata a client needs for pagination. The edges hold the individual items (the node) and their cursors. The pageInfo holds the navigation state.

The query

First page
 
query {
  users(first: 20) {
    edges {
      node { id name }
      cursor
    }
    pageInfo {
      hasNextPage
      endCursor
    }
  }
}
Next page
 
query {
  users(first: 20, after: "eyJpZCI6IjIwIn0=") {
    edges {
      node { id name }
      cursor
    }
    pageInfo {
      hasNextPage
      endCursor
    }
  }
}

The client sends after with the endCursor from the previous page. The server returns the next 20 items after that cursor.

The arguments

ArgumentMeaning
firstFetch the first N items (forward pagination)
afterStart after this cursor
lastFetch the last N items (backward pagination)
beforeEnd before this cursor
filterOptional — filter the items
orderByOptional — sort order

The Relay spec requires either first or last on every connection — never both, never neither. The server can require first: Int! with a max (100) to enforce a page size.

The cursor encoding

The cursor is opaque — usually base64-encoded JSON of the last item's sort key:

CursorDecoded
eyJpZCI6IjIwIn0={"id": "20"}
eyJjcmVhdGVkX2F0IjoiMjAyNi0xMS0xMlQxMDowMDowMFoiLCJpZCI6IjQyIn0={"created_at": "2026-11-12T10:00:00Z", "id": "42"}

The client must not parse the cursor — it is opaque, and its format can change. The client just passes endCursor back as after.

The composite cursor (with a tiebreaker) handles the same problem as REST — multiple items with the same sort key. The cursor contains both the sort key and the unique ID, so the next page starts after the exact position.

The totalCount field

The Relay spec allows a totalCount on the connection, which the client uses for "showing 1–20 of 1,234". But totalCount is expensive — a full count of the filtered list. Some servers omit it or compute it lazily (only when the client requests it). For large lists, the client should use hasNextPage instead.

The "first N" problem

The client must provide first or last — there is no "give me all". This is deliberate: the server cannot return an unbounded list, because it would exhaust memory. The client always pages; the server always limits.

The server should also cap the max — a request for first: 10000 should be rejected. The cap is documented (the schema can express it via validation) and enforced in the resolver.

Connections for non-list fields

The Relay connection pattern applies to any field that returns a list of items with pagination. A user's posts field returns a PostConnection; a product's reviews returns a ReviewConnection. The pattern is uniform — one shape for all paginated lists.

Offset pagination in GraphQL

Some teams use offset pagination in GraphQL (users(offset: 0, limit: 20)) — simpler, but the same problems as REST: inconsistency under writes, slow at deep offsets. The Relay connection exists precisely to make cursor pagination the standard. For a new GraphQL API, use connections.

The overhead

The connection pattern is verbose — 10 lines of query for what REST expresses in one URL. The verbosity is the cost of the flexibility (the client can request specific fields per edge). Tools like fragments reduce the verbosity:

Fragment
 
fragment UserFields on User { id name avatar }
fragment PageInfoFields on PageInfo { hasNextPage endCursor }

query {
  users(first: 20) {
    edges { node { ...UserFields } }
    pageInfo { ...PageInfoFields }
  }
}
Common Pitfall

Exposing the raw cursor to the client as a parsed value. The client should treat it as opaque — storing it, passing it back, never inspecting it. If the client parses it, changing the cursor format becomes a breaking change. Document the opacity; enforce it by encoding the cursor as base64 (which the client cannot "accidentally" understand).

Interview Framing

Say: "The Relay connection pattern — edges, node, cursor, pageInfo. The client pages with after and before cursors; cursors are opaque. The server caps the page size and requires first or last, so no unbounded queries." That covers the design and the constraints.

GraphQL vs REST — when does each actually win?

Short Answer

GraphQL wins when clients need flexible, nested data shapes and iterate faster than the backend — mobile apps, complex UIs, aggregating multiple services, reducing round trips. REST wins when the API is resource-oriented, cacheable at the HTTP layer, simple for public consumption, or has a small client set. Most mature systems use both — GraphQL at the edge for the product surface, REST/gRPC internally for service-to-service.

DimensionGraphQLREST
Shape of responseClient-defined — asks for exactly what it needsServer-defined — fixed per endpoint
Over-fetchingEliminated (client asks only for fields it uses)Common — the server returns all fields
Under-fetchingEliminated (one query fetches nested data)Requires multiple round trips
Number of round tripsOften one (for a screen)Often several
CachingClient normalized cache; server-side caching is complexHTTP caching (CDN, browser) is native
Learning curveSteep — schema, resolvers, DataLoader, complexity limitsShallow — HTTP and JSON, universally known
ToolingRich (Apollo, Relay, GraphiQL)Universal (curl, Postman, OpenAPI)
Real-timeNative subscriptionsRequires WebSocket or SSE separately
VersioningAdditive via @deprecated (Volume 3, Question 8)URL or header versioning (Volume 3, Question 2)
Rate limitingComplexity scoring per queryPer endpoint, simpler
Public APILess common — the query language is a barrier for partnersThe standard — any developer can consume it
AggregationNatural — one graph over many servicesRequires a BFF or gateway
StreamingSubscriptionsSSE, WebSocket, or HTTP streaming
File uploadsAwkward — usually a REST endpoint alongsideNative — multipart form data

Where GraphQL wins

  • Heterogeneous client set — mobile, web, partner apps all need different shapes of the same data. GraphQL lets each ask for its shape without per-client endpoints.
  • Rapid frontend iteration — the frontend team can add a field to the query without a backend change, decoupling release cadences.
  • Complex data models — deeply nested data (user → posts → comments → reactions) is one query in GraphQL, several in REST.
  • Aggregation over services — a single GraphQL gateway over many microservices; the client sees one graph, the services are independent.
  • Reducing round trips on mobile — every extra round trip on mobile is 100+ ms. One query replacing 5 round trips is a 4× speedup.
  • Real-time UI — subscriptions are integrated into the same schema as queries and mutations.

Where REST wins

  • Public APIs — Stripe, GitHub, Twilio are REST. The universal language (HTTP, JSON) has zero learning curve; every developer, every tool, every client supports it.
  • HTTP caching — a CDN caches GET requests by URL natively. GraphQL needs persisted queries + CDN configuration to match (Question 5).
  • Simple CRUD — a handful of resources, one client, straightforward shapes. GraphQL's complexity is not justified.
  • File uploads and downloads — REST handles multipart forms and binary streaming naturally; GraphQL requires a separate mechanism.
  • Operational simplicity — REST has no resolvers, no DataLoader, no complexity scoring, no query parsing. The monitoring, caching, and debugging are all well-understood.
  • Service-to-service — gRPC is better than GraphQL for internal calls (performance, typing, streaming); REST is fine for simpler cases. Neither REST nor GraphQL is the right tool for internal APIs at scale — gRPC usually wins there (Volume 13).

The hybrid reality

Most large systems use both, at different layers:

LayerProtocol
Web/mobile client → BFFGraphQL (flexibility, one round trip)
BFF → servicesgRPC (performance, typing)
External partner → APIREST (universal, cacheable)
Service → servicegRPC (Volume 13) or message queue (Volume 11)
Public data → CDNREST (native HTTP caching)

The pattern: GraphQL where the client's needs vary and the schema is complex; REST where the resource is simple and public; gRPC where the call is internal and performance matters.

The migration question

Migrating from REST to GraphQL is expensive — a new schema, new resolvers, new clients. The triggers:

  • Multi-client complexity — REST's fixed shapes force per-client endpoints (or per-client filtering), and the endpoints multiply.
  • Round trip pain — a screen requires 10 sequential requests, and the latency is killing the UX.
  • Frontend velocity — the frontend team is blocked by backend changes for every new field, and the release cadence is suffering.
  • Aggregation need — the client talks to 5 services, and the routing is complex.

If none of these applies, GraphQL is premature. REST is fine; adding GraphQL because it is fashionable is a common and expensive mistake.

The honest assessment

GraphQL is neither a superset of REST nor a replacement. It is a different tool for a different problem. The problem it solves is "the client's data needs are diverse and evolving faster than the server can expose". If that is your problem, GraphQL is worth the complexity. If it is not, REST is simpler, faster to build, easier to operate, and better for public consumption.

The complexity cost of GraphQL is real: N+1, query complexity attacks, caching, schema design, per-field authorization, resolvers, DataLoader, persisted queries, subscriptions. A team that adopts GraphQL without adopting these disciplines will have a slower, less secure, less reliable API than the REST API it replaced.

Trade-off

GraphQL trades server complexity for client flexibility. REST trades client flexibility for server simplicity. The right answer depends on which side needs the flexibility more — a team with many clients that change rapidly should pay the GraphQL cost; a team with one client and stable needs should not.

Interview Framing

Say: "GraphQL for the product surface where the client's needs vary and iterate fast. REST for public APIs where caching and simplicity matter. gRPC internally for service-to-service. Most systems use all three at different layers." That demonstrates judgment without dogma.
