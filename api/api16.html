Design the API for a to-do list application.

The Answer

A to-do list API has three resources: lists (collections of tasks), tasks (individual items), and users (owners of lists). The design is a straightforward CRUD API with authentication, per-user authorization, and pagination — the foundational shape that every other API in this volume extends.

Clarify requirements

  • Users create lists and add tasks to them.
  • Tasks have a title, description, status (pending/completed), due date, and priority.
  • Lists can be shared with other users (read or write access).
  • Personal scale — a user has tens of lists and hundreds of tasks; no special scale requirement.
  • Mobile and web clients — the API must work for both; offline sync is out of scope for v1.

The resource model

ResourceRelationshipIdentity
UserOwns lists; is a member of shared listsuser_id
ListBelongs to an owner; has members; contains taskslist_id
TaskBelongs to a listtask_id
MembershipJoin table: user × list × roleComposite (user_id, list_id)

Endpoints

Method & PathPurpose
GET /v1/listsList the user's lists (owned + shared)
POST /v1/listsCreate a list
GET /v1/lists/{id}Get a list with its metadata
PATCH /v1/lists/{id}Update list name, colour
DELETE /v1/lists/{id}Delete a list (and its tasks)
GET /v1/lists/{id}/tasksList tasks in a list (cursor pagination)
POST /v1/lists/{id}/tasksCreate a task in a list
GET /v1/tasks/{id}Get a task by ID (top-level, for deep links)
PATCH /v1/tasks/{id}Update a task (title, status, due date)
DELETE /v1/tasks/{id}Delete a task
POST /v1/lists/{id}/membersInvite a user to the list
DELETE /v1/lists/{id}/members/{user_id}Remove a member

Key design decisions

  • Tasks are a sub-resource of lists — they belong to a list, so /lists/{id}/tasks is the natural creation path. But a task also has a top-level URL (/tasks/{id}) for deep links and updates, because the task has its own identity (Volume 2, Question 3).
  • Membership is a sub-resource — the list's members are managed at /lists/{id}/members. The membership has a role (owner, editor, viewer), which controls what the user can do.
  • PATCH for updates — the client only sends the fields it wants to change; the server does not require the full representation (Volume 2, Question 4).
  • Cursor pagination — even for a small dataset, cursor pagination is the right default because it is stable and consistent (Volume 4, Question 1).
  • Authorization in the query — a request for a task checks that the caller has access to the containing list; the query filters by the caller's membership (Volume 6, Question 10).

Authentication and authorization

The API uses OAuth 2.0 with PKCE for the mobile and web clients — the user logs in via the provider, the client gets a token, and every request carries Authorization: Bearer ....

Authorization is at the list level:

RolePermissions
OwnerRead, write, delete the list; manage members
EditorRead, write tasks; cannot delete the list or manage members
ViewerRead only

Every task operation looks up the task's list and checks the caller's membership role. The BOLA check is in the query: SELECT * FROM tasks WHERE id = ? AND list_id IN (SELECT list_id FROM memberships WHERE user_id = ?).

Response shape and pagination

A list's tasks endpoint returns a paginated collection:

FieldContent
dataArray of tasks
meta.has_moreWhether there is another page
meta.next_cursorCursor for the next page

The page size is capped at 100; the client can request fewer. The default is 20.

Error handling

RFC 7807 for every error. The common cases:

  • 400 — malformed JSON, missing required field.
  • 401 — missing or invalid token.
  • 403 — authenticated but not a member of the list.
  • 404 — list or task not found (or not accessible — same response, to hide existence).
  • 409 — concurrent modification (if optimistic concurrency is used).
  • 422 — validation failure (a task with an invalid due date).
  • 429 — rate limit exceeded (1000 requests per minute per user).

What is intentionally left out of v1

  • Real-time updates — no WebSocket or SSE; the client polls or refreshes.
  • Offline sync — no local-first design; the mobile app requires connectivity.
  • Task dependencies — no "task A blocks task B"; just flat tasks.
  • Recurring tasks — no repeat rules; each task is one-off.
  • File attachments — no file uploads; text only.
  • Full-text search — no search across lists and tasks.

Each is a future feature that changes the API. Mentioning what is left out demonstrates the scope discipline — the API is what it is, and the roadmap is what it is not yet.

What Makes This Answer Strong

The task's dual URL (/lists/{id}/tasks for creation, /tasks/{id} for updates) demonstrates the identity test. The membership roles demonstrate fine-grained authorization. The explicit "what is left out" list demonstrates scope discipline. The cursor pagination for a small dataset demonstrates that the right default does not depend on scale.

Design the API for a social media platform — posts, feeds, follows, likes.

The Answer

A social API has five core resources: users, posts, comments, likes, and follows. The hard part is the feed — assembling posts from the people a user follows, ordered by recency, at scale. The design separates the write path (post creation, fan-out) from the read path (feed generation), with cursor pagination and aggressive caching.

Clarify requirements

  • Users create posts (text, image, or both), comment on posts, like posts.
  • Users follow other users; a user's feed shows posts from the people they follow.
  • Public and private accounts — public accounts' posts are visible to anyone; private accounts' posts are visible only to followers.
  • Scale — 100 million users, 1 billion posts, 10,000 posts per second at peak.
  • Read-heavy — the feed is read 100× more than a post is written.

Resource model

ResourceRelationshipsIdentity
UserHas posts; has followers and followinguser_id
PostBelongs to a user; has comments and likespost_id
CommentBelongs to a post and a usercomment_id
LikeBelongs to a post and a userComposite (post_id, user_id)
FollowFollower → followeeComposite (follower_id, followee_id)

Endpoints

Method & PathPurpose
GET /v1/users/{id}User profile
GET /v1/users/{id}/postsUser's posts (cursor pagination)
POST /v1/postsCreate a post
GET /v1/posts/{id}Get a post
DELETE /v1/posts/{id}Delete a post (author or admin only)
GET /v1/posts/{id}/commentsComments on a post
POST /v1/posts/{id}/commentsComment on a post
PUT /v1/posts/{id}/likesLike a post (idempotent)
DELETE /v1/posts/{id}/likesUnlike a post
POST /v1/users/{id}/followFollow a user
DELETE /v1/users/{id}/followUnfollow a user
GET /v1/feedThe authenticated user's feed

The feed — the hard problem

The feed is the posts from the people the user follows, ordered by recency, with pagination. Two strategies:

StrategyMechanismProsCons
Fan-out on read On feed request, query the posts of everyone the user follows, merge, sort No precomputation; always fresh Slow for users who follow many; the query is expensive
Fan-out on write On post creation, insert the post into every follower's feed (a precomputed list) Fast reads — the feed is a single query Slow writes for users with many followers; a celebrity's post fans out to millions

The pragmatic answer: hybrid. For ordinary users (few followers), fan-out on write — the feed is precomputed, reads are fast. For celebrities (millions of followers), fan-out on read — the post is not pushed to every follower's feed; instead, the feed query includes the celebrity's recent posts alongside the precomputed list. This is the standard "celebrity problem" solution (Volume 5 of the distributed systems series, Question 7).

Feed pagination

Cursor pagination, stable across writes. The cursor encodes the last post's (created_at, post_id). The query:

Query
 
SELECT * FROM feed_items
WHERE user_id = ?
  AND (created_at, post_id) < (?, ?)
ORDER BY created_at DESC, post_id DESC
LIMIT 20

For the celebrity component, a separate query for the celebrity's recent posts, merged with the precomputed list. The merge is a bounded K-way merge — fast.

Fan-out at write

When a user posts, the fan-out to followers is asynchronous — a job queue processes it:

  1. Post created — the post is written to the posts table.
  2. Event published — a post.created event goes to the queue.
  3. Fan-out worker — reads the event; for each follower, inserts the post ID into their feed table.
  4. Bounded — if the user has millions of followers, the worker is capped (or the user is treated as a celebrity, and fan-out on read is used).

The feed table is sharded by user_id; the fan-out worker writes to the appropriate shard. The table is small (recent posts only — older posts are trimmed); the query is fast.

Likes and counts

Likes are stored as rows in a likes table (composite key (post_id, user_id)). The count is denormalized — a like_count column on posts, updated by the write path. A read of the post's like count is a single column read, not a COUNT(*).

The PUT /posts/{id}/likes is idempotent — a user can like a post multiple times with the same result (one like). The unique constraint on (post_id, user_id) makes the duplicate insert a no-op.

Public vs private accounts

The visibility rule:

AccountWho can see the posts
PublicAnyone
PrivateOnly approved followers

The visibility check is in the query: WHERE (author.is_public = true) OR (author.id IN (SELECT followee_id FROM follows WHERE follower_id = ? AND status = 'accepted')). The check is per post, in the query, not after fetching.

Caching

The read-heavy workload is served by:

  • Feed cache — the first page of the feed is cached in Redis for 5 minutes. Most users see the cached version; the cache is invalidated on new posts (or just refreshed every 5 min).
  • User profile cache — profiles are cached; they change rarely.
  • Like count cache — the denormalized count is cached; the write updates both.
  • CDN for media — images and videos are served from a CDN; the API returns the URLs.
Trade-off

Fan-out on write is fast to read, expensive to write. Fan-out on read is the opposite. The hybrid — write for ordinary users, read for celebrities — is the standard answer. The threshold (10,000 followers? 100,000?) is chosen based on the fan-out cost; the celebrities are identified and handled separately.

What Makes This Answer Strong

The hybrid fan-out with the explicit celebrity threshold. The idempotent PUT for likes with the unique constraint. The visibility check in the query (BOLA prevention). The asynchronous fan-out with the bounded worker. The denormalized like count. Each is a specific answer to a specific scale problem.

Design the API for an e-commerce platform — catalogue, cart, checkout.

The Answer

An e-commerce API has four domains: catalogue (products, categories, prices), cart (items the user intends to buy), checkout (converting the cart to an order, with payment), and orders (the resulting purchases). The hard parts are inventory (preventing overselling), pricing (discounts, taxes, shipping), and payments (idempotency and correctness — Question 8).

Clarify requirements

  • Products — the catalogue is browsed by anonymous users; a product has a name, description, images, price, and stock.
  • Cart — a logged-in user adds products to a cart; the cart persists across devices.
  • Checkout — the user pays, the cart becomes an order, the inventory is decremented.
  • Orders — the user can view their orders, track shipments.
  • Scale — 1 million products, 100,000 orders per day, thousands of concurrent carts.

Resource model

ResourceRelationshipsIdentity
ProductBelongs to a category; has variants (size, colour)product_id
CategoryContains products; can be nestedcategory_id
CartBelongs to a user; has cart itemscart_id (or user_id)
CartItemBelongs to a cart; references a product variantComposite (cart_id, product_id, variant_id)
OrderBelongs to a user; has order linesorder_id
OrderLineBelongs to an order; snapshots the productComposite (order_id, line_no)
PaymentBelongs to an order; has a statuspayment_id

Endpoints

Method & PathPurpose
GET /v1/productsBrowse the catalogue (filter, sort, paginate)
GET /v1/products/{id}Get a product
GET /v1/categoriesBrowse categories
GET /v1/cartGet the current user's cart
POST /v1/cart/itemsAdd a product to the cart
PATCH /v1/cart/items/{id}Update quantity

The catalogue — read-heavy, cached

The catalogue is read-heavy (1000:1 vs writes) and changes rarely. The design:

  • Read replicas — the catalogue is served from read replicas; writes go to the primary.
  • CDN caching — the product pages are cached at the CDN with a short TTL (5 minutes); the invalidation is on product update.
  • Denormalized category data — the category path is stored on the product, so filtering by category does not require a join.
  • Filtering and sorting — only indexed fields are filterable (category, price range, availability); the sort is by price or popularity; both are indexed.

The product listing uses cursor pagination (Volume 4, Question 1) — the catalogue is large, and offset pagination breaks at scale.

Cart — a stateful resource

The cart is a persistent resource, keyed by user. Every add/update/remove is an operation on the cart:

OperationEndpointIdempotency
Add itemPOST /cart/itemsIdempotent by (product_id, variant_id) — adding the same item again increments the quantity
Update quantityPATCH /cart/items/{id}Idempotent — setting the quantity is a set operation
Remove itemDELETE /cart/items/{id}Idempotent — removing a missing item returns 204

The cart is stored in a database (not just a session cookie) — the cart persists across devices, and the cart items reference the actual products (a product removed from the catalogue shows as unavailable).

Checkout — the hard part

Checkout is a multi-step operation:

  1. Reserve inventory — for each cart item, decrement the available count. This must be atomic — no overselling.
  2. Compute pricing — discounts, taxes, shipping. The pricing is computed server-side (never trust the client's total).
  3. Charge payment — with an idempotency key (Question 8) — the charge is not duplicated on retry.
  4. Create order — with the order lines, the total, the payment reference. The order lines snapshot the product details (name, price) — the order history is preserved even if the product is updated later.
  5. Confirm — send the confirmation email; notify the warehouse; update the inventory permanently.

The whole flow is a saga (Volume 5 of the distributed systems series) — each step has a compensating action if a later step fails:

StepCompensation
Reserve inventoryRelease the reservation
Charge paymentRefund the charge
Create orderCancel the order; refund

The saga is orchestrated by a checkout service — it calls the inventory, payment, and order services, and orchestrates the compensations.

Inventory — preventing overselling

The classic race condition (Volume 14, Question 8): two users buy the last item, both succeed, the stock goes to -1. The fix: an atomic SQL operation:

VulnerableFixed
 
stock = SELECT stock FROM inventory WHERE product_id = ?
if stock >= qty:
    UPDATE inventory SET stock = stock - qty
 
UPDATE inventory SET stock = stock - qty
WHERE product_id = ? AND stock >= qty
# if rows affected = 0, insufficient stock

The database performs the check and the decrement atomically — no window between them. The checkout service calls this and, if it fails, aborts the checkout.

Idempotency for checkout

The POST /orders endpoint requires an Idempotency-Key header (Question 8). The client generates a UUID at the moment of intent; the server stores the key → order mapping; a retry returns the existing order, not a duplicate.

This is critical — the checkout flow involves a payment, and a duplicate charge is a customer-facing incident. Without the key, a client's retry (after a timeout) would double-charge the customer.

Order cancellation

An order can be cancelled if it has not shipped:

StatusCan cancel?Side effects
pendingYesRelease inventory; refund payment
confirmedYesRelease inventory; refund payment
shippedNoReturn process, not cancellation
deliveredNoReturn process

The cancellation is a state transition, implemented as a sub-resource (Volume 2, Question 7): POST /orders/{id}/cancellations. The cancellation has its own state (pending refund, refunded); the client can track it.

The Pitfall to Avoid

Trusting the client's total. The checkout must recompute the price — the client's "total" is a hint, not the truth. A modified total in the request would let the customer pay less; the server's computation is the authoritative amount.

What Makes This Answer Strong

The explicit saga with compensations. The atomic inventory operation (Volume 14, Question 8 applied). The order-line snapshot for history preservation. The idempotency key on checkout. The sub-resource cancellation. Each is a specific answer to a specific e-commerce problem.

Design the API for a ride-sharing service — rides, drivers, matching.

The Answer

A ride-sharing API has four core resources: riders, drivers, ride requests, and trips. The hard part is the matching — assigning a nearby driver to a ride request in real time — and the location tracking — the driver's location is updated continuously. The API is stateful (the ride has a lifecycle) and real-time (both parties track the ride's progress).

Clarify requirements

  • Riders request a ride from a pickup to a destination.
  • Drivers go online, receive requests, accept or decline.
  • Matching — the system assigns a nearby driver to the request, considering availability, distance, and rating.
  • Real-time — the rider sees the driver's location; the driver sees the route.
  • Scale — 1 million rides per day, 100,000 concurrent drivers, 100,000 concurrent riders.
  • Payments — the ride ends with a charge; idempotency is mandatory.

Resource model

The ride lifecycle — state machine

The trip's status is a state machine; each transition is a sub-resource (Volume 2, Question 7):

FromToTriggered by
(none)requestedRider creates a request
requestedassignedSystem assigns a driver
assignedacceptedDriver accepts
acceptedarrivingDriver navigates to pickup

Each transition is idempotent — the same transition called twice is a no-op, returning the current state. The POST /trips/{id}/acceptance is idempotent: if the driver accepts twice, the second call returns 200 with the already-accepted state, not an error.

The matching algorithm

When a rider requests a ride, the system must find a nearby available driver. The mechanism:

  1. Find candidates — query the drivers within a radius (e.g., 5 km) of the pickup, who are online and available. This uses a geospatial index — PostGIS, Redis Geo, or a dedicated service.
  2. Rank candidates — score by distance, driver rating, acceptance rate, and time since last ride.
  3. Assign — pick the top candidate; send them the request (via a push channel or a long-poll).
  4. Await acceptance — the driver has N seconds to accept; if they decline or time out, try the next candidate.
  5. Confirm — once accepted, the ride is assigned; the rider sees the driver's info.

The candidate query is the bottleneck — with 100,000 drivers, finding the nearby ones requires a spatial index. The index is updated on every location update (which is frequent — every 5 seconds per driver).

Location updates

Every driver sends their location every 5 seconds. With 100,000 drivers, that is 20,000 updates per second. The design:

  • Write to an in-memory geospatial store (Redis Geo or a custom service) — the update is a GEOADD; the query is a GEOSEARCH.
  • Batch the writes — the driver's app batches a few seconds of location updates; the server writes them in one call.
  • Durability for active trips — the location of a driver on an active trip is persisted (for the route history); the location of an idle driver is in-memory only (it is stale within seconds).
  • Rate limit — the driver's app is rate-limited; a misbehaving app cannot flood the server.

Real-time updates

Both the rider and the driver need real-time updates: the rider sees the driver's location; the driver sees the request. The mechanism:

ChannelUse caseProtocol
WebSocket Bidirectional — the rider tracks the driver, the driver sends location WebSocket or gRPC streaming
Push notification Ride status changes (assigned, arrived, completed) — works when the app is backgrounded APNs / FCM
Long-poll Fallback for older clients HTTP

The rider's app keeps a WebSocket connection open; the server pushes the driver's location (throttled to every 2 seconds — the UI does not need 5 updates per second). The push notifications handle the backgrounded app (the user gets a notification when the driver arrives).

Payment at trip completion

When the trip completes, the fare is computed (distance × rate + time × rate + surge × multiplier), and the payment is charged. The charge uses an idempotency key derived from the trip ID (Question 8) — the completion handler can retry without double-charging.

The fare computation is server-side — the client's estimate is a hint, not the truth. The actual fare depends on the actual route, the actual time, and the actual surge at completion.

The Pitfall to Avoid

Treating the ride as a synchronous request. The ride is a long-lived resource with a state machine and a saga. The API is not "give me a ride" (which would time out); it is "create a ride request, track its status, receive updates". The 202 + status endpoint pattern (Volume 11) applies, plus the WebSocket for real-time tracking.

What Makes This Answer Strong

The state machine with idempotent transitions. The geospatial index for matching. The rate limit on location updates. The WebSocket for real-time and push notifications for backgrounded apps. The idempotency key on the charge. Each is a specific answer to a ride-sharing scale problem.

Design the API for a banking system — accounts, transfers, statements.

The Answer

A banking API has three core resources: accounts, transactions (every credit and debit), and transfers (a movement between two accounts). The hard parts are atomicity (a transfer debits one account and credits another — both or neither), idempotency (a retry must not double-transfer), and reconciliation (every transaction is traceable and auditable).

Clarify requirements

  • Accounts — a customer has one or more accounts (checking, savings); each has a balance and a history.
  • Transfers — between the customer's own accounts or to another customer.
  • Statements — the history of transactions on an account, filterable by date range.
  • Strict consistency — the balance is always correct; a transfer either completes fully or not at all.
  • Auditability — every transaction is recorded; nothing is silently lost or modified.
  • Regulatory — the data is retained for years; the API is audited.

Resource model

ResourceRelationshipsIdentity
AccountBelongs to a customer; has a balanceaccount_id
TransactionBelongs to an account; is the atomic unit of changetransaction_id
TransferLinks two transactions (debit and credit)transfer_id
StatementA view of the transactions over a periodDerived from transactions

Endpoints

Method & PathPurpose
GET /v1/accountsList the customer's accounts
GET /v1/accounts/{id}Get account details
GET /v1/accounts/{id}/balanceCurrent balance (strongly consistent)
GET /v1/accounts/{id}/transactionsTransaction history (cursor pagination)
GET /v1/accounts/{id}/statementsStatements (monthly)

GET /v1/transfers/{id}Get transfer status
POST /v1/transfers/{id}/cancellationsCancel a pending transfer

The ledger model

The correct way to model a banking system is a double-entry ledger:

  • Every transaction is recorded as a pair of entries (debit and credit) that sum to zero. The account balance is not a mutable field — it is derived from the entries.
  • The balance is the sum of the entries for the account. The sum is maintained as a cached column (updated on every entry) for performance, but the entries are the source of truth.
  • Every transfer creates two transactions (debit from source, credit to destination), plus a transfer record linking them.
  • Nothing is deleted — a reversal is a new transfer in the opposite direction; the history is preserved.

This model is auditable, recoverable, and correct — the balance can always be recomputed from the ledger, and any discrepancy is detectable.

The transfer — atomicity

The transfer is atomic: either the debit and credit both happen, or neither. The mechanism:

StepAction
1 BEGIN a database transaction
2 Lock both accounts (in a deterministic order, to prevent deadlocks)
3 Check the source balance is sufficient (the check is in the locked read)
4 Insert the debit entry; insert the credit entry
5 Update the cached balances for both accounts
6 Insert the transfer record
7 COMMIT

All steps are in a single database transaction — if anything fails, the whole transfer rolls back. The locking is essential: without it, two concurrent transfers could both see a $100 balance and both proceed, leaving the account at -$100.

For transfers between accounts at different banks, the saga pattern applies (the counterparty's system is a separate service) — the local transaction is followed by a message to the other bank, and the reconciliation handles the settlement.

Idempotency — the transfer must not duplicate

The POST /transfers requires an Idempotency-Key header (Question 8). The client generates a UUID; the server stores the key → transfer mapping; a retry returns the existing transfer, not a new one.

The storage is durable (a database, not Redis) — the key must survive a failover. The TTL is long (months, not hours) — a banking transfer is not a short-lived operation, and the customer may retry days later.

The balance — strongly consistent

The balance endpoint returns the current balance, read from the ledger. The read is strongly consistent: it reads from the primary, not a replica, so the balance reflects the latest committed transaction. The client sees its own transfer's effect immediately.

The alternative — reading from a replica — risks a stale balance. The replica might lag by milliseconds, but the user might see a balance before their transfer completed and be confused. For banking, strong consistency is the right choice, and the latency cost is acceptable (Volume 3, Question 3).

Statements and transaction history

The transaction history is paginated with cursors (the entries are ordered by timestamp + ID). The cursor encodes the last seen (created_at, transaction_id); the query is an index scan.

The statements are monthly — precomputed and stored (a PDF or a structured document). A statement endpoint returns the statement for a month; the statement is generated once (on the first request for that month) and cached. The generation aggregates the month's transactions and produces the document.

Security

The banking API has the strictest security:

  • OAuth 2.0 with strong authentication — MFA, hardware tokens for high-value operations.
  • Scopes — read:accounts, transfer:own, transfer:external.
  • Transaction limits — per day, per transfer, per account.
  • Anomaly detection — a transfer that looks unusual triggers a review.
  • Audit log — every read and write is logged; the log is immutable.
  • Encryption — data in transit and at rest.
  • Regulatory compliance — KYC, AML, PCI, GDPR.
Trade-off

Strong consistency (reading from primary) costs latency and availability. For banking, this is the right choice — a stale balance is unacceptable. For a less critical API (a social profile), eventual consistency with read replicas is fine. The choice depends on what the user expects — and a bank user expects their balance to be exact.

What Makes This Answer Strong

The double-entry ledger — the balance is derived, not stored as truth. The atomic transfer with deterministic lock ordering. The idempotency key with long TTL and durable storage. The strongly consistent balance read. The monthly statement precomputation. The layered security. Each is a specific answer to a banking correctness problem.

Design the API for a notification service — push, email, SMS, in-app, and user preferences.

The Answer

A notification API has three core resources: notifications (the message to deliver), preferences (which channels the user accepts for which types), deliveries (the per-channel attempt and its status). The hard parts are multi-channel fan-out, user preferences, and reliability — a notification is not lost because the email provider was slow.

Clarify requirements

  • Channels — push (APNs, FCM), email (SendGrid, SES), SMS (Twilio), in-app (the notification feed), and webhook.
  • Notification types — transactional (order confirmation), marketing (promotion), security (password changed), social (new follower).
  • Preferences — the user can opt out per type per channel; the transactional notifications are mandatory.
  • Priority — security and transactional are immediate; marketing is batched and rate-limited.
  • Reliability — the notification is delivered at least once; the user does not miss the security alert.
  • Scale — 100 million users; a marketing campaign sends 10 million notifications in an hour.

  3. Rate limiting — the sending is rate-limited (the provider's rate limit; the sending service's capacity).
  4. Preference check — each user's preferences are checked; the opt-outs are skipped.
  5. Deduplication — the same user is not sent the same campaign twice.
  6. Progress tracking — the campaign status is tracked (sent, failed, in progress).

  • Sending — the worker is calling the provider.

  • Delivered — the provider confirms delivery (email delivered, push received).
  • Failed — the provider rejected; the retries exhausted.

Design the API for a file storage service — upload, download, share, versioning.

The Answer

A file storage API has three core resources: files (the metadata — name, size, type, checksum), versions (the historical copies), and shares (permissions granted to other users). The actual file bytes are stored in object storage (S3, GCS); the API stores metadata and issues signed URLs for the upload and download. The hard parts are large uploads (resumable, chunked), sharing (permissions), and versioning (preserving history).

Clarify requirements

  • Download — the user downloads a file by ID.
  • Share — the user shares a file with another user (read or write) or via a public link.
  • Versioning — when a file is re-uploaded, the old version is preserved; the user can download a specific version.
  • Large files — files can be up to 5 GB; the upload must be resumable.
  • Scale — 1 billion files; 100 TB of storage; 10,000 uploads per second at peak.

The upload — chunked and resumable

A 5 GB file cannot be uploaded in one HTTP request — the timeout would fire, the connection would drop, and the upload would restart. The chunked upload:

  1. Initiate — POST /uploads with the file name, size, and checksum. The server returns an upload_id and the part size (e.g., 5 MB).
  2. Upload parts — the client sends each chunk to PUT /uploads/{id}/parts/{n}. The server stores the chunk in object storage.
  3. Complete — POST /uploads/{id}/complete with the list of parts and their checksums. The server verifies the parts, assembles them, and creates the file record.

The resumability: if the upload is interrupted, the client can query which parts are already uploaded and resume from there. The parts are idempotent — re-uploading a part replaces it.

Direct-to-storage upload

The efficient architecture uses signed URLs — the client uploads directly to object storage, bypassing the API server:

  1. The client asks the API for a signed URL (POST /uploads).
  2. The API generates a pre-signed S3 PUT URL (with a TTL) and returns it.
  3. The client uploads the bytes directly to S3 via the signed URL.
  4. The client notifies the API (POST /uploads/{id}/complete); the API verifies the object exists and creates the file record.

The API server is not in the data path — the bytes go from the client to S3, and the API only handles metadata. This is the standard architecture for file storage at scale.

The download

Similarly, the download is via a signed URL:

  1. The client asks the API for a download URL (GET /files/{id}/content).
  2. The API authorizes (the user owns or is shared the file) and generates a signed S3 GET URL.
  3. The API returns a 302 redirect to the signed URL (or the URL in the body).
  4. The client downloads from S3 directly (or via a CDN).

The signed URL has a short TTL (minutes) — it is not a permanent link; the client must request a new one.

Sharing and permissions

The share is a resource; it has an ID and can be revoked. The public link is a URL with a share token; the token is random (not guessable), and the link is checked on every request.

Versioning

Every re-upload creates a new version. The file has a current version and a history. The version is identified by a number (1, 2, 3) or a timestamp. The old versions are preserved (until a retention policy removes them); the user can download a specific version.

The storage cost: versioning multiplies the storage. The retention policy limits it — keep the last N versions, or the versions for the last N days. The user can also delete a version explicitly.

Security

  • Signed URLs — the URLs are signed with a secret and a TTL; they cannot be guessed or forged.
  • Authorization — the API checks the user's access to the file before issuing the signed URL.
  • Encryption — the files are encrypted at rest (S3 SSE); the signed URLs use HTTPS.
  • Virus scanning — the uploaded files are scanned asynchronously; an infected file is quarantined.
  • Content-type validation — the API does not trust the client's Content-Type; the type is inferred from the file, or the upload is restricted to specific types.
Trade-off

Direct-to-storage upload (signed URL) saves the API server from handling the bytes — it is faster and cheaper. The cost is that the API cannot inspect the bytes during the upload (only after); the virus scan and content validation are asynchronous. For most use cases, the trade is worth it; for high-security cases (classified documents), the API proxies the upload for inspection.

The signed URLs for direct-to-storage upload and download. The chunked, resumable upload. The versioning with retention policy. The share types (user, public, password, expiring). The asynchronous virus scan. Each is a specific answer to a file storage scale and security problem.

Design a payment API with strict idempotency and correctness.

The Answer

A payment API has three core resources: payment intents (the intent to charge), charges (the actual charge), and refunds (the reversal). The API is idempotent — a retry must not double-charge — and correct — every charge is traceable, every refund is linked, every state transition is recorded. The design follows Stripe's model — the industry reference.

Clarify requirements

  • Charge a customer — the merchant requests a charge for an amount, with a payment method.
  • Refund a charge — a full or partial refund.
  • Idempotency — a retry with the same key returns the same result, not a new charge.
  • Correctness — the amount is exact; the state is consistent; the audit is complete.
  • Reliability — the charge is processed even if the merchant's server crashes; the webhook notifies the merchant when the charge succeeds or fails.
  • Security — PCI compliance; the card data never touches the merchant's server (tokenization).

Resource model

ResourceRelationshipsIdentity
CustomerHas payment methods; has chargescustomer_id
PaymentMethodBelongs to a customer; is a tokenized cardpayment_method_id
PaymentIntentThe intent to charge; results in a chargeintent_id
ChargeBelongs to an intent; has a statuscharge_id
RefundBelongs to a chargerefund_id

Endpoints

Method & PathPurpose
POST /v1/payment-intentsCreate a payment intent (with idempotency key)
POST /v1/payment-intents/{id}/confirmConfirm and charge (with idempotency key)
GET /v1/payment-intents/{id}Get intent status
POST /v1/charges/{id}/refundsRefund a charge (with idempotency key)
GET /v1/refunds/{id}Get refund status

The idempotency — the core mechanism

Every mutating endpoint requires an Idempotency-Key header (Volume 5, Questions 2–7). The flow:

  1. Client generates a key — a UUID, per logical operation, at the moment of intent.
  2. Server claims the key — atomically inserts the key into the idempotency store, with a fingerprint of the request body.
  3. Process — the charge is processed; the response is stored under the key.
  4. Retry — the same key returns the stored response; a different body with the same key returns 422.

The idempotency store is durable (a database) and scoped per account. The TTL is 24 hours — long enough for any realistic retry; the customer does not retry a payment after a day.

The payment intent — the two-phase charge

The payment intent separates the intent (the request to charge) from the charge (the actual money movement). The flow:

  1. Create the intent — POST /payment-intents with the amount, currency, and customer. The intent is requires_payment_method; it is not charged yet.
  2. Attach the payment method — the client sends the payment method ID (a tokenized card). The intent becomes requires_confirmation.
  3. Confirm the intent — POST /payment-intents/{id}/confirm. The server charges the card; the intent becomes succeeded or failed.
  4. Webhook — the server notifies the merchant of the outcome (Question 10).

The two-phase design allows the merchant to handle 3D Secure (the customer is redirected to the issuer's page for authentication) and other asynchronous payment flows. The intent tracks the state across the redirect; the charge happens when the authentication completes.

The charge — atomic and recorded

The charge is processed by the payment processor (Stripe, Adyen, a bank). The merchant's API:

  • Validates — the amount, the currency, the payment method.
  • Records the intent — before calling the processor.
  • Calls the processor — with the processor's idempotency key (derived from the intent ID).
  • Records the outcome — the charge ID, the status, the processor's reference.
  • Emits the event — the charge.succeeded or charge.failed event, which triggers the webhook.

The processor's idempotency key is critical — the processor must not double-charge if the merchant's API retries. The key is the merchant's intent ID; the processor deduplicates on it.

Refunds

The refund is a resource with its own lifecycle:

StateMeaning
pendingThe refund is being processed
succeededThe refund has been issued
failedThe refund was rejected (e.g., insufficient balance)

The refund has its own idempotency key — a partial refund can be retried without duplicating. The refund's amount is checked against the charge's remaining refundable amount; the refund cannot exceed the charge.

The webhook — the notification

The merchant's server needs to know when a charge succeeds or fails. The webhook (Question 10):

  • Subscribed — the merchant registers a URL for charge.succeeded, charge.failed, refund.succeeded.
  • Signed — the payload is signed with HMAC; the merchant verifies.
  • Retried — the webhook is retried with backoff; the merchant's server may be down.
  • Reconcilable — the merchant can query the API for the event if the webhook is missed.

Security and PCI

  • Tokenization — the card data is tokenized by the processor (Stripe.js, Adyen's components); the merchant's server sees a token, not the card number. The merchant is not in the PCI scope for the card data.
  • HTTPS only — the API rejects any non-HTTPS request.
  • API keys — the merchant's API key has a restricted scope (charge, refund); it cannot read other merchants' data.
  • Webhook signatures — the merchant verifies the signature; a forged webhook is rejected.
  • Audit log — every charge, refund, and state change is logged; the log is immutable.
The Pitfall to Avoid

Not requiring the idempotency key. The merchant's server retries after a timeout; the payment is charged twice; the customer disputes. The API must require the key on every mutating endpoint — a request without it is a 400. The key is the merchant's responsibility; the API enforces it.

What Makes This Answer Strong

The payment intent as a two-phase charge, enabling 3D Secure. The idempotency key on every mutating endpoint, with durable storage and 24h TTL. The processor idempotency derived from the intent. The webhook with signing and reconciliation. The tokenization for PCI. Each is a specific answer to a payments correctness problem.

Design a webhook delivery system — signed, retried, reconcilable.

The Answer

A webhook system has five components: a subscription registry (who wants which events), an event queue (durable, survives crashes), a dispatcher (sends the HTTP requests), a retry scheduler (exponential backoff), and a reconciliation endpoint (so a receiver that missed events can catch up). The delivery is signed with HMAC, verified by the receiver, and idempotent — a duplicate delivery is harmless (Volume 11, Questions 3–6).

The event envelope

FieldContent
idUnique event ID (for receiver idempotency)
typeorder.created, payment.succeeded

The subscription registry

Each subscription has:

  • URL — the receiver's HTTPS endpoint.
  • Event types — which events the receiver wants.
  • Secret — for signing (per subscription; rotatable).
  • Status — active, paused, disabled (after repeated failures).
  • Metadata — description, contact, creation date.

The delivery flow

  1. Event emitted — the business logic publishes order.created.
  2. Event stored — in a durable outbox, in the same transaction as the business change (Volume 11, Question 6).
  3. Dispatcher reads — the worker reads the outbox, finds the subscribers for the event type.
  4. For each subscriber:
    • Builds the payload.
    • Signs it with the subscription's secret.
    • POSTs to the URL with a 10-second timeout.
    • Reads the response.
  5. Success (2xx) — mark delivered; move on.
  6. Retryable failure (5xx, timeout, 429) — schedule a retry with backoff.
  7. Non-retryable failure (4xx) — mark failed; move to DLQ.
  8. Retries exhausted — mark failed; move to DLQ.

The signature

The signature is HMAC-SHA256 over timestamp + "." + body, sent in the X-Webhook-Signature header:

Header
X-Webhook-Signature: t=1699999999,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd

The receiver verifies:

  1. Extract t and v1.
  2. Check abs(now - t) < 300 (5 minutes) — reject old requests (replay prevention).
  3. Compute HMAC-SHA256(secret, t + "." + body).
  4. Compare with v1 using constant-time comparison.
  5. Process if matched; reject with 401 if not.

The SSRF prevention

The webhook URL is an SSRF vector (Volume 11, Question 8). The defenses:

  • HTTPS only — reject http://.
  • DNS resolution + IP validation — resolve the hostname; reject private, loopback, link-local, and metadata IPs.
  • Re-validate on every delivery — the DNS may rebind.
  • No redirects — a 3xx is a failure, not a follow.
  • Network isolation — the dispatcher runs in a subnet with no route to internal services.
  • Egress firewall — deny outbound to RFC 1918 and 169.254.0.0/16.

The reconciliation endpoint

The receiver can query for missed events:

GET /events?since=2026-11-12T00:00:00Z&type=order.createdList of events since the timestamp, paginated

The receiver stores its last-seen timestamp; on startup or periodically, it queries for events after that timestamp. This guarantees eventual delivery even if webhooks fail — the receiver can always pull.

The DLQ

Exhausted retries go to a dead-letter queue. The receiver can query the DLQ for missed events; the sender can replay after fixing a problem. Without a DLQ, the failed events are silently lost.

The Pitfall to Avoid

Relying on webhooks alone. The webhooks fail — the receiver is down, the network is broken, the secret is rotated. Without a reconciliation endpoint, the events are lost permanently. The webhooks are the fast path; the reconciliation is the guarantee.

What Makes This Answer Strong

The durable outbox for the event. The HMAC signature with the timestamp for replay prevention. The exponential backoff schedule. The SSRF defenses (HTTPS, DNS + IP validation, no redirects, network isolation). The reconciliation endpoint. The DLQ. Each is a specific answer to a webhook reliability problem.

Caching

HTTP caching does not work for GraphQL (POST with a body). The caching strategy:

  • Client normalized cache — Apollo Client or Relay stores entities by __typename + id; subsequent queries read from the cache.
  • Persisted queries + GET + CDN — for public queries, the persisted hash goes in the URL; the CDN caches the response.
  • Resolver-level cache — expensive resolvers cache their results in Redis.
  • DataLoader per-request cache — the same entity requested twice in one query is fetched once.

Authorization

Field-level authorization (Volume 12, Question 6):

  • Operation-level — can the user run this query? (a check before the resolvers).
  • Field-level — can the user see this field on this object? (a directive or middleware).
  • Object-level — can the user see this specific post? (a check in the resolver).

The nested-field BOLA is the subtle bug: a query that fetches user.posts.author.salary — the top-level user is authorized, but the nested author's salary needs its own check.

The Pitfall to Avoid

Forgetting DataLoader for a single field. The feed's author resolver is batched, but the comment's author resolver is not — the query fails at the comment level. Every field that does a per-item lookup needs its own loader.

What Makes This Answer Strong

The schema designed for the client's queries. The DataLoader at every nesting level. The complexity score and depth limit. The persisted queries for security and caching. The client normalized cache. The field-level authorization with the nested BOLA check. Each is a specific answer to a GraphQL production problem.

Design cursor pagination for a high-volume feed.

The Answer

Cursor pagination for a high-volume feed uses an opaque cursor that encodes the last item's sort key. The query is a keyset scan — WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20 — which uses an index and is O(limit) regardless of how deep the page is. The cursor is base64-encoded JSON, opaque to the client, and stable across writes. The response includes has_more and next_cursor; the client passes the cursor back for the next page.

The schema

TableColumns
feed_items user_id, created_at, post_id, author_id, content_snapshot
posts id, author_id, content, created_at, like_count

The feed_items is a denormalized table (the precomputed feed, from fan-out on write). The composite index is (user_id, created_at DESC, post_id DESC).

The endpoint

RequestResponse
 
GET /v1/feed?limit=20&cursor=eyJjcmVhdGVkX2F0IjoiMjAyNi0xMS0xMlQxMDowMDowMFoiLCJpZCI6MTIzNDV9
 
{
  "data": [...],
  "meta": {
    "has_more": true,
    "next_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNi0xMS0xMVQwOTowMDowMFoiLCJpZCI6MTIzNDB9"
  }
}

The cursor

The cursor is base64-encoded JSON:

CursorDecoded
eyJjcmVhdGVkX2F0IjoiMjAyNi0xMS0xMlQxMDowMDowMFoiLCJpZCI6MTIzNDV9{"created_at": "2026-11-12T10:00:00Z", "id": 12345}

The cursor is opaque to the client — it must not parse it; it just passes it back. The opacity allows the server to change the cursor format without breaking clients (the encoding is internal).

The query

First page (no cursor)Next page (with cursor)
 
SELECT * FROM feed_items
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 21
 
SELECT * FROM feed_items
WHERE user_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 21

The LIMIT 21 (one more than the page size) lets the server determine has_more — if 21 rows are returned, there is another page; if 20, this is the last. The extra row is discarded from the response.

The query uses the composite index (user_id, created_at DESC, id DESC) — an index range scan, O(limit). The key insight: this is O(limit) regardless of how deep the page is, because the index seeks directly to the cursor position — no OFFSET, no scanning from the beginning.

The stability under writes

With offset pagination, an item inserted before the current page shifts every subsequent page — the user sees duplicates or misses items. With cursor pagination, the cursor references the last item's position — an insert after the cursor appears on the next page; an insert before the cursor is not seen (it is in the past). The cursor is stable.

The tiebreaker (the ID) handles the case where multiple items have the same created_at — the composite comparison (created_at, id) < (?, ?) gives a deterministic order even when timestamps collide.

The reverse pagination

For "newer" pages (backward pagination), the cursor is the first item on the current page; the query is WHERE (created_at, id) > (?, ?) ORDER BY created_at ASC, id ASC LIMIT 21 — the reverse. The results are reversed again for the response. The cursor and the query direction are part of the same contract.

The total count

The total count of the feed is expensive to compute (a COUNT(*) over all feed items). The design: do not return a total. Return has_more. If the total is needed (for a "showing 1–20 of 1,234" display), compute it once and cache it — the count changes slowly, and the cache is valid for a minute.

The page size

The client requests limit (default 20, max 100). A request for more than 100 is capped at 100 — the response's limit field reflects the actual size. The cap prevents the client from requesting 10,000 items in one query.

The CDN caching

For the public portion of the feed (the first page, for anonymous users or shared profiles), the response is cached at the CDN. The cache key is the URL with the cursor — every page is a distinct URL. The cache is invalidated on new feed items (or just refreshed with a short TTL). For the personalized feed (the authenticated user's), the response is Cache-Control: private, no-store — not cached at the CDN.

The infinite scroll

The client's infinite scroll is the primary consumer of the cursor. The client:

  1. Loads the first page (no cursor).
  2. Renders the items.
  3. When the user scrolls near the bottom, loads the next page with next_cursor.
  4. Appends the items.
  5. Continues until has_more = false.

The cursor survives app restarts — the client can persist the last cursor and resume.

The Pitfall to Avoid

Using offset pagination for the feed. The query becomes O(offset) — page 1,000 takes seconds. And the page shifts under writes — the user sees duplicates. The cursor is the only design that scales to deep pages and is stable.

What Makes This Answer Strong

The opaque cursor encoding (created_at, id). The LIMIT 21 for has_more. The composite index matching the sort. The reverse pagination. The "do not return a total" decision. The CDN caching for public, no-store for personalized. Each is a specific answer to a pagination scale problem.

Design a multi-tenant rate limiter — fair, distributed, resilient.

The Answer

A multi-tenant rate limiter has four requirements: fairness (one tenant cannot starve others), per-tenant configuration (different plans, different limits), distributed enforcement (across the gateway fleet), and resilience (the limiter itself must not be a single point of failure). The design: a per-tenant token bucket in Redis, with the key rate:{tenant_id}:{endpoint}, and a local fallback if Redis is unavailable.

The tiers

TierRate limitBurstConcurrency
Free60/min105
Pro1,000/min10050

InternalUnlimited——

The algorithm — token bucket in Redis

The token bucket (Volume 7, Question 3) is the right algorithm for APIs — it allows bursts up to the bucket size while enforcing the sustained rate.

The Redis implementation uses a Lua script for atomicity:

Lua script (pseudo)
 
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local cost = tonumber(ARGV[4])

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

-- Refill the bucket based on elapsed time
local elapsed = math.max(0, now - last_refill)
local refill = elapsed * rate
tokens = math.min(capacity, tokens + refill)

if tokens >= cost then
  tokens = tokens - cost
  redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
  redis.call('EXPIRE', key, math.ceil(capacity / rate) * 2)
  return 1
else
  return 0
end

The script is atomic — no race between the read, the refill, and the decrement. The EXPIRE cleans up the key after the bucket would be full again, bounding the memory.

The key design

KeyPurpose
rate:{tenant_id}The global rate limit for the tenant
rate:{tenant_id}:{endpoint}Per-endpoint limit (for expensive endpoints)
rate:{tenant_id}:concurrencyThe concurrent requests (a different counter)
rate:{api_key}Per-key limit (a tenant may have multiple keys)

The per-endpoint limit is important — a tenant's 1,000/min can be consumed entirely by a single expensive endpoint, starving the other endpoints. The per-endpoint limit ensures the expensive endpoint is bounded separately.

The multi-dimensional check

A request passes if it satisfies all the applicable limits:

  1. Tenant limit — the global rate for the tenant.
  2. Endpoint limit — the rate for this specific endpoint.
  3. Key limit — the rate for this API key.
  4. Concurrency limit — the in-flight requests.

The check is done in sequence — the cheapest first (concurrency), the most expensive last. If any fails, the request is rejected with the appropriate headers (which limit was exceeded).

The distributed enforcement

With multiple gateway instances, the rate limiter must be shared. The options:

ApproachProsCons
Central Redis Exact; one source of truth Every request is a Redis round trip; Redis is a hotspot
Local + sync Fast; no Redis on the hot path Approximate — the effective limit is N × local
Hybrid Fast for the local check; exact for the global Complex; two mechanisms

The hybrid is the production answer:

  1. Local bucket — each gateway instance has its own token bucket, sized to limit / N. A request that exceeds the local bucket is rejected immediately (no Redis call).
  2. Global bucket — every Kth request (or every request when the local bucket is near full), the gateway syncs the consumption to Redis. The global bucket enforces the tenant-wide limit.
  3. Periodic sync — every 100 ms, the local consumption is flushed to Redis; the global bucket is decremented.

The result: the local check is fast (no network); the global check is exact (within the sync window). The overshoot is bounded — a burst that briefly exceeds the limit by the sync window.

The failure mode

If Redis is down, what happens?

PolicyBehaviourTrade-off
Fail-openAllow all requestsAvailability; the system is unprotected
Fail-closedReject all requestsProtection; the API is down
Fail-localUse the local bucket onlySome protection; the effective limit is per-instance

Fail-local is the pragmatic answer: the local bucket (which is always available) continues to enforce a per-instance limit; the fleet may over-consume by N × the local limit, which is degraded but not catastrophic. When Redis recovers, the global bucket resumes.

The tenant configuration

The tiers are stored in a database; the gateway caches them (5-minute TTL). A change to a tenant's tier propagates within 5 minutes. The config is declarative — a YAML or a table — not code, so the customer success team can change a tier without a deploy.

The observability

  • Rate limit hits — per tenant, per endpoint; the count and the trend.
  • Near-limit alerts — a tenant at 80% of the limit; the customer success team is notified.
  • Rejected requests — the 429s; the client's retry behaviour.
  • Redis health — the latency; the error rate; the fail-local activations.
The Pitfall to Avoid

Using a single Redis key for all tenants. The key is a hotspot — every request hits the same Redis shard. The fix: per-tenant keys; Redis Cluster shards them across nodes. Even with per-tenant keys, a huge tenant's key is a hotspot — the local bucket absorbs most of it.

What Makes This Answer Strong

The token bucket in Lua for atomicity. The multi-dimensional check (tenant, endpoint, key, concurrency). The hybrid local + global for performance. The fail-local policy for resilience. The declarative tier configuration. Each is a specific answer to a multi-tenant rate limiting problem.

Design a versioning strategy for a rapidly evolving product.

The Answer

A rapidly evolving product has a tension: the API must evolve quickly (the product changes), but the clients must not break (the integrations continue). The strategy: additive-by-default (non-breaking changes happen within the version), URL versioning (a breaking change gets a new /v2/), a deprecation policy (the old version is supported for 12–18 months), a migration guide (the clients have a path), and the tooling (a breaking-change check in CI; a linter; the SDK versioning).

The versioning scheme

URL versioning: /v1/, /v2/. The version is in the path; the routing at the gateway sends each version to the appropriate backend. The old version continues to be served until the sunset.

The alternative — header versioning — was considered and rejected: it is invisible in logs, easy to forget, and hard to test. URL versioning is visible everywhere (Volume 3, Question 2).

The rapid evolution problem

A rapidly evolving product adds features weekly. If every feature requires a version bump, the API accumulates versions at an unsustainable rate. The solution: most changes are additive.

The additive changes happen within /v1/; the client follows the tolerant reader pattern (unknown fields are ignored; unknown enum values are handled). The breaking changes trigger a new version.

In practice, a rapidly evolving product has a version bump every 12–18 months — not every week. The additive changes are the norm; the breaking changes are the exception that requires coordination.

The clients need a path from v1 to v2. The support:

  • Migration guide — every change, with the before/after, the code samples, the behaviour changes.
  • Compatibility shim — for the most common patterns, the v1 → v2 mapping in the SDK; the client upgrades the SDK, the code works.
  • Testing tools — a test mode where the API serves both v1 and v2 shapes, so the client can compare.
  • Support — the dedicated channel for the migration questions; the office hours.
  • Tracking — the usage of v1 by client, so the team knows who has not migrated.

The enforcement — CI

A breaking change in a PR fails the build. The fix: the change goes in a new version (the URL prefix changes), and the old version is untouched. The CI prevents the accidental breaking change.

The tolerant reader pattern

The additive changes require the clients to tolerate unknown fields and enum values. The API documents this requirement prominently; the SDKs implement it; the tests verify it. A client that fails on an unknown field will break on every additive change — the client's bug, but the API's problem.

The sunset enforcement

When v1 is sunset, the API returns 410 Gone for every v1 endpoint. The response includes a link to the migration guide. The removal is intentional and visible, not a silent 404.

The "never version" alternative

Some APIs — Stripe is the famous example — never bump the version; instead, each API key is pinned to a version (a date), and the API serves the shape the key was created with. The old shapes are supported indefinitely (or for a very long time). The advantage: the client never has to migrate (the version is pinned); the API team maintains every shape. The cost: the API team carries the legacy code forever. This works for a stable API with a small surface; for a rapidly evolving API, it is too much overhead.

The pragmatic choice: URL versioning with a long support window (12–18 months). The client migrates on a known schedule; the API team supports a finite set of versions. The maintenance is bounded.

The Pitfall to Avoid

Bumping the version for every change. The API accumulates versions; the clients are constantly migrating; the API team spends all its time on maintenance. The fix: additive changes within the version (which is most changes); the version bump is reserved for the genuine breaking changes. A rapidly evolving product still has a version bump every 12–18 months, not every week.

Multi-tenancy

The organisation is the tenant. Every request is scoped to an organisation:

  • Tenant in the token — the JWT includes the org_id; the client cannot supply a different org.
  • Per-request check — the user is a member of the org (a membership lookup, cached per request).
  • Row-level filter — every query includes WHERE org_id = ?; the composite index on (org_id, ...) makes the filter efficient.
  • RLS (optional) — for the highest isolation, row-level security in PostgreSQL enforces the filter at the database layer; the application cannot forget it.

The cross-tenant leak is the worst bug — the tests verify that user A of org X cannot see the data of user B of org Y.

Authorization

Two levels:

The database design

  • PostgreSQL — the primary; strong consistency; the transactional writes.
  • Shared schema with org_id — every table has the tenant column; the composite indexes start with org_id.
  • Read replicas — for the read-heavy endpoints (project lists, task lists); the replication lag is tolerated for reads.

What the startup intentionally does not build

  • GraphQL — the REST API is sufficient for the frontend; the GraphQL complexity (N+1, complexity limits) is not justified at the startup's scale.
  • gRPC — the internal services speak REST; the gRPC performance is not the bottleneck.
  • Microservices — the startup is a modular monolith; the services are modules within one deployment; the microservices extraction is a future refactor.
  • Real-time — the webhooks handle the integrations; the in-app real-time (WebSocket) is a future feature.
  • Multi-region — the startup is single-region; the multi-region is a scaling concern, not a startup concern.

Each is a "not yet" — the startup's scale does not require the complexity. The design is future-proof (the abstractions allow the additions) but not over-engineered.

The Trade-off

A startup's API is the product's foundation — it must be good enough to support the current clients, but not so over-engineered that it delays the launch. The modular monolith with a well-designed REST API is the right balance. The microservices, the GraphQL, the multi-region — each is a future investment, not a startup requirement. The design is future-proof without being complex.
