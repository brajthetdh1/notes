Part A — Compatibility What breaks, what doesn't, and why it is rarely obvious

1

What is a breaking change vs a non-breaking change?

Short Answer

A breaking change is any change that can cause an existing, correctly-written client to fail or to misinterpret data. A non-breaking change is one that a tolerant client can survive without modification. The critical insight is that "breaking" is defined by the client's tolerance, not by the server's intent — and the same change can be breaking for one client and non-breaking for another.

The definitive list

ChangeBreaking?Why
Adding a new endpointNoExisting clients do not call it
Adding an optional request fieldNoExisting clients omit it; server applies default
Adding a required request fieldYesExisting clients omit it; validation fails
Adding a response fieldNo — if clients are tolerantStrict clients may reject unknown fields
Removing a response fieldYesClients read it; now it is undefined
Renaming a fieldYesEquivalent to remove + add
Changing a field's typeYes42 → "42" breaks parsers
Narrowing a type (string → enum)YesExisting values may be rejected
Widening a type (int32 → int64)Usually noClients can parse the larger value — but not always
Adding a new enum valueConditionalSafe if clients handle unknown values
Removing an enum valueYesClients may still send it
Tightening validation (max length reduced)YesPreviously valid requests now fail
Loosening validationNoPreviously rejected requests now succeed
Changing a default valueYesClients that omit the field see different behaviour
Changing a status code (200 → 201)Usually yesClients may switch on the code
Changing error formatYesClients parse error bodies
Changing URL structureYesClients hardcode URLs
Removing an endpointYesObvious
Changing authentication schemeYesExisting tokens become invalid

Why "adding a response field" is conditional

In JSON, most parsers ignore fields they do not recognise — so adding a field is non-breaking in practice for most clients. But not all:

  • Strict deserialisers. Some typed languages (Java with certain Jackson configurations, Go with DisallowUnknownFields, Rust with deny_unknown_fields) fail on unknown fields. If a client was built strictly, adding a field breaks it.
  • Schema validators. A client that validates the response against a JSON Schema with additionalProperties: false will reject any new field.
  • Database schemas. A client that inserts the response directly into a table with a fixed schema will fail on the new column.
  • Contract tests. A client with a strict contract test that asserts the exact response shape will fail — though this is a test failure, not a runtime failure.

The practical rule: adding a field is non-breaking if you have documented the tolerant reader pattern and your clients follow it. If you have not, assume it breaks some clients and communicate accordingly.

Why changing a default is breaking

Defaults are invisible contracts. If a field has a default of 10, and a client omits it, the client expects 10. Change the default to 20 and the client silently gets different behaviour — no error, just wrong results. This is the most insidious class of breaking change because it is silent. The mitigation is to treat defaults as part of the contract and version them like any other field.

Semantic breaking changes

The hardest class: the schema does not change but the meaning does. Examples:

  • A price field that used to be in cents and is now in dollars — same type, different semantics.
  • A status field whose meaning shifts (formerly "active" meant "logged in"; now it means "not deleted").
  • A field that used to be nullable that is now always set — clients that handled null may not handle non-null correctly.
  • Response timing: a field that was eventually consistent becomes strongly consistent (or vice versa).

These are the changes that no schema validator catches. The only defence is a written contract that specifies semantics, and a design review process that asks "does this change what the field means?"

The compatibility taxonomy

TypeMeaningWho is affected
Backward compatibleNew server works with old clientsNo one — the standard goal
Forward compatibleOld server works with new clientsRarely required, but valuable for rolling deployments
Full compatibleBoth directions workThe gold standard — requires tolerant readers on both sides

Most APIs aim for backward compatibility: new versions of the server work with existing clients. Forward compatibility — old servers working with new clients — matters during rolling deployments, where a new client may reach an old server. Tolerant readers on both sides are what make this possible.

Common Pitfall

Assuming that "adding a field is safe". It is safe only if every consumer ignores unknown fields. In a polyglot ecosystem with at least one strict deserialiser, it is a breaking change that will surface as a production incident. Document the tolerant reader requirement explicitly, and test for it.

What are the versioning strategies, and what are their trade-offs?

Short Answer

Four strategies: URL versioning (/v1/users) — the most common and most visible. Header versioning (API-Version: 1) — clean URLs but hidden from view. Media-type versioning (Accept: application/vnd.api+json;version=1) — the most RESTful but the least usable. Query-parameter versioning (/users?version=1) — easy but pollutes the resource identity. Each trades visibility for cleanliness in a different way.

StrategyExampleProsCons
URL /v1/users Visible, bookmarkable, easy to route at the gateway, simple to cache, obvious in logs Pollutes the URL with a non-resource concept; changing versions changes URLs (breaks bookmarks unless old is kept); ugly for purists
Header API-Version: 1 Clean URLs; version is orthogonal to identity Invisible in a browser; hard to test with curl; easy to forget; proxies and CDNs may not vary on custom headers correctly
Media type Accept: application/vnd.api+json;version=1 Theoretically purest — the representation is versioned, not the URL; supports content negotiation Painful in practice — verbose, awkward in tooling, rarely used, confuses developers
Query parameter /users?version=1 Easy to add; no routing changes Mixes version with resource identity; caching may vary incorrectly; not standard

URL versioning — the pragmatic default

Despite the purity arguments, URL versioning is what most public APIs use — Stripe, GitHub, Twilio, Slack all version in the URL (or via a header, but the URL is dominant). The reasons:

  • It is visible everywhere. In logs, in browser history, in the dev tools, in a support ticket. The version is not hidden state.
  • It routes trivially. An API gateway can send /v1/* to one service cluster and /v2/* to another. No header parsing, no content negotiation logic.
  • It caches correctly. /v1/users and /v2/users are distinct URLs, so CDN caching works without custom Vary headers.
  • It is easy for clients. Change the base URL and everything works.
  • It is honest. A version change is a big deal, and the URL makes it look like a big deal.

The purity objection — that a version is not a resource — is real but academic. The usability advantage dominates in practice.

Header versioning — when URLs must stay pristine

Some APIs adopt header versioning so that the URL is stable and semantic. This is useful when URLs are meaningful identifiers (HATEOAS links, or URLs that appear in permanent documents). The cost is that the version is invisible — a curl command in a bug report does not show which version was used, and developers forget to send the header. If you use header versioning, make it required and fail loudly when it is missing (rather than defaulting silently).

Media-type versioning — the purist's choice

Media-type versioning is technically the most RESTful: the representation's format is negotiated via Accept, so the resource identity (the URL) is stable. This is how the original REST papers imagined evolution working. In practice, it is painful: Accept headers are opaque, tooling support is poor, and developers struggle to remember the syntax. Almost no one uses it for new APIs.

Query-parameter versioning — the quick hack

Adding ?version=1 is the easiest to implement and the worst to design. It muddles the URL's meaning — is /users?version=1 a different resource from /users?version=2 or the same resource with a different format? Caching can vary incorrectly. It is generally a sign that the API was not designed for versioning and is being retrofitted.

Semantic versioning vs API versioning

API versions are typically simple integers (v1, v2), not semver (2.4.1). This is because API versions mark breaking changes, and there is no useful meaning to "minor" and "patch" in a server API — non-breaking changes do not require a version bump. Some APIs use date-based versions (2024-01-15) to allow clients to pin to a behaviour, which is more granular but harder to reason about. Stripe famously uses date-based versions with pinned behaviour per API key.

The version-everything anti-pattern

Some teams bump the version on every change, producing /v47/users. This is a symptom of not distinguishing breaking from non-breaking changes. Version bumps should be rare — the whole point of designing for compatibility is that most changes do not require a new version. If you are bumping versions weekly, the real problem is that the API is not stable, not that the versioning scheme is wrong.

Interview Framing

Say: "I'll use URL versioning — it's visible in logs, routes trivially at the gateway, and caches correctly. I'll only bump the major version for breaking changes, so most evolution happens without a new version." That demonstrates you understand the trade-off and the discipline it requires.

How do you deprecate an API gracefully?

Short Answer

Deprecation is a multi-month process, not an email. The steps: announce well in advance, mark the API as deprecated in the response (Deprecation and Sunset headers), instrument usage per client so you know who is affected, migrate clients with tooling and support, and only then remove. Removing without this process is how companies lose customers.

The RFC 8594 Sunset header

The standard mechanism for announcing deprecation is HTTP headers, defined in RFC 8594:

HeaderPurposeExample
DeprecationMarks the resource as deprecated (RFC 9745)Deprecation: @1743465600
SunsetThe date after which the resource will stop workingSunset: Wed, 01 Apr 2026 00:00:00 GMT
LinkPoints to a migration guideLink: <https://docs.example.com/migrate-v2>; rel="deprecation"
WarningOptional human-readable warningWarning: 299 - "Deprecated, use /v2/users"

These headers are machine-readable — an automated client can detect them and alert its maintainers. They are also visible in dev tools and logs, which means a developer investigating "why is this slow?" sees "this is deprecated" without needing to check the docs.

The five-phase deprecation process

  1. Announce. Publish the deprecation in the changelog, docs, developer newsletter, and any direct communication channel per client. Give a date.
  2. Mark. Add the headers. Update the docs to mark the endpoint as deprecated. Add a prominent warning banner on the reference page.
  3. Instrument. Track usage per API key, per client version, per endpoint. Build a dashboard showing "who is still using /v1/users?" — you cannot migrate clients you cannot identify.
  4. Migrate. Provide migration tooling (a compatibility shim, a code generator, a side-by-side test harness). Contact the top users directly with engineering support.
  5. Remove. Only when usage is below a threshold (ideally zero), and after the announced date. Return 410 Gone — not 404 — so clients know it was removed intentionally.

The instrumentation problem

The hardest part of deprecation is not the announcement — it is knowing who is affected. A consumer that authenticates with an API key is identifiable; one that uses the API anonymously is not. This is a design argument for requiring authentication even on "public" APIs: it gives you a channel to communicate deprecation and a way to measure impact.

The instrumentation should track: number of requests per client per deprecated endpoint, distinct API keys using it, and the trend over time. If usage is not declining, the deprecation will not succeed, and the scheduled date should be moved.

The migration guide

A deprecation without a migration guide is an ultimatum. The guide should include:

  • The diff. What changed, with before/after code samples for each affected endpoint.
  • The mapping table. Every old field → new field, every old endpoint → new endpoint.
  • The behaviour changes. Semantic differences that no schema diff captures.
  • A test plan. How to verify that a migrated client behaves the same way.
  • A timeline. The announced sunset date and the schedule for reminders.

Timelines, by audience

AudienceTypical windowWhy
Internal services1–4 weeksYou control the deployment; one PR per consumer
Partner APIs3–6 monthsCoordinated release cycles, integration testing
Public APIs12–24 monthsUnknown clients, long-lived integrations, SDK versioning lag
Enterprise contractsPer contractOften specify a support window — the contract wins

What not to do

  • Removing without warning. This is the fastest way to lose enterprise customers, and occasionally to face legal action if a contract specified a support window.
  • Deprecating everything at once. If every endpoint in v1 is deprecated on the same day, clients cannot stagger their migration. Deprecate one path at a time.
  • Silently changing behaviour. A "deprecation" that quietly changes the response before the sunset date is worse than an abrupt removal — clients cannot tell whether their integration broke because of the change or their own code.
  • Setting an unrealistic date. A 30-day sunset for a public API breaks every enterprise customer who integrated in good faith. The date must be achievable by the slowest consumer, not the fastest.
  • Not following through. A deprecation with a date that passes with no removal trains clients to ignore all future deprecations.
Common Pitfall

Deprecating in the documentation but not in the response headers. Developers do not read docs — they read logs and dev tools. The Sunset header is the only way a developer investigating a slow or failing request discovers the deprecation without reading a changelog they did not know existed.

How do you add a required field to an existing API?

Short Answer

You cannot add a required field directly — existing clients do not send it, and validation will break them. The correct process is the expand-contract migration: add the field as optional with a server-side default, migrate clients to send it, then tighten validation. This takes weeks or months, but it is the only way to add a required field without an outage.

The four-phase process

  1. Expand — add as optional. Deploy the server accepting the field as optional. If the client omits it, the server applies a default. Document the field, add it to the request schema, and log when it is absent.
  2. Migrate — get clients to send it. Update SDKs, announce the change, provide a code sample. Monitor the percentage of requests that include it. This is where the time goes.
  3. Tighten — require it. Once all known clients send it (or the remaining usage is below a threshold), change the server to reject requests without it. This is the breaking change, and it requires the previous phases to have completed.
  4. Contract — clean up. Remove the default-handling code, update the docs to say the field is required, and remove any "optional" compatibility shims.

The "default is a contract" problem

During phase 1, the server needs a default. But the default is now part of the contract — a client that omits the field gets the default, and that behaviour must not change until the field is made required. This is a subtle trap: a developer sees an unused default and "cleans it up" by changing the value, silently changing behaviour for every client that has not migrated yet. The mitigation is to mark the default as part of the compatibility shim, with a comment and a test.

What about a required field on a new endpoint?

New endpoints have no existing clients, so the field can be required from day one. This is why adding a new endpoint is a non-breaking change, and why new endpoints are the easiest place to add requirements. The expand-contract dance is only necessary for changes to existing endpoints.

Response fields — the easier case

Adding a required response field is easier because the server controls it entirely. A new field in a response is backward-compatible as long as clients tolerate unknown fields (the tolerant reader pattern, Question 6). The caveat is that if a client has a strict schema validator or a strict deserialiser, adding a field can break it — which is an argument for documenting tolerant-reader expectations and for making clients tolerant from the start.

The alternative: a new endpoint

If the migration is too disruptive, the alternative is a new endpoint that requires the field, with the old endpoint frozen. POST /v2/orders requires customer_id, while POST /v1/orders still accepts it as optional. This duplicates endpoint logic but avoids the migration. It is the right choice when the field is fundamental (the resource is meaningless without it) and the existing clients cannot be migrated.

Adding a required field to a request in GraphQL

GraphQL makes this harder, because a non-null argument is enforced at the schema level — a query that omits it fails validation before reaching the resolver. The expand-contract approach works, but it requires the schema to declare the argument as nullable, and the resolver to enforce its presence, until all clients have migrated. Then the schema can be tightened. This is awkward but doable, and it demonstrates why GraphQL versioning is subtle (Question 8).

Adding a required field in gRPC

Protobuf has no concept of a required field (since proto3). Every field has a default value (0, "", false), and the server cannot distinguish "client sent 0" from "client omitted the field". This means gRPC does not really support required fields — the server must validate explicitly. For adding a field, the pattern is to add it with a default, validate that it is non-zero, and treat zero as absent. This is a known limitation of proto3 and a reason some teams use proto2 (which has required) or validation annotations (buf validate).

Trade-off

The expand-contract migration is slow and requires coordination, but it is the only safe way to add a required field to an existing API. A new endpoint is faster but duplicates logic. The choice depends on how fundamental the field is — if the resource cannot exist without it, a new endpoint may be cleaner; if it is an additional constraint, expand-contract is the standard.

How do you remove or rename a field safely?

Short Answer

Removing and renaming are both breaking changes, so both require deprecation. The pattern is the same as for adding a required field, but in reverse: stop documenting the field, mark it as deprecated in the response, monitor which clients still read it, and only remove it after a deprecation window. Renaming is remove + add, done in two phases so clients have time to switch.

Removing a field — the phased approach

  1. Announce. Document the field as deprecated, add the Deprecation and Sunset headers to responses that include it, and notify known consumers.
  2. Monitor. Track which clients read the field — hard unless the client is instrumented, but you can at least track which clients receive responses containing it and correlate with their activity. Some APIs provide a "field access log" in developer portals for this purpose.
  3. Stop populating (optional). Some teams transition through a phase where the field is present but always null. This forces clients that read it to notice the change before removal, and it makes the deprecation visible in dev tools.
  4. Remove. After the deprecation window, stop returning the field. Clients that read it will get undefined or null and may fail — which is why monitoring and communication matter.

Renaming a field — remove + add

Renaming is not a single operation; it is remove + add, and it must be done in two phases:

PhaseResponse containsClient behaviour
1 — Add new nameBoth old_name and new_nameClients can migrate at their pace
2 — Deprecate old nameBoth, old marked deprecatedClients see the deprecation signal
3 — Remove old nameOnly new_nameAny client still reading old fails

The two-field phase is the key. A client that reads old_name continues to work, a client that reads new_name also works, and both can coexist. During this window, the server has the cost of returning both (a small bandwidth cost) and the obligation to keep them in sync. Once every known client has migrated, the old field is removed and the response shrinks.

What about request fields?

Renaming a request field is harder because the server cannot tell whether a client meant the old or the new name. The pattern:

  • Accept both for a transition period. Document old_name as deprecated, but keep accepting it. If both are sent, prefer the new one or return 400 — document the policy.
  • Announce and monitor. Log requests that use the old name. Notify clients still using it.
  • Reject the old name after the sunset date. Return 400 with a clear message pointing at the new name.

The "silently ignore" anti-pattern

A common mistake: when a client sends a field the server no longer recognises, silently ignore it. This seems friendly, but it is harmful — the client thinks its request succeeded with the field set, but it was dropped. The client then reads the resource back and sees the old value, leading to a confusing "why did my update not stick?" bug. The correct behaviour is to reject unknown fields in requests with a 400 and a message that names the offending field. This is strict, but honest.

For responses, the equivalent is the opposite: clients must ignore unknown fields (tolerant reader). The asymmetry is deliberate — servers should be strict about what they accept and liberal about what they send (Postel's law), and clients should be liberal about what they receive.

Removing a field from a strict client's schema

If a client validates responses against a schema with additionalProperties: false, removing a field is a breaking change regardless of how long the deprecation window was. The client's validator will fail because the field it expects is missing. There is no server-side fix for this — the client must be updated. This is why documenting the tolerant reader requirement is critical, and why adding additionalProperties: false to a client is usually a mistake.

Removing entire endpoints or versions

The same process applies at the endpoint level: deprecate the endpoint, add the Sunset header, monitor usage, and return 410 Gone after the sunset date. For entire versions, the process is identical but the stakes are higher — a version deprecation affects every endpoint in that version, so the communication and migration support must be correspondingly thorough.

Common Pitfall

Removing a field and returning the same response shape with a null value. A client that expects a string will crash on null. If a field is deprecated but not yet removed, either keep populating it or return it as null only if the client has been told to expect null. Silently changing the type to null is worse than removing the field, because it looks like the field is still there.

6

What is the tolerant reader pattern?

Short Answer

The tolerant reader pattern says: a client must ignore fields it does not recognise, and must handle missing optional fields and unknown enum values gracefully. It is the client-side discipline that makes non-breaking changes actually non-breaking. Without tolerant readers, every addition is a breaking change, and the only safe evolution is to add a version.

Why it matters

The server's ability to evolve depends entirely on the client's tolerance. If every client breaks when a field is added, the server can never add a field without a version bump. If every client handles unknown values, the server can evolve continuously, and versions only happen for genuine breaking changes.

This is the mechanism by which large APIs (Stripe, GitHub) evolve without versioning everything. Their clients are tolerant — their SDKs, their clients, and their documentation all state that unknown fields must be ignored. Stripe's API has been evolving since 2011 with only a handful of version bumps, because every change is designed to be additive and tolerated.

What tolerance requires

  • Ignore unknown fields in responses. When a client deserialises a response, it must discard fields it does not recognise, not fail. This is the default in most JSON parsers, but strict deserialisers (DisallowUnknownFields in Go, FAIL_ON_UNKNOWN_PROPERTIES in Jackson, deny_unknown_fields in Rust's serde) must be turned off.
  • Handle missing optional fields. A field that was present may be absent — the client must handle undefined or a missing key without crashing. This is especially important when the server stops populating a deprecated field.
  • Handle unknown enum values. An enum that had [active, inactive] may now have [active, inactive, pending]. A client that switches on the value must handle pending gracefully — typically by treating it as "unknown" rather than crashing.
  • Handle new response types. A polymorphic response may now return a variant the client does not recognise. The client must handle it gracefully, not crash.
  • Handle new status codes. A server may return a status code the client did not expect (e.g., 429 for rate limiting, 409 for conflict). The client should handle unexpected 4xx codes by logging and failing gracefully, not by crashing.

The documentation obligation

The tolerant reader pattern only works if clients know to be tolerant. This means every API must document, prominently, that:

  • Clients must ignore unknown fields.
  • Clients must handle unknown enum values.
  • Clients must handle missing optional fields.
  • Clients must handle unexpected status codes.

This documentation should be in the getting-started guide, not buried in a footnote — clients that read it on day one are the ones that will not break when the API evolves.

The server's obligation

The server must honour its side of the bargain:

  • Never repurpose a field. A field named status that used to mean one thing must not mean something else. If the semantics change, add a new field.
  • Never change a field's type. int → string is a breaking change even if the client is tolerant, because the client's type system will reject it.
  • Never remove a field without deprecation. Tolerant readers can handle absence only if they expected it — which is what the deprecation window is for.
  • Never add a required field to an existing endpoint. Tolerant readers cannot handle a required field they do not know about.

The Postel's Law framing

The tolerant reader pattern is the client-side of Postel's Law (the robustness principle): "be conservative in what you send, be liberal in what you accept". Servers should be conservative in what they send (well-typed, well-documented, no experimental fields leaked), and clients should be liberal in what they accept (ignore unknown, handle missing). This asymmetry is what allows evolution.

The anti-pattern: strict clients

A strict client that validates responses against a fixed schema is a client that will break on every server change. The most common culprits are typed language clients using strict deserialisers, JSON Schema validators with additionalProperties: false, and hand-written parsers that assume a fixed structure. These are all fixable — but they require the client team to understand the tolerant reader requirement and to have configured their tooling accordingly. The API team's job is to make that requirement impossible to miss.

Interview Framing

Say: "I'll document the tolerant reader requirement in the getting-started guide — clients must ignore unknown fields and handle unknown enum values. That lets the API evolve additively without a version bump for every change." That shows you understand the client-side discipline and why it matters.

How do you handle enum evolution?

Short Answer

Enums grow, and clients must tolerate values they do not recognise. The rules: adding a value is usually safe if clients handle unknown values; removing a value is breaking; renaming a value is remove + add. Document the enum as open (can grow) rather than closed (fixed set), and design clients to fall back to an "unknown" case.

The three cases

ChangeBreaking?Why
Add a valueUsually noA tolerant client treats it as unknown; a strict client crashes
Remove a valueYesA client may still send it, and the server will reject it
Rename a valueYesEquivalent to remove + add; any persisted client data breaks
Change the meaning of a valueYes — and silentNo schema change, but behaviour changes
Change from string to integerYesType change
Add a new enum fieldNoNew field, existing clients ignore it

Why adding a value is only "usually" safe

A client that switches on the enum without a default case will crash on an unknown value. This is surprisingly common — switch (status) { case "active": ...; case "inactive": ...; } with no default. When the server adds "pending", the client either crashes or, worse, silently falls through to whatever the language does by default (which might be nothing, or might be the first case).

The fix is on the client side: every enum handling must have a default/unknown case. This is the tolerant reader pattern applied to enums (Question 6). The server's job is to document that enums are open, so clients know to handle unknown values.

The closed vs open enum distinction

TypeMeaningClient behaviourExample
Closed enum The set of values is fixed and will never grow Safe to exhaustively switch; unknown value is a bug ISO 3166 country codes, ISO 4217 currency codes
Open enum The set may grow in future Must handle unknown values gracefully Order status, payment state, job state

Most enums in a domain API are open — statuses, states, types that will gain new values as the product evolves. Standards-body enums (country codes, currencies, MIME types) are effectively closed. Document which is which, because it changes how clients should be written.

The fallback pattern

The client's enum handling should look like:

LanguagePattern
TypeScriptdefault: handleUnknown(status)
JavaA custom @JsonCreator that maps unknown to UNKNOWN
PythonAn Enum with a _missing_ class method
GoAn Unknown constant plus a switch with a default
RustAn #[serde(other)] variant

In every case, the client's model has an UNKNOWN variant that it can reason about. The client can then display "unknown status" or treat it as an opaque value, rather than crashing or silently mis-handling it.

Enum evolution in persisted data

If the client persists the enum value (in a cache, a local database, a URL), the persisted data may contain a value that a newer server no longer recognises. This is the mirror image of the problem — the server must handle receiving an old value. The mitigations:

  • Never remove an enum value from the server's accepted set, even if it is no longer produced. Keep accepting it, map it to a legacy state, or return a 410.
  • Migrate persisted data when values are removed — a background job that rewrites old values to their successors.
  • Use a lookup table instead of a hardcoded enum, so the set can grow without a schema change.

Enums vs strings vs lookup tables

An alternative to enums is to use a string with a documented set of valid values, or a lookup table with a foreign key. Both allow adding values without a schema change:

  • Enums — validated at parse time, self-documenting, but every change requires a code deploy on both sides.
  • Strings with a documented set — flexible, but no compile-time check.
  • Lookup tables — the set is data, not schema, so it can grow without a deploy. The API returns the value as a string, and clients look it up if they need labels.

For rapidly evolving value sets (feature flags, tags, categories), a lookup table is the right answer. For stable, finite sets (order status with 5 values), an enum is fine — and the tolerant reader pattern handles the rare additions.

Common Pitfall

Using a language's built-in enum type for an open enum. TypeScript string unions, Rust enum, Java enum, and Python Enum all fail on unknown values by default. They are the right tool for closed enums, the wrong tool for open ones. Use a string-typed field with an UNKNOWN fallback instead.

8

How do you version GraphQL and gRPC APIs?

Short Answer

GraphQL prefers continuous evolution over versioning: add fields and types, never remove them, mark deprecated with @deprecated, and let the schema grow. gRPC uses .proto field numbers for compatibility: add fields with new numbers, never reuse or change a number, and mark fields reserved when removing them. Neither style uses URL-style versioning; both rely on the schema's own mechanisms.

GraphQL versioning

GraphQL has no built-in versioning mechanism, and the community consensus is that it should not have one. Instead, the schema evolves continuously:

  • Add new fields and types. Clients that do not query them are unaffected.
  • Mark deprecated fields with @deprecated(reason: "..."). The field still works, but tools (GraphiQL, Apollo Studio) show it as deprecated, and a deprecation is a signal for clients to migrate.
  • Never remove a field — or only after a long deprecation period and confirmation that no client queries it. The schema can be instrumented to track field usage per client, which is the GraphQL-specific version of "instrument before removing".
  • Never change a field's type — that is a breaking change. If a type must change, add a new field with the new type, deprecate the old one, and migrate.
  • Adding a required argument is breaking — clients that do not supply it will fail validation. Use a nullable argument with server-side default, then tighten.

The advantage is that clients query only what they need, so adding fields to a type does not increase the payload for clients that do not query them. This means GraphQL can evolve additively more aggressively than REST — a new field on the User type costs nothing to clients that do not request it.

The risk is that the schema can grow unboundedly, with dozens of deprecated fields accumulating. The mitigation is field usage instrumentation: Apollo Studio, for example, tracks which fields are actually queried, so you know when a deprecated field is truly unused and can be removed.

gRPC versioning

Protocol Buffers have a well-defined compatibility model based on field numbers:

ChangeBreaking?Why
Add a field with a new numberNoOld clients ignore unknown fields
Change a field's numberYesThe wire format depends on the number
Change a field's typeYes (usually)Wire encoding differs; int32 ↔ int64 is the exception
Remove a fieldUsually no — but reserve the numberOld clients may still send it; the field is silently ignored
Reuse a field numberYes — catastrophicOld data is misinterpreted as the new field
Rename a fieldNoThe wire uses numbers, not names
Change a field from optional to repeatedYesWire format differs
Add a new serviceNoExisting clients do not call it
Remove a serviceYesExisting clients call it

The critical rule: never reuse a field number. When a field is removed, its number is reserved, so a future developer cannot accidentally reuse it:

SyntaxPurpose
reserved 3, 5, 7;Reserve specific numbers
reserved 9 to 11;Reserve a range
reserved "old_field_name";Reserve a name (less critical, but good hygiene)

Renaming a field is safe in the wire format (numbers are what matter), but it breaks generated code — the client's field name changes. In practice, treat renames as breaking for the codegen layer even though the wire is compatible.

The gRPC versioning question

Should you version a gRPC service (users.v1.UsersService → users.v2.UsersService)? Two schools:

  • Version the package. users.v1 and users.v2 coexist as separate packages, each with its own service. This is the Google convention and allows a clean break when the schema needs a major change.
  • Evolve in place. Keep one version, add fields with new numbers, reserve removed ones. This is the protobuf-native approach and works for most changes.

The pragmatic answer: version the package only for genuine breaking changes that cannot be expressed additively. Most changes can be additive, and a new package for every change fragments the codebase.

The difference from REST

Both GraphQL and gRPC avoid URL versioning because they have schema-level mechanisms for compatibility. A REST API without a schema (JSON with no enforced types) has no such mechanism, which is why URL versioning is the pragmatic default there. This is a genuine advantage of schema-first styles: the schema is the versioning mechanism, and compatibility is checked by tooling (buf breaking for protobuf, schema diffing for GraphQL) rather than by convention.

Interview Framing

Say: "For GraphQL I'll evolve the schema additively — add fields, deprecate old ones with @deprecated, and instrument field usage so I know when removal is safe. For gRPC I'll add fields with new numbers and reserve removed ones. Neither needs URL versioning; the schema is the versioning mechanism." That demonstrates you understand both ecosystems.

What is contract testing, and how do Pact and Schemathesis work?

Short Answer

Contract testing verifies that a provider (server) and a consumer (client) agree on the API contract, without requiring them to be running together. Consumer-driven contract testing (Pact) has each consumer publish its expectations, and the provider verifies it satisfies them. Provider-side testing (Schemathesis, Dredd) generates requests from the contract and verifies the responses match. Both catch breaking changes in CI, before they reach production.

The problem contract testing solves

Traditional integration testing requires both services to be deployed together, which is impractical in a microservices architecture where dozens of services deploy independently. Unit tests do not catch contract violations — a unit test of the server's serialiser does not check that the client can parse the output. End-to-end tests are slow, flaky, and cover only a few paths.

Contract testing sits between unit and integration: it verifies the agreement without running the full stack. The consumer's expectations are encoded as a contract, and the provider verifies it satisfies that contract — either by running against the contract (consumer-driven) or by validating its responses against the schema (provider-side).

Pact — consumer-driven contract testing

Pact inverts the usual relationship: the consumer defines what it expects, and the provider verifies it. The flow:

  1. Consumer test. The consumer's test suite runs against a Pact mock server. Each time the consumer calls the mock, Pact records the request and the expected response — these are the interactions.
  2. Pact file. The recorded interactions are written to a JSON pact file — the contract.
  3. Pact broker. The pact file is published to a broker (PactFlow or a self-hosted one), with a version tag.
  4. Provider verification. The provider runs its own tests, replaying each interaction against its real implementation and checking that the response matches the expected response.
  5. Can-I-deploy. Before deploying either side, a CI check queries the broker: "has this version of the provider passed verification against all pacts for this version of the consumer?" If not, the deploy is blocked.

The advantage is that the contract is consumer-driven — it captures exactly what consumers need, not what the provider happens to expose. The provider cannot accidentally remove a field that a consumer uses, because the provider's verification would fail.

The disadvantage is that the contract is only as complete as the consumer's tests — if a consumer does not test a field, the contract does not cover it. This is manageable with good consumer test discipline, but it is a real limitation.

Schemathesis — provider-side, schema-based testing

Schemathesis takes a different approach: it takes the OpenAPI (or GraphQL) schema and generates requests from it, then validates that the provider's responses match the schema. It is property-based testing for APIs:

  • Generates requests from the schema — every endpoint, every parameter, every body shape, with valid and invalid values.
  • Sends them to the running server.
  • Validates the response against the schema — status codes, headers, body shape.
  • Reports any request that produces a response the schema does not allow.

Schemathesis catches a different class of bug than Pact: it finds cases where the server's actual behaviour diverges from its documented schema. Pact catches cases where the server's behaviour breaks a specific consumer's expectation. They are complementary.

The two approaches compared

AspectPact (consumer-driven)Schemathesis (provider-side)
Source of truthConsumer testsOpenAPI / GraphQL schema
CatchesBreaking changes for specific consumersSchema violations in the implementation
RequiresBoth consumer and provider test suitesOnly the provider
Catches over-fetchingYes — the contract names the fieldsOnly if the schema says
Catches under-fetchingYes — the consumer expects fieldsOnly if the schema says
Catches unknown fieldsNot typicallyYes, if schema forbids additional properties
Setup costHigh — broker, both sidesLow — schema and a running server
Best forMicroservices with a known consumer setPublic APIs, single-team APIs

The CI integration

The value of contract testing comes from the CI enforcement, not from the test itself. The pattern:

  1. Consumer tests run on every PR; if a consumer's expectation changes, the new pact is published.
  2. Provider tests run on every PR; if the provider breaks a pact, the build fails.
  3. Before deploy, a "can I deploy?" check queries the broker; if the pact is not verified, deploy is blocked.
  4. The schema is validated (Spectral, Schemathesis) on every provider build; a schema violation fails the build.

This is what makes "non-breaking changes" enforceable rather than aspirational. Without it, every change is a bet that no one is relying on the field you are removing.

The limitation

Contract testing verifies the format, not the semantics. A contract test cannot tell you that price changed from cents to dollars, because both are integers. It cannot tell you that a status code now means something different. Those are semantic changes, and they require human review and documentation. Contract testing catches the mechanical breaking changes; semantic ones still need a design review process.

Common Pitfall

Publishing the pact from a test that does not actually call the fields the consumer uses. The contract is only as complete as the consumer's test, so a consumer that queries a subset of fields in tests but all of them in production has a false sense of safety. Consumer tests must exercise every field the consumer actually reads.

How long should you support an old API version, and how do you communicate the lifecycle?

Short Answer

There is no universal answer, but there are defensible defaults: internal APIs 1–4 weeks, partner APIs 3–6 months, public APIs 12–24 months. The number should be driven by how long the slowest consumer takes to migrate, not how long the API team wants. The lifecycle should be published as a policy, with clear dates and multiple reminders, and the removal should be enforced with 410 Gone rather than silently turning off.

The support window as a function of the audience

AudienceTypical windowDriven by
Internal services (same org, same deployment pipeline)1–4 weeksOne PR per consumer; the API team controls the schedule
Internal services (different org, coordinated)1–3 monthsQuarterly planning cycles
Partner APIs (named organisations, under contract)3–6 monthsPartner's release cadence; contract terms
Public APIs (unknown consumers)12–24 monthsUnknown client lifecycles, SDK versioning lag, enterprise integration cycles
Enterprise contract APIsPer contractThe contract wins — read it before announcing a sunset date

The "nobody uses it" trap

The most common mistake is to believe that a deprecated endpoint is unused because the API team does not know of any users. In reality, long-tail usage is the norm: a single internal service, a partner's integration built three years ago, a script someone runs quarterly, a mobile app version that still has 2% of users. The only reliable way to know is instrumentation — track usage per API key, per endpoint, per version, and look at the trend, not the point-in-time.

The rule: do not remove a version until the usage graph is flat at zero, or until you have contacted every consumer you can identify and confirmed they have migrated. "We haven't heard from anyone" is not a plan.

The communication calendar

A deprecation is a campaign, not a notice. A defensible schedule for a public API:

WhenWhatChannel
T−12 monthsInitial announcement; sunset date publishedChangelog, developer newsletter, docs banner, direct email to known consumers
T−9 monthsReminder; migration guide publishedSame channels, plus a status page notice
T−6 monthsResponses start carrying Deprecation and Sunset headersIn-band — every client sees it
T−3 monthsFinal reminder; top consumers contacted directlyEmail, support tickets, account manager
T−1 monthLast call; support is escalatedEmail, status page, developer newsletter
TRemoval; responses return 410 GoneChangelog, status page
T+forever410 Gone with a link to the migration guideIn-band

Why 410 Gone, not 404

Returning 404 Not Found for a removed endpoint is misleading — the client cannot tell whether the URL was never valid or was removed. 410 Gone is explicit: "this resource existed and is gone". The response should include a Link header pointing at the migration guide, so a developer hitting the error in production can find the fix without searching.

The published lifecycle policy

Every public API should have a written lifecycle policy that states:

  • How long each version is supported after a successor is announced.
  • How deprecation is communicated (channels, cadence).
  • What counts as a breaking change (so a version bump is predictable).
  • How long old versions remain available after the sunset date (usually zero — but some APIs keep a read-only mode for a grace period).
  • What the support policy is for enterprise customers with contractual exceptions.

Publishing this policy is not just good hygiene — it is a signal of maturity. Developers choose APIs that they can rely on for years, and a stated policy is evidence that the API will not be pulled out from under them.

The internal API lifecycle

Internal APIs have a different calculus. The consumers are known, the deployment is coordinated, and the support window can be short. But the mistake of using "internal" as an excuse to break things without notice is common and costly — the internal consumers are often teams that did not know the API was being changed, and their production breaks. The internal API should have the same discipline, scaled down: a deprecation announcement to the consuming teams, a migration guide, a week or two of support, then removal.

The "never remove anything" alternative

Some APIs (notably internal ones) adopt the policy of never removing anything — every old endpoint stays alive forever, so no consumer ever breaks. This is tempting but has costs: the codebase accumulates dead endpoints, the security surface grows, and every new developer must understand the legacy. The pragmatic middle ground is to never remove a version that has active usage, but to aggressively deprecate endpoints with zero usage. This keeps the surface from growing unboundedly without breaking anyone.

Trade-off

A long support window protects consumers but imposes a maintenance burden (bug fixes, security patches, monitoring) on the API team. A short window reduces the burden but risks breaking consumers. The right balance depends on the audience and the contract — public APIs must err on the side of the consumer, internal APIs can err on the side of the team. Either way, publish the policy so consumers know what to expect.
