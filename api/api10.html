Part A — HTTP Caching The protocol's built-in performance mechanism, and why most APIs misuse it

1

How does HTTP caching actually work? Explain the mental model.

Short Answer

HTTP caching is a contract between the server and any intermediary — browser, CDN, proxy — about how long a response may be reused and under what conditions. The server declares cacheability via headers (Cache-Control, ETag, Last-Modified); the cache decides whether to serve a stored response, validate it with the server, or fetch fresh. Done right, it eliminates round trips and dramatically reduces load; done wrong, it serves stale data or leaks information between users.

The three participants

ParticipantRole
Origin serverProduces responses and declares their cacheability via headers
CacheStores responses and decides whether to serve them, validate them, or fetch fresh
ClientIssues requests; may itself be a cache (browser)

The lifecycle of a cached response

  1. Fresh — the response is within its max-age. The cache serves it directly, no request to the origin. Zero latency for the client.
  2. Stale — the response has exceeded its max-age. The cache has three options:
    • Validate — send a conditional request to the origin with If-None-Match (ETag) or If-Modified-Since. If the origin returns 304 Not Modified, the cache refreshes the freshness and serves the stored response. If 200, the cache replaces the stored response.
    • Serve stale — if the origin is unreachable and stale-if-error is set, the cache serves the stale copy anyway. Better than a 500.
    • Fetch fresh — if the origin allows it, the cache can revalidate unconditionally.
  3. Evicted — the cache removes the response due to size pressure or expiry.

The two kinds of cache

TypeLocationGoverned byNotes
Private cache Browser Cache-Control: private Specific to one user; can store authenticated responses
Shared cache CDN, reverse proxy, load balancer Cache-Control: public or s-maxage Shared across users; must NOT store per-user responses

The distinction is critical: a response with Cache-Control: private is stored only in the browser. A CDN will refuse to store it — because storing it would serve one user's data to another. A response with public can be stored anywhere, but the server must guarantee that it is safe for all users.

The "it is cacheable by default" rule

HTTP is opt-out, not opt-in. A response is cacheable by default unless it says otherwise. The rule:

Response includesCacheable?
Authorization header (request)No — private responses are not cached by shared caches
Cache-Control: no-storeNo — never stored anywhere
Cache-Control: privateYes — but only in private caches (browser)
Cache-Control: public, max-age=60Yes — anywhere, for 60 seconds
No cache headers, but a status of 200Yes, but heuristically — caches may apply a small default

The heuristic case is the source of many bugs: a response without cache headers may still be cached by a browser or CDN, with a heuristic freshness (often 10% of the time since Last-Modified). To avoid this, always set explicit headers — either a real TTL or no-store.

The mistake most APIs make

Most APIs do not set cache headers at all. This means:

  • Browsers apply heuristic caching — the response is cached for some interval, and updates are not seen until the cache expires.
  • CDNs refuse to cache — because there is no explicit public declaration for per-user endpoints, the CDN either does not cache (default) or applies an unsafe heuristic.
  • Proxies have no guidance — corporate proxies, mobile carriers' transparent caches, and other intermediaries cache based on defaults that the server did not choose.

The fix is to set cache headers explicitly on every response — either a real cache policy for cacheable endpoints, or Cache-Control: no-store for anything that must not be cached. Silence is not the safe option; it delegates the decision to someone else's heuristic.

The performance impact

A cache hit is roughly:

  • Zero network latency — no round trip to the origin.
  • Zero server load — the origin does not see the request.
  • Zero database queries — the response is the stored bytes.

For a public API serving millions of requests to a stable resource, a well-configured CDN can absorb 95%+ of the traffic. The remaining 5% is the origin's load — a 20× reduction with no code change and no extra infrastructure. This is why HTTP caching is the single highest-leverage performance mechanism available, and why most APIs underuse it.

Interview Framing

Say: "HTTP is opt-out, not opt-in — responses are cacheable by default unless I say otherwise. I'll set explicit Cache-Control on every response: public with a TTL for static content, no-store for per-user endpoints. Silence is the bug." That demonstrates the mental model and the discipline in one sentence.

What do the Cache-Control directives mean, and when do you use each?

Short Answer

Cache-Control is the primary caching directive. The key ones: max-age (TTL for private caches), s-maxage (TTL for shared caches like CDNs), no-store (never cache), no-cache (must revalidate before use), private (only private caches), public (any cache), stale-while-revalidate (serve stale while refreshing in the background), stale-if-error (serve stale on origin failure).

DirectiveMeaningWhen to use
max-age=N Response is fresh for N seconds in any cache (unless overridden by s-maxage) Default TTL for publicly cacheable content
s-maxage=N Overrides max-age for shared caches (CDN, proxy) CDN TTL when you want it different from browser TTL
no-store Never store the response anywhere (browser, CDN, proxy) Per-user sensitive data, tokens, private data
no-cache Store, but revalidate with the origin before each use Content that changes often and must be fresh but is expensive to regenerate
private Only private caches (browser) may store; CDNs must not Per-user data that the browser can cache but the CDN must not
public Any cache may store Static content, public API data
must-revalidate Once stale, must validate before serving; do not serve stale Security-sensitive data
immutable Never revalidate, even on user reload Versioned assets (JS bundles with hashes in filename)
stale-while-revalidate=N Serve stale for up to N seconds while refreshing in background Acceptable-staleness content — feeds, recommendations
stale-if-error=N Serve stale if the origin returns 5xx for up to N seconds Resilience — serving stale is better than an error

max-age vs s-maxage — why both

A response often needs different TTLs for different caches:

  • Browser (private) — should cache briefly, because the user might expect fresh data on reload.
  • CDN (shared) — should cache longer, because the origin load reduction is more valuable than a few seconds of freshness.
HeaderBrowser TTLCDN TTL
Cache-Control: max-age=300300s300s
Cache-Control: max-age=60, s-maxage=360060s3600s

The second form is common for public API data: the CDN caches for an hour, but the user's browser revalidates every minute. The origin sees one request per hour per CDN edge, not one per minute per user.

no-store vs no-cache — the most confused pair

DirectiveStored?Revalidated?Use for
no-store Never N/A — no copy to revalidate Passwords, tokens, per-user sensitive data
no-cache Yes Every time, before use Expensive-to-generate content that must be fresh

The name no-cache is misleading — it means "no unvalidated cache use", not "do not cache". A response with no-cache is stored but must be revalidated with the origin on every use. A response with no-store is not stored at all.

For anything that must never be cached — banking data, personal information, authentication tokens — use no-store. For data that changes but is expensive — a computed report — use no-cache with an ETag, so the browser can send a conditional request.

stale-while-revalidate — the resilience directive

This directive (RFC 5861) says: after the response becomes stale, the cache may serve the stale response for up to N seconds while revalidating in the background. The user sees an instant response (the stale one); the next request after the revalidation completes sees the fresh one.

HeaderBehaviour
Cache-Control: max-age=60, stale-while-revalidate=600Fresh for 60s; stale for up to 600s more, with background refresh

This is enormously useful for feeds, recommendations, and any content where a few seconds of staleness is acceptable in exchange for zero latency. The CDN serves the stale response instantly, and the origin regenerates in the background for the next request.

stale-if-error — the availability directive

When the origin returns 5xx or is unreachable, the cache may serve the stale response for up to N seconds. This turns an origin outage into a degraded experience (stale data) rather than a failed one (error page). For a public API, this is often the right trade-off — a user sees yesterday's recommendations rather than an error.

The complete policy for an API

Endpoint typeCache-Control
Static assets (versioned JS, CSS, images)public, max-age=31536000, immutable
Public API data (catalog, public profile)public, max-age=60, s-maxage=300, stale-while-revalidate=600
Authenticated API data (user's orders)private, max-age=0, must-revalidate
Sensitive data (banking, tokens)no-store
Error responsesno-store (do not cache 4xx/5xx)
Common Pitfall

Caching a response with Set-Cookie in a shared cache. The cookie is served to the next user, which is a session-hijacking vulnerability. Any response with Set-Cookie must be private (or no-store). Most CDNs strip Set-Cookie when caching publicly, but the origin should not rely on that — the header should be correct.

Interview Framing

Say: "Static assets get max-age=1year, immutable. Public API data gets max-age=60, s-maxage=300, stale-while-revalidate=600. Authenticated data gets private, no-cache. Sensitive data gets no-store. The directive depends on the freshness requirement and the audience." That covers the policy in one sentence.

What are ETags and Last-Modified, and how do conditional requests work?

Short Answer

An ETag is an opaque version identifier for a response; a Last-Modified is the timestamp of the last change. The client sends them back in conditional requests (If-None-Match, If-Modified-Since) to ask "has this changed?". If not, the server returns 304 Not Modified with no body — saving bandwidth and generation cost. Conditional requests are also the mechanism for optimistic concurrency (Volume 5, Question 8).

The two validators

ValidatorWhat it isProsCons
ETag An opaque identifier — usually a hash or a version number Precise — detects any change, even if the timestamp did not move Must be generated; expensive if hashing the whole body
Last-Modified The timestamp of the last modification Cheap — one column read Second-level granularity — two changes in the same second look identical

ETag is more precise and preferred. Last-Modified is cheaper and useful as a fallback when ETag is expensive to compute. Both can be present; the client will prefer ETag if both are given.

The conditional request flow

StepClientServer
1. Initial GETGET /users/42200 OK with ETag: "v42" and body
2. CacheStores the response and the ETag—
3. RevalidationGET /users/42 with If-None-Match: "v42"—
4a. UnchangedSees 304 Not Modified; uses cached bodyCompares ETag; matches; returns 304 with no body
4b. ChangedSees 200 OK with new body and new ETagETag differs; returns the new response

The key insight: a 304 response has no body. The client uses its cached copy, but the bandwidth and CPU of regenerating the response are saved. For a large response (a 1 MB JSON, an image), the saving is substantial.

If-None-Match vs If-Match

HeaderSemanticsUse
If-None-MatchOnly return 200 if the ETag is differentCaching (return 304 if unchanged)
If-MatchOnly return 200 if the ETag matchesOptimistic concurrency (prevent lost updates)
If-Modified-SinceOnly return 200 if modified after the given dateCaching, using Last-Modified
If-Unmodified-SinceOnly return 200 if not modified since the dateWeaker form of If-Match

The two families are opposite in intent: None-Match asks "has it changed?"; Match asks "is it still what I think it is?". Caching uses the first; concurrency control uses the second. Confusing them is a common source of bugs — using If-None-Match for an update will succeed only if the resource changed, which is the opposite of what an update wants.

How to generate an ETag

ApproachProsConsBest for
Content hash (SHA-256 of body)Precise; detects any byte changeExpensive for large bodiesSmall responses, exact correctness
Version column (a monotonically increasing integer)Cheap; deterministicRequires a column; changes on every writeDatabase-backed resources
Last-updated timestampCheapSecond-level granularity; clock skewSlow-changing resources
Composite (version + schema version)Detects schema and data changesMore complexAPIs with evolving schemas

The version column is the most practical for high-volume APIs. It is cheap to generate, it is deterministic (the same version produces the same ETag), and it works correctly with concurrent updates (the version increments on each write, so an old ETag is always "stale").

Strong vs weak ETags

TypeSyntaxMeaningUse
Strong ETag: "v42" Byte-for-byte identical Caching and optimistic concurrency
Weak ETag: W/"v42" Semantically equivalent, but possibly byte-different Caching only — must not be used for If-Match (concurrency)

The weak form is useful when the response can vary byte-wise but is semantically the same — a JSON response with fields reordered, a gzip-compressed response that decompresses to the same body. The W/ prefix warns caches that the bytes may differ, so a client using it for concurrency would get wrong results.

304 and the headers that must be repeated

Even though a 304 has no body, it must repeat the headers that the cache needs:

  • ETag — the same ETag (or a new one, if the ETag changed but the content is semantically the same).
  • Cache-Control — the freshness policy (so the cache knows how long to extend).
  • Vary — the cache key components (Question 4).
  • Date — the current time.

Forgetting these means the cache does not know how to update its freshness, and revalidates again immediately — turning the 304 into a wasted round trip.

The performance impact

A 304 response is typically 200–500 bytes (headers only). A full response of 100 KB is 200× larger. The origin still processes the request (checks the ETag) but does not serialise the body. The bandwidth savings dominate for large responses; the generation savings dominate for expensive-to-compute responses.

Interview Framing

Say: "ETag is the version — the client sends If-None-Match, the server returns 304 if unchanged. That saves the body on every cached-but-revalidated response. For optimistic concurrency, If-Match uses the same ETag the opposite way: only apply the write if the version has not changed." That covers caching and concurrency in one sentence.

How does CDN caching work, and how do you design cache keys?

Short Answer

A CDN is a globally distributed set of caching proxies. When a client requests a URL, the nearest edge checks its cache: if fresh, serve; if not, fetch from the origin (or a mid-tier shield), store, and serve. The cache key determines what counts as "the same request" — usually the URL, optionally extended with specific headers or query parameters. Designing the cache key correctly is the difference between a 95% hit rate and a 5% one, or between correct isolation and a data leak.

The CDN request flow

StepWhat happens
1. DNS / anycastThe client's DNS resolves the hostname to the nearest CDN edge (anycast or GeoDNS)
2. Edge lookupThe edge checks its cache using the cache key
3a. HitServes the cached response — latency is a few milliseconds
3b. MissForwards to the mid-tier shield or the origin, stores the response, serves it
4. OriginReceives one request per cache miss, not per client — the load reduction comes from here
5. RevalidationOn expiry, the edge sends a conditional request; origin returns 304 if unchanged

Cache keys

The cache key determines which requests share a stored response. The default key is the URL — scheme, host, path, and query string. Additional components can be included:

ComponentInclude?Reason
PathAlwaysDifferent resources
Query stringUsually?page=2 and ?page=3 are different
HostUsuallyapi.example.com vs admin.example.com
Accept-EncodingYes, by default in most CDNsgzip vs brotli vs identity
Accept-LanguageOnly if the response varies by languageLocalised content
AuthorizationNever as a key, but presence affects cacheabilityPer-user — should not be shared
CookieRarely; only for specific cookiesUsually per-user
Vary header componentsAs declared by the originOrigin's explicit instruction

The Vary header

Vary tells the CDN which request headers are part of the cache key. A response with Vary: Accept-Language is cached separately per language — so a French user does not get the English cached copy.

The classic failure: caching a response that varies by Authorization without including it in the cache key. The first user's response is served to every subsequent user — a data leak. The fix: either Vary: Authorization (which fragments the cache into one entry per user — impractical) or, better, Cache-Control: private on authenticated responses (which tells the CDN not to store them).

The rule: if the response varies by user, do not cache it in a shared cache. Do not try to include user identity in the cache key — the cardinality is too high, and the risk of a mistake is a data leak.

Origin shielding

Without shielding, hundreds of edge locations may each miss the same object and hit the origin — hundreds of requests for the same resource. Shielding inserts a mid-tier cache between the edges and the origin:

Without shieldWith shield
Each edge miss → originEach edge miss → shield; shield miss → origin
Hundreds of origin requests per objectAt most a few — one per shield region
Cache stampede on cold startShield coalesces concurrent misses

The shield also provides request collapsing — if 100 edges miss simultaneously, the shield sends one request to the origin and serves the response to all 100. This is the CDN's answer to the thundering-herd problem.

The cache key design process

  1. List the dimensions the response varies on — language, device, currency, user segment.
  2. Decide which dimensions are worth including — each one multiplies the cache size and reduces the hit rate.
  3. Include the minimum set — the smaller the cache key, the higher the hit rate.
  4. Use the Vary header for standard header-based variation; use custom CDN config for more complex cases.
  5. Test the leak scenario — a request as user A, then as user B; if B sees A's data, the cache key is wrong.

The cache key in practice

EndpointCache keyVary
Static JSURL (with hash in filename)Accept-Encoding
Product catalogue (all users)URL + query stringAccept-Language, Accept-Encoding
User's orders (per-user)Not cached (private)—
Search resultsURL + queryOptional
Homepage for logged-in userSplit: public shell (URL), user fragment (per-user, no CDN)—

The "cache the shell, not the content" pattern

For a page that is mostly the same for all users but has a personalised fragment (a "Hello, Alice" header, a cart icon count), cache the shell and fetch the personalised fragment separately. The CDN caches the shell (high hit rate, safe); the personalised fragment is a separate API call, not cached. This gives the CDN's benefit for most of the page, while keeping the user data safe.

Common Pitfall

Setting Vary: User-Agent. User agents are thousands of distinct strings, each with sub-versions and feature flags. The cache fragments into thousands of entries, most with a single request each — the hit rate collapses. If the response varies by device type, map the user agent to a small set of device classes (mobile, tablet, desktop) and include only that in the key.

Interview Framing

Say: "The cache key is the URL plus the dimensions the response varies on — usually Accept-Language and Accept-Encoding. Per-user data is not cached in the CDN at all; it uses private. The shell is cached; the personalised fragment is fetched separately." That covers the design and the safety in one sentence.

How do you invalidate a cache safely?

Short Answer

There are four invalidation strategies, each with a different trade-off: TTL (wait for expiry — simple, but stale until then), explicit purge (delete the cache entry — fast, but propagation is asynchronous and global purges are slow), versioned URLs (change the URL when content changes — instant and safe), cache tagging (purge all entries sharing a tag). The right strategy depends on how much staleness is acceptable.

StrategySpeedReliabilityBest for
TTL expiry Slow — up to the TTL Deterministic Content where bounded staleness is acceptable (catalogue, feeds)
Explicit purge Seconds to minutes — asynchronous Best-effort; may miss edges Breaking news, product updates
Versioned URLs Instant Deterministic Static assets, anything that can change its URL
Cache tags Seconds Best-effort Content with related items (a product and its reviews)

TTL expiry

The simplest strategy: set a TTL that is shorter than the acceptable staleness window, and let the cache expire naturally. A response with max-age=60 is guaranteed fresh for 60 seconds and may be stale for a few more; after that, the next request revalidates or fetches fresh.

The TTL is a decision about staleness tolerance, not about invalidation. A catalogue with hourly updates can use max-age=3600; the users see the version from up to an hour ago, which is fine for the domain. A stock price with second-level updates needs max-age=1 or no-cache — HTTP caching cannot keep up with that, and the design should use a different mechanism (WebSocket, SSE, or polling with no-store).

Explicit purge

A CDN API call tells the CDN to delete a specific URL (or URLs matching a pattern) from its caches. Cloudflare, Fastly, Akamai, and AWS CloudFront all support this.

TypeScopeSpeed
Single URL purgeOne specific URLSeconds
Tag/wildcard purgeAll URLs matching a patternSeconds to minutes
Full purgeEverythingMinutes — expensive, rarely needed

The critical caveat: purge is asynchronous and best-effort. The CDN accepts the request, but propagation across hundreds of edges takes time. A user in Tokyo might still see the stale version for a few seconds after the purge is issued. For a breaking-news event or a mispriced product, this latency is unacceptable — which is why the highest-stakes content uses versioned URLs.

Versioned URLs

The safest invalidation: if the content changes, the URL changes. A static asset /static/app.a3f2c1.js becomes /static/app.b8e4d2.js on rebuild. The old URL can be cached forever (immutable), because its content never changes; the new URL is a cache miss, fetching the fresh content.

For APIs, the equivalent is a version in the URL (/v2/products) or a version in the resource's identifier (/products?version=abc). The benefit is that invalidation is instantaneous — the new URL was never cached, so it is a guaranteed miss.

The cost: every content change creates a new URL, which means bookmarks break, shared links change, and search engines re-index. Versioned URLs are ideal for assets (where clients always fetch the latest from an HTML page), not for user-facing resources.

Cache tags

Modern CDNs support tagging responses with one or more tags, and purging all responses with a given tag. This is useful when one content change affects many URLs:

ContentTag
Product page /products/42product-42, category-shoes
Product reviews /products/42/reviewsproduct-42
Home page featuring product 42featured-products

When product 42 is updated, purge product-42 — all related URLs are invalidated. When the featured-products list changes, purge featured-products — the home page re-renders. This is the granularity that explicit URL purges cannot provide.

The CDN must support tags (Cloudflare, Fastly, Akamai, and CloudFront all do, with different names — "cache tags", "surrogate keys", "purge keys"). The origin sets a Cache-Tag header (or equivalent); the purge API accepts a tag.

The safe invalidation pattern

For content that must be fresh immediately:

  1. Version the URL — the new content has a new URL; the old content is still cached but no longer served.
  2. Update the reference — the HTML, the API response, or the redirect points to the new URL.
  3. Purge the reference — the reference itself (the HTML page, the catalogue index) is purged so the new URL is served.
  4. Let the old URL expire — no purge needed; nobody requests it.

This combines the safety of versioned URLs with the reach of a targeted purge. It is the pattern used by every major site for asset deployment and content updates.

The "I purged and it is still stale" bug

Common causes:

  • Purge is asynchronous — the CDN accepted the request, but not all edges have processed it. Wait or check the purge status.
  • Multiple cache layers — the browser, the CDN, and the origin's own cache may all hold a copy. Purging the CDN does not clear the browser.
  • Cache key mismatch — the purge used a different key than the cache stored. The URL normalisation (trailing slash, query order) may differ.
  • Vary headers — if the response varies by language, purging the URL may only purge one language's entry. Check the variant handling.
Trade-off

Shorter TTLs reduce staleness but increase origin load. Purging gives instant invalidation but is asynchronous and best-effort. Versioned URLs are instant and safe but only apply to assets. The right mix depends on the content: assets use versioned URLs, catalogue data uses TTL + purge, and per-user data is not cached at all.

Interview Framing

Say: "Assets use versioned URLs, immutable. Catalogue data uses TTL with an explicit purge on update. The purge is asynchronous, so for anything that must be instant — a mispriced product — the design should version the URL instead." That demonstrates the four strategies and their trade-offs.

Compare gzip, brotli, and zstd for API compression — when do you use each?

Short Answer

gzip is the universal default — supported everywhere, ~70% compression on JSON, fast. brotli compresses better (~20% smaller than gzip) and is supported by all modern browsers, but is slower to compress at max levels. zstd is the fastest at comparable compression, with a wide range of levels, but browser support is still limited. Use gzip for maximum compatibility, brotli for web content, and zstd for service-to-service where both sides control the client.

AlgorithmCompression ratio (JSON)SpeedBrowser supportBest for
gzip Baseline (~70% reduction) Fast Universal Everything — the safe default
brotli ~20% better than gzip Slower at high levels; a fast level (4) is competitive All modern browsers (via HTTPS) Web content — HTML, JS, CSS, JSON
zstd ~10–20% better than gzip; comparable to brotli Fastest at comparable ratios; excellent high levels Limited (Chrome supports it via custom, not universal) Service-to-service; internal APIs

Why compression matters for APIs

A 100 KB JSON response compresses to ~20 KB with gzip — a 5× reduction. On a mobile network at 5 Mbps, the transfer time drops from ~160 ms to ~32 ms. The savings are even larger on slower connections: a 100 KB response on a 1 Mbps link takes 800 ms uncompressed, 160 ms compressed. Compression is the single biggest transport-level win for text-heavy APIs.

Binary formats (protobuf, Avro, MessagePack) compress less well than JSON, because they are already compact. For protobuf, compression gives ~30% reduction; for JSON, ~70%. The choice of format and the choice of compression are somewhat substitutes: if you use protobuf, you need compression less; if you use JSON, you need it more.

How negotiation works

The client sends Accept-Encoding: gzip, br, zstd; the server picks the best one it supports and sets Content-Encoding in the response. If the client sends nothing, the server may send uncompressed — but for compatibility, most APIs default to gzip if the client accepts anything.

ClientServer
Accept-Encoding: gzipContent-Encoding: gzip
Accept-Encoding: gzip, brContent-Encoding: br (prefers brotli)
Accept-Encoding: identityNo compression
(no header)No compression, or gzip (server's choice)

When NOT to compress

ContentCompress?Why
Small responses (< 1 KB)NoCompression overhead exceeds the savings; a gzip header alone is ~20 bytes
Already-compressed content (JPEG, PNG, ZIP, MP4)NoCompressing compressed data produces larger output
Real-time streams (small messages)Usually no, unless batchingPer-message overhead dominates
Sensitive data over TLSYes, but beware BREACHCompression + encryption can leak secrets (see below)

The BREACH attack

Compressing a response that mixes secret data (a CSRF token, a session cookie) with user-controlled input (a search query, a form field) can leak the secret. The attacker sends many requests with guessed prefixes of the secret; the compressed size reveals which guess was correct, byte by byte. This is the BREACH attack (CVE-2013-3587), and it affects HTTP compression of any page that reflects user input alongside a secret.

The mitigations: do not reflect user input in the same response as secrets, use Cache-Control: no-store on sensitive responses, use per-response random padding, or disable compression for sensitive endpoints. For pure API endpoints (JSON responses with no HTML), BREACH is mostly theoretical — but for anything that returns a page mixing a token with a user-controlled value, it is real.

brotli4Fast, good ratioDynamic responses
brotli11Slowest, best ratioStatic assets, pre-compressed
zstd3Fast, good ratioReal-time
zstd19Slow, best ratioArchival, offline

For dynamic API responses, use a fast level (gzip 6, brotli 4, zstd 3). The bottleneck is CPU, not bandwidth, and a fast level captures most of the ratio. For static assets, pre-compress at a high level (brotli 11) once and serve the compressed bytes — the CPU cost is paid once, not per request.

Pre-compression for static assets

Static assets (JS, CSS, HTML) should be pre-compressed at build time at a high level, stored alongside the original, and served based on Accept-Encoding. The server does not compress on the fly — it serves the pre-compressed file directly. The compression level is the highest available (brotli 11, gzip 9), because it is paid once at build time and reused for every request.

Common Pitfall

Compressing already-compressed content (JPEG, PNG, MP4, ZIP). The output is larger than the input, because the compressor tries to find patterns in random bytes and fails. Check the Content-Type and skip compression for image/*, video/*, audio/*, and application/zip.

Interview Framing

Say: "gzip is the universal default; brotli for web content where it saves 20% more; zstd for service-to-service. Do not compress small responses or already-compressed data. And beware BREACH — compressing a response that mixes secrets with user input leaks the secret." That covers the algorithms, the rules, and the security concern.

Why does connection reuse matter, and how do you design connection pooling?

Short Answer

Establishing a new TCP connection takes one round trip (SYN/SYN-ACK) plus, for HTTPS, several more (TLS handshake). Reusing an existing connection eliminates those round trips — saving 100+ ms per request on high-latency networks. Connection pooling is the mechanism: a pool of warm connections reused across requests, sized to match the concurrency, with health checks and timeouts.

The cost of a new connection

StepRound tripsNotes
DNS lookup1Cached for a TTL, but the first lookup is a round trip
TCP handshake1SYN / SYN-ACK / ACK
TLS 1.2 handshake2ClientHello/ServerHello, then key exchange
TLS 1.3 handshake1 (or 0 with resumption)The improvement over TLS 1.2
HTTP request/response1The actual work

For HTTPS over TLS 1.3 on a 100 ms RTT link, a new connection costs ~200 ms (TCP + TLS + request). A reused connection costs ~100 ms (just the request). That is a 2× speedup, and the difference dominates for small API responses where the payload is only a few kilobytes.

HTTP keep-alive

HTTP/1.1 has persistent connections by default: a Connection: keep-alive header (implicit in 1.1) means the connection stays open for subsequent requests. The client reuses it for the next request to the same host, eliminating the handshake cost.

The server should send Keep-Alive: timeout=N, max=M to tell the client how long the connection will be held open and how many requests it will serve. A timeout shorter than the client's idle timeout causes the client to try to reuse a closed connection — a race that produces confusing errors. The server's keep-alive timeout must be longer than the client's, or the client must handle reconnect gracefully.

Connection pooling

A connection pool maintains a set of pre-established connections and reuses them across requests. The pool is the client-side equivalent of keep-alive — it is how an application with many concurrent requests reuses a small number of connections.

ParameterMeaningTypical value
Max connections per hostUpper bound on concurrent connections10–50 for internal APIs; 2–6 for external hosts (browser default)
Max total connectionsAcross all hosts100–500, depending on capacity
Idle timeoutHow long a connection sits idle before being closed30s to 5 min
Max lifetimeMaximum age of a connection before it is recycled5–30 min (to handle DNS changes, deployment)
Connect timeoutHow long to wait for the TCP handshake1–5 s
Request timeoutHow long to wait for the response10–60 s, depending on the operation

The pool sizing problem

A common mistake: sizing the pool too large. A pool of 100 connections per instance sounds generous, but with 20 instances, that is 2,000 connections to the upstream — which may have a limit of 500. The pool must be sized with the downstream's capacity in mind, not just the client's concurrency.

Upstream limitClient instancesMax pool per instance
500 connections2025 (500 / 20)
1000 connections5020
Unbounded (e.g., a public API)—Limited by the client's concurrency and thread pool

An oversized pool is also a resource leak on the client — file descriptors, memory for socket buffers, and TCP connection state. The pool should be sized to the actual concurrent request load, not to the maximum possible.

Connection pooling for databases

The database connection is the most expensive connection. A PostgreSQL connection has significant memory (a few MB) and startup cost (parsing the schema, setting up the session). A pool of 10–20 per application instance is standard; a pool of 100 is usually wrong (the database cannot handle 100 concurrent active queries efficiently — the CPU is the bottleneck, not the connection).

The pool should be sized based on: the database's max_connections (typically 100–500), the number of application instances, and the average query duration. The formula: pool_size × instances ≤ 80% of max_connections.

Connection reuse in HTTP/2

HTTP/2 changes the pool calculus. A single HTTP/2 connection can carry many concurrent streams — no need for a pool of connections, one connection multiplexes them. This is why modern HTTP clients (gRPC, HTTP/2-enabled load balancers) often use a much smaller pool: one or two connections per host, each with many concurrent streams.

The benefit: fewer TCP connections means fewer handshakes, less state, less resource usage. The trade-off: a single connection is a single point of failure — if it dies, all in-flight streams fail. The right design uses a small pool (2–4 connections per host) and retries on connection failure.

Common Pitfall

Not configuring a connection pool at all — using a new connection per request. This is the default in many HTTP libraries, and it adds a handshake (and often a TLS negotiation) to every call. For a chatty API (dozens of calls per request), the handshake cost dwarfs the actual work. Always configure a pool or use a keep-alive client.

Interview Framing

Say: "Every new connection is a TCP handshake plus a TLS handshake — 100+ ms of overhead on a high-latency link. Connection pooling reuses warm connections, sized to the downstream's capacity, not the client's concurrency. HTTP/2 reduces the need for a large pool because one connection multiplexes." That covers the cost and the design in one sentence.

What does HTTP/2 change, what is head-of-line blocking, and what does HTTP/3 fix?

Short Answer

HTTP/1.1 suffers from head-of-line (HOL) blocking at the HTTP level — one slow response blocks all subsequent requests on the same connection. HTTP/2 fixes this with multiplexing — many concurrent streams on one TCP connection. But TCP itself has HOL blocking — a lost packet blocks all streams on that connection. HTTP/3 runs over QUIC (UDP-based), where each stream is independent — no HOL blocking at the transport level.

VersionTransportHOL blockingMultiplexingKey feature
HTTP/1.1 TCP Yes — at the HTTP level No (or via pipelining, abandoned) Keep-alive
HTTP/2 TCP Yes — at the TCP level Yes — many streams per connection Multiplexing, header compression
HTTP/3 QUIC (UDP) No Yes — independent streams 0-RTT, connection migration

HTTP/1.1 and head-of-line blocking

On a single HTTP/1.1 connection, only one request is in flight at a time. The next request cannot be sent until the previous response is complete. If the first response is slow (a slow database query, a large payload), every subsequent request waits — even if they would be fast.

The workarounds:

  • Multiple connections — browsers open 6 connections per host, allowing 6 concurrent requests. Beyond that, requests queue.
  • Domain sharding — serve assets from multiple subdomains (static1.example.com, static2.example.com), each with 6 connections. This multiplies concurrency but adds DNS lookups and complexity.
  • Bundling and spriting — combine assets into fewer requests. This works, but makes cache invalidation coarse (one change invalidates the whole bundle).

HTTP/2 multiplexing

HTTP/2 introduces streams: many requests can be in flight on one connection, and their responses can be interleaved. A slow request does not block the others — the streams share the connection bandwidth but are not serialised.

Other HTTP/2 features:

  • Header compression (HPACK) — headers are compressed with a shared table, reducing overhead. This matters because APIs often have large headers (Authorization, cookies).
  • Server push — the server can send resources the client did not request (usually an asset the client will need). This is deprecated in HTTP/2 (browsers did not use it well).
  • Stream prioritisation — the client can indicate which streams matter most. In practice, prioritisation is not widely implemented well.
  • Binary framing — a binary protocol, more efficient than HTTP/1.1's text format.

TCP head-of-line blocking

HTTP/2 multiplexing works at the HTTP layer, but the underlying TCP connection is a single ordered stream of bytes. If a packet is lost, TCP stalls delivery of all subsequent bytes until the lost packet is retransmitted — even if the subsequent bytes belong to a different HTTP/2 stream. All streams stall together.

On a healthy network (low loss), this is rare. On a lossy network (mobile, WiFi at the edge of range, long-distance links), a single lost packet stalls every request. This is the HOL blocking that HTTP/2 cannot solve — because it is in the transport, not the application protocol.

HTTP/3 and QUIC

HTTP/3 replaces TCP with QUIC, a UDP-based protocol that implements reliable, ordered delivery per stream — not per connection. Each HTTP/3 request is a separate QUIC stream; a packet loss on stream A does not stall stream B. This eliminates TCP HOL blocking.

Other QUIC benefits:

  • Faster handshake — QUIC combines transport and TLS handshakes into one round trip (1-RTT), or zero on resumption (0-RTT). TLS 1.3 over TCP requires two round trips on a new connection.
  • Connection migration — a client can change IP addresses (WiFi to cellular) without re-establishing the connection. TCP connections are bound to a 4-tuple; QUIC connections are not.
  • Better loss recovery — QUIC has more sophisticated loss detection and recovery than TCP, particularly for high-latency or lossy networks.

The caveat: QUIC runs over UDP, which some networks block or throttle (corporate firewalls, some ISPs). HTTP/3 clients fall back to HTTP/2 over TCP when QUIC is unavailable, so the benefit is lost on those networks — but the fallback is graceful.

Adoption and recommendations

EnvironmentRecommendation
Modern browsers, CDNHTTP/2 or HTTP/3; the CDN negotiates automatically
Mobile clientsHTTP/3 where supported — the handshake and migration benefits are large
Service-to-serviceHTTP/2 (or gRPC, which uses HTTP/2)
Legacy clientsFall back to HTTP/1.1

For an API, the pragmatic recommendation: support HTTP/2 and HTTP/3 on the edge (CDN, load balancer), HTTP/2 internally (gRPC), and let the protocol negotiation handle the rest. The client gets the best protocol it supports; the server does not have to think about it.

Common Pitfall

Domain sharding for HTTP/2 sites. The HTTP/1.1 technique of spreading assets across many subdomains is actively harmful for HTTP/2 — it defeats multiplexing (each subdomain needs a separate connection) and prevents header compression from being shared. Modern best practice is one connection, all assets on one host.

Interview Framing

Say: "HTTP/1.1 has HOL blocking at the HTTP level; HTTP/2 fixes it with multiplexing. But TCP itself has HOL blocking — one lost packet stalls all streams. HTTP/3 over QUIC fixes that with independent streams. HTTP/2 is the safe default; HTTP/3 is better on lossy mobile networks." That covers the three versions and their distinctions.

What are request coalescing and batching, and when do they matter?

Short Answer

Request coalescing (also called single-flight or request collapsing) means that when multiple clients request the same expensive resource at the same time, the server computes it once and shares the result. Batching means combining multiple small requests into one. Both reduce the total work and the tail latency — coalescing eliminates redundant work; batching reduces per-request overhead.

Request coalescing

The scenario: 100 clients request GET /products/42 in the same second, the cache is empty (the key just expired), and the database query takes 200 ms. Without coalescing, the server executes 100 queries — the thundering herd (Volume 2, Question 1). With coalescing, the first request triggers the query; the next 99 wait for the result and receive the same response.

Without coalescingWith coalescing
100 database queries1 database query
200 ms latency per request, but the database is saturated200 ms for the first, ~200 ms for all (they wait for the result)
The cache is filled 100 timesThe cache is filled once

The implementation: a map of "in-flight requests" keyed by the cache key. The first request inserts a promise; subsequent requests for the same key get the same promise. When the promise resolves, all waiters receive the result and the entry is removed.

Libraries that implement it: singleflight in Go, async-cache-dedupe in Node, the collapse feature in Fastly and Cloudflare's request collapsing (at the CDN level).

Batching

The scenario: a client needs 100 resources, each identified by an ID. Without batching, the client sends 100 requests (or 100 parallel requests, which is still 100 round trips). With batching, the client sends one request with 100 IDs, and the server returns 100 resources in one response.

Without batchingWith batching
100 round trips, 100 latency × 1001 round trip, 1 latency
100 request headers, 100 response overheadsOne set of headers, one response
100 connections from the pool (or 6, with queuing)1 connection

The batching API: POST /batch with an array of requests, or a multi-value parameter (GET /products?ids=1,2,3). The response contains an array of results, in the order of the request, with per-item status (Volume 8, Question 9).

The DataLoader pattern

In GraphQL and other resolver-based systems, the N+1 problem produces one query per item — a list of 100 posts fetches 100 authors separately. DataLoader solves it by batching the author fetches within a single event-loop tick: it collects all the author IDs requested, issues one batched query, and distributes the results. This is request-level batching, automatic — the resolver code does not know it is batched.

The pattern is general: any system where the same logical operation is repeated with different IDs can batch them. DataLoader is the canonical implementation, but the principle applies to any resolver-based architecture.

Batching trade-offs

ProCon
Fewer round trips → lower latencyLarger payloads → higher per-request bandwidth
Fewer connections → less overheadOne slow item delays the whole batch
Server can parallelise the workPartial failure must be handled per item
Simpler client logicBatch size limits; do not batch 10,000 items

The "batch size" question

Every batching API must have a maximum batch size. A client that sends 100,000 items in one batch will exhaust the server's memory or time out. The batch is sized to the server's capacity — typically 100 to 1,000 items — and the client chunks larger requests into multiple batches.

Chunking on the client side: if the client has 10,000 items, it sends 10 batches of 1,000. Each batch is independent (or idempotent, if it must be retried). The client parallelises the batches to reduce total time, but limits parallelism to avoid overwhelming the server.

When coalescing and batching matter

  • High-traffic, cacheable endpoints — coalescing prevents thundering herds on cache misses.
  • List endpoints with related resources — batching prevents N+1 (a list of posts with authors, a list of orders with customers).
  • Chatty clients — mobile apps that need many resources per screen; batching reduces the round trips.
  • Batch jobs and data pipelines — processing a large set of items; batching is the natural pattern.

When they do not matter: single-resource endpoints (one request, no coalescing or batching needed), or when the client's latency is dominated by something else (a slow render, a slow database). Coalescing and batching are optimisations — apply them where the cost is measurable.

The CDN's coalescing

CDNs already implement coalescing: when 1,000 edges miss the same object simultaneously, they send one request to the origin (via the shield) and serve the response to all. This is why origin shielding (Question 4) is important — without it, each edge coalesces independently, and the origin still sees many requests.

Common Pitfall

Implementing coalescing without a timeout. If the first request hangs (a slow database, a stuck dependency), all subsequent requests wait for it — a single slow query stalls the entire key. The coalescing implementation must have a timeout: if the first request does not complete within N seconds, the waiters should fail or retry.

Interview Framing

Say: "Coalescing eliminates duplicate work — 100 requests for the same missing key trigger one query. Batching eliminates round trips — 100 IDs in one request instead of 100 requests. Both reduce load and latency; both need timeouts and size limits." That covers the two patterns and their constraints.

What causes tail latency, and how do you reduce it?

Short Answer

Tail latency (p99, p999) is dominated by a few causes: queuing (requests waiting for a resource), fan-out amplification (many parallel calls where the slowest determines the total), GC pauses, network jitter, contention (locks, connection pool exhaustion), and background tasks (compaction, backups). It is what users actually experience, because the slowest request in a page determines the page load time.

Why tail latency matters

A page load issues 20 backend calls. If the p99 of each call is 500 ms and the p50 is 20 ms, the probability that at least one of the 20 calls is at the p99 is:

CallsProbability at least one is p99
11%
10~10%
20~18%
100~63%

So the page load is dominated by the tail, not the median. This is the fan-out amplification of tail latency — the more calls, the worse the user experience. The same math applies to a single slow query in a database with a queue: the queue depth amplifies the tail.

The causes

CauseMechanismTypical magnitude
QueuingRequests wait for a resource (CPU, thread, connection, lock)Arbitrary — grows with load
Fan-outMany parallel calls; the slowest determines the responseAmplifies other tails
GC pausesStop-the-world GC stalls all requestsTens to hundreds of ms
Network jitterPacket loss, reordering, routing changesMilliseconds to seconds
ContentionLock waits, connection pool exhaustion, database row locksArbitrary
Background tasksCompaction, backups, cron jobs sharing resourcesSeconds to minutes
Cold cachesFirst request after eviction hits the databaseDepends on the query
Thundering herdMany requests hit a missing key simultaneouslySeconds under load

The reduction techniques

  1. Reduce fan-out. Combine sequential calls into one, cache aggressively, use a BFF to aggregate. Every call removed is one less tail to amplify.
  2. Hedged requests. Send the request to two replicas after a delay (say, p95 of the first); take whichever responds first. This cuts the tail dramatically — the p99 becomes the p50 of the fastest of two. The cost: extra load. Used sparingly for critical, idempotent requests.
  3. Timeouts and deadlines. A request that is already over its deadline should be cancelled, not allowed to consume resources. Deadline propagation (the deadline flows through every service call) ensures the whole chain gives up together.
  4. Backpressure and load shedding. When the system is overloaded, reject requests early rather than queueing them (Volume 7, Question 7). A queued request that eventually times out is worse than a rejected one.
  5. Request coalescing (Question 9) — eliminates duplicate work for the same key.
  6. Connection pooling and keep-alive (Question 7) — eliminates handshake latency on every request.
  7. GC tuning — use a low-pause GC (ZGC, Shenandoah, the Go GC), monitor pause times, and ensure heap is sized appropriately. A GC pause that lasts 500 ms stalls every request on that instance.
  8. Isolate background tasks. Compaction, backups, and batch jobs must be rate-limited or run on separate resources. A nightly backup that competes with production traffic causes latency spikes.
  9. Warm caches — pre-load caches at startup, use request coalescing on misses, and avoid evictions during peak traffic.
  10. Monitor the tail, not the mean. Alert on p99 and p999, not just p50. A mean of 20 ms with a p99 of 5 seconds is a bad experience for 1% of users — which is a lot of users at scale.

The "coordinated omission" trap

A subtle measurement problem: if the load generator waits for each response before issuing the next request, it stops generating load when the system is slow — so the slow responses are never measured at the rate they would occur in production. The result is a latency report that looks much better than reality. The fix is open-loop load generation (fixed arrival rate, independent of response time) and measuring latency from the intended send time.

Tail latency at the storage layer

For a database, tail latency comes from: slow queries (unindexed scans, lock waits), compaction (LSM-tree stores like Cassandra, RocksDB), page cache misses, and connection pool exhaustion. The mitigations: query optimization, read replicas, caching, and monitoring the slow query log. The p99 of the database often determines the p99 of the API — the API is only as fast as its slowest query.

The tail tolerance

Not all tails need to be eliminated. A 1% tail of 2 seconds on a background analytics endpoint is acceptable; a 1% tail of 2 seconds on the checkout flow is not. The design should:

  • Define the tail budget per endpoint — what p99 is acceptable?
  • Monitor and alert when the tail exceeds the budget.
  • Prioritise the fixes on the endpoints that matter most.
  • Accept the tails on endpoints where the cost of elimination exceeds the benefit.
Common Pitfall

Optimising the mean latency. A system with a mean of 50 ms and a p99 of 5 seconds is worse than one with a mean of 80 ms and a p99 of 150 ms, for most users — the mean hides the tail. Optimise the tail, measure the tail, alert on the tail.

Interview Framing

Say: "Tail latency is what users feel — the slowest request in a page determines the page load. Reduce fan-out, use hedged requests for critical paths, propagate deadlines, and shed load rather than queue. Monitor p99 and p999, not the mean." That covers the cause, the techniques, and the discipline.
