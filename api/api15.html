Part A — The Three Pillars Metrics, logs, and traces — what each answers, and how they combine

1

What are the three pillars of observability, and what does each answer?

Short Answer

The three pillars are metrics (aggregated numeric measurements over time), logs (discrete timestamped events), and traces (the causal flow of a single request across services). Each answers a different question: metrics answer "is something wrong right now?", logs answer "what exactly happened?", traces answer "where in the flow did it happen?". All three are necessary; none is a substitute for the others.

What each pillar is good at

PillarShapeCostAnswersBad at
Metrics Numeric time series, tagged Cheap — aggregate by tags "What is the error rate right now?" "Is latency above the SLO?" High cardinality; details of individual events
Logs Text/JSON events, timestamped Expensive — storage scales with volume "What error message?" "What request ID?" "What was the input?" Aggregation across many events; slow at high volume
Traces Spans with parent-child links Moderate — one trace per sampled request "Which service in the flow is slow?" "What did this request call?" Full-population aggregation (traces are sampled)

Metrics — the pulse

A metric is a number over time: request count, error count, latency histogram, CPU usage, queue depth. Tags (labels) split the series by dimension: method, status, endpoint, region. The tags are what makes metrics queryable: "error rate for POST /orders in us-east" is a query over the tagged series.

Metrics are the cheapest pillar — the data is aggregated at collection time, so storing a thousand series is cheap. The trade-off: high cardinality (unique values per tag) explodes the cost. A metric tagged with user_id (millions of values) is a cardinality disaster — the metric system stores millions of series and the query engine slows. The discipline: never tag with unbounded dimensions (user ID, request ID, email); use bounded dimensions (endpoint, status, region).

The standard metric types:

  • Counter — monotonically increasing (requests, errors). The rate over a window is the useful signal.
  • Gauge — a value that goes up and down (in-flight requests, queue depth, memory).
  • Histogram — a distribution (latency buckets). The percentile (p50, p95, p99) is the useful signal.
  • Summary — pre-computed percentiles (limited — cannot be aggregated across instances).

Logs — the detail

A log line is a timestamped event: {"timestamp": "...", "level": "ERROR", "service": "orders", "trace_id": "...", "message": "payment declined", "user_id": "u_42"}. Logs are the record of exactly what happened, with the input, the output, and the exception.

The modern best practice is structured logging — every log line is JSON with a consistent schema. This makes logs queryable ("show me all logs for trace_id X") and parseable by downstream systems. The alternative (plain text with printf) is cheap to write and expensive to query.

Logs are expensive at volume. A high-traffic API generates terabytes per day. The strategies:

  • Sampling — log 1% of successful requests, 100% of errors.
  • Retention tiers — hot (7 days, searchable), warm (30 days, queryable), cold (1 year, archive).
  • Truncation — cap the log line size; large payloads are separate.
  • Redaction — never log secrets, tokens, or full PII (Volume 14).

Traces — the story

A trace is the full picture of one request across services: the entry point, each downstream call, each database query, each external API call, with the time spent in each. Each segment is a span with a parent; the trace is a tree. The trace_id ties the whole tree together; the span_id identifies each piece; the parent span_id gives the structure.

Traces answer the question metrics and logs cannot: "where in the flow is the latency?" A p99 of 2 seconds on GET /orders is a metric; the trace shows that 1.8 seconds is spent in the database query, or in a specific downstream service, or in an external call. Without the trace, the engineer guesses; with it, the engineer knows.

Traces are sampled — storing every trace is too expensive. The typical sampling: 1–10% of successful requests, 100% of errors or slow requests. Head-based sampling (decided at the entry point) is simple; tail-based sampling (decided after the trace is complete) keeps the interesting traces.

How they combine

The three pillars are complementary, not alternatives. The workflow:

  1. Alert fires on a metric — error rate on POST /orders is above the SLO.
  2. A trace shows where — the trace for a failing request reveals that the payment-service is slow.
  3. Logs show why — the logs from payment-service for that trace ID show the specific error (a timeout from the payment provider).
  4. Fix, verify — the metric returns to normal; the trace is fast again; the logs show no errors.

Without all three, the workflow has a gap. Without metrics, no one knows there is a problem. Without traces, no one knows where. Without logs, no one knows why.

The correlation key

All three pillars are linked by the correlation ID (also called the request ID or trace ID). Every log line includes it; every span has it; the metric system can tag it (sparingly — high cardinality risk). The correlation ID is what lets an engineer start from a metric, drill into a trace, and find the logs — all for the same request.

Interview Framing

Say: "Metrics answer 'is something wrong?', logs answer 'what happened?', traces answer 'where in the flow?'. All three are linked by the correlation ID. Metrics are cheap and aggregate; logs are detailed and expensive; traces are sampled and causal." That covers the roles and the trade-offs.

What are the RED and USE metric frameworks, and when do you use each?

Short Answer

RED (Rate, Errors, Duration) is the framework for services — what the caller experiences. USE (Utilization, Saturation, Errors) is the framework for resources — the servers, databases, queues, and disks that back the service. Use RED for the API's user-facing endpoints; use USE for the infrastructure that serves them. Together they cover both the symptom (RED) and the cause (USE).

RED — the service framework

MetricWhat it measuresExample
Rate Requests per second rate(http_requests_total[1m]) — how many requests per second
Errors The rate of failed requests rate(http_requests_total{status=~"5.."}[1m]) — the error rate
Duration The latency distribution histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) — the p99

RED is what the caller cares about — the service is receiving traffic, it is succeeding, and it is fast. Every API endpoint should have RED metrics. When the p99 latency is above the SLO, the alert fires; when the error rate is above the SLO, the alert fires. The metric is the symptom, not the cause — a slow service could be slow because the database is slow, but RED does not say that.

USE — the resource framework

MetricWhat it measuresExample
Utilization How busy the resource is CPU at 75%, memory at 60%, database connection pool at 90%
Saturation How much work is queued waiting for the resource Run queue length, thread pool backlog, database lock waits, disk queue depth
Errors The rate of resource-level errors Disk errors, network errors, connection failures, allocation failures

USE is what the operator cares about — is the resource healthy, or is it about to be the bottleneck? High utilization is not a problem by itself; high utilization combined with growing saturation is. A database at 90% CPU with zero lock waits is fine; a database at 50% CPU with rising lock waits is the problem.

How they connect

The workflow:

  1. RED alerts — the error rate on POST /orders is above the SLO.
  2. USE investigates — the database CPU is at 95%, the connection pool is exhausted, the lock waits are rising.
  3. Fix the resource — add a read replica, optimize the slow query, increase the pool.
  4. RED recovers — the error rate returns to normal.

RED tells you something is wrong; USE tells you where. The two together are the standard observability framework for any service backed by infrastructure.

What each framework misses

  • RED misses the cause — it does not show the database load, the GC pauses, the thread pool state, the queue backlog. The operator sees the symptom but not the cause.
  • USE misses the impact — it does not show the user experience. A database at 100% CPU might be fine if the queries are fast; a database at 30% CPU might be a problem if the lock waits are high. USE needs to be interpreted in the context of RED.
  • Both miss the business metrics — signups, conversions, revenue. The API might be healthy on RED and USE but the business might be failing (a checkout bug that the technical metrics do not catch). Business metrics are a third framework, layered on top.

The four golden signals

Google's SRE book defines a related framework: latency, traffic, errors, saturation. It is RED plus saturation — the service's signals with the resource's most important signal. The four golden signals are a superset of RED with the saturation dimension. In practice, use RED for the service metrics and USE for the resources; the four golden signals are a useful mental model that combines both.

The business metrics

The technical metrics answer "is the API working?" The business metrics answer "is the product working?" — signups per minute, orders per minute, revenue per hour, checkout conversion. A drop in orders with a healthy RED metric is a product bug, not an infrastructure bug. The business metrics catch:

  • Feature bugs — a checkout button that returns 200 but does not create the order.
  • Third-party outages — the payment provider's API is down; the orders fail but the API returns 200 (async failure).
  • Data quality — the orders are created but the analytics pipeline is broken.

The dashboard should include both the technical metrics and the business metrics; the alert should fire on either. A business metric drop is often the earliest signal of a real problem.

Trade-off

RED is cheap and universal; USE is per-resource and requires specific instrumentation. The pragmatic answer: implement RED on every endpoint (mandatory), implement USE on every critical resource (databases, queues, caches, load balancers), and add business metrics for the flows that matter. Each layer catches a class the others miss.

Interview Framing

Say: "RED for the service — rate, errors, duration — is what the caller experiences. USE for the resources — utilization, saturation, errors — is where the cause lives. Layer business metrics on top for the flows that matter. The workflow is: RED alerts, USE investigates." That covers the frameworks and how they connect.

What are SLIs, SLOs, and SLAs, and how does an error budget work?

Short Answer

An SLI is the measurement — the actual latency, error rate, availability. An SLO is the target for that measurement — 99.9% of requests succeed in under 300 ms. An SLA is the legal commitment — the consequences (credits, penalties) if the SLO is missed. The error budget is the allowed failure — 0.1% of requests in a 30-day window, which is the margin the SLO permits. The budget funds the risk; when it is exhausted, the team stops shipping features and focuses on reliability.

The three terms, defined precisely

TermDefinitionExample
SLI (Indicator) A quantifiable measure of the service's behaviour, from the caller's perspective Proportion of HTTP requests that return 2xx/3xx, or the p99 latency, measured at the load balancer
SLO (Objective) A target value or range for the SLI over a period 99.9% of requests succeed; 95% of requests return in under 300 ms; measured over 30 days
SLA (Agreement) A legal or contractual commitment with consequences if missed If the API is below 99.9% for a month, the customer receives a 10% credit

The relationship: the SLI is the measurement, the SLO is the internal target, the SLA is the external commitment. The SLO is almost always stricter than the SLA — the team targets 99.95% so that the 99.9% SLA is never breached.

Choosing an SLI

The SLI must reflect what the user experiences, not what the system measures internally. The dimensions:

DimensionWhat it measuresExample
Availability Is the service responding? % of requests that succeed (non-5xx, or explicit success response)
Latency Is the service fast enough? % of requests returning in under 300 ms; or p99 latency
Throughput Is the service handling the load? Requests per second; or % of requests that do not hit the rate limit
Durability Is the data safe? % of writes that survive a read-back
Freshness Is the data up to date? Age of the replica data at read time

The critical choice: the SLI is measured from the caller's side — the load balancer, the client, the edge — not from the server's internal metrics. A server that reports "all requests served successfully" might be lying (the request errored after the metric was recorded); the caller's SLI is the truth.

The SLO specification

A well-specified SLO includes:

  • The SLI — what is measured, from where.
  • The target — the percentage, the latency threshold.
  • The window — over what period (30 days, 90 days, rolling).
  • The scope — which endpoints, which customers, which regions.
  • The consequences — what happens if missed (page on-call, inform the customer, initiate the error-budget policy).

Example: "POST /orders and GET /orders/{id} succeed with a 200 response within 500 ms for 99.9% of requests, measured at the load balancer, over a rolling 30-day window."

The error budget

The error budget is the SLO's complement — the allowed failure. For 99.9% over 30 days:

SLOError budget (30 days)Downtime equivalent
99%1%~7.2 hours
99.9%0.1%~43 minutes
99.95%0.05%~21 minutes
99.99%0.01%~4.3 minutes
99.999%0.001%~26 seconds

The budget is a spendable resource. The team spends it on:

  • Risky deploys — a new feature might have bugs; the budget absorbs them.
  • Experiments — a new database engine, a new region, a new configuration.
  • Planned maintenance — a brief outage during a migration.

When the budget is healthy, the team ships fast. When the budget is depleted, the team stops shipping features and focuses on reliability. This is the fundamental tension the budget resolves — it converts the vague "we should be more reliable" into a concrete, measurable policy.

The budget policy

Budget remainingPolicy
>50%Ship features freely; the risk is covered
25–50%Ship with caution; review risky changes
10–25%Prioritise reliability work; ship only critical features
<10%Feature freeze; the team focuses entirely on reliability
0%The SLO is breached; postmortem, action items, and a plan to recover the budget

The policy must be agreed upon before the budget is depleted — the team cannot negotiate the policy while the service is on fire. The policy is a pre-commitment, and it is enforced by the team's leadership.

The SLA and its consequences

The SLA is the external commitment. It is typically 99.9% for a paid service, with credits for the customer if the target is missed. The SLA is what the customer's contract specifies, and its breach is a business event, not just an engineering one.

The SLA should be:

  • Wider than the SLO — the SLO is 99.95%, the SLA is 99.9%.
  • Measured consistently — the same SLI, the same window, the same scope.
  • Communicated clearly — the customer knows what is measured and what the consequences are.
  • Reviewed periodically — as the service improves, the SLA can be tightened.

The "five nines" myth

Five nines (99.999%) allows 26 seconds of downtime per month. This is not achievable with standard deployment practices — a single rolling deploy takes longer than 26 seconds. Achieving five nines requires either perfect deployments (impossible) or a multi-region active-active architecture with sub-second failover (very expensive). Most services are 99.9% or 99.95% — the cost of each additional nine grows exponentially, and the benefit is measured in minutes of avoided downtime per year.

Common Pitfall

Setting the SLO from the server's internal metrics, not the caller's experience. The server reports 99.99% success, but the load balancer sees 99.5% — the difference is the requests that failed before reaching the server (connection errors, timeouts, DNS failures). The server's metrics lie; the caller's are the truth.

Interview Framing

Say: "SLI is the measurement, SLO is the internal target, SLA is the external commitment. The error budget is the complement — 0.1% for 99.9% — and it funds the risky work. When the budget is depleted, the team stops shipping features and fixes reliability. The SLA is always wider than the SLO." That covers the framework in one paragraph.

Part B — Alerting & Investigation Symptoms vs causes, dashboards, and traces

How do you design alerts that page on symptoms rather than causes?

Short Answer

An alert should fire when the user is being affected — when the SLO is at risk — not when a specific component is showing a particular value. The symptom is "the error rate is above the SLO", "the p99 is above 500 ms", "the checkout success rate dropped". The cause is "the database CPU is 90%", "the connection pool is full", "the queue is backing up" — these are diagnostics, not alerts. Alerts page the on-call; diagnostics inform the investigation.

Why symptom-based alerts are better

Cause-based alertSymptom-based alert
Database CPU > 80% Error rate > 0.1% or p99 > SLO
Memory usage > 90% OOMKilled pods > 0 in the last 5 min
Disk usage > 85% Writes failing / logs dropping
Thread pool queue > 100 Request latency > SLO
Kafka consumer lag > 1000 Event processing time > SLO; users see stale data

The cause-based alert fires at 3 AM because the CPU is 81% — the service is fine, the CPU is just high. The on-call wakes up, investigates, finds nothing wrong, goes back to bed. This is alert fatigue, and it is the reason most on-call rotations are miserable. The symptom-based alert does not fire until the users are affected — when the p99 is above the SLO, the users are experiencing the problem, and the page is justified.

What to alert on

CategoryExamplePage or ticket?
SLO burn rate Error rate is burning the error budget 10× faster than the SLO allows Page
Availability Health check is failing for more than 1 minute Page
Saturation with impact Database connection pool at 100%, and requests are queuing Page (the impact is the symptom)
Business metric drop Orders per minute dropped 50% versus the same time last week Page
Saturation without impact CPU at 70%, memory at 60%, connection pool at 40% Ticket — investigate during business hours
Capacity trending Disk growth predicts full in 14 days Ticket — capacity planning
Non-urgent A deprecated endpoint is still being called by 0.1% of traffic Slack notification

The burn rate alert

The best symptom-based alert is the error budget burn rate. The SLO allows 0.1% errors over 30 days — that is a rate of 0.1% / (30 × 24 × 60) = ~2.3 × 10⁻⁶ per minute. If the actual error rate is 10× that, the budget is being consumed 10× faster; at that rate, the budget is exhausted in 3 days. The alert is: "the burn rate is above 10× for the last hour" — the error budget is at risk.

Burn rateTime to exhaust the 30-day budgetAlert
1×30 daysNormal
2×15 daysTicket
10×3 daysTicket (or page if sustained)
100×~7 hoursPage
1000×~43 minutesPage immediately

The burn rate alert is the highest-signal alert: it fires when the user is genuinely being affected, and it escalates with severity. It does not fire on a healthy system that happens to have high CPU; it fires on a system that is losing the reliability the team committed to.

The multi-window approach

A single window (the last 5 minutes) has two failure modes: it fires on a brief spike (the alert is noisy), or it misses a slow degradation (the alert is blind). The multi-window approach:

WindowThresholdMeaning
1 minuteBurn rate > 1000×Catastrophic — page immediately
5 minutesBurn rate > 100×Severe — page
1 hourBurn rate > 10×Warning — ticket
6 hoursBurn rate > 2×Trending — ticket

The shorter windows catch the acute incidents; the longer windows catch the slow burns. The alerts are tiered: the 1-minute alert pages; the 6-hour alert creates a ticket.

What not to alert on

  • Individual host metrics — a single host's CPU is high; the load balancer should route around it. Alert on the service, not the host.
  • Thresholds without impact — "memory above 80%" is a ticket, not a page. Memory above 80% is normal; it is only a problem if the process is OOMKilled or the response time is affected.
  • Metrics that fluctuate naturally — request rate, traffic patterns. These are expected; alerting on them creates noise.
  • Everything that has a dashboard — a metric is not an alert. The dashboard is for investigation; the alert is for the user impact.

The alert quality checklist

Every alert should pass:

  1. Is it actionable? If the on-call cannot do anything, it is not an alert.
  2. Is it urgent? If it can wait until morning, it is a ticket, not a page.
  3. Is it accurate? If it fires when nothing is wrong, it is noisy.
  4. Is it specific? The alert should name the service, the symptom, and the runbook.
  5. Does it have a runbook? The on-call should have a documented first step.
  6. Does it have a clear owner? Who fixes it if it fires?

The alert quality metrics

Measure the alert quality — the discipline is data-driven:

  • Signal-to-noise ratio — how many alerts are actionable vs noise.
  • Pages per shift — how many times is the on-call paged.
  • Time to acknowledge — how quickly the on-call responds.
  • Time to resolve — how long the incident takes.
  • Actionability — what percentage of pages lead to a fix.

The target: fewer than 2 pages per 12-hour shift; >80% of pages actionable; time to acknowledge under 5 minutes. When these are missed, the alerting is broken and the team is burning out.

Common Pitfall

Alerting on every metric the dashboard shows. The result: dozens of alerts per day, most of them noise, and the on-call ignores them. The real alert is lost in the noise, and the incident is discovered by the customer instead of the team. Alert on the symptoms that users experience; leave the rest to dashboards.

Interview Framing

Say: "Alerts fire on symptoms — SLO burn rate, user-facing errors, business metrics. Causes are for dashboards and investigation. Multi-window burn rates catch both the acute and the slow. Every alert is actionable, urgent, and has a runbook." That covers the principle and the implementation.

5

How do you design dashboards that actually help during an incident?

Short Answer

A dashboard is not a wall of charts — it is a diagnostic tool that answers a sequence of questions in order: is something wrong? where? how bad? what changed? The design follows the investigation: top-level health (SLO burn, error rate), then the breakdown (by endpoint, by region, by dependency), then the resource (USE metrics), then the recent changes (deploys, config changes). Each panel answers a question the on-call will ask.

The questions the dashboard answers

OrderQuestionPanel
1 Is there a problem right now? SLO burn rate; error rate; p99 latency; availability
2 How bad is it? Absolute error rate (%); traffic volume; affected users
3 Where is it? Error rate by endpoint; by region; by downstream dependency
4 Why? Latency breakdown; database query time; downstream call time
5 What changed? Recent deploys; config changes; feature flags; infra events
6 Is it getting better? Trend of the above; the timeline of the incident

The top row — the health snapshot

The top of the dashboard is the "is there a problem?" row. It shows the SLI for each SLO, with a visual indicator of the target. The on-call glances at it and knows immediately whether the service is healthy. Panels:

PanelWhat it shows
SLO status A big number per SLO: 99.97% (green) or 99.82% (red) — against the target
Error budget remaining 0–100% — the fuel gauge; the number that drives the ship/fix decision
Traffic Requests per second — the denominator for all the rates
Error rate % of requests failing — the numerator
p99 latency The tail — what the users feel

The breakdown row — where is it?

The second row splits the top-level metric by dimension. The on-call uses this to narrow the investigation:

  • By endpoint — is GET /orders slow, or just POST /checkout?
  • By region — is us-east the problem, or all regions?
  • By version — did the new deploy introduce it?
  • By downstream — is payment-service slow, or inventory?
  • By client — is the mobile app, or the web, or a specific partner?

The split is the fastest way to narrow the problem. A 50% error rate that is 100% on one endpoint is a very different problem from a 50% error rate across all endpoints — the first is a bug in that endpoint, the second is infrastructure.

The resource row — USE metrics

The third row shows the infrastructure:

ResourcePanels
DatabaseCPU, connections, slow query count, lock waits, replication lag
CacheHit rate, memory, evictions, connections
QueueDepth, consumer lag, producer rate, consumer rate
HostsCPU, memory, disk, network
Load balancerRequest rate, error rate, 5xx, 4xx, latency

The change row — what changed?

Most incidents are caused by a change — a deploy, a config change, a feature flag, a scaling event, a dependency upgrade. The dashboard shows the changes:

  • Deploy markers — a vertical line on the timeline when a deploy happened.
  • Config changes — a marker when a config was updated.
  • Feature flags — a marker when a flag was toggled.
  • Infra events — a marker when an instance was added, removed, or restarted.

The "what changed?" question is often the fastest path to the cause. A latency spike at 14:32 with a deploy marker at 14:31 is probably the deploy; a deploy marker at 12:00 and a spike at 14:32 is probably not. Without the markers, the on-call has to remember or look up the deploy history — which is the kind of thing that fails during an incident.

The investigation flow

The dashboard supports the flow:

  1. Glance at the top — the SLO is at risk; the error rate is 5%.
  2. Look at the breakdown — the errors are on POST /checkout in us-east.
  3. Look at the resource — the database in us-east is at 95% CPU, the connection pool is exhausted.
  4. Look at the changes — a deploy at 14:31, five minutes before the error rate spiked.
  5. Correlate — the deploy introduced a query that is not indexed; the database is overloaded; the checkouts fail.
  6. Roll back — the deploy is reverted; the dashboard returns to normal.

The dashboard is designed for this flow — each row is a step, and the rows together tell the story. Without the design, the on-call stares at 50 charts and does not know which one to look at first.

The "wall of charts" anti-pattern

A common bad dashboard: every metric the team could think of, arranged in a grid, with no hierarchy. The on-call looks at it and sees 50 lines; the relevant one is somewhere; the correlation is invisible. The fix is design: each dashboard has a purpose (health, investigation, capacity), and each panel answers a specific question. A dashboard that tries to show everything shows nothing.

The layered dashboards

LayerAudienceContent
Executive Leadership SLO status across services; error budget burn; customer impact
Service health On-call, service owner The top-level dashboard: SLO, errors, latency, traffic, breakdown
Investigation On-call during an incident Detailed panels: per-endpoint, per-instance, per-dependency, resource USE
Capacity SRE, capacity planner Trends: growth rate, projected limits, resource headroom
Business Product, leadership Orders, signups, revenue, conversion

Each layer has its audience. The executive dashboard is not the investigation dashboard; the investigation dashboard is not the capacity dashboard. The right dashboard for the question.

Common Pitfall

Building dashboards from the data that is easy to collect, not the questions the on-call will ask. The result is charts that are technically accurate but useless during an incident. The fix: design the dashboard from the questions, then collect the data to answer them — not the other way around.

Interview Framing

Say: "The dashboard answers a sequence — is there a problem, where, how bad, what changed. Top row is the health snapshot, then the breakdown, then the resources, then the change markers. Each panel answers a question the on-call asks." That covers the design and the purpose.

How does distributed tracing work, and how do you correlate a request across services?

Short Answer

A distributed trace is a tree of spans — each span represents one unit of work (an HTTP request, a database query, an RPC call) with a start time, duration, and metadata. The trace_id is shared across all spans in the request; each span has a span_id and a parent_span_id that links it to its caller. The tree shows the full flow: the entry point, each downstream call, the time spent in each. The correlation is the trace context propagated in headers.

The anatomy of a trace

ConceptMeaningExample
Trace The full request, from entry to exit The whole GET /checkout request, 200 ms
Span One unit of work in the trace "Call payment-service: 120 ms"
trace_id The identifier shared by all spans in the trace 4bf92f3577b34da6a3ce929d0e0e4736
span_id The identifier for this span 00f067aa0ba902b7
parent_span_id The span that called this one The span for "handle checkout" is the parent of "call payment-service"
tags/attributes Metadata: service, method, status, peer http.method=POST, http.status_code=200, peer.service=payment
events/logs Discrete events within a span "cache miss", "retry #1", "exception"

The propagation

For the trace to span services, the context must propagate. When service A calls service B, A injects the trace context into the outbound request (headers); B extracts it and starts a child span. The standard headers:

StandardHeaders
W3C Trace Context traceparent: 00-{trace_id}-{parent_span_id}-{flags}; tracestate for vendor data
B3 (Zipkin) X-B3-TraceId, X-B3-SpanId, X-B3-ParentSpanId, X-B3-Sampled
Jaeger uber-trace-id: {trace_id}:{span_id}:{parent}:{flags}

W3C Trace Context is the modern standard; OpenTelemetry uses it by default. The propagation is the key — without it, each service's trace is isolated, and the "distributed" trace is actually N separate traces.

The instrumentation layers

LayerWhat it instruments
Auto-instrumentation HTTP servers/clients, database drivers, RPC frameworks — spans created automatically by the OpenTelemetry SDK
Framework instrumentation Express, Django, Spring — middleware that creates the root span and propagates the context
Manual instrumentation Custom spans for business logic — a span for "process order", for "validate payment"
Async instrumentation Message queues, scheduled jobs — the trace context is stored with the message and restored when consumed

Auto-instrumentation covers the infrastructure spans; manual instrumentation covers the business logic. A trace with only auto-instrumentation shows the HTTP calls but not "what was being done"; a trace with both shows the full picture.

The sampling

Storing every trace is too expensive — a high-traffic API generates billions. The sampling:

StrategyHowProsCons
Head-based (probabilistic) Decide at the root span: 1% of traces are sampled Simple; consistent across services Misses rare events (the slow request you wanted to see)
Tail-based Decide after the trace is complete: 100% of errors and slow traces, 1% of the rest Catches the interesting traces; drops the boring ones Requires a buffering layer; more complex
Rate limiting Cap the number of traces per second per service Bounded cost May miss the incident if the rate limit is exceeded

The pragmatic mix: tail-based sampling for errors and slow requests (100%), head-based for the rest (1%). The trace storage cost is bounded, and the interesting traces are always kept.

The trace in the investigation

A trace is the fastest way to find "where in the flow is the latency?" The trace viewer shows a waterfall — each span as a horizontal bar, with the parent-child structure. The on-call looks at the waterfall:

  • The total is 2 seconds — the SLI for the endpoint.
  • The first span (handle checkout) is 2 seconds — the whole request.
  • The child span (call payment-service) is 1.8 seconds — the bulk of the time.
  • The grandchild span (call stripe API) is 1.7 seconds — the specific downstream call.
  • The grandchild span (database query) is 50 ms — not the bottleneck.

The trace answered "where" in seconds — the on-call knows to investigate the Stripe API, not the database. Without the trace, the on-call might look at the database first (it is often the culprit) and waste time.

The trace in the incident

During an incident, the trace is the tool for the "how" question: how does the request flow, how does the failure propagate, how is the downstream affecting the upstream? The trace viewer lets the on-call click into a slow span, see its tags (method, status, peer), and correlate with the logs for that trace_id.

The workflow:

  1. Dashboard — the p99 is high on GET /checkout.
  2. Trace list — filter to slow traces; pick one.
  3. Trace waterfall — the payment-service call is 1.8 seconds.
  4. Click into the span — the tags show http.status_code=200, peer.service=stripe.
  5. Logs for trace_id — the logs from payment-service show "stripe API timeout after 1500 ms".
  6. Fix — increase the Stripe timeout, or add a retry, or degrade gracefully.

The trace in production — the sampling problem

A trace is only useful if it was sampled. In an incident, the on-call needs to see the trace of a specific failing request — but if the tracing is sampled at 1%, that specific request is probably not recorded. The mitigations:

  • Tail-based sampling — keep 100% of errors and slow traces; the failing request is always recorded.
  • On-demand tracing — a header or query parameter that forces the trace to be recorded; the on-call adds it to a failing request.
  • Correlation with logs — even if the trace is not recorded, the logs for the trace_id are; the log line has the trace context.

The trace in async flows

Async flows (webhooks, message queues, scheduled jobs) break the trace — the request is not a single call chain. The mitigation: the trace context is stored with the message and restored when the message is consumed. The trace then spans the producer, the queue, and the consumer — a single trace for the whole async flow.

For webhooks (Volume 11), the trace context is injected into the outbound header; the receiver extracts it and starts a child span. The trace spans the sender and the receiver, and the trace viewer shows the full flow.

Common Pitfall

Instrumenting the HTTP layer but not the async boundary. The trace shows the API request but stops at the message queue — the consumer's processing is a separate trace with no link. The fix: propagate the trace context in the message metadata; the consumer starts a child span.

Interview Framing

Say: "A trace is a tree of spans — each span is one unit of work, linked by trace_id and parent_span_id. The context propagates via W3C traceparent headers, and the trace shows where the latency is. Sampling keeps 100% of errors and slow traces, 1% of the rest." That covers the mechanism and the sampling strategy.

How do you run an incident — roles, communication, and the timeline?

Short Answer

An incident is a structured response to an unplanned event. The roles: Incident Commander (IC) — coordinates, makes decisions, does not fix; Operations Lead — does the technical work; Communications Lead — updates stakeholders; Scribe — logs the timeline. The phases: detect, triage, mitigate, resolve, learn. The discipline is communication: what happened, who is affected, what is being done, when the next update is.

The roles

RoleResponsibilityWhat they do NOT do
Incident Commander (IC) Coordinate; make decisions; manage the timeline; keep the team focused Debug or fix — they are the coordinator, not a firefighter
Operations Lead Do the technical work; investigate; fix; coordinate the technical team Communicate with stakeholders; make policy decisions
Communications Lead Update stakeholders; write status updates; coordinate with support and PR Debug; make technical decisions
Scribe Log the timeline; capture decisions; document the investigation Debug; participate in the technical work

The key insight: the IC does not fix. In a small team, the senior engineer often jumps into the fix and loses the coordination view — the team becomes fragmented, the communication lapses, and the fix takes longer. The IC's job is to keep the whole picture and the whole team, not to write the code. In a small incident, one person can be IC and Ops Lead, but the roles are distinct.

The phases

PhaseGoalActions
Detect Know there is an incident Alert fires; customer report; metric crosses SLO
Triage Assess severity and scope What is affected? How many users? What is the impact? Declare severity
Mitigate Stop the bleeding Roll back, route around, disable feature, scale up — the fastest path to reducing impact
Resolve Return to normal Confirm the fix; verify the SLO is recovering; close the incident
Learn Prevent recurrence Postmortem; action items; the fix that makes the class of incident impossible

Severity levels

SeverityImpactResponse
SEV1 Full outage or critical data loss; all users affected All hands; page IC and Ops immediately; exec notification; war room
SEV2 Major feature broken; significant user impact Page on-call; Ops investigates; IC if extended
SEV3 Minor feature broken; workaround available Ticket; next business day
SEV4 Cosmetic; no user impact Backlog

The severity drives the response — a SEV1 is all hands, a SEV3 is a ticket. The IC declares the severity in triage, and it can escalate if the scope expands.

The communication discipline

During an incident, communication is as important as the technical work. The stakeholders need:

  • What happened — the symptom, the scope, the impact.
  • Who is affected — all users, a subset, a specific region.
  • What is being done — investigating, mitigating, rolling back.
  • When the next update — a specific time (every 30 minutes, hourly).

The updates are on a schedule — even if nothing has changed, the update is "still investigating, next update at 14:30". This prevents the stakeholders from chasing the IC for status, which is exactly what the IC does not need.

StakeholderUpdate frequencyChannel
Support / customer-facingEvery 15–30 minutesSlack channel; customer-facing status page
Engineering leadershipEvery 30 minutesSlack; email for SEV1
ExecutiveAt declaration and resolutionDirect message / phone
CustomersStatus page updatesPublic status page

The status page

The public status page is the customer's source of truth. It shows:

  • Current status — operational, degraded, partial outage, major outage.
  • Affected services — which parts of the product are impacted.
  • The incident timeline — when it started, what is being done, the next update.
  • Postmortems — the public postmortem after resolution (for significant incidents).

The status page must be updated during the incident, not after. Customers see the same outage the team does; a silent status page implies the team has not noticed, which erodes trust.

The war room

For a SEV1, the war room is a single channel (or call) where all the participants are. The benefits:

  • Shared context — everyone sees the same investigation, the same metrics, the same decisions.
  • Fast decisions — the IC asks "do we roll back?", the Ops says "yes", it happens.
  • No miscommunication — the chat channel is the record; everyone knows what was decided.
  • The scribe documents — the timeline is captured in real time; the postmortem is easier.

The post-incident

The incident is over when the SLO is recovering and the customer impact has stopped. The post-incident work:

  1. Confirm resolution — the metrics are healthy; the customer has confirmed.
  2. Communicate resolution — to stakeholders and to the status page.
  3. Schedule the postmortem — within a week, before the memory fades.
  4. Preserve the evidence — the logs, the traces, the dashboards, the chat transcript.
  5. Draft the postmortem — the timeline, the root cause, the action items.
  6. Track the action items — the fixes are the point; without them, the incident will recur.
Common Pitfall

The IC jumps into the debugging. The team loses the coordinator; the communication stops; the fix takes longer. The IC's job is to ask "what is the state?", "what are we doing?", "when is the next update?" — not to read the logs. In a small incident, the IC can also be Ops Lead, but when the incident expands, the roles must separate.

Interview Framing

Say: "The IC coordinates and does not fix; Ops Lead does the technical work; Comms Lead updates stakeholders; Scribe logs the timeline. The phases are detect, triage, mitigate, resolve, learn. The communication is on a schedule, even if nothing has changed." That covers the roles and the discipline.

What is a blameless postmortem, and what should it contain?

Short Answer

A blameless postmortem is a written analysis of an incident that focuses on systems and processes, not individuals. The premise: people do not act maliciously; they act reasonably given the information, tools, and pressures they had. Blaming people shuts down the honest reporting that the postmortem depends on. The postmortem contains: the timeline, the root cause (and contributing causes), the impact, what went well, what went poorly, and the action items with owners and deadlines.

Why "blameless"

The temptation after an incident is to find the person who "caused" it — the engineer who deployed the bad code, the operator who ran the wrong command. But:

  • The engineer did not act alone. The deploy was approved, the test passed, the monitor did not catch it. The "cause" is a chain, not a person.
  • Blaming destroys the signal. If people fear blame, they hide mistakes, and the team loses the data it needs to prevent recurrence.
  • Blaming does not fix the system. Firing one engineer does not change the process that allowed the mistake. The next engineer will make the same mistake.
  • Blaming is factually wrong. The incident is a property of the system — the tools, the process, the culture — not of the individual. The individual is the messenger, not the cause.

The structure

SectionContent
Header Incident number, date, severity, duration, affected services, IC
Summary 2–3 sentences: what happened, for how long, what was the impact
Impact Users affected, requests failed, revenue lost, SLO burned
Timeline The minute-by-minute sequence: detection, triage, decisions, mitigations, resolution
Root cause The primary cause — the change or condition that triggered the incident
Contributing factors What made it worse or prevented the fix — the missing test, the misleading monitor, the slow rollback
What went well The detection, the rollback, the communication — the things to preserve
What went poorly The missing alert, the slow triage, the confusing runbook — the things to fix
Action items Specific, owned, dated; the prevention — not "be more careful"
Lessons learned The generalizable insight — the class of problem to watch for

The timeline

The timeline is the most valuable section — it forces the team to reconstruct the sequence and identify the delays. The format:

TimeEvent
14:32Deploy of v2.4.1 completes
14:35Error rate on POST /checkout begins to rise
14:38Alert fires — error rate > SLO
14:42On-call acknowledges, opens incident channel
14:45IC assigned; severity declared SEV2
14:50Ops Lead identifies database CPU at 95%
14:55Rollback to v2.4.0 begins
15:02Rollback complete; error rate begins to fall
15:10Error rate back to baseline; incident resolved

The timeline reveals the delays: 3 minutes from deploy to error, 3 minutes from error to alert, 4 minutes from alert to acknowledge, 17 minutes from detection to mitigation. Each delay is an action item — the alert threshold, the acknowledge SLA, the rollback procedure.

The root cause

The root cause is the change or condition that triggered the incident — not the person who made the change. "The deploy introduced an unindexed query" is a root cause; "the engineer who wrote the query" is not. The contributing factors are the conditions that made it worse or prevented the fix: "the staging environment did not have production-scale data, so the missing index did not show up in tests."

The 5-whys technique is often used: "why?" five times, until the answer is a systemic condition rather than a surface symptom. But it is used carefully — the goal is to understand, not to assign blame. The chain often ends at "the process did not catch it", which is where the action item belongs.

The action items

The action items are the point. Each should be:

  • Specific — "add the index on orders.created_at", not "improve database performance".
  • Owned — a named person, not "the team".
  • Dated — a deadline, not "soon".
  • Verifiable — the fix can be checked; the test can be run.
  • Systemic — the fix prevents the class, not just the instance. The missing index is fixed, and the staging data is scaled to production, so the next missing index is caught.

The categories of action item:

CategoryExample
Prevent Fix the bug; add the test; correct the configuration
Detect Add the alert; improve the monitor; shorten the detection window
Mitigate Improve the rollback; add the feature flag; enable the circuit breaker
Respond Update the runbook; add the dashboard; clarify the escalation
Learn Share the analysis; update the training; revise the architecture

A postmortem with only "prevent" items will not catch the next incident. The detection, mitigation, and response items are the infrastructure that makes the next incident smaller.

The distribution

The postmortem is written for:

  • The team — the detailed analysis; the technical depth.
  • The broader org — the summary and the lessons learned; the pattern to watch for.
  • The customer (for significant incidents) — a redacted version with the timeline, the impact, and the fixes; no internal details or blame.
  • The public (for major incidents) — a blog post or status page entry; the trust rebuild.

The "no root cause" trap

Some incidents do not have a single root cause — they are complex, with multiple contributing factors. The postmortem should resist the pressure to name one thing. The analysis can say "several factors combined", and the action items address each. Forcing a single root cause often produces a wrong fix.

The action item follow-through

The most common failure of the postmortem process: the postmortem is written, and the action items are never done. The next incident has the same cause, and the postmortem is now a ritual, not a learning. The fix:

  • Track the items in the same system as the regular work — the backlog; the Jira project; the sprint.
  • Review at the weekly meeting — the action items are part of the team's regular review.
  • Assign a deadline — the item is due; if it slips, it is re-discussed, not forgotten.
  • Publicise the completion — the team sees that the items are done, which reinforces the culture.
Common Pitfall

Writing "the engineer should have tested more carefully" as an action item. It is not actionable (the engineer is not going to "test more carefully" without a change to the process), it is not systemic (the next engineer will make the same mistake), and it is not blameless (it blames the engineer). The fix is to change the process — the missing test, the staging environment, the code review checklist.

Interview Framing

Say: "Blameless means we focus on systems, not people. The postmortem has a timeline, root cause, contributing factors, what went well, what went poorly, and owned action items. The action items are tracked like any other work — the postmortem is only valuable if the fixes actually happen." That covers the culture and the discipline.

Compare deployment strategies — rolling, blue-green, canary, and feature flags.

Short Answer

Rolling replaces instances one at a time — the default, simple, but mixed versions run during the rollout. Blue-green deploys to a parallel environment, switches all traffic atomically, and rolls back by switching back — fast rollback, double the infrastructure. Canary routes a small percentage of traffic to the new version, monitors, and ramps up — gradual risk, requires good observability. Feature flags deploy the code to production but keep it disabled, enabling per-user or per-tenant — decouples deploy from release, the fastest rollback.

StrategyRollbackCostRiskBest for
Rolling Slow — the previous version is gone; must re-deploy Normal Medium — mixed versions during the rollout Stateless services; the default
Blue-green Fast — flip the switch back Double (two environments) Low — the switch is atomic Major changes; database migrations; anything where the old version must be available
Canary Fast — reduce the canary weight to 0 Small (a few extra instances) Very low — limited blast radius Most production deploys; the standard for high-traffic
Feature flags Instant — flip the flag off Minimal Very low — the code is present but disabled User-facing features; A/B tests; gradual releases

Rolling deployment

The default in Kubernetes and most orchestrators. The new version is deployed alongside the old; as new instances become healthy, old instances are terminated. The process continues until all instances are on the new version.

The advantages: simple, no extra infrastructure, works with any stateless service. The disadvantage: for a period (minutes), both versions are running and serving traffic. If the new version has a bug, the traffic is partially affected; if the bug is severe, some users see errors until the rollout completes.

The rollback is a new rolling deployment to the previous version — the old version is no longer running, so it must be re-deployed. This takes as long as the rollout, which is the reason rolling is the weakest for rollback.

The prerequisites: backward-compatible schema (the old and new versions share the database); health checks that reflect readiness (not just liveness); zero-downtime connection draining (the old instance finishes in-flight requests before terminating).

Blue-green deployment

Two full environments — blue (current) and green (new). The new version is deployed to green; it is tested; the load balancer switches all traffic to green atomically. If there is a problem, the switch is reversed — blue is still running.

The advantage: rollback is instant — a single load balancer change. The disadvantage: double the infrastructure (two full environments), and the two environments must be kept in sync (same config, same schema).

The database problem: if the new version has a schema change, both versions must be compatible with the same database. Blue uses the old schema; green uses the new — they cannot both use the same database if the schema is incompatible. The solution is expand-contract (Volume 3, Question 4): add the new field, backfill, deploy the new code, remove the old field. The blue-green deploy happens at the deploy step, not the schema step.

Canary deployment

The standard for high-traffic services. The new version is deployed alongside the old; a small percentage of traffic (1%, 5%, 10%) is routed to the new version; the metrics are compared to the baseline; if healthy, the percentage is increased; if not, it is reduced to 0.

StepWeightDuration
Deploy canary0%Smoke tests
Initial canary1%15 minutes
Ramp5%30 minutes
Ramp10%1 hour
Ramp50%1 hour
Full rollout100%Complete

The prerequisites:

  • Per-version metrics — the canary's error rate, latency, and business metrics must be tagged and visible.
  • Automated comparison — the system compares the canary to the baseline and alerts or auto-reverts if the canary is worse.
  • Backward-compatible schema — both versions run against the same database.
  • Sticky routing — a user is consistently in the canary or the baseline (not flipping between them).

The advantage: the blast radius is limited — a bad canary affects 1% of traffic, not 100%. The canary is the safest deploy strategy for most services.

Feature flags

The code is deployed to production but the feature is disabled; a flag controls whether the feature is active. The flag can be per-user, per-tenant, per-region, per-percentage.

The advantages:

  • Decouple deploy from release — the code is in production; the release is a flag toggle.
  • Instant rollback — flip the flag off; the code is still deployed but inert.
  • Gradual rollout — enable for 1% of users, then 10%, then 100%.
  • A/B testing — enable for group A, not group B; compare the metrics.
  • Kill switch — if the feature causes problems, disable it without a deploy.

The costs:

  • Flag debt — flags accumulate; old flags are never removed; the code becomes a maze of conditional branches.
  • Testing complexity — every combination of flags is a test case; the combinatorics explode.
  • Configuration as code — the flags are configuration; misconfiguration is a bug.

The discipline: every flag has an owner, a purpose, and a removal date. When the feature is fully rolled out, the flag is removed from the code (not just disabled). The flag debt is the cost; the management is the discipline.

The combination

In practice, the strategies are layered:

  1. Deploy — canary or blue-green (the infrastructure change).
  2. Release — feature flag (the user-facing change).
  3. Experiments — flag with an A/B test (the measurement).

The deploy is safe (the canary catches the infrastructure bugs); the release is reversible (the flag catches the feature bugs); the experiment is measurable (the A/B test tells you whether the feature is worth keeping). Each layer catches what the previous one misses.

The zero-downtime requirements

All the strategies require the same prerequisites for zero downtime:

RequirementWhy
Backward-compatible schema The old and new versions run against the same database
Health checks The load balancer knows when an instance is ready
Connection draining In-flight requests complete before the instance is terminated
Graceful shutdown The application stops accepting new requests, finishes existing ones, then exits
Readiness vs liveness The readiness probe reflects the ability to serve; the liveness probe reflects the process alive
Rollback plan The previous version is available (blue-green) or the rollback is fast (canary)
Common Pitfall

Using canary without per-version metrics. The canary is deployed, but the metrics are aggregated across versions — the canary's error rate is invisible. The canary becomes a placebo: it "looks" safe but the team cannot tell if it is failing. The fix: tag every metric with the version; compare the canary to the baseline explicitly.

Interview Framing

Say: "Rolling is the default, simple, but slow to rollback. Blue-green is fast rollback at double the infrastructure. Canary is the standard for high-traffic — 1% to 100% with per-version metrics. Feature flags decouple deploy from release — the code is in production, the feature is off. The full stack is canary deploy + feature flag release." That covers the four strategies and their combination.

What is chaos engineering, and how do you run a game day?

Short Answer

Chaos engineering is the discipline of deliberately injecting failures into a system to verify that it recovers. The premise: distributed systems have failure modes that testing does not exercise; the only way to know how they behave is to break them. A game day is a planned exercise where the team injects a specific failure (kills a database, drops a network, corrupts a config) and verifies the system's response. The goal is not to break things — it is to learn what breaks and to fix it before it happens in production.

The principles

  1. Build a hypothesis — "if we kill the primary database, the failover completes in under 30 seconds and the error rate returns to baseline within 1 minute."
  2. Define the steady state — the metrics that characterize the healthy system (error rate, latency, throughput, SLO).
  3. Introduce the failure — kill the database, drop the network, corrupt the config.
  4. Verify the hypothesis — does the system recover as predicted? If not, the hypothesis is wrong (or the system has a bug).
  5. Fix the gap — the system did not recover as expected; the gap is the learning; the fix is the action item.

What to inject

FailureWhat it tests
Instance kill Does the load balancer route around it? Does the service auto-recover?
AZ failure Does the multi-AZ deployment survive? Does the failover complete?
Region failure Does the multi-region deployment failover? What is the recovery time?
Network latency Does the timeout work? Does the retry succeed? Does the circuit breaker open?
Network partition Does the system split-brain? Does the consensus protocol recover?
Packet loss Does the application handle lost messages? Does the retry storm?
Database slow Does the read replica take over? Do the slow queries back up?
Database down Does the failover work? Does the cache absorb the reads?
DNS failure Does the client cache resolve? Does the fallback work?
Disk full Does the log rotation work? Does the process fail gracefully?
Memory exhaustion Does the OOM killer terminate the right process? Does the replacement start?
Clock skew Does the timestamp-based logic break? Does the JWT validation fail?
Dependency failure Does the circuit breaker open? Does the fallback work? Does the error propagate gracefully?
Certificate expiry Does the renewal work? Does the client reject the connection?
Traffic spike Does the auto-scaling work? Does the load shedding prevent the cascade?

The tools

The game day

A game day is a planned exercise — a specific failure, a specific hypothesis, a specific set of observers. The structure:

PhaseActivity
Plan Choose the failure; write the hypothesis; identify the metrics; notify the participants
Pre-flight Verify the baseline; confirm the hypothesis; the rollback is ready
Execute Inject the failure; monitor; note the timeline
Observe Does the system respond as predicted? What was the detection time? The mitigation time?
Recover Remove the failure; verify the system returns to normal; the baseline is restored
Debrief What happened? What surprised us? What are the action items?

The game day example

Hypothesis: "If the primary database is killed, the failover to the replica completes in under 30 seconds, and the error rate returns to baseline within 2 minutes."

TimeEventMetric
10:00Baseline confirmedError rate 0.02%, p99 150 ms
10:01Primary database killed—
10:01:15Error rate spikesError rate 15%
10:01:25Failover beginsAlert fires
10:01:45Replica promotedError rate 5%
10:02:00Traffic routed to new primaryError rate 1%
10:03:00Error rate back to baselineError rate 0.02%

The hypothesis was partially correct — the failover completed in ~45 seconds (not 30), and the error rate recovered in 2 minutes. The finding: the failover is slower than expected. The action item: investigate the failover delay; possibly reduce the health check interval.

The "we cannot test in production" objection

Chaos engineering is often objected to as "too risky for production". The response:

  • Production is where the failures happen. Testing in staging tests the staging environment; the production environment has different traffic, different data, different configuration.
  • The failures will happen anyway. The only question is whether the team has practiced the response, or discovers it during the real incident.
  • Start small. The first experiments are low-blast-radius — kill one non-critical instance; inject a brief network delay; verify the recovery. Gradually increase the scope as the confidence grows.
  • Use a game day, not continuous chaos. Netflix runs Chaos Monkey continuously; most teams start with planned game days and gradually automate the safe experiments.

The continuous chaos

The mature practice is continuous chaos — the failure injection runs continuously, at a low rate, so the system is always being tested. Netflix's Chaos Monkey kills instances in production every day; the system is designed to tolerate it. The benefit: the failures are caught and fixed continuously, not batched into a quarterly game day.

The prerequisites: the system is genuinely designed for failure (auto-scaling, retries, circuit breakers); the observability is good enough to detect the problem (metrics, traces); the team is practiced (the game days came first).

The learning loop

Chaos engineering is a learning loop:

  1. Hypothesize — the system should recover from this failure.
  2. Test — inject the failure; observe.
  3. Learn — the system did not recover as expected; the gap is the learning.
  4. Fix — the code, the configuration, the runbook.
  5. Repeat — the next game day; the system is more resilient.
Common Pitfall

Running a game day without a hypothesis. The failure is injected, the team watches the dashboards, and afterwards no one can say what was learned. The fix: the hypothesis is the point — "the system should recover in X seconds" — and the verification is whether the hypothesis holds. Without a hypothesis, the game day is a demo, not an experiment.

Interview Framing

Say: "Chaos engineering is deliberate failure injection to verify recovery. The hypothesis is the point — the system should recover in X seconds — and the game day tests it. Start small, in production, with a clear hypothesis and a rollback. The learning is the gap between the hypothesis and the actual behavior." That covers the discipline and the practice.
