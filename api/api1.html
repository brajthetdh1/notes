Part A — Vocabulary API, protocol, service, contract, SDK

1

What is an API, and what role does it play in a distributed system?

Short Answer

An API (Application Programming Interface) is a defined contract by which one piece of software requests behaviour or data from another. In a distributed system, the API is the architecture — it is the only thing two separately deployed services can see of each other. Everything else — language, database, internal structure — is private, and the API is the boundary that makes independent evolution possible.

What an API actually is

Strip away the marketing and an API is three things: a set of operations (what can be asked), a set of schemas (what the inputs and outputs look like), and a set of guarantees (what happens on failure, what is atomic, what is idempotent). The URL and the HTTP method are just the transport for those three things. When people say "the API changed", they usually mean one of the three changed — most often the guarantees, which is the change that breaks clients hardest.

Why the API is the architecture in a distributed system

In a monolith, one module calling another is a function call: fast, synchronous, transactional, and invisible to the outside world. In a distributed system, one service calling another crosses a network — which means latency, partial failure, and an inability to roll back together. The API is the seam where these differences become visible. It is where:

  • Coupling is decided. A narrow API allows a service to be rewritten; a wide API makes every consumer a stakeholder in every internal change.
  • Failure is exposed. A function call either returns or throws. An API call can time out, return a 500, return a 200 with a stale body, or return a 429. The API's error contract is what makes failure legible.
  • Versioning happens. Two teams deploy on different schedules, so the API must support old and new consumers simultaneously — or one team is blocked.
  • Security is enforced. Authentication, authorisation, and rate limiting all live at the API boundary because it is the only place the system can see "who is asking and for what".

The four roles an API plays

  1. Interface for clients. The public contract that mobile apps, web frontends, and third parties code against.
  2. Contract between services. The internal protocol by which microservices cooperate — often gRPC rather than REST for performance reasons.
  3. Boundary for the domain. The API defines what a service is from the outside, which is the mechanism by which bounded contexts (in the DDD sense) stay bounded.
  4. Surface for operations. Metrics, tracing, rate limiting, and access logs all hang off the API boundary. A service with no API is a service you cannot observe.

Why this matters in a design interview

When an interviewer asks you to "design the system", they expect you to draw boxes and arrows — and each arrow is an API. The quality of the design is largely the quality of those APIs: are they narrow, are they versioned, are they idempotent where they need to be, do they expose internal state, do they allow independent deployment? A candidate who draws a beautiful diagram with vague arrows has designed an API surface that will not survive contact with a second team. A candidate who says "this endpoint is idempotent, takes an idempotency key, and returns 202 with a status URL" has demonstrated the thing the interviewer is actually testing.

The interface as a product

For public APIs — Stripe, Twilio, GitHub — the API is the product. The quality of the design determines adoption, and a breaking change is a business event, not just an engineering one. This is why companies invest in API design reviews, style guides, and versioning policies. Internal APIs benefit from the same discipline, just with a smaller blast radius: a bad internal API spreads through the organisation and becomes impossible to change.

Interview Framing

Say: "The API is the only thing these two services know about each other, so I want it to be narrow, versioned, and explicit about failure." That single sentence signals you understand the API is the architecture, not an afterthought drawn on top of it.

What is the difference between an API, a protocol, and a service?

Short Answer

A protocol is a set of rules for how bytes move across a wire (HTTP, TCP, WebSocket, gRPC's HTTP/2 transport). An API is a contract for what those bytes mean — the operations, schemas, and guarantees layered on top of the protocol. A service is the running deployment of software that implements one or more APIs. Protocol is the grammar, API is the language, service is the speaker.

LayerWhat it definesExamples
ProtocolWire format, message framing, connection semantics, error signalling at the transport levelHTTP/1.1, HTTP/2, HTTP/3, TCP, WebSocket, gRPC's HTTP/2 transport, AMQP
APIOperations, request/response schemas, status semantics, guaranteesStripe API, GitHub REST API, Slack Web API, an internal orders.v1 gRPC service
ServiceA running deployment of software that implements APIsorders-service (2 replicas in eu-west-1), auth-service (5 replicas)

Concrete example

Suppose you have an orders service. It speaks HTTP/2 (the protocol), exposes a GET /v1/orders/{id} endpoint returning a JSON document with a defined schema (the API), and runs as three pods behind a load balancer (the service). If you replace it with a gRPC implementation tomorrow, the protocol changes (HTTP/2 with gRPC framing), the API changes (from JSON over HTTP to protobuf over gRPC), but the service — the logical thing that owns order data — is unchanged. The distinction matters because each layer has a different rate of change and a different set of concerns.

Why the distinction matters in design

  • Protocol choice is a performance and compatibility decision. HTTP/1.1 vs HTTP/2 affects connection multiplexing. TCP vs QUIC affects head-of-line blocking. This is separate from what the API means.
  • API design is a product and coupling decision. It determines what clients can do and how easily the implementation can change. The same API can be served over different protocols — GraphQL over HTTP, gRPC over HTTP/2, or a REST API implemented in any language.
  • Service topology is an operational decision. How many replicas, in which regions, on which hardware, with which deployment strategy. This is about the runtime, not the interface.

The common conflation

"We use a REST API" is often a statement about the protocol (HTTP), the style (REST), and the service (a running deployment) all at once. In an interview, being precise distinguishes you: "The API is REST over HTTPS, implemented by the orders service which runs three replicas" is much stronger than "we use REST". The same applies to "we use gRPC" — gRPC is a protocol plus a code-generation framework, not a service description.

Protocols vs APIs in the OSI model

Protocols live in layers 5–7 of the OSI model: HTTP is layer 7, TCP is layer 4, TLS is between. APIs are not in the OSI model at all — they are semantic agreements built on top. This is why protocol changes (HTTP/1.1 to HTTP/2) are usually invisible to the API, and why API changes (renaming a field) do not require a protocol change. Conflating the two leads to designs like "we will switch to gRPC to fix our API design problems" — which does not work, because gRPC is a transport, not a design methodology.

Trade-off

Protocol choices are largely reversible (a proxy can translate HTTP/1.1 to HTTP/2, or REST to gRPC). API choices are much harder to reverse, because they live in every client's code. This is why the API deserves careful design and the protocol can be chosen pragmatically.

Common Pitfall

Saying "the API is the service". An API can be implemented by many services (a façade), and a service can expose many APIs (public REST, internal gRPC, admin REST). Keeping the terms separate lets you reason about which one is changing when something breaks.

What is an API contract, and why does it matter?

Short Answer

An API contract is the complete, precise, testable specification of how an API behaves: its operations, request and response schemas, status codes, error formats, idempotency guarantees, ordering guarantees, and rate limits. It is the thing two teams can point at and say "this is what we agreed to". When the contract is vague, every consumer guesses, and every guess is a future outage.

What a contract includes

  • Operations. Every endpoint, method, and path, with its purpose.
  • Schemas. Field names, types, formats, required/optional, validation rules.
  • Status codes. Which codes can be returned, and what each means in this API's context.
  • Error format. The structure of error responses and the set of error codes.
  • Guarantees. Idempotency, atomicity, ordering, consistency, rate limits, timeouts.
  • Versioning policy. How and when the contract can change, and how consumers are notified.
  • Security. Authentication scheme, scopes, permissions per operation.

A contract that specifies operations and schemas but not guarantees is not a contract — it is a menu. The guarantees are exactly what distinguishes a well-run API from a fragile one, because they determine what happens when the network misbehaves.

Why it matters — four reasons

1. Independent evolution. Two teams can develop simultaneously against a shared contract, using mocked servers or generated clients, without waiting for each other. This is the entire point of microservices, and it collapses if the contract is ambiguous.

2. Testability. A contract can be turned into executable tests — contract tests — that run on every build. A schema violation fails the build instead of the client's production. This is what tools like Pact, Schemathesis, and Dredd do.

3. Documentation. A machine-readable contract (OpenAPI, Protobuf, GraphQL SDL) can generate reference docs, client SDKs, and server stubs automatically. The documentation cannot drift from the implementation because it is generated from the same file.

4. Change management. A contract lets you define what counts as a breaking change. Renaming a field, removing a field, tightening validation — each is a change to the contract that requires a version bump and a deprecation process. Without a contract, every change is a coin flip.

How to express a contract

StyleFormatTooling
RESTOpenAPI 3.x (JSON/YAML)Swagger, Redoc, Stoplight, openapi-generator
gRPCProtocol Buffers (.proto)protoc, buf, grpc-gateway
GraphQLSchema Definition Language (SDL)Apollo, GraphQL Codegen

Design-first vs code-first

Design-first writes the contract before any implementation, generates stubs, and treats the contract as the source of truth. It surfaces disagreement early (while it is cheap), enables parallel work, and is the industry best practice for anything consumed by another team. Code-first generates the contract from annotated code. It is faster to start and easier to keep consistent with the implementation, but it tends to produce contracts that reflect the implementation rather than the domain, and it makes review harder because reviewers must infer the contract from code.

The best practice for public or multi-team APIs is design-first with contract tests in CI. For internal single-team APIs, code-first with a good annotation setup is acceptable.

Contract testing

Contract tests verify that the implementation still satisfies the contract, and that consumers are using the API as specified. The two patterns are provider-side tests (the provider verifies it fulfils the contract) and consumer-driven tests (each consumer publishes its expectations, the provider verifies it satisfies all of them). Pact is the standard tool for consumer-driven. Without contract tests, the contract is documentation; with them, it is an enforced agreement.

Common Pitfall

Treating the OpenAPI file as a formality that is generated after the fact and never validated. A contract that is not tested is a contract that has already drifted. The value comes entirely from the enforcement: CI must fail when the implementation violates the contract.

What is the difference between a public API, a partner API, and an internal API?

Short Answer

Internal APIs are consumed by services you own, deployed together, and can break freely-ish. Partner APIs are consumed by a known, finite set of external organisations under a contract — stable but with coordinated change. Public APIs are consumed by anyone, including unknown developers, and therefore require the highest stability, documentation, security, and support bar. The same engineering team may produce all three, with the same code, but the design constraints are completely different.

DimensionInternalPartnerPublic
ConsumersYour own servicesNamed external organisationsAnyone
Change cadenceFast; coordinated deploymentPlanned; announcementsSlow; strict versioning
VersioningLight — often just re-deployDeprecation windows (weeks/months)Long windows (months/years)
DocumentationInternal wiki, code commentsPartner portal, integration guidesPublic docs, tutorials, SDKs
AuthmTLS, service tokensOAuth, API keys with scopesOAuth, API keys, signature schemes
Rate limitingCoarse, capacity-basedPer-partner quotasPer-plan tiers
SupportSlack, on-callAccount manager, SLADocs, community, maybe SLA
Breaking change costOne deploymentCoordinated migrationIndustry incident

Internal APIs

The defining property is that the producer and consumer are in the same organisation and usually the same deployment pipeline. This allows a level of informality that would be dangerous elsewhere: you can break an internal API if you update all consumers in the same PR, and the rollback is symmetric. The trade-off is that "internal" becomes a trap when the number of consumers grows beyond a handful or when the consumers are owned by teams that do not deploy together — at that point, an internal API has the same problems as a partner API and deserves the same discipline.

Internal APIs are usually gRPC for performance and schema enforcement (protobuf gives you a contract whether you want one or not), or REST/JSON for simplicity. Authentication is typically mTLS, service mesh identity, or short-lived service tokens.

Partner APIs

Partner APIs are interesting because they combine the stability requirements of a public API with the manageability of a small, known consumer set. You know exactly who the consumers are, so you can notify them directly of changes and coordinate migrations. But you cannot deploy them, so you must publish versioning policies and honour them.

The key design patterns are: scoped API keys per partner (so revocation is surgical), per-partner rate limits (so one partner cannot starve others), signed webhooks (so partners can trust the source), and a sandbox environment (so partners can test without touching production). Partner APIs typically have SLAs, which means their failure is a contractual event, not just an engineering one.

Public APIs

A public API is a product. Its consumers are unknown, its failure modes are public, and its design directly affects revenue. The design constraints are the strictest:

  • Backward compatibility is sacred. Adding a field is fine; removing one requires a deprecation period measured in months. Consumers you have never heard of depend on it.
  • Versioning is explicit. /v1/ in the URL or a version header, with a documented support policy.
  • Documentation is comprehensive. Reference docs, tutorials, code samples in multiple languages, a changelog, and a status page.
  • Security is exposed to hostile actors. Enumeration prevention, rate limiting, DDoS mitigation, OAuth flows, secret rotation.
  • Developer experience is a competitive differentiator. Time-to-first-call, SDK quality, and error messages determine adoption.

When the classification blurs

In practice, many APIs sit between categories. A "public" API might really be a partner API in disguise (fintech). An internal API consumed by twenty teams is functionally a partner API. The right question is not "which category is this?" but "how many consumers, how much do I control them, and what is the cost of breaking one?" — and design to that answer.

Interview Framing

Say: "This is a partner API, so I'll version it, scope the API keys per partner, and enforce per-partner rate limits — but I don't need the full public-API documentation surface." That demonstrates you are designing to the consumer, not applying a one-size-fits-all discipline.

What is the difference between an API and an SDK?

Short Answer

An API is a contract — the interface exposed over the network. An SDK (Software Development Kit) is a library that wraps that API for a specific language, handling the protocol, authentication, retries, and serialisation so the developer does not have to. The API is the source of truth; the SDK is a convenience layer on top of it.

DimensionAPISDK
What it isContract: endpoints, schemas, guaranteesLibrary: code that calls the contract
FormNetwork protocol (HTTP, gRPC)Language-specific package (npm, pip, Maven)
Who consumes itAny client, in any languageDevelopers in one language
Failure semanticsStatus codes, error bodiesExceptions, typed errors, retries
VersioningURL/header versioned, independentSemver, tied to language ecosystem
Support burdenDocs and contractMultiple languages, each maintained

What an SDK buys you

  • Reduced boilerplate. Instead of constructing HTTP requests, handling JSON, and parsing responses, the developer calls client.orders.create(...) and gets a typed object.
  • Authentication handling. The SDK manages tokens, refresh, and signature computation — notoriously hard to get right manually.
  • Retry and backoff. The SDK knows which errors are retryable and implements exponential backoff with jitter by default. Manual retries are usually wrong.
  • Pagination helpers. Iterators, auto-pagination, and cursor management are wrapped in ergonomic APIs.
  • Type safety. Compiled languages get compile-time checking; typed languages like TypeScript get autocomplete and refactor safety.
  • Consistency across the ecosystem. All consumers in a language use the same idioms, which makes code review, onboarding, and debugging easier.

What an SDK costs

  • Maintenance burden per language. A public API with SDKs in five languages is five codebases to test, version, and release, each with its own ecosystem conventions and compatibility matrix.
  • Update lag. When the API adds a feature, the SDK lags behind. Users who need the new feature immediately must bypass the SDK — which is often harder than using raw HTTP.
  • Hidden behaviour. SDKs add retries, caching, and connection pooling that the developer cannot easily see or control. When something goes wrong, the mental model is wrong.
  • Version lock. An SDK that depends on a specific runtime version, or a specific transitive dependency, can force users onto versions they do not want.

The "SDK is a product" trap

Stripe and Twilio are famous for their SDKs, and for good reason — the SDK is often what developers experience rather than the raw API. But this means the SDK is the product for those developers, and its quality determines adoption. A buggy SDK will block adoption of a great API, and a great SDK can mask a mediocre API. The design principle: build the API first, make it usable directly, and then build the SDK as a convenience, not as a requirement.

Generated SDKs vs hand-written SDKs

Modern tooling (openapi-generator, protoc, GraphQL Codegen) can generate SDKs from a machine-readable contract. This is invaluable for breadth — you get consistent clients in ten languages without ten teams. The trade-off is that generated code often lacks idioms: awkward method names, no retry logic, no pagination helpers. The best practice is generated SDKs as a starting point, with hand-written wrappers on the hot paths for the languages that matter most.

In an interview

If you are asked to "design an API", do not jump to the SDK. The API is the contract; the SDK is a distribution mechanism. Saying "I'll provide SDKs in Python and TypeScript generated from the OpenAPI spec, with hand-written ergonomic wrappers for pagination and retries" shows you understand both layers and their trade-offs. Saying "I'll design the SDK" without designing the API reveals that you are thinking about the wrong abstraction.

Interview Framing

Say: "The API contract is the source of truth. I'll generate SDKs from it for the languages we care about, but keep a thin hand-written layer for ergonomics on hot paths." That demonstrates you understand the relationship and are not conflating the two.

Part B — The Four Major Styles REST, RPC, gRPC, GraphQL, plus tRPC and SOAP

What is REST, and what are its architectural constraints?

Short Answer

REST (Representational State Transfer) is an architectural style defined by Roy Fielding in 2000. It has six constraints — client-server, statelessness, cacheability, uniform interface, layered system, and code on demand (optional). An API is only truly RESTful if it satisfies all six. Most "REST" APIs satisfy the first three and call it a day, which is why the distinction between "REST" and "RESTful" matters.

The six constraints

ConstraintWhat it meansWhat it buys
Client-server UI and data storage are separated; each evolves independently Portability of UI, scalability of server
Statelessness Each request contains all information needed to process it; the server stores no per-client session state Horizontal scaling, easier recovery, simpler failure handling
Cacheability Responses must be explicitly marked as cacheable or non-cacheable Reduced load, lower latency, CDN compatibility
Uniform interface Resources identified by URLs, manipulated through representations, self-descriptive messages, HATEOAS Simplicity, discoverability, independence from implementation
Layered system Client cannot tell if it is connected directly to the origin or to an intermediary Proxies, gateways, load balancers without client changes
Code on demand (optional) Servers can send executable code (JavaScript) to clients Extensibility — rarely used in APIs

Why statelessness matters most

Of the six, statelessness is the one that most affects the design and is most often violated. In a stateless API, every request must carry its own authentication token, its own idempotency key if relevant, and its own pagination cursor. The server does not remember who you are between requests. This is what makes horizontal scaling possible — any server can handle any request — and it is what makes failure handling simple: a crashed server loses nothing because there is nothing to lose.

The cost of statelessness is bandwidth: tokens and context are sent on every request. The cost is real but usually worth it. Session cookies, sticky sessions, and server-side session state all trade the scaling benefit for a small bandwidth saving, and the trade almost never pays off in a modern system.

The uniform interface in practice

Four sub-constraints make up the uniform interface:

  1. Resource identification. Every resource has a URL — /users/42, /orders/2024-01.
  2. Manipulation through representations. Clients modify state by sending representations (JSON bodies), not by calling RPC-style methods. A PUT /users/42 with a full representation, not POST /updateUser.
  3. Self-descriptive messages. Responses include media types, which specify how to parse them. The client does not need out-of-band knowledge.
  4. HATEOAS (Hypermedia as the Engine of Application State). Responses include links to related resources and valid next actions, so clients can discover the API dynamically rather than hardcoding URLs.

HATEOAS is the constraint almost no one implements, and it is the most debated. In practice, most APIs document their URL structure and clients hardcode it. This makes HATEOAS an academic nicety in most cases — but it also means most "REST" APIs are really "HTTP-based RPC with resource-oriented URLs".

What most "REST" APIs actually are

Real-world REST APIs satisfy client-server, statelessness, cacheability, uniform interface (partially), and layered system. They usually skip HATEOAS and often violate the uniform interface by using verbs in URLs (POST /users/42/activate). This is fine — it is a pragmatic compromise, not a failure. But when an interviewer asks "is your API RESTful?" the honest answer is often "it's HTTP-based, resource-oriented, and satisfies most of the constraints but not HATEOAS" — and saying that demonstrates more understanding than claiming "yes, fully REST" when the API has verbs in URLs.

Common Misconception

"REST = JSON over HTTP." No — REST is an architectural style, JSON is a serialisation format, and HTTP is a protocol. You can do REST over XML; you can do JSON over a non-REST API. The style is about constraints, not formats.

What is RPC, and how does it differ from REST?

Short Answer

RPC (Remote Procedure Call) models a remote call as a function call: createUser(...) rather than POST /users. REST models the API as a set of resources operated on by a uniform set of verbs. RPC is action-oriented and natural for operations; REST is resource-oriented and natural for CRUD. Neither is better — they optimise for different things.

DimensionRESTRPC
Mental modelResources (nouns)Operations (verbs)
URL style/users/42/createUser, /getUser?id=42
HTTP methodsMeaningful (GET, POST, PUT, PATCH, DELETE)Usually POST for everything
CachingNative HTTP cachingRequires custom cache keys
IdempotencyDerived from the methodMust be designed explicitly
Best forCRUD, public APIs, resource-heavy domainsActions, workflows, internal service calls
ToolingOpenAPI, Swagger, browsersProtobuf, Thrift, gRPC

What RPC actually buys you

The natural fit is when the operation is not a CRUD operation. transferFunds(from, to, amount) is not a resource — it is an action with side effects on two resources. Modelling it as POST /transfers with a body is a REST-idiomatic compromise, but the underlying semantics are RPC-shaped. For workflows, transactions, and domain operations, RPC models the intent directly, which makes the API easier to use and reason about.

RPC also allows richer type systems. In gRPC, the client and server are generated from a strongly-typed schema (protobuf), which means compile-time checking, code completion, and consistent serialisation across languages. REST can match this with OpenAPI codegen, but the ecosystem is less integrated.

What REST buys you

The natural fit is when the domain is fundamentally resource-shaped and the operations are CRUD-like. Users, posts, comments, products, orders — these are resources, and GET /users/42 is more natural than getUser(id=42). The uniform interface means the same patterns apply everywhere: caching, pagination, filtering, and conditional requests are baked into HTTP.

REST also wins for public APIs because developers already know HTTP. A developer can test a REST API with curl without any client library. They can inspect it in a browser or a proxy. They can cache it with a CDN without configuration. The learning curve is nearly zero, and the tooling is universal.

The hybrid reality

Most real APIs are hybrids. A REST API for resources (GET /users/42) plus RPC-style endpoints for actions (POST /users/42/verify-email). This is fine and increasingly common. The design principle is not "pick one" but "use REST for resources, RPC for actions, and be consistent about which is which".

JSON-RPC and XML-RPC

Before gRPC, there were standard RPC protocols over HTTP. JSON-RPC wraps every call in a standard envelope — {"jsonrpc": "2.0", "method": "transfer", "params": [...], "id": 1} — which gives you consistent error handling and batching across all methods. XML-RPC did the same with XML and is now mostly legacy. These are the RPC patterns to name if an interviewer asks about "RPC over HTTP".

When to choose RPC

  • The operations are actions, not CRUD. Transfers, workflows, batch jobs, domain commands.
  • Internal service-to-service. Performance, schema enforcement, and codegen are worth more than HTTP caching.
  • Strong typing is a requirement. When the client and server must agree on every field, protobuf enforces it.
  • Streaming is needed. RPC frameworks support server-push and bidirectional streaming natively; REST does not.
Trade-off

RPC is natural for operations but loses the HTTP ecosystem — caching, conditional requests, browser tooling, CDN support. REST is natural for resources but awkward for actions. The pragmatic answer is a hybrid: REST for the resource surface, RPC for the action surface. Keep them clearly delineated so consumers know what to expect.

What is gRPC, and why is it faster than REST/JSON?

Short Answer

gRPC is an RPC framework from Google that uses Protocol Buffers (binary serialisation) over HTTP/2 (multiplexed transport). It is faster than REST/JSON for three reasons: binary payloads are ~3–10× smaller than JSON, HTTP/2 multiplexes many concurrent calls over one connection without head-of-line blocking, and protobuf deserialisation is significantly cheaper than JSON parsing. It also gives strongly-typed clients generated from a .proto file, which makes schema drift impossible.

The three performance reasons

  • Binary serialisation. JSON is text: {"id": 42, "name": "Alice"} is 30 bytes. Protobuf is binary: the same message might be 6 bytes. Payload size matters most on high-latency, low-bandwidth networks — mobile, cross-region, high-fan-out microservices.
  • Faster parsing. JSON parsing involves a parser, string allocation, and type coercion. Protobuf is a length-prefixed binary format with generated decoders — typically 5–10× faster to decode, which matters when a service handles tens of thousands of RPCs per second.
  • HTTP/2 multiplexing. HTTP/1.1 serialises requests on a single connection (with pipelining being a partial and abandoned solution). HTTP/2 multiplexes many streams over one TCP connection, eliminating head-of-line blocking at the HTTP layer and reducing connection overhead. gRPC uses HTTP/2 by default, so a single connection can carry hundreds of concurrent calls.

Benchmarks, honestly

In practice, gRPC is often 2–10× faster than REST/JSON for small messages on local networks, with the gap narrowing for large payloads or over high-latency networks. The 10× numbers come from microbenchmarks with tiny payloads and no I/O. In a real system, gRPC's advantage is often more about connection efficiency and typed clients than raw serialisation speed.

What gRPC gives you beyond speed

  • Generated clients and servers. The .proto file is the contract; code is generated for every language, so client and server are always in sync.
  • Streaming. Unary, server-streaming, client-streaming, and bidirectional-streaming RPCs are first-class. This is enormously harder in REST.
  • Deadlines and cancellation. Every call carries a deadline; the framework propagates it and cancels work when exceeded. REST requires manual implementation.
  • Rich error model. google.rpc.Status encodes error codes, messages, and structured details, with a standard mapping to HTTP status codes for gateways.
  • Interceptors. Middleware for auth, logging, tracing, and retries is first-class.

What gRPC costs

  • Browser support is limited. gRPC-Web requires a proxy (Envoy) and has limitations (no bidirectional streaming). For browser clients, REST or GraphQL is usually still easier.
  • Debugging is harder. Binary payloads are opaque; you need grpcurl and a .proto file. curl and browser dev tools do not work.
  • Caching is harder. HTTP caching (ETag, Cache-Control) is built into HTTP/1.1 and understood by every CDN. gRPC does not play well with HTTP caches.
  • Schema changes are visible. Adding a field is backward-compatible in protobuf, but removing one or changing its type is a breaking change that requires a new field number — a discipline many teams get wrong.

The standard architecture

The dominant pattern is gRPC for internal service-to-service, REST/GraphQL at the edge. The edge (API gateway) terminates HTTP, authenticates the client, and translates to gRPC internally. The services speak gRPC to each other for performance, streaming, and typed contracts. This combines the ecosystem of HTTP externally with the performance of gRPC internally.

When to choose gRPC

  • Internal microservices where performance and schema enforcement matter.
  • Streaming RPCs — real-time updates, log tailing, bidirectional interaction.
  • Polyglot environments where consistent codegen across languages saves months.
  • Mobile clients where payload size and battery matter.
  • Low-latency services where the 3–5× serialisation speedup is meaningful.
Common Misconception

"gRPC is always faster than REST." It is faster for small, frequent, internal calls. For large payloads, the compression difference shrinks. For browser clients, gRPC-Web adds a proxy hop. For cached reads, HTTP caching dominates the raw performance difference. Choose gRPC for the ecosystem (typing, streaming, codegen), not just for the benchmark.

What is GraphQL, and what problems does it solve?

Short Answer

GraphQL is a query language and runtime for APIs, developed at Facebook in 2012. The client specifies exactly what data it needs in a single query, and the server returns exactly that shape. It solves over-fetching (getting more fields than needed), under-fetching (needing multiple round trips to get complete data), and client-driven schema evolution (adding fields without breaking clients).

The problems GraphQL solves

  • Over-fetching. A REST endpoint GET /users/42 returns every field the server thinks the client might want. On mobile, most of those fields are wasted bandwidth. In GraphQL, the client asks for { user(id: 42) { name avatar } } and gets exactly those two fields.
  • Under-fetching and the N+1 problem. In REST, getting a user, their posts, and each post's comments requires three sequential calls (or one heavily nested custom endpoint). In GraphQL, one query fetches all three levels in a single round trip.
  • Client-specific views. Different clients (mobile, web, partner) need different shapes of the same data. In REST, this means multiple endpoints or heavy client-side filtering. In GraphQL, each client queries the shape it needs from the same schema.
  • Rapid frontend iteration. When the frontend needs a new field, the backend does not need a new endpoint — the schema is extended and the client queries it. This decouples frontend and backend release cycles.
  • Strongly-typed schema. The GraphQL schema is a contract, in the same way OpenAPI or protobuf is, and tooling generates typed clients automatically.

The core concepts

ConceptMeaning
SchemaThe type system that defines what can be queried — types, fields, arguments
QueryA read request; selects fields from types
MutationA write request; changes server state
SubscriptionA real-time stream; server pushes updates
ResolverA function that fetches the data for a field
FragmentA reusable set of fields
DirectiveMetadata on a query (@include, @skip)

The N+1 problem and DataLoader

GraphQL has its own performance trap. A query that fetches 100 posts and, for each, resolves its author will invoke the author resolver 100 times — one database lookup per post. This is the N+1 problem, and it can turn a 10 ms query into a 1-second one. The solution is DataLoader: a batching and caching layer that collects all the author IDs for a single event-loop tick, issues one batched query, and distributes the results. Every GraphQL server needs this discipline, or it will collapse under load.

What GraphQL costs

  • Complexity. The server is harder to build — resolvers, batching, caching, authorisation per field. The schema is a new artifact to design and version.
  • Query complexity attacks. A malicious client can submit a deeply nested query that forces the server to fetch enormous amounts of data. Mitigations: depth limits, complexity scoring, and cost analysis before execution.
  • Caching is hard. HTTP caching assumes the URL identifies the resource. In GraphQL, every query is POST /graphql with a body — so HTTP caching does not apply. You must implement application-level caching (persisted queries, CDN-friendly GET queries) or accept the loss.
  • Monitoring is harder. A single GraphQL endpoint handles all operations, so per-field performance and errors are less visible than per-endpoint REST metrics.
  • Not naturally RESTful. GraphQL is not REST and does not claim to be — that is fine, but it is a different paradigm with a different ecosystem.

When GraphQL is the right choice

  • Client-driven products where the frontend iterates faster than the backend.
  • Aggregating multiple backends into one graph — GraphQL as an API gateway is a common pattern.
  • Multiple heterogeneous clients — mobile, web, partner — needing different shapes.
  • Rich, nested data models where a single query naturally spans several resources.
Interview Framing

Say: "GraphQL is right here because the web and mobile clients need different shapes of the same data, and the frontend iterates faster than the backend. I'll add depth and complexity limits, use DataLoader to solve N+1, and use persisted queries for CDN caching." That shows you know the pattern and its known problems.

What are tRPC and SOAP, and when would you use each?

Short Answer

tRPC is a TypeScript-only RPC framework that eliminates the schema/contract layer entirely by sharing TypeScript types between client and server. It is astonishingly ergonomic for full-stack TypeScript apps and unusable outside them. SOAP is an XML-based enterprise protocol with strict WSDL contracts, WS-Security, and transaction support. It is heavy and old-fashioned, but it is still mandated in banking, healthcare, and government integrations.

tRPC — the TypeScript-native RPC

In tRPC, the server defines procedures as TypeScript functions. The client imports the type of the server's router and gets full type inference across the network — no schema files, no code generation, no .proto, no OpenAPI. When you rename a field on the server, the client fails to compile. When you add an argument, the client sees it in autocomplete. It is the closest thing to "call the server like a function" that the web ecosystem has produced.

When tRPC is the right choice:

  • Full-stack TypeScript — Next.js, Remix, SvelteKit, or a React frontend talking to a Node backend.
  • Small teams, internal products, or MVP-stage products where the ergonomic win is large.
  • Monorepo setups where client and server code are in the same repository and can share types.

When tRPC is wrong:

  • Non-TypeScript clients (mobile, Python, Go, third parties) — they cannot consume tRPC at all.
  • Public APIs — you cannot publish a TypeScript type as a contract for the outside world.
  • Multi-language organisations — the server is TypeScript-only, so the backend team is locked to TypeScript.

SOAP — the enterprise survivor

SOAP (Simple Object Access Protocol) wraps every message in an XML envelope and defines the interface in WSDL (Web Services Description Language). It has a strict, machine-readable contract, built-in security (WS-Security), transaction support (WS-AtomicTransaction), and reliable messaging (WS-ReliableMessaging). It runs over HTTP, but also over SMTP, JMS, and raw TCP.

Why it survives:

  • Formal contracts. WSDL is precise and machine-verifiable in ways OpenAPI historically was not. Enterprises like this for compliance and integration testing.
  • Security standards. WS-Security supports message-level signing and encryption, which is necessary for some banking and government scenarios where TLS alone is not accepted.
  • Transactions and reliability. WS-AtomicTransaction and WS-ReliableMessaging provide guarantees that REST does not.
  • Legacy integration. Existing enterprise systems (SAP, Oracle, mainframes) expose SOAP interfaces, and there is no business case to rewrite them.

When SOAP is the right choice:

  • Integrating with a partner whose API is SOAP — the choice is made for you.
  • Highly regulated industries (banking, insurance, healthcare) where WS-Security and message-level signing are mandated.
  • Enterprise service buses and legacy systems.

When SOAP is wrong: everything else. It is verbose, its tooling is dated, its learning curve is steep, and it is dramatically slower and heavier than REST or gRPC. For new APIs, there is no reason to choose it except regulatory mandate.

The comparison

AspecttRPCSOAP
LanguageTypeScript onlyAny (via WSDL tooling)
ContractShared TypeScript typesWSDL (XML)
FormatJSONXML
PerformanceFastSlow — large XML payloads
EcosystemTiny, modernHuge, legacy, enterprise
Best forFull-stack TS appsBanking, healthcare, enterprise integration

Why these two sit together in an interview

They represent the extremes of the API spectrum. tRPC is the newest, most ergonomic, most language-locked approach — it optimises for developer velocity within a narrow ecosystem. SOAP is the oldest, most formal, most interoperable approach — it optimises for regulated enterprise integration. Naming both demonstrates that you understand API styles are chosen for context, not for fashion.

Interview Framing

Say: "If this were a full-stack TypeScript product, tRPC would be the fastest way to ship. But it has non-TypeScript clients and a public surface, so I'll use REST or GraphQL and generate TypeScript types from the schema instead." That shows you know tRPC exists and understand its constraints.

What is the difference between "REST" and "RESTful"?

Short Answer

"REST" is the architectural style; "RESTful" is a description of an API that satisfies REST's six constraints. In practice, "REST" has become a shorthand for "HTTP + JSON" — most so-called REST APIs are not RESTful at all. The distinction matters because calling an API RESTful when it is not is a signal that the designer does not understand the constraints — and therefore does not know when they are being violated.

What "RESTful" requires

An API is RESTful only if it satisfies all six constraints from Fielding's dissertation:

  1. Client-server — separation of concerns between UI and data.
  2. Statelessness — no per-client session state on the server.
  3. Cacheability — responses declare themselves cacheable or not.
  4. Uniform interface — resource identification via URLs, manipulation through representations, self-descriptive messages, and HATEOAS.
  5. Layered system — clients cannot tell if they are talking to the origin or an intermediary.
  6. Code on demand (optional) — servers may send executable code.

What most "REST" APIs actually satisfy

ConstraintSatisfied by typical API?
Client-serverYes — almost universally
StatelessnessUsually — unless cookies/sessions are used
CacheabilityOften ignored — Cache-Control headers missing
Uniform interface (resources, URLs)Often, but verbs creep in (/activate)
Uniform interface (HATEOAS)Almost never — clients hardcode URLs
Layered systemYes — gateways and proxies are everywhere
Code on demandRarely, and it is optional

The typical "REST" API is HTTP-based, resource-oriented, mostly stateless, and missing HATEOAS. It is closer to "HTTP RPC with nouns" than to REST. That is fine — it is a good pragmatic style — but calling it RESTful is inaccurate.

Why the distinction matters in design

  • If you claim RESTful, you invite the constraints. If you are missing cache headers, an interviewer can point out that your API is not cacheable, which means your CDN strategy is broken.
  • HATEOAS is the dividing line. Almost no API implements it, which means almost no API is actually RESTful. Saying "the uniform interface here is resource-oriented URLs and HTTP verbs, but not HATEOAS, because our clients hardcode URLs" is more honest than claiming full REST.
  • REST is a spectrum, not a binary. A well-designed HTTP API that satisfies five of six constraints is more RESTful than one that satisfies three. The point is not the label, it is the discipline.

What to say instead

A more accurate vocabulary: "HTTP API" or "resource-oriented HTTP API" for most of what people call REST. "RPC over HTTP" for RPC-style endpoints with HTTP transport. "REST" reserved for APIs that genuinely satisfy the constraints. This precision is not pedantry — it is what lets you reason about caching, statelessness, and versioning correctly.

The pragmatist's view

For an internal API, the label does not matter. For a public API, the label is marketing, and "REST" is the term developers search for. The pragmatic approach: use the vocabulary that gets you the ecosystem (REST, HTTP, JSON) and implement the constraints that give you benefits (statelessness, cacheability, resource orientation). Skip the ones that cost more than they give (HATEOAS for most APIs). Be honest about the compromises when asked.

Common Misconception

"RESTful means using JSON and HTTP verbs." No — you can do RPC over HTTP with JSON and verbs and be entirely non-RESTful. The style is about constraints, not surface syntax. A RESTful API over XML with a proper uniform interface is more RESTful than a JSON API with verbs in URLs.

Compare REST, RPC, GraphQL, and gRPC — when would you choose each?

Short Answer

Choose REST for public, resource-oriented APIs where the HTTP ecosystem (caching, browsers, tooling) is valuable. Choose gRPC for internal service-to-service where performance, streaming, and typed contracts matter. Choose GraphQL for client-driven products with heterogeneous clients and rapidly iterating frontends. Choose plain RPC (JSON-RPC, tRPC) for small teams in a single language where the action is the unit of work.

DimensionRESTgRPCGraphQLJSON-RPC / tRPC

TransportHTTP/1.1, HTTP/2HTTP/2HTTP (usually POST)HTTP
FormatJSON (usually)ProtobufJSONJSON

The five decision questions

  1. Who are the consumers? Unknown developers → REST. Known internal services → gRPC. Multiple client types needing different data shapes → GraphQL. Full-stack TypeScript team → tRPC.
  2. What is the access pattern? CRUD → REST. Actions and workflows → RPC. Arbitrary nested reads → GraphQL. Streaming → gRPC or WebSocket.
  3. What is the performance requirement? If internal latency is paramount → gRPC. If public cacheability is paramount → REST. If the frontend is doing a lot of round trips → GraphQL.
  4. What is the ecosystem constraint? Browser clients → REST or GraphQL. Mobile with limited bandwidth → gRPC. Enterprise partners → SOAP or REST.
  5. What does the team already know? The style that the team can execute well beats the style that is theoretically optimal.

The hybrid architecture

The dominant modern pattern is REST or GraphQL at the edge, gRPC internally:

  • Public API: REST or GraphQL, over HTTPS, cached by a CDN, authenticated with OAuth.
  • API gateway: terminates HTTPS, authenticates, rate-limits, translates to gRPC.
  • Internal services: gRPC between each other — performance, typed, streaming-capable.
  • Data access: services query their own databases and may speak gRPC or events to each other.

This combination gives the client ecosystem the ubiquity of HTTP and the internal system the performance and contract enforcement of gRPC. It is what most large-scale systems converge on.

Anti-patterns to avoid

  • "We use GraphQL for everything" — GraphQL for a simple CRUD API is overkill; the complexity of a GraphQL server is not worth it when clients just need GET /users/42.
  • "We use gRPC for the public API" — browser clients cannot consume it directly, so you need a gRPC-Web proxy, which negates much of the benefit.
  • "We use REST internally" — internal services benefit from typed contracts and streaming; REST is not the wrong answer, but gRPC is often better.
  • "We use tRPC for a public API" — you cannot publish it to non-TypeScript consumers.
  • "We mix all four" — a system where different teams use different styles is a system with no shared understanding. Pick one dominant style per layer.

The choice that matters most

In an interview, the most important decision is usually edge vs internal. Whatever you pick at the edge (REST, GraphQL), the internal services should use something faster and more typed (gRPC). Say this explicitly, and the interviewer knows you have thought about the two layers separately.

Interview Framing

Say: "REST at the edge because the client ecosystem demands it; gRPC internally because performance and typed contracts matter. If the frontend iterates faster than the backend, I'll add GraphQL as a gateway over the gRPC services." That names all four styles and their roles in three sentences.

What is the difference between a synchronous and an asynchronous API?

Short Answer

A synchronous API returns the result in the same request-response cycle — the client blocks until it gets the answer. An asynchronous API accepts the request, returns immediately with an acknowledgement (usually 202 Accepted), and delivers the result later via a status endpoint, webhook, or queue. Sync is simpler and immediate; async is necessary when the operation is slow, bursty, or requires coordination across services.

AspectSynchronousAsynchronous
Client behaviourBlocks until responseReturns immediately, polls or receives callback
Response200 OK with result202 Accepted with status URL or task ID
Latency budgetSub-secondSeconds to hours
Failure handlingImmediate — client retries or failsOut-of-band — status endpoint, webhook, dead letter
Resource useConnection held openConnection released immediately
CouplingTight — the caller waitsLoose — the caller moves on
Best forLookups, writes, low-latency opsBatch jobs, media processing, external calls, slow workflows

When sync is the right answer

  • Reads and lookups. GET /users/42 is synchronous by definition — the client needs the answer to proceed.
  • Fast writes. Creating a record that commits in 5 ms — synchronous is fine and simplest.
  • User-initiated operations. When the user is waiting for a response (login, form submit), synchronous is what they expect.

When async is the right answer

  • Slow operations. Video transcoding, report generation, ML inference — anything that takes more than a few seconds.
  • External dependencies. Calling a third-party API that might take 10 seconds — sync requests hold a thread for the duration, which is expensive.
  • Bursty work. A flash sale produces 100,000 orders in a minute — processing them asynchronously smooths the load and prevents cascade failures.
  • Multi-step workflows. An order involves payment, inventory, shipping, notification — coordinating these synchronously means any failure makes the user wait for the slowest step.
  • Operations with unpredictable latency. Machine learning, third-party calls, batch jobs — you cannot promise a latency SLO, so you must not block.

The async API patterns

There are three ways to deliver the result of an async operation:

  1. Polling. The client gets a task ID and polls GET /tasks/{id} until status is completed. Simple, universally supported, but wastes requests and is slow to reflect completion.
  2. Webhooks. The client provides a URL, and the server POSTs the result when done. Efficient, but requires the client to have a public endpoint and handle retries and signatures.
  3. Streaming. The client holds a WebSocket or SSE connection and receives the result as it becomes available. Best for incremental results, but requires long-lived connections.

The 202 Accepted pattern

The standard way to acknowledge an async request: return 202 Accepted with a Location header pointing to the status resource, and a body containing the task ID and any initial state. The client then polls or waits for a webhook. The status endpoint should return 200 with the current state (pending, running, completed, failed) and, when complete, the result.

Critical detail: the status endpoint must be idempotent and cheap. It is polled frequently and must not itself be an expensive operation.

Idempotency in async

Async operations must be idempotent, because the client will retry if the initial request times out — and the initial request may have already been accepted. The standard solution is an idempotency key: the client sends a UUID with the initial request, and the server returns the same task ID for repeated requests with the same key. This is even more critical for async than sync, because the "did it work?" ambiguity is greater.

Trade-off

Synchronous APIs are simpler for the client but hold resources for the duration of the operation. Asynchronous APIs free resources immediately but shift complexity to the client (polling, webhooks, state machines) and to the server (task queues, status tracking, retries). Choose async when the operation is slow, external, or bursty — sync otherwise.

What is the difference between a batch API and a bulk API?

Short Answer

A batch API executes multiple independent operations in a single HTTP request — for efficiency and atomicity. A bulk API operates on a large collection of a single resource type — importing 10,000 rows, uploading a file. Batch is about grouping; bulk is about volume. Batch is usually synchronous and transactional; bulk is usually asynchronous and streaming.

AspectBatch APIBulk API
PurposeGroup several operations into one requestMove large volumes of one type of data
Typical size2–100 operations1,000–1,000,000 items
ShapeArray of heterogeneous requestsOne homogeneous dataset
ResponseArray of per-operation resultsJob ID + status, or streaming response
AtomicitySometimes all-or-nothingRarely — partial success is expected
Sync/asyncUsually synchronousUsually asynchronous
ExampleStripe's /batch endpointSalesforce Bulk API, Elasticsearch _bulk

Batch APIs in detail

A batch endpoint accepts an array of operations and returns an array of results. The classic example is Stripe's batch endpoint, which lets a client make up to 100 API calls in one HTTP request. The advantage is network efficiency — 100 requests become 1 — and the option for atomicity — either all succeed or all fail.

Partial success handling. The most important design decision in a batch API is what happens when some operations succeed and others fail. There are three options:

  • All-or-nothing. Any failure rolls back the entire batch. Simple for the client but wasteful — one bad item invalidates 99 good ones.
  • Best-effort. Each operation succeeds or fails independently, and the response contains a per-item status. This is the standard for most APIs.
  • Configurable. The client specifies atomic: true or false in the request. Most flexible, but requires the server to support both.

The response must be per-item: [{status: 200, body: {...}}, {status: 409, error: {...}}]. A top-level 200 means "the batch was processed" — the individual statuses tell you what actually happened. Returning a single 4xx for a partially-failed batch is a common design mistake.

Bulk APIs in detail

A bulk API is built for volume. The typical pattern:

  1. Create a bulk job: POST /bulk-jobs → returns a job ID.
  2. Upload data in batches: PUT /bulk-jobs/{id}/batches — usually 10,000 rows per batch.
  3. Close the job: POST /bulk-jobs/{id}/close.
  4. Poll status: GET /bulk-jobs/{id} → returns processing, completed, or failed.
  5. Download results: GET /bulk-jobs/{id}/results — per-row success/failure.

This is the Salesforce Bulk API model, and it is what large-scale data import/export looks like. The key design properties:

  • Chunked upload. A million rows cannot fit in one HTTP request. Chunking allows resumable uploads — if the network fails at 500,000, the client resumes rather than restarting.
  • Async processing. The server can process the data at its own pace, with retries and dead-letter handling.
  • Per-row results. A bulk import almost always has some bad rows. The result must be per-row, so the client knows which to fix.
  • Idempotency. Re-uploading the same batch should not duplicate rows. Use a client-provided batch ID or a natural key for upsert.

The rules of thumb

  • If it fits in one request (under ~1 MB), use a batch API.
  • If it needs chunking (over ~10 MB), use a bulk API.
  • If the client needs per-item atomicity, use a batch API.
  • If the client needs to stream, use a bulk API.

Combining them

The best bulk APIs are built on top of batch APIs. The bulk job chunks the data into batches, and each batch is processed by the batch endpoint. This gives the bulk API the volume handling and the batch API the per-item semantics, without duplicating logic. Design the batch API first, and the bulk API becomes a scheduler around it.

Common Pitfall

Designing a "bulk" endpoint that accepts 100,000 rows in one synchronous HTTP request. It will time out, it will exhaust memory, and it will not be resumable. Anything over a few thousand items must be asynchronous and chunked — this is not optional, it is a physical limit of the request lifecycle.

What is a webhook, and how does it differ from a callback and an API call?

Short Answer

A webhook is a user-defined HTTP callback — you give a service a URL, and the service POSTs to that URL when an event occurs. An API call is you asking the server for something; a webhook is the server telling you something happened. A callback is the general programming concept of passing a function (or in this context, a URL) to be invoked later; a webhook is the HTTP-specific instance.

AspectAPI callWebhook
DirectionClient → ServerServer → Client
TimingClient-initiated, immediateServer-initiated, on event
DeliveryResponse is the resultHTTP POST to the registered URL
ReliabilityClient controls retriesServer controls retries — must be documented
AuthClient presents credentialsServer signs the payload; client verifies
OrderingSequential by clientNot guaranteed — must be designed for

Why webhooks exist

Without webhooks, the only way to know when something happens on another system is to poll. Polling is wasteful — a client checking every 10 seconds for a status that changes once a day makes 8,640 requests for one event. Webhooks flip the model: the client registers interest once, and the server delivers only when there is something to deliver. This is enormously more efficient and gives lower latency for event-driven workflows.

The canonical use cases: payment providers (Stripe notifies on payment success), CI/CD (GitHub notifies on push), messaging (Slack notifies on message events), infrastructure (AWS notifies on S3 uploads). Every modern B2B SaaS platform exposes webhooks for exactly this reason.

The delivery contract

A well-designed webhook system must specify:

  • Event types. Which events exist, and what triggers each. Document the schema of each payload.
  • Subscription API. How the client registers a URL, which events it wants, and how to deactivate. POST /webhooks, DELETE /webhooks/{id}.
  • Retry policy. How many retries, with what backoff, over what window. The standard is exponential backoff (1s, 5s, 30s, 5m, 30m, ...) over 24 hours, with a per-attempt timeout (e.g., 5 seconds).
  • Delivery semantics. At-least-once, which means duplicates are possible — and receivers must handle them idempotently.
  • Ordering. Almost no webhook system guarantees ordering. The receiver must use the event timestamp or a sequence number to handle out-of-order delivery.
  • Signature. Each payload must be signed with a secret, so the receiver can verify the sender. HMAC-SHA256 of the body with a shared secret is the standard.
  • Dead-letter handling. After retries are exhausted, what happens? A DLQ the client can query, a UI to view failures, or both.

The receiver's responsibilities

Webhook receivers have as much design work as senders:

  • Respond quickly. Most senders time out at 5 seconds. If the work takes longer, respond immediately and process asynchronously via a queue.
  • Verify the signature. Before processing, verify the HMAC. Reject unsigned or incorrectly-signed payloads.
  • Be idempotent. The same event may be delivered twice. Use the event ID as an idempotency key.
  • Handle out-of-order events. Use the event timestamp or sequence number to reconcile.
  • Protect against SSRF. If you also send webhooks, never POST to localhost, private IPs, or metadata services.
  • Return 2xx quickly. Non-2xx triggers retries — make sure your handler distinguishes "I cannot accept this" from "I am currently down".

Webhook vs callback

In programming, a callback is a function passed to another function to be invoked later. A webhook is the HTTP equivalent: a URL passed to a remote service to be invoked on an event. The terms are often used interchangeably in API design, and "callback URL" is a common synonym for "webhook URL". The distinction is only meaningful if you are discussing the general concept vs the HTTP-specific implementation.

Webhook vs polling — the decision

Use a webhook when the client can run a public HTTPS endpoint, when latency matters, and when event volume is low relative to polling frequency. Use polling when the client cannot accept incoming connections (behind a firewall, mobile-only), when the client needs to control timing, or as a fallback when webhooks fail. A well-designed system supports both: webhooks as the primary channel, polling as the reconciliation mechanism.

Common Pitfall

Assuming webhooks are reliable. They are best-effort: the network can drop them, the receiver can be down, the sender's retry policy can expire. Always provide a reconciliation endpoint — "list events since timestamp T" — so a receiver that missed events can recover. Webhooks without reconciliation are a system that silently loses data.

Streaming APIs: WebSocket, SSE, and long-polling — when does each apply?

Short Answer

WebSocket is bidirectional and persistent — best for chat, real-time collaboration, and games. Server-Sent Events (SSE) is unidirectional (server → client) over plain HTTP — best for feeds, notifications, and progress updates. Long-polling is a hack that keeps an HTTP request open until data is available — a fallback when neither WebSocket nor SSE is possible. The choice depends on directionality, infrastructure, and fallback requirements.

DimensionWebSocketSSELong-polling
DirectionBidirectionalServer → client onlyServer → client (per request)
TransportTCP (upgraded from HTTP)HTTP/1.1 or HTTP/2HTTP
Protocolws://, wss://text/event-streamStandard HTTP
ReconnectionManualAutomatic, with Last-Event-IDPer-request
Binary supportYesNo — text onlyYes (base64)

Browser supportExcellentExcellent (except IE)Universal
Best forChat, collab editing, gamesFeeds, notifications, progressFallback only

WebSocket in detail

WebSocket opens a persistent, full-duplex connection. After a one-time HTTP upgrade handshake, the connection stays open, and both sides can send frames at any time. Frames are tiny (2–14 bytes of overhead, versus hundreds for HTTP), so the per-message cost is minimal. This makes it the right choice for anything where the client sends frequent small messages — keystrokes in collaborative editing, moves in a game, typing indicators in chat.

The design challenges:

  • Connection management. Each connection holds server resources. Millions of concurrent connections require a distributed gateway tier with connection state per server.
  • Reconnection. WebSocket does not reconnect automatically. The client must detect the drop (heartbeat), reconnect, and re-synchronise state — including any messages missed during the disconnect.
  • Routing. To deliver a message to user X, the server must know which gateway node holds X's connection. A registry (Redis pub/sub, a coordination service) is required.
  • Load balancer support. Not all load balancers handle WebSocket upgrades gracefully. Sticky routing (to keep a connection on the same node) and idle timeouts must be configured.

Server-Sent Events in detail

SSE is a one-way stream from server to client, over a plain HTTP connection with the media type text/event-stream. The server sends lines like event: update\ndata: {"id": 42}\n\n, and the client receives them via the EventSource API.

SSE's advantages:

  • Works over HTTP/1.1 and HTTP/2. No upgrade handshake, no special load balancer support.
  • Automatic reconnection. The browser reconnects automatically if the connection drops.
  • Last-Event-ID recovery. The client sends the last event ID it received, so the server can resume from where the client left off. This is enormously useful and much harder with WebSocket.
  • Simple implementation. No protocol framing, no special client library — just a streaming HTTP response.

SSE's limitations: it is unidirectional (the client must use regular HTTP for actions), it is text-only (binary must be base64-encoded), and there is a per-domain connection limit in some browsers (6 per domain over HTTP/1.1 — much higher on HTTP/2).

Long-polling in detail

The client sends a normal HTTP request, and the server holds it open until an event occurs or a timeout fires. When the server responds, the client immediately sends another request. It is essentially a simulation of push over pull.

It is a fallback, not a first choice. The cost is high: each request requires a full round trip, headers are expensive, and the server must manage many open requests. But it works everywhere — no special protocol, no load balancer configuration, no browser restrictions. When WebSocket and SSE fail (usually because of a corporate proxy that breaks streaming), long-polling is the fallback.

The decision framework

  1. Does the client need to send frequent messages? Yes → WebSocket. No → SSE or long-polling.
  2. Does the infrastructure support streaming? Yes → SSE. No → long-polling.
  3. Do you need binary data? Yes → WebSocket. No → SSE.
  4. Do you need automatic reconnection and recovery? Yes → SSE. No → either.

The fallback chain

Robust real-time APIs implement a fallback chain: try WebSocket, fall back to SSE, fall back to long-polling, fall back to short-polling. Socket.IO does this automatically. Building it yourself is considerable work but is the right answer for a product that must work on hostile networks — corporate proxies, old browsers, restrictive firewalls.

Interview Framing

Say: "For the notification feed I'll use SSE because it is unidirectional, works over HTTP, and has automatic reconnection. For the chat interface I'll use WebSocket because both sides need to send messages continuously." That names the directionality and infrastructure constraints that drive the choice.

What is the difference between an API gateway and a service mesh in terms of API design?

Short Answer

An API gateway sits at the edge and handles north-south traffic — clients entering the system. It is application-aware, exposes the public API surface, and implements authentication, rate limiting, and routing. A service mesh sits inside the cluster and handles east-west traffic — service-to-service calls. It is infrastructure, not API design: it implements mTLS, retries, and observability transparently, without exposing any new API surface.

The API gateway's role in API design

The gateway is where the public API is defined. It handles:

  • Routing. /v1/orders/* goes to the orders service; /v1/users/* to the users service. The public URL does not expose internal service names.
  • Authentication. OAuth token validation, API key lookup, JWT verification. The gateway resolves the identity and forwards it as a trusted header to the backend.
  • Rate limiting. Per-client, per-endpoint, per-plan. Enforced before the request reaches the backend, which is the only place it can actually protect the system.
  • Request/response transformation. The gateway can rename fields, aggregate responses, and translate between the public API and the internal service contract.
  • Versioning. /v1/ and /v2/ can route to different backend services, letting old and new versions coexist.
  • BFF pattern. A gateway per client type (mobile, web, partner) with a shape tailored to that client.
  • Canary and blue-green routing. Weighted routing, header-based routing, and traffic mirroring.

Every one of these is a decision about the public API: what clients can call, how they authenticate, how much they can call, and what shape they see. The gateway is therefore an API-design artifact.

The service mesh's role in API design

The service mesh handles the calls between services. It does not define API surfaces — it makes the existing surfaces reliable and secure. Its role:

  • mTLS. Every service gets a cryptographic identity and encrypts all internal traffic. This is the strongest justification for a mesh — it is a security property that no service team has to implement.
  • Retries and timeouts. Default policies applied uniformly across every service, so no team forgets to configure them.
  • Circuit breaking. Uniform protection against cascading failures.
  • Observability. Every request is traced and metered, with consistent labels.
  • Traffic management. Weighted routing for canary deploys, fault injection for chaos engineering, mirroring for testing.

The mesh is an infrastructure layer that makes the existing APIs work. It is not where you design the public API — that happens at the gateway, and the internal APIs happen at the service level, and the mesh simply enforces cross-cutting concerns on them.

Where they overlap and where they do not

Both do retries, timeouts, and observability, but at different layers and for different reasons. The gateway's retries protect the backend from problematic clients; the mesh's retries protect a service from a flaky dependency. The gateway's observability is about who is calling what; the mesh's observability is about which service is slow.

Both can do traffic shifting, but the gateway's shifts are for public API versioning; the mesh's shifts are for internal canary deploys of one service.

The mesh is often not deployed at all in small systems. A gateway plus a shared library (or a few well-configured service clients) delivers most of the benefit with none of the operational cost. The mesh becomes worth it at around 20+ services where the uniformity of mTLS and observability justifies the new control plane.

Do you need both?

For a microservices deployment with external clients: yes, both. The gateway handles the public surface; the mesh handles the internal reliability. They are complementary, not alternatives.

For a small system: an ingress controller (which is a minimal gateway) plus a well-configured client library is enough. A mesh is over-engineering.

The decision to adopt a mesh should be driven by a specific need — usually the security requirement for universal mTLS, or the operational pain of inconsistent retry configuration across many services. Adopting it "because microservices" is a common and expensive mistake.

Common Misconception

"The service mesh is where I define my APIs." No — the service mesh is transparent infrastructure. Your APIs are defined by your services (and exposed by your gateway). The mesh routes, secures, and observes traffic for APIs it does not know the semantics of.
