Part A — The Status Code Vocabulary What each code actually means, and the pairs everyone confuses

1

Give the definitive guide to HTTP status codes — what each class means, and when to use each.

Short Answer

Status codes are grouped by class: 2xx success, 3xx redirection, 4xx client error, 5xx server error. A 4xx means the client sent something that cannot succeed on retry without changing the request; a 5xx means the server failed while the request was valid. Getting the class right matters more than the specific code — monitoring, alerting, retry logic, and caching all key off the class.

The full guide

The 2xx family in detail

  • 200 OK is the default success. Use it when the response body contains the result (a fetched resource, an updated resource).
  • 201 Created follows a POST that creates a resource. It must include a Location header pointing at the new resource, so the client can fetch it without a lookup.
  • 202 Accepted means the request was received and queued, but processing has not completed. It must include a way to check the status (a Location header to a status endpoint, or a job ID in the body). This is the correct code for any long-running operation (Volume 11 covers the full pattern).
  • 204 No Content is for a successful operation with no useful response body — typically a DELETE or a PATCH that does not return the updated resource. It must not include a body.
  • 207 Multi-Status is used by WebDAV for per-item results in a batch. Most modern APIs prefer 200 with a per-item body (see Question 9), because 207 is not widely understood and couples the response to WebDAV conventions.

The 3xx family — why APIs rarely use them

Redirects are a browser mechanism. Most APIs do not use them, with three exceptions:

  • 301/308 for deprecated endpoints — redirect old URLs to new ones so clients get the new location without updating. The difference: 301/302 allow the client to change the method to GET (historically), while 307/308 preserve the original method. For APIs, always use 307/308 to preserve POST semantics.
  • 304 Not Modified for conditional GETs — the client has a cached copy, and the server confirms it is still fresh. Covered in Volume 10.
  • 3xx for authentication flows in OAuth — the redirect from the client to the authorisation server (Volume 6, Question 3).

For an API endpoint that simply no longer exists, 410 Gone is the right code — not a redirect.

The 4xx family — client errors

A 4xx means the client sent a request that cannot succeed without modification. The three critical distinctions, covered in Questions 2 and 3, are:

  • 400 vs 422 — malformed vs semantically invalid.
  • 401 vs 403 — not authenticated vs authenticated but not authorized.
  • 404 vs 410 — does not exist (or you cannot know) vs existed and was permanently removed.

The class rule matters: a monitoring system that pages on any 4xx is broken, because legitimate clients produce 400s and 401s routinely. A monitoring system that pages only on 5xx is right — 5xx means the server failed at something the client did correctly.

The 5xx family — server errors

A 5xx means the client's request was valid but the server failed to fulfil it. The distinction between the codes (500, 502, 503, 504) is covered in Question 4. The general rule: a 5xx should always be retryable (with backoff), while a 4xx should not be.

The codes you should not use

  • 200 with an error in the body — the RPC-over-REST anti-pattern (Volume 2, Question 10). It breaks every monitoring system and forces the client to inspect every response body.
  • 418 I'm a teapot — fun, but not a real error code. Do not use it in production.
  • 999 or other non-standard codes — no tooling understands them, and clients will misclassify them.
  • 500 for validation errors — validation failures are the client's fault; 400 or 422 is correct.
  • 400 for internal errors — the client cannot fix what it did not cause; 500 is correct.
Interview Framing

Say: "The class matters more than the specific code — 4xx means the client is wrong and should not retry, 5xx means the server is wrong and retry may help. Then I pick the specific code for precision: 401 for authentication, 403 for authorization, 422 for validation, 409 for conflict." That covers the taxonomy and the practical guidance in two sentences.

What is the difference between 400 and 422, and which should you use for validation errors?

Short Answer

400 Bad Request means the request is malformed — invalid JSON, missing required field, wrong type. 422 Unprocessable Entity means the request is well-formed but semantically invalid — a valid date format in the past when future was required, a string that is the right type but not a valid email, a business-rule violation. In practice most APIs use 400 for everything; the precise design uses 400 for syntax and 422 for semantics.

Problem400 or 422?Why
Invalid JSON syntax400The request cannot be parsed
Missing required field400The request is structurally incomplete
Field has wrong type (string where int expected)400Structural error
Invalid Content-Type415Specific code for the media type
Email does not contain @422Well-formed string, invalid as a value
Birth date is in the future422Well-formed date, invalid semantically
Quantity exceeds the maximum allowed422Business rule violation
Field value not in the allowed enum422Structural or semantic, depends on the framing
Cross-field constraint (start_date > end_date)422Semantic
Business rule (cannot cancel a shipped order)422 or 409422 for validation; 409 if it is a state conflict

The historical context

422 was introduced in WebDAV (RFC 4918) and made its way into general use through Rails and Laravel. The distinction it encodes — "I understood what you sent, but I cannot process it" — is real and useful, but the industry has never agreed on exactly where the line falls. Some APIs use 422 for all semantic validation errors, some use 400 for both syntax and simple validation, and some (most) use 400 for everything.

This ambiguity is not a reason to avoid 422 — it is a reason to document the convention clearly. A client that expects 400 and gets 422 will misclassify the error. The documentation must state: "this API uses 400 for malformed requests and 422 for semantic validation errors" or "this API uses 400 for all client errors." Pick one and be consistent.

The argument for 400 for everything

  • Simpler. One code to know; clients handle one code path.
  • Widely understood. Every HTTP client, every library, every tool knows what 400 means.
  • What most APIs do. Stripe, GitHub, Twilio all use 400 for validation errors. The industry consensus has drifted toward simplicity.

The argument for 422

  • Precision. A client can distinguish "your JSON is broken" (fix the serializer) from "your value is invalid" (fix the input).
  • Richer monitoring. A spike in 400 means a client is sending malformed requests (probably a code bug); a spike in 422 means users are entering invalid values (probably a UX issue).
  • Semantic clarity. The code's name — Unprocessable Entity — says exactly what happened.

The pragmatic recommendation

For a new API, either is defensible. The recommendation:

  • Use 400 for syntax errors — invalid JSON, wrong types, missing required fields. These are mechanical; the client cannot fix them without changing the request.
  • Use 422 for semantic errors — the JSON is valid, the types are right, but the values do not make sense. This gives the client the precise signal.
  • Document the choice clearly in the API reference, with examples of each.
  • If simplicity wins (a small API, a client team that will not benefit from the distinction), use 400 for everything and move on. The distinction is only valuable if it is used.

The error body is what matters

The status code tells the client what class of error occurred. The error body tells it what specifically went wrong. A 400 with a body {"error": "Bad request"} is worse than a 422 with a body that says {"errors": [{"field": "email", "message": "must be a valid email address"}]}, because the client cannot act on the vague error. The error body does more work than the code — invest in it (Questions 5, 6, 7).

Common Pitfall

Using 500 for validation errors because the validation logic threw an exception. The validation failure is the client's fault (400/422), not the server's (500). This misclassification breaks every monitoring system — a spike in 500 should mean "the server is broken", not "users typed bad data".

Interview Framing

Say: "I'll use 400 for malformed requests — invalid JSON, wrong types. 422 for semantically invalid — valid format, invalid value. And the error body names the field and the rule, so the client can fix it." That demonstrates the distinction and the practical answer in one sentence.

3

Explain 401 vs 403, 404 vs 410, and 409 vs 412.

Short Answer

401 vs 403: not authenticated vs authenticated but not allowed. 404 vs 410: does not exist (or you cannot know it exists) vs existed and was permanently removed. 409 vs 412: state conflict (concurrent write, duplicate resource) vs a specific HTTP precondition failure (If-Match did not match). These three pairs are the source of more design debates than any others in the API world.

401 vs 403

Aspect401 Unauthorized403 Forbidden
MeaningYou are not authenticated, or your credentials are invalidYou are authenticated, but you do not have permission
Client actionLog in, refresh token, present credentialsDo not retry — the action is not permitted
Required headerWWW-Authenticate describing the auth schemeNone required
Body contentMinimal; do not leak whether the user existsShould not reveal the policy — could help an attacker map permissions
ExampleNo token, expired token, invalid signatureValid token, but the user is not an admin

The 401 code's name is misleading: "Unauthorized" really means "Unauthenticated". The distinction from 403 is that 401 invites the client to authenticate; 403 says the authenticated identity is not permitted. A client receiving 401 should prompt for login; a client receiving 403 should show an error.

The WWW-Authenticate header in a 401 response tells the client what kind of authentication is expected: WWW-Authenticate: Bearer realm="api" or WWW-Authenticate: Basic realm="api". A 401 without this header is technically malformed.

404 vs 410

Aspect404 Not Found410 Gone
MeaningThe resource does not exist — or you cannot know whether it existsThe resource existed and was permanently removed
PermanenceAmbiguous — may exist later, may never have existedPermanent — do not request it again
Client actionCheck the URL; do not retry immediatelyStop requesting; update bookmarks/code
CachingUsually not cached (unless explicitly)May be cached aggressively — the removal is permanent
ExampleGET /users/999 (no such user)GET /v1/users (v1 deprecated and removed)

The 410 code is underused. When an endpoint is deliberately removed, 410 tells the client "stop trying" — which is more informative than 404, which could mean "temporary glitch" or "wrong URL". Google's search crawler treats 410 as a signal to remove a page from the index faster than 404, for exactly this reason.

The security pattern (Volume 6, Question 1) uses 404 instead of 403 to hide existence: if a caller asks for another tenant's resource, returning 403 confirms it exists; returning 404 pretends it does not. This is the right trade-off for sensitive resources, but it must be documented — a 404 that might mean "forbidden" is confusing for legitimate clients debugging a problem.

409 vs 412

Aspect409 Conflict412 Precondition Failed
MeaningThe request conflicts with the current state of the resourceAn HTTP precondition (If-Match, If-None-Match) failed
CauseConcurrent write, duplicate resource, state transition not allowedETag or version did not match the current resource
Client actionRe-read the resource, merge, retry — or surface the conflictRe-fetch the resource to get the current ETag, then retry
WhenBusiness-level conflictOptimistic concurrency conflict (HTTP-specific)
ExampleCreating a user with an existing emailPUT with If-Match: "v1" when the resource is at "v2"

The distinction is subtle: 409 is the general "state conflict" code, 412 is specifically about the HTTP precondition mechanism. A PUT with If-Match that fails gets 412; a PUT without If-Match that conflicts with another write (e.g., a unique constraint violation) gets 409.

Both are retryable with a re-read, so a well-written client can treat them similarly. But the semantics are different: 412 says "the specific version I was checking did not match"; 409 says "there is a conflict with the current state". If the API uses If-Match for optimistic concurrency, 412 is the correct response — it gives the client a precise signal that the precondition failed (Volume 5, Question 8).

Why these pairs matter

Each pair represents a design decision that a client will build logic around. A client that treats 401 as "show a login prompt" and 403 as "show an error" behaves correctly; a client that treats both the same way behaves badly. Getting the codes right is not pedantry — it is what lets the client's error-handling code be correct without inspecting the error body.

Common Pitfall

Using 403 when the client forgot to send a token. That is 401. The distinction matters because a client receiving 403 will not try to log in — it will assume the user genuinely cannot do this. The result is that a client whose token has expired sees a confusing "forbidden" error instead of a clear "please log in".

4

What is the difference between 500, 502, 503, and 504?

Short Answer

500: the application threw an unhandled exception — the server itself broke. 502: a reverse proxy or gateway received an invalid response from an upstream service. 503: the server is temporarily unable to handle the request — overloaded, in maintenance, or starting up. 504: a proxy or gateway waited for an upstream that did not respond in time. The last three are gateway-adjacent — they describe the proxy's view of the request, not the application's.

CodeWho generatesWhat happenedClient action
500 The application Unhandled exception; a bug Retry with backoff; if persistent, report a bug
502 The proxy / gateway Upstream service sent an invalid response (malformed HTTP, connection reset, TLS failure) Retry with backoff; the upstream may be temporarily broken
503 The application or proxy Server overloaded, in maintenance, or starting up Retry after the Retry-After header; if persistent, check the status page
504 The proxy / gateway Upstream did not respond within the proxy's timeout Retry with backoff; if persistent, the upstream is slow or the operation is too heavy

500 Internal Server Error

The application's catch-all. The server received a valid request, attempted to process it, and an exception was thrown that the application did not catch. This is always a bug — either a genuine code defect, or a transient dependency failure (a database connection dropped), or a data issue (a null that should not be null).

A 500 response should not leak the exception details to the client — that is an information disclosure (Volume 14). Return a generic body with a correlation ID that the client can use to file a bug, and log the full exception server-side with the same correlation ID.

502 Bad Gateway

The proxy received an invalid response from the upstream. Common causes:

  • The application crashed and returned nothing.
  • The application returned malformed HTTP (a bug in a custom server, rarely).
  • The connection was reset (TLS handshake failure, protocol error).
  • The upstream is behind a load balancer that cannot reach any healthy instance.

502 is a signal that the request reached the proxy but could not reach (or got a bad response from) the backend. The client cannot fix this; it must retry. The operations team must investigate why the upstream is unreachable or misbehaving.

503 Service Unavailable

The server explicitly says "I cannot handle this right now". The most useful 5xx code because it carries a Retry-After header (or should):

CauseSignal
Overload (concurrency limit reached, thread pool exhausted)503 with Retry-After: 1
Planned maintenance503 with Retry-After: 3600 and a maintenance page
Deployment in progress503 with Retry-After: 10
Circuit breaker open503 (or a fallback response if one exists)

The Retry-After header converts 503 from "something is broken" to "try again in N seconds". A well-written client reads it and waits; a client that does not retries blindly and makes the overload worse.

504 Gateway Timeout

The proxy waited for the upstream for the configured timeout and gave up. Common causes:

  • The upstream is slow (a database query without an index, a slow downstream dependency).
  • The upstream is hung (deadlock, infinite loop).
  • The operation is genuinely too heavy for the proxy's timeout (e.g., a report query that takes minutes).

504 is the signal that the proxy's timeout is shorter than the upstream's actual latency. This is a design mismatch: either the timeout should be increased (if the operation is legitimately slow) or the operation should be made faster, or it should be async (Volume 11). For the client, 504 is retryable — the operation may succeed on the next attempt if the slowness was transient.

The layered timeout model

The reason 504 exists is that real systems have timeouts at every layer, and they must be ordered:

LayerTimeoutPurpose
Client30sThe client's patience
CDN / edge25sFail before the client does
Load balancer / proxy20sFail before the CDN does; return 504
Application15sFail before the proxy does; return 503 or 500
Database query10sFail before the application does

Each layer's timeout must be shorter than the layer above. If the application's timeout is longer than the proxy's, the proxy will time out first (returning 504), and the application will continue processing a request nobody is waiting for — wasted resources. The ordering ensures that the fastest-failing layer is the one closest to the resource, and the client's 504 or 503 comes with useful timing information.

Choosing the right 5xx

  • Application exception → 500. The default; the app cannot say more.
  • Upstream unreachable or malformed → 502. The proxy reports it.
  • Overloaded or in maintenance → 503, with Retry-After. The app or proxy signals recovery time.
  • Upstream slow → 504. The proxy timed out waiting.

The mistake to avoid: returning 500 for all upstream failures. A 500 tells the client "the server has a bug"; a 502/503/504 tells the client "the infrastructure is having a moment". The distinction changes the client's response (retry with backoff, check status page, file a bug) and the operations team's investigation path.

Common Pitfall

Returning 500 for rate limiting, authentication failures, or validation errors. A 500 pages the on-call engineer; a 429/401/422 does not. Using the wrong class for the error means every incident looks like a server bug, and the real bugs are lost in the noise.

Part B — Error Body Design RFC 7807, machine-readable codes, validation errors

5

What is RFC 7807, and how do you design an error body that a machine and a human can both understand?

Short Answer

RFC 7807 (now updated by RFC 9457) defines Problem Details for HTTP APIs — a standard JSON structure for error responses with fields type, title, status, detail, and instance. It gives every API a consistent error shape, so clients can parse any error without guessing the format, and extensions can be added without breaking the base contract.

The standard fields

FieldTypePurposeExample
typeURIIdentifies the error category — a stable, documentation-linked identifierhttps://api.example.com/errors/insufficient-funds
titlestringShort, human-readable summary of the error type (same for all instances of this type)Insufficient Funds
statusintegerThe HTTP status code (redundant with the response but useful when the body is parsed independently)422
detailstringHuman-readable explanation specific to this occurrenceAccount balance is $30, but the transfer requires $50.
instanceURIIdentifies this specific occurrence — usually a correlation ID or a link to the log entry/errors/instances/abc-123

The key insight: type and title are stable across occurrences — they say "what kind of error is this". detail is specific — it says "what happened this time". A client switches on type to decide what to do; a human reads detail to understand why.

A complete example

Response
 
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/insufficient-funds",
  "title": "Insufficient Funds",
  "status": 422,
  "detail": "Account balance is $30, but the transfer requires $50.",
  "instance": "/errors/instances/abc-123",
  "balance": 3000,
  "required": 5000,
  "currency": "USD"
}

The extension fields (balance, required, currency) are the RFC's greatest strength: the standard fields are the floor, and each error type can add structured data specific to its needs. A client parsing the response can rely on type, title, detail being present; the extensions are optional and specific.

The media type

RFC 7807 responses use Content-Type: application/problem+json, not application/json. This is a signal to the client: "this is a problem detail, not a normal response body". A client that checks the content type can route the response to the error handler; a client that does not still sees JSON, which is fine.

The media type also allows the API to distinguish a successful response with an error in the body (never correct, but possible in legacy APIs) from a genuine error response.

Designing your own error taxonomy

The type URI is the key design decision. Three conventions:

  • Documentation URL — https://api.example.com/errors/insufficient-funds. The URI points to a documentation page describing the error and what the client should do. This is the best practice: the client gets structured data, and a developer debugging can click the URL for the guide.
  • URN — urn:problem-type:insufficient-funds. Stable, but not resolvable. Use when you cannot guarantee a documentation URL.
  • About:blank — the RFC's default, meaning "no additional information beyond the status code". This is a placeholder, not a real choice.

The documentation URL convention is worth the effort. It turns every error into a self-documenting event: the client's error log contains a URL, the developer clicks it, and sees exactly what happened and what to do. This is one of the highest-leverage things an API can do for its developer experience.

The extension namespace

RFC 7807 recommends namespacing extension fields to avoid collisions across different error types. A simple prefix or a nested object works: retry_after_seconds is fine; if the API has many extensions, "meta": {"retry_after_seconds": 30} is cleaner. The standard fields are reserved and should not be overridden.

What to include in the body

FieldInclude?Why
Error type / codeAlwaysMachine-readable classification
Human-readable messageAlwaysFor debugging and user-facing display
Field-level errorsFor validationSo the client can highlight the offending field
Correlation / request IDAlwaysFor support to find the log entry
Documentation URLAlwaysSelf-documenting errors
Retry guidanceFor transient errorsRetry-After header, or a field
Stack traceNever (in production)Information disclosure (Volume 14)
Internal IDs, SQL, file pathsNeverInformation disclosure
Interview Framing

Say: "Every error uses RFC 7807 — type, title, status, detail, instance — with a documentation URL as the type so clients can look up what happened and what to do. Extension fields carry field-level details for validation errors." That demonstrates the standard and its value in one sentence.

6

How do you design machine-readable error codes that clients can switch on?

Short Answer

A machine-readable error code is a stable, lowercase, underscore-separated string that identifies a specific failure mode — insufficient_funds, card_declined, rate_limit_exceeded. It is the field that client code switches on; the human-readable message is for logs and UI. The code must be stable (part of the contract), specific (one failure mode per code), and documented.

Why a code, not just a message

A human-readable message is for humans. A program cannot reliably switch on "Your card was declined" — the wording might change, the language might be localised, the punctuation might differ. A machine-readable code is the stable identifier that the client matches against.

Client wants to…Matches on
Show a specific UI for "card declined"error.code === "card_declined"
Retry on rate limiterror.code === "rate_limit_exceeded"
Prompt the user to re-enter emailerror.code === "invalid_email"
Treat all "transient" errors the sameerror.category === "transient"

Without a code, the client has to string-match the message — which breaks the first time the message is reworded. The error code is the contract; the message is a convenience.

The naming conventions

  • Lowercase with underscores — insufficient_funds, not INSUFFICIENT_FUNDS or insufficientFunds. Case and separator should be uniform across the API.
  • Specific — one code per failure mode. invalid_request is too vague; a client cannot distinguish a missing field from a wrong type. invalid_email_format is specific.
  • Stable — the code is part of the contract. Renaming it is a breaking change (Volume 3, Question 1). Document it like any other public field.
  • Not overloaded — a code should not mean different things in different contexts. If not_found means "user not found" in one endpoint and "order not found" in another, the client cannot tell them apart. Better: user_not_found and order_not_found.
  • Extensible — clients must handle unknown codes gracefully (treat as a generic error in that category), so new codes can be added without breaking old clients.

The hierarchy: category, code, message

LevelPurposeStabilityExample
HTTP statusClass of failureVery stable422
CategoryBroad classificationStablevalidation, transient, auth
CodeSpecific failure modeStableinvalid_email_format
MessageHuman-readable explanationCan change"The email address 'foo' is not valid."
DetailsStructured data for this occurrenceVaries{"field": "email", "value": "foo"}

The category is useful when the client does not care about the specific code — "any transient error should be retried with backoff". The code is useful when the client does care — "show the card-declined UI specifically". The message is for humans. This three-level hierarchy gives clients the granularity they need at each level.

The mapping to HTTP status

Each code must correspond to a status code. The mapping is many-to-one: multiple codes can share a 422 (invalid_email_format, invalid_phone_format, invalid_date), but each code maps to exactly one status. This lets a client handle errors at the status level (does this need a retry?) and at the code level (what specifically went wrong?).

CodeStatusCategory
invalid_email_format422validation
insufficient_funds422business
card_declined402business
rate_limit_exceeded429transient

permission_denied403auth
resource_not_found404client

The documentation obligation

Every error code must be documented with:

  • Description — what it means.
  • Causes — the conditions that produce it.
  • Resolution — what the client should do.
  • Example — a request that produces it and the response.
  • Retryable — yes or no, and if yes, after how long.

This documentation is what makes the codes useful. A code without documentation is a code the client cannot act on — the client either ignores it or guesses, and either is worse than a clear error.

The evolutionary contract

Adding a new error code is a non-breaking change — clients that do not know it should treat it as a generic error in its category. Removing a code is breaking — clients that switch on it will break. Renaming a code is breaking for the same reason. The API version must reflect these changes (Volume 3).

Common Pitfall

Putting the same information in the message that should be in the code. "error": "Email is invalid" cannot be switched on; {"code": "invalid_email_format", "message": "Email is invalid"} can. The message should add context ("'foo' is not a valid email"), not replace the code.

How do you design validation error responses that a form can display?

Short Answer

A validation error response must identify every failing field in a single response (not just the first), with a machine-readable code per field, a human-readable message, and optionally the rejected value. The response shape should be an array under a dedicated field, so a form can highlight each error next to the corresponding input without re-parsing a string.

The naive response (and why it fails)

ResponseProblem
{"error": "Invalid input"}Which field? What is wrong?
{"error": "Email is invalid"}Which field is "email"? What is the value?
400 with only the first errorThe user fixes one field and discovers another
Errors as a single stringThe form cannot map them to fields

The structured response

Response
 
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation Failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/errors/instances/abc-123",
  "errors": [
    {
      "field": "email",
      "code": "invalid_email_format",
      "message": "The email address is not valid.",
      "value": "foo"
    },
    {
      "field": "birth_date",
      "code": "date_in_future",
      "message": "Birth date must be in the past.",
      "value": "2099-01-15"
    },
    {
      "field": "address.postal_code",
      "code": "invalid_postal_code",
      "message": "Postal code must be 5 digits for US addresses.",
      "value": "123"
    }
  ]
}

Field naming and nesting

The field value should match the JSON path of the field in the request body, so a form can map it to the input:

  • Simple field — "email".
  • Nested object — "address.postal_code" or "address[postal_code]".
  • Array element — "items[0].quantity" or "items.0.quantity".

The dotted path is the most common; it matches JSON Pointer (RFC 6901) if the API uses JSON Patch (Volume 2, Question 4). Document the convention clearly — a form implementation must know how to map it.

Every error, not just the first

The most common mistake: returning only the first validation error. The user fixes it, submits, and gets the next error — a terrible experience. A good API validates the whole request and returns all errors at once. The trade-off is complexity (the validation must run all rules, not fail-fast) — but the UX payoff is enormous.

The exception is when a later error depends on an earlier one — if password is missing, there is no point validating password_confirmation. For these, return only the first error in the dependency chain, and the independent errors from other fields.

Field-level codes

The code per field is essential for i18n and for UI. The form can show a localised message based on the code (invalid_email_format → "Please enter a valid email address") without relying on the server's English message. This is the same principle as the top-level error code (Question 6), applied per field.

The server's message is a fallback for the developer and a debugging aid. The client's translation is what the user sees.

Including the rejected value

Including the rejected value ("value": "foo") helps the form display "this is what you entered" and helps the developer debug. The exception is sensitive fields — never include the value of a password, a token, or a credit_card in a validation error. The response may end up in a log, a browser console, or an error tracker.

The status code

Validation errors are 400 or 422 (Question 2). The RFC 7807 body's type field identifies it as a validation failure (.../errors/validation), and the errors array is the structured data. This makes a validation error self-describing: the client sees type: ".../errors/validation" and knows to read the errors array.

What not to include

  • Stack traces — information disclosure.
  • The rule's internal name — "@Size(min=5,max=10)" is meaningless to the client. Use a semantic code instead.
  • All the possible values — if the field must be one of 10,000 enum values, do not list them all in the error. Give the client a link to a lookup endpoint.
  • The value for sensitive fields — passwords, tokens, credit cards.
Trade-off

Returning every error at once is better UX but requires more validation work (running all rules, not failing fast) and produces a larger response. For a small form, the difference is negligible; for a large batch import, validating everything can be expensive. The pragmatic answer: validate all fields in a single request, but for batch operations return the first N errors (with a "more" indicator) rather than a million.

Interview Framing

Say: "Validation errors use 422 with an RFC 7807 body and an errors array — every failing field, with a code, a message, and the rejected value. The field name is the JSON path so the form can map it to the input." That demonstrates the structured response and its purpose in one sentence.

How do you classify errors as retryable vs non-retryable, and how does the client know?

Short Answer

The HTTP status code class is the first signal: 4xx is non-retryable (the client must fix the request), 5xx is retryable (the server may recover), with exceptions for 408, 429, 409, and 412. Beyond the code, the response should include an explicit retryable flag or a Retry-After header so the client does not have to guess. The final arbiter is the error code, not the status — a 422 might be retryable if the validation failed for a transient reason.

The status-code signal

StatusRetryable?Notes
400 Bad RequestNoThe request is malformed; retry will fail identically
401 UnauthorizedYes — after refreshing the tokenNot a blind retry; fix the credentials first
403 ForbiddenNoPermission is fixed; retry will fail
404 Not FoundNoThe resource does not exist; retry will fail
408 Request TimeoutYesThe request took too long; retry with a shorter timeout or async
409 ConflictYes — after re-readingRetry after reconciling state
410 GoneNoPermanently removed
412 Precondition FailedYes — after re-fetching the ETagRetry with the current version
415 Unsupported Media TypeNoChange the Content-Type
422 Unprocessable EntityUsually noFix the input; exception for transient business rules
429 Too Many RequestsYes — after Retry-AfterWait and retry
500 Internal Server ErrorYes — with backoffThe server may recover
502 Bad GatewayYes — with backoffUpstream may recover
503 Service UnavailableYes — after Retry-AfterThe server is temporarily unavailable
504 Gateway TimeoutYes — with backoffThe upstream may be faster next time

The Retry-After header

For 429 and 503, the Retry-After header tells the client exactly how long to wait:

ValueMeaning
Retry-After: 30Wait 30 seconds
Retry-After: Wed, 21 Oct 2026 07:28:00 GMTWait until this date/time (HTTP-date)

The seconds form is simpler and immune to clock skew. Use it. The header converts "something is wrong" into "come back in N seconds", which is what a well-behaved client needs.

The explicit retryable flag

For cases where the status code is ambiguous — a 500 that is actually permanent (a bug), a 422 that happens to be transient (a temporary business rule) — the error body can include an explicit flag:

FieldValueMeaning
retryabletrueThe client may retry, with backoff
retryablefalseRetrying will not help
retry_after_seconds30Specific wait time (equivalent to Retry-After)
category"transient", "permanent", "validation", "auth"Classification the client can act on

The category is more useful than a binary flag because it lets the client differentiate: an auth error means "log in and retry"; a validation error means "fix the input"; a transient error means "wait and retry". A single "retryable" boolean cannot express these different recovery actions.

The idempotency requirement

A retry is only safe if the operation is idempotent or carries an idempotency key (Volume 5, Question 1). This is why the error response should be accompanied by idempotency design: a client that receives a 504 on a non-idempotent POST cannot retry without the risk of duplicate execution. The retryable flag should not be set to true for a non-idempotent operation that was not designed for retry — the client will duplicate.

The design rule: if the endpoint is non-idempotent, the response should say so — either by requiring an idempotency key (and returning 400 if it is missing) or by documenting that the client must not retry.

Retry with backoff and jitter

The retryable flag tells the client that retry is allowed. It does not tell it how to retry. The client must use exponential backoff with jitter (Volume 5, Question 10): wait 1s, 2s, 4s, 8s, and cap at ~30s. Without backoff, a retry storm amplifies the server's problem.

The Retry-After header overrides the backoff — if the server says "wait 30 seconds", the client should wait 30 seconds, not 1 second. This is particularly important for 429 and 503, where the server knows when it will be ready.

The "retry budget" perspective

A client should have a retry budget — a cap on total retries as a fraction of requests (Volume 5, Question 10). The error response can help: if the API consistently returns retryable errors for a specific client, the client's budget will exhaust and it will stop retrying. The API should also enforce a server-side retry budget (reject retries that arrive too quickly), so a misbehaving client cannot retry forever.

Common Pitfall

Marking a 500 as non-retryable because "it is a bug". A 500 is often transient (a connection dropped, a timeout, a temporary resource exhaustion) and a retry with backoff succeeds. Marking it non-retryable means legitimate transient failures become permanent client errors. The retryable flag should reflect the operation's retry-safety, not the error's apparent cause.

Interview Framing

Say: "The status class is the primary signal — 4xx is not retryable, 5xx is. Then the error body can add a category and a retry-after for precision. And retry is only safe if the operation is idempotent or has an idempotency key." That covers the signal, the nuance, and the safety requirement in one sentence.

How do you handle partial success in batch operations without lying to the client?

Short Answer

Return per-item results in a structured array, with each item carrying its own status, code, and (on success) the created or updated resource ID. The top-level status is 200 (the batch was processed) or 207 (WebDAV multi-status); the individual outcomes are in the array. Never return a single status for a batch with mixed results — it lies to the client about what happened.

The response shape

Response
 
HTTP/1.1 200 OK
Content-Type: application/json

{
  "results": [
    { "index": 0, "status": 201, "id": "user_1" },
    { "index": 1, "status": 409, "code": "duplicate_email",
      "message": "Email already exists" },
    { "index": 2, "status": 201, "id": "user_3" },
    { "index": 3, "status": 422, "code": "invalid_email_format",
      "message": "Email is not valid" }
  ],
  "summary": { "succeeded": 2, "failed": 2, "total": 4 }
}

The three design decisions

  1. Top-level status. The batch was "processed successfully" — even if some items failed. This is 200 OK (or 207 Multi-Status for the WebDAV-inclined). The top-level status does not signal whether the items succeeded; that is in the body.
  2. Per-item result. Each item carries its own status, code, message, and (on success) the resulting resource. The index field lets the client correlate the result to the request, even if the order is not preserved.
  3. Summary. A top-level summary object gives counts, so the client can quickly see "2 succeeded, 2 failed" without iterating the array.

The client's obligation

A client that receives a batch response must inspect every item — not just the top-level status. This is the whole point of the per-item structure. The client should:

  • Iterate the results and build a list of failures.
  • Decide what to do with failures (retry, report, skip).
  • Not assume "200 = success" at the batch level.

The API's documentation should state this explicitly. A client that treats 200 as "everything worked" will silently drop the failed items — which is a data integrity bug that might not surface for days.

Correlation by index or client ID

The index field matches the position in the request array. Alternatively, the client can supply a client-generated ID per item, which is echoed back:

ApproachProsCons
IndexSimple; no client changesFails if the server reorders the results
Client IDRobust to reordering; supports retry-by-IDClient must supply an ID per item
BothBelt and suspendersSlightly redundant

For most APIs, index is sufficient. For batch operations where the client may retry individual items, client IDs are worth the extra field — the client can retry by ID without knowing the array position.

When to use 207 vs 200

CodeWhenTrade-off
200 OK Batch processed; per-item results in the body Standard; clients see "success" and must read the body
207 Multi-Status WebDAV-style; signals mixed results at the status level Widely understood only in WebDAV; most tools treat it as 2xx anyway
400 / 422 The batch itself is malformed (not the items) Useful when the request is structurally wrong; per-item validation is separate

The pragmatic recommendation: use 200 OK with a per-item body. It is the standard, every client library understands it, and the body carries the important information. 207 adds complexity for minimal benefit outside WebDAV.

All-or-nothing vs best-effort

The batch can be designed as:

  • All-or-nothing — any failure rolls back the entire batch. The response is a single 400 with the failing item; the other items were not processed. Simpler for the client, but one bad item blocks the whole batch.
  • Best-effort — each item succeeds or fails independently. The response has per-item results. More useful for bulk imports, but the client must handle mixed outcomes.
  • Configurable — the client specifies atomic: true or false. Most flexible, but requires the server to support both.

For a batch of independent items (creating 100 users, updating 50 records), best-effort is the right default. For a transaction (moving money between accounts), all-or-nothing. The choice should match the domain, not the convenience of the implementation.

Idempotency in batch

A batch that partially succeeded must be safe to retry. The client retries the whole batch — the succeeded items fail with "already exists" or duplicate. The fix is per-item idempotency keys (Volume 5, Question 2) — each item carries a key, so retries are no-ops for the succeeded items. This is the only way to make partial batches safe to retry.

Common Pitfall

Returning a single 200 with no per-item information — "batch accepted". The client has no way to know which items succeeded, which failed, and why. The result is silent data loss: the client assumes everything worked, and the user discovers the missing records later. Every batch must return per-item results.

Interview Framing

Say: "A batch returns 200 with a per-item results array — status, code, and ID for each. The summary gives counts. The client must inspect every item; treating 200 as 'all succeeded' is a bug." That demonstrates the response shape and the client obligation in one sentence.

How do you handle errors in async operations and webhooks?

Short Answer

Async operations (202 Accepted, job IDs) report errors through a status endpoint or a webhook, not the original HTTP response. The status endpoint returns the job's state (pending, running, completed, failed) with the error detail on failure. The webhook delivers the result as an event, with retries and a dead-letter queue for persistent failures. Both require the same error structure as a synchronous API — the RFC 7807 body, the retryable flag, the documentation URL.

The async lifecycle

StepClient actionServer response
1. SubmitPOST /jobs202 Accepted with job ID and status URL
2. Poll (or wait for webhook)GET /jobs/{id}200 with {"status": "running"}
3. CompleteGET /jobs/{id}200 with {"status": "completed", "result": ...}
4. FailGET /jobs/{id}200 with {"status": "failed", "error": {RFC 7807}}

The status endpoint

The status endpoint always returns 200 (the job exists and is queryable), and the body carries the state. This is deliberate: a 404 for "job not found" is distinct from a failed job, and a 500 would imply the status endpoint is broken, not that the job failed.

StateBody
pending{"status": "pending", "created_at": "..."}
running{"status": "running", "progress": 0.45, "started_at": "..."}
completed{"status": "completed", "result": {...}, "completed_at": "..."}
failed{"status": "failed", "error": {RFC 7807}}
cancelled{"status": "cancelled", "cancelled_at": "..."}

The error object inside a failed job uses the same RFC 7807 structure as a synchronous error. This means the client's error-handling code is the same: read the type, the code, the retryable flag, and display the message.

The webhook delivery

For long-running operations, polling is wasteful. The webhook delivers the result as an event:

EventWhenBody
job.completedThe job finished successfully{"type": "job.completed", "job_id": "...", "result": {...}}
job.failedThe job failed{"type": "job.failed", "job_id": "...", "error": {RFC 7807}}

Webhook error handling — the receiver's perspective

A webhook can fail in three ways:

FailureWhoHandling
The receiver is downThe receiver's infrastructureRetry with backoff; eventually DLQ
The receiver returns 5xxThe receiver's applicationRetry with backoff; 5xx means "try again"
The receiver returns 4xxThe receiver's applicationDo not retry; the payload is rejected. Move to DLQ.
The receiver times outNetwork or receiverRetry with backoff
The signature is invalidAn attacker or a bugLog and alert; do not retry

The receiver must respond within a few seconds. If the work takes longer, the receiver should acknowledge quickly (200) and process asynchronously (in a queue). A slow receiver that holds the connection forces the sender to time out and retry — doubling the load.

The webhook sender's retry policy

The sender must implement:

  • Exponential backoff — 1s, 5s, 30s, 5m, 30m, 2h, 6h, 24h. Retry across a 24-hour window by default.
  • A signature — HMAC of the body with a shared secret, so the receiver can verify the source. Without it, the receiver cannot distinguish a legitimate webhook from an attacker's POST.
  • A dead-letter queue — after retries exhaust, the event goes to a DLQ. The receiver can query the DLQ to find missed events and process them manually.
  • A reconciliation endpoint — "list events since timestamp T" — so a receiver that was down for days can catch up without relying on the webhook.
  • Idempotency — each event has a unique ID; the receiver must deduplicate. A webhook is at-least-once delivery; duplicates are expected.

The error propagation chain

When an async job fails, the error must propagate through the chain:

  1. The worker that ran the job records the error.
  2. The job's status is updated to failed with the error detail.
  3. The webhook fires a job.failed event.
  4. The client's webhook handler logs it and (if applicable) surfaces it to the user.

Each step preserves the RFC 7807 structure — the error body is the same whether the client sees it via polling or via webhook. This consistency is what makes async errors debuggable.

The information-disclosure boundary

Async errors have a subtle risk: the error detail may include information that was not meant for the client. A worker failure might include a stack trace, a database error, or an internal identifier. The job status endpoint and webhook must sanitise the error to the client-facing form (RFC 7807, no stack traces), while logging the full error internally. This is the same rule as the synchronous 500 — the client sees the sanitised error, the log sees the full error, and the correlation ID links them.

Common Pitfall

Returning the job's error in the initial 202 Accepted response. A 202 means "accepted, not yet processed" — it cannot carry an error, because there has not been processing yet. If the submission itself is invalid, return 400/422 immediately. If the job fails later, the error is in the status endpoint or webhook, not in the 202.

Interview Framing

Say: "Async errors are reported through the status endpoint or a webhook, with the same RFC 7807 body as sync errors. The webhook has retries with backoff, a dead-letter queue, and a reconciliation endpoint, so a receiver never loses an event permanently." That covers the reporting, the retry, and the safety net in one sentence.
