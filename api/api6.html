Part A — Authentication Establishing identity: who is calling?

1

What is the difference between authentication and authorization?

Short Answer

Authentication answers "who are you?" — it verifies the identity of the caller. Authorization answers "what may you do?" — it verifies that the identified caller has permission for the specific action. Authentication happens first, always; authorization happens after, on every request. Confusing the two is the root cause of the OWASP API Top 10 number-one risk.

The two questions, separately

DimensionAuthenticationAuthorization
QuestionWho is this?May they do this?
WhenOnce per session (or per token issuance)Every request, for every resource
Failure response401 Unauthorized403 Forbidden
MechanismPassword, API key, OAuth, mTLS, JWTRBAC, ABAC, ReBAC, scopes, ownership checks
Wrong question"Is this user allowed?""Is this user who they say?"
Example"I am user 42""User 42 may read order 1001, but not order 1002"

Why the distinction matters in API design

In a simple system, the distinction is obvious. In a real API, it is constantly blurred:

  • A JWT is signed by the issuer, so presenting a valid JWT authenticates the holder. But the JWT's claims also say what the holder may do — so it is authentication and authorization in one artifact. That is convenient and also dangerous: a stolen JWT gives an attacker both.
  • An API key identifies the calling application. It does not identify the user of that application. If the API needs per-user permissions, the API key authenticates the app and a separate mechanism (an OAuth token, a session cookie) authenticates the user. Two-layer authentication.
  • Scopes in OAuth say what an application may do on behalf of a user, but the actual authorization decision ("may Alice read Bob's order?") is a resource-level check that scopes cannot express.

Each layer must be designed explicitly. A system that "authenticates with an API key" but has no authorization logic is a system where every API key can do everything — which is the classic OWASP API1 vulnerability (Broken Object Level Authorization, Question 10).

The 401 vs 403 distinction

This is the most common interview question on the topic, and it maps directly to the two concepts:

CodeMeaningWho is at faultClient action
401 UnauthorizedYou are not authenticated (or your token is invalid/expired)Authentication problemLog in again, refresh the token, or present credentials
403 ForbiddenYou are authenticated, but not allowed to do thisAuthorization problemDo not retry — the action is not permitted. Show an error.
404 Not FoundThe resource does not exist — or you are not allowed to know it existsAmbiguous by designTreat as not found; do not leak existence

The 401 response should include a WWW-Authenticate header describing what credentials are expected. The 403 response should not tell the client why — that would leak the authorization model and help an attacker map the permissions.

The "404 instead of 403" pattern

If a client is not allowed to see that a resource exists, returning 403 leaks information: "this resource exists, you just cannot access it." For sensitive resources (other users' data, internal-only records), many APIs return 404 instead of 403 — pretending the resource does not exist. This trades clarity for privacy, and it is the right trade-off for anything where existence itself is sensitive. Document the choice — a 404 that might mean "forbidden" is confusing to legitimate clients debugging a problem.

The layering in practice

A well-designed API has three layers, in order:

  1. Authentication at the edge (API gateway or auth service) — verify the token, resolve the identity, attach it to the request. Fails with 401.
  2. Coarse authorization at the edge — check that the token's scopes permit the operation class (e.g., "write:orders"). Fails with 403.
  3. Fine authorization at the service — check that the resolved identity owns or can access the specific resource. Fails with 403 or 404 (per the pattern above).

Every layer is necessary. Skipping the first means unauthenticated traffic reaches services. Skipping the third means any authenticated caller can access any resource — the BOLA vulnerability. The layers are not redundant; they answer different questions.

Interview Framing

Say: "Authentication is at the edge — token validation, identity resolution, 401. Authorization is per-resource in the service — ownership checks, role checks, 403 or 404 depending on whether existence is sensitive." That demonstrates the layering, the 401/403 split, and the 404 pattern in one sentence.

What are API keys, how do you design them, and what can they not do?

Short Answer

An API key is a long random string that identifies an application (not a user). The server issues it once, stores only a hash of it, and looks it up on every request. API keys are simple and useful for machine-to-machine authentication and for metering (rate limits, billing), but they are not a user authentication mechanism, they cannot express per-user permissions, and they are dangerous when leaked.

What an API key actually is

An API key is a bearer token — anyone who has it can use it. It is typically:

  • Random and high-entropy — at least 128 bits, generated with a cryptographically secure random number generator. Never derived from a user ID or timestamp.
  • Prefixed — e.g., sk_live_abc123... — so secret scanners (GitHub, GitGuardian) can detect leaked keys and so the key's environment (test/live) is visible at a glance.
  • Stored hashed — the server stores SHA-256(key), never the key itself. If the database is compromised, the attacker gets hashes, not usable keys.
  • Scoped and labelled — associated with an application, an environment (test/production), a set of permissions, and a human-readable label ("CI pipeline", "Mobile app v2").
  • Rotatable and revocable — the user can generate a new key and revoke the old one without downtime (Question 9).

The key's lifecycle

What API keys are good for

  • Machine-to-machine authentication. A CI pipeline, a backend service, or a script authenticates as an application, not a user. There is no user session, no browser, no OAuth dance — a key is the right primitive.
  • Metering and rate limiting. The key identifies the application for per-app quotas, billing, and abuse detection. Usage dashboards are per-key.
  • Low-friction developer onboarding. A developer can make their first call in minutes without OAuth setup. Stripe, SendGrid, and most developer APIs offer API keys for exactly this reason.
  • Public read-only data. A public API (weather data, financial data) that any app can call can use a key to track usage and throttle abuse.

What API keys cannot do

  • Authenticate a user. A key identifies the application, not the person using it. If two users of the same app share a key, the API cannot tell them apart, cannot apply per-user permissions, cannot show per-user data. This is why "user-facing apps with API keys" always end up in the BOLA vulnerability (Question 10).
  • Express fine-grained permissions. A key can be scoped (read-only, read-write), but it cannot express "Alice may read Bob's orders, but not Carol's." That requires a user-level authorization model.
  • Be safely embedded in client-side code. A key in a mobile app, a JavaScript bundle, or a desktop binary is visible to anyone who inspects the app. It will be extracted and abused. Client-side apps must use OAuth or a backend-for-frontend (BFF) that holds the key server-side.
  • Be revoked granularly. Revoking a key invalidates all uses of it. If the key is shared across many users (which it should not be), revocation logs everyone out at once.
  • Provide replay protection. A stolen key can be used from anywhere; there is no binding to a device or session.

The common API key mistakes

MistakeConsequenceFix

When to use API keys vs OAuth

The rule: API keys for applications, OAuth for users. If the API caller is a machine acting on its own behalf (a cron job, a backend integration, a public data consumer), an API key is sufficient. If the caller is acting on behalf of a user (a mobile app reading "my orders", a third-party app accessing "your Google Calendar"), OAuth is required — because only OAuth can express "this app, acting for this user, with these scopes" and allow the user to revoke access without changing their password.

Common Pitfall

Using API keys as user authentication. The API cannot distinguish two users of the same app, so any per-user authorization is either missing (BOLA) or implemented by trusting a client-supplied user ID (a privilege escalation). If the API returns "my data", it needs to know who "my" is — and an API key does not answer that question.

What are the OAuth 2.0 flows, and when do you use each?

Short Answer

OAuth 2.0 defines several flows ("grant types") for obtaining an access token. The two you should know for APIs are authorization code + PKCE (for user-facing apps — web, mobile, SPA) and client credentials (for machine-to-machine). Implicit and password grants are deprecated and should not be used. Device code is for input-constrained devices (TVs, CLI tools).

FlowUse caseStatusWhy
Authorization Code + PKCEWeb apps, SPAs, mobile apps — anything with a userCurrent best practiceThe client never sees the user's password; the token is exchanged server-side (or with a code verifier for public clients)
Client CredentialsMachine-to-machine (services, cron jobs, daemons)CurrentNo user involved; the client authenticates with its own credentials
Device CodeTVs, CLI tools, input-constrained devicesCurrentThe user authorises on a phone while the device polls for the token
ImplicitHistorical SPAsDeprecated (OAuth 2.1 removes it)Token exposed in URL fragment; no client authentication
Resource Owner PasswordLegacy first-party appsDeprecated (OAuth 2.1 removes it)The client handles the password; no MFA; no consent; trains users to trust any app with credentials

Authorization Code + PKCE — the default

The canonical flow for any app where a user is present:

  1. Authorisation request. The client redirects the user to the authorisation server with client_id, redirect_uri, scope, state, and — for PKCE — a code_challenge (a hash of a random code_verifier the client generated).
  2. User authentication and consent. The authorisation server authenticates the user (password, MFA, SSO) and shows a consent screen listing the requested scopes.
  3. Redirect with code. The server redirects back to redirect_uri with a short-lived code and the same state (which the client checks to prevent CSRF).
  4. Token exchange. The client POSTs the code and the code_verifier to the token endpoint. The server verifies the verifier hashes to the challenge, and returns the access_token, refresh_token, and (optionally) an id_token.
  5. Use the token. The client sends Authorization: Bearer {access_token} to the API.

Why PKCE matters. Without PKCE, a public client (SPA, mobile app) has no client secret — anyone who can intercept the code can exchange it for a token. PKCE binds the code to the client: only the client that generated the code_verifier can complete the exchange. This makes authorisation code safe for public clients, which is why PKCE is now required for all clients, not just public ones.

Client Credentials — for machines

When there is no user — a service calling another service, a cron job, a daemon — the client authenticates directly with its own credentials (client ID + secret, or a signed assertion, or mTLS) and receives a token. There is no user, no consent, no redirect. The token represents the application itself, and its scopes are the application's permissions.

The critical difference from authorization code: client credentials tokens should not be used for user-facing APIs, because there is no user context. If the endpoint does "get my orders", a client credentials token has no "my" — the authorisation fails, or worse, the API trusts a client-supplied user ID and returns anything (BOLA, Question 10).

Device Code — for constrained devices

A smart TV or CLI tool cannot render a login page. The device code flow:

  1. The device requests a device code and a user code from the authorisation server.
  2. It displays the user code ("go to example.com/activate and enter ABC-123").
  3. The user enters the code on their phone or laptop, authenticates, and approves.
  4. The device polls the token endpoint until the user has approved, then receives the token.

This is the only safe way to authenticate on a device that has no keyboard, no browser, and no way to keep a secret.

Why implicit and password are deprecated

  • Implicit puts the access token in the URL fragment (accessible to JavaScript, browser history, referrer headers). It has no client authentication, no refresh tokens, and no way to bind the token to the client. PKCE solves all of these for public clients, making implicit obsolete.
  • Password requires the client to handle the user's password directly, which trains users to give their password to any app, defeats MFA, and gives the client permanent credential access. Modern applications use a redirect-based flow with the identity provider handling the password.

The scopes and consent dimension

Every OAuth flow requests scopes — the permissions the token will have (Question 7). The user (in authorization code and device flows) sees the scopes on the consent screen and can reject. The authorisation server issues a token limited to the granted scopes, and the API enforces them at every request. This is the mechanism by which OAuth provides least privilege.

Common Pitfall

Using authorization code without PKCE for a SPA or mobile app. The code is exposed in the redirect URL, and without the code verifier binding, an attacker who intercepts it can exchange it for a token. OAuth 2.1 makes PKCE mandatory for all clients precisely because this mistake was so common.

Interview Framing

Say: "User-facing clients use authorization code with PKCE; machine-to-machine uses client credentials. Implicit and password grants are deprecated — I would not use them." That covers the current state of the art in two sentences.

What is the difference between JWT and opaque tokens?

Short Answer

A JWT is a self-contained, signed token whose claims can be verified without a database lookup. An opaque token is a random string whose meaning is stored server-side; every request requires a lookup. JWT is faster to verify and scales without a shared store, but cannot be revoked easily. Opaque tokens are revocable instantly but require a lookup per request and a shared session store.

AspectJWTOpaque token
FormatBase64url header.payload.signatureRandom string
VerificationSignature check — no lookupLookup in a database or cache
ScalabilityExcellent — statelessRequires shared state
RevocationHard — must wait for expiry or maintain a blocklistInstant — delete the row
SizeLarge (hundreds of bytes)Small (32–64 bytes)
ClaimsEmbedded (user ID, roles, scopes)Looked up per request
Leak impactClaims visible to the holder (not the secret)Only the token value is leaked
Best forStateless APIs, microservices, short-lived tokensRevocable sessions, high-security flows

What a JWT actually contains

A JWT has three base64url-encoded parts, separated by dots:

PartContentExample
HeaderAlgorithm and token type{"alg": "RS256", "typ": "JWT"}
PayloadClaims — the data{"sub": "user_42", "scope": "read:orders", "exp": 1705314600, "iss": "https://auth.example.com"}
SignatureCryptographic proof of integrityRSA/ECDSA/HMAC signature over the first two parts

The critical property: the payload is readable by anyone (base64 is not encryption), but not modifiable (the signature would fail). A JWT is a signed document, not an encrypted one. Never put secrets in a JWT — only claims that are safe to be public.

Standard claims

  • iss — issuer (who created the token)
  • sub — subject (who the token is about)
  • aud — audience (who the token is for)
  • exp — expiration time
  • nbf — not before
  • iat — issued at
  • jti — unique token ID (for revocation)
  • scope — permissions (OAuth-specific)

The verifier must check iss and aud against expected values, and must reject tokens where exp < now or nbf > now. A token with valid signature but wrong audience is valid for a different service, not this one.

The revocation problem

This is the fundamental limitation of JWT and the reason most production systems use a hybrid. A self-contained JWT cannot be invalidated before its expiry — the verifier has no way to know that the user has logged out, the password has changed, the account has been disabled, or the token has been stolen. The token is valid until exp.

The mitigations:

  • Short expiry. Set exp to 5–15 minutes. A stolen token is usable for at most that long. The cost is that the user must refresh frequently.
  • Refresh tokens. The short-lived access token is refreshed using a long-lived refresh token that is checked against a store. Logout revokes the refresh token; the access token expires shortly after.
  • Blocklist. Maintain a list of revoked jti values. Every verifier checks it. This reintroduces the lookup that JWT was supposed to avoid — but the lookup is only for revoked tokens (usually a small list), so it can be cached aggressively.
  • Token version. Store a "token version" per user; embed it in the JWT; on revocation (logout, password change), increment it. Verifiers check the version against a cached value. This is a blocklist for the user level rather than the token level.

The hybrid in practice

The standard production architecture uses both:

  1. Access token — a short-lived JWT (5–15 minutes). Verified locally, no lookup. Contains the user ID and scopes.
  2. Refresh token — a long-lived opaque token (days to weeks). Stored server-side, checked on each refresh, revocable instantly.
  3. Revocation — logout deletes the refresh token. The access token remains valid for up to 15 minutes, but the user cannot get a new one. Password changes and account disables increment the user's token version, invalidating all access tokens within 15 minutes.

This gives the scalability of JWT for the hot path (verification) and the revocability of opaque tokens for the cold path (refresh). It is what Auth0, Okta, Cognito, and most identity providers implement.

JWT signing algorithms

AlgorithmTypeUse
HS256HMAC (symmetric)Single service that both signs and verifies. Simple, but shares the secret.
RS256RSA (asymmetric)Issuer signs, verifiers hold only the public key. Standard for OAuth.
ES256ECDSA (asymmetric)Same as RS256 but smaller keys/signatures. Modern choice.

The verifier must reject tokens whose alg is not in the expected set. A token with alg: none and no signature is trivially forged; a verifier that accepts it is compromised. This is the most common JWT vulnerability in the wild.

Common Pitfall

Putting sensitive data in the JWT payload. The payload is base64-encoded, not encrypted — anyone with the token can decode it. Never put passwords, PII, or internal IDs that should not be visible. Only put claims that are safe to be public.

What is mTLS, and when should you use it for machine-to-machine authentication?

Short Answer

Mutual TLS (mTLS) is TLS where both the client and the server present certificates and verify each other. Regular TLS only verifies the server (so the client knows it is talking to the real server); mTLS also verifies the client (so the server knows who is calling). It is the standard for service-to-service authentication in a zero-trust network, and the basis of SPIFFE/SPIRE and service mesh identity.

How it works

StepClientServer
1. ClientHelloSends supported TLS versions and ciphers—
2. ServerHello + certificate—Sends its certificate
3. Client verifies serverChecks the server's certificate against a trusted CA—
4. CertificateRequest—Asks the client for its certificate
5. Client certificateSends its certificate—
6. Server verifies client—Checks the client's certificate against a trusted CA, and maps the identity to a policy
7. Key exchangeBoth derive a shared session key; the channel is now encrypted and mutually authenticated

The critical part is step 6: the server maps the client certificate's identity (its Subject or a SPIFFE ID) to an authorisation policy. "This certificate is for orders-service, so it may call GET /inventory." The policy is enforced at the network layer, not by the application.

SPIFFE — the standard for workload identity

SPIFFE (Secure Production Identity Framework for Everyone) defines a standard for issuing identities to workloads. The identity is a URI — spiffe://example.com/ns/production/sa/orders-service — encoded in a short-lived X.509 certificate. The SPIFFE Verifiable Identity Document (SVID) is the certificate, and the SPIFFE Workload API is how the workload obtains it.

SPIRE is the reference implementation. The workload proves its identity (via a Kubernetes service account, a cloud instance identity, or a metadata service), and SPIRE issues a short-lived certificate bound to that identity. The workload uses the certificate for mTLS to other services. Certificate rotation is automatic — the SVID is renewed well before expiry, typically every few hours.

Why mTLS in a service mesh

In a service mesh (Istio, Linkerd, Consul Connect), the sidecar proxy handles mTLS transparently. The application does not know or care — it makes plain HTTP calls, the sidecar upgrades them to mTLS, the receiving sidecar verifies the certificate, and the request is delivered. The benefits:

  • Zero application changes. The mesh handles identity and encryption; every service gets mTLS without writing crypto code.
  • Encryption in transit everywhere. Even "internal" traffic is encrypted, which is essential in zero-trust networks where the internal network is not trusted.
  • Identity-based authorisation. Policies like "only frontend may call backend" are enforced by the mesh, not the application.
  • Automatic rotation. The mesh's CA rotates certificates every few hours; there is no manual key management.

What mTLS does not solve

  • User authentication. mTLS authenticates the workload, not the user. A user's request flowing through a service still needs user identity (a JWT or a session) propagated through the call chain.
  • Authorization logic. mTLS says "this is orders-service"; it does not say "orders-service may read inventory" — that is a policy decision that must be expressed and enforced (by the mesh's AuthorizationPolicy, or by the application).
  • Compromised workloads. If a service is compromised, its mTLS certificate is valid, and the attacker can call everything the service could call. mTLS limits the blast radius to the service's permissions, not beyond.
  • End-user threat. mTLS protects the channel between services. It does not protect against a malicious user exploiting the application's logic.

When to use mTLS

  • Service-to-service in a zero-trust network. All internal traffic is encrypted and authenticated. This is the standard in modern microservice deployments.
  • Regulated industries where encryption in transit is a compliance requirement, including for internal traffic.
  • Partners or B2B integrations where both sides need cryptographic proof of identity — much stronger than an API key, which can be leaked.
  • IoT and device authentication. Each device has a unique certificate; the server knows exactly which device is calling.
  • High-value machine-to-machine (financial transfers, administrative operations) where an API key is not sufficient assurance.

When not to use mTLS

  • Browser clients. mTLS with client certificates is painful in browsers (installation, selection dialogs, no mobile support). Use OAuth or session cookies for user-facing.
  • Public APIs where developers need to onboard easily. API keys or OAuth are friendlier.
  • Small systems without a service mesh or a CA. Setting up mTLS from scratch is a real operational burden; a shared secret in a sealed secret manager may be enough.
Trade-off

mTLS gives the strongest machine identity (cryptographic, not bearer), but requires a certificate authority, a rotation mechanism, and either application-level or mesh-level integration. A service mesh amortises the cost across many services; doing mTLS manually for a few services is expensive relative to the benefit.

Interview Framing

Say: "For service-to-service I'll use mTLS with SPIFFE identities, either via a service mesh or a workload identity system. It gives cryptographic identity, automatic rotation, and encryption in transit — with no application changes if the mesh handles it." That demonstrates understanding of both the mechanism and its operational reality.

Part B — Authorization Enforcing permissions: what may they do?

6

What is the difference between RBAC, ABAC, and ReBAC?

Short Answer

RBAC assigns permissions to roles, and roles to users — simple and good for stable organisational structures. ABAC evaluates policies over attributes of the user, the resource, and the environment — more flexible, more complex. ReBAC evaluates relationships between the user and the resource ("is this user an editor of this document?") — the model behind Google Docs, GitHub permissions, and Google's Zanzibar.

ModelQuestion it answersStrengthWeakness
RBAC "Does the user have role X?" Simple, auditable, well-understood Cannot express per-resource permissions; role explosion for fine-grained needs
ABAC "Do the attributes satisfy the policy?" Flexible, can express context (time, location, resource attributes) Complex policies, hard to audit, hard to reason about
ReBAC "Is there a relationship path from user to resource?" Natural for nested resources (docs in folders, orgs, teams) Graph traversal cost, requires a relationship store

RBAC — role-based access control

The classic model. Define roles (admin, editor, viewer), assign permissions to roles, assign roles to users. The check is: "does the user have a role that grants the required permission?"

Strengths: simple to understand, easy to audit ("who has admin?"), well-supported by every framework. It maps naturally to organisational roles.

Weakness: it is global. "Editor" means "can edit everything" — there is no way to say "Alice is an editor of this document but a viewer of that one." The standard workaround is to create roles per resource ("editor_of_doc_42"), which leads to role explosion: thousands of roles, most used by one person. This is the well-known problem that ReBAC solves.

ABAC — attribute-based access control

Policies are expressions over attributes: subject attributes (department, clearance level), resource attributes (classification, owner, creation date), action attributes, and environment attributes (time, IP, location). The check is: "evaluate the policy against the attributes."

Strengths: extremely flexible — "managers can approve expenses up to $10k during business hours from the corporate network" is directly expressible. Context-aware decisions (location, time) work naturally.

Weakness: policies become complex and hard to audit. "Why was this request denied?" is a hard question when the policy is a tree of expressions. Attribute sources must be trusted and up to date. Tooling is less mature than RBAC.

ReBAC — relationship-based access control

Permissions are derived from the graph of relationships between users and resources. "Alice is an editor of document 42" is a relationship. "Editors of a document can read it" is a permission rule. The check is: "is there a path from Alice to document 42 through relationships that grant read?"

ReBAC naturally handles:

  • Nested resources. "Editors of a folder are editors of everything in it." The check traverses the folder → document relationship.
  • Group membership. "Members of the engineering group are viewers of the design doc group." The check traverses group membership.
  • Delegation. "Anyone Alice has shared the document with can reshare it." Recursion follows the sharing relationship.

Strengths: the natural model for document collaboration, multi-tenant SaaS, and any domain with hierarchies and sharing. Permissions are expressed as relationships, which mirror how humans think about access.

Weakness: requires a relationship store (a graph or a carefully indexed relational table), and the check is a graph traversal. Google's Zanzibar paper describes the system that handles Google's ReBAC at scale; OpenFGA and SpiceDB are open-source implementations.

The Zanzibar model

Zanzibar encodes permissions as tuples: (object, relation, subject). For example: (doc:42, editor, user:alice). A permission rule is a union/intersection of relations: can_read = owner ∪ editor ∪ viewer ∪ (viewer of parent folder). The check is a recursive graph traversal against these rules. Zanzibar handles billions of tuples and millions of checks per second with a combination of caching, sharding, and clever indexing.

OpenFGA (CNCF) and SpiceDB (AuthZed) implement the Zanzibar model. They are the right tools when you need ReBAC at scale and do not want to build a graph store yourself.

The hybrid reality

Most systems use a combination. A typical SaaS app:

  • RBAC for platform roles — "admin", "support", "billing" — who can access the admin console.
  • ReBAC for customer content — "Alice can edit this document because she is an editor of the folder it is in."
  • ABAC for context — "Only during business hours from an internal IP" for sensitive operations.

Each model is used where it is strongest. The mistake is to try to express all three in one model — a role explosion in RBAC, or an unmaintainable policy in ABAC, is the result.

Trade-off

RBAC is simple but global. ABAC is flexible but complex. ReBAC is natural for hierarchies but needs a relationship store. Start with RBAC for organisational permissions; add ReBAC when per-resource sharing becomes a requirement; add ABAC only for specific context-dependent rules. Most systems need less than they think.

Interview Framing

Say: "Platform roles are RBAC — admin, support, billing. Customer content is ReBAC — Alice is an editor of this folder, so she can edit everything in it. That's the Zanzibar model, and I'd use OpenFGA or a relational equivalent." That names the models and their boundaries in one sentence.

How do you design OAuth scopes for least privilege?

Short Answer

Scopes are the permissions an OAuth token carries. Design them as resource:action strings (read:orders, write:orders), keep them coarse enough to be usable and fine enough to be meaningful, avoid scope explosion, and never grant wildcard access. Every scope should map to a user-facing consent decision — if the user cannot understand what a scope grants, the scope is designed wrong.

What scopes are

A scope is a string the client requests, the user approves, the authorisation server embeds in the token, and the API enforces. It answers a coarse authorization question: "may this application do this class of operation on behalf of this user?" — not "may this user access this specific order?" (that is a resource-level check).

Design principles

PrincipleMeaningExample
Resource:action Name the resource and the operation read:orders, write:orders, read:profile, delete:account
Least privilege Each scope grants the minimum necessary Separate read:orders from read:order_items if they are genuinely different
User-understandable The consent screen can explain what it grants "View your orders" — not "scope:orders:*:read"
Not too fine Scope explosion makes clients request everything Do not create read:orders:2024 and read:orders:2025 — use a filter at the resource layer
Not too coarse Wildcard scopes defeat the purpose Do not offer * or admin for general use
Stable Scope names are part of the contract Renaming a scope is a breaking change (Volume 3)

The resource:action convention

The most common convention is {action}:{resource} — read:orders rather than orders:read. The action first reads naturally ("read orders") and sorts scopes by operation in the consent screen (all the read:* together). Some APIs use {resource}:{action} (orders:read) — either is fine; pick one and be consistent.

Common actions:

  • read — list and get
  • write — create, update, delete (or split into create, update, delete for finer control)
  • admin — configuration, permissions, webhooks

Scopes vs roles

They are different layers and both may be needed:

AspectScopeRole
Who definesThe API (resource server)The application (or the identity provider)
What it says"This app may do X on behalf of the user""This user is an admin"
GranularityPer operation classPer organisational role
Exampleread:ordersrole:admin
Enforced byThe API (per operation)The API (per action), often in addition to scope checks

A token may have both: scope: "read:orders write:profile" and role: "customer". The API checks the scope first (does this app have permission for this operation?) and then the role/ownership (does this user have permission for this specific resource?). Both must pass.

Scope enforcement

The API must enforce scopes on every request, in the service, not just at the gateway. A gateway can reject requests whose token lacks the required scope, but the service must also verify — defense in depth, and because the gateway may not know the fine-grained mapping between endpoints and scopes.

The check is mechanical: for each endpoint, declare the required scope. For GET /orders, require read:orders. For POST /orders, require write:orders. Enforce it in middleware so no endpoint is forgotten.

Scope creep

The failure mode: over time, every endpoint gets its own scope, the list grows to hundreds, and clients cannot reasonably pick the right one — so they request everything. The mitigation: keep scopes at the level of user-understandable permission groups ("view your orders", "manage your profile"), and use resource-level checks for the finer distinctions. A scope should be something a user can decide "yes, that makes sense" or "no, that app should not be able to do that."

Revocation via scopes

Scopes give the user a way to revoke partially: revoke the read:orders scope but keep the read:profile one. The user's OAuth consent screen shows which apps have which scopes and lets them revoke individually. This is far more usable than "revoke all or nothing", and it depends on scopes being meaningful and well-separated.

Common Pitfall

Treating scopes as the only authorization mechanism. Scopes say "this app may read orders"; they do not say "this app may read this user's orders." That is a resource-level check, and skipping it is the BOLA vulnerability (Question 10). Scopes are necessary but not sufficient.

How do you enforce multi-tenant authorization and prevent cross-tenant access?

Short Answer

Every tenant's data is isolated at the storage and API layers. The tenant identity is derived from the authentication token (never from a client-supplied parameter), and every query is scoped to that tenant. Cross-tenant access is prevented by a combination of tenant-scoped tokens, row-level filtering (in the query or via row-level security), and integration tests that verify a request from tenant A cannot touch tenant B's data.

The three isolation models

ModelIsolationCostBest for
Shared schema (tenant_id column) Logical — all tenants in one table with a tenant_id column Lowest — one database, easy to manage Most SaaS; small-to-medium tenants
Schema per tenant Logical — separate schemas in one database Medium — per-tenant migrations, more objects Tenants needing some isolation (custom schemas)
Database per tenant Physical — separate databases Highest — per-tenant provisioning, backups, cost Enterprise tenants with compliance requirements

The shared-schema model is the default because it is the cheapest and simplest to operate. Its isolation is entirely logical — the tenant_id column and the query filter are the only thing separating tenants. That makes the application responsible for enforcing the filter on every query, which is exactly where bugs happen (BOLA, Question 10).

The token carries the tenant

The tenant identity must be derived from the token, never from a request parameter. A JWT for Alice should include her tenant: {"sub": "user_42", "tenant_id": "acme", "scope": "read:orders"}. The API extracts the tenant from the token and uses it for every query — WHERE tenant_id = 'acme' AND id = ?. A client-supplied tenant_id parameter is either ignored or used only for a user who has access to multiple tenants (and then must be validated against the user's memberships).

If the client can supply the tenant ID, the API must verify the user is a member of that tenant before proceeding. This is the "tenant switching" feature for users who belong to multiple organisations. The check is a membership lookup, and it must happen before any data access.

Enforcing the filter — three approaches

  1. Application-level — every query includes WHERE tenant_id = ?. Simple, but one forgotten filter leaks everything. The mitigation is a data access layer that requires the tenant context and refuses to issue a query without it.
  2. Row-level security (RLS) — the database enforces the filter. PostgreSQL's ROW LEVEL SECURITY policy applies automatically based on a session variable set at connection time. The application cannot forget the filter — the database adds it. This is the strongest defense.
  3. Separate database per tenant — the isolation is physical; there is no cross-tenant query possible. The cost is per-tenant operations (migrations, backups, scaling).

The strongest practical design is RLS for the shared-schema model. The application sets SET LOCAL app.tenant_id = 'acme' at the start of each transaction, and RLS policies automatically filter every query. A developer who forgets the filter in code still gets correct isolation, because the database enforced it.

Cross-tenant access in resource-level checks

Even with tenant filtering on list endpoints, resource-level endpoints need explicit checks. A request for GET /orders/123 must verify that order 123 belongs to the caller's tenant. The query is WHERE tenant_id = 'acme' AND id = 123 — if the order belongs to a different tenant, the query returns no rows and the API returns 404 (Question 1 — hiding existence).

The bug to avoid: SELECT * FROM orders WHERE id = 123 followed by a check in application code. This is the classic BOLA — the query fetched the row, the check was forgotten or wrong, and the row was returned. The fix is to put the tenant filter in the query, not after it.

Authorization for cross-tenant features

Some features genuinely need cross-tenant access:

  • Support impersonation — a support engineer from the platform team needs to see a customer's data to resolve a ticket. The impersonation must be explicit, logged, time-limited, and require elevated permissions.
  • Shared resources — a document shared across organisations (a joint project). The ReBAC model (Question 6) expresses this: "Alice has viewer access on doc 42, regardless of tenant."
  • Platform admin — the operator of the SaaS needs aggregate access for operations and billing. This must be a separate authentication path, not the customer's token with a magic scope.

Each of these is a deliberate exception with its own audit trail. The general rule is "tenant isolation by default, explicit exceptions with audit."

Testing tenant isolation

Cross-tenant bugs are silent — they work in normal use and fail catastrophically in production. The defense is a test suite that, for every endpoint, creates two tenants with data and verifies that a request from tenant A cannot access tenant B's data. This is one of the highest-ROI test suites for a multi-tenant SaaS — it catches the missing filter, the wrong token claim, the bypassed RLS policy.

Common Pitfall

Trusting a client-supplied tenant ID. If the API accepts ?tenant_id=acme and uses it for the query without checking that the caller belongs to acme, any authenticated user can access any tenant's data by changing the parameter. The tenant must come from the token, and any client-supplied tenant must be validated against the caller's memberships.

Interview Framing

Say: "The tenant comes from the JWT — never from a request parameter. Every query filters by tenant, and I enforce it with row-level security so the filter cannot be forgotten. Resource-level endpoints filter by tenant in the query, so cross-tenant access returns 404." That covers token, RLS, and the 404 pattern in one sentence.

How do you implement token rotation, revocation, and logout across a distributed system?

Short Answer

Use short-lived access tokens (5–15 min) plus long-lived refresh tokens stored server-side. Rotation means issuing a new refresh token on each refresh and invalidating the old one. Revocation means deleting or blocklisting the token so it cannot be used. Logout revokes the refresh token; the access token expires on its own within minutes. For JWT access tokens, a per-user token version or a short blocklist handles immediate revocation.

The two-token architecture

TokenLifetimeStorageVerificationRevocable?
Access token (JWT) 5–15 min Client memory Signature check — no lookup Indirect — via refresh revoke + short expiry
Refresh token (opaque) Days to weeks HttpOnly cookie, secure storage Lookup in DB or cache Yes — delete the row

The access token is fast because it is stateless. The refresh token is revocable because it is stored. The combination gives both properties: scalable verification on the hot path, revocable sessions on the cold path. This is what every identity provider implements, and it is the right architecture.

Refresh token rotation

Rotation means every time a refresh token is used, it is replaced with a new one, and the old one is invalidated. This limits the damage if a refresh token is stolen:

  1. Client sends the refresh token to the token endpoint.
  2. Server verifies it, marks it used (or deletes it), and issues a new refresh token plus a new access token.
  3. Client stores the new refresh token, discards the old one.
  4. If the old token is used again (replay), the server detects the reuse and revokes the entire token family — an attacker who stole the old token will trigger this on their next attempt.

The reuse detection is the point. If an attacker steals a refresh token and uses it, they get a new pair; the legitimate user also gets a new pair; when the attacker's next use comes, the server sees the reuse and revokes everything — which logs the legitimate user out, but denies the attacker. The user must re-authenticate, but the attacker is stopped.

Revocation

Revocation is the ability to invalidate a token before its natural expiry. There are three mechanisms:

MechanismLatencyScopeTrade-off
Delete refresh token Instant for refresh, ≤ access TTL for access One session Simple; access token remains valid briefly
Token version (per user) ≤ cache TTL (seconds) All sessions of one user Requires a version in the JWT and a cache of current versions
JWT blocklist (jti) Instant, if cache is shared One specific token Reintroduces a lookup; the blocklist grows until tokens expire

Logout

Logout must do two things:

  1. Revoke the refresh token. Delete it from the store. The user can no longer obtain new access tokens.
  2. Invalidate the access token. Since the access token is a JWT with a short expiry, the simplest approach is to let it expire (5–15 minutes). For immediate logout, either bump the user's token version (which invalidates all their access tokens on the next check) or add the token's jti to a blocklist.

The UX question: should logout be instant everywhere (all devices) or just this device? Most apps support both:

  • Logout this device — revoke this refresh token. Other devices keep working.
  • Logout all devices — bump the token version, which invalidates every access token and refresh token for the user.

Revocation in a distributed system

If the API is served by many services, a JWT can be verified locally without a shared store. But revocation requires shared state. The design:

  • Short access TTL is the primary defence — a stolen token is useless after 15 minutes.
  • Refresh revocation is checked centrally — the token endpoint is a single service.
  • User-level revocation (logout all, password change, account disable) propagates via a cache of user token versions. Each service caches the version with a short TTL (5–30 seconds); on revocation, the version is incremented in the store, and services see the new version within the TTL.
  • Token-level revocation (specific jti) uses a Redis blocklist, shared by all services. The list is small (only revoked tokens within their expiry window) and can be cached aggressively.

The "logout does not work" bug

The classic bug: a user logs out, but their JWT is still valid, so they can still use it. This happens because the logout only cleared the client-side token — the server has no idea it should be rejected. The fix is one of the three revocation mechanisms above. In practice, short access TTL + refresh revocation covers most cases; a user who logs out will find that any active request fails within 15 minutes, and their ability to get a new one is gone immediately.

The token theft scenario

An attacker who steals an access token can use it until it expires. An attacker who steals a refresh token can get new access tokens until the refresh token is revoked or rotated. This is why:

  • Refresh tokens should be bound to the client (DPoP, or a sender-constrained token). A stolen refresh token cannot be used from a different device.
  • Refresh tokens should be stored in HttpOnly, Secure cookies (for browsers) so XSS cannot read them.
  • Rotation + reuse detection catches the theft within one refresh cycle.
Common Pitfall

Storing refresh tokens in localStorage. Any XSS on the page can read them and exfiltrate them, giving the attacker a long-lived session. Refresh tokens must be in HttpOnly cookies (not readable by JavaScript) or in a native secure store (iOS Keychain, Android Keystore). Access tokens can live in memory, but refresh tokens must be protected from XSS.

What are the OWASP API Top 10, and how do you prevent BOLA, IDOR, and mass assignment?

Short Answer

The OWASP API Security Top 10 lists the most critical API vulnerabilities. The three most common are: BOLA (Broken Object Level Authorization — no check that the caller owns the specific resource), IDOR (Insecure Direct Object Reference — a client-supplied ID exposes another user's data), and mass assignment (accepting more fields than the client should control). All three are authorization bugs, and all three are prevented by explicit, per-resource permission checks.

The OWASP API Top 10 (2023)

#VulnerabilityOne-line description
API1Broken Object Level Authorization (BOLA)The API does not check that the caller may access this specific object
API2Broken AuthenticationWeak login, credential stuffing, missing MFA, exposed tokens
API3Broken Object Property Level AuthorizationMass assignment or excessive data exposure
API4Unrestricted Resource ConsumptionNo rate limits, no result caps, expensive queries
API5Broken Function Level AuthorizationMissing role checks; users can call admin endpoints
API6Unrestricted Access to Sensitive Business FlowsNo protection against abuse (scraping, hoarding, spam)
API7Server-Side Request Forgery (SSRF)The server fetches a client-supplied URL, reaching internal services
API8Security MisconfigurationDefault creds, open CORS, verbose errors, unpatched software
API9Improper Inventory ManagementForgotten endpoints, old versions, shadow APIs
API10Unsafe Consumption of APIsTrusting third-party API responses without validation

BOLA — Broken Object Level Authorization

The number-one API vulnerability, and the one that every API team eventually creates. The bug: the API authenticates the caller (valid token) and authorizes the operation (has read:orders scope), but never checks that the caller may access this specific order.

EndpointVulnerable codeAttack
GET /orders/{id} SELECT * FROM orders WHERE id = ? Alice changes id to Bob's order ID and gets Bob's order
GET /users/{id}/profile SELECT * FROM users WHERE id = ? Alice enumerates IDs and reads every user's profile
DELETE /documents/{id} DELETE FROM documents WHERE id = ? Alice deletes Bob's documents

The fix is to always filter by the caller's identity in the query:

Fixed code
SELECT * FROM orders WHERE id = ? AND user_id = ? (the caller's user_id)
Or SELECT * FROM orders WHERE id = ? AND tenant_id = ? (the caller's tenant)
Or a ReBAC check: "does the caller have read on order:{id}?"

The critical insight: the check must be in the query, not after it. Fetching the row and then checking in application code is a bug waiting to happen — one branch that forgets the check leaks the row. Filtering in the query means the row is never fetched unless the caller is authorized.

IDOR — Insecure Direct Object Reference

IDOR is the client-facing manifestation of BOLA. The client sends a direct reference to an object (/orders/123) and the server returns the object without checking that the client is allowed. The two terms are often used interchangeably; BOLA is the category, IDOR is the specific attack pattern.

The classic IDOR test: create two accounts, log in as account A, request an object belonging to account B by changing the ID. If the response is the object, the API has an IDOR. This is the first test in any API security assessment.

The mitigation is the same as BOLA: filter by the caller's identity, and return 404 (not 403) when the object exists but the caller cannot see it — so the attacker cannot use response codes to enumerate which IDs exist.

Mass assignment

The bug: the API accepts a JSON body and maps it directly to an object, allowing the client to set fields it should not control.

Client sendsWhat the server doesImpact
{"name": "Alice", "is_admin": true} Maps all fields to the user object Alice becomes an admin — privilege escalation
{"email": "x@y.com", "role": "owner"} Updates the role field The user grants themselves higher permissions
{"amount": 100, "status": "paid"} Sets status directly Bypasses payment and marks the order paid

The fix: never map the raw request body to the object. Define an explicit allowlist of fields the client may set, and copy only those:

  • DTO (Data Transfer Object). A separate class with only the allowed fields. The request body is deserialized into the DTO, and the DTO's fields are copied to the entity.
  • Explicit field mapping. user.name = body.name; user.email = body.email; — never Object.assign(user, body) or a reflection-based mapper without an allowlist.
  • Read-only fields. Mark fields like id, created_at, role, is_admin as read-only in the schema, so an update can never change them.

Broken function level authorization

The cousin of BOLA: the endpoint itself should be restricted to a role, but the check is missing. A DELETE /users/{id} endpoint that any authenticated user can call is broken function-level authorization — a customer can delete other customers. The fix is a role check on the endpoint (RBAC, Question 6) in addition to the resource check. Both are needed: role check on the operation, resource check on the object.

Defense in depth

No single check prevents these vulnerabilities. The design:

  1. Authentication middleware — every request has a verified identity.
  2. Scope check middleware — the token has the scope required for the operation class.
  3. Role check — the user has the role required for this endpoint (function-level).
  4. Resource check — the query filters by the caller's identity (object-level).
  5. Response shaping — the DTO controls which fields are returned, and the request DTO controls which fields can be set.
  6. Tests — a two-account test for every endpoint verifies that account A cannot touch account B's data.

Each layer catches what the others miss. The tests are the final safety net — they catch the forgotten check, the wrong query, the new endpoint that was added without the pattern.

Interview Framing

Say: "BOLA is the number-one API vulnerability, and the fix is to put the caller's identity in the query — WHERE id = ? AND user_id = ? — never fetch and then check. Mass assignment is prevented by a request DTO with an allowlist, never Object.assign from the raw body." That names the two vulnerabilities and the two fixes in one sentence.

Common Pitfall

Assuming that "the client would never send that" is a defense against mass assignment. Automated scanners and attackers will send every field to see what sticks. The field must be explicitly rejected by the server, not left to the client's goodwill.
