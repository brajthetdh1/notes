Docker Networking Basics

Docker networking enables containers to communicate with each other, the host system, and external networks. Understanding Docker networking is crucial for building distributed applications.

Why Docker Networking?

Container Communication

Enable containers to talk to each other securely and efficiently

Network Isolation

Isolate application components for better security and organization

Service Discovery

Automatically discover and connect to services using container names

External Connectivity

Connect containers to external networks and services

Default Networks

Bridge Network (Default)
  • • Default network for containers
  • • NAT-based networking
  • • Port mapping required for external access
  • • Good for single-host development
Host Network
  • • Shares host's network namespace
  • • No network isolation
  • • Best performance
  • • Useful for network monitoring tools
None Network
  • • Completely isolated network
  • • No network interfaces
  • • Only loopback interface available
  • • For completely isolated workloads

Docker Network Drivers

Bridge

Default network driver. Containers on the same bridge network can communicate, while isolation is provided from containers not connected to that bridge network.

# Create bridge network
docker network create my-bridge

# Run container on bridge
docker run -d --network my-bridge --name web nginx

Best for: Single-host applications, development

Host

Remove network isolation between container and host. Container uses host's networking directly.

# Run with host networking
docker run -d --network host nginx

# Container binds to host ports directly
# Access via localhost:80 (no port mapping)

Best for: Performance-critical applications

Overlay

Enable communication between Docker daemons in Swarm mode. Overlay networks connect multiple Docker hosts.

# Create overlay network in Swarm
docker network create -d overlay my-overlay

# Service uses overlay network
docker service create --network my-overlay nginx

Best for: Multi-host applications, Docker Swarm

Macvlan

Assign MAC addresses to containers, making them appear as physical devices on your network.

# Create macvlan network
docker network create -d macvlan \
--subnet=192.168.1.0/24 \
--gateway=192.168.1.1 \
-o parent=eth0 my-macvlan

Best for: Legacy applications, network appliances

IPvlan

Similar to Macvlan but uses same MAC address with different IP addresses. More scalable than Macvlan.

# Create ipvlan network
docker network create -d ipvlan \
--subnet=192.168.1.0/24 \
-o ipvlan_mode=l2 \
-o parent=eth0 my-ipvlan

Best for: High-density container deployments

None

Completely disables networking for a container. Only loopback interface is available.

# Run without networking
docker run -d --network none alpine sleep 3600

# Check network interfaces
docker exec container-name ip addr
# Only shows: lo (loopback)

Best for: Security-sensitive workloads

Network Management Commands

Create & Inspect

docker network create my-network Create a custom network
docker network ls List all networks
docker network inspect my-network Show network details
docker network prune Remove unused networks

Container Networking

docker run -d --network my-network nginx Run container on custom network
docker network connect my-network container-name Connect running container to network
docker network disconnect my-network container-name Disconnect container from network
docker run -p 8080:80 nginx Port mapping (host:container)

Network Configuration

docker network create \
--subnet=172.20.0.0/16 \
--gateway=172.20.0.1 \
my-custom-subnet Custom subnet and gateway
docker network create \
--driver overlay \
--attachable \
my-overlay Attachable overlay network
docker network create \
-o "com.docker.network.bridge.name"="my-bridge" \
my-network Custom bridge name
docker network create \
--internal \
my-internal-network Internal network (no external access)

Diagnostics & Troubleshooting

docker exec container-name ip addr Check container IP addresses
docker exec container-name ping other-container Test connectivity between containers
docker exec container-name nslookup other-container Test DNS resolution
docker logs container-name Check container logs for network issues

Basic Network Configuration

version: '3.8'
services:

    image: nginx:alpine
    ports:
      - "80:80"
    networks:
      - frontend

  api:
    image: my-api:latest
    networks:
      - frontend
      - backend

  database:
    image: postgres:13
    networks:
      - backend

    driver: bridge
    ipam:
      config:
        - subnet: 172.20.0.0/16
  backend:
    driver: bridge
    internal: true

Practical Networking Examples

Multi-tier Application Architecture

Create isolated networks for different application tiers with controlled communication between them.

# Create networks
docker network create frontend
docker network create backend
docker network create database

# Frontend services
docker run -d --name web --network frontend nginx
docker run -d --name load-balancer --network frontend nginx

# Backend services
docker run -d --name api --network backend my-api
docker run -d --name cache --network backend redis

# Database (isolated)
docker run -d --name db --network database postgres

# Connect API to database network
docker network connect database api

# Connect load balancer to backend
docker network connect backend load-balancer

# Verify connectivity
docker exec api ping db  # Should work
docker exec web ping db  # Should fail (security)

Service Discovery with DNS

Docker provides built-in DNS resolution for container names on user-defined networks.

# Create custom network
docker network create app-network

# Start services
docker run -d --name database --network app-network postgres
docker run -d --name redis --network app-network redis
docker run -d --name api --network app-network my-api

# Test DNS resolution
docker exec api nslookup database
# Returns: 172.18.0.2

docker exec api nslookup redis
# Returns: 172.18.0.3

# Applications can connect using service names
# Connection string: postgresql://database:5432/mydb
# Redis connection: redis:6379

# Scale services with unique names
docker run -d --name api-1 --network app-network my-api
docker run -d --name api-2 --network app-network my-api

# Load balancing requires external solution
# (HAProxy, Nginx, or application-level logic)

DNS Features:

  • Automatic container name to IP resolution
  • Works on user-defined networks
  • Container aliases for multiple names
  • Round-robin DNS for multiple containers
DNS Round Robin
# Multiple containers with same network alias
docker run -d --name web1 --network-alias web nginx
docker run -d --name web2 --network-alias web nginx

# DNS queries return multiple IPs
docker exec client nslookup web
# Returns: 172.18.0.2, 172.18.0.3

Development Environment with Hot Reload

Set up a development environment with live reload using Docker Compose and bind mounts.

# docker-compose.dev.yml
version: '3.8'
services:
  frontend:
    build: ./frontend
    ports:
      - "3000:3000"
    volumes:
      - ./frontend:/app
      - /app/node_modules
    networks:
      - app-network
    environment:
      - CHOKIDAR_USEPOLLING=true
    command: npm run dev

  backend:
    build: ./backend
    ports:
      - "5000:5000"
    volumes:
      - ./backend:/app
      - /app/node_modules
    networks:
      - app-network
    environment:
      - NODE_ENV=development
    command: npm run dev

  database:
    image: postgres:13
    environment:
      - POSTGRES_DB=devdb
      - POSTGRES_USER=devuser
      - POSTGRES_PASSWORD=devpass
    networks:
      - app-network
    volumes:
      - postgres-data:/var/lib/postgresql/data

networks:
  app-network:
    driver: bridge

volumes:
  postgres-data:

  • Consistent environment across team
  • Service discovery via container names
  • Isolated from production networks

Network Security Best Practices

Use Internal Networks

Create internal networks for services that don't need external internet access.

docker network create --internal my-internal

Network Segmentation

Separate different application tiers into different networks with controlled access.

Least Privilege

Only connect containers to networks they absolutely need for their function.

Avoid Host Networking

Use host networking sparingly as it removes network isolation and security boundaries.

Custom Subnets

Use custom subnets to avoid conflicts and have predictable IP addressing.

Regular Audits

Regularly audit network configurations and remove unused networks.

Secure Multi-tier Architecture

docker-compose.yml

version: '3.8'
services:
  # Public-facing service
  web:
    image: nginx:alpine
    ports:
      - "80:80"
    networks:
      - public

  # Internal application services
  api:
    image: my-api:latest
    networks:
      - public
      - private
    depends_on:
      - database

  # Database (completely isolated)
  database:
    image: postgres:13
    networks:
      - database
    environment:
      - POSTGRES_DB=mydb
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass

networks:
  public:
    driver: bridge
  private:
    driver: bridge
    internal: false  # But only connected to API
  database:
    driver: bridge
    internal: true   # No external access

Security Controls

Network Isolation

Database is on an internal network, inaccessible from outside

Controlled Access

Only API service can access the database network

Port Management

Only necessary ports are exposed to the host

Security Checklist
  • ✓ Use internal networks for sensitive services
  • ✓ Limit container network connections
  • ✓ Use custom subnets
  • ✓ Regularly audit network configurations
  • ✓ Monitor network traffic

Common Network Issues & Solutions

Connectivity Problems

Issue: Containers can't ping each other

Containers are on different networks or firewall blocking.

# Check container networks
docker inspect container-name | grep Network

# Verify containers are on same network
docker network inspect network-name

# Test basic connectivity
docker exec container-1 ping container-2

# Check if containers are running
docker ps

# Connect container to network
docker network connect my-network container-name

# Check iptables rules
sudo iptables -L DOCKER-USER

DNS Resolution Issues

Issue: Container names not resolving

DNS not working on custom networks or container restart.

# Test DNS resolution
docker exec container-name nslookup other-container

# Check if on user-defined network
docker network ls
docker inspect container-name | grep NetworkMode

# Restart Docker DNS
sudo systemctl restart docker

# Use IP address instead of name (temporary)
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' container-name

# Check Docker daemon logs
sudo journalctl -u docker.service

# Verify network configuration
docker network inspect network-name | grep -A 10 IPAM

Network Performance Optimization

Performance Tips

  • Use host network for performance-critical applications
  • Use overlay networks for multi-host communication instead of port publishing
  • Minimize network hops between containers
  • Use macvlan for near-native network performance
