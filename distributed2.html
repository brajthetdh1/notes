What is a distributed cache, and how does it differ from a local cache?

Short Answer

A local cache lives inside the application process — nanoseconds to microseconds, but invisible to other instances and lost on restart. A distributed cache is a separate networked service (Redis, Memcached, Hazelcast) shared by all instances — sub-millisecond to a few milliseconds, consistent across the fleet, but with a network hop, its own failure modes, and a much larger operational surface. Most mature systems use both, in tiers.

DimensionLocal (in-process) cacheDistributed cache
Latency~50–500 ns~0.2–2 ms (network hop)
CapacityBounded by heap of one processBounded by cluster size — effectively unbounded
ConsistencyPer-instance; instances divergeShared view, but still not transactional
Hit ratioLower (only this instance's traffic)Higher (aggregated traffic warms the cache)
Failure modeLost on restart — harmlessA cache outage becomes an application outage if not degraded
CostFree (uses app memory)Extra infrastructure, network, and ops
InvalidationHard — must broadcast to every instanceEasy — one delete affects everyone

Why local caches still matter

A local cache is the fastest possible cache because it avoids serialization and the network entirely. For data that is tiny, extremely hot, and tolerant of a few seconds of staleness — feature flags, configuration, currency exchange rates, a small reference table — an in-process cache refreshed every 30 seconds eliminates millions of network calls. The JVM and Go ecosystems have mature libraries for this (Caffeine, Ristretto, BigCache). The constraint is memory: an app instance with 2 GB of heap can only afford a few hundred megabytes of cache before garbage-collection pressure and latency degrade.

Why distributed caches are the default for shared data

The decisive advantage is aggregate hit ratio. With ten app instances each caching independently, a popular item needs to be fetched once per instance — ten database queries instead of one. A shared cache is warmed by any instance and serves all of them, so the database sees one query. For a high-cardinality working set this is the difference between 90% and 99% cache hit rate, and therefore between a database at 10% load and one at 50% load. Invalidation is the second advantage: a single DEL updates everyone, whereas a local cache requires a pub/sub broadcast or a version-key scheme.

The two-tier pattern

The standard production architecture combines both. An in-process L1 cache holds the hottest few thousand keys with a short TTL (5–30 seconds); a distributed L2 cache holds the full working set with a longer TTL (minutes to hours); the database is the source of truth. Reads check L1, then L2, then the DB, and populate backwards. Writes invalidate L2 and publish an invalidation event to which every instance's L1 subscribes. This gives microsecond latency for hot keys, high aggregate hit ratio for the long tail, and bounded staleness of a few seconds.

Failure modes you must design for

  • Cache stampede / thundering herd. A popular key expires and hundreds of concurrent requests all miss and hit the database simultaneously. Mitigations: request coalescing (single-flight), probabilistic early expiry, and a mutex around recomputation.
  • Hot key. One key (a celebrity's profile) receives a disproportionate share of traffic and saturates a single cache node. Mitigation: replicate the key across nodes with a random suffix, or cache it in L1 everywhere.
  • Cache outage. If Redis goes away and the application has no fallback, the database receives the full uncached load and collapses. The defence is deliberate: a local fallback cache, request shedding, or accepting degraded (stale) responses.
  • Inconsistency. Write to DB then invalidate cache is not atomic; the window between the two allows a read to repopulate stale data. Mitigations: delete-after-commit, version-stamped keys, or a short TTL as a safety net.
Trade-off

A cache is a bet that stale data for a bounded window is acceptable. Write that window down explicitly — “profile data may be up to 60 seconds stale” — and verify the product agrees. Caches silently change your consistency model, and that change should be a decision, not a side effect.

What is the role of a load balancer in a distributed system?

Short Answer

A load balancer distributes incoming traffic across multiple backend instances so that no single instance is overwhelmed, and it removes unhealthy instances from rotation so that failures are invisible to clients. It is simultaneously a scalability device (spread the load), an availability device (route around failure), and a flexibility device (decouple the public address from the instance set).

The four responsibilities

  1. Traffic distribution. Spread requests across healthy backends using an algorithm suited to the workload.
  2. Health checking. Continuously probe backends and remove failures from rotation before clients notice.
  3. Address abstraction. Clients connect to a stable virtual address; instances can be added, removed, and replaced behind it without client changes.
  4. Connection management. Terminate TLS, pool backend connections, apply timeouts, and absorb connection churn.

Layer 4 vs Layer 7

AspectL4 (TCP/UDP)L7 (HTTP/HTTPS)
Operates onIP + port, opaque byte streamHTTP method, path, headers, cookies
Routing decisions5-tuple onlyPath, host, header, query, cookie
PerformanceVery high throughput, low latencySlower — must parse and buffer
TLSPass-through or terminateUsually terminates, can re-encrypt to backend
Content awarenessNoneCan rewrite headers, compress, retry
Use caseDatabases, gRPC, WebSocket, extreme throughputHTTP APIs, path routing, canary deploys

In practice you often chain them: an L4 balancer at the edge for raw throughput and DDoS absorption, then an L7 balancer inside for path-based routing and per-route policies.

Algorithms and when they matter

  • Round robin — simple and fair when requests cost roughly the same. Fails when they do not: one instance gets three slow requests and falls behind while others idle.
  • Least connections — sends to the backend with the fewest in-flight requests. The right default for variable-latency workloads.
  • Least response time — weighs connection count by observed latency; adapts to slow backends automatically.
  • Consistent hashing / IP hash — sticky routing for cache locality or session affinity. Reintroduces the problems statelessness solved; use only when the backend genuinely holds state.
  • Weighted — used for canary deploys and heterogeneous instance sizes.

Health checks: the part teams get wrong

A health check that only verifies the process is alive will happily route traffic to an instance whose database pool is exhausted or whose dependency is timing out. The result is a slow, partially-broken fleet. Good health checks verify the actual dependencies required to serve a request, run on a separate lightweight endpoint, and use consecutive-failure thresholds to avoid flapping on a single timeout. Crucially, the check must be fast — a health endpoint that takes 2 seconds under load will be marked down by the balancer precisely when the instance is merely busy.

Connection draining and zero-downtime deploys

When an instance is removed — for deployment, scaling in, or a node failure — the balancer must stop sending new requests but allow in-flight requests to complete. This is connection draining, and its absence is the cause of most “deploy caused a spike in 502s” incidents. The sequence is: mark unhealthy, stop new routing, wait for in-flight requests to finish (bounded by a timeout), then terminate.

Common Pitfall

The load balancer itself becomes a single point of failure. Always deploy it as a redundant pair with a floating virtual IP, or use a managed service that is inherently replicated — and remember that DNS in front of it is another potential SPOF.

Explain the difference between a reverse proxy and a load balancer.

Short Answer

A reverse proxy sits in front of servers and forwards client requests to them — its job is to intermediate: terminate TLS, cache, compress, filter, and hide the backend topology. A load balancer distributes requests across several backends — its job is to distribute. Every load balancer is a reverse proxy; not every reverse proxy balances load. Modern products (NGINX, Envoy, HAProxy) do both, which is why the terms are used interchangeably in practice.

CapabilityReverse proxyLoad balancer
Primary purposeIntermediation and abstractionDistribution and availability
Number of backendsCan be exactly oneBy definition, many
TLS terminationYesYes
Response cachingYes, central featureSometimes
CompressionYesSometimes
Request/response rewritingYesRarely
Health checksOptionalEssential
Balancing algorithmsNot necessarilyCore feature
Security filtering / WAFYesSometimes

Forward proxy vs reverse proxy

The distinction that actually matters conceptually is direction. A forward proxy sits in front of clients and makes requests on their behalf — corporate egress proxies, VPNs, and anonymising services. The server does not know the proxy exists. A reverse proxy sits in front of servers and receives requests on their behalf — clients think they are talking to the server directly. The reverse proxy is invisible from the client's perspective; the forward proxy is invisible from the server's.

What reverse proxies do that load balancers often do not

  • Path-based routing to different origins. /api/* to the API service, /static/* to object storage, /admin/* to an internal-only service — all under one hostname.
  • Response caching. A reverse proxy can serve a cached response without touching the backend at all, which is a different mechanism from load balancing.
  • Compression and protocol translation. HTTP/2 to HTTP/1.1, gzip/brotli encoding, request and response header rewriting.
  • Security filtering. WAF rules, IP allow/deny lists, request size limits, and bot detection.
  • Backend shielding. The backend never sees the public internet; it only accepts connections from the proxy, which limits the attack surface dramatically.

How they compose in practice

A typical production request path uses both roles at different layers. At the edge, a CDN acts as a caching reverse proxy. Behind it, an L7 load balancer terminates TLS and distributes across the API fleet. Inside, an API gateway (itself a specialised reverse proxy) routes by path to individual microservices, and each service may sit behind a sidecar proxy that handles service-to-service mTLS and retries. Each layer is a reverse proxy with a different primary job.

Why the distinction still matters in interviews

When a candidate says “I'll put a load balancer in front of the static assets”, the interviewer learns they are thinking about distribution when caching and compression are the actual requirements. When they say “I'll put a reverse proxy in front so I can cache and compress, and it will also load-balance across two origins”, they demonstrate they understand the component's capabilities rather than just its name. The distinction is a vocabulary test that reveals the depth of the mental model.

Interview Framing

Use “reverse proxy” when describing the general position in the architecture and “load balancer” when specifically discussing distribution and health checking. If you are unsure, “reverse proxy that also load balances” is always defensible.

What is an API gateway, and what problems does it solve?

Short Answer

An API gateway is a specialised reverse proxy that acts as the single entry point for all client traffic into a microservices architecture. It handles the concerns that would otherwise be duplicated across every service: authentication, rate limiting, routing, request aggregation, protocol translation, and response shaping. Its value is centralising cross-cutting concerns; its cost is an extra hop and a potential bottleneck.

The problems it addresses

  • Authentication and authorisation in one place. Validate the JWT, check the API key, and forward the resolved identity to backends as a trusted header. Without a gateway, every service implements token parsing and signature verification, and one team eventually does it wrong.
  • Rate limiting and quotas. Centralised per-client, per-endpoint, or per-plan throttling. Implementing this per service is both duplicated and inconsistent, because limits must be enforced before the work is done.
  • Routing and versioning. Map public /v1/orders to an internal service name, and route /v2/orders to a different deployment. Clients see a stable surface while services move underneath.
  • Client-specific API shaping. A mobile client needs fewer fields and smaller payloads than a web client. The gateway can aggregate several backend calls into one response (BFF pattern) or project out fields the client does not need.
  • Protocol translation. Public REST or GraphQL on the outside, gRPC between services on the inside. The gateway converts, so services can use the most efficient internal protocol.
  • Observability and traffic policy. One place to emit access logs, propagate trace IDs, apply timeouts, and run canary routing by header or percentage.
  • Backend shielding. Services are never exposed publicly. The gateway is the only ingress, which sharply reduces the attack surface and allows per-route WAF policies.

How it differs from a load balancer

A load balancer distributes traffic across instances of the same service. An API gateway routes between different services and applies business-adjacent policy. In practice the gateway also load-balances each downstream service, so the two roles overlap, but the mental model is different: the LB is concerned with capacity and health, the gateway with policy and the client contract.

The BFF variant

A Backend for Frontend is an API gateway per client type — one for mobile, one for web, one for third-party partners. Each exposes the shape that client needs and aggregates the appropriate services. This avoids the classic problem of a single general-purpose gateway accumulating conditional logic for every client, which turns it into a distributed monolith. The trade-off is more deployments to manage, but the separation is usually worth it when clients have genuinely different needs.

Why it can be an anti-pattern

The gateway is on the critical path for every request. If it holds business logic — order validation, pricing, promotion rules — it becomes a single point of both failure and coupling, and every team must coordinate through it. The rule is that the gateway should only implement cross-cutting, client-facing concerns and delegate all domain logic to services. When you see a gateway with a branching tree of per-endpoint business rules, that is a distributed monolith forming.

Performance implications

Every hop adds latency: typically 0.5–2 ms per request through a well-tuned gateway. At 10,000 requests per second that is also real CPU and connection cost, and the gateway must be horizontally scaled and given headroom. It is worth measuring whether an extra hop through a gateway is cheaper than the duplicate authentication work it removes — almost always it is, but the calculation should be made rather than assumed.

Trade-off

Centralising concerns into a gateway reduces duplication and standardises policy, but it also centralises failure and can centralise coupling. Keep the gateway thin, deploy it redundantly, and treat any business logic in it as a design smell.

What is a CDN, and how does it fit into a distributed architecture?

Short Answer

A Content Delivery Network is a globally distributed set of caching reverse proxies placed physically close to users. It reduces latency by serving content from an edge location instead of the origin, reduces origin load by absorbing the majority of read traffic, and absorbs DDoS attacks at the network edge. It is the single highest-leverage latency optimisation for any geographically distributed user base.

Why physics forces this

Light in fibre travels roughly 200 km per millisecond round trip. A user in Singapore fetching from Virginia pays at least 80 ms of propagation delay before any server work happens, and realistically 150–250 ms with real routing. No amount of server optimisation removes that. A CDN puts a cache 5–20 ms from the user, so the same request completes in tens of milliseconds. For static content the speedup is one to two orders of magnitude, and it is fundamentally unavailable to origin-side optimisations.

What a CDN caches, and how

  • Static assets — images, CSS, JS, fonts, video segments. Long TTLs, content-addressed filenames (a hash in the filename), immutable. Cache hit ratios above 95% are normal.
  • Dynamic content with short TTLs — API responses that are the same for all users and change slowly: product catalogues, public profiles, trending lists. TTLs of seconds to minutes.
  • Personalised content via edge compute — modern CDNs (Cloudflare Workers, Lambda@Edge, Fastly Compute) run code at the edge, allowing per-user responses assembled from cached fragments without a trip to the origin.
  • Streaming video — segmented with HLS/DASH and cached as individual chunks, which is what makes adaptive bitrate streaming economically viable.

Cache keys and invalidation

The cache key determines what counts as “the same request”. By default it is the URL plus the Host header, but CDNs let you include or exclude specific headers, cookies, or query parameters. Including too much fragments the cache and destroys the hit ratio; including too little serves the wrong content to the wrong user — a security incident, not just a bug. The classic failure is caching a response containing a Set-Cookie or an Authorization-specific body under a shared key. Invalidation is via TTL expiry, explicit purge API, or versioned URLs. Purging globally takes seconds to minutes and is not instantaneous, so versioned URLs are the preferred approach for anything that must change immediately.

Origin shielding

With hundreds of edge locations, a cold or expired object can produce hundreds of simultaneous misses against the origin — the CDN becomes a thundering herd. Origin shielding inserts a mid-tier cache between the edges and the origin, so at most one request per region reaches the origin. It also gives you request collapsing, where concurrent misses for the same object are coalesced into a single origin fetch.

Where the CDN sits in the architecture

The CDN is the outermost layer: client → DNS (often the CDN's own anycast DNS) → edge PoP → shield → origin load balancer → application. This means the CDN absorbs DDoS traffic before it reaches your network, terminates TLS close to the user, and can serve stale content during an origin outage — a genuine availability win, not just a performance one. Configuring stale-while-revalidate and stale-if-error means users keep seeing content even while the origin is down.

Dynamic content acceleration

Even for uncacheable responses, a CDN helps by optimising the path between the edge and the origin — maintaining warm TCP and TLS connections, using optimised backbone routes rather than the public internet, and applying compression. This “dynamic acceleration” typically saves 20–40% of origin latency and is the reason CDNs are used even for fully personalised APIs.

Common Pitfall

Caching a response that varies by user identity without including identity in the cache key, or without a Vary header. This is a data-leak class bug, not a performance bug — one user's private data served to thousands. Any endpoint that sets cookies or reads authorisation must either be marked non-cacheable or have identity explicitly in the key.

What is a message queue, and why use one?

Short Answer

A message queue is a durable buffer between a producer and a consumer. The producer enqueues a message and moves on; the consumer dequeues and processes it asynchronously, at its own pace. It decouples the two in time and in failure, which buys you load levelling, retry, buffering during consumer outages, and the ability to add consumers without touching producers.

The problems it solves

  • Temporal decoupling. The producer does not wait for the consumer. A checkout can return 200 OK in 40 ms while the email, invoice, and warehouse notification happen asynchronously over the next few seconds.
  • Load levelling / burst absorption. A flash sale produces 50,000 orders in a minute against a system that can process 5,000 per minute. The queue absorbs the spike and the workers drain it over ten minutes. Without a queue, the system either falls over or must be provisioned for a peak it hits twice a year.
  • Failure isolation. If the email service is down for an hour, messages accumulate in the queue and are processed when it recovers. No orders are lost because of an unrelated dependency.
  • Retry and dead-letter handling. Failed processing is retried with backoff, and persistently failing messages go to a dead-letter queue for inspection rather than blocking the pipeline.
  • Fan-out of work. Add ten more workers to increase throughput; no producer changes are needed, because the queue is the boundary.
  • Backpressure. Queue depth becomes an explicit, observable signal of overload, which is far better than discovering it through thread-pool exhaustion.

The costs you accept

  • Eventual consistency. The client sees success before the work is done. The UI must say “processing” rather than “done”, or the system needs a way to notify completion.
  • Duplicate delivery. Almost all queues guarantee at-least-once, not exactly-once, so consumers must be idempotent. This is not optional — it is a design requirement.
  • Ordering. Global ordering across a queue is expensive and usually unnecessary. Ordering is guaranteed per partition, so you must choose the partition key carefully (per-user, per-order).
  • Operational surface. A new stateful component to monitor, scale, back up, and reason about during incidents. Consumer lag is now a metric you own.
  • Debugging complexity. A request no longer follows a single stack trace; it becomes a sequence of events across services, which requires distributed tracing to follow.

Queue vs direct call: the decision

Use a queue when the caller does not need the result to respond, when the work is slow or bursty, when the consumer may be temporarily unavailable, or when you want to add consumers over time. Use a synchronous call when the client genuinely needs the answer — a login, a price lookup, a payment authorisation. A useful heuristic is: if the response to the user would be the same whether or not the downstream work succeeded immediately, it belongs in a queue.

The outbox pattern

Publishing to a queue and writing to a database in the same transaction is impossible — one of them will fail, and you get either a lost message or a phantom one. The transactional outbox solves this: write the message into an outbox table in the same database transaction as the business change, then a separate relay process reads the outbox and publishes to the queue. This guarantees that a committed business change always produces a message, at the cost of a small delay and a relay component.

Trade-off

A queue converts a synchronous failure into a delayed failure. That is usually an improvement — but only if someone is watching the dead-letter queue and the consumer lag. An unmonitored queue is a silent data-loss mechanism: messages retry until they expire and vanish.

What is the difference between a message queue and a publish-subscribe system?

Short Answer

In a queue, each message is delivered to exactly one consumer — it is a work-distribution mechanism. In publish-subscribe, each message is delivered to every subscriber — it is a notification mechanism. Queues scale work; pub/sub scales fan-out. They are different primitives, and the choice changes your system's semantics.

DimensionMessage queuePublish-subscribe
DeliveryOne consumer per message (competing consumers)Every subscriber gets a copy
PurposeDistribute work, level loadBroadcast events to interested parties
Adding a consumerIncreases throughput; competes for messagesIncreases fan-out; receives all new messages
CouplingProducer knows the queue, not the consumerProducer knows the topic, not the subscribers
OrderingPer queue, straightforwardPer topic/partition per subscriber
ExampleSQS, RabbitMQ queue, Redis listSNS, Kafka topics, Google Pub/Sub, RabbitMQ fanout exchange
Typical useImage resizing, email sending, payment processingOrder events consumed by billing, analytics, notifications

Why the distinction is not academic

Consider an order-placed event that three systems care about: billing, inventory, and analytics. If you put it on a queue with three consumers, each event goes to exactly one of them — billing might receive an event that inventory never sees. That is almost certainly a bug, and a subtle one that only manifests as missing data in one subsystem. Publishing to a topic delivers a copy to each subscriber, which is the correct semantics. The primitive must match the intent.

The hybrid: topics with competing consumer groups

Real systems need both at once. Kafka provides this directly: a topic is divided into partitions; each consumer group receives every message once, distributed across the members of that group. So a topic can serve billing (group 1), inventory (group 2), and analytics (group 3) — each group receives all events, while within a group the work is distributed across many instances. This is the dominant model in modern event-driven architectures precisely because it composes the two primitives.

Replay and retention

A traditional queue deletes a message once it is acknowledged; there is no going back. A log-based pub/sub system (Kafka, Kinesis, Pulsar) retains messages for a configured window and lets each consumer group maintain its own offset. This enables replay: a new consumer can read history from the beginning to bootstrap a projection, and a buggy consumer can be reset and reprocessed. Replay is enormously valuable — it makes derived data rebuildable — but it requires storage proportional to retention × throughput, and consumers must be idempotent because replay reprocesses everything.

Delivery guarantees

Both models offer at-most-once, at-least-once, or (approximately) exactly-once delivery. Exactly-once in a distributed system requires either transactional consumers with idempotent writes or a broker that supports transactional produce-and-consume (Kafka does, with some caveats). In most designs the pragmatic answer is at-least-once delivery plus idempotent consumers, which produces exactly-once effects without the cost of exactly-once infrastructure.

Interview Framing

Say: “I'll publish the order-placed event to a topic so billing, inventory, and analytics each get a copy, and each of those is its own consumer group that scales horizontally.” That sentence demonstrates you understand both primitives and how they compose.

What is a distributed file system? Give examples and use cases.

Short Answer

A distributed file system stores files across many machines while presenting a single namespace and POSIX-like (or object-like) access to clients. It provides capacity beyond one machine, durability through replication or erasure coding, and throughput by reading from many disks in parallel. HDFS, GFS, Ceph, and GlusterFS are the canonical examples; S3 is the object-store variant that has largely replaced them for new workloads.

The core design problem

A local file system assumes the disk is present, so it can update metadata and data together. A distributed file system cannot: disks fail constantly, nodes disappear mid-write, and the network partitions. Every design therefore answers three questions: how is the namespace managed (a single metadata server or a distributed directory), how is data chunked (fixed-size blocks distributed across nodes), and how is durability achieved (replication or erasure coding).

The GFS/HDFS model

Files are split into large blocks — 64 MB in GFS, 128 MB in HDFS — and each block is replicated three times across different racks. A single NameNode holds the entire namespace and block map in memory; the DataNodes store the actual blocks and report their contents via heartbeats. Reads and writes go directly between clients and DataNodes, so the NameNode is a control-plane component only and does not become a throughput bottleneck.

The trade-off is intentional: this design is optimised for large sequential reads and appends, not random writes. HDFS explicitly does not support efficient random writes or low-latency small-file access. It exists to feed batch analytics engines (MapReduce, Spark) that stream enormous files, and it is very good at exactly that.

Why large blocks

A 128 MB block means a terabyte file has only 8,000 blocks, so the NameNode's in-memory map is small and the per-block overhead is amortised. It also means each read is a long sequential transfer that saturates disk and network bandwidth instead of paying seek time. The downside is the small-file problem: a directory of a million 1 KB files consumes a million NameNode entries and a million blocks, which crushes the metadata server. The standard mitigation is archiving or compacting small files before ingestion.

Replication vs erasure coding

StrategyStorage overheadDurabilityRead costBest for
3× replication300%Tolerates 2 node failuresRead from any replicaHot data, low-latency reads
Erasure coding (10+4)140%Tolerates 4 failuresMust read and decode multiple fragmentsCold/archival data

Erasure coding cuts storage cost dramatically but increases read latency and CPU, so the common pattern is triple replication for hot data and erasure coding for data that has aged out.

Object storage has largely won

Amazon S3, GCS, and Azure Blob replaced HDFS for most new workloads because they offer effectively unlimited capacity, eleven-nines durability, HTTP-native access, and no operational burden. The trade-off is higher per-request latency (tens of milliseconds, not microseconds), eventual consistency in some paths, and no random-write or append semantics. For user-uploaded media, backups, data lakes, and static assets, object storage is the default answer. Distributed file systems remain appropriate for HPC, on-premises analytics, and workloads that genuinely need POSIX semantics across many nodes.

Where you would use one in a design

Any time the interview involves large binary payloads — videos, images, ML training sets, logs — the answer is object storage with a CDN in front, not a database BLOB column. The database should store the metadata (owner, size, content type, checksum, storage key) and the object store holds the bytes. This keeps the database small, makes backups tractable, and lets the CDN serve the content directly without the application in the path.

Common Pitfall

Storing large binaries in a relational database. It works at small scale, then row size limits, backup windows, replication bandwidth, and buffer-pool pollution all become problems at once. The metadata/bytes split is nearly always the right design.

What is a distributed database, and how does it differ from a traditional RDBMS?

Short Answer

A traditional RDBMS runs on one machine and offers full ACID transactions with a single serialisation point. A distributed database spreads storage and query processing across many machines, gaining capacity and availability but paying for it in coordination latency and consistency trade-offs. NewSQL systems (Spanner, CockroachDB, YugabyteDB) attempt to keep ACID semantics while distributing, using consensus and synchronized clocks.

DimensionTraditional RDBMSDistributed database
CapacityBounded by one machineScales with node count
AvailabilitySingle point of failure unless replicated externallySurvives node/AZ failure natively
TransactionsLocal, fast, strongly consistentCross-node — consensus, 2PC, or per-partition
LatencySingle-digit ms for indexed readsHigher — quorum round trips, cross-region hops
ConsistencyAlways strongConfigurable (tunable, per-query)
SchemaRigid, centralOften schema-less or per-partition flexible
Operational modelMature, well understoodComplex — rebalancing, repair, topology
ExamplesPostgreSQL, MySQL, OracleCassandra, DynamoDB, Spanner, CockroachDB, TiDB

The four families

  • Key-value stores (DynamoDB, Redis, Riak) — partition by key, no cross-key transactions. Extremely fast, extremely limited query model.
  • Wide-column stores (Cassandra, HBase, Bigtable) — partition key plus clustering columns; excellent write throughput and time-series access; no joins.
  • Document stores (MongoDB, Couchbase) — JSON documents, secondary indexes, some multi-document transactions in recent versions.
  • NewSQL / distributed SQL (Spanner, CockroachDB, YugabyteDB, TiDB) — the familiar relational model with SQL and ACID, but automatically sharded and replicated underneath.

How NewSQL recovers ACID across shards

The core challenge is that a transaction touching rows on different shards cannot be serialised by a single lock manager. Spanner and CockroachDB use a replicated, range-sharded key space where each range has a Raft group; a cross-range transaction uses a two-phase protocol over those groups, with timestamps providing global ordering. Spanner's key trick is TrueTime — GPS and atomic clocks give every node a bounded uncertainty window, so it can wait out the uncertainty and assign globally meaningful commit timestamps. CockroachDB uses a hybrid logical clock and a transaction-record mechanism to resolve conflicts without dedicated hardware. The cost in both cases is commit latency: cross-shard transactions require multiple round trips, typically 5–50 ms even in the same region.

Choosing between them

Use a traditional RDBMS when the data fits on one well-sized machine (modern servers handle terabytes), when transactions and joins are central to correctness, and when operational simplicity matters. Use a distributed database when the dataset genuinely exceeds a machine, when the workload must survive a datacenter failure without manual intervention, or when writes come from multiple regions and a single primary would impose unacceptable latency. The common error is choosing a distributed database for a workload that one PostgreSQL instance would serve comfortably — you pay in latency, operational complexity, and query expressiveness for capacity you do not need.

Trade-off

Distribution buys capacity and availability with latency and complexity. A single-node RDBMS with a synchronous standby and a read replica covers a surprising amount of the real world; “we might grow” is not sufficient justification for a sharded cluster.

Explain the difference between shared-memory, shared-disk, and shared-nothing architectures.

Short Answer

The three architectures describe how processors access data. Shared memory: all processors use one address space and one clock — tightly coupled, fast, limited to one machine. Shared disk: separate processors and memory, but all attach to the same storage — easy failover, but the disk is a bottleneck and a contention point. Shared nothing: each node has its own CPU, memory, and disk, communicating only by messages — the architecture of every horizontally scalable system, at the cost of cross-node coordination.

Shared memory

All processors see the same RAM. Synchronisation uses hardware primitives — compare-and-swap, memory barriers — and is measured in nanoseconds. This is the fastest possible model and is what a single multi-core server gives you. Its ceiling is the largest machine you can buy, and its scaling behaviour is governed by cache coherence traffic and lock contention, which is why adding cores past a point yields diminishing and eventually negative returns.

Shared disk

Each node has its own CPU and memory but they all mount the same storage. Any node can serve any request because the data is one copy, which makes failover trivial: another node picks up the same disk. Oracle RAC is the canonical example. The problem is that the disk subsystem is a shared resource, so its bandwidth and IOPS cap the whole cluster — you cannot scale past it. Worse, cache coherence across nodes requires a distributed lock manager over the interconnect, which adds latency to every block access. Shared disk is attractive for legacy workloads needing high availability without sharding, and largely obsolete for new designs.

Shared nothing

Every node owns a disjoint subset of the data and no resource is shared. This scales nearly linearly because there is no shared bottleneck, and it tolerates partial failure because losing a node loses only its partition. The price is that any operation spanning partitions needs coordination: joins become distributed joins, aggregations become two-phase (partial then merge), and transactions need 2PC or consensus. Shared nothing is the foundation of MapReduce, Hadoop, Spark, Kafka, Cassandra, DynamoDB, and essentially every modern horizontally scalable system.

Why shared nothing is the default answer

Only shared nothing removes the shared bottleneck, and only shared nothing lets you add capacity by adding cheap commodity machines. The industry's whole cloud computing model — many small servers rather than a few enormous ones — is a bet on shared nothing. The engineering cost is coordination, and the entire discipline of distributed systems (consensus, replication, partitioning, consistency models) exists to manage that cost.

Where the model leaks

In practice the boundaries blur. A shared-nothing cluster runs on a shared network switch, so there is a shared resource one level up. A Kubernetes node is shared-memory internally but shared-nothing at the cluster level. Modern analytical engines (Snowflake, BigQuery) use a shared-disk architecture for storage with shared-nothing compute — decoupling storage and compute is arguably a fourth model, and it is where the industry is converging because it lets each layer scale independently.

Interview Framing

When you justify sharding, name it: “I'll use a shared-nothing design so there's no shared bottleneck and a node failure only loses one partition.” When you justify keeping a single database, name the alternative cost: “shared nothing would force me into distributed transactions for queries that are trivially local today.”

Part C — Service Topology Sidecars, meshes, and the monolith question

What is a sidecar proxy, and how is it used in service meshes?

Short Answer

A sidecar is a helper process deployed alongside each application instance, sharing its network namespace and lifecycle. In a service mesh, the sidecar is a proxy that intercepts all of the application's inbound and outbound traffic, giving the platform a uniform place to implement mTLS, retries, timeouts, circuit breaking, load balancing, and telemetry — without the application knowing.

The problem it solves

In a microservices architecture with twenty services written in four languages, cross-cutting networking concerns must be implemented everywhere. Each team writes its own retry logic with slightly different backoff, its own TLS handling, its own metrics, and its own circuit breaker — or, more commonly, forgets to. The result is inconsistent reliability behaviour and no uniform observability. A sidecar moves that logic out of the application and into a proxy that every service gets automatically.

How traffic flows

  1. An iptables rule or eBPF program redirects the pod's outbound traffic through the sidecar.
  2. The sidecar resolves the destination service via the control plane's registry.
  3. It establishes an mTLS connection using a certificate issued by the mesh's CA, presenting the pod's cryptographic identity (e.g., a SPIFFE ID).
  4. It applies the configured policy — timeout, retry budget, circuit breaker, outlier detection — and load-balances across healthy endpoints.
  5. It emits metrics, access logs, and trace spans for the request.

None of this requires the application to change a line of code. Envoy is the dominant sidecar implementation; Istio, Linkerd, Consul Connect, and AWS App Mesh are control planes that configure it.

Advantages

  • Language-agnostic. A Java service and a Go service get identical networking behaviour.
  • Uniform security. mTLS with automatic certificate rotation becomes the default, not an opt-in — a large improvement over per-service TLS configuration.
  • Consistent observability. Every request produces the same metrics and trace spans, which makes cross-service debugging tractable.
  • Policy changes without redeployment. Tighten a timeout or enable a circuit breaker via control-plane config, not a code release.

Costs and criticisms

  • Latency and resource overhead. Each request makes an extra hop through a proxy, adding roughly 1–3 ms and doubling the pod's memory and CPU footprint.
  • Operational complexity. A new distributed system to run: control plane, CA, proxies, and their upgrade lifecycle. Debugging now involves proxy config as well as application config.
  • Interception fragility. iptables-based interception breaks with certain protocols, non-standard ports, or applications that manage their own sockets.
  • The “it's not my code” problem. When a request fails, the first question is whether the proxy or the app dropped it — a new debugging dimension that teams must learn.

The sidecar-less direction

The overhead of one proxy per pod has driven two alternatives. Node-level proxies run one proxy per node instead of per pod, reducing resource cost but reducing per-pod isolation. eBPF-based meshes (Cilium Service Mesh) implement much of the data plane in the kernel, avoiding the extra userspace hop entirely for L4 concerns, though L7 policy still needs a proxy somewhere. Ambient mesh (Istio's newer mode) separates L4 handling — done by a per-node ztunnel — from L7 handling, which is only spun up for workloads that need it. The direction is clear: keep the benefits of a uniform data plane while eliminating the per-pod tax.

Trade-off

A service mesh is worth it when you have many services, multiple languages, and a regulatory or security requirement for universal mTLS. Below roughly ten services or a single language, a shared library plus a well-configured ingress usually delivers most of the benefit at a fraction of the operational cost.

What is a service mesh, and what problems does it address?

Short Answer

A service mesh is an infrastructure layer that handles all service-to-service communication. It consists of a data plane (the proxies that actually carry traffic) and a control plane (which configures them, issues identities, and collects telemetry). It addresses four problems uniformly: secure identity, reliable communication, fine-grained traffic control, and deep observability.

The four problems, in detail

  • Security and identity. Every service gets a cryptographic identity and mutual TLS is automatic, with certificate rotation handled by the control plane. Authorisation policy can be expressed as “service A may call GET /orders on service B” and enforced at the proxy, independent of the application. This is the single strongest justification for adopting a mesh — it converts security from something each team must remember into something the platform guarantees.
  • Reliability. Uniform timeouts, retries with jitter and budgets, circuit breaking, outlier detection, and connection pooling. Applied consistently, these prevent the cascading failures that heterogeneous per-service implementations produce.
  • Traffic management. Weighted routing for canary and blue-green deploys, header-based routing for internal testing, fault injection for chaos experiments, traffic mirroring to a shadow version, and per-route rate limiting. Changing a canary weight becomes a config change rather than a code release.
  • Observability. Every proxy emits consistent request-level metrics (latency histograms, status codes, retry counts) and trace spans, and generates uniform access logs. Because the instrumentation is at the proxy, services that were never instrumented still produce telemetry.

Control plane vs data plane

LayerResponsibilityExamples
Data planeCarries request traffic; enforces policy; emits telemetryEnvoy, Linkerd2-proxy, ztunnel
Control planeService discovery, config distribution, certificate issuance, policyIstiod, Linkerd control plane, Consul

The separation matters operationally: if the control plane goes down, existing proxies keep serving with their last known configuration — traffic does not stop, but new config and certificate renewals do. That graceful degradation is a deliberate design property.

What it does not solve

A service mesh is a networking layer, not an architecture fix. It does not fix a badly partitioned domain model, it does not provide distributed transactions, it does not make a chatty service decomposition efficient, and it does not replace application-level idempotency. Teams sometimes adopt a mesh expecting reliability and discover they still have cascading failures because their services have no timeouts inside the application's own database calls. The mesh sees only the network boundary.

The cost-benefit calculus

Adopt when: many services, multiple languages, a compliance requirement for service-to-service encryption, and a platform team able to operate it. Do not adopt when: a handful of services, one language, or a small team without dedicated platform capacity — the operational cost will exceed the benefit. A reasonable middle path is a mesh only for the security and mTLS use case, with L7 policy handled at the ingress and a shared library for retries.

Common Pitfall

Adding a mesh and assuming retries are now handled. Retries at the proxy layer can multiply: three app instances retrying three times each against a struggling dependency produces nine times the load. Always combine proxy retries with a retry budget (a cap on retries as a fraction of total requests) and jitter, or you will build a retry storm amplifier.

What is the difference between a monolith, microservices, and serverless in distributed contexts?

Short Answer

A monolith is one deployable unit — simplest to build, operate, and debug, but scales only as a whole and couples teams. Microservices are independently deployable services owning their own data — maximum team autonomy and independent scaling, at the cost of distributed systems complexity. Serverless runs functions on demand with no server management — near-zero idle cost and automatic scaling, but with cold starts, execution limits, and a harder local development story. These are points on a spectrum of operational ownership, not a maturity ladder.

The monolith deserves rehabilitation

The industry spent a decade over-correcting. For most products under a certain scale, a modular monolith — one deployable, but with strict internal module boundaries and no cross-module database access — delivers almost all the productivity benefit with none of the distributed systems tax. The key discipline is that module boundaries must be enforced (by build rules, package visibility, or separate schemas), otherwise the modularity erodes and you get the “big ball of mud” that motivated microservices in the first place. A well-modularised monolith is also the best possible starting point for extracting services later, because the boundaries already exist.

What microservices actually buy

They buy independent deployability and independent scaling. Those are organisational and capacity benefits, not correctness benefits. A team of eight with a single product does not need independent deployability — they can coordinate. An organisation of two hundred engineers across fifteen teams does, because the coordination cost of a shared release train becomes the dominant constraint. This is why Conway's Law is the real driver: microservices make the organisation's communication structure explicit in the architecture.

The scaling argument is narrower than it appears. Most services within a system have similar resource profiles, so independent scaling rarely saves much unless one component is genuinely different — an image transcoder next to a JSON API, or a search index next to a transactional ledger.

What serverless changes

Serverless removes capacity planning entirely and prices at zero when idle, which is transformative for spiky or low-volume workloads. The constraints are real though: execution time limits (typically 15 minutes), cold starts (100 ms to several seconds depending on runtime and package size), no persistent local state, and a notoriously difficult local development and testing loop. Serverless is at its best for event handlers, scheduled jobs, glue between managed services, and unpredictable APIs — and at its worst for long-running processes, high-throughput steady-state workloads where per-invocation pricing exceeds server cost, and latency-critical paths where a cold start would violate the SLO.

The pragmatic answer

Start with a modular monolith. Extract a service when a specific pain appears — a component that needs to scale independently, a team that needs to release independently, or a boundary that must be enforced by a network. Use serverless for well-bounded event handlers and operational glue. Most large systems end up hybrid: a monolith core, several extracted services, a fleet of functions for asynchronous side-effects, and managed infrastructure underneath. The mistake is choosing the topology first and the domain second.

Interview Framing

Say: “Given this is an early product with an unclear domain, I'll start modular-monolith and extract services along the boundaries that prove themselves — I'd extract the media-processing path first because it has a different resource profile.” That signals you understand microservices are a response to specific pressures, not a default.
