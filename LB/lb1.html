Part 1 Load Balancing: Architecture & Traffic

LB-07

What are sticky sessions? When are they necessary, and how do you migrate a stateful application to stateless?

What sticky sessions are

Sticky sessions (session affinity) force a load balancer to route every request from the same client to the same backend for the lifetime of a session. The LB identifies the client by a cookie it injects (cookie-based affinity), by source IP (IP hash), or by a header. The goal is to preserve local state — an in-memory session, a shopping cart held in process memory, a WebSocket connection, or a warm local cache — without building shared storage.

When they are genuinely necessary

  • Long-lived connections: WebSocket, Server-Sent Events, or gRPC streaming sessions are inherently pinned to one backend for the connection's life. Affinity is not optional here; it is a property of the protocol.
  • Legacy stateful applications that store session data in process memory and cannot be modified quickly. Affinity is a stopgap, not a destination.
  • Local cache locality: routing the same user or the same key to the same node improves cache hit rate (this is the same motivation as consistent hashing).

Why they are a problem

Sticky sessions create skewed load (a heavy user pins to one node), session loss on node failure (the state dies with the node), and slow scale-in (you cannot remove a node until its sessions expire). They also make rolling deployments painful: a redeploy of the pinned node logs every one of its users out. As one analysis puts it, sticky sessions "reduce immediate pressure, but they are not a substitute for shared state. A replacement instance or deployment rollout still breaks local session and upload storage". Another source states the trade-off bluntly: affinity "lets a stateful app scale out, at a cost: skewed load, sessions lost when a node dies, slow scale-in" and concludes that "externalizing session state is usually the better answer".

Migration path to stateless

  1. Externalize session state into a shared store: Redis, Memcached, or a database. The application reads and writes session data by session ID; no backend owns it. This is the single highest-leverage step.
  2. Move uploads and ephemeral files to object storage (S3/GCS) so any instance can serve any request.
  3. Use signed tokens (JWT) for identity and coarse context so each service can validate a request without calling a session store on every hop. One source describes this as "mostly stateless tokens, where each service validates signed tokens and reconstructs enough context without calling a session store on every request".
  4. For WebSockets, decouple the connection layer from the logic layer: the WebSocket gateway holds the connection, but publishes/subscribes to a backplane (Redis Pub/Sub, NATS, Kafka) so any logic instance can handle a message for any connected user. This removes the need for affinity at the logic tier.
  5. Finally, disable sticky sessions and verify that a request succeeding on one instance succeeds on any other. Then you can use pure round-robin or least-requests and get real elasticity.

The pragmatic order is: externalize state first, then remove affinity. Trying to remove affinity while state is still local causes user-visible failures. As one guide notes, "the best solution is often to eliminate the need for session persistence entirely," but when stateless is not an option (legacy systems, raw WebSockets), affinity remains a legitimate bridge.

LB-08

Design the load balancing layer for a service with autoscaling backends and no sticky-session requirement. Include L4/L7 placement, service discovery, and TLS termination.

Requirements and constraints

The service autoscales horizontally, so backends appear and disappear continuously. There is no session affinity, so any request can go to any healthy instance. The design must handle TLS, discover new instances without manual config, health-check them, and drain them gracefully on scale-in.

Layered architecture

Use two tiers, not one:

  1. L4 network load balancer (edge). An anycast or cloud network LB (AWS NLB, GCP TCP proxy) receives client TCP connections. It does not parse HTTP; it forwards connections at line rate, absorbs volumetric attacks, and distributes across availability zones. It preserves client IP via the PROXY protocol or DSR where needed. Its job is throughput and fault isolation, not routing intelligence.
  2. L7 proxy / application load balancer (regional). Behind the L4 tier sits an L7 tier (Envoy, NGINX, ALB, or a gateway). This terminates TLS, parses HTTP/gRPC, performs health checks, applies routing rules, and balances requests (not just connections) across the autoscaling pool. Because it sees individual requests, it can use least-requests or P2C + EWMA latency, which correctly handles HTTP/2 multiplexing and variable request cost.

This split matters: if you put L7 at the edge, it becomes the throughput bottleneck and the TLS CPU sink. If you put only L4, you cannot balance requests or route by path. Layering both lets each tier do what it is good at.

TLS termination

Terminate TLS at the L7 tier. This centralizes certificate management (ACME/Let's Encrypt automation, or a secret manager), offloads expensive handshakes from application pods, and enables L7 inspection (headers, JWTs). Re-encrypt (mTLS) from the L7 proxy to backends if the internal network is not trusted, or use plaintext inside a private VPC if it is. Use SNI-based certificate selection if multiple domains share the same listener. Keep TLS versions and cipher suites in a central policy so every service inherits the same posture.

Service discovery

Autoscaling means the backend set changes every few seconds. Do not maintain static IP lists. Use a registry — Kubernetes Endpoints/EndpointSlices, Consul, or AWS Cloud Map — and have the L7 proxy subscribe to it. In Kubernetes, the Ingress/Gateway controller watches EndpointSlices and updates upstream clusters automatically. In a VM world, Consul Template or a control plane (xDS) pushes updates. The proxy must support graceful endpoint updates: new endpoints are added with a warmup weight, removed endpoints enter draining rather than being cut instantly. One HAProxy case study describes exactly this pattern: the LB "should consume events from the service discovery and on the other side it should configure load balancers".

Health checking and autoscaling integration

Expose a cheap /readyz on each backend that checks only local readiness (listener bound, config loaded, warmup complete) — not shared dependencies, which would cause correlated eviction. Configure the L7 proxy with active checks (2–5 s interval, 2–3 failure threshold) plus passive outlier detection (eject on consecutive 5xx or latency outliers). The autoscaler and the LB must agree on readiness: a pod that is starting should fail readiness until it is warm, and a pod that is terminating should fail readiness before it stops accepting connections. As Azure's guidance notes, if a probe cannot reach an instance within the timeout, the LB stops sending traffic to it.

Connection draining on scale-in

When the autoscaler decides to remove an instance, the sequence must be: (1) mark it unready so the LB stops sending new requests; (2) wait for in-flight requests to complete, bounded by a drain timeout; (3) send SIGTERM; (4) let the process exit. This is connection draining, and it is what makes scale-in invisible to users. A zero-downtime deployment guide describes the pattern as: "remove it from the load balancer pool, update it, verify it works, then re-enable traffic," with the LB draining in-flight requests before deletion. Set the drain timeout to at least the longest expected request duration; for long-lived connections (WebSockets, gRPC streams), either migrate the connection or accept a controlled reconnect.

LB-09

How does a load balancer handle node failure? Explain connection draining during deployments.

Node failure: detection and reaction

A load balancer handles failure in three phases: detect, evict, and recover.

  • Detect. Active health checks probe the node on a fixed interval. Passive outlier detection watches real request outcomes. The combination catches both hard failures (process dead → TCP refuse) and soft failures (process alive but returning 5xx or hanging).
  • Evict. After N consecutive failures (typically 2–3), the node is removed from rotation. Critically, eviction should be partial and bounded: never evict more than a configured percentage of the pool (e.g., 50%), or a shared dependency failure will empty the pool entirely. Evicted nodes enter an exponential-backoff quarantine so a flapping node does not rejoin and fail repeatedly.
  • Recover. The node is probed while quarantined. After M consecutive successes (typically 2–5), it re-enters rotation — but with a slow-start ramp (weight rising from ~10% to 100% over 30–60 s), because a cold node cannot handle full traffic immediately.

What happens to in-flight requests when a node dies

If the node crashes, in-flight requests fail. The LB cannot save them; the only mitigations are (a) fast detection so new requests stop going there, (b) retries at the client or proxy for idempotent requests, with a retry budget to prevent amplification, and (c) redundancy — at least two healthy replicas so a single node failure is survivable. This is why availability is an architectural property, not a load-balancer feature.

Connection draining (graceful shutdown)

Planned removal (deploy, scale-in, maintenance) is different from a crash, and it must be graceful. Connection draining is the coordinated sequence that lets a backend finish its work before it disappears:

  1. Stop new traffic. The node is marked unhealthy/unready in the LB, or deregistered from the service registry. The LB immediately stops sending new requests to it.
  2. Wait for in-flight work. Existing connections and requests are allowed to complete. The LB holds the connection open until the backend closes it or the drain timeout expires. AWS ALB calls this "deregistration delay"; a typical value is 300 seconds, sized to the longest expected request.
  3. Signal the process. After draining (or after the timeout), send SIGTERM. The application finishes its handler, flushes logs and metrics, closes its listener, and exits.
  4. Force-kill as a backstop. After terminationGracePeriodSeconds (Kubernetes) or an equivalent hard limit, SIGKILL ensures the node does not linger.

The order matters: if you send SIGTERM first and the process exits immediately, the LB may still be routing to it for a few seconds, producing 502s. The correct pattern, as one zero-downtime guide describes, is that the preStop hook "delays SIGTERM, giving load balancers time to update," because "external load balancers need time to stop routing traffic to terminating pods". Envoy Gateway implements the same idea: graceful connection draining during pod termination, with health-check failure removing the pod from rotation before the process exits.

Interview signal: distinguish crash from planned removal. Crashes require fast detection and redundancy; planned removals require draining and coordination. Saying "the load balancer handles it" without this distinction is a junior answer.
LB-10

How do you design a multi-region failover strategy using DNS-based routing? What are the limitations of DNS failover?

The design

A multi-region failover design has three layers:

  1. Global traffic steering (DNS / GSLB). A DNS-based Global Server Load Balancer (Route 53, Azure Traffic Manager, NS1, or a GSLB appliance) answers the client's DNS query with the IP address of a regional endpoint. It uses health checks on each region and a policy: failover (primary → secondary), weighted (e.g., 90/10 for cost or gradual migration), or latency-based (nearest region). When the primary region fails its health check, the GSLB removes its IP from answers and returns the secondary's IP.
  2. Regional entry point. Each region has its own L4/L7 load balancer, which distributes across that region's availability zones and autoscaling pool. The GSLB points at the regional LB, not at individual instances.
  3. Data-layer replication. The hard part is state. Active-passive with asynchronous replication (RPO > 0) is simpler; active-active requires conflict resolution or consensus. Failover is only as good as the data layer's ability to serve from the standby region — a DNS switch to a region with stale or missing data is not a real failover.

Health checking at the global layer

The GSLB must probe a regional endpoint that reflects regional health, not just "the DNS server is up." A deep check (can the region serve a real request?) is more accurate but risks false positives; a shallow check (is the regional LB alive?) is fast but can point traffic at a region whose database is down. The practical answer is a synthetic canary request that exercises the critical path, with a conservative failure threshold (e.g., 3 consecutive failures) to avoid flapping on a single blip. Azure's multi-region guidance emphasizes familiarizing yourself with the probe policies of each layer and tuning failure thresholds so a transient error does not trigger a global switch.

Limitations of DNS failover — the honest list

DNS failover is slow and not deterministic. This is the single most important limitation and the one interviewers want you to name.
  • TTL caching makes failover time unbounded. DNS answers are cached by resolvers, OSes, and browsers. A 300-second TTL means up to 5 minutes of traffic still going to the dead region. Worse, some clients ignore TTLs: "some clients (notably JVMs with default settings, and some libraries) cache far longer than the TTL instructs". Failover time is therefore not deterministic — it is "TTL plus whatever the client decides," and research notes that "75% of the TTLs are at 5 min and the remaining 25%..." vary.
  • Propagation is not instant. "DNS propagation delays affect failover time" and "DNS caches can impact proper functioning". There is no push mechanism; you wait for caches to expire.
  • Health checking is coarse. DNS-based systems have "limited custom health check support" compared to an L7 LB that can evaluate response codes and latency.
  • The GSLB is itself a failure point. "The GSLB devices constitute added failure points in the enterprise," and they require additional network traffic to resolve and health-check. A broken GSLB can take down all regions at once.
  • Latency after failover. Traffic that lands in a distant region may be healthy but slow; "the performance can be a problem based on the latency of the traffic that now travels to a remote region". Failover restores availability, not performance.
  • Connection-level failures. DNS only affects new connections. Existing TCP connections to the failed region remain broken; clients must reconnect, which the DNS change does not accelerate.

Mitigations and the better pattern

Use a short TTL (30–60 s) on the records you may need to fail over, accepting higher DNS query volume. Combine DNS steering with anycast: a global anycast IP routes to the nearest healthy PoP at the network layer, bypassing DNS caching entirely. One source recommends exactly this: "prefer an anycast global load balancer over DNS-based failover" because "DNS-based failover cannot be faster than the record's TTL plus resolver and client caching". Keep DNS failover as the coarse, last-resort mechanism and use anycast or an HTTP-level global accelerator for fast, deterministic steering.

LB-11

Design a load balancing and routing plan to support canary and blue-green deployments. What are the responsibilities of the LB, API Gateway, and CI/CD pipeline?

The two strategies, precisely

Blue-green runs two identical environments (blue = current, green = new). Traffic is switched from blue to green all at once (or in one weighted step) after green passes verification. Rollback is an instant switch back. It gives a clean cutover and trivial rollback, at the cost of double infrastructure during the deploy window.

Canary sends a small slice of production traffic (1%, 5%, 10%) to the new version while the old version serves the rest. You compare error rate, latency, and business metrics between the two; if the canary is healthy, you ramp to 25%, 50%, 100%. Rollback is a weight change back to zero. It limits blast radius but requires traffic splitting and good observability.

Responsibility split

ComponentResponsibilityMust NOT do
Load Balancer (L4/L7) Maintains two backend pools (stable and canary). Executes the weighted split at the request level. Performs health checks on both pools. Drains connections from the old pool during cutover. Decide whether to promote the canary; evaluate business metrics; own deployment logic.
API Gateway Adds request-level routing policy on top: header-based canary (x-canary: true), user-ID-based cohorts, path-based versioning (/v2/*), auth, rate limiting per version. Can mirror traffic to the canary without affecting users. Replace the LB's job of distributing load across replicas; act as the CI/CD controller.
CI/CD Pipeline Builds and deploys the new version, registers it in the canary pool, runs automated smoke tests, queries observability (error rate, p99, saturation) against the canary, and decides to promote or roll back by calling the LB/gateway API to change weights. Hard-code traffic percentages in the LB; bypass health checks; promote without metric gates.

Canary flow end-to-end

  1. CI/CD deploys version N+1 into a separate canary pool (or a separate Deployment with a distinct label). It waits for readiness.
  2. LB adds the canary pool with weight 0 and health-checks it. Once healthy, CI/CD sets weight to 1% via the LB API. Alternatively, the API Gateway routes only synthetic/header-tagged traffic to the canary first (dark launch), then a small percentage of real users.
  3. Observability compares canary vs stable on error rate, latency percentiles, and saturation. The pipeline enforces a gate: if canary error rate exceeds baseline by more than X for Y minutes, automatic rollback.
  4. On success, CI/CD ramps weights 1% → 5% → 25% → 50% → 100%, pausing for a bake time at each step. The LB shifts weights without dropping connections (existing connections drain naturally).
  5. Old pool is drained and scaled down. The whole loop is automated; the LB is a dumb, reliable executor of weights.

API gateway products explicitly support this weighted routing: one vendor describes "create a new upstream pointing to a new version... cleverly route a portion" for canary, and "smoothly switch all traffic to the new version" for blue-green. Gateway API (Kubernetes) provides native traffic splitting through weighted backend references, enabling canary, blue-green, and A/B "without external tools or annotations".

Blue-green flow

Deploy green fully, run the full test suite against it (including smoke tests through the gateway with a test tenant), then flip the weight from blue 100 / green 0 to blue 0 / green 100 in one step. Keep blue alive and warm for a rollback window (e.g., 1 hour). The LB drains blue connections gracefully; the gateway can route internal test traffic to green before the public flip. Rollback is the reverse flip — seconds, not minutes.

Common mistakes to avoid

  • Splitting by connection instead of request. An L4 LB that hashes connections will pin a user to one version for the connection's life, so a 1% canary may actually reach 1% of connections, not requests — and long-lived connections skew the sample. Use an L7 proxy that splits per request.
  • Forgetting state compatibility. If the canary writes a new DB schema or cache format, the stable version may break. Canary only works when both versions can run against the same state, or when state is versioned.
  • Promoting on technical metrics alone. A canary can have perfect error rates and still be a business regression. Gate on the metric that matters (conversion, latency-to-first-byte for the user journey).
  • No baseline. "Canary error rate is 0.1%" means nothing without the stable version's error rate on the same traffic mix.
LB-12

Explain the difference between a Load Balancer and an API Gateway.

Intent, not implementation

The same software (NGINX, Envoy, HAProxy) can act as a load balancer, a reverse proxy, or an API gateway. The difference is what problem you are asking it to solve. As one engineering handbook puts it: "A load balancer distributes connections across identical replicas at sub-millisecond cost. A reverse proxy terminates TLS. An API gateway adds per-route policy: auth...".

Load balancer

A load balancer's job is traffic distribution for availability and throughput. It takes a set of equivalent backends and spreads connections or requests across them. It operates primarily at L4 (TCP/UDP) and, in its L7 form, at the request level for HTTP. Its features are health checks, algorithms, session affinity, TLS termination, and connection draining. It is deliberately unaware of API semantics: it does not know what an "endpoint" means, what a user's role is, or how to enforce a quota per API key. It is the air-traffic controller assigning runways so planes keep moving safely.

API gateway

An API gateway's job is API management at the application layer. It sits in front of microservices and handles concerns that are common to all APIs but should not be reimplemented in each service:

  • Authentication and authorization (JWT validation, OAuth token introspection, API keys, mTLS identity).
  • Rate limiting and quotas per client, per API key, per route.
  • Request/response transformation (protocol translation, header injection, payload shaping, versioning).
  • Routing by API semantics (/users/* → user service, /orders/* → order service), composition/aggregation, and canary routing by header or cohort.
  • Observability and policy: per-route metrics, distributed tracing, logging, WAF, schema validation.

As one comparison states: "A load balancer distributes network traffic across multiple backend servers to maximize throughput and availability. An API gateway operates at the application layer to manage, secure, and transform API traffic with features like authentication, rate limiting, and request routing". Another source captures the distinction in one line: load balancers connect microservices' replicas, while an API gateway connects different microservices to each other and to clients.

They compose, they don't compete

A production path is often: client → API gateway (auth, quotas, routing to the right service) → L7 load balancer (distribute requests across that service's replicas) → pods. The gateway decides which service; the LB decides which instance of that service. The gateway may also need its own load balancing to be highly available, but that is a separate concern from its API-management role.

When the line blurs

Modern gateways (Envoy, Kong, Apigee, AWS API Gateway) include load-balancing capability, and modern LBs (ALB) include some L7 routing. The interview-safe framing is to lead with primary purpose: "An LB optimizes distribution across replicas; a gateway optimizes API policy across services. In practice they overlap in features, but the design intent is different — and if you use one component for both, you must ensure the data plane still scales and the policy layer doesn't become the bottleneck."

LB-13

Can you perform load balancing without a dedicated load balancer instance? Explain client-side load balancing and the service-mesh sidecar pattern.

Yes — and it is increasingly the default east-west

A dedicated LB is a centralized hop. Client-side load balancing removes that hop: the client itself holds the list of healthy backends and chooses one per request. This eliminates the extra network hop and the centralized failure domain, at the cost of pushing complexity into the client (or a local proxy).

Client-side load balancing

The client (an SDK or library) subscribes to service discovery, receives the set of healthy instances, and applies an algorithm — round-robin, least-requests, or P2C — locally. gRPC's built-in load balancing works this way: the client resolves the service to a set of addresses and balances across them. Finagle (Twitter) is the classic example of a language-specific client-side stack. The trade-off is explicit: client-side "avoids the LB hop but demands language-specific clients" and is the right choice "when you control all callers and want latency-aware selection (gRPC with xDS, Finagle)". If you have polyglot services, you must reimplement the logic in every language, or standardize on a sidecar.

The service-mesh sidecar: the synthesis

A sidecar is a small proxy (typically Envoy) injected next to every service instance. The application talks to localhost; the sidecar intercepts the outbound call, applies client-side load balancing using its local view of the service registry, and forwards directly to the chosen backend. Traffic goes client → server without a central LB in the path.

This is the pattern that resolves the client-side vs server-side tension. As one source describes: the sidecar "brings client-side load balancing" — it has information about every instance the client may talk to and balances directly between them, with traffic going "directly from client to server, without going through a central load balancer like F5". Another frames it as: "client-side wins on latency and L7 awareness; server-side wins on operational simplicity, language-independence... Modern service meshes are server-side discovery that lives next to each client — the sidecar pattern is the synthesis".

Why the sidecar fixes HTTP/2 and gRPC

A classic problem: an L4 LB balances connections, but HTTP/2 multiplexes thousands of requests over one connection. One client's connection pins to one backend, so load becomes skewed. A sidecar proxy balances at the request level: it "intercepts outbound gRPC calls and distributes individual requests across all available pods, regardless of the underlying HTTP/2 connection". This is a strong argument for L7 sidecars over L4-only load balancing for east-west traffic.

Costs and caveats

  • Latency: the sidecar adds a small per-hop overhead — "single-digit millisecond p99 latency overhead in typical sidecar deployments". Usually acceptable; measure it.
  • Operational complexity: you now run a proxy per pod, with its own config, upgrades, and resource limits. The control plane (Istio, Consul Connect) becomes a critical system.
  • Debugging: mTLS, retries, and routing policies are now enforced in the sidecar, not the app — visibility requires mesh-aware tooling.
  • Not a replacement for edge load balancing: client-side/mesh LB handles east-west. For north-south (client → your system), you still want a managed edge LB for DDoS, TLS, and global routing.

Other no-dedicated-LB options

  • DNS round-robin: return multiple A records; the client picks one. Crude, no health awareness beyond DNS, and caching breaks it. Not recommended for serious use.
  • Anycast: the network routes to the nearest healthy PoP; no application-level LB instance per se, but you still need health-aware routing inside each PoP.
  • Peer-to-peer / gossip-based distribution: used in some storage systems; not general-purpose.

The practical answer for a modern architecture: edge LB for north-south, service mesh sidecars for east-west. That covers both without a central bottleneck.

Part 2 System Design: Core Concepts

SD-01

Explain horizontal vs vertical scaling. When would you choose vertical scaling?

Definitions

Vertical scaling (scale up) means making one machine bigger: more CPU cores, more RAM, faster disks, a bigger NIC. Horizontal scaling (scale out) means adding more machines and distributing load across them.

The trade-offs

DimensionVerticalHorizontal
CeilingHard physical limit (largest instance size)Effectively unbounded if the app scales
ComplexityLow — no distributed coordinationHigh — needs LB, statelessness, distributed data
Failure domainSingle point of failureRedundant by design
Cost curveSuperlinear at the high end (big iron is expensive per core)Linear-ish (commodity instances)
Downtime to scaleUsually requires a restart/migrationRolling, zero-downtime
StateEasy — state stays localHard — state must be externalized

When vertical scaling is the right call

  • Early-stage systems. Before product-market fit, a single large database is far cheaper in engineering time than a sharded cluster. Optimize for iteration speed, not theoretical scale.
  • Stateful systems that resist sharding. A relational database with complex transactions, foreign keys, and ad-hoc queries is much easier to scale up than to shard. Sharding a transactional core is a multi-quarter project; buying a bigger box is a purchase order.
  • Low-latency, single-node workloads. In-memory caches, real-time analytics on a working set that fits in RAM, or anything where cross-node coordination would dominate latency. One big machine can outperform a cluster for tightly coupled work.
  • Licensing or operational constraints. Some commercial software is licensed per node; fewer, bigger nodes can be cheaper and simpler to operate.

The pragmatic pattern is scale up until it hurts, then scale out the parts that hurt. Most systems end up hybrid: a vertically scaled primary database with read replicas horizontally scaled for reads; stateless application servers scaled horizontally behind a load balancer.

Why horizontal eventually wins

Vertical scaling has a hard ceiling and a single-point-of-failure problem. Horizontal scaling gives fault tolerance and elastic cost. But it demands that the application be stateless or partitioned — which is an architectural property, not a deployment toggle. The interview point is: "Horizontal is the long-term answer, but it is a rewrite of how state is managed. Vertical is the correct short-term answer when state is complex and scale is not yet the bottleneck."

SD-02

What are different caching strategies (write-through, write-back, write-around)? What are common cache eviction policies?

Cache strategies: the read/write paths

Cache-aside (lazy loading). The application checks the cache; on a miss, it reads from the database, writes the result to the cache, and returns it. Reads are fast on hits; the first read of any key is slow. The cache holds only what is actually requested. Most common pattern; simple and resilient (a cache outage degrades to database reads, not failure).

Read-through. The cache itself sits in front of the database and loads missing data on a miss. The application only talks to the cache. Similar to cache-aside but the loading logic lives in the cache layer. Good when you want a uniform interface; less control over what gets cached.

Write-through. Every write goes to the cache and synchronously to the database. The cache is always consistent with the database, and reads immediately see new data. Cost: every write pays both latencies, and you cache data that may never be read.

Write-back (write-behind). The write goes to the cache and is acknowledged immediately; the cache asynchronously flushes to the database in batches. This gives the lowest write latency and absorbs write bursts. The risk: if the cache dies before flushing, data is lost. It also complicates consistency — a reader hitting the database directly may see stale data. Use it for write-heavy workloads where some durability loss is acceptable (counters, metrics, feeds).

Write-around. Writes bypass the cache and go straight to the database; the cache is populated only on subsequent reads. This avoids polluting the cache with write-once data (logs, archives) and avoids the write-through penalty. The downside is that a just-written item is a cache miss on first read.

Eviction policies

  • LRU (Least Recently Used): evict the item not accessed for the longest time. Great for temporal locality; the default for many caches. A single scan can flush a useful working set (the "scan pollution" problem).
  • LFU (Least Frequently Used): evict the item with the fewest accesses. Protects frequently used items from scans; slow to adapt when access patterns change (an item that was hot yesterday but is cold today keeps its high count).
  • FIFO: evict the oldest inserted. Simple, but ignores usage — a frequently read item can be evicted just because it is old.
  • TTL-based: items expire after a fixed time. Essential for correctness when data changes; often combined with LRU (evict expired first, then LRU).
  • Random / 2-random: evict a random item. Surprisingly competitive in some workloads and trivially cheap to implement; used when precise metadata is expensive.
  • ARC / segmented LRU: adaptively balances recency and frequency. Better hit rate across mixed workloads; more complex.

What interviewers probe

  • Invalidation is harder than population. A cache is only correct if it is invalidated when the source changes. TTL is the blunt tool; explicit invalidation on write is precise but must be reliable (a missed invalidation = stale data forever). Name the trade-off.
  • Cache stampede / thundering herd. When a hot key expires, many requests miss simultaneously and hammer the database. Mitigate with request coalescing (single-flight), probabilistic early expiration, or a lock on the miss path.
  • Hot key problem. One key (a celebrity's profile) can overwhelm a single cache shard. Replicate hot keys or add a small local cache in front.
  • Consistency. Write-through is strongly consistent for reads through the cache; write-back is eventually consistent and can lose data. Cache-aside can serve stale data for up to the TTL.
SD-03

SQL vs NoSQL: how do they differ, and when would you use each? Explain database sharding and partitioning, and how to choose a shard key.

SQL vs NoSQL: the real axes

The useful distinction is not "SQL vs NoSQL" as a binary; it is a set of trade-offs across four lenses: data model, query flexibility, consistency/transactions, and scaling model. As one source puts it, "leading with 'SQL vs NoSQL' skips all four lenses".

AxisRelational (SQL)NoSQL
Data modelTables, rows, normalized relations, joinsDocuments, key-value, wide-column, graph — denormalized for access patterns
QueryRich declarative SQL, ad-hoc queries, joinsOften key-based access; query flexibility varies (some support secondary indexes)
TransactionsACID, multi-row/multi-tableOften per-item or per-partition; some support limited multi-item transactions
SchemaFixed/evolving via migrationsFlexible/schemaless (which shifts validation to the app)
ScalingVertical first; read replicas; sharding is manual and painfulDesigned to scale horizontally via partitioning/replication

Choose SQL when you have complex, evolving queries and strong transactional requirements: financial ledgers, order management, inventory, anything where correctness and joins matter more than raw write throughput. Choose NoSQL when you have a known access pattern at massive scale, semi-structured data, or write-heavy ingestion where per-item consistency is sufficient: session stores, product catalogs, time-series, chat messages, feeds. Many systems use both: a relational core for transactions and a NoSQL store for high-volume access paths.

Partitioning vs sharding

Partitioning is splitting a large table into smaller pieces (partitions) within the same database instance, usually by range, list, or hash. It improves manageability and can enable partition pruning, but all partitions still share the instance's CPU, memory, and disk. Sharding is partitioning across separate database instances, each owning a subset of the data. Sharding is what gives you horizontal write scale; it is also what introduces cross-shard queries, distributed transactions, and rebalancing complexity. Data typically gets "partitioned (sharded, for scalability), replicated (for availability) and cached (for performance)".

Choosing a shard key

The shard key decides everything: distribution, query routing, and hot spots. A good key has three properties:

  • High cardinality — many distinct values, so data spreads evenly.
  • Even access distribution — no single value dominates traffic (avoid country = 'US' or status = 'active').
  • Query alignment — most queries include the key, so they can be routed to one shard. A key that forces every query to fan out to all shards defeats the purpose.

Common choices: user_id for social data (all of a user's data is co-located); tenant_id for multi-tenant SaaS; a hash of the primary key for uniform distribution (at the cost of range-query efficiency); a composite key (e.g., user_id + timestamp) for time-series per user. Avoid low-cardinality keys and avoid keys that create hot shards — a single celebrity, a single large tenant, or a monotonically increasing ID that concentrates all new writes on the last shard. If a hot key is unavoidable, isolate it (dedicated shard) or add a random suffix to spread it (at the cost of scatter-gather reads).

Replication and its lag

Replication copies shards for durability and read scale. Leader-follower (master-slave) sends all writes to the leader and replicates to followers; reads can be served by followers. Multi-leader allows writes in multiple regions, with conflict resolution. Leaderless (Dynamo-style) uses quorums. Replication introduces replication lag: a follower may serve stale data. If a user writes and immediately reads from a lagging follower, they see their own write disappear — a read-your-writes violation. Mitigate by routing a user's reads to the leader for a short window after a write, or by using a session-consistent token.

SD-04

Explain the CAP theorem and the practical consistency trade-offs it implies.

The precise statement

CAP says: in a distributed system, when a network partition occurs (nodes cannot communicate), you must choose between Consistency (every read sees the latest write or an error) and Availability (every request gets a non-error response, though possibly stale). Partition tolerance is not optional — networks partition, so a real system must tolerate partitions. The choice is what to sacrifice during a partition. As one source states: "network partitions happen, so partition tolerance is not optional; during a partition a replicated store chooses consistency or availability".

What people get wrong

  • "Pick two of three" is misleading. You do not get to opt out of P. The meaningful choice is C vs A when a partition happens.
  • CAP ignores latency. Most of the time there is no partition, but there is always latency. PACELC extends CAP: if there is a Partition, choose A or C; Else (no partition), choose Latency or Consistency. "PACELC adds the trade-off that exists without a partition: synchronous replication buys consistency with latency". This is the more useful lens for day-to-day design.
  • Consistency is a spectrum. Strong consistency (linearizability) is expensive; eventual consistency is cheap and sufficient for many use cases (feeds, likes, recommendations).

Practical models

  • Strong consistency: linearizable reads/writes; requires quorum coordination or a single leader per shard; higher latency, lower availability during partitions. Use for money, inventory, unique constraints.
  • Eventual consistency: replicas converge; reads may be stale. High availability and low latency. Use for social feeds, view counts, search indexes, caches.
  • Read-your-writes / monotonic reads / causal consistency: session-level guarantees that avoid the worst user-visible anomalies without full strong consistency. Often the pragmatic middle ground.

Leading with CAP is fine, but the senior answer quickly moves to PACELC and to where in the system each consistency level is appropriate — not a single global choice.

SD-05

Explain forward proxy vs reverse proxy. What is a CDN and how does it work?

Forward proxy

A forward proxy sits in front of clients and forwards their requests to the internet. The server sees the proxy's IP, not the client's. Uses: corporate egress control, anonymity, caching for a client population, and bypassing geo-restrictions. The client is configured to use it (explicitly or via PAC file). It represents the client's interests.

Reverse proxy

A reverse proxy sits in front of servers and forwards client requests to the appropriate backend. The client thinks it is talking to the origin; the proxy hides the backend topology. Uses: TLS termination, load balancing, caching, compression, WAF, and unified entry point. NGINX and Envoy are common reverse proxies. It represents the server's interests. The load balancer is a specialized reverse proxy; the API gateway is a reverse proxy with API policy.

CDN

A Content Delivery Network is a globally distributed reverse-proxy cache. It works by placing points of presence (PoPs) close to users and serving cached content from the nearest one, reducing latency and origin load.

  • DNS steering: the CDN's DNS returns the IP of a nearby PoP (anycast or geo-DNS).
  • Cache hit: the PoP serves the object from its local cache, with a TTL set by origin headers. Static assets (images, JS, CSS, video segments) get very high hit rates.
  • Cache miss: the PoP fetches from origin (or from a parent/shield tier), caches it, and serves it. A shield tier (a mid-tier cache) reduces origin requests by having many edge PoPs fetch from a few shield caches instead of all hitting origin.
  • Dynamic acceleration: even for uncacheable API responses, CDNs optimize the network path (TCP termination, TLS offload, HTTP/3, persistent connections to origin), which reduces latency.
  • Invalidation: purge by URL or tag; TTLs are the fallback. Invalidation is asynchronous and can take seconds to propagate globally.
  • Security: CDNs absorb DDoS, provide WAF, and terminate TLS at the edge.

For video streaming, the CDN is the core of the architecture: video is segmented (HLS/DASH), each segment is cacheable, and adaptive bitrate players pick a rendition based on measured bandwidth. The CDN absorbs the enormous egress that would otherwise crush the origin.

SD-06

Why is concurrency control important in multi-threaded systems?

The problem

When multiple threads (or processes, or requests) access shared mutable state without coordination, the result depends on interleaving. Classic failures: lost updates (two threads read-modify-write; one overwrites the other), dirty reads (reading uncommitted state), race conditions (check-then-act), and deadlocks (each thread holds a lock the other needs). These are non-deterministic and often only appear under load — the worst kind of bug.

Mechanisms

  • Mutual exclusion (locks/mutexes): only one thread enters a critical section. Simple but risks contention, priority inversion, and deadlock if lock ordering is inconsistent.
  • Optimistic concurrency: read a version number, compute, then write only if the version is unchanged (compare-and-swap / CAS). No lock held during computation; conflicts cause a retry. Great for low-contention workloads.
  • Pessimistic concurrency: lock before reading, hold until write. Safer under high contention, but reduces throughput and risks deadlock.
  • Immutable data / actor model: avoid shared mutable state entirely; each actor owns its state and communicates by messages. Eliminates data races by construction.
  • Serialization / single-writer: route all writes for a key to one thread (e.g., a sharded executor). Simpler than locking, at the cost of per-key throughput.

In distributed systems

The same problem appears across machines: two services updating the same row, two consumers processing the same message, two regions accepting writes for the same key. Distributed concurrency control uses distributed locks (etcd/Redis/ZooKeeper), optimistic versioning (ETags, conditional writes), transactions with isolation levels (serializable, snapshot), and consensus for critical metadata. The CAP trade-off reappears: a distributed lock is a consistency mechanism, and it is unavailable during a partition.

The interview point is not to name every primitive but to identify the shared mutable state, choose a mechanism proportional to contention, and explain the failure mode of that mechanism (lock service down, version conflict, deadlock).

Part 3 Classic Design Problems

CD-01

Design a URL Shortener (TinyURL)

Requirements

Functional: given a long URL, return a short URL; visiting the short URL redirects to the original. Optionally: custom aliases, expiration, analytics.

Non-functional: high read throughput (redirects dominate), low-latency redirects, high availability, short codes that are hard to enumerate, and durability of the mapping.

Capacity estimation

Assume 100M new URLs/day (write QPS ≈ 1,160) and a 100:1 read:write ratio (read QPS ≈ 116k). Over 5 years, ~180B URLs. At ~500 bytes per record, that is ~90 TB — a sharded key-value store, not a single SQL box.

Core design

  1. ID generation. Generate a globally unique 64-bit ID (Snowflake, a distributed counter, or a database sequence), then encode it in Base62 (a–z, A–Z, 0–9) to get a short string. 7 Base62 characters give 62⁷ ≈ 3.5 trillion combinations — enough for decades. Base62 is preferred over Base64 because it is URL-safe (no +//). Hashing the URL (MD5/SHA) and truncating risks collisions; if you hash, you must detect and rehash on collision. The ID approach has no collisions by construction.
  2. Storage. A key-value store: short_code → {long_url, created_at, owner, expires_at}. Partition by hash(short_code) for even distribution and single-shard lookups. Cache hot mappings in Redis (most traffic goes to a small fraction of links).
  3. Redirect. On GET /{code}, look up the long URL (cache first, then KV store) and return 301 (permanent) or 302 (temporary). 301 is cacheable by browsers, reducing load, but loses analytics and makes the mapping hard to change; 302 keeps the redirect under your control and preserves click tracking. Most production shorteners use 302 (or 307) for this reason.
  4. Custom aliases and collisions. Check availability atomically (conditional put on the key). If taken, reject. This is the one place where a unique constraint matters.

Scaling and trade-offs to discuss

  • Read path: CDN/edge cache for redirects is tricky because a 301 may be cached for a long time; a 302 with a short cache TTL lets you change the destination. Use a multi-tier cache (edge → regional Redis → KV store).
  • Write path: ID generation must be available and monotonic-ish. A centralized counter is a bottleneck and a single point of failure; use per-node ID ranges (each node gets a block of IDs) or Snowflake.
  • Hot keys: a viral short link can overwhelm one shard. Replicate hot mappings and add a local in-process cache.
  • Expiration: store TTL and lazily delete on read, plus a background sweeper. Don't scan the whole store.
  • Analytics: redirects should emit an event asynchronously (queue → stream processor) so the redirect path stays fast.
CD-02

Design a Rate Limiter

Requirements

Limit requests per client (IP, user ID, API key) over a window. Return HTTP 429 with Retry-After when exceeded. Low latency (< 1 ms overhead). Work across a distributed fleet. Be accurate enough to protect downstream services without being unfair.

Algorithms

AlgorithmHow it worksTrade-off
Token bucketA bucket of capacity B refills at rate R. Each request takes a token; empty bucket → reject.Allows bursts up to B; smooth average rate. Most common general-purpose choice.
Leaky bucketRequests enter a queue and drain at a fixed rate.Perfectly smooth output; adds queueing latency; bursts are delayed, not rejected.
Fixed windowCount per calendar window (e.g., per minute).Simple; burst at window boundary (2× limit across the boundary).
Sliding window logKeep timestamps of accepted requests; count within the last W seconds.Exact; memory grows with request volume.
Sliding window counterWeighted sum of current and previous fixed windows.Approximate, memory-efficient; good default for large scale.

Distributed implementation

Use Redis with atomic Lua scripts: INCR + EXPIRE for fixed windows; a sorted set or token-bucket script for sliding/token bucket. Redis is fast and the operations are atomic. The rate limiter sits in the API gateway or as a sidecar, so every request passes through it before reaching the service.

Local + global two-tier: keep a small local token bucket per instance for the cheapest decisions, and periodically sync with Redis for global accuracy. This reduces Redis round-trips at the cost of slight over-admission (each instance can burst locally).

Failure handling

  • Redis down: choose fail-open (allow traffic, risk overload) or fail-closed (reject, protect backend but hurt availability). Usually fail-open for user-facing APIs, fail-closed for abuse-prone endpoints. Make it configurable.
  • Hot key: a single abusive client's key concentrates on one Redis shard. Shard the limiter by key, or use local counters for the hottest keys.
  • Clock skew: use Redis server time, not client time, for window boundaries.
  • Race conditions: the check-and-increment must be atomic — a Lua script or INCR with TTL is required; a read-then-write is not safe.
CD-03

Design a Key-Value Store

Requirements

Put(key, value), Get(key), Delete(key). Scalable horizontally, highly available, tunably consistent, durable. Low latency for reads and writes.

Core building blocks

  • Partitioning: consistent hashing to distribute keys across nodes with minimal remapping on membership change. Virtual nodes for uniform distribution and capacity weighting. Replicate each key to the next R nodes clockwise for durability.
  • Replication and consistency: Dynamo-style quorum: write to W replicas, read from R replicas, with W + R > N for strong-ish consistency (read sees the latest write). Tune W and R for latency vs consistency. Use vector clocks or version numbers to detect conflicts; resolve with last-write-wins (simple, lossy) or application-level merge (CRDTs).
  • Storage engine: LSM tree (write-optimized: memtable → SSTable, compaction) for write-heavy workloads; B-tree for read-optimized. Most distributed KV stores use LSM (RocksDB, LevelDB) because writes are sequential and compaction is background.
  • Failure handling: hinted handoff (a neighbor temporarily stores writes for a down node), read repair (on read, reconcile divergent replicas), and Merkle trees for efficient anti-entropy between replicas.
  • Membership: gossip protocol to detect failures and disseminate membership; no central coordinator.

API and data model

Simple: get(key), put(key, value, context), delete(key). Values are opaque bytes. Expose consistency knobs per request (e.g., ONE, QUORUM, ALL) so callers choose their trade-off.

Trade-offs to name

  • Availability vs consistency: quorum with W+R>N gives strong consistency but is unavailable if too many replicas are down. W=1/R=1 gives high availability but stale reads.
  • Latency vs durability: synchronous replication to all replicas is slow; asynchronous risks data loss on failover.
  • Compaction cost: LSM compaction consumes I/O and can cause latency spikes; rate-limit it.
  • Hot keys: consistent hashing does not help a single hot key; replicate it or cache it.
CD-04

Design a Web Crawler

Requirements

Start from seed URLs, fetch pages, extract links, and repeat. Scale to billions of pages. Be polite (respect robots.txt, rate-limit per host). Avoid duplicates. Handle failures and traps (infinite calendars, session IDs). Store content for indexing.

Components

  1. URL frontier (queue): priority queue by importance/freshness, partitioned by host so one slow host does not block others. Deduplication via a bloom filter + exact set.
  2. Fetcher pool: distributed workers that fetch URLs, respect per-host politeness (a delay between requests to the same host), handle retries with backoff, and respect robots.txt (cached per host).
  3. Parser and link extractor: HTML parsing, link normalization (resolve relative URLs, strip fragments), and extraction of new URLs. Must handle malformed HTML and non-HTML content (skip or store).
  4. Deduplication: canonicalize URLs (lowercase host, remove default ports, sort query params), then check against a seen-set. Use a bloom filter for the hot path and a persistent store for confirmation.
  5. Storage: raw HTML in object storage, extracted links in a graph store, metadata (fetch time, status, content hash) in a KV store.
  6. Scheduler: re-crawl frequency based on change rate (news sites often, static pages rarely).

Scale and politeness

  • Politeness: a per-host token bucket; never more than one connection per host by default. This dominates crawl rate for many small sites.
  • Distributed coordination: partition the frontier by host so the same host is always handled by one worker — this makes politeness and dedup local.
  • Traps: cap depth per host, detect near-infinite URL patterns, and blacklist pathological sites.
  • Freshness: prioritize by estimated change frequency; use conditional GETs (ETag/If-Modified-Since) to avoid re-downloading unchanged pages.
CD-05

Design a Chat Application (WhatsApp / Messenger)

Requirements

One-to-one and group messaging, real-time delivery, presence (online/offline/typing), message history, delivery/read receipts, multi-device support. Millions of concurrent connections. Low latency.

Core architecture

  • Connection layer: persistent WebSocket (or long-poll/SSE fallback) connections terminated at a gateway fleet. Each gateway holds many connections; a registry maps user_id → gateway. This is the key indirection: the message service does not need to know which server a user is on; it asks the registry.
  • Message service: accepts a message, persists it, and routes it. For 1:1, look up the recipient's gateway and push. For groups, fan out to each member's gateway (or to a group channel).
  • Persistence: a wide-column store (Cassandra/HBase) partitioned by conversation_id with timestamp clustering — this gives efficient history reads. Messages are immutable; edits/deletes are new records.
  • Presence: heartbeats from clients; a presence service tracks last-seen and online state in Redis with TTL. Typing indicators are ephemeral pub/sub events, not persisted.
  • Push notifications: when the recipient is offline, send APNs/FCM so the device wakes and syncs. The message is already persisted; push is a hint, not the transport.
  • Multi-device: treat each device as a separate connection; sync a per-device cursor. End-to-end encryption (Signal protocol) means the server stores ciphertext and cannot read messages; multi-device requires key sharing.

Delivery semantics

At-least-once delivery with client-side dedup by message ID. Sender gets an ack when the server persists; recipient gets an ack when delivered; read receipt when displayed. Store per-message status per recipient.

Scale challenges

  • Connection churn: mobile clients reconnect constantly; the gateway must handle millions of connect/disconnect events without overloading the registry.
  • Group fan-out: a 1,000-member group means 1,000 pushes per message. For very large groups, use a pub/sub channel per group and let gateways subscribe.
  • Ordering: per-conversation ordering is usually sufficient; use a server-assigned sequence number per conversation, not a global timestamp.
  • History pagination: cursor-based (by timestamp/sequence), never offset-based at scale.
CD-06

Design a Social Media Newsfeed (Facebook / Twitter)

Requirements

When a user opens the app, show a ranked list of posts from people they follow. Handle follows, likes, comments. Millions of users, celebrity accounts with tens of millions of followers. Low-latency read.

The core problem: fan-out

When a user posts, how does it reach followers' feeds?

  • Push (fan-out on write): when a user posts, write the post ID into every follower's feed list immediately. Reads are fast (precomputed feed), but a celebrity with 50M followers triggers 50M writes per post — a write amplification disaster.
  • Pull (fan-out on read): store posts per author; when a reader opens the feed, fetch recent posts from everyone they follow and merge. Writes are cheap, but reads are expensive (merge N lists) and slow for users following thousands.
  • Hybrid: push for normal users (bounded follower count), pull for celebrities. When a reader opens the feed, merge the precomputed push feed with the pulled celebrity posts. This is the standard answer. One case study describes it as "Hybrid fan-out (Push vs Pull vs Celebrity)".

Storage and ranking

  • Feed cache: Redis sorted sets per user, keyed by post ID with score = timestamp/rank. Precomputed for push users; merged on read for pull.
  • Post store: a wide-column store keyed by author_id + post_id, plus a media store for images/video (object storage + CDN).
  • Social graph: who follows whom — a graph store or a sharded adjacency list. Needed for fan-out and privacy checks.
  • Ranking: the feed is not purely chronological; it is ranked by predicted engagement (affinity, recency, media type). Ranking happens at read time over a candidate set (the precomputed feed + pulled posts), using a lightweight model. Keep the candidate set bounded (e.g., 1,000) to control latency.

Scale challenges

  • Celebrity problem: the hybrid approach is the answer; also cache celebrity posts aggressively and merge at read.
  • Feed consistency: a new post may take seconds to appear in followers' feeds; this is acceptable (eventual consistency).
  • Hot posts: a viral post's like/comment counts are hot keys; batch updates or use a counter service with sharded counters.
  • Media: store in object storage, serve via CDN, transcode asynchronously.
CD-07

Design a Ride-Sharing Service (Uber / Lyft)

Requirements

Riders request a ride; the system matches them with nearby available drivers; real-time location tracking; fare estimation; trip lifecycle (requested → matched → en route → in-trip → completed). High write throughput for location updates, low-latency matching.

Core components

  • Location ingestion: drivers send GPS pings every few seconds. At 1M active drivers × 0.2 Hz, that is ~200k writes/s — a high-throughput stream (Kafka) feeding an in-memory geospatial index. Do not persist every ping to a relational DB synchronously.
  • Geospatial index: Uber H3 hexagons (or geohash/S2 cells) map a location to a cell ID. Maintain an in-memory index (Redis) of cell → available drivers. To find nearby drivers, query the rider's cell and its neighbors. H3 is preferred because hexagons have uniform neighbor distance (unlike lat/lon grids). One case study notes "in-memory spatial indexing (Uber H3 hexagons)" and "125k telemetry updates/sec".
  • Matching service: on a ride request, search expanding rings of cells until enough drivers are found; rank by ETA (road distance, not straight-line), rating, and acceptance likelihood. Use a two-phase lease: atomically offer the ride to one driver with a short timeout; if they decline or time out, offer to the next. This prevents two riders from booking the same driver. One source describes "atomic two-phase driver leases" as the mechanism.
  • Trip state machine: a durable store (SQL or KV) for trip records, with an event log for state transitions. Idempotency keys on the request prevent double-booking on retry.
  • Pricing: base fare + distance + time + surge multiplier. Surge is computed per cell from demand/supply ratio; it must be consistent and auditable.
  • Notifications: push to rider and driver at each state change; WebSocket for live location updates during the trip.

Scale and failure considerations

  • Location data is ephemeral: old pings are useless; keep only the latest per driver in memory, and persist a downsampled trail for analytics.
  • Matching under contention: the two-phase lease is critical; without it, two matching workers can assign the same driver. Use a conditional write (driver status = available → reserved) as the atomic primitive.
  • Hot cities: a single dense city (Manhattan at rush hour) concentrates load; partition the matching service by city/region.
  • Network partitions: if a driver's connection drops, the lease must expire and the trip must be reassigned or cancelled; build timeout-based recovery.
CD-08

Design a Video Streaming Platform (YouTube / Netflix)

Requirements

Upload, transcode, store, and stream video to millions of concurrent viewers with adaptive quality. Low startup latency, smooth playback, global reach. Recommendations and search.

Upload and processing pipeline

  1. Resumable upload to object storage (S3/GCS) in chunks. The client gets an upload ID and can resume after a network failure.
  2. Transcoding: a queue of jobs fans out to a worker fleet that produces multiple resolutions and codecs (H.264, VP9, AV1, HDR) and segments them into HLS/DASH chunks (2–10 s each). Transcoding is CPU/GPU-intensive; it is asynchronous and can take minutes. Prioritize popular/new uploads.
  3. Packaging: generate a manifest (M3U8/MPD) listing renditions and segment URLs. Store segments in object storage; they are immutable and cacheable.
  4. Metadata: title, description, thumbnails, duration, ownership in a database; search index updated asynchronously.

Streaming architecture

  • CDN is the core. Segments are served from edge PoPs; a shield tier reduces origin load. The CDN absorbs the enormous egress. One case study lists "large-scale video streaming platform (YouTube/Netflix) | Resumable chunked uploads..." as the canonical problem.
  • Adaptive bitrate (ABR): the player measures throughput and buffer level, then requests the next segment at a rendition it can sustain. This is why segmentation matters: switching quality happens at segment boundaries. Start conservative, ramp up.
  • Low-latency variants: LL-HLS/LL-DASH reduce segment size and use partial segments; for live streaming, this trades efficiency for latency.
  • DRM: encrypt segments and license keys via Widevine/FairPlay/PlayReady; the CDN serves encrypted content, the license server issues keys.

Scale challenges

  • Egress cost: video is bandwidth-dominated; CDN peering and multi-CDN strategies matter. Use the cheapest CDN that meets quality, and fail over between CDNs.
  • Cold content: the long tail of rarely watched videos should not occupy edge caches; tiered caching (edge → shield → origin) handles this.
  • Live vs VOD: live needs a low-latency ingest (RTMP/SRT) → transcode → packager → CDN path with seconds of latency; VOD can pre-process fully.
  • Recommendations: precompute candidate sets offline; serve a ranked list at request time. Do not run a heavy model on the critical playback path.

Part 4 Advanced & Failure Handling

AD-01

How do you design for backpressure in a high-traffic system? How do you prevent cascading failures and retry storms?

Backpressure

Backpressure is a mechanism by which an overloaded component signals upstream to slow down, rather than accepting work it cannot complete. Without it, queues grow unboundedly, latency explodes, memory exhausts, and the component collapses — taking its callers with it.

Techniques:

  • Bounded queues with rejection: when the queue is full, reject new work immediately (HTTP 429/503) instead of enqueuing. A fast rejection is better than a slow timeout.
  • Load shedding: drop low-priority requests (e.g., prefetch, analytics) to protect high-priority ones. Classify requests and shed by class.
  • Rate limiting / throttling: cap the accepted rate at the edge and at each tier; "throttling buys time for reactive responses during events like scaling operations".
  • Pull-based consumption: consumers fetch at their own pace (Kafka consumer groups) rather than being pushed; the broker holds the backlog. This is backpressure by design.
  • Adaptive concurrency limits: measure latency and reduce the in-flight request limit when latency rises (Netflix's concurrency limits, Envoy's adaptive concurrency).

Cascading failures

A cascading failure is a local problem that propagates: a slow dependency causes threads to block, which exhausts the thread pool, which makes the caller slow, which exhausts its pool, and so on up the stack. Retries amplify it.

Prevention:

  • Timeouts everywhere: never wait forever. A timeout bounds the damage a slow dependency can do. Set them per-hop, not just at the edge.
  • Circuit breakers: when a dependency's error rate crosses a threshold, stop calling it for a cooldown period and fail fast. This "can prevent a caller service from retrying a call to another service when the call has previously caused repeated timeouts or failures" and "detect when the callee service is functional again".
  • Bulkheads: isolate thread pools/connection pools per dependency so one slow dependency cannot exhaust all resources. Like watertight compartments in a ship.
  • Fallbacks: serve a degraded response (cached data, default value) instead of failing.

Retry storms

Naive retries are the most common cause of cascading failure: a brief failure triggers every client to retry simultaneously, multiplying load on an already-struggling service. As one source puts it, retries "amplify small failures into cascading effects such as retry storms, thread exhaustion, and queue buildup". The canonical example: "a 3-second database lock at Uber became a 3-minute cascading failure via Thread.sleep(100) retry loops".

Fixes:

  • Exponential backoff with jitter: wait 100 ms, 200 ms, 400 ms... plus a random jitter so retries de-synchronize. Jitter is essential; without it, all clients retry at the same instant.
  • Retry budgets: cap retries as a fraction of total requests (e.g., 10%). When the budget is exhausted, stop retrying and fail fast. This prevents retry amplification from consuming all capacity.
  • Only retry idempotent operations (GET, or writes with an idempotency key). Retrying a non-idempotent write can double-charge a customer.
  • Circuit breakers + backpressure together: the breaker stops the retry loop; backpressure tells upstream to stop sending.
  • Retry at one layer only: if every layer retries, a single request can become 3×3×3 = 27 requests. Pick one layer (usually the client or the edge proxy) to own retries.
AD-02

How do you handle idempotency in a distributed system (e.g., for payments)? Explain "exactly-once" semantics.

Why idempotency

In a distributed system, the network can fail after the server processes a request but before the client receives the response. The client retries — and the operation happens twice. For a payment, that is a double charge. Idempotency makes a retried request safe: the effect is applied once, and subsequent identical requests return the same result.

The idempotency key pattern

  1. The client generates a unique idempotency key per logical operation (a UUID, or a hash of the request). It sends the key in a header or field with every retry of that operation.
  2. The server, before processing, checks a store for the key. If it exists and the original request succeeded, return the stored response. If it exists and is in progress, return a conflict/in-progress response (or wait). If it does not exist, process the request and atomically record the key + result.
  3. The atomicity is critical: a conditional write (INSERT ... IF NOT EXISTS, or a Redis SETNX with a state machine) ensures two concurrent retries cannot both process. One source describes anchoring "each transaction to a unique identifier and enforcing uniqueness at the database layer" so "duplicate processing attempts resolve without creating additional financial entries".
  4. Stripe's implementation is the canonical example: Idempotency-Key, atomic phases, recovery points, and transactionally staged job drains.

The "exactly-once" myth

Exactly-once delivery is impossible in a distributed system. You can have at-most-once (may lose) or at-least-once (may duplicate). "Exactly-once" is achieved as a combination of at-least-once delivery + idempotent processing — the effect is exactly once even if the message is delivered multiple times.

One source states it plainly: "why exactly-once delivery is a myth, how idempotency keys make at-least-once feel exactly-once". Another notes that "networks may deliver requests repeatedly, workers may execute repeatedly, and webhooks may be observed repeatedly" — so the guarantee must be enforced at the effect layer, not the transport layer.

Practical details

  • Key scope and TTL: keys should be scoped per client and expire after a window (e.g., 24 hours) so the store does not grow forever. The window must exceed the maximum retry period.
  • Response storage: store the original response (status, body) so a retry returns the same result, not a different one.
  • State machine: the record has states: processing, succeeded, failed. A retry during processing must not start a second execution; it should wait or return 409.
  • Idempotency is not deduplication: dedup is a weaker form (drop duplicates); idempotency guarantees the same result for the same key, which is stronger for payments.
  • For consumers: use the message ID as the idempotency key; before applying the effect, check if the ID was already processed. Kafka's transactional producer (enable.idempotence=true, acks=all) provides idempotent writes to Kafka itself, but not to external systems — you still need an idempotency layer for the side effect.
AD-03

Explain the role of message queues (Kafka vs RabbitMQ) and distributed consensus (Paxos, Raft).

Why queues

Queues decouple producers from consumers: producers publish without waiting for consumers; consumers process at their own pace; a spike in load buffers instead of crashing the consumer; a consumer failure does not lose messages. They also enable fan-out (one event, many consumers) and replay (Kafka).

Kafka vs RabbitMQ

The choice is one of "the most common architectural decisions you'll face". They are different models:

DimensionKafkaRabbitMQ
ModelDistributed append-only log; consumers pull by offsetMessage broker with exchanges/queues; push to consumers
ThroughputVery high (millions/sec per cluster), sequential I/OHigh but lower; per-message routing overhead
ReplayYes — rewind offset and reprocessNo (message removed after ack)
OrderingPer partitionPer queue (with caveats)
RoutingTopic/partition; simpleRich exchanges (direct, topic, fanout, headers)
Use caseEvent streaming, log aggregation, CDC, replay pipelinesTask queues, RPC, complex routing, per-message TTL

Choose Kafka when you need a durable, replayable event log with very high throughput: analytics pipelines, change-data-capture, event sourcing. Choose RabbitMQ when you need flexible routing, per-message priorities/TTL, and a traditional task queue where messages are consumed once and discarded.

Delivery semantics

Both support at-most-once and at-least-once. Exactly-once is a transport illusion; the practical guarantee is at-least-once + idempotent consumers (see AD-02). Kafka adds transactions for exactly-once within Kafka (read-process-write), but external side effects still need idempotency.

Distributed consensus: Paxos and Raft

Consensus is how a cluster agrees on a value despite failures. It is the foundation of replicated logs, leader election, and distributed locks (etcd, ZooKeeper, Consul).

  • Paxos: the classic protocol. A proposer sends a prepare to a majority; if a majority promises, it sends an accept; if a majority accepts, the value is chosen. It is notoriously difficult to understand and implement. Multi-Paxos extends it to a log.
  • Raft: designed for understandability. It separates leader election, log replication, and safety. A leader is elected by a majority; it appends entries to its log and replicates to followers; an entry is committed when a majority has it. Raft "only allows servers with up-to-date logs to become leaders," which simplifies the safety argument compared to Paxos. It also defines membership changes via joint consensus.

Both require a majority quorum, so a 3-node cluster tolerates 1 failure; a 5-node cluster tolerates 2. They trade availability for consistency during a partition (CP in CAP terms). The interview point is: consensus is expensive (round trips, leader bottleneck); use it only for critical metadata (configuration, leadership, locks), not for high-throughput data paths.

Part 5 ML & GenAI System Design

ML-01

What is a feature store, and why is it needed?

Definition

A feature store is a system that centralizes the computation, storage, and serving of machine-learning features so that the same feature definition is used for training and inference. It has two sides:

  • Offline store: historical feature values for training (data warehouse/lake, Parquet, BigQuery). Optimized for throughput and point-in-time correctness.
  • Online store: low-latency latest feature values for real-time inference (Redis, DynamoDB, Cassandra). Optimized for p99 read latency.

Why it is needed

The core problem is training-serving skew: the feature computed in a training pipeline (batch SQL) differs from the feature computed at serving time (streaming code), so the model performs worse in production than in evaluation. A feature store prevents this by defining the feature once and materializing it to both stores. It also prevents duplicate work: "the same features (e.g., 'last 7 days of user purchases') [are not] computed differently by different teams," and it "prevents training-serving skew" by using the same computation in training and production.

Secondary benefits: feature reuse across teams (one team's "user lifetime value" feature is available to all models), discovery (a catalog of features), and governance (lineage, access control, freshness SLAs).

When it is justified

A feature store is justified by two conditions: online/offline consistency (train/serve skew) and feature reuse across teams. If you have one model and a simple pipeline, a feature store is over-engineering. If you have many models, many teams, and real-time serving, it becomes essential infrastructure.

Key design considerations

  • Point-in-time correctness: when building training data, you must use the feature value as it was at the time of the label event, not the latest value. Otherwise you leak future information (label leakage).
  • Freshness: how stale can the online feature be? Batch-computed features may be hours old; streaming features seconds old. The store must expose freshness metadata.
  • Consistency: the offline and online stores must be populated from the same pipeline (or a validated dual-write) to avoid skew.
  • Backfills: when a feature definition changes, you must recompute history — the store needs a backfill mechanism.
ML-02

Explain model serving architectures: batch, real-time, and streaming. What is the role of a model registry?

Serving modes

ModeHow it worksUse case

Real-time (online)Call the model per request via an API; return the prediction in the response.Fraud detection, dynamic pricing, ranking at request time.

The interview point is to match the mode to the latency requirement and the freshness of the features. Real-time serving is the hardest: you need low-latency feature fetch (online store), model inference within the request budget, and fallbacks when the model is slow or unavailable.

Model registry

A model registry is a versioned catalog of trained models: artifacts, metadata (training data, hyperparameters, metrics), stage (staging/production/archived), and lineage. It is the source of truth for "which model is deployed where." Serving systems pull from the registry; rollbacks are a pointer change to a previous version. Without a registry, you get untraceable models, irreproducible deployments, and no clean rollback path.

Serving infrastructure concerns

  • Inference server: a runtime that loads the model and serves predictions (TorchServe, Triton, TF Serving, or a custom FastAPI service). It handles batching, GPU scheduling, and model versioning.
  • Dynamic batching: group multiple requests into one forward pass to improve GPU utilization, at the cost of a small latency increase. Critical for throughput.
  • Autoscaling: scale on GPU utilization / queue depth, not CPU. Cold start of a model can take minutes; keep warm pools.
  • Monitoring: track prediction drift, feature drift, latency, and error rate. A model can be technically healthy (200 OK) but semantically broken (predicting garbage).
  • Fallbacks: if inference times out, serve a cached prediction or a rule-based default rather than failing the request.
ML-03

How would you design a system around a Large Language Model (LLM)? What are the unique challenges?

The basic pipeline

User input → prompt construction (system prompt + retrieved context + conversation history) → LLM inference → output validation/safety → response. Around this core you need retrieval, memory, tool calling, and cost/rate control.

Retrieval-Augmented Generation (RAG)

LLMs have a fixed context window and no knowledge of your private data. RAG solves this: embed documents into a vector database, embed the user query, retrieve the top-k relevant chunks, and include them in the prompt as context. The model generates an answer grounded in retrieved text. This avoids fine-tuning for every data update and reduces hallucination (though it does not eliminate it). Design considerations: chunking strategy, embedding model choice, hybrid search (vector + keyword/BM25), reranking, and freshness of the index.

Unique challenges

  • Latency: LLM inference is slow (hundreds of ms to seconds) and output is generated token by token. Streaming the response to the user is essential for perceived performance. Use smaller models or speculative decoding where possible.
  • Cost: inference is expensive (GPU hours or per-token API pricing). Control cost with caching (semantic cache for similar queries), prompt compression, model routing (small model for simple queries, large model for complex), and hard token limits per user.
  • Rate limiting and quotas: per-user and per-tenant token budgets; queueing during peak; graceful degradation to a smaller model.
  • Safety and guardrails: input moderation (prompt injection, jailbreak detection), output moderation (toxic content, PII leakage), and grounding checks (does the answer cite retrieved sources?). Never trust the model's output blindly.
  • Evaluation: traditional accuracy metrics do not work well for free-text generation. Use human evaluation, LLM-as-judge (with its own biases), and task-specific metrics (faithfulness, relevance, toxicity).
  • State and memory: conversation history must be truncated or summarized to fit the context window. A memory service stores long-term facts and retrieves them when relevant.
  • Non-determinism: the same prompt can produce different outputs. This complicates testing, caching, and reproducibility. Set temperature to 0 for deterministic tasks; accept variability for creative tasks.

Architecture sketch

Client → API Gateway (auth, rate limit) → Orchestrator
  ├── Retriever (vector DB + keyword search) → context
  ├── Prompt Builder (system + history + context)
  ├── LLM Provider (with fallback to a second provider/model)
  ├── Output Guardrails (moderation, PII, grounding)
  └── Cache (semantic cache for repeated queries)

The orchestrator is the key component: it decides whether to retrieve, which model to call, how to handle a provider outage (fallback), and when to return a cached response. It is a classic system-design problem wrapped around a probabilistic model.

Part 6 Fresher-Level Questions

FR-01

What is system design, and why is it important?

System design is the process of defining the architecture, components, data flow, and trade-offs of a software system to meet functional and non-functional requirements. It answers questions like: What are the major components? How do they communicate? Where does data live? How does the system behave under load, failure, and scale?

It matters because code-level correctness is not enough. A system can be functionally correct and still collapse under traffic, lose data on a node failure, or cost 10× more than necessary. System design is about the properties that emerge when components interact: availability, scalability, latency, durability, and operability. Interviews test it because senior engineers spend more time on these decisions than on writing individual functions.

FR-02

What is a load balancer, and why is it used?

A load balancer distributes incoming traffic across multiple backend servers. It is used to (1) scale horizontally — add more servers instead of buying a bigger one; (2) achieve high availability — if one server dies, others continue serving; (3) improve performance — spread load so no single server is saturated; and (4) enable zero-downtime deployments — drain and replace servers one at a time. It also provides TLS termination, health checks, and a single point for observability and security policy.

FR-03

Design a basic API for a to-do app.

Resources: users, lists, tasks. Endpoints:

POST   /users                 create user
GET    /users/{id}            get user
POST   /lists                 create list (owner from auth)
GET    /lists/{id}/tasks      list tasks
POST   /lists/{id}/tasks      create task
PATCH  /tasks/{id}            update (title, done, due_date)
DELETE /tasks/{id}            delete

Use JSON, standard HTTP status codes (201 for create, 404 for missing, 401/403 for auth), and cursor-based pagination for task lists. Store in a relational DB (users, lists, tasks with foreign keys) because the data is relational and transactional. Authenticate with JWT or session cookies. Add a cache for read-heavy list endpoints if needed. This is a low-scale design; the interview point is clean resource modeling, not sharding.
