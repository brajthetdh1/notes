Question 01

Define load balancing and explain its primary objectives (high availability, scalability, reliability).

Definition

Load balancing is the practice of distributing incoming work — TCP connections, HTTP requests, gRPC calls, database queries, or messages pulled from a queue — across a pool of backend resources so that no single resource becomes a bottleneck or a single point of failure. It is both a component (a load balancer, LB) and an architectural property (the system as a whole spreads load).

Formally: given a set of backends B = {b1..bn} with heterogeneous and time-varying capacity, and a stream of requests R with heterogeneous and time-varying cost, a load balancer is a function that maps each request to a backend such that (a) no backend is overloaded, (b) the mapping is stable enough to preserve useful locality, and (c) the mapping adapts when backends fail or join.

Why it exists

A single server has hard ceilings: CPU cores, memory, file descriptors, ephemeral ports, NIC bandwidth, and disk IOPS. Long before those ceilings are hit, queueing theory tells us latency degrades non-linearly — as utilization approaches 1, wait time approaches infinity. Beyond performance, a single server is a single failure domain. Load balancing solves three problems simultaneously: it breaks the capacity ceiling, it removes the single point of failure, and it gives you a control point where you can observe, route, and shape traffic.

Primary objectives

1. High availability. The LB continuously probes backends via health checks and removes unhealthy ones from rotation. With N healthy replicas, the system tolerates N−1 failures (and often more, with capacity headroom). Availability compounds multiplicatively in series — a 99.9% backend behind a 99.99% LB still yields roughly 99.89% end-to-end — so the LB itself must be deployed redundantly (active-active pairs, anycast VIPs, or a cloud-managed LB with an SLA).

2. Scalability. Load balancing is what makes horizontal scaling possible. Adding a backend is a config/discovery event rather than a re-architecture. This enables elastic autoscaling: when CPU or request rate crosses a threshold, new instances register with the LB and begin receiving traffic within seconds. Crucially, horizontal scaling requires the application to be stateless or to externalize state (sessions, uploads) — the LB is a necessary but not sufficient condition.

3. Reliability. Reliability here means predictable, correct behavior under stress and partial failure. A good LB provides: avoidance of hot spots (a single slow backend doesn't get 1/N of traffic forever), graceful degradation (shed load rather than collapse), connection draining during deploys so in-flight requests complete, retry budgets with idempotency awareness, and outlier ejection so that a backend returning 5xx is quarantined before it poisons the user experience.

Secondary objectives worth naming

  • Efficiency / utilization: a good algorithm keeps all backends near a similar utilization band, which directly reduces cost per request.
  • Latency control: least-latency or P2C routing avoids slow-tail backends; this is the difference between p50 optimization and p99 optimization.
  • Zero-downtime deployment: LBs enable canary, blue-green, and rolling updates by shifting traffic weights.
  • Security boundary: an L7 LB terminates TLS, hides backend topology, and is a natural place for WAF, mTLS, and rate limiting.
  • Observability: the LB is the single chokepoint where you can measure true request rate, error rate, and latency per backend.

What load balancing does NOT do

Senior-signal answer: interviewers look for this distinction. A load balancer does not make a slow backend fast; it does not reduce total work; it does not fix a stateful design; it does not replace capacity planning; and it does not by itself reduce end-to-end latency. It redistributes load and failure. If every backend is saturated, an LB just makes the failure orderly.

Where load balancing lives

Production systems typically have several layers: global DNS/GSLB for geo-routing, an edge L7 LB/CDN, a regional L4 network LB, a service-mesh sidecar layer for east-west traffic, and client-side load balancing inside SDKs. Each layer solves a different problem; naming this layering is a strong senior signal.

Question 02

Explain the difference between Layer 4 (L4) and Layer 7 (L7) load balancing. When would you choose one over the other?

The core distinction

The difference is how much of the packet the LB understands. An L4 LB operates on the OSI transport layer: it sees IP addresses, ports, and TCP/UDP headers. It forwards packets or proxies byte streams without parsing the payload. An L7 LB terminates the application protocol — it reassembles HTTP/1.1, HTTP/2, HTTP/3, gRPC, or WebSocket — and makes routing decisions based on the actual request: method, path, host, headers, cookies, query parameters, or even a JWT claim.

L4 characteristics

  • Routing key: the 5-tuple (src IP, src port, dst IP, dst port, protocol).
  • Implementation: often kernel-level — IPVS, ECMP hashing, DSR (direct server return) where the response bypasses the LB entirely.
  • Performance: extremely high — millions of concurrent connections and multi-terabit throughput per cluster, with microsecond added latency.
  • Protocol-agnostic: works for MySQL, Postgres, Redis, MQTT, DNS, custom TCP protocols — anything.
  • Limitations: cannot route by URL, cannot terminate TLS (unless SNI-based, which is a hybrid), cannot do per-request retries, cannot inject headers, cannot do L7 rate limiting.
  • Connection semantics: a connection is pinned to one backend for its lifetime. This matters enormously — an L4 LB cannot rebalance a long-lived multiplexed HTTP/2 connection, so a single connection can carry thousands of requests to one backend.

L7 characteristics

  • Routing key: anything in the request. Path-based (/api/v1/*), host-based (tenant.example.com), header-based (x-canary: true), weight-based, or content-based.
  • TLS termination and re-encryption, SNI routing, mTLS to backends.
  • Traffic management: retries with budgets, timeouts, circuit breaking, request mirroring, header mutation, compression, response caching.
  • Observability: per-route metrics, distributed trace propagation, structured access logs.
  • Cost: higher CPU (parsing, TLS crypto), higher added latency (typically 1–10 ms), and it must handle connection fan-in/fan-out.
  • Protocol support: limited to what the proxy implements. gRPC and HTTP/2 require proper stream-level handling; naive L7 proxies break multiplexing.

Decision framework

Choose L4 when…Choose L7 when…
Protocol is non-HTTP (databases, Redis, Kafka, custom TCP) You need path/host/header routing for microservices
Raw throughput and minimal latency dominate (ad tech, gaming, real-time bidding) You need TLS termination, auth, WAF, or rate limiting
You need to preserve client IP and avoid proxy overhead (DSR) You need canary/blue-green with request-level weights
Connections are long-lived and you want simple stream affinity You need retries, timeouts, circuit breaking, or observability per route
Cost per request must be near zero at massive scale You need to inspect or transform payloads (headers, JWTs, cookies)

Real architectures layer both

A typical production path is: anycast/DNS → L4 network LB (fast, DDoS absorption, cross-zone distribution) → L7 proxy (Envoy/NGINX/ALB: routing, TLS, retries) → service mesh sidecar (east-west L7) → pod. The L4 tier exists precisely so the L7 tier doesn't have to be the throughput bottleneck, and the L7 tier exists because L4 can't make intelligent decisions.

Nuances interviewers probe

  • SNI-based routing is technically L4 but peeks into TLS — a useful hybrid to mention.
  • L4 + connection pooling mismatch: if an L4 LB balances connections but clients use HTTP/2, load becomes skewed. L7 proxies fix this by balancing requests.
  • Proxy protocol exists because L4 forwarding destroys the client IP.
  • Latency amplification: each L7 hop adds tail latency; p99 through 4 hops can be much worse than the sum of p50s.
Question 03

Compare common load balancing algorithms: Round Robin, Weighted Round Robin, Least Connections, Least Response Time, IP Hashing.

The framing

Every algorithm is an answer to the same question: given the current state I can observe, which backend should get the next request? The differences are (a) how much state the algorithm tracks, (b) what it assumes about request cost and backend capacity, and (c) how it behaves when those assumptions break. Strong answers always connect the algorithm to the workload shape.

Round Robin (RR)

Cycle through backends in order. O(1) state (a counter), zero coordination, perfectly even request distribution. Works well when requests are homogeneous in cost and backends are identical. Breaks when: backend capacities differ, request costs vary by orders of magnitude (a 5 ms cache hit and a 2 s report generation both count as "1"), or a backend is slow-but-alive (it still gets 1/N).

Weighted Round Robin (WRR)

Each backend gets a weight proportional to capacity; the scheduler allocates proportionally (smooth WRR, as in NGINX, avoids burstiness by tracking current weights). Use it when you have known heterogeneous capacity — mixed instance sizes, or canary deploys where the new version gets 5% weight. Limitation: weights are static and operator-supplied. They don't adapt to real-time load or to a backend that is temporarily degraded.

Least Connections (LC)

Send to the backend with the fewest in-flight requests/connections. This is a proxy for queue depth and handles variable request duration far better than RR — a backend stuck on slow requests naturally stops receiving new ones. Weighted Least Connections divides by weight. The critical caveat: it counts connections, not requests, unless the LB is L7. With HTTP/2 or keep-alive, one connection carries many concurrent requests, so connection count badly misrepresents load. Modern L7 proxies therefore track active requests per backend.

Least Response Time

Route to the backend with the lowest observed latency (often a weighted blend of latency and active connections, e.g., NGINX's least_time or Envoy's EWMA). This directly optimizes the metric users feel. Risks: it is a feedback loop — a backend that gets a lucky fast sample attracts a burst, which slows it, causing oscillation; and latency measured at the LB includes network RTT, so a distant-but-idle backend may look worse than a nearby-but-busy one. Use EWMA smoothing and a connection/queue penalty term.

IP Hashing / Source IP Affinity

hash(client_ip) mod N deterministically maps a client to a backend, giving session affinity without cookies and improving cache locality. Problems: (a) clients behind NAT/CGNAT/corporate proxies share an IP and all land on one backend — a hot spot; (b) mod N remaps almost every key when N changes, which is why production uses consistent hashing or rendezvous (HRW) hashing instead; (c) mobile clients change IPs constantly, destroying affinity.

Others worth naming

  • Random / Random Two Choices (P2C): pick two backends at random, choose the less loaded. Provably near-optimal (within a constant factor of optimal) with almost no state — this is what Envoy and many RPC frameworks default to. Excellent default when per-request state is expensive to share.
  • Consistent hashing ring: for cache-affinity or sharded backends; minimal key remapping on scale events.
  • Power-of-two with EWMA latency: the practical production winner for microservices.
  • Priority / failover: primary pool, secondary pool on failure.
  • Least Bandwidth / Least Load (CPU-based): requires backends to report load; accurate but adds a telemetry dependency and lag.

Choosing: the workload matrix

Mixed instance sizesWeighted RR / Weighted LCCapacity-proportional

Key line to use in interview: "The algorithm matters less than the signal quality — a least-connections LB with a 30-second stale view performs worse than round robin with accurate health checks."
Question 04

What are the drawbacks of Round Robin? Explain Consistent Hashing and why virtual nodes are needed.

Round Robin drawbacks, precisely

Round Robin is the correct answer when requests are homogeneous, backends are identical, and every backend is healthy. Each of those assumptions is usually false:

  • Ignores capacity heterogeneity. A 2-core pod and a 32-core pod each get 1/N. The small pod saturates; the large pod idles. Utilization becomes bimodal and cost per request rises.
  • Ignores request cost. A cached lookup and a full-text search are both "one request." Under RR, a shard of expensive requests can land consecutively on one backend purely by chance — variance in queue depth grows, and tail latency (p99) degrades even while mean throughput looks fine.
  • Ignores current load. If backend B is processing a batch job or GC-pausing, RR keeps feeding it. LC would have steered away within one RTT.
  • Slow-start / JIT warmup. A freshly started instance gets full traffic immediately. Connection pools aren't warm, caches are cold, and it may be several times slower — but RR doesn't care. This is why warmup/ramp weights exist.
  • Failure detection lag. RR is only as good as the health check. Between a backend dying and the health check marking it down, 1/N of requests fail. Passive outlier detection (consecutive 5xx) is needed to shorten that window.
  • No affinity. With stateful backends or per-backend caches, RR maximizes cache misses and cross-node chatter.
  • Amplification in fan-out systems. If a request fans out to 100 backends and each has a 1% chance of being overloaded, RR gives you ~63% chance of hitting at least one slow backend. Tail latency compounds — this is the classic "tail at scale" problem.

Consistent Hashing

The problem it solves: with hash(key) mod N, changing N from 10 to 11 remaps roughly 90% of keys. In a cache tier that's a catastrophic miss storm that hammers the origin; in a sharded store it's a mass data migration.

Mechanism. Map both backends and keys onto a circular hash space (e.g., 0 to 2³²−1). Each backend is placed at hash(backend_id). To place a key, compute hash(key) and walk clockwise to the first backend. When a backend is added or removed, only the keys in the arc between it and its predecessor move — on average K/N keys, not K·(N−1)/N. That's the defining property: minimal disruption on membership change.

Why virtual nodes are needed

With one point per backend, two problems appear immediately:

  • Non-uniform distribution. Hashing N identifiers onto a ring produces uneven arcs — with 3 nodes, the largest arc can easily be 2–3× the average. One backend gets a disproportionate share, which is exactly the imbalance you were trying to eliminate.
  • No capacity weighting. A 2-core and a 32-core machine get identical expected share.

Solution: place each backend at many points — hash(backend_id + "#" + i) for i in 1..V (typically 100–1000 virtual nodes). Now each physical node owns many small arcs scattered across the ring. By the law of large numbers, load variance collapses: with V virtual nodes, the standard deviation of load share scales roughly as 1/√V. And capacity weighting becomes trivial — give a 4× larger machine 4× the virtual nodes.

Refinements to mention

  • Bounded load / power-of-two-choices on the ring: when the next node is above avg_load × (1+ε), continue clockwise. Prevents hot keys from overwhelming one node.
  • Replication: write each key to the next R nodes clockwise for durability; read from the first. This is the Dynamo/Cassandra model.
  • Jump Consistent Hash (Google): O(1) memory and no ring, but doesn't support weights or arbitrary removal order.
  • Maglev hashing (Google LB): builds a fixed lookup table, designed for very fast, very uniform LB decisions with minimal disruption.
  • Rendezvous (HRW) hashing: score each backend as hash(key, backend) and take the max — no ring needed, same minimal-disruption property, naturally weightable.
Where consistent hashing shows up in LB interviews: cache-affinity routing (route the same user/URL to the same cache node), sharded stateful services, sticky sessions without cookies, and distributed storage placement. Name at least one concrete system (Cassandra, DynamoDB, Envoy's ring_hash) to show applied knowledge.
Question 05

What is the difference between a hardware and a software load balancer?

Hardware load balancers

Purpose-built appliances — F5 BIG-IP, Citrix NetScaler, A10 Thunder, Radware — with custom ASICs or FPGAs for packet processing. They are deployed in pairs at the network edge, often using Direct Server Return (DSR): the LB rewrites the destination MAC/IP on the way in, but the backend replies directly to the client, so the return path never touches the appliance. That's why an appliance with modest throughput can front a much larger response volume.

Strengths: deterministic, extremely low, low-variance latency (hardware forwarding, no GC, no context switches); very high connection-per-second rates; mature feature sets (SSL offload, WAF, GSLB, connection limits, extensive health checks); vendor support and SLAs, which matters in regulated industries.

Weaknesses: expensive (six figures with licensing tiers); capacity is fixed and over-provisioned for peak — you buy for Black Friday and idle the rest of the year; scaling means buying another chassis; configuration is vendor-proprietary (iRules, policies) and often managed by a separate network team, creating an org bottleneck; upgrading is a maintenance window on physical hardware.

Software load balancers

Software running on commodity compute or containers: NGINX/NGINX Plus, HAProxy, Envoy, Traefik, and the kernel datapath (IPVS, eBPF/XDP, DPDK). Cloud-managed LBs (AWS ALB/NLB, GCP Cloud Load Balancing, Azure Front Door) are software LBs with the operational burden outsourced.

Strengths: elastic — scale horizontally with demand, pay for what you use; programmable — declarative config, APIs, GitOps, dynamic service discovery so backends register/deregister automatically; cheap to run many instances for redundancy; fast release cadence; runs anywhere (on-prem, cloud, edge); rich L7 features (header routing, retries, tracing, mTLS) because it's just code.

Weaknesses: the data plane competes with the app for CPU/memory; noisy-neighbor effects; TLS handshakes are CPU-expensive in userspace; the control plane (config distribution) becomes its own distributed-systems problem; at extreme throughput, generic kernels struggle — hence eBPF/XDP and DPDK, which push forwarding into the kernel or bypass it entirely.

Comparison

DimensionHardware LBSoftware LB
LatencyMicroseconds, very low jitterLow but variable (GC, scheduling)
Throughput ceilingVery high per deviceHigh per node; scales horizontally
ElasticityPoor — fixed capacityExcellent
Cost modelCapEx, licensingOpEx, per-instance

Service discoveryLimited, static poolsNative (K8s, Consul, EDS)

Blast radiusLarge (one device fronting everything)Small (many small instances)

How to choose

The industry has decisively moved to software-defined load balancing, but the honest answer is nuanced:

  • Choose hardware/managed-appliance when you need guaranteed line-rate throughput with bounded tail latency, when regulatory or vendor-support requirements demand it, or when you have a very large, stable, non-HTTP footprint and a network team already operating appliances.
  • Choose software for anything cloud-native, anything that autoscales, anything needing L7 routing or frequent configuration change. The default in modern architectures is a managed cloud LB at the edge plus a software L7 proxy/mesh inside.
  • Hybrid is common: a hardware/anycast edge for DDoS absorption and TLS offload, with software L7 behind it.
Scale nuance to mention: a naive userspace proxy saturates a core at roughly 100k–200k req/s. That's why high-scale software LBs use kernel bypass — eBPF/XDP (Cilium), DPDK (some NFV), or IPVS in the kernel — to reach millions of packets per second on commodity hardware. This is the real answer to "can software match hardware?"
Question 06

Explain the role of health checks in a load balancer. How would you design them?

The role

Health checks are the load balancer's model of reality. Every routing decision implicitly assumes the backend is alive and able to serve; health checks are what keep that assumption true. Without them, a failed backend receives its share of traffic until an operator intervenes — converting a single-node failure into a sustained partial outage and, often, a cascading one as clients retry against the same dead endpoint.

The design goal is not "detect failure" but detect failure fast, without false positives, and recover without a thundering herd. Those three requirements are in direct tension.

Two mechanisms, used together

  • Active checks: the LB proactively probes an endpoint on a schedule (TCP connect, HTTP GET /healthz, gRPC health protocol). Deterministic and independent of traffic, but costs resources and only samples the endpoint — it can pass while real requests fail.
  • Passive checks (outlier detection): the LB observes real request outcomes and ejects backends with elevated error rates or latency. Zero extra traffic, catches real failures, but only detects a backend when it is already serving bad traffic — so it must be paired with active checks.

Design parameters

ParameterTypical valueReasoning
Interval2–10 sShorter = faster detection but more probe load
Timeout1–3 sMust be < interval to avoid overlapping probes
Unhealthy threshold2–3 consecutive failsAvoids evicting on a single blip
Healthy threshold2–5 consecutive passesPrevents flapping on unstable nodes
Ejection time30 s, exponential backoffDon't immediately re-add a still-broken node
Max ejection %≤ 50% of poolPrevents evicting everything

Shallow vs deep checks — the critical design decision

Shallow ("is this process able to accept a connection and return 200?") tells you the instance is alive. Deep ("can this instance reach the database, cache, and downstream service?") tells you it can do useful work — but it is dangerous.

The classic failure: if every health check queries the shared database, and the database has a brief slowdown, every backend fails its check simultaneously. The LB evicts the entire pool and a partial degradation becomes a total outage. Deep checks turn shared dependencies into a correlated failure mode.

Correct pattern: expose two endpoints. /livez (liveness) — is the process running; used to restart, never to remove from LB rotation. /readyz (readiness) — should this instance receive traffic; checks only local state (is it still warming up, is its own listener bound, has config loaded). Downstream dependency health should be handled by circuit breakers and outlier detection in the data path, not by the health check.

Warmup and slow start

A newly started instance is not equal to a warm one — empty connection pools, cold caches, un-JITted code. Without protection, the health check marks it ready and it immediately receives full 1/N traffic, producing a latency spike and sometimes failing under the load. Design a slow-start ramp: linearly increase the weight from ~10% to 100% over 30–60 s after the first successful check. Envoy's slow_start and NGINX's slow_start both implement this.

Recovery storms

When a large pool recovers, all nodes are marked healthy at once and traffic floods in. If the cause of the original failure was overload, you immediately re-trigger it. Mitigate with randomized health-check intervals (jitter), ramp-up weights, and consecutive-success thresholds so nodes rejoin gradually and at different times.

Practical details that signal experience

  • Health endpoint must be cheap: no auth, no heavy DB query, no logging spam. It will be called every few seconds by every LB instance.
  • Don't let health checks depend on the LB's own hostname — that creates a circular dependency.
  • Use the right probe type: TCP connect detects process death but not a hung-but-listening app; HTTP GET detects app-level hangs; gRPC requires the standard health-checking service.
  • Health checks are a DoS vector if the endpoint is expensive and the LB fleet is large — monitor probe volume.
  • Distinguish graceful shutdown: on SIGTERM, flip readiness to failing first, wait for connection draining (deregistration delay ≈ longest request timeout), then shut down.
  • Alert on ejection rate, not just availability — a slowly rising ejection rate is the earliest signal of a systemic problem.
