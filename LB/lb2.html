Part 1 Load Balancing — Fundamentals

What load balancing is, how L4 and L7 differ, which algorithm to choose, and how to keep backends healthy.

LB-01

Define load balancing and explain its primary objectives.

Definition. Load balancing is the practice of distributing incoming work — TCP connections, HTTP requests, gRPC calls, queue messages — across a pool of backends so no single resource becomes a bottleneck or a single point of failure. It is both a component (a load balancer) and an architectural property.

Formally: given backends with heterogeneous, time-varying capacity and requests with heterogeneous cost, a load balancer maps each request to a backend such that no backend is overloaded, the mapping preserves useful locality, and it adapts when backends fail or join.

Why it exists

A single server has hard ceilings — CPU, memory, file descriptors, NIC bandwidth, disk IOPS. Queueing theory says latency degrades non-linearly as utilization approaches 1. Beyond performance, a single server is a single failure domain. Load balancing breaks the ceiling, removes the SPOF, and creates a control point for routing and observation.

Primary objectives

  • High availability: health checks remove unhealthy backends; N replicas tolerate N−1 failures. Availability compounds in series, so the LB itself must be redundant.
  • Scalability: makes horizontal scaling possible — adding a backend is a discovery event, not a re-architecture. Requires statelessness or externalized state.
  • Reliability: no hot spots, graceful degradation, connection draining on deploy, retry budgets, outlier ejection of failing backends.

Secondary objectives

  • Utilization/efficiency: even utilization across backends lowers cost per request.
  • Latency control: P2C or least-latency routing avoids slow-tail backends (p99, not p50).
  • Zero-downtime deploys: weighted traffic shifting enables canary and blue-green.
  • Security boundary: TLS termination, hidden topology, WAF, mTLS, rate limiting.
  • Observability: the single chokepoint for true request rate, error rate, and per-backend latency.
What it does NOT do: make a slow backend fast, reduce total work, fix a stateful design, replace capacity planning, or reduce end-to-end latency by itself. It redistributes load and failure. If every backend is saturated, the LB only makes the failure orderly.

Where it lives

Production systems layer several: global DNS/GSLB, edge L4 network LB, regional L7 proxy, API gateway, service-mesh sidecar for east-west, and client-side LB in SDKs. Each solves a different problem (see LB-14).

LB-02

Explain Layer 4 vs Layer 7 load balancing. When do you choose each?

The difference is how much of the packet the LB understands. An L4 LB sees IPs, ports, and TCP/UDP headers and forwards byte streams. An L7 LB terminates the application protocol — HTTP/1.1, HTTP/2, HTTP/3, gRPC, WebSocket — and routes on method, path, host, headers, cookies, or JWT claims.

L4 characteristics

  • Routing key: the 5-tuple (src IP, src port, dst IP, dst port, protocol).
  • Often kernel-level: IPVS, ECMP hashing, DSR (direct server return).
  • Extremely high throughput, microsecond latency, millions of connections.
  • Protocol-agnostic: works for MySQL, Postgres, Redis, MQTT, custom TCP.
  • Cannot route by URL, terminate TLS (except SNI), retry per request, or inject headers.
  • A connection is pinned to one backend for its lifetime — fatal for HTTP/2 multiplexing.

L7 characteristics

  • Routes on anything in the request: path, host, header, weight, content.
  • TLS termination and re-encryption, SNI routing, mTLS to backends.
  • Retries with budgets, timeouts, circuit breaking, request mirroring, compression, caching.
  • Per-route metrics, trace propagation, structured access logs.
  • Higher CPU (parsing, crypto), 1–10 ms added latency.
  • Only supports protocols the proxy implements; naive gRPC handling breaks stream multiplexing.

Real architectures layer both

anycast/DNS → L4 network LB (line rate, DDoS absorption, cross-AZ) → L7 proxy (routing, TLS, retries) → service-mesh sidecar → pod. The L4 tier exists so the L7 tier isn't the throughput bottleneck; the L7 tier exists because L4 can't make intelligent decisions.

Nuances interviewers probe

  • SNI routing is technically L4 but peeks into TLS — a useful hybrid.
  • L4 + HTTP/2: balancing connections while clients multiplex requests causes severe skew; L7 fixes this by balancing requests.
  • PROXY protocol exists because L4 forwarding destroys the client IP.
  • Tail latency compounds across L7 hops (see LB-14).
LB-03

Compare load balancing algorithms. How do you choose?

Every algorithm answers one question: given the state I can observe, which backend gets the next request? They differ in how much state they track, what they assume about request cost and capacity, and how they fail when assumptions break.

  • Round Robin: O(1) state, perfectly even request distribution. Breaks when capacities differ, request costs vary, or a backend is slow-but-alive.
  • Weighted RR: capacity-proportional; smooth WRR (NGINX) avoids burstiness. Weights are static and operator-supplied — they don't adapt to real-time degradation.
  • Least Connections: proxy for queue depth; handles variable request duration well. Critical caveat: it counts connections, not requests, unless L7 — HTTP/2 multiplexing makes connection count meaningless.
  • Least Response Time: optimizes the metric users feel. Risks a feedback loop (lucky fast sample attracts a burst, causing oscillation); use EWMA smoothing plus a queue penalty.
  • IP Hashing: deterministic affinity without cookies. Breaks under NAT/CGNAT (many clients share an IP), remaps ~all keys when N changes, and mobile clients change IPs constantly.
  • Power of Two Choices (P2C): pick two at random, take the less loaded. Near-optimal with almost no shared state — the practical default in Envoy and many RPC frameworks.
  • Consistent hashing / rendezvous (HRW): affinity with minimal remapping on membership change (see LB-04).
  • Priority/failover: primary pool, secondary on failure.

LB-04

What are the drawbacks of Round Robin? Explain consistent hashing and virtual nodes.

Round Robin drawbacks

  • Ignores capacity heterogeneity: a 2-core and a 32-core pod each get 1/N.
  • Ignores request cost: a cache hit and a full-text search both count as "1"; queue-depth variance grows and p99 degrades.
  • Ignores current load: a GC-pausing backend keeps receiving its share.
  • No slow start: a cold instance gets full traffic immediately.
  • Failure detection lag: between a node dying and the health check marking it down, 1/N of requests fail.
  • No affinity: maximizes cache misses for stateful backends.
  • Fan-out amplification: 100 backends each with 1% chance of being slow → ~63% chance a request hits a slow one.

Consistent hashing

With hash(key) mod N, changing N from 10 to 11 remaps ~90% of keys — a cache miss storm or a mass data migration. Consistent hashing maps backends and keys onto a circular hash space; a key walks clockwise to the first backend. Adding or removing a backend moves only the keys in the arc between it and its predecessor — on average K/N, not K·(N−1)/N. That minimal disruption is the defining property.

Why virtual nodes are needed

  • Non-uniform distribution: hashing N identifiers onto a ring produces uneven arcs — with 3 nodes the largest arc can be 2–3× the average.
  • No capacity weighting: a 2-core and a 32-core machine get identical expected share.

Solution: place each backend at V points — hash(id + "#" + i), typically 100–1000. Each physical node now owns many small arcs; load variance collapses roughly as 1/√V. Weighting becomes trivial — a 4× larger machine gets 4× the virtual nodes.

Refinements worth naming

  • Bounded load: if the next node exceeds avg × (1+ε), continue clockwise — prevents hot-key overload.
  • Replication: write to the next R nodes clockwise (Dynamo/Cassandra model).
  • Jump Consistent Hash: O(1) memory, no ring, but no weights.
  • Maglev hashing: fixed lookup table for very fast, uniform decisions (Google LB).
  • Rendezvous (HRW): score each backend and take the max — no ring, same minimal-disruption property, naturally weightable.
Where it appears: cache-affinity routing, sharded stateful services, sticky sessions without cookies, and distributed storage placement. Name a concrete system — Cassandra, DynamoDB, Envoy's ring_hash.
LB-05

What is the difference between a hardware and a software load balancer?

Hardware load balancers

Purpose-built appliances (F5 BIG-IP, Citrix NetScaler, A10, Radware) with ASICs/FPGAs. Deployed in pairs at the edge, often with Direct Server Return: the LB rewrites the destination on the way in, but the backend replies directly to the client, so the return path bypasses the appliance.

Strengths: deterministic, low-variance latency (no GC, no context switches); very high connection-per-second rates; mature features (SSL offload, WAF, GSLB); vendor SLAs for regulated industries.

Weaknesses: expensive; fixed capacity over-provisioned for peak; scaling means buying another chassis; proprietary config managed by a separate network team; upgrades require maintenance windows.

Software load balancers

NGINX, HAProxy, Envoy, Traefik, kernel datapath (IPVS, eBPF/XDP, DPDK), and cloud-managed LBs (ALB/NLB, GCP CLB, Azure Front Door).

Strengths: elastic, pay-for-use; programmable via API/GitOps with dynamic service discovery; cheap to run many instances for redundancy; rich L7 features because it's just code; runs anywhere.

Weaknesses: data plane competes with the app for CPU; noisy neighbors; userspace TLS is expensive; the control plane is its own distributed-systems problem; generic kernels struggle at extreme throughput without eBPF/DPDK.

How to choose

  • Hardware/appliance when you need guaranteed line-rate throughput with bounded tail latency, regulatory/vendor-support requirements, or a very large stable non-HTTP footprint with an existing network team.
  • Software for anything cloud-native, autoscaling, needing L7 routing or frequent config change. The modern default is a managed cloud LB at the edge plus a software L7 proxy/mesh inside.
  • Hybrid is common: anycast/hardware edge for DDoS and TLS offload, software L7 behind it.
Scale nuance: a naive userspace proxy saturates a core around 100k–200k req/s. High-scale software LBs use kernel bypass — eBPF/XDP (Cilium), DPDK, or IPVS — to reach millions of packets/sec on commodity hardware. That is the real answer to "can software match hardware?"
LB-06

Explain the role of health checks. How would you design them?

Health checks are the load balancer's model of reality. Without them, a failed backend keeps receiving its share of traffic until an operator intervenes — turning a single-node failure into a sustained partial outage and often a cascading one as clients retry the dead endpoint.

The goal is not "detect failure" but detect fast, without false positives, and recover without a thundering herd — three requirements in direct tension.

Two mechanisms, used together

  • Active checks: scheduled probes (TCP connect, HTTP GET /healthz, gRPC health protocol). Deterministic, but only samples the endpoint — it can pass while real requests fail.
  • Passive checks (outlier detection): observe real outcomes and eject backends with elevated errors or latency. Zero extra traffic, but only detects a backend after it has served bad traffic.

Shallow vs deep — the critical decision

Classic failure: if every health check queries the shared database and the DB has a brief slowdown, every backend fails simultaneously. The LB evicts the entire pool and a partial degradation becomes a total outage. Deep checks turn shared dependencies into correlated failure.

Correct pattern: two endpoints. /livez — is the process running (used to restart, never to remove from rotation). /readyz — should this instance receive traffic; checks only local state (listener bound, config loaded, warmup complete). Downstream health belongs in circuit breakers and outlier detection in the data path, not in the health check.

Warmup and recovery storms

A cold instance has empty pools, cold caches, un-JITted code. Without protection it receives full 1/N traffic and spikes latency or fails. Use a slow-start ramp (Envoy/NGINX slow_start): weight rises from ~10% to 100% over 30–60 s after the first success. On recovery, randomize health-check intervals (jitter) and use consecutive-success thresholds so nodes rejoin gradually rather than flooding in at once.

Practical details that signal experience

  • Keep the endpoint cheap: no auth, no heavy DB query, no log spam — it is called every few seconds by every LB instance.
  • Never let the health check depend on the LB's own hostname (circular dependency).
  • Pick the right probe: TCP detects process death, HTTP GET detects app-level hangs, gRPC needs the standard health service.
  • Health checks are a DoS vector if the endpoint is expensive and the LB fleet is large.
  • On SIGTERM, flip readiness to failing first, wait for draining, then exit.
  • Alert on ejection rate, not just availability — a slowly rising rate is the earliest systemic signal.

Part 2 Load Balancing — Architecture & Traffic

Sticky sessions, autoscaling backends, failure handling, global failover, deployment strategies, and the LB vs gateway boundary.

LB-07

What are sticky sessions? When are they necessary, and how do you migrate to stateless?

Sticky sessions (session affinity) force the LB to route every request from the same client to the same backend for the session's lifetime — identified by an injected cookie, source IP, or header. The goal is to preserve local state: an in-memory session, a shopping cart, a WebSocket, or a warm cache.

When genuinely necessary

  • Long-lived connections: WebSocket, SSE, gRPC streaming are inherently pinned for the connection's life — affinity is a property of the protocol, not a choice.
  • Legacy stateful apps storing session data in process memory that cannot be changed quickly. A stopgap, not a destination.
  • Local cache locality: routing the same user or key to the same node improves hit rate.

Why they are a problem

Sticky sessions create skewed load (a heavy user pins to one node), session loss on node failure (state dies with the node), and slow scale-in (you cannot remove a node until its sessions expire). Redeploying a pinned node logs all its users out. Affinity lets a stateful app scale out at the cost of skew, session loss, and slow scale-in — externalizing session state is usually the better answer.

Migration path to stateless

  1. Externalize session state to Redis/Memcached/DB, keyed by session ID. Highest-leverage step.
  2. Move uploads to object storage so any instance can serve any request.
  3. Use signed tokens (JWT) for identity and coarse context so services validate without a session-store call on every hop.
  4. For WebSockets, decouple the connection layer from logic: the gateway holds the connection but publishes to a backplane (Redis Pub/Sub, NATS, Kafka) so any logic instance can handle a message for any user.
  5. Then disable affinity and verify a request succeeding on one instance succeeds on any other. Now you can use pure round-robin or least-requests.

The order matters: externalize state first, remove affinity second. Removing affinity while state is local causes user-visible failures. For raw WebSockets and unmodifiable legacy systems, affinity remains a legitimate bridge.

LB-08

Design the load balancing layer for autoscaling backends with no sticky sessions.

Backends appear and disappear continuously; any request can go to any healthy instance. The design must handle TLS, discover instances without manual config, health-check them, and drain gracefully on scale-in.

Two tiers, not one

  1. L4 network LB (edge). Anycast or cloud NLB. Does not parse HTTP; forwards at line rate, absorbs DDoS, distributes across AZs, preserves client IP via PROXY protocol or DSR. Its job is throughput and fault isolation, not routing intelligence.
  2. L7 proxy / ALB (regional). Envoy, NGINX, ALB, or gateway. Terminates TLS, parses HTTP/gRPC, health-checks, applies routing, and balances requests (not connections) using least-requests or P2C + EWMA — which correctly handles HTTP/2 multiplexing and variable request cost.

Putting L7 at the edge makes it the throughput and TLS bottleneck; putting only L4 means no request-level routing. Layering lets each tier do what it is cheap at.

TLS termination

Terminate at the L7 tier: central certificate management (ACME or secret manager), offload handshakes from pods, enable L7 inspection. Re-encrypt with mTLS if the internal network is untrusted, or use plaintext inside a private VPC. Use SNI-based cert selection for multiple domains on one listener, and keep TLS versions/ciphers in a central policy.

Service discovery

Never maintain static IP lists. Use a registry — Kubernetes EndpointSlices, Consul, or Cloud Map — and have the L7 proxy subscribe. In K8s the Ingress/Gateway controller watches EndpointSlices; on VMs, Consul Template or an xDS control plane pushes updates. Support graceful endpoint updates: new endpoints enter with a warmup weight; removed endpoints drain rather than being cut instantly.

Health checking + autoscaler agreement

Expose a cheap /readyz checking only local readiness — not shared dependencies, which cause correlated eviction. Configure active checks (2–5 s interval, 2–3 failure threshold) plus passive outlier detection. The autoscaler and LB must agree: a starting pod fails readiness until warm; a terminating pod fails readiness before it stops accepting connections.

Connection draining on scale-in

  1. Mark unready so the LB stops sending new requests.
  2. Wait for in-flight requests, bounded by a drain timeout.
  3. Send SIGTERM; the app finishes handlers, flushes telemetry, closes its listener.
  4. SIGKILL as a backstop after the grace period.
Client → Anycast DNS / GSLB
       → L4 Network LB      (line rate, cross-AZ, DDoS)
       → L7 Proxy / ALB     (TLS, request balancing, health checks)
       → Autoscaling pool   (/readyz + draining participation)

Result: no manual config when pods scale, request-level fairness, centralized TLS, fast failure detection, zero-downtime scale events.

LB-09

How does an LB handle node failure? Explain connection draining.

Detect, evict, recover

  • Detect: active checks catch hard failures (process dead) and soft failures (alive but 5xx or hanging); passive outlier detection watches real outcomes.
  • Evict: after 2–3 consecutive failures. Eviction must be bounded — never more than a configured percentage (e.g., 50%) or a shared-dependency failure empties the pool. Evicted nodes enter exponential-backoff quarantine to stop flapping.
  • Recover: after 2–5 consecutive successes, re-enter rotation with a slow-start ramp (~10% → 100% over 30–60 s), because a cold node cannot take full traffic.

In-flight requests on a crash

They fail; the LB cannot save them. Mitigations: fast detection so new requests stop going there, retries with a budget for idempotent operations, and redundancy (at least two healthy replicas). Availability is an architectural property, not an LB feature.

Connection draining (graceful shutdown)

Planned removal must be graceful — a different problem from a crash.

  1. Stop new traffic: mark unhealthy/unready or deregister from the registry.
  2. Wait for in-flight work: allow existing connections to complete, bounded by a drain timeout (AWS ALB "deregistration delay", typically 300 s, sized to the longest request).
  3. Signal the process: SIGTERM; finish handlers, flush logs/metrics, close the listener, exit.
  4. Force-kill as backstop after terminationGracePeriodSeconds.

Order matters. SIGTERM first causes 502s while the LB still routes for a few seconds. The correct pattern uses a preStop hook that delays SIGTERM so external load balancers have time to stop routing to terminating pods. For long-lived connections (WebSockets, gRPC streams), either migrate the connection or accept a controlled reconnect.

Interview signal: distinguish crash (needs fast detection and redundancy) from planned removal (needs draining and coordination). "The load balancer handles it" without this distinction is a junior answer.
LB-10

Design multi-region failover with DNS routing. What are the limitations?

The design — three layers

  1. Global traffic steering (GSLB): Route 53, Azure Traffic Manager, NS1, or an appliance answers DNS with a regional endpoint IP. Policies: failover (primary → secondary), weighted (90/10), or latency-based (nearest). When the primary fails its check, the GSLB stops returning its IP.
  2. Regional entry point: each region has its own L4/L7 LB distributing across AZs and the autoscaling pool. The GSLB points at the regional LB, never at instances.
  3. Data-layer replication: the hard part. Active-passive with async replication (RPO > 0) is simpler; active-active needs conflict resolution or consensus. A DNS switch to a region with stale or missing data is not a real failover.

Global health checking

Probe an endpoint that reflects regional health. A deep check (can the region serve a real request?) is accurate but false-positive-prone; a shallow check (is the regional LB alive?) is fast but can point traffic at a region whose database is down. The practical answer is a synthetic canary request exercising the critical path, with a conservative threshold (3 consecutive failures) to avoid flapping.

Limitations — the honest list

DNS failover is slow and non-deterministic. Failover time = TTL + whatever the client decides.
  • TTL caching makes failover unbounded. A 300 s TTL means up to 5 minutes of traffic to the dead region. Some clients (notably JVMs with default settings) cache far longer than the TTL instructs.
  • No push mechanism. You wait for caches to expire; propagation is not instant.
  • Coarse health checking. Limited custom checks compared to an L7 LB that evaluates response codes and latency.
  • The GSLB is itself a failure point and adds resolution and health-check traffic. A broken GSLB can take down all regions.
  • Latency after failover: a distant region may be healthy but slow. Failover restores availability, not performance.
  • Connection-level failures: DNS only affects new connections; existing TCP connections to the failed region stay broken.

Mitigations

Use a short TTL (30–60 s) on records you may need to fail over, accepting higher query volume. Combine with anycast — a global IP routed to the nearest healthy PoP at the network layer, bypassing DNS caching entirely. DNS failover is the coarse last resort; anycast or an HTTP-level global accelerator provides fast, deterministic steering.

LB-11

Design routing for canary and blue-green deployments. Who does what?

Blue-green: two identical environments; traffic flips from blue to green after verification. Instant rollback, clean cutover, but double infrastructure during the window.

Canary: send 1% → 5% → 25% → 50% → 100% to the new version, comparing metrics at each step. Limits blast radius; requires traffic splitting and good observability.

Responsibility split

ComponentDoesMust NOT do
Load BalancerMaintains stable + canary pools; executes the weighted split at request level; health-checks both; drains on cutoverDecide whether to promote; evaluate business metrics; own deploy logic
API GatewayRequest-level policy: header canary (x-canary), user-ID cohorts, path versioning, auth, per-version rate limits, traffic mirroringReplace the LB's replica distribution; act as the CI/CD controller
CI/CD PipelineDeploys, registers the canary pool, runs smoke tests, queries observability, decides to promote or roll back by calling the LB APIHard-code percentages; bypass health checks; promote without metric gates

Canary flow

  1. Deploy N+1 into a separate canary pool; wait for readiness.
  2. LB adds the pool at weight 0 and health-checks it. CI/CD sets 1% — or the gateway routes header-tagged synthetic traffic first (dark launch).
  3. Compare error rate, latency percentiles, and saturation against the stable baseline. Auto-rollback if the canary exceeds baseline by X for Y minutes.
  4. Ramp 1 → 5 → 25 → 50 → 100% with bake time at each step; the LB shifts weights without dropping connections.
  5. Drain and scale down the old pool. The LB is a dumb, reliable executor of weights.

Common mistakes

  • Splitting by connection instead of request: an L4 LB pins a user to one version for the connection's life, so a "1% canary" reaches 1% of connections, not requests — and long-lived connections skew the sample. Use L7 request splitting.
  • State incompatibility: if the canary writes a new schema or cache format, the stable version may break. Canary only works when both versions run against compatible state.
  • Promoting on technical metrics alone: a canary can have perfect error rates and still be a business regression. Gate on the metric that matters.
  • No baseline: "0.1% error rate" means nothing without the stable version's rate on the same traffic mix.
LB-12

Explain the difference between a Load Balancer and an API Gateway.

The same software (NGINX, Envoy, HAProxy) can be an LB, a reverse proxy, or a gateway. The difference is what problem you are asking it to solve.

Load balancer

Its job is traffic distribution for availability and throughput: spread connections or requests across equivalent backends. Features are health checks, algorithms, session affinity, TLS termination, and connection draining. It is deliberately unaware of API semantics — it does not know what an endpoint means, what a user's role is, or how to enforce a per-key quota. It is the air-traffic controller assigning runways.

API gateway

Its job is API management at the application layer — concerns common to all APIs that should not be reimplemented per service:

  • Authn/authz: JWT validation, OAuth introspection, API keys, mTLS identity.
  • Rate limiting and quotas per client, key, or route.
  • Transformation: protocol translation, header injection, payload shaping, versioning.
  • Semantic routing: /users/* → user service, composition/aggregation, cohort-based canary.
  • Policy and observability: per-route metrics, tracing, logging, WAF, schema validation.

They compose

A typical path: client → API gateway (auth, quotas, route to the right service) → L7 load balancer (distribute across that service's replicas) → pods. The gateway decides which service; the LB decides which instance. Load balancers connect a service's replicas; a gateway connects different services to each other and to clients.

When the line blurs

Modern gateways (Envoy, Kong, Apigee) include load balancing, and modern LBs (ALB) include L7 routing. Lead with primary purpose: "An LB optimizes distribution across replicas; a gateway optimizes API policy across services. They overlap in features, but if you use one component for both, ensure the data plane still scales and the policy layer doesn't become the bottleneck."

LB-13

Can you load balance without a dedicated LB? Explain client-side balancing and the sidecar pattern.

Yes — and it is increasingly the default for east-west traffic. A dedicated LB is a centralized hop; client-side balancing removes it by having the caller hold the list of healthy backends and choose per request.

Client-side load balancing

The client (SDK/library) subscribes to service discovery, receives healthy instances, and applies an algorithm locally — round-robin, least-requests, or P2C. gRPC's built-in balancing works this way (resolve to addresses, balance across them); Finagle is the classic language-specific stack. It avoids the LB hop but demands language-specific clients and is right "when you control all callers and want latency-aware selection." With polyglot services you must reimplement in every language — or standardize on a sidecar.

The service-mesh sidecar: the synthesis

A sidecar (typically Envoy) is injected next to every instance. The app talks to localhost; the sidecar intercepts the outbound call, applies client-side balancing using its local registry view, and forwards directly to the chosen backend — no central LB in the path.

This resolves the client-side vs server-side tension: the sidecar "brings client-side load balancing" with knowledge of every instance, so traffic goes directly from client to server without passing through a central appliance. Modern meshes are effectively server-side discovery that lives next to each client — the sidecar is the synthesis.

Why the sidecar fixes HTTP/2 and gRPC

An L4 LB balances connections, but HTTP/2 multiplexes thousands of requests over one connection, so one client pins to one backend and load skews badly. A sidecar balances at the request level, distributing individual gRPC calls across all pods regardless of the underlying connection. This is the strongest argument for L7 sidecars in east-west traffic.

Costs

  • Latency: single-digit millisecond p99 overhead per hop in typical deployments — measure it.
  • Operational complexity: a proxy per pod with its own config and upgrades; the control plane (Istio, Consul Connect) becomes critical infrastructure.
  • Debugging: mTLS, retries, and routing live in the sidecar — visibility requires mesh-aware tooling.
  • Not a replacement for the edge: north-south still wants a managed LB for DDoS, TLS, and global routing.

Other no-dedicated-LB options

  • DNS round-robin: multiple A records; crude, no health awareness, broken by caching. Not recommended.
  • Anycast: the network routes to the nearest healthy PoP; you still need health-aware routing inside each PoP.
  • Gossip-based distribution: used in some storage systems; not general-purpose.

The practical answer: edge LB for north-south, mesh sidecars for east-west — both covered, no central bottleneck.

Part 3 Load Balancing — Advanced

The layered reality of production LB architecture, tail latency amplification, and the limits of what an LB can do.

LB-14

Describe the layered LB architecture. What is tail latency amplification?

There is no single "load balancer" in production. There are five or six layers, each solving a different problem — and naming them is a senior signal.

The layers

  1. Global DNS / GSLB: geo-routes to the nearest healthy region. Coarse, TTL-bound, slow to fail over, but the only layer that can route around a dead region. Often replaced by anycast, which bypasses DNS caching.
  2. Edge L4 network LB: terminates TCP at the region edge; line-rate forwarding, DDoS absorption, cross-AZ distribution, often DSR. Exists to absorb volume, not to decide.
  3. Edge/regional L7 proxy: TLS termination, HTTP/gRPC parsing, path/host/header routing, request-level balancing, retries, timeouts, circuit breaking, observability. Where the "smart" balancing happens.
  4. API gateway: API-level policy — auth, quotas, rate limits, versioning, cohort canary. Distinct from the LB (LB-12) but often co-located.
  5. Service-mesh sidecar (east-west): per-pod Envoy doing client-side balancing, mTLS, retries, outlier detection. Removes the central LB from the east-west path (LB-13).
  6. Client-side LB in the SDK: gRPC/xDS resolves the service and balances locally. Lowest latency, language-specific.

Each layer has a different scope and cost profile: DNS is global but slow, L4 is fast but dumb, L7 is smart but CPU-expensive, the sidecar is local but adds per-pod overhead. Layering means no single tier has to be everything — at the cost of each hop adding a little latency.

Tail latency amplification

Setup: one backend has p50 = 10 ms and p99 = 1 s. A single call has a 1% chance of being slow — acceptable.

Amplification: a user request fans out to 100 backends. The chance that at least one is slow is 1 − 0.99¹⁰⁰ ≈ 63%. The user's median experience is now dominated by the slowest backend's tail. The tail of one component becomes the median of the whole request.

Why hops make it worse: if each of four hops has a p99 of 50 ms, end-to-end p99 is worse than 200 ms — unlucky requests pay penalties at multiple hops, and tails compound.

Mitigations

  • Reduce fan-out: fewer backends per request means fewer chances to hit a tail. Batch, cache, co-locate.
  • Hedged requests: send to two backends, take the first response, cancel the other. Trades extra load for a large tail reduction.
  • Tied requests: send the second request only after a delay (e.g., at p95), so extra load is paid only when the primary is likely slow.
  • Latency-aware LB: P2C with EWMA steers away from currently slow backends.
  • Outlier ejection: remove the slowest backends before they poison more requests.
  • Async / micro-batching: stop making the user wait for the slowest shard.
Interview line: "Load balancing is not just about spreading average load — it is about bounding tail latency. Perfect average utilization with a 1% slow backend still yields a terrible experience once fan-out is high. The LB's job is to keep the tail from becoming the median."
LB-15

What load balancing does NOT do. What are its failure modes?

What it does not do

  • Make a slow backend fast — it redistributes requests, it does not reduce work per request.
  • Reduce total work — the same requests must be served; the LB adds a little work rather than removing any.
  • Fix a stateful design — sticky sessions are a band-aid (LB-07); externalizing state is the fix.
  • Replace capacity planning — if aggregate capacity is insufficient, no algorithm saves you; the LB only decides who fails.
  • Reduce end-to-end latency by itself — the hop adds latency (1–10 ms L7, microseconds L4), and multi-hop compounds it.
  • Provide correctness — it detects errors and timeouts, not wrong answers.
  • Eliminate the need for retries, timeouts, or circuit breakers — these are complementary; without budgets, you still cascade.
  • Magically provide HA — a single LB is a SPOF; HA needs redundancy.

Failure modes of the LB itself

  • LB as SPOF: a single appliance or VM. Require at least two, ideally in different AZs, fronted by anycast or DNS.
  • Misconfigured health checks: the most common LB-induced outage. A deep check on a shared DB turns a blip into a full-pool eviction; a TCP-only check misses a hung app; an aggressive threshold flaps backends. Test local readiness only (LB-06).
  • Connection skew with L4 + HTTP/2: one multiplexed connection carries thousands of requests to one backend; the algorithm becomes irrelevant. The strongest argument for L7.
  • Thundering herd on recovery: all nodes marked healthy at once and traffic floods in, re-triggering the original overload. Mitigate with jitter, slow-start ramps, and bounded ejection.
  • Configuration drift: different LB instances end up with different backend sets or thresholds; a request routed to the "wrong" instance behaves differently. Manage config as code and validate in CI.
  • TLS CPU bottleneck: a surge of new connections saturates an L7 LB's crypto even when backend capacity is fine. Offload TLS, use session resumption, or terminate at the edge.
  • Control plane as a failure domain: service discovery and xDS are distributed systems. If the control plane is down, the data plane should fail static (last known good config), not fail open or closed.
  • Retry amplification: if the LB, gateway, and client all retry, one failed request becomes many. Pick one layer to own retries and enforce budgets elsewhere.

When not to use a dedicated LB

  • Single-instance services that genuinely do not need HA — a batch job, a dev environment.
  • East-west in a mesh — the sidecar is the LB; a central LB is a bottleneck and failure domain.
  • Client-side balancing with a small, stable backend set and controlled callers.
  • Anycast routing — the network distributes; you may still need per-PoP health-aware routing.
The honest summary: a load balancer is a distribution and failure-detection mechanism. It is not a performance optimizer, correctness guarantee, capacity planner, or substitute for stateless design. The best load balancer is the one whose failure modes you have already designed around.

Part 4 System Design — Core Concepts

Scalability, caching, data stores, consistency, proxies and CDNs, and concurrency.

SD-01

Explain horizontal vs vertical scaling. When do you choose vertical?

Vertical (scale up): make one machine bigger — more cores, RAM, faster disks, bigger NIC. Horizontal (scale out): add more machines and distribute load.

DimensionVerticalHorizontal
CeilingHard physical limitEffectively unbounded if the app scales
ComplexityLow — no coordinationHigh — LB, statelessness, distributed data
Failure domainSingle point of failureRedundant by design
Cost curveSuperlinear at the high endLinear-ish (commodity instances)
Scale downtimeUsually a restart/migrationRolling, zero-downtime
StateEasy — stays localHard — must be externalized

When vertical is right

  • Early-stage systems: a single large database is far cheaper in engineering time than a sharded cluster. Optimize iteration speed, not theoretical scale.
  • Stateful systems that resist sharding: a relational core with complex transactions and ad-hoc queries is easier to scale up than to shard — sharding is a multi-quarter project; a bigger box is a purchase order.
  • Low-latency, tightly coupled work: in-memory caches, real-time analytics on a working set that fits in RAM — one big machine can beat a cluster when coordination would dominate latency.
  • Licensing/ops constraints: per-node licensing favors fewer, bigger nodes.

The pragmatic pattern: scale up until it hurts, then scale out the parts that hurt. Most systems end hybrid — a vertically scaled primary with horizontally scaled read replicas and stateless app servers behind an LB.

Horizontal wins long-term (no ceiling, fault tolerance, elastic cost) but demands statelessness or partitioning — an architectural property, not a deployment toggle. Horizontal is the rewrite of how state is managed; vertical is correct while state is complex and scale is not yet the bottleneck.

SD-02

Caching strategies and eviction policies.

Read/write strategies

  • Cache-aside (lazy loading): app checks cache; on miss, reads DB, writes cache, returns. First read is slow; cache holds only what is requested. Simple and resilient — a cache outage degrades to DB reads.
  • Read-through: the cache itself loads on a miss; the app only talks to the cache. Uniform interface, less control over what is cached.
  • Write-through: every write goes to cache and synchronously to the DB. Always consistent; every write pays both latencies and caches possibly-unread data.
  • Write-back (write-behind): write to cache, acknowledge immediately, flush to DB asynchronously in batches. Lowest write latency, absorbs bursts — but a cache failure before flush loses data, and direct DB readers may see stale values. Use for counters, metrics, feeds.
  • Write-around: writes bypass the cache to the DB; cache populates on read. Avoids polluting the cache with write-once data (logs, archives), at the cost of a miss on first read.

Eviction policies

  • LRU: evict the least recently used. Great temporal locality; a single scan can flush the working set ("scan pollution").
  • LFU: evict the least frequently used. Protects hot items from scans; slow to adapt when patterns change.
  • FIFO: evict the oldest inserted. Simple but ignores usage.
  • TTL: expire after a fixed time. Essential for correctness; usually combined with LRU.
  • Random / 2-random: evict at random. Surprisingly competitive and trivially cheap.
  • ARC / segmented LRU: adaptively balances recency and frequency; better hit rate across mixed workloads, more complex.

What interviewers probe

  • Invalidation is harder than population. TTL is blunt; explicit invalidation on write is precise but must be reliable — one missed invalidation means stale data forever.
  • Cache stampede: a hot key expires and many requests miss simultaneously, hammering the DB. Use request coalescing (single-flight), probabilistic early expiration, or a lock on the miss path.
  • Hot key: one key can overwhelm a shard. Replicate it or add a small local cache in front.
  • Consistency: write-through is consistent for reads through the cache; write-back is eventual and lossy; cache-aside is stale for up to the TTL.
SD-03

SQL vs NoSQL. Sharding, partitioning, and choosing a shard key.

The useful distinction is not a binary; it is trade-offs across four lenses: data model, query flexibility, consistency/transactions, and scaling model.

AxisRelationalNoSQL
Data modelTables, normalized relations, joinsDocuments, KV, wide-column, graph — denormalized for access patterns
QueryRich SQL, ad-hoc, joinsOften key-based; secondary index support varies
TransactionsACID, multi-row/tableOften per-item or per-partition
SchemaFixed, migratedFlexible (validation shifts to the app)
ScalingVertical first; read replicas; painful shardingDesigned to partition and replicate

Choose SQL for complex evolving queries and strong transactions: ledgers, orders, inventory, anything where correctness and joins matter more than raw write throughput. Choose NoSQL for a known access pattern at scale, semi-structured data, or write-heavy ingestion where per-item consistency suffices: sessions, catalogs, time-series, chat, feeds. Many systems use both — a relational core for transactions and a NoSQL store for high-volume paths.

Partitioning vs sharding

Partitioning splits a large table into pieces within one instance (by range, list, or hash). It improves manageability and enables partition pruning, but all partitions share CPU, memory, and disk. Sharding partitions across separate instances, which is what gives horizontal write scale — and what introduces cross-shard queries, distributed transactions, and rebalancing. Data is typically partitioned (sharded), replicated, and cached.

Choosing a shard key

A good key has three properties:

  • High cardinality — many distinct values so data spreads evenly.
  • Even access distribution — no single value dominates (avoid country='US' or status='active').
  • Query alignment — most queries include the key, so they route to one shard. A key that forces every query to fan out defeats the purpose.

Common choices: user_id (all of a user's data co-located), tenant_id for SaaS, a hash of the PK for uniform distribution (at the cost of range queries), or a composite like user_id + timestamp. Avoid low-cardinality keys and keys that create hot shards — a single celebrity, a large tenant, or a monotonically increasing ID that concentrates all new writes on the last shard. If a hot key is unavoidable, isolate it on a dedicated shard or add a random suffix (at the cost of scatter-gather reads).

Replication and lag

Leader-follower sends writes to the leader and replicates; reads can go to followers. Multi-leader allows writes in several regions with conflict resolution. Leaderless (Dynamo-style) uses quorums. All introduce replication lag: a follower may serve stale data, and a user writing then reading a lagging follower sees their own write vanish — a read-your-writes violation. Mitigate by routing that user's reads to the leader briefly or by using a session-consistent token.

SD-04

Explain CAP and the practical consistency trade-offs.

CAP: when a network partition occurs, a replicated system must choose between Consistency (every read sees the latest write or an error) and Availability (every request gets a non-error response, possibly stale). Partition tolerance is not optional — networks partition.

What people get wrong

  • "Pick two of three" is misleading. You cannot opt out of P. The real choice is C vs A during a partition.
  • CAP ignores latency. PACELC extends it: if there is a Partition, choose A or C; Else (normal operation) choose Latency or Consistency. Synchronous replication buys consistency with latency — the more useful lens day to day.
  • Consistency is a spectrum, not a boolean.

Practical models

  • Strong (linearizable): quorum coordination or a single leader per shard; higher latency, lower availability during partitions. Use for money, inventory, unique constraints.
  • Eventual: replicas converge; reads may be stale. High availability, low latency. Use for feeds, view counts, search indexes, caches.
  • Session guarantees (read-your-writes, monotonic reads, causal): avoid the worst user-visible anomalies without full strong consistency — often the pragmatic middle ground.

The senior framing: consistency is chosen per operation, not globally. Demanding strong consistency everywhere makes a system slow, expensive, and fragile for the 80% of operations that do not need it.

SD-05

Forward proxy vs reverse proxy. What is a CDN and how does it work?

Forward proxy

Sits in front of clients and forwards their requests outward. The server sees the proxy's IP, not the client's. Used for corporate egress control, anonymity, client-side caching, and geo-restriction bypass. The client is configured to use it. It represents the client's interests.

Reverse proxy

Sits in front of servers and forwards client requests to the right backend. The client thinks it is talking to the origin; the backend topology is hidden. Used for TLS termination, load balancing, caching, compression, WAF, and a unified entry point. It represents the server's interests. A load balancer is a specialized reverse proxy; an API gateway is a reverse proxy with API policy.

CDN

A globally distributed reverse-proxy cache. It places points of presence (PoPs) near users and serves cached content from the nearest one.

  • DNS steering / anycast: the client is directed to a nearby PoP.
  • Cache hit: the PoP serves the object with a TTL from origin headers. Static assets and video segments get very high hit rates.
  • Cache miss: the PoP fetches from origin or a parent shield tier, which reduces origin load by having many edges fetch from a few shields instead of all hitting origin.
  • Dynamic acceleration: even for uncacheable API responses, CDNs optimize the path — TCP termination, TLS offload, HTTP/3, persistent origin connections.
  • Invalidation: purge by URL or tag; TTLs are the fallback. Invalidation is asynchronous and takes seconds to propagate globally.
  • Security: DDoS absorption, WAF, edge TLS termination.

For video, the CDN is the core of the architecture: content is segmented (HLS/DASH), each segment is cacheable, and ABR players pick a rendition by measured bandwidth. The CDN absorbs egress that would otherwise crush the origin.

SD-06

Why is concurrency control important in multi-threaded systems?

The problem

When multiple threads or requests touch shared mutable state without coordination, the result depends on interleaving: lost updates (two read-modify-writes, one overwrites the other), dirty reads, race conditions (check-then-act), and deadlocks. These are non-deterministic and typically appear only under load — the worst class of bug.

Mechanisms

  • Mutual exclusion: one thread in the critical section. Simple, but contention, priority inversion, and deadlock risk if lock ordering is inconsistent.
  • Optimistic concurrency: read a version, compute, write only if unchanged (CAS). No lock during computation; conflicts retry. Great for low contention.
  • Pessimistic concurrency: lock before reading, hold until write. Safer under high contention, lower throughput, deadlock risk.
  • Immutable data / actor model: no shared mutable state; each actor owns its state and communicates by message. Eliminates data races by construction.
  • Single-writer / serialization: route all writes for a key to one thread (sharded executor). Simpler than locking, at the cost of per-key throughput.

Across machines

The same problem appears distributed: two services updating a row, two consumers processing a message, two regions accepting writes for a key. Tools: distributed locks (etcd, Redis, ZooKeeper), optimistic versioning (ETags, conditional writes), transactions with isolation levels, and consensus for critical metadata. CAP reappears — a distributed lock is a consistency mechanism and is unavailable during a partition.

The interview point is not to list primitives but to identify the shared mutable state, choose a mechanism proportional to contention, and explain that mechanism's failure mode (lock service down, version conflict, deadlock).

Part 5 Classic Design Problems

Ten worked designs — requirements, core architecture, scaling, and the trade-offs to name out loud.

CD-01

Design a URL Shortener (TinyURL)

Requirements

Given a long URL, return a short one; visiting it redirects. Optional: custom aliases, expiry, analytics. Non-functional: high read throughput (redirects dominate), low latency, high availability, hard-to-enumerate codes, durable mappings.

Capacity

Assume 100M new URLs/day (≈1,160 write QPS), 100:1 read:write (≈116k read QPS). Five years ≈ 180B URLs. At ~500 bytes/record, ~90 TB — a sharded key-value store, not a single SQL box.

Core design

  1. ID generation: generate a globally unique 64-bit ID (Snowflake, distributed counter, DB sequence), then Base62-encode it. Seven Base62 chars give 62⁷ ≈ 3.5 trillion combinations. Base62 is URL-safe (no +//). Hashing the URL risks collisions requiring rehash; the ID approach has no collisions by construction.
  2. Storage: KV store short_code → {long_url, created_at, owner, expires_at}, partitioned by hash(short_code). Cache hot mappings in Redis.
  3. Redirect: on GET /{code}, look up (cache → KV) and return 301 or 302. 301 is browser-cacheable (less load) but loses analytics and makes the mapping hard to change; 302 keeps control and preserves click tracking — most production shorteners use 302/307.
  4. Custom aliases: check availability atomically with a conditional put; reject if taken. The one place a unique constraint matters.

Scaling trade-offs

  • Read path: a long-cached 301 is hard to change; a 302 with a short TTL lets you change the destination. Use edge → regional Redis → KV store.
  • Write path: a centralized counter is a bottleneck and SPOF; use per-node ID ranges or Snowflake.
  • Hot keys: a viral link can overwhelm one shard — replicate hot mappings and add a local in-process cache.
  • Expiry: store TTL, lazily delete on read, plus a background sweeper. Never scan the whole store.
  • Analytics: emit an event asynchronously (queue → stream processor) so the redirect path stays fast.
CD-02

Design a Rate Limiter

Requirements

Limit requests per client (IP, user, API key) over a window; return 429 with Retry-After; <1 ms overhead; work across a distributed fleet; accurate enough to protect downstream without being unfair.

Algorithms

AlgorithmHowTrade-off
Token bucketCapacity B, refill rate R; each request takes a tokenAllows bursts up to B; smooth average. Common default.
Leaky bucketQueue drains at a fixed ratePerfectly smooth; adds queueing latency; bursts delayed not rejected
Fixed windowCount per calendar windowSimple; 2× burst at boundaries

Distributed implementation

Redis with atomic Lua scripts: INCR + EXPIRE for fixed windows; sorted sets or token-bucket scripts for sliding/token bucket. The limiter sits in the gateway or a sidecar so every request passes through it.

Local + global two-tier: a small local bucket per instance for the cheapest decisions, periodically synced with Redis for global accuracy. Fewer round-trips, at the cost of slight over-admission during local bursts.

Failure handling

  • Redis down: choose fail-open (risk overload) or fail-closed (protect backend, hurt availability). Usually fail-open for user APIs, fail-closed for abuse-prone endpoints. Make it configurable.
  • Hot key: one abusive client concentrates on a single shard — shard by key or use local counters for the hottest keys.
  • Clock skew: use Redis server time for window boundaries, never client time.
  • Race conditions: check-and-increment must be atomic — Lua script or INCR+TTL. Read-then-write is unsafe.
CD-03

Design a Key-Value Store

Requirements

Put/Get/Delete. Horizontally scalable, highly available, tunably consistent, durable, low latency.

Building blocks

  • Partitioning: consistent hashing with virtual nodes for even distribution and capacity weighting; replicate each key to the next R nodes clockwise for durability.
  • Consistency: Dynamo-style quorum — write W replicas, read R, with W + R > N for read-your-latest. Tune W/R for latency vs consistency. Vector clocks or version numbers detect conflicts; resolve with last-write-wins (simple, lossy) or application merge (CRDTs).
  • Storage engine: LSM tree (memtable → SSTable, background compaction) for write-heavy workloads; B-tree for read-optimized. Most distributed KV stores use LSM (RocksDB, LevelDB) because writes are sequential.
  • Failure handling: hinted handoff (a neighbor stores writes for a down node), read repair (reconcile divergent replicas on read), and Merkle trees for efficient anti-entropy.
  • Membership: gossip to detect failures and disseminate membership; no central coordinator.

API

get(key), put(key, value, context), delete(key); opaque byte values; per-request consistency knobs (ONE, QUORUM, ALL) so callers choose the trade-off.

Trade-offs to name

  • Availability vs consistency: W+R>N is strongly consistent but unavailable when too many replicas are down; W=1/R=1 is highly available but stale.
  • Latency vs durability: synchronous replication is slow; asynchronous risks loss on failover.
  • Compaction cost: LSM compaction consumes I/O and causes latency spikes — rate-limit it.
  • Hot keys: consistent hashing does not help a single hot key; replicate or cache it.
CD-04

Design a Web Crawler

Requirements

Start from seeds, fetch, extract links, repeat. Billions of pages. Be polite (respect robots.txt, per-host rate limits). Avoid duplicates. Handle traps. Store content.

Components

  1. URL frontier: priority queue by importance/freshness, partitioned by host so one slow host does not block others. Dedup via bloom filter + exact set.
  2. Fetcher pool: workers that fetch, respect per-host politeness (a delay between requests to the same host), retry with backoff, and honor robots.txt (cached per host).
  3. Parser / link extractor: HTML parsing, link normalization (resolve relative URLs, strip fragments), new-URL extraction. Tolerate malformed HTML and skip non-HTML.
  4. Deduplication: canonicalize URLs (lowercase host, drop default ports, sort query params), check the seen-set via bloom filter on the hot path and a persistent store for confirmation.
  5. Storage: raw HTML in object storage, extracted links in a graph store, metadata (fetch time, status, content hash) in a KV store.
  6. Scheduler: re-crawl frequency by change rate — news often, static pages rarely.

Scale and politeness

  • Politeness: a per-host token bucket; by default no more than one connection per host. This dominates crawl rate for many small sites.
  • Distributed coordination: partition the frontier by host so the same host is always handled by one worker — making politeness and dedup local.
  • Traps: cap depth per host, detect near-infinite URL patterns, blacklist pathological sites.
  • Freshness: prioritize by estimated change frequency and use conditional GETs (ETag / If-Modified-Since) to avoid re-downloading unchanged pages.
CD-05

Design a Chat Application (WhatsApp / Messenger)

Requirements

1:1 and group messaging, real-time delivery, presence, history, delivery/read receipts, multi-device. Millions of concurrent connections, low latency.

Core architecture

  • Connection layer: persistent WebSocket (SSE/long-poll fallback) connections at a gateway fleet. A registry maps user_id → gateway — the key indirection, so the message service never needs to know which server a user is on.
  • Message service: accepts, persists, and routes. For 1:1, look up the recipient's gateway and push. For groups, fan out to each member's gateway or to a group channel.
  • Persistence: wide-column store (Cassandra/HBase) partitioned by conversation_id with timestamp clustering for efficient history reads. Messages are immutable; edits and deletes are new records.
  • Presence: client heartbeats; a presence service tracks last-seen and online state in Redis with TTL. Typing indicators are ephemeral pub/sub events, never persisted.
  • Push notifications: when offline, APNs/FCM wakes the device to sync. The message is already persisted; push is a hint, not the transport.
  • Multi-device: each device is a separate connection with a per-device cursor. E2E encryption (Signal) means the server stores ciphertext and multi-device requires key sharing.

Delivery semantics

At-least-once with client-side dedup by message ID. Sender ack on persistence; recipient ack on delivery; read receipt on display. Per-message status stored per recipient.

Scale challenges

  • Connection churn: mobile clients reconnect constantly; the gateway must absorb millions of connect/disconnect events without overloading the registry.
  • Group fan-out: a 1,000-member group means 1,000 pushes per message — for very large groups use a pub/sub channel per group and let gateways subscribe.
  • Ordering: per-conversation ordering suffices; use a server-assigned sequence per conversation, not a global timestamp.
  • Pagination: cursor-based by timestamp/sequence, never offset-based at scale.
CD-06

Design a Social Media Newsfeed

Requirements

Show a ranked list of posts from followed accounts. Follows, likes, comments. Millions of users, celebrities with tens of millions of followers. Low-latency reads.

The core problem: fan-out

  • Push (fan-out on write): on post, write the post ID into every follower's feed list. Reads are precomputed and fast, but a celebrity with 50M followers triggers 50M writes per post — write amplification disaster.
  • Pull (fan-out on read): store posts per author; on read, fetch recent posts from everyone followed and merge. Cheap writes, expensive reads, slow for users following thousands.
  • Hybrid (the standard answer): push for normal users, pull for celebrities. On read, merge the precomputed push feed with the pulled celebrity posts.

Storage and ranking

  • Feed cache: Redis sorted sets per user keyed by post ID with score = timestamp/rank. Precomputed for push users; merged on read for pull.
  • Post store: wide-column keyed by author_id + post_id; media in object storage served via CDN.
  • Social graph: graph store or sharded adjacency list; needed for fan-out and privacy checks.
  • Ranking: not purely chronological — ranked by predicted engagement (affinity, recency, media type) at read time over a bounded candidate set (e.g., 1,000) to control latency.

Scale challenges

  • Celebrity problem: hybrid fan-out, aggressive caching of celebrity posts, merge at read.
  • Feed consistency: a new post may take seconds to appear — acceptable eventual consistency.
  • Hot posts: viral like/comment counts are hot keys — batch updates or use a sharded counter service.
  • Media: object storage, CDN, asynchronous transcoding.
CD-07

Design a Ride-Sharing Service (Uber / Lyft)

Requirements

Riders request; the system matches nearby drivers; real-time tracking; fare estimation; full trip lifecycle. High write throughput for location, low-latency matching.

Core components

  • Location ingestion: drivers ping GPS every few seconds. At 1M drivers × 0.2 Hz that is ~200k writes/s — a Kafka stream feeding an in-memory geospatial index. Never persist every ping synchronously to a relational DB.
  • Geospatial index: H3 hexagons (or geohash/S2) map a location to a cell; an in-memory Redis index maps cell → available drivers. Query the rider's cell and neighbors. H3 is preferred because hexagons have uniform neighbor distance, unlike a lat/lon grid.
  • Matching: search expanding rings of cells until enough drivers are found; rank by road ETA (not straight-line), rating, and acceptance likelihood. Use an atomic two-phase lease: offer to one driver with a short timeout; if declined or expired, offer to the next — this prevents two riders booking the same driver.
  • Trip state machine: durable store plus an event log for transitions; idempotency keys on the request prevent double-booking on retry.
  • Pricing: base + distance + time + surge multiplier. Surge is computed per cell from demand/supply ratio and must be auditable.
  • Notifications: push at each state change; WebSocket for live location during the trip.

Failure considerations

  • Location is ephemeral: keep only the latest per driver in memory; persist a downsampled trail for analytics.
  • Matching under contention: the lease is critical; the atomic primitive is a conditional write on driver status (available → reserved).
  • Hot cities: a dense city at rush hour concentrates load — partition matching by city/region.
  • Partitions: if a driver's connection drops, the lease must expire and the trip reassigned or cancelled.
CD-08

Design a Video Streaming Platform (YouTube / Netflix)

Requirements

Upload, transcode, store, and stream to millions of concurrent viewers with adaptive quality; low startup latency; global reach; recommendations and search.

Upload and processing

  1. Resumable chunked upload to object storage; the client gets an upload ID and resumes after failures.
  2. Transcoding: a job queue fans out to a worker fleet producing multiple resolutions and codecs (H.264, VP9, AV1, HDR), segmented into HLS/DASH chunks of 2–10 s. CPU/GPU-intensive, asynchronous, can take minutes; prioritize new and popular uploads.
  3. Packaging: generate a manifest (M3U8/MPD) listing renditions and segment URLs. Segments are immutable and cacheable.
  4. Metadata: title, description, thumbnails, duration, ownership in a database; search index updated asynchronously.

Streaming architecture

  • CDN is the core: segments served from edge PoPs with a shield tier to reduce origin load. The CDN absorbs the enormous egress.
  • Adaptive bitrate (ABR): the player measures throughput and buffer level and requests the next segment at a sustainable rendition. Switching happens at segment boundaries — this is why segmentation matters. Start conservative, ramp up.
  • Low latency: LL-HLS / LL-DASH use smaller segments and partial segments, trading efficiency for latency on live streams.
  • DRM: encrypt segments and license keys (Widevine/FairPlay/PlayReady); the CDN serves encrypted content, the license server issues keys.

Scale challenges

  • Egress cost: video is bandwidth-dominated — multi-CDN strategies, peering, and failover between CDNs matter.
  • Cold content: the long tail should not occupy edge caches; tiered caching (edge → shield → origin) handles it.
  • Live vs VOD: live needs low-latency ingest (RTMP/SRT) → transcode → package → CDN with seconds of latency; VOD can pre-process fully.
  • Recommendations: precompute candidate sets offline; serve a ranked list at request time. Never run a heavy model on the playback path.
CD-09

Design a Search Engine

Requirements

Given a text query, return a ranked list of relevant documents in milliseconds. Support pagination, spelling correction, basic operators. Non-functional: p99 ≈ 200–500 ms, billions of queries/day, freshness of hours-to-days, hundreds of billions of documents.

Two loosely coupled systems

  1. Offline indexing pipeline: crawl → parse → analyze → build inverted index → rank signals. Batch/streaming, high throughput, latency-tolerant (hours to days per document). Essentially CD-04 feeding a document store and an indexer.
  2. Online query pipeline: parse query → retrieve candidates → rank → return top-k. Synchronous, low latency, must scale with query volume.

The inverted index

Instead of document → words, store word → posting list of documents (with term frequency, positions, field info). "Find documents containing X" becomes an O(1) lookup plus a scan of a sorted list. Query processing tokenizes (split, lowercase, stopwords, stemming), looks up each term, combines (AND for all terms, OR for optional), and uses positional indexes for phrase queries.

Sharding and replication

  • Document sharding (standard): partition by hash(doc_id); each shard holds a complete index for its subset. A query scatters to all shards, each returns its local top-k, and an aggregator merges and re-ranks. Simple, balanced, supports arbitrary queries — at the cost of fan-out and tail latency (LB-14). This is how Elasticsearch and Solr work.
  • Term sharding: partition by term. Queries hit only relevant shards, which is efficient for rare terms — but common terms concentrate load and phrase queries become cross-shard joins. Rarely used.
  • Replication: leader + followers per shard for availability and read throughput; followers serve queries.

Index structure

Use immutable segments (Lucene's model): new documents go into a small in-memory segment, flush to an immutable on-disk segment, and background merges combine small segments. Deletes are tombstones applied at merge. LSM-like: sequential writes, reads consult multiple segments (mitigated by caching and merging).

Ranking — multi-stage

  1. Candidate generation: retrieve a few thousand documents via the index (cheap, recall-oriented).
  2. Lightweight scoring: BM25/TF-IDF plus static signals (PageRank, authority, freshness) over thousands.
  3. Heavy ranking: a learning-to-rank model scores the top few hundred using query-document relevance, click history, location, language, page quality.
  4. Re-ranking: diversity, dedup, safety filters, sponsored results.

BM25 rewards term frequency but saturates and normalizes by document length. Learning-to-rank models learn weights from click data and human judgments.

Caching and latency budget

Query cache for head queries (very high hit rate), posting-list cache for hot terms, snippet cache. For a 300 ms p99: parsing 1 ms, shard fan-out 50–100 ms, light scoring 20 ms, heavy ranking 100 ms, snippets 30 ms, network 20 ms. The budget is dominated by fan-out tail latency and the ranker — which is why the ranker sees only a small candidate set and why hedged requests are used.

Trade-offs

  • Freshness vs index cost: re-indexing everything continuously is prohibitive; prioritize by change rate and importance.
  • Recall vs latency: more candidates improve recall but cost time; cap the set and accept some recall loss.
  • Scatter-gather tail: a query hitting 100 shards waits for the slowest — hedged requests, shard timeouts, partial results.
  • Index size vs features: positional indexes enable phrase queries but double index size; store positions only where needed.
CD-10

Design a File Storage / Sync System (Drive, Dropbox)

Requirements

Upload, download, folders, sharing, multi-device sync, version history, offline access, conflict resolution. Durability (never lose a byte), availability, seconds-level sync latency, exabyte scale, bandwidth efficiency (don't re-upload 1 GB for a one-character edit).

The key split: metadata vs content

  • Metadata store: relational or strongly consistent distributed store for the file tree, ownership, permissions, versions, and sync state. Small, transactional, needs strong consistency — a folder rename must be atomic.
  • Blob store: object store or distributed block store for the bytes. Huge, immutable, can be eventually consistent.

Chunking and deduplication

Split files into blocks (e.g., 4 MB), store each separately, keyed by content hash. This enables:

  • Deduplication: identical blocks stored once — 30–60% storage savings in organizations.
  • Delta sync: editing one block uploads only that block.
  • Parallel transfer and resumability from the last completed block.

Fixed vs content-defined chunking: fixed-size blocks break dedup when content shifts — inserting one byte at the start shifts every boundary and changes every hash. Content-defined chunking (Rabin fingerprint / rolling hash) places boundaries by content, so insertions only change affected blocks. This is what rsync and backup systems use and it dramatically improves dedup for edited files.

The sync protocol

Each client keeps a local metadata DB and a sync cursor (version or change ID).

  1. Change detection: watch the filesystem (inotify/FSEvents) and compute a delta.
  2. Push: upload new blocks (skipping ones the server already has, by hash), then send the metadata change.
  3. Pull: ask "what changed since my cursor?" — the server returns a change log of metadata mutations; the client applies them and fetches missing blocks.
  4. Notifications: push (long-poll, WebSocket, APNs/FCM) so the client pulls immediately. This is what makes sync feel instant.

The change log is the heart: an append-only, ordered sequence of mutations per user or shared folder, letting any client catch up from any point.

Conflict resolution

  • Last-write-wins: the later timestamp wins; the earlier edit is silently lost. Only for low-value data.
  • Conflict copies (Dropbox): keep both as "file (conflicted copy)". No data loss; manual resolution.
  • Version vectors: each version carries (device, counter) pairs; the server distinguishes causally ordered versions (no conflict) from concurrent ones (true conflict). The correct general solution.
  • OT / CRDTs: for real-time collaborative editing, merge character-level operations instead of whole files. Much harder, but automatic merge without conflict copies.

Sharing, versioning, GC

  • Permissions: an ACL (owner, list of user/group → role). Shared folders form a permission graph evaluated transitively — sharing a subfolder does not grant the parent. Cache decisions aggressively but invalidate on change.
  • Versioning: every change creates a new version pointing at a block list; retain for a window, then GC. Blocks are reference-counted and deleted when unreferenced — with a grace period so in-progress syncs don't lose data.
  • Sharding: metadata by user_id (co-locate a user's tree) or file_id for shared files; blobs by content hash (natural dedup and even distribution). Hot shared files are cached at the edge.
Interview line: "Storage is the easy part — object stores solve it. The hard part is the change log and conflict model: how does a client catch up from any point, and what happens when two clients edit the same file offline? Get metadata and conflict semantics right and the blob layer is commodity."

Part 6 Architecture Patterns

When to decompose a monolith, and how event sourcing and CQRS change the shape of a system.

AD-04

When would you split a monolith into microservices? Costs and anti-patterns.

Microservices are not an architecture goal — they are a scaling strategy for organizations and deployment. A monolith is the correct default until you have a concrete problem decomposition solves.

When NOT to split

  • Small team (< ~20 engineers): you trade code complexity for operational complexity you cannot afford.
  • Unclear domain boundaries: you will draw the wrong seams and pay with distributed transactions and chatty interfaces. A monolith lets you refactor boundaries cheaply.
  • Strong transactional requirements: if most operations span entities and need ACID, a single database is far simpler than sagas.
  • Low scale: a well-tuned monolith on a few large machines handles tens of thousands of RPS.
  • Early-stage product: iteration speed dominates; a monolith deploys faster and debugs easier.

When to split

  • Independent scaling needs: search needs 50× the CPU of billing — the strongest technical driver.
  • Independent deployment cadence: one team daily, another quarterly; coupling forces the slower cadence on everyone.
  • Team autonomy: Conway's Law is real — architecture mirrors communication structure.
  • Fault isolation: a memory leak in recommendations should not take down checkout.
  • Polyglot needs: ML in Python, latency-critical in Go, legacy in Java.
  • Regulatory/security boundaries: a PII service may need a stricter network and access boundary.

The costs — name them explicitly

  • Distributed transactions: no cross-service COMMIT. You get sagas — sequences of local transactions with compensating actions. Eventually consistent, hard to debug, requiring idempotency.
  • Network calls replace function calls: milliseconds instead of nanoseconds, and a new failure mode at every boundary.
  • Data consistency: joins become API calls or denormalized projections that must be built and kept fresh.
  • Operational complexity: dozens of deployables, each with config, secrets, scaling policy, dashboards, alerts.
  • Debugging: a request crosses 10 services — without tracing (AD-06) you cannot answer "where did it go wrong?"
  • Testing: integration tests require many services; contract testing becomes essential.

How to split

  1. Domain-Driven Design: identify bounded contexts — areas with their own ubiquitous language. "Order" in sales and "Order" in fulfillment may be different things.
  2. Event storming: map events, commands, and aggregates with domain experts to surface real seams.
  3. Strangler fig: do not rewrite. Put a proxy in front of the monolith and route one capability at a time to a new service. Lowest-risk, industry-standard migration.
  4. Start with the highest-pain boundary: extract the service that most needs independent scaling or deployment. Prove the pattern, then repeat.
  5. Database per service: the moment two services share a database you have a distributed monolith. Cross-service data goes through APIs or events.

Anti-patterns

  • Distributed monolith: services that must be deployed together, share a DB, or chain synchronous calls for every request. All the complexity, none of the independence. Smell: "we can't deploy A without B and C."
  • Nano-services: splitting so finely that one request needs 20 network calls. Boundaries follow business capabilities, not code classes.
  • Shared database: the fastest way to couple two services forever.
  • Chatty interfaces: 50 calls to render one page — batch or aggregate at the edge (BFF pattern).
  • Resume-driven decomposition: splitting because it is trendy, not because you have a problem.
Interview line: "Microservices are an org-scaling strategy. Split when you have a concrete driver — independent scaling, deploy cadence, or team autonomy — and can afford the operational cost. Otherwise a modular monolith is the better engineering decision, and it keeps the option to split later."
AD-05

Explain Event Sourcing and CQRS. When to use them, and what are the pitfalls?

Event sourcing

A traditional system stores current state (balance = 100). Event sourcing stores the sequence of events that produced it (Opened, Deposited(50), Deposited(50)). Current state is derived by replay. The event log is the system of record; state is a projection.

Benefits

  • Complete audit trail — who, what, when, why. Invaluable in finance, healthcare, and regulated domains; audit comes for free.
  • Temporal queries — "what was the balance on March 1?" is a replay to a timestamp.
  • New projections from replay — need a new read model? Replay the log. No data migration.
  • Decoupling — consumers subscribe to events; new consumers need no producer change.
  • Debugging — reproduce any bug by replaying the exact event sequence.

Challenges

  • Event schema evolution: events are immutable and stored forever. Use versioned events or upcasters that transform old events on read — the hardest operational problem in event sourcing.
  • Replay cost: rebuilding from 10M events is slow. Use snapshots and replay only events after the snapshot.
  • Eventual consistency: read models lag the log; a user may not see their own write immediately. This is a UX problem that must be designed for.
  • Query complexity: you cannot efficiently query the log for arbitrary questions — you need projections, which is where CQRS comes in.
  • Storage growth: the log grows forever. Tier storage (hot/cold) and use snapshots to bound replay.

CQRS

Separate the write model (commands that change state) from the read model (queries). Minimally it is just separating read and write paths. Fully, the write side is an event-sourced aggregate and the read side is one or more projections built by consuming events.

Command → Write Model (validates, emits events) → Event Log
                                                    │
                                    ┌───────────────┼───────────────┐
                                    ▼               ▼               ▼
                               Projection A    Projection B    Projection C
                               (read DB)       (search index)  (cache)
                                    ▲               ▲               ▲
                                 Queries         Queries         Queries

Benefits: read and write models optimized independently (normalized writes, denormalized reads tailored per query); reads scale horizontally; complex queries never slow writes. Cost: the read model is eventually consistent, and you now operate two models plus a projection pipeline.

When to use

  • Audit-critical domains: banking, insurance, healthcare, supply chain — the event log is a business requirement.
  • Complex domains with rich behavior where state transitions are the core logic (order lifecycle, claims).
  • Multiple read shapes: the same data queried by user, region, full-text, and analytics.
  • Event-driven integrations: other services genuinely need to react to changes.

When NOT to use

  • Simple CRUD — a settings page or to-do list does not need an event log.
  • Small scale — the operational overhead is not justified.
  • Immediate consistency everywhere — eventual consistency will fight you.
  • Teams unfamiliar with the pattern — it is easy to get wrong (events-as-CRUD, missing domain events, no upcasting strategy).
Interview line: "Event sourcing is right when the history is the business value, not just the current state. CQRS is right when reads and writes have fundamentally different shapes and scaling needs. They pair naturally, but each works alone, and neither belongs in simple CRUD."

Part 7 Failure & Resilience

Backpressure, cascading failure, retry storms, idempotency, delivery semantics, queues, and consensus.

AD-01

Design for backpressure. Prevent cascading failures and retry storms.

Backpressure

Backpressure is how an overloaded component signals upstream to slow down instead of accepting work it cannot complete. Without it, queues grow unboundedly, latency explodes, memory exhausts, and the component collapses — taking its callers with it.

  • Bounded queues with rejection: when full, reject immediately (429/503). A fast rejection beats a slow timeout.
  • Load shedding: drop low-priority requests (prefetch, analytics) to protect high-priority ones. Classify and shed by class.
  • Rate limiting / throttling: cap accepted rate at the edge and each tier; throttling buys time for reactive responses like scaling.
  • Pull-based consumption: consumers fetch at their own pace (Kafka consumer groups); the broker holds the backlog. Backpressure by design.
  • Adaptive concurrency limits: measure latency and reduce in-flight limits when it rises (Netflix concurrency limits, Envoy adaptive concurrency).

Cascading failures

A local problem propagates: a slow dependency blocks threads, exhausting a pool, making the caller slow, exhausting its pool, and so on up the stack. Retries amplify it.

  • Timeouts everywhere: never wait forever; set them per hop, not just at the edge.
  • Circuit breakers: when a dependency's error rate crosses a threshold, stop calling it for a cooldown and fail fast. Breakers prevent retrying a call that has repeatedly timed out, and detect when the callee is functional again.
  • Bulkheads: isolate thread/connection pools per dependency so one slow dependency cannot exhaust everything.
  • Fallbacks: serve cached or default responses instead of failing.

Retry storms

Naive retries are the most common cause of cascading failure: a brief failure triggers every client to retry simultaneously, multiplying load. Retries amplify small failures into retry storms, thread exhaustion, and queue buildup — the canonical example being a 3-second database lock that became a 3-minute cascading failure through naive retry loops.

  • Exponential backoff with jitter: 100 ms, 200 ms, 400 ms plus random jitter so retries de-synchronize. Jitter is essential — without it all clients retry at the same instant.
  • Retry budgets: cap retries as a fraction of total requests (e.g., 10%). When exhausted, fail fast — this prevents retry amplification from consuming all capacity.
  • Only retry idempotent operations (GET, or writes with an idempotency key). Retrying a non-idempotent write can double-charge a customer.
  • Breaker + backpressure together: the breaker stops the retry loop; backpressure tells upstream to stop sending.
  • Retry at one layer only: if every layer retries, one request can become 27. Pick one owner (usually the client or edge proxy).
AD-02

Handle idempotency in a distributed system. Explain "exactly-once".

Why

The network can fail after the server processes a request but before the client sees the response. The client retries — and the operation happens twice. For a payment, that is a double charge. Idempotency makes a retried request safe: the effect is applied once and subsequent identical requests return the same result.

The idempotency key pattern

  1. The client generates a unique key per logical operation (UUID or a hash of the request) and sends it with every retry.
  2. The server checks a store: if the key exists and the original succeeded, return the stored response; if it exists and is in progress, return 409 or wait; if absent, process and atomically record the key + result.
  3. Atomicity is critical: a conditional write (INSERT ... IF NOT EXISTS, Redis SETNX with a state machine) ensures two concurrent retries cannot both process. Anchor each transaction to a unique identifier and enforce uniqueness at the database layer so duplicate attempts resolve without creating additional entries.
  4. Stripe is the canonical example: Idempotency-Key, atomic phases, recovery points, transactionally staged job drains.

The "exactly-once" myth

Exactly-once delivery is impossible in a distributed system. You can have at-most-once (may lose) or at-least-once (may duplicate). "Exactly-once" is achieved as at-least-once delivery + idempotent processing — the effect happens once even if the message is delivered many times.

Networks may deliver requests repeatedly, workers may execute repeatedly, and webhooks may be observed repeatedly — so the guarantee must be enforced at the effect layer, not the transport layer.

Practical details

  • Key scope and TTL: scope per client, expire after a window (e.g., 24 h) that exceeds the maximum retry period.
  • Store the response (status, body) so a retry returns the same result, not a different one.
  • State machine: processing / succeeded / failed. A retry during processing must not start a second execution.
  • Idempotency ≠ deduplication: dedup drops duplicates; idempotency guarantees the same result for the same key — stronger for payments.
  • Consumers: use the message ID as the key; check before applying the effect. Kafka's transactional producer gives idempotent writes to Kafka, but external side effects still need an idempotency layer.
AD-03

Message queues (Kafka vs RabbitMQ) and distributed consensus (Paxos, Raft).

Why queues

They decouple producers from consumers: producers publish without waiting; consumers process at their own pace; spikes buffer instead of crashing the consumer; consumer failures do not lose messages. They enable fan-out and (in Kafka) replay.

Kafka vs RabbitMQ

Delivery semantics

Both support at-most-once and at-least-once. Exactly-once is a transport illusion; the practical guarantee is at-least-once + idempotent consumers (AD-02). Kafka adds transactions for exactly-once within Kafka (read-process-write), but external side effects still need idempotency.

Consensus: Paxos and Raft

Consensus is how a cluster agrees on a value despite failures — the foundation of replicated logs, leader election, and distributed locks (etcd, ZooKeeper, Consul).

  • Paxos: a proposer sends prepare to a majority; if a majority promises, it sends accept; if a majority accepts, the value is chosen. Notoriously difficult to understand and implement; Multi-Paxos extends it to a log.
  • Raft: designed for understandability. It separates leader election, log replication, and safety. A leader is elected by a majority, appends entries, and replicates; an entry is committed when a majority has it. Raft only allows servers with up-to-date logs to become leaders, which simplifies the safety argument, and defines membership changes via joint consensus.

Both need a majority quorum: 3 nodes tolerate 1 failure, 5 tolerate 2. They trade availability for consistency during a partition (CP). Consensus is expensive — round trips and a leader bottleneck — so use it only for critical metadata (configuration, leadership, locks), never for high-throughput data paths.

Part 8 Operability, Security & Cost

Observability and SLOs, security and compliance, cost and maintainability, and NFRs as design drivers.

AD-06

Design for observability: metrics, logs, traces, SLOs, alerting.

Monitoring answers known questions ("is CPU above 80%?"). Observability lets you ask new questions about a system you did not anticipate ("why are only German Android users slow since the 3pm deploy?"). The three pillars are metrics, logs, and traces.

Metrics

  • Counter (monotonic: requests, errors — rate matters), gauge (queue depth, in-flight), histogram (latency buckets → percentiles). Averages hide tails; p50/p95/p99 are the only latency metrics that reflect UX.
  • RED for services: Rate, Errors, Duration. USE for resources: Utilization, Saturation, Errors. Prometheus collects, Grafana displays.

Logs

  • Structure them: JSON with consistent fields — timestamp, level, service, trace_id, user_id, message. Unstructured text cannot be queried at scale.
  • Correlation IDs: a trace_id in every log line and every downstream call is what lets you reconstruct a request across services.
  • Sampling: sample INFO/DEBUG heavily, keep WARN/ERROR at 100%, and sample by trace ID so a sampled request has all its logs.
  • Retention: hot searchable storage for days, cold compressed for months. Most debugging happens in the last 24 hours.

Distributed tracing

A trace is one request's journey across services, composed of spans (one unit of work with start, duration, parent, attributes). The trace is a tree; the root span is the user request.

  • Context propagation: trace and parent-span IDs travel in headers (W3C Trace Context, B3) through every service and async boundary — message queues carry them too.
  • Instrumentation: OpenTelemetry is the vendor-neutral standard — instrument once, export to Jaeger, Tempo, Datadog, or Honeycomb.
  • Sampling: head-based decides at the start (e.g., 1%); tail-based decides after completion, letting you keep 100% of slow or errored traces — far more useful, at the cost of buffering.
  • What it answers: which service added the 800 ms, whether the DB call retried, whether latency is in our code or the network. Impossible with metrics and logs alone.

SLOs, SLIs, error budgets

  • SLI: a measured quantity ("fraction of requests < 300 ms").
  • SLO: the target ("99.9% over 30 days").
  • Error budget: the allowed failure — 0.1% of 30 days ≈ 43 minutes. When exhausted, freeze feature releases and focus on reliability. This is the mechanism that balances velocity and stability.

Alerting

  • Alert on symptoms, not causes. "High error rate" is what users feel; "CPU at 90%" may not affect them. Cause-based alerts produce fatigue.
  • Multi-window burn-rate alerts: a fast burn (5% of budget in 1 h) pages; a slow burn (10% in 6 h) opens a ticket.
  • Every alert needs a runbook with a first diagnostic step. An alert without an action is noise.
  • Dashboards per service and route: RED metrics, dependency health, saturation, and recent deploys overlaid on the graphs.
Interview line: "Observability is a design property, not a tool you bolt on. If a request crosses 10 services and you cannot answer 'where did the 800 ms go?' from traces, metrics, and logs, the system is not observable — regardless of how many dashboards you have."
AD-07

Design for security and compliance.

Security is a set of properties designed in from the start. In an interview the goal is to show you think about who can do what, how data is protected, and what happens when something is compromised. Compliance turns these into hard requirements with legal consequences.

Authentication

  • OAuth 2.0 / OIDC: the user authenticates with an IdP; the client gets an access token and an ID token (JWT) carrying claims and expiry, validated by the resource server without a per-request IdP call.
  • JWT vs opaque: JWT is stateless and fast but cannot be revoked before expiry; opaque tokens require introspection (revocable but a per-request lookup). Use short-lived JWTs (minutes) plus refresh tokens and a revocation list for emergencies.
  • Session cookies: for browsers, HttpOnly + Secure + SameSite beats localStorage, which is XSS-vulnerable.
  • mTLS: short-lived certs (SPIFFE/SPIRE) prove both sides for service-to-service — the zero-trust model: never trust the network, authenticate every call.
  • MFA for privileged accounts and sensitive operations.

Authorization

  • RBAC: users → roles → permissions. Simple and auditable; role explosion in complex domains.
  • ABAC: policies evaluate attributes (department, owner, time, location). More expressive, harder to reason about.
  • Policy-as-code: Open Policy Agent externalizes decisions into a declarative, testable policy that services query — critical for multi-tenancy.
  • Least privilege: every service, user, and token gets the minimum needed. A reporting service should not have write access to the primary DB.
  • Tenant isolation: every query scoped by tenant_id, enforced at the data layer. A missing WHERE tenant_id = ? is a cross-tenant breach.

Encryption

  • In transit: TLS 1.2+ everywhere including internal calls — zero trust assumes a hostile network.
  • At rest: AES-256 for databases, object storage, backups; enable provider default encryption.
  • Key management: KMS (AWS/GCP KMS, Vault). Never hard-code keys. Use envelope encryption — a data key encrypts data, a master key in KMS encrypts the data key — limiting blast radius and making rotation feasible.
  • Field-level encryption for the most sensitive fields (SSN, card numbers) so the DB never sees plaintext. It complicates indexing — use tokenization or searchable encryption where needed.
  • Secrets: Vault/Secrets Manager, rotated and audited. Secrets in env vars or config files are a common breach vector.

Application security

  • Validate input at every boundary; never trust clients.
  • OWASP Top 10: injection (parameterized queries), broken access control (enforce authz on every endpoint, not just the UI), XSS (output encoding, CSP), SSRF (validate outbound URLs), insecure deserialization.
  • Rate limiting and WAF at the edge (CD-02).
  • Dependency scanning, SBOM, and prompt patching — most breaches exploit known vulnerabilities.

Compliance

  • GDPR: minimization, purpose limitation, right to access, right to erasure (delete a user's data across all stores — an architectural requirement), data residency, 72-hour breach notification.
  • HIPAA: PHI encrypted, access logged, only authorized personnel; BAAs with vendors.
  • PCI-DSS: never store raw card numbers — tokenize via Stripe/Adyen; segmentation, audit logs, quarterly scans.
  • SOC 2: audited controls — access reviews, change management, incident response, backed by evidence.

The architectural implication is data classification: tag every field public / internal / confidential / restricted and apply different storage, access, retention, and encryption per class. That is what makes erasure and residency tractable.

Audit and detection

  • Audit logs: append-only, tamper-evident, separate from application logs, retained for years, access-controlled.
  • Anomaly detection: alert on unusual access (10,000 records at 3am), privilege escalation, failed-auth spikes.
  • Incident response: documented plan, rotation, post-mortems. Incidents happen; what matters is detection and containment speed.
AD-08

Balance maintainability and cost. What are the scale-vs-cost trade-offs?

Junior candidates optimize for "it works." Senior candidates optimize for "it works, it is operable, and it does not bankrupt us." Cost and maintainability are design constraints, not afterthoughts — a system 20% faster but 5× more expensive and requiring a dedicated team is usually the wrong design.

Cost drivers

  • Compute: VMs, containers, serverless. Over-provisioning for peak is the most common waste.
  • Storage: hot (SSD, databases) vs cold (object storage, archives) — hot can be 10–100× more per GB.
  • Egress: the silent killer. CDN or video-heavy systems can spend more on egress than compute; cross-AZ traffic is often billed too.
  • Managed services: higher unit cost, but they save engineering time and operational risk — unit cost vs total cost of ownership.
  • Idle capacity: a cluster sized for Black Friday idles 90% of the year.
  • Operational labor: the salary cost of the team running the system — often the largest cost, and the most often ignored in design reviews.

Optimization techniques

  • Autoscaling on the right signal (queue depth, concurrency, CPU) with sane min/max to avoid flapping.
  • Spot/preemptible instances: 60–90% cheaper for fault-tolerant batch work; unsuitable for stateful services without interruption handling.
  • Tiered storage: hot in SSD/Redis, warm in standard object storage, cold in archival. Move automatically by age or access pattern.
  • Compression and dedup: compress logs and backups, dedupe file storage — 3× compression is 3× storage savings.
  • Caching: a hit is orders of magnitude cheaper than a DB query — but right-size the cache, it costs money too.
  • Right-sizing: most services are over-provisioned; a 2-core instance at 15% CPU is a 4-core instance you did not need.
  • Reserved capacity: 30–60% discount on steady-state baseline, combined with autoscaling for the variable part.
  • Batch vs real-time: real-time is expensive (always-on, low latency); batch runs on cheap spot instances. Use real-time only where UX requires it.

Maintainability

  • Modularity: clear boundaries, explicit interfaces, no hidden coupling. A modular monolith often beats a poorly-bounded microservice architecture.
  • Ownership: every service has a team, an on-call rotation, and a runbook. Unowned services rot.
  • Infrastructure as Code: Terraform/Pulumi for everything; no manual console changes. Reproducible environments and reviewable changes.
  • Testing: unit, integration, contract, load. A system without tests cannot be safely changed.
  • Documentation: ADRs for why decisions were made, runbooks for operations, API docs generated from code.
  • Observability (AD-06) — you cannot maintain what you cannot see.
  • Boring technology: the cost of a new tool is the learning curve, operational unknowns, and hiring pool, not the license.

  • Budgets and anomaly alerts per team — a sudden 3× spike is usually a bug (runaway loop, misconfigured autoscaler).
  • Unit economics: track cost per request, per user, per transaction — that is what tells you whether scaling is viable.

AD-09

How do you treat NFRs as first-class design drivers?

Functional requirements say what the system does; non-functional requirements say how well. Two systems with identical features can require a single Postgres instance or a multi-region active-active cluster depending on latency, availability, and consistency targets. The senior move is to elicit NFRs first and let them drive every decision.

The checklist

  • Latency: p50/p95/p99 targets, per operation — a number, not "fast."
  • Throughput: RPS, writes/sec, events/sec at peak.
  • Availability: 99.9% ≈ 8.7 h/year downtime; 99.99% ≈ 52 min; 99.999% ≈ 5 min. Each nine costs exponentially more.
  • Durability: can we lose data, and for how long? RPO/RTO.
  • Consistency: strong, eventual, or session-level — and where each applies.
  • Scalability: current load, 10× load, growth rate.
  • Security/compliance: classification, residency, audit.
  • Cost: budget per request, per user, or total.
  • Operability: who runs it, how it deploys, how it is debugged.

Latency vs durability

A write can be acknowledged at different points:

  • Memory only: microseconds; a crash loses it. Fine for analytics events.
  • Local fsync: milliseconds; survives a process crash, not a disk failure.
  • Replicated to one node: a few ms; survives a node failure.
  • Quorum: tens of ms; survives a minority failure. Strong durability, higher latency.
  • All replicas: highest latency and durability, lowest availability (one slow replica blocks the write).

The question is what is the cost of losing this write? Payments: quorum + fsync. Likes: acknowledge in memory and reconcile later. The answer is per-operation, not per-system.

Consistency vs availability

Consistency is a per-operation choice, not a global one.

  • Strong required: balance, inventory, unique usernames. Pay with higher latency (quorum) and lower availability during partitions.
  • Eventual acceptable: feeds, view counts, search indexes, recommendations. Stale for seconds is fine; you get low latency and high availability.
  • Session consistency: read-your-writes for a user's own data — avoids the worst UX anomaly without full strong consistency. Often the pragmatic middle.

Demanding strong consistency everywhere makes a system slow, expensive, and fragile for no user-visible benefit on the 80% of operations that do not need it.

Peak vs average load

Systems are sized for peak but billed for average — the fundamental tension. Three strategies:

  • Provision for peak: always-on worst-case capacity. Simple and reliable, 10–50× the cost of average. Justified only when the peak is unpredictable and failure cost is extreme.
  • Autoscale on demand: cheaper, but scaling is not instant (instances take seconds to minutes to warm) and sudden spikes can outrun it. Pair with a small always-on baseline.
  • Shed load gracefully: when capacity is exceeded, queue, rate-limit, or serve a simpler response (AD-01). Predictable degradation beats catastrophic failure at the edge of capacity.

The question is: what is the cost of being unavailable at peak versus the cost of idle capacity? A ticket site during a concert sale provisions for peak; an internal dashboard autoscales and accepts slower responses.

Eliciting NFRs in the interview

  • "What is the expected scale — DAU, RPS, data volume?"
  • "What is the latency target for the critical path — 200 ms or sub-50 ms?"
  • "Can we lose data? What is the acceptable window?"
  • "Is strong consistency required, or is eventual acceptable for some features?"
  • "What is the availability target — 99.9% or 99.99%?"
  • "Are there compliance or data residency constraints?"
  • "What is the cost sensitivity?"

Answers shape the architecture: 99.99% rules out single-AZ; 50 ms p99 rules out synchronous cross-region calls; "can lose 5 minutes" allows async replication at lower cost.

Interview line: "NFRs are not a checklist at the end — they are the inputs to the design. Elicit them first, let them drive every architectural decision, and state the trade-off explicitly at each step."

Part 9 ML & GenAI System Design

Feature stores, model serving, LLM systems, end-to-end pipelines, semantic search, and AI agents.

ML-01

What is a feature store, and why is it needed?

A feature store centralizes the computation, storage, and serving of ML features so the same definition is used for training and inference. It has two sides:

  • Offline store: historical values for training (warehouse/lake, Parquet, BigQuery) — optimized for throughput and point-in-time correctness.
  • Online store: latest values for real-time inference (Redis, DynamoDB, Cassandra) — optimized for p99 read latency.

Why it is needed

The core problem is training-serving skew: the feature computed in a training pipeline (batch SQL) differs from the one computed at serving time (streaming code), so the model underperforms in production. A feature store defines the feature once and materializes it to both stores. It also prevents duplicate work — "last 7 days of user purchases" is not recomputed differently by different teams.

Secondary benefits: reuse across teams, discovery (a catalog), and governance (lineage, access control, freshness SLAs).

When it is justified

Two conditions: train/serve consistency and feature reuse across teams. One model and a simple pipeline? Over-engineering. Many models, many teams, real-time serving? Essential infrastructure.

Design considerations

  • Point-in-time correctness: when building training data, use the feature value as of the label event, not the latest value — otherwise you leak future information (label leakage).
  • Freshness: batch features may be hours old, streaming seconds old; expose freshness metadata.
  • Consistency: populate both stores from the same pipeline or a validated dual-write.
  • Backfills: when a definition changes you must recompute history — the store needs a backfill mechanism.

A versioned catalog: artifacts, metadata (training data, hyperparameters, metrics), stage (staging/production/archived), and lineage. It is the source of truth for "which model is deployed where." Serving infrastructure

  • Inference server: TorchServe, Triton, TF Serving, or a custom service. Handles batching, GPU scheduling, versioning.
  • Dynamic batching: group requests into one forward pass to improve GPU utilization, at the cost of a small latency increase — critical for throughput.
  • Autoscaling: scale on GPU utilization or queue depth, not CPU. Model cold start can take minutes; keep warm pools.
  • Monitoring: prediction drift, feature drift, latency, error rate. A model can return 200 OK while predicting garbage.
  • Fallbacks: on timeout, serve a cached prediction or rule-based default rather than failing the request.
ML-03

How would you design a system around an LLM? What are the unique challenges?

The basic pipeline

User input → prompt construction (system prompt + retrieved context + history) → LLM inference → output validation/safety → response. Around this core you need retrieval, memory, tool calling, and cost/rate control.

Retrieval-Augmented Generation

LLMs have a fixed context window and no knowledge of your private data. RAG embeds documents into a vector database, embeds the query, retrieves the top-k chunks, and includes them as context. This avoids fine-tuning for every data update and reduces (but does not eliminate) hallucination. Design considerations: chunking, embedding model choice, hybrid search, reranking, and index freshness.

Unique challenges

  • Latency: hundreds of ms to seconds, generated token by token. Stream the response; use smaller models or speculative decoding where possible.
  • Cost: expensive inference. Control with semantic caching, prompt compression, model routing (small for simple, large for complex), and hard token limits per user.
  • Rate limiting and quotas: per-user and per-tenant token budgets; queueing at peak; graceful degradation to a smaller model.
  • Safety and guardrails: input moderation (prompt injection, jailbreak), output moderation (toxicity, PII), and grounding checks (does the answer cite retrieved sources?). Never trust model output blindly.
  • Evaluation: accuracy metrics do not work for free text. Use human evaluation, LLM-as-judge (with its own biases), and task metrics (faithfulness, relevance, toxicity).
  • State and memory: history must be truncated or summarized to fit the window; a memory service stores long-term facts and retrieves them when relevant.
  • Non-determinism: the same prompt yields different outputs, complicating testing, caching, and reproducibility. Temperature 0 for deterministic tasks; accept variance for creative ones.
Client → API Gateway (auth, rate limit) → Orchestrator
  ├── Retriever (vector DB + keyword search) → context
  ├── Prompt Builder (system + history + context)
  ├── LLM Provider (fallback to a second provider/model)
  ├── Output Guardrails (moderation, PII, grounding)
  └── Cache (semantic cache for repeated queries)

The orchestrator is the key component: it decides whether to retrieve, which model to call, how to handle a provider outage, and when to serve a cached response. It is a classic system-design problem wrapped around a probabilistic model.

ML-04

Describe an end-to-end ML pipeline.

A production ML system is 10% modeling and 90% plumbing. The model is one artifact; the pipeline that produces, serves, and monitors it is the engineering work — and production failures are almost never in the architecture.

1. Data ingestion

  • Sources: transactional DBs (CDC via Debezium), event streams (Kafka), third-party APIs, files, user content.
  • Raw layer: land everything immutably in a data lake in original form — the source of truth for reprocessing.
  • Modes: batch (nightly), micro-batch (minutes), streaming (real-time) — driven by feature freshness, not tooling preference.
  • Quality: schema validation at ingest, null/range checks, volume anomaly detection. Bad data silently entering is the number one cause of degradation.

2. Feature engineering

  • Transformations: cleaning, normalization, encoding, aggregations (last 7 days of purchases), joins with reference data.
  • Feature store (ML-01): compute once, materialize offline and online — this is what prevents training-serving skew.
  • Point-in-time correctness: join features as of the label timestamp, not the latest value. Getting this wrong causes label leakage — great offline, broken in production.
  • Backfills: when a definition changes, recompute history deterministically from raw data.

3. Training

  • Splits: train/validation/test, split by time for temporal problems — a random split leaks future information.
  • Experiment tracking: MLflow, W&B, SageMaker. Every run logs hyperparameters, metrics, dataset version, and code commit — without this, results are not reproducible.
  • Infrastructure: single GPU for small models, data/model parallel for large; spot instances with checkpointing.
  • Reproducibility: pin library versions, seed RNGs, version the dataset. A model you cannot reproduce is one you cannot debug.

4. Evaluation

  • Offline metrics matched to the business objective: recall for fraud, precision for spam.
  • Beyond accuracy: calibration, fairness across subgroups, robustness to shift.
  • Slices: report per segment (new users, mobile, region). 90% overall can be 60% on the segment that matters.
  • Shadow evaluation: run the new model on live traffic without affecting users and compare predictions — catches what offline eval misses.

5. Deployment

  • Model registry (ML-02): versioned artifacts with stage, metadata, lineage.
  • Serving mode: batch, real-time, or streaming, matched to latency and freshness.
  • Rollout: shadow → canary (1–5%) → gradual ramp → full, monitoring business metrics at each step (LB-11).
  • Rollback: a pointer change in the registry — seconds, not hours.

6. Monitoring

This is where most ML systems fail, because traditional monitoring does not detect a model that is healthy but semantically broken.

  • Operational: latency, throughput, error rate, GPU utilization — necessary, not sufficient.
  • Data drift: input feature distributions shift from training (a new app version changes user demographics).
  • Concept drift: the feature→target relationship changes (a new fraud pattern the model never saw).
  • Prediction drift: output distribution shifts (suddenly 10× more "fraud" predictions) — often the earliest signal.
  • Ground-truth lag: labels arrive days late; monitor proxies and close the feedback loop.
  • Retraining triggers: scheduled (weekly) or drift-triggered, with a staging gate before production.

Orchestration

Airflow, Dagster, Prefect, or Kubeflow Pipelines handle scheduling, dependencies, retries, and lineage. The key property is idempotency — re-running a stage must produce the same result so a failed run retries safely.

Interview line: "The model is the easy part. The hard part is reproducible training, point-in-time-correct features, safe rollout, and drift monitoring. Most production ML failures are data failures, not model failures."
ML-05

Explain semantic search and vector databases. How does RAG retrieval work at scale?

Lexical vs semantic

Lexical (BM25) matches exact terms — fast and interpretable, but fails on synonyms: "fix a broken laptop" will not match "repairing a damaged notebook." Semantic search embeds queries and documents into a vector space where meaning is captured by position, so those two land close together. The cost is an embedding model, a vector index, and loss of exact-match precision.

Embeddings

An embedding model (OpenAI text-embedding-3, Cohere, BGE, E5, Sentence-Transformers) maps text to a fixed-length vector, typically 384–3,072 dimensions; similarity is cosine or dot product.

  • Model choice: trade-off between quality, dimension (storage cost), latency, and local-run capability. Multilingual for international content; domain-tuned for specialized corpora.
  • Chunking: documents are split into 200–1,000-token chunks before embedding, because of token limits and because retrieval works better on focused passages. Semantic chunking (paragraph/section boundaries) preserves meaning; 10–20% overlap prevents losing context at boundaries.
  • Asymmetry: queries and documents are different distributions; some models use separate encoders or query:/passage: prefixes.

Vector databases

Pinecone, Weaviate, Qdrant, Milvus, pgvector, and FAISS (a library). Exact nearest neighbor over billions is too slow, so ANN indexes trade a little recall for large speedups:

  • HNSW: a multi-layer navigable graph, searched greedily from the top. Best recall/latency trade-off for most workloads, but memory-hungry (the graph lives in RAM).
  • IVF: k-means clusters; search only the nearest clusters. Cheaper memory, lower recall, tunable via nprobe.
  • PQ: compress vectors into codes — precision traded for memory; often combined as IVF-PQ for billion-scale.
  • DiskANN: graph index on SSD — billion-scale without fitting everything in RAM; higher latency, much cheaper.

Metadata filtering: real queries combine similarity with structured filters (tenant_id = X, date > 2024). Filters must apply during search, not after — post-filtering can return too few results. This is a key differentiator between vector databases.

Hybrid search

Pure semantic misses exact matches (product codes, names, error strings); pure lexical misses paraphrase. Hybrid runs both and fuses with Reciprocal Rank Fusion — summing 1/(k + rank) across ranked lists. This is the production default: semantic recall plus lexical precision.

RAG retrieval at scale

Query → Query Rewriting (expand, disambiguate)
      → Hybrid Retrieval (vector ANN + BM25, top-50)
      → Reranking (cross-encoder, top-5)
      → Context Assembly (dedupe, order, fit window)
      → LLM Generation (with citations)
  • Query rewriting: ambiguous or conversational questions are rewritten into a standalone query, expanded with synonyms, or split into sub-queries.
  • Retrieval: fetch top-k (e.g., 50) from the hybrid index — larger than the final context because the reranker will cut it down.
  • Reranking: a cross-encoder scores each (query, chunk) pair jointly — far more accurate than vector similarity, but too expensive for the whole corpus. Run it on the top-50 to get the top-5. This cheap-recall → expensive-precision two-stage design is the core of modern retrieval.
  • Context assembly: deduplicate near-identical chunks, order logically, fit the window, include source metadata for citations.
  • Generation: answer only from retrieved context, instruct the model to say "I don't know" when context is insufficient, and cite sources so the user can verify.

Freshness and multi-tenancy

  • Freshness: embeddings are immutable, so an updated document requires re-embedding and upserting; detect changes via CDC or webhook, re-embed only changed chunks, and tombstone deletes.
  • Multi-tenancy: namespace by tenant and enforce a mandatory tenant_id filter at the query layer — a filter bug becomes a cross-tenant leak.
  • Cost: embedding is cheap per document but adds up; HNSW storage is RAM-heavy. Tier indexes — hot tenants in HNSW, cold in IVF-PQ or on disk.
Interview line: "Semantic search complements rather than replaces lexical search. Production retrieval is hybrid: vector ANN for recall, BM25 for precision, a reranker for the final order. The vector database is the easy part; chunking, freshness, and evaluation are where the system succeeds or fails."
ML-06

Design an AI agent layer for customer support.

It must answer from the knowledge base, take actions (refund, cancel, update address), escalate when unsure, and never say anything harmful or wrong — while being fast, cheap per conversation, and auditable.

Components

  1. Channel gateway: web chat, email, WhatsApp, in-app. Normalizes messages and maintains conversation state.
  2. Orchestrator / agent loop: decides what to do next — retrieve, call a tool, ask a clarifying question, or respond. A loop over an LLM with a system prompt and a tool manifest (function calling / ReAct).
  3. Retriever: RAG over help articles, policy docs, and resolved tickets — hybrid search plus reranking (ML-05).
  4. Tool layer: typed functions — get_order_status, issue_refund, update_address — each with a strict schema, validation, and its own authorization. The LLM proposes; the tool layer enforces.
  5. Guardrails: input moderation (prompt injection, jailbreak), output moderation (toxicity, PII), grounding checks (does the answer cite a source?).
  6. Memory: short-term (history, summarized when it exceeds the window) and long-term (profile, past tickets, preferences).
  7. Human handoff: a queue with full conversation context so the human does not start from scratch.
  8. Observability and evaluation: log every turn, tool call, and retrieved chunk; track resolution rate, escalation rate, satisfaction, and hallucination rate.
while not done:

    action  = llm.decide(context, available_tools)
    if action.type == "respond":  return guardrails.check(action.text)

The loop needs a maximum iteration count and a timeout — an agent that loops forever is a cost and latency disaster. When the limit is hit, escalate.

Safety and reliability

  • Tool authorization: the agent must never exceed the permissions of the user it acts for. Tool calls execute with the user's identity and scopes. Refunds above a threshold require human approval regardless of what the model says.
  • Confirmation for destructive actions: summarize what is about to happen and ask the user to confirm before cancelling or refunding.
  • Grounding: cite the source for factual claims; if no source is found, escalate rather than guess. Hallucinated policy is worse than "let me connect you to a human."
  • Prompt injection: user input and retrieved documents can contain instructions. Treat retrieved content as untrusted data, never as instructions — use structured delimiters and a system prompt that separates data from commands.
  • PII: redact before sending to a third-party provider, use a no-training guarantee, log only redacted text.
  • Evaluation: a golden set of conversations with expected outcomes, run on every prompt or model change; LLM-as-judge for open-ended quality plus human review of a sample; track regressions, not just absolute quality.
  • Cost control: route simple queries to a small model, cache frequent answers, cap tokens per conversation. Cost per resolved ticket must beat the human cost, or the agent is not worth deploying.
  • Fallback: if the provider is down or slow, fall back to a deterministic FAQ bot or immediate human handoff. The support channel must never be dead.

What "good" looks like

  • Resolution rate: conversations resolved without a human — the primary business metric.
  • Escalation quality: does the human receive full context? A bad handoff is worse than no agent.
  • Containment cost: cost per resolved conversation vs the human baseline.
  • Safety incidents: hallucinated policy, wrong refund, PII leak — should be zero; any incident is a stop-the-line event.
Interview line: "An AI support agent is an LLM in a loop with tools and guardrails — but the hard part is the trust boundary. The model proposes; the tool layer enforces authorization and confirmation; guardrails check output; escalation is always available. The agent resolves the easy 60% and hands off the rest with full context; it does not pretend to do everything."

LLD-01

Design a Parking Lot (low-level design)

LLD tests domain modeling: clear entities, correct responsibilities, sensible inheritance vs composition, and extensibility. Code need not compile, but the class structure must be coherent.

Requirements

  • Multiple floors, each with multiple spots.
  • Spot types: motorcycle, compact, large. Vehicle types: motorcycle, car, truck.
  • Compatibility: motorcycle fits any, car fits compact/large, truck fits large only.
  • Entry issues a ticket with time and spot; exit computes the fee, frees the spot, takes payment.
  • Track availability per spot type per floor.

Entities

ParkingLot
  ├── floors: List<ParkingFloor>
  ├── entryPanels / exitPanels
  └── pricingStrategy: PricingStrategy

ParkingFloor
  ├── floorId
  └── spots: Map<SpotType, List<ParkingSpot>>

ParkingSpot
  ├── spotId, type: SpotType
  ├── status: FREE | OCCUPIED
  └── vehicle: Vehicle (null if free)

  ├── licensePlate, type: VehicleType
  └── subclasses: Motorcycle, Car, Truck

Key design decisions

  • Vehicle as abstract class vs enum: subclasses are more extensible for divergent behavior; an enum is simpler when behavior is uniform. Name the trade-off — I'd use an enum plus a Vehicle class, since behavior does not vary much.
  • Spot allocation is a Strategy: NearestFirst, FloorByFloor, Random. The lot holds a reference; swapping policy touches nothing else.
  • Pricing is another Strategy: Hourly (rate × hours by vehicle type), FlatRate, Peak. The exit panel calls pricingStrategy.calculate(ticket). Naming the pattern and justifying it is a strong signal.
  • Concurrency: two entry panels can try to assign the same spot. Allocation must be atomic — a lock per spot or a compare-and-set on status. This is the most important non-obvious point in the problem.
  • Payment: a PaymentProcessor interface with card/cash/UPI implementations; the exit panel does not know which is used.

Core methods

Ticket enter(Vehicle v):
    spot = allocationStrategy.findSpot(v.type)
    if spot == null: throw LotFullException
    spot.status = OCCUPIED; spot.vehicle = v
    return new Ticket(v, spot, now())

Payment exit(Ticket t):
    t.exitTime = now()
    amount  = pricingStrategy.calculate(t)
    payment = paymentProcessor.charge(amount)
    spot.status = FREE; spot.vehicle = null
    return payment

Extensibility questions

  • EV charging spots? Add a spot type and a compatibility rule; allocation handles it.
  • Time-of-day pricing? A new pricing strategy; nothing else changes.
  • Lost ticket? A lost-ticket flow charging a flat penalty, looked up by license plate.
  • Lot full? A clear error from the entry panel; optionally a waitlist or overflow lot.
  • Reservations? A reservation entity holding a spot for a window; allocation skips reserved spots.
What is scored: clean entities, correct responsibilities (the lot does not compute prices — the strategy does), interfaces for variation, and concurrency awareness.

Design an Elevator System (low-level design)

Requirements

  • N elevators, M floors. Each has a direction (UP/DOWN/IDLE) and pending requests.
  • External requests: a person on floor F presses UP or DOWN.
  • Internal requests: a passenger presses a destination floor.
  • Dispatch external requests to an elevator; each serves its requests in a sensible order.
  • Safety: doors never open while moving; the elevator does not reverse while carrying passengers in the current direction.

An elevator moving up serves all requested floors above it in ascending order until none remain, then reverses and serves floors below in descending order. This is why real elevators do not zig-zag: it minimizes direction changes and is fair over time. TreeSet gives O(log n) insert and O(1) access to the nearest floor in the current direction.

Algorithm 2 — dispatch: which elevator?

  • Nearest idle: simple, good when most elevators are idle, bad under load.
  • Least busy: count pending requests, assign to the fewest. Balances load but ignores direction.
  • Direction-aware ETA (the good one): prefer an elevator already moving in the requested direction and positioned to arrive soon. Score each by estimated time to arrival, accounting for direction and pending stops. Assign the minimum ETA.
  • Zoning: dedicate elevators to floor ranges (low-rise/high-rise) to reduce stops per trip. A static partition, simpler than dynamic dispatch.

State machine

IDLE → MOVING → DOOR_OPEN → IDLE, triggered by requests and arrivals. Modeling it explicitly prevents illegal states (doors open while moving).

Concurrency

  • Multiple external requests arrive at once; the dispatcher must assign atomically. It is not high-throughput, so a coarse lock is fine.
  • Request sets are touched by both the movement thread and the request thread — use concurrent structures or synchronize.
  • A request for the current floor while doors are open should hold the door, not queue.

Extensibility

  • Breakdown? A maintenance state excluded by the dispatcher; pending requests reassigned.
  • VIP/priority? Priority requests jump the queue and are served first by the movement algorithm.
  • 100 floors, 20 elevators? Zoning or a richer ETA model; the interface is unchanged.
  • Fire alarm? A system-level override sending all elevators to the ground floor and opening doors, bypassing normal dispatch.
What is scored: separating movement (SCAN) from dispatch (ETA strategy), an explicit state machine, and concurrency awareness. The naive first-come-first-served answer is obviously wrong; the correct one requires both local and fleet-level optimization.

Part 11 Fresher-Level Questions

FR-01

What is system design, and why is it important?

System design is defining the architecture, components, data flow, and trade-offs of a software system to meet functional and non-functional requirements. It answers: what are the major components? How do they communicate? Where does data live? How does the system behave under load, failure, and scale?

It matters because code-level correctness is not enough. A system can be functionally correct and still collapse under traffic, lose data on a node failure, or cost 10× more than necessary. System design is about the properties that emerge when components interact: availability, scalability, latency, durability, operability. Interviews test it because senior engineers spend more time on these decisions than on writing individual functions.

FR-02

What is a load balancer, and why is it used?

A load balancer distributes incoming traffic across multiple backend servers. It is used to:

  • Scale horizontally — add servers instead of buying a bigger one.
  • Achieve high availability — if one server dies, others keep serving.
  • Improve performance — spread load so no single server is saturated.
  • Enable zero-downtime deployments — drain and replace servers one at a time.

It also provides TLS termination, health checks, and a single point for observability and security policy.

FR-03

Design a basic API for a to-do app.

Resources: users, lists, tasks.

POST   /users                 create user
GET    /users/{id}            get user
POST   /lists                 create list (owner from auth)
GET    /lists/{id}/tasks      list tasks
POST   /lists/{id}/tasks      create task
PATCH  /tasks/{id}            update (title, done, due_date)
DELETE /tasks/{id}            delete

Use JSON, standard status codes (201 create, 404 missing, 401/403 auth), and cursor-based pagination for task lists. Store in a relational DB — users, lists, tasks with foreign keys — because the data is relational and transactional. Authenticate with JWT or session cookies. Add a cache for read-heavy list endpoints if needed.

This is a low-scale design; the interview point is clean resource modeling, not sharding.

FR-04

Design a basic chat application (simplified).

Keep the scope small: one-to-one messaging, history, online status. Do not over-engineer with multi-region or E2E encryption unless asked.

Components

  • WebSocket server: persistent connections; a registry maps user_id → connection.
  • Message service: validates, persists, and routes to the recipient's connection if online.
  • Database: a messages table keyed by conversation_id and timestamp. Postgres is fine at this scale.
  • Presence: a Redis key per user with a TTL refreshed by heartbeats; expiry means offline.

Flow

Sender → WebSocket → Message Service
  1. persist message (conversation_id, sender, text, timestamp)
  2. look up recipient connection in the registry
  3. if online: push over WebSocket
  4. if offline: store as unread; send push notification
  5. ack to sender (message_id, delivered status)

History

On opening a conversation, the client requests the last N messages with cursor-based pagination by timestamp; the server returns them newest first.

If asked to scale

  • Multiple WebSocket servers → a shared registry (Redis) so any server can route to any user.
  • Message storage → wide-column store (Cassandra) partitioned by conversation.
  • Group chat → fan out to each member's connection, or use a pub/sub channel per group.
FR-05

Design a basic file storage application (simplified).

Upload, download, list, delete. No sync, sharing, or versioning unless asked.

Components

  • API server: metadata operations (create, list, delete) and pre-signed URL issuance.
  • Object storage (S3/GCS): the file bytes. The API server never proxies content — clients upload directly, keeping the server stateless and cheap.
  • Metadata DB: (file_id, user_id, filename, size, content_type, storage_key, created_at).

Upload flow

1. Client → POST /files {name, size, type}
2. Server creates metadata (status=pending), returns pre-signed PUT URL
3. Client uploads bytes directly to object storage
4. Client → POST /files/{id}/complete
5. Server verifies the object exists, marks status=ready

Download flow

GET /files/{id} — the server checks ownership and returns a short-lived pre-signed GET URL; the client downloads directly from storage.

Why pre-signed URLs

The API server does not handle large transfers, so it needs no bandwidth or memory for them — only small, fast metadata. This is the single most important design decision here.

Security

  • Every metadata query is scoped by user_id; never trust a client-supplied file ID without an ownership check.
  • Pre-signed URLs expire in minutes.
  • Validate content type and size before issuing the URL.
FR-06

Design a URL shortener (simplified).

The interviewer wants to see the core idea: map a short code to a long URL and redirect.

Components

  • API server: POST /shorten and GET /{code}.
  • Database: (short_code PRIMARY KEY, long_url, created_at).
  • Cache: Redis mapping short_code → long_url for hot links.

Generating the code

Simplest correct approach: generate a unique ID (auto-increment or UUID) and Base62-encode it. Seven characters give ~3.5 trillion combinations, and the ID approach avoids collisions by construction — no availability check needed.

Alternative: hash the long URL (MD5) and take the first 7 characters. Faster, but collisions must be handled by rehashing. The ID approach is simpler and the better fresher answer.

Redirect

GET /{code}:
   url = cache.get(code)
   if url == null:
       url = db.findByCode(code)
       if url == null: return 404
       cache.set(code, url)
   return 302 Location: url

Why 302 instead of 301

301 is permanent and cached by browsers — less load, but hard to change and it breaks click analytics. 302 keeps the redirect under your control. For a simple app either works; naming the trade-off shows awareness.

If asked to scale

  • Shard the DB by hash(short_code).
  • Cache hot links in Redis — most traffic hits a small fraction of links.
  • Generate IDs with a distributed counter or Snowflake instead of a single sequence.
