Part A Missing Classic Designs

CD-09

Design a Search Engine (Google-scale web search)

Requirements

Functional: given a text query, return a ranked list of relevant documents (web pages) in milliseconds. Support pagination, spelling correction, and basic operators (quotes, site:, -word).

Non-functional: low query latency (p99 ≈ 200–500 ms), high read throughput (billions of queries/day), freshness (recent pages indexed within hours/days), high availability, and scale (hundreds of billions of documents).

The two halves of the system

A search engine is two loosely coupled systems joined by an index:

  1. Offline (indexing) pipeline: crawl → parse → analyze → build inverted index → rank signals. This is batch/streaming, high-throughput, latency-tolerant. It can take hours to days per document.
  2. Online (query) pipeline: parse query → retrieve candidate documents → rank → return top-k. This is synchronous, low-latency, and must scale with query volume.

The offline pipeline is essentially CD-04 (Web Crawler) feeding a document store and an indexer. The online pipeline is the interesting part.

The inverted index

The core data structure. Instead of "document → words", store "word → list of documents". For each term, a posting list contains document IDs and, depending on the index, term frequency, positions, and field information. This makes "find all documents containing 'distributed systems'" an O(1) lookup followed by a scan of a sorted posting list, rather than a scan of every document.

Query processing: tokenize the query (split, lowercase, remove stopwords, stem/lemmatize), look up each term's posting list, and combine them (AND for all terms, OR/union for optional terms). For phrase queries, use positional indexes to check word adjacency. For ranking, use term frequencies and document statistics.

Index sharding and replication

A single index cannot hold 100B documents. Shard it:

  • Document sharding (the standard): partition documents across shards by hash(doc_id). Each shard holds a complete inverted index for its subset. A query is sent to all shards (scatter-gather); each returns its local top-k; a aggregator merges and re-ranks to produce the global top-k. This is how Elasticsearch and Solr work. Simple, balanced, and supports arbitrary queries — at the cost of fan-out and tail latency (see LB-14).
  • Term sharding: partition by term. Each shard owns a subset of the vocabulary. Queries are routed to only the shards that own the query terms. More efficient for rare terms, but load is skewed (common terms like "the" concentrate on one shard) and phrase queries across terms become cross-shard joins. Rarely used in production.
  • Replication: each shard is replicated (leader + followers) for availability and read throughput. Followers serve queries; the leader handles index updates.

Index structure and updates

Building an index in place is expensive (random writes to a huge structure). Production engines use immutable segments (Lucene's model): new documents are indexed into a small in-memory segment, flushed to disk as an immutable segment, and background merges combine small segments into larger ones. Deletes are tombstones applied at merge time. This is an LSM-tree-like design: writes are sequential and cheap, reads consult multiple segments (mitigated by caching and merging), and updates are handled by writing a new version of the document and marking the old one deleted.

Ranking

Retrieval gives you candidates; ranking decides the order. Modern search uses a multi-stage ranking pipeline:

  1. Candidate generation: retrieve a few thousand documents via the inverted index (cheap, recall-oriented).
  2. Lightweight scoring: BM25 or TF-IDF over the candidates, plus static signals (PageRank, domain authority, freshness). Cheap enough to score thousands.
  3. Heavy ranking: a machine-learned model (learning-to-rank) scores the top few hundred using features: query-document relevance, click history, user location, language, and page quality. This is the expensive stage and runs only on a small set.
  4. Re-ranking / business rules: diversity, deduplication, safety filters, and any sponsored results.

BM25 is the classic lexical scorer: it rewards term frequency but saturates (a document mentioning a term 100 times is not 100× more relevant) and normalizes by document length. Learning-to-rank models (LambdaMART, neural rankers) learn the weights from click data and human judgments.

Caching

  • Query cache: the full result list for a popular query (head queries). Very high hit rate for the long-tail distribution of queries.
  • Posting list cache: hot terms' posting lists kept in memory.
  • Result snippets: the generated snippet for a (query, doc) pair.

Latency budget

For a p99 of 300 ms: query parsing 1 ms, shard fan-out and retrieval 50–100 ms (parallel across shards), light scoring 20 ms, heavy ranking 100 ms, snippet generation 30 ms, network and serialization 20 ms. The budget is dominated by fan-out tail latency and the heavy ranker — which is why the ranker is capped to a small candidate set and why hedged requests are used.

Trade-offs to name in the interview

  • Freshness vs. index cost: re-indexing every page continuously is prohibitively expensive. Prioritize by change rate and importance.
  • Recall vs. latency: retrieving more candidates improves recall but costs latency. Cap the candidate set and accept some recall loss.
  • Scatter-gather tail: a query hitting 100 shards waits for the slowest. Use hedged requests, shard-level timeouts, and partial results.
  • Index size vs. features: positional indexes enable phrase queries but double the index size. Store positions only where needed.
CD-10

Design a File Storage / Sync System (Google Drive, Dropbox)

Requirements

Functional: upload, download, organize files in folders, share with other users, sync across devices, version history, offline access, conflict resolution.

Non-functional: durability (never lose a byte), availability, low sync latency (seconds), scale (exabytes of storage, hundreds of millions of users), efficient bandwidth (do not re-upload a 1 GB file for a one-character edit).

Core split: metadata vs. content

The single most important design decision is separating the two:

  • Metadata store: a relational database (or a strongly consistent distributed store) for the file tree, ownership, permissions, versions, and sync state. This is small, transactional, and needs strong consistency — a renamed folder must be atomic.
  • Blob store: an object store (S3/GCS) or a custom distributed block store for the actual file bytes. This is huge, immutable, and can be eventually consistent.

Chunking and deduplication

Files are split into blocks (e.g., 4 MB) and each block is stored separately. This enables:

  • Deduplication: identical blocks are stored once, keyed by content hash (SHA-256). Two users uploading the same file share storage. Across an organization, this can cut storage by 30–60%.
  • Delta sync: editing one block uploads only that block, not the whole file. A 1 GB video with a one-byte edit uploads 4 MB, not 1 GB.
  • Parallel upload/download: blocks transfer concurrently, saturating the client's bandwidth.
  • Resumability: a dropped connection resumes from the last completed block.

Fixed vs. content-defined chunking. Fixed-size blocks (every 4 MB) are simple but break dedup when content shifts — inserting one byte at the start shifts every block boundary, and every block hash changes. Content-defined chunking (Rabin fingerprint or a rolling hash) places boundaries based on content, so insertions only change the affected blocks. This is what rsync and backup systems use, and it dramatically improves dedup for edited files.

The sync protocol

Each client keeps a local database of file metadata and a sync cursor (a version number or change ID). The flow:

  1. Change detection: the client watches the local filesystem for changes (inotify/FSEvents) and computes a delta (new/changed/deleted blocks).
  2. Push: upload new blocks (skipping ones the server already has, by hash), then send a metadata change (new version, new block list) to the server.
  3. Pull: the client asks the server "what changed since my cursor?" The server returns a change log — a list of metadata mutations (files created/renamed/deleted, new versions). The client applies them and fetches any missing blocks.
  4. Notifications: when another device changes something, the server pushes a notification (long-poll, WebSocket, or APNs/FCM) so the client pulls immediately rather than waiting for its polling interval. This is what makes sync feel instant.

The change log is the heart of the system. It is an append-only, ordered sequence of mutations per user (or per shared folder), and it is what lets a client catch up from any point.

Conflict resolution

Two devices edit the same file offline. Both upload. The server must decide. Options:

  • Last-write-wins: the later timestamp wins; the earlier edit is lost. Simple, but silently destroys data. Acceptable only for low-value data.
  • Conflict copies (Dropbox's approach): keep both — the second upload is saved as "file (conflicted copy)." No data loss, but the user must resolve manually.
  • Version vectors / vector clocks: each file version carries a vector of (device, counter). The server can tell whether two versions are causally ordered (one is a descendant of the other → no conflict) or concurrent (true conflict). This is the correct general solution and is used by distributed sync systems.
  • Operational transformation / CRDTs: for collaborative real-time editing (Google Docs), merge character-level operations instead of whole files. Much harder, but gives automatic merge without conflict copies.

Sharing and permissions

A file or folder has an ACL: owner, list of (user/group, role). Roles are typically viewer/commenter/editor/owner. Shared folders create a graph of permissions that must be evaluated transitively — if I share a folder with you and you share a subfolder with a third person, that person can access the subfolder but not the parent. Cache permission decisions aggressively, but invalidate on change (a revoked share must take effect within seconds).

Versioning and garbage collection

Every metadata change creates a new version pointing at a block list. Old versions are retained for a window (e.g., 30 days) and then garbage-collected. Blocks are reference-counted: when no version references a block, it is deleted (or moved to cold storage). GC must be careful not to delete a block that a sync in progress still needs — use a grace period or a lease.

Scale numbers and sharding

For 500M users × 10 GB average = 5 EB of content. The metadata store is sharded by user_id (all of a user's tree is co-located) or by file_id for shared files. The blob store is sharded by content hash, which also gives natural dedup and even distribution. Hot files (a popular shared doc) are cached at the edge or in a CDN.

Interview line: "The hard part of file sync is not storage — object stores solve that. The hard part is the change log and conflict model: how does a client catch up from any point, and what happens when two clients edit the same file offline? Get the metadata and conflict semantics right, and the blob layer is commodity."

Part B Architectural Patterns

AD-04

When would you split a monolith into microservices? What are the costs, and what are the anti-patterns?

The honest framing

"Microservices" is not an architecture goal; it is a scaling strategy for organizations and deployment. A monolith is not a failure — it is the correct default until you have a concrete problem that decomposition solves. The interview answer should start with when not to split, because that is where most teams go wrong.

When NOT to split

  • Small team (< ~20 engineers). Microservices trade code complexity for operational complexity. A small team cannot afford the ops burden (service discovery, observability, CI/CD per service, on-call rotation).
  • Unclear domain boundaries. If you do not yet understand the domain, you will draw the wrong service boundaries and pay for it with distributed transactions and chatty interfaces. A monolith lets you refactor boundaries cheaply.
  • Strong transactional requirements. If most operations span multiple entities and need ACID, a monolith with a single database is far simpler than sagas and eventual consistency.
  • Low scale. A well-tuned monolith on a few large machines handles tens of thousands of requests per second. Decomposition buys you nothing if you are not near that ceiling.
  • Early-stage product. Before product-market fit, iteration speed dominates. A monolith deploys faster, debugs easier, and lets you change the data model without cross-service migrations.

When to split

  • Independent scaling needs. The search service needs 50× the CPU of the billing service. In a monolith you scale both; in microservices you scale search alone. This is the strongest technical driver.
  • Independent deployment cadence. One team deploys daily, another quarterly. Coupling them in one deployable forces the slower cadence on everyone and makes releases risky.
  • Team autonomy. Conway's Law is real: the architecture will mirror the communication structure. If you have multiple teams, giving each ownership of a service reduces coordination overhead.
  • Fault isolation. A memory leak in the recommendation service should not take down checkout. Process isolation bounds the blast radius.
  • Polyglot needs. A ML service in Python, a latency-critical service in Go, a legacy service in Java. Separate processes let each use the right tool.
  • Regulatory / security boundaries. A service handling PII may need a stricter network and access boundary than the rest of the system.

The costs — name them explicitly

  • Distributed transactions. No more BEGIN...COMMIT across services. You get the saga pattern: a sequence of local transactions with compensating actions on failure. Sagas are eventually consistent, complex to debug, and require idempotency (AD-02).
  • Network calls replace function calls. A local call is nanoseconds; a network call is milliseconds and can fail. Every boundary adds latency and a new failure mode.
  • Data consistency. Each service owns its database, so joins become API calls or denormalized projections. Read models must be built and kept fresh.
  • Operational complexity. Dozens of deployables, each with its own config, secrets, scaling policy, dashboards, and alerts. This is why a service mesh and a strong platform team matter.
  • Debugging. A single request crosses 10 services. Without distributed tracing (AD-06), you cannot answer "where did it go wrong?"
  • Testing. Unit tests are easy; integration tests require standing up many services. Contract testing (Pact) becomes essential.

How to split — the process

  1. Domain-Driven Design (DDD). Identify bounded contexts: areas of the business with their own ubiquitous language and model. "Order" in the sales context and "Order" in the fulfillment context may be different things. Each bounded context is a candidate service boundary.
  2. Event storming. A workshop technique: gather domain experts, map events (things that happen), commands (things that trigger them), and aggregates (consistency boundaries). It surfaces the real seams.
  3. Strangler fig pattern. Do not rewrite. Put a proxy in front of the monolith, route one capability at a time to a new service, and let the monolith shrink. This is the lowest-risk migration path and is the industry standard.
  4. Start with the highest-pain boundary. Extract the service that most needs independent scaling or deployment first. Prove the pattern, then repeat.
  5. Database per service. The moment two services share a database, you have a distributed monolith. Each service must own its schema; cross-service data goes through APIs or events.

Anti-patterns to call out

  • Distributed monolith. Services that must be deployed together, share a database, or make synchronous call chains for every request. You get all the complexity of microservices and none of the independence. The classic smell: "we can't deploy service A without deploying B and C."
  • Nano-services. Splitting so finely that a single user request requires 20 network calls. Boundaries should follow business capabilities, not code classes.
  • Shared database. Two services writing to the same tables is the fastest way to couple them forever.
  • Chatty interfaces. A service that requires 50 calls to render one page. Batch or aggregate at the edge (BFF pattern).
  • Resume-driven decomposition. Splitting because microservices are trendy, not because you have a scaling or organizational problem.
Interview line: "Microservices are an org-scaling strategy. Split when you have a concrete driver — independent scaling, independent deploy cadence, or team autonomy — and when you can afford the operational cost. Otherwise a modular monolith is the better engineering decision, and it keeps the option to split later."
AD-05

Explain Event Sourcing and CQRS. When would you use them, and what are the pitfalls?

Event Sourcing

In a traditional system, you store the current state: a row with balance = 100. In event sourcing, you store the sequence of events that produced the state: AccountOpened, Deposited(50), Deposited(50), Withdrew(0). Current state is derived by replaying the events. The event log is the system of record; state is a projection.

Benefits

  • Complete audit trail. Every change is recorded with who, what, when, and why. This is invaluable in finance, healthcare, and any regulated domain — you get audit for free, not as an afterthought.
  • Temporal queries. "What was the balance on March 1?" is answered by replaying events up to that timestamp. No need for separate history tables.
  • Event replay for new projections. Need a new read model (e.g., "total deposits by region")? Replay the event log into a new projection. No data migration, no backfill from a lossy schema.
  • Decoupling. Other services subscribe to events rather than being called synchronously. New consumers can be added without touching the producer.
  • Debugging. You can reproduce any bug by replaying the exact event sequence that caused it.

Challenges

  • Event schema evolution. Events are immutable and stored forever. When the business changes, you need versioned events (Deposited_v2) or upcasters that transform old events on read. This is the hardest operational problem in event sourcing.
  • Replay cost. Rebuilding state from 10 million events is slow. Mitigate with snapshots: periodically persist the current state, and replay only events after the snapshot.
  • Eventual consistency. Read models lag the event log. A user who just wrote may not see their change immediately in a projection. This is a UX problem that must be designed for.
  • Query complexity. You cannot query the event log efficiently for arbitrary questions ("all users with balance > 100"). You need projections — which is where CQRS comes in.
  • Storage growth. The event log grows forever. Use tiered storage (hot for recent, cold for archive) and snapshots to bound replay cost.

CQRS (Command Query Responsibility Segregation)

CQRS separates the write model (commands that change state) from the read model (queries that return data). In its simplest form it is just "separate the read and write paths." In its full form, the write side is an event-sourced aggregate and the read side is one or more projections built by consuming events.

Command → Write Model (validates, emits events) → Event Log
                                                      │
                                        ┌─────────────┼─────────────┐
                                        ▼             ▼             ▼
                                   Projection A  Projection B  Projection C
                                   (read DB)     (search index) (cache)
                                        ▲             ▲             ▲
                                     Queries       Queries       Queries

Benefits: read and write models can be optimized independently (a normalized write model, a denormalized read model tailored to each query); reads can scale horizontally with replicas; complex queries do not slow down writes. Cost: the read model is eventually consistent with the write model, and you now operate two models plus the projection pipeline.

When to use them

  • Audit-critical domains: banking, insurance, healthcare, supply chain. The event log is a business requirement, not a technical choice.
  • Complex domains with rich behavior: where state transitions are the core of the business logic (order lifecycle, claim processing).
  • Multiple read shapes: when the same data must be queried in very different ways (by user, by region, full-text, analytics) and a single schema cannot serve all efficiently.
  • Event-driven integrations: when other services genuinely need to react to changes, and an event log is the natural integration contract.

When NOT to use them

  • Simple CRUD. A settings page or a to-do list does not need an event log. The overhead is pure cost.
  • Small scale. The operational complexity (event store, projections, snapshots, schema versioning) is not justified.
  • Strong immediate consistency required everywhere. If every read must see the latest write instantly, eventual consistency will fight you.
  • Teams unfamiliar with the pattern. Event sourcing is easy to get wrong (events as CRUD, missing domain events, no upcasting strategy). It requires discipline.
Interview line: "Event sourcing is the right answer when the history is the business value, not just the current state. CQRS is the right answer when reads and writes have fundamentally different shapes and scaling needs. They pair naturally — events feed projections — but each can be used alone, and neither should be applied to simple CRUD."

Part C Operability, Security & Cost

AD-06

How do you design for observability? Explain metrics, logs, and distributed tracing, plus SLOs and alerting.

Observability vs. monitoring

Monitoring answers known questions: "is CPU above 80%?" Observability lets you ask new questions about a system you did not anticipate: "why are only users in Germany seeing slow checkouts on Android since the 3pm deploy?" A monitored system tells you it is broken; an observable system tells you why. The three pillars are metrics, logs, and traces.

Metrics

Numeric time series, cheap to store and query, ideal for dashboards and alerts.

  • Counter: monotonically increasing (requests, errors). Rate over time is what matters.
  • Gauge: a value that goes up and down (queue depth, in-flight requests, temperature).
  • Histogram: distribution of values (latency buckets). Enables percentile queries (p50, p95, p99) — the only latency metric that matters for user experience. Averages hide tails (see LB-14).

The two frameworks to name: RED for request-driven services — Rate (requests/sec), Errors (failed requests/sec), Duration (latency distribution). USE for resources — Utilization (% busy), Saturation (queue depth), Errors. RED for services, USE for hosts and infrastructure. Prometheus is the standard collector; Grafana is the standard dashboard.

Logs

Discrete events with context. The difference between useful and useless logs is structure: emit JSON with consistent fields (timestamp, level, service, trace_id, user_id, message, plus event-specific fields). Unstructured text logs cannot be queried at scale.

  • Correlation IDs: every request carries a trace_id (and a request_id) that appears in every log line and every downstream call. This is what lets you reconstruct a request across services.
  • Sampling: at high volume, log everything is too expensive. Sample INFO/DEBUG heavily (1–10%) but keep WARN/ERROR at 100%. Sample by trace ID so a sampled request has all its logs, not a random subset.
  • Retention: hot storage (searchable) for days, cold storage (cheap, compressed) for months. Most debugging happens in the last 24 hours.

ELK (Elasticsearch/Logstash/Kibana), Loki, and cloud-native log services are the common stacks.

Distributed tracing

A trace is the full journey of one request across services. It is composed of spans: each span is one unit of work (an HTTP call, a database query, a function) with a start time, duration, parent span, and attributes. The trace is a tree of spans, and the root span is the user request.

  • Context propagation: the trace ID and parent span ID travel in headers (W3C Trace Context, B3) through every service and every async boundary (message queues carry them too).
  • Instrumentation: OpenTelemetry (OTel) is the vendor-neutral standard for generating and exporting traces, metrics, and logs. Instrument once, export anywhere (Jaeger, Tempo, Datadog, Honeycomb).
  • Sampling: tracing every request is expensive. Head-based sampling decides at the start (e.g., 1% of requests); tail-based sampling decides after the trace completes, which lets you keep 100% of slow or errored traces — far more useful. Tail sampling requires buffering traces until completion.
  • What it answers: "which service added the 800 ms?" "did the database call retry?" "is the latency in our code or the network?" This is impossible with metrics and logs alone.

SLOs, SLIs, and error budgets

Observability exists to answer "is the system healthy?" The rigorous way to define that:

  • SLI (Service Level Indicator): a measured quantity. "Fraction of requests with latency < 300 ms" or "fraction of requests returning non-5xx."
  • SLO (Service Level Objective): the target for that SLI. "99.9% of requests succeed over a 30-day window."
  • Error budget: the allowed failure — 0.1% of 30 days is about 43 minutes. When the budget is exhausted, you freeze feature releases and focus on reliability. This is the mechanism that balances velocity and stability.

Alerting

  • Alert on symptoms, not causes. "High error rate" is a symptom users feel; "CPU at 90%" is a cause that may not affect users. Cause-based alerts produce fatigue. Symptom-based alerts (SLO burn rate) are actionable.
  • Multi-window burn-rate alerts. Alert when the error budget is burning much faster than allowed — a fast burn (5% of budget in 1 hour) pages immediately; a slow burn (10% in 6 hours) opens a ticket.
  • Every alert must have a runbook with a first diagnostic step. An alert without an action is noise.
  • Dashboards per service and per route: RED metrics, dependency health, saturation, and recent deploys overlaid on the graphs.
Interview line: "Observability is a design property, not a tool you bolt on. If a request crosses 10 services and you cannot answer 'where did the 800 ms go?' from traces, metrics, and logs, the system is not observable — regardless of how many dashboards you have."
AD-07

How do you design for security and compliance? Cover authentication, authorization, encryption, and regulatory requirements.

The framing

Security is not a feature you add at the end; it is a set of properties that must be designed in. In a system design interview, the goal is not to recite every OWASP item, but to show that you think about who can do what, how data is protected, and what happens when something is compromised. Compliance (GDPR, HIPAA, PCI-DSS, SOC2) turns these into hard requirements with legal consequences.

Authentication (who are you?)

  • OAuth 2.0 / OIDC: the standard for delegated authorization. The user authenticates with an identity provider (IdP); the client receives an access token and an ID token (JWT). The token carries claims (user ID, scopes, expiry) and is validated by the resource server without calling the IdP on every request.
  • JWT vs. opaque tokens: a JWT is self-contained and stateless (fast validation, no DB lookup) but cannot be revoked before expiry. An opaque token requires introspection at the auth server (revocable, but a per-request lookup). Use short-lived JWTs (minutes) plus refresh tokens, and maintain a revocation list for emergencies.
  • Session cookies: for browser apps, an HttpOnly, Secure, SameSite cookie is safer than storing tokens in localStorage (which is vulnerable to XSS).
  • mTLS: for service-to-service authentication, mutual TLS with short-lived certificates (SPIFFE/SPIRE) proves both sides' identity. This is the zero-trust model — never trust the network, authenticate every call.
  • MFA: for privileged accounts and sensitive operations. Never rely on passwords alone for admin access.

Authorization (what can you do?)

  • RBAC (Role-Based Access Control): users → roles → permissions. Simple, auditable, and sufficient for most systems. The problem is role explosion in complex domains.
  • ABAC (Attribute-Based Access Control): policies evaluate attributes (user department, resource owner, time, location). More expressive, more complex to reason about.
  • Policy-as-code: Open Policy Agent (OPA) externalizes authorization decisions into a declarative policy (Rego) that services query. This centralizes policy, makes it testable, and avoids scattering authorization logic across services. Critical for multi-tenant systems.
  • Principle of least privilege: every service, user, and token gets the minimum permissions needed. A reporting service should not have write access to the primary database.
  • Tenant isolation: in multi-tenant systems, every query must be scoped by tenant_id, and this must be enforced at the data layer, not just the API. A missing WHERE tenant_id = ? is a cross-tenant data breach.

Encryption

  • In transit: TLS 1.2+ everywhere, including internal service-to-service calls. No plaintext HTTP inside the VPC — zero trust assumes the network is hostile.
  • At rest: AES-256 for databases, object storage, and backups. Cloud providers offer transparent encryption; enable it by default.
  • Key management: use a KMS (AWS KMS, GCP KMS, Vault). Never hard-code keys. Use envelope encryption: a data key encrypts the data, and a master key (in KMS) encrypts the data key. This limits the blast radius of a key compromise and makes rotation feasible.
  • Field-level encryption: for the most sensitive fields (SSN, credit card), encrypt at the application layer so the database never sees plaintext. This complicates queries (you cannot index encrypted fields directly) — use tokenization or a searchable-encryption scheme if needed.
  • Secrets management: Vault, AWS Secrets Manager, or Kubernetes Secrets (with encryption at rest). Secrets in environment variables or config files are a common breach vector. Rotate regularly and audit access.

Application security

  • Input validation at every boundary. Never trust client input; validate type, length, and format server-side.
  • OWASP Top 10: injection (parameterized queries, never string concatenation), broken access control (enforce authorization on every endpoint, not just the UI), XSS (output encoding, CSP), SSRF (validate outbound URLs), insecure deserialization.
  • Rate limiting and WAF at the edge to blunt brute-force, scraping, and common exploits (see CD-02).
  • Dependency scanning: SBOM, automated vulnerability scanning in CI, and prompt patching. Most breaches exploit known vulnerabilities.

Compliance

  • GDPR (EU): data minimization, purpose limitation, right to access, right to erasure (you must be able to delete all of a user's data across all stores — this is an architectural requirement, not a legal afterthought), data residency (EU data stays in the EU), and breach notification within 72 hours.
  • HIPAA (US healthcare): PHI must be encrypted, access logged, and only accessible to authorized personnel. BAAs with vendors.
  • PCI-DSS (payments): never store raw card numbers; use a tokenization provider (Stripe, Adyen). Network segmentation, audit logs, and quarterly scans.
  • SOC 2: audited controls for security, availability, and confidentiality. Mostly about process (access reviews, change management, incident response) backed by evidence.

The architectural implication of compliance: data classification. Tag every field as public / internal / confidential / restricted, and apply different storage, access, retention, and encryption policies per class. This is what makes "delete all of a user's data" and "keep EU data in the EU" tractable.

Audit and detection

  • Audit logs: append-only, tamper-evident records of who did what and when. Separate from application logs; retained for years; access-controlled.
  • Anomaly detection: alert on unusual access patterns (a user downloading 10,000 records at 3am), privilege escalation, and failed-auth spikes.
  • Incident response: a documented plan, a rotation, and post-mortems. Security incidents will happen; the question is how fast you detect and contain them.
Interview line: "Security in system design is three questions: how do we prove identity, how do we enforce least privilege, and how do we protect data at rest and in transit. Compliance adds constraints — data residency, right to erasure, audit retention — that must shape the data model and storage choices from day one, because retrofitting them is a multi-quarter project."
AD-08

How do you balance maintainability and cost in system design? What are the trade-offs of scale vs. cost?

Why this matters in interviews

Junior candidates optimize for "it works." Senior candidates optimize for "it works, it is operable, and it does not bankrupt us." Cost and maintainability are not afterthoughts — they are design constraints. A system that is 20% faster but costs 5× more and requires a dedicated team to operate is usually the wrong design.

The cost drivers

  • Compute: VMs, containers, serverless invocations. The dominant cost for most services. Over-provisioning for peak is the most common waste.
  • Storage: hot (SSD, databases) vs. cold (object storage, archives). Hot storage can be 10–100× the cost per GB of cold.
  • Egress: data leaving the cloud or region. This is the silent killer — a video or CDN-heavy system can spend more on egress than compute. Cross-AZ traffic is often billed too.
  • Managed services: a managed database costs more per unit than self-hosted, but saves engineering time and operational risk. The trade-off is unit cost vs. total cost of ownership.
  • Idle capacity: the biggest waste. A cluster sized for Black Friday idles 90% of the year.
  • Operational labor: the salary cost of the team that runs the system. Often the largest cost for a complex architecture, and the one most often ignored in design reviews.

Cost optimization techniques

  • Autoscaling: match capacity to demand. Scale on the right signal (queue depth, concurrency, CPU) and set sane min/max bounds to avoid flapping.
  • Spot / preemptible instances: 60–90% cheaper for fault-tolerant batch work. Not suitable for stateful services unless you handle interruption gracefully.
  • Tiered storage: hot data in SSD/Redis, warm in standard object storage, cold in archival (Glacier, Coldline). Move data automatically by age or access pattern.
  • Compression and deduplication: compress logs and backups, dedupe file storage (CD-10). A 3× compression ratio is a 3× storage cost reduction.
  • Caching: a cache hit is orders of magnitude cheaper than a database query. But caches cost money too — right-size them.
  • Right-sizing: most services are over-provisioned. Use utilization data to shrink instance sizes. A 2-core instance at 15% CPU is a 4-core instance you didn't need.
  • Reserved capacity / committed use: 30–60% discount for a 1–3 year commitment on steady-state baseline load. Combine with autoscaling for the variable portion.
  • Batch vs. real-time: real-time serving is expensive (always-on capacity, low latency). Batch processing can run on cheap spot instances on a schedule. Use real-time only where the user experience requires it.

Maintainability

Maintainability is the cost of changing the system. It is not measurable in dollars directly, but it shows up as engineering velocity, incident frequency, and onboarding time.

  • Modularity: clear boundaries between components, explicit interfaces, and no hidden coupling. A modular monolith is often more maintainable than a poorly-bounded microservice architecture.
  • Ownership: every service has a team that owns it, with an on-call rotation and a runbook. Unowned services rot.
  • Infrastructure as Code: Terraform/Pulumi for all infrastructure. No manual console changes. This makes environments reproducible and changes reviewable.
  • Testing: unit, integration, contract, and load tests. A system without tests is a system that cannot be safely changed.
  • Documentation: architecture decision records (ADRs) for why decisions were made, not just what. Runbooks for operations. API documentation generated from the code.
  • Observability: (AD-06) — you cannot maintain what you cannot see.
  • Boring technology: prefer proven, well-understood tools over novel ones. The cost of a new technology is not the license; it is the learning curve, the operational unknowns, and the hiring pool. "Choose boring technology" is a real engineering principle.

FinOps in practice

  • Tag every resource by team, service, and environment. Untagged spend is unmanageable.
  • Budgets and alerts: per-team monthly budgets with anomaly detection. A sudden 3× spike in a service's spend is usually a bug (a runaway loop, a misconfigured autoscaler).
  • Unit economics: track cost per request, per user, per transaction — not just total spend. This is what tells you whether scaling is economically viable.
  • Regular review: a monthly cost review with the engineering teams, not just finance. Engineers make the cost decisions; they need to see the bill.
Interview line: "The cheapest system is not the one with the lowest cloud bill — it is the one with the lowest total cost of ownership: infrastructure plus engineering time plus incident cost. A managed service that costs 2× more per unit but eliminates a dedicated ops team is usually the cheaper choice. Conversely, a microservice architecture that shaves 10% off latency but triples operational complexity is usually the more expensive one."
AD-09

How do you treat Non-Functional Requirements (NFRs) as first-class design drivers? Discuss latency vs. durability, consistency vs. availability, and peak vs. average load.

NFRs are the design

Functional requirements tell you what the system does; non-functional requirements tell you how well it must do it. In system design interviews, the NFRs are what differentiate designs. Two systems can have identical features and completely different architectures because one needs 10 ms p99 and the other can tolerate 2 seconds. The senior move is to elicit NFRs early and let them drive the architecture, rather than designing first and hoping the NFRs are met.

The NFR checklist

  • Latency: p50, p95, p99 targets. Not "fast" — a number, per operation.
  • Throughput: requests/sec, writes/sec, events/sec at peak.
  • Availability: the "nines" — 99.9% (8.7 hours/year downtime) vs. 99.99% (52 minutes) vs. 99.999% (5 minutes). Each nine costs exponentially more.
  • Durability: can we lose data? For how long? RPO (recovery point objective) and RTO (recovery time objective).
  • Consistency: strong, eventual, or session-level. Where does each apply?
  • Scalability: current load, 10× load, growth rate.
  • Security and compliance: data classification, residency, audit.
  • Cost: budget per request, per user, or total.
  • Operability: who runs it, how it is deployed, how it is debugged.

Latency vs. durability

A write can be acknowledged at different points:

  • After writing to memory only: lowest latency (~microseconds), but a crash loses the write. Unacceptable for payments; acceptable for analytics events.
  • After writing to a local disk (fsync): ~milliseconds, survives a process crash but not a disk failure.
  • After replicating to one other node: ~a few milliseconds, survives a node failure.
  • After replicating to a quorum: ~tens of milliseconds, survives a minority failure. Strong durability, higher latency.
  • After replicating to all replicas: highest latency, highest durability, lowest availability (one slow replica blocks the write).

The design question is: what is the cost of losing this write? For a payment, replicate to a quorum and fsync. For a "like" count, acknowledge after memory and reconcile later. The answer is per-operation, not per-system. A single system can have different durability levels for different data classes.

Consistency vs. availability

This is CAP/PACELC (SD-04) applied as a design driver. The senior framing is: consistency is not a global choice — it is a per-operation choice.

  • Strong consistency required: account balance, inventory count, unique username. These operations must be linearizable. They pay with higher latency (quorum) and lower availability during partitions.
  • Eventual consistency acceptable: social feed, view count, search index, recommendations. These can be stale for seconds and still be useful. They get low latency and high availability.
  • Session consistency: read-your-writes for a user's own data, even if other users see stale data. This is often the pragmatic middle ground — it avoids the worst UX anomaly (a user not seeing their own change) without full strong consistency.

The mistake is to demand strong consistency everywhere ("just in case"). It makes the system slow, expensive, and fragile for no user-visible benefit on the 80% of operations that do not need it.

Peak vs. average load

Systems are sized for peak, but billed for average — this is the fundamental tension. A shopping site may average 1,000 req/s but peak at 50,000 on Black Friday. Three strategies:

  • Provision for peak: always-on capacity for the worst case. Simple, reliable, and 10–50× the cost of average. Only justified when the peak is unpredictable and the cost of failure is extreme.
  • Autoscale on demand: add capacity when load rises. Cheaper, but scaling is not instant (a new instance takes seconds to minutes to warm up), and sudden spikes can outrun it. Pair with a small always-on baseline.
  • Shed load gracefully: when capacity is exceeded, degrade rather than collapse — queue, rate-limit, or serve a simpler response. This is backpressure (AD-01). A system that sheds load predictably is better than one that scales perfectly but fails catastrophically at the edge of capacity.

The design question is: what is the cost of being unavailable at peak, versus the cost of idle capacity? For a ticketing site during a concert sale, provision for peak. For an internal analytics dashboard, autoscale and accept slower responses at peak.

Eliciting NFRs in an interview

The first five minutes of a system design interview should be requirements clarification. Ask:

  • "What is the expected scale — daily active users, requests per second, data volume?"
  • "What is the latency target for the critical path? Is 200 ms acceptable, or does it need to be under 50 ms?"
  • "Can we lose data? What is the acceptable window?"
  • "Is strong consistency required, or is eventual consistency acceptable for some features?"
  • "What is the availability target? 99.9% or 99.99%?"
  • "Are there compliance or data residency constraints?"
  • "What is the budget or cost sensitivity?"

The answers shape the architecture: a 99.99% target rules out single-AZ deployments; a 50 ms p99 rules out synchronous cross-region calls; a "can lose 5 minutes of data" requirement allows async replication and lower cost.

Interview line: "NFRs are not a checklist at the end — they are the inputs to the design. The same feature set can require a single Postgres instance or a multi-region active-active cluster depending on the latency, availability, and consistency targets. Elicit them first, then let them drive every architectural decision, and state the trade-off explicitly at each step."
