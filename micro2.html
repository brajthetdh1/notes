Microservices: Service Discovery

How microservices locate and communicate with each other dynamically

Question

Which pattern is commonly used for service discovery in microservices?

  • A. Singleton
  • B. Observer
  • C. Eureka / Consul / Zookeeper ✅
  • D. Adapter
Answer: C – Eureka / Consul / Zookeeper

Explanation

In microservices architecture, service discovery is crucial for enabling services to dynamically find and communicate with each other. Tools like Eureka, Consul, and Zookeeper are commonly used for this purpose.

  • They maintain a registry of available service instances.
  • Enable clients to discover services dynamically without hardcoding URLs.
  • Support load balancing and fault tolerance.
  • Allow services to register themselves at startup and deregister on shutdown.

Example: Using Eureka for Service Discovery

@SpringBootApplication
@EnableEurekaServer
public class EurekaServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(EurekaServerApplication.class, args);
    }
}

@SpringBootApplication
@EnableEurekaClient
public class MicroserviceApplication {
    public static void main(String[] args) {
        SpringApplication.run(MicroserviceApplication.class, args);
    }
}

Key Points

  • Eureka / Consul / Zookeeper act as **service registries**.
  • Services **register themselves** at startup for discovery by other services.
  • Enables dynamic **load balancing**, failover, and scaling in microservices.

Spring Cloud: Registering Services with Eureka

How microservices register themselves for discovery

Question

Which Spring Cloud annotation is used to register a service with Eureka?

  • A. @EnableDiscoveryClient ✅
  • B. @EnableEurekaServer
  • C. @SpringBootApplication
  • D. @EnableFeignClients
Answer: A – @EnableDiscoveryClient

Explanation

The @EnableDiscoveryClient annotation registers a Spring Boot microservice with a service registry such as Eureka. This allows other microservices to discover and communicate with it dynamically.

Example: Registering a Microservice with Eureka

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.client.discovery.EnableDiscoveryClient;

@SpringBootApplication
@EnableDiscoveryClient
public class ProductServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(ProductServiceApplication.class, args);
    }
}

Key Points

  • @EnableDiscoveryClient enables the service to register with Eureka or other discovery servers.
  • @EnableEurekaServer is used to **create** a Eureka server, not a client.
  • Once registered, services can be discovered by other microservices for dynamic communication and load balancing.

Microservices: Circuit Breaker

How circuit breakers help maintain system stability

Question

What is the role of a Circuit Breaker in microservices?

  • A. Prevents a failing service from overwhelming dependent services ✅
  • B. Monitors traffic and throttles requests
  • C. Logs service metrics
  • D. Routes requests
Answer: A – Prevents a failing service from overwhelming dependent services

Explanation

A Circuit Breaker is a design pattern used in microservices to improve system resilience. It detects failing services and temporarily stops calls to them to prevent cascading failures that could impact the entire system.

  • Common implementations include Resilience4j and Hystrix.
  • It can automatically reset after a timeout, allowing services to recover gracefully.
  • Prevents dependent services from being overwhelmed by repeated failures.

Example: Using Resilience4j Circuit Breaker

import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    @CircuitBreaker(name = "paymentService", fallbackMethod = "fallbackPayment")
    public String processPayment(String orderId) {
        // Call to external payment service
        return "Payment processed for " + orderId;
    }

    public String fallbackPayment(String orderId, Throwable t) {
        return "Payment service unavailable, please try later for " + orderId;
    }
}

Key Points

  • Stops repeated calls to failing services.
  • Protects dependent services and prevents cascading failures.
  • Supports fallback methods to handle failures gracefully.

Spring Cloud: Inter-Service Communication

Using declarative REST clients with OpenFeign

Question

Which Spring Cloud module is used for inter-service communication using declarative REST clients?

  • A. Spring Cloud Gateway
  • B. Spring Cloud Config
  • C. Spring Cloud OpenFeign ✅
  • D. Spring Cloud Bus
Answer: C – Spring Cloud OpenFeign

Explanation

Spring Cloud OpenFeign provides a declarative way to create REST clients for inter-service communication in microservices. It automatically handles HTTP calls, serialization, and error handling, reducing boilerplate code.

Example: Using OpenFeign Client

import org.springframework.cloud.openfeign.FeignClient;
import org.springframework.web.bind.annotation.GetMapping;

@FeignClient(name = "user-service")
public interface UserClient {

    @GetMapping("/users/{id}")
    User getUserById(@PathVariable("id") Long id);
}

Key Points

  • Declarative REST client simplifies HTTP calls to other microservices.
  • @FeignClient annotation binds the interface to a service registered in Eureka or another discovery server.
  • Supports load balancing, fallback mechanisms, and integration with Spring Cloud features.

Spring Cloud: Client-Side Load Balancing

Distributing requests among multiple service instances

Question

Which Spring Cloud component provides client-side load balancing?

  • A. Ribbon ✅
  • B. Zuul
  • C. Eureka
  • D. Feign
Answer: A – Ribbon

Explanation

Ribbon is a client-side load balancer in Spring Cloud that distributes requests across multiple instances of a service. It works with service discovery tools like Eureka to dynamically determine available service instances and balance the load among them.

  • Ribbon allows clients to choose which service instance to call based on load balancing rules.
  • It integrates seamlessly with Eureka for dynamic discovery of service instances.
  • Supports various load balancing strategies like round-robin, random, and weighted response time.

Example: Using Ribbon with Feign

@FeignClient(name = "user-service")
public interface UserClient {
    @GetMapping("/users/{id}")
    User getUserById(@PathVariable("id") Long id);
}

// Ribbon automatically balances requests between multiple "user-service" instances

Key Points

  • Ribbon provides client-side load balancing in microservices.
  • Works with Eureka to discover multiple instances dynamically.
  • Can be integrated with Feign or used directly in RestTemplate clients.

Spring Cloud: Spring Cloud Bus

Propagating events and configuration changes across microservices

Question

Which of the following is true about Spring Cloud Bus?

  • A. Propagates configuration changes across services ✅
  • B. Sends events between microservices ✅
  • C. Can work with Kafka or RabbitMQ ✅
  • D. All of the above ✅
Answer: D – All of the above

Explanation

Spring Cloud Bus links distributed services using a lightweight message broker like Kafka or RabbitMQ. It propagates configuration changes, refresh events, and custom events across all connected microservices, reducing manual intervention and improving consistency.

  • Automatically broadcasts configuration updates after changes in Spring Cloud Config.
  • Supports sending and listening to custom application events.
  • Requires a message broker (Kafka, RabbitMQ) for communication between services.

Example: Using Spring Cloud Bus with Config Refresh

# Enable bus refresh endpoint
management.endpoints.web.exposure.include=bus-refresh

# Trigger refresh across services
curl -X POST http://localhost:8080/actuator/bus-refresh

Key Points

  • Propagates configuration changes and events automatically across services.
  • Reduces the need to restart services after config updates.
  • Integrates with message brokers like Kafka and RabbitMQ for event delivery.

Microservices: Distributed Tracing

Monitoring requests and identifying performance bottlenecks

Question

Which tool is commonly used for distributed tracing in microservices?

  • A. Zipkin ✅
  • B. Eureka
  • C. Kafka
  • D. Resilience4j
Answer: A – Zipkin

Explanation

Zipkin is a distributed tracing system that collects timing and trace information from microservices. It helps developers monitor requests, analyze latency, and identify bottlenecks in a distributed system.

  • Tracks requests as they flow through multiple microservices.
  • Provides visualization of service dependencies and request timings.
  • Helps identify slow or failing services to optimize system performance.

Example: Integrating Zipkin with Spring Cloud Sleuth

# Add dependencies in pom.xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-sleuth</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-zipkin</artifactId>
</dependency>

# application.properties
spring.zipkin.base-url=http://localhost:9411/
spring.sleuth.sampler.probability=1.0

Key Points

  • Zipkin collects distributed traces across microservices.
  • Works with Spring Cloud Sleuth for automatic trace instrumentation.
  • Helps monitor system performance, latency, and troubleshoot bottlenecks.

Spring Cloud: Enabling Feign Clients

Declarative REST clients for inter-service communication

Question

Which annotation is used in Spring Cloud to enable Feign clients?

  • A. @EnableFeignClients ✅
  • B. @EnableEurekaClient
  • C. @EnableDiscoveryClient
  • D. @EnableCircuitBreaker
Answer: A – @EnableFeignClients

Explanation

The @EnableFeignClients annotation in Spring Cloud scans for interfaces annotated with @FeignClient and registers them as beans. This enables declarative REST calls to other microservices without manually creating HTTP clients.

Example: Enabling Feign Clients

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.openfeign.EnableFeignClients;

@SpringBootApplication
@EnableFeignClients
public class OrderServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }
}

Key Points

  • Scans and registers Feign interfaces automatically.
  • Simplifies inter-service communication via declarative REST clients.
  • Can be combined with Eureka for service discovery and load balancing.

Microservices: Bulkhead Pattern

Isolating resources to prevent cascading failures

Question

Which pattern isolates different microservices to avoid cascading failures?

  • A. Circuit Breaker
  • B. Bulkhead ✅
  • C. Retry
  • D. Rate Limiter
Answer: B – Bulkhead

Explanation

The Bulkhead pattern isolates resources for different microservices, such as threads, connection pools, or other limited resources. This prevents a failure in one service from consuming all resources and causing cascading failures across other services.

  • Each service or operation gets its own isolated resource pool.
  • Helps maintain availability of other services even when one is failing.
  • Commonly used alongside Circuit Breaker for resilience.

Example: Bulkhead in Resilience4j

import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import org.springframework.stereotype.Service;

@Service
public class PaymentService {

    @Bulkhead(name = "paymentBulkhead", type = Bulkhead.Type.THREADPOOL)
    public String processPayment(String orderId) {
        // Payment processing logic
        return "Payment processed for " + orderId;
    }
}

Key Points

  • Isolates resources to prevent one failing service from affecting others.
  • Improves overall system resilience and stability.
  • Works well with thread pools, connection pools, and rate-limited resources.

Spring Cloud: Real-Time Configuration Updates

Propagating configuration changes across microservices

Question

Which Spring Cloud component helps propagate configuration changes in real-time?

  • A. Spring Cloud Config
  • B. Spring Cloud Bus ✅
  • C. Eureka
  • D. Zuul
Answer: B – Spring Cloud Bus

Explanation

Spring Cloud Bus works with a message broker (Kafka or RabbitMQ) to broadcast events such as configuration changes to all connected microservices. This allows services to update their configuration dynamically without restarting.

  • Automatically propagates configuration updates received from Spring Cloud Config Server.
  • Reduces manual intervention for configuration changes.
  • Supports custom application events for real-time updates across services.

Example: Triggering Config Refresh via Bus

# Expose bus-refresh endpoint
management.endpoints.web.exposure.include=bus-refresh

# Trigger refresh for all services
curl -X POST http://localhost:8080/actuator/bus-refresh

Key Points

  • Propagates configuration changes in real-time.
  • Integrates with message brokers like Kafka or RabbitMQ.
  • Works seamlessly with Spring Cloud Config to keep services updated.
