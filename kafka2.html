Q1: Kafka Architecture Overview

Fundamentals
What is the overall architecture of Apache Kafka? Describe all components.

Apache Kafka is a distributed event streaming platform with a publish-subscribe architecture. Its core components are:

  • Producers: Publish messages to topics.
  • Consumers: Subscribe to topics and process messages.
  • Brokers: Kafka servers that store and serve messages.
  • Topics: Logical categories for messages.
  • Partitions: Physical segments of topics for scalability.
  • ZooKeeper/KRaft: Cluster coordination and metadata management.
  • Controller: Manages cluster state and leadership.
  • Consumer Groups: Group of consumers that work together.
// High-level architecture flow:
Producer → Topic (Partition) → Broker → Consumer

Q2: Kafka Broker

Fundamentals
What is a Kafka Broker and what responsibilities does it have?

A Kafka Broker is a server that stores and serves Kafka messages. It is a node in the Kafka cluster.

Responsibilities:

  • Storage: Stores messages in partitions (log segments) on disk.
  • Replication: Manages replicas of partitions (leader/follower).
  • Produce requests: Accepts messages from producers.
  • Fetch requests: Serves messages to consumers.
  • Replication: Syncs data with follower replicas.
  • Metadata: Provides cluster metadata to clients.
  • Partition leadership: Acts as leader for assigned partitions.

Broker IDs: Each broker has a unique numeric ID (0, 1, 2, ...).

Q3: Kafka Cluster

Fundamentals
What is a Kafka Cluster and how are brokers organized in it?

A Kafka Cluster is a group of brokers working together to provide high availability, fault tolerance, and scalability.

Organization:

  • Brokers: Multiple brokers form the cluster (typically 3+ for production).
  • Controller: One broker acts as the controller (elected via ZooKeeper/KRaft).
  • Partitions: Distributed across brokers for load balancing.
  • Replication: Each partition has a leader and followers on different brokers.
  • ZooKeeper/KRaft: Manages cluster metadata (broker list, topics, ISR).

Benefits: Fault tolerance, horizontal scaling, high availability.

Q4: Kafka Topic

Fundamentals
Explain the concept of a Topic in Kafka architecture.

A Topic is a logical category or feed name to which messages are published. It is a logical container that organizes messages.

Key points:

  • Topics are immutable – messages are appended, never modified.
  • Topics are durable – messages persist on disk based on retention policy.
  • Topics are scalable – divided into partitions for parallelism.
  • Topics are multi-subscriber – many consumers can read from the same topic.
  • Naming convention: alphanumeric, underscores, hyphens (avoid special characters).
// Creating a topic
bin/kafka-topics.sh --create --bootstrap-server localhost:9092 \
  --topic orders --partitions 3 --replication-factor 2

Use cases: Orders, user-events, system-logs, sensor-data.

Q5: Partitions

Fundamentals
What are Partitions and why are they important in Kafka architecture?

Partitions are the physical, ordered, immutable sequences of messages that make up a topic. They are the fundamental unit of parallelism and scaling in Kafka.

Why they are important:

  • Scalability: Partitions can be distributed across multiple brokers.
  • Parallelism: Multiple consumers can read from different partitions in parallel.
  • Ordering: Messages within a partition are guaranteed to be ordered.
  • Load balancing: Producers can distribute messages across partitions.
  • Replication: Partitions can be replicated for fault tolerance.
// Topic "orders" with 3 partitions
// Partition 0: messages 0-9
// Partition 1: messages 10-19
// Partition 2: messages 20-29

Key property: Messages are appended to the end of a partition (append-only log).

Q6: Topics, Partitions & Brokers

Fundamentals
What is the relationship between Topics, Partitions, and Brokers?

The relationship is hierarchical and architectural:

  • Topic → Partition: A topic is composed of 1 or more partitions.
  • Partition → Broker: Each partition is assigned to a leader broker and replicated to follower brokers.
  • Broker → Multiple Partitions: A broker can host leaders/followers for many partitions across different topics.
// Example: Topic "orders" with 3 partitions, replication factor 2
// Broker 0: Partition 0 (Leader), Partition 1 (Follower)
// Broker 1: Partition 1 (Leader), Partition 2 (Follower)
// Broker 2: Partition 2 (Leader), Partition 0 (Follower)

Key insight: This distribution enables horizontal scaling and fault tolerance.

Q7: Message Storage

Fundamentals
How are messages stored in Kafka partitions?

Messages are stored in Kafka partitions as an append-only commit log on disk.

Storage details:

  • Each partition is stored as a directory on the broker's filesystem.
  • Messages are written to log segments (files) sequentially.
  • Each message has a unique offset (index) within the partition.
  • Messages are stored in binary format with key, value, timestamp, and headers.
  • Segments are rolled over when they reach a certain size or time limit.
// Storage path on broker
/var/lib/kafka/data/topic_name-partition_0/00000000000000000000.log
/var/lib/kafka/data/topic_name-partition_0/00000000000000000000.index
/var/lib/kafka/data/topic_name-partition_0/00000000000000000001.log

Key concept: Kafka uses zero-copy for efficient message transfer.

Q8: Offset

Fundamentals
What is an Offset and how does it uniquely identify messages?

An offset is a unique, sequential, 64-bit integer that identifies a message within a partition.

Characteristics:

  • Offsets are monotonically increasing within a partition.
  • Each message in a partition has a unique offset.
  • Offsets are immutable – they never change.
  • Consumers use offsets to track their position in the partition.
  • Offsets are per partition – same offset numbers exist in different partitions.
// Message structure with offset
Message {
  offset: 42,
  timestamp: 1700000000000,
  key: "user-123",
  value: "{\"event\": \"login\"}",
  headers: [("trace-id", "abc123")]
}

Note: Offsets are not reused, even after message deletion.

Q9: Replication

Fundamentals
Explain the concept of Replication in Kafka architecture.

Replication is the process of maintaining multiple copies of partitions across different brokers for fault tolerance and high availability.

Key concepts:

  • Replication Factor (RF): Number of copies of each partition (default: 1, recommended: 3+).
  • Leader: The replica that handles all produce and fetch requests for a partition.
  • Followers: Replicas that replicate data from the leader.
  • ISR (In-Sync Replicas): Followers that are fully caught up with the leader.
  • Replication Lag: The difference between the leader's and follower's log end offsets.

Why it matters: If a broker fails, a follower can be elected as the new leader.

Q10: Replica Types

Fundamentals
What is a Replica and what are its types (Leader/Follower)?

A Replica is a copy of a partition stored on a broker.

Types:

  • Leader Replica:
    • Handles all produce and fetch requests for the partition.
    • Only the leader accepts writes from producers.
    • Responsible for maintaining order and consistency.
  • Follower Replica:
    • Continuously replicates data from the leader.
    • Only serves read requests if enabled (consumer offsets).
    • Cannot accept write requests.
    • Ineligible for client requests unless it becomes the leader.

Key point: The leader-follower relationship ensures consistency and high availability.

Q11: ISR (In-Sync Replica)

Fundamentals
What is the ISR (In-Sync Replica) and how does it work?

ISR (In-Sync Replicas) is the set of replicas that are fully caught up with the leader, meaning they have replicated all messages written to the leader.

How it works:

  • Followers maintain a replication queue and fetch data from the leader.
  • If a follower is caught up (no lag), it's in the ISR.
  • If a follower falls behind (replication lag > replica.lag.time.max.ms), it's removed from ISR.
  • Only ISR members can become the new leader.
  • Producers can choose acks=all to wait for all ISR replicas to acknowledge.
// ISR for partition 0 with RF=3
Partition 0: [Leader: Broker 0] ISR: [Broker 0, Broker 1, Broker 2]

Importance: ISR ensures data durability and consistency.

Q12: Leadership & Replication

Fundamentals
How does Kafka handle partition leadership and follower replication?

Partition Leadership:

  • One broker is elected as the leader for each partition.
  • The leader handles all produce and fetch requests.
  • If the leader fails, a new leader is elected from the ISR.

Follower Replication:

  • Followers continuously fetch data from the leader.
  • They replicate the data and keep their logs in sync.
  • Followers are in the ISR only if they are caught up.
  • Replication is pull-based (followers pull from leader).

Election Algorithm:

  • Controller uses ZooKeeper/KRaft for leader election.
  • Preferre leader: The first replica in the list (broker assignment order).

Q13: ZooKeeper in Kafka

Fundamentals
What is the role of ZooKeeper in Kafka architecture?

ZooKeeper was the external coordinator for Kafka clusters. Its roles include:

  • Broker Registration: Brokers register themselves with ZooKeeper (ephemeral nodes).
  • Controller Election: The first broker to create a specific ZooKeeper node becomes the controller.
  • Metadata Storage: Stores cluster metadata (topics, partitions, ISR, leader information).
  • Consumer Group Management: Stores consumer group offsets (older versions).
  • Cluster Health: Monitors broker heartbeats.

Limitations:

  • ZooKeeper has scalability issues (number of nodes/partitions).
  • External dependency makes operations more complex.
  • Split brain scenarios possible.

Q14: KRaft (Kafka Raft)

Fundamentals
What is KRaft and how does it differ from ZooKeeper-based architecture?

KRaft (Kafka Raft) is the new consensus protocol that replaces ZooKeeper, introduced in Kafka 2.8 (production-ready in 3.0+).

Differences:

Key KRaft features: Self-managed metadata, higher scalability, simpler operations.

Q15: Kafka Storage Layer

Fundamentals
What are the components of the Kafka storage layer?

The storage layer in Kafka consists of:

  • Log Directory: Root directory for all partitions on a broker.
  • Partition Log: Each partition is a log directory containing segment files.
  • Log Segments: Files that contain messages (data files) and index files.
  • Index Files: Offset-to-position mappings for fast lookups.
  • Time Index Files: Timestamp-to-offset mappings.
  • Snapshot Files: Producer state snapshots (for idempotent producers).
  • Leader Epoch Checkpoints: Store leader epoch information.

Q16: Producer Architecture

Producer
Explain the architecture of a Kafka Producer.

The Kafka Producer architecture consists of:

  • Producer Client: The application that sends messages.
  • Producer Configuration: Bootstrap servers, acks, retries, compression, etc.
  • Partitioner: Determines which partition to send each message to.
  • Accumulator: Batch buffer that groups messages for efficiency.
  • Sender Thread: Background thread that sends batches to brokers.
  • Metadata: Caches topic/partition metadata.
// Producer flow
send() → Partitioner → Accumulator (batch) → Sender → Broker

Key configs:

  • bootstrap.servers – Broker addresses.
  • acks – Acknowledgment level.
  • retries – Number of retry attempts.
  • batch.size – Batch size in bytes.
  • linger.ms – Wait time for batching.

Q17: Partition Assignment

Producer
How does a producer determine which partition to send a message to?

The producer uses a partitioner to decide the partition for each message. The logic is:

  • If a partition is specified: Use that partition.
  • If a key is specified: Use the hash of the key to determine the partition (consistent hashing).
  • If no key and no partition: Use round-robin (or sticky partitioner) to distribute load.

Partitioner types:

  • Default Partitioner: Hash-based for keys, round-robin for no keys.
  • Sticky Partitioner: Sticks to a partition for a batch to reduce metadata requests.
  • Custom Partitioner: Implement Partitioner interface.
// Custom partitioner logic
int partition(String topic, Object key, byte[] keyBytes,
    Object value, byte[] valueBytes, Cluster cluster) {
    return key.hashCode() % totalPartitions;
}

Q18: Partitioner Role

Producer
What is the role of the Partitioner in producer architecture?

The Partitioner is responsible for determining which partition a message goes to.

Role and responsibilities:

  • Partition selection: Decides the target partition based on key/partition configuration.
  • Load balancing: Distributes messages evenly across partitions.
  • Order preservation: Ensures messages with the same key go to the same partition (preserving order).
  • Custom logic: Allows custom routing based on message content, headers, etc.

Partitioner implementation:

class CustomPartitioner implements Partitioner {
  void configure(Map<String, ?> configs) { }
  int partition(...) {
    // Custom logic to select partition
    return somePartition;
  }
}

Best practice: Use keys for related messages to maintain order.

Q19: Producer Send Flow

Producer
Explain the producer send flow from client to broker.

The send flow has the following steps:

  • 1. Application Call: producer.send(record) is called.
  • 2. Serialization: Key and value are serialized.
  • 3. Partition Selection: Partitioner determines the target partition.
  • 4. Metadata Fetch: If metadata is stale, the producer fetches updated metadata (leader info).
  • 5. Accumulator: The record is added to the batch buffer (accumulator).
  • 6. Sender Thread: A background thread sends batches to the broker.
  • 7. Broker Write: The leader broker writes the message to the partition.
  • 8. Acknowledgment: The broker returns an acknowledgment (based on acks config).
  • 9. Callback: Producer invokes the callback (if provided).
// Send flow code
Future<RecordMetadata> future = producer.send(record, callback);

Q20: Accumulator/Batch Buffer

Producer
What is the accumulator/batch buffer in producer architecture?

The accumulator (or batch buffer) is a component that groups messages into batches for efficient network transmission.

How it works:

  • Messages are stored in the accumulator until a batch is full (batch.size) or a timeout occurs (linger.ms).
  • Batches are organized by topic/partition.
  • When a batch is ready, it's sent to the broker by the sender thread.
  • Batching improves throughput by reducing the number of network requests.

Memory management:

  • buffer.memory controls the total memory used by the accumulator.
  • If the buffer is full, send() blocks or throws an exception.
// Batching configuration
batch.size=16384 // 16KB
linger.ms=5 // Wait 5ms for more messages
buffer.memory=33554432 // 32MB

Q21: Retries & Backoff

Producer
How does the producer handle retries and backoff?

The producer has a built-in retry mechanism with exponential backoff to handle transient errors.

Retry behavior:

  • Retries: retries (default: 2147483647 – infinite).
  • Backoff: retry.backoff.ms (default: 100ms).
  • Exponential backoff: The delay increases with each retry.
  • Retryable errors: Network errors, leader election, not enough replicas.
  • Non-retryable errors: Invalid configuration, authentication failure, message too large.

Retry strategies:

  • Retries are performed on the same partition.
  • If the broker fails, the producer may get a new leader and retry.
  • Idempotent producers ensure exactly-once even with retries.

Important: max.in.flight.requests.per.connection controls parallel requests (default 5).

Q22: Acknowledgment Levels

Producer
What are the different acknowledgment (acks) levels and how do they affect architecture?
acksDescriptionDurabilityLatency
acks=0No acknowledgment from brokerLowest (data may be lost)Lowest
acks=1Leader writes to its logModerate (leader failure may lose data)Moderate
acks=all (-1)All ISR replicas acknowledgeHighest (strongest durability)Highest

Impact on architecture:

  • acks=0: High throughput, but message loss possible. Used for logging/metrics.
  • acks=1: Leader confirms. Balanced durability/performance. Recommended for most use cases.
  • acks=all: Ensures data is replicated to all ISR. Used for financial/transactional data.

With acks=all: The producer waits for all ISR to acknowledge, ensuring no data loss.

Q23: Exactly-Once Semantics

Producer
How does the producer achieve exactly-once semantics?

Exactly-Once Semantics (EOS) in Kafka is achieved through a combination of features:

  • Idempotent Producer: Prevent duplicate messages in case of retries.
  • Transactions: Atomic writes across multiple partitions/topics.
  • Idempotent configuration: enable.idempotence=true

How it works:

  • Each producer gets a unique producer ID (PID) and sequence number per partition.
  • The broker tracks the last sequence number for each PID/partition.
  • If a duplicate sequence is received, the broker rejects it.
  • Transactions allow atomic commits across multiple partitions.
// Exactly-once configuration
enable.idempotence=true
acks=all
max.in.flight.requests.per.connection=1 (or 5 with idempotence)

Transactional producer: initTransactions(), beginTransaction(), commitTransaction().

Q24: Idempotent Producer

Producer
What is an idempotent producer and how does it work architecturally?

An idempotent producer ensures that message writes are idempotent, meaning that re-sending the same message does not result in duplicates.

Architectural mechanism:

  • Producer ID (PID): Each producer is assigned a unique PID.
  • Sequence Numbers: Each message sent to a partition has a monotonic sequence number.
  • Broker Tracking: The broker tracks the last sequence number for each PID/partition.
  • Duplicate Detection: If a message with an already-used sequence number arrives, the broker rejects it.
// Idempotent producer flow
Producer: [PID=123] sends msg with seq=5
Broker: Accepts (seq=5 is new)
Producer: Retries (same PID, seq=5)
Broker: Rejects (seq=5 already used)

Benefits: Exactly-once delivery within a single partition, no duplicate messages.

Q25: Broker Failure Handling

Producer
How does the producer handle broker failures?

The producer handles broker failures through a combination of mechanisms:

  • Metadata Refresh: When a broker fails, the producer refreshes metadata to discover the new leader.
  • Retries: The producer retries the request with exponential backoff.
  • Broker Fallback: If the initial broker is down, the producer tries other brokers in the bootstrap list.
  • Leader Discovery: The producer asks for the new leader for the partition.

Failure scenarios:

  • Broker down: Producer retries, fetches new leader metadata.
  • Network partition: Producer may fail, but retries succeed when network recovers.
  • Leader election: Producer may get LeaderNotAvailableException, waits for new leader.

Configuration:

  • reconnect.backoff.ms – Delay before reconnecting.
  • retry.backoff.ms – Delay between retries.

Q26: Consumer Architecture

Consumer
Explain the architecture of a Kafka Consumer.

The Kafka Consumer architecture includes:

  • Consumer Client: The application that reads messages.
  • Consumer Group: A group of consumers that share the workload.
  • Poll Loop: The consumer polls for new messages from the broker.
  • Offset Management: Tracks the last read offset for each partition.
  • Rebalancing: Handles partition assignment changes.
// Consumer flow
poll() → Broker → Message Processing → commit() offsets

Key configs:

  • group.id – Consumer group identifier.
  • enable.auto.commit – Auto-commit offsets.
  • auto.offset.reset – Where to start when no offset exists.
  • max.poll.records – Maximum records per poll.

Q27: Consumer Group

Consumer
What is a Consumer Group and how does it work?

A Consumer Group is a set of consumers that work together to consume messages from one or more topics.

How it works:

  • Each partition in a topic is assigned to exactly one consumer in the group.
  • Consumers in the same group coordinate to share the load.
  • If a consumer fails, its partitions are reassigned to other consumers (rebalancing).
  • Offsets are committed per consumer group and partition.
// Consumer group with 2 consumers
Topic: orders (3 partitions)
Consumer Group: order-processing
Consumer 1 → Partitions 0, 1
Consumer 2 → Partition 2

Key concept: Multiple consumer groups can read the same topic independently.

Q28: Consumer Group Rebalancing

Consumer
Explain the consumer group rebalancing process.

Rebalancing is the process of reassigning partitions to consumers in a group when changes occur.

Triggers for rebalancing:

  • A new consumer joins the group.
  • A consumer leaves the group (crash or shutdown).
  • A consumer times out (no heartbeat).
  • New partitions are added to a topic.
  • Consumer group membership changes.

Rebalancing process:

  • Group Coordinator detects the change.
  • The coordinator initiates rebalancing.
  • Consumers pause consumption and revoke their current partitions.
  • Partitions are reassigned based on the assignment strategy.
  • Consumers resume consumption with new assignments.

Impact: During rebalancing, consumption pauses briefly.

Q29: Rebalance Protocols

Consumer
What are the different rebalance protocols in Kafka?

Kafka supports different rebalance protocols (introduced in KIP-429):

  • Eager Rebalance (Classic):
    • Consumers revoke all partitions before rebalancing.
    • No consumption during rebalancing.
    • Simpler but less efficient.
  • Cooperative Rebalance (Incremental):
    • Consumers only revoke partitions that need to be moved.
    • Consumption continues on unaffected partitions.
    • More efficient for large consumer groups.
  • Protocol selection:
    • partition.assignment.strategy with CooperativeStickyAssignor.

Cooperative rebalance benefits:

  • Reduced rebalancing time.
  • Less impact on application throughput.
  • Better for large-scale deployments.

Q30: Offset Commit & Storage

Consumer
How does a consumer commit offsets? Explain offset storage.

Offset commit is how a consumer acknowledges that it has processed messages up to a certain offset.

Offset storage:

  • Internal __consumer_offsets topic: Stores offsets for all consumer groups.
  • Each commit is a message to this internal topic.
  • Offsets are stored per (group, topic, partition).
  • Default retention: 7 days.

Commit strategies:

  • Auto-commit: enable.auto.commit=true (periodic commit).
  • Manual commit: commitSync() or commitAsync().
  • Batch commit: Commit after processing a batch of messages.
// Manual commit
while (true) {
  ConsumerRecords<String, String> records = consumer.poll(100);
  processRecords(records);
  consumer.commitSync(); // commit after processing
}

Q31: Pull-Based Consumption

Consumer
Explain the architecture of Kafka's pull-based consumption model.

Kafka uses a pull-based model where consumers actively request messages from brokers.

How it works:

  • Consumers call poll() to fetch messages.
  • Consumers control their own consumption rate (no backpressure issues).
  • Consumers can choose the number of messages per poll.
  • Brokers are decoupled from consumer processing speed.

Benefits of pull model:

  • Consumer-controlled: Consumers can handle varying processing speeds.
  • Efficient batching: Fetches multiple messages at once.
  • No backpressure: Brokers don't get overwhelmed by slow consumers.
  • Flexibility: Consumers can choose when to consume.
// Poll loop
while (true) {
  ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
  for (ConsumerRecord record : records) {
    process(record);
  }
}

Q32: Partition Assignment

Consumer
How does partition assignment work in consumer groups?

Partition assignment in consumer groups is coordinated by the Group Coordinator using an assignment strategy.

Assignment flow:

  • Each consumer sends a JoinGroup request to the coordinator.
  • The coordinator selects a leader among the consumers.
  • The leader computes the assignment for all consumers.
  • The leader sends the assignment via SyncGroup.
  • Consumers receive their assigned partitions.

Assignment strategies:

  • Range Assignor: Assigns partitions in ranges based on partition count.
  • RoundRobin Assignor: Distributes partitions evenly in a round-robin fashion.
  • Sticky Assignor: Minimizes partition movement during rebalancing.
  • CooperativeSticky Assignor: Incremental rebalancing.

Q34: Multiple Partitions Consumption

Consumer
How does a consumer handle messages from multiple partitions?

A consumer handles messages from multiple partitions by polling and processing records from all assigned partitions.

Key mechanisms:

  • Poll loop: poll() returns records from multiple partitions.
  • Batch processing: Records are retrieved in a batch (can be from different partitions).
  • Interleaving: Records from different partitions are interleaved in the poll response.
  • Ordering guarantee: Within each partition, order is preserved.
// Handling records from multiple partitions
for (ConsumerRecord<String, String> record : records) {
  String topic = record.topic();
  int partition = record.partition();
  long offset = record.offset();
  process(record.value());
}

Best practices:

  • Process records in the order they are received.
  • Commit offsets after processing is complete.
  • Use pause() and resume() for flow control.

Q35: Consumer-Broker Coordination

Consumer
How does the consumer coordinate with the broker?

Consumer-broker coordination involves several mechanisms:

  • Heartbeat: Consumers send periodic heartbeats to the group coordinator (every heartbeat.interval.ms).
  • Session timeout: If the coordinator doesn't receive a heartbeat within session.timeout.ms, the consumer is considered dead.
  • Offset management: Consumers commit offsets to the broker (__consumer_offsets topic).
  • Metadata refresh: Consumers fetch metadata (partition leaders, etc.) from brokers.
  • Group coordination: The group coordinator manages consumer group membership and rebalancing.

Coordination flow:

  • Join group: Consumer joins the group.
  • Heartbeat: Regular heartbeats to maintain membership.
  • Poll: poll() triggers heartbeats and metadata refresh.
  • Leave group: On close or failure, the consumer leaves the group.

Q36: Kafka Controller

Coordination
What is the Kafka Controller and what are its responsibilities?

The Kafka Controller is a special broker that manages cluster-wide metadata and coordination.

Responsibilities:

  • Leader election: Elects partition leaders when needed.
  • Broker management: Handles broker join/leave events.
  • Topic management: Creates/deletes topics and partitions.
  • ISR management: Updates ISR lists.
  • Replica management: Manages replica assignment.
  • Metadata propagation: Updates metadata for all brokers.
  • Controller election: Coordinates its own election.

Why it's important: The controller ensures cluster-wide consistency and orchestrates all major administrative operations.

Q37: Controller Election

Coordination
How is the Kafka Controller elected in the cluster?

The controller election mechanism depends on the coordination system:

With ZooKeeper (legacy):

  • All brokers try to create an ephemeral node in ZooKeeper (/controller).
  • The first broker to successfully create the node becomes the controller.
  • If the controller fails, the ephemeral node is removed, and other brokers compete.
  • Brokers watch the /controller node for changes.

With KRaft (new):

  • Controllers are part of the Raft quorum.
  • The controller is elected through the Raft consensus algorithm.
  • Controllers are configured as part of the metadata quorum.
  • Follower controllers replicate the metadata.

High availability: Multiple brokers can be configured to act as controllers.

Q38: Leader Election

Coordination
Explain the role of the Controller in partition leader election.

The Controller is responsible for electing partition leaders when needed.

Leader election scenarios:

  • Broker failure: The leader broker fails, and the controller selects a new leader from the ISR.
  • Preferred leader election: The controller may reassign leadership to the preferred leader.
  • Partition reassignment: The controller elects leaders for reassigned partitions.

Election process:

  • The controller checks the ISR (In-Sync Replicas) for the partition.
  • The first replica in the ISR is selected as the new leader.
  • The controller updates the metadata and propagates it to all brokers.
  • Producers and consumers learn about the new leader through metadata refresh.

Key point: Only ISR members can become leaders, ensuring no data loss.

Q39: Broker Failure & Recovery

Coordination
How does the Controller manage broker failures and recoveries?

Broker failure handling:

  • ZooKeeper/KRaft detects the broker failure (session timeout).
  • The controller is notified of the broker's departure.
  • For all partitions where the failed broker was the leader, the controller elects new leaders from the ISR.
  • Replicas on the failed broker are marked as offline.
  • The controller triggers partition reassignment if needed.

Broker recovery:

  • The broker restarts and registers with ZooKeeper/KRaft.
  • The controller adds the broker back to the cluster.
  • Replicas on the recovered broker catch up with the leaders.
  • Once caught up, the replicas are added back to the ISR.
  • Preferred leader election may occur to restore the original leadership.

Impact: During failure, affected partitions may be unavailable briefly.

Q40: Metadata Management

Coordination
What is the Metadata in Kafka architecture and how is it managed?

Metadata is the cluster-wide state information that includes:

  • Broker list and their information.
  • Topic list and configurations.
  • Partition assignments (broker → partition mapping).
  • Leader information for each partition.
  • ISR (In-Sync Replicas) list.
  • Replica assignments.

Metadata management:

  • ZooKeeper (legacy): Metadata is stored in ZooKeeper nodes. Brokers and controllers watch for changes.
  • KRaft (new): Metadata is stored in the __cluster_metadata partition. Controllers act as metadata servers.
  • Clients: Producers and consumers cache metadata and refresh periodically.

Metadata propagation: The controller sends metadata updates to all brokers in the cluster.

Q41: Broker Communication

Coordination
How do brokers communicate with each other in a Kafka cluster?

Brokers communicate with each other for various purposes:

  • Inter-broker communication: Uses the Kafka RPC protocol over TCP.
  • Replication: Followers pull data from leaders.
  • Metadata propagation: The controller sends metadata updates to all brokers.
  • Controller communication: The controller instructs brokers on leadership changes, partition assignments, etc.
  • Heartbeat: Brokers send heartbeats to ZooKeeper/KRaft.

Communication mechanisms:

  • Internal requests: LeaderAndIsr, UpdateMetadata, StopReplica, etc.
  • Replication protocol: Fetch requests from followers to leaders.
  • Client-server: Produce, Fetch, ListOffsets requests.

Ports: Brokers listen on a dedicated port (9092 by default) for client and inter-broker communication.

Q42: Group Coordinator

Coordination
What is the role of the Group Coordinator in Kafka?

The Group Coordinator is a broker responsible for managing consumer groups. Each consumer group is assigned to a coordinator broker.

Responsibilities:

  • Consumer group management: Tracks all consumer groups in the cluster.
  • Group membership: Manages joining, leaving, and heartbeat of consumers.
  • Rebalancing: Triggers and coordinates rebalancing within the group.
  • Offset management: Handles offset commits and reads from the __consumer_offsets topic.
  • Partition assignment: Coordinates partition assignment with the group leader.

Assignment:

  • The coordinator for a group is determined by the hash of the group ID.
  • If the coordinator fails, a new coordinator is elected.

Q43: ZooKeeper & Controller Relationship

Coordination
Explain the relationship between ZooKeeper and the Kafka Controller.

In the ZooKeeper-based architecture, the controller and ZooKeeper have a close relationship:

  • Controller election: The controller is elected through ZooKeeper (ephemeral node).
  • Metadata storage: ZooKeeper stores all cluster metadata (topics, partitions, ISR, etc.).
  • Watch mechanism: The controller watches ZooKeeper for changes (e.g., broker failures, topic changes).
  • Controller acts as a proxy: The controller updates ZooKeeper when cluster state changes.
  • Broker registration: Brokers register with ZooKeeper (ephemeral nodes).

In KRaft:

  • ZooKeeper is replaced by the Raft-based controller.
  • The controllers act as both metadata servers and the cluster controller.
  • No external coordination dependency.

Q44: Split Brain & Network Partitions

Coordination
How does the cluster handle network partitions (split brain scenario)?

Split brain occurs when a cluster splits into two or more groups that can't communicate, potentially leading to multiple controllers.

How Kafka prevents it:

  • ZooKeeper's leader election: Uses ZooKeeper's consensus mechanism, ensuring only one controller at a time.
  • Ephemeral nodes: Only the broker that holds the /controller node is the controller.
  • Heartbeat mechanism: Brokers maintain heartbeats with ZooKeeper.
  • Quorum-based: ZooKeeper requires a quorum for leader election.
  • KRaft: Uses Raft consensus, which inherently handles split brain through majority voting.

Mitigation:

  • Minimum 3 brokers for production.
  • ZooKeeper quorum: odd number of nodes (3, 5, 7).
  • KRaft: majority of controllers for consensus.

The Metadata API is the interface through which clients (producers, consumers) and brokers access cluster metadata.

Key aspects:

  • Client metadata: Producers and consumers use the Metadata API to learn about topic partitions, leaders, and broker addresses.

Q46: Message Storage (Log Segments)

Storage & Retention
Explain how Kafka stores messages on disk (log segments).

Kafka stores messages in log segments on disk, organized by partition.

Log segment structure:

  • Log File (.log): Contains the actual message data.
  • Index File (.index): Maps offsets to physical positions in the log file.
  • Time Index File (.timeindex): Maps timestamps to offsets.
  • Snapshot Files: Producer state snapshots for idempotent producers.

Segment management:

  • Segments are created when the previous segment reaches a size limit (log.segment.bytes) or time limit (log.roll.ms).
  • Segments are closed (write-once) after they are rolled.
  • Closed segments are immutable.
  • Segments are deleted based on retention policy.
// Segment files
00000000000000000000.log // Messages 0-99
00000000000000000000.index
00000000000000000100.log // Messages 100-199

Q47: Log Segments Management

Storage & Retention
What are log segments and how are they managed?

Log segments are the physical files that store messages for a partition.

Segment lifecycle:

  • Creation: A new segment is created when the active segment fills up (size or time).
  • Active segment: The segment that is currently being written to (latest segment).
  • Closed segment: Segments that are no longer being written to (immutable).
  • Deletion: Segments are deleted when they exceed the retention policy (age or size).

Segment configurations:

  • log.segment.bytes (default: 1GB) – Maximum segment size.
  • log.roll.ms – Maximum time before rolling a segment.
  • log.index.interval.bytes (default: 4KB) – Index entry frequency.
  • log.index.size.max.bytes (default: 10MB) – Maximum index file size.

Segment indexing: The index file maps offsets to file positions for efficient reads.

Q48: Message Retention & Cleanup

Storage & Retention
How does Kafka handle message retention and cleanup?

Kafka handles retention and cleanup through retention policies:

Retention policies:

  • Time-based retention: retention.ms (default: 7 days).
  • Size-based retention: retention.bytes (default: -1, no limit).
  • Log compaction: Retains only the latest value for each key.

Cleanup process:

  • Background threads (log cleaner, log flusher) periodically check for expired segments.
  • Segments that exceed the retention policy are deleted.
  • For log compaction, records are removed based on keys.
  • Cleanup is performed per partition.

Retention configurations:

  • log.retention.hours – Default retention in hours.
  • log.retention.bytes – Size-based retention.
  • log.cleanup.policy – delete or compact.

Q49: Log Compaction

Storage & Retention
What is log compaction and how does it work architecturally?

Log compaction is a retention policy that retains only the latest value for each key in a partition.

How it works:

  • The log cleaner runs in the background.
  • It examines segments and identifies duplicate keys.
  • For each key, only the latest record is retained.
  • Compacted segments replace the original segments.
  • All offsets remain valid (some records may be removed).

Use cases:

  • Kafka internal topics (__consumer_offsets).
  • Applications that need to maintain the latest state of a key (e.g., user profiles).
  • Change data capture (CDC) with key-based updates.
// Log compaction example
// Before: (k1, v1), (k2, v2), (k1, v3), (k3, v4)
// After compact: (k1, v3), (k2, v2), (k3, v4)

Configuration: log.cleanup.policy=compact

Q50: Message Deletion & Compaction

Storage & Retention
How does Kafka handle message deletion and compaction?

Kafka handles message deletion and compaction through two mechanisms:

  • 1. Deletion (Time/Size-based):
    • When retention is reached, entire segments are deleted.
    • Individual messages are never deleted separately.
    • Deletion is segment-level.
  • 2. Compaction (Key-based):
    • Only the latest value for each key is retained.
    • Older records with the same key are removed.
    • Compaction preserves the latest state.
    • Compaction can be configured per topic.

Cleanup process:

  • Log cleaner runs in the background.
  • For deletion, segments are removed.
  • For compaction, segments are rewritten with only the latest keys.
  • Both processes are asynchronous and configurable.
