Declarative vs Imperative Models

Declarative Model

"What" you want to achieve

You declare the desired end state of the system, and the platform automatically determines and executes the necessary steps to achieve and maintain that state.

The system continuously reconciles the actual state with the declared desired state, making automatic adjustments whenever deviations occur.

This approach is self-healing and idempotent, allowing the same declaration to be applied repeatedly without causing errors or unintended side effects.

Kubernetes Example

kubectl apply -f deployment.yaml

Apply a YAML file describing the desired state

Imperative Model

"How" to achieve it

You provide explicit, step-by-step commands that specify exactly how to perform each operation, managing the entire process flow manually.

Each command must be executed in the correct sequence, and you are responsible for monitoring and maintaining the system state over time.

This approach requires manual intervention for recovery and scaling, and repeated execution of the same commands may produce different results.

Traditional Example

docker run --name app -p 80:80 nginx
docker exec app apt-get update
docker exec app service nginx restart

Execute specific commands in sequence

Immutability in Kubernetes

Immutable

Cannot be modified after creation

Create New

Immutability in Kubernetes means that container images and running containers cannot be modified once they are created and deployed, which ensures that every deployment starts from a known, versioned state rather than allowing in-place modifications that could lead to configuration drift and unpredictable behavior.

This principle is fundamentally important because it guarantees consistent, reproducible deployments across all environments by preventing runtime changes and ensuring that the only way to update an application is to build a new container image and redeploy it, which dramatically improves reliability and makes rollbacks straightforward and predictable.

The immutable infrastructure approach enhances security by eliminating the possibility of unauthorized changes to running containers, simplifies debugging by ensuring that what you test is exactly what gets deployed to production, and enables powerful deployment strategies like blue-green and canary deployments that rely on version consistency.

Pod Health Probes: Liveness, Readiness & Startup

Liveness Probe

Container Health Check

The liveness probe determines if a container is running properly and restarts it when the probe fails, ensuring that applications become healthy again after hanging, deadlocking, or entering broken states.

When to Use:

When your application could become unresponsive but continue running, requiring a restart to recover

Readiness Probe

Traffic Control Check

The readiness probe determines if a container is ready to accept incoming traffic and temporarily removes the Pod from service endpoints when the probe fails, preventing requests from being sent to containers that are starting up or overloaded.

When to Use:

When your application needs time to warm up, load data, or should not receive traffic during maintenance

Startup Probe

Initialization Check

The startup probe determines if a container application has started successfully and disables other probes until it succeeds, protecting slow-starting applications from being killed by liveness checks before they become ready.

When to Use:

When you have legacy applications that take a long time to start on their first initialization

kubectl apply -f pod.yaml Journey
1

kubectl Client

kubectl parses the pod.yaml file, validates the syntax, and converts the YAML/JSON manifest into a Kubernetes API object. It then sends an HTTP POST/PATCH request to the Kubernetes API server using the configured kubeconfig credentials.

2

API Server

API Server receives the request, authenticates the user, authorizes the action via RBAC, validates the Pod specification, applies admission controllers (like validating/mutating webhooks), and stores the validated Pod object in etcd. It then returns success to kubectl.

3

etcd

The Pod object is persistently stored in etcd's distributed key-value store. etcd ensures consistency across all control plane components and provides the single source of truth for the cluster's desired state.

4

Controller Manager

Various controllers watch for Pod changes via the API Server. The Endpoints Controller updates Endpoints objects, and other relevant controllers ensure the cluster's actual state matches the desired state declared in the Pod specification.

5

Scheduler

The Scheduler detects the newly created Pod with no assigned node. It evaluates resource requirements, node constraints, affinity/anti-affinity rules, and selects the optimal worker node for the Pod to run on.

6

API Server (Update)

The Scheduler updates the Pod object via the API Server, binding it to the selected node. The API Server validates this binding and persists the updated Pod specification back to etcd.

7

Kubelet

The Kubelet on the assigned worker node watches for Pods scheduled to its node. It pulls the Pod specification from the API Server, pulls container images, creates the container runtime environment, and starts the containers.

8

Container Runtime

Docker/containerd creates the containers, sets up networking (via CNI), mounts volumes, and starts the application processes inside the containers according to the Pod specification.

9

Status Reporting

Kubelet continuously monitors the Pod's health and reports status back to the API Server, which updates etcd. kubectl get pods can now query this status to show the Pod as Running.

Continuous Reconciliation

This entire process demonstrates Kubernetes' declarative model and continuous reconciliation loop. The control plane constantly works to ensure the actual state (running containers) matches the desired state (Pod specification in etcd).

StatefulSet vs Deployment: When to Choose?

Databases & Data Stores

Choose StatefulSet when running databases like MySQL, PostgreSQL, or MongoDB that require stable network identities and persistent storage that survives pod rescheduling, ensuring each replica maintains its own data volume and identity.

Clustered Applications

Use StatefulSet for applications like Elasticsearch, Cassandra, or ZooKeeper clusters where each node has a specific role, requires ordered deployment and scaling, and needs stable hostnames for cluster member discovery and communication.

Ordered Operations

Select StatefulSet when your application requires ordered, sequential deployment, scaling, and rolling updates where pod N+1 must be ready before pod N starts, ensuring proper initialization sequences and dependency management.

Stateless Web Services

Choose Deployment for stateless applications like web servers, API gateways, or microservices where any pod instance can handle any request and there's no need for stable network identities or persistent local storage.

Random Pod Access

Use Deployment when load balancing across identical pod replicas where client requests can be distributed randomly to any available pod without requiring specific pod identity or ordered access patterns.

Rapid Scaling

Select Deployment when you need fast, parallel scaling operations where pods can be created and destroyed simultaneously without ordered sequences, making it ideal for handling variable traffic loads efficiently.

Quick Decision Guide

Choose StatefulSet If:

✓ Need stable network identifiers

✓ Require persistent storage per pod

✓ Ordered deployment/scaling needed

✓ Running stateful applications

Choose Deployment If:

✓ Application is stateless

✓ Pods are interchangeable

✓ Random load balancing

✓ Fast parallel scaling

Ingress Controller vs LoadBalancer Service

Ingress Controller

An Ingress Controller is a specialized load balancer that manages external access to services within a Kubernetes cluster, typically providing HTTP and HTTPS routing capabilities with features like SSL termination, path-based routing, and virtual hosting.

It operates at the application layer (Layer 7) and uses Ingress resources to define routing rules that determine how external traffic should be directed to different services based on hostnames, paths, or other HTTP attributes.

Layer 7 Routing SSL Termination Path-Based Routing Name-Based Virtual Hosting

LoadBalancer Service

A LoadBalancer Service is a Kubernetes service type that automatically provisions an external cloud load balancer to expose services directly to the internet, operating primarily at the transport layer (Layer 4) for TCP/UDP traffic.

It provides basic load distribution across service endpoints but lacks advanced application-level routing capabilities, making it suitable for simple TCP/UDP services that don't require HTTP-aware routing or SSL termination.

Layer 4 Load Balancing Cloud Integration External IP TCP/UDP Protocols

Key Differences

Network Layer

Ingress works at L7 (application), LoadBalancer at L4 (transport)

Routing Capabilities

Ingress supports host/path-based routing, LoadBalancer does basic load distribution

SSL/TLS

Ingress handles SSL termination, LoadBalancer typically passes through encrypted traffic

Cost & Complexity

LoadBalancer creates cloud LB per service, Ingress uses one controller for multiple services

Use Ingress When

  • You need HTTP/HTTPS routing with host or path-based rules
  • SSL termination at the edge of your cluster
  • Multiple services behind a single external IP

Use LoadBalancer When

  • Exposing TCP/UDP services directly
  • Simple load balancing without HTTP-aware routing
  • When cloud provider integration is sufficient
Network Policies & Namespace Traffic Control

How Network Policies Work

Network Policies are Kubernetes resources that define how groups of pods are allowed to communicate with each other and other network endpoints, acting as a firewall for your cluster by controlling traffic flow at the IP address and port level.

They operate using selector-based rules that specify which pods can communicate based on labels, namespaces, and CIDR blocks, with policies being enforced by the CNI plugin when supported by the underlying network provider.

By default, if no Network Policies are applied, all pods can communicate freely, but once a policy is created for a pod, it becomes isolated and only allowed connections defined in the policy are permitted, following a whitelist model.

Pod Dependency Management

Using Init Containers

Init containers run to completion before the main application containers start, allowing you to implement dependency checks and wait for required services to be ready.

Readiness Probes

Implement readiness probes in the dependency Pod and configure init containers in dependent Pods to poll until the dependency becomes ready.

Service Dependencies

Use init containers to check Service endpoints, ensuring network connectivity and proper DNS resolution before starting the main application containers.
