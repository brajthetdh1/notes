Part A — The Theoretical Frameworks CAP, PACELC, and what they actually claim

1

State the CAP theorem and explain its three components.

Short Answer

CAP states that a distributed data store cannot simultaneously guarantee Consistency, Availability, and Partition tolerance — at most two of the three can be satisfied during a network partition. Since partitions are inevitable in any real network, the practical choice is always between consistency and availability when a partition occurs.

What each letter actually means

The formal definitions come from Gilbert and Lynch's 2002 proof of Brewer's conjecture, and they are stricter than the colloquial versions:

  • Consistency (C) — here specifically linearizability. Every read sees the most recently completed write, and all operations appear to occur in a single global order. If you write x = 1 and the write returns, every subsequent read — from any node — returns 1. This is a much stronger guarantee than “the database doesn't return contradictory rows”.
  • Availability (A) — every non-failing node must return a non-error response to every request, in a bounded amount of time. Not “the system is up sometimes”; every healthy node must always answer. This is what makes CAP so strong: a single node refusing a read violates A.
  • Partition tolerance (P) — the system continues to operate despite arbitrary message loss between nodes. A network partition means some nodes cannot communicate with others, and the system must still function.

Why it reduces to CP vs AP

CAP says “pick two of three”, but in practice you cannot choose to give up P. Networks partition — switches fail, cables are cut, datacenters lose connectivity, packets are dropped. A system that does not tolerate partitions is a system that is unavailable whenever the network misbehaves, which is unacceptable. So P is not optional, and the real choice is: when a partition happens, does the system prioritise consistency or availability?

ChoiceBehaviour during partitionExample systems
CP — prioritise consistency Minority partition refuses writes and possibly reads; system returns errors rather than stale data ZooKeeper, etcd, HBase, Spanner, CockroachDB, MongoDB (with majority read/write concern)
AP — prioritise availability All partitions continue serving; writes diverge and must be reconciled later Cassandra, DynamoDB, Riak, CouchDB, DNS

The crucial nuance most candidates miss

CAP only describes behaviour during a partition. When the network is healthy — which is 99.9% of the time — you can have both C and A. This is why CAP alone is not a useful design tool: it tells you what happens in the rare disaster, not what happens every millisecond of every day. That gap is exactly what PACELC was invented to fill (Question 3).

A second nuance: CAP's “consistency” is linearizability, not the broader consistency of ACID transactions. A system can be “CP” in the CAP sense and still have non-serializable transactions. These are different guarantees that happen to share a letter.

Concrete example

Two replicas of a user balance, R1 and R2, connected by a network that partitions. A user withdraws $100 from R1 (balance 500 → 400) while another request reads from R2 (still 500). If R2 answers with 500, the system has chosen availability (AP) and the read is stale — inconsistent with the completed write. If R2 refuses to answer until it can confirm R1's state, the system has chosen consistency (CP) but is unavailable on R2. There is no third option: R2 cannot both answer correctly and answer at all while disconnected.

Interview Framing

Say: “Since partitions are unavoidable, this is really a CP-vs-AP question during the partition. For the payment ledger I'll choose CP; for the product catalogue I'll choose AP with reconciliation.” That framing immediately signals that you understand CAP is a partition-behaviour choice, not a three-way sacrifice.

2

What are the limitations of the CAP theorem in practice?

Short Answer

CAP is a binary statement about a rare event. It ignores latency, treats availability as all-or-nothing, doesn't distinguish between degrees of consistency, doesn't describe behaviour in the absence of partitions, and says nothing about partial partitions. It is a useful starting vocabulary, not a useful design framework — which is why PACELC exists.

Limitation 1 — It only applies during a partition

Partitions are rare. A well-run system might experience a handful of partitions per year. CAP tells you nothing about the other 8,760 hours, which is when you are choosing not between consistency and availability but between consistency and latency. That trade-off is the one you make on every request, every day, and CAP is silent on it.

Limitation 2 — Availability is defined too strictly

CAP's definition of availability requires every non-failing node to respond in bounded time. Under this definition, a system where 99 of 100 nodes respond is not available. In real operations, “available” means “the service as a whole meets its SLO”, which allows degraded performance, a subset of nodes serving, and partial functionality. A system can fail CAP's availability but pass its SLA.

Limitation 3 — Consistency is a single, very strong point

CAP's consistency is linearizability, the strongest possible single-object guarantee. But there is a spectrum of consistency models — sequential, causal, read-your-writes, eventual — and most real systems operate somewhere in between. A system that provides causal consistency is neither “C” nor “not C” in CAP's binary taxonomy; it is something more useful that CAP cannot express.

Limitation 4 — Partitions are not binary

Real networks experience gray failures: partial partitions where some node pairs communicate and others don't, asymmetric connectivity, high latency that looks like loss, and degraded bandwidth that leads to timeouts. CAP treats a partition as a clean split into two groups, which almost never happens. The practical result is unpredictable behaviour: some requests succeed, some fail, and it is not obvious which side of the CAP choice the system has taken because it is straddling both.

Limitation 5 — It ignores latency entirely

This is the biggest limitation for real design. A strongly consistent system that takes 200 ms per write is technically available and consistent — it passes CAP — but it is unusable for many workloads. A system that relaxes consistency to gain 20 ms is making a trade-off CAP cannot describe. Every cross-region replicated database confronts this daily.

Limitation 6 — Systems are tunable, not classified

Labelling DynamoDB as “AP” is misleading, because DynamoDB offers strongly consistent reads on demand. Labelling MongoDB as “CP” is misleading, because its default write concern is 1 (leader only), which behaves like AP during a partition. The correct statement is: this operation on this system, under this configuration, behaves this way. CAP's classification scheme does not accommodate this granularity, and interview answers that speak in slogans rather than per-operation guarantees are weaker for it.

Limitation 7 — It doesn't address the recovery problem

CAP says nothing about what happens after the partition heals. An AP system must reconcile divergent writes; a CP system must re-elect leaders and repair replicas. These recovery semantics are often harder than the partition behaviour itself, and CAP provides no vocabulary for them. The real design question is “how do I converge after the partition?” and that requires understanding conflict resolution, anti-entropy, and CRDTs — none of which appear in CAP.

The Better Framework

Use CAP to establish the vocabulary and to name the partition behaviour. Then use PACELC (Question 3) for the everyday trade-off, and the spectrum of consistency models (Questions 4–8) for the granularity you actually need. Naming all three in an interview demonstrates depth, not just knowledge of the acronym.

Common Misconception

“My system is CA.” No — no distributed system is CA, because P is not a choice, it is a property of the network. Systems that ignore partitions do so by sacrificing availability when the partition inevitably arrives. The CA corner is a single-node system, which is not distributed.

3

Explain PACELC and how it extends CAP.

Short Answer

PACELC, proposed by Abadi in 2012, says: if there is a Partition, choose between Availability and Consistency (the CAP choice); Else, when there is no partition, choose between Latency and Consistency. This adds the dimension CAP ignores — the latency cost of consistency — and makes the framework useful for the 99.9% of time when the network is healthy.

The two-part decision

The notation is PA/EL or PC/EC — the first pair describes partition behaviour, the second describes normal-operation behaviour. That is where the practical value lies: almost every real system is fully functional during normal operation, and the choice between serving a read in 5 ms (eventually consistent) and 200 ms (strongly consistent) is made thousands of times per second.

ClassificationPartition behaviourNormal behaviourExample systems
PC/ECConsistencyConsistencySpanner, CockroachDB, VoltDB, traditional RDBMS (single-node)
PA/ECAvailabilityConsistencyMongoDB (with majority reads/writes), some configs of DynamoDB
PC/ELConsistencyLatencyVery rare — would mean consistency sacrificed for latency in normal operation but not in partitions, which is unusual
PA/ELAvailabilityLatencyCassandra, DynamoDB (default), Riak, most AP systems

Why the “Else” clause is the important one

Consider two database operations on a replicated dataset:

  • Strongly consistent read: the node must contact a quorum of replicas and take the latest version. If the replicas are in three datacenters, that is 50–200 ms of cross-region round-trip latency.
  • Eventually consistent read: the node serves from local state. Latency is a single-digit millisecond disk read.

Both are valid during a healthy network. The difference is 10× latency — a difference CAP cannot describe but PACELC can. This is the trade-off that decides whether a user perceives a page load as fast or slow, and it is present every moment of every day.

Real system classifications, carefully

Spanner is often called PC/EC — strongly consistent, with a latency cost of ~100 ms per commit due to TrueTime and consensus across regions. DynamoDB is PA/EL by default, but strongly consistent reads are available per request, making it tunable. Cassandra is PA/EL but every query can specify its consistency level (ONE, QUORUM, ALL), making it tunable at the operation level. This means the classification is not a property of the product but of the configuration and the specific operation.

The latency dimension in one sentence

Consistency costs coordination, and coordination costs round trips, and round trips cost latency. Every system that offers strong consistency pays this tax, and the tax grows with the geographic distance between replicas. PACELC gives you the vocabulary to name that tax explicitly and to decide whether the workload justifies paying it.

How to use PACELC in a design interview

For each data access, ask:

  1. Does this operation tolerate stale data during a partition? (If yes, PA. If no, PC.)
  2. Does this operation tolerate the latency of strong consistency during normal operation? (If yes, EC. If no, EL.)

Then design the storage choice and replication strategy to match. A payment ledger answers PC/EC — strong consistency, latency accepted. A social feed answers PA/EL — availability and speed over freshness. A shopping cart answers PA/EC — available during partitions, but every user sees their own cart consistently. Each answer is a design decision, not a label.

Interview Framing

Say: “This is a PACELC decision. During a partition I'll choose availability, and during normal operation I'll choose latency over strong consistency, so this is PA/EL and I'll use eventual consistency with read repair.” That demonstrates both theoretical grounding and the practical taxonomy.

Part B — The Spectrum of Consistency Models From linearizability down to eventual consistency

4

What is the difference between strong consistency and eventual consistency?

Short Answer

Strong consistency guarantees that every read sees the most recent completed write — the system behaves as if there were one copy of the data, updated atomically. Eventual consistency guarantees only that, if no new writes occur, all replicas will eventually converge to the same value. Between now and “eventually”, reads may return stale or out-of-order data. Strong is expensive; eventual is cheap but shifts complexity to the application.

What strong consistency costs

To guarantee that every read sees the latest write, the system must coordinate across replicas before acknowledging either the write or the read. That coordination takes at least one round trip, usually more, and it must contact a majority of replicas — which means the write cannot proceed if a majority is unreachable. Strong consistency therefore pays in two currencies:

  • Latency. The commit latency is bounded below by the round-trip time to the slowest replica in the quorum. In one region this is single-digit milliseconds; across regions it is tens to hundreds.
  • Availability. A network partition that isolates the quorum from a subset of replicas makes the system refuse writes (or refuse reads) on the minority side, because it cannot guarantee freshness.

Spanner charges ~100 ms for a cross-region strongly consistent write. PostgreSQL on one machine charges microseconds, because the “quorum” is one process. The cost is proportional to the geographical spread of the replicas.

What eventual consistency costs

Eventual consistency acknowledges the write at one replica and propagates asynchronously. The write returns in microseconds, and the system is always available — but there is a window (replication lag) during which different replicas hold different values. That window creates specific anomalies:

  • Stale reads. A user writes, then reads from a lagged replica, and does not see their own write. Confusing and often unacceptable.
  • Non-monotonic reads. A user reads value A, refreshes, and reads an older value B because they hit a different, more lagged replica. Violates every intuition.
  • Lost updates. Two replicas accept conflicting writes and one overwrites the other depending on the conflict resolution policy.
  • Phantom reads of deleted data. A row was deleted on the primary but the read replica has not yet applied the delete, so it reappears.

The spectrum, not a binary

Between strong and eventual sits a range of useful intermediate guarantees — sequential, causal, read-your-writes, monotonic reads. Each is cheaper than linearizability and stronger than pure eventual consistency, and each matches a specific user expectation. The question is never “strong or eventual” but “which specific anomalies can this user-facing operation tolerate?”

ModelGuaranteeCoordination costUse case
LinearizableEvery read sees the latest writeHighest — quorum on every opBank balance, inventory, locks
SequentialAll ops in some total order consistent with program orderHighDistributed transactions
CausalHappens-before respected; concurrent ops can be ordered arbitrarilyLow — tracking onlySocial feeds, comments, messaging
Read-your-writesA client sees its own writes on subsequent readsLow — per-sessionProfile updates, form submissions
EventualConvergence if writes stopMinimalLikes, view counts, recommendations

The honest reason eventual is the default

Most data is not read and written by the same user in a tight loop. A product view count, a “likes” number, a recommendation list, a search index, an analytics aggregate — these are eventual by nature because their truth does not matter at the millisecond level. Using strong consistency for them is paying for a guarantee no one needs. The mistake in the other direction — using eventual consistency for a payment ledger or an inventory deduction — is a bug waiting to become an incident.

Common Pitfall

“Eventual consistency” is often used in design documents to mean “we didn't specify.” That is not consistency, that is unspecified behaviour. Every eventual-consistency choice should name the convergence window and the conflict resolution policy — “likes converge within 5 seconds via last-write-wins” is a design; “eventual consistency” is a placeholder.

5

What is linearizability, and how does it differ from serializability?

Short Answer

Linearizability is a guarantee about single objects: each operation appears to take effect instantaneously at some point between its invocation and its response, respecting real time. Serializability is a guarantee about transactions: they appear to execute in some serial order, but that order need not respect real time. They are orthogonal dimensions. The combination — both at once — is called strict serializability.

Linearizability in detail

A linearizable register guarantees: if write W completes before read R begins, R must return the value written by W (or a later write). More precisely, there exists a total order of all operations such that (a) the order respects real time — if A completed before B started, A comes before B — and (b) every read returns the value of the most recent write in that order. This is the “single, atomic register” abstraction users intuitively expect.

The important subtlety: operations can overlap in time, and the “linearization point” can be anywhere within their interval. If read R and write W overlap, R may return either the old or the new value — both are valid linearizable executions. Only operations that are ordered in real time are forced to be ordered in the linearization.

Serializability in detail

A serializable transaction system guarantees: the effect of executing a set of transactions concurrently is equivalent to executing them one at a time in some serial order. This is what database isolation levels (2PL, serializable snapshot isolation) provide. Crucially, the serial order need not match real time — a transaction that started earlier could appear later in the serial order as long as no conflict requires otherwise.

Serializability is about preserving invariants across multiple objects (bank account balances, inventory quantities) despite concurrency. Linearizability is about the freshness of individual objects. They solve different problems.

Concrete example showing they differ

Consider a database that is serializable but not linearizable. Transaction T1 reads x and y, computes z = x + y, writes z. Transaction T2 reads x and y and writes z differently. Serializability guarantees the outcome is some valid serial order of T1 and T2 — no interleaving produces an inconsistent sum. But a client that wrote x, waited for the write to complete, then read z might see a value computed from an older x. That is not linearizable, because the real-time order was not respected. The system could be perfectly serializable while violating linearizability.

Conversely, a linearizable system on a single register is not serializable across two registers, because there is no transaction concept at all — you cannot atomically read two registers.

PropertyLinearizabilitySerializability
ScopeSingle object / operationMulti-object transaction
Respects real time?Yes — requiredNo — only program order
ConcernFreshnessInvariants
Violated byStale readsWrite skew, phantoms
Provided bySpanner, ZooKeeper, etcdSerializable isolation (PostgreSQL SSI, etc.)

Strict serializability — both at once

Strict serializability combines them: transactions are serializable and the serial order respects real time. This is the strongest and most intuitive guarantee, and it is what Spanner claims to provide. CockroachDB provides serializable (without linearizability in all cases) and offers follower reads that are linearizable but not serializable across transactions. The distinction matters when you are choosing a database for a workload that requires both freshness and multi-object invariants.

Why the confusion is common

Both start with S or L, both are described as “strong”, and both appear in the same literature. But when an interviewer asks “is your database strongly consistent?”, the right clarification is: “do you mean linearizable reads, or serializable transactions?” A database can provide one without the other, and the design consequences differ substantially.

Interview Framing

Say: “I'll use a strongly consistent store — specifically linearizable reads — for the ledger, and I'll make the transaction layer serializable so transfers don't violate the invariant.” That names both properties and the mechanism, and demonstrates you know they are not the same thing.

6

What is causal consistency, and when is it sufficient?

Short Answer

Causal consistency guarantees that operations that are causally related are seen by everyone in the same order. If A caused B — A happened-before B — then no replica sees B without having seen A. Operations that are concurrent (no causal relationship) can be seen in any order. It is the strongest consistency model achievable in an always-available, partition-tolerant system.

The middle ground

Causal consistency sits between eventual and sequential consistency. It is stronger than eventual because it prevents causally impossible histories — a reply appearing before the post it replies to. It is weaker than sequential because concurrent operations can be reordered. It requires no coordination for concurrent operations, which is why it can be provided in a partition-tolerant system.

What “causally related” means

Two operations are causally related if one could have influenced the other — through program order on the same node, through a read-write dependency, or through transitivity. Concretely:

  • User A posts a message (write W).
  • User A then replies to their own message (write W').
  • W happens-before W' because of program order.
  • Causal consistency guarantees every replica sees W before W'.

Now suppose User B comments on A's message. B's comment is causally after W because B must have read W to reply to it. So any replica showing B's comment must also show W. But two independent posts by A and B, with no read-write relationship, are concurrent and can appear in either order — no user should be surprised by either.

Why it is often sufficient

Almost every user-facing anomaly that people notice is a causality violation:

  • Seeing a reply before the post it replies to.
  • Seeing a comment on a deleted post.
  • Seeing a message thread in the wrong order.
  • Seeing a “followed” notification before seeing the follow action.

These are the kinds of problems users actually complain about. The anomalies that distinguish sequential from causal consistency — reordered concurrent operations with no causal relationship — are almost invisible to users because there is no semantic expectation of order. A user does not care whether Alice's post or Bob's post appears first if they are unrelated; they do care if a reply appears before its parent. Causal consistency eliminates the anomalies that matter and costs far less than sequential.

The theoretical significance

Mahajan, Alvisi, and Dahlin (2011) proved that causal consistency (specifically causal+ — causal plus convergence of concurrent writes) is the strongest consistency model that can be provided in a partition-tolerant, always-available, one-way communication system. Weaker than causal, you get anomalies users notice; stronger than causal, you need coordination, which sacrifices availability. This is the technical justification for the industry's shift towards causally consistent systems (MongoDB causal sessions, Cosmos DB consistency levels, some CRDT-based stores).

How it is implemented

Implementations typically track causal dependencies using version vectors or hybrid logical clocks. When a node writes, it attaches the dependency metadata; when a replica receives a write, it blocks applying it until all its causal dependencies have been applied. The overhead is metadata per write — a few dozen bytes — and occasional buffering of writes awaiting their dependencies. The coordination cost is zero for concurrent operations, which is why the model remains always-available.

Trade-off

Causal consistency is not free: the metadata overhead is real (version vectors grow with the number of writers), and complex dependency graphs can slow propagation. But for social, messaging, and collaborative applications — where the anomalies users notice are causal — it is the sweet spot between user-visible correctness and availability.

Interview Framing

Say: “For the comment feed I need at least causal consistency so replies never appear before their parents, but concurrent comments can be in any order.” That demonstrates you can reason about user-perceived correctness rather than reaching for linearizability by default.

7

What is read-your-writes consistency, and how do you implement it?

Short Answer

Read-your-writes (RYW) guarantees that after a client performs a write, its subsequent reads — within the same session — will see that write (or a later one). It is a per-session guarantee, not a global one: other users may still see stale data, but the writer does not. It is the minimum consistency users expect, and it is achievable without any global coordination.

Why it is the intuitive baseline

Imagine posting a photo, refreshing the feed, and not seeing it. The user assumes the post failed and re-posts, creating duplicates. This is not a subtle correctness issue — it is a fundamental UX break. Users expect: “I wrote it, therefore I see it.” Delivering that expectation requires read-your-writes consistency, and nothing weaker will do.

RYW is weaker than linearizability because it only constrains the writer's own session. Alice writes to her profile, and Bob might still see the old profile for a few seconds. That is usually acceptable; Bob has no real-time expectation about Alice's data. But Alice seeing her own stale data is not acceptable.

How to implement it

TechniqueMechanismTrade-off
Sticky routing to the primary After a write, route the user's reads to the leader for N seconds Simple; requires session tracking; load concentrates on leader
Version tracking Write returns a version/timestamp; client sends it on read; replica waits or rejects if behind Client changes; replica may block on lag
Write-through session cache Write updates a per-session cache; reads consult cache before replica Extra cache layer; needs invalidation
Optimistic local echo Client stores the write locally and merges with server data; reconciles when available Eventually consistent UI; must handle conflicts
Synchronous replication for the writer Write waits for at least one replica to be updated before acking Higher write latency; still no guarantee about other replicas

The version-token approach in detail

The cleanest solution uses vector clocks or logical timestamps. On write, the primary returns a version number V. On read, the client includes V in the request. The replica checks: if its own version is ≥ V, serve the read; if not, either wait until it catches up (bounded by a timeout) or return a “not ready” signal that the client can retry. This is how MongoDB causal sessions and Cosmos DB session consistency work under the hood. It is precise, requires modest client changes, and degrades gracefully — a request that times out waiting can simply fall back to the primary.

The monotonic reads companion guarantee

RYW is often paired with monotonic reads: once a client has seen a value, subsequent reads never return an older one. Without monotonic reads, a client could write, read the fresh value, refresh, hit a laggier replica, and see the old value again — a different but equally confusing anomaly. Together, RYW + monotonic reads form the minimal “sane session” guarantee that most consumer applications need.

When it is not enough

RYW does not guarantee that a user sees another user's writes. If Alice posts a comment and Bob is watching the thread, Bob may still see the pre-comment state. If the product needs Bob to see Alice's comment “in real time”, the system needs either causal consistency (delivering comments in causal order) or a push channel (WebSocket, SSE) — not a stronger database consistency model. The right abstraction depends on the product requirement, not on a generic “stronger is better” instinct.

Common Pitfall

Implementing RYW by always routing the user to the primary. It works, but it defeats the entire purpose of read replicas and concentrates load on the most fragile node. Always route to the primary only for a short window after a write, or use version tracking to serve from replicas when they are caught up.

8

What is session consistency, and what are the four session guarantees?

Short Answer

Session consistency is a family of guarantees scoped to a single client session. The four classic session guarantees are read-your-writes, monotonic reads, monotonic writes, and writes-follow-reads. They cost essentially nothing to implement because they only require tracking per-session metadata — no global coordination — yet they eliminate almost every anomaly a user perceives.

The four guarantees

GuaranteeStatementWhat it prevents
Read-your-writes A client's reads see its own earlier writes Posting a photo and not seeing it in the feed
Monotonic reads A client never reads a value older than one it has already seen Refreshing and seeing an older state — a count going down, a comment disappearing
Monotonic writes A client's writes are applied in the order the client issued them A rename followed by a delete applying in reverse order
Writes-follow-reads A client's write is ordered after any read the client has already performed A reply being applied to a version of the post that the replier had not seen

The common abstraction: PRAM

The combination of read-your-writes, monotonic reads, and monotonic writes is called PRAM (Pipeline RAM) consistency. It creates the illusion that the client is interacting with a single, private copy of the data — every session sees a monotonic, causally coherent view of its own operations. PRAM is achievable without global coordination and matches the mental model of an individual user far better than any global guarantee.

Implementation — session tokens

The standard mechanism is a session token. On every write, the server returns a token representing the causal context — a version vector, a hybrid logical clock, or a simple version number. On every read, the client sends the token. The server checks whether the replica has advanced to at least that point; if yes, serve the read locally; if no, route to a replica that has caught up, or wait, or fall back to the primary. The token is carried as a cookie, an HTTP header, or a field in the session store, and it is derived entirely from the session's own history.

This is exactly how Cosmos DB session consistency works, and how MongoDB causal sessions are implemented. The overhead is a few bytes per request and a small amount of state; the benefit is a user experience that feels strongly consistent even on a fundamentally eventually consistent backend.

Why session consistency is the right default for consumer apps

Users do not care whether the global system is linearizable. They care that their own actions have visible effects and that the screen does not contradict itself between refreshes. Session guarantees deliver both, at essentially no coordination cost. A globally eventually consistent system with session consistency is indistinguishable from a strongly consistent system from the point of view of any individual user — which is the only point of view the user has.

What session consistency does not solve

It does not give users visibility into other users' recent writes. If Alice writes and Bob reads, Bob may still see stale data. For multi-user real-time interactions — chat, collaborative editing, live auctions — the system needs either causal consistency (so causally related operations are globally ordered) or an explicit real-time delivery channel. Session consistency is a per-user illusion; the product may need a per-conversation or per-document one.

Trade-off

Session guarantees are cheap, but they require end-to-end participation — the client must carry the token, every server must respect it, and every replica must report its freshness. That is an architectural commitment, not a database feature you can enable by accident. The payoff is that the system can use aggressive replication, read replicas, and cross-region reads while still presenting a coherent experience per user.

Interview Framing

Say: “I'll implement read-your-writes and monotonic reads using a version-token carried in the session, so the user's own view is always fresh while the system remains eventually consistent across users.” That demonstrates a pragmatic understanding of which guarantee matters and how to deliver it cheaply.

Part C — Making It Work in Production Quorums, real databases, UI patterns, CRDTs, multi-region

9

How do quorum reads and writes work? Explain R + W > N.

Short Answer

With N replicas, a write is acknowledged after W replicas confirm it, and a read queries R replicas. If R + W > N, every read quorum overlaps every write quorum by at least one node, so at least one responding replica has the latest write. The read can then return the freshest value seen among the R responses.

The overlapping-quorum argument

Suppose N = 3, W = 2, R = 2. Every write reaches at least 2 replicas, and every read queries 2 replicas. Any two 2-element subsets of a 3-element set must overlap in at least one element. So every read is guaranteed to contact at least one replica that received the most recent write. That replica returns the latest version, and the read returns the maximum. This is the mathematical heart of quorum systems: overlapping majorities guarantee visibility.

Choosing R and W

Configuration (N=3)R + WBehaviourUse case
W=3, R=14 > 3Fast reads; every write must reach all replicas (fragile)Read-heavy; tolerate write unavailability on one node
W=2, R=24 > 3Balanced; one node can fail on either sideGeneral purpose
W=1, R=34 > 3Fast writes; reads query all replicas (slow)Write-heavy
W=1, R=12 < 3No overlap guarantee; reads may be staleEventual consistency
W=2, R=13 = 3No guaranteed overlap (the sets can be disjoint)Eventual consistency

The choice is a trade-off between write latency/availability and read latency/freshness. A write with W=3 is blocked by any single replica failure; a read with R=3 is blocked by any single replica failure. W=2, R=2 tolerates one failure on either side while retaining the overlap guarantee.

The crucial caveat: quorum ≠ linearizability

R + W > N gives you “read the freshest of the R responses”, but it does not give linearizability. Several issues can break the guarantee in practice:

  • Non-atomic writes. If the write operation is not itself atomic across replicas — some nodes get the new value, others the old — a read may see a partially applied write.
  • Concurrent writes. Two writers at W=2 may both succeed on overlapping but different subsets, leaving replicas with conflicting values. The read sees one or the other arbitrarily.
  • Sloppy quorums. Dynamo-style systems allow a write to be acknowledged by “hinted” nodes that are not the designated replicas, so the “quorum” may not overlap the read quorum in the intended way.
  • Read repair races. If a read discovers divergent values and repairs in the background, the repair itself may take time.
  • Replica catch-up. A replica that was down during the write may rejoin with stale data, and a read quorum including it might return stale data.

These are not theoretical — Jepsen's analyses of Cassandra and DynamoDB have documented each. The honest statement is: quorums give strong probabilistic freshness, not linearizability. Achieving linearizability requires additional mechanisms — read repair with quorum confirmation, consensus-based commits, or a single-leader design.

Quorum and local vs global

In multi-region deployments, quorum is usually scoped per region: LOCAL_QUORUM in Cassandra requires a majority of replicas within the local region, which gives low latency while ensuring a single region's data is fresh. A cross-region EACH_QUORUM provides a stronger global guarantee at significant latency cost. Choosing between them is the PACELC decision in miniature: local quorum is EL, global quorum is EC.

Common Pitfall

Assuming R + W > N implies strong consistency without checking whether the underlying engine provides atomic multi-replica writes and read repair. Many systems advertise quorum consistency but deliver only “read-repair eventually”, which allows stale reads during the window before repair. Read the documentation of the specific engine and test it under failure.

Compare the consistency models of DynamoDB, Cassandra, and MongoDB.

Short Answer

DynamoDB is eventually consistent by default, strongly consistent on request, with transactions available. Cassandra is tunable per query via consistency levels (ONE, QUORUM, ALL, LOCAL_QUORUM). MongoDB exposes separate read concern and write concern settings plus causal sessions. All three are PA/EL by default but offer paths to stronger guarantees — at latency and availability cost.

DynamoDB

By default, GetItem and Query are eventually consistent and cost 1 read capacity unit. Setting ConsistentRead=true gives a strongly consistent read — always sees the latest committed write — at the cost of 2 RCUs and higher latency (the read must contact a quorum of replicas rather than the nearest one). DynamoDB uses a single-writer-per-partition model with synchronous replication to three availability zones within a region, so strongly consistent reads are available and reasonably fast.

For multi-item atomicity, DynamoDB offers TransactWriteItems and TransactGetItems, which provide ACID semantics across up to 100 items and cost 2× the normal capacity. Global Tables are eventually consistent across regions with last-writer-wins conflict resolution; there is no strongly consistent cross-region mode. This is a clean PA/EL design with EC available per-request within a region.

Cassandra

Cassandra exposes consistency as a per-query setting, which is both its strength and its complexity. The levels:

  • ONE — read/write from a single replica. Fastest; no freshness guarantee.
  • QUORUM — majority of replicas in the cluster. With R=QUORUM and W=QUORUM, gives quorum freshness (with the caveats from Question 9).
  • ALL — every replica must respond. Strongest, but any node failure blocks the operation.
  • LOCAL_QUORUM — majority within the local datacenter. Low latency; single-DC consistency but not global.
  • EACH_QUORUM — quorum in every datacenter. Global consistency; higher latency.
  • LOCAL_SERIAL — used with lightweight transactions (compare-and-set), which use Paxos.

Cassandra's model is tunable per query, so the same cluster can serve both strongly and weakly consistent workloads. The operational burden is that the developer must choose — and get it right — for every access pattern. The engine does not enforce or even warn about the choice.

MongoDB

MongoDB separates two orthogonal settings and adds a session-level abstraction:

  • Write concern — how many nodes must acknowledge the write. {w:1} (default, leader only) is fast but loses writes on failover; {w:"majority"} waits for a majority of replicas and is durable; {w:"majority", j:true} additionally waits for the journal on a majority.
  • Read concern — how fresh the read data must be. "local" (default) reads whatever the node has; "majority" reads only data acknowledged by a majority of replicas; "linearizable" waits for confirmation that the read is not stale.
  • Causal sessions — the session-level guarantee from Question 8, implemented via a server-side cluster time and client-side operation time.

The combination gives fine-grained control. {readConcern:"majority", writeConcern:"majority"} with a causal session provides a strongly consistent, causally coherent experience per session without full linearizability. {readConcern:"linearizable"} on a single document provides linearizable reads at significant latency cost.

What this means in a design interview

When you choose one of these systems, name the specific configuration and the guarantee it provides. Saying “I'll use DynamoDB with ConsistentRead=true for the balance lookup and eventual reads for the history list” is far stronger than “I'll use DynamoDB”. The database is a toolbox, not a label, and the consistency decision must be made per operation.

Interview Framing

Say: “For the ledger I'll use Cassandra with QUORUM reads and QUORUM writes to get quorum freshness, or DynamoDB with ConsistentRead=true. For the activity feed I'll use ONE/LOCAL_QUORUM reads with eventual consistency.” That demonstrates both theoretical and operational awareness.

How do you handle stale reads in a user-facing UI?

Short Answer

Stale reads are inevitable in any eventually consistent system, so the job is not to eliminate them but to make them invisible or harmless. Techniques: optimistic local echo, read-your-writes routing, version tokens, layered caches with short TTLs, and UI affordances that reset expectations. The right mix depends on which reads matter to the user and how stale they can tolerate.

Step 1 — Classify the reads

Not every read in a UI has the same freshness requirement. Before choosing a technique, draw the screen and mark each read:

  • The user's own write (post, comment, profile edit) — the user must see it immediately. This is a read-your-writes requirement.
  • A fresh read of the user's own data (unread count, inbox, notifications) — should be current; users notice if it isn't.
  • Other users' recent activity — can tolerate seconds of staleness; users do not expect real-time.
  • Aggregates and counters (likes, views, follower counts) — can tolerate minutes of staleness; nobody measures.
  • Historical and search data — can tolerate much longer; staleness of hours is fine.

Step 2 — Match techniques to categories

TechniqueFreshness providedBest for
Optimistic local echoInstant for the writerPosts, comments, likes — merges with server data on load
Read-your-writes routingFresh on next readForm submissions, profile edits — session-scoped
Version tokenFresh, verified per requestAnything that must be both fast and correct — the precise mechanism
Short-TTL cacheFresh within N secondsActivity feeds, counts — bounded staleness is acceptable
Primary fallback for own dataAlways freshCritical reads — expensive but simple

Step 3 — The optimistic echo pattern

The most common and most effective technique for user-generated content. The client writes the data to a local store (Redux, IndexedDB, an in-memory model) and updates the UI immediately, without waiting for the server. The server response then reconciles the local state. If the server rejects the write (rare), the local echo is rolled back with a visible error. Users see their post instantly, even though the system is eventually consistent. The complexity is modest — a reconciliation function — and the UX benefit is enormous.

Step 4 — The consistency boundary

A key insight from production systems: only the user's own actions require strong consistency; everything else can be eventual. A social feed can show stale comments from other users; it cannot show stale state of the current user's own comment. This distinction lets the system use cheap eventual consistency almost everywhere while routing just the write-adjacent reads to a fresh source. The result is a UI that feels strongly consistent at a fraction of the cost.

Step 5 — Make staleness visible when it is unavoidable

Some systems cannot avoid staleness and should not pretend otherwise. Showing “Updated 2 minutes ago” or a refresh button sets accurate expectations. A “pending” indicator on a post that has been written but not yet propagated is better than showing nothing. When the API is genuinely eventually consistent, the UI should communicate it — but only when the staleness is unavoidable, not as an excuse for a slow system.

The worst pattern

Serving stale data silently while the UI pretends it is fresh. This creates the duplicate-posting, double-clicking, missing-comment behaviour that motivates the whole problem. The user assumes the action failed and retries, which under at-least-once semantics creates duplicates or double charges. Every eventually consistent write endpoint should be idempotent, and every stale-read situation should be either invisible (via echo) or explicitly indicated.

Common Pitfall

Relying on the browser's HTTP cache or a CDN to hide staleness without considering cache-key correctness. A cached response with a per-user body served to another user is not a staleness problem — it is a data leak. Any response that varies by identity must not be cached under a shared key.

How do CRDTs achieve strong eventual consistency?

Short Answer

A CRDT (Conflict-free Replicated Data Type) is a data structure whose replicas can be updated independently and merged deterministically, without coordination, converging to the same state once all updates are exchanged. It provides strong eventual consistency — all correct replicas that have seen the same set of updates are identical — because the merge function is commutative, associative, and idempotent.

The mathematical foundation

A CRDT exploits properties of a join semilattice: a partially ordered set where every pair of elements has a least upper bound (the “join” or “merge”). If the merge operation has these properties, replica order does not matter:

  • Commutativity — merge(A, B) = merge(B, A). The order replicas communicate does not affect the outcome.
  • Associativity — merge(merge(A, B), C) = merge(A, merge(B, C)). Grouping of updates does not matter.
  • Idempotence — merge(A, A) = A. Receiving the same update twice has no effect, which handles duplicate delivery from at-least-once networks.

These three properties guarantee convergence regardless of message order, duplication, or delay. That is the whole trick: no coordination because the operation is well-defined as an unordered join.

Concrete example — the OR-Set

An OR-Set allows additions and removals without coordination. Each add tags the element with a unique ID. A remove operation removes only the tags the removing replica has actually observed — not later concurrent adds. So if Alice adds X and Bob concurrently removes X, the result is defined: Bob's remove did not observe Alice's add, so the add survives, and the final state contains X. This is the “add wins” semantics that users intuitively expect (you do not lose data because of a concurrent delete).

What CRDTs cost

  • Metadata size. CRDTs carry per-replica metadata. An OR-Set with 1M elements and 10 replicas may carry tens of MB of metadata. The space overhead is proportional to the number of replicas and operations.
  • Garbage collection of tombstones. Removals must be recorded (so later merges know the element was removed), and these tombstones accumulate. Collecting them requires causal stability — knowing that all replicas have seen the removal — which reintroduces coordination.
  • Limited invariants. CRDTs handle simple algebraic properties well (counters, sets, sequences) but cannot express arbitrary invariants like “balance ≥ 0” or “at most one appointment per slot.” Those require coordination.
  • Read overhead. Computing the current value often requires folding all operations, which costs CPU on every read unless materialised.

Where they are used

Collaborative editing (Yjs, Automerge, ShareDB) uses sequence CRDTs to merge concurrent text edits without operational transformation's transformation table explosion. Offline-first mobile applications use them to merge changes from disconnected clients. Distributed counters (views, likes) use G-Counters to avoid hot-row contention. Shopping carts use OR-Sets so concurrent add/remove does not lose items. The pattern is the same: the data has an obvious commutative semantics and the operations can proceed without coordination.

When CRDTs are the wrong tool

When the invariant is not algebraic. A bank balance cannot be a CRDT (debit on one replica, debit on another, both valid, result negative balance — the invariant must be checked globally). An inventory count cannot be a CRDT for the same reason. A seat booking cannot be a CRDT (two replicas both accept the booking). These require linearizable operations or explicit consensus. The mistake is thinking CRDTs make consistency free; they make a specific class of consistency free, and the rest still needs coordination.

Trade-off

CRDTs eliminate coordination at the cost of metadata and limited expressiveness. They are excellent for counters, sets, sequences, and collaborative editing; they are useless for financial invariants. Choose them when the merge semantics are genuinely commutative and the overhead is acceptable; otherwise use consensus.

How does the CAP theorem apply to multi-region deployments?

Short Answer

Multi-region deployments make the CAP trade-off continuous rather than rare, because the wide-area network between regions is significantly less reliable than a datacenter LAN. Every write and read must choose between a fast, local, potentially stale answer and a slow, cross-region, guaranteed-fresh answer. This is PACELC's “Else” branch in operation, all the time, at scale.

Why multi-region is different

Within a datacenter, network partitions are rare and latency is microseconds. Across regions, partitions happen regularly — BGP issues, undersea cable damage, regional cloud outages — and round-trip latency is 50–300 ms. The probability of a partition per unit time is much higher, and the cost of strong consistency (measured in latency) is much larger. Both dimensions of the CAP/PACELC trade-off are amplified.

The architectural patterns

PatternCAP behaviourLatencyUse case
Active-passive with async replication AP during partition; primary region can lose recent writes Low (local reads in primary); high for failover Cost-sensitive; tolerable RPO of seconds
Active-active with eventual reconciliation AP always; divergence reconciled later Low (local reads and writes) Global user base; UGC, feeds, carts
Active-active with last-writer-wins AP; data loss on conflict (silent overwrites) Low Counters, low-conflict data
Global consensus (Spanner, CockroachDB) CP during partition; minority region becomes unavailable for writes High — 100+ ms per commit Financial ledgers, inventory, compliance
Regional consistency with async global Strong within region; eventual across regions Low within region Most SaaS — users primarily interact within a region

The latency tax of global consistency

A globally linearizable write must contact a majority of replicas across regions. With replicas in three regions (US, EU, Asia), the commit latency is bounded below by the round-trip time to the second-fastest region — at least 80–150 ms in the best case, and often more. For a user-facing write that is expected to complete in 100 ms, this is unacceptable unless the workload genuinely requires it. This is why Spanner's ~100 ms cross-region commit latency is a real cost, not a marketing footnote.

Regional consistency as the pragmatic default

The pattern used by most large-scale systems: keep the user's data primarily in their region, enforce strong consistency within that region, and use asynchronous replication to other regions for disaster recovery and cross-region reads. A user in Europe reads and writes European replicas with low latency and strong consistency; the system asynchronously replicates to the US and Asia, where it may serve stale data to other users. When the user travels, they may see a slightly stale view, which is usually acceptable.

This is not a pure CAP classification — it is a hybrid. Within a region the system is CP; across regions it is AP with eventual consistency. The classification depends on which scope you are examining, which is why labelling a multi-region system with a single CAP letter is misleading.

The conflict resolution problem

Active-active across regions means concurrent writes to different replicas with no coordination. The system must have a conflict resolution policy:

  • Last-writer-wins — timestamp-based; simple, but silently discards data and depends on clock synchronisation (a subtle failure mode).
  • Application-defined merge — domain-specific logic to reconcile; correct but requires the application to understand conflicts.
  • CRDTs — commutative merges for algebraic data; no coordination, correct convergence, but limited to certain data types.
  • Escalation to user — surface the conflict for manual resolution; correct but high friction.

Each option is a design decision, and none is universally correct. The wrong choice produces silent data loss or user-visible contradictions.

Failure modes specific to multi-region

Beyond partitions: regional failures (a whole cloud region becoming unavailable), asymmetric network issues (one region cannot reach another but both can reach a third), and cross-region bandwidth saturation. A well-designed multi-region system has to tolerate each. The standard pattern is cell-based isolation — partition the system into self-contained cells so a failure in one does not cascade across regions — combined with explicit runbooks for failover and reconciliation.

Trade-off

Multi-region is not a single design; it is a family. The choice between global consensus (~100 ms per write), regional consistency with async replication (~5 ms per write, eventually consistent across regions), and active-active eventual (~5 ms per write, conflict resolution required) is a decision about latency, consistency, and data-loss tolerance. There is no universally correct answer — only a decision that must be made explicitly.

Interview Framing

Say: “I'll use regional strong consistency with async cross-region replication — users get low-latency consistent reads and writes in their own region, and we accept RPO of a few seconds across regions for disaster recovery.” That demonstrates you understand the multi-region trade-off as a concrete design choice, not an abstract one.
