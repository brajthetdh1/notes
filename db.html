Database Replication

Consistency, durability, topology, failover, and multi-region design.

▶ What is the difference between synchronous and asynchronous replication? What does each sacrifice? Core

Synchronous replication means the primary does not acknowledge a write to the client until at least one replica has confirmed receipt and persisted the change. The consequence is a zero Recovery Point Objective (RPO): if the primary fails and you promote that replica, no committed write is lost. The price is latency — every write requires an additional network round trip, and more importantly, availability is coupled to replica health. If the synchronous replica goes down, writes on the primary block entirely unless the system degrades to async.

Asynchronous replication means the primary writes to its own log, acknowledges the client immediately, and streams changes to replicas in the background. Write latency is low and the primary is never blocked by replica failure. The risk is replication lag: if the primary crashes before changes are streamed, the last few committed writes are lost. RPO is non-zero.

AspectSynchronousAsynchronous
RPOZero (no committed write lost)Non-zero (last writes may be lost)
Write latencyHigher (extra round trip)Lower
Write availabilityCoupled to replica healthIndependent of replica health
Typical useFinancial ledgers, inventoryAnalytics replicas, read scaling
Interview signal: Frame the choice as an RPO-vs-latency trade-off, not a binary preference. A strong answer names the workload ("for payments I accept the latency cost of synchronous") rather than reciting definitions.
▶ What is semi-synchronous replication? Core

Semi-synchronous replication is a middle ground: the primary waits for acknowledgment from one replica (not all of them) before acknowledging the client. This gives you durability against the loss of a single node — the write exists on at least two machines — while avoiding the latency cost of waiting for every replica.

MySQL's semi-sync plugin is the classic example. You configure how many replicas must acknowledge (usually one) and how long the primary waits before falling back to async. The fallback behaviour matters: if the designated replica is slow or down, the primary may time out and continue asynchronously, which silently reopens the data-loss window. Interviewers often probe this: "What happens if the semi-sync replica fails mid-operation?" The answer is that the primary degrades to async after a timeout, so you must monitor and alert on that degradation.

Use semi-sync when you want meaningful durability with tolerable latency — a common production default for transactional databases that cannot afford full synchronous fan-out but refuse to accept pure async data loss.

▶ What is replication lag, and how do you handle the read-your-writes problem? Core

Replication lag is the delay between a write being committed on the primary and its becoming visible on a replica. Under light load it is milliseconds; under heavy write load, a slow network, or a large batch operation it can stretch to seconds. Lag is inherent to asynchronous replication — the goal is to measure it accurately and hide its user-visible effects.

The read-your-writes anomaly is the classic symptom. A user updates their profile → the write goes to the primary → success is returned → the user's next request is routed to a lagging replica → the old profile is displayed. From the user's perspective, the update silently failed. This is one of the most common consistency bugs in read-scaled systems.

Mitigations, in increasing order of sophistication:

  • Sticky primary routing: route a user's own reads to the primary for a short window (e.g., 5 seconds) after any write. Simple, but coarse — it adds primary load and does not help across devices.
  • Read-your-writes token: the primary returns a logical timestamp or WAL LSN on write; the client passes it on subsequent reads; the router checks replica progress and falls back to the primary if the replica has not caught up.
  • Session pinning: keep the user's session on the same replica that has applied their writes, advancing the pin as lag is resolved.
Related anomalies: monotonic reads (data appears to move backwards across reads) is fixed by session stickiness; causality violations (seeing a reply before its parent post) are fixed by causal tokens or consistent-prefix reads.
▶ What are other replication lag anomalies beyond read-your-writes? Advanced

Beyond read-your-writes, two other anomalies appear when reads can hit different replicas with different lag:

  • Monotonic reads violation: a user refreshes and sees newer data, then refreshes again and sees older data because the second read hit a more-lagging replica. The fix is session stickiness — pin a user's reads to one replica (or a set) for the duration of their session, or track a per-user high-water mark and refuse to serve below it.
  • Causality violation: a user sees a comment before the post it replies to, or a message reply before the original, because the two records were written at different times and replicated in an order that hides the dependency. Fixes include causal consistency tokens (carry a vector clock with each record), consistent-prefix reads (ensure causally related data is ordered), or writing related records in the same partition so they replicate together.

These matter because users experience them as "the app is broken" or "data disappeared," which erodes trust far more than raw latency does. A senior answer names the anomaly, the user-visible symptom, and the mechanism that bounds it.

▶ What is a multi-master (active-active) replication topology, and when would you use it? Advanced

In multi-master replication, more than one node accepts writes, and changes are propagated between nodes. This is attractive because each region or node can accept writes locally — a user in Frankfurt writes to the Frankfurt node with local latency, instead of paying a cross-Atlantic round trip to a primary in Virginia.

The fundamental problem is write conflicts. If two users in two regions update the same record at the same time, both local commits succeed but they contradict each other. Replication will not resolve that automatically. Common strategies:

  • Last-write-wins (LWW): highest timestamp wins. Simple, but depends on clock synchronization and silently discards data — dangerous for anything beyond ephemeral state.
  • Vector clocks / version vectors: detect concurrent writes and surface conflicts to the application for explicit resolution.
  • CRDTs (Conflict-free Replicated Data Types): design data structures whose merge operation is deterministic and commutative (counters, sets, sequences), so concurrent updates always converge without application intervention.
  • Consensus-based strong consistency: systems like Spanner and CockroachDB use Paxos/Raft to serialize writes globally, eliminating most conflicts at the cost of higher write latency.

Use multi-master when write locality genuinely matters (globally distributed users, offline-capable clients) and when the data model can tolerate or resolve conflicts — not as a general default.

▶ What are the trade-offs of primary-replica vs multi-primary replication? Advanced

Primary-replica gives you a single write authority, which means a simple conflict model: there are no conflicting writes by construction. Reads scale out to replicas easily. The costs are (a) all writes funnel through one node, so write throughput is capped by that node's capacity and distant writers pay long round trips; (b) primary failure blocks writes until failover completes; and (c) failover under async replication can lose recent writes.

Multi-primary removes the write bottleneck and gives local write latency in every region. The costs are conflict resolution (complex application logic or CRDT design), higher operational complexity (topology management, loop prevention, schema-change coordination across nodes), and the risk of subtle divergence if conflict logic has bugs.

Write latencyDepends on distance to primaryLocal in every region

Most teams start with primary-replica and only move to multi-primary when write locality or write throughput becomes the measured bottleneck.

▶ What is a quorum in replication? Core

A quorum is the minimum number of replicas that must acknowledge an operation before it is considered successful. With N replicas, a write quorum W and a read quorum R such that W + R > N guarantees that every read overlaps with the most recent write — a strong-consistency property without requiring all replicas to participate.

Common configurations:

  • N=3, W=2, R=2 — tolerates one node failure for both reads and writes, while guaranteeing consistency.
  • N=3, W=3, R=1 — writes require all replicas (slow, intolerant of failure), reads are fast. Suited to write-rare, read-heavy workloads.
  • N=3, W=1, R=1 — low latency, eventual consistency; useful when staleness is acceptable.

Quorums are the foundation of systems like Cassandra, DynamoDB, and Riak, where consistency is tunable per operation. The trade-off is latency and availability versus freshness: higher quorums mean more nodes must respond, so a single slow node can stall the operation. Interviewers often follow up with "what happens if a write succeeds on W nodes but a node later fails?" — the answer is that read repair and hinted handoff or anti-entropy processes reconcile the gap once the node returns.

▶ Design a read routing strategy for a high-traffic web application that uses PostgreSQL with two read replicas. Design

Start with the constraint: writes must go to the primary, and reads should be spread across two replicas to reduce primary load — but you cannot blindly route all reads to replicas because of read-your-writes and lag anomalies.

A concrete architecture:

  • Write path: all INSERT/UPDATE/DELETE and transactions go to the primary. Use a separate connection pool per role so writes cannot accidentally land on a replica.
  • Read path: route reads to replicas using least-connections or round-robin, but exclude replicas that fail a health check. Health checks should include actual query probes, not just TCP pings.
  • Read-your-writes: after a write, return a logical LSN or timestamp to the client. On subsequent reads, the router checks each replica's applied LSN (available via pg_stat_replication or the replica's recovery position) and serves only from replicas that have caught up to the client's LSN; otherwise fall back to the primary. A simpler alternative is to pin the user's session to the primary for a short window after any write.
  • Analytics isolation: route heavy reporting or aggregation queries to a dedicated replica (or a separate analytics replica) so they cannot starve the latency-sensitive read pool.
  • Degradation: if both replicas are unhealthy, fail open to the primary rather than failing reads — availability over read scaling, with an alert so the team responds.

This design makes the consistency contract explicit: normal reads are eventually consistent, and a user's own reads are strongly consistent via LSN fallback. That is the kind of precision senior interviewers look for.

▶ What happens if the primary fails in primary-replica replication? What is the risk of automatic failover? Trap

If the primary fails, the system loses its write authority. Reads can continue from replicas (possibly stale), but no writes succeed until a new primary is appointed or the old one recovers. The failover process involves detecting the failure, choosing a replica to promote, reconfiguring clients and remaining replicas, and fencing the old primary if it returns.

The risks are:

  • Data loss under async replication: the promoted replica may be missing the last few committed writes. This is unavoidable without synchronous replication; the mitigation is to bound the lag and accept the RPO, or to use semi-sync.
  • Split-brain: if the old primary comes back and still believes it is the primary, both nodes accept writes and the data diverges. Fencing (STONITH, network isolation, or a quorum-based leader election) is mandatory. This is the risk most candidates miss.
  • False positives: a transient network partition or a slow node can be misdiagnosed as failure, triggering an unnecessary failover and its associated data loss. Detection should use multiple consecutive health-check failures and quorum agreement where possible.
  • Cascading client errors: connection pools must re-resolve the new primary quickly, or clients keep hammering the dead node.
Senior signal: Mention fencing and split-brain before the interviewer asks. Automatic failover without fencing is a data-corruption bug waiting to happen.
▶ How would you design replication for a multi-region application? Design

The design depends on two questions: where must writes be fast, and how much data loss can you tolerate on a regional failure?

  • Read locality: deploy at least one replica in each region so reads are served locally. Users in Europe read from the European replica; latency drops from a cross-ocean round trip to single-digit milliseconds.
  • Write strategy: the simplest model is a single primary region with asynchronous replication to other regions. Writes from other regions are routed to the primary, paying cross-region latency but keeping a simple consistency model. If write latency is unacceptable, use multi-primary per region with conflict resolution, or a consensus system (Spanner/CockroachDB) that provides strong consistency at the cost of higher write latency.
  • Disaster recovery: maintain an asynchronous replica in a geographically separate region with a bounded lag. On a regional outage, promote it. Accept the RPO implied by the lag; monitor it continuously.
  • Quorum across regions: with three regions (e.g., US, EU, APAC), a quorum of two regions can tolerate one regional failure while preserving consistency. Writes require acknowledgment from a majority, so latency is the round trip to the second region.
  • Failover routing: use global DNS or a traffic manager with health checks to steer users to the surviving region, and ensure clients reconnect to the new primary automatically.

The interview-winning move is to state the RPO/RTO targets first, then show that your topology meets them — rather than drawing regions and hoping the interviewer is satisfied.

▶ How do you measure and monitor replication health? Core

Effective monitoring goes beyond "is the replica up?" to "is it keeping up, and can it serve consistent reads?" The key metrics are:

  • Replication lag: the gap between the primary's write position and the replica's applied position, measured in bytes (WAL segments) or seconds. In PostgreSQL, pg_stat_replication exposes write_lag, flush_lag, and replay_lag; in MySQL, SHOW REPLICA STATUS gives position and time behind.
  • Replica apply rate: how fast the replica is applying changes relative to the primary's write rate. A shrinking rate indicates the replica is falling behind.
  • Replication slot / connection status: is the replication connection alive? Is a slot retaining WAL excessively and risking disk exhaustion on the primary?
  • Heartbeat latency: write a known timestamp to the primary and read it from the replica to measure true end-to-end lag.
Classic trap: in MySQL, Seconds_Behind_Master = 0 does not reliably mean zero lag. If the replica SQL thread is idle or stalled, the timestamp comparison can report zero while the replica is actually behind. Use an external heartbeat tool (e.g., pt-heartbeat) for accurate measurement.

Alert on sustained lag above a threshold, on replication connection drops, and on WAL/slot accumulation. Tie alerts to user impact: lag matters because it causes stale reads, so route monitoring thresholds to the consistency contract you've promised.

Database Sharding

Partitioning strategies, shard-key selection, hot keys, and resharding.

▶ What is database sharding, and what are the trade-offs between range, hash, and directory-based strategies? ShardingCore

Sharding horizontally partitions rows across independent database instances so that no single machine holds all the data. It scales write throughput and storage beyond a single node's ceiling, at the cost of cross-shard query complexity. The strategy determines the balance between even distribution, query flexibility, and operational overhead.

  • Range sharding assigns contiguous key ranges to each shard (e.g., user IDs 1–1M to shard A, 1M–2M to shard B). Range queries on the shard key are efficient, and data locality is natural. The danger is hot spots: if the key is monotonically increasing (timestamps, auto-increment IDs), every new write lands on the last shard while earlier shards idle.
  • Hash sharding computes hash(key) % N and assigns to a shard. Writes spread evenly and hot spots are rare. The cost is that range queries become scatter-gather — a query for "orders in the last 24 hours" must query every shard and merge results.
  • Directory-based sharding maintains a lookup service mapping keys to shards. It is the most flexible: you can move any key to any shard, and different keys can follow different strategies. The directory itself becomes a highly-available, low-latency dependency, and it must be cached aggressively.
Key constraint: cross-shard joins do not work natively. The data model must be designed for co-location — everything you join together should share the same shard key. A common design puts a user and all their related records (orders, messages, settings) on the same shard so per-user operations are single-shard.

The choice is workload-driven: read-heavy with range scans favors range; write-heavy with point lookups favors hash; complex migration or multi-strategy needs favor directory. Many production systems combine them — range-shard tenants, then hash within each tenant.

▶ When would you choose hash sharding over range sharding for a multi-tenant SaaS application? Sharding

Choose hash sharding when uniform load distribution across shards matters more than range-query flexibility on the shard key. In a multi-tenant SaaS application, tenants vary enormously in activity: a handful of enterprise tenants can generate more writes than thousands of small accounts combined. If you range-shard by tenant ID, a newly onboarded enterprise tenant may land on one shard and overwhelm it, while other shards sit idle.

Hashing the tenant ID spreads tenants probabilistically across shards, so no single shard receives a disproportionate share. The trade-off is that you lose range queries on tenant ID — but in a typical SaaS app, the dominant query is "fetch data for tenant X," which is a point lookup and works perfectly with hashing. Cross-tenant range queries (e.g., "all tenants created last month") are rare operational queries and can be served by a separate analytics replica or data warehouse.

Must-avoid mistake: never shard on a timestamp or auto-increment ID in a write-heavy system. All writes funnel to the shard holding the latest range, defeating the purpose of sharding and creating a guaranteed hot spot.

A hybrid approach is common: range-shard large tenants onto dedicated shards (so their heavy load is isolated and their range queries are fast), and hash-shard the long tail of small tenants for even distribution. This gives you the best of both strategies where each matters.

▶ Explain the difference between sharding and partitioning. ShardingCore

Partitioning splits data into smaller pieces within a single database instance. The database engine manages the partitions: queries are routed to the relevant partition, indexes are maintained per partition, and the whole thing behaves like one logical database. Partitioning improves manageability (drop an old partition instead of deleting rows), query performance (prune irrelevant partitions), and maintenance (vacuum/optimize one partition at a time). It does not scale write throughput beyond what one machine can handle.

Sharding distributes data across multiple independent database instances. Each shard is a separate database with its own CPU, memory, disk, and connection limits. Sharding scales write throughput and storage horizontally, but introduces cross-shard query complexity, distributed transactions, resharding operations, and a routing layer. In practice, sharding is a form of horizontal partitioning across nodes.

The relationship: partitioning is a single-node concern; sharding is a distributed-systems concern. You can use both together — partition each shard's tables by time for manageability, while sharding by tenant for scale. A strong answer notes that you should exhaust partitioning, indexes, and read replicas before sharding, because sharding is a one-way complexity increase.

▶ What does a good shard key look like? Sharding

A good shard key has four properties:

  • High cardinality: many distinct values, so data can be spread finely. A boolean flag is a terrible shard key; a user ID is excellent.
  • Even access distribution: no subset of keys receives disproportionate traffic. A "celebrity" user ID that receives millions of reads creates a hot shard even if data volume is balanced.
  • Query alignment: the most common queries should hit a single shard. If 90% of queries are "get user X's data," sharding on user ID makes them single-shard point lookups.
  • Stability: the key should not change over an entity's lifetime. A mutable key forces re-sharding when it changes.

Common mistakes: sharding on a low-cardinality field (country, status), sharding on a timestamp or auto-increment ID (monotonic → write hot spot on the last shard), and sharding on a key that does not align with the access pattern (shard on order ID when every query fetches by user ID, forcing scatter-gather).

Design principle: choose the shard key from the access pattern, not from the entity's primary key. The shard key should be whichever field appears in the WHERE clause of your most frequent and most latency-sensitive queries.
▶ How do you handle a "celebrity" or hot-key problem where one shard receives disproportionate traffic? ShardingTrap

The celebrity problem: one shard key (a famous user, a viral post, a flash-sale SKU) receives orders of magnitude more traffic than its peers. Data volume may be balanced, but request volume is not — and the shard holding that key saturates while others idle.

Detection first: per-shard latency, QPS, and CPU metrics will show the imbalance. Slow-query logs identify the offending key.

Mitigations, in order of effort:

  • Cache aggressively: serve the hot key's reads from a distributed cache (Redis) or CDN so the shard sees a fraction of the traffic. This is usually the first and cheapest fix.
  • Isolate the hot key: move it to a dedicated shard via a directory entry, so its load no longer affects other keys. This is a targeted fix for known celebrities.
  • Split the hot shard: if the shard holds many hot keys, split it into smaller shards (range split) to spread load.
  • Read replicas for the hot shard: if the problem is read-heavy, add replicas and load-balance reads across them.
  • Salting: for write-heavy hot keys, append a random suffix to spread writes across multiple shard keys, then aggregate reads. This complicates read logic, so use it only when writes are the bottleneck.
  • Rate limiting / load shedding: a short-term defensive measure at the API layer to protect the shard from cascading failure.

The senior signal is naming detection before mitigation, and preferring cache isolation over structural resharding because it is reversible and fast.

▶ How do you handle resharding — adding a new shard — without downtime? ShardingAdvanced

Resharding difficulty depends on the strategy:

  • Hash sharding with modulo: the worst case. Changing N in hash(key) % N remaps almost every key, so nearly all data must move. Avoid naive modulo hashing if you expect to grow; use consistent hashing instead.
  • Consistent hashing: maps keys and nodes onto a ring. Adding a node only remaps the keys between that node and its predecessor — a fraction of the total. This is why consistent hashing is the standard for distributed caches and sharded stores.
  • Directory-based sharding: the most graceful. Update the lookup table entries for the keys to move, migrate data in the background, then flip the directory entry. The application follows the directory, so no code change is needed.
  • Range sharding: split a range and migrate half the data. Use an online migration: enable dual-writes to both old and new shards, backfill historical data, verify consistency, then cut reads over to the new shard and disable dual-writes.

The no-downtime pattern for any strategy is dual-write → backfill → verify → cutover → cleanup. During the migration window, writes go to both locations, a background job copies existing rows, a reconciliation job verifies checksums, and traffic is switched atomically (via the directory or a feature flag). Always keep the old shard readable until verification passes, and have a rollback path.

Senior signal: Mention that resharding is an operational problem as much as a data problem — throttling migration throughput so you don't saturate the network or disk, and monitoring lag throughout.
▶ Design the sharding strategy for an e-commerce order system that needs to support both "get orders for user X" and "get all orders in the last 24 hours." ShardingDesign

These two access patterns conflict directly. "Get orders for user X" is a point lookup scoped to one user — it wants the shard key to be user ID. "Get all orders in the last 24 hours" is a time-range scan across all users — it wants the shard key to be a timestamp. You cannot shard on both without a secondary structure.

Resolution: shard the primary operational table by user ID, because the per-user query is the high-frequency, latency-sensitive path (order history, checkout, support). Co-locate each user's orders on one shard so the lookup is single-shard. This handles the operational workload well.

For the time-range query, do not run it against the sharded primary. Instead, maintain a secondary copy in a time-ordered structure:

  • Write an order event to a message queue (Kafka) on every order creation.
  • A stream processor consumes events and writes to a time-partitioned store — either a partitioned table in an analytics database (e.g., ClickHouse, BigQuery) or a time-partitioned table in a separate database instance.
  • The "last 24 hours" query runs against this time-ordered copy, which can prune to the relevant time partitions and scan efficiently.

This is the classic CQRS pattern: the operational store is optimized for per-user transactions; a read-optimized projection serves analytics and time-range queries. The trade-off is eventual consistency on the analytics path (acceptable for reporting) and the operational cost of maintaining the secondary copy. A senior answer names this explicitly rather than pretending a single shard key can serve both patterns.

▶ What is consistent hashing, and why is it used in sharding? Sharding

Consistent hashing maps both data keys and nodes onto a circular hash space (a "ring"). Each key is assigned to the first node encountered clockwise from its hash position. When a node is added or removed, only the keys between that node and its predecessor need to move — a fraction of the total, rather than nearly all keys as with hash(key) % N.

The problem it solves: with modulo hashing, changing N remaps almost every key, forcing a massive data migration and cache invalidation storm. With consistent hashing, adding a node moves only 1/(N+1) of the keys, and removing a node moves only that node's keys to its successor.

Virtual nodes are the refinement that makes it practical. A single point per physical node on the ring produces uneven distribution — by chance, one node may own a large arc and receive disproportionate load. Virtual nodes represent each physical node as many points on the ring (e.g., 100–200 per node). This smooths the distribution statistically and also means that when a node fails, its load is spread across many other nodes rather than dumped on a single successor.

Consistent hashing is used in distributed caches (Memcached clients), distributed databases (Cassandra, DynamoDB), and load balancers with session affinity. The interview signal is explaining why virtual nodes are necessary — not just that they exist — and tying it to the load-distribution and failure-handling properties it provides.

▶ How do you avoid hot partitions and skew? ShardingAdvanced

Hot partitions arise from two distinct causes: data skew (one partition holds far more rows) and access skew (one partition receives far more requests). The fixes differ.

  • Choose a high-cardinality, evenly-distributed shard key that aligns with the access pattern. Avoid low-cardinality fields and monotonic keys.
  • Composite keys: combine the natural key with a high-cardinality suffix — e.g., user_id + bucket where bucket is a random or hash-derived integer. This spreads a hot key across multiple partitions while keeping reads routable.
  • Salting: append a random suffix to the shard key to spread writes. Reads must then fan out to all suffixes and aggregate — a write-scaling technique with a read cost.
  • Directory-based routing: detect hot keys and move them to dedicated shards via the lookup table, isolating their load.
  • Read replicas: if the skew is read-heavy, add replicas for the hot partition and load-balance reads across them.
  • Continuous monitoring: per-partition QPS, latency, and CPU. Skew is often dynamic — a new viral item can create a hot partition overnight — so detection must be continuous, with automated alerts or auto-splitting.

The wrong fix is easy to spot: increasing the shard count does not help if the skew comes from one key's access pattern. A senior answer distinguishes data skew from access skew and chooses the mechanism that addresses the actual cause.

System Design in Context

Scalability, consistency, failure handling, and classic design problems.

▶ How do I decide when to split a monolith into services? Design

Split when the pain is real and measurable, not because microservices are fashionable. The signals:

  • Independent scaling needs: one component (e.g., image processing) needs 10x the CPU of the rest. Scaling the whole monolith wastes resources; isolating that component lets you scale it independently.
  • Different release cadences: one team needs to deploy daily while another ships quarterly. A monolith forces shared release trains; services give independent deployability.
  • Team autonomy: when multiple teams contend on the same codebase and deployment pipeline, boundaries reduce coordination cost.
  • Clear bounded contexts: domains with genuinely separable data and logic (billing vs. catalog vs. identity) are natural service boundaries.
  • Technology constraints: a component needs a different language, database, or runtime.

The counter-argument: microservices add network partitions, distributed transactions, service discovery, observability complexity, and operational overhead. A modular monolith with clear internal boundaries captures most of the maintainability benefit at a fraction of the operational cost. The pragmatic path is to start modular, extract services when the organizational or scaling pain is real, and always split along boundaries you can draw cleanly. A senior answer explains the trade-off rather than declaring one architecture superior.

▶ What are the real trade-offs between vertical and horizontal scaling? Design

Vertical scaling (bigger machine) is operationally simple: no code changes, no distributed coordination, no data partitioning. It is the right first move for most systems because it buys time cheaply. But it has a hard ceiling — there is a maximum machine size — and it creates a single point of failure and a maintenance window for upgrades. Cost grows super-linearly: a 2x machine often costs more than 2x.

Horizontal scaling (more machines) is theoretically unbounded and improves availability through redundancy. It is the only way to scale beyond one machine's capacity. The cost is complexity: services must be stateless (or externalize state), data must be partitioned or replicated, and the system must tolerate partial failure and network partitions.

Effort to implementLowHigh
CeilingHard (max machine size)Effectively unbounded
AvailabilitySingle point of failureRedundancy built in

The pragmatic strategy is scale up first, then out — vertical scaling delays the complexity of distribution until you actually need it, and many systems never outgrow a large machine plus replicas. When you do scale out, design for statelessness and partitionable data from the beginning so the transition is possible.

▶ How do I design for backpressure in a high-traffic system? DesignAdvanced

Backpressure is the mechanism by which a saturated downstream component signals upstream producers to slow down or stop. Without it, queues grow unbounded, memory exhausts, latency spikes catastrophically, and the system collapses — a classic cascading failure.

Design techniques:

  • Bounded queues: never use unbounded in-memory queues. A bounded queue forces a decision when full — block the producer, drop the request, or reject it with a clear error.
  • Rate limiting: token-bucket or sliding-window limiters at the edge cap the arrival rate to what downstream can handle.
  • Load shedding: when queue depth or latency exceeds a threshold, reject a fraction of requests early (HTTP 429/503) rather than accepting work that will time out. Shedding low-priority traffic first preserves the experience for critical requests.
  • Circuit breakers: when a dependency fails repeatedly, open the circuit and fail fast instead of piling up requests that will never succeed. Periodically half-open to test recovery.
  • Bulkheads: isolate resource pools (threads, connections) per dependency so a slow dependency cannot exhaust resources needed by healthy ones.
  • Asynchronous processing with bounded queues: absorb bursts in a durable queue with a bounded consumer concurrency, and let the queue drain at the downstream's pace.

The senior signal: explain what happens when a queue fills — the answer must be a deliberate policy (reject, shed, degrade), not "it grows." Backpressure without a rejection policy is just unbounded buffering in disguise.

▶ How do I protect downstream services from traffic spikes? Design

Traffic spikes come from organic virality, flash sales, retries during an outage, or abuse. Protection is layered:

  • Edge rate limiting: cap requests per user/IP/API key at the CDN or API gateway. This absorbs the spike before it reaches application servers.
  • Queue-based load leveling: put a durable queue between the ingress and the processing tier. The queue absorbs the burst; workers process at a controlled rate. This decouples arrival rate from processing rate.
  • Autoscaling with buffers: scale out based on queue depth or request rate, with headroom so scaling completes before saturation. Predictive scaling for known events (sales, launches).
  • Load shedding: when capacity is genuinely exhausted, reject excess requests with a fast 503 and a Retry-After header, rather than queueing them to time out.
  • Circuit breakers and timeouts: prevent a slow dependency from turning a spike into a cascading failure. Set aggressive timeouts and retry budgets.
  • Caching: serve hot data from a CDN or distributed cache to reduce origin load dramatically.
  • Graceful degradation: disable non-essential features (recommendations, personalization) under load to preserve core functionality.

The key insight: spikes are a capacity mismatch problem. The solution is either to reduce demand (rate limit, cache, shed) or increase supply (autoscale, queue), and usually both. A senior answer names the layer where each mechanism belongs.

▶ How do I handle idempotency for write APIs? DesignAdvanced

Idempotency means that repeating the same request produces the same result as executing it once. It is critical for payment, order, and provisioning APIs where a timeout-then-retry could otherwise charge twice or create duplicates.

The standard pattern:

  • The client generates a unique idempotency key per logical operation (e.g., a UUID) and sends it in a header.
  • The server, before executing, checks a dedicated store (database table or Redis) for that key.
  • If the key exists and the operation completed, return the stored response — do not re-execute.
  • If the key exists but the operation is in progress, return a conflict or wait, depending on the API contract.
  • If the key does not exist, record it as "in progress" atomically, execute the operation, store the result alongside the key, and return.

Implementation details that matter:

  • Atomicity: the check-and-insert must be atomic (unique constraint on the key, or a Redis SET NX) to prevent two concurrent requests from both executing.
  • Scoping: keys should be scoped per user or API client to prevent cross-tenant collisions.
  • Expiry: idempotency records should expire (e.g., 24 hours) to bound storage; the client must generate a new key for a genuinely new operation.
  • Response replay: store the status code and body so retries receive the exact same response, not a re-executed one.
Senior signal: Mention that idempotency must survive crashes — the "in progress" record must be written before the side effect, so a crash mid-operation is detected on retry rather than silently re-executed.
▶ Explain the CAP theorem and its practical implications. DesignAdvanced

CAP states that in a distributed system experiencing a network partition (P), you must choose between consistency (C) and availability (A). The common misreading is "pick two of three" — but partition tolerance is not optional in any real distributed system, because networks partition. The real choice is: when a partition occurs, do you sacrifice consistency or availability?

  • CP systems (e.g., consensus-based databases) refuse writes or reads on the minority side of a partition to preserve consistency. Writes fail during the partition, but data is never wrong.
  • AP systems (e.g., Dynamo-style stores) continue serving both sides, accepting that the two sides may diverge. Consistency is restored later via conflict resolution. Users get a response, but it may be stale or conflicting.

Practical implications: the decision framework is to ask "what does the user experience if they see stale or inconsistent data for a short period?" If the answer is "nothing catastrophic," AP is acceptable. If the answer is "financial loss or legal liability," you need CP, and you must design for write unavailability during partitions.

Nuance: CAP is binary only during a partition. In normal operation you can tune consistency continuously — e.g., quorum reads/writes in Cassandra, or read-your-writes in a system that is otherwise eventually consistent. A senior answer explains that CAP is about failure-mode behaviour, and that PACELC extends it: even without partitions, there is a latency-vs-consistency trade-off.
▶ When do I accept eventual consistency vs strict consistency? Design

Accept eventual consistency when temporary staleness is tolerable — the user experience does not break and no business rule is violated if a read returns slightly old data. Typical candidates: social feeds, view counts, recommendations, search indexes, analytics dashboards, and profile data in systems where the user is not immediately reading their own write.

Demand strict consistency when incorrect data causes direct harm or a violated invariant: account balances, inventory counts (overselling), payment status, permission checks, and anything with legal or financial liability. In these domains, serving a stale read is equivalent to serving a wrong answer, and the cost of the CP write-unavailability trade-off is justified.

The nuance most candidates miss: consistency is per-operation, not per-system. A single application can use eventual consistency for the newsfeed and strict consistency for the wallet. The design question is not "which database" but "which operations need which guarantee." A common pattern is session consistency — the user always sees their own writes (read-your-writes) while other users' views of their data converge eventually. This captures most of the user-perceived correctness at much lower cost than global strong consistency.

Interview-winning move: state the consistency contract explicitly for each data type, and show how the system enforces it (quorums, sticky sessions, LSN fallback, or synchronous replication for the critical path only).

▶ How do I implement distributed transactions without 2PC pain? DesignAdvanced

Two-phase commit (2PC) is blocking, fragile, and couples participant availability to a coordinator. The modern alternative is the Saga pattern: break the global transaction into a sequence of local transactions, each paired with a compensating action that undoes it if a later step fails. For example, an order flow: reserve inventory → charge payment → create shipment. If shipment creation fails, compensate by refunding payment and releasing inventory.

Reliability is the hard part. Two patterns make Sagas robust:

  • Outbox pattern: write the business change and the event to an outbox table in the same local transaction. A separate relay process publishes the outbox rows to the message broker. This guarantees "at least once" delivery without a distributed transaction, because the local transaction is atomic.
  • Inbox pattern: consumers record processed message IDs in an inbox table within their local transaction, making consumption idempotent and preventing duplicate effects on retry.

The trade-off: Sagas are eventually consistent and expose intermediate states to the outside world (a payment may be charged before the order is confirmed). Compensations are business-level undo operations, not database rollbacks — refunds have their own latency and failure modes. Design the state machine so intermediate states are visible and recoverable, and ensure every step is idempotent so retries are safe.

A senior answer names the failure mode: "if the compensation itself fails, we need a dead-letter queue and manual reconciliation" — rather than pretending Sagas are a complete replacement for transactions.

▶ Explain the difference between 2PC, Saga, and TCC. DesignAdvanced

All three coordinate multi-service transactions, but with different consistency and failure models.

  • 2PC (Two-Phase Commit): a coordinator asks all participants to prepare (lock resources, verify feasibility), then commit if all prepare successfully. It provides atomicity — strong consistency — but is blocking: participants hold locks between phases, and coordinator failure can leave participants stuck. It does not scale well across many services or regions.
  • Saga: a sequence of local transactions with compensating actions. Non-blocking, eventually consistent, and scalable. The application must design compensations and tolerate intermediate states. Failure handling is business logic, not protocol magic.
  • TCC (Try-Confirm/Cancel): a structured Saga variant with explicit phases: Try reserves resources (e.g., hold inventory), Confirm finalizes, Cancel releases. It gives more control over intermediate state than a plain Saga — resources are reserved but not committed until Confirm — at the cost of implementing three operations per service instead of two.

▶ Design a distributed counter that can handle high write throughput. DesignAdvanced

A single counter row in a database is a write bottleneck: every increment locks the row and serializes. At high throughput, this saturates the database. The solution is to shard the counter.

  • Sharded counters: maintain N counter instances, each storing a partial count. An increment writes to one shard, chosen by a random or hash-based distribution. Writes scale linearly with N.
  • Reads aggregate: a read sums the partial counts across all N shards. This is eventually consistent and costs N reads, but reads are usually far less frequent than writes for counters (views, likes, metrics).
  • Time-bucketed shards: for extremely hot counters, shard by time window (e.g., per minute) and aggregate over the windows for a range query. Old buckets can be compacted into hourly/daily totals, bounding the number of shards to aggregate.
  • In-memory + periodic flush: accumulate counts in memory (Redis INCR) and flush to durable storage periodically. Redis INCR is atomic and fast; the trade-off is durability — a crash loses unflushed increments unless you use AOF persistence.
  • CRDT counters: a G-Counter (grow-only counter) is a CRDT where each node maintains its own count and reads sum them. This is the principled version of sharded counters — merge is commutative, so nodes can reconcile without coordination.

The trade-off to state explicitly: write scalability comes at the cost of read-time aggregation and eventual consistency. For a "likes" counter this is fine; for a financial counter, you would accept lower throughput and use a strongly-consistent design instead.

▶ How do I model data differently for OLTP vs OLAP workloads? Design

OLTP (online transaction processing) handles high-volume short transactions: insert an order, update a profile, fetch a record. The data model is normalized to eliminate redundancy and update anomalies. Storage is row-oriented (reading a row reads all its columns efficiently). Indexes are tuned for point lookups and short range scans. The priority is write throughput, low-latency reads, and strong consistency.

OLAP (online analytical processing) handles large scans and aggregations: "revenue by region per month," "funnel conversion." The data model is denormalized (star schema with fact and dimension tables) to avoid expensive joins. Storage is column-oriented (reading a column reads only that column, and compression is highly effective). The priority is scan throughput and aggregation speed, not per-row write latency.

In practice, run them on separate systems: OLTP in PostgreSQL/MySQL, OLAP in ClickHouse/BigQuery/Snowflake, with data flowing via CDC (Change Data Capture) or batch ETL. Running analytics against the OLTP primary is a classic anti-pattern — a single large aggregation can saturate the database and degrade user-facing latency. ▶ How do I decide between SQL, NoSQL, and search engines? Design

The choice follows from the access pattern and consistency requirement, not from a general ranking of technologies.

  • SQL (relational): strong consistency, ACID transactions, complex joins, mature tooling and ecosystem. It is the default for transactional data with clear relationships. It scales vertically very far and horizontally via read replicas and sharding. Choose SQL unless you have a specific reason not to — most systems are not large enough to outgrow it.
  • NoSQL: a family, not a single thing. Key-value stores (Redis, DynamoDB) for simple high-throughput lookups; document stores (MongoDB) for flexible, evolving schemas and nested data; wide-column stores (Cassandra, HBase) for high write throughput and time-series patterns; graph databases (Neo4j) for highly connected data. Choose NoSQL when the schema is rapidly evolving, the scale exceeds a single SQL node, or the access pattern is a simple high-throughput key lookup.
  • Search engines (Elasticsearch, OpenSearch): full-text search, relevance ranking, fuzzy matching, faceted aggregation. Choose when search is a primary product feature — not as a general-purpose database and not as a reporting afterthought. They are usually a secondary index fed from the primary data store.
Interview signal: Name the access pattern and consistency requirement first, then the technology. "We need single-digit-millisecond lookups by session token at 100k QPS with no joins — that points to a key-value store" is far stronger than "I'd use NoSQL because it scales."
▶ How do I shard data — by user, tenant, region, or something else? ShardingDesign

The shard key must come from the dominant access pattern. Three common choices:

  • By user: the right choice when most queries are scoped to a single user ("get my orders," "my messages," "my profile"). Co-locates everything belonging to a user on one shard, making per-user operations single-shard. Risk: celebrity/hot users create hot shards.
  • By tenant: for multi-tenant SaaS, sharding on tenant ID isolates each customer's data. Small tenants can be hash-distributed for even load; large tenants can be range-isolated onto dedicated shards. Risk: a single massive tenant dominates one shard unless isolated.
  • By region: when data is naturally geo-partitioned and latency requirements differ by region, sharding by region puts data close to its users and simplifies data-residency compliance (GDPR). Risk: cross-region queries become expensive, and regions can be unbalanced in size.

For mixed workloads, combine strategies. A common pattern: range-shard by region or tenant tier, then hash within each range for even distribution. Another: use a directory that routes different query types to different shard sets — operational queries to a user-sharded store, analytics to a time-partitioned store (CQRS).

The senior signal: explain the trade-off in terms of the dominant query. "If every query is per-user, sharding by user makes them single-shard; sharding by region would force a scatter-gather for the common case, so region is the wrong key here even though it sounds operationally cleaner."

▶ How do I design pagination for massive datasets efficiently? DesignAdvanced

Offset pagination (OFFSET n LIMIT m) is the intuitive approach and the wrong one at scale. The database must scan and discard n rows before returning m, so page 10,000 is dramatically slower than page 1. It also produces inconsistent results when rows are inserted or deleted between requests — rows can shift across pages, appearing twice or disappearing.

Cursor-based (keyset) pagination solves both problems. Instead of an offset, the client passes the last seen sort key:

-- First page
SELECT * FROM orders ORDER BY created_at, id LIMIT 20;

-- Next page (cursor = last row's created_at, id)
SELECT * FROM orders
WHERE (created_at, id) > ('2024-05-01T12:00:00Z', 1042)
ORDER BY created_at, id LIMIT 20;

This uses an index on (created_at, id) and seeks directly to the cursor position — O(log n) rather than O(n). It is stable under inserts and deletes because the cursor is anchored to a row's value, not a position. The limitation is that you cannot jump to an arbitrary page number (no "page 50" link) — which is acceptable for infinite-scroll and feed UIs, the dominant use case.

Implementation details: the cursor should be opaque (base64-encoded, signed) so clients cannot manipulate it; the sort key must be unique or composite with a tiebreaker (e.g., created_at, id) to avoid skipping rows with equal timestamps; and the query must have an index matching the sort order, or it degrades to a full scan.

Senior signal: Mention that offset pagination is also a security/performance concern — a scraper can request OFFSET 100000000 and force the database to do enormous work, a cheap denial-of-service vector.
▶ Design a URL Shortener (TinyURL). Design

Requirements: given a long URL, return a short URL; given a short code, redirect to the original. Read-heavy (redirects vastly outnumber creations), low latency, high availability.

Key challenge — unique ID generation at scale: you cannot use an auto-increment database sequence because it is a single bottleneck and leaks the creation order. Options:

  • Range-based key allocation: a central service allocates blocks of IDs to each application server (server A gets 1–10,000, server B gets 10,001–20,000). Each server generates short codes locally by base62-encoding its IDs, with no coordination per request. This is the classic scalable solution.
  • Hash-based: hash the long URL and take the first 7 characters. Collisions must be detected and resolved (re-hash with a salt), which adds write-path complexity.
  • Snowflake-style IDs: timestamp + machine ID + sequence, base62-encoded. Unique without coordination, but longer codes.

Storage: a key-value store mapping short_code → long_url, sharded by a hash of the short code for even distribution and horizontal scale. Replicate each shard for read availability.

Read path: redirects are pure point lookups — cache hot codes in Redis (or a CDN edge cache with a short TTL) so the database sees a fraction of the traffic. A 301 (permanent) redirect lets browsers cache, reducing load further, at the cost of losing analytics; a 302 (temporary) preserves analytics.

Scale estimates to state: if you shorten 100M URLs/day and serve 10B redirects/day, the read-to-write ratio is 100:1 — optimize and cache the read path aggressively. Sharding and replication make the storage tier horizontally scalable; the key-generation service removes the write bottleneck.

▶ Design a Rate Limiter for APIs. Design

Requirements: limit requests per user/IP/API key over a time window (e.g., 100 requests/minute), with low latency and correctness under concurrency.

Algorithms:

  • Fixed window: count requests per minute, reset at the boundary. Simple but allows a burst at the boundary (200 requests in a 2-second span across two windows).
  • Sliding window log: store timestamps of each request and count those within the window. Accurate but memory-heavy at scale.
  • Sliding window counter: interpolate between the current and previous fixed windows. Approximate but memory-efficient — the standard production choice.
  • Token bucket: a bucket refills at a steady rate; each request consumes a token. Allows controlled bursts and is easy to implement atomically in Redis.

Storage and distribution: counters live in a distributed cache (Redis) with atomic operations — INCR plus EXPIRE, or a Lua script for token-bucket atomicity. Shard counters by user ID or API-key hash so no single Redis node is a bottleneck. Replicate for availability.

Failure mode — the critical design decision: if the rate-limiter store is unavailable, do you fail open (allow traffic) or fail closed (reject)? Fail-open preserves availability but removes protection; fail-closed preserves protection but can take down the API. For most APIs, fail-open with aggressive alerting is the right choice — the limiter is a protection mechanism, not a correctness requirement.

Placement: enforce at the API gateway or edge so abusive traffic never reaches application servers. Return 429 Too Many Requests with Retry-After and rate-limit headers (X-RateLimit-Remaining) so clients can back off gracefully.

▶ Design a social media news feed. Design

Requirements: show a user the recent posts from accounts they follow, with low latency, at massive read scale.

The core tension — fan-out on write vs fan-out on read:

  • Fan-out on write (push): when a user posts, insert the post ID into the feed cache of every follower. Reads are trivial — fetch the precomputed feed. But a celebrity with 50M followers triggers 50M writes per post, which is infeasible.
  • Fan-out on read (pull): when a user opens their feed, fetch recent posts from everyone they follow and merge. Writes are trivial, but reads are expensive and scale poorly for users who follow thousands of accounts.

The hybrid (standard solution): fan-out on write for normal users, fan-out on read for celebrities. When a normal user posts, push to followers' feed caches. When a celebrity posts, do not push — instead, merge their recent posts at read time. This bounds write amplification while keeping reads fast for the common case.

Storage: feed caches are per-user, sharded by user ID, stored in Redis (as a list of post IDs) with a bounded length (e.g., last 500 entries) and a TTL. Post content is stored separately, sharded by post ID, and fetched on hydration. The social graph is its own sharded store, often cached.

Read path: fetch the user's cached feed IDs → merge in celebrity posts from the read-time path → hydrate post content (cache-first) → rank/filter → return. Replication of feed and graph stores provides read availability. The senior signal is naming the celebrity case explicitly and explaining the hybrid fan-out trade-off rather than drawing a single pipeline.

▶ Design a distributed queue like RabbitMQ/Kafka. Design

Requirements: durable message storage, at-least-once delivery, horizontal scale, and consumer groups that process messages in parallel.

Partitioning: a topic is split into partitions. Each message is assigned to a partition by its key (hash of the key, or round-robin if no key). Ordering is guaranteed within a partition, not across partitions — this is the fundamental constraint. To preserve per-user ordering, key by user ID so all of a user's messages land in the same partition.

Consumer groups: each partition is assigned to exactly one consumer within a group, so consumers process partitions in parallel without duplicate consumption within the group. Rebalancing redistributes partitions when consumers join or leave.

Replication: each partition is replicated across brokers (leader + followers). Producers write to the leader; followers replicate. A write is acknowledged when the configured quorum (e.g., acks=all for durability) has persisted it. If the leader fails, a follower is promoted — the same failover and split-brain concerns as database replication apply.

Durability: messages are appended to a commit log on disk, which provides sequential-write throughput far higher than random writes. Retention is time- or size-based; consumers track their offset, enabling replay.

Delivery semantics: at-least-once is the default — a consumer that crashes after processing but before committing its offset will re-consume. Exactly-once requires idempotent consumers (dedupe by message ID) or transactional offset commits. A senior answer states that at-least-once plus idempotent consumers is the practical choice; exactly-once is achievable but costly.

Backpressure: if consumers lag, the queue grows. Monitor consumer lag and scale consumers or shed production rather than letting the log grow unbounded past retention.

▶ Design a ride-sharing service (Uber/Lyft). Design

Requirements: match riders to nearby drivers in real time, track driver locations, and compute pricing — all with low latency and high availability across a geographic area.

Geo-sharding: the world is partitioned into cells using a spatial index — geohash, Google S2, or Uber's H3. Driver locations are stored in a geo-indexed store, sharded by cell. When a rider requests a ride, the system queries the rider's cell and neighboring cells for available drivers. This is the core design decision: proximity queries require spatial partitioning, not a hash of user ID.

Location tracking: drivers send location updates every few seconds via a persistent connection (WebSocket). Updates are written to an in-memory store (Redis) keyed by cell, with a TTL so stale drivers drop out automatically. The write volume is enormous — millions of drivers updating every few seconds — so the in-memory store is sharded by cell and replicated for availability.

Matching: the matcher scores nearby drivers by distance, rating, and availability, then sends a ride offer with a timeout. Drivers accept or decline; declined offers move to the next candidate. This is a distributed matching problem — concurrency control ensures a driver is not offered to two riders simultaneously (a lock or atomic claim on the driver).

Pricing: a separate service computes surge multipliers from local supply/demand per cell. It reads aggregate counts, not individual trips, and is eventually consistent.

Failure handling: if a cell's store is unavailable, fall back to neighboring cells or degrade to a wider search. Regional isolation means a failure in one city does not affect others. The senior signal is naming the spatial partitioning choice and the atomic driver-claim problem.

▶ Design a video streaming service (Netflix/YouTube). Design

Requirements: upload, transcode, store, and deliver video to millions of concurrent viewers with low startup latency and adaptive quality.

Upload and transcoding: a raw upload is stored in object storage (S3). A transcode pipeline — a distributed task queue with worker fleet — converts it into multiple resolutions and bitrates (an adaptive bitrate ladder: 240p through 4K). Transcode jobs are sharded by video ID and run in parallel per segment (chunked encoding). The output is segmented into small chunks (2–10 seconds) with manifests (HLS/DASH) describing the available streams.

Delivery — CDN is the core: video bytes are served from CDN edge nodes, never from origin. The origin (object storage) only serves cache misses. Popular videos are effectively served entirely from edge caches; long-tail videos fall back to origin. This is what makes streaming economically viable — the origin sees a tiny fraction of total bytes.

Adaptive bitrate (ABR): the player measures bandwidth and buffer health and switches between bitrate chunks dynamically. This is why the manifest lists multiple renditions — the client chooses per-segment.

Metadata and sharding: video metadata (title, description, view counts, recommendations) is stored separately in a sharded database, sharded by video ID or user ID. View counts are sharded counters (see the distributed counter design). Recommendations are computed offline and cached.

Replication and availability: metadata replicated across regions; CDN provides geographic redundancy for video bytes. A regional origin failure is absorbed by CDN caches and multi-origin failover. The senior signal: emphasize that the CDN is the scaling mechanism, and that transcoding is an asynchronous, sharded batch pipeline rather than a synchronous path.

▶ Design a notification system (push, email, in-app). Design

Requirements: deliver notifications across multiple channels (push, email, SMS, in-app), at high volume, with retries, deduplication, and per-user preferences.

Pipeline: producers (order service, social service) publish notification events to a message queue (Kafka). A notification service consumes events, applies user preferences and rate limits, renders the message per channel, and dispatches to channel-specific adapters (APNs/FCM for push, SES/SendGrid for email, an in-app store for the feed). This decouples producers from delivery — the order service does not block on email delivery.

Sharding: the queue is partitioned by user ID so all of a user's notifications are ordered within a partition. The in-app notification store is sharded by user ID for per-user reads. Channel adapters scale independently — email throughput needs differ from push.

Idempotency and deduplication: each notification carries a unique ID. Before sending, check a dedupe store (Redis with TTL) so a retried event does not send twice. This is critical — duplicate push notifications are a visible quality bug.

Rate limiting and preferences: per-user rate limits (no more than N notifications per hour) and per-channel opt-outs are enforced before dispatch. This prevents notification fatigue, which drives uninstalls.

Retries and failure: channel adapters retry with exponential backoff on transient failures; permanent failures (invalid device token) are dropped and the token marked stale. A dead-letter queue captures failures for inspection. Circuit breakers prevent a failing provider (e.g., APNs outage) from backing up the whole pipeline — the push adapter opens its circuit while email continues.

Replication: the queue and in-app store are replicated for durability. The senior signal is separating the decision to notify (business logic, preferences) from the delivery (channel adapters), and designing dedupe and rate limiting as first-class concerns.

▶ How do you design a system that can handle 10x more traffic with minimal changes? DesignAdvanced

Identify the bottleneck first — 10x traffic does not mean 10x everything. Profile the current system: is the database CPU-bound, is the application tier saturated, is the network the limit? The design must address the actual constraint.

Design for elasticity from the start:

  • Stateless application tier: externalize sessions (Redis) and file uploads (object storage) so any instance can serve any request. Then horizontal scaling is just adding instances behind the load balancer.
  • Read scaling: read replicas for the database, caching at every layer (CDN, Redis, local in-process cache). Most systems are read-heavy, and read scaling is far cheaper than write scaling.
  • Asynchronous processing: move non-critical work (emails, image processing, analytics) off the request path into queues. This reduces request latency and decouples throughput from the application tier.
  • Database sharding plan: design the schema with a shard key in mind even before sharding is needed, so horizontal partitioning is possible when the write ceiling is hit. Avoid features that block sharding (cross-shard joins, global sequences).
  • Autoscaling with headroom: scale on the right metric (queue depth, request rate, CPU) with enough headroom that scaling completes before saturation. Predictive scaling for known events.
  • Load shedding and rate limiting: protect the system from overload rather than letting it collapse. A system that degrades gracefully at 12x is better than one that fails completely at 10x.

The senior signal: "10x with minimal changes" is achieved by removing state and bottlenecks ahead of time — statelessness, externalized sessions, and partitionable data make horizontal scaling a matter of adding instances. If the design requires re-architecting at 10x, the original design was not built for growth.

▶ What is backpressure and why is it important? (cross-reference: see also the design question above) Design

Backpressure is the mechanism by which a saturated downstream component signals upstream producers to slow down or stop. It is the difference between a system that degrades gracefully and one that collapses under load.

Without backpressure, a fast producer feeds a slow consumer: the queue grows unbounded, memory exhausts, latency for all requests spikes (because the consumer is working on stale work), and eventually the process is killed by the OOM killer or stops responding entirely. This is a classic cascading failure — one slow dependency takes down the whole request path.

Backpressure is implemented by making the boundary between components explicit about its limits:

  • Bounded queues: the queue has a maximum size; when full, the producer blocks, drops, or receives an error — a deliberate policy, not infinite buffering.
  • Blocking writes: TCP's flow control is the canonical example — the receiver advertises a window size, and the sender stops when it is full.
  • Rate limiting and load shedding: reject excess work at the edge with a clear status code, so the system stays within its capacity.
  • Reactive streams / pull-based consumption: consumers request a bounded number of items, so the producer never outpaces them.

The key insight for interviews: backpressure requires a rejection policy. A system that "handles" backpressure by buffering indefinitely is not applying backpressure — it is deferring the failure. The senior answer names the policy (block, drop, shed, degrade) and ties it to the user experience.

▶ What is the circuit breaker pattern? DesignAdvanced

The circuit breaker prevents a failing dependency from cascading into a system-wide outage. It wraps calls to a dependency and tracks failures. When the failure rate exceeds a threshold, the breaker opens — subsequent calls fail immediately (returning a fallback or error) without attempting the dependency. This stops the request pile-up that would otherwise exhaust threads, connections, and memory.

The three states:

  • Closed: normal operation; calls pass through. Failures are counted.
  • Open: calls fail fast. After a timeout, the breaker transitions to half-open.
  • Half-open: a limited number of test calls are allowed through. If they succeed, the breaker closes (recovery). If they fail, it reopens and the timeout resets.

Why it matters: without a breaker, a slow or failing dependency causes every request to wait for a timeout, exhausting the thread pool and taking down the caller even though the caller itself is healthy. The breaker converts a slow failure into a fast one, preserving the caller's capacity and giving the dependency time to recover.

Implementation details that matter:

  • Per-dependency breakers: isolate failures — a failing email provider should not trip the breaker for the payment gateway.
  • Fallbacks: define what happens when the circuit is open — cached data, a degraded response, or a queued retry.
  • Tuning: thresholds, timeout, and half-open probe count must be tuned to the dependency's failure characteristics; too sensitive causes false trips, too lax defeats the purpose.

The senior signal: pair the circuit breaker with timeouts and retry budgets — a breaker without timeouts still waits for slow calls, and unbounded retries amplify load during an outage.

▶ How do you choose a shard key for a globally distributed database? ShardingDesign

The shard key must balance even distribution, query locality, and locality of access (data close to its users). These goals often conflict, so the choice is workload-specific.

  • Start from the dominant query: if most queries are per-user, shard on user ID so they are single-shard point lookups. If most queries are per-tenant, shard on tenant ID. The shard key should appear in the WHERE clause of your most frequent and latency-sensitive queries.
  • Handle skew: if user activity is highly skewed (a few power users dominate), a plain user-ID key creates hot shards. Use a composite key (user ID + region or user ID + bucket) or a directory to isolate hot users onto dedicated shards.
  • Avoid monotonic keys: timestamps and auto-increment IDs concentrate writes on the newest shard. If time-based partitioning is required, combine it with a high-cardinality component (e.g., hash(user_id) + time_bucket).
  • Geo-locality: if data residency or latency requirements demand regional placement, shard by region as the top-level key, then by user within each region. This satisfies GDPR-style requirements and keeps reads local, at the cost of cross-region queries becoming expensive.
  • Plan for growth: prefer consistent hashing or a directory-based scheme over modulo hashing, so adding shards does not require remapping nearly all keys.

The senior answer states the trade-off explicitly: "Sharding by user ID makes per-user reads single-shard, but celebrity users create hot shards — I'd isolate those onto dedicated shards via a directory rather than compromising the common-case key."
