Maven Transitive Dependency — How It Works

Learn how Maven resolves transitive dependencies, applies conflict rules, and how you can manage exclusions and versions.

What is Transitive Dependency?

If your project depends on a library A, and library A depends on another library B, then your project implicitly depends on B. This indirect dependency is called a transitive dependency.

How Maven Solves Transitive Dependency

Maven automatically downloads and includes transitive dependencies using its dependency graph, so you don’t need to declare them explicitly.

Example

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
        <version>3.2.0</version>
    </dependency>
</dependencies>

This pulls in spring-web, spring-webmvc, spring-boot-starter-json, tomcat, and more.

Conflict Resolution Rules

  • Nearest-wins strategy: the version closest to your project in the dependency tree is used.
  • First-declaration wins: if equally near, the one that appears first in the POM hierarchy is chosen.

Inspect the Dependency Tree

mvn dependency:tree
[INFO] com.example:my-app:jar:1.0
[INFO] +- org.springframework.boot:spring-boot-starter-web:3.2.0
[INFO] |  +- org.springframework.boot:spring-boot-starter:3.2.0
[INFO] |  +- org.springframework.boot:spring-boot-starter-json:3.2.0
[INFO] |  |  +- com.fasterxml.jackson.core:jackson-databind:2.15.0
[INFO] |  |  \- com.fasterxml.jackson.core:jackson-core:2.15.0

Control Transitive Dependencies

Exclude Unwanted Transitives

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-tomcat</artifactId>
        </exclusion>
    </exclusions>
</dependency>

Force a Specific Version

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>2.16.0</version>
        </dependency>
    </dependencies>
</dependencyManagement>

Summary

  • Maven automatically resolves and downloads transitive dependencies.
  • Conflicts are handled via nearest-wins and first-declaration-wins.
  • Use dependency:tree to inspect, exclusions to remove, and dependencyManagement to pin versions.

Dependency Mediation in Maven

Maven automatically resolves version conflicts when multiple dependencies bring in different versions of the same library. This process is known as dependency mediation. Understanding how Maven chooses the right version helps you avoid unexpected runtime issues.

What is Dependency Mediation?

When your project depends on multiple libraries that include different versions of the same dependency, Maven must decide which version to use. This selection process is called dependency mediation.

How Maven Chooses the Right Version

  • Nearest-Wins Strategy: Maven picks the version that is closest to your project in the dependency tree.
  • First Declaration Wins: If two versions are equally close, Maven selects the one declared first in the POM hierarchy.
  • Direct Dependencies Override: If you declare a version explicitly in your pom.xml, Maven always prefers it over transitive ones.

Example of Mediation

Suppose your project declares two dependencies:

<dependencies>
    <dependency>
        <groupId>A</groupId>
        <artifactId>A-lib</artifactId>
        <version>1.0</version>
    </dependency>

    <dependency>
        <groupId>B</groupId>
        <artifactId>B-lib</artifactId>
        <version>2.0</version>
    </dependency>
</dependencies>

Now consider the transitive dependencies:

  • A-lib:1.0 depends on C-lib:1.1
  • B-lib:2.0 depends on C-lib:2.0

Both bring in different versions of C-lib. Maven applies mediation:

✔ If A-lib is closer or declared first → C-lib:1.1 is chosen.

✔ If B-lib is closer or declared first → C-lib:2.0 is chosen.

Inspecting the Dependency Tree

You can view which version Maven picked with:

mvn dependency:tree
[INFO] com.example:my-app:jar:1.0
[INFO] +- A-lib:jar:1.0:compile
[INFO] |  \- C-lib:jar:1.1:compile
[INFO] \- B-lib:jar:2.0:compile
[INFO]    \- C-lib:jar:2.0:compile (omitted for conflict with 1.1)

Here Maven selected C-lib:1.1.

Overriding Mediation

You can control which version Maven should use:

Explicit Declaration

<dependency>
    <groupId>C-lib</groupId>
    <artifactId>C-lib</artifactId>
    <version>2.0</version>
</dependency>

Dependency Management

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>C-lib</groupId>
            <artifactId>C-lib</artifactId>
            <version>2.0</version>
        </dependency>
    </dependencies>
</dependencyManagement>

Summary

  • Dependency mediation decides which version of a dependency Maven should use when conflicts occur.
  • Maven uses nearest-wins and first-declaration-wins rules.
  • Direct dependencies override transitive ones.
  • Use mvn dependency:tree to inspect the chosen versions.
  • Override with explicit dependencies or dependencyManagement for consistent builds.

Multi-Module Example: dependencies vs dependencyManagement

🔹 Example Project Structure

my-project
│── pom.xml (parent POM)
│── module-a
│    └── pom.xml
│── module-b
     └── pom.xml

🔹 Parent POM (my-project/pom.xml)

Here we use dependencyManagement to define versions in one place:

<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>my-project</artifactId>
    <version>1.0.0</version>
    <packaging>pom</packaging>

    <modules>
        <module>module-a</module>
        <module>module-b</module>
    </modules>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.springframework</groupId>
                <artifactId>spring-core</artifactId>
                <version>6.1.2</version>
            </dependency>
            <dependency>
                <groupId>org.apache.commons</groupId>
                <artifactId>commons-lang3</artifactId>
                <version>3.12.0</version>
            </dependency>
        </dependencies>
    </dependencyManagement>
</project>

👉 spring-core and commons-lang3 are not added to the classpath here. They are just managed.

🔹 Module A (module-a/pom.xml)

Here we use dependencies without specifying versions:

<project>
    <parent>
        <groupId>com.example</groupId>
        <artifactId>my-project</artifactId>
        <version>1.0.0</version>
    </parent>

    <modelVersion>4.0.0</modelVersion>
    <artifactId>module-a</artifactId>

    <dependencies>
        <dependency>
            <groupId>org.springframework</groupId>
            <artifactId>spring-core</artifactId>
            <!-- No version, inherited from dependencyManagement -->
        </dependency>
    </dependencies>
</project>

👉 Maven will use spring-core:6.1.2 because that version was defined in the parent’s dependencyManagement.

🔹 Module B (module-b/pom.xml)

Now we declare another dependency:

<project>
    <parent>
        <groupId>com.example</groupId>
        <artifactId>my-project</artifactId>
        <version>1.0.0</version>
    </parent>

    <modelVersion>4.0.0</modelVersion>
    <artifactId>module-b</artifactId>

    <dependencies>
        <dependency>
            <groupId>org.apache.commons</groupId>
            <artifactId>commons-lang3</artifactId>
            <!-- No version, inherited from dependencyManagement -->
        </dependency>
    </dependencies>
</project>

👉 Maven automatically chooses commons-lang3:3.12.0 from the parent’s dependencyManagement.

🔹 If We Used Only dependencies in Parent

<dependencies>
    <dependency>
        <groupId>org.springframework</groupId>
        <artifactId>spring-core</artifactId>
        <version>6.1.2</version>
    </dependency>
</dependencies>

👉 Both Module A and Module B would automatically include spring-core:6.1.2 in their classpath, even if they don’t declare it. This may cause unwanted dependencies in modules that don’t need them.

🔹 Summary of Difference with Example

dependencyManagement

  • Defines versions.
  • Child modules still must declare dependencies explicitly.
  • Example: Module A/B must say “I need spring-core”.

dependencies

  • Actually adds to classpath.
  • Child modules inherit them automatically, even if not declared.
  • Example: If parent adds spring-core, all children get it, whether they need it or not.

👉 Best practice in large multi-module projects: Use dependencyManagement in parent POM for consistent version control, and dependencies only in child POMs that actually need them.

Maven Phases

🔹 What is a Phase?

A phase in Maven represents a step in the build lifecycle. Running a phase automatically executes all preceding phases in sequence. Each phase may call plugin goals associated with it.

🔹 Maven Build Lifecycles

Maven has three built-in lifecycles:

  • default – handles project deployment
  • clean – handles cleaning the project
  • site – handles generating project documentation

🔹 Default Lifecycle Phases

Phase Description
validate Check if the project is correct and all necessary information is available
compile Compile the source code of the project
test Run unit tests using a suitable testing framework
package Package compiled code into JAR, WAR, or other formats
verify Run checks to ensure the package meets quality criteria
install Install the package into the local repository for other projects
deploy Copy the final package to a remote repository for sharing

🔹 Example Commands

mvn compile    → executes validate → compile
mvn package    → executes validate → compile → test → package
mvn install    → executes all phases up to install

✅ Running a later phase automatically executes all preceding phases in order.

🔹 Key Points

  • Phases are sequential steps in the build lifecycle.
  • Plugins execute goals bound to each phase; the phase itself does not perform work.
  • Custom plugins can be bound to any phase.
  • Understanding phases helps control the build order of compilation, testing, packaging, and deployment.

✅ Summary: A phase is a step in the Maven build lifecycle that determines the order in which plugin goals are executed. Running a phase automatically triggers all preceding phases to ensure the build process is complete and consistent.

Maven Goals

🔹 What is a Goal?

A goal is a specific task executed by a Maven plugin. While a phase represents a step in the build lifecycle, a goal is the actual work unit performed. Goals can run automatically as part of a phase or manually by specifying the plugin and goal.

🔹 How Goals Work

  • Each plugin contains one or more goals. Example: maven-compiler-plugin has compile and testCompile goals.
  • Goals are often bound to lifecycle phases. Example: compile goal is bound to the compile phase.
  • Goals can be run manually: mvn <plugin>:<goal>. Example: mvn clean:clean runs the clean goal of the maven-clean-plugin.

🔹 Example: Compiler Plugin

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.11.0</version>
            <configuration>
                <source>17</source>
                <target>17</target>
            </configuration>
        </plugin>
    </plugins>
</build>

✅ Plugin: maven-compiler-plugin Goals: compile, testCompile Phase binding: compile → compile phase, testCompile → test-compile phase

🔹 Phase vs Goal

  • Phase = a step in the build lifecycle (e.g., compile, test, package)
  • Goal = the specific task executed by a plugin (e.g., compile goal of maven-compiler-plugin)
  • Goals can run automatically as part of a phase or manually.
  • Plugins may contain multiple goals bound to different phases.

✅ Summary: A goal is the actual task a Maven plugin performs. A phase defines when the task runs. Maven executes plugin goals automatically as part of phases or manually when specified.

Maven Plugins

🔹 What is a Plugin?

A Maven plugin is a collection of goals that perform specific tasks in the build lifecycle. Plugins extend Maven’s capabilities beyond the default build. Every Maven command (like mvn compile, mvn test, mvn package) invokes plugin goals behind the scenes.

🔹 How Plugins Work

Maven build lifecycle phases:

validate → compile → test → package → verify → install → deploy

Each phase can call plugin goals. Examples:

  • mvn compile → invokes compiler plugin
  • mvn package → invokes jar plugin

🔹 Common Maven Plugins

Plugin Purpose
maven-compiler-plugin Compiles Java source code (compile & test-compile phases)
maven-surefire-plugin Runs unit tests during the test phase
maven-jar-plugin Packages compiled code into a JAR (package phase)
maven-clean-plugin Cleans the target directory (clean phase)
maven-dependency-plugin Manages dependencies (copy, analyze, tree)
maven-site-plugin Generates project documentation site

🔹 Example: Compiler Plugin

Configure Maven to use Java 17 to compile your project: 

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.11.0</version>
            <configuration>
                <source>17</source>
                <target>17</target>
            </configuration>
        </plugin>
    </plugins>
</build>

✅ The compile goal is automatically bound to the compile phase.

🔹 Key Points About Maven Plugins

  • Plugins provide goals, each goal does a specific action.
  • Goals can be bound to lifecycle phases or run manually.
  • Plugins are configurable with versions, options, and executions.
  • Third-party plugins can be added (e.g., spring-boot-maven-plugin for Spring Boot).

✅ Summary: Maven plugins are tools that extend Maven’s build process. Each plugin contains goals that execute tasks like compiling, testing, packaging, or generating documentation. By configuring plugins, you control your build lifecycle and customize how your project is built and deployed.

Maven Plugin Management

🔹 What is Plugin Management?

<pluginManagement> in Maven is similar to <dependencyManagement>, but for plugins. It defines plugin versions and configuration for child modules, but does not execute plugins by itself. Child modules can inherit versions/configurations automatically without specifying them again.

🔹 Example: Parent POM

Define plugin version and configuration centrally: 

<build>
    <pluginManagement>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.11.0</version>
                <configuration>
                    <source>17</source>
                    <target>17</target>
                </configuration>
            </plugin>
        </plugins>
    </pluginManagement>
</build>

✅ This does not execute the plugin automatically.

🔹 Example: Child Module

Use the plugin without specifying the version: 

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
        </plugin>
    </plugins>
</build>

👉 Maven automatically applies the version 3.11.0 and configuration from the parent’s pluginManagement.

🔹 Comparison: <plugins> vs <pluginManagement>

<pluginManagement>

  • Defines versions and configuration for plugins.
  • Does not execute plugins automatically.
  • Child modules must declare the plugin to run it.
  • Useful for multi-module projects to ensure consistency.

<plugins>

  • Actually adds the plugin to the build and executes it.
  • Must include version unless inherited from pluginManagement.
  • Directly affects the build lifecycle.

✅ Summary: <pluginManagement> is for defining plugin versions/configuration centrally without executing them. <plugins> is for adding plugins to the build lifecycle. Best practice in multi-module projects: manage plugin versions in parent POM using pluginManagement and execute them in child modules using plugins.

Ensuring Consistent Plugin Versions Across All Maven Modules

In a multi-module Maven project, different modules might use the same plugins but with different versions. This can lead to build inconsistencies or unexpected behavior. Maven provides a mechanism called pluginManagement to enforce consistent plugin versions across all modules.

Step 1: Use pluginManagement in the Parent POM

Define all plugin versions in the parent POM under <build><pluginManagement>: 

<build>
  <pluginManagement>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.11.0</version>
      </plugin>

      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-surefire-plugin</artifactId>
        <version>3.1.2</version>
      </plugin>
    </plugins>
  </pluginManagement>
</build>

pluginManagement only specifies the versions and configuration. It does not automatically apply the plugins to child modules.

Step 2: Declare Plugins in Child Modules

In child modules, declare the plugin without specifying the version. Maven will use the version from the parent’s pluginManagement: 

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
    </plugin>

    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
    </plugin>
  </plugins>
</build>

This ensures all modules use the **same plugin versions**, avoiding version drift.

Step 3: Benefits of Plugin Management

  • Centralizes plugin version control in the parent POM.
  • Prevents module-specific version conflicts.
  • Facilitates consistent build behavior across all modules.
  • Works well with CI/CD pipelines to guarantee repeatable builds.

✅ Summary:
- Use pluginManagement in the parent POM to specify plugin versions.
- Declare plugins in child modules without specifying versions.
- Ensures all modules use consistent plugin versions and configuration.
- Prevents version conflicts and ensures reliable builds across a multi-module project.

The Complete Maven Build Story

Maven builds projects in a structured and consistent way using three main concepts: phases, plugins, and goals. Understanding how they work together is key to mastering Maven.

🔹 Phase – Step in the Build Lifecycle

A phase represents a point in the build process, like compile, test, package, or install.

Phases are sequential: running a later phase automatically runs all preceding phases. Phases don’t perform work themselves; they define when plugin goals should run.

🔹 Plugin – Tool That Performs Tasks

Plugins extend Maven’s capabilities, providing a set of goals to accomplish different tasks. Example: maven-compiler-plugin compiles Java code, maven-surefire-plugin runs tests, maven-jar-plugin packages JARs.

🔹 Goal – The Specific Task

A goal is the unit of work, like compile, testCompile, or test. Goals can be bound to a lifecycle phase or executed manually with mvn <plugin>:<goal>.

🔹 Plugin Executions – Customizing Goal Bindings

You can explicitly bind a plugin goal to a specific phase using <executions>. This gives fine-grained control over when and how plugin goals run. 

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <version>3.11.0</version>
  <executions>
    <execution>
      <id>custom-compile</id>
      <phase>process-sources</phase>
      <goals>
        <goal>compile</goal>
      </goals>
    </execution>
  </executions>
</plugin>

🔹 Manual Goal Execution

Any plugin goal can be executed directly using: 

mvn <plugin>:<goal>
mvn clean:clean

Useful for one-off tasks like cleaning, site generation, or dependency analysis.

🔹 Plugin Management

In multi-module projects, <pluginManagement> in the parent POM ensures consistent plugin versions and configurations. Child modules must still declare the plugin under <plugins> to execute goals.

🔹 Putting It All Together

When you run mvn package, Maven executes all phases up to package. For each phase, it identifies plugins bound to that phase and executes the corresponding goals. Custom executions are respected, and plugin versions/configurations are applied from pluginManagement if defined.

The result: a structured, predictable, and consistent build where phases determine timing, plugins provide tools, goals do the work, executions allow customization, and pluginManagement ensures consistency.

✅ Summary: - Phase = step in the build lifecycle (timing) - Plugin = tool providing goals - Goal = specific task executed by a plugin - Executions = customize which goal runs in which phase - Plugin Management = centralize plugin versions and configurations

Why Plugins Don't Appear in a Simple POM

In a simple Maven POM, you often don’t see plugins explicitly declared because Maven uses default plugins and default bindings.

🔹 Default Plugins for Lifecycle Phases

Maven automatically uses built-in plugins for tasks like compiling, testing, and packaging. Examples include:

Phase Default Plugin & Goal
compile maven-compiler-plugin:compile
test maven-surefire-plugin:test
package maven-jar-plugin:jar
install maven-install-plugin:install
deploy maven-deploy-plugin:deploy

🔹 Example: Simple POM Without Plugins

<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>my-app</artifactId>
  <version>1.0.0</version>
  <packaging>jar</packaging>

  <dependencies>
    <dependency>
      <groupId>org.apache.commons</groupId>
      <artifactId>commons-lang3</artifactId>
      <version>3.12.0</version>
    </dependency>
  </dependencies>
</project>

Even without declaring plugins, Maven will still compile code, run tests, and package a JAR using default plugins.

🔹 When to Add Plugins Explicitly

  • To override default behavior (e.g., custom compiler version).
  • To add extra goals not bound by default.
  • To create custom executions in different phases.
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.11.0</version>
    <configuration>
        <source>17</source>
        <target>17</target>
    </configuration>
</plugin>

✅ Key Point: Plugins exist even if not declared. Maven uses default plugins and goals based on lifecycle phases. You declare them only when you need custom behavior or configuration.

Binding a Plugin Goal to a Maven Lifecycle Phase

In Maven, **plugins provide goals** that perform specific tasks, like compiling code, running tests, or packaging artifacts. You can bind a plugin goal to a specific **lifecycle phase** so that Maven executes it automatically during the build process.

Step 1: Identify the Lifecycle Phase

Maven has three built-in lifecycles: default, clean, and site. Each lifecycle contains phases such as validate, compile, test, package, install, and deploy. Decide which phase you want the plugin goal to execute in.

Step 2: Bind the Plugin Goal in POM

Use the <plugins> section under <build> in your POM. Specify the <phase> and <goal>: 

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.11.0</version>
      <executions>
        <execution>
          <id>compile-java</id>
          <phase>compile</phase>
          <goals>
            <goal>compile</goal>
          </goals>
        </execution>
        <execution>
          <id>compile-test</id>
          <phase>test-compile</phase>
          <goals>
            <goal>testCompile</goal>
          </goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

In this example:

  • The compile goal is bound to the compile phase.
  • The testCompile goal is bound to the test-compile phase.
  • Maven will execute these goals automatically when you run mvn compile or a lifecycle that includes these phases.

Step 3: Run Maven Build

Execute the Maven lifecycle phase. The bound plugin goals will run automatically: 

mvn compile
mvn test-compile
mvn package

Maven ensures the goals execute in the correct order according to the lifecycle phases you specified.

✅ Summary:
- Plugins provide goals that perform specific tasks.
- Bind a plugin goal to a lifecycle phase using <executions> in the <build> section.
- Maven automatically runs the goal during the specified phase.
- This ensures consistent and automated builds without manual execution of plugin goals.

Configuring Maven to Run Custom Build Steps

Maven allows you to integrate **custom build steps** like code generation, linting, or documentation checks into the build lifecycle. You can achieve this by configuring plugins and binding their goals to specific lifecycle phases.

Step 1: Choose a Plugin

Maven plugins provide specific tasks (goals). For example:

  • Code generation: jaxb2-maven-plugin to generate Java classes from XML schemas.
  • Linting/Code formatting: maven-checkstyle-plugin or spotless-maven-plugin.
  • Custom scripts: exec-maven-plugin to run arbitrary commands or scripts.

Step 2: Configure the Plugin in POM

Add the plugin under <build><plugins> and bind goals to lifecycle phases: 

<build>
  <plugins>
    <plugin>
      <groupId>org.codehaus.mojo</groupId>
      <artifactId>jaxb2-maven-plugin</artifactId>
      <version>2.6</version>
      <executions>
        <execution>
          <id>generate-sources</id>
          <phase>generate-sources</phase>
          <goals>
            <goal>>generate</goal>
          </goals>
        </execution>
      </executions>
    </plugin>

    <plugin>
      <groupId>>org.apache.maven.plugins</groupId>
      <artifactId>>maven-checkstyle-plugin</artifactId>
      <version>3.2.0</version>
      <executions>
        <execution>
          <id>>validate-code-style</id>
          <phase>>validate</phase>
          <goals>
            <goal>>check</goal>
          </goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

In this example:

  • JAXB generates source code during generate-sources phase.
  • Checkstyle validates code style during validate phase.
  • Both steps are now part of the automated Maven build lifecycle.

Step 3: Run the Build

Execute the Maven build as usual. The bound plugin goals will run automatically: 

mvn clean install

Maven ensures all plugin goals bound to lifecycle phases execute in the correct order, including your custom steps.

Additional Tips

  • You can define multiple executions per plugin for different phases or goals.
  • Custom scripts can be executed with exec-maven-plugin for tasks like code generation or database setup.
  • Use validate or generate-sources phases for tasks that must happen before compilation.
  • CI/CD pipelines can rely on these automated steps for consistent builds.

✅ Summary:
- Maven plugins enable custom build steps like code generation and linting.
- Bind plugin goals to lifecycle phases in the POM using <executions>.
- Run mvn clean install to execute the custom steps automatically.
- This integrates your custom build logic into Maven’s lifecycle for reliable, automated builds.

Building a Specific Module in a Multi-Module Maven Project

In a multi-module Maven project, you might want to build only one module without building the entire project. Maven provides commands to focus on a specific module, saving time and resources.

Step 1: Use the -pl Option

The -pl (project list) option allows you to specify which module(s) to build: 

mvn clean install -pl module-a

- Replace module-a with the directory name of the module you want to build. - Only the specified module and its dependencies will be built.

Step 2: Use the -am Option (Also Make)

If your module depends on other modules in the project, you can include -am to also build its dependencies: 

mvn clean install -pl module-a -am

This ensures that all required modules are built before the target module, avoiding build errors.

Step 3: Build Multiple Modules

You can also build multiple modules at once by separating them with commas: 

mvn clean install -pl module-a,module-b -am

Maven will build the listed modules along with their dependencies.

Step 4: Benefits of Building Specific Modules

  • Saves build time by avoiding unnecessary modules.
  • Focuses on the module you are actively developing or testing.
  • Works well in CI/CD pipelines for targeted builds.

✅ Summary:
- Use -pl module-name to build a specific module.
- Use -am to also build its dependencies.
- You can specify multiple modules by separating them with commas.
- This approach saves time and allows targeted builds in multi-module projects.

Maven Repositories

🔹 What is a Maven Repository?

A Maven repository is a storage location for project artifacts like JARs, libraries, plugins, and POM files. Maven retrieves dependencies from repositories when you build a project and can upload your own artifacts for sharing.

🔹 Types of Maven Repositories

  • Local Repository – Stored on your machine, usually at ~/.m2/repository. Maven checks here first for dependencies. Fast and works offline.
  • Remote Repository – Hosted on the internet or internally (e.g., Maven Central, company Nexus/Artifactory). Maven downloads artifacts from here if not found locally.
  • Central Repository – The official global repository (Maven Central) for open-source Java libraries.
  • Snapshot vs Release Repositories – Snapshots are ongoing development builds (mutable), e.g., 1.0.1-SNAPSHOT. Releases are stable, versioned artifacts (immutable), e.g., 1.0.0.

🔹 How Maven Resolves Dependencies

When you declare a dependency:

<dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-lang3</artifactId>
  <version>3.12.0</version>
</dependency>

Maven follows this resolution order:

  1. Check local repository (~/.m2/repository).
  2. Check remote repositories (Maven Central or custom ones).
  3. Download missing artifact into local repository.
  4. Use the artifact for compilation, testing, or packaging.

🔹 Adding a Custom Repository

If a dependency isn’t in Maven Central, you can add a remote repository in your POM: 

<repositories>
  <repository>
    <id>company-repo</id>
    <url>https://repo.mycompany.com/maven2</url>
  </repository>
</repositories>

For snapshots, enable them explicitly: 

<snapshots>
  <enabled>true</enabled>
</snapshots>

✅ Summary:
- Local repository: cached on your machine.
- Remote repository: hosted online or internally.
- Central repository: default global repo for open-source libraries.
- Snapshots vs releases: development vs stable versions.
- Maven resolves dependencies locally first, then remotely.

Configuring a Private Nexus/Artifactory Repository in Maven

A private repository (like Nexus or Artifactory) allows your organization to host internal artifacts, snapshots, or third-party libraries that are not available in Maven Central. Maven can be configured to use these repositories for downloading and deploying artifacts.

Step 1: Configure Repositories in POM

Add your private repository under the <repositories> section to download dependencies: 

<repositories>
  <repository>
    <id>private-nexus</id>
    <url>https://nexus.mycompany.com/repository/maven-releases/</url>
    <releases>
      <enabled>true</enabled>
    </releases>
    <snapshots>
      <enabled>false</enabled>
    </snapshots>
  </repository>

  <repository>
    <id>private-nexus-snapshots</id>
    <url>https://nexus.mycompany.com/repository/maven-snapshots/</url>
    <releases>
      <enabled>false</enabled>
    </releases>
    <snapshots>
      <enabled>true</enabled>
    </snapshots>
  </repository>
</repositories>

This configuration separates release artifacts from snapshot artifacts for better version control.

Step 2: Configure Distribution Management

To deploy your artifacts to the private repository, configure <distributionManagement>: 

<distributionManagement>
  <repository>
    <id>private-nexus</id>
    <name>Company Releases</name>
    <url>https://nexus.mycompany.com/repository/maven-releases/</url>
  </repository>

  <snapshotRepository>
    <id>private-nexus-snapshots</id>
    <name>Company Snapshots</name>
    <url>https://nexus.mycompany.com/repository/maven-snapshots/</url>
  </snapshotRepository>
</distributionManagement>

The <id> should match the repository ID defined in your settings.xml for authentication.

Step 3: Configure Authentication in settings.xml

To provide credentials for your private repository, update your Maven settings.xml file (usually located at ~/.m2/settings.xml): 

<servers>
  <server>
    <id>private-nexus</id>
    <username>your-username</username>
    <password>your-password</password>
  </server>

  <server>
    <id>private-nexus-snapshots</id>
    <username>your-username</username>
    <password>your-password</password>
  </server>
</servers>

The <id> must match the repository IDs in your POM so Maven can authenticate automatically.

✅ Summary:
1. Add your private Nexus/Artifactory URLs under <repositories> for downloading dependencies.
2. Configure <distributionManagement> in your POM to deploy artifacts.
3. Add credentials in settings.xml with matching <id> for authentication.
4. Separate snapshots and releases for better version control.

Using a Mirror in Maven to Improve Dependency Resolution

Maven downloads dependencies from remote repositories, typically Maven Central. If your network is slow or you want to centralize downloads for multiple developers, you can configure a mirror. A mirror is a server that caches dependencies from remote repositories, improving download speed and reliability.

Step 1: Configure Mirror in settings.xml

Add the mirror configuration under the <mirrors> section in ~/.m2/settings.xml: 

<mirrors>
  <mirror>
    <id>company-mirror</id>
    <mirrorOf>central</mirrorOf>
    <url>https://maven.mycompany.com/mirror/maven-central/</url>
  </mirror>
</mirrors>

Explanation:

  • <id>: Unique identifier for the mirror.
  • <mirrorOf>: Specifies which repository this mirror replaces (e.g., Maven Central).
  • <url>: URL of the mirror repository.

Step 2: How Mirrors Improve Speed

  • Downloads are redirected to a faster, local, or proxied server rather than the remote Maven Central.
  • Reduces dependency resolution time, especially in corporate networks.
  • Caches previously downloaded artifacts, making builds repeatable and reliable even if the external repository is temporarily unavailable.

Step 3: Additional Tips

  • Mirrors can be configured for multiple repositories, including snapshots and company-specific repos.
  • In multi-developer teams, using a mirror reduces redundant downloads for everyone.
  • Combine mirrors with a local repository manager (Nexus/Artifactory) for optimal caching and speed.

✅ Summary:
- A Maven mirror redirects downloads from remote repositories to a faster or proxied server.
- Configure mirrors in settings.xml under <mirrors>.
- Mirrors improve dependency resolution speed, reliability, and caching efficiency.
- Ideal for corporate networks and CI/CD pipelines.

Compile-Time vs Runtime Classpath in Maven

In Maven, dependencies can be used at **compile-time**, **runtime**, or both. Understanding the difference between compile-time classpath and runtime classpath is crucial for proper dependency management.

🔹 Compile-Time Classpath

The compile-time classpath includes all dependencies required to **compile your code**. Maven ensures that classes from these dependencies are available when you run mvn compile.

  • Includes dependencies with compile and provided scopes.
  • Does not include dependencies only needed at runtime, like JDBC drivers for optional databases.
  • If a dependency is missing here, compilation will fail.

🔹 Runtime Classpath

The runtime classpath includes all dependencies required when **running your application**. Maven ensures these dependencies are packaged or available during mvn exec:java, mvn test, or deployment.

  • Includes dependencies with runtime and compile scopes.
  • Excludes provided dependencies, since the runtime environment (like a servlet container) supplies them.
  • If a dependency is missing here, the application may fail at runtime even if it compiled successfully.

🔹 Dependency Scope Mapping

Scope Compile-Time Classpath Runtime Classpath
compile Included Included
provided Included Excluded
runtime Excluded Included
test Excluded Excluded

✅ Summary:
- Compile-time classpath: Required for compilation; includes compile and provided scopes.
- Runtime classpath: Required for running the application; includes compile and runtime scopes.
- Proper scope selection ensures correct builds, avoids runtime errors, and prevents unnecessary dependencies from being included in the final artifact.

Creating a Fat JAR / Uber JAR with Maven

A fat JAR (also called an uber JAR) packages your application along with all its dependencies into a single JAR. This is useful for distributing your application or running it on systems without Maven installed.

Step 1: Use the Maven Shade Plugin

The maven-shade-plugin is commonly used to create a fat JAR. Add it to your pom.xml: 

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-shade-plugin</artifactId>
      <version>3.5.0</version>
      <executions>
        <execution>
          <phase>package</phase>
          <goals>
            <goal>shade</goal>
          </goals>
          <configuration>
            <transformers>
              <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                <mainClass>com.example.Main</mainClass>
              </transformer>
            </transformers>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Key points:

  • <phase>package</phase> ensures the fat JAR is created during the package phase.
  • <goal>shade</goal> triggers the plugin to include dependencies.
  • <mainClass> specifies the entry point for the JAR.

Step 2: Build the Fat JAR

Run Maven to create the uber JAR: 

mvn clean package

After building, you’ll find a JAR in the target/ directory that contains your application and all dependencies.

Step 3: Run the Fat JAR

Execute the JAR using: 

java -jar target/my-app-1.0.0-shaded.jar

This will run your application without needing to separately include dependencies on the classpath.

Alternative Plugins

  • maven-assembly-plugin: Another option for creating a jar with dependencies.
  • spring-boot-maven-plugin: For Spring Boot projects, can build an executable JAR with embedded dependencies.

✅ Summary:
- Use maven-shade-plugin to create a fat JAR including all dependencies.
- Bind the shade goal to the package phase in your POM.
- Specify the main class using the ManifestResourceTransformer.
- Run the resulting JAR with java -jar without additional classpath configuration.

Configuring Maven to Work with Corporate Proxies

Many corporate environments require all internet traffic to pass through a proxy server. Maven needs to be configured to use the proxy to download dependencies, plugins, and updates from remote repositories.

Step 1: Locate Maven Settings File

Maven proxy configuration is done in the settings.xml file, typically located at:

  • $MAVEN_HOME/conf/settings.xml (global settings)
  • ~/.m2/settings.xml (user-specific settings)

Step 2: Add Proxy Configuration

Add a <proxy> entry inside <proxies> in settings.xml: 

<settings>
  <proxies>
    <proxy>
      <id>corporate-proxy</id>
      <active>true</active>
      <protocol>http</protocol>
      <host>proxy.company.com</host>
      <port>8080</port>
      <username>your-username</username>
      <password>your-password</password>
      <nonProxyHosts>localhost|127.0.0.1</nonProxyHosts>
    </proxy>
  </proxies>
</settings>

Key points:

  • active: Set to true to enable the proxy.
  • host and port: Your corporate proxy server details.
  • username and password: If your proxy requires authentication.
  • nonProxyHosts: Hosts that should bypass the proxy.

Step 3: Test Maven with Proxy

Run a simple Maven command to verify that dependencies can be downloaded through the proxy: 

mvn clean install

If Maven can resolve dependencies, the proxy is configured correctly. Otherwise, check your settings.xml for typos or missing credentials.

Additional Tips

  • You can define multiple proxies in <proxies> and activate them as needed.
  • Use nonProxyHosts to avoid routing local repositories or internal servers through the proxy.
  • If your corporate proxy uses HTTPS, set <protocol>https</protocol> and the appropriate port.
  • Environment variables HTTP_PROXY and HTTPS_PROXY can also be used in some setups, but settings.xml is preferred for Maven.

✅ Summary:
- Configure Maven proxies in settings.xml under <proxies>.
- Provide proxy host, port, authentication, and non-proxy hosts.
- Activate the proxy and test with a Maven build.
- This ensures Maven can download dependencies and plugins in a corporate network.

Enforcing Quality Checks in Maven Builds (PMD, Checkstyle, SpotBugs)

Maven allows integration of static code analysis tools like PMD, Checkstyle, and SpotBugs. By configuring these plugins, you can automatically enforce coding standards, detect bugs, and maintain high code quality during builds.

Step 1: Add Plugins in pom.xml

Configure each plugin under <build><plugins> and bind their goals to appropriate lifecycle phases: 

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-checkstyle-plugin</artifactId>
      <version>3.2.0</version>
      <executions>
        <execution>
          <phase>validate</phase>
          <goals><goal>check</goal></goals>
        </execution>
      </executions>
      <configuration>
        <configLocation>checkstyle.xml</configLocation>
        <failOnViolation>true</failOnViolation>
      </configuration>
    </plugin>

    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-pmd-plugin</artifactId>
      <version>3.20.0</version>
      <executions>
        <execution>
          <phase>verify</phase>
          <goals><goal>pmd</goal></goals>
        </execution>
      </executions>
      <configuration>
        <failOnViolation>true</failOnViolation>
      </configuration>
    </plugin>

    <plugin>
      <groupId>>com.github.spotbugs</groupId>
      <artifactId>spotbugs-maven-plugin</artifactId>
      <version>4.8.0</version>
      <executions>
        <execution>
          <phase>>verify</phase>
          <goals><goal>>check</goal></goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Step 2: How Each Plugin Works

  • Checkstyle: Validates code style rules from checkstyle.xml. Fails build if violations exist.
  • PMD: Detects potential bugs, code smells, and dead code. Bound to verify phase to run after compilation and tests.
  • SpotBugs: Performs static analysis to find likely bugs. Bound to verify phase.

Step 3: Run Maven Build with Checks

Execute the Maven build normally. Plugins automatically run during their configured phases: 

mvn clean verify

- If any rule violations or bugs are found, the build will fail (because failOnViolation is set to true). - Reports are generated in target/site/ directories for review.

Benefits of Enforcing Quality Checks

  • Maintains consistent code style across the project.
  • Detects potential bugs and code smells early in the development lifecycle.
  • Integrates quality checks into CI/CD pipelines for automated enforcement.
  • Generates readable reports to help developers fix issues efficiently.

✅ Summary:
- Use maven-checkstyle-plugin, maven-pmd-plugin, and spotbugs-maven-plugin for static code analysis.
- Bind each plugin goal to a lifecycle phase such as validate or verify.
- Configure failOnViolation to ensure the build fails on violations.
- Running mvn clean verify will execute all checks and generate detailed reports.

Detailed Guide to Maven settings.xml Topics

Maven’s settings.xml allows configuring global or user-specific settings to control Maven’s behavior, repository access, networking, and build profiles without modifying project POMs. The file is typically located at $MAVEN_HOME/conf/settings.xml (global) or ~/.m2/settings.xml (user-specific).

1. Local Repository

Defines the location where Maven stores downloaded dependencies and built artifacts. 

<localRepository>/path/to/custom/repo</localRepository>

Use a custom path to separate local caches, support CI/CD agents, or resolve permission issues.

2. Proxies

Configures HTTP/HTTPS proxies for environments where direct internet access is restricted. 

<proxies>
  <proxy>
    <id>corporate-proxy</id>
    <active>true</active>
    <protocol>http</protocol>
    <host>proxy.company.com</host>
    <port>8080</port>
    <username>user</username>
    <password>pass</password>
    <nonProxyHosts>localhost|127.0.0.1</nonProxyHosts>
  </proxy>
</proxies>

- active: Enable or disable the proxy.
- nonProxyHosts: Hosts that bypass the proxy.
- Supports authentication for corporate networks.

3. Mirrors

Mirrors are alternative repositories that Maven uses to download artifacts faster or redirect from central repositories. 

<mirrors>
  <mirror>
    <id>central-mirror</id>
    <mirrorOf>central</mirrorOf>
    <url>https://internal.repo.com/maven2/</url>
  </mirror>
</mirrors>

- mirrorOf: Specifies which repositories are mirrored (e.g., "central", "*").
- Improves build speed and reliability by using local or corporate mirrors.

4. Repositories

Defines remote repositories for downloading project dependencies. 

<profiles>
  <profile>
    <id>internal-repo</id>
    <repositories>
      <repository>
        <id>nexus</id>
        <url>https://nexus.company.com/repository/maven-public/</url>
      </repository>
    </repositories>
  </profile>
</profiles>

Profiles allow activating repositories conditionally, e.g., for internal builds or specific environments.

5. Plugin Repositories

Specifies repositories where Maven should search for plugins: 

<pluginRepositories>
  <pluginRepository>
    <id>company-plugins</id>
    <url>https://plugins.company.com/maven2/</url>
  </pluginRepository>
</pluginRepositories>

Useful when corporate policies require custom or private plugin repositories.

6. Servers

Stores authentication credentials for private repositories or deployment targets: 

<servers>
  <server>
    <id>nexus</id>
    <username>deploy-user</username>
    <password>deploy-password</password>
  </server>
</servers>

The id must match the repository ID in your POM or profiles.

7. Profiles

Profiles allow conditional configuration for builds based on environment, JDK, OS, or properties: 

<profiles>
  <profile>
    <id>jdk11-profile</id>
    <activation>
      <jdk>11</jdk>
    </activation>
    <properties>
      <maven.compiler.source>11</maven.compiler.source>
      <maven.compiler.target>11</maven.compiler.target>
    </properties>
  </profile>
</profiles>

Profiles can be activated automatically or manually via command line: mvn clean install -P jdk11-profile.

✅ Summary of settings.xml Topics:
- Local Repository: Where artifacts are stored locally.
- Proxies: For corporate network access.
- Mirrors: Redirect or speed up downloads.
- Repositories: Define dependency sources.
- Plugin Repositories: Specify sources for Maven plugins.
- Servers: Store authentication credentials.
- Profiles: Conditional configurations for environments, JDKs, OS, or custom properties.

Difference Between repository and pluginRepository in Maven

Maven uses repositories to download artifacts, but there are two distinct types: repository for project dependencies and pluginRepository for Maven plugins.

1. repository

A repository is a remote location from which Maven downloads **project dependencies** like libraries or frameworks. These are declared in the POM or in settings.xml (via profiles). 

<repositories>
  <repository>
    <id>nexus</id>
    <url>https://nexus.company.com/repository/maven-public/</url>
  </repository>
</repositories>

Key points:
- Provides JARs, WARs, and other dependency artifacts.
- Used by Maven when resolving <dependencies> in your project.
- Can be internal (corporate Nexus/Artifactory) or public (Maven Central).

2. pluginRepository

A pluginRepository is a remote location from which Maven downloads **plugins** used in the build process. Plugins include compilers, code analyzers, packaging tools, and custom build steps. 

<pluginRepositories>
  <pluginRepository>
    <id>company-plugins</id>
    <url>https://plugins.company.com/maven2/</url>
  </pluginRepository>
</pluginRepositories>

Key points:
- Used when resolving Maven plugins declared under <build><plugins>.
- Ensures your build tools and plugins come from trusted or internal sources.
- Separates dependency resolution from plugin resolution for better control.

Summary

| Feature | repository | pluginRepository |
|---------|------------|-----------------|
| Purpose | Resolve project dependencies (JARs, WARs) | Resolve Maven plugins (compiler, PMD, etc.) |
| Usage | Declared in POM or settings.xml | Declared in POM or settings.xml |
| Examples | Maven Central, internal Nexus | Custom plugin repos, corporate Artifactory |

Tip: Always use repository for dependencies and pluginRepository for build plugins to avoid confusion and maintain clear separation of concerns.

Maven Master Password and Encrypted Passwords

Maven allows storing credentials for private repositories and deployment servers securely. Instead of storing plaintext passwords in settings.xml, Maven can use **encrypted passwords** protected by a **master password**.

Step 1: Create Master Password

The master password encrypts all server passwords in settings-security.xml. It is stored in your local Maven configuration folder ~/.m2/settings-security.xml. 

<settingsSecurity>
  <master>EncryptedMasterPasswordHere</master>
</settingsSecurity>

To generate a master password, run: 

mvn --encrypt-master-password

Step 2: Encrypt Server Passwords

Each server in settings.xml can have its password encrypted using the master password: 

<servers>
  <server>
    <id>nexus</id>
    <username>deploy-user</username>
    <password>{encrypted}EncryptedPasswordHere</password>
  </server>
</servers>

Use Maven command to encrypt a password: 

mvn --encrypt-password

Step 3: How Maven Uses Them

  • During a build, Maven reads settings-security.xml to decrypt the master password.
  • It then uses the master password to decrypt any encrypted passwords in settings.xml servers.
  • Credentials are used securely to access private repositories or deploy artifacts without exposing plaintext passwords.

Step 4: Best Practices

  • Never commit settings.xml with plaintext passwords to source control.
  • Use {encrypted} passwords protected by a master password.
  • Keep settings-security.xml secure; it contains the master password.
  • For CI/CD pipelines, consider environment variable overrides to avoid storing sensitive files on the build server.

✅ Summary:
- Master password: Encrypts passwords in settings.xml.
- Encrypted passwords: Stored in settings.xml using the master password.
- Maven decrypts them at build time to securely access repositories or deploy artifacts.
- Ensures credentials are not exposed in plaintext.

Difference Between settings.xml Profiles and pom.xml Profiles

Maven supports profiles to allow conditional builds. Profiles can be defined in both pom.xml and settings.xml, but they serve different purposes and scopes.

1. pom.xml Profiles

Profiles in the POM are **project-specific**. They define conditional build configurations, such as:

  • Dependency versions or additional dependencies
  • Plugin configuration
  • Build settings like compiler source/target
  • Resource filtering or environment-specific properties
<profiles>
  <profile>
    <id>dev</id>
    <properties>
      <env>development</env>
    </properties>
  </profile>
</profiles>

These profiles travel with the project and can be activated via command line: mvn clean install -P dev.

2. settings.xml Profiles

Profiles in settings.xml are **user-specific or environment-specific**. They are primarily used to:

  • Define private repositories or plugin repositories
  • Configure servers (authentication) for deployment
  • Set environment-specific properties without modifying the POM
  • Activate corporate-specific settings or CI/CD overrides
<profiles>
  <profile>
    <id>corporate</id>
    <repositories>
      <repository>
        <id>nexus</id>
        <url>https://nexus.company.com/repository/maven-public/</url>
      </repository>
    </repositories>
    <properties>
      <env>corporate</env>
    </properties>
  </profile>
</profiles>

These profiles do not travel with the project and are activated per user environment: mvn clean install -P corporate.

3. Key Differences

Aspect pom.xml Profile settings.xml Profile
Scope Project-specific, travels with POM User/environment-specific, local to machine
Purpose Conditional build configuration, dependencies, plugins Repositories, servers, properties, corporate/CI/CD settings
Activation Via POM or command line Via settings.xml or command line
Version Control Usually committed to VCS Never committed, user-specific

Activating Maven Profiles Based on Environment Variables or OS

Maven profiles can be activated automatically depending on the environment, OS, JDK version, or custom properties. This allows building the same project differently on development, staging, or production systems without changing the POM manually.

1. Activate via Environment Variable

You can activate a profile automatically if a certain environment variable is defined or has a specific value: 

<profile>
  <id>ci-profile</id>
  <activation>
    <property>
      <name>env.CI</name>
      <value>true</value>
    </property>
  </activation>
  <properties>
    <env>CI</env>
  </properties>
</profile>

- Here env.CI refers to the environment variable CI.
- The profile ci-profile is activated only if CI=true.

2. Activate via Operating System

Profiles can also be activated based on OS name, family, or architecture: 

<profile>
  <id>windows-profile</id>
  <activation>
    <os>
      <family>Windows</family>
    </os>
  </activation>
  <properties>
    <env>windows</env>
  </properties>
</profile>

- Maven will activate windows-profile automatically if the build runs on a Windows system. - Supported OS activation elements: name, family, arch.

3. Combined Activation

You can combine multiple activation conditions: 

<profile>
  <id>linux-ci-profile</id>
  <activation>
    <os><family>Linux</family></os>
    <property><name>env.CI</name><value>true</value></property>
  </activation>
</profile>

- Activated only when running on Linux AND the environment variable CI=true.

✅ Summary:
- Profiles in Maven can be activated automatically based on environment variables or OS properties.
- Use <activation><property> for environment variables.
- Use <activation><os> for operating system-based activation.
- Supports flexible, automated builds for multiple environments without changing the POM manually.

Passing Profile-Specific Properties in Maven Builds

Maven profiles allow defining **properties** that are only active when the profile is enabled. These properties can control build behavior, plugin configurations, or resource filtering dynamically.

1. Define Properties in POM Profile

You can define properties under a profile in your pom.xml: 

<profiles>
  <profile>
    <id>dev</id>
    <properties>
      <env>development</env>
      <api.url>https://dev.api.company.com</api.url>
    </properties>
  </profile>

  <profile>
    <id>prod</id>
    <properties>
      <env>production</env>
      <api.url>https://api.company.com</api.url>
    </properties>
  </profile>
</profiles>

- dev and prod profiles define different values for api.url and env. - Properties are only active when the respective profile is activated.

2. Activate Profile at Build Time

Use the -P flag to activate a profile: 

mvn clean install -P dev
mvn clean install -P prod

- Maven applies the properties defined in the active profile only.

3. Use Properties in Plugin Configurations

Profile-specific properties can be referenced using ${property.name} syntax in plugin configuration: 

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-resources-plugin</artifactId>
      <version>3.3.0</version>
      <configuration>
        <filters>
          <filter>src/main/filters/${env}.properties</filter>
        </filters>
      </configuration>
    </plugin>
  </plugins>
</build>

- The property ${env} will resolve to development or production depending on the active profile. - Useful for resource filtering, environment-specific endpoints, or plugin behavior.

4. Override Properties from Command Line

You can override profile properties at build time with -D: 

mvn clean install -P dev -Dapi.url=https://custom.dev.api.com

- This overrides api.url defined in the dev profile without changing the POM.

✅ Summary:
- Define profile-specific properties under <properties> in pom.xml or settings.xml profiles.
- Activate a profile using -P <profile-id>.
- Use ${property} in plugin configuration or POM elements.
- Optionally override property values via -Dproperty=value at build time for flexibility.

Configuring Offline Builds in Maven via settings.xml

Maven usually downloads dependencies from remote repositories during builds. For environments without internet access or to speed up builds, you can configure Maven to work in **offline mode**. This prevents Maven from connecting to remote repositories and uses only locally cached artifacts.

1. Activate Offline Mode Temporarily

You can run Maven in offline mode temporarily via the command line: 

mvn clean install -o

- The -o or --offline flag tells Maven not to contact remote repositories. - Only locally cached dependencies in ~/.m2/repository will be used.

2. Configure Offline Mode in settings.xml

You can set offline mode as a default in your local Maven settings (~/.m2/settings.xml): 

<settings>
  <offline>true</offline>
</settings>

- This ensures all Maven builds on this machine run offline by default. - You can still override this temporarily with -o or disable offline mode with -U (force update).

3. Use Offline Repositories

Offline mode only works if all required dependencies are already present in the local repository. You can pre-populate your local repository by:

  • Running a regular online build once
  • Using mvn dependency:go-offline to download all project dependencies
  • Copying pre-populated local repositories from another machine
mvn dependency:go-offline

4. Best Practices

  • Enable offline mode only in stable environments where dependencies are fully cached.
  • Keep a separate offline repository for CI/CD pipelines in restricted networks.
  • Use mvn dependency:go-offline before switching to offline mode to ensure all dependencies are available locally.

✅ Summary:
- Use -o or --offline for temporary offline builds.
- Configure <offline>true</offline> in settings.xml for default offline behavior.
- Pre-populate the local repository using mvn dependency:go-offline to avoid missing dependencies.
- Offline mode ensures faster builds and works in restricted or air-gapped environments.

How Mirrors and Proxy Configuration Affect Maven Artifact Resolution

Maven resolves dependencies and plugins from remote repositories. Configuring mirrors and proxies in settings.xml can optimize and control how Maven retrieves artifacts.

1. Mirrors

A mirror is an alternative URL for a repository. Maven will use the mirror instead of the original repository URL. 

<mirrors>
  <mirror>
    <id>nexus-mirror</id>
    <mirrorOf>central</mirrorOf>
    <url>https://nexus.company.com/repository/maven-central/</url>
  </mirror>
</mirrors>

- All requests to Maven Central will be redirected to the corporate Nexus mirror. - Mirrors improve performance, provide internal caching, and enforce corporate policies. - They can also reduce internet bandwidth usage by serving artifacts locally.

2. Proxies

If your Maven build runs behind a corporate firewall, you may need a proxy to access external repositories. 

<proxies>
  <proxy>
    <id>corp-proxy</id>
    <active>true</active>
    <protocol>http</protocol>
    <host>proxy.company.com</host>
    <port>8080</port>
    <username>proxyuser</username>
    <password>proxypass</password>
  </proxy>
</proxies>

- Maven will route all repository requests through the proxy. - Proxy ensures access to external repositories even behind firewalls or network restrictions. - Can be combined with mirrors for internal caching.

3. Combined Effect on Artifact Resolution

  • Maven first checks the local repository for artifacts.
  • If not found locally, Maven uses mirrors to fetch artifacts instead of the original repositories.
  • If the mirror URL is behind a firewall, Maven uses the configured proxy to connect.
  • Proper mirror and proxy configuration ensures faster, reliable, and secure artifact resolution.

4. Best Practices

  • Use mirrors for all external repositories in corporate environments to improve speed and caching.
  • Configure proxies only when necessary; avoid conflicts with mirrors.
  • Test mirror and proxy settings with mvn help:effective-settings to verify correct configuration.
  • Keep sensitive proxy credentials encrypted using Maven’s master password mechanism.

✅ Summary:
- Mirrors redirect repository requests for faster, internal access.
- Proxies route Maven requests through firewalls to external repositories.
- Proper configuration ensures reliable artifact resolution, optimal performance, and secure builds.
- Combine mirrors and proxies carefully to maintain build consistency in corporate or restricted networks.

Combining Profiles in settings.xml and pom.xml

Maven allows you to define profiles in both pom.xml (project-specific) and settings.xml (user/environment-specific). These profiles can be **activated together** to customize builds based on both project and environment needs.

1. Define a Profile in settings.xml

In ~/.m2/settings.xml, you can define an environment-specific profile: 

<profiles>
  <profile>
    <id>corporate</id>
    <properties>
      <env>corporate</env>
      <repo.url>https://nexus.company.com/repository/maven-public/</repo.url>
    </properties>
  </profile>
</profiles>

2. Define a Profile in pom.xml

In pom.xml, you can define a project-specific profile: 

<profiles>
  <profile>
    <id>dev</id>
    <properties>
      <env>development</env>
      <api.url>https://dev.api.company.com</api.url>
    </properties>
  </profile>
</profiles>

3. Activating Both Profiles

Maven allows activating multiple profiles simultaneously using the -P flag: 

mvn clean install -P corporate,dev

- Properties from both profiles are merged. - If the same property exists in both, the **project POM profile usually overrides** the settings.xml profile.

4. Common Use Cases

  • Use a settings.xml profile to define corporate or CI/CD environment settings like repositories, servers, or global properties.
  • Use a pom.xml profile to define project-specific build behavior like dependencies, plugins, or API endpoints.
  • Combine both to produce environment-specific builds without modifying the POM manually.

✅ Summary:
- Profiles in settings.xml control user/environment-specific configurations.
- Profiles in pom.xml control project-specific configurations.
- Multiple profiles can be activated together via -P flag.
- Properties are merged, with POM profile properties usually taking precedence.
- This enables flexible, environment-aware, and project-aware builds.
