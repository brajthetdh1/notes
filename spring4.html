Database Configuration Issues

Connection Pool Exhaustion

Database Performance

Problem: Application becomes unresponsive with "Timeout waiting for connection from pool" errors.

HikariPool-1 - Connection is not available, request timed out after 30000ms

Root Cause: Insufficient connection pool configuration or connection leaks.

Solution

1. Optimize HikariCP Configuration:


# application.properties
spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.minimum-idle=5
spring.datasource.hikari.idle-timeout=300000
spring.datasource.hikari.connection-timeout=20000
spring.datasource.hikari.max-lifetime=1200000
spring.datasource.hikari.leak-detection-threshold=60000

2. Detect Connection Leaks:


@Bean
@ConfigurationProperties("spring.datasource.hikari")
public DataSource dataSource() {
    return DataSourceBuilder.create().build();
}

// Add to detect leaks in development
@Profile("dev")
@Bean
public DataSource leakDetectionDataSource() {
    HikariDataSource dataSource = (HikariDataSource) dataSource();
    dataSource.setLeakDetectionThreshold(30000);
    return dataSource;
}

3. Monitor Pool Statistics:


@Component
public class ConnectionPoolMonitor {
    
    @Autowired
    private DataSource dataSource;
    
    @Scheduled(fixedRate = 60000)
    public void monitorPool() {
        if (dataSource instanceof HikariDataSource) {
            HikariDataSource hikari = (HikariDataSource) dataSource;
            HikariPoolMXBean pool = hikari.getHikariPoolMXBean();
            
            log.info("Active Connections: {}", pool.getActiveConnections());
            log.info("Idle Connections: {}", pool.getIdleConnections());
            log.info("Total Connections: {}", pool.getTotalConnections());
            log.info("Threads Awaiting Connection: {}", 
                    pool.getThreadsAwaitingConnection());
        }
    }
}

Database Schema Creation Issues

Database Deployment

Problem: Hibernate fails to create/update database schema with DDL errors.

Schema-validation: missing table [users] or Table 'mydb.users' doesn't exist

Root Cause: Incorrect ddl-auto configuration or database permissions.

Solution

1. Environment-specific DDL Strategy:


# application-dev.properties
spring.jpa.hibernate.ddl-auto=create-drop
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

# application-prod.properties
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.show-sql=false

# application-test.properties  
spring.jpa.hibernate.ddl-auto=create
spring.sql.init.mode=always

2. Use Flyway/Liquibase for Production:


# Disable Hibernate DDL
spring.jpa.hibernate.ddl-auto=validate

# Enable Flyway
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
spring.flyway.baseline-on-migrate=true

3. Database Initialization Configuration:


# Initialize schema and data
spring.sql.init.mode=always
spring.datasource.initialization-mode=always

# Custom schema and data files
spring.sql.init.schema-locations=classpath:custom-schema.sql
spring.sql.init.data-locations=classpath:custom-data.sql

Profile Configuration Issues

Profile-Specific Properties Not Loading

Profiles Deployment

Problem: Profile-specific configuration files (application-{profile}.properties) are not being loaded.

Could not resolve placeholder 'app.custom.property' in value "${app.custom.property}"

Root Cause: Incorrect profile activation or file naming.

Solution

1. Correct Profile Activation:


# application.properties - Set default profile
spring.profiles.active=dev

# Command line activation
java -jar app.jar --spring.profiles.active=prod

# Environment variable activation
export SPRING_PROFILES_ACTIVE=prod

2. Profile-Specific File Naming:


# Correct naming convention
src/main/resources/
  application.properties          # Default
  application-dev.properties      # Development
  application-prod.properties     # Production  
  application-test.properties     # Testing

# YAML alternative
application.yml
application-dev.yml
application-prod.yml

3. Programmatic Profile Activation:


@SpringBootApplication
public class Application {
    
    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(Application.class);
        
        // Check environment and set profile
        String env = System.getenv("APP_ENV");
        if ("production".equals(env)) {
            app.setAdditionalProfiles("prod");
        } else {
            app.setAdditionalProfiles("dev");
        }
        
        app.run(args);
    }
}

// Or using configuration
@Configuration
public class ProfileConfig {
    
    @Bean
    @Profile("dev")
    public DataSource devDataSource() {
        // Development datasource
    }
    
    @Bean  
    @Profile("prod")
    public DataSource prodDataSource() {
        // Production datasource
    }
}

Multiple Active Profiles Conflict

Profiles

Problem: When multiple profiles are active, properties from different profiles conflict or override unexpectedly.

Consider the following: The bean 'dataSource' could not be registered... or Property conflicts between active profiles

Solution

1. Profile Precedence Understanding:


# Later profiles override earlier ones
spring.profiles.active=common,dev,database

# Properties loading order:
# 1. application.properties
# 2. application-common.properties  
# 3. application-dev.properties (overrides common)
# 4. application-database.properties (overrides dev)

2. Profile-Specific Bean Configuration:


@Configuration
public class MultiProfileConfig {
    
    @Bean
    @Profile({"dev", "test"})
    public DataSource embeddedDataSource() {
        return new EmbeddedDatabaseBuilder()
            .setType(EmbeddedDatabaseType.H2)
            .build();
    }
    
    @Bean
    @Profile("prod")
    public DataSource productionDataSource() {
        HikariDataSource ds = new HikariDataSource();
        // Production configuration
        return ds;
    }
    
    // Bean active only when BOTH profiles are active
    @Bean
    @Profile("dev & database")
    public DataSource devDatabaseDataSource() {
        // Special dev database config
    }
}

Bean Configuration Issues

Circular Dependency Problems

Beans

Problem: Application fails to start due to circular dependencies between beans.

The dependencies of some of the beans in the application context form a cycle: serviceA → serviceB → serviceA

Solution

1. Use Setter/Field Injection:


@Service
public class ServiceA {
    private ServiceB serviceB;
    
    // Use setter injection instead of constructor
    @Autowired
    public void setServiceB(ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}

@Service  
public class ServiceB {
    private ServiceA serviceA;
    
    @Autowired
    public void setServiceA(ServiceA serviceA) {
        this.serviceA = serviceA;
    }
}

2. Use @Lazy Annotation:


@Service
public class ServiceA {
    private final ServiceB serviceB;
    
    // Lazy initialization breaks the cycle
    public ServiceA(@Lazy ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}

3. Restructure Dependencies:


// Extract common functionality to a third service
@Service
public class CommonService {
    // Common functionality used by both ServiceA and ServiceB
}

@Service
public class ServiceA {
    private final CommonService commonService;
    // Remove direct dependency on ServiceB
}

@Service  
public class ServiceB {
    private final CommonService commonService;
    // Remove direct dependency on ServiceA
}

Bean Override and Conditional Issues

Beans

Problem: Multiple bean definitions or conditional beans not working as expected.

The bean 'dataSource' could not be registered. A bean with that name has already been defined...

Solution

1. Use @Primary for Default Beans:


@Configuration
public class DataSourceConfig {
    
    @Bean
    @Primary  // This bean will be used by default
    public DataSource primaryDataSource() {
        return DataSourceBuilder.create().build();
    }
    
    @Bean
    public DataSource secondaryDataSource() {
        // Alternative datasource
    }
}

2. Use @Qualifier for Specific Beans:


@Configuration
public class DataSourceConfig {
    
    @Bean("primaryDataSource")
    public DataSource primaryDataSource() {
        return DataSourceBuilder.create().build();
    }
    
    @Bean("secondaryDataSource")  
    public DataSource secondaryDataSource() {
        // Alternative datasource
    }
}

@Service
public class MyService {
    
    @Autowired
    @Qualifier("secondaryDataSource")
    private DataSource dataSource;
}

3. Conditional Bean Configuration:


@Configuration
public class ConditionalBeanConfig {
    
    @Bean
    @ConditionalOnProperty(name = "app.cache.enabled", havingValue = "true")
    @ConditionalOnClass(RedisTemplate.class)
    public CacheManager redisCacheManager() {
        return new RedisCacheManager();
    }
    
    @Bean
    @ConditionalOnMissingBean(CacheManager.class)
    public CacheManager simpleCacheManager() {
        return new ConcurrentMapCacheManager();
    }
    
    @Bean
    @ConditionalOnWebApplication
    public WebMvcConfigurer webConfigurer() {
        return new WebConfig();
    }
    
    @Bean
    @ConditionalOnExpression("${app.feature.advanced:false} && ${app.mode.expert:false}")
    public AdvancedService advancedService() {
        return new AdvancedService();
    }
}

Property Binding Issues

@ConfigurationProperties Binding Failures

Beans

Problem: Properties are not binding correctly to @ConfigurationProperties classes.

Failed to bind properties under 'app.security' to com.example.AppProperties or Could not resolve placeholder 'app.security.jwt.secret' in value "${app.security.jwt.secret}"

Solution

1. Proper @ConfigurationProperties Setup:


@Component
@ConfigurationProperties(prefix = "app.security")
@Validated
public class SecurityProperties {
    
    @NotNull
    private Jwt jwt = new Jwt();
    
    @NotEmpty
    private List allowedOrigins = new ArrayList<>();
    
    // Nested class
    public static class Jwt {
        @NotBlank
        private String secret;
        
        @Min(1000)
        private long expiration = 86400000;
        
        // Getters and setters
        public String getSecret() { return secret; }
        public void setSecret(String secret) { this.secret = secret; }
        
        public long getExpiration() { return expiration; }
        public void setExpiration(long expiration) { this.expiration = expiration; }
    }
    
    // Getters and setters
    public Jwt getJwt() { return jwt; }
    public void setJwt(Jwt jwt) { this.jwt = jwt; }
    
    public List getAllowedOrigins() { return allowedOrigins; }
    public void setAllowedOrigins(List allowedOrigins) { 
        this.allowedOrigins = allowedOrigins; 
    }
}

// Enable in main application
@SpringBootApplication
@EnableConfigurationProperties(SecurityProperties.class)
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

2. Corresponding Properties:


# application.properties
app.security.jwt.secret=mySuperSecretKey
app.security.jwt.expiration=86400000
app.security.allowed-origins[0]=http://localhost:3000
app.security.allowed-origins[1]=https://myapp.com

# Relaxed binding works with different formats
app.security.jwt.secret=mySecret  # kebab-case
app.security.jwt_secret=mySecret  # underscore
app.security.jwtSecret=mySecret   # camelCase

3. Property Validation:


@Component
@Validated
public class PropertyValidator {
    
    @Value("${app.security.jwt.expiration:86400000}")
    @Min(1000)
    @Max(86400000)
    private long jwtExpiration;
    
    // Custom validation
    @AssertTrue(message = "JWT expiration must be at least 1 minute")
    public boolean isJwtExpirationValid() {
        return jwtExpiration >= 60000;
    }
}

Security Configuration Issues

CSRF Protection Breaking API Calls

Security

Problem: REST API calls failing with 403 Forbidden due to CSRF protection.

403 Forbidden: Invalid CSRF Token

Solution

1. Disable CSRF for API Endpoints:


@Configuration
@EnableWebSecurity
public class SecurityConfig {
    
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf
                .ignoringRequestMatchers("/api/**")  // Disable CSRF for APIs
                .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            )
            .authorizeHttpRequests(authz -> authz
                .requestMatchers("/api/public/**").permitAll()
                .requestMatchers("/api/**").authenticated()
                .anyRequest().permitAll()
            )
            .httpBasic(Customizer.withDefaults());
        
        return http.build();
    }
}

2. JWT-based Stateless Authentication:


@Configuration
@EnableWebSecurity
public class JwtSecurityConfig {
    
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())  // Disable CSRF for stateless JWT
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            )
            .authorizeHttpRequests(authz -> authz
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/api/public/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .addFilterBefore(jwtAuthenticationFilter(), 
                UsernamePasswordAuthenticationFilter.class);
        
        return http.build();
    }
    
    @Bean
    public JwtAuthenticationFilter jwtAuthenticationFilter() {
        return new JwtAuthenticationFilter();
    }
}

Configuration Debugging Tips

1. Enable Configuration Debug Mode


# Enable debug mode to see auto-configuration report
java -jar myapp.jar --debug

# Or in application.properties
debug=true

This shows which auto-configuration classes were applied and why others were not.

2. Use Actuator for Configuration Inspection


# Enable actuator endpoints
management.endpoints.web.exposure.include=env,beans,configprops,conditions
management.endpoint.env.enabled=true
management.endpoint.beans.enabled=true
management.endpoint.configprops.enabled=true
management.endpoint.conditions.enabled=true

# Access via HTTP
# GET /actuator/env - All environment properties
# GET /actuator/beans - All Spring beans
# GET /actuator/configprops - @ConfigurationProperties beans
# GET /actuator/conditions - Auto-configuration conditions report

3. Property Source Debugging


@Component
public class PropertyDebugger {
    
    @Autowired
    private Environment environment;
    
    @PostConstruct
    public void debugProperties() {
        System.out.println("=== Active Profiles ===");
        Arrays.stream(environment.getActiveProfiles())
            .forEach(System.out::println);
            
        System.out.println("=== Property Sources ===");
        ((AbstractEnvironment) environment).getPropertySources()
            .forEach(ps -> System.out.println(ps.getName()));
            
        // Check specific property
        String value = environment.getProperty("app.custom.property");
        System.out.println("Custom property value: " + value);
    }
}

4. Configuration Problem Resolution Checklist

Problem Check Solution
Properties not loading File location, naming, encoding Check classpath, use --debug flag
Bean creation errors Dependencies, profiles, conditions Check @Conditional annotations, profiles
Database connection issues URL, credentials, driver class Verify datasource configuration, pool settings
Profile-specific config not working Profile activation, file naming Check spring.profiles.active, file names
Security configuration problems CSRF, CORS, authentication Review SecurityFilterChain configuration
