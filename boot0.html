Spring Boot vs Spring Framework

🌱 What is Spring Framework?

The Spring Framework is a powerful, flexible, and comprehensive Java framework for building enterprise applications. It provides features like dependency injection, aspect-oriented programming, transaction management, and a rich ecosystem of modules (Spring MVC, Spring Security, Spring Data, etc.).

🚀 What is Spring Boot?

Spring Boot is a project built on top of the Spring Framework that makes it easier to create stand-alone, production-ready applications quickly. It removes boilerplate configuration by providing:

  • Auto-configuration – automatically configures Spring and third-party libraries.
  • Embedded servers – ships with Tomcat/Jetty so you don’t need external setup.
  • Starter dependencies – pre-packaged dependency sets (e.g., spring-boot-starter-web).
  • Production-ready features – metrics, health checks, externalized config.

⚖️ Key Differences

Feature Spring Framework Spring Boot
Configuration Manual XML/Java-based setup required Auto-configuration reduces setup
Setup Complex, time-consuming Quick start with starters
Server Requires external server deployment Embedded Tomcat/Jetty available
Focus Broad enterprise app foundation Rapid development and microservices
Learning Curve Steeper, requires configuration knowledge Easier, beginner-friendly

✅ In short: Spring Boot is built on Spring Framework and simplifies development by handling configurations, offering production-ready defaults, and speeding up the creation of microservices and web applications.

Difference Between @SpringBootApplication and @Configuration + @EnableAutoConfiguration + @ComponentScan

In Spring Boot, the @SpringBootApplication annotation is a convenient shortcut that bundles three key Spring annotations. Let’s explore both approaches in detail.

1. What @SpringBootApplication Does

  • @Configuration – Marks the class as a configuration source (like XML in Spring).
  • @EnableAutoConfiguration – Triggers Spring Boot’s auto-configuration based on classpath dependencies.
  • @ComponentScan – Automatically detects components in the package and sub-packages.
@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

2. Using Them Separately

@Configuration
@EnableAutoConfiguration
@ComponentScan
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

This approach is equivalent but gives more control. You can omit any annotation if you don’t want a feature. For example:

  • Skip @EnableAutoConfiguration if you want to configure everything manually.
  • Skip @ComponentScan if you prefer explicit bean registration.

3. Key Differences

Aspect @SpringBootApplication @Configuration + @EnableAutoConfiguration + @ComponentScan
Convenience Single shortcut annotation Requires writing all three explicitly
Customization All three are always active Can include/exclude specific ones
Best Practice Preferred in modern Spring Boot apps Useful for fine-grained control

4. Summary

@SpringBootApplication is essentially a shorthand for @Configuration, @EnableAutoConfiguration, and @ComponentScan. Both work the same, but the shortcut keeps your codebase clean and concise.

Difference Between application.properties and application.yml in Spring Boot

In Spring Boot, configuration settings can be defined in either application.properties or application.yml. Both serve the same purpose but differ in syntax, readability, and structure.

1. application.properties

A simple key-value format, widely used and easy for small configurations: 

server.port=8081
spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=secret

2. application.yml

A hierarchical, YAML-based format that is cleaner for nested configurations: 

server:
  port: 8081

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    password: secret

3. Key Differences

Aspect application.properties application.yml
Format Flat key-value pairs Hierarchical, tree-like structure
Readability Good for small configs Better for complex/nested configs
Profiles application-dev.properties Profiles defined under --- blocks
Ease of Use Simple and familiar to many devs More expressive but whitespace-sensitive

4. Can You Use Both?

✅ Yes. Spring Boot allows you to use both files in the same project. If both are present:

  • application.properties and application.yml are loaded by default.
  • If a property is defined in both, the one that is loaded later in the order wins.
  • The typical loading order is: application.properties → application.yml.
  • You can override using profiles like application-dev.yml or application-test.properties.

5. Summary

Use application.properties for simple setups and application.yml for complex hierarchical configs. Both can coexist, and Spring Boot merges them, giving flexibility to developers.

What Are Spring Boot Starters? (With Examples)

In Spring Boot, starters are a set of pre-defined dependency descriptors that simplify adding commonly used libraries to your project. Instead of manually searching for and adding multiple individual dependencies, you just include one starter, and Spring Boot brings in everything you need.

1. Why Starters?

  • Convenience: No need to manage versions of multiple dependencies manually.
  • Consistency: Ensures compatible versions of libraries across Spring Boot projects.
  • Faster Development: Quickly set up common features like web apps, JPA, security, etc.

2. Examples of Common Starters

Starter Purpose
spring-boot-starter-web Build RESTful web applications using Spring MVC and Tomcat/Jetty.
spring-boot-starter-data-jpa Integrates Spring Data JPA with Hibernate for database access.
spring-boot-starter-security Adds authentication and authorization using Spring Security.
spring-boot-starter-test Includes JUnit, Hamcrest, and Mockito for testing.
spring-boot-starter-thymeleaf Enables server-side rendering with Thymeleaf template engine.
spring-boot-starter-actuator Adds monitoring and management endpoints for health, metrics, etc.

3. Example Usage in Maven

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

4. Example Usage in Gradle

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
}

5. Summary

Spring Boot starters are dependency bundles that remove the need for manual dependency management. For example, spring-boot-starter-web automatically brings in Spring MVC, Jackson for JSON, and Tomcat as the default server. This makes project setup faster, reduces compatibility issues, and promotes best practices.

Steps to Create a Spring (No Spring Boot) Project

1. Set Up Project Structure

  • Create a Maven or Gradle project.
  • Choose packaging:
    • jar → for console-based Spring apps.
    • war → for web-based Spring REST/MVC apps.
  • Define src/main/java for code and src/main/resources for configs.

2. Add Dependencies

Include the necessary Spring libraries:

  • Spring Core and Spring Context for basic IoC (Inversion of Control).
  • Spring Web MVC if you’re building REST APIs or web apps.
  • Spring Data JPA + Hibernate if using a database.
  • H2 Database for an in-memory DB.
  • Servlet API if deploying on Tomcat/Jetty.

3. Configure Application Context

Decide how you will define your beans:

  • XML configuration → use applicationContext.xml.
  • Java-based configuration → use @Configuration + @Bean.
  • Define your beans (services, repositories, etc.) here.

4. Set Up Web Layer (Optional if REST API)

Register a DispatcherServlet as the front controller:

  • Old school → define in web.xml.
  • Modern → implement WebApplicationInitializer in Java config.
  • Configure component scanning with @ComponentScan to detect controllers.

5. Create Model Layer

Define your entity classes:

  • Example: Book, User.
  • Annotate with @Entity, @Id, etc.

Create the Repository Layer — detailed guide

The repository layer (aka data access layer) is responsible for persisting and retrieving your domain objects. In a plain Spring + JPA project you have two main approaches: Spring Data JPA repositories (preferred for most apps) or manual DAO implementations using EntityManager. Below is a detailed comparison, patterns, best-practices and examples.

Overview — two approaches

  • Spring Data JPA (JpaRepository): declarative, generates queries from method names, supports paging/sorting, custom queries, and easy extension.
  • Manual DAO (EntityManager): full control, best for highly custom SQL/JPQL, complex performance tuning, batch processing, or legacy requirements.

1. Spring Data JPA repositories (recommended)

Spring Data saves boilerplate: you declare an interface and get CRUD, pagination, derived queries, and easy custom methods. It integrates well with transactions and Spring's exception translation infrastructure. 

// Example (conceptual)
public interface BookRepository extends JpaRepository {
    List findByAuthor(String author);
    Page findByTitleContaining(String titlePart, Pageable pageable);

    @Query("select b from Book b where b.title = :title")
    Optional findByExactTitle(@Param("title") String title);
}
  • Derived queries: method names like findByEmailAndActiveTrue generate JPQL automatically.
  • @Query support: JPQL or native SQL via @Query(..., nativeQuery = true).
  • Paging & sorting: return Page<T> and accept Pageable or Sort.
  • Modifying queries: use @Modifying + @Transactional for update/delete statements.
  • Projections: interface- or class-based projections to select subsets of columns/DTOs.
  • Custom implementations: mix a custom interface + implementation when you need behavior Spring Data can’t generate.

Custom implementation pattern

If you need custom behavior, create a separate interface and impl. Spring Data will detect it by naming: MyRepoCustom + MyRepoImpl.

When to choose Spring Data JPA: most CRUD apps, admin panels, services where rapid development and consistent behaviour matter.

2. Manual DAO using EntityManager

Manual DAOs give you precise control over queries, entity lifecycle operations, batching, and low-level optimizations. You write JPQL/Criteria API/native SQL and call persist, merge, remove, or use createQuery. 

// Conceptual snippet using EntityManager
@Repository
public class BookDao {
    @PersistenceContext
    private EntityManager em;

    public Book save(Book b) { em.persist(b); return b; }
    public Book find(Long id) { return em.find(Book.class, id); }
    public List findByAuthor(String author) {
        return em.createQuery("SELECT b FROM Book b WHERE b.author = :a", Book.class)
                 .setParameter("a", author)
                 .getResultList();
    }
}
  • Criteria API: for safe, type-safe dynamic queries.
  • Native queries: when you need vendor-specific SQL or extreme performance.
  • Batching & bulk ops: manual control helps for large imports/exports.
  • Transaction control: annotate service methods with @Transactional; DAOs should be simple.

When to choose manual DAO: complex queries, performance-critical paths, legacy DB schemas, or when Spring Data cannot express what you need efficiently.

3. Side-by-side: pros & cons

Aspect Spring Data JPA Manual DAO (EntityManager)
Boilerplate Very low — you get implementations automatically Higher — you write queries and CRUD logic yourself
Flexibility Good, but constrained by method naming and @Query Maximum — full control over SQL/JPQL and batching
Performance tuning Can be tuned, but sometimes awkward for complex batches Easier to optimize for bulk and native SQL paths
Learning curve Lower — quick to adopt Higher — must understand JPA internals

4. Patterns & best practices

  • Keep transactions at the service layer: annotate services with @Transactional rather than individual repository/DAO methods (keeps transaction boundaries clear).
  • Use repositories for standard CRUD + simple queries and introduce a custom DAO only for complex operations.
  • Custom repo implementations: for Spring Data, create a FooRepositoryCustom and FooRepositoryImpl and extend your main repository with the custom interface.
  • Exception translation: annotate DAOs with @Repository and register PersistenceExceptionTranslationPostProcessor (plain Spring) to convert JPA exceptions into Spring's DataAccessException.
  • Pagination & streaming: prefer Pageable and Stream or JPA scroll for large result sets (careful with memory).
  • Testing: load a minimal ApplicationContext for integration tests, use an in-memory DB (H2), mark tests transactional and rollback by default to isolate tests.
  • Package structure: keep repositories/daos in a dedicated package (e.g., com.example.repository) and configure component scanning accordingly.

5. Common pitfalls

  • Calling lazy associations outside a transaction → LazyInitializationException.
  • Using @Transactional on private methods or internal self-invocation — Spring proxies won’t apply transactions.
  • Overusing native queries — harder to maintain and not portable.
  • Placing custom repository impl in wrong package/name so Spring Data cannot find it (naming conventions matter).

Quick decision guide

Use Spring Data JPA for most applications (fast, consistent, less code). Use manual DAO for complex queries, heavy batch work or when you need absolute control over SQL and performance.

Required Configurations in a Plain Spring + JPA Project

Let’s list all the configurations you need to set up in a plain Spring (non-Boot) project with JPA so that your project can run properly with repositories, transactions, and REST APIs. Example: Spring Core + Spring Data JPA + H2.

  1. DataSource Configuration
    Provides DB connection details (URL, username, password, driver). Can be configured in XML or Java config. Needs to define:
    • JDBC driver class
    • DB URL
    • Username/password
    • Optional connection pool (HikariCP, Apache DBCP)
  2. JPA / EntityManagerFactory
    Configures JPA provider (Hibernate) and maps entities. Required beans:
    • LocalContainerEntityManagerFactoryBean
    • JpaVendorAdapter (e.g., HibernateJpaVendorAdapter)
    Settings:
    • Database dialect
    • Show SQL (optional)
    • DDL auto (create, update, validate)
    • Packages to scan for entities
  3. Transaction Manager
    Spring requires a PlatformTransactionManager bean for @Transactional. For JPA, use JpaTransactionManager. Associates EntityManagerFactory and manages transactions automatically.
  4. Enable Transaction Management
    Required to activate @Transactional annotation.
    • XML: <tx:annotation-driven />
    • Java Config: @EnableTransactionManagement
  5. Repository Configuration
    Spring Data JPA repositories require scanning and registration.
    • XML: <jpa:repositories base-package="com.example.repository" />
    • Java Config: @EnableJpaRepositories(basePackages="com.example.repository")
  6. Component Scanning
    Detects @Service, @Repository, @Controller, @RestController.
    • XML: <context:component-scan base-package="com.example" />
    • Java Config: @ComponentScan(basePackages="com.example")
  7. DispatcherServlet (Web Layer)
    For REST or MVC applications, the front controller must be registered.
    • XML: define in web.xml
    • Java Config: implement WebApplicationInitializer
  8. Properties / Config Settings
    Hibernate / JPA properties: hibernate.hbm2ddl.auto, hibernate.dialect, hibernate.show_sql. JDBC properties: URL, username, password, driver class. Can go in application.properties, database.properties, or directly in XML/Java config.
  9. Optional: Exception Translation
    Spring can convert JPA exceptions to DataAccessException.
    • XML: <bean class="org.springframework.dao.annotation.PersistenceExceptionTranslationPostProcessor"/>
    • Java Config: define @Bean PersistenceExceptionTranslationPostProcessor()
  10. Optional: View Resolver (If MVC, not REST)
    Only needed if returning JSP / Thymeleaf views. For REST APIs, usually return JSON via MappingJackson2HttpMessageConverter.

config class for JPA


Let’s create a complete Java configuration class for a plain Spring (non-Boot) project using 
Spring Data JPA + Hibernate + H2, including all necessary beans:

package com.example.config;

import javax.persistence.EntityManagerFactory;
import javax.sql.DataSource;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.dao.annotation.PersistenceExceptionTranslationPostProcessor;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.jdbc.datasource.DriverManagerDataSource;
import org.springframework.orm.jpa.JpaTransactionManager;
import org.springframework.orm.jpa.LocalContainerEntityManagerFactoryBean;
import org.springframework.orm.jpa.vendor.HibernateJpaVendorAdapter;
import org.springframework.transaction.annotation.EnableTransactionManagement;

import java.util.Properties;

@Configuration
@EnableTransactionManagement
@ComponentScan(basePackages = "com.example")
@EnableJpaRepositories(basePackages = "com.example.repository")
public class AppConfig {

    // 1. DataSource bean
    @Bean
    public DataSource dataSource() {
        DriverManagerDataSource dataSource = new DriverManagerDataSource();
        dataSource.setDriverClassName("org.h2.Driver");
        dataSource.setUrl("jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1");
        dataSource.setUsername("sa");
        dataSource.setPassword("");
        return dataSource;
    }

    // 2. EntityManagerFactory bean
    @Bean
    public LocalContainerEntityManagerFactoryBean entityManagerFactory() {
        LocalContainerEntityManagerFactoryBean em = new LocalContainerEntityManagerFactoryBean();
        em.setDataSource(dataSource());
        em.setPackagesToScan("com.example.model");

        HibernateJpaVendorAdapter vendorAdapter = new HibernateJpaVendorAdapter();
        vendorAdapter.setGenerateDdl(true);
        vendorAdapter.setShowSql(true);
        em.setJpaVendorAdapter(vendorAdapter);

        Properties jpaProperties = new Properties();
        jpaProperties.setProperty("hibernate.hbm2ddl.auto", "update");
        jpaProperties.setProperty("hibernate.dialect", "org.hibernate.dialect.H2Dialect");
        em.setJpaProperties(jpaProperties);

        return em;
    }

    // 3. TransactionManager bean
    @Bean
    public JpaTransactionManager transactionManager(EntityManagerFactory emf) {
        JpaTransactionManager tm = new JpaTransactionManager();
        tm.setEntityManagerFactory(emf);
        return tm;
    }

    // 4. Exception translation
    @Bean
    public PersistenceExceptionTranslationPostProcessor exceptionTranslation() {
        return new PersistenceExceptionTranslationPostProcessor();
    }
}

✅ Explanation of the Configuration

DataSource → connects to the database (H2 in-memory).

EntityManagerFactory → manages entities and integrates with Hibernate.

JpaTransactionManager → handles @Transactional methods.

EnableTransactionManagement → activates Spring’s annotation-driven transaction support.

EnableJpaRepositories → scans for repository interfaces.

ComponentScan → detects @Service, @Repository, @RestController.

PersistenceExceptionTranslationPostProcessor → translates JPA exceptions into Spring’s DataAccessException.

Hibernate properties → configure DDL, dialect, and SQL logging.

This single class fully replaces XML configuration and sets up Spring + JPA properly for a plain project.

🔹 Key Points for Manual EntityManager

No @EnableJpaRepositories → because you are not using Spring Data JPA repositories.

Your DAO classes will look like this:

@Repository
public class BookDao {
    @PersistenceContext
    private EntityManager em;

    public Book save(Book book) { em.persist(book); return book; }
    public Book find(Long id) { return em.find(Book.class, id); }
    public void delete(Book book) { em.remove(book); }
}


@Transactional should still be applied at the service layer for proper transaction management.

JPA (Java Persistence API)

It is a specification (a standard) that defines how Java objects map to database tables (ORM).
It’s just a set of interfaces and annotations, not an implementation.

Examples of JPA providers (implementations):

  • Hibernate (most common, used by default in Spring)
  • EclipseLink
  • OpenJPA

👉 Think of JPA as the contract.

🔹 EntityManager

It is a core interface defined by JPA specification.
Provided at runtime by the JPA implementation (e.g., Hibernate).
It manages the lifecycle of entities and is used to:

  • persist (save) objects → em.persist(entity)
  • find (read) objects → em.find(Entity.class, id)
  • merge (update) objects → em.merge(entity)
  • remove (delete) objects → em.remove(entity)
  • query data → em.createQuery("JPQL...")

👉 EntityManager is like the API you call to work with your database, while Hibernate (or another provider) does the heavy lifting.

🔹 Simple Analogy

JPA → The law (rules & contracts).
EntityManager → The lawyer (the person you talk to, following those rules).
Hibernate → The law firm (the actual implementation doing the job).

✅ So:

  • JPA defines the standard.
  • EntityManager is the interface defined by JPA.
  • Hibernate (or another JPA provider) gives you a real EntityManager instance at runtime.

Spring Data JPA Repositories

When you write a Spring Data JPA repository interface, like: 

public interface BookRepository extends JpaRepository<Book, Long> {
    List<Book> findByAuthor(String author);
}

👉 You don’t see EntityManager, but Spring Data JPA uses it under the hood.

🔹 How it works internally

  • You define the interface (e.g., BookRepository).
  • At runtime, Spring Data JPA creates a proxy class that implements your interface.
  • That proxy internally calls EntityManager methods (provided by Hibernate or another JPA provider).
  • save() → uses EntityManager.persist() or merge().
  • findById() → uses EntityManager.find().
  • delete() → uses EntityManager.remove().
  • Derived queries like findByAuthor() → Spring Data parses the method name, builds a JPQL query, and executes it using EntityManager.createQuery().

You just call repository methods, but behind the scenes, it’s EntityManager doing all DB interactions.

🔹 Analogy

You (developer) → use Repository interface (easy front desk).
Repository proxy → translates your request.
EntityManager → the real worker who talks to the database (via Hibernate).

So, yes:

  • 👉 Repositories = abstraction layer
  • 👉 EntityManager = core API
  • 👉 Hibernate = JPA implementation that powers EntityManager

Spring Project with Data Layer: Repositories vs EntityManager

Let’s outline step-by-step how to create a Spring project using:

  • 1️⃣ Spring Data JPA Repository interface (simpler, declarative)
  • 2️⃣ Manual EntityManager DAO (full control)

A. Using Spring Data JPA Repository Interface

  1. Set up project structure: Maven/Gradle project, src/main/java, src/main/resources, packaging (jar/war)
  2. Add dependencies: Spring Core, Spring Context, Spring Web MVC (if REST), Spring Data JPA, Hibernate, H2 (or other DB), Servlet API
  3. Configure ApplicationContext / Spring Config: DataSource, EntityManagerFactory, transaction management
  4. Create Model Layer (Entities): @Entity, @Id, map fields to DB columns
  5. Create Repository Interface: extend JpaRepository, optionally define query methods (findBy..., @Query)
  6. Create Service Layer: Autowire repository, annotate methods with @Transactional, add business logic
  7. Create Controller Layer (REST API): @RestController, inject service, return JSON
  8. Build and Run: deploy WAR to Tomcat or run JAR, test endpoints via Postman / curl

B. Using Manual EntityManager (DAO Pattern)

  1. Set up project structure: same as above
  2. Add dependencies: same as above
  3. Configure ApplicationContext / Spring Config: DataSource, EntityManagerFactory, transaction management
  4. Create Model Layer (Entities): same as above
  5. Create DAO Classes: @Repository, inject EntityManager (@PersistenceContext), implement CRUD manually (persist, find, merge, remove), implement custom queries using JPQL or Criteria API
  6. Create Service Layer: Autowire DAO, annotate service methods with @Transactional, add business logic
  7. Create Controller Layer (REST API): same as above, inject service, return JSON responses
  8. Build and Run: same as above

JPA with Spring vs Spring Boot

Ah, perfect question! Let’s break this down carefully. Using JPA with plain Spring vs Spring Boot mainly affects configuration, setup, and defaults, not the core JPA concepts.

🔹 1. Dependency Management

Plain Spring:

  • You have to manually include dependencies in pom.xml or build.gradle: Spring Core, Spring Context, Spring Data JPA, Hibernate, H2/other DB, Spring Web MVC, Servlet API, Jackson (for REST).
  • Versions must be compatible with each other.

Spring Boot:

  • You just add starters: spring-boot-starter-data-jpa, spring-boot-starter-web, spring-boot-starter-h2
  • Boot manages all compatible versions automatically.

🔹 2. Configuration

Plain Spring:

  • You manually configure: DataSource bean, EntityManagerFactory bean, TransactionManager bean, PersistenceUnit properties (dialect, DDL, etc.)

Spring Boot:

  • Auto-configures DataSource, EntityManagerFactory, TransactionManager based on application.properties / application.yml.
  • You can override defaults if needed. Example: just set 
    spring.datasource.url=jdbc:h2:mem:testdb
spring.datasource.username=sa
spring.jpa.hibernate.ddl-auto=update
  • Spring Boot creates all necessary beans automatically.

🔹 3. DispatcherServlet / Web Layer

  • Plain Spring: You must manually configure DispatcherServlet either via web.xml or WebApplicationInitializer.
  • Spring Boot: Boot auto-registers DispatcherServlet and maps / by default.

🔹 4. Repositories

  • Plain Spring: Need to define @EnableJpaRepositories(basePackages=...) in config.
  • Spring Boot: Auto-detects repositories in your main package/sub-packages. No extra annotation needed unless you want custom scanning.

Why DispatcherServlet is Not Configured in the AppConfig Class

Ah! This is an important point — and a very common question when moving from Spring Core to Spring Boot. Let’s clarify step by step.

1️⃣ DispatcherServlet in Spring MVC (non-Boot)

  • The DispatcherServlet is the front controller in Spring MVC.
  • It intercepts all HTTP requests and dispatches them to your controllers (@Controller or @RestController).
  • It is part of the web layer, not the JPA/data layer.
  • So in a plain Spring + JPA configuration class, we only define:
    • DataSource
    • EntityManagerFactory
    • TransactionManager
    • Component scanning for services/repositories
  • ⚠️ DispatcherServlet is not included here because this class is for application context / data layer, not for the web layer.

2️⃣ How DispatcherServlet is Normally Configured

Option A — XML (web.xml)

<servlet>
    <servlet-name>dispatcher</servlet-name>
    <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>
    <load-on-startup>1</load-on-startup>
</servlet>

<servlet-mapping>
    <servlet-name>dispatcher</servlet-name>
    <url-pattern>/</url-pattern>
</servlet-mapping>

Option B — Java Config (recommended, Servlet 3+)

public class WebAppInitializer implements WebApplicationInitializer {
    @Override
    public void onStartup(ServletContext servletContext) throws ServletException {
        AnnotationConfigWebApplicationContext context = new AnnotationConfigWebApplicationContext();
        context.register(AppConfig.class, WebMvcConfig.class);

        DispatcherServlet dispatcherServlet = new DispatcherServlet(context);
        ServletRegistration.Dynamic registration = servletContext.addServlet("dispatcher", dispatcherServlet);
        registration.setLoadOnStartup(1);
        registration.addMapping("/");
    }
}

AppConfig.class → your data/config layer
WebMvcConfig.class → your MVC/web layer (view resolvers, message converters, CORS, etc.)

3️⃣ In Spring Boot

  • DispatcherServlet is auto-registered by Spring Boot.
  • You don’t need web.xml or WebApplicationInitializer.
  • Just add @RestController classes, and the Boot auto-configures the front controller.

🔹 Key Takeaways

Aspect Plain Spring Spring Boot
DispatcherServlet registration Manual (web.xml or WebApplicationInitializer) Automatic
Location Web layer config, separate from AppConfig Auto-managed
Why not in AppConfig AppConfig is data/config layer, not web layer —

💡 Rule of thumb:
Data beans → AppConfig
Web beans → WebMvcConfig
DispatcherServlet registration → WebApplicationInitializer

Is it just a convention or can we do it in one class?

It’s not just a convention — you can technically register DispatcherServlet in the same configuration class as your data layer, but it’s not recommended.

  • Reason: Layer separation, flexibility, servlet lifecycle, clean initialization.

Example (works but not recommended):

@Configuration
@EnableTransactionManagement
@ComponentScan(basePackages = "com.example")
public class AppConfig implements WebApplicationInitializer {

    // Data beans
    @Bean
    public DataSource dataSource() { ... }

    @Bean
    public LocalContainerEntityManagerFactoryBean entityManagerFactory() { ... }

    @Bean
    public JpaTransactionManager transactionManager(EntityManagerFactory emf) { ... }

    // Web startup
    @Override
    public void onStartup(ServletContext servletContext) throws ServletException {
        AnnotationConfigWebApplicationContext ctx = new AnnotationConfigWebApplicationContext();
        ctx.register(AppConfig.class);

        DispatcherServlet dispatcher = new DispatcherServlet(ctx);
        ServletRegistration.Dynamic reg = servletContext.addServlet("dispatcher", dispatcher);
        reg.setLoadOnStartup(1);
        reg.addMapping("/");
    }
}

✅ Works, but now AppConfig mixes data layer and web layer, which is harder to maintain.
3️⃣ Best Practice: Separate AppConfig (data layer) from WebMvcConfig + WebApplicationInitializer (web layer). Keeps concerns modular, easier to test, and re-use beans in different contexts.
