Introduction to Services

A Kubernetes Service is an abstraction that defines a logical set of Pods and a policy by which to access them. Services enable network access to a set of Pods.

Services solve the problem of connecting clients to Pods in a dynamic environment where Pods can be created, destroyed, and moved between nodes.

Key Concept: Services provide a stable IP address and DNS name that clients can use to connect to your application, regardless of which Pods are currently running.

Service Features

  • Stable IP address and DNS name
  • Load balancing across Pods
  • Automatic service discovery
  • Multiple access patterns
  • Integration with external systems
  • Session affinity support

The Problem Services Solve

Without Services, clients would need to track individual Pod IP addresses, which change frequently as Pods are rescheduled or scaled. Services provide a stable endpoint that abstracts away the underlying Pod instability.

What is a Service?

Service Architecture

A Service acts as a stable network endpoint that routes traffic to one or more Pods. It uses labels and selectors to identify which Pods to target.

Client
Service app=frontend
Pod app=frontend
Pod app=frontend
Pod app=frontend

How Services Work

  1. Label Selection - Service uses label selectors to find matching Pods
  2. Endpoints Creation - Kubernetes creates Endpoints object with Pod IPs
  3. kube-proxy - Network rules are configured on each node
  4. Load Balancing - Traffic is distributed across available Pods
  5. DNS Registration - Service gets DNS entry in cluster DNS
  6. Continuous Updates - Endpoints updated automatically as Pods change

Key Components:

  • kube-proxy - Maintains network rules on nodes
  • CoreDNS - Provides DNS resolution for Services
  • Endpoints - Tracks Pod IP addresses for the Service

ClusterIP Service

ClusterIP Overview

ClusterIP is the default Service type. It exposes the Service on a cluster-internal IP address, making it only reachable from within the cluster.

When to Use ClusterIP:

  • • Communication between microservices
  • • Database access from application Pods
  • • Internal APIs and backend services
  • • Any service that shouldn't be exposed externally

Key Characteristics:

  • Only accessible within the cluster
  • Stable virtual IP address
  • Automatic DNS registration
  • Load balancing across Pods

ClusterIP Example


apiVersion: v1
kind: Service
metadata:
  name: backend-service
  labels:
    app: backend
spec:
  type: ClusterIP  # This is optional (default)
  selector:
    app: backend
    tier: api
  ports:
  - name: http
    port: 80
    targetPort: 8080
    protocol: TCP
  - name: metrics
    port: 9090
    targetPort: 9090
    protocol: TCP

Access Patterns

DNS Access

Services are automatically available via DNS within the cluster:

backend-service.default.svc.cluster.local

Environment Variables

Pods get environment variables for Services:

BACKEND_SERVICE_SERVICE_HOST=10.96.105.15
BACKEND_SERVICE_SERVICE_PORT=80

NodePort Service

NodePort Overview

NodePort exposes the Service on each Node's IP at a static port. The Service becomes accessible from outside the cluster by contacting any node on that port.

When to Use NodePort:

  • • Development and testing environments
  • • Bare-metal Kubernetes clusters
  • • Simple external access without cloud load balancer
  • • When you need direct node access

Port Ranges:

  • NodePort Range: 30000-32767 (configurable)
  • Automatically assigned if not specified
  • Manually configurable within the valid range

NodePort Example


apiVersion: v1
kind: Service
metadata:
  name: webapp-nodeport
  labels:
    app: webapp
spec:
  type: NodePort
  selector:
    app: webapp
    tier: frontend
  ports:
  - name: http
    port: 80
    targetPort: 8080
    nodePort: 30080  # Optional: specify custom port
    protocol: TCP

Access Patterns

External Access

Access via any node's IP address and the NodePort:

http://<node-ip>:30080

Internal Access

Still accessible internally via ClusterIP and DNS:

http://webapp-nodeport:80

LoadBalancer Service

LoadBalancer Overview

LoadBalancer exposes the Service externally using a cloud provider's load balancer. This is the standard way to expose services in cloud environments.

When to Use LoadBalancer:

  • • Production applications in cloud environments
  • • When you need cloud load balancer features
  • • Automatic SSL termination and health checks
  • • High availability and scalability requirements

Cloud Provider Integration:

  • AWS → Elastic Load Balancer (ELB)
  • GCP → Cloud Load Balancing
  • Azure → Azure Load Balancer
  • Automatically provisions and configures load balancer

LoadBalancer Example


apiVersion: v1
kind: Service
metadata:
  name: webapp-loadbalancer
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    service.beta.kubernetes.io/aws-load-balancer-ssl-cert: "arn:aws:acm..."
spec:
  type: LoadBalancer
  selector:
    app: webapp
  ports:
  - name: https
    port: 443
    targetPort: 8080
    protocol: TCP
  - name: http
    port: 80
    targetPort: 8080
    protocol: TCP
  externalTrafficPolicy: Local

External Traffic Policy

Cluster (Default)

Traffic is load balanced across all cluster nodes

  • ✓ Preserves source IP
  • ✗ Extra network hop possible
  • ✓ Better load distribution

Local

Traffic is only sent to nodes running the Pod

  • ✓ Preserves source IP
  • ✓ No extra network hops
  • ✗ Uneven load distribution

Service Specification

Services are defined using YAML configuration files. Understanding the complete specification is essential for effective service management.

Complete Service Definition


apiVersion: v1
kind: Service
metadata:
  name: complete-service
  namespace: production
  labels:
    app: my-application
    environment: production
  annotations:
    cloud-provider-specific: "value"
spec:
  type: LoadBalancer
  selector:
    app: my-application
    tier: frontend
  ports:
  - name: web
    protocol: TCP
    port: 80
    targetPort: 8080
    nodePort: 30080  # For NodePort type
  - name: metrics
    protocol: TCP
    port: 9090
    targetPort: 9090
  clusterIP: 10.96.105.15  # Optional: specify ClusterIP
  externalIPs:
  - 192.168.1.100
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800
  externalTrafficPolicy: Local
  healthCheckNodePort: 32456  # For LoadBalancer with Local policy
  loadBalancerIP: "78.11.24.19"  # For LoadBalancer type
  ipFamilyPolicy: RequireDualStack
  ipFamilies:
  - IPv6
  - IPv4

Key Specification Fields

spec.selector

Label query over Pods to target. Required for most Service types.

spec.ports

List of ports exposed by the Service with protocol, port, and targetPort.

spec.sessionAffinity

Session affinity type (None, ClientIP). Defaults to None.

spec.externalTrafficPolicy

Controls routing of external traffic (Cluster, Local).

spec.clusterIP

ClusterIP address. Set to "None" for headless services.

spec.loadBalancerIP

LoadBalancer IP address (cloud providers).

DNS & Service Discovery

Kubernetes provides built-in DNS-based service discovery, making it easy for applications to find and communicate with Services.

DNS Naming Convention

Same Namespace

service-name

Short name resolves within the same namespace

Cross Namespace

service-name.namespace-name

Namespace-qualified name for cross-namespace access

Fully Qualified

service-name.namespace-name.svc.cluster.local

Full DNS name for explicit resolution

Service Discovery Methods

DNS-Based Discovery

Applications use DNS names to resolve Services

nslookup backend-service

Environment Variables

Automatic environment variables in Pods

BACKEND_SERVICE_SERVICE_HOST
BACKEND_SERVICE_SERVICE_PORT

API-Based Discovery

Direct Kubernetes API queries for Service information

Headless Services


apiVersion: v1
kind: Service
metadata:
  name: headless-service
spec:
  clusterIP: None  # This makes it headless
  selector:
    app: stateful-app
  ports:
  - port: 80
    targetPort: 8080

Headless services return individual Pod IPs instead of a Service IP, useful for stateful applications and direct Pod access.

kubectl Service Commands

Essential Service Commands

Basic Operations

kubectl create service clusterip my-svc --tcp=80:8080
kubectl apply -f service.yaml
kubectl get services
kubectl describe service my-service

Debugging & Inspection

kubectl get endpoints my-service
kubectl logs -l app=my-app
kubectl port-forward service/my-service 8080:80
kubectl exec -it pod-name -- nslookup service-name

Advanced Commands

Command Description
kubectl edit service/my-service Edit service configuration in default editor
kubectl patch service my-service -p '{"spec":{"type":"LoadBalancer"}}' Patch service type
kubectl get service my-service -o yaml Get service configuration in YAML format
kubectl expose deployment my-deployment --port=80 --target-port=8080 Create service from deployment

Service Best Practices

Configuration Guidelines

Use Meaningful Service Names

Choose descriptive names that reflect the service purpose and follow naming conventions.

Define Clear Selectors

Use specific label selectors to ensure Services target the correct Pods.

Use Appropriate Service Types

Choose the right Service type based on access requirements and environment.

Operational Practices

Monitor Endpoints

Regularly check Service endpoints to ensure they're correctly targeting Pods.

Use Readiness Probes

Implement readiness probes to ensure Services only route to healthy Pods.

Secure External Services

Use Network Policies and proper authentication for externally exposed Services.

Pro Tip: Service Mesh Integration

For advanced networking features like mutual TLS, traffic splitting, and detailed metrics, consider using a service mesh (Istio, Linkerd) alongside Kubernetes Services.
