Introduction to Deployments

A Deployment provides declarative updates for Pods and ReplicaSets. You describe a desired state in a Deployment, and the Deployment Controller changes the actual state to the desired state at a controlled rate.

Deployments are the recommended way to manage stateless applications in Kubernetes, providing powerful features for rolling updates, rollbacks, and scaling.

Key Benefit: Deployments abstract away the complexity of managing individual Pods and provide zero-downtime updates through rolling deployment strategies.

Deployment Features

  • Declarative application updates
  • Rolling updates and rollbacks
  • Scalability and self-healing
  • Version tracking and history
  • Multiple update strategies
  • Integration with Services

What is a Deployment?

Deployment Architecture

A Deployment manages a ReplicaSet, which in turn manages the Pods. This layered approach provides the foundation for declarative updates and rollbacks.

How Deployments Work

  1. Desired State Declaration - You define the desired state in a Deployment manifest
  2. ReplicaSet Creation - Deployment creates a ReplicaSet to manage Pod replicas
  3. Pod Management - ReplicaSet ensures the specified number of Pod replicas are running
  4. Update Coordination - When updating, Deployment creates a new ReplicaSet and manages the transition
  5. Health Monitoring - Continuously monitors Pod health and replaces failed Pods

Deployment vs Pod

Understanding when to use Deployments versus bare Pods is crucial for effective Kubernetes application management.

Aspect Deployment Bare Pod
Use Case Stateless applications, web servers, APIs One-off tasks, init containers, debugging
Scaling Automatic scaling and self-healing Manual management only
Updates Rolling updates with zero downtime Manual recreation required
Rollbacks Automatic rollback capability No built-in rollback
Production Use Recommended for production Not recommended for production

Important Note

You should almost always use Deployments instead of bare Pods for production workloads. Bare Pods are not restarted if they fail and don't support rolling updates.

Deployment Specification

Deployments are defined using YAML configuration files. Understanding the specification is key to effectively managing your applications.

Complete Deployment Example


apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
    environment: production
  annotations:
    deployment.kubernetes.io/revision: "1"
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
  minReadySeconds: 10
  revisionHistoryLimit: 10
  progressDeadlineSeconds: 600
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.21
        ports:
        - containerPort: 80
        resources:
          requests:
            memory: "64Mi"
            cpu: "250m"
          limits:
            memory: "128Mi"
            cpu: "500m"
        livenessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 5

Key Specification Fields

spec.replicas

Number of desired Pod replicas

spec.selector

Label selector to identify managed Pods

spec.strategy

Update strategy (RollingUpdate or Recreate)

spec.template

Pod template specification

spec.revisionHistoryLimit

Number of old ReplicaSets to retain

spec.progressDeadlineSeconds

Maximum time for deployment progress

Update Strategies

Kubernetes Deployments support different update strategies to control how application updates are rolled out.

RollingUpdate

Default Strategy

Gradually replaces old Pods with new ones while maintaining application availability.

Configuration:

maxSurge: 25%
maxUnavailable: 25%
  • Zero downtime updates
  • Gradual traffic migration
  • Automatic rollback on failure

Recreate

Simple Strategy

Kills all existing Pods before creating new ones. Causes downtime during update.

Use Cases:

• Database schema migrations
• Breaking changes
• Stateful applications
  • Application downtime
  • Simple to understand
  • Good for stateful apps

RollingUpdate Parameters

maxSurge

Maximum number of Pods that can be created over the desired number of Pods during an update.

Can be a number (e.g., 2) or percentage (e.g., 25%)

maxUnavailable

Maximum number of Pods that can be unavailable during the update process.

Can be a number (e.g., 1) or percentage (e.g., 25%)

Rolling Update Example


apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp-deployment
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2
      maxUnavailable: 1
  replicas: 4
  template:
    # ... pod template ...

Rolling Back Deployments

Kubernetes maintains a revision history of your Deployments, allowing you to roll back to previous versions if issues occur.

Revision History

Each time you update a Deployment, Kubernetes creates a new revision. The revisionHistoryLimit field controls how many old ReplicaSets are retained.

View Deployment History:

kubectl rollout history deployment/my-app

Best Practice:

Set revisionHistoryLimit: 10 to keep sufficient history for rollbacks while managing cluster resources.

Rollback Commands

Rollback to previous version

kubectl rollout undo deployment/my-app

Rollback to specific revision

kubectl rollout undo deployment/my-app --to-revision=3

Check rollout status

kubectl rollout status deployment/my-app

Rollback Process

  1. Kubernetes identifies the previous ReplicaSet from the revision history
  2. Scales down the current ReplicaSet to 0 replicas
  3. Scales up the previous ReplicaSet to the desired number of replicas
  4. Updates the Deployment's revision history
  5. Monitors the rollout to ensure successful completion

Scaling Deployments

Deployments can be scaled manually or automatically to handle varying loads and ensure application availability.

Manual Scaling

Scale deployments using kubectl commands

kubectl scale deployment

Horizontal Pod Autoscaler

Automatic scaling based on CPU/Memory usage

kubectl autoscale deployment

Custom Metrics

Scale based on custom application metrics

Custom Metrics API

Scaling Commands

Manual Scaling

kubectl scale deployment/my-app --replicas=5
kubectl scale deployment/my-app --replicas=3

Horizontal Pod Autoscaler

kubectl autoscale deployment/my-app --min=2 --max=10 --cpu-percent=80
kubectl get hpa

HPA Configuration Example


apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: webapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: webapp-deployment
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80

Advanced Commands

Command Description
kubectl edit deployment/my-app Edit deployment configuration in default editor
kubectl patch deployment/my-app -p '{"spec":{"replicas":5}}' Patch deployment with JSON
kubectl get deployment my-app -o yaml Get deployment configuration in YAML format
kubectl rollout restart deployment/my-app Restart all Pods in deployment

Deployment Best Practices

Configuration Guidelines

Use RollingUpdate Strategy

Always use RollingUpdate for zero-downtime deployments in production.

Set Resource Limits

Always define CPU and memory requests and limits for predictable performance.

Configure Health Checks

Implement liveness and readiness probes for reliable self-healing.

Operational Practices

Maintain Revision History

Set appropriate revisionHistoryLimit for rollback capability.

Use Meaningful Labels

Apply consistent labels for better organization and service discovery.

Monitor Rollout Status

Always check rollout status after updates and configure progress deadlines.

Pro Tip

Use kubectl rollout status in your CI/CD pipelines to wait for deployments to complete successfully. This ensures your pipeline fails if the deployment encounters issues.
