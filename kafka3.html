📚 Kafka

What is ZooKeeper in Kafka?

Apache ZooKeeper is a centralized coordination service used in older Kafka versions (pre-3.3) to manage cluster metadata and broker coordination. It ensures proper leader election, metadata consistency, and smooth operation of the Kafka cluster.

1. Cluster Metadata Management

ZooKeeper stores critical metadata such as topics, partitions, brokers, and ACLs, ensuring that all brokers in the Kafka cluster stay synchronized.

2. Controller Election

ZooKeeper elects a Controller Broker, which manages partition leaders and ensures fault tolerance when brokers go offline.

3. Broker Registration

Brokers register themselves in ZooKeeper using ephemeral znodes, which automatically get removed if a broker disconnects.

4. Metadata Change Notifications

ZooKeeper notifies brokers about metadata changes, such as new topic creation or leader reassignments.

5. Client Interaction

Kafka clients (producers and consumers) never talk to ZooKeeper directly. They interact only with Kafka brokers, which handle ZooKeeper communication behind the scenes.

Conclusion

ZooKeeper was a critical part of Kafka’s architecture before version 3.3. With KRaft mode (Kafka Raft Metadata mode), Kafka has eliminated the need for ZooKeeper, making cluster management more efficient and self-contained.

⚙️ Kafka Core Components (Legacy vs Modern)

Role in Kafka (pre-KRaft):

  • Keeps cluster metadata (topics, partitions, broker IDs).
  • Elects the controller broker.
  • Tracks broker liveness (via ephemeral znodes).
  • Stores configurations and ACLs.
  • Does NOT store messages → only manages coordination.

👉 Think of ZooKeeper as the “cluster manager / coordinator”.

What it is: A Kafka server process (usually one per machine or container).

Responsibilities:

  • Stores messages in topics/partitions.
  • Handles producer writes and consumer reads.
  • Manages replication (leader/follower roles).
  • Communicates with ZooKeeper (in old mode) or Controller Quorum (in KRaft).
  • Each broker has a unique broker.id.
  • A broker can host thousands of partitions.

👉 Think of a broker as the “data warehouse + messenger”.

🔹 3. Node

What it is: A physical machine or VM where Kafka runs.

A node can run:

  • One Kafka broker process.
  • One ZooKeeper process (in old clusters).
  • Or both (in small test clusters, though not best practice).

👉 In most setups: One node = one broker (Kafka server).
But node is hardware/OS, while broker is the Kafka process running on it.

⚙️ How KRaft Works in Kafka

🔹 Controller Quorum

In KRaft mode, a controller quorum replaces ZooKeeper. It is a small set of Kafka nodes (usually 3 or 5) that maintain all cluster metadata, including topic configurations, partition assignments, and broker registrations. The quorum uses the Raft consensus protocol to ensure that all metadata changes are consistent and fault-tolerant.

🔹 Brokers and Roles

Kafka nodes can act as brokers, controllers, or both. Brokers store and serve messages for producers and consumers, while controller nodes manage metadata. Using process.roles, a node can be configured to handle both roles, making deployment flexible.

🔹 Leader Election

KRaft uses Raft to elect a controller leader from the quorum. The leader is responsible for processing all metadata changes, such as creating or deleting topics, updating partition assignments, or handling broker joins/leaves. Raft ensures that metadata updates are committed only after a majority of controllers agree, preventing inconsistencies.

🔹 Metadata Storage

All metadata is stored in special Kafka logs inside the controller quorum. This allows the cluster to recover state after failures without requiring an external system like ZooKeeper. Brokers query the controllers to get up-to-date metadata for topics and partitions.

🔹 Broker Coordination

Regular brokers communicate with the controller quorum to register themselves, report health, and learn the current partition leadership. The controllers notify brokers about leadership changes or reassignments automatically. This removes the need for a separate coordination service.

🔹 Fault Tolerance

Since KRaft uses Raft, the controller quorum can tolerate failures of some nodes as long as a majority of controllers remain operational. This guarantees metadata consistency and enables automatic failover of controller leadership without downtime.

✅ Summary

KRaft integrates cluster metadata management directly into Kafka using a Raft-based controller quorum. Brokers focus on message storage, controllers focus on metadata, and Raft ensures strong consistency, leader election, and fault tolerance—all without ZooKeeper.

Kafka ISR (In-Sync Replicas) – Detailed Explanation

ISR (In-Sync Replicas) is the set of replicas that are fully caught up with the leader for a Kafka partition. ISR ensures that Kafka can provide **strong durability and consistency guarantees** for all writes.

What is ISR?

- ISR stands for In-Sync Replicas.
- It includes the leader and all follower replicas that are fully caught up.
- Only replicas in ISR are eligible to acknowledge writes when strong durability is required.

How ISR Works

1. Each partition has a leader and multiple followers.
2. Followers replicate data asynchronously from the leader.
3. Kafka maintains a list of replicas fully caught up with the leader – the ISR.
4. Replicas that lag too far behind are removed from ISR until they catch up.
5. ISR is used to decide if a write can succeed based on min.insync.replicas.

ISR vs Replication Factor

| Aspect | Description |
|-----------------------------|-------------|
| Replication Factor | Total number of replicas for a partition |
| ISR | Subset of replicas fully caught up with the leader |
| min.insync.replicas | Minimum number of ISR members required for successful write |

Key: ISR ≤ Replication Factor. Not all replicas are guaranteed to be in-sync at all times.

Example Scenario

Topic partition has replication factor 3, min.insync.replicas = 2.
ISR = {R1 (leader), R2} → Write succeeds.
R2 goes offline → ISR = {R1} → ISR < min.insync.replicas → Writes fail → NotEnoughReplicasException.

ISR and Failover

- If a leader fails, one of the in-sync followers is elected as the new leader.
- Followers not in ISR are not eligible to become leader, preventing stale data from being served.
- This ensures **strong consistency and fault tolerance** in Kafka.

Monitoring ISR

Use the Kafka CLI to check ISR for a partition: 

kafka-topics.sh --describe --topic my-topic --bootstrap-server localhost:9092

Sample output: 

Partition: 0  Leader: 1  Replicas: 1,2,3  ISR: 1,2
Here, ISR = {1,2} → replicas 1 and 2 are in-sync; replica 3 is behind.

Summary

  • ISR = replicas fully caught up with the leader.
  • Essential for durable, consistent writes in Kafka.
  • Writes with acks=all rely on ISR and min.insync.replicas.
  • Monitoring ISR is critical to prevent NotEnoughReplicasException.

Kafka NotEnoughReplicasException: Causes & Solutions

The NotEnoughReplicasException occurs when a producer tries to send a message, but the Kafka broker cannot meet the required number of in-sync replicas (ISR) for a partition. This ensures that Kafka maintains strong durability and consistency guarantees.

Kafka Replication Basics

- Each topic partition has multiple replicas for fault tolerance.
- One replica acts as the leader and handles all reads and writes; other replicas are followers.
- Kafka tracks in-sync replicas (ISR), which are replicas fully caught up with the leader.
- min.insync.replicas defines the minimum number of replicas required to acknowledge a write.

Common Causes

  • Some replicas are offline: When one or more replicas are not reachable, ISR falls below min.insync.replicas. Producers with acks=all will get NotEnoughReplicasException.
  • Replication factor > available brokers: If a topic has replication factor 3 but only 2 brokers exist, Kafka cannot create enough replicas. Writes requiring all replicas may fail.
  • Under-replicated partitions: Followers lagging behind the leader reduce ISR. If ISR < min.insync.replicas, the exception may occur.

Key idea: The exception is triggered whenever the number of available in-sync replicas is insufficient to satisfy producer write requirements.

How NotEnoughReplicasException Happens

1. Producer sends message with acks=all.
2. Broker checks ISR (replicas that are fully caught up).
3. ISR < min.insync.replicas.
4. Broker rejects message and throws NotEnoughReplicasException.

This mechanism ensures **strong durability**, preventing writes from succeeding when replication guarantees cannot be met.

How to Fix

  • Bring offline brokers back online to restore ISR.
  • Ensure replication factor ≤ number of brokers when creating topics.
  • Reduce min.insync.replicas (trade-off: reduces durability).
  • Adjust producer acks to 1 if full replication acknowledgment is not critical.
  • Monitor under-replicated partitions using kafka-topics.sh --describe or metrics.

Real-World Example

A topic has replication factor 3 and min.insync.replicas=2. One broker goes offline:

  • ISR drops to 2 → still meets min.insync.replicas → writes succeed.
  • Another broker goes offline → ISR drops to 1 → less than min.insync.replicas → producer with acks=all receives NotEnoughReplicasException.

Kafka Broker Down & ISR Drops to 0

In Kafka, ISR (In-Sync Replica) is the set of replicas fully caught up with the leader’s log. Producers can safely write messages only if enough replicas are in sync, depending on the min.insync.replicas configuration. When a broker goes down and ISR for some partitions drops to 0, it means no replica is fully in sync — a critical situation.

1️⃣ Causes

  • Broker crash or shutdown: The broker hosting the leader or followers goes down unexpectedly. Followers cannot replicate messages, and the leader may be unavailable.
  • Network partition: Followers temporarily lose connectivity to the leader. Kafka considers them out-of-sync, decreasing ISR.
  • Disk or hardware failure: A broker cannot write to disk or serve requests. Replication stops, ISR drops.

2️⃣ Consequences

Issue Explanation
Data loss risk If acks=all is used, producers require all ISR members to acknowledge writes. With ISR=0, messages cannot be confirmed. If a new leader is elected and no replica has all messages, unreplicated messages are lost.
Producers fail Producers configured with acks=all will receive NotEnoughReplicasException because no in-sync replicas exist. This halts message production until ISR recovers.

Additional Effects:

  • Consumer read availability may decrease if the leader broker is down.
  • Partitions may temporarily become unavailable until a new leader is elected.

3️⃣ Internal Kafka Behavior

  • Broker goes down → followers stop replicating.
  • Kafka detects ISR drop → partitions with ISR < min.insync.replicas become under-replicated.
  • Producers requiring acknowledgment from all ISR members fail writes (NotEnoughReplicasException).
  • Once a new leader is elected from available replicas (if any), ISR is recalculated.

Kafka Guarantees: Strong Durability & Replication Consistency

Kafka provides **strong durability** and **replication consistency**, ensuring that messages are never lost and replicated reliably across brokers, even in case of failures.

1. Strong Durability

Durability ensures that once a message is acknowledged as written, it **will not be lost**, even if brokers fail.

  • Append-Only Log: Partitions store messages on disk; data is never overwritten.
  • Replication: Each partition has a leader and multiple followers. Writes are replicated to ISR.
  • Acknowledgment Settings:
    • acks=0 → No durability guarantee
    • acks=1 → Durable if leader survives
    • acks=all / -1 → Waits for all ISR replicas → strong durability
  • min.insync.replicas: Minimum ISR members required to acknowledge a write. If ISR < min.insync.replicas, broker rejects write → ensures durability.

Example: Replication factor = 3, min.insync.replicas = 2 → write succeeds if leader + 1 follower acknowledge. Even if one broker fails, data is durable.

2. Replication Consistency

Consistency ensures that all followers eventually have the same data as the leader, and only in-sync replicas can become leader on failover.

  • Leader-Follower Model: All writes go to leader, followers replicate asynchronously.
  • ISR (In-Sync Replicas): Only replicas fully caught up are in ISR. Producers with acks=all rely on ISR for consistency.
  • Follower Catch-Up: Lagging replicas are removed from ISR; once they catch up, they rejoin ISR.
  • Leader Failover: Only replicas in ISR are eligible to become new leader, preventing stale data from being served.

Example: Leader L1, followers F1, F2. L1 receives message M1 → replicated to F1 (in ISR), F2 lagging. Producer with acks=all → write acknowledged → consistency guaranteed. F2 catches up → ISR includes F2 → fully consistent.

3. Key Points

  • Durability = data written to disk + replicated to ISR.
  • Consistency = all in-sync replicas eventually have the same data.
  • Leader failover uses ISR to prevent stale data.
  • Configurations like acks and min.insync.replicas allow tuning durability vs performance.

Effect: More messages per network call → fewer round-trips → higher throughput.

  • High round-trip time due to distance between producer and broker

Effect: Consumers with more partitions fall behind → higher lag.

Kafka Consumer Lag Troubleshooting

Consumer lag occurs when Kafka consumers in a group fall behind in processing messages from a topic. Even if brokers are healthy, lag can indicate processing bottlenecks, uneven partition assignment, or network issues.

1️⃣ What is Consumer Lag?

Consumer lag is the difference between the latest offset in a partition and the last committed offset by a consumer. It shows how far behind a consumer is in processing messages.

Example: Partition latest offset = 1500, consumer committed offset = 1400 → lag = 100 messages.

2️⃣ Common Causes of Consumer Lag

  • Slow consumer processing: Consumers take too long to process each message.
  • Uneven partition assignment: Some consumers handle multiple hot partitions, others remain idle.
  • Network congestion: Slow connectivity between brokers and consumers.
  • Blocking operations: Consumer code performing synchronous/blocking I/O delays offset commits.
  • Large message batches: Consumers taking long to deserialize or process large messages.

3️⃣ Troubleshooting Steps

  1. Check Consumer Lag Metrics: Use Kafka tools like kafka-consumer-groups.sh or monitoring dashboards to identify lag per partition and per consumer.
  2. Inspect Consumer Code: Identify any blocking or long-running operations. Consider processing messages asynchronously or using parallel processing.
  3. Review Partition Assignment: Ensure partitions are evenly distributed among consumers in the group. Use round-robin or sticky assignor strategies for better balance.
  4. Optimize Batch Sizes: Adjust fetch.min.bytes, fetch.max.wait.ms, and max.poll.records to allow consumers to fetch and process batches efficiently.
  5. Check Network and Broker Load: Verify there is no network bottleneck or broker overload affecting message delivery.
  6. Enable Parallel Processing: If messages are independent, consider processing them in parallel threads to reduce lag.
  7. Offset Commit Strategy: Ensure offsets are committed appropriately. Use asynchronous commits or commit after successful processing to avoid repeated processing without progress.

4️⃣ Resolution Strategies

  • Increase the number of consumers if partitions allow for more parallelism.
  • Optimize consumer processing logic to reduce per-message processing time.
  • Balance partitions evenly across consumers using proper assignor strategy.
  • Scale up consumers horizontally to handle higher message throughput.
  • Monitor consumer lag continuously to detect new bottlenecks early.

5️⃣ Key Takeaways

Kafka Duplicate Messages – Causes & Remedies

Kafka consumers may sometimes receive the same message multiple times due to at-least-once delivery semantics. Identifying the root causes and applying proper remedies can reduce duplicates or help achieve exactly-once processing.

1. Consumer Not Committing Offsets Properly

Consumers track their read position using offsets. If offsets are not committed correctly or frequently enough, messages may be re-read after a consumer crash or restart.

Effect: Messages are processed multiple times → duplicates occur.

Remedy: Commit offsets only after successful message processing. Use synchronous or asynchronous commit depending on requirements.

2. Rebalance Occurred Before Offset Commit

Consumer groups periodically rebalance when a consumer joins or leaves the group, or when partitions are reassigned. If a rebalance occurs before the latest offsets are committed, messages may be reassigned to another consumer and reprocessed.

Effect: Messages are consumed again by another consumer → duplicates.

Remedy: Commit offsets frequently, adjust max.poll.interval.ms to allow sufficient processing time, and implement idempotent processing logic.

3. Producer Retries Without Idempotence

Kafka producers may retry sending messages on network failures or broker unavailability. Without enabling idempotence, retries can result in the same message being written multiple times in the topic.

Effect: Consumers see duplicate messages even if the producer logically sent each message only once.

Remedy: Enable enable.idempotence=true for the producer, or use Kafka transactions to achieve exactly-once semantics.

4. Summary of Causes & Remedies

Cause Effect on Duplicates Remedy
Consumer not committing offsets properly Messages reprocessed after restart → duplicates Commit offsets after successful processing, use auto-commit wisely
Rebalance before offset commit Another consumer reprocesses messages → duplicates Commit frequently, adjust max.poll.interval.ms, implement idempotent processing
Producer retries without idempotence Broker writes the same message multiple times → duplicates Enable enable.idempotence=true or use Kafka transactions

5. Key Takeaways

  • Kafka defaults to at-least-once delivery → duplicates are possible.
  • Duplicate messages often arise from offset mismanagement, rebalances, or non-idempotent producer retries.
  • Exactly-once processing requires a combination of idempotent producers, transactions, and careful offset commits.

Kafka Offset Committing – Explained

Kafka consumers track which messages they have processed using offsets. Proper offset management ensures reliable processing and avoids duplicates or message loss.

1. Types of Offset Commit

a) Automatic Offset Commit

Controlled via enable.auto.commit=true. Kafka commits the latest offset automatically at intervals defined by auto.commit.interval.ms, regardless of whether messages were fully processed.

Risk: Crashes between auto-commit intervals can lead to skipped or duplicate messages.

Example: Consumer reads messages 1–3, auto-commit interval 5 seconds, crashes before processing message 3 fully → message 3 may be considered processed, causing duplicates or message loss.

b) Manual Offset Commit

Controlled via enable.auto.commit=false. Consumers explicitly commit offsets only after successfully processing messages.

Methods:

  • commitSync() – synchronous commit, waits for broker acknowledgment.
  • commitAsync() – asynchronous commit, non-blocking but may fail silently.

Reduces duplicates because only successfully processed messages are committed.

2. When Offset Commit Happens

  • Automatic: Periodically based on auto.commit.interval.ms.
  • Manual: Only when commitSync() or commitAsync() is called.
  • Rebalance: Uncommitted offsets may be reassigned to another consumer, leading to potential reprocessing.

3. Offset Storage

Offsets are stored in the special Kafka topic __consumer_offsets, ensuring high durability. Consumers fetch the last committed offset on startup.

4. Common Issues

Issue Cause Effect
Duplicate messages Consumer crashes before manual commit Messages reprocessed on restart
Message loss Auto-commit occurs before processing completes Messages may be skipped or lost
Offset out of sync Long processing without commit Consumer may lag or process duplicates after rebalance

5. Best Practices

  • Use manual offset commits for critical applications.
  • Commit offsets after successfully processing messages.
  • Use commitSync() for reliability; commitAsync() for high throughput.
  • Handle rebalances properly using ConsumerRebalanceListener.
  • Implement idempotent processing logic to handle duplicates safely.

6. Example Scenario

Consumer crashes before auto-commit → Kafka resends Order1 and Order2 on restart.

Without manual commits or idempotent logic, Order2 is processed twice, leading to duplicates.

Key Takeaways

  • Offsets track which messages have been processed by consumers.
  • Automatic commits are convenient but can lead to duplicates or message loss.
  • Manual commits give control and reduce duplicate processing.
  • Combine offset management with idempotent processing and proper rebalance handling for reliability.

Kafka Broker Disk Full – Consequences & Remedies

When a Kafka broker runs out of disk space, it impacts writes, partition availability, and replication. Understanding the internal behavior helps prevent production disruptions and maintain high availability.

1. Stops Accepting Writes

Kafka brokers reject new messages if there is insufficient disk space to avoid corrupting log segments. Producers attempting to write will receive errors such as DiskError or NotEnoughReplicasException.

Effect: Applications experience write failures and message throughput decreases.

Remedy: Increase broker disk capacity, delete old log segments, or configure log retention policies to free up space. Monitor disk usage to prevent reaching critical thresholds.

2. Partitions Become Unavailable

Each partition has a leader broker responsible for reads and writes. If the leader runs out of disk space, the partition becomes temporarily unavailable for writes.

Effect: Writes fail on affected partitions, and some consumers may experience read delays depending on replica availability.

Remedy: Maintain a proper replication factor so another broker can become leader. Monitor leader brokers and partition availability regularly.

3. Replication Fails

Followers replicate log segments from the leader broker. If a broker’s disk is full, followers cannot replicate new data, increasing replication lag.

Effect: The ISR (in-sync replica) count drops. Producers using acks=all may experience write failures. Durability and fault-tolerance guarantees are temporarily affected.

Remedy: Increase disk space, reassign partitions to brokers with sufficient space using kafka-reassign-partitions.sh, and monitor ISR status.

4. Summary of Consequences & Remedies

Consequence Internal Behavior Remedy
Stops accepting writes Broker rejects new messages → producers get errors Increase disk, delete old logs, configure retention policies, monitor disk usage
Partitions become unavailable Partition leader cannot write → writes blocked Maintain replication factor, monitor leader partitions
Replication fails Followers cannot replicate → ISR drops, write failures Increase disk, reassign partitions, monitor ISR

5. Key Takeaways

  • Kafka brokers must have sufficient disk space to handle writes and replication.
  • Disk-full brokers stop accepting writes, cause partition unavailability, and prevent replication.
  • Monitoring disk usage, ISR, and leader brokers is critical for high availability.
  • Proactive log retention policies and partition reassignment prevent production disruptions.

Kafka Uneven Partition Traffic

Kafka topics are divided into partitions to achieve parallelism. Sometimes, one partition receives most of the messages while others remain idle. This section explains why this happens and how to fix it.

1️⃣ Causes

  • Key-based partitioning with the same key: Messages with the same key always go to the same partition, causing hot partitions.
  • Custom partitioner issues: An incorrectly implemented partitioner may always return the same partition.
  • Default partitioner with null key: Round-robin only works if the key is null. Using a constant key results in skewed distribution.
  • Small number of partitions: Even with round-robin, timing and batching can cause uneven load in topics with very few partitions.

2️⃣ Effects of Uneven Partitioning

  • Uneven broker load: The broker handling the hot partition may become a bottleneck.
  • Reduced throughput: Idle partitions waste cluster resources.
  • Increased latency: Messages queue in the overloaded partition, causing delays.

3️⃣ How Kafka Assigns Partitions

  • Key provided: Kafka computes partition = hash(key) % numPartitions. Same key → same partition → ordered messages per key.
  • No key provided (key=null): Kafka distributes messages round-robin across partitions → even distribution.

4️⃣ How to Fix Uneven Partition Traffic

  • Use null keys for round-robin distribution if ordering by key is not required.
  • Use varied or dynamic keys to avoid hot partitions.
  • Increase the number of partitions to improve distribution and parallelism.
  • Check custom partitioner logic to ensure even key distribution.
  • Monitor partition load using Kafka metrics like BytesInPerPartition.

5️⃣ Example Scenario

Topic orders has 3 partitions. All messages use the key "user123".

Kafka computes partition = hash("user123") % 3 → always partition 1. Partitions 0 and 2 remain idle.

Fix: Use different keys (e.g., userID % 3) or set key=null for round-robin distribution.

Key Takeaways

  • Uneven partition traffic is often caused by constant or poorly distributed keys.
  • Null keys result in round-robin distribution; varied keys balance hash-based partitioning.
  • Monitor partitions and increase partition count if needed to improve throughput and parallelism.

Kafka topics are divided into partitions to achieve parallelism and scalability. Partition assignment affects message ordering, throughput, and load distribution for both producers and consumers.

- You can implement custom logic to decide partitions based on message content, user ID, or region. - Ensure the logic evenly distributes messages to avoid hot partitions.

Kafka Message Ordering Guarantee

Kafka guarantees message ordering at the partition level. Messages produced to a single partition are delivered to consumers in the same order they were written. Ordering across partitions is not guaranteed.

1️⃣ Partition-Level Ordering

Messages are always appended in order within a partition. Consumers reading a partition will always see messages in the order they were produced.

Example: Topic orders with 3 partitions. Messages sent to partition 0:

  • Order1 → Order2 → Order3

Consumer reading partition 0 sees messages in the same sequence.

2️⃣ Key-Based Ordering

Using a message key ensures all messages with the same key are sent to the same partition. This guarantees ordering for related messages.

Example:

  • UserID: "123" → all orders go to partition 1
  • UserID: "456" → all orders go to partition 2

Messages for the same user are ordered, while messages for different users may be interleaved across partitions.

3️⃣ Factors That Can Affect Ordering

  • Producer retries: Without enable.idempotence=true, retries may reorder messages.
  • Multiple partitions: Ordering is guaranteed only within a partition, not across partitions.
  • Consumer concurrency: Multiple consumers reading from different partitions may process messages out of global order.

4️⃣ Best Practices for Maintaining Order

  • Use message keys to ensure related messages go to the same partition.
  • Keep related messages in a single partition to preserve processing order.
  • Enable enable.idempotence=true for producers to maintain order during retries.
  • Be aware that parallelism across partitions can break global order.

5️⃣ Key Takeaways

  • Kafka guarantees message order only at the partition level.
  • Messages with the same key always go to the same partition → order preserved per key.
  • Messages across different partitions may arrive out of order to consumers.
  • Use idempotent producers to prevent ordering issues during retries.
  • Design systems around partition-level ordering, not topic-level global order.

Kafka Replication Factor and Broker Failures

A replication factor of 1 means each partition has only one replica (the leader) and no backups. If the broker hosting the partition crashes, it can lead to data loss and unavailability. Proper replication and cluster design are critical to ensure durability and fault tolerance.

1️⃣ Problem Overview

With replication factor = 1:

  • Each partition has only one replica (the leader).
  • No follower replicas exist to take over if the leader broker fails.
  • Broker failure can cause permanent data loss for messages not yet consumed or replicated.
  • Consumers cannot read from partitions on the failed broker until it recovers.

2️⃣ Potential Consequences

  • Data Loss: Messages on the crashed broker that were not replicated to another broker are lost permanently.
  • Partition Unavailability: Consumers cannot fetch messages from partitions on the failed broker until it recovers.
  • Application Impact: Downstream applications relying on real-time data may see missing or delayed data.
  • Manual Recovery Required: Administrators must restore data from backups or redo operations.

3️⃣ Redesign Strategies

a) Increase Replication Factor

- Set replication factor ≥ 2 (recommended ≥ 3 for production). - Each partition will have multiple replicas distributed across different brokers. - If one broker fails, another replica can become the leader with no data loss.

b) Use min.insync.replicas

- Configure min.insync.replicas ≥ 2 with acks=all on producers. - Ensures messages are acknowledged only when replicated to the required number of brokers. - Provides strong durability and prevents message loss if a broker crashes before replication.

c) Distribute Partitions Across Brokers

- Spread replicas of partitions evenly across brokers to avoid single points of failure. - Avoid co-locating leader and replicas of the same partition on the same broker.

d) Monitor and Automate Failover

- Enable Kafka’s automatic leader election to promote in-sync replicas quickly. - Use monitoring tools to detect broker failures and under-replicated partitions proactively.

4️⃣ Example Scenario

Topic payments with replication factor = 1, partition 0 leader on broker 1.

  • Broker 1 crashes → partition 0 unavailable → data on that broker lost.
  • Redesign:
    • Set replication factor = 3.
    • Distribute replicas across brokers 1, 2, 3.
    • Configure producer with acks=all and min.insync.replicas=2.

Result: Even if broker 1 fails, partition 0 remains available on broker 2 or 3, ensuring no data loss.

5️⃣ Key Takeaways

  • A replication factor of 1 is unsafe for critical topics; it risks permanent data loss on broker failure.
  • Increase replication factor and use min.insync.replicas with acks=all for durability.
  • Distribute replicas across brokers to avoid single points of failure.
  • Monitor ISR and under-replicated partitions to ensure high availability.

Ensuring Message Ordering per Key in Kafka

Kafka guarantees message ordering only within a single partition. To ensure strict ordering per key across multiple partitions, careful topic design, partitioning strategy, and consumer configuration are required.

1️⃣ Problem Overview

In a scenario where a service consumes messages from a topic with multiple partitions, ordering can break if:

  • Messages with the same key are sent to different partitions.
  • Consumers process partitions independently without coordination.

To guarantee ordering per key, messages with the same key must always go to the same partition, and each partition should be consumed by a single consumer at a time.

2️⃣ Design Strategies

a) Key-based Partitioning

- Use the message key to determine the partition. Kafka’s default partitioner hashes the key to a partition. - All messages with the same key go to the same partition, maintaining ordering.

b) Single Consumer per Partition

- In a consumer group, Kafka ensures each partition is consumed by only one consumer at a time. - This guarantees that messages in a partition are processed in order.

c) Partition Count Planning

- The number of partitions should balance throughput and ordering requirements. - Too few partitions → limited parallelism. - Too many partitions → can increase consumer group complexity but does not break ordering per key.

d) Avoid Rebalancing During Critical Processing

- Consumer rebalances can temporarily pause consumption and change partition ownership. - Minimize unnecessary consumer joins/leaves during critical processing to maintain strict ordering.

3️⃣ Example Scenario

Topic: orders Partitions: 4 Consumers: 2 in the same consumer group Key: customerId

  • Kafka hashes each customerId to determine the partition.
  • All orders for a specific customer always go to the same partition.
  • Each partition is consumed by a single consumer → strict order per customerId is preserved.
  • Different customerIds may go to different partitions → allows parallelism while maintaining per-key ordering.

Result: Each customer’s orders are processed in the exact order they were produced, while multiple customers’ orders are processed in parallel across partitions.

4️⃣ Best Practices

  • Always provide a key when ordering is required.
  • Design partition count based on expected key cardinality and throughput.
  • Monitor consumer rebalances and handle them gracefully to prevent ordering gaps.
  • Consider idempotent processing if exactly-once semantics are needed alongside ordering.
  • For very large-scale topics, combine key-based partitioning with batch processing to optimize throughput.

5️⃣ Key Takeaways

  • Kafka guarantees ordering only within a partition, not across partitions.
  • Use message keys to direct related messages to the same partition.
  • Ensure a single consumer per partition to maintain processing order.
  • Plan partitions carefully to balance throughput and ordering requirements.
  • Minimize unnecessary consumer group rebalances during critical message processing.

Building a Real-Time Analytics System with Kafka

Real-time analytics systems require ingesting high-volume events from multiple services, processing them instantly, and producing aggregated insights for dashboards or downstream systems. Kafka acts as the backbone for event streaming, while a processing framework handles computation.

Kafka Consumer Recovery After Microservice Downtime

When a microservice consuming from Kafka goes down for several hours, it must be able to catch up on all missed messages once it comes back online — without losing data. To achieve this, we need to configure consumers, offsets, and retention policies carefully.

1️⃣ Consumer Configuration

  • Consumer Group ID
    The microservice should always use the same group.id.
    Kafka will track offsets per consumer group. When the service comes back, it resumes from the last committed offset instead of starting over.
  • Enable Auto Commit?
    Prefer manual offset commits (enable.auto.commit=false) to have fine-grained control.
    Commit offsets after successful processing of messages → avoids marking messages as consumed before they are really processed.
  • max.poll.interval.ms
    Increase if the service may take longer to process a batch of messages.
    Prevents Kafka from thinking the consumer is dead during heavy processing.

2️⃣ Offset Management

  • Committed Offsets
    Kafka stores offsets in a special internal topic: __consumer_offsets.
    If the service goes down, offsets remain unchanged until it comes back.
    On restart, the consumer resumes from the last committed offset, continuing where it left off.
  • auto.offset.reset
    earliest → if no committed offset is found (e.g., new consumer group), start from the beginning of the topic.
    latest → start from new messages only.
    For catching up on missed data → use committed offsets (default behavior).

3️⃣ Retention Policies

  • log.retention.hours (Broker Level)
    Defines how long Kafka keeps messages (default 168 hours = 7 days).
    Must be longer than the maximum downtime you expect for consumers.
  • log.retention.bytes
    Retain messages based on size as well as time.
    Ensure disk capacity can hold enough backlog for consumers to catch up.
  • Consumer Lag and Retention
    If retention period is too short, old messages may expire before the service comes back → data loss.
    Configure retention so that the topic retains messages at least as long as possible consumer downtime.

4️⃣ Example Scenario

  • Microservice order-processor goes down at 2 PM.
  • It has consumed and committed offsets up to message Order500.
  • During downtime, producers keep writing new orders (Order501 to Order1200).
  • Kafka retains all messages in topic orders because retention is 7 days.
  • At 6 PM, the microservice restarts:
    • Kafka checks the __consumer_offsets topic.
    • Finds the last committed offset = Order500.
    • Resumes consuming from Order501 onward.
  • Result: The service catches up on all missed messages without losing any data.

Kafka NetworkProcessorAvgIdlePercent Low

1️⃣ What It Means

NetworkProcessorAvgIdlePercent measures how much time broker network threads (handling producer/consumer I/O) are idle.
Low value (e.g., consistently < 0.2 or 20%) → network threads are busy almost all the time.
This indicates the broker is network I/O bound.

2️⃣ Causes

Cause Explanation
High client traffic Too many producers/consumers sending or fetching data at once.
Insufficient network threads (num.network.threads) Too few threads configured, defaults may not handle heavy load.
Large requests/responses Oversized messages or batches keep network threads busy longer.
Slow disk or CPU saturation Threads blocked waiting for disk writes or CPU cycles.
Network bottlenecks NIC bandwidth limits, packet drops, or high latency.

3️⃣ Troubleshooting Steps

  • Check broker metrics – Compare with RequestHandlerAvgIdlePercent, CPU, and disk I/O.
  • Analyze traffic – Look for spikes or imbalanced partition traffic.
  • Inspect message sizes – Check producer configs (batch.size, linger.ms, compression.type).
  • Validate broker configs – Review num.network.threads and socket.request.max.bytes.
  • Check cluster balance – Ensure partitions are evenly spread across brokers.

4️⃣ Possible Fixes

Fix When to Apply
Increase num.network.threads If network threads are consistently saturated.
Tune producer configs Use compression, adjust batch size and linger to optimize request handling.
Add brokers or rebalance partitions If load is too high for current cluster capacity.
Upgrade hardware/network If NIC bandwidth or system resources are limiting throughput.
Investigate disk/CPU bottlenecks If network threads are blocked waiting for slow I/O.

Kafka Consumers Skipping Messages or Processing Out of Order After Rebalance

1️⃣ What Happens

In Kafka, when a consumer group rebalance occurs, partitions are reassigned to consumers.

During the rebalance:

  • Consumers may lose ownership of partitions temporarily.
  • Uncommitted messages may be reprocessed by another consumer.
If offsets are committed incorrectly or auto-commit is delayed, consumers can:
  • Skip messages (offset advanced before processing).
  • Process messages out of order (messages reassigned to a different consumer).

2️⃣ Causes

Cause Explanation
Auto offset commit too frequent or too early Messages may be marked consumed before actual processing, causing skipped messages.
Long rebalance duration During rebalance, messages assigned to a consumer may be reassigned to another consumer, causing temporary out-of-order processing.
Multiple consumers per partition Only one consumer can consume from a partition at a time; improper group setup may cause unexpected reassignments.
Manual offset commit mismanagement If offsets are committed before processing completes, skipped messages may occur.

3️⃣ Consumer Group Configuration Changes

  • Disable auto commit
    enable.auto.commit=false
    Commit offsets after successful processing of messages.
  • Use a smaller max.poll.records
    Reduces the number of messages in a poll, allowing faster processing and more frequent commits.
  • Tune session.timeout.ms and heartbeat.interval.ms
    Reduce unnecessary rebalances caused by heartbeat timeouts.
  • Implement idempotent processing
    Even if messages are reprocessed after a rebalance, the final state remains correct.
  • Use partition-aware logic
    For strict ordering, ensure messages for a key always go to the same partition and are processed by one consumer.

4️⃣ Example Scenario

Topic orders with 3 partitions, consumer group order-processors with 2 consumers.

  • Consumer A owns partition 0 & 1; Consumer B owns partition 2.
  • Consumer B crashes → rebalance occurs.
  • Partition 2 is reassigned to Consumer A.
  • Messages already fetched by Consumer A from partition 0 & 1 are processed first; partition 2 messages start later.
  • Without proper offset handling, messages from partition 2 could appear out of order relative to partition 0 & 1.

✅ Key Takeaways

  • Rebalances temporarily interrupt consumption; proper offset management prevents skipped messages.
  • Disable auto-commit, commit after processing, and tune rebalance/heartbeat settings.
  • For strict ordering, combine key-based partitioning with careful consumer configuration.

Kafka Producer Retrying Messages Indefinitely

1️⃣ What Happens

Kafka producers can be configured to retry sending messages if the broker does not acknowledge them.

When a producer is retrying indefinitely, messages accumulate in the topic and create a backlog.

This behavior can lead to:

  • Increased latency for new messages.
  • Memory pressure on producer clients.
  • Risk of duplicate messages if retries are not idempotent.

2️⃣ Possible Causes

Cause Explanation
Broker unavailable or network issues Producer cannot reach the broker or receives timeouts.
Replication issues If acks=all and the minimum number of in-sync replicas are not available, producer retries continuously.
Misconfigured retry settings retries is set very high or delivery.timeout.ms is too large, causing indefinite retries.
Slow brokers or high load Brokers cannot process requests quickly enough → producer keeps retrying.
Idempotence not enabled Without idempotence, retries may cause duplicates if messages eventually succeed.

3️⃣ Configuration Adjustments

Producer-side

  • Limit retries
    retries → set a reasonable number (e.g., 5-10). Prevents infinite retry loops.
  • Set delivery timeout
    delivery.timeout.ms → bounds the total time a message can be retried.
  • Enable idempotence
    enable.idempotence=true → ensures retries don’t produce duplicates.
  • Adjust retry backoff
    retry.backoff.ms → space out retries to reduce broker load.

Broker-side

  • Ensure sufficient ISR
    Increase min.insync.replicas and ensure enough replicas are available to acknowledge messages.
  • Monitor broker health
    Check for under-replicated partitions, disk space, and network saturation.
  • Tune request timeouts
    replica.lag.time.max.ms and replica.socket.timeout.ms to reduce prolonged replication failures.

4️⃣ Example Scenario

Topic orders with replication factor 3 and acks=all.
Broker 2 goes down temporarily → only 2 replicas available.
Producer configured with retries=Integer.MAX_VALUE.
Producer keeps retrying messages indefinitely until Broker 2 returns → backlog grows in producer memory and topic queue.
Fix: set retries=10, delivery.timeout.ms=120000, enable idempotence. Producer retries only a bounded number of times, reducing backlog and preventing duplicate processing.

✅ Key Takeaways

  • Infinite retries can overwhelm producers and topics.
  • Combine bounded retries, delivery timeout, and idempotence to ensure safe, controlled message delivery.
  • Monitor broker health and replication status to prevent retry storms.
