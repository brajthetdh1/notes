Kubernetes Basics

A comprehensive guide to understanding and using Kubernetes for container orchestration

Container Orchestration DevOps Cloud Native Microservices

Introduction to Kubernetes

Kubernetes is an open-source container orchestration platform that automates the deployment, scaling, and management of containerized applications.

Originally developed by Google and now maintained by the Cloud Native Computing Foundation (CNCF), Kubernetes has become the de facto standard for container orchestration.

Key Benefit: Kubernetes helps you manage containerized applications in different deployment environments - physical, virtual, cloud, or hybrid.

Why Kubernetes?

  • Service discovery and load balancing
  • Storage orchestration
  • Automated rollouts and rollbacks
  • Automatic bin packing
  • Self-healing capabilities
  • Secret and configuration management

Kubernetes Architecture: Complete Theoretical Foundation

Fundamental Architecture Overview

Kubernetes operates on a declarative, master-worker architecture designed for managing containerized applications at scale. The entire system is built around a central philosophy: users declare the desired state of their applications, and Kubernetes continuously works to maintain and reconcile this desired state with the actual running state of the cluster. This architectural approach enables self-healing capabilities, automated rollouts and rollbacks, and seamless scaling operations.

At its core, Kubernetes follows a client-server model where the control plane (master nodes) makes global decisions about the cluster and the worker nodes execute the actual workload. This separation of concerns allows for horizontal scaling, high availability, and fault tolerance. The architecture is completely API-driven, with all components communicating through a well-defined REST API that serves as the single source of truth for the entire system.

Core Architectural Principle: Kubernetes implements a control loop pattern where controllers continuously watch the current state of the cluster through the API server and take corrective actions to drive the current state toward the desired state specified by the user. This pattern enables the system's famous self-healing capabilities and declarative nature.

Control Plane Architecture: The Cluster Brain

The control plane serves as the central nervous system of the Kubernetes cluster, responsible for maintaining the overall cluster state and making global scheduling decisions. It consists of several tightly integrated components that work in concert to manage the cluster's operations. The control plane's primary responsibility is to ensure that the actual state of the cluster matches the user's declared desired state.

kube-apiserver: The Central Gateway

The kube-apiserver acts as the front door to the Kubernetes cluster, exposing the Kubernetes API that all other components use to communicate. It is the only component that directly interacts with etcd, the cluster's persistent storage. The API server validates and processes all API requests, enforcing authentication, authorization, and admission control policies. It implements a watch mechanism that allows clients to receive real-time notifications about changes to cluster resources, enabling the reactive nature of the Kubernetes ecosystem.

etcd: The Cluster Memory

etcd is a consistent, distributed key-value store that serves as Kubernetes' persistent backing store for all cluster data. It maintains the entire state of the cluster, including configuration data, current status of all resources, and cluster metadata. etcd uses the Raft consensus algorithm to ensure data consistency across multiple nodes, making it highly available and fault-tolerant. The data is organized in a hierarchical structure under the /registry prefix, with separate branches for different resource types like pods, services, and deployments.

kube-scheduler: The Resource Allocator

The kube-scheduler is responsible for assigning pods to nodes based on resource requirements, constraints, and policies. It operates in a two-phase process: first, it filters all available nodes to find those that can potentially host the pod (considering factors like resource availability, node selectors, and taints), then it scores the remaining nodes to determine the optimal placement. The scheduler's decisions are based on a pluggable set of policies that can be customized to meet specific workload requirements.

kube-controller-manager: The State Reconciler

The kube-controller-manager runs controller processes that regulate the state of the cluster. Each controller is a separate control loop that watches the shared state of the cluster through the API server and makes changes attempting to move the current state towards the desired state. Key controllers include the node controller (responsible for node health monitoring), replication controller (maintaining the correct number of pod replicas), and endpoints controller (populating endpoint objects for services).

Control Plane Communication Pattern: All control plane components communicate exclusively through the API server. They watch for changes to resources and respond by creating, updating, or deleting other resources. This decoupled architecture allows components to be developed and scaled independently while maintaining a consistent view of the cluster state.

Worker Node Architecture: The Execution Environment

Worker nodes are the machines (virtual or physical) where containerized applications actually run. Each node runs the necessary services to manage networking, storage, and the container runtime. Nodes are responsible for maintaining the pods and containers assigned to them by the control plane, reporting their status back, and ensuring the desired state is achieved at the container level.

kubelet: The Primary Node Agent

The kubelet is the primary node agent that runs on each worker node. It acts as the bridge between the control plane and the container runtime on the node. The kubelet's primary responsibility is to ensure that containers are running in a pod according to the specifications provided by the control plane. It takes a set of PodSpecs (pod specifications) and ensures that the containers described in those PodSpecs are running and healthy. The kubelet manages the complete lifecycle of pods on its node, including volume mounting, container creation, health checking, and resource monitoring.

kube-proxy: The Network Proxy

kube-proxy is a network proxy that runs on each node and maintains network rules that allow network communication to your pods from network sessions inside or outside of the cluster. It implements the Kubernetes Service concept by maintaining network rules on the host and performing connection forwarding. kube-proxy supports multiple modes of operation, including iptables mode (which uses Linux iptables to redirect traffic) and IPVS mode (which uses the Linux kernel's IP Virtual Server for better performance at scale).

Container Runtime: The Execution Engine

The container runtime is the software responsible for running containers. Kubernetes supports several container runtimes through the Container Runtime Interface (CRI), which provides a pluggable architecture for different runtime implementations. Common runtimes include containerd (a high-performance container runtime), CRI-O (a lightweight Kubernetes-native runtime), and Docker (via dockershim, though this is being deprecated). The container runtime handles the low-level tasks of pulling container images, creating container filesystems, and managing container processes.

Node Operation Principle: Worker nodes operate in a reactive mode, constantly receiving instructions from the control plane and reporting back their status. The kubelet watches for pod assignments from the API server, creates the containers through the container runtime, and continuously reports the status of pods and nodes back to the control plane.

Networking Architecture: The Communication Fabric

Kubernetes implements a sophisticated networking model that enables seamless communication between containers, pods, services, and external clients. The networking architecture is built on several fundamental requirements that ensure consistent and reliable communication across the entire cluster.

The core networking requirement mandates that every pod gets its own unique IP address and that all pods can communicate with all other pods without network address translation (NAT). This flat networking model simplifies application architecture and enables traditional network applications to work without modification. The actual implementation of this networking model is handled by CNI (Container Network Interface) plugins, which are responsible for assigning IP addresses to pods and configuring network connectivity.

Services in Kubernetes provide a stable endpoint for accessing a group of pods, abstracting away the ephemeral nature of individual pod IP addresses. When a service is created, it is assigned a virtual IP address (ClusterIP) that remains constant throughout the service's lifetime. kube-proxy on each node then manages the translation between this virtual IP and the actual pod IPs, providing load balancing across the pod endpoints.

For external access, Kubernetes provides several service types including NodePort (which exposes the service on a port across all nodes) and LoadBalancer (which integrates with cloud provider load balancers). Additionally, Ingress resources provide HTTP and HTTPS routing to services, offering features like SSL termination, virtual hosting, and path-based routing.

Network Policy Enforcement: Kubernetes Network Policies allow administrators to control traffic flow between pods. These policies are implemented by the CNI plugin and provide fine-grained control over which pods can communicate with each other, enabling microsegmentation and enhancing cluster security.

Storage Architecture: Persistent Data Management

Kubernetes provides a comprehensive storage architecture that supports both ephemeral and persistent storage for containerized applications. The storage system is designed to abstract away the underlying storage infrastructure while providing consistent APIs for applications to consume storage resources.

At the foundation are Volumes, which represent directories that are accessible to containers in a pod. Volumes can be backed by various storage technologies including local storage, network storage, and cloud storage. However, volumes have the same lifecycle as the pod, meaning they are created and destroyed with the pod.

For data that needs to persist beyond the lifecycle of individual pods, Kubernetes provides PersistentVolumes (PVs) and PersistentVolumeClaims (PVCs). A PersistentVolume represents a piece of storage in the cluster that has been provisioned by an administrator or dynamically provisioned using StorageClasses. A PersistentVolumeClaim is a request for storage by a user, which can be bound to a PersistentVolume that meets the claim's requirements.

The Container Storage Interface (CSI) provides a standard interface for storage providers to integrate with Kubernetes. CSI enables storage vendors to develop plugins that work across multiple container orchestrators, providing features like dynamic provisioning, snapshotting, and cloning. This pluggable architecture allows Kubernetes to support a wide variety of storage backends including block storage, file storage, and object storage.

Storage Provisioning Flow: When a user creates a PersistentVolumeClaim, the control plane looks for a PersistentVolume that matches the claim's requirements. If no suitable static volume exists and dynamic provisioning is enabled, the system automatically creates a new volume using the specified StorageClass. The volume is then mounted into the pod by the kubelet, making it available to the containers.

Controller Pattern: The Heart of Kubernetes

The controller pattern is the fundamental mechanism that enables Kubernetes' declarative nature and self-healing capabilities. A controller is a control loop that watches the shared state of the cluster through the API server and makes changes attempting to move the current state towards the desired state.

Each controller is responsible for a specific type of resource and operates independently of other controllers. For example, the Deployment controller manages Deployment objects, ensuring that the specified number of pod replicas are running. When a user creates a Deployment, the Deployment controller notices this change and creates a ReplicaSet. The ReplicaSet controller then notices the new ReplicaSet and creates the actual pods. Finally, the scheduler assigns these pods to nodes, and the kubelet on each node runs the pods.

This separation of concerns allows each controller to focus on a specific aspect of the system while the overall coordination emerges from their interactions. The controllers use a watch-based mechanism to receive notifications about changes to resources, enabling them to react quickly to changes in the cluster state. When multiple changes occur simultaneously, the controllers reconcile the state until it matches the desired specification.

The controller pattern also enables extensibility through custom resources and custom controllers. Users can define their own resource types (CustomResourceDefinitions) and write controllers that manage these resources, effectively extending the Kubernetes API to support domain-specific applications and workflows.

Reconciliation Loop: Every controller follows the same basic pattern: watch for changes to resources, compare the current state with the desired state, and take corrective actions if they differ. This continuous reconciliation process is what makes Kubernetes self-healing and ensures that the cluster always moves toward the user's declared desired state.

API-Driven Architecture: The Single Source of Truth

Kubernetes is fundamentally an API-driven system where every operation, whether initiated by a user or performed automatically by the system, goes through the Kubernetes API. This API-centric architecture provides several key benefits including consistency, auditability, and extensibility.

The Kubernetes API is a RESTful API that supports standard HTTP verbs (GET, POST, PUT, PATCH, DELETE) for managing resources. All resources are represented as JSON or YAML objects that can be easily serialized and stored. The API supports optimistic concurrency control through resource versions, preventing conflicts when multiple clients attempt to modify the same resource simultaneously.

The API server implements several important mechanisms including authentication (verifying user identity), authorization (checking user permissions), and admission control (validating and mutating requests). Admission controllers can modify incoming requests (mutating admission) or reject them based on policy (validating admission), enabling features like defaulting, resource validation, and policy enforcement.

The watch mechanism allows clients to receive continuous updates about changes to resources, enabling the reactive behavior that characterizes Kubernetes. When a client opens a watch on a resource, the API server sends an initial list of existing resources followed by a stream of events for any changes. This mechanism is used extensively by controllers, the scheduler, and kubelets to stay synchronized with the cluster state.

Declarative Configuration: The API-driven architecture enables declarative configuration management, where users specify what they want the system to look like rather than issuing commands to make it happen. This approach allows for version control of configuration, automated management through GitOps workflows, and reliable reproduction of cluster states.

Extension Architecture: Pluggable Components

Kubernetes is designed with extensibility as a first-class concern, providing multiple mechanisms for extending and customizing its behavior. This pluggable architecture allows Kubernetes to adapt to different environments and use cases without requiring changes to the core system.

The Container Network Interface (CNI) allows different networking solutions to be plugged into Kubernetes. CNI plugins are responsible for providing networking to pods, including IP address assignment and network connectivity. Popular CNI plugins include Calico (which provides network policy enforcement and BGP routing), Flannel (a simple overlay network), and Cilium (which uses eBPF for advanced networking and security features).

The Container Storage Interface (CSI) provides a standard interface for storage providers to integrate with Kubernetes. CSI drivers handle volume provisioning, attachment, mounting, and snapshot operations. This interface allows storage vendors to develop plugins that work across multiple container orchestrators while providing advanced storage features to Kubernetes users.

Custom Resource Definitions (CRDs) allow users to extend the Kubernetes API with their own resource types. When combined with custom controllers, CRDs enable the creation of domain-specific operators that manage complex applications using the same patterns as built-in Kubernetes resources. This operator pattern has become the foundation for managing stateful applications and platform services in Kubernetes.

Admission webhooks provide another extension point, allowing external services to participate in the API request lifecycle. Mutating webhooks can modify incoming requests before they are persisted, while validating webhooks can reject requests that violate policies. This mechanism enables features like automatic sidecar injection, policy enforcement, and resource validation.

Operator Pattern: The operator pattern represents the pinnacle of Kubernetes extensibility, where custom resources and custom controllers work together to manage complex applications. Operators encode human operational knowledge into software, automating tasks like backups, updates, and failure recovery for stateful applications.

High Availability and Scalability Architecture

Kubernetes is designed for high availability and horizontal scalability from the ground up. The architecture supports running multiple instances of control plane components and distributing workloads across many worker nodes, ensuring that the cluster can withstand failures and handle increasing loads.

For the control plane, high availability is achieved through redundancy and leader election. Multiple API server instances can run behind a load balancer, with each instance capable of handling any API request. etcd typically runs as a cluster of 3, 5, or 7 nodes using the Raft consensus algorithm to maintain data consistency. The scheduler and controller manager use leader election to ensure that only one instance of each is actively making decisions at any time, preventing conflicts while providing failover capability.

Worker node scalability is handled through the pod scheduling system. As more nodes are added to the cluster, the scheduler automatically distributes pods across them based on resource availability and scheduling policies. The horizontal pod autoscaler can automatically adjust the number of pod replicas based on CPU utilization or custom metrics, ensuring that applications can handle varying loads.

The entire system is designed to be resilient to failures. If a worker node fails, the pods running on that node are rescheduled on other nodes. If a control plane component fails, other instances take over its responsibilities. This resilience, combined with the self-healing nature of the controller pattern, ensures that the cluster can maintain service availability even in the face of component failures.

Scalability Limits: While Kubernetes can scale to thousands of nodes and hundreds of thousands of pods, practical limits depend on factors like etcd performance, API server load, and network configuration. Large clusters often require careful tuning of etcd parameters, API server resources, and network plugins to maintain performance and stability.

Security Architecture: Defense in Depth

Kubernetes implements a comprehensive security model based on the principle of defense in depth, with multiple layers of security controls protecting the cluster and its workloads. This multi-layered approach ensures that a breach at one level does not compromise the entire system.

At the infrastructure level, nodes should be hardened following security best practices, with minimal attack surfaces and regular security updates. Network segmentation should isolate the control plane from worker nodes and restrict access to etcd ports. All communication between components should be encrypted using TLS, with proper certificate management and rotation.

Within the cluster, Role-Based Access Control (RBAC) provides fine-grained authorization for users and service accounts. RBAC allows administrators to define roles that specify permitted actions on resources and bind those roles to specific users or groups. Service accounts provide identity for processes running in pods, enabling applications to authenticate to the API server and other services.

Pod security is enforced through security contexts and pod security standards. Security contexts allow fine-grained control over privileges, capabilities, and access controls for pods and containers. Pod security standards define baseline and restricted security profiles that can be enforced across namespaces to ensure consistent security posture.

Network policies provide microsegmentation within the cluster, controlling which pods can communicate with each other. These policies are implemented by the CNI plugin and can restrict traffic based on pod labels, namespaces, and IP blocks. When combined with encryption and mutual TLS, network policies can create secure communication channels between application components.

Zero Trust Security: Modern Kubernetes security practices are moving toward a zero-trust model where no component is inherently trusted. This approach involves verifying identity at every communication, enforcing least privilege access, encrypting all traffic, and continuously monitoring for anomalous behavior.

Architectural Summary

Kubernetes architecture represents a sophisticated distributed system that combines declarative configuration, reactive control loops, and pluggable components to provide a robust platform for container orchestration. The separation between control plane and worker nodes, combined with the API-driven communication model, creates a system that is both scalable and resilient.

The controller pattern enables the self-healing and declarative nature that makes Kubernetes powerful, while the extensive extension mechanisms allow it to adapt to diverse environments and use cases. From networking and storage to custom resources and operators, every aspect of Kubernetes is designed for extensibility and customization.

Understanding this architectural foundation is essential for effectively deploying, operating, and troubleshooting Kubernetes clusters. The consistent patterns and well-defined interfaces provide a stable base upon which complex distributed applications can be built and managed with confidence.

Kubernetes Control Plane - Complete Architecture Guide

Introduction to Control Plane

The Kubernetes Control Plane is the brain of the Kubernetes cluster, responsible for maintaining the desired state of the system, making global decisions about the cluster, and detecting and responding to cluster events. It consists of several components that work together to manage the worker nodes and the Pods running on them.

Core Function: The Control Plane continuously works to match the current state of the cluster with the desired state declared by users through Kubernetes objects like Deployments, Services, and ConfigMaps.

Control Plane Responsibilities

  • Cluster state management and persistence
  • API request processing and validation
  • Pod scheduling decisions
  • Node health monitoring
  • Service discovery and load balancing
  • Configuration management
  • Security and authentication

kube-apiserver - The Cluster Gateway

Primary Role: kube-apiserver is the front-end of the control plane that exposes the Kubernetes API. It's the only component that communicates directly with etcd and validates and processes all API requests.

Key Functions

  • API Validation: Validates and configures data for API objects
  • Authentication: Verifies user identity via various methods
  • Authorization: Checks if user has permission for requested action
  • Admission Control: Mutating and validating webhook execution
  • Rate Limiting: Prevents API abuse and ensures stability
  • Watch Mechanism: Provides real-time updates to clients

API Request Flow

  1. Request received from client (kubectl, UI, etc.)
  2. Authentication (X.509, Bearer tokens, etc.)
  3. Authorization (RBAC, ABAC, Webhook)
  4. Admission Control (Mutating/Validating webhooks)
  5. Schema Validation
  6. Persistence to etcd
  7. Response to client

In production, run multiple kube-apiserver instances behind a load balancer. Each instance is stateless and can handle any request. Use --etcd-servers with multiple etcd endpoints for redundancy.

etcd - The Cluster Database

Primary Role: etcd is a consistent and highly available key-value store used as Kubernetes' backing store for all cluster data. It stores the entire cluster state, configuration, and secrets.

etcd Characteristics

  • Consistent: All nodes see the same data at the same time
  • Highly Available: Tolerates node failures
  • Watchable: Clients can watch for key changes
  • Fast: Benchmarked at thousands of writes per second
  • Secure: Supports SSL/TLS client certificate authentication
  • Persistent: Data persists to disk

Data Organization

  • /registry/pods: All Pod definitions
  • /registry/services: Service definitions
  • /registry/deployments: Deployment objects
  • /registry/secrets: Encrypted secret data
  • /registry/configmaps: Configuration data
  • /registry/nodes: Node information

kube-scheduler - The Resource Allocator

Primary Role: kube-scheduler assigns Pods to Nodes based on resource requirements, constraints, and policies. It finds the best fit node for each Pod that doesn't have a node assigned.

Scheduling Process

  1. Filtering: Find feasible nodes that can host the Pod
  2. Scoring: Rank feasible nodes to find the best fit
  3. Binding: Bind the Pod to the selected node

Scheduling Policies

  • Resource-based: CPU, memory, storage requirements
  • Affinity/Anti-affinity: Pod and node affinity rules
  • Taints/Tolerations: Node taint matching
  • Topology: Spread Pods across zones, hosts
  • Custom Policies: User-defined scheduling rules

Scheduler Configuration


# Scheduler policy configuration (scheduler-policy-config.yaml)
apiVersion: kubescheduler.config.k8s.io/v1beta3
kind: KubeSchedulerConfiguration
clientConnection:
  kubeconfig: /etc/kubernetes/scheduler.conf
profiles:
  - schedulerName: default-scheduler
    plugins:
      score:
        disabled:
        - name: NodeResourcesLeastAllocated
        enabled:
        - name: NodeResourcesBalancedAllocation
    pluginConfig:
    - name: NodeResourcesFit
      args:
        scoringStrategy:
          type: LeastAllocated

# Custom scheduler example
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  schedulerName: my-custom-scheduler  # Use custom scheduler
  containers:
  - name: nginx
    image: nginx:1.25

# kube-scheduler startup flags
kube-scheduler \
  --kubeconfig=/etc/kubernetes/scheduler.conf \
  --leader-elect=true \
  --bind-address=0.0.0.0 \
  --secure-port=10259 \
  --profiling=false \
  --config=/etc/kubernetes/scheduler-config.yaml

Scheduling Sequence Details

Filtering Phase (Predicates):

  • PodFitsResources: Node has enough resources
  • PodFitsHostPorts: Node has free ports
  • MatchNodeSelector: Node matches node selector
  • CheckNodeMemoryPressure: Node not under memory pressure

Scoring Phase (Priorities):

  • LeastRequestedPriority: Prefer nodes with fewer requested resources
  • BalancedResourceAllocation: Prefer balanced resource usage
  • NodeAffinityPriority: Respect node affinity rules

kube-controller-manager - The State Reconciler

Primary Role: kube-controller-manager runs controller processes that regulate the state of the cluster. Each controller is a separate process that continuously watches the API server and works to move the current state towards the desired state.

Built-in Controllers

  • Node Controller: Monitors node status and health
  • Replication Controller: Maintains correct number of Pod replicas
  • Endpoint Controller: Populates Endpoint objects
  • Service Account Controller: Creates default ServiceAccounts
  • Namespace Controller: Manages namespace lifecycle
  • Deployment Controller: Manages Deployment objects
  • Job Controller: Manages Job objects

Controller Pattern

  • Watch: Continuously watches for changes to resources
  • Reconcile: Compares current state with desired state
  • Act: Takes action to move towards desired state
  • Retry: Implements retry logic for failures
  • Backoff: Uses exponential backoff for rate limiting

Controller Leader Election

In high availability setups, multiple controller manager instances run with --leader-elect=true. Only the leader actively runs controllers while others are standby. This prevents conflicts from multiple controllers trying to reconcile the same resources.

Kubernetes Namespaces - Complete Guide

Introduction to Namespaces

Namespaces in Kubernetes provide a mechanism for isolating groups of resources within a single cluster. They are virtual clusters backed by the same physical cluster, enabling multiple teams or projects to share cluster resources while maintaining logical separation and organization.

Key Concept: Namespaces provide scope for resource names and are essential for dividing cluster resources between multiple users via resource quotas and access controls.

Core Concepts

What Namespaces Provide

  • Logical isolation of resources
  • Name scoping (same resource names in different namespaces)
  • Resource quota enforcement
  • Access control boundaries
  • Network policy boundaries
  • Organization structure

What Namespaces Don't Provide

  • Complete network isolation (without additional policies)
  • Performance isolation
  • Hard security boundaries
  • Resource performance guarantees

Default Namespaces

System Namespaces

  • default: Default namespace for user resources
  • kube-system: Kubernetes system components
  • kube-public: Publicly accessible resources
  • kube-node-lease: Node heartbeat leases

Purpose

  • Never delete system namespaces
  • Avoid deploying applications to system namespaces
  • Use for cluster operations only

Resource Quotas

ResourceQuotas provide constraints that limit aggregate resource consumption per namespace. 


apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-team-quota
  namespace: development
spec:
  hard:
    # Compute Resources
    requests.cpu: "2"
    requests.memory: 4Gi
    limits.cpu: "4"
    limits.memory: 8Gi
    
    # Object Counts
    pods: "20"
    services: "10"
    secrets: "20"
    configmaps: "20"
    persistentvolumeclaims: "10"
    
    # Storage
    requests.storage: 50Gi
    
    # Extended Resources
    requests.nvidia.com/gpu: 2
---
apiVersion: v1
kind: LimitRange
metadata:
  name: dev-limits
  namespace: development
spec:
  limits:
  - default:
      cpu: 500m
      memory: 512Mi
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    type: Container

Important: Always combine ResourceQuota with LimitRange to ensure proper resource allocation and prevent resource starvation.

kubectl config get-contexts                  # List all contexts
kubectl config current-context               # Show current context
kubectl config use-context my-cluster        # Switch context
kubectl config set-context --current --namespace=dev  # Set namespace
kubectl config view                          # View merged kubeconfig
kubectl config view --minify                 # Show current context only
kubectl config view --raw                    # Show full configuration

Pro Tip: Use kubectl config set-context --current --namespace to set default namespace for current context.

2. Resource Management Commands

kubectl get

Display one or many resources with various output formats.


# Basic get commands
kubectl get pods                           # List all pods
kubectl get pods -n default               # List pods in specific namespace
kubectl get pods --all-namespaces         # List pods across all namespaces
kubectl get pods -o wide                  # Additional information
kubectl get pods -w                       # Watch mode
kubectl get pods --show-labels            # Show labels
kubectl get pods --field-selector status.phase=Running  # Filter by field

# Output formats
kubectl get pods -o yaml                  # YAML format
kubectl get pods -o json                  # JSON format
kubectl get pods -o name                  # Resource names only
kubectl get pods -o custom-columns=NAME:.metadata.name,STATUS:.status.phase

# Multiple resources
kubectl get pods,services,deployments     # Get multiple resource types
kubectl get all                           # Get all resources in namespace
kubectl get all --all-namespaces          # Get all resources in all namespaces
-n, --namespace: Specify namespace
-A, --all-namespaces: All namespaces
-o, --output: Output format
-w, --watch: Watch for changes
-l, --selector: Label selector
--field-selector: Field selector

Common Resource Types: pods, services, deployments, replicasets, statefulsets, daemonsets, jobs, cronjobs, configmaps, secrets, nodes, namespaces, persistentvolumes, persistentvolumeclaims, storageclasses, ingress, networkpolicies

kubectl describe

Show detailed information about specific resources or groups of resources.


kubectl describe pod my-pod                 # Describe specific pod
kubectl describe pod my-pod -n production   # In specific namespace
kubectl describe nodes                      # Describe all nodes
kubectl describe node node-1               # Describe specific node
kubectl describe deployment my-app         # Describe deployment
kubectl describe service my-service        # Describe service

# With selectors
kubectl describe pods -l app=nginx         # Describe pods by label
kubectl describe all -n default            # Describe all resources in namespace

Troubleshooting: Essential for debugging - shows events, conditions, volumes, and container status in one consolidated view.

kubectl create vs apply

Different approaches to creating and updating resources.


# kubectl create - Imperative (creates new resource)
kubectl create deployment nginx --image=nginx:1.25
kubectl create namespace dev
kubectl create configmap my-config --from-literal=key=value
kubectl create secret generic my-secret --from-literal=password=secret

# kubectl apply - Declarative (creates or updates)
kubectl apply -f deployment.yaml
kubectl apply -f ./manifests/              # Apply all files in directory
kubectl apply -f https://example.com/manifest.yaml
kubectl apply -k ./kustomize/              # Apply kustomization

# With flags
kubectl apply -f config.yaml --dry-run=client    # Dry run
kubectl apply -f config.yaml --server-dry-run    # Server-side dry run
kubectl apply -f config.yaml --validate=true     # Schema validation
kubectl apply -f config.yaml --prune             # Remove old resources
kubectl create
  • Imperative approach
  • Fails if resource exists
  • Good for one-time creation
  • No tracking with kubectl.kubernetes.io/last-applied-configuration
kubectl apply
  • Declarative approach
  • Creates or updates resources
  • Maintains last-applied-configuration
  • Recommended for GitOps workflows

kubectl delete

Delete resources by file, names, or selectors.


# Delete by file
kubectl delete -f deployment.yaml
kubectl delete -f ./manifests/              # Delete all in directory

# Delete by resource type and name
kubectl delete pod my-pod
kubectl delete deployment my-app
kubectl delete service my-service

# Delete by selector
kubectl delete pods -l app=nginx
kubectl delete all -l app=my-app

# Delete all in namespace (DANGEROUS)
kubectl delete all --all -n dev
kubectl delete pods,services,deployments --all

# Force delete
kubectl delete pod my-pod --grace-period=0 --force

# Specific delete options
kubectl delete pod my-pod --now             # Immediate deletion
kubectl delete -f config.yaml --ignore-not-found  # Skip if not found

Warning: kubectl delete all --all deletes ALL resources including persistent volumes, config maps, and secrets. Use with extreme caution!

3. Debugging & Troubleshooting Commands

kubectl logs

Print logs from containers in pods.


# Basic log viewing
kubectl logs my-pod                         # Pod logs
kubectl logs my-pod -c my-container        # Multi-container pod
kubectl logs my-pod --previous             # Previous instance logs
kubectl logs -f my-pod                     # Follow (stream) logs
kubectl logs --tail=50 my-pod              # Last 50 lines

# Advanced log options
kubectl logs --since=1h my-pod             # Last hour of logs
kubectl logs --since-time="2024-01-01T00:00:00Z" my-pod
kubectl logs --timestamps my-pod           # Add timestamps
kubectl logs --prefix my-pod               # Add pod name prefix

# Multiple pods
kubectl logs -l app=nginx                  # All pods with label
kubectl logs deployment/my-app            # All pods in deployment
kubectl logs -f deployment/my-app         # Follow deployment logs
-f, --follow: Stream logs live
--tail: Number of lines from end
--since: Relative time (1h, 30m)
-c, --container: Container name
--previous: Previous container instance
--timestamps: Include timestamps

kubectl exec

Execute a command in a container.


# Basic execution
kubectl exec my-pod -- ls /app             # Run command
kubectl exec my-pod -c container -- ps aux # Specific container
kubectl exec -it my-pod -- /bin/bash       # Interactive shell
kubectl exec -it my-pod -- /bin/sh         # Alternative shell

# Multiple commands
kubectl exec my-pod -- sh -c "cd /app && ls -la"

# File operations
kubectl exec my-pod -- cat /etc/config/app.conf
kubectl exec my-pod -- tail -f /var/log/app.log

# Debugging commands
kubectl exec my-pod -- env                 # Check environment
kubectl exec my-pod -- netstat -tulpn      # Check network
kubectl exec my-pod -- df -h               # Check disk space
-i, --stdin: Pass stdin to container
-t, --tty: Stdin is a TTY
-c, --container: Container name

kubectl port-forward

Forward one or more local ports to a pod.


# Basic port forwarding
kubectl port-forward pod/my-pod 8080:80           # Pod port forward
kubectl port-forward deployment/my-app 8080:80    # Deployment
kubectl port-forward service/my-service 8080:80   # Service

# Multiple ports
kubectl port-forward pod/my-pod 8080:80 8443:443

# Specific address binding
kubectl port-forward pod/my-pod 8080:80 --address=0.0.0.0

# Background execution
kubectl port-forward pod/my-pod 8080:80 &
kubectl port-forward pod/my-pod 8080:80 --address=127.0.0.1

# Resource selection
kubectl port-forward -l app=nginx 8080:80

Development Use: Essential for local development and debugging applications running in the cluster without exposing them externally.

kubectl cp

Copy files and directories to and from containers.


# Copy from local to pod
kubectl cp /local/file.txt my-pod:/remote/path/file.txt
kubectl cp /local/directory/ my-pod:/remote/path/

# Copy from pod to local
kubectl cp my-pod:/remote/file.txt /local/file.txt
kubectl cp my-pod:/remote/logs/ /local/logs/

# With container specification
kubectl cp /local/file.txt my-pod:/remote/ -c my-container

# Archive mode (preserves permissions)
kubectl cp /local/dir/ my-pod:/remote/ --no-preserve=true

# Specific file patterns
kubectl cp my-pod:/var/log/*.log /local/logs/

Note: The tar binary must be available in the container for copy operations to work.

kubectl debug

Create debugging sessions for troubleshooting pods.


# Interactive debugging session
kubectl debug my-pod -it --image=busybox --target=my-pod
kubectl debug node/my-node -it --image=busybox

# Copy pod for debugging
kubectl debug my-pod -it --copy-to=my-pod-debug --share-processes

# Ephemeral containers
kubectl debug my-pod -it --image=nicolaka/netshoot --container=debugger

# Common debugging images
kubectl debug my-pod -it --image=busybox
kubectl debug my-pod -it --image=nicolaka/netshoot  # Network tools
kubectl debug my-pod -it --image=alpine

Advanced Debugging: Use ephemeral containers for troubleshooting production pods without restarting or modifying the original pod.

4. Advanced Operations

kubectl rollout

Manage the rollout of resources like deployments and daemonsets.


# Rollout status and history
kubectl rollout status deployment/my-app
kubectl rollout history deployment/my-app
kubectl rollout history deployment/my-app --revision=2

# Rollout management
kubectl rollout pause deployment/my-app
kubectl rollout resume deployment/my-app
kubectl rollout restart deployment/my-app   # Rolling restart
kubectl rollout undo deployment/my-app      # Rollback to previous
kubectl rollout undo deployment/my-app --to-revision=1

# Daemonset and statefulset rollouts
kubectl rollout status daemonset/my-daemon
kubectl rollout restart statefulset/my-db

kubectl scale

Set a new size for deployments, replicasets, or statefulsets.


# Scale deployments
kubectl scale deployment my-app --replicas=5
kubectl scale --replicas=3 deployment/my-app

# Scale with current replicas
kubectl scale deployment my-app --current-replicas=2 --replicas=5

# Scale multiple resources
kubectl scale --replicas=3 deployment/my-app statefulset/my-db

# Scale based on resource file
kubectl scale -f deployment.yaml --replicas=3

kubectl auth

Inspect authorization and permissions.


# Check permissions
kubectl auth can-i create pods
kubectl auth can-i delete pods --as=system:serviceaccount:default:my-sa
kubectl auth can-i list nodes --all-namespaces

# Check for specific user
kubectl auth can-i get pods --as=developer@company.com

# List all API resources and verbs
kubectl auth can-i --list
kubectl auth can-i --list --namespace=production

# Check specific resource
kubectl auth can-i get pods/my-pod
kubectl auth can-i create deployments.apps

kubectl top

Display resource usage (CPU/Memory) of nodes and pods.


# Node resource usage
kubectl top nodes
kubectl top node my-node

# Pod resource usage
kubectl top pods
kubectl top pods --all-namespaces
kubectl top pods -l app=nginx
kubectl top pods --containers           # Show container-level usage
kubectl top pods --sort-by=cpu          # Sort by CPU usage
kubectl top pods --sort-by=memory       # Sort by memory usage

# With selectors and sorting
kubectl top pods -A --sort-by=memory --selector=app=web

Requirements: Requires metrics-server installed in the cluster.
