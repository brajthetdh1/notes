Kubernetes Control Plane

The Kubernetes control plane is the central management entity that maintains the desired state of the cluster. It consists of several core components that work together to manage the cluster's workload and direct communication.

Control Plane Theory & Architecture

API Server Theory

The API Server serves as the central management gateway for the entire Kubernetes cluster, exposing a RESTful API that enables both internal components and external users to interact with the cluster's resources and state.

It functions as the front door to the control plane by handling authentication, authorization, and validation of all incoming requests while maintaining the integrity and consistency of cluster operations through its stateless architecture.

Every communication between components flows through the API Server, which acts as the single source of truth for the current state of the cluster while providing watch capabilities for real-time updates and change notifications.

etcd Theory

etcd operates as the persistent, distributed, and consistent key-value store that serves as the single source of truth for all Kubernetes cluster data, storing the complete state and configuration information in a reliable and fault-tolerant manner.

This highly available datastore implements the Raft consensus algorithm to ensure data consistency across multiple nodes, providing strong consistency guarantees that are essential for maintaining cluster stability and operational reliability.

All cluster objects including pods, services, replication controllers, and secrets are persistently stored in etcd, which the API Server exclusively accesses to retrieve and modify the cluster's desired state configuration.

Controller Manager Theory

The Controller Manager operates as the brain of the control plane by continuously running various controller processes that monitor the cluster state and drive it toward the desired configuration specified by users and administrators.

It implements the core reconciliation loop pattern where controllers watch the API Server for changes to resources and automatically take corrective actions to align the actual state with the declared desired state of the cluster.

Key controllers include the Node Controller that manages node status and health, the Replication Controller that maintains the correct number of pod replicas, and the Endpoints Controller that populates endpoint objects for services.

Scheduler Theory

The Scheduler functions as the intelligent placement engine that automatically assigns newly created pods to suitable worker nodes based on resource requirements, constraints, and policies defined in the cluster configuration.

It continuously monitors the API Server for unscheduled pods and evaluates each node against multiple criteria including resource availability, hardware constraints, affinity rules, and anti-affinity specifications to determine optimal placement.

Through its two-phase scheduling process of filtering and scoring, the Scheduler ensures efficient resource utilization while respecting operational constraints and maintaining the performance and reliability requirements of deployed applications.

Cloud Controller Manager Theory

The Cloud Controller Manager serves as the bridge between Kubernetes and underlying cloud infrastructure by embedding cloud-specific control logic that enables seamless integration with cloud provider APIs and services.

It decouples cloud platform dependencies from the core Kubernetes codebase, allowing cloud providers to develop and maintain their integration components independently while ensuring consistent cluster operations across different environments.

This component manages cloud-specific controllers including the Node Controller for handling cloud provider node lifecycle, the Route Controller for configuring network routes, and the Service Controller for managing cloud load balancers.

By abstracting cloud provider specifics, the Cloud Controller Manager enables Kubernetes to maintain its portable nature while leveraging cloud-native capabilities for enhanced networking, storage, and compute resource management.

Architecture Principles & Design Philosophy

Kubernetes embraces a modular and decoupled architecture where each control plane component operates independently while communicating exclusively through the API Server, creating a loosely coupled system that enables individual component scaling and updates without disrupting overall cluster operations.

The control plane implements a declarative model where users specify the desired state of the system, and the various controllers work continuously to reconcile the actual state with this declared configuration, automatically healing and adapting to changes in the environment.

High availability is achieved through component replication and leader election mechanisms, ensuring that critical control plane functions remain operational even during node failures or network partitions, while the stateless design of most components facilitates easy recovery and horizontal scaling.

This architectural approach enables Kubernetes to manage complex distributed systems reliably while providing the flexibility to extend functionality through custom resources and controllers, making it adaptable to diverse workload requirements and infrastructure environments.

Cloud Controller Manager

What is cloud-controller-manager?

The Cloud Controller Manager is a specialized Kubernetes control plane component that embeds cloud-specific control logic, acting as a bridge between your Kubernetes cluster and your cloud provider's API to manage cloud resources that are outside the scope of your cluster.

Core Functionality

It separates the Kubernetes core from cloud provider dependencies by handling cloud-specific operations like managing load balancers, storage volumes, and networking routes while maintaining the cluster's desired state through cloud provider APIs.

When is it used?

The Cloud Controller Manager is essential when running Kubernetes on cloud infrastructure like AWS, Google Cloud, Azure, or other cloud platforms where you need to integrate with cloud services such as load balancers, persistent disks, and virtual networks.

Integration Scenarios

It becomes crucial when you need automatic provisioning of cloud resources, such as creating cloud load balancers for Kubernetes Services, attaching persistent cloud storage to Pods, or managing cloud-specific networking configurations for node communications.

External Database Connection Issues

Slow connections from Kubernetes pods to external database

Potential Causes

Network Policy Restrictions

Kubernetes NetworkPolicies may be blocking or throttling egress traffic to external databases on specific ports.

DNS Resolution Problems

CoreDNS or kube-dns might be experiencing delays resolving external database hostnames to IP addresses.

CNI Plugin Overhead

Container Network Interface plugins like Calico or Flannel adding latency through encapsulation or routing rules.

Resource Constraints

CPU or memory limits on pods causing slow TLS handshakes or connection establishment with external databases.

Troubleshooting Steps

1

Test DNS Resolution

kubectl exec -it [POD] -- nslookup database-host.com

Check if external hostnames resolve correctly from inside the pod.

2

Check Network Connectivity

kubectl exec -it [POD] -- telnet db-host 5432

Test basic TCP connectivity to the database port from within the pod.

3

Inspect Network Policies

kubectl get networkpolicies -A

Verify no NetworkPolicies are blocking egress traffic to your database.

4

Monitor Resource Usage

kubectl top pod [POD_NAME]

Check if pods are hitting CPU/memory limits during connection attempts.

Quick Potential Fixes

Add Egress NetworkPolicy

Allow specific egress traffic to your database endpoint

Use IP Instead of Hostname

Bypass DNS resolution issues by using direct IP addresses

Increase Resource Limits

Provide more CPU for TLS handshakes and connection pooling

Check CNI Configuration

Verify CNI plugin isn't adding unnecessary network hops

Worker Node Failure Scenario

Pods on Failed Node

When a worker node becomes unreachable, all Pods running on that node enter a Terminating/Unknown state as the kubelet can no longer report their status to the control plane.

After the node-monitor-grace-period (default 40s) expires, Kubernetes marks the node as NotReady and the scheduler stops assigning new Pods to it.

Once the pod-eviction-timeout (default 5m) is reached, the control plane automatically deletes the Pods and recreates them on other healthy nodes if they are managed by a controller.

Kubernetes Automatic Response

The Node Controller detects the node failure through heartbeat timeouts and updates the node status to reflect the unreachable state in the cluster.

For Pods managed by Deployments, StatefulSets, or ReplicaSets, new replicas are automatically scheduled on available healthy nodes to maintain the desired state.

The scheduler identifies available capacity on other nodes and redistributes the workload while respecting PodDisruptionBudgets and resource constraints.

Administrator Response Actions

Investigate

Check node status with kubectl get nodes and examine events

Diagnose

Use kubectl describe node and check system logs

Recover/Drain

Restart the node or use kubectl drain if permanently failed

Verify

Ensure all Pods are rescheduled and applications are healthy

Important Notes

• Static Pods and DaemonSet Pods will not be rescheduled until the node recovers

• Pods without controllers (bare Pods) will not be automatically recreated

• Persistent volumes may remain attached to the failed node until manually detached

• Set appropriate resource requests/limits and PodDisruptionBudgets for better resilience

DNS Resolution Issue

Symptoms

my-service.namespace.svc.cluster.local FAILS

10.96.123.45 (ClusterIP) WORKS

Likely Cause

CoreDNS is not functioning properly in your Kubernetes cluster. CoreDNS is responsible for resolving Kubernetes Service DNS names to their corresponding ClusterIP addresses. When CoreDNS is down or misconfigured, DNS resolution fails while direct IP connectivity continues to work.

How to Fix It

1

Check CoreDNS Pod Status

kubectl get pods -n kube-system -l k8s-app=kube-dns
2

Verify CoreDNS Service

kubectl get svc -n kube-system kube-dns
3

Check Pod DNS Configuration

kubectl exec -it [POD_NAME] -- cat /etc/resolv.conf

Should point to kube-dns service IP

4

Restart CoreDNS if Needed

kubectl delete pods -n kube-system -l k8s-app=kube-dns

Quick Diagnostics

  • Check if CoreDNS pods are running
  • Verify network policies aren't blocking DNS
  • Ensure nodes can reach CoreDNS service

Prevention Tips

  • Set resource limits for CoreDNS
  • Configure proper liveness/readiness probes
  • Run multiple CoreDNS replicas
ImagePullBackOff Error - Private Registry

Common Causes

Missing ImagePullSecrets

Kubernetes needs credentials to access your private registry. Check if ImagePullSecrets are properly configured in your Pod spec or ServiceAccount.

Service Account Permissions

The ServiceAccount used by the Pod might not have the necessary ImagePullSecrets attached to authenticate with your registry.

Image Tag Mismatch

Verify the image tag exists in your registry and matches exactly what's specified in your deployment configuration.

Troubleshooting Steps

1

Check Pod Details

kubectl describe pod <pod-name>

Look for events and error messages in the Pod description

2

Verify ImagePullSecrets

kubectl get secrets --all-namespaces

Ensure your registry credentials secret exists and is properly referenced

3

Check ServiceAccount

kubectl describe serviceaccount default

Verify ImagePullSecrets are attached to the ServiceAccount

Quick Fix - Add ImagePullSecret

Create Secret

kubectl create secret docker-registry my-registry-key \
--docker-server=registry.example.com \
--docker-username=myuser \
--docker-password=mypassword

Add to Pod Spec

spec:
  containers:
  - name: my-app
    image: registry.example.com/my-app:latest
  imagePullSecrets:
  - name: my-registry-key

Network Policy Troubleshooting

Verification Steps

1. Check Network Policies

kubectl get networkpolicies --all-namespaces

2. Inspect Specific Policy

kubectl describe networkpolicy <policy-name>

3. Test Connectivity

kubectl exec -it frontend-pod -- curl backend-service:port

4. Check Pod Labels

kubectl get pods --show-labels

Fix Solutions

1. Allow Frontend to Backend

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-backend
spec:
  podSelector:
    matchLabels:
      app: backend
  ingress:
    - from:
      - podSelector:
          matchLabels:
            app: frontend

2. Apply the Policy

kubectl apply -f network-policy.yaml

3. Temporary Disable (if needed)

kubectl delete networkpolicy <restrictive-policy>

Check Labels Match

Ensure podSelector labels align with policy rules

Verify Namespace

Policies apply to pods in the same namespace

Default Deny State

No policies = All traffic allowed
