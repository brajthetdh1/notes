Kubernetes API Fundamentals

The Kubernetes API is the central nervous system of the entire Kubernetes ecosystem, serving as the single source of truth and the primary interface for all cluster operations. It is a RESTful API that follows the OpenAPI specification, providing a consistent, versioned, and discoverable interface for managing all Kubernetes resources. Every operation in Kubernetes, whether initiated by a user through kubectl, by a controller, or by system components, ultimately translates to API calls that are processed by the kube-apiserver.

The API is built around the concept of resources, which are endpoints in the API that represent collections of API objects of a certain kind. For example, the pods resource represents a collection of Pod objects. Each resource has a standard set of operations (verbs) that can be performed on it, including create, get, list, watch, update, patch, and delete. The API is organized into API groups, which are sets of related resources that evolve together. Core resources like Pods, Services, and Nodes are in the core API group (often referred to as the legacy group), while newer resources are organized into named API groups like apps/v1 for Deployments and ReplicaSets.

API Server Role: The kube-apiserver is the only component that directly interacts with etcd. It validates, processes, and stores all API requests, making it the gatekeeper and source of truth for the entire cluster state. All other components, including controllers, schedulers, and kubelets, act as clients to the API server.

API Request Lifecycle: From Request to Persistence

When a request reaches the Kubernetes API server, it goes through a sophisticated multi-stage processing pipeline that ensures security, validation, and consistency. The complete lifecycle of an API request involves several distinct phases that transform a raw HTTP request into a persisted cluster state change.

1. Authentication Phase

The first step in processing an API request is authentication, where the API server verifies the identity of the requester. Kubernetes supports multiple authentication mechanisms including X.509 client certificates, bearer tokens, authenticating proxies, and basic authentication. The API server attempts each authentication method in sequence until one succeeds. If no authentication method succeeds, the request is rejected with a 401 status code. It's important to note that authentication only establishes who is making the request, not what they are allowed to do.

2. Authorization Phase

Once authenticated, the request proceeds to authorization, where the API server determines whether the authenticated user has permission to perform the requested action. Kubernetes primarily uses Role-Based Access Control (RBAC) for authorization, though it also supports other modes like ABAC (Attribute-Based Access Control) and Webhook authorization. RBAC evaluates whether there exists a Role or ClusterRole that grants the necessary permissions to the user or their group, and whether a RoleBinding or ClusterRoleBinding links that role to the user.

3. Admission Control Phase

After authorization, the request enters the admission control phase, which consists of two types of admission controllers: mutating and validating. Mutating admission controllers can modify the incoming object before it's persisted. For example, they might inject sidecar containers, set default resource limits, or add labels. Validating admission controllers cannot modify objects but can reject requests that violate policies. Common admission controllers include NamespaceLifecycle (prevents object creation in non-existent namespaces), LimitRanger (enforces resource limits), and ResourceQuota (enforces namespace quotas).

4. Validation and Schema Checking

Before persistence, the API server performs schema validation to ensure that the object conforms to the expected API schema. This includes checking required fields, validating field types, and ensuring that values are within acceptable ranges. The schema validation is based on the OpenAPI specification that the API server exposes, ensuring that only well-formed objects are accepted.

5. Persistence to etcd

Finally, the validated and admitted object is persisted to etcd, the cluster's persistent key-value store. The API server writes the object to the appropriate key in etcd and updates the resource version. Once persisted, the change becomes visible to other components through the watch mechanism.

Request Flow Summary: HTTP Request → Authentication → Authorization → Mutating Admission → Validating Admission → Schema Validation → etcd Persistence → Response to Client. This multi-stage pipeline ensures that only authorized, validated, and policy-compliant changes are made to the cluster state.

kubectl Command Execution: Behind the Scenes

When you run a kubectl command, it undergoes a complex transformation from a simple command-line instruction to a series of API calls that orchestrate changes across the entire cluster. Understanding this process is crucial for effective troubleshooting and advanced Kubernetes operations.

kubectl apply -f deployment.yaml: The Complete Journey

Let's examine what happens when you run kubectl apply -f deployment.yaml, one of the most common Kubernetes operations. This seemingly simple command triggers a sophisticated sequence of events across the cluster. 


# Step-by-step execution of: kubectl apply -f deployment.yaml

1. kubectl reads and parses the YAML file
2. kubectl constructs HTTP request to API server
3. API server processes request through authn/authz pipeline
4. Admission controllers mutate/validate the Deployment
5. Deployment object persisted to etcd
6. Deployment controller detects new Deployment
7. Deployment controller creates ReplicaSet
8. ReplicaSet controller detects new ReplicaSet  
9. ReplicaSet controller creates Pod specifications
10. Scheduler assigns Pods to Nodes
11. kubelet on each node creates containers
12. Containers start running and report status

Phase 1: Client-Side Processing - kubectl first reads the YAML file and parses it into internal Go structs. It then checks the current state of the resource in the cluster by making a GET request to the API server. kubectl computes the difference between the desired state (from the YAML) and the current state (from the API server), and generates a strategic merge patch. This patch contains only the changes needed to transform the current state into the desired state.

Phase 2: API Server Processing - kubectl sends a PATCH request to the API server's endpoint for the Deployment resource. The API server processes this request through the complete authentication, authorization, and admission control pipeline. If the Deployment doesn't exist, kubectl falls back to a CREATE operation. The API server validates the patch against the Deployment schema and applies it to the current object.

Phase 3: Controller Reconciliation - Once the Deployment is persisted to etcd, the Deployment controller (running in kube-controller-manager) detects the change through its watch on Deployment objects. The controller compares the desired replica count with the current number of available Pods and creates a ReplicaSet if needed. The ReplicaSet controller then detects the new ReplicaSet and creates Pod specifications to match the desired replica count.

Phase 4: Pod Scheduling and Execution - The scheduler detects the newly created Pods (which are in Pending state) and assigns each Pod to a suitable Node based on resource availability, node selectors, affinity rules, and other constraints. The kubelet on each assigned Node detects the Pod assignment and instructs the container runtime to create the containers. The kubelet continuously reports the Pod status back to the API server.

Detailed Command Analysis: Common Operations

kubectl get pods -o wide --watch

This command demonstrates several advanced API features working together. The get pods operation translates to a LIST request to the /api/v1/namespaces/{namespace}/pods endpoint. The -o wide flag causes kubectl to request additional fields from the API server and format them in a tabular view.

The --watch flag is particularly interesting. Instead of making a single request, kubectl first makes a LIST request to get the current state, then opens a persistent HTTP connection to the WATCH endpoint. The API server streams events (ADDED, MODIFIED, DELETED) to the client as they occur. This watch mechanism is the foundation for Kubernetes' reactive architecture - it's how controllers, the scheduler, and kubelets stay synchronized with the cluster state. 


# What kubectl actually does:
1. GET /api/v1/namespaces/default/pods?watch=true
2. Server responds with initial list followed by event stream:
   {"type":"ADDED","object":{...}}
   {"type":"MODIFIED","object":{...}}
   {"type":"DELETED","object":{...}}
3. kubectl parses each event and updates the display

kubectl exec -it my-pod -- /bin/bash

The exec command demonstrates Kubernetes' ability to handle streaming protocols through the API server. When you run this command, kubectl doesn't directly connect to the Pod. Instead, it makes a POST request to the /api/v1/namespaces/{namespace}/pods/{name}/exec endpoint with several important parameters.

The API server acts as a proxy, forwarding the request to the kubelet on the node where the Pod is running. The kubelet then establishes a connection to the container runtime and creates a streaming session. This multi-hop architecture ensures that all exec sessions are authenticated, authorized, and audited through the central API server, even though the actual data stream bypasses it for performance reasons. 


# Execution flow:
1. kubectl → API server: POST /api/v1/namespaces/default/pods/my-pod/exec
   Parameters: command=/bin/bash, stdin=true, stdout=true, tty=true
   
2. API server → kubelet: Forwarded request with authentication
   
3. kubelet → container runtime: Create exec session
   
4. Establish bidirectional streams:
   kubectl ↔ API server ↔ kubelet ↔ container

kubectl logs -f deployment/my-app

This command showcases how kubectl can abstract complex operations into simple commands. Here, kubectl first queries the API server to discover all Pods belonging to the Deployment, then opens multiple log streams simultaneously.

The log retrieval goes through the API server, which proxies the request to the appropriate kubelets. Each kubelet reads logs from the container runtime and streams them back. The -f (follow) flag causes kubectl to keep the connections open and stream new log lines as they're generated, similar to the tail -f command in Unix. 


# Log retrieval process:
1. kubectl GET /apis/apps/v1/namespaces/default/deployments/my-app
2. Extract selector labels from Deployment
3. kubectl GET /api/v1/namespaces/default/pods?labelSelector=...
4. For each Pod, GET /api/v1/namespaces/default/pods/{pod-name}/log?follow=true
5. API server proxies each request to the appropriate kubelet
6. kubelet reads logs from container runtime and streams back
7. kubectl aggregates and displays logs from all Pods

API Resources and Discovery Mechanism

Kubernetes employs a sophisticated API discovery mechanism that allows clients to dynamically learn about available resources and their capabilities. This is why kubectl can work with custom resources without needing precompiled knowledge of them.

When kubectl starts, it queries the API server's discovery endpoints to build a complete map of available API resources. The primary discovery endpoint is /apis, which returns a list of all available API groups. For each API group, kubectl queries the group version endpoint (e.g., /apis/apps/v1) to discover the resources available in that group and their supported operations.

This discovery mechanism enables several powerful features. It allows kubectl to provide tab completion for resource types, validate resource names and namespaces, and handle custom resources defined through CustomResourceDefinitions (CRDs). When you create a CRD, the API server automatically exposes endpoints for that custom resource, and kubectl can discover and interact with it just like built-in resources. 


# API Discovery Flow
1. kubectl GET /apis
   Response: {"groups": [{"name": "apps", "versions": [...]}]}

2. kubectl GET /apis/apps/v1
   Response: {"resources": [{"name": "deployments", "verbs": [...]}]}

3. kubectl now knows how to interact with deployments.apps/v1

# For custom resources:
1. User creates CustomResourceDefinition
2. API server automatically exposes /apis/your-group/your-version
3. kubectl discovers the new resource through normal discovery
4. kubectl can now get, create, update your custom resource

Controller Watch Mechanism: The Reactivity Engine

The watch mechanism is the cornerstone of Kubernetes' reactive architecture. It enables components to receive real-time notifications about changes to resources, allowing them to respond immediately without polling. This is how controllers maintain the desired state of the cluster.

When a controller starts, it first lists all existing objects of the resource type it manages, then opens a watch connection to receive updates. The API server sends events for each change, including the entire object in its new state. The controller uses the resourceVersion field to ensure it doesn't miss any changes - if the watch connection breaks, the controller can resume from the last resourceVersion it processed.

The watch mechanism is highly efficient because the API server can serve many watchers from a single change event. When an object is updated, the API server notifies all watchers subscribed to that resource type (with optional field selectors and label selectors to filter the watch). This publish-subscribe pattern scales well because the work of processing the change is done once by the API server and distributed to all interested watchers.

Watch Performance Characteristics: The watch mechanism is designed for scalability. Watchers don't significantly impact API server performance because they're mostly idle HTTP connections. The real cost comes from the memory needed to maintain watch state and the CPU for serializing objects to JSON for each watcher. Large clusters with many watchers may need to tune API server resources accordingly.

Custom Resource Definitions: Extending the API

Custom Resource Definitions (CRDs) allow users to extend the Kubernetes API with their own resource types. This powerful feature enables the creation of domain-specific APIs that follow the same patterns and conventions as built-in resources.

When you create a CRD, you're essentially teaching the API server about a new kind of resource. The CRD specification defines the resource's API group, version, kind, and schema. Once the CRD is created, the API server automatically exposes REST endpoints for that resource and handles storage in etcd. The API server also applies the same authentication, authorization, and admission control pipeline to custom resources as it does to built-in resources.

The real power of CRDs emerges when combined with custom controllers. These controllers watch the custom resources and take action to implement the desired state. This pattern, known as the operator pattern, allows you to encode operational knowledge into software. For example, a database operator might watch for Database custom resources and automatically handle tasks like provisioning, backups, scaling, and updates. 


# Example: Creating and using a CRD

# 1. Define the CRD
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com
spec:
  group: example.com
  versions:
    - name: v1
      served: true
      storage: true
      schema: {...}
  scope: Namespaced
  names:
    plural: databases
    singular: database
    kind: Database

# 2. Create a custom resource instance
apiVersion: example.com/v1
kind: Database
metadata:
  name: my-database
spec:
  version: "13"
  storage: 100Gi

# 3. Custom controller watches Database resources and takes action

API Server Internals: Advanced Features

The API server implements several advanced features that are crucial for production Kubernetes clusters. Understanding these internals helps in troubleshooting complex issues and optimizing cluster performance.

Etcd Optimization and Caching

To reduce load on etcd, the API server implements sophisticated caching layers. The most important is the watch cache, which maintains an in-memory cache of recent resource versions. When a watcher connects, the API server can serve initial state from the watch cache rather than querying etcd. The API server also implements client-side throttling to prevent etcd from being overwhelmed by too many concurrent requests.

API Priority and Fairness

In large clusters, the API server can become a bottleneck. API Priority and Fairness (APF) is a feature that provides fine-grained control over request concurrency. APF classifies requests into priority levels and ensures that high-priority requests (like node heartbeats) aren't starved by low-priority requests (like bulk list operations).

Aggregated API Servers

Kubernetes supports aggregated API servers, which are separate API servers that can be fronted by the main kube-apiserver. This allows extension APIs to be served by dedicated processes while maintaining a unified API endpoint. The main API server proxies requests to aggregated servers based on the API group, providing a seamless experience for clients.

API Server Scaling Considerations: In high-scale environments, the API server may need tuning. Key parameters include --max-requests-inflight and --max-mutating-requests-inflight to control concurrent requests, and etcd-specific settings like --etcd-compaction-interval to manage storage growth. Monitoring API server metrics like request latency, error rates, and etcd performance is essential for maintaining cluster health.

API Architecture Summary

The Kubernetes API is a remarkably sophisticated system that provides a consistent, secure, and scalable interface for cluster management. Its RESTful design, combined with powerful features like watches, admission control, and extensibility through CRDs, makes it suitable for everything from small development clusters to massive enterprise deployments.

Understanding the API's inner workings - from the multi-stage request pipeline to the watch-based reactivity - is essential for effective Kubernetes administration. This knowledge enables better troubleshooting, more efficient operations, and the ability to extend Kubernetes to meet specific needs through custom resources and operators.

The API's design principles of consistency, security, and extensibility have proven remarkably durable, supporting Kubernetes' evolution from a container orchestrator to a universal control plane for cloud-native applications.

Custom Resource Definitions (CRDs)

CRDs extend the Kubernetes API to support custom resources, enabling users to create their own API objects and controllers.

CRD Benefits:

  • • Extend Kubernetes with domain-specific resources
  • • Reuse Kubernetes tooling (kubectl, dashboard)
  • • Leverage Kubernetes API conventions
  • • Build custom controllers and operators

CRD Components:

  • CustomResourceDefinition: API schema definition
  • Custom Resource: Instances of the custom type
  • Controller: Business logic and reconciliation
  • Webhooks: Validation and mutation

CRD Example


apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com
spec:
  group: example.com
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              databaseName:
                type: string
              engine:
                type: string
                enum: [mysql, postgresql, mongodb]
              version:
                type: string
              size:
                type: string
                pattern: "^[0-9]+(Gi|Mi)$"
  scope: Namespaced
  names:
    plural: databases
    singular: database
    kind: Database
    shortNames:
    - db

# Custom Resource Instance

API Best Practices

API Usage Guidelines

Use Client Libraries

Prefer client-go over direct REST calls for better error handling and resource management.

Implement Retry Logic

Handle transient failures with exponential backoff and retry mechanisms.

Use Watch Instead of Polling

Leverage watch API for real-time updates rather than periodic polling.

Security Practices

Implement RBAC

Use least privilege principle and proper Role-Based Access Control.

Validate Webhook Configurations

Properly configure validating and mutating webhooks with timeouts and failure policies.

Secure etcd Access

Protect etcd with TLS, authentication, and network policies.

Pro Tip: API Priority and Fairness

Enable API Priority and Fairness (APF) to prevent noisy neighbors and ensure critical requests get through during high load. Configure with --enable-priority-and-fairness=true and define FlowSchema and PriorityLevelConfiguration resources.
