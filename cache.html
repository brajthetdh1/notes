Section A — Caching Fundamentals

Q1. What is a cache, and what are its primary objectives?Core

A cache is a smaller, faster data store that holds a copy of a subset of data owned by a slower, authoritative store (the source of truth). It exploits two properties of real workloads: temporal locality (recently used data is likely to be used again) and skewed access distribution (a small fraction of keys receives most of the requests).

Its objectives, in rough order of importance:

  • Reduce latency — memory access (100 ns) or a local Redis round trip (~0.2–1 ms) instead of a disk-backed SQL query or a remote service call (5–100 ms).
  • Offload the source of truth — a 95% hit ratio means the database sees 1/20th of the traffic, which is often the difference between 5 servers and 1.
  • Cost efficiency — cached reads are dramatically cheaper than database reads, especially on managed/cloud pricing models.
  • Absorb traffic spikes — the cache rides out flash sales, viral posts, and retry storms that would otherwise collapse the database.
  • Availability under degradation — serving slightly stale data is better than serving errors when the backend is unhealthy.

The core vocabulary: a hit is served from cache, a miss falls through to the backing store. Hit ratio = hits / (hits + misses) — the single most important operational number, because latency and backend load both scale with it. The working set (the keys actually accessed in a time window) must fit in the cache for a high hit ratio; if it doesn't, a cache can add overhead with almost no benefit.

Most importantly, a cache is a correctness trade-off, not just a performance feature: every cache introduces a window in which data can be stale, and the design question is always "how much staleness can this read path tolerate?"

Q2. Why do we need a cache? When is it unnecessary or actively harmful?Core

Why we need it: there is a large and growing gap between compute speed and storage/network speed. A CPU cache hit is ~1 ns, a Redis GET ~0.2 ms, a well-tuned indexed SQL read ~1–10 ms, and a cross-region or unindexed query can be 100 ms+. For read-heavy services — which describes the vast majority of user-facing systems — the same rows are requested over and over, so recomputing or re-fetching them is pure waste. Caching collapses that repeat cost to near zero and simultaneously protects the database from the "read amplification" of millions of clients.

When caching is unnecessary:

  • The dataset is small enough that the database's own buffer pool keeps it in memory (e.g. 2 GB of reference data on a 64 GB DB host). A second cache adds a hop and a consistency problem for no gain.
  • Traffic is low or the workload is overwhelmingly write-heavy with little re-read.
  • Every request is genuinely unique (rare, but e.g. a search over a huge corpus with high-cardinality query parameters).

When caching is actively harmful:

  • Strong consistency is mandatory — balances, inventory at checkout, authorization/permission checks, financial ledgers. Serving stale data here is a bug, not a latency win.
  • Access patterns are diffuse — if the working set exceeds cache capacity, you pay the overhead and the invalidation complexity while still missing most of the time (low hit ratio, high cost).
  • Security-sensitive data with revocation semantics — caching a permissions lookup for 10 minutes means a revoked user keeps access for 10 minutes.
  • Operational complexity outweighs the benefit — a cache is a new distributed system with its own failure modes (stampede, penetration, hot keys) and a new consistency contract that every engineer on the team must understand.
Rule of thumb: cache when (read frequency × cost saved per read) clearly exceeds (invalidation complexity + staleness risk + operational burden). If you cannot state the staleness budget in one sentence, you are not ready to cache that data.
Q3. What are the different cache levels in a typical web architecture?Core

Q4. Compare local (in-process) cache vs distributed cache. What are the trade-offs?Core

A local cache lives inside the application's heap (or off-heap memory) and is reachable without any network call. A distributed cache is a separate fleet of servers reached over the network, shared by every application instance.

DimensionLocal (in-process)Distributed (Redis/Memcached)
Latency50–500 ns (no serialization, no network)0.2–2 ms round trip
CapacityBounded by app heap (a few GB at most, shared with business logic)Terabytes, scaled horizontally
ConsistencyEach instance diverges; N copies of the truthOne shared view per key
InvalidationHard — requires pub/sub broadcast to every instanceEasy — one DELETE reaches everyone
AvailabilitySurvives cache-fleet outages; dies with the processNew network dependency; failure needs a fallback path
GC impactHeap pressure, promotion to old gen, pause riskNone on the app (only serialization garbage)
CostFree (uses existing RAM)Real infrastructure cost

When local wins: tiny, hot, rarely-changing data — feature flags, configuration, currency rates, static reference tables, a per-request memoization layer, or the top few hundred keys of a hot catalog. Also excellent as an L1 in front of an L2 distributed cache, where it absorbs the 80% of traffic that hits the top 1% of keys.

When distributed wins: session state, user profiles, rate-limit counters, anything where all instances must agree, or where the working set is too large for a heap. It is also the only sane choice when you run autoscaling fleets — a local cache is cold on every new instance.

The pragmatic answer in interviews: use both, with the local layer having a very short TTL (1–10 s) and receiving explicit invalidation messages, so that correctness ultimately rests on the distributed layer and the local layer is only a latency optimization.

Q5. What is a near cache (hybrid cache), and what is the main challenge in managing it?Advanced

A near cache is an architectural pattern that combines a small local (in-process) cache — the "near" or L1 layer — with a shared distributed cache — the "far" or L2 layer. Reads check L1 first (nanoseconds), then L2 (sub-millisecond), then the source of truth. Writes go to L2 and asynchronously invalidate the L1 copies of every application instance.

The main challenge is invalidation fan-out. With 200 app instances each holding a copy of a key, a single write must reach all 200 copies, or some fraction of users will see stale data indefinitely (until the local TTL expires). This turns a simple DEL into a distributed broadcast problem with its own failure modes: dropped messages, instances that were temporarily partitioned, and messages that arrive out of order relative to a concurrent read.

Common solutions:

  • Pub/sub invalidation — Redis Pub/Sub, Kafka, or a gossip channel broadcasts "key X changed" to all instances. Subscribers drop their local copy. Must handle missed messages (Redis Pub/Sub is fire-and-forget) by falling back on TTL.
  • Very short local TTLs — 1–10 seconds, bounding worst-case staleness even if every invalidation message is lost.
  • Versioned keys — the local entry is stored with the version it was loaded at; a lightweight version check (or a global "epoch" counter) invalidates whole namespaces at once.
  • Built-in mechanisms — Redis 6+ client-side caching with RESP3 tracking does exactly this: the server tracks which keys each client has cached and pushes invalidation messages. Hazelcast, Ignite, and Oracle Coherence offer near-cache as a first-class feature.
Interview framing: the near cache trades consistency latency for read latency. State the staleness bound explicitly (e.g. "worst case 5 seconds, typical sub-millisecond after the pub/sub message lands") and explain why your business domain tolerates it.
Q6. Explain the role of a CDN as a caching layer. How does it work?Core

A Content Delivery Network is a globally distributed set of reverse-proxy caches (Points of Presence, PoPs) placed physically close to users. It is essentially a geographically distributed HTTP cache that terminates requests at the edge instead of at your origin.

Request flow:

  1. The client resolves cdn.example.com; anycast routing or GeoDNS directs it to the nearest PoP (typically 5–30 ms away).
  2. The edge checks its cache using a cache key built from the URL path, selected query parameters, the Host header, and any Vary dimensions (e.g. Accept-Encoding).
  3. Hit → the object is served from edge memory/SSD. Miss → the edge fetches from the origin (often via an intermediate origin shield that collapses misses from many PoPs into one origin request), stores the response per its headers, and serves it.
  4. Responses carry Cache-Control (max-age, s-maxage, stale-while-revalidate) and validators (ETag, Last-Modified) that control freshness and revalidation.

What it buys you: latency reduction (physics, not optimization), massive origin offload (a 95% edge hit ratio cuts origin egress by 20×), absorption of DDoS and traffic spikes, TLS termination near the user, and image/video transformation at the edge.

Design considerations:

  • Cache key hygiene — stray query strings or analytics parameters fragment the cache into uselessness. Normalize them at the edge.
  • Invalidation — purges by URL or by surrogate key / cache tag (e.g. tag every response containing product 42 with product-42, then purge the tag when the product changes). Purge propagation across hundreds of PoPs is eventual, not instant.
  • Personalization — never put user-specific data in a shared edge cache keyed only by URL. Use Vary: Cookie sparingly, split public vs private endpoints, or render personalized fragments via edge compute / ESI.
  • Immutable assets — fingerprinted filenames (app.4f2a9c.js) with max-age=31536000, immutable are the gold standard: no invalidation ever needed.
Q7. Compare Redis vs Memcached. When would you choose one over the other?Core

Both are in-memory key-value stores. Memcached is a deliberately minimal, multi-threaded cache; Redis is a single-threaded (per-shard) data-structure server that is also usable as a database, queue, and coordination primitive.

FeatureMemcachedRedis
Data typesStrings / opaque blobs onlyStrings, hashes, lists, sets, sorted sets, bitmaps, HyperLogLog, streams, geospatial
ThreadingMulti-threaded, scales across cores on one boxSingle-threaded command execution per shard (I/O threads in 6+)
PersistenceNone — restart = cold cacheRDB snapshots, AOF log
Replication / HANone built in (clients hash across nodes)Replication, Sentinel, Redis Cluster with automatic failover
ClusteringClient-side consistent hashingServer-side cluster mode with 16384 hash slots
AtomicitySingle-key ops onlyLua scripting, MULTI/EXEC transactions, atomic data-structure ops
Pub/Sub & streamsNoYes (also keyspace notifications)
Max object size1 MB default512 MB
Memory efficiencySlab allocator, very predictableHigher per-key overhead, jemalloc

Choose Memcached when you need a pure, simple, high-throughput object cache with a fixed-size working set, you want to exploit many cores on a single box, and you genuinely do not care about losing the cache on restart (which is usually true for caches). It is operationally simpler and often cheaper per byte.

Choose Redis when you need any of: richer data structures (leaderboards, rate limiters, queues, counters), atomic multi-step operations via Lua, persistence across restarts, built-in replication and failover, or pub/sub for invalidation. The overwhelming majority of new systems pick Redis because the extra capabilities cost little and eliminate the need for a second system.

Honest caveat: Redis's single-threaded execution means one hot key can saturate a core — an O(N) command on a large collection (e.g. KEYS, SMEMBERS on a million-member set, ZRANGE with a huge range) blocks everything on that shard. Memcached has no such global-blocking operations.

Q8. What is TTL in caching systems, and what role does it play?Core

TTL (Time-to-Live) is the duration after which a cache entry is considered expired and must not be served — it is a staleness bound enforced by the cache itself, independent of whether any application code remembered to invalidate it.

Its roles:

  • Bounds staleness — turns "stale forever if a bug drops an invalidation" into "stale for at most N seconds". This is the single most important safety property of any cache.
  • Bounds memory growth — keys that are never read again are eventually reclaimed without needing a full eviction sweep.
  • Self-healing — after a missed invalidation, a partition, or a deploy bug, the system converges automatically. No manual cleanup runbook required.
  • Backstop for correctness — combined with explicit invalidation, TTL is the safety net; explicit invalidation is the fast path.

How expiry actually works: Redis uses a hybrid. Lazy (passive) expiry checks the TTL on access and deletes on the spot. A background active expiry cycle samples keys with TTLs 20 times per second and deletes a fraction of expired ones, so memory is reclaimed even for keys never touched again. Memcached is purely lazy plus LRU eviction.

Choosing a TTL: derive it from a stated staleness budget, not from a guess. "Price display can be 30 s stale; checkout must be exact." Then vary it: hot, expensive-to-recompute data gets a longer TTL; volatile, cheap data gets a shorter one. Add jitter (±10–20%) to every TTL — if a million keys are populated at deploy time with the same TTL, they all expire together and produce an avalanche.

Trap to avoid: setting TTL = infinity "to improve hit ratio." It improves the hit ratio and destroys the safety net — the cache becomes a permanently divergent copy of the database, and any invalidation bug becomes permanent corruption.

Section B — Read & Write Caching Strategies

Q9. Explain the Cache-Aside (Lazy Loading) pattern. Advantages and disadvantages?Core

Cache-aside is the default pattern: the application is responsible for talking to both the cache and the database. It reads the cache first, and on a miss it reads the database and populates the cache itself.

def get_product(pid):
    v = cache.get(f"product:{pid}")
    if v is not None:
        return v                     # HIT
    v = db.query("SELECT ... WHERE id=?", pid)   # MISS
    if v is None:
        cache.set(f"product:{pid}", NULL_SENTINEL, ttl=30)   # negative cache
    else:
        cache.set(f"product:{pid}", v, ttl=300 + jitter())
    return v

def update_product(pid, data):
    db.execute("UPDATE products SET ... WHERE id=?", pid)   # 1. DB first
    cache.delete(f"product:{pid}")                          # 2. then invalidate

Advantages

  • Dead simple and completely explicit — the caching logic is visible in one place.
  • Only caches what is actually requested, so memory is spent on real demand. Excellent for large datasets with a skewed hot set.
  • Cache failure is not fatal — if Redis is down, every request becomes a miss and the app still works (slowly). The cache is a pure optimization.
  • Works with any cache technology and any data shape; the cache need not understand your schema.

Disadvantages

  • Every miss costs three round trips (cache miss → DB read → cache write), and the very first request after expiry is always slow.
  • Write/read race conditions — a concurrent reader can repopulate the cache with a stale value after a writer has invalidated it (see Q14).
  • Consistency depends entirely on application discipline — every write path in every service must remember to invalidate, and one forgotten path means permanent staleness.
  • Cache stampedes on popular keys, since many clients miss simultaneously (see Q24).
Q10. Explain the Read-Through pattern. How does it differ from Cache-Aside?Core

In read-through, the application talks only to the cache. The cache (or a cache library sitting in front of the database) is configured with a loader that knows how to fetch a missing key from the source of truth. On a miss, the cache itself calls the loader, stores the result, and returns it.

# Application code — no DB access at all
product = product_cache.get(pid)   # loader configured inside the cache

# Cache configuration
product_cache = ReadThroughCache(
    loader = lambda pid: db.query("SELECT ... WHERE id=?", pid),
    ttl    = 300
)

Difference from cache-aside: the miss-handling logic moves into the cache layer rather than living in application code. The application never sees a miss; it just sees a slower response.

Advantages

  • Thinner, cleaner application code — no duplicated cache logic in every service, no chance of a developer forgetting to populate on miss.
  • Uniform loading path — makes it easy to add request coalescing (single-flight), metrics, and retry policy in one place.
  • Works well with ORM-level caches (Hibernate L2 cache) and cache libraries that support loaders (Guava/Caffeine CacheLoader, Ehcache).

Disadvantages

  • The cache becomes part of the critical path and must understand the data model — a coupling that is awkward in microservice architectures, where a shared cache shouldn't know how to query three different services' databases.
  • Cache outages become hard failures rather than graceful degradation, unless a fallback loader is implemented.
  • Read-through alone says nothing about writes — you still need write-through, write-behind, or explicit invalidation alongside it.
  • Cold-start and mass-expiry behaviour is invisible to the app, which can hide problems.

Interview soundbite: "Read-through is cache-aside with the miss logic inverted into the cache library. It trades application flexibility for consistency of behaviour across services."

Q11. Explain the Write-Through pattern. What are the trade-offs?Core

In write-through, every write goes to the cache and the database synchronously, in the same operation. The cache (or cache library) is responsible for propagating the write to the backing store before acknowledging success to the caller. The cache is typically placed in front of the database as an intercepting layer.

def update_product(pid, data):
    cache.put(f"product:{pid}", data)   # cache writes to DB *and* stores, then returns
    # caller only returns after both succeed

Advantages

  • The cache is never stale for data it holds — write-through combined with read-through gives read-your-writes consistency for cached keys, with no invalidation messages at all.
  • No invalidation race conditions — there is no "delete after write" window in which a stale value can be repopulated, because the new value is written atomically into both tiers.
  • Simple mental model — one code path for writes, one for reads.
  • Recovery is easier: after a cache restart, cached reads are correct by construction once loaded.

Disadvantages

  • Write latency increases to roughly the max of cache and DB write time, and every write pays for both. For write-heavy workloads this is significant.
  • Cache pollution — you write into the cache data that may never be read (e.g. a user updates a setting once and never views it again). This evicts genuinely hot entries and lowers the hit ratio.
  • Two systems must succeed — you need to decide what "the cache succeeded but the DB failed" means, and vice versa. Usually the DB is authoritative and a cache failure is tolerated (write DB, log cache error).
  • Not useful for write-once/read-never data, or for bulk writes.

Best fit: read-heavy systems that also write moderately and need tight read-after-write consistency — user profile updates, configuration, catalog metadata with immediate-visibility requirements.

Q12. Explain the Write-Behind (Write-Back) pattern. Benefits and risks?Core

In write-behind (also called write-back), the application writes only to the cache, which acknowledges immediately and flushes the writes to the database asynchronously, usually in batches, after a delay, or on a schedule.

def increment_view_count(video_id):
    cache.incr(f"views:{video_id}")       # returns instantly
    # a background flusher every 5s does:
    #   MULTI; GET views:*; DEL views:*; EXEC
    #   then bulk UPDATE videos SET views = views + ? ...

Benefits

  • Very low write latency — the client waits for an in-memory operation (sub-millisecond) instead of a disk commit.
  • Massive write reduction on the database — 100,000 increments to the same counter can collapse into a single UPDATE ... SET n = n + 100000. This is the key insight for counters, view counts, likes, and metrics.
  • Absorbs write spikes — a flash sale or viral event is buffered in the cache instead of crushing the database.
  • Batching amortizes transaction and fsync overhead across many writes.

Risks

  • Data loss window — anything not yet flushed is lost if the cache node dies. This is unacceptable for money, orders, or anything with a durability guarantee. It is perfectly acceptable for view counts and metrics.
  • The cache becomes the temporary source of truth — reads must come from the cache or they'll see the old DB value, so write-behind is only coherent when paired with reads-from-cache.
  • Ordering and idempotency — flushing must preserve per-key ordering (writes to key X must be applied in order), and retries after a failed flush must be idempotent or they'll double-apply (e.g. increment 1,000,000 twice).
  • Operational complexity — the flusher is now a critical component with its own monitoring, backpressure, and replay logic (usually backed by a durable queue like Kafka to close the loss window).
Safe pattern: write-behind into the cache, but append the same event to a durable log (Kafka) in the same critical section. Then a lost flush can be replayed, converting "data loss" into "delayed write".
Q13. Explain the Write-Around pattern. When would you use it?Core

In write-around, writes go directly to the database and bypass the cache entirely. The cache is populated only later, when someone actually reads the data (typically via cache-aside or read-through).

def update_document(doc_id, body):
    db.execute("UPDATE documents SET body=? WHERE id=?", body)
    # deliberately NOT writing to cache — next read will populate it

Why you'd do this:

  • Avoids cache pollution — if writes are large (multi-MB documents, log entries, audit records) and are rarely read back soon, caching them on write evicts genuinely hot entries and wastes memory.
  • Protects the cache from write storms — bulk imports, backfills, and batch jobs should never go through the cache.
  • Good for write-once, read-later data — e.g. an uploaded report that the user will view a few minutes later, or an archived order.

Trade-off: the first read after a write is always a miss and pays full database latency. For data that is written and immediately re-read (e.g. a user submits a form and is redirected to the result page), write-around creates a visible latency bump — a hybrid of write-through-for-hot-keys and write-around-for-cold-keys is often the right answer.

Also important: write-around does not mean "ignore the cache on write". If the key is already cached and you write directly to the DB without invalidating, you have created stale data. The correct form is write to DB, then delete the cache key — which is precisely the cache-aside write path. "Write-around" is really shorthand for "write to DB, invalidate, and do not repopulate."

Q14. In the Cache-Aside pattern, should you update or delete the cache entry after a write? Why?Trap

Delete (invalidate), do not update. This is the standard answer, and the reasoning matters more than the conclusion.

Why deleting is safer:

  1. Update races lose data. Two concurrent writers computing a new value from a read-modify-write cycle can write their results to the cache out of order, leaving the cache permanently holding the older value even though the database has the newer one. A DELETE is idempotent and order-insensitive — deleting twice or out of order still yields "absent", and the next read repopulates from the database with whatever value is current.
  2. Delete is cheaper and smaller — one command with no payload, versus serializing and shipping a whole object that may be much larger than the key.
  3. It avoids caching data nobody will read. The next read (if any) populates the cache on demand, preserving the "only cache what's requested" property.
  4. It sidesteps partial/derived state. If the cached value is an aggregate (a JSON blob assembled from three tables), the write path may not be able to reconstruct the full cached representation cheaply.

But deletion has its own race. The classic failure sequence:

t1  Reader: cache miss for key K
t2  Reader: reads DB  → value v1
t3  Writer: writes DB → value v2
t4  Writer: deletes cache key K
t5  Reader: writes v1 into cache        <-- STALE, and no TTL to save it

Mitigations:

  • Always set a TTL as a backstop, so the stale entry cannot live forever.
  • Delayed double delete — delete after the write, then delete again after a delay greater than the read-repopulate window (a pragmatic hack, not a guarantee).
  • Versioned / CAS writes — store a monotonically increasing version with the value and only accept a cache write if its version is newer than the cached version. This closes the race properly.
  • Delete-after-commit — invalidate only after the DB transaction commits, ideally driven by CDC (see Q21), so the invalidation ordering is globally correct.
  • Leases — the reader that misses takes a short lease; concurrent readers wait for it, so only one thread can repopulate (also solves the stampede).
Q15. Which caching pattern would you choose for a read-heavy system vs a write-heavy system?Core

There is no universal answer — the right pattern follows the read/write ratio, the staleness budget, and the durability requirement. A useful decision table:

Workload characteristicRecommended patternWhy
Read-heavy, tolerate seconds of staleness (product pages, profiles)Cache-aside + TTL + delete-on-writeMaximum hit ratio for minimum memory; simple; degrades gracefully if the cache dies
Read-heavy, need read-after-write visibilityRead-through + write-throughNo invalidation race; cache is never stale for keys it holds
Write-heavy with hot re-reads (counters, likes, views, metrics)Write-behind (+ durable log)Coalesces thousands of writes into one DB update; sub-millisecond write ack
Write-heavy, write-once/read-later, large payloadsWrite-around (DB write + invalidate)Avoids polluting the cache with cold, bulky objects
Mostly writes, almost no repeat readsNo cache at allCache adds a hop, a consistency problem, and no benefit
Read-heavy, tiny hot set, extreme QPSLocal cache + write-behind invalidationNanosecond reads; the top 1% of keys absorbs 80% of traffic

Read-heavy reasoning: the cache pays for itself on the first read and every read thereafter, so favour patterns that maximize hit ratio and keep the read path short. Cache-aside is usually best because it only stores what's actually demanded; write-through is the upgrade when stale reads are visible to users.

Write-heavy reasoning: a cache helps only if writes are aggregatable or re-readable. For counters, write-behind is transformative (a 100× reduction in DB writes). For independent, unique writes with no re-read, the cache is dead weight — and worse, keeping it coherent consumes more capacity than the writes themselves.

The senior-level nuance: most real systems are mixed and use per-entity patterns. An e-commerce app might use write-through for inventory (must be accurate), cache-aside for product descriptions (tolerates minutes of staleness), write-behind for view counters (loss-tolerant), and no cache at all for order placement. State the mapping per data class, not per system.

Q16. What is the relationship between caching patterns and the consistency model they provide?Advanced

Each pattern implies a different consistency guarantee, and being explicit about this is what separates a senior answer from a memorized one.

PatternConsistency for the writing clientConsistency for other clients
Cache-aside, no invalidation, TTL onlyNone (may read its own old write)Eventually consistent after TTL
Cache-aside + delete-on-writeRead-your-writes usually, with a small race windowEventually consistent (next read repopulates)
Write-through (+ read-through)Read-your-writes, strongly for cached keysRead-your-writes for anyone hitting the same cache node
Write-behindRead-your-writes from cache onlyEventually consistent; readers of the DB see old data
Write-aroundNone until the cache entry is deletedStale until TTL or explicit invalidation
Near cache with pub/sub invalidationRead-your-writes if invalidation is synchronousEventually consistent within the invalidation propagation window

The general rule: a cache can never provide stronger consistency than the underlying store, and every caching layer weakens consistency by adding a replication step that isn't transactional with the write.

How to get read-your-writes without giving up caching:

  • Write-through for the writing user, and let everyone else be eventually consistent.
  • Session pinning — route a user's reads to the same cache shard that received their write (fragile, breaks on failover).
  • Version tokens — return the new version in the write response; the client (or the gateway) refuses cache entries with a lower version.
  • Bypass the cache for the writing user for N seconds — a "read from primary after write" flag, common in social feeds and profile edits.

What you cannot have: strong consistency, sub-millisecond reads, and high availability, all at once. That is a CAP-theorem trade-off expressed at the cache tier, and the interviewer wants to hear you name it.

Section C — Eviction & Invalidation

Q17. What is the difference between cache expiration (TTL) and cache eviction?Core

They are frequently confused, but they are driven by completely different triggers and serve different purposes.

Expiration (TTL)Eviction
TriggerTime elapsed since the entry was writtenMemory/space pressure — the cache is full
PurposeBound staleness and correctnessBound memory; decide what to sacrifice
Decided byThe application (when it sets the TTL)The cache server (LRU, LFU, random, ...)
OutcomeEntry becomes invalid and is deletedEntry is removed even if still fresh
Can it happen early?No — TTL is a minimum lifetimeYes — eviction can remove a brand-new entry

Both usually coexist. A Redis instance with maxmemory and allkeys-lru will evict entries to stay under the memory limit, and expire entries whose TTL has passed. An entry can therefore leave the cache for either reason — and if eviction pressure is high, TTLs are largely irrelevant because entries die long before they expire.

Why the distinction matters in design:

  • If your correctness depends on staleness bounds, TTL is mandatory — eviction gives you no guarantees at all about freshness (an entry can survive forever if memory never fills).
  • If your memory is over-provisioned and nothing is ever evicted, you are relying entirely on TTL for correctness — fine, but say so explicitly.
  • When the cache is under heavy eviction, the hit ratio collapses even though TTLs look correct. That's a capacity problem, not a correctness problem, and the fix is more memory or a better key design, not shorter TTLs.

Operationally: monitor them separately. A rising eviction rate with a stable TTL distribution means the working set has outgrown the cache. A rising miss rate with no evictions means TTLs are too short or invalidation is too aggressive.

Q18. Explain common cache eviction policies: LRU, LFU, FIFO, TTL-based.Core

Eviction policies answer: when memory is full, which entry do we drop?

  • LRU (Least Recently Used) — evict the entry whose last access is oldest. Based on temporal locality: what you used recently you'll likely use again. Excellent for workloads with a stable hot set; catastrophically bad for scans (a single full-table scan flushes the entire cache, and none of the scanned data is ever re-read). Requires a hash map plus a doubly linked list, so every read mutates the structure — a concurrency hot spot under high QPS.
  • LFU (Least Frequently Used) — evict the entry with the fewest accesses. Protects long-lived popular keys from one-off bursts. Its weakness is stale popularity: a key that was hot last month keeps a high counter and won't be evicted even after it goes cold. Practical implementations add aging — counters decay over time (Redis's LFU uses a probabilistic 8-bit counter with a decay rate) — or use TinyLFU (a count-min sketch for frequency plus a small LRU window) which gives excellent hit ratios with tiny memory overhead and is what Caffeine uses.
  • FIFO (First-In, First-Out) — evict the oldest inserted entry, ignoring access entirely. Trivially cheap (a queue), but it will evict a hot key just because it was loaded early. Rarely the right choice; occasionally used where all entries have equal expected value and TTL is the real freshness control.
  • TTL-based — entries expire on a timer regardless of capacity. Not really an eviction policy (it doesn't respond to pressure) but it is often the only policy in caches that are never allowed to fill, and it's the universal backstop for correctness.
  • Random — evict a random entry. Surprisingly competitive, extremely cheap and lock-free, and it avoids the pathological scan behaviour of LRU. Redis's allkeys-random.
  • CLOCK / second-chance — an LRU approximation using a reference bit and a circular buffer; used by Linux page cache and many hardware caches because it's O(1) with no list surgery.

Choosing: default to LRU (or TinyLFU if the library offers it — it is strictly better in practice), switch to LFU with aging when there are long-lived hot keys and periodic scans, and use TTL as the correctness layer regardless of which eviction policy you pick. For interview answers, always mention that Redis implements approximated LRU by sampling a handful of random keys and evicting the best candidate — precise LRU is too expensive under its single-threaded model.

Q19. How would you implement an LRU cache with O(1) get and put?Core

The classic answer: a hash map plus a doubly linked list.

  • The hash map gives O(1) lookup from key to the list node — this is what makes get O(1).
  • The doubly linked list maintains recency order: most recently used at the head, least recently used at the tail. Because each node has both prev and next pointers, removing a node or moving it to the head is O(1) without scanning — this is why it must be doubly linked, not singly.
class LRUCache:
    def __init__(self, capacity):
        self.cap = capacity
        self.map = {}                    # key -> node
        self.head = Node()               # sentinel: most recent
        self.tail = Node()               # sentinel: least recent
        self.head.next, self.tail.prev = self.tail, self.head

    def _unlink(self, n):
        n.prev.next, n.next.prev = n.next, n.prev

    def _push_front(self, n):
        n.next, n.prev = self.head.next, self.head
        self.head.next.prev, self.head.next = n, n

    def get(self, key):
        if key not in self.map: return -1
        n = self.map[key]
        self._unlink(n); self._push_front(n)      # O(1) recency update
        return n.val

    def put(self, key, val):
        if key in self.map:
            n = self.map[key]; n.val = val
            self._unlink(n); self._push_front(n)
        else:
            if len(self.map) == self.cap:          # evict LRU
                lru = self.tail.prev
                self._unlink(lru); del self.map[lru.key]
            n = Node(key, val)
            self.map[key] = n; self._push_front(n)

In Python, collections.OrderedDict does exactly this internally: move_to_end and popitem(last=False) give O(1) LRU in five lines. In Java, LinkedHashMap with accessOrder=true and an overridden removeEldestEntry does the same.

What the interviewer wants beyond the data structure:

  • Thread safety — a global lock serializes everything; the real answer is to shard the cache into N independent LRUs (by hash(key) % N), each with its own lock, which also improves locality.
  • Memory overhead — each entry costs a key, a value, two pointers, and hash-bucket overhead; doubling memory usage for the linked list is real.
  • Why production caches don't do exact LRU — mutating a linked list on every read is a contention nightmare at 100k+ QPS. Redis samples ~5 random keys and evicts the least-recently-used among them, trading a small hit-ratio loss for a huge throughput gain.
Q20. What is cache invalidation, and why is it considered one of the hardest problems in computer science?Core

Cache invalidation is the process of ensuring that a cached copy stops being served once the underlying data has changed. It is hard because the cache and the source of truth are two independent systems with no shared transaction — you can never atomically update both, so there is always a window, a race, or a failure mode where they disagree.

Why it's genuinely hard:

  1. No distributed transaction. Writing to the DB and deleting from the cache are two operations against two systems. Either can fail independently, and there is no rollback across them. You end up with "DB updated, cache not invalidated" (stale forever) or "cache deleted, DB write failed" (harmless — a miss just reloads the old value).
  2. Concurrent read/write interleaving. The sequence in Q14 shows how a slow reader can resurrect a stale value after invalidation. Fixing this properly requires versions, CAS, or leases — all of which add complexity to the hot path.
  3. Multiple cache layers. Browser, CDN, reverse proxy, local in-process, and distributed cache each hold a copy. Invalidating all of them correctly and in order is a distributed broadcast problem.
  4. Derived and aggregate data. A cached page may combine 30 database rows from 6 services. A change to one row must map to the correct cache keys — which requires surrogate keys/tagging, and every writer must know the tagging scheme.
  5. Replication lag. If the reader hits a database replica that hasn't caught up, it repopulates the cache with the old value even though the write already happened. This is the most commonly missed cause of "impossible" staleness.
  6. Deletes and re-creates. A key deleted from the DB but still in the cache returns a "ghost" object. A key re-created with a new ID after deletion may collide with a negative cache entry.
  7. It's unobservable when it fails. A missed invalidation doesn't throw an exception — it silently serves wrong data until someone notices, which may be days later.
The pragmatic answer interviewers want: you cannot solve invalidation perfectly, so you bound it. Combine (a) explicit invalidation on write for the fast path, (b) TTL as a guaranteed staleness ceiling, (c) CDC-driven invalidation so no write path can forget, and (d) versioned keys for data where correctness is critical. Then state the resulting staleness budget in seconds.
Q21. What are the different strategies for cache invalidation at scale?Advanced

At scale, no single mechanism is sufficient — production systems layer several.

  • TTL-based expiry. The universal backstop. Cheap, requires no coordination, and guarantees a maximum staleness window. Weakness: it is not responsive to writes, so data can be stale for the full TTL after a change. Always add jitter so a cohort of keys doesn't expire simultaneously.
  • Write-through / explicit delete-on-write. The fast path: the writing service deletes or updates the cache key immediately after committing. Sub-second freshness. Weakness: requires every writer in every service to participate, and it is easy to miss a code path. Also subject to the read-repopulate race.
  • CDC (Change Data Capture) driven invalidation. Tail the database's write-ahead log with Debezium/Maxwell, publish change events to Kafka, and have an invalidator service delete the corresponding cache keys. This is the gold standard at scale because it is impossible for a write to bypass it — even direct SQL migrations, manual fixes, and other services' writes generate events. It also decouples invalidation from application code. Weakness: added latency (typically 100 ms–2 s), an extra pipeline to operate, and ordering must be preserved per key.
  • Versioned / immutable keys. Instead of invalidating, change the key: product:42:v17, or embed a global version/epoch in the key. Old entries simply age out via TTL and are never read again. Ideal for CDN assets (content-hash filenames) and for any object that is cheap to re-key. Downside: key churn increases memory pressure and cold-miss rates.
  • Surrogate keys / cache tags. Tag every cached object with the entities it depends on (tag:product-42) and purge by tag. This is how CDNs and reverse proxies (Varnish, Fastly, Cloudflare) handle "invalidate everything that mentions product 42" without knowing the URLs in advance.
  • Pub/sub fan-out for near caches. Broadcast invalidation messages to every application instance holding a local copy (Redis Pub/Sub, Kafka, or the cache's native tracking, like Redis RESP3 client-side caching).
  • Leases / CAS / version guards. Prevent stale repopulation structurally: only accept a cache write if its version is newer than what's already stored.

How to combine them: explicit delete for latency, CDC as the safety net that catches writes the app forgot, TTL with jitter as the absolute correctness ceiling, and versioned keys where even a one-second staleness is unacceptable. Then instrument invalidation lag as a first-class metric — if it's not measured, it's not working.

Q22. What is cache warming (preloading), and why would a backend service use it?Core

Cache warming is populating the cache with the expected hot keys before real traffic arrives, so the system doesn't start cold. A cold cache means every early request is a miss, so the database sees a spike of full latency and full load at exactly the moment traffic is highest — a self-inflicted thundering herd.

When warming matters:

  • After a deploy or rolling restart — a fleet of fresh instances each with an empty local cache.
  • After a cache cluster restart or failover — a 10 TB cache coming back empty will stampede the database instantly.
  • Before a known traffic event — a flash sale, a product launch, a Super Bowl ad, a scheduled promotion. Preload the specific SKUs or pages involved.
  • After adding capacity — a new Redis node owns a fresh hash range; warm it before routing traffic there.
  • Recovering from a mass expiry — deliberately repopulate rather than let requests do it one by one.

How to warm:

  • Replay the access log — take the top-N keys from the last 24 hours of request logs and MGET/pipeline them into the cache.
  • Offline job over known-popular entities — top 10,000 products, all active feature flags, the current front-page content.
  • Shadow / canary traffic — send a fraction of real traffic to the new node with responses used to populate, not served to users.
  • Lazy warming on startup — background thread populates while the instance is still marked unready in the load balancer.
  • Warm on read-replica promotion — before accepting traffic.

Caveats: warming costs real backend load and time (a 10 TB cache cannot be fully warmed cheaply), so warm only the hot subset — the top few percent of keys that absorb most traffic. It also risks warming the wrong data after an access pattern shift. And a warmed cache can mask a broken loading path, so keep the cold-start path exercised.

Related technique: never-expire + async refresh — hot keys are stored without a TTL and refreshed by a background job. Combined with warming, this eliminates the expiry spike entirely, at the cost of the cache needing to be treated as semi-durable.

Q23. How do you choose a TTL for a given piece of data? Walk through the reasoning.Core

TTL selection is a product decision expressed as an engineering parameter. The reasoning chain:

  1. State the staleness budget. Ask the product owner: "If a user sees this data up to N seconds old, is that acceptable?" Typical answers: view counts, minutes; product descriptions, minutes; prices, seconds to a minute (with a revalidation at checkout); inventory availability, seconds; account balance, zero — do not cache; user permissions, seconds to a minute with explicit revocation hooks.
  2. Estimate the recompute cost. A 2 ms indexed read tolerates a short TTL; a 3-second aggregation over 50 million rows justifies a 10-minute TTL. TTL should be long enough that the cache actually saves work — if a key is read twice per hour and the TTL is 60 s, you're barely caching.
  3. Estimate the invalidation mechanism's reliability. If you have solid CDC-based invalidation, you can use a long TTL because explicit invalidation handles freshness and the TTL is only a backstop. If you rely on TTL alone, it must be short enough to carry the entire correctness burden.
  4. Budget the memory. Longer TTLs mean more live keys and a larger working set. If the cache is already evicting heavily, extending TTLs will lower the hit ratio, not raise it.
  5. Add jitter. Apply ±10–20% randomization to every TTL so keys populated together don't expire together — the difference between an avalanche and a smooth refresh.
  6. Measure and tune. Watch hit ratio, database QPS, and the distribution of observed staleness (if you have version numbers, you can literally measure how stale served data is). Adjust until the hit ratio plateaus.

Composite pattern worth naming: a short TTL plus stale-while-revalidate. Serve the cached value immediately even if it's slightly past its fresh window, and kick off a single background refresh. The user gets consistent low latency; the data converges within the stale window; the backend sees one refresh instead of a thousand misses.

Anti-patterns: a single global TTL for every data type (guarantees you're either too stale somewhere or too cold somewhere); TTLs chosen once and never revisited; TTLs of 24 hours on data that changes hourly "because the hit ratio is great" (you've built a second, wrong database).

Section D — Failure Modes & Mitigations

Q24. What is a cache stampede (thundering herd)? How do you prevent it?Trap

A cache stampede — also called dog-piling or the thundering herd — happens when a single popular key expires or is invalidated and a large number of concurrent requests all miss simultaneously. Every one of them hits the database to recompute the same value, so the backend receives N duplicate expensive queries for one logical piece of work. A hot key with 50,000 QPS and a 300 ms recompute time can produce a 50,000-request burst against the database in the space of a few hundred milliseconds — usually enough to push a query latency from milliseconds to seconds, which then causes more requests to pile up.

Causes: a popular key reaching its TTL; a deploy that invalidates everything at once; a cache node restart; an explicit purge of a hot key; synchronized TTLs across many keys (a TTL avalanche at a smaller scale).

Mitigations, in rough order of preference:

  • Single-flight / request coalescing (a per-key mutex). The first requester to miss acquires a lock for that key and recomputes; all others either wait briefly and then read the freshly populated cache, or return stale data. This reduces N database reads to exactly 1. In-process: singleflight in Go, CacheLoader in Caffeine (which coalesces concurrent loads automatically), a SETNX lock in Redis for cross-instance coordination.
  • Serve stale while revalidating. Never let a hot key simply vanish. Keep serving the old value slightly past expiry, and let exactly one request refresh it in the background (stale-while-revalidate, or an explicit "soft TTL / hard TTL" pair). Users see instant responses and the backend sees one refresh.
  • Probabilistic early refresh (XFetch). Each request that hits a key computes a small probability of refreshing it early, increasing as the expiry approaches. This spreads refresh work smoothly over time instead of concentrating it at expiry. The formula is roughly: refresh if now - (ttl * beta * ln(random())) >= expiry.
  • Jittered TTLs. Prevents mass simultaneous expiry — essential when millions of keys are written in one batch (a deploy or a bulk import).
  • Cache warming / never-expire hot keys. Remove the expiry event for the top-K keys entirely and refresh them on a schedule.
  • Backpressure at the database. A connection-pool limit plus a circuit breaker ensures a stampede degrades the affected endpoint rather than taking down the entire database.

The key insight for interviews: a stampede is a concurrency problem, not a caching problem. The fix is always to reduce N concurrent identical computations to 1, and the cheapest way to do that is to never let the hot key become absent in the first place.

Q25. What is cache penetration? How does it differ from a stampede, and how do you solve it?Trap

Cache penetration is when requests are made for keys that do not exist at all — neither in the cache nor in the database. Because there is nothing to cache, every single request falls through to the database. A malicious actor (or a buggy client) issuing millions of requests for random non-existent IDs can therefore bypass the cache entirely and hit the database with 100% of its traffic.

How it differs from a stampede:

Cache stampedeCache penetration
Key exists?Yes — one hot, real keyNo — the key is invalid/nonexistent
PatternMany requests, all at once, at expirySustained requests, often for different random keys
Root causeConcurrency on a single keyRequests that can never be satisfied by the cache
Typical triggerTTL expiry on a popular keyScanning/attack with random IDs; deleted entities

Solutions:

  • Cache the negative result. Store a sentinel (NULL, __NOT_FOUND__) for the missing key with a short TTL (30–120 s). Subsequent requests hit the cache and are rejected immediately. This is the simplest and most common fix. Trade-off: a newly created entity may be invisible for the negative TTL, so invalidate the sentinel on create, or keep the TTL short.
  • Bloom filter. Maintain a Bloom filter of all valid keys in front of the cache. A request for a key the filter says is absent is rejected without touching the cache or database. Bloom filters are tiny (~10 bits per key for a 1% false-positive rate) and O(1), but they can produce false positives (which just fall through harmlessly) and need rebuilding as the key set changes — or a counting/rotating Bloom filter.
  • Input validation and authorization. If IDs are UUIDs or signed tokens rather than sequential integers, guessing valid ones becomes infeasible. Reject malformed or unauthorized IDs at the gateway.
  • Rate limiting and anomaly detection. Per-IP/per-user request limits, plus alerting on an unusually high miss ratio for a single client or key prefix — a near-100% miss rate on a random-looking ID range is an attack signature.
  • WAF / bot protection at the edge.

Why negative caching alone is usually enough: it converts an unbounded attack into a bounded one, because every unique invalid key costs exactly one database lookup and is then absorbed by the cache for the TTL. The Bloom filter is the upgrade for when even that single lookup is too expensive.

Q26. What is a cache avalanche? How is it different from a stampede, and what are the mitigations?Trap

A cache avalanche is a mass failure of the caching tier, where a very large fraction of keys become unavailable at once, sending essentially all traffic to the database simultaneously. The database, sized for maybe 5% of traffic, collapses; the resulting timeouts make clients retry, which adds more load, and the whole system fails in a cascade.

Common causes:

  • Synchronized expiry — millions of keys written at the same moment (a deploy, a nightly job, a bulk import) with the same TTL all expire together.
  • Cache node or cluster restart — a full Redis restart brings back an empty cache; if it's not warmed, the next minute is 100% database traffic.
  • Cache tier outage — network partition, OOM kill, AZ failure, or a bad deploy of the cache fleet.
  • Memory exhaustion — the cache starts evicting aggressively, collapsing the hit ratio to near zero.

How it differs from a stampede and from penetration: a stampede is one key and a burst of concurrent identical work; penetration is requests for keys that never existed; an avalanche is a systemic loss of cache capacity affecting all keys at once. The blast radius is the whole service, not one endpoint.

Mitigations:

  • TTL jitter (the single most important fix). Randomize every TTL by ±10–20% so expirations spread out over time instead of clustering. Also stagger bulk loads.
  • Multi-tier caching. A local L1 in front of the distributed L2 means an L2 outage still leaves a meaningful hit ratio locally — often enough to keep the database under its limit.
  • Circuit breakers and load shedding. When the cache is unavailable, the database must be protected: limit its connection pool, return 503/429 for a fraction of requests, and serve degraded responses (cached-at-edge fallbacks, empty recommendations) rather than collapsing.
  • Graceful degradation policy. Decide in advance what happens per endpoint: serve stale from a local emergency cache, serve a static fallback, or fail fast. "Fail open to the database for everything" is the wrong default.
  • High availability for the cache itself. Replicas, automatic failover (Redis Sentinel/Cluster), multi-AZ placement, and enough headroom that a single node loss doesn't cause a cascade.
  • Warm restart. Persist the cache (RDB/AOF) or warm from access logs before returning a restarted cache to the load balancer, and ramp traffic gradually.
  • Retry budgets and jittered backoff. Prevents retry storms from multiplying the load on an already-struggling database.
Q27. What is the hot key problem, and how do you handle a single key receiving massive traffic?Advanced

A hot key is a single cache key that receives a disproportionate share of traffic — a celebrity's post, a front-page banner, a viral video, a popular SKU during a flash sale, a global configuration flag. Even though the cache is hit almost 100% of the time, the load is not distributed: all requests for that key land on the single node that owns it. Because sharding is by key hash, you cannot spread one key across shards by adding nodes. The result is one saturated CPU core (Redis is single-threaded per shard) and one saturated NIC, while the rest of the cluster sits idle.

Symptoms: one Redis node at 100% CPU while siblings are at 10%; rising p99 for one specific endpoint; hot key detection warnings in managed Redis consoles; timeouts concentrated on a single key.

Mitigations:

  • Key replication (fan-out on read). Store the value under N replicas: post:42:0 … post:42:9, and have each client pick a random suffix on read. This spreads the load across N shards. Writes go to all N copies (or to a single source plus a background replicator). This is the standard fix and cheap to implement.
  • Local / near cache. Cache the hot key in each application process with a 1–5 s TTL. This is the most effective fix for true viral keys because it removes the network hop entirely and the Redis cluster sees near-zero traffic for that key.
  • Request coalescing at the edge. A CDN or API gateway caches the response so millions of users are served without ever reaching the cache tier.
  • Dedicated hot-key pool. Detect hot keys dynamically (sampling, or a count-min sketch of request frequency) and promote them to a separate, over-provisioned cache cluster or a different key namespace with more replicas.
  • Read replicas for the shard. If reads dominate (they always do for hot keys), add read replicas of the owning shard and have clients read from replicas round-robin.
  • Shard the key by design. For counters specifically (view counts, likes), shard the counter into N partial counters and sum on read — views:42:0..9 — which converts one hot write into ten distributed writes.
  • Push instead of pull. For things like a global config flag or a banner, push updates to clients via WebSocket/pub-sub so there is no read traffic at all.
Interview framing: the hot key problem is a partitioning problem, not a caching problem. Consistent hashing can't help because the key is indivisible — the only solutions are to replicate the key, cache it closer to the reader, or reduce the number of readers.
Q28. What is negative caching? How does it defend against cache penetration?Core

Negative caching is storing the fact that a lookup returned "not found" — rather than only caching successful results — so that repeated requests for the same missing key are answered from the cache instead of hitting the database.

SENTINEL = "__NULL__"
TTL_NEG = 60   # short TTL

def get_user(uid):
    v = cache.get(f"user:{uid}")
    if v == SENTINEL:
        return None                    # negative hit, no DB call
    if v is not None:
        return v
    v = db.query("SELECT ... WHERE id=?", uid)
    if v is None:
        cache.set(f"user:{uid}", SENTINEL, ttl=TTL_NEG)   # remember the miss
        return None
    cache.set(f"user:{uid}", v, ttl=600)
    return v

def create_user(uid, data):
    db.insert("users", uid, data)
    cache.delete(f"user:{uid}")        # clear the negative entry immediately

How it defends against penetration: penetration attacks work by sending an unbounded stream of requests for keys that don't exist. Without negative caching, every one is a guaranteed database hit, so the cache provides zero protection. With negative caching, each distinct invalid key costs exactly one database lookup and is then absorbed for the negative TTL. An attacker sending 10 million requests across 100,000 random IDs now produces 100,000 database lookups instead of 10 million — a 100× reduction, and one that is further reduced by rate limiting.

The main risk: stale negatives. If you cache "user 123 does not exist" for an hour and then user 123 is created, that user is invisible for an hour. Mitigations:

  • Short TTLs for negative entries (30–120 s) — much shorter than positive TTLs, because negatives are cheap to recompute and expensive to get wrong.
  • Explicit invalidation on create. The create path deletes the negative sentinel, as shown above. This is mandatory, not optional.
  • Separate key namespace or a versioned key so that a create operation can bump a version rather than hunting individual entries.

When not to use it: if "not found" is a normal, high-cardinality outcome (e.g. a search over a huge corpus with arbitrary query strings), negative caching can consume more memory than it saves and should be replaced by a Bloom filter or by simply not caching. Also avoid it for authorization checks where a stale negative could lock out a legitimately granted resource.

Section E — Advanced & Distributed Caching

Q29. Design a distributed cache. What are the key components?Advanced

A distributed cache is a fleet of nodes that collectively present the illusion of one large key-value store, with data partitioned across nodes and replicated for durability of availability.

Key components:

  • Client library / proxy layer. The entry point. It maintains a copy of the cluster topology (the hash ring or slot map), computes which shard owns a key, manages connection pools, pipelines/batches requests, and handles retries and failover. Examples: Redis Cluster client, Twemproxy, Envoy Redis proxy. This layer is where most of the latency and correctness lives.
  • Partitioning scheme. Consistent hashing (or Redis Cluster's 16,384 fixed hash slots) determines key ownership. Fixed slots decouple key ownership from node identity, so moving a shard means moving slot ranges, not remapping the ring.
  • Cache nodes (shard owners). Each node owns a set of keys and serves gets/sets for them. Typically an event-loop or sharded-thread model with in-memory storage and an eviction policy.
  • Replication. Each shard has 1–2 replicas (async by default) for availability. Writes go to the primary; reads may go to replicas if slight staleness is acceptable.
  • Coordination / control plane. Cluster membership, failure detection, and failover. Two designs: a consensus-backed coordinator (Redis Cluster with gossip + a slot map, Sentinel, ZooKeeper/etcd), or a fully decentralized Dynamo-style gossip protocol with consistent hashing and hinted handoff.
  • Failure detection. Heartbeats, gossip, and quorum-based failure declaration to avoid split-brain when a node is merely slow.
  • Eviction and expiry engine. Per-node memory limits with LRU/LFU/random eviction, plus TTL expiry (lazy + sampled background).
  • Observability. Hit ratio, per-node CPU/memory/NIC, p50/p99 latency, evictions/sec, hot-key detection, replication lag, and rebalance progress.
  • Control plane for scaling. Add/remove nodes, migrate slot ranges, throttle migration, and update clients' topology views (via a versioned ring published over pub/sub).

Request flow: client hashes key → looks up slot/shard in its cached topology → sends to the owning node → node returns hit or miss → on miss the app loads from the source of truth and writes back through the same path.

Design decisions to call out: Do you need persistence (RDB/AOF) or is a cache allowed to be empty after restart? Is replication synchronous (safe, slow) or asynchronous (fast, may lose the last few writes — fine for a cache)? Do clients embed the routing logic (Redis Cluster) or go through a proxy (Twemproxy) — the former is faster and more resilient, the latter simplifies heterogeneous clients?

Q30. How do you shard data across multiple cache nodes? Explain consistent hashing and virtual nodes.Advanced

The naive approach: modulo hashing. node = hash(key) % N. Simple and perfectly balanced — but when N changes (a node dies, or you add one), almost every key remaps to a different node, which means the cache is effectively empty and the database receives a full stampede. For a cache this is catastrophic; for a stateful store it means massive data movement.

Consistent hashing fixes this by placing both keys and nodes on a circular hash space (a "ring", e.g. 0 to 2³²−1).

  • Each node is hashed onto the ring at one or more positions.
  • Each key is hashed onto the same ring; it belongs to the first node encountered walking clockwise.
  • Adding or removing a node only remaps the keys in the arc between the new node and its predecessor — approximately K/N keys move instead of nearly all of them.

Why virtual nodes are essential. With one position per physical node, the ring is divided into arcs of random and often wildly unequal size — one node might own 60% of the space and another 2%, and when a node fails its entire arc dumps onto a single successor. Virtual nodes (vnodes) solve this: each physical node is hashed to many positions on the ring (typically 100–1000), each acting as a replica of that node for the keys in its arc.

  • Even distribution. With hundreds of vnodes per node, the law of large numbers produces near-uniform load — variance shrinks proportionally to 1/√V.
  • Graceful failure. When a node dies, its many arcs are inherited by many different successors, spreading the load rather than concentrating it on one node.
  • Weighting for heterogeneous hardware. A node with twice the memory gets twice as many vnodes — trivially supports mixed instance sizes.
  • Faster rebalancing — many small ranges can be migrated in parallel instead of one giant range.

The alternative: rendezvous (highest-random-weight) hashing. For each key, compute a score against every node and pick the highest. No ring, no data structure, perfectly balanced, and adding a node only steals its fair share — O(N) per lookup, which is fine for client libraries with a few hundred nodes. Redis Cluster takes a third approach: hash keys into a fixed 16,384 slots and assign slots to nodes, which keeps the topology map small and explicit.

Q31. How do you ensure high availability and failover in a distributed cache?Advanced

High availability for a cache means "a node loss degrades capacity, not correctness or availability" — and because a cache can always reload from the source of truth, the requirements are looser than for a database. There are two broad architectural approaches.

1. Primary–replica per shard with a coordinator (Redis Sentinel / Redis Cluster).

  • Each shard has one primary and one or more replicas. Writes go to the primary and replicate asynchronously.
  • Sentinel (or the cluster's gossip + quorum logic) monitors the primary with heartbeats. When a quorum of monitors agrees the primary is unreachable, a replica is promoted and clients are redirected.
  • Trade-offs: async replication means the last few writes may be lost on failover — entirely acceptable for a cache (they'll be re-read from the DB) but not for a primary data store. Failover takes seconds (detection + promotion + client topology refresh), during which requests to that shard fail or time out.
  • Quorum requirements prevent split-brain: a minority partition cannot elect a new primary.

2. Peer-to-peer / Dynamo-style with gossip (Cassandra-style).

  • Every node is equal; data is replicated to the N successors on the ring. Any node can coordinate a request, fanning out to the replicas that own the key.
  • Failure detection via gossip; hinted handoff means a coordinator temporarily stores writes intended for a down node and delivers them when it returns; read repair fixes stale replicas on read.
  • Trade-offs: no failover event at all (which is a huge operational win), but more complex, higher tail latency, and tunable consistency (quorum reads/writes) that a cache rarely needs.

Client-side resilience (equally important):

  • Topology-aware clients that refresh the slot map on a MOVED response and cache it with a version number.
  • Timeouts and retries with jitter — retry once on a different replica, then fail open to the database.
  • Circuit breakers so a slow cache doesn't tie up application threads — the biggest cache-outage risk is thread-pool exhaustion in the app, not the cache itself.
  • Local L1 cache so that a total cache-tier failure still leaves a partial hit ratio and a survivable database load.
  • Multi-AZ / multi-region placement with replicas in a different availability zone from the primary.
The key design stance: a cache should be allowed to fail open — the system should degrade to database-backed slowness, not to an outage. That means bounding connections to the database, shedding load, and having a documented degraded mode for every cached endpoint.
Q32. How does a cache cluster rebalance when a node is added or removed?Advanced

Rebalancing is moving key ownership from over-loaded nodes to under-loaded ones — triggered by adding capacity, losing a node, or detecting a hot shard.

The process:

  1. Compute the new ownership map. With consistent hashing, the new node takes over a set of vnode ranges; existing nodes only give up the arcs that now belong to it (~1/N of total keys). With Redis Cluster's slot model, a specified subset of the 16,384 slots is migrated.
  2. Publish the new topology to all clients (a versioned ring over pub/sub, or the cluster's gossip-propagated config epoch). Clients must learn the new map or they will route to the wrong node.
  3. Migrate data. Two strategies:
    • Active migration — copy keys from the old owner to the new one in batches (MIGRATE in Redis Cluster), with the source continuing to serve reads for those keys until the move is confirmed.
    • Lazy / on-demand migration — the new owner accepts ownership immediately; on a miss it fetches from the source of truth. Far simpler and cheaper, and usually the right choice for a pure cache: the "migration" is just a temporary dip in hit ratio. This is a key advantage of caches over databases.
  4. Handle in-flight requests. During the move, requests to a key may land on the old owner. The old owner either serves it and forwards a copy, or replies with a redirect (MOVED/ASK) so the client retries on the new owner.
  5. Throttle and observe. Migration competes with serving traffic for CPU, NIC, and memory. Rate-limit the batch size, run it during low traffic, monitor migration lag and p99 latency, and be prepared to pause.

Handling node removal: the difference from a clean scale-up is urgency. If a node fails, its keys are gone (for a cache, that's just a hit-ratio dip) and its replica takes over; the data is reloaded lazily. If you're decommissioning a healthy node, migrate its keys first so there is no dip at all.

Pitfalls: rebalancing without replication can create a window where a shard has no copy; rebalancing during peak traffic causes latency spikes that look like cache failures; and stale client topology maps cause repeated redirects (detectable via MOVED rates). Monitor the ring version each client is using.

Q33. How do you handle data consistency across multiple cache nodes during updates and deletes?Advanced

The honest starting point: a cache should be eventually consistent by design, and the engineering job is to make the convergence window measurable and bounded rather than to chase strong consistency, which would cost far more than the cache saves.

Why inconsistency arises across nodes:

  • Replication lag — a write lands on the primary of shard 5; a read hits its replica 20 ms later and repopulates the cache with the old value.
  • Multiple copies of a key — if you replicate hot keys (post:42:0..9) or use a near cache, an update must reach every copy.
  • Derived keys — a single DB change may invalidate five different cache keys owned by different shards; the deletes are not atomic.
  • Concurrent writers — two writers to the same key whose cache writes arrive out of order.

Techniques, from cheapest to strongest:

  • Single ownership per key. Assign exactly one owner per key (the shard it hashes to) and route all writes through that owner. This eliminates the multi-writer problem entirely and is the reason consistent hashing is so valuable.
  • Version numbers / CAS. Store (version, value) and only accept a cache write whose version exceeds the stored one. This makes stale repopulation structurally impossible regardless of message ordering, at the cost of 8 extra bytes per entry.
  • Write-through for critical keys. If correctness matters for a key, write to the cache and the DB in one operation instead of invalidating — no window at all.
  • Pub/sub invalidation for replicated copies. A DEL broadcast to all nodes holding a copy, with TTL as the fallback when a message is lost.
  • Read repair. On read, if a replica's version is behind, update it before returning. Turns a read into a convergence opportunity (Dynamo-style).
  • Quorum reads/writes. Require R + W > N. Gives true consistency but adds latency and availability loss — rarely justified for a cache.
  • TTL as the universal backstop. No matter how many invalidation paths break, every key converges within its TTL. This is the answer to "what if everything fails?"

How to reason about it in the interview: split your data by consistency requirement. Prices and inventory: write-through + version + short TTL. Product descriptions: cache-aside + CDC invalidation + 5-minute TTL. View counts: write-behind, loss-tolerant. Then state that the worst-case divergence for each class is bounded and measured, not hoped for.

Q34. What is the impact of cache size and object churn on garbage collection, and how do you tune for it?Advanced

In managed runtimes (JVM, Go, .NET, Python), an in-process cache is a large population of long-lived objects living in the heap. This has three adverse effects on the runtime's garbage collector, all of which surface as latency problems rather than throughput problems.

1. Long GC pauses. A multi-gigabyte cache occupies old-generation space and forces longer marking and compaction cycles. A 10 ms pause is fine; a 400 ms stop-the-world pause at 5,000 QPS blows through client timeouts, which triggers retries, which adds load — a small GC problem becomes a cascade.

2. Object churn and allocation pressure. Every cache write allocates a new object; every eviction makes it garbage. High churn promotes short-lived objects into the old generation (premature promotion), so the cache both fills the old gen with garbage and holds real entries there. Frequent full GCs follow.

3. Heap sizing conflicts. The cache competes with request-handling allocations for heap. Sizing the heap for the cache leaves no headroom for traffic spikes; sizing it for traffic leaves the cache evicting constantly. On a 32 GB JVM you must also account for compressed-oops limits and region sizes.

Tuning strategies:

  • Move the cache off-heap. Store serialized values in direct ByteBuffers or native memory (Caffeine's off-heap variant, OHC, MapDB, or a native cache like RocksDB/LMDB). The GC never sees them. Costs: explicit serialization/deserialization and manual memory management.
  • Shard into many small processes. Ten JVMs with 2 GB heaps each have far shorter pauses than one with 20 GB. Smaller heaps are the single most effective pause reduction.
  • Choose a modern collector. G1 with a target pause time (e.g. MaxGCPauseMillis=50) is the floor; ZGC or Shenandoah give sub-millisecond pauses and are the right answer for large heaps holding caches.
  • Reduce per-entry overhead. Compact keys (IDs, hashes), avoid nested object graphs in cached values, use primitive collections, and consider serialized blobs rather than object trees. Metadata overhead per entry (hash map node, list pointers, headers) can easily exceed the payload.
  • Bound and size deliberately. Use maximumSize/maximumWeight with a weigher rather than an unbounded map, and leave 30–50% heap headroom for request handling.
  • Prefer a distributed cache for large working sets. If the working set is 50 GB, it does not belong in a JVM heap — put it in Redis and keep only the top few percent locally.
  • Watch fragmentation and promotion rate. Monitor GC frequency, promotion rate, and pause histograms, not just average latency — the tail is where cache-induced GC damage shows up.
The design-level takeaway: a local cache is a heap-lifetime trade-off. If you cannot bound it, isolate it (off-heap), shard it (small heaps), or move it out of process entirely.
Q35. How would you choose a session store for a globally distributed web application?Advanced

Session state is the canonical caching use case, because it is small, read on every request, changes rarely, and must be available on any instance. The options, with their real trade-offs:

Sticky sessions (LB affinity)Zero infrastructure, in-memory speedBreaks autoscaling and failover; a node loss logs out everyone on it; uneven load; incompatible with rolling deploys

For a globally distributed app, the design usually looks like this:

  1. Store a session ID (or short-lived signed token) in an HttpOnly, Secure, SameSite cookie. Never put sensitive session data in a cookie the client can read.
  2. Keep the session payload in Redis with a sliding TTL (e.g. 30 minutes idle, 12-hour absolute max). Sliding expiry means active users stay logged in without unbounded growth.
  3. Pin sessions to a region for latency — write to the user's home region and replicate asynchronously to other regions, so a cross-region request reads a locally available (possibly slightly stale) copy. Session data tolerates seconds of staleness far better than a cross-region round trip.
  4. Handle the active-active conflict. Two concurrent requests in different regions can both update the session. Either accept last-write-wins with a version field, or route all writes for a session to its home region (session affinity by region rather than by server, which is compatible with autoscaling).
  5. Design for store failure. If Redis is unavailable, decide explicitly: fail closed (log everyone out — terrible UX, no security risk) or fail open (accept a signed token — better UX, weaker revocation). Most consumer apps use short-lived signed tokens precisely so a cache outage doesn't log out the world.
  6. Security: encrypt at rest, rotate signing keys, bind the session to a user-agent/IP fingerprint only loosely (IP changes on mobile networks), invalidate all sessions on password change, and rate-limit login.

The interview answer to lead with: "Prefer a stateless, signed token for the hot path and a Redis-backed revocation/refresh store for the things that must be revocable. That gives edge verification at sub-millisecond latency and a bounded, explicit revocation window — and it fails gracefully when the cache is down."

Q36. Design a caching layer for an e-commerce service (GET /catalog and GET /product/{id}).Advanced

  • Cache only the first 3–5 pages of each popular filter combination — deep pages have tiny traffic and are better served live.
  • Normalize the cache key: sort query parameters alphabetically, drop analytics/tracking params, round prices to buckets, and cap the number of combinations admitted (an LRU over the key space).
  • Alternative: cache the ID list only (catalog:cat=shoes:brand=nike:page=1 → a list of 48 product IDs), then MGET the product objects from the per-product cache. This reuses product-detail cache entries across every listing and keeps the cached payload small.

5. Flash sale handling. This is where interviewers dig in. Pre-warm the relevant SKUs and listing pages before the sale starts; replicate the hot product keys across N shards with a random suffix to defeat the hot-key problem; put the CDN in front of the listing endpoints; move inventory to an atomic Redis counter with a Lua script for the decrement (never a read-modify-write across two round trips); and rate-limit per user at the gateway. Queue the order writes so the database sees a smoothed stream rather than a spike.

6. Failure behaviour. If Redis is down, the app fails open to the database with a bounded connection pool and a circuit breaker that sheds catalogue traffic while always admitting checkout traffic. Local L1 caches keep a meaningful hit ratio. Degraded mode returns a static "popular products" fallback for listing pages rather than errors.

7. Observability. Hit ratio per key prefix, p99 cache latency, evictions/sec, stale-serve ratio, invalidation lag, and a per-endpoint dashboard for the flash-sale path.

Q37. Design a distributed in-memory cache (like Redis) for 10M RPS, 10 TB data, sub-millisecond latency.Advanced

1. Back-of-the-envelope sizing. 10 TB at ~64 GB usable per node gives ~160 nodes for the primary copy. With replication factor 2, ~320 nodes. 10M RPS spread over 160 primaries is ~62,500 RPS per node — above a single-threaded Redis's comfortable range (~100k+ for simple GETs, but with network overhead this is tight), so plan for ~300–500 primary shards to leave headroom, or use multi-threaded shards. Sub-millisecond latency rules out anything involving disk.

2. Data model and protocol. Keys and values are opaque byte strings; values are capped (e.g. 1 MB) to bound worst-case latency and prevent a single giant value from blocking a shard. Protocol is a compact binary or RESP with pipelining, since round-trip count dominates at these rates.

3. Partitioning. Consistent hashing with virtual nodes, or a fixed slot map (16,384 slots, as Redis Cluster does) assigned to nodes. Fixed slots make migration a slot-range operation and keep the client topology map tiny. A client-side proxy or a topology-aware client computes ownership locally — no central router on the hot path, because that would be both a latency tax and a SPOF.

4. Node internals for sub-millisecond. Shard each node into several threads, each owning a disjoint key range and a hash table (no global locks, no cross-thread contention). Or use a single-threaded event loop per node with many small nodes, accepting a linear memory cost per process. Avoid O(N) commands on large collections entirely. Memory allocation via jemalloc/slab to avoid fragmentation; store keys inline where possible.

5. Availability. Async replication per shard (RF=2 or 3) with automatic failover driven by gossip + quorum. A write lost in failover is acceptable for a cache — it will be re-read from the source of truth. Hinted handoff or lazy reload covers the gap. Nodes spread across AZs.

6. Eviction and expiry. Per-node memory cap with approximated LRU (sample K random keys, evict the least recently used) or TinyLFU for a better hit ratio; lazy TTL expiry plus a sampled background sweep. Monitor eviction rate as the primary capacity signal.

7. Scaling and rebalancing. Adding a node triggers slot migration with throttled batch moves; the topology version is published to clients over pub/sub. For a pure cache, prefer lazy migration (route to the new owner, reload on miss) over copying 10 TB of data.

8. Hot keys. Detect via sampled key-frequency tracking; mitigate with key replication, a client-side near cache, and per-key request coalescing.

9. Failure and degradation. Circuit breakers in clients; fail open to the source of truth with a bounded connection pool; local L1 caches to preserve a partial hit ratio; load shedding at the gateway. The design must specify what happens when the cache tier is gone, because at 300+ nodes it will happen regularly.

10. Observability. Per-shard CPU/NIC/memory, hit ratio, p50/p99/p999, evictions, replication lag, hot keys, migration progress, and client-side timeout/error rates.

Q38. Design the caching strategy for a social media newsfeed (celebrity with 50M followers).Advanced

1. The core tension: fan-out on write vs fan-out on read.

  • Fan-out on write (push): when a user posts, write the post ID into every follower's cached feed list. Reads are then a single O(1) lookup of the pre-built list. Fast reads, but a user with 50M followers generates 50M writes per post — impossible.
  • Fan-out on read (pull): store the post once; at read time, merge the posts of everyone the reader follows. Cheap writes, expensive reads (merge N sources), and catastrophic for a user following 2,000 people.
  • Hybrid (the correct answer): fan-out on write for normal users; fan-out on read for celebrities. When a reader's feed is assembled, merge their pre-built push feed with a pull of recent posts from the small set of high-follower accounts they follow.

2. Data model in the cache.

  • feed:{user_id} — a Redis sorted set or capped list of post IDs, newest first, trimmed to ~800 entries. Memory is small because it stores IDs only.
  • post:{post_id} — the post content, cached separately and shared by all readers. This is where the hot key lives.
  • user:{id} — author profile, cached on the same hot path.
  • followees:celebrities:{user_id} — the small cached list of celebrity IDs the reader follows, so the read path knows what to pull.

3. Read path. Fetch the reader's push feed (top ~200 IDs) plus recent posts from followed celebrities, merge by timestamp, take the top N IDs, then MGET the post contents from post:{id}, hydrate author data, and return. This is 3–4 cache round trips (pipelined into 1–2) and no database access on the happy path.

4. The celebrity post is the hot key. A single post by a 50M-follower account is requested millions of times in the first minute. Mitigations: replicate the key (post:{id}:{0..19}, read a random suffix); put the content in a local L1 cache in every app instance with a 30–60 s TTL; serve it from the CDN if the feed is rendered server-side; and use request coalescing at the edge so a single origin fetch serves the whole PoP.

5. Write path. A normal user's post: write to the DB, then push the post ID into the followers' feed lists asynchronously via a queue (fan-out workers, batched in chunks of a few hundred). The author's own feed is updated synchronously so they see their post immediately. A celebrity's post: write once, and only update the author's own feed — everyone else pulls it.

6. Invalidation and deletion. Post content is write-through and cached with a long TTL (immutable in practice). Deletion needs a tombstone that is checked on read, plus an async purge of post:{id} and any CDN entries. Feed lists are rebuilt from the follow graph rather than invalidated item by item.

7. Consistency and failure. Feeds are eventually consistent by nature — a few seconds of delay before a post appears is expected product behaviour, which is exactly what makes caching here cheap. If the feed cache is unavailable, fall back to a database query for the top 20 posts with a hard timeout, and return a stale cached feed rather than an error.

8. Metrics. Feed cache hit ratio, fan-out queue depth and lag, hot-key detection on post:{id}, feed assembly p99, and per-celebrity read amplification.

1. Requirements. Enforce N requests per window per key (user, IP, API key, endpoint), across hundreds of stateless app instances, at sub-millisecond overhead, with a graceful failure mode. The shared counter must be atomic, which is why Redis is the standard choice.

2. Algorithms and their trade-offs.

-- Fixed window, atomic
local c = redis.call('INCR', KEYS[1])
if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
if c > tonumber(ARGV[2]) then return 0 else return 1 end

4. Distribution and hot keys. Shard by rate-limit key (user:{id}) so all requests for one user hit one shard and the counter stays authoritative. A global limit (e.g. per-tenant across all endpoints) is the hot-key risk: use a sharded counter (N partial counters summed on read) with an acceptable approximation, or batch local pre-aggregation — each instance counts locally for 100 ms and flushes a delta, trading a small over-admission for a huge reduction in Redis traffic.

5. Local pre-check. Keep a per-instance local counter to reject obviously-over-limit requests without a network hop; only requests that pass locally consult Redis. This cuts Redis RPS by 10–100× in practice.

6. Failure mode — decide explicitly. If Redis is unreachable, do you fail open (admit all requests — protects availability, risks abuse) or fail closed (reject — protects the backend, risks a total outage)? Standard practice: fail open for general API limits, fail closed for security-critical limits (login attempts, password reset). Fall back to a local in-memory limiter as a degraded mode so some protection remains.

7. Response contract. Return HTTP 429 with Retry-After and X-RateLimit-Limit/Remaining/Reset headers so well-behaved clients back off instead of retrying immediately and making things worse.

8. Eviction. Rate-limit keys must not be evicted under memory pressure or limits silently reset — use a separate Redis instance or database with volatile-ttl eviction and per-key TTLs that are always set.

Q40. How would you design the caching strategy for a URL shortener?Advanced

1. Workload. Overwhelmingly read-heavy (redirects outnumber creations by 1000:1 or more), extremely latency-sensitive (a redirect that takes 200 ms is a bad user experience), and the mapping is immutable — this last property is what makes the caching design unusually easy.

2. Redirect path (short code → long URL).

  • Key: url:{short_code} → the destination URL plus metadata (expiry, owner, flags).
  • Pattern: cache-aside with a long TTL. Because short codes never change their target after creation, there is essentially nothing to invalidate — the only writes are create and delete. This is a rare case where "cache forever" is genuinely correct, with a TTL (e.g. 24 hours) purely as a memory-management mechanism.
  • Layers: CDN edge cache for 301s (permanent, aggressively cacheable) — but note that 301s are cached by browsers and are hard to undo, so many services deliberately return 302 to retain control. Then a local L1 cache for the top few thousand codes (redirects have an extreme power-law distribution), then Redis, then the database.
  • Negative caching: unknown short codes are a prime penetration vector (people probe random codes). Cache "not found" with a 60 s TTL to absorb the scan, plus rate limiting at the edge.

3. Write path (create).

  • Generate a unique code — a counter-based scheme (distributed ID generator, then base62) or a random string with a uniqueness check via SETNX.
  • Write to the database (the source of truth), then write-through to the cache so the creator's own first redirect is a hit. Write-through is safe here because there is no invalidation race — the value never changes.
  • Delete the negative-cache sentinel for that code, if one exists.

4. Deletion / expiry of links. This is the only invalidation case. Mark the row deleted, then delete the cache key and purge the CDN entry. Because the CDN may hold a 301, use a short edge TTL (or 302s) for links that can expire, so revocation actually takes effect.

5. Hot links. A link shared in a mass email or on a billboard can receive millions of hits. Replicate the hot key across shards, serve from the local L1 cache, and ensure the CDN absorbs the bulk of it — the redirect is a 30-byte response, so edge caching is nearly free and extremely effective.

6. Numbers that matter. A 99% cache hit ratio at 100k RPS means 1,000 database reads per second — trivially handled. The database becomes almost read-free, so the design is dominated by cache memory sizing (how many codes fit, and what the hot-set distribution looks like) rather than by database scaling.

7. What makes this a good interview answer: recognizing that immutability collapses the hardest part of caching (invalidation) to almost nothing, and then spending the saved complexity on the read path — multi-layer caching, negative caching, and hot-link replication.

Q41. Design a Top-K / leaderboard system using a cache.Advanced

1. Requirements. Rank N players by score, support score updates at high write rates (millions per second during a game event), and return the top K (K typically 10–100) plus an individual player's rank — all in single-digit milliseconds.

2. The core data structure: a Redis Sorted Set. This is the canonical answer because every required operation is O(log N):

  • ZINCRBY leaderboard:global 10 player:42 — atomic score update.
  • ZREVRANGE leaderboard:global 0 9 WITHSCORES — top 10, already sorted.
  • ZREVRANK leaderboard:global player:42 — a player's rank in O(log N).
  • ZSCORE — a player's current score, useful for showing the gap to the next rank.

At 1M members, the sorted set costs roughly 100–150 bytes per member (~150 MB) and each operation touches ~20 nodes in the skip list — microseconds.

3. Time-windowed leaderboards. Store a separate sorted set per period — lb:daily:2024-05-01, lb:weekly:2024-W18, lb:alltime — and compute aggregate boards with ZUNIONSTORE into a temporary key (with a short TTL so it doesn't leak memory). Daily boards expire after a few days; all-time is kept indefinitely. Alternative: keep one set per period and only ever read the current period, letting old sets expire naturally.

4. When the leaderboard is too large for one sorted set. At 100M+ members, a single key becomes a hot key and a memory problem. Then:

  • Shard by hash into 16–64 sorted sets, compute the top K per shard (ZREVRANGE 0 K-1), and merge the small results in the application to get the global top K. This is exact and cheap because you only merge K × shards elements.
  • Approximate heavy hitters — a count-min sketch or Space-Saving algorithm gives an approximate top-K with fixed memory, which is often acceptable for "trending" features.
  • Two tiers — an exact board for the top 1,000 (maintained by promoting from shards) and approximate ranks for everyone else, since only the top ranks are ever displayed.

5. Hot-key and read-scaling mitigation. The leaderboard is read constantly (every app load), so: cache the rendered top-K in a plain string key with a 1–5 s TTL (converting thousands of ZREVRANGE calls into one); serve it from a local L1 cache in each app instance; and put the CDN in front if it's publicly displayed. Rank lookups for individual players should be batched per request.

6. Durability. A Redis sorted set is a cache unless you enable persistence. For a real leaderboard, either enable AOF/RDB (making Redis the primary store) or rebuild the board from an event stream in Kafka on restart — the latter is more robust and also gives you an auditable history.

7. Anti-cheat / correctness. Use ZINCRBY rather than read-modify-write (ZSCORE then ZADD) — the latter races under concurrent updates and silently loses points. If a score is absolute rather than incremental, use ZADD with GT/LT flags to prevent a lower value from overwriting a higher one.

The 8-Step Caching Answer Framework

For any open-ended caching question in an interview, walk these eight steps in order. It demonstrates senior-level structure and ensures you cover correctness and failure, not just the happy path.

  1. Name the source of truth. Which database or service owns this data, and how expensive is a miss?
  2. Define the cache key and scope. Per-user, per-tenant, global, or per-process? What exactly is in the key, and what is deliberately excluded?
  3. Describe the workload. Read/write ratio, request rate, object size, working-set size, and access skew. This drives every later decision.
  4. Set the freshness contract. State the staleness budget in seconds, and whether read-your-writes is required for the writer only or for everyone.
  5. Choose the loading and write path. Cache-aside, read-through, write-through, write-behind, or write-around — and justify it against the workload from step 3.
  6. Separate expiration from eviction. Give a TTL with jitter (correctness backstop) and an eviction policy (memory safety), and explain why each was chosen.
  7. Protect against misses and failures. Name your defences: single-flight for stampedes, negative caching or Bloom filters for penetration, TTL jitter and multi-tier caching for avalanches, key replication or a near cache for hot keys, and fail-open behaviour for cache outages.
  8. Explain failure behaviour and measurement. What happens when the cache is gone, what the system degrades to, and which metrics (hit ratio, p99, evictions, invalidation lag) tell you it's working.

Closing line that lands well: "The cache is a correctness trade-off, not just a performance feature — so I've bounded the staleness explicitly and made the system degrade to slow-but-correct rather than fast-but-wrong."
