4.Q1: What is an AMI and what does it contain?

Q: What is an AMI and what does it contain?

Answer: An Amazon Machine Image (AMI) is a comprehensive, pre-configured template that contains the necessary information to launch an EC2 instance. It serves as the blueprint for your virtual servers in the AWS cloud.

4.Q2: AMI vs EBS Snapshot

Q: What is the difference between an AMI and an EBS Snapshot?

Answer: An AMI and an EBS Snapshot are related but serve fundamentally different purposes. While both are used to create EC2 resources, they operate at different levels of abstraction.

AspectAMIEBS Snapshot
DefinitionA complete template for launching EC2 instancesA point-in-time backup of a single EBS volume
ScopeEntire instance configuration (OS, apps, multiple volumes)Single EBS volume
ContainsRoot volume template, launch permissions, block device mappingOnly the data on one specific volume
Can Launch Instance?✅ Yes, directly❌ No, must be restored to a volume first
Multiple Volumes?✅ Yes, can include multiple EBS volumes❌ No, only one volume
ArchitectureIncludes OS, applications, and settingsRaw block-level data only
CostStorage costs for underlying snapshotsStorage costs for snapshot data
Use CaseServer deployment, scaling, golden imagesBackup, disaster recovery, data migration

💡 Key Takeaways:
  • An AMI is a higher-level construct that includes multiple snapshots and metadata about how to launch an instance.
  • An EBS Snapshot is a lower-level backup of a single volume's data.
  • An AMI contains one or more EBS snapshots as part of its block device mapping.
  • You cannot launch an instance directly from an EBS snapshot.

4.Q3: Sharing an AMI

Q: How can you share an AMI with another AWS account?

Answer: You can share an AMI with another AWS account by modifying its launch permissions to grant the target account permission to launch instances from it. The AMI remains in your account, and you retain ownership.

Method 1: Using the AWS Management Console
  1. Navigate to EC2 → AMIs → Owned by me tab
  2. Select your AMI
  3. Click Actions → Edit AMI permissions
  4. Enter the target AWS account ID (12-digit number)
  5. IMPORTANT: Check "Add 'Create volume' permission to associated snapshots"
  6. Click Save

Method 2: Using the AWS CLI
# Share AMI with a specific account aws ec2 modify-image-attribute \ --image-id ami-1234567890abcdef0 \ --launch-permission "{\"Add\":[{\"UserId\":\"123456789012\"}]}" # Share AMI with snapshot permissions aws ec2 modify-image-attribute \ --image-id ami-1234567890abcdef0 \ --launch-permission "{\"Add\":[{\"UserId\":\"123456789012\",\"SnapshotPermission\":\"CreateVolume\"}]}"

⚠️ Critical Requirement: Snapshot Permissions
Without snapshot permissions, the destination account will receive:
"You do not have permission to access the storage of this AMI"
Always select "Add 'Create volume' permission to associated snapshots" when sharing AMIs.

Important Considerations:
ConsiderationDetail
OwnershipThe AMI remains in the source account
CostNo additional storage costs for the source account
RevocationPermissions can be revoked at any time
LimitsMaximum of 1,000 AMI launches per account, per Region
Public AMIsCan be shared with all accounts, but cannot contain encrypted volumes or product codes

4.Q4: Deregistering an AMI

Q: What happens to the underlying EBS volumes when you deregister an AMI?

Answer: When you deregister an AMI, the underlying EBS snapshots are NOT automatically deleted unless you explicitly choose to delete them using the --delete-associated-snapshots flag (introduced in 2025). The snapshots remain in your account and continue to incur storage costs until you manually delete them.

DEREGISTRATION - WHAT REMAINS ┌─────────────────────────────────────────────────────────────────────────────────────┐ │ DEREGISTRATION - WHAT REMAINS │ ├─────────────────────────────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────────────────────────────────┐ │ │ │ BEFORE DEREGISTRATION │ │ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ │ │ AMI: ami-12345678 (Active) │ │ │ │ │ │ └─ Snapshot A (Root) ├── Incurring storage costs │ │ │ │ │ │ └─ Snapshot B (Data) ├── Incurring storage costs │ │ │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────────────────────────┐ │ │ │ AFTER DEREGISTRATION │ │ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ │ │ AMI: ami-12345678 (Deregistered) │ │ │ │ │ │ └─ ❌ No longer in "Owned by me" list │ │ │ │ │ │ └─ ❌ Cannot launch new instances │ │ │ │ │ │ │ │ │ │ │ │ Snapshots: ✅ STILL EXIST (unless deleted) │ │ │ │ │ │ └─ Snapshot A (Root) ├── Still incurring storage costs │ │ │ │ │ │ └─ Snapshot B (Data) ├── Still incurring storage costs │ │ │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────────────────────┘

Option 1: Deregister Without Deleting Snapshots (Default)
aws ec2 deregister-image --image-id ami-1234567890abcdef0

Option 2: Deregister and Delete Snapshots (New Feature - 2025)
aws ec2 deregister-image \ --image-id ami-1234567890abcdef0 \ --delete-associated-snapshots

⚠️ Important Note: If a snapshot is associated with multiple AMIs, it will not be deleted even if you specify --delete-associated-snapshots. The AMI will still be deregistered, but the snapshot remains.

📌 AWS Backup Consideration: AMIs managed by AWS Backup cannot be deregistered through the EC2 console or CLI. You must manage them through AWS Backup by deleting the recovery point, which automatically removes both the AMI and its associated snapshots.

4.Q5: Copying AMIs to Another Region

Q: Why would you copy an AMI to another region?

Answer: Copying an AMI to another AWS Region is essential for global deployment, disaster recovery, compliance, and latency optimization. Since AMIs are regional resources, copying is the only way to use your custom AMI in a different Region.

4.Q6: Golden AMI

Q: What is a "Golden AMI" and why is it important?

Answer: A Golden AMI (also called a "golden image") is a hardened, pre-configured, and thoroughly tested AMI that serves as the single source of truth for your infrastructure. It contains the exact configuration of operating system, security settings, applications, and agents required for your production environment.

What Makes an AMI "Golden"?
✅ Hardened OS
Security patches applied
✅ Pre-installed Apps
Apache, Nginx, Node.js, etc.
✅ Monitoring Agents
CloudWatch, Datadog
✅ Logging Config
CloudWatch Logs, ELK
✅ Firewall Rules
Security groups configured
✅ Regular Updates
Latest patches

Why Golden AMIs Are Critical:
📋 Consistency
Every instance starts with the exact same configuration
⚡ Speed
Instances ready immediately — no manual setup
🔒 Security
Hardening baked into the image; regular updates
📈 Scale
Auto Scaling Groups launch fully functional instances quickly
🔧 Reliability
Changes tested once, not on every instance
✅ Compliance
Standardized images simplify audits

💡 Best Practices:
  • 📌 Version Control: Use version numbers (v1.0, v2.0, etc.) in naming
  • 🤖 Automated Builds: Use EC2 Image Builder or Packer
  • 🔄 Regular Updates: Schedule builds for latest security patches
  • 🧪 Testing: Validate AMIs before deploying to production
  • 🧹 Cleanup: Deregister old AMIs and delete snapshots
  • 📝 Documentation: Document contents and purpose
  • 🏷️ Tagging: Use tags for purpose, version, build date
