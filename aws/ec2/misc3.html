10.3 Security Groups (SGs)

📖 Complete Theory: The Virtual Firewall

An AWS Security Group (SG) acts as a virtual, stateful firewall for your EC2 instances, controlling both inbound (ingress) and outbound (egress) traffic at the instance level. It is a foundational component of network security on AWS, operating on an allow-list basis: all traffic is implicitly denied unless explicitly permitted by a rule.
🛡️ Security Groups 🔥 stateful firewall 🔒 allow-list
🔑

10.3.1 Core Concepts

🔑 Stateful Nature
Security Groups are stateful. If you allow an inbound request, the corresponding outbound response is automatically allowed, regardless of outbound rules. This simplifies rule management by eliminating the need for symmetric inbound/outbound rules.

💡 Analogy: Think of a security group like a bouncer at a club. When you show your ID and are allowed in, the bouncer remembers you and lets you leave without showing your ID again.

📋 Default Rules:
  • ❌ Denies all inbound traffic
  • ✅ Allows all outbound traffic

🔗 Connection Tracking:
Security groups track the state of connections to determine if traffic should be allowed based on existing connections. For TCP/UDP flows with open rules (0.0.0.0/0 in both directions for any port), traffic is not tracked to optimize performance. In such cases, changing a rule will immediately interrupt existing connections.

10.3.2 Working with Security Groups

Creating a Security Group (CLI)
aws ec2 create-security-group \ --group-name my-sg \ --description "My security group" \ --vpc-id vpc-1a2b3c4d # Output: { "GroupId": "sg-903004f8" }

Adding Inbound Rules (CLI)
# SSH (Linux) aws ec2 authorize-security-group-ingress \ --group-id sg-903004f8 \ --protocol tcp \ --port 22 \ --cidr 203.0.113.0/24 # HTTP (Web) aws ec2 authorize-security-group-ingress \ --group-id sg-903004f8 \ --protocol tcp \ --port 80 \ --cidr 0.0.0.0/0 # RDP (Windows) aws ec2 authorize-security-group-ingress \ --group-id sg-903004f8 \ --protocol tcp \ --port 3389 \ --cidr 203.0.113.0/24

💡 Note: Security group rules can be referenced by IP address or by other security groups.

Deleting a Security Group (CLI)
aws ec2 delete-security-group --group-id sg-903004f8
⚠️ Note: You cannot delete a security group that is currently attached to an instance.

10.3.1 Review Questions

Q1: What is a Security Group in AWS?
A Security Group is a virtual, stateful firewall that controls inbound and outbound traffic for EC2 instances at the instance level. It operates on an allow-list basis, where all traffic is denied unless explicitly permitted by a rule.
Q2: What does it mean that Security Groups are "stateful"?
Being stateful means that if you allow an inbound request, the corresponding outbound response traffic is automatically allowed, regardless of your outbound rules. This simplifies configuration by eliminating the need to create symmetric inbound/outbound rules.
Q3: What are the default rules for a new Security Group?
A newly created Security Group denies all inbound traffic and allows all outbound traffic. The default VPC's security group, however, allows instances in the same group to communicate with each other.
Q4: What is the difference between a Security Group and a Network ACL?
A Security Group operates at the instance level and is stateful, allowing only "allow" rules. A Network ACL operates at the subnet level and is stateless, supporting both "allow" and "deny" rules, which are evaluated in order.
Q5: Why is it a bad practice to allow SSH traffic from 0.0.0.0/0?
Allowing SSH (port 22) from 0.0.0.0/0 means any computer on the internet can attempt to connect to your instance, significantly increasing the attack surface. It should be restricted to specific trusted IP addresses (e.g., your office IP range) to implement the principle of least privilege.

10.3.2 Inbound and Outbound Rules

📖 Complete Theory: Defining Traffic Flow

Security group rules are the individual permissions that control traffic to and from your EC2 instances. Inbound (ingress) rules control traffic coming into your instances, while outbound (egress) rules control traffic leaving your instances.

Each rule specifies a protocol, a port range, and a source (for inbound) or destination (for outbound).

10.3.2 Review Questions

Q1: What is the difference between inbound and outbound security group rules?
Inbound rules control traffic coming into your EC2 instance, while outbound rules control traffic leaving your instance. For example, an inbound rule might allow SSH (port 22) from your IP, while an outbound rule might allow HTTPS (port 443) to the internet.
Q2: Why does a security group not require an explicit outbound rule for responses to inbound traffic?
Security groups are stateful. When you allow an inbound request, the corresponding response traffic is automatically allowed to leave the instance, regardless of outbound rules. This eliminates the need for symmetric inbound/outbound rules.
Q3: What is the recommended source for SSH (port 22) rules?
You should restrict SSH to specific IP addresses or ranges (e.g., your corporate office IP range) rather than using 0.0.0.0/0 (anywhere). This implements the principle of least privilege.
Q4: How do you grant a web server access to a database server without using IP addresses?
You can reference the web server's security group in the database's inbound rule. For example, in the database security group, add an inbound rule with source = sg-web (the web server's security group). This allows traffic from any instance in that SG, without maintaining IP address lists.
Q5: What happens when a security group rule references another security group?
The rule allows traffic based on the referenced security group. No rules are added from the referenced SG; instead, the rule acts as a dynamic authorization that applies to the private IP addresses of instances associated with the referenced security group. This enables simplified management as instances scale.

10.3.3 Security Group References

📖 Complete Theory: Dynamic, Logical Firewall Rules

One of the most powerful features of AWS Security Groups is the ability to reference another security group as a source (for inbound rules) or destination (for outbound rules). Instead of using static IP addresses or CIDR blocks, you can say: "Allow traffic from any resource that has this specific security group attached."

10.3.3 Review Questions

Q1: What is a security group reference and when would you use it?
A security group reference is a rule where the source or destination is another security group ID instead of an IP address or CIDR block. You use it to allow traffic based on logical grouping (e.g., "allow any instance with the sg-app security group to access the database") rather than maintaining lists of IP addresses.
Q2: Can you reference a security group from a VPC that is in a different region?
No. Security group references across VPC peering connections only work when both VPCs are in the same region. For cross-region scenarios, you must use CIDR blocks instead.
Q3: How do you reference a security group from a different AWS account?
Include the account ID with the security group ID, separated by a forward slash: 123456789012/sg-1a2b3c4d. This works for VPCs in the same region with an active VPC peering connection.
Q4: Can a security group reference itself? Why would you do this?
Yes, a security group can reference itself. This is commonly used for intra-group communication in distributed systems (e.g., HPC clusters, Kubernetes) where all instances in the group need to communicate with each other. It also enables EFA communication and cluster diagnostics.
Q5: What is a stale security group reference and how do you find it?
A stale security group reference is a rule that references a security group that has been deleted, or references a security group in a peer VPC whose VPC peering connection has been deleted. You can find them using the describe-security-group-references AWS CLI command, which shows which VPCs are referencing your security groups.

Best Practices

Principle of Least Privilege: Only allow the minimum required traffic
Restrict SSH/RDP: Never use 0.0.0.0/0 for administrative protocols
Reference Security Groups: Use SG references instead of IPs for multi-tier architecture
Create Tier-Specific Groups: Web, App, and DB tiers should have dedicated security groups
Regular Audits: Review and remove unused or overly permissive rules
Use Tags: Tag security groups for better organization and management
Layer Security: Use both SGs and NACLs for defense in depth
Understand Stateful Behavior: Changes to "open" rules can immediately impact existing connections

💡 Key Insight: Security groups operate on an allow-list basis — all traffic is implicitly denied unless explicitly permitted. Start with no access, then grant only what is needed.

Key Takeaways

  • Security Groups are stateful, virtual firewalls at the instance level — return traffic is automatically allowed.

  • Default rules: Deny all inbound, Allow all outbound. Operate on an allow-list basis.

  • Inbound rules control who can reach your instance; outbound rules control what your instance can access.

  • Security Group References allow dynamic, logical rules — reference other SGs instead of IP addresses.

  • SG vs NACL: Security Groups are stateful (instance-level), NACLs are stateless (subnet-level).

  • Principle of Least Privilege: Only allow the minimum required traffic — never use 0.0.0.0/0 for SSH/RDP.

  • Connection Tracking: For "open" rules (0.0.0.0/0 in both directions), rule changes immediately interrupt existing connections.

  • Cross-account references use format: 123456789012/sg-1a2b3c4d (same region only).

  • Self-references allow intra-group communication for distributed systems (HPC, Kubernetes).

  • Stale references should be cleaned up using describe-security-group-references.
