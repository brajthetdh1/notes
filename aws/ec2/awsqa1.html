3.Q1: Root User Best Practices

Q: Why is it a bad practice to use the root user for daily tasks?

Answer: The AWS root user has unrestricted, irrevocable access to all resources and services in your AWS account. Using it for daily administrative tasks creates severe security risks and operational challenges.

1. Unrestricted Permissions (The "God Mode" Problem)
ROOT USER PERMISSIONS COMPARISON ┌─────────────────────────────────────────────────────────────────────────────┐ │ ROOT USER PERMISSIONS COMPARISON │ ├─────────────────────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ ROOT USER PERMISSIONS │ │ │ │ ┌──────────────────────────────────────────────────────────────┐ │ │ │ │ │ ✅ Create/Delete IAM users and policies │ │ │ │ │ │ ✅ Delete all S3 buckets and data │ │ │ │ │ │ ✅ Terminate all EC2 instances │ │ │ │ │ │ ✅ Delete RDS databases and backups │ │ │ │ │ │ ✅ Delete CloudTrail logs (hiding activity) │ │ │ │ │ │ ✅ Close the AWS account permanently │ │ │ │ │ └──────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ IAM ADMIN USER PERMISSIONS │ │ │ │ ┌──────────────────────────────────────────────────────────────┐ │ │ │ │ │ ✅ Manage resources (EC2, S3, RDS, etc.) │ │ │ │ │ │ ❌ Cannot delete CloudTrail logs (auditable) │ │ │ │ │ │ ❌ Cannot modify root user credentials │ │ │ │ │ │ ❌ Cannot close the account │ │ │ │ │ │ ❌ Cannot change support plans │ │ │ │ │ │ ⚠️ Actions are logged in CloudTrail │ │ │ │ │ └──────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────────────┘

2. No Audit Trail for Root Actions
CloudTrail logs record all API calls. However, the root user can delete CloudTrail trails and S3 buckets containing logs, erasing all evidence of malicious activity.

3. Violates the Principle of Least Privilege
The root user has unlimited permissions — far more than needed for any daily task — and you cannot apply IAM policies to restrict it.

⚠️ What Tasks Actually Require Root Access?
  • Closing the AWS account
  • Changing the root user email or password
  • Restoring IAM user permissions when all administrators are locked out
  • Changing the AWS Support plan (in some cases)

3.Q2: AWS CLI

Q: What is the AWS CLI and why is it useful?

Answer: The AWS Command Line Interface (AWS CLI) is a unified tool that allows you to interact with AWS services directly from your terminal or command prompt. It provides the same functionality as the AWS Management Console but with the power, speed, and scriptability of the command line.

Key Features:
FeatureDescription
Unified InterfaceOne tool for all AWS services
Multi-PlatformWindows, macOS, and Linux
ScriptableUse with Bash, PowerShell, Python, etc.
Idempotent OperationsCommands can be run multiple times without changing the result
JSON OutputEasy integration with jq and other parsers
AWS SSO SupportSecure integration with AWS Single Sign-On

Why is the AWS CLI Useful?
  • 🤖 Automation and Scripting: Manual tasks are slow, error-prone, and not repeatable. The CLI enables full automation.
  • 📦 Infrastructure as Code (IaC): Define infrastructure in scripts, version control configurations, and replicate environments consistently.
  • 🔄 CI/CD Integration: Seamlessly integrates into GitHub Actions, Jenkins, and other pipelines.
  • 💰 Cost Management: Quickly check resources and costs with commands.
  • ⚡ Rapid Debugging: Often faster than the console for diagnosing issues.

Console vs. CLI Comparison:

3.Q3: Access Keys and Secret Keys

Q: What are Access Keys and Secret Keys used for?

Answer: Access Keys are long-term credentials used for programmatic access to AWS services. They consist of an Access Key ID (public identifier) and a Secret Access Key (private key). Together, they authenticate API requests made through the AWS CLI, SDKs, or direct API calls.

⚠️ Critical Security: The Secret Access Key is only displayed once when the key is created. If lost, you must delete the key and create a new one.

AWS SDKsAuthenticate applications in Python, Java, Node.js
API CallsDirect API calls via REST or SDK

Best Practices for Access Keys:
  • 🔢 Limit Number of Keys: Max 2 active keys per user (enables zero-downtime rotation)
  • 🔄 Rotate Keys Regularly: Every 90 days (30-60 days for high-security)
  • 🎭 Use IAM Roles on EC2: Instead of access keys, use roles for temporary credentials
  • 🚫 Never Share Keys: Access keys are for a single user
  • 📁 Never Commit to Code: Never hardcode access keys or commit to version control

3.Q4: Securing AWS CLI Credentials

Q: How can you secure your AWS CLI credentials?

Answer: Securing your AWS CLI credentials is critical because compromised credentials can lead to data breaches, financial losses, and account takeover.

1. Use IAM Roles Instead of Access Keys
For applications running on EC2, ECS, or Lambda, use IAM Roles instead of access keys.
# GitHub Actions with OIDC (no access keys) name: Deploy to AWS on: push: branches: [ main ] permissions: id-token: write contents: read jobs: deploy: runs-on: ubuntu-latest steps: - name: Configure AWS credentials uses: aws-actions/configure-aws-credentials@v2 with: role-to-assume: arn:aws:iam::123456789012:role/github-actions-role aws-region: us-east-1

2. Store Credentials Securely
✅ DO
• Use environment variables (with caution)
• AWS credentials file with chmod 600
• AWS Secrets Manager
• Password managers
❌ DON'T
• Hardcode keys in code
• Commit keys to Git
• Store keys in plain text
• Share keys via email/Slack

3. Rotate Keys Regularly
Security LevelRecommended Rotation Period
General WorkloadsEvery 90 days
High-Security WorkloadsEvery 30-60 days
Regulatory ComplianceAs required (e.g., PCI-DSS: every 90 days)

✅ CLI CREDENTIAL SECURITY CHECKLIST
✅ MFA enabled on all users with CLI access
✅ Access keys rotated within the last 90 days
✅ No access keys in code repositories
✅ ~/.aws/credentials has permissions 600
✅ IAM roles used instead of access keys for EC2
✅ CloudTrail is enabled and logs are secured
✅ GuardDuty is enabled

3.Q5: IAM and EC2

Q: What is IAM and how does it relate to EC2?

Answer: AWS Identity and Access Management (IAM) is a global, no-cost AWS service that enables you to securely control access to AWS services and resources. IAM provides the infrastructure to manage authentication (who can sign in) and authorization (what permissions they have) across your AWS environment.

How IAM Relates to EC2:
ActionIAM Role
Launch EC2 instancesUser must have ec2:RunInstances permission
Stop/Start instancesUser must have ec2:StopInstances / ec2:StartInstances
Terminate instancesUser must have ec2:TerminateInstances
Create AMIsUser must have ec2:CreateImage
Attach EBS volumesUser must have ec2:AttachVolume

IAM Entities and EC2:

IAM UserA person or application that interacts with EC2A developer launching instances
IAM GroupA collection of users with similar permissions"EC2-Developers" group
IAM RoleAn identity that can be assumed by EC2 instancesEC2 instance accessing S3

💡 IAM vs. Security Groups (Common Confusion):
  • IAM: Controls who can perform actions on EC2 (identity-level)
  • Security Groups: Controls network traffic to/from EC2 (instance-level firewall)
