8.2 Scaling Policies

Scaling policies are the instructions that tell your Auto Scaling Group how and when to adjust its capacity. They transform a static group of instances into a dynamic system that responds intelligently to changing demand. The policy you choose determines whether your application scales reactively, proactively, or on a fixed schedule.

8.2.1 Dynamic Scaling

Target Tracking, Step Scaling, Simple Scaling
1. Target Tracking Scaling (Recommended)
Works like a thermostat: you set a target value (e.g., 50% CPU), and Auto Scaling adds or removes instances to maintain that target.

Predefined Metrics:
  • ASGAverageCPUUtilization — Average CPU utilization
  • ASGAverageNetworkIn/Out — Network traffic
  • ALBRequestCountPerTarget — ALB requests per target

💡 Best Practice: Use Target Tracking for simple, automated scaling. AWS manages the underlying CloudWatch alarms for you.

2. Step Scaling (Granular Control)
Define multiple thresholds and corresponding actions based on severity.

Example Step Adjustments:
Metric ValueAdjustment
40% → 60%No change
60% → 70%Add 10% capacity
70% → ∞Add 30% capacity

3. Simple Scaling (Legacy)
Single action triggered by a CloudWatch alarm with a cooldown period.

⚠️ Why Simple Scaling is Discouraged:
  • Cooldown periods make scaling slow and less responsive
  • Lacks nuanced response to load variation
  • AWS recommends Target Tracking or Step Scaling instead
📈 dynamic 🎯 target tracking 📊 step scaling
🔄

Handling Multiple Policies

Multiple Dynamic Scaling Policies
When multiple policies trigger at the same time, Amazon EC2 Auto Scaling chooses the policy that provides the largest capacity for both scale-out and scale-in.

📊 Example:
  • CPU policy wants to add 1 instance
  • SQS policy wants to add 2 instances
  • Both trigger simultaneously → Amazon EC2 Auto Scaling launches 2 instances

⚠️ Caution: Using target tracking with step scaling can cause conflicts. Test thoroughly.

⏳ Instance Warm-Up
New instances need time to become ready. During the warm-up period, the instance is not counted in the group's aggregated metrics for scaling decisions.

  • Default: Group's default instance warm-up time
  • Purpose: Prevents over-scaling based on partially initialized instances
🔄 multiple policies ⏳ warm-up ⚠️ conflicts

When to Use Predictive Scaling

✅ Good Fit
  • Recurring daily/weekly patterns
  • Business hours traffic
  • Seasonal workloads
  • Applications with slow startup times
❌ Poor Fit
  • Unpredictable, random traffic
  • News-driven spikes
  • Social media virality
  • No recurring patterns

  • Forecast Horizon: Next 48 hours

Cron Expression Format:

ScheduleCron Expression

CLI Example (Recurring):
aws autoscaling put-scheduled-update-group-action \ --auto-scaling-group-name my-asg \ --scheduled-action-name weekday-scale-up \ --recurrence "0 8 * * 1-5" \ --desired-capacity 10 \ --time-zone "America/New_York"

CLI Example (One-Time):
aws autoscaling put-scheduled-update-group-action \ --auto-scaling-group-name my-asg \ --scheduled-action-name black-friday-scaling \ --start-time "2026-11-27T08:00:00Z" \ --desired-capacity 20 \ --min-size 10 \ --max-size 30

🔄

Combining Scheduled + Dynamic Scaling

💡 Recommended Pattern:
  • 8:00 AM: Scheduled action sets Desired Capacity to 10
  • 9:00 AM - 5:00 PM: Target Tracking adjusts based on CPU (10-15)
  • 6:00 PM: Scheduled action sets Desired Capacity to 3

Result: Proactive baseline + Reactive response to unexpected spikes.

📌 Limitations:
  • Max: 125 scheduled actions per Auto Scaling group
  • Unique times: Cannot schedule actions at the same time
  • Delay: Actions may be delayed up to 2 minutes
  • Past: Cannot schedule actions in the past
🔄 combined 📊 scheduled + dynamic ✅ proactive + reactive

Key Takeaways

  • Target Tracking is the recommended dynamic scaling policy for most workloads — automated and self-managing.

  • Step Scaling gives you granular control with multiple thresholds and adjustments.

  • Simple Scaling is a legacy method and should be avoided for new configurations.

  • Predictive Scaling uses machine learning to proactively launch capacity before demand increases — ideal for recurring patterns.

  • Scheduled Scaling works like a cron job for your infrastructure — perfect for predictable, time-based patterns.

  • Combine scheduled and dynamic scaling to get both proactive baseline and reactive response to unexpected load.

  • Instance Warm-up prevents over-scaling by excluding new instances from metrics until they are ready.

  • When multiple policies trigger, Auto Scaling chooses the action that provides the largest capacity.

Review Questions

Q1: Which dynamic scaling policy is recommended by AWS for most workloads?
Answer: Target Tracking Scaling. It automatically maintains a metric at a target value, similar to a thermostat, and AWS manages the underlying CloudWatch alarms for you.
Q2: What is the difference between Step Scaling and Simple Scaling?
Answer: Step Scaling uses multiple adjustments based on the severity of the alarm breach (e.g., add 1 instance at 60% CPU, add 3 at 80%). Simple Scaling uses a single adjustment per alarm and includes a cooldown period between activities. Simple Scaling is considered legacy.
Q3: How much historical data does Predictive Scaling need to start forecasting?
Answer: Predictive scaling requires a minimum of 24 hours of historical metric data to start generating forecasts. However, forecasts are more effective if the data spans two full weeks (14 days). New Auto Scaling groups need at least 24 hours of load data before predictive scaling can be used.
Q4: What is the difference between "Forecast Only" and "Forecast and Scale" modes in Predictive Scaling?
Answer: In Forecast Only mode, Auto Scaling generates capacity forecasts but does not scale based on them — this allows you to evaluate accuracy. In Forecast and Scale mode, it generates forecasts and proactively scales based on those forecasts. Best practice: start with Forecast Only to evaluate before enabling active scaling.
Q5: What is the format of a cron expression for scheduled scaling?
Answer: A cron expression has five fields separated by spaces: [Minute] [Hour] [Day_of_Month] [Month_of_Year] [Day_of_Week]. For example, 0 8 * * 1-5 runs at 8:00 AM every Monday through Friday. The asterisk (*) is a wildcard that matches all values for a field.
