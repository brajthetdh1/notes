7.3 Spot Instances

📖 Complete Theory

Spot Instances offer access to Amazon EC2's spare compute capacity at up to a 90% discount compared to On-Demand prices. In exchange for this deep discount, AWS can reclaim the instance with a two-minute warning when the capacity is needed elsewhere.

This makes Spot Instances ideal for workloads that are fault-tolerant, flexible, or can be interrupted and resumed.
⚡ Spot Instances 💰 up to 90% ⚠️ interruptible
📊

The Core Mechanism

The Spot market is driven by the relationship between spare capacity and demand. The Spot Price is determined by long-term trends in supply and demand for EC2 spare capacity.

💡 Key Insight: You specify a maximum price you are willing to pay. If your bid meets or exceeds the current Spot Price, your request is fulfilled and your instances run.

You will often pay less than your bid. Everyone pays the same Spot Price for that period, regardless of their bid. You will never pay more than your bid.

Interruption Behavior

When your Spot Instance is interrupted, you can control what happens by specifying the InstanceInterruptionBehavior. The default is to terminate.

🗑️ Terminate (Default)
Instance is permanently deleted
Stateless workloads where you don't need to preserve state
⏸️ Stop
Instance is stopped (EBS volumes preserved)
Workloads where you want to preserve data and restart later
💤 Hibernate
Instance is hibernated (RAM state saved to EBS)
Workloads where you want to resume exactly where you left off

📌 Important: For Stop behavior:
  • The Spot Instance request must be persistent
  • Amazon EC2 will restart the stopped instance when capacity becomes available again
  • While stopped, you are only charged for EBS volumes, not compute

💰 Billing for Interrupted Spot Instances:
  • You terminate: Pay for any partial hour used
  • AWS interrupts: NOT charged for any partial hour of usage
🔄 interruption 🗑️ terminate ⏸️ stop 💤 hibernate
📡

Receiving Interruption Notices

AWS provides a two-minute warning before interrupting your Spot Instance. You can detect these notices in two ways:

1. Via Instance Metadata (IMDSv2)
# Get session token TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600") # Check for interruption notice curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/spot/instance-action
Example Output:
{"action": "terminate", "time": "2026-08-02T10:30:00Z"}

2. Via Amazon EventBridge
AWS emits an EC2 Spot Instance Interruption Warning event two minutes before interruption.

⚠️ Important: The notices are emitted on a "best effort" basis. It is possible that your instance could be interrupted before the warning is sent out. Your applications must be designed to handle an unexpected interruption.
📡 notices ⏱️ 2-minute warning ⚠️ best effort

🔬 Scientific Research
Genomic sequencing, simulations
🎬 Media Processing

❌ When NOT to Use Spot Instances:
  • Stateful Databases: Cannot survive a two-minute eviction
  • Long-Running Stateful Applications: Interruption would cause data loss
  • Synchronous Tasks: Requires predictable, uninterrupted performance
  • Critical Production Systems: Cannot tolerate interruptions

7.3.3 Spot Fleet & Mixed Instances

📖 Spot Fleet: The Legacy Fleet Management API
A Spot Fleet is a collection of Spot Instances and optionally On-Demand Instances that is launched based on criteria you specify.

⚠️ Important Deprecation Notice: The RequestSpotFleet API is a legacy API with no planned investment. AWS strongly discourages using it for new workloads.

For modern implementations, use:
  • EC2 Fleet for one-time or fleet management without lifecycle management
  • Auto Scaling Groups with Mixed Instances Policy for managed lifecycle and scaling

Spot Allocation Strategies:
📊 capacity-optimized
Launches from Spot pool with optimal capacity
Best for: Maximizing availability
⚖️ price-capacity-optimized
Balances price and capacity
Best for: Cost and availability balance
💰 lowest-price
Launches from lowest-priced Spot pool
Best for: Maximizing cost savings

  • prioritized: Launches On-Demand Instances based on priority order you define

Capacity Rebalancing

Capacity Rebalancing is a feature that proactively replaces Spot Instances that are at an elevated risk of interruption. It uses a signal from the Spot service to identify instances at risk before the actual interruption occurs.

Key Takeaways

  • Spot Instances offer up to 90% discount on EC2 spare capacity in exchange for interruptibility.

  • The two-minute warning is provided on a "best effort" basis — your application must handle unexpected interruptions.

  • Interruption behaviors: Terminate (default), Stop, or Hibernate.

  • If AWS interrupts your Spot Instance, you are NOT charged for any partial hour of usage.

  • Spot Fleet is a legacy API with no planned investment — use EC2 Fleet or Auto Scaling Groups with Mixed Instances Policy.

  • Mixed Instances Policies allow you to combine Spot and On-Demand Instances, maintaining a guaranteed baseline of On-Demand capacity.

  • Capacity Rebalancing proactively replaces Spot Instances at elevated risk of interruption before they are terminated.

  • Allocation strategies: capacity-optimized (max availability), price-capacity-optimized (balanced), lowest-price (max cost savings).

Review Questions

Q1: What is the fundamental trade-off of Spot Instances?
Answer: Spot Instances offer steep discounts (up to 90% off On-Demand prices) in exchange for the possibility that AWS can reclaim the instance with a two-minute interruption notice when spare capacity is needed elsewhere.
Q2: What is the key difference in billing between user-initiated termination and AWS-initiated interruption?
Answer: If you terminate a Spot Instance, you pay for any partial hour used (like On-Demand). However, if AWS interrupts the instance to reclaim capacity, you are NOT charged for any partial hour of usage.
Q3: What are the three interruption behaviors for Spot Instances?
Answer: The three behaviors are: Terminate (default — permanently deletes the instance), Stop (stops the instance, preserves EBS volumes), and Hibernate (saves RAM state to EBS for resume).
Q4: Why is Spot Fleet considered a legacy API?
Answer: The RequestSpotFleet API is a legacy API with no planned investment. AWS strongly discourages using it for new workloads. Modern implementations should use EC2 Fleet or Auto Scaling Groups with Mixed Instances Policy.
Q5: What is Capacity Rebalancing and how does it improve Spot Instance availability?
Answer: Capacity Rebalancing is a feature that monitors Spot Instances for signals indicating an elevated risk of interruption. When a risk is detected, the fleet launches a replacement instance in a different capacity pool before the original instance is interrupted, allowing for zero-downtime replacement.
Q6: What are the recommended Spot allocation strategies and when should each be used?
Answer: The recommended strategies are:
  • capacity-optimized — launches from pools with optimal capacity, maximizing availability
  • price-capacity-optimized — balances price and capacity
  • lowest-price — launches from lowest-priced pools, maximizing cost savings
AWS recommends capacity-optimized for most workloads.
