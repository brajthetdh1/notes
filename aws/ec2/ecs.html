AWS ECS (Elastic Container Service) – Detailed Guide

Introduction

AWS ECS is a fully managed container orchestration service that allows you to run Docker containers at scale. It integrates tightly with AWS services like IAM, VPC, CloudWatch, and ALB/NLB.

  • Supports Docker containers
  • Highly scalable and secure
  • EC2 or Fargate launch types
  • Service auto-scaling and deployment management

Core Components

Cluster
A logical grouping of ECS resources where your tasks run. Can be EC2-backed or Fargate-backed.
Task Definition
Blueprint for running containers: defines Docker image, CPU/memory, environment variables, networking, IAM roles, and logging.
Task
An instantiation of a task definition running on EC2 or Fargate; can scale horizontally.
Service
Ensures desired number of tasks are running, manages scaling, replacements, and load balancer integration. Supports rolling updates, blue/green deployments.
Container
The actual Docker container running inside a task. Multiple containers can exist per task definition.

Launch Types

  • EC2 Launch Type: ECS schedules tasks on your EC2 instances. Scaling is handled via Auto Scaling Groups.
  • Fargate Launch Type: Serverless mode where AWS manages compute resources. Pay per task usage.

Networking & Security

Tasks run in a VPC and can use security groups for network isolation. ECS supports multiple network modes:

  • Bridge: Default for EC2; containers share host IP
  • awsvpc: Each task gets its own ENI and private IP (recommended for Fargate)
  • Host: Container shares host network
  • None: No networking

Service discovery via AWS Cloud Map and load balancing via ALB/NLB is supported.

Scaling

  • Service Auto Scaling: Scale tasks based on CPU, memory, or custom CloudWatch metrics.
  • Cluster Auto Scaling: Adjust EC2 instance count automatically using Auto Scaling Groups.

Deployment Patterns

  • Rolling Updates – Gradually replace tasks to minimize downtime.
  • Blue/Green Deployment – Deploy new version in parallel and switch traffic after verification.
  • Canary Deployment – Shift traffic gradually to new version to monitor behavior.

Observability

  • CloudWatch Logs – Capture container logs.
  • CloudWatch Metrics – Monitor CPU, memory, and network usage.
  • AWS X-Ray – Distributed tracing for microservices.
  • Container Insights – Advanced monitoring and diagnostics.

Best Practices

  • Use Fargate for serverless deployments with less operational overhead.
  • Enable awsvpc networking for task isolation and security.
  • Store sensitive information in AWS Secrets Manager or SSM Parameter Store.
  • Implement service auto-scaling for dynamic workloads.
  • Use rolling, blue/green, or canary deployments for zero-downtime updates.

ECS Clusters, Tasks, and Services

1. ECS Cluster

A cluster is a logical grouping of ECS resources where your tasks and services run. It serves as the “workspace” or “environment” for your containers.

  • Organizes ECS resources and determines where tasks will run.
  • Can be EC2-backed (you manage instances) or Fargate-backed (AWS manages compute).
  • Provides isolation for different environments (e.g., dev, staging, production).

Analogy: Cluster = a building, where tasks are rooms and services manage occupancy.

2. ECS Task

A task is a running instance of a task definition. It represents a deployment of one or more containers.

  • Defined by a task definition specifying Docker image, CPU/memory, networking, environment variables, IAM roles, and logging.
  • Can contain multiple containers (main container + sidecars).
  • Runs on an EC2 instance or Fargate.
  • Can be started, stopped, or restarted independently.

Analogy: Task = a room in the building (cluster) containing one or more containers (people working in the room).

3. ECS Service

A service ensures that a specified number of tasks are running and manages their lifecycle. It integrates with load balancers and scaling mechanisms.

  • Maintains the desired task count and replaces failed tasks automatically.
  • Supports deployment strategies: rolling updates, blue/green deployments, and canary deployments.
  • Integrates with ALB/NLB for traffic distribution.
  • Supports auto-scaling based on CPU, memory, or custom metrics.

Analogy: Service = building management, ensuring enough rooms (tasks) are always occupied and handles replacements if a room becomes unavailable.

Key Differences

Definition Single running instance of a task definition Ensures desired number of tasks are running Logical grouping of tasks and services
Lifecycle Starts/stops independently Manages tasks automatically Persistent group
Scaling Manual or service-driven Auto-scalable Contains resources to run tasks

ECS Launch Types

1. What is a Launch Type?

A launch type in AWS ECS specifies where and how your containers run. It determines whether ECS tasks run on EC2 instances that you manage or in a serverless environment managed by AWS.

ECS supports two primary launch types:

  • EC2 Launch Type
  • Fargate Launch Type

2. EC2 Launch Type

Definition:
With the EC2 launch type, ECS schedules tasks on a cluster of EC2 instances that you manage. You are responsible for managing these instances, including scaling, patching, and monitoring.

Key Points:

  • ECS schedules tasks based on available CPU and memory on EC2 instances.
  • You manage Auto Scaling Groups to scale instances up or down.
  • Network modes supported:
    • Bridge mode (default): Containers share the host IP and ports.
    • awsvpc mode: Each task gets its own ENI and private IP.

Use Case Example: Running large-scale microservices that require custom AMIs or specialized networking. Applications that require GPU instances.

3. Fargate Launch Type

Definition:
With Fargate, you do not manage any servers. AWS provisions and manages compute resources automatically. You simply define the CPU and memory requirements per task, and Fargate runs them in a serverless environment.

Key Points:

  • Tasks run in awsvpc networking mode only.
  • You pay per task based on allocated CPU and memory.
  • ECS automatically handles scaling based on tasks and load.

Use Case Example: Web applications with variable traffic patterns. Short-lived or event-driven tasks. Teams looking for a serverless approach without managing infrastructure.

4. Summary

- EC2 launch type: ECS tasks run on EC2 instances that you manage. You control the infrastructure and networking.

- Fargate launch type: ECS tasks run serverlessly. AWS handles infrastructure management, scaling, and provisioning.

- The choice depends on workload type, control requirements, and operational preferences.

How to Create an ECS Cluster

Creating an ECS cluster allows you to run and manage containers in a scalable environment. Follow these steps to set up a cluster in AWS ECS:

  1. Access the ECS Console: Go to AWS Management Console → ECS → Clusters → Create Cluster.
  2. Choose a Cluster Template:
    • EC2 Linux + Networking: For the EC2 launch type where you manage underlying instances.
    • Fargate: Serverless option where AWS handles compute resources.
  3. Configure Cluster Settings:
    • Cluster Name: Provide a descriptive name for the cluster.
    • EC2 Instance Type & Number: Only for EC2 launch type; select instance size and count.
    • VPC & Subnets: Choose networking settings to deploy your tasks.
  4. Create Cluster: Click Create Cluster to finalize setup.
  5. Cluster Ready: The cluster is now ready to deploy ECS tasks and services.

Tips for ECS Clusters

  • Use descriptive cluster names for easier management across environments (dev, staging, prod).
  • For EC2 clusters, monitor instance utilization to optimize cost.
  • Use multiple subnets across availability zones for high availability.
  • For Fargate, no need to manage EC2 instances, focus on task definitions and networking.

ECS Task Definitions and Running Tasks

1. How to Define a Task Definition

A task definition is a blueprint describing how your ECS tasks should run, including the containers, resources, and configurations required.

  1. Access ECS Task Definitions: Go to ECS Console → Task Definitions → Create New Task Definition.
  2. Select Launch Type Compatibility: Choose EC2 or Fargate depending on your deployment needs.
  3. Define Task Parameters:
    • Task Name: Give a descriptive name for the task.
    • Container Definitions: Specify Docker image, port mappings, memory, and CPU requirements.
    • Environment Variables and Secrets: Configure environment variables or link to AWS Secrets Manager / SSM Parameter Store.
    • Logging Configuration: Enable CloudWatch Logs for container output.
  4. Create Task Definition: Click Create to finalize. The task definition is now ready to be used for running tasks or creating services.

2. How to Run a Task

Once you have a task definition, you can run tasks in your ECS cluster.

  1. Access Cluster: Go to ECS → Clusters → Select Cluster → Run Task.
  2. Choose Task Parameters:
    • Task Definition: Select the task definition you created.
    • Launch Type: EC2 or Fargate, depending on cluster setup.
    • Number of Tasks: Specify how many instances to run.
    • Subnet and Security Groups: Required for Fargate tasks for networking.
  3. Run Task: Click Run Task. ECS schedules and starts the tasks on the cluster.

Tips for Task Definitions and Running Tasks

  • Use versioned task definitions so updates do not disrupt running tasks.
  • Always configure CloudWatch Logs to capture container output for troubleshooting.
  • Use environment variables for dynamic configuration and avoid hardcoding sensitive information.
  • For Fargate, ensure proper subnet selection and security group configuration for connectivity.

How to Create an ECS Service

A service in ECS is responsible for maintaining a desired number of tasks running at all times, automatically replacing failed tasks, and optionally integrating with load balancers.

  1. Access the ECS Console: Go to AWS Management Console → ECS → Clusters → Select your Cluster → Create → Create Service.
  2. Select Launch Type: Choose EC2 or Fargate depending on your cluster configuration.
  3. Configure Service:
    • Service Name: Provide a descriptive name for the service.
    • Task Definition: Select the task definition to run.
    • Number of Tasks: Set the desired count of tasks to keep running.
  4. Configure Optional Features:
    • Load Balancer: Integrate with ALB/NLB to distribute traffic across tasks and configure listeners and target groups.
    • Deployment Type: Rolling update or blue/green deployment with CodeDeploy.
    • Auto Scaling: Optionally set scaling policies based on CPU, memory, or custom CloudWatch metrics.
  5. Configure Networking (Fargate only): Select VPC, subnets, and security groups. Tasks receive ENIs and private IPs for secure communication.
  6. Create Service: Click Create Service. ECS schedules tasks and monitors their health.
  7. Verify: Go to the cluster → Services → Select the service → check tasks and events. Ensure tasks are running and view CloudWatch Logs if needed.

Summary

  • Tasks are individual container instances.
  • Services ensure high availability, scaling, and managed deployment of tasks.
  • Using a service allows ECS to automatically replace failed tasks, integrate with load balancers, and handle rolling updates.

📘 Full Amazon ECS Tutorial

1. What is Amazon ECS?

Amazon ECS is a fully managed container orchestration service by AWS. It allows you to run and scale Docker containers without manually managing servers. You can run it in two ways:

  • EC2 Launch Type → You manage the EC2 instances (more control).
  • Fargate Launch Type → AWS manages compute (serverless containers).

2. Prerequisites

Before starting, you need:

  • An AWS account.
  • AWS CLI installed and configured (aws configure).
  • Docker installed locally.
  • A sample Java app packaged in a JAR file (we’ll dockerize it).

3. Step 1 – Containerize Your Java App

FROM openjdk:17-jdk-alpine
WORKDIR /app
COPY target/myapp.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
        
docker build -t my-java-app .
docker run -p 8080:8080 my-java-app

4. Step 2 – Push Image to Amazon ECR

  1. Create a repository: 
    aws ecr create-repository --repository-name my-java-app
  2. Authenticate Docker with ECR: 
    aws ecr get-login-password --region ap-south-1 | docker login --username AWS --password-stdin <account-id>.dkr.ecr.ap-south-1.amazonaws.com
  3. Tag and push the image: 
    docker tag my-java-app:latest <account-id>.dkr.ecr.ap-south-1.amazonaws.com/my-java-app:latest
docker push <account-id>.dkr.ecr.ap-south-1.amazonaws.com/my-java-app:latest

5. Step 3 – Create an ECS Cluster

  • Go to AWS Console → ECS → Clusters → Create Cluster.
  • Choose Fargate (recommended for beginners).
  • Give your cluster a name (e.g., java-app-cluster).
  • Click Create.

6. Step 4 – Define a Task Definition

  1. Go to ECS → Task Definitions → Create new task definition.
  2. Choose Fargate.
  3. Configure:
    • Task name: java-task
    • Container image: your ECR image URL
    • Port mapping: 8080
    • CPU & Memory: 0.5 vCPU, 1 GB RAM
    • Logging: Enable CloudWatch Logs
  4. Save task definition.

7. Step 5 – Create a Service

  1. Go to ECS → Your Cluster → Services → Create Service.
  2. Choose Fargate.
  3. Select your task definition.
  4. Configure:
    • Service name: java-service
    • Number of tasks: 2
    • Networking: Select VPC & Subnets, attach Security Group allowing port 8080
    • Load Balancer (recommended): Attach an Application Load Balancer (ALB)
  5. Create service.

8. Step 6 – Run a Task (Optional)

If you want to run a one-off task (not long-running like a service):

  • Go to Cluster → Run Task.
  • Pick your task definition and run it.

9. Step 7 – Access Your Java App

  • If you used an ALB, AWS gives you a DNS name like: 
    http://java-app-alb-123456.ap-south-1.elb.amazonaws.com
  • If no ALB, get the public IP of the Fargate task/EC2 instance and hit port 8080.

10. Step 8 – Monitoring and Scaling

  • Use CloudWatch Logs to see container logs.
  • Use Service Auto Scaling to scale containers up/down based on CPU or memory.

🔑 Summary

Dockerize app → Push to ECR → Create Cluster → Define Task → Create Service → Access App

ECS automates scaling, health checks, and task restarts.

Use Fargate for serverless ease, or EC2 for cost control.

ECS Fargate Networking Mode: awsvpc

In AWS Fargate, the only supported networking mode is awsvpc. This mode ensures that each Fargate task is assigned its own Elastic Network Interface (ENI) and private IP address directly inside your VPC, making tasks behave like independent EC2 instances from a networking perspective.

Why awsvpc Mode?

  • Dedicated IP Address: Each task gets its own private IP address from the subnet.
  • Security Isolation: Security groups and network ACLs can be applied at the task level.
  • Service-to-Service Communication: Tasks communicate using private IPs inside the VPC.
  • Load Balancer Integration: Tasks register directly with ALB or NLB for scalable access.

Key Points

  • Other modes like bridge or host are not supported in Fargate.
  • Requires configuration of a VPC, subnets, and security groups before running tasks.
  • Provides a secure, consistent networking model for microservices.

Example Scenario

Imagine deploying two microservices (Orders API and Payments API) as ECS Fargate tasks in awsvpc mode:

  • Orders API → ENI with private IP 10.0.1.15.
  • Payments API → ENI with private IP 10.0.1.25.
  • Both communicate securely inside the VPC using private IPs.
  • Different security groups can control which services talk to each other.

Conclusion

The awsvpc mode ensures Fargate tasks are first-class citizens in your VPC. It enhances network security, simplifies communication, and integrates seamlessly with load balancers and other AWS services.

Task Execution Role

ECS tasks assume this role to pull images from ECR, write logs to CloudWatch, etc.

What is the ECS Task Execution Role?

The ECS Task Execution Role is an IAM role that ECS tasks assume to perform actions required for the task to run properly. It is not the same as the Task Role, which your application uses to access AWS resources.

The execution role is specifically used by the ECS agent and underlying platform to:

  • Pull container images from Amazon ECR or other registries.
  • Send logs to Amazon CloudWatch Logs.
  • Fetch secrets from AWS Secrets Manager or SSM Parameter Store.

Why is it needed?

When a task starts:

  • ECS needs to pull the container image from ECR. Without permissions, this operation fails.
  • ECS optionally streams logs from the container to CloudWatch Logs.
  • ECS may need to access secrets or environment variables securely.

Without an execution role, ECS cannot perform these essential operations, even if your application has its own Task Role.

Key Features

  • Separation of Concerns: The execution role is for ECS platform operations, while the Task Role is for the application’s access to AWS resources.
  • Managed Policies: AWS provides a managed policy (AmazonECSTaskExecutionRolePolicy) which includes permissions like:
    • ecr:GetAuthorizationToken, ecr:BatchGetImage, ecr:BatchCheckLayerAvailability
    • logs:CreateLogGroup, logs:CreateLogStream, logs:PutLogEvents
  • Attachable at Task Definition: Each ECS task definition can specify its execution role under executionRoleArn.

Example Use Case

Suppose you have an ECS Fargate task running a Java microservice:

  • The container image is stored in a private ECR repository.
  • Logs are configured to go to CloudWatch Logs.
  • Some configuration is stored in SSM Parameter Store.

The ECS task will assume the Task Execution Role to pull the image, create log streams, push logs, and retrieve configuration values securely. Meanwhile, the Task Role allows the application to access other AWS services like DynamoDB or SQS.

Best Practices

  • Use least privilege: grant only permissions required for pulling images and writing logs.
  • Use AWS managed policy when possible to reduce configuration errors.
  • Keep Execution Role and Task Role separate to avoid over-permissioning your application.
  • Ensure tasks in multiple accounts or VPCs have the correct role trust relationships.

ECS Scaling with CloudWatch Alarms

It can scale ECS tasks based on CloudWatch alarms. ECS supports Service Auto Scaling (number of tasks) and Cluster Auto Scaling (EC2 instances).

Service Auto Scaling

Service Auto Scaling ensures that your ECS service runs the right number of tasks based on demand. You define scaling policies and CloudWatch alarms monitoring metrics like CPU, memory, or custom metrics. When the metric exceeds the threshold, ECS adds more tasks; when it falls below, ECS reduces the tasks.

Example: An Orders API service has 2 tasks initially. CPU usage goes above 70%, triggering a CloudWatch alarm. ECS adds 2 more tasks, increasing total tasks to 4. When load decreases, ECS scales back down automatically.

Cluster Auto Scaling (CAS)

Cluster Auto Scaling automatically adjusts the number of EC2 instances in your ECS cluster to accommodate tasks. ECS integrates with Auto Scaling Groups (ASG). If tasks cannot be placed due to insufficient CPU or memory, ECS increases the number of EC2 instances. Idle resources allow ECS to scale in and save cost.

Example: An ECS cluster has 3 EC2 instances running 10 tasks. New tasks cannot be placed due to insufficient CPU. ECS CAS triggers the Auto Scaling Group to add 2 more EC2 instances. All tasks are successfully placed, and the system continues scaling automatically.

CloudWatch Alarms Integration

  • CloudWatch monitors metrics for tasks or instances.
  • Alarms define thresholds and evaluation periods.
  • Alarms trigger scaling policies for ECS service (tasks) or cluster (EC2 instances).
  • Custom metrics can also be used for scaling, like request count per task or queue length in SQS.

Key Points

  • Service Auto Scaling scales the number of tasks and works for both Fargate and EC2 launch types.
  • Cluster Auto Scaling scales the underlying EC2 instances and is applicable only for EC2 launch type.
  • Fargate tasks do not need Cluster Auto Scaling because AWS provisions infrastructure automatically.
  • Auto Scaling ensures high availability, cost optimization, and responsive performance.

Private Subnets with NAT Gateway

Tasks should run in private subnets for security, and a NAT Gateway allows outbound internet access.

Overview

When deploying ECS tasks, network placement is crucial for both security and functionality. Private subnets are subnets without direct internet access, meaning resources inside cannot be reached from the public internet. A NAT Gateway provides outbound internet access for resources in private subnets without exposing them directly to the internet.

Why Use Private Subnets for ECS Tasks?

  • Security: Prevents direct internet access to containers and reduces the attack surface.
  • Compliance: Meets regulatory standards requiring workloads to reside in private networks.
  • Controlled Access: All inbound traffic must go through controlled entry points like an ALB in a public subnet.

Role of NAT Gateway

Tasks in private subnets may still need outbound access to download images from ECR or Docker Hub, access external APIs, or send metrics and logs. The NAT Gateway acts as a bridge: it is allocated in a public subnet with a public IP and routes outbound traffic from private subnets to the internet, ensuring ECS tasks remain private and inaccessible directly from the internet.

Network Architecture Example

  • VPC: Contains both public and private subnets.
  • Public subnet: NAT Gateway resides here, along with ALB or NLB.
  • Private subnet: ECS tasks run here with the default route pointing to the NAT Gateway for outbound internet access.

Flow: Private ECS Task → Private Subnet Route Table → NAT Gateway in Public Subnet → Internet

Key Points

  • ECS tasks should run in private subnets to enhance security.
  • NAT Gateway enables outbound-only internet access without exposing tasks.
  • Tasks can communicate with internal services (RDS, S3, other ECS services) directly over the VPC.
  • Public-facing access is managed via ALB or API Gateway, not directly through task networking.

Benefits

  • Secure container placement.
  • Controlled outbound internet access.
  • Supports private communication and internal service calls.
  • Meets security best practices for production workloads.
