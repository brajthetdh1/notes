3.2.2 IAM Policies and Permissions

IAM policies are the foundation of access control in AWS. They define who can do what on which resources and under what conditions. Understanding how policies work is essential for implementing secure, least-privilege access in your AWS environment.
📜 policies 🔐 permissions 🛡️ access control
📖

What is an IAM Policy?

An IAM policy is a JSON (or YAML) document that defines permissions. When attached to an identity (user, group, or role) or a resource, it specifies what actions are allowed or denied.

Policies are the mechanism through which you grant or restrict access. By default, all requests are implicitly denied — you must explicitly allow access through a policy.

Policy Structure:
{ "Version": "2012-10-17", "Statement": [ { "Sid": "AllowS3ReadOnly", "Effect": "Allow", "Action": [ "s3:GetObject", "s3:ListBucket" ], "Resource": [ "arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*" ], "Condition": { "IpAddress": { "aws:SourceIp": "203.0.113.0/24" } } } ] }
ElementDescription
VersionThe policy language version. Always use "2012-10-17".
StatementThe main block containing one or more permission statements.
SidA statement ID for identifying the statement (optional).
EffectEither "Allow" or "Deny".
ActionThe API actions being permitted or denied (e.g., s3:GetObject, ec2:RunInstances).
ResourceThe AWS resources affected (using ARNs).
ConditionConditions under which the policy applies (optional).

AWS Managed Policies

AWS managed policies are standalone policies created and maintained by AWS. They make it convenient to assign appropriate permissions without writing policies yourself.

Key Characteristics:
  • You cannot modify the permissions defined in an AWS managed policy
  • When AWS launches new services or APIs, these policies are automatically updated
  • Updates affect all entities attached to the policy

Categories:
CategoryDescriptionExamples
Job FunctionAlign with common IT job rolesAdministratorAccess, PowerUserAccess, ReadOnlyAccess
Full AccessGrant complete access to a specific serviceAmazonS3FullAccess, AmazonEC2FullAccess
Partial AccessGrant specific levels of access to a serviceAmazonEC2ReadOnlyAccess
Power UserFull access except user/group managementAWSCodeCommitPowerUser

📌 Recommendation: If you are new to AWS, start by using AWS managed policies for common use cases.

Customer Managed Policies

Customer managed policies give you precise control. You create, edit, and manage them.

Example: Custom Policy for EC2 Management
{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": [ "ec2:StartInstances", "ec2:StopInstances", "ec2:DescribeInstances" ], "Resource": "arn:aws:ec2:us-east-1:123456789012:instance/*", "Condition": { "StringEquals": { "ec2:ResourceTag/Environment": "Development" } } } ] }

When to Use Inline Policies:
  • A specific user needs a temporary permission
  • A custom role requires a unique set of permissions
  • You need to enforce a strict, one-off policy

Resource-Based Policies

Resource-based policies are attached directly to an AWS resource (such as an S3 bucket, SQS queue, or KMS key), rather than an IAM identity.

RESOURCE-BASED POLICIES ┌─────────────────────────────────────────────────────────────┐ │ RESOURCE-BASED POLICIES │ ├─────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────────┐ │ │ │ AWS RESOURCE │ │ │ │ │ │ │ │ ┌─────────────────────────────────────────────┐ │ │ │ │ │ RESOURCE-BASED POLICY │ │ │ │ │ │ │ │ │ │ │ │ Defines: WHO can access and WHAT actions │ │ │ │ │ │ Example: S3 bucket policy │ │ │ │ │ └─────────────────────────────────────────────┘ │ │ │ │ │ │ │ └─────────────────────────────────────────────────────┘ │ │ │ │ Services supporting resource-based policies: │ │ • Amazon S3 (bucket policies) │ │ • IAM Roles (trust policies) │ │ • AWS KMS (key policies) │ │ • Amazon SQS (queue policies) │ └─────────────────────────────────────────────────────────────┘

Key Difference:
  • Identity-based policies: "What can this user/role do?"
  • Resource-based policies: "Who can access this resource?"

Example: S3 Bucket Policy (Cross-Account Access)
{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::222222222222:role/CrossAccountRole" }, "Action": "s3:GetObject", "Resource": "arn:aws:s3:::shared-bucket/*" } ] }

IAM Policy Evaluation Logic

AWS evaluates policies in a specific order to determine whether to allow or deny a request.

IAM POLICY EVALUATION HIERARCHY ┌─────────────────────────────────────────────────────────────────────────────┐ │ IAM POLICY EVALUATION HIERARCHY │ ├─────────────────────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ 1. EXPLICIT DENY (Override Everything) │ │ │ │ └─ If any policy explicitly denies the action → DENY │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ 2. ORGANIZATIONS SCPs & RCPs │ │ │ │ └─ If SCP/RCP denies → DENY; If allows → Continue to Resource │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ 3. RESOURCE-BASED POLICIES │ │ │ │ └─ If resource policy denies → DENY; If allows → Continue │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ 4. IDENTITY-BASED POLICIES │ │ │ │ └─ If identity policy allows → ALLOW (unless boundary limits) │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ 5. PERMISSION BOUNDARIES & SESSION POLICIES │ │ │ │ └─ Implicit deny if permissions exceed boundary │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────────────┘

Core Principles:
  • Deny by Default: All requests are implicitly denied unless explicitly allowed
  • Explicit Deny Overrides All: An explicit deny in any policy overrides all allows
  • Multiple Policies Combine: Effective permissions = union of allowed actions minus any explicit denies

{ "Version": "2012-10-17", "Statement": [ { "Effect": "Deny", "Action": "ec2:TerminateInstances", "Resource": "*", "Condition": { "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" } } } ] }

Best Practices for IAM Policies

  • 📦 Use AWS Managed Policies for common use cases and job functions

  • ✏️ Create Customer Managed Policies for custom, reusable permissions

  • 📎 Avoid Inline Policies unless you have a specific, one-off use case

  • 🔐 Grant Least Privilege — only the minimum permissions needed

  • 🔍 Use Conditions to add context-based restrictions (IP, MFA, time)

  • 🧪 Validate Policies using the IAM policy simulator before applying

  • 📊 Audit Regularly using AWS Access Analyzer and IAM Credential Reports

Key Takeaways

  • Policies are JSON documents that define who can access what resources and under what conditions.

  • Explicit deny overrides all allows — this is the most fundamental rule of IAM authorization.

  • AWS managed policies are pre-built by AWS, updated automatically, and cannot be modified.

  • Customer managed policies give you full control and are reusable across multiple entities.

  • Inline policies are embedded in a single identity and deleted with it — use sparingly.

  • Resource-based policies attach directly to resources and define who can access them.

  • SCPs and RCPs add organization-level guardrails that override identity-based permissions.

  • Least privilege is a journey — start with broader permissions and progressively restrict over time.
