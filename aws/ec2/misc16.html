14.Q1: How do you troubleshoot an EC2 instance that is unreachable via SSH?

📝 Answer:
Troubleshooting an EC2 instance unreachable via SSH follows a systematic approach, starting from the network layer and moving inward to the instance configuration. The process involves checking security groups, network ACLs, instance health, and finally, the operating system itself.
🔍 Detailed Troubleshooting Steps:
SSH TROUBLESHOOTING FLOW ┌─────────────────────────────────────────────────────────────────────────────────────┐ │ SSH TROUBLESHOOTING FLOW │ ├─────────────────────────────────────────────────────────────────────────────────────┤ │ │ │ 1. CHECK NETWORK CONFIGURATION │ │ └─ Security Group: Ensure SSH (port 22) is allowed from your IP │ │ └─ Network ACL: Ensure both inbound (22) and outbound (1024-65535) are allowed│ │ └─ Public IP: Verify the instance has a public IP or Elastic IP │ │ └─ Route Table: Ensure route to Internet Gateway exists (for public subnets) │ │ │ │ 2. CHECK INSTANCE HEALTH │ │ └─ System Status Check: 2/2 passed? If not → Stop/Start the instance │ │ └─ Instance Status Check: 2/2 passed? If not → OS-level issue │ │ │ │ 3. CHECK SSH CONFIGURATION │ │ └─ Verify username (ec2-user, ubuntu, root, etc.) │ │ └─ Verify key pair matches the instance │ │ └─ Check file permissions: .ssh directory (700), authorized_keys (600) │ │ │ │ 4. ALTERNATIVE ACCESS METHODS │ │ └─ EC2 Instance Connect (browser-based SSH) │ │ └─ AWS Systems Manager Session Manager (if SSM Agent is installed) │ │ │ │ 5. ADVANCED RECOVERY (if all else fails) │ │ └─ Use EC2 Serial Console (if supported) │ │ └─ Use Rescue Instance method (stop → detach root volume → attach to rescue) │ │ │ └─────────────────────────────────────────────────────────────────────────────────────┘

Common Causes and Fixes:
IssueSymptomFix
Security GroupConnection timeoutAdd inbound rule for SSH from your IP
Network ACLConnection timeoutAllow ephemeral ports (1024-65535) outbound
Public IPConnection timeoutUse Elastic IP or note IP change after stop/start
Key Pair MismatchPermission denied (publickey)Use correct key pair

14.Q2: What is the EC2 Serial Console and when would you use it?

📝 Answer:
The EC2 Serial Console is a text-based, BIOS-level connection to your EC2 instance that provides access before the operating system boots. It is a last-resort troubleshooting tool for instances that are completely unreachable via SSH or RDP.
🔍 Detailed Explanation:

Key Characteristics:
FeatureDetail
Access LevelBIOS/UEFI and bootloader (pre-OS)
Instance TypePrimarily Nitro-based instances
Access MethodAWS Management Console or CLI
PrerequisiteMust be enabled at account level per Region
AuthenticationIAM-based access control

When to Use the Serial Console:
ScenarioWhy Serial Console Helps
Kernel panicView the panic stack trace
Bad fstab entryBoot drops to emergency shell; fix fstab directly
Broken GRUBInterrupt boot and edit kernel parameters
Lost root passwordBoot into single-user mode and reset password
Broken SSH configFix sshd_config even if SSH won't start
Network misconfigurationFix network config files without network access

Enabling the Serial Console:
aws ec2 enable-serial-console --region us-east-1

Connecting via CLI:
aws ssm start-session \ --target i-1234567890abcdef0 \ --document-name AWS-StartInteractiveCommand \ --parameters command="sudo -i"

14.Q3: How do you reset the root password of a Linux EC2 instance?

📝 Answer:
The most reliable method to reset the root password for a Linux EC2 instance involves using a temporary rescue instance to access the root volume. This method works even if you have lost your SSH key pair or the instance is completely unreachable.
🔍 Step-by-Step Instructions:

Method 1: Using a Rescue Instance (Universal)
  1. Stop the instance (cannot detach root volume while running)
  2. Detach the root volume (typically /dev/xvda)
  3. Launch a temporary rescue instance in the same Availability Zone
  4. Attach the root volume to the rescue instance as a secondary device (e.g., /dev/sdf)
  5. SSH into the rescue instance and mount the volume
sudo mkdir /mnt/recovery sudo mount /dev/xvdf1 /mnt/recovery
  1. Enter the chroot environment
for i in dev proc sys run; do sudo mount --bind /$i /mnt/recovery/$i; done sudo chroot /mnt/recovery
  1. Reset the password
passwd root # Or for the default user: passwd ec2-user
  1. Exit chroot, unmount, detach, reattach to the original instance, and start it

Method 2: Using EC2 Serial Console (If Supported)
  1. Access the Serial Console
  2. Reboot and interrupt the boot process to access GRUB
  3. Edit the kernel line to boot into single-user mode (add single)
  4. Once in single-user mode, reset the password using passwd

Method 3: Automated Recovery (AWSSupport-ResetAccess)
aws ssm start-automation-execution \ --document-name AWSSupport-ResetAccess \ --parameters "InstanceId=i-1234567890abcdef0"

14.Q4: What is the "Stop/Start" method for instance recovery?

📝 Answer:
The "Stop/Start" method is a recovery technique where you stop an EBS-backed EC2 instance and then start it again. This action typically migrates the instance to new, healthy underlying hardware, resolving host-level issues that a simple reboot cannot fix.
🔍 Detailed Explanation:

Why Stop/Start Works:
AspectRebootStop/Start
Physical HostUnchangedMigrates to new host
IP AddressUnchangedPublic IP changes (unless Elastic IP)
Instance StoreData persistsData is lost
EBS VolumesPersistPersist
When to UseOS-level issuesHost-level issues

When to Use Stop/Start:
ScenarioAction
System Status Check failureStop and start (host-level issue)
Instance stuck/hungStop and start
Hardware degradationStop and start
Instance unreachable due to host issuesStop and start

Step-by-Step Process:
# 1. Stop the instance aws ec2 stop-instances --instance-ids i-1234567890abcdef0 # 2. Wait for stopped state aws ec2 wait instance-stopped --instance-ids i-1234567890abcdef0 # 3. Start the instance aws ec2 start-instances --instance-ids i-1234567890abcdef0

💡 Important Considerations:
  • Public IP changes unless you're using an Elastic IP
  • Instance Store data is lost
  • Private IP remains the same
  • EBS volumes persist

14.Q5: How do you view the System Log of an EC2 instance?

📝 Answer:
The EC2 System Log (console output) provides the boot messages and diagnostic information from your instance. It is accessible even if the instance is unreachable via SSH.
🔍 Detailed Explanation:

Using the AWS Management Console:
  1. Navigate to EC2 Dashboard → Instances
  2. Select your instance
  3. Click Actions → Monitor and troubleshoot → Get System Log

Using the AWS CLI:
# Get the full console output aws ec2 get-console-output --instance-id i-1234567890abcdef0 # Get the latest output (truncated, more readable) aws ec2 get-console-output \ --instance-id i-1234567890abcdef0 \ --latest \ --output text

Using Boto3 (Python):
import boto3 ec2 = boto3.client('ec2') response = ec2.get_console_output( InstanceId='i-1234567890abcdef0', Latest=True ) print(response['Output'])

What to Look For:
InformationWhat It Reveals
Kernel versionOS and kernel details
Kernel panicsBoot failures, stack traces
fstab errorsMount failures
cloud-init logsUser data execution status
SSH host keysFingerprints for verification

14.Q6: What is EC2Rescue and how does it help with troubleshooting?

📝 Answer:
EC2Rescue is an open-source diagnostic and troubleshooting tool that automates the identification and remediation of common issues on EC2 Linux and Windows instances. It can be run manually or automatically via AWS Systems Manager.
🔍 Detailed Explanation:

Key Capabilities:
FeatureDescription
DiagnosticsIdentifies SSH misconfigurations, kernel issues, file system problems
RemediationAutomatically fixes common issues
Linux ModulesOver 100 YAML-based modules containing BASH or Python scripts
Windows SupportRegenerates Windows Administrator passwords via SSM

Common Use Cases:
Use CaseDescription
Diagnosing SSH failuresIdentifies and fixes OpenSSH configuration issues
Gathering system logsCollects syslog, package manager logs, and boot logs
Diagnosing kernel parametersIdentifies problematic kernel parameters
Repairing boot issuesFixes fstab entries, kernel panics, and GRUB misconfigurations
Windows password resetRegenerates Windows Administrator passwords via SSM

Usage Methods:
MethodDescription
ManualRun directly on a running instance: sudo ./ec2rl run
Rescue InstanceRun on a detached root volume mounted to a helper instance
Systems Manager AutomationUse AWSSupport-ExecuteEC2Rescue runbook

Running EC2Rescue Manually:
# Download and install wget https://s3.amazonaws.com/ec2rescuelinux/ec2rl.tgz tar -xzf ec2rl.tgz # Run all modules sudo ./ec2rl run # Run specific module sudo ./ec2rl run --only-modules=dig --domain=amazon.com # Run with remediation sudo ./ec2rl run --remediate # View results cat /var/tmp/ec2rl/{timestamp}/mod_out/run/dig.log

📝 Answer:
The Instance Status Check monitors the operating system and software configuration of your EC2 instance. When it fails, it indicates a problem with your OS or application that requires your intervention.

14.Q8: How do you recover an instance with a corrupted kernel?

📝 Answer:
Recovering an instance with a corrupted kernel involves using a rescue instance (or EC2 Serial Console) to reinstall the kernel and regenerate the bootloader configuration.
🔍 Step-by-Step Instructions:

Method 1: Using a Rescue Instance (Universal)
  1. Stop the instance, detach its root volume, and attach it to a rescue instance
  2. Mount the volume and enter the chroot environment
sudo mkdir /mnt/recovery sudo mount /dev/xvdf1 /mnt/recovery for i in dev proc sys run; do sudo mount --bind /$i /mnt/recovery/$i; done sudo chroot /mnt/recovery
  1. Reinstall the kernel and regenerate boot files

RPM-based systems (Amazon Linux, RHEL, CentOS):
# Reinstall the kernel package yum reinstall kernel -y # Regenerate initramfs dracut -f -vvvvv # Rebuild GRUB configuration grub2-mkconfig -o /boot/grub2/grub.cfg

Debian-based systems (Ubuntu):
# Reinstall the kernel apt install --reinstall linux-image-$(uname -r) # Regenerate initramfs update-initramfs -u -vvvvv # Rebuild GRUB configuration update-grub

Method 2: Using EC2 Serial Console (If Supported)
  1. Access the Serial Console and interrupt the boot process
  2. From the GRUB menu, select a previous working kernel (if available)
  3. Once booted, reinstall the kernel and regenerate GRUB
yum reinstall kernel -y dracut -f grub2-mkconfig -o /boot/grub2/grub.cfg

💡 If Recovery Fails: Create a new AMI from the repaired volume and launch a fresh instance.

Key Takeaways

  • SSH troubleshooting follows a systematic flow: Network → Instance Health → SSH Config → Alternative Access → Advanced Recovery.

  • EC2 Serial Console provides BIOS-level access before the OS boots — essential for kernel panics, bad fstab, and lost passwords.

  • Reset root password using a rescue instance — the universal method that works even with lost SSH keys.

  • Stop/Start migrates your instance to new hardware — use for System Status Check failures. Reboot keeps the same host — use for transient OS issues.

  • EC2 System Log (console output) is accessible even when SSH is broken — always check it first for boot failures.

  • EC2Rescue is an open-source automated recovery tool with over 100 diagnostic modules — run it manually or via SSM Automation.

  • Instance Status Check failures indicate OS-level issues (bad fstab, kernel panic, corrupted filesystem) — you are responsible for fixing them.

  • System Status Check failures indicate host-level issues (hardware, power, network) — Stop/Start resolves them.

  • Corrupted kernel recovery involves reinstalling the kernel and regenerating GRUB via rescue instance — use yum reinstall kernel or apt install --reinstall.

  • AWSSupport-ResetAccess is a Systems Manager automation runbook that can automate password resets.
