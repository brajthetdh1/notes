Rescue Instance Method

📖 Complete Theory: The Rescue Instance Method

The rescue instance method is the universal approach for recovering an EC2 instance that is completely unreachable. The core idea is simple: since EBS volumes are persistent, you can detach the root volume from a failed instance, attach it to a healthy "rescue" instance, fix the problem, and then reattach it.

This method works for any issue that prevents the instance from booting, including:
  • Corrupted file systems
  • Misconfigured network settings
  • Broken SSH configurations
  • Bad /etc/fstab entries
  • Kernel panics

P12.1 Stop Main Instance

Simulate OS Corruption
📖 Theory: Simulating a Failure
To simulate a real-world failure scenario, we will stop the instance. In a real disaster, the instance might be unreachable due to a corrupted kernel, bad fstab entry, or network misconfiguration. Stopping the instance is the first step in any recovery process because you cannot detach the root volume of a running instance.

Step 1: Get the Instance ID
INSTANCE_ID=$(aws ec2 describe-instances \ --filters "Name=tag:Name,Values=Golden-AMI-Builder" \ --query 'Reservations[0].Instances[0].InstanceId' \ --output text) echo "Instance ID: $INSTANCE_ID"

Step 2: Stop the Instance
aws ec2 stop-instances --instance-ids $INSTANCE_ID aws ec2 wait instance-stopped --instance-ids $INSTANCE_ID

✅ Verification Checklist:
□ Instance state is stopped
□ Instance is no longer running
⏹️ P12.1 🔄 stop instance ⚠️ simulate failure
🔌

P12.2 Detach Root EBS Volume

📖 Theory: Detaching the Root Volume
Once the instance is stopped, you can detach its root EBS volume. This volume contains the operating system and all data. Detaching it allows you to attach it to another instance for inspection and repair.

Step 1: Get the Root Volume ID
ROOT_VOLUME_ID=$(aws ec2 describe-instances \ --instance-ids $INSTANCE_ID \ --query 'Reservations[0].Instances[0].BlockDeviceMappings[?DeviceName==`/dev/xvda`].Ebs.VolumeId' \ --output text) echo "Root Volume ID: $ROOT_VOLUME_ID"

Step 2: Detach the Root Volume
aws ec2 detach-volume --volume-id $ROOT_VOLUME_ID aws ec2 wait volume-available --volume-ids $ROOT_VOLUME_ID

✅ Verification Checklist:
□ Volume state is available
□ Volume is no longer attached to any instance
🔌 P12.2 📊 detach volume 💾 root volume
🆘

P12.3 Launch Rescue Instance

Same Availability Zone
📖 Theory: The Rescue Instance
The rescue instance serves as a temporary "workspace" to repair the corrupted volume. It must be in the same Availability Zone as the corrupted volume, as EBS volumes can only be attached to instances in the same Availability Zone.

Step 1: Get the Availability Zone
AZ=$(aws ec2 describe-volumes \ --volume-ids $ROOT_VOLUME_ID \ --query 'Volumes[0].AvailabilityZone' \ --output text) echo "Availability Zone: $AZ"

Step 2: Get VPC and Subnet
VPC_ID=$(aws ec2 describe-instances \ --instance-ids $INSTANCE_ID \ --query 'Reservations[0].Instances[0].VpcId' \ --output text) SUBNET_ID=$(aws ec2 describe-instances \ --instance-ids $INSTANCE_ID \ --query 'Reservations[0].Instances[0].SubnetId' \ --output text)

Step 3: Create Security Group
SG_RESCUE=$(aws ec2 create-security-group \ --group-name rescue-sg \ --description "Security group for rescue instance" \ --vpc-id $VPC_ID \ --query 'GroupId' --output text) aws ec2 authorize-security-group-ingress \ --group-id $SG_RESCUE \ --protocol tcp --port 22 --cidr 0.0.0.0/0

Step 4: Launch the Rescue Instance
AMI_ID=$(aws ssm get-parameters \ --names /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 \ --query 'Parameters[0].Value' --output text) RESCUE_INSTANCE_ID=$(aws ec2 run-instances \ --image-id $AMI_ID \ --instance-type t3.micro \ --subnet-id $SUBNET_ID \ --security-group-ids $SG_RESCUE \ --key-name MyKeyPair \ --associate-public-ip-address \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=Rescue-Instance}]' \ --query 'Instances[0].InstanceId' --output text) aws ec2 wait instance-running --instance-ids $RESCUE_INSTANCE_ID RESCUE_PUBLIC_IP=$(aws ec2 describe-instances \ --instance-ids $RESCUE_INSTANCE_ID \ --query 'Reservations[0].Instances[0].PublicIpAddress' \ --output text)

✅ Verification Checklist:
□ Rescue instance is running
□ Same AZ as the root volume
□ SSH access available
🆘 P12.3 🖥️ rescue instance 🌐 same AZ
🔗

P12.4 Attach Corrupted Volume

as Secondary Device (/dev/sdf)
📖 Theory: Attaching the Volume
Attaching the corrupted volume as a secondary device allows the rescue instance to access its file system. The device name /dev/sdf is a standard convention for secondary volumes on Nitro instances.

Step 1: Attach the Volume
aws ec2 attach-volume \ --volume-id $ROOT_VOLUME_ID \ --instance-id $RESCUE_INSTANCE_ID \ --device /dev/sdf

✅ Verification Checklist:
□ Volume attached to rescue instance
□ Volume state is in-use
🔗 P12.4 📊 attach volume 💾 /dev/sdf
🔧

P12.5 SSH into Rescue Instance

Mount the Volume
📖 Theory: Mounting the Volume
Once the volume is attached, you need to mount it to access its file system. The root partition is typically the first partition (/dev/xvdf1), but this can vary.

Step 1: SSH into the Rescue Instance
ssh -i MyKeyPair.pem ec2-user@$RESCUE_PUBLIC_IP

Step 2: Identify the Attached Device
sudo lsblk # Expected: xvdf 202:80 0 30G 0 disk # └─xvdf1 202:81 0 30G 0 part ← root volume

Step 3: Mount the Root Partition
sudo mkdir -p /mnt/rescue sudo mount /dev/xvdf1 /mnt/rescue df -h /mnt/rescue

✅ Verification Checklist:
□ Device identified correctly
□ Volume mounted to /mnt/rescue
□ File system visible (etc, home, var)
🔧 P12.5 📁 mount volume 🖥️ SSH access
🛠️

P12.6 Fix the Issue

fstab, Password, fsck, SSH
📖 Theory: The Fix
Once the volume is mounted, you can fix the underlying issue. This example covers two common fixes: reverting a corrupted fstab entry and resetting the root password.

Step 1: Fix Corrupted fstab (Scenario A)
sudo vi /mnt/rescue/etc/fstab # Comment out or fix the problematic line # # UUID=wrong-uuid /data ext4 defaults 0 0

Step 2: Reset Root Password (Scenario B)
for i in dev proc sys run; do sudo mount --bind /$i /mnt/rescue/$i; done sudo chroot /mnt/rescue passwd ec2-user # Or: passwd root exit for i in dev proc sys run; do sudo umount /mnt/rescue/$i; done

Step 3: (Optional) Repair the File System
sudo umount /mnt/rescue sudo fsck -y /dev/xvdf1 sudo mount /dev/xvdf1 /mnt/rescue

Step 4: (Optional) Fix SSH Configuration
sudo vi /mnt/rescue/etc/ssh/sshd_config # Ensure PasswordAuthentication is set correctly

✅ Verification Checklist:
□ fstab fixed (if applicable)
□ Password reset (if applicable)
□ File system repaired (if applicable)
🛠️ P12.6 📋 fix issue 🔄 chroot

P12.7 Unmount and Detach

📖 Theory: Cleanup
After fixing the issue, you must unmount the volume and detach it from the rescue instance. Failing to unmount properly can lead to data loss or file system corruption.

Step 1: Unmount the Volume
sudo umount /mnt/rescue # If "target is busy": sudo lsof /mnt/rescue sudo umount -f /mnt/rescue

Step 2: Detach from Rescue Instance
ATTACHMENT_ID=$(aws ec2 describe-volumes \ --volume-ids $ROOT_VOLUME_ID \ --query 'Volumes[0].Attachments[0].AttachmentId' \ --output text) aws ec2 detach-volume --volume-id $ROOT_VOLUME_ID aws ec2 wait volume-available --volume-ids $ROOT_VOLUME_ID

✅ Verification Checklist:
□ Volume unmounted from rescue instance
□ Volume detached from rescue instance
□ Volume state is available
🧹 P12.7 📊 unmount 🔌 detach
🔄

P12.8 Reattach as /dev/xvda

Root Device to Original Instance
📖 Theory: Restoring the Root Volume
After fixing the issue, you must reattach the volume to the original instance as the root device. The device name must be /dev/xvda (or the original root device name) so the instance can boot from it.

Step 1: Reattach the Volume
aws ec2 attach-volume \ --volume-id $ROOT_VOLUME_ID \ --instance-id $INSTANCE_ID \ --device /dev/xvda

✅ Verification Checklist:
□ Volume attached to original instance
□ Volume device is /dev/xvda
□ Volume state is in-use
🔄 P12.8 📊 reattach 💾 root device
✅

P12.9 Start and Verify

📖 Theory: Verification
The final step is to start the instance and verify that the fix was successful. This includes checking the instance status, connecting via SSH, and confirming that the application is running as expected.

Step 1: Start the Instance
aws ec2 start-instances --instance-ids $INSTANCE_ID aws ec2 wait instance-running --instance-ids $INSTANCE_ID

Step 2: Check Instance Status
aws ec2 describe-instance-status \ --instance-ids $INSTANCE_ID \ --query 'InstanceStatuses[0].[InstanceStatus.Status,SystemStatus.Status]' \ --output table # Expected: | ok | ok |

Step 3: Connect and Verify
PUBLIC_IP=$(aws ec2 describe-instances \ --instance-ids $INSTANCE_ID \ --query 'Reservations[0].Instances[0].PublicIpAddress' \ --output text) ssh -i MyKeyPair.pem ec2-user@$PUBLIC_IP cat /etc/fstab # Check fstab sudo journalctl -p err -b # Check logs

Step 5: Clean Up Rescue Instance
aws ec2 terminate-instances --instance-ids $RESCUE_INSTANCE_ID aws ec2 delete-security-group --group-id $SG_RESCUE

✅ Verification Checklist:
□ Original instance starts successfully
□ Status checks pass (2/2)
□ SSH connection works
□ The issue is resolved
✅ P12.9 📊 verify 🔄 recovery success

Key Takeaways

  • The rescue instance method is the most reliable way to recover an unreachable EC2 instance. It works for any issue that prevents the OS from booting.

  • Stop the instance before detaching the root volume. You cannot detach the root volume of a running instance.

  • The rescue instance must be in the same Availability Zone as the corrupted volume. EBS volumes are zonal resources.

  • Use chroot to operate inside the broken file system. This allows you to fix configurations, reset passwords, and repair file systems.

  • Always unmount the volume before detaching it. Failing to do so can lead to data loss or file system corruption.

  • The public IP will change after a stop/start cycle. Make sure you have the new IP to connect.

  • Terminate the rescue instance after recovery. It's only needed temporarily and will incur charges if left running.

  • lsblk is used to identify attached devices and partitions.

  • fsck repairs corrupted file systems — use -y to auto-confirm fixes.

  • Always verify the instance passes both status checks (2/2) after recovery.
