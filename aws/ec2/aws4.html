8.4 Placement Groups

A placement group is a logical construct that allows you to control the physical placement of your EC2 instances relative to each other within an Availability Zone. By influencing how instances are distributed across the underlying hardware, placement groups enable you to optimize for specific application needs, such as low-latency network performance, high throughput, or fault isolation.

Placement groups are optional; if you don't launch your instances into one, EC2 attempts to spread them across underlying hardware to minimize correlated failures.

8.4.1 Cluster Placement Group

Low Latency, High Throughput
📖 Complete Theory
A cluster placement group packs instances close together inside a single Availability Zone, placing them in the same high-bisection bandwidth segment of the network. This enables workloads to achieve the low-latency network performance and high throughput necessary for tightly-coupled node-to-node communication.

Performance Benefits:
  • Up to 10 Gbps for single-flow traffic (vs. 5 Gbps outside the group)
  • Lower latency between instances
  • Enhanced networking support (ENA)

Key Characteristics:
📍 Single AZ
All instances in same Availability Zone
🚫 Not Supported
T-series (burstable), M7i-flex, Mac1
🚀 Launch Best Practice
Launch all instances in a single request, use same instance type
🔒 Capacity
Use On-Demand Capacity Reservation to guarantee capacity

When to Use:
  • High-Performance Computing (HPC)
  • Tightly-coupled Big Data workloads
  • Database clusters requiring minimal latency
  • Financial trading systems
Creating a Cluster Placement Group (CLI):
# Create the placement group aws ec2 create-placement-group \ --group-name my-hpc-cluster \ --strategy cluster # Launch instances into the group aws ec2 run-instances \ --image-id ami-0abcdef1234567890 \ --instance-type c5n.18xlarge \ --placement GroupName=my-hpc-cluster \ --key-name my-key \ --count 4

⚠️ Important Limitation: Traffic to the internet or over AWS Direct Connect is limited to 5 Gbps for instances in a cluster placement group.

8.4.2 Partition Placement Group

Hardware Isolation for Large Distributed Systems
📖 Complete Theory
A partition placement group divides your instances into logical groups called partitions. Each partition is placed on its own set of racks, where each rack has independent network and power sources. This ensures that instances in one partition do not share the underlying hardware with instances in other partitions.

8.4.3 Spread Placement Group

Maximum Fault Tolerance for Critical Workloads
📖 Complete Theory
A spread placement group places a small group of instances across distinct underlying hardware to reduce the risk of simultaneous failures. This strategy provides the highest level of fault tolerance for critical components.

Key Characteristics:
🔒 Hardware Isolation
Each instance on a distinct physical rack with independent power/network
📊 Instance Limit
Maximum of 7 running instances per AZ per group
🌍 Multi-AZ Support
Can span multiple Availability Zones (21 instances in 3 AZs)
💰 No Cost
No additional charge for using spread placement groups

When to Use:
  • Database clusters (MongoDB, Cassandra, Redis) — replicas on different hardware
  • Quorum-based systems (ZooKeeper, etcd) — prevent quorum loss
  • Active-active failover pairs
  • Critical application tiers (control-plane nodes, load balancers)
  • Payment processing systems
Creating a Spread Placement Group (CLI):
# Create spread placement group aws ec2 create-placement-group \ --group-name critical-db-spread \ --strategy spread \ --spread-level rack # Launch instances aws ec2 run-instances \ --image-id ami-0abcdef1234567890 \ --instance-type r5.2xlarge \ --count 1 \ --placement GroupName=critical-db-spread \ --key-name my-key

⚠️ The 7-Instance Limit: If you attempt to launch an eighth instance in the same AZ and same spread group, the launch will fail.

Workarounds:
🌍 Use multiple AZs
3 AZs = up to 21 instances
📊 Multiple groups
Separate groups for different tiers
🧩 Partition groups
For larger systems needing isolation

Key Takeaways

  • Cluster — Low latency, high throughput within a single AZ. Up to 10 Gbps single-flow traffic. Best for HPC and tightly coupled workloads.

  • Partition — Rack-level isolation for large distributed systems. 7 partitions per AZ. Best for Hadoop, Cassandra, and Kafka.

  • Spread — Maximum fault tolerance for critical small clusters. 7 instances per AZ. Best for database clusters and quorum systems.

  • One group per instance — An instance can only belong to one placement group at a time.

  • No modifications — You cannot change an instance's placement group after launch.

  • Capacity constraints — Cluster groups can experience "insufficient capacity" errors if adding instances later.

  • No cost — Placement groups are free to use.

Review Questions

Q1: What are the three main placement strategies in AWS and what is each used for?
Answer: The three strategies are Cluster (for low latency and high throughput within a single AZ, ideal for HPC), Partition (for fault isolation in large distributed systems like HDFS and Kafka), and Spread (for maximum fault tolerance for a small number of critical instances).
Q2: What is the key limitation of a cluster placement group?
Answer: A cluster placement group cannot span multiple Availability Zones; all instances must be in the same AZ. Additionally, you may receive capacity errors if you try to add instances later, so it's best to launch all required instances at once.
Q3: What is the maximum number of running instances in a spread placement group?
Answer: A spread placement group supports a maximum of 7 running instances per Availability Zone. If your Region has three AZs, you could have up to 21 instances in a single spread group.
Q4: Why would you use a partition placement group instead of a spread placement group?
Answer: Partition placement groups are designed for large-scale, replicated workloads (like HDFS or Kafka) that require fault isolation for many instances across up to 7 partitions per AZ. Spread placement groups are limited to only 7 instances per AZ and are better suited for a small number of critical components.
Q5: What are the workarounds for the 7-instance-per-AZ limit in a spread placement group?
Answer: You can either:
  • Use multiple AZs — 3 AZs = up to 21 instances
  • Create multiple spread groups — separate groups for different tiers
  • Switch to partition placement groups — for larger systems needing hardware isolation
