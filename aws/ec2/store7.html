EFS Architecture

📖 Complete Theory: EFS Architecture

Amazon EFS is a regional service that stores data redundantly across multiple Availability Zones (AZs) by default. To access the file system, you create mount targets in the VPC's subnets. Each mount target provides an NFS endpoint that allows EC2 instances in that subnet to connect to the EFS file system.

Key Architecture Points:
  • EFS is regional — data is replicated across AZs by default
  • Mount targets provide NFS endpoints in each subnet
  • Instances in different AZs can access the same EFS file system
  • NFS protocol enables shared, concurrent access

P9.3.1 Create EFS Filesystem

With Mount Targets in Multiple AZs
📖 Theory: EFS File System Creation
EFS is a regional service. By default, a Regional EFS file system is designed to redundantly store data across multiple Availability Zones (AZs) within a Region, protecting it from a single AZ failure.

Step 1: Create Security Groups
# Security group for EFS mount targets SG_EFS=$(aws ec2 create-security-group \ --group-name efs-sg \ --description "Security group for EFS mount targets" \ --vpc-id $VPC_ID \ --query 'GroupId' --output text) # Security group for EC2 instances SG_INSTANCE=$(aws ec2 create-security-group \ --group-name instance-sg \ --description "Security group for EC2 instances" \ --vpc-id $VPC_ID \ --query 'GroupId' --output text) # Allow SSH aws ec2 authorize-security-group-ingress --group-id $SG_INSTANCE --protocol tcp --port 22 --cidr 0.0.0.0/0 # Allow NFS access to EFS aws ec2 authorize-security-group-ingress \ --group-id $SG_EFS \ --protocol tcp --port 2049 \ --source-group $SG_INSTANCE

Step 2: Create the EFS File System
FS_ID=$(aws efs create-file-system \ --creation-token "shared-data-efs-$(date +%s)" \ --performance-mode generalPurpose \ --throughput-mode elastic \ --tags Key=Name,Value=shared-data-efs \ --query 'FileSystemId' \ --output text) echo "EFS File System ID: $FS_ID" aws efs wait file-system-available --file-system-id $FS_ID

Step 3: Create Mount Targets
SUBNET_A=$(aws ec2 describe-subnets --filters "Name=tag:Name,Values=public-subnet-a" --query 'Subnets[0].SubnetId' --output text) SUBNET_B=$(aws ec2 describe-subnets --filters "Name=tag:Name,Values=public-subnet-b" --query 'Subnets[0].SubnetId' --output text) aws efs create-mount-target --file-system-id $FS_ID --subnet-id $SUBNET_A --security-groups $SG_EFS aws efs create-mount-target --file-system-id $FS_ID --subnet-id $SUBNET_B --security-groups $SG_EFS aws efs wait mount-target-available --file-system-id $FS_ID

✅ Verification Checklist:
□ EFS file system created
□ Mount targets created in two AZs
□ Security groups configured for NFS access

P9.3.2 Mount EFS on Two EC2 Instances

At /shared
📖 Theory: Mounting EFS
To mount an EFS file system, your EC2 instance must have the NFS client installed. You can use either the standard NFS mount command or the EFS mount helper (amazon-efs-utils). The EFS mount helper simplifies the mounting process and enables TLS encryption for data in transit.

Step 1: Launch Two EC2 Instances
AMI_ID=$(aws ssm get-parameters --names /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --query 'Parameters[0].Value' --output text) INSTANCE_A=$(aws ec2 run-instances \ --image-id $AMI_ID \ --instance-type t3.micro \ --subnet-id $SUBNET_A \ --security-group-ids $SG_INSTANCE \ --key-name MyKeyPair \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=EFS-Instance-A}]' \ --query 'Instances[0].InstanceId' --output text) INSTANCE_B=$(aws ec2 run-instances \ --image-id $AMI_ID \ --instance-type t3.micro \ --subnet-id $SUBNET_B \ --security-group-ids $SG_INSTANCE \ --key-name MyKeyPair \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=EFS-Instance-B}]' \ --query 'Instances[0].InstanceId' --output text) aws ec2 wait instance-running --instance-ids $INSTANCE_A $INSTANCE_B

Step 2: Install the EFS Mount Helper
# On each instance sudo dnf install -y amazon-efs-utils which mount.efs

Step 3: Mount the EFS File System
# On each instance sudo mkdir -p /shared sudo mount -t efs -o tls $FS_ID:/ /shared df -h /shared

Step 4: Configure Auto-Mount
echo "$FS_ID:/ /shared efs _netdev,noresvport,tls 0 0" | sudo tee -a /etc/fstab

💡 Key Options Explained:
  • _netdev — Mounts after network is available
  • noresvport — Survives network reconnections
  • tls — Encrypts data in transit

✅ Verification Checklist:
□ amazon-efs-utils installed on both instances
□ EFS mounted at /shared on both instances
□ df -h /shared shows the EFS file system
□ /etc/fstab configured for auto-mount
🔗 P9.3.2 📁 mount EFS 🔒 TLS encryption

P9.3.3 Write/Read Across Instances

📖 Theory: Shared Storage Verification
EFS is designed to be a shared file system. When you write a file from one instance, it should be visible from any other instance that has the same file system mounted. This demonstrates the core value of EFS: shared, scalable, and accessible across multiple compute nodes.

Step 1: Write a File from Instance A
# On Instance A cd /shared echo "Hello from Instance A at $(date)" | sudo tee test-file.txt sudo dd if=/dev/urandom of=random-file.bin bs=1M count=10

Step 2: Read the File from Instance B
# On Instance B cd /shared ls -la cat test-file.txt ls -lh random-file.bin

💡 Expected Output on Instance B:
-rw-r--r-- 1 root root 45 Aug 3 10:30 test-file.txt -rw-r--r-- 1 root root 10M Aug 3 10:31 random-file.bin Hello from Instance A at Tue Aug 3 10:30:15 UTC 2026

Step 3: Write from Instance B, Verify from Instance A
# On Instance B echo "Hello from Instance B at $(date)" | sudo tee from-instance-b.txt # On Instance A ls -la /shared/ cat /shared/from-instance-b.txt

✅ Verification Checklist:
□ File written from Instance A is readable on Instance B
□ File written from Instance B is readable on Instance A
□ EFS provides shared, consistent storage across instances
✅ P9.3.3 📊 shared storage 🔄 verification

P9.3.4 Set Up EFS Lifecycle Policy

Move to IA after 30 days
📖 Theory: EFS Lifecycle Policies
EFS Lifecycle Management automates tiering between storage classes. The default recommended configuration is to move files to EFS Infrequent Access (IA) after 30 days of no access. This transition is based on the last time the file was accessed while in the Standard storage class, and metadata operations like ls do not count as file access.

Step 1: Create a Lifecycle Configuration
aws efs put-lifecycle-configuration \ --file-system-id $FS_ID \ --lifecycle-policies '[ {"TransitionToIA": "AFTER_30_DAYS"} ]'

Step 2: Verify the Lifecycle Configuration
aws efs describe-lifecycle-configuration --file-system-id $FS_ID

💡 Expected Output:
{ "LifecyclePolicies": [ { "TransitionToIA": "AFTER_30_DAYS" } ] }

Step 3: (Optional) Add Archive Lifecycle
aws efs put-lifecycle-configuration \ --file-system-id $FS_ID \ --lifecycle-policies '[ {"TransitionToIA": "AFTER_30_DAYS"}, {"TransitionToArchive": "AFTER_90_DAYS"} ]'

Step 4: (Optional) Enable Intelligent-Tiering
aws efs put-lifecycle-configuration \ --file-system-id $FS_ID \ --lifecycle-policies '[ {"TransitionToIA": "AFTER_30_DAYS"}, {"TransitionToArchive": "AFTER_90_DAYS"}, {"TransitionToPrimaryStorageClass": "AFTER_1_ACCESS"} ]'

✅ Verification Checklist:
□ Lifecycle policy configured to move files to IA after 30 days
□ Lifecycle policy verified using describe-lifecycle-configuration

Key Takeaways

  • EFS is a regional service that can be mounted by instances across multiple Availability Zones.

  • Mount targets provide NFS endpoints for each Availability Zone.

  • Security groups must allow NFS traffic (port 2049) for EFS mounting.

  • amazon-efs-utils simplifies EFS mounting and enables TLS encryption for data in transit.

  • Files written from one instance are immediately visible from other instances with the same EFS mount.

  • Lifecycle policies automatically tier data to lower-cost storage classes (IA, Archive) based on access patterns.

  • _netdev and noresvport in fstab ensure reliable auto-mounting.

  • dd can be used to create large test files for performance testing.

  • Intelligent-Tiering moves files back to Standard when accessed in IA/Archive.

  • EFS vs EBS: EFS is shared, multi-instance storage; EBS is single-instance block storage.
🧠 takeaways 📁 EFS 📊 shared storage

💡 Remember: You must delete all mount targets before you can delete an EFS file system. Also ensure the file system is empty (or force delete) before deletion.
