P6.1 Create Custom VPC

Public/Private Subnets (2 AZs)
📖 Theory: Why a Custom VPC?
A custom VPC gives you full control over your network architecture, including CIDR blocks, subnet configurations, and routing tables. For production workloads, you should isolate your application servers in private subnets while keeping load balancers in public subnets.

Step 1: Create the VPC
# Create VPC with CIDR 10.0.0.0/16 aws ec2 create-vpc \ --cidr-block 10.0.0.0/16 \ --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=production-vpc}]' # Note the VPC ID from the output VPC_ID=$(aws ec2 describe-vpcs --filters "Name=tag:Name,Values=production-vpc" --query 'Vpcs[0].VpcId' --output text) echo "VPC ID: $VPC_ID"
Step 2: Create Subnets (2 Public, 2 Private)
# Get Availability Zones AZS=($(aws ec2 describe-availability-zones --query 'AvailabilityZones[0:2].[ZoneName]' --output text)) # Public Subnet A (AZ-a) SUBNET_PUB_A=$(aws ec2 create-subnet \ --vpc-id $VPC_ID \ --cidr-block 10.0.1.0/24 \ --availability-zone ${AZS[0]} \ --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=public-subnet-a}]' \ --query 'Subnet.SubnetId' --output text) # Private Subnet A (AZ-a) SUBNET_PRIV_A=$(aws ec2 create-subnet \ --vpc-id $VPC_ID \ --cidr-block 10.0.3.0/24 \ --availability-zone ${AZS[0]} \ --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=private-subnet-a}]' \ --query 'Subnet.SubnetId' --output text)
Step 3: Enable Auto-Assign Public IP
aws ec2 modify-subnet-attribute \ --subnet-id $SUBNET_PUB_A \ --map-public-ip-on-launch
Step 4: Create and Attach Internet Gateway
IGW_ID=$(aws ec2 create-internet-gateway \ --tag-specifications 'ResourceType=internet-gateway,Tags=[{Key=Name,Value=production-igw}]' \ --query 'InternetGateway.InternetGatewayId' --output text) aws ec2 attach-internet-gateway \ --internet-gateway-id $IGW_ID \ --vpc-id $VPC_ID
Step 5: Create Route Tables
# Public Route Table RT_PUB=$(aws ec2 create-route-table --vpc-id $VPC_ID --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=public-rt}]' --query 'RouteTable.RouteTableId' --output text) aws ec2 create-route --route-table-id $RT_PUB --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW_ID aws ec2 associate-route-table --route-table-id $RT_PUB --subnet-id $SUBNET_PUB_A
✅ Verification Checklist:
  • □ VPC created with CIDR 10.0.0.0/16
  • □ 4 subnets created (2 public, 2 private across 2 AZs)
  • □ Internet Gateway created and attached
  • □ Public route table has route to IGW
🌐 VPC 📊 10.0.0.0/16 🔀 4 subnets

P6.2 Set Up NAT Gateway

📖 Theory: Why NAT Gateway?
NAT Gateway allows instances in private subnets to access the internet (for updates, downloads) while preventing inbound connections from the internet. This is critical for security.

Step 1: Allocate Elastic IP for NAT Gateway
EIP_ALLOC=$(aws ec2 allocate-address \ --domain vpc \ --tag-specifications 'ResourceType=elastic-ip,Tags=[{Key=Name,Value=nat-eip}]' \ --query 'AllocationId' --output text)
Step 2: Create NAT Gateway in Public Subnet A
NAT_GW=$(aws ec2 create-nat-gateway \ --subnet-id $SUBNET_PUB_A \ --allocation-id $EIP_ALLOC \ --tag-specifications 'ResourceType=natgateway,Tags=[{Key=Name,Value=production-nat}]' \ --query 'NatGateway.NatGatewayId' --output text) # Wait for NAT Gateway to become available aws ec2 wait nat-gateway-available --nat-gateway-ids $NAT_GW
Step 3: Add Route to Private Route Table
aws ec2 create-route \ --route-table-id $RT_PRIV \ --destination-cidr-block 0.0.0.0/0 \ --nat-gateway-id $NAT_GW
✅ Verification Checklist:
  • □ Elastic IP allocated for NAT Gateway
  • □ NAT Gateway created in public subnet A
  • □ Private route table has route to NAT Gateway
🔒 NAT Gateway 🌐 private subnet 🔐 security

P6.3 Create Launch Template

Custom AMI + User Data
📖 Theory: Why a Launch Template?
A Launch Template defines the configuration for EC2 instances launched by the Auto Scaling Group. It includes the AMI, instance type, security groups, IAM role, and User Data scripts.

Step 1: Create Security Group for Web Servers
SG_WEB=$(aws ec2 create-security-group \ --group-name web-server-sg \ --description "Security group for web servers" \ --vpc-id $VPC_ID \ --tag-specifications 'ResourceType=security-group,Tags=[{Key=Name,Value=web-server-sg}]' \ --query 'GroupId' --output text) aws ec2 authorize-security-group-ingress \ --group-id $SG_WEB \ --protocol tcp \ --port 80 \ --source-group $SG_WEB
Step 2: Create IAM Role for EC2 Instances
aws iam create-role --role-name web-server-role --assume-role-policy-document file://trust-policy.json aws iam attach-role-policy --role-name web-server-role --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore aws iam create-instance-profile --instance-profile-name web-server-instance-profile aws iam add-role-to-instance-profile --instance-profile-name web-server-instance-profile --role-name web-server-role
Step 3: Create the Launch Template
aws ec2 create-launch-template \ --launch-template-name web-app-template \ --version-description "v1.0 - Production web server" \ --launch-template-data '{ "ImageId": "'"$AMI_ID"'", "InstanceType": "t3.micro", "KeyName": "MyKeyPair", "SecurityGroupIds": ["'"$SG_WEB"'"], "IamInstanceProfile": {"Name": "web-server-instance-profile"}, "UserData": "'"$(base64 -w0 <<'EOF' #!/bin/bash TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600" 2>/dev/null) INSTANCE_ID=$(curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id 2>/dev/null) AZ=$(curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/availability-zone 2>/dev/null) cat > /var/www/html/index.html <✅ Auto Scaling Demo

Instance ID: $INSTANCE_ID

Availability Zone: $AZ

HTML sudo systemctl restart httpd EOF )"' }'
✅ Verification Checklist:
  • □ Security group created for web servers
  • □ IAM role and instance profile created
  • □ Launch Template created with custom AMI and User Data
📋 Launch Template 🖥️ t3.micro 📦 User Data

P6.4 Create Application Load Balancer (ALB)

Public Subnets
📖 Theory: Why an ALB?
An Application Load Balancer distributes incoming HTTP/HTTPS traffic across multiple targets in different Availability Zones, improving availability and fault tolerance.

Step 1: Create Security Group for ALB
SG_ALB=$(aws ec2 create-security-group \ --group-name alb-sg \ --description "Security group for ALB" \ --vpc-id $VPC_ID \ --tag-specifications 'ResourceType=security-group,Tags=[{Key=Name,Value=alb-sg}]' \ --query 'GroupId' --output text) aws ec2 authorize-security-group-ingress \ --group-id $SG_ALB \ --protocol tcp \ --port 80 \ --cidr 0.0.0.0/0 aws ec2 authorize-security-group-ingress \ --group-id $SG_WEB \ --protocol tcp \ --port 80 \ --source-group $SG_ALB
Step 2: Create Target Group
TG_ARN=$(aws elbv2 create-target-group \ --name webapp-tg \ --protocol HTTP \ --port 80 \ --vpc-id $VPC_ID \ --health-check-path /index.html \ --query 'TargetGroups[0].TargetGroupArn' --output text)
Step 3: Create ALB
ALB_ARN=$(aws elbv2 create-load-balancer \ --name webapp-alb \ --type application \ --scheme internet-facing \ --subnets $SUBNET_PUB_A $SUBNET_PUB_B \ --security-groups $SG_ALB \ --query 'LoadBalancers[0].LoadBalancerArn' --output text) aws elbv2 wait load-balancer-available --load-balancer-arns $ALB_ARN
Step 4: Create Listener
LISTENER_ARN=$(aws elbv2 create-listener \ --load-balancer-arn $ALB_ARN \ --protocol HTTP \ --port 80 \ --default-actions Type=forward,TargetGroupArn=$TG_ARN \ --query 'Listeners[0].ListenerArn' --output text) ALB_DNS=$(aws elbv2 describe-load-balancers --load-balancer-arns $ALB_ARN --query 'LoadBalancers[0].DNSName' --output text) echo "ALB DNS Name: $ALB_DNS"
✅ Verification Checklist:
  • □ ALB security group allows HTTP from anywhere
  • □ Web server SG allows HTTP from ALB SG
  • □ Target Group created with health check path
  • □ ALB created in public subnets
⚖️ ALB 🌐 internet-facing 🔀 target group
🔄

P6.5 Create Auto Scaling Group

min=2, desired=2, max=5
📖 Theory: Auto Scaling Group Basics
An Auto Scaling Group manages a collection of EC2 instances, maintaining the desired number of healthy instances and automatically replacing any that fail.

Step 1: Create the ASG
ASG_NAME="web-app-asg" aws autoscaling create-auto-scaling-group \ --auto-scaling-group-name $ASG_NAME \ --launch-template LaunchTemplateName=web-app-template,Version='$Latest' \ --min-size 2 \ --max-size 5 \ --desired-capacity 2 \ --vpc-zone-identifier "$SUBNET_PRIV_A,$SUBNET_PRIV_B" \ --health-check-type ELB \ --health-check-grace-period 300 \ --tags "Key=Name,Value=web-app-prod,PropagateAtLaunch=true" \ "Key=Environment,Value=Production,PropagateAtLaunch=true"
Step 2: Verify ASG Status
aws autoscaling describe-auto-scaling-groups \ --auto-scaling-group-names $ASG_NAME \ --query 'AutoScalingGroups[0].Instances[*].[InstanceId,LifecycleState,HealthStatus]' \ --output table INSTANCE_COUNT=$(aws autoscaling describe-auto-scaling-groups \ --auto-scaling-group-names $ASG_NAME \ --query 'AutoScalingGroups[0].Instances[?LifecycleState==`InService`] | length(@)' --output text) echo "In-service instances: $INSTANCE_COUNT"
✅ Verification Checklist:
  • □ ASG created with min=2, desired=2, max=5
  • □ ASG launched instances in both private subnets
  • □ All instances are "InService" and "Healthy"
🔄 ASG 📊 min=2 📈 max=5

P6.6 Attach ASG to ALB Target Group

📖 Theory: ASG + ALB Integration
When you attach an Auto Scaling Group to a Target Group, instances are automatically registered with the Target Group when launched and deregistered when terminated.

Step 1: Attach Target Group to ASG
aws autoscaling attach-load-balancer-target-groups \ --auto-scaling-group-name $ASG_NAME \ --target-group-arns $TG_ARN
Step 2: Verify Integration
aws elbv2 describe-target-health \ --target-group-arn $TG_ARN \ --query 'TargetHealthDescriptions[*].[Target.Id,TargetHealth.State]' \ --output table curl -s http://$ALB_DNS | head -20
✅ Verification Checklist:
  • □ Target Group attached to Auto Scaling Group
  • □ Instances are automatically registered with Target Group
  • □ ALB is distributing traffic to healthy instances
  • □ Web page is accessible via ALB DNS
🔗 ASG + ALB 🔄 auto-registration ✅ health checks

P6.7 Configure Step Scaling Policy

CPU > 70% → Add 1 | CPU < 30% → Remove 1
📖 Theory: Step Scaling Policies
Step scaling policies allow you to define multiple scaling adjustments based on the severity of the metric deviation.

Step 1: Create CloudWatch Alarms
# CPU high alarm (scale out trigger) aws cloudwatch put-metric-alarm \ --alarm-name "$ASG_NAME-high-cpu" \ --metric-name CPUUtilization \ --namespace AWS/EC2 \ --statistic Average \ --period 60 \ --evaluation-periods 2 \ --threshold 70 \ --comparison-operator GreaterThanThreshold \ --dimensions Name=AutoScalingGroupName,Value=$ASG_NAME # CPU low alarm (scale in trigger) aws cloudwatch put-metric-alarm \ --alarm-name "$ASG_NAME-low-cpu" \ --metric-name CPUUtilization \ --namespace AWS/EC2 \ --statistic Average \ --period 60 \ --evaluation-periods 2 \ --threshold 30 \ --comparison-operator LessThanThreshold \ --dimensions Name=AutoScalingGroupName,Value=$ASG_NAME
Step 2: Create Scaling Policies
# Scale out policy (add 1 instance) aws autoscaling put-scaling-policy \ --auto-scaling-group-name $ASG_NAME \ --policy-name scale-out-step \ --policy-type StepScaling \ --adjustment-type ChangeInCapacity \ --step-adjustments '[{"MetricIntervalLowerBound":0.0,"MetricIntervalUpperBound":100.0,"ScalingAdjustment":1}]' \ --estimated-instance-warmup 120 # Scale in policy (remove 1 instance) aws autoscaling put-scaling-policy \ --auto-scaling-group-name $ASG_NAME \ --policy-name scale-in-step \ --policy-type StepScaling \ --adjustment-type ChangeInCapacity \ --step-adjustments '[{"MetricIntervalLowerBound":-100.0,"MetricIntervalUpperBound":0.0,"ScalingAdjustment":-1}]' \ --estimated-instance-warmup 120
✅ Verification Checklist:
  • □ CPU high alarm created (threshold: 70%)
  • □ CPU low alarm created (threshold: 30%)
  • □ Scale out policy configured (add 1 instance)
  • □ Scale in policy configured (remove 1 instance)
📊 scaling 📈 CPU > 70% 📉 CPU < 30%

P6.8 Enable Warm-up and Cooldown

📖 Theory: Warm-up and Cooldown
  • Instance Warm-up: Time for a new instance to become fully initialized before it's counted in metrics (prevents over-scaling)
  • Cooldown: Time to wait after a scaling activity before another scaling activity can start (prevents flapping)

Step 1: Update ASG with Default Instance Warmup
aws autoscaling update-auto-scaling-group \ --auto-scaling-group-name $ASG_NAME \ --default-instance-warmup 120
Step 2: Verify Warm-up Configuration
aws autoscaling describe-auto-scaling-groups \ --auto-scaling-group-names $ASG_NAME \ --query 'AutoScalingGroups[0].DefaultInstanceWarmup' \ --output text
✅ Verification Checklist:
  • □ Default Instance Warmup set to 120 seconds
  • □ Cooldown configured (if using simple scaling)
⏱️ warm-up 🔄 cooldown 📊 120s

P6.9 Perform Load Test

Trigger Scaling with Apache Bench
📖 Theory: Load Testing
Apache Bench (ab) is a simple tool for generating load to test how your Auto Scaling Group responds.

Step 1: Install Apache Bench
# On Amazon Linux sudo dnf install -y httpd-tools
Step 2: Run Load Test
ALB_DNS=$(aws elbv2 describe-load-balancers --names webapp-alb --query 'LoadBalancers[0].DNSName' --output text) ab -n 10000 -c 100 http://$ALB_DNS/index.html
Step 3: Monitor Scaling
# Monitor ASG instances while true; do clear echo "=== ASG Status ===" aws autoscaling describe-auto-scaling-groups \ --auto-scaling-group-names $ASG_NAME \ --query 'AutoScalingGroups[0].[DesiredCapacity,MinSize,MaxSize,Instances[*].[InstanceId,LifecycleState,HealthStatus]]' \ --output table sleep 10 done
Step 4: Observe Scaling Out
After 1-2 minutes of load:
  • CPU alarm enters ALARM state
  • ASG launches additional instances
  • Desired capacity increases from 2 to 3+

Step 5: Observe Scaling In
After the load test completes:
  • Low CPU alarm triggers
  • ASG removes instances
  • Desired capacity returns to 2
✅ Verification Checklist:
  • □ Load test executed successfully
  • □ CPU alarm triggered (scale out)
  • □ ASG launched additional instances
  • □ After load drops, ASG scaled back in
⚡ load test 📊 ab -n 10000 🔄 scale out

P6.10 Simulate AZ Failure

Observe ASG Rebalancing
📖 Theory: AZ Failure Simulation
Simulating an Availability Zone failure tests your application's resilience. When instances in one AZ become unavailable, the ASG should launch replacements in the remaining AZs.

Step 1: Identify Instances and AZs
aws autoscaling describe-auto-scaling-groups \ --auto-scaling-group-names $ASG_NAME \ --query 'AutoScalingGroups[0].Instances[*].[InstanceId,AvailabilityZone]' \ --output table INSTANCE_IN_AZ_A=$(aws autoscaling describe-auto-scaling-groups \ --auto-scaling-group-names $ASG_NAME \ --query 'AutoScalingGroups[0].Instances[?AvailabilityZone==`'${AZS[0]}'`].[InstanceId]' \ --output text)
Step 2: Simulate AZ Failure
aws ec2 terminate-instances --instance-ids $INSTANCE_IN_AZ_A
Step 3: Monitor ASG Rebalancing
while true; do clear echo "=== ASG Rebalancing Monitor ===" aws autoscaling describe-auto-scaling-groups \ --auto-scaling-group-names $ASG_NAME \ --query 'AutoScalingGroups[0].[DesiredCapacity,Instances[*].[InstanceId,AvailabilityZone,LifecycleState]]' \ --output table sleep 10 done
Expected Behavior:
  1. The terminated instance goes from running → terminated
  2. ASG detects the instance is no longer healthy
  3. ASG launches a new instance in the same AZ (or another AZ)
  4. ASG returns to desired capacity (2 instances)
  5. New instances are registered with the Target Group
✅ Verification Checklist:
  • □ Instance terminated successfully
  • □ ASG detected the instance failure
  • □ ASG launched a replacement instance
  • □ ASG returned to desired capacity
  • □ ALB is distributing traffic to healthy instances
  • □ Application remains accessible
💥 AZ failure 🔄 rebalancing ✅ resilience
