📚 Amazon VPC

Amazon VPC (Virtual Private Cloud)

Amazon VPC (Virtual Private Cloud) allows you to provision a logically isolated section of the AWS cloud where you can launch AWS resources such as EC2 instances, RDS databases, and more. It provides complete control over your networking environment including IP address ranges, subnets, route tables, internet gateways, and security groups.

🔑 Key Features

  • Isolation: Create a logically isolated environment within AWS cloud.
  • Subnets: Divide VPC into public and private subnets.
  • Security: Use Security Groups and Network ACLs to control traffic.
  • Connectivity: Connect to internet (via IGW), to on-premises (via VPN), or to other VPCs (via Peering).
  • Custom IP Addressing: Define your own IPv4/IPv6 CIDR ranges.
  • Multi-AZ: Distribute resources across Availability Zones for resilience.

🌍 Core Components

  • Subnets: Public & Private resource isolation.
  • Route Tables: Define routing rules.
  • Internet Gateway: Enable external connectivity.
  • NAT Gateway: Private subnet outbound traffic.
  • Security Groups: Stateful instance firewall.
  • Network ACLs: Stateless subnet firewall.
  • VPC Peering: Connect multiple VPCs.
  • Transit/VPN Gateway: Extend to on-premises.

🚀 Benefits

  • Granular control over network design.
  • Enhanced security with SGs & ACLs.
  • Scalable IP addressing and multi-AZ deployments.
  • Seamless integration with hybrid environments.

📊 Example Architecture

A common setup includes:

  • VPC: CIDR block 10.0.0.0/16
  • Public Subnets: Hosting load balancers in 2 AZs
  • Private Subnets: Hosting app servers & RDS
  • Internet Gateway: Public access
  • NAT Gateway: Secure outbound internet from private subnets
  • Security Groups: Allow HTTPS/SSH inbound

Example Use Case: A scalable web application with public-facing EC2 instances behind a load balancer, databases in private subnets, and outbound traffic managed through a NAT Gateway.

🌐 Internet Gateway & NAT Gateway in VPC

🔹 Internet Gateway (IGW)

An Internet Gateway is a horizontally scaled, highly available VPC component that allows communication between instances in your VPC and the internet.

  • Provides a target in your VPC route tables for internet-routable traffic.
  • Performs Network Address Translation (NAT) for instances with public IPv4 addresses.
  • Enables IPv6 traffic without NAT (as IPv6 is inherently public).

Use Case: Required when your EC2 instances need direct internet access (e.g., web servers).

🔹 NAT Gateway (NGW)

A NAT Gateway enables instances in a private subnet to connect to the internet or other AWS services, but prevents the internet from initiating connections with those instances.

  • Used for outbound-only internet connectivity.
  • Managed AWS service (scales automatically up to 45 Gbps).
  • Each NAT Gateway is created in a specific Availability Zone.
  • Requires an Elastic IP (public IPv4 address).

Use Case: Required when private instances (e.g., application servers, DB instances) need to download updates or connect securely to the internet without exposing themselves.

Feature Internet Gateway (IGW) NAT Gateway (NGW)
Traffic Direction Inbound & Outbound Outbound only
Subnet Association Used with Public Subnets Used with Private Subnets
Scalability Horizontally Scaled Auto Scales up to 45 Gbps
Cost Free Charged per hour + per GB processed
Elastic IP Requirement Not required (used with public IPs) Required

🛡 Network ACLs vs Security Groups in AWS VPC

🔹 Network ACL (NACL)

A Network ACL is a stateless layer of security at the subnet level. It controls inbound and outbound traffic for all resources within the subnet.

  • Operates at the subnet level.
  • Stateless: return traffic must have explicit rules.
  • Supports allow and deny rules with numbered priorities.
  • Processed in order of rule numbers, first match applies.

Use Case: Add an extra layer of protection, control traffic between subnets, block malicious IPs.

🔹 Security Group (SG)

A Security Group is a stateful virtual firewall for EC2 instances. It controls inbound and outbound traffic at the instance level.

  • Operates at the instance level.
  • Stateful: return traffic is automatically allowed.
  • Supports only allow rules (no explicit deny).
  • All rules are evaluated before allowing traffic.

Use Case: Control which traffic can reach your EC2 instances, RDS, or other resources.

Feature Network ACL (NACL) Security Group (SG)
Level Subnet Instance
Type Stateless Stateful
Rule Types Allow / Deny Allow only
Evaluation Rules are processed in numbered order All rules are evaluated; first match not required
Default Behavior Allow all inbound/outbound Deny all inbound, allow all outbound
Use Case Extra subnet-level control, IP blocking Protect instances, control allowed traffic

NACLs control traffic at the subnet level, applying to all instances in the subnet. Security Groups control traffic for individual instances.

Amazon VPC & Subnets

Amazon VPC (Virtual Private Cloud) is your own isolated network inside AWS, where you can launch resources such as EC2, RDS, and Lambda with full control over networking. Inside a VPC, you divide your IP address range into smaller segments called Subnets, which can be public or private.

🌐 Virtual Private Cloud (VPC)

  • Isolation: Dedicated logical network in AWS.
  • CIDR Block: Choose your IP range (e.g., 10.0.0.0/16).
  • AZ Integration: Spans across multiple Availability Zones.
  • Connectivity: Supports Internet Gateway, NAT, VPN, Transit Gateway.
  • Security: Control traffic via Security Groups & Network ACLs.

📦 Subnets

Subnets are subdivisions of a VPC’s IP address range. Each subnet resides in a single Availability Zone and can be categorized as:

🌍 Public Subnet

  • Connected to Internet Gateway (IGW).
  • Hosts Load Balancers, Bastion Hosts, Web Servers.
  • Direct inbound/outbound internet access.

🔒 Private Subnet

  • No direct access to the Internet.
  • Uses NAT Gateway for outbound traffic.
  • Hosts Application Servers, Databases.

🚀 Benefits of VPC + Subnets

  • Flexible and granular control of resources.
  • Improved security by isolating workloads.
  • High availability with Multi-AZ subnet distribution.
  • Hybrid connectivity with VPN/Direct Connect.

📊 Example Architecture

A typical VPC and subnet design might look like this:

  • VPC: 10.0.0.0/16
  • Public Subnet 1 (AZ-1): 10.0.1.0/24 → Internet Gateway
  • Public Subnet 2 (AZ-2): 10.0.2.0/24 → Internet Gateway
  • Private Subnet 1 (AZ-1): 10.0.3.0/24 → NAT Gateway
  • Private Subnet 2 (AZ-2): 10.0.4.0/24 → NAT Gateway
  • Security: Web servers in public subnets, DB in private subnets.

Example Use Case: A highly available web application running EC2 instances in public subnets behind an Elastic Load Balancer, while storing data in RDS instances inside private subnets. Outbound traffic from private subnets goes through a NAT Gateway.

🔗 AWS VPC Peering

📌 What is VPC Peering?

VPC Peering allows you to **connect two VPCs** privately using AWS network infrastructure, enabling instances in different VPCs to communicate as if they were in the same network. Peering can be **within the same AWS Region** (intra-region) or **across regions** (inter-region).

🔹 Key Features

  • **Private, low-latency network connectivity** between VPCs.
  • No single point of failure, fully managed by AWS.
  • Traffic stays **within AWS network**, not over the public internet.
  • Supports **intra-region** and **inter-region** peering.
  • Instances in peered VPCs can communicate using **private IP addresses**.
  • Peering is **one-to-one**; for multiple VPCs, you need multiple peering connections or Transit Gateway.

🔹 Use Cases

  • Connect **development, testing, and production VPCs** securely.
  • Share services like databases or caches across VPCs without public access.
  • Enable **cross-account communication** between VPCs.
  • Integrate **multi-region applications** for latency optimization.

📈 Example Architecture

VPC Peering allows instances in VPC A and VPC B to communicate privately using private IP addresses without going through the public internet.

🔹 How VPC Peering Works

  1. Create a **VPC Peering Connection** request from the requester VPC to the accepter VPC.
  2. The accepter VPC **accepts the peering request**.
  3. Update **route tables** in both VPCs to direct traffic destined for the peered VPC’s CIDR through the peering connection.
  4. Security groups in each VPC must **allow inbound and outbound traffic** for the desired resources.
  5. Instances in both VPCs can now communicate **privately**.

⚠️ Limitations

  • **No transitive peering**: VPC A peered with B and B with C cannot reach C via B.
  • **Peering is one-to-one**; you need multiple connections for multiple VPCs.
  • Requires proper **route table and security group configuration** to work.
  • Cannot peer VPCs with **overlapping CIDR ranges**.

🏗️ VPC-Based Three-Tier Architecture

📌 What is VPC Three-Tier Architecture?

In AWS, a Three-Tier Architecture can be deployed inside a Virtual Private Cloud (VPC) to ensure isolation, security, and scalability. The architecture separates applications into three tiers: Presentation Layer (Web Tier), Application Layer (Logic Tier), and Data Layer (Database Tier), each deployed in its own subnet type.

🔹 Layers and Subnets

  • Presentation Layer (Web Tier):
    • Hosted in Public Subnets
    • Contains web servers (EC2 / ELB / CloudFront)
    • Accessible from the internet
  • Application Layer (Logic Tier):
    • Hosted in Private Subnets
    • Contains application servers or APIs (EC2 / Beanstalk / Lambda)
    • No direct internet access; communicates with web tier via ELB
  • Data Layer (Database Tier):
    • Hosted in Private Subnets, isolated
    • Contains databases (RDS, Aurora, DynamoDB)
    • Only accessible from application layer; not directly exposed to internet

✅ Advantages

  • Improved security using private/public subnets and security groups
  • Independent scalability of each layer
  • Supports high availability using Multi-AZ deployments and Load Balancers
  • Easy to monitor and troubleshoot each tier separately

📈 VPC Three-Tier Architecture Diagram

The Public Subnet hosts the Web Tier (Internet-facing). The Private Subnets host Application and Database Tiers. Security Groups and Network ACLs control access between tiers and the internet.

☁️ AWS Implementation

  • Web Tier (Public Subnet): ELB, EC2, CloudFront, Route 53
  • App Tier (Private Subnet): EC2, Auto Scaling Group, Elastic Beanstalk, Lambda
  • Database Tier (Private Subnet): RDS Multi-AZ, Aurora, DynamoDB
  • Security: Security Groups, Network ACLs, IAM roles
  • High Availability: Multi-AZ deployment across subnets

⚡ Key Notes

  • Each layer can scale horizontally with Auto Scaling Groups.
  • Application tier communicates with Database tier only via private endpoints.
  • Public subnets can host NAT Gateways for outbound internet access for private tiers.
  • Route 53 and CloudFront provide DNS routing and caching at the edge.

🏗️ VPC-Based Three-Tier Architecture

📌 Overview

A Three-Tier Architecture in AWS VPC divides an application into three logical layers: Web (Presentation), Application (Logic), and Database (Data). This separation enhances security, scalability, and manageability. Each layer resides in its own subnet (public or private), and traffic flows between layers under controlled security policies.

🔹 Layer-Wise Breakdown

1️⃣ Presentation Layer (Web Tier)

This is the public-facing layer that handles client requests (HTTP/HTTPS). It resides in Public Subnets and can directly communicate with the Internet.

  • Hosted on EC2 instances, Elastic Load Balancers (ELB), or behind CloudFront CDN.
  • Receives requests from users via Route 53 DNS.
  • Uses Security Groups to restrict inbound traffic to standard ports (e.g., 80, 443).
  • Does not directly interact with the database layer.

2️⃣ Application Layer (Logic Tier)

This layer processes business logic, application rules, and computations. It resides in Private Subnets to prevent direct Internet access.

  • Hosts API servers, backend services, or serverless functions (Lambda, ECS, Beanstalk).
  • Communicates with Web Tier through private load balancers or internal endpoints.
  • Uses Security Groups to allow traffic only from Web Tier and allow outbound access via NAT Gateway if needed.
  • Scales horizontally using Auto Scaling Groups without exposing the instances directly to the internet.

3️⃣ Database Layer (Data Tier)

This layer stores persistent data and resides in Private Subnets for maximum isolation. No direct Internet access is allowed.

  • Hosts relational databases (RDS, Aurora) or NoSQL databases (DynamoDB).
  • Communicates only with Application Layer via secure connections.
  • Supports Multi-AZ deployment for high availability and automated backups.
  • Can use Read Replicas to scale read operations and reduce load on primary DB.

✅ Advantages of Layer Separation

  • Enhanced security by isolating public-facing components from sensitive data.
  • Independent scaling of each layer based on traffic and resource needs.
  • High availability and disaster recovery by deploying layers across multiple Availability Zones (Multi-AZ).
  • Clear separation of concerns simplifies maintenance and monitoring.

📈 Architecture Diagram

Public Subnets host the Web Tier accessible via Internet (Route 53 + ELB). Private Subnets host Application and Database tiers. Security Groups, Network ACLs, and NAT Gateways control communication and outbound access.

📊 AWS VPC Flow Logs

🔹 What are VPC Flow Logs?

VPC Flow Logs capture information about the **IP traffic going to and from network interfaces** in your VPC. You can monitor, analyze, and troubleshoot network traffic for security and operational purposes.

🔹 Key Features

  • Records inbound and outbound traffic at the **VPC, subnet, or ENI (Elastic Network Interface) level**.
  • Supports **filtering** by accepted or rejected traffic.
  • Logs are delivered to **Amazon CloudWatch Logs** or **Amazon S3** for storage and analysis.
  • Helps in **security analysis**, **compliance auditing**, and **troubleshooting network issues**.
  • Supports custom **log format** including source/destination IP, port, protocol, traffic accept/reject info, and bytes transferred.

🔹 Use Cases

  • Detect unusual traffic patterns or potential intrusions.
  • Audit network access for compliance standards.
  • Analyze network traffic to optimize architecture or costs.
  • Debug connectivity issues between EC2 instances, subnets, or on-premises networks.

📈 Example Architecture

VPC Flow Logs capture traffic data from ENIs in subnets and VPCs, and deliver the logs to CloudWatch Logs or S3 for monitoring and analysis.

🔹 How VPC Flow Logs Work

  1. Enable Flow Logs for a **VPC, subnet, or ENI** in AWS Management Console, CLI, or SDK.
  2. Choose the **destination**: CloudWatch Logs or S3 bucket.
  3. Define a **filter**: Accepted, Rejected, or All traffic.
  4. Traffic metadata such as source/destination IP, port, protocol, action (accept/reject), and bytes is logged.
  5. Analyze logs using **CloudWatch Insights**, Athena, or third-party SIEM tools.
