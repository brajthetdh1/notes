11.3 Instance Store (Ephemeral Storage)

📖 Complete Theory: Temporary, High-Performance Local Storage

An Amazon EC2 Instance Store provides temporary, block-level storage for your EC2 instances. This storage is located on disks that are physically attached to the host computer running your instance. Because it is directly attached rather than accessed over the network, instance store offers very high performance with extremely low latency. However, this performance comes with a critical trade-off: the data is ephemeral — it exists only for the lifetime of the instance.

11.3.1 What is Instance Store?

📖 Definition and Core Concept

An Amazon EC2 Instance Store provides temporary, block-level storage that is physically attached to the host computer running your EC2 instance. Unlike network-attached storage like Amazon EBS, instance store volumes are directly connected to the physical server, which delivers extremely high performance with low latency.

🔑 Key Characteristics:

1. Ephemeral Nature (The Critical Trade-off)
Instance store volumes exist only for the lifetime of the instance. Data is permanently lost in several scenarios:

⚠️ Critical Warning: When an instance is stopped, hibernated, or terminated, every block of the instance store volume is cryptographically erased. Instance store data is not persistent — it is temporary storage tied to the physical host.

2. High Performance (The Primary Benefit)
Because instance store volumes are physically attached to the host, they offer:
  • Ultra-low latency — lower than network-attached EBS
  • Very high IOPS — ideal for I/O-intensive workloads
  • High throughput — suitable for temporary data processing
  • No network dependency — data doesn't traverse a network

📝 Review Questions
Q1: What is an EC2 Instance Store?
An instance store provides temporary, block-level storage that is physically attached to the host computer running your EC2 instance. It offers high performance with low latency but is ephemeral — data is lost when the instance is stopped or terminated.
Q2: What happens to data on an instance store volume when you stop an instance?
Data on instance store volumes is permanently lost when you stop an instance. The storage is tied to the physical host, and when the instance is stopped, the resources are deallocated and every block is cryptographically erased.
Q3: Can you detach an instance store volume from one instance and attach it to another?
No, you cannot detach an instance store volume. Instance store volumes are physically attached to the host computer and exist only during the lifetime of the instance to which they are attached.
Q4: When should you use instance store instead of EBS?
Use instance store for temporary storage that requires high performance and low latency, such as caches, buffers, scratch data, and temporary content for load-balanced web servers. For persistent data that must survive instance stops and terminations, use EBS.
Q5: Is there an additional cost for instance store volumes?
No, instance store volumes are included as part of the EC2 instance usage cost. There is no additional charge to use them.

11.3.2 Performance Characteristics

High IOPS, Low Latency
📖 Complete Theory: Performance Characteristics

Instance Store volumes are renowned for their exceptional performance, primarily because they are physically attached to the host machine rather than accessed over a network. This architecture is the key to their high Input/Output Operations Per Second (IOPS) and ultra-low latency.

🏆 High IOPS and Throughput:
For modern Nitro-based EC2 instances, Instance Store volumes are exposed as NVMe (Non-Volatile Memory Express) SSDs. This technology is designed for extreme performance, offering significantly higher IOPS and throughput than standard SSDs.

💡 Raw Performance Specifications:
  • A large i3en.3xlarge instance can deliver up to 3.3 million read IOPS
  • Typical IOPS can reach hundreds of thousands for both read and write operations
  • Ultra-low latency — lower than network-attached EBS

⚡ Ultra-Low Latency:
The direct physical connection of instance store volumes eliminates network latency, enabling extremely fast data access. This is particularly valuable for workloads that require consistent, low-latency storage, such as:
  • Real-time caching
  • Scratch space for high-performance computing
  • Applications with many small, random reads and writes

🏗️ Architectural Drivers:
  • Directly Attached to Host: Enables a direct data path with minimal overhead
  • Ephemeral Nature Trade-off: High performance is the direct result of the storage being temporary and tied to the instance's lifecycle

💡 Real-World Impact: A high-traffic web application using instance store for caching user session data can achieve extremely low-latency access, resulting in faster user experiences. The data loss risk is acceptable because the session data is transient and can be regenerated.

11.3.3 Data Persistence and Lifetime

📖 Complete Theory: Data Persistence and Lifetime

Understanding when data on an Instance Store volume persists is critical for making correct architectural decisions. The fundamental rule is that data is ephemeral and tied to the instance's physical host.

The Core Rule of Instance Store Lifetime:
The data on an Instance Store volume exists only during the lifetime of the instance to which it is attached. Unlike EBS, you cannot configure an Instance Store volume to persist beyond the instance's lifecycle.

📊 Persistence by Event Type:
Instance Reboot
✅ Data persists
Instance Stop
❌ Data does NOT persist
Instance Hibernation
❌ Data does NOT persist
Instance Termination
❌ Data does NOT persist
Instance Type Change
❌ Data does NOT persist
Hardware Failure
❌ Data does NOT persist
Power Failure
✅ Data persists upon reboot
EBS-backed AMI Creation
❌ Data NOT included in AMI

⚠️ Cryptographic Erasure:
When an instance is stopped, hibernated, or terminated, every block of the Instance Store volume is cryptographically erased. This ensures that no residual data remains for other users to access. This erasure is complete and irreversible — you cannot recover data from a stopped instance's Instance Store.
🔍 Critical Details and Warnings:
  • Attach/Detach Limitations: Instance Store volumes are attached only at instance launch. You cannot attach or detach an instance store volume after launch.
  • Instance Type Change: If you change the instance type, the data does not persist. The new instance receives fresh, empty volumes.
  • Operating System Shutdown: Termination protection and stop protection do not protect your instance against stops or terminations initiated from within the OS.

🎯 Best Practices:
  • Do not store valuable, long-term data on Instance Store volumes
  • Only store temporary data such as caches, buffers, and scratch data
  • Manually copy critical data to persistent storage (EBS, S3, EFS) before stopping or terminating
  • Use fault-tolerant architectures — replicate data across a fleet of instances
  • Always consider the persistence rules when using automation or lifecycle management tools
📝 Review Questions
Q1: Does data on an Instance Store volume persist if the instance is rebooted?
Yes. Data on Instance Store volumes persists when the instance is rebooted, whether initiated by the user or by AWS scheduled events.
Q2: What is the critical difference between Instance Store and EBS regarding data persistence?
Instance Store data is ephemeral and is lost when the instance is stopped, hibernated, or terminated, whereas EBS data persists independently of the instance lifecycle. Instance Store volumes are also cryptographically erased when the instance stops.
Q3: If an instance type change is made to a new instance type that supports Instance Store, does the data from the original Instance Store volumes transfer?
No. The data does not transfer to the new instance store volumes. The new instance receives fresh, empty volumes.
Q4: Does an EBS-backed AMI created from an instance include data from the Instance Store volumes?
No. The data on Instance Store volumes is not included in the EBS-backed AMI.
Q5: What happens to Instance Store data if the underlying disk fails?
The data on the failed disk does not persist. This is an unplanned event that results in permanent data loss.

Key Takeaways

  • Instance Store provides temporary, block-level storage physically attached to the host — included with the instance cost.

  • Ephemeral Nature: Data is permanently lost on stop, hibernation, termination, hardware failure, or instance type change.

  • High Performance: Ultra-low latency, very high IOPS, and high throughput — ideal for caches, buffers, and scratch data.

  • Reboot Persistence: Data persists on instance reboot (user-initiated or AWS scheduled).

  • Cannot Detach: Instance store volumes cannot be detached from one instance and attached to another.

  • Must Specify at Launch: Instance store volumes must be specified at launch — cannot attach after launch.

  • No Snapshots: Instance store volumes cannot be backed up via snapshots.

  • Cryptographic Erasure: When an instance stops, every block is cryptographically erased — data is irrecoverable.

  • Best Practice: Only store temporary, non-critical data on instance store — use EBS for persistent data.

  • Fault-Tolerant Architectures: Use load balancing and replication across a fleet for web servers using instance store.
