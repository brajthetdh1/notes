Introduction

Web hosting and application serving represent the most common and foundational use case for Amazon EC2. In fact, it was the primary use case envisioned by the original EC2 team in 2006 — providing developers with a simple, scalable way to deploy websites and web applications to the internet without the headaches of managing physical servers.

Today, EC2 powers millions of websites and web applications globally, ranging from:
  • 📄 Simple static websites — personal blogs, portfolios
  • 🛒 Dynamic web applications — e-commerce platforms, SaaS products
  • 🏢 Enterprise web portals — intranets, customer dashboards
  • 🔌 API backends — RESTful APIs, GraphQL endpoints
  • 🧩 Microservices architectures — distributed systems
  • 📝 Content Management Systems (CMS) — WordPress, Drupal, Joomla

Static Web Hosting

Definition: A static website serves the same pre-built content (HTML, CSS, JavaScript, images) to every visitor. There is no server-side processing.

Characteristics:
  • Content is fixed and doesn't change per user
  • No backend logic or database required
  • Very fast and cheap to host

Traditional Static Hosting on EC2:
  • Launch an EC2 instance (e.g., t3.micro)
  • Install a web server (Apache, Nginx)
  • Upload your static files to the server's document root
  • Expose port 80/443 to the internet
EC2 Instance Configuration for Static Website +---------------------------------------------------+ | EC2 Instance (Static Web Server) | +---------------------------------------------------+ | OS: Amazon Linux 2023 | | Web Server: Nginx | | Content: /var/www/html/ | | - index.html | | - style.css | | - script.js | | - images/ | | Ports Open: 80 (HTTP), 443 (HTTPS) | | Security Group: Allow from 0.0.0.0/0 | +---------------------------------------------------+
When to use EC2 for static sites:
  • When you need full control over the server configuration
  • When you have custom requirements (e.g., specific modules, rewrites)
  • When you're running a legacy application that doesn't fit modern static hosting

💡 Better Alternatives for Static Sites:
  • Amazon S3 + CloudFront — cheaper, more scalable, CDN-enabled
  • AWS Amplify — Git-based deployments, built-in CI/CD
📄 static 🖥️ HTML/CSS/JS ⚡ fast & cheap

Dynamic Web Hosting

Definition: A dynamic website generates content in real-time based on user requests, session data, database queries, and business logic.

Characteristics:
  • Content is generated per request
  • Requires server-side programming (PHP, Python, Node.js, Java, .NET, Ruby)
  • Usually requires a database (MySQL, PostgreSQL, MongoDB)
  • Can maintain user sessions and state
Traditional Dynamic Hosting on EC2 +---------------------------------------------------+ | EC2 Instance (Dynamic Web Server) | +---------------------------------------------------+ | OS: Amazon Linux 2023 | | Web Server: Apache/Nginx | | Application: Wordpress / Django / Node.js | | Language Runtime: PHP / Python / Node.js | | Database: MySQL / PostgreSQL (self-managed) | | Content: /var/www/html/application/ | | Ports Open: 80 (HTTP), 443 (HTTPS), 22 (SSH) | +---------------------------------------------------+
Where This Architecture Fails:
  • ❌ Single Point of Failure: If the instance goes down, the website goes down
  • ❌ Scalability Limitations: A single instance has fixed CPU/RAM capacity
  • ❌ Database Performance: The database shares resources with the web server
  • ❌ Maintenance Downtime: Updates/patches require taking the server offline
⚡ dynamic 🗄️ database 🧑‍💻 server-side

EC2 Instance Types for Web Hosting

Choosing the right EC2 instance type depends on your specific requirements.

A. General Purpose Instances (M-series, T-series)
Instance TypevCPUsMemory (GiB)Best For
t3.micro21Low-traffic blogs (Free Tier)
t3.small22Small business websites
t3.medium24Medium-traffic WordPress
m5.large28Production web applications
m5.xlarge416High-traffic web apps
m5.2xlarge832Enterprise web portals

T-series (Burstable):
  • Use CPU Credits to burst above baseline
  • Perfect for websites with spiky traffic (blogs, news sites)
  • Low cost but predictable performance issues under sustained load
M-series (Fixed Performance):
  • Consistent, predictable performance
  • No CPU credits to manage
  • Suitable for steady-state production workloads
B. Compute-Optimized Instances (C-series)
Instance TypevCPUsMemory (GiB)Best For
c6g.large24High-performance web apps (Graviton ARM)
c5.xlarge48CPU-intensive web apps, API gateways
c6a.xlarge48Web servers with heavy PHP/Python processing

When to use C-series:
  • Applications with heavy compute (e.g., image processing, video transcoding)
  • High-traffic API endpoints requiring low latency
  • GraphQL or REST APIs with complex resolvers

C. Memory-Optimized Instances (R-series, X-series)
Instance TypevCPUsMemory (GiB)Best For
r5.large216In-memory databases (Redis, Memcached)
r5.xlarge432Memory-intensive web apps
x1e.xlarge4122Large in-memory caches, SAP applications

When to use R-series:
  • Applications with large in-memory caches
  • Real-time analytics dashboards with in-memory processing
  • Java-based applications with large heap sizes
  • WordPress with extensive caching (W3 Total Cache in memory)

Web Hosting Software Stacks

The Most Common Deployments
1. LAMP Stack Linux, Apache, MySQL, PHP
Use Case: WordPress, Drupal, Joomla
# Install Apache sudo dnf install httpd -y sudo systemctl start httpd sudo systemctl enable httpd # Install MariaDB sudo dnf install mariadb-server -y sudo systemctl start mariadb sudo systemctl enable mariadb # Install PHP sudo dnf install php php-mysqlnd -y sudo systemctl restart httpd # Create a test file echo "<?php phpinfo(); ?>" | sudo tee /var/www/html/info.php

2. LEMP Stack Linux, Nginx, MySQL, PHP-FPM
Use Case: High-traffic websites, microservices
Advantages of LEMP over LAMP:
  • Nginx is event-driven (asynchronous, non-blocking)
  • Better performance under high concurrency
  • Lower memory footprint
  • Better for serving static files
  • PHP-FPM separates PHP processing from the web server

3. MEAN/MERN Stack Node.js, Express, Angular/React, MongoDB
Use Case: Modern SPAs (Single Page Applications)
# Install Node.js curl -sL https://rpm.nodesource.com/setup_20.x | sudo bash - sudo dnf install nodejs -y # Install PM2 for process management sudo npm install -g pm2 # Clone your app git clone https://github.com/your-app.git /var/www/app cd /var/www/app npm install # Start with PM2 pm2 start app.js pm2 startup pm2 save

4. Java Stack Tomcat, Spring Boot
Use Case: Enterprise web applications, APIs
5. .NET Stack IIS, .NET Core/ASP.NET
Use Case: Enterprise .NET applications

Performance Optimization

A. Nginx Configuration for High Traffic
# /etc/nginx/nginx.conf # Worker processes equal to number of vCPUs worker_processes auto; # Increase worker connections events { worker_connections 1024; multi_accept on; use epoll; } # Enable gzip compression http { gzip on; gzip_types text/plain text/css application/javascript; gzip_min_length 1000; gzip_comp_level 6; # Enable caching open_file_cache max=1000 inactive=20s; open_file_cache_valid 30s; open_file_cache_min_uses 2; # Client settings client_max_body_size 100M; keepalive_timeout 65; include /etc/nginx/conf.d/*.conf; }

B. Caching Hierarchy
CACHING HIERARCHY +---------------------------------------------------+ | Layer 1: CloudFront (CDN) | | └─ Caches static assets globally (images, CSS, JS) | | Layer 2: Varnish / Nginx FastCGI Cache | | └─ Caches full HTML pages | | Layer 3: Redis / Memcached (Object Cache) | | └─ Caches database queries, sessions | | Layer 4: MySQL Query Cache | | └─ Caches SELECT query results | +---------------------------------------------------+

Implementing Redis Cache on EC2:
# Install Redis sudo dnf install redis -y sudo systemctl start redis sudo systemctl enable redis # Configure Redis (optimize for web caching) sudo vi /etc/redis.conf # Set maxmemory 512mb # Set maxmemory-policy allkeys-lru # Set timeout 300 # Install PHP Redis extension (if using PHP) sudo dnf install php-redis -y sudo systemctl restart httpd

C. Content Delivery Network (CDN) Integration
CloudFront with EC2 Origin:
1. User requests static asset (image, CSS, JS) 2. CloudFront checks edge location cache 3. If cache miss → Fetch from EC2 origin server 4. Cache asset at edge location for TTL 5. Future requests served directly from edge (Reduces load on EC2 instances)

B. SSL/TLS Configuration (HTTPS)
# Using Let's Encrypt with Certbot # Install Certbot sudo dnf install certbot python3-certbot-nginx -y # Obtain certificate sudo certbot --nginx -d yourdomain.com -d www.yourdomain.com # Auto-renewal cron job echo "0 0,12 * * * root python3 -c 'import random; import time; time.sleep(random.random() * 3600)' && certbot renew" | sudo tee -a /etc/crontab

C. Web Application Firewall (WAF)
AWS WAF + ALB + EC2 1. User request hits ALB 2. AWS WAF evaluates request against rules 3. If request is malicious (SQL injection, XSS, bot traffic) → Deny 4. If request is legitimate → Forward to EC2

Common WAF Rules:
  • 🚫 Block SQL injection patterns
  • 🚫 Block cross-site scripting (XSS)
  • ⏱️ Rate limiting (block excessive requests from single IP)
  • 🌍 Geographic restrictions
  • 🤖 Bot mitigation (block known bot IPs, enforce captcha)

Key Takeaways

  • Web hosting is the #1 EC2 use case — powering millions of websites, from personal blogs to global e-commerce platforms.

  • Architecture matters — modern web hosting uses layered architecture (web tier, app tier, database tier) with multiple Availability Zones for high availability.

  • Choose the right instance type — T-series (burstable) for spiky traffic, M-series (general purpose) for steady workloads, C-series (compute optimized) for CPU-intensive apps, R-series (memory optimized) for caching/databases.

  • Auto Scaling is essential — Automatically adjust the number of instances based on traffic to optimize cost and performance.

  • Load Balancing is critical — ALB distributes traffic, performs health checks, and enables zero-downtime deployments.

  • Caching layers improve performance — CDN (CloudFront) → Page Cache (Varnish) → Object Cache (Redis) → Database Cache.

  • Security must be layered — VPC, Security Groups, NACLs, WAF, SSL/TLS, and IAM Roles together create defense-in-depth.

  • Monitoring is mandatory — CloudWatch, ALB metrics, custom metrics, and synthetics provide full observability.

  • Automation saves time — Use User Data, custom AMIs, and Infrastructure as Code (CloudFormation/Terraform) for repeatable deployments.

  • Cost optimization is continuous — Right-size instances, use Spot/Reserved/Savings Plans, and set up budgets and alerts.
