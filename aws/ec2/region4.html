2.2 Availability Zones (AZs)

Availability Zones (AZs) are the building blocks of AWS's high-availability and fault-tolerant infrastructure. While an AWS Region is a distinct geographical location, an Availability Zone is a fully isolated data center within that Region.

Understanding AZs is crucial for designing resilient, highly available applications that can withstand infrastructure failures.
🔌 AZs 🏗️ infrastructure ⚡ high availability
🗺️

What is an Availability Zone (AZ)?

An Availability Zone (AZ) is one or more discrete data centers with redundant power, networking, and connectivity within an AWS Region. Each AZ is designed to be physically and logically isolated from failures in other AZs.

Key Characteristics:
CharacteristicDescription
Physical IsolationEach AZ is located in a separate facility, miles away from other AZs in the same Region
Independent InfrastructureEach AZ has its own power source, cooling, and networking equipment
Low-Latency ConnectivityAZs are connected via redundant, ultra-low-latency fiber links (< 5ms round-trip latency)
Logical IsolationAZs are independent failure domains — a failure in one AZ does not affect others
Minimum of 3 AZsEvery AWS Region launched after 2014 has a minimum of 3 AZs

How AZs are Structured

Physical Infrastructure:
  • 🏢 Data Centers: Each AZ typically contains one or more data centers. Large AZs may have multiple buildings.
  • ⚡ Power: Each AZ has independent, redundant power feeds from multiple utility substations and backup generators.
  • ❄️ Cooling: Redundant cooling systems ensure servers operate at optimal temperatures.
  • 🌐 Networking: Each AZ has multiple, redundant network paths with high-bandwidth connections to other AZs.
  • 🔒 Security: Physical security includes 24/7 guards, biometric access controls, and surveillance systems.

Logical Structure:

Why Availability Zones Matter

1. High Availability (HA)
By distributing your application across multiple AZs, you ensure that if one AZ experiences a failure, your application continues running from another AZ. This is the foundation of achieving 99.99% (four nines) availability SLA.

2. Fault Isolation
AZs are isolated failure domains. A catastrophic event affecting one AZ — such as a power outage, flood, or network disruption — will not impact other AZs in the same Region.

3. Disaster Recovery (DR)
While AZs provide regional-level redundancy, for true DR you should also consider multi-Region deployments. However, for most applications, distributing across multiple AZs is the first and most important step.

4. Scalability
By using multiple AZs, you can scale your application horizontally across more resources, as each AZ has its own compute, storage, and networking capacity.

EC2 Auto Scaling Across AZs

Auto Scaling Groups can be configured to distribute EC2 instances across multiple Availability Zones, ensuring that the application remains available even if an entire AZ fails.
# Create Auto Scaling Group across multiple AZs aws autoscaling create-auto-scaling-group \ --auto-scaling-group-name my-asg \ --launch-template LaunchTemplateName=my-template \ --min-size 2 \ --max-size 10 \ --desired-capacity 2 \ --vpc-zone-identifier "subnet-12345678,subnet-87654321,subnet-abcdef12"

Best Practices

  • Always Use at Least 2 AZs: For production workloads, never deploy in a single AZ.

  • Use 3 AZs for Critical Workloads: For 99.99% availability, 3 AZs provide better fault tolerance and eliminate "split-brain" scenarios in distributed systems.

  • Distribute Resources Evenly: Use Auto Scaling Groups to maintain an even distribution of instances across AZs.

  • Use Multi-AZ Managed Services: Use RDS Multi-AZ, ELB Multi-AZ, and other managed services that provide built-in cross-AZ resilience.

  • Test AZ Failover: Regularly test your application's behavior during AZ failures to ensure it recovers gracefully.

Review Questions

Q1 – Q5
Q1: What is the primary purpose of Availability Zones in AWS?
Answer: The primary purpose of Availability Zones (AZs) is to provide fault isolation and high availability. Each AZ is a physically separate data center with independent power, cooling, and networking. By deploying your application across multiple AZs, you ensure that a failure in one data center does not impact your application's overall availability. This is the foundation of building resilient, highly available applications in the cloud.
Q2: How many Availability Zones does a typical AWS Region have?
Answer: Most AWS Regions launched after 2014 have a minimum of 3 Availability Zones. Some older Regions (like us-west-1 in Northern California) may have 2 AZs. Larger Regions like us-east-1 (N. Virginia) have 6 AZs. Always check the specific Region's AZ count when planning your architecture.
Q3: What is the relationship between a Region and an Availability Zone?
Answer: An AWS Region is a geographical area that contains multiple Availability Zones. Each Availability Zone is an isolated data center within that Region. Availability Zones are connected by redundant, ultra-low-latency fiber links (< 5ms round-trip latency), allowing them to function as a single, highly available cluster. The Region provides a logical boundary for your resources, while AZs provide physical isolation for fault tolerance.
Q4: Why does AWS map AZ names differently across accounts?
Answer: AWS intentionally randomizes the mapping of AZ names (a, b, c) across accounts to prevent customers from assuming that us-east-1a in one account is the same physical data center as us-east-1a in another account. This design ensures a more balanced distribution of workloads across the actual physical infrastructure. For example, Account A's us-east-1a might be physically located in Data Center X, while Account B's us-east-1a might be in Data Center Y.
Q5: How can you use Availability Zones to improve application reliability?
Answer: You can improve application reliability using Availability Zones in several ways:
  • Multi-AZ Deployment: Deploy your EC2 instances across at least 2 AZs using an Auto Scaling Group.
  • Load Balancing: Use an Application Load Balancer (ALB) that routes traffic to instances in all available AZs.
  • Database Replication: Use RDS Multi-AZ for automatic failover to a standby instance in a different AZ.
  • Data Replication: Use EBS snapshots to back up data to another AZ or Region.
  • Distributed Caching: Use ElastiCache clusters that distribute nodes across AZs.

Review Questions

Q6 – Q10
Q6: What is the maximum latency between Availability Zones in the same Region?
Answer: AWS ensures that the round-trip latency between Availability Zones in the same Region is typically less than 5 milliseconds. This ultra-low latency is achieved through dedicated, redundant fiber connections between the data centers, enabling them to function as a single, highly available cluster.
Q7: Can an EC2 instance be moved from one Availability Zone to another?
Answer: An EC2 instance cannot be directly moved from one Availability Zone to another. However, you can achieve the same effect by:
  • Taking a snapshot of the instance's EBS volumes
  • Creating an AMI from the instance
  • Launching a new instance in the desired AZ using the AMI
  • Terminating the original instance
This process is effectively a migration, not a move, and should be carefully planned to minimize downtime.
Q8: What happens to resources in an Availability Zone during a failure?
Answer: During an AZ failure:
  • All EC2 instances in that AZ become unreachable
  • EBS volumes attached to those instances become unavailable
  • Databases without Multi-AZ support in that AZ become unavailable
  • Resources in other AZs remain unaffected
  • The load balancer automatically routes traffic away from the failed AZ (if properly configured)
Best Practice: Always deploy your application across at least 2 AZs to ensure availability during an AZ failure.
Q9: What is the difference between an Availability Zone and a Local Zone?
Answer:
AspectAvailability Zone (AZ)Local Zone (LZ)
LocationWithin an AWS RegionOn the edge, outside the Region
Latency< 5ms round-trip to other AZs< 5ms round-trip to the Region
ServicesFull AWS servicesSubset of AWS services
Use CaseGeneral-purpose, high availabilityLow-latency applications, edge computing
Local Zones are designed for applications that require single-digit millisecond latency to users in specific metropolitan areas.
Q10: How do Auto Scaling Groups work with Availability Zones?
Answer: Auto Scaling Groups (ASGs) support multi-AZ deployment by:
  • Distributing EC2 instances evenly across the specified Availability Zones
  • Maintaining a minimum number of instances in each AZ
  • Replacing failed instances with new ones in the same AZ
  • Rebalancing the distribution if there's an imbalance
Best Practice: Always configure your ASG to use at least 2 AZs for production workloads.

Key Takeaways

  • An AZ is an isolated data center within an AWS Region, with independent power, cooling, and networking.

  • AZs are connected by ultra-low-latency fiber links (< 5ms round-trip), enabling them to function as a single cluster.

  • Every Region has a minimum of 3 AZs (except for some older Regions).

  • Multi-AZ deployment is the foundation of high availability — distributing resources across multiple AZs protects against data center failures.

  • AZ names are randomized across AWS accounts to ensure balanced workload distribution.

  • Managed services like RDS and ELB provide built-in Multi-AZ support for automatic failover.

  • Use Auto Scaling Groups to maintain an even distribution of EC2 instances across AZs.

  • AZs are isolated failure domains — a failure in one AZ does not impact other AZs.

  • Local Zones extend AZ functionality to the edge for ultra-low-latency applications.

  • Disaster Recovery (DR) requires multi-Region deployment, not just multi-AZ.

Multi-AZ Architecture
Objective: Design and deploy a highly available web application across 2 Availability Zones.

Steps:
  1. Create a VPC with 2 public subnets and 2 private subnets across 2 AZs.
  2. Deploy an Internet Gateway and a NAT Gateway.
  3. Set up an Application Load Balancer that spans both AZs.
  4. Launch an Auto Scaling Group with instances distributed across both AZs.
  5. Configure RDS Multi-AZ for automatic database failover.
  6. Test AZ failover by simulating an AZ failure.

✅ Expected Outcome: A fully functional web application that remains available during an AZ failure.
