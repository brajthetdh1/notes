4.4.1 Creating an AMI from an Instance

Creating a custom Amazon Machine Image (AMI) from an existing EC2 instance is a fundamental skill for any AWS practitioner. This process captures the entire state of your instance — including the operating system, applications, configurations, and data — into a reusable template that can be used to launch identical instances.
🖼️ AMI creation 📋 custom AMI 🔄 instance → AMI
📖

Why Create an AMI from an Instance?

Creating an AMI from an existing instance is the most common method for building custom images because it allows you to:

  • ✅ Standardize Your Environment: Once you have a perfectly configured instance, capture it as an AMI and use it to launch multiple identical instances.

  • ⚡ Reduce Deployment Time: Instead of manually configuring each instance, launch from a pre-configured AMI that is ready to serve traffic immediately.

  • 📈 Enable Scaling: Auto Scaling Groups can use your custom AMI to launch new instances with the exact configuration needed.

  • 🏆 Implement Golden Images: Create a "golden image" that serves as the single source of truth for your infrastructure.

  • 🔄 Simplify Disaster Recovery: Rebuild infrastructure quickly in another region or account using your custom AMI.
📖 benefits 🏆 golden image ⚡ speed
📋

Prerequisites

Before you create an AMI from an instance, ensure the following:

🔄 Instance State
The instance must be in a running or stopped state
💾 EBS-Backed
The instance must be EBS-backed (not instance store-backed)
🔑 Permissions
You must have ec2:CreateImage permission for the instance
🧹 Clean Instance
Remove sensitive data, temporary files, and logs before creating the AMI
✅ Application Consistent
Ensure all applications are in a consistent state (data written to disk)

Method 2: Using the AWS CLI

The AWS CLI provides a faster, scriptable way to create AMIs.

Basic Command:
aws ec2 create-image \ --instance-id i-1234567890abcdef0 \ --name "my-web-server-ami-v1.0" \ --description "AMI for production web servers" \ --no-reboot \ --tag-specifications 'ResourceType=image,Tags=[{Key=Environment,Value=Production},{Key=Version,Value=v1.0}]'

Example with Block Device Mapping:
aws ec2 create-image \ --instance-id i-1234567890abcdef0 \ --name "my-web-server-ami-v1.0" \ --description "AMI for production web servers" \ --block-device-mappings \ 'DeviceName=/dev/xvda,Ebs={VolumeSize=40,VolumeType=gp3,DeleteOnTermination=true}' \ 'DeviceName=/dev/sdf,Ebs={VolumeSize=100,VolumeType=io2,Iops=5000,DeleteOnTermination=false}'

📋 Response Output:
{ "ImageId": "ami-1234567890abcdef0" }
💻 CLI ⚙️ create-image 📋 block-device-mappings
🔧

Method 3: Using AWS Systems Manager (SSM)

For a more automated and controlled process, you can use SSM Automation to create AMIs.
aws ssm start-automation-execution \ --document-name AWS-UpdateLinuxAmi \ --parameters "{\"InstanceId\":[\"i-1234567890abcdef0\"],\"SourceAmiId\":[\"ami-12345678\"],\"AutomationAssumeRole\":[\"arn:aws:iam::123456789012:role/SSMAutomationRole\"]}"

💡 This method is more advanced and can include patching, validation, and rollback capabilities.
🔧 SSM 🤖 automation 📋 patching
💡

Best Practices: The "No Reboot" Option

The No reboot option controls whether EC2 reboots your instance during AMI creation:

OptionEffectWhen to Use
Reboot (default) EC2 gracefully shuts down, creates snapshot, then reboots Production workloads where data consistency is critical
No reboot EC2 creates a live snapshot without stopping the instance Non-production workloads, or when downtime is not acceptable

⚠️ Important Considerations:
  • If you choose No reboot: No guarantee of data consistency; database servers will have inconsistent data
  • If you choose Reboot: Instance is temporarily unavailable (1-5 minutes); all writes are flushed to disk
💡 no reboot 🔄 consistency ⚡ downtime
🧹

Best Practices: Clean Up Before AMI Creation

Run these commands on the instance before creating an AMI to reduce size and remove sensitive data:

# Amazon Linux / RHEL / CentOS sudo dnf clean all sudo rm -rf /var/log/* /tmp/* /var/tmp/* history -c sudo rm -rf ~/.ssh/authorized_keys sudo rm -rf ~/.bash_history # Ubuntu / Debian sudo apt clean sudo rm -rf /var/log/* /tmp/* /var/tmp/* history -c sudo rm -rf ~/.ssh/authorized_keys sudo rm -rf ~/.bash_history

📌 Best Practices:
  • 🏷️ Tag Your AMIs: Environment, Version, Build Date, CreatedBy, Application
  • 🌍 Copy to All Regions: Use aws ec2 copy-image for global deployment
  • 🤖 Automate: Use EC2 Image Builder, Packer, or SSM Automation

4.4.2 Deregistering an AMI

📖 Complete Theory: Why Deregister AMIs?

Deregistering an AMI is the process of removing an AMI from your AWS account so that it can no longer be used to launch new instances. You should deregister AMIs when:
  • They are no longer used (old versions are no longer needed)
  • You want to reduce costs (AMI deregistration is free, but associated EBS snapshots incur storage costs)
  • You need to rotate AMIs (replacing old AMIs with newer, more secure versions)
  • You are cleaning up unused resources (maintaining a lean AWS environment)

⚠️ Important: Deregistering an AMI does NOT affect any instances already launched from that AMI. Those instances continue running normally.
🗑️ deregister 💰 cost 🔄 rotation
🔄

Deregistering an AMI: CLI

Basic Deregistration Command:
aws ec2 deregister-image --image-id ami-1234567890abcdef0

Deregister AMI and Delete Associated Snapshots (2025 Feature):
aws ec2 deregister-image \ --image-id ami-1234567890abcdef0 \ --delete-associated-snapshots

⚠️ Important: If a snapshot is associated with multiple AMIs, it will not be deleted even if you specify --delete-associated-snapshots. The AMI will still be deregistered.

Verify Deregistration:
# Check if AMI still exists aws ec2 describe-images --image-ids ami-1234567890abcdef0 # If deregistered, this will return an error or empty result # View snapshots still in the account aws ec2 describe-snapshots --owner-ids self

Cleanup & Deprecation

Identifying Snapshots Associated with an AMI:
# Find snapshots associated with a specific AMI aws ec2 describe-images \ --image-ids ami-1234567890abcdef0 \ --query 'Images[0].BlockDeviceMappings[*].Ebs.SnapshotId' \ --output text

Deleting Snapshots:
aws ec2 delete-snapshot --snapshot-id snap-1234567890abcdef0

Deprecating an AMI (instead of immediate deregistration):
aws ec2 enable-image-deprecation \ --image-id ami-1234567890abcdef0 \ --deprecate-at "2027-01-01T00:00:00Z"

💡 Benefits of Deprecation:
  • Allows a transition period before permanent removal
  • Maintains availability for existing processes
  • Enables easier tracking of legacy AMIs

Important Considerations

✅ Instances Continue Running
Deregistering an AMI has no impact on running instances
📸 Snapshots Are Not Deleted
Snapshots remain unless you use --delete-associated-snapshots
💰 Cost Impact
You continue to incur storage costs for snapshots until you delete them
📦 Backup AMIs
AMIs managed by AWS Backup must be managed through AWS Backup
🔄 Snapshots with Multiple AMIs
If a snapshot is associated with multiple AMIs, it will not be deleted even with --delete-associated-snapshots
🌍 Cross-Region Copies
If an AMI has been copied to other regions, those copies remain and must be deregistered separately

Key Takeaways

  • Creating an AMI from an instance captures the entire system state into a reusable template.

  • You can create an AMI using the Console, CLI, or AWS Systems Manager.

  • The No reboot option avoids downtime but does not guarantee data consistency.

  • Clean up your instance before creating an AMI to reduce size and remove sensitive data.

  • Tag your AMIs to enable efficient management and organization.

  • Deregistering an AMI removes it from your account and prevents new instance launches.

  • Running instances are unaffected by AMI deregistration.

  • Associated snapshots are not automatically deleted unless you use --delete-associated-snapshots.

  • Use deprecation instead of immediate deregistration to allow a transition period.

  • Automate AMI creation using EC2 Image Builder, Packer, or SSM Automation.

Review Questions

Q1: What happens to running instances when you deregister an AMI?
Answer: Deregistering an AMI has no effect on any running instances that were launched from that AMI. They continue to run normally. The only impact is that you cannot launch new instances from the deregistered AMI.
Q2: How can you automatically delete snapshots when deregistering an AMI?
Answer: You can use the AWS CLI with the --delete-associated-snapshots flag:
aws ec2 deregister-image --image-id ami-12345678 --delete-associated-snapshots
However, if a snapshot is associated with multiple AMIs, it will not be deleted even with this flag.
Q3: How do you clean up snapshots after deregistering an AMI?
Answer: After deregistering an AMI, the underlying snapshots remain in your account. To clean them up:
  • Identify the snapshots using aws ec2 describe-images --image-ids ami-12345678
  • Delete each snapshot using aws ec2 delete-snapshot --snapshot-id snap-12345678
  • Alternatively, use the --delete-associated-snapshots flag during deregistration
Q4: What is the difference between deregistering and deprecating an AMI?
Answer:
  • Deregistering removes the AMI from your account permanently. You cannot launch new instances from it.
  • Deprecating marks the AMI as deprecated but keeps it in your account. You can still launch instances until the deprecation date.
Q5: What are the considerations when deregistering an AMI?
Answer:
  • Deregistering an AMI does not affect running instances
  • Snapshots remain unless you use --delete-associated-snapshots
  • Storage costs continue for kept snapshots
  • AWS Backup-managed AMIs must be managed through AWS Backup
  • Snapshots shared with multiple AMIs will not be deleted
  • Cross-region copies must be deregistered separately
