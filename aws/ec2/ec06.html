1.2.4 Batch Processing and High-Performance Computing (HPC)

Batch processing and High-Performance Computing (HPC) represent two of the most demanding and transformative use cases for Amazon EC2. These workloads require massive computational power, often running thousands of tasks in parallel, and have unique requirements for networking, storage, and orchestration.

EC2 provides specialized infrastructure and services designed specifically for these demanding workloads.
⚡ batch 🚀 HPC 📊 compute
🧩

Understanding Batch Processing and HPC

While often discussed together, batch processing and HPC serve different purposes with distinct technical requirements.

📦 Batch Processing
Running Jobs at Scale

Characteristics:
  • Job-Oriented: Work organized into discrete units
  • Fault-Tolerant: Individual failures don't impact others
  • Parallelizable: Jobs run simultaneously
  • Ephemeral: Resources provisioned only when needed

Common Workloads:
  • Data transformation & ETL
  • Image/video processing
  • Financial risk calculations
  • Genomic sequence analysis
  • Rendering & media production
🔬 High-Performance Computing
Complex Simulations

Characteristics:
  • Tightly Coupled: Nodes communicate frequently
  • Low Latency: Network performance is critical
  • High Throughput: Massive data processing
  • Scientific Focus: Simulations, modeling, research

Common Workloads:
  • Computational Fluid Dynamics (CFD)
  • Weather forecasting & climate modeling
  • Molecular dynamics & drug discovery
  • Crash simulations & structural analysis
  • Seismic reservoir simulations

AWS Batch

Managed Batch Processing
AWS Batch is the primary service for batch processing on EC2. It efficiently runs hundreds of thousands of computing jobs by dynamically provisioning EC2 instances based on resource requirements.

Core Components:
  • 1. Compute Environments: Contain the resources used to execute jobs. Managed compute environments automatically provision EC2 instances using ECS, Fargate, or EKS resources.
  • 2. Job Definitions: Define the type of job — specifying Docker image, required GPU/CPU resources, disk mounts, and environment variables.
  • 3. Job Queues: Route waiting jobs to compute environments. Jobs exit in FIFO order unless a Scheduling Policy is specified.
  • 4. Scheduling Policies: Control how and when jobs exit the job queue and enter the compute environment.

Cost Optimization Strategies:
⚡ Spot Instances: Batch allows fault-tolerant workloads to leverage Spot Instances with up to 90% discounts.
// CDK Example: Fargate Compute Environment with Spot Vpc vpc = new Vpc(this, "VPC"); FargateComputeEnvironment.Builder.create(this, "myFargateComputeEnv") .vpc(vpc) .spot(true) .build();
Spot Bid Percentage:
Batch allows specifying the percentage of the On-Demand price to bid for Spot instances. Default is 100% (recommended).
// Only use Spot instances at most 20% of On-Demand price ManagedEc2EcsComputeEnvironment.Builder.create(this, "myEc2ComputeEnv") .vpc(vpc) .spot(true) .spotBidPercentage(20) .build();

  • For Spot workloads: Use SPOT_PRICE_CAPACITY_OPTIMIZED (default if spot is enabled) to minimize interruption risk while optimizing cost
  • For On-Demand: Use BEST_FIT_PROGRESSIVE (default) to maximize throughput while maintaining cost efficiency

Instance Type Selection in Batch

Batch provides several ways to configure instance types. As of November 2025, optimal is dynamically updated and behaves the same as default_x86_64, automatically selecting cost-effective instance types from m6i, c6i, r6i, and c7i families.

// Use default x86_64 instances (recommended) ManagedEc2EcsComputeEnvironment.Builder.create(this, "X86_64Ec2ComputeEnv") .vpc(vpc) .defaultInstanceClasses(List.of(DefaultInstanceClass.X86_64)) .build(); // Use ARM64 instances (e.g., m6g, c6g, r6g, c7g families) ManagedEc2EcsComputeEnvironment.Builder.create(this, "Arm64Ec2ComputeEnv") .vpc(vpc) .defaultInstanceClasses(List.of(DefaultInstanceClass.ARM64)) .build(); // Use only specific instance types ManagedEc2EcsComputeEnvironment.Builder.create(this, "M5AdLargeEc2ComputeEnv") .vpc(vpc) .useOptimalInstanceClasses(false) .instanceTypes(List.of(InstanceType.of(InstanceClass.M5AD, InstanceSize.LARGE))) .build();

Amazon ParallelCluster

HPC Cluster Management
Amazon ParallelCluster is an AWS-supported open-source cluster management tool that simplifies deploying and managing HPC clusters on AWS.

Best Practices for ParallelCluster:

1. Head Node Selection:
The head node orchestrates scaling logic and is responsible for attaching new nodes to the scheduler. For large clusters, provide extra compute capacity to the head node. Consider network bandwidth and EBS bandwidth for shared file systems like NFS.

2. Network Performance Optimization:
Placement Groups: Configure each Slurm queue to use a cluster placement group for low-latency, high-throughput communication. Starting with ParallelCluster 3.3.0, each compute resource is assigned its own managed placement group to reduce insufficient capacity errors.
# Placement Group Configuration Networking: PlacementGroup: Enabled: true Name: your-placement-group-name
Enhanced Networking: Use current generation instances that support enhanced networking for optimal network performance.

Elastic Fabric Adapter: Choose EFA network interfaces for high levels of scalable instance-to-instance communication. EFA's custom-built OS bypass hardware enhances communications with cloud elasticity and flexibility.
# EFA Configuration ComputeResources: - Name: your-compute-resource-name Efa: Enabled: true
3. Budget and Cost Management:
Use AWS Budgets actions to create budget thresholds and alerts. Similarly, create CloudWatch billing alarms to monitor estimated AWS charges.

4. Cluster Migration:
To move a cluster to a new ParallelCluster version:
  • Save personal data in external volumes (EFS, FSx for Lustre) created outside the cluster
  • Use existing file system definitions (VolumeId, FileSystemId) so they're preserved when deleting the cluster
  • Use custom bootstrap actions rather than custom AMIs to avoid recreating AMIs for each version release

Real-World Case Study

Adobe's Large-Scale ML Inferencing on AWS Batch
Adobe's Search, Discovery, and Content (SDC) team manages billions of image assets generated using Adobe Firefly and the Adobe Stock ecosystem. Processing these assets for semantic search requires running AI models on hundreds of millions of assets with thousands of parallel inference jobs.

Challenges:
  • Processing 29+ billion assets across multiple Adobe products
  • Embedding models constantly evolving, requiring periodic re-computation
  • Different models require different GPU architectures
  • Sequential processing would take weeks to complete

Solution Architecture with AWS Batch:
1. Data Preparation: Adobe separated dataset preparation into its own AWS Batch job. This preprocessing job runs multiple workers to shard the S3 bucket and compress object addresses into compact binary files.

2. Distributed Inferencing:
  • AWS Batch provisions EC2 GPU nodes (G5, G6, G6e instances)
  • Each node receives AWS_BATCH_JOB_NODE_INDEX and AWS_BATCH_JOB_NUM_NODES environment variables
  • Each node downloads only its assigned binary shard based on its index
  • PyTorch DataLoaders stream samples directly from S3 into containers
  • Each node's CPUs handle preprocessing while GPUs run inference

3. GPU Optimization:
  • GPU utilization runs at 100% consistently
  • Data sharding prevents overlapping and ensures balanced throughput
  • Optimal batch sizes experimented with before large runs
  • Data localized in the same AWS region to avoid cross-region charges

Results Achieved:
  • ⚡ 10x faster execution compared to sequential processing
  • 💰 95%+ cost reduction covering both compute and engineering investment
  • Compute time reduced from 30 days to under 20 hours for Adobe Stock image embeddings

Lessons Learned:
  • Efficient data sharding is critical — without it, simple S3 listing can take hours
  • Implement retry mechanisms for S3 rate limits (HTTP 429)
  • Use hybrid compute definitions across multiple GPU families to address availability challenges
  • Process data in optimal batches for GPU workloads

Cost Optimization for Batch and HPC

1. Spot Instances:
Batch workloads that are fault-tolerant or stateless can leverage Spot Instances with up to 90% discounts.

2. Capacity Blocks for ML:
Reserve GPU capacity for short-term predictable workloads (3-6 months).

3. Budget Controls:
  • Limit who can submit jobs via LDAP groups
  • Limit instance types that can be provisioned (e.g., exclude GPU instances unless required)
  • Force jobs to run only on Reserved Instances
  • Limit concurrent jobs or provisioned instances

4. Instance Right-Sizing:
Use the optimal instance type for each workload. For compute-intensive workloads not requiring HPC-specific features, C-family instances offer the best price-performance.

⚠️ Important: HPC instances (Hpc8a, Hpc7a, Hpc6id, Hpc7g, Hpc6a) do NOT support Spot — they require On-Demand or Reserved capacity.

Key Takeaways

  • Batch processing and HPC represent distinct workload types with different technical requirements — batch for independent parallel jobs, HPC for tightly coupled simulations.

  • C-family instances (C9g, C7g, C5) provide the best price-performance for CPU-bound workloads, with Graviton-based options offering significant cost savings.

  • HPC-optimized instances (Hpc8a, Hpc7a, Hpc6id, Hpc7g, Hpc6a) are purpose-built with high core density, high memory bandwidth, and EFA enabled by default, delivering up to 300 Gbps network bandwidth.

  • AWS Batch simplifies running hundreds of thousands of jobs by managing compute environments, job queues, definitions, and scaling automatically.

  • Spot Instances can reduce batch processing costs by up to 90% for fault-tolerant workloads.

  • Allocation strategies (BEST_FIT, BEST_FIT_PROGRESSIVE, SPOT_CAPACITY_OPTIMIZED) allow fine-tuning cost vs. throughput trade-offs.

  • ParallelCluster provides cluster management for HPC with features like placement groups and EFA to optimize network performance.

  • Adobe's success story demonstrates 95% cost reduction and 10x faster execution using AWS Batch for large-scale ML inference on GPU instances.

  • HPC instances do NOT support Spot — they require On-Demand or Reserved capacity.

  • Graviton5-powered C9g instances (2026) deliver 25% better compute performance and are the first with Nitro Isolation Engine for mathematically proven security.
