P8.1 Create IAM Role

EC2-Secure-Role (S3ReadOnly + SSMManagedInstanceCore)
📖 Theory: Least Privilege IAM Role
The principle of least privilege dictates that an entity should have only the permissions required to perform its function. For EC2 instances, this means:
  • SSMManagedInstanceCore: Enables Systems Manager features (Session Manager, patching)
  • S3ReadOnlyAccess: Allows reading from S3 (e.g., downloading application assets)

Step 1: Create the IAM Role
# Create trust policy document cat > ec2-trust-policy.json <<'EOF' { "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Principal": { "Service": "ec2.amazonaws.com" }, "Action": "sts:AssumeRole" } ] } EOF # Create the role aws iam create-role \ --role-name EC2-Secure-Role \ --assume-role-policy-document file://ec2-trust-policy.json \ --description "EC2 role with least privilege - SSM + S3 ReadOnly" # Attach SSM policy aws iam attach-role-policy \ --role-name EC2-Secure-Role \ --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore # Attach S3 ReadOnly policy aws iam attach-role-policy \ --role-name EC2-Secure-Role \ --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess # Create instance profile aws iam create-instance-profile \ --instance-profile-name EC2-Secure-Role-Profile # Add role to instance profile aws iam add-role-to-instance-profile \ --role-name EC2-Secure-Role \ --instance-profile-name EC2-Secure-Role-Profile
✅ Verification Checklist:
□ IAM role EC2-Secure-Role created
□ AmazonSSMManagedInstanceCore policy attached
□ AmazonS3ReadOnlyAccess policy attached
□ Instance profile EC2-Secure-Role-Profile created
🔐 P8.1 📋 IAM role 🔒 least privilege

P8.2 Launch Instance

No Key Pair Required
📖 Theory: Key Pair-less Launch
When you use SSM Session Manager for access, you don't need a key pair. This eliminates the risk of SSH key mismanagement and reduces the attack surface.

Step 1: Launch the Instance
# Get the AMI ID for Amazon Linux 2023 AMI_ID=$(aws ssm get-parameters --names /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 --query 'Parameters[0].Value' --output text) # Launch the instance with IAM role INSTANCE_ID=$(aws ec2 run-instances \ --image-id $AMI_ID \ --instance-type t3.micro \ --associate-public-ip-address \ --iam-instance-profile Name=EC2-Secure-Role-Profile \ --user-data "#!/bin/bash sudo dnf install -y httpd sudo systemctl start httpd sudo systemctl enable httpd echo 'Secure Instance - \$(hostname)' > /var/www/html/index.html" \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=Secure-Instance-Demo}]' \ --query 'Instances[0].InstanceId' --output text) echo "Instance ID: $INSTANCE_ID"
⚠️ No key pair selected — You will need to connect using SSM Session Manager.

✅ Verification Checklist:
□ Instance launched with IAM role attached
□ No key pair associated
□ Instance is running (state: running)
🖥️ P8.2 🔑 no key pair ⚡ SSM access

P8.3 Connect via SSM Session Manager

Port 22 Closed
📖 Theory: Secure, Keyless Access
SSM Session Manager provides secure shell access without open inbound ports or SSH keys. The connection is initiated from the instance to AWS over HTTPS.

Step 1: Verify the Instance is Managed
aws ssm describe-instance-information \ --filters "Key=InstanceIds,Values=$INSTANCE_ID"
Step 2: Start a Session
aws ssm start-session --target $INSTANCE_ID
Step 3: Verify SSH is Closed
sudo systemctl status sshd

Step 4: Verify IAM Role is Attached
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600") curl -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/

✅ Verification Checklist:
□ SSM Agent registered with Systems Manager
□ Session started successfully
□ SSH service is masked/inactive
□ IAM role is visible in instance metadata
🔗 P8.3 🖥️ Session Manager 🔒 port 22 closed

P8.4 Configure Security Groups

Allow HTTP/HTTPS only from ALB SG
📖 Theory: Security Group Least Privilege
Security groups should only allow traffic that is absolutely necessary. For web servers, this means:
  • HTTP (port 80) and HTTPS (port 443) from the ALB security group only
  • No direct internet access to the web server

Step 1: Create Web Server SG
SG_WEB=$(aws ec2 create-security-group \ --group-name web-server-sg \ --description "Web server SG - only allow from ALB" \ --vpc-id $VPC_ID \ --query 'GroupId' --output text)
Step 2: Create ALB SG
SG_ALB=$(aws ec2 create-security-group \ --group-name alb-sg \ --description "ALB SG - allows internet traffic" \ --vpc-id $VPC_ID \ --query 'GroupId' --output text) aws ec2 authorize-security-group-ingress --group-id $SG_ALB --protocol tcp --port 80 --cidr 0.0.0.0/0 aws ec2 authorize-security-group-ingress --group-id $SG_ALB --protocol tcp --port 443 --cidr 0.0.0.0/0 # Allow ALB to access web server aws ec2 authorize-security-group-ingress \ --group-id $SG_WEB \ --protocol tcp --port 80 \ --source-group $SG_ALB
Step 3: Update Instance's Security Group
aws ec2 modify-instance-attribute \ --instance-id $INSTANCE_ID \ --groups $SG_WEB
✅ Verification Checklist:
□ Web server SG only allows HTTP/HTTPS from ALB SG
□ ALB SG allows HTTP/HTTPS from anywhere
□ Instance security group updated
🛡️ P8.4 🔒 SG least privilege 🔗 SG reference

P8.5 Configure NACLs

Block SSH from 0.0.0.0/0
📖 Theory: NACL Defense-in-Depth
Network ACLs provide an additional layer of security at the subnet level. They are stateless and support both ALLOW and DENY rules. By blocking SSH at the NACL level, we ensure that even if a security group allows SSH, the traffic is blocked at the subnet boundary.

Step 1: Get Subnet and Current NACL
SUBNET_ID=$(aws ec2 describe-instances --instance-ids $INSTANCE_ID --query 'Reservations[0].Instances[0].SubnetId' --output text) NACL_ID=$(aws ec2 describe-network-acls --filters "Name=association.subnet-id,Values=$SUBNET_ID" --query 'NetworkAcls[0].NetworkAclId' --output text)
Step 2: Add SSH Deny Rule to NACL
# Add DENY rule for SSH (port 22) at a low priority aws ec2 create-network-acl-entry \ --network-acl-id $NACL_ID \ --rule-number 100 \ --protocol tcp \ --port-range From=22,To=22 \ --cidr-block 0.0.0.0/0 \ --rule-action deny \ --ingress
Step 3: Test SSH is Blocked
PUBLIC_IP=$(aws ec2 describe-instances --instance-ids $INSTANCE_ID --query 'Reservations[0].Instances[0].PublicIpAddress' --output text) ssh -i your-key.pem ec2-user@$PUBLIC_IP
⚠️ The SSH connection should time out or be rejected because:
  • NACL blocks SSH at the subnet boundary (rule 100)
  • Security group does not allow SSH (only HTTP/HTTPS from ALB)

✅ Verification Checklist:
□ NACL has DENY rule for SSH (port 22) from 0.0.0.0/0
□ SSH connections are blocked at the subnet level
🚫 P8.5 🛡️ NACL 🔒 SSH blocked
✅

P8.6 Test IAM Permissions

📖 Theory: Least Privilege IAM Testing
The EC2 instance should have:
  • ✅ S3 ReadOnly Access: Can list S3 buckets
  • ❌ EC2 Describe: Should fail (no permissions)

P8.6.1: Test S3 Access (Should Work)
aws s3 ls
✅ Works — returns list of buckets


P8.6.2: Test EC2 Describe (Should Fail)
aws ec2 describe-instances
❌ Fails — UnauthorizedOperation


P8.6.3: Verify IAM Role Permissions
aws iam list-attached-role-policies --role-name EC2-Secure-Role --query 'AttachedPolicies[*].PolicyName' --output table

✅ Verification Checklist:
□ aws s3 ls works
□ aws ec2 describe-instances fails
□ IAM policies are correctly attached

P8.7 Enable AWS Config

Monitor SG Changes
📖 Theory: AWS Config for Compliance
AWS Config enables you to assess, audit, and evaluate the configurations of your AWS resources. By enabling Config and creating a rule to monitor Security Group changes, you can detect and alert on security policy violations.

Step 1: Enable AWS Config
# Create S3 bucket for Config logs BUCKET_NAME="config-bucket-$(aws sts get-caller-identity --query 'Account' --output text)" aws s3 mb s3://$BUCKET_NAME # Create SNS topic TOPIC_ARN=$(aws sns create-topic --name config-alerts --query 'TopicArn' --output text) # Enable AWS Config aws configservice put-configuration-recorder \ --configuration-recorder name=default,roleARN=arn:aws:iam::$(aws sts get-caller-identity --query 'Account' --output text):role/aws-service-role/config.amazonaws.com/AWSServiceRoleForConfig \ --recording-group AllSupported=true,IncludeGlobalResourceTypes=true aws configservice put-delivery-channel \ --delivery-channel name=default,s3BucketName=$BUCKET_NAME,snsTopicARN=$TOPIC_ARN aws configservice start-configuration-recorder
Step 2: Create a Config Rule to Monitor SG Changes
aws configservice put-config-rule \ --config-rule '{ "ConfigRuleName": "restricted-ssh", "Description": "Security groups should not allow SSH from 0.0.0.0/0", "Scope": { "ComplianceResourceTypes": ["AWS::EC2::SecurityGroup"] }, "Source": { "Owner": "AWS", "SourceIdentifier": "EC2_SECURITY_GROUP_INBOUND_RESTRICTED_SSH" }, "InputParameters": "{\"restrictedProtocols\":\"tcp=22\",\"allowedCidrs\":\"10.0.0.0/8,192.168.0.0/16\"}" }'
Step 3: Create SNS Subscription for Alerts
aws sns subscribe \ --topic-arn $TOPIC_ARN \ --protocol email \ --notification-endpoint your-email@example.com
✅ Verification Checklist:
□ AWS Config enabled
□ Config recorder started
□ Restricted SSH rule created
□ SNS topic configured for alerts
📊 P8.7 📋 AWS Config 🛡️ compliance

Key Takeaways

  • Least privilege IAM roles limit the blast radius of a compromised instance.

  • SSM Session Manager provides secure access without SSH keys or open inbound ports.

  • Defense in depth uses multiple layers: IAM (least privilege) + Security Groups + NACLs.

  • Security group references (e.g., allowing traffic from ALB SG) are more secure than IP-based rules.

  • NACLs block SSH at the subnet boundary, preventing even misconfigured security groups from exposing SSH.

  • AWS Config provides continuous monitoring and compliance enforcement.

  • No key pair launch is possible when using SSM, reducing SSH key management overhead.

  • IAM least privilege testing: verify that only required permissions work, and all others fail.
