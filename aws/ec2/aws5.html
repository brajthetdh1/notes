8.5 Elastic Load Balancing (ELB)

📖 Complete Theory: The Traffic Distributor

Elastic Load Balancing (ELB) is an AWS service that automatically distributes incoming application traffic across multiple targets, such as EC2 instances, containers, IP addresses, and Lambda functions. It acts as a single point of contact for clients, routing traffic to healthy targets to ensure that your application remains highly available and fault-tolerant.

A load balancer uses listeners to accept incoming traffic on specified protocols and ports (e.g., HTTP on port 80), and target groups to route traffic to registered targets based on health checks and routing rules.

Application Load Balancer (ALB)

Layer 7 — The Intelligent Application Router
The ALB operates at Layer 7 and is designed for modern application architectures. It supports advanced routing features such as path-based and host-based routing, making it ideal for microservices and containerized environments.

Operating at Layer 7: By operating at the application layer, the ALB understands HTTP and HTTPS protocols and can inspect the content of requests to route traffic intelligently.

APPLICATION LOAD BALANCER OPERATION ┌─────────────────────────────────────────────────────────────────────────────────────┐ │ Incoming Request: http://www.example.com/api/users │ └─────────────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────────────────────┐ │ Application Load Balancer (Layer 7) │ │ ┌─────────────────────────────────────────────────────────────────────────┐ │ │ │ Listener Rules: │ │ │ │ ┌─────────────────────────────────────────────────────────────────────┐│ │ │ │ │ Rule 1: IF host-header is 'www.example.com' AND path is '/api/*' │ │ │ │ │ THEN forward to API Target Group │ │ │ │ │ │ │ │ │ │ Rule 2: IF host-header is 'www.example.com' AND path is '/*' │ │ │ │ │ THEN forward to Web Target Group │ │ │ │ └─────────────────────────────────────────────────────────────────────┘│ │ │ └─────────────────────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌──────────────────────────┐ ┌──────────────────────────────────────────────────┐ │ Target Group: API │ │ Target Group: Web │ │ └─ EC2 Instances │ │ └─ EC2 Instances │ └──────────────────────────┘ └──────────────────────────────────────────────────┘

Target Types: ALB supports EC2 Instances, IP Addresses, Containers (ECS/EKS), and Lambda Functions.
Advanced Routing Features:
  • Path-Based Routing: Route /api/* to one target group, /* to another
  • Host-Based Routing: Route api.example.com vs www.example.com
  • Query Parameter and Header Routing: Based on HTTP headers, cookies, or query strings

Key Features:
  • SSL/TLS Termination: Offloads encryption/decryption from backend instances
  • Sticky Sessions: Routes requests from the same client to the same target
  • Slow Start Mode: Gradually increases traffic to new targets
  • Deregistration Delay: Allows in-flight requests to complete
  • Cross-Zone Load Balancing: Distributes traffic evenly across all AZs
  • AWS WAF Integration: Protects against web exploits

ALB Review Questions

Q1: What is the primary purpose of an Application Load Balancer?
The ALB operates at Layer 7 to route incoming HTTP/HTTPS traffic based on the content of the request, such as URL path, host header, and query parameters. It is ideal for modern application architectures, including microservices and container-based applications.
Q2: What types of targets can an ALB route traffic to?
An ALB can route traffic to EC2 instances, IP addresses, containers (in ECS or EKS), and Lambda functions.
Q3: What is the difference between path-based routing and host-based routing?
Path-based routing routes requests based on the URL path (e.g., /api/* to one target group, /* to another). Host-based routing routes requests based on the Host header (e.g., api.example.com to one target group, www.example.com to another).
Q4: What is SSL/TLS termination and why is it beneficial?
SSL/TLS termination is the process of decrypting incoming HTTPS traffic at the load balancer and forwarding it to targets as HTTP. This offloads the CPU-intensive encryption/decryption work from the backend instances.
Q5: How does cross-zone load balancing work with ALB?
With cross-zone load balancing enabled, each target group distributes traffic evenly across all registered targets in all enabled Availability Zones, rather than just within each zone independently.

Network Load Balancer (NLB)

Layer 4 — The High-Performance Traffic Forwarder
The NLB operates at Layer 4 (Transport Layer), routing TCP, UDP, and TLS traffic based on IP protocol and port number. Unlike ALB which inspects HTTP headers, the NLB simply forwards packets without inspecting their content, enabling it to handle millions of requests per second with ultra-low latency.

NETWORK LOAD BALANCER OPERATION ┌─────────────────────────────────────────────────────────────────────────────────┐ │ Incoming Traffic: TCP/UDP/TLS on Port 443 │ └─────────────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────────────────────┐ │ Network Load Balancer (Layer 4) │ │ ┌─────────────────────────────────────────────────────────────────────────┐ │ │ │ Listener: TCP on Port 443 │ │ │ │ Routing: Based on IP protocol and port only │ │ │ │ Actions: Forward to Target Group │ │ │ └─────────────────────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────────────────────┐ │ Target Group │ │ └─ Targets: EC2 instances (registered by IP address) │ │ └─ Protocol: TCP │ │ └─ Health Checks: TCP/HTTP/HTTPS │ └─────────────────────────────────────────────────────────────────────────────────┘

Target Types: NLB supports EC2 Instances, IP Addresses, and Application Load Balancer (as a target).

Key Features:
  • Static IP Addresses: Elastic IP per AZ — critical for IP allowlisting
  • Source IP Preservation: Natively preserves the actual source IP address
  • Multiple Secondary IPs: Up to 8 IPs per NLB, increasing concurrent connections from 64K to 512K per target
  • Listener Rules for Dual-Stack: Route IPv4 vs IPv6 traffic to different target groups
  • TLS Termination: Supports TLS listeners at Layer 4
  • PrivateLink Integration: NLB is the only load balancer type that can be used directly as a PrivateLink endpoint service

NLB Review Questions

Q1: What OSI layer does the Network Load Balancer operate at, and what protocols does it support?
The NLB operates at Layer 4 (Transport Layer). It supports TCP, UDP, TLS, TCP_UDP, and QUIC protocols. This makes it ideal for non-HTTP traffic and workloads that require high throughput.
Q2: What is the primary performance advantage of NLB over ALB?
NLB can handle millions of requests per second with sub-millisecond latency. This is because it operates at Layer 4 and does not inspect application-layer content, enabling it to forward packets with minimal processing overhead.
Q3: How does NLB preserve client source IP addresses?
NLB preserves the client source IP natively. Unlike ALB, which uses the X-Forwarded-For header, NLB maintains the original source IP address when forwarding traffic to targets.
Q4: What is the benefit of the multiple secondary IP addresses feature for NLB?
The feature allows up to 7 additional IPv4 addresses on the NLB's egress interface, increasing concurrent connections per target from 64K to 512K. This reduces TCP ephemeral port allocation errors.

Gateway Load Balancer (GWLB)

Layer 3 — The Transparent Traffic Inspector
The GWLB operates at Layer 3 (Network Layer), making it fundamentally different from ALB (Layer 7) and NLB (Layer 4). It is designed to deploy, scale, and manage third-party virtual appliances such as firewalls, intrusion detection/prevention systems (IDS/IPS), and deep packet inspection (DPI) tools.

The Core Concept: Centralized Inspection
Instead of routing traffic to application servers, the GWLB acts as a transparent gateway that intercepts all IP traffic, inspects it using your chosen virtual appliances, and then forwards it to its final destination. This is known as a "bump-in-the-wire" architecture.

How GWLB Works:
  • GENEVE Protocol: Uses GENEVE on port 6081 to encapsulate and forward traffic
  • Gateway Load Balancer Endpoints (GWLBe): VPC endpoints (PrivateLink) that connect consumer VPCs to the GWLB
  • Flow Stickiness: 5-tuple hash ensures all packets from a connection go to the same appliance
  • Automated Scaling: Scales virtual appliances based on demand
  • LCU Reservation: Reserve capacity for predictable traffic spikes

✅ When to Use GWLB:
  • Next-Generation Firewalls (NGFW): Centrally deploy and scale firewalls
  • IDS/IPS: Monitor network traffic for malicious activity
  • Advanced Packet Analytics: Deep packet inspection and network logging
  • Centralized Security: Manage a single fleet across multiple VPCs and accounts

GWLB Review Questions

Q1: What OSI layer does the Gateway Load Balancer operate at, and what is its primary purpose?
The GWLB operates at Layer 3 (the network layer). Its primary purpose is to simplify the deployment, scaling, and management of third-party virtual appliances (like firewalls and IDS/IPS) by acting as a transparent network gateway.
Q2: How does GWLB ensure that traffic from a single connection is consistently sent to the same virtual appliance?
GWLB uses flow stickiness by creating a 5-tuple hash (based on protocol, source/destination IP, and source/destination port). This hash ensures that all packets belonging to the same connection are routed to the same target appliance.
Q3: What is the role of the Gateway Load Balancer Endpoint (GWLBe)?
The GWLBe is a VPC endpoint (powered by PrivateLink) deployed in the consumer VPC. It intercepts traffic (via route table entries) and securely forwards it to the Gateway Load Balancer and its appliances in the service provider VPC.
Q4: What protocol does GWLB use to communicate with its target virtual appliances?
GWLB uses the GENEVE (Generic Network Virtualization Encapsulation) protocol on port 6081 to encapsulate and forward IP packets between the load balancer and the virtual appliances.

Classic Load Balancer (CLB)

Deprecated — The Legacy Load Balancer
The Classic Load Balancer (CLB) is the original load balancer from Elastic Load Balancing, providing basic load balancing across multiple EC2 instances at both the request level (Layer 7) and the connection level (Layer 4). It is now considered legacy and officially deprecated.

⚠️ The Legacy Status: Deprecated & Security-Stuck

The most critical fact about CLB is that it is no longer receiving updates. The Classic Load Balancer stopped receiving new TLS/Security policy updates after 2017, meaning it does not support modern protocols like TLS v1.3.

This puts CLB on a deprecated trajectory. While AWS has not announced an immediate retirement date, the recommendation for new deployments is unambiguous: use ALB or NLB.

How CLB Works:
  • Configured with listeners that check for connection requests
  • Each listener uses a front-end (client → LB) and back-end (LB → instances) protocol and port
  • Basic load balancing across registered EC2 instances
  • Limited health checks (ping path)

CLB Review Questions

Q1: What is the Classic Load Balancer and why is it considered deprecated?
The CLB is the original AWS load balancer, supporting both Layer 4 and Layer 7 traffic. It is considered deprecated because it has not received new security policy updates since 2017 and does not support modern protocols like TLS v1.3. AWS strongly recommends migrating to ALB (for Layer 7) or NLB (for Layer 4).
Q2: What are the key limitations of Classic Load Balancer compared to ALB and NLB?
Key limitations include: frozen security policies (no TLS v1.3), no support for multiple SSL certificates (no SNI), limited routing capabilities (no path/host-based routing), and support for only EC2 instances as targets.
Q3: What is the recommended AWS migration path for Classic Load Balancer users?
AWS recommends migrating to ALB for Layer 7 (HTTP/HTTPS) features such as path-based routing and advanced request handling, and NLB for Layer 4 (TCP/UDP) traffic, high performance, or static IP addresses.

ELB + Auto Scaling Groups

A Complete, Highly Available Architecture
ELB integrates seamlessly with Auto Scaling Groups (ASGs) to provide a complete, highly available architecture. The ASG automatically scales the number of EC2 instances based on demand, and the load balancer distributes incoming traffic to the healthy instances.

ELB Pricing

Elastic Load Balancing pricing consists of two main components:

1. Hourly Charges: You are charged for each hour (or partial hour) that your load balancer is running.

2. LCU Charges (ALB & NLB): Application and Network Load Balancers use a metric called Load Balancer Capacity Units (LCUs) to measure performance. An LCU is a measure of:
  • New connections
  • Concurrent connections
  • Processed bytes
  • Rule evaluations

Free Tier:
The AWS Free Tier includes:
  • 750 hours per month (shared between Classic, Application, and Network load balancers)
  • 15 GB of data processing for Classic load balancers, or 15 LCUs for Application load balancers

Key Takeaways

  • Elastic Load Balancing distributes incoming traffic across multiple targets to ensure high availability and fault tolerance.

  • ALB (Layer 7) is ideal for HTTP/HTTPS applications with advanced routing (path, host, header-based). Supports EC2, IP, Lambda, and containers as targets.

  • NLB (Layer 4) delivers ultra-low latency and millions of requests per second. Supports static IP addresses, source IP preservation, and PrivateLink integration.

  • GWLB (Layer 3) provides transparent inspection for third-party virtual appliances (firewalls, IDS/IPS) using GENEVE encapsulation.

  • CLB is deprecated — no new security policies since 2017, no TLS v1.3 support. Migrate to ALB or NLB.

  • ELB integrates seamlessly with Auto Scaling Groups — new instances are automatically registered, unhealthy instances are deregistered.

  • NLB is the only load balancer that can be used directly as a PrivateLink endpoint service.

  • Pricing consists of hourly charges and LCU charges (for ALB/NLB). Free tier includes 750 hours/month and 15 GB/15 LCUs.
