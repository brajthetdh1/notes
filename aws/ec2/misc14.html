14.4 Common Fixes

📖 Complete Theory: Diagnosing and Fixing EC2 Issues

When an EC2 Linux instance becomes unreachable — failing status checks, refusing SSH connections, or stuck during boot — the fixes can be methodically applied once you diagnose the root cause. This section covers the most common EC2 issues and their fixes, organized by symptom.

For each fix, two recovery paths are provided: using the EC2 Serial Console (where supported) and the Rescue Instance method (the universal fallback).

Fix 1: SSH Permission Denied / Lost SSH Key

🛠️ Problem: You have the correct key pair, but still get Permission denied (publickey). The public key is missing, misconfigured, or permissions on .ssh are wrong.

The fix is to add your SSH public key to the instance's authorized_keys file.

Using a Rescue Instance (Universal):
  1. Stop the problematic instance
  2. Detach its root EBS volume
  3. Attach the volume to a temporary rescue instance as a secondary device (/dev/sdf)
  4. SSH into the rescue instance, mount the volume, and chroot into it
  5. Add your public key to ~/.ssh/authorized_keys for the appropriate user (ec2-user or root), or reset the password with passwd
  6. Unmount, detach, reattach as root volume, and start the original instance

Using EC2 Serial Console (If Supported):
  1. Connect to the Serial Console
  2. Reboot and interrupt the boot process to access the GRUB menu
  3. Edit the kernel line to boot into single-user mode (add single to the end)
  4. Once in single-user mode, reset the password (passwd ec2-user) or add the SSH key

Fix 2: Bad /etc/fstab Entry

🛠️ Problem: A misconfigured /etc/fstab is one of the most common causes of boot failure. The system tries to mount a non-existent or incorrectly specified partition and drops to an emergency shell.

Using a Rescue Instance:
  1. Stop, detach the root volume, attach it to a rescue instance
  2. Mount the volume and chroot into it
  3. Edit /etc/fstab to comment out or correct the problematic entry
  4. Unmount, detach, reattach as root volume, and start the original instance

Using the Serial Console:
  1. Access the Serial Console
  2. When the boot drops to the emergency shell, remount the root as read-write: mount -o remount,rw /
  3. Edit /etc/fstab to fix or comment out the bad line
  4. Reboot

💡 Prevention: The nofail Option
A best practice to prevent a single bad fstab entry from taking down your entire server is to use the nofail mount option. This tells the system to continue booting even if the specified mount fails.
UUID=your-uuid /data ext4 defaults,nofail 0 2
📝 Review Questions
Q1: What is the most common symptom of a bad /etc/fstab entry on a Linux EC2 instance?
The instance fails to boot completely, typically dropping to an emergency or recovery shell with an error message about a failed mount. It will likely fail the Instance Status Check.
Q2: How can you fix a bad /etc/fstab entry without using a rescue instance?
If your instance supports it, you can use the EC2 Serial Console. By accessing the console, you can watch the boot process, drop into an emergency shell, remount the root as read-write, and directly edit the /etc/fstab file.
Q3: What is the purpose of the nofail option in /etc/fstab?
The nofail option tells the system not to halt the boot process if the device specified in the fstab entry is unavailable. Using this option for non-critical mounts prevents a single misconfiguration from making the entire instance unreachable.

Fix 3: Network Interface Misconfiguration

🛠️ Problem: Network connectivity failures often happen when the instance is configured with static IP addresses or hardcoded MAC addresses that don't match the AWS environment.

  • Hardcoded MAC addresses in udev rules (e.g., /etc/udev/rules.d/70-persistent-net.rules) cause the interface to fail
  • Static IP addresses inherited from an AMI built with a static config cause DHCP failure

Fix via Rescue Instance:
  1. Enter chroot on the mounted root volume
  2. For hardcoded MAC: Remove or disable the offending udev rules file
  3. For static IP: Open /etc/sysconfig/network-scripts/ifcfg-eth0 (Amazon Linux). Ensure BOOTPROTO=dhcp and remove lines like IPADDR, NETMASK, GATEWAY
  4. Verify ONBOOT=yes in the interface config file
  5. On Ubuntu/Debian, ensure dhcp4: true in the netplan configuration

Fix via Serial Console:
  1. Connect to the Serial Console
  2. Edit the configuration files directly
  3. After making changes, restart the networking service
🌐 fix 3 📊 network config 🔄 DHCP
⚙️

Fix 4: Kernel Panic or GRUB Corruption

🛠️ Problem: A "Kernel panic" or a grub> prompt indicates that the bootloader or kernel is broken.

⚠️ Typical Error Message:
Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)

Using a Rescue Instance:
  1. Mount the root volume and chroot into it
  2. Reinstall GRUB: grub2-install /dev/xvdf (use the correct device path)
  3. Regenerate the GRUB configuration: grub2-mkconfig -o /boot/grub2/grub.cfg
  4. If the kernel itself is missing, reinstall the kernel package (yum install kernel)

For RPM-based systems (Amazon Linux, RHEL, CentOS):
# Reinstall the kernel package yum reinstall kernel -y # Regenerate initramfs dracut -f -vvvvv # Rebuild GRUB configuration grub2-mkconfig -o /boot/grub2/grub.cfg

For Debian-based systems (Ubuntu):
# Reinstall the kernel apt install --reinstall linux-image-$(uname -r) # Regenerate initramfs update-initramfs -u -vvvvv # Rebuild GRUB configuration update-grub

💡 Key Insight: Insufficient disk space in /boot is a common root cause — clean up old kernels to prevent this issue.

Fix 5: Permission Corruption

🛠️ Problem: Accidentally running chmod -R 777 / or similar destructive commands can break SSH and other critical services.

Fix via Rescue Instance:
  1. Mount the root volume and chroot into it
  2. Reset permissions on critical SSH directories:
chmod 755 /home chmod 750 /home/<username> chmod 700 /home/<username>/.ssh chmod 600 /home/<username>/.ssh/authorized_keys

💡 Use passwd to reset the user password after fixing permissions to ensure you can log in.
🗑️ fix 5 📋 permissions 🆘 chroot
📁

Fix 6: Root Volume Full

🛠️ Problem: If the root volume fills up, the system may fail to boot or become extremely slow.

Fix:
  1. Increase the EBS volume size via the console or CLI (aws ec2 modify-volume)
  2. Extend the partition and filesystem from within the instance (or from a rescue instance):
# For XFS sudo xfs_growfs / # For ext4 sudo resize2fs /dev/xvda1

💡 Alternative: Clean up unnecessary files (e.g., old logs, temporary files) to free up space without resizing.

14.4.1 Reset Root Password

🛠️ Step-by-Step: Reset Root Password (Linux)

1. Stop the Target Instance
aws ec2 stop-instances --instance-ids i-1234567890abcdef0

2. Detach the Root Volume
aws ec2 detach-volume --volume-id vol-1234567890abcdef0

3. Attach the Volume to a Rescue Instance
aws ec2 attach-volume \ --volume-id vol-1234567890abcdef0 \ --instance-id i-0987654321fedcba0 \ --device /dev/sdf

4. Access the Volume from the Rescue Instance
sudo mkdir /mnt/recovery sudo mount /dev/xvdf1 /mnt/recovery

5. Reset the Password using chroot
sudo chroot /mnt/recovery passwd root # Follow prompts to enter and confirm new password exit

6. Reattach the Volume and Restart
sudo umount /mnt/recovery aws ec2 detach-volume --volume-id vol-1234567890abcdef0 aws ec2 attach-volume \ --volume-id vol-1234567890abcdef0 \ --instance-id i-1234567890abcdef0 \ --device /dev/xvda aws ec2 start-instances --instance-ids i-1234567890abcdef0

💡 Alternative Methods:
  • AWSSupport-ResetAccess: Systems Manager automation runbook that automates the process
  • EC2 Serial Console: Boot into single-user mode to reset the password

14.4.2 Fix Corrupted /etc/fstab

🧠 How to Identify a Bad fstab Entry:
The boot process will likely fail with a message such as "Welcome to emergency mode!" or "Dependency failed for /data".

⚠️ Typical Problematic Entry:
UUID=wrong-uuid-here /data ext4 defaults 0 2

Fix Using a Rescue Instance:
  1. Stop and detach the root volume
  2. Attach to a rescue instance in the same AZ
  3. Mount the volume: sudo mount /dev/xvdf1 /mnt/recovery
  4. Edit the fstab file: sudo vi /mnt/recovery/etc/fstab
  5. Comment out or correct the problematic line
  6. Unmount, detach, reattach, and start

Fix Using EC2 Serial Console:
  1. Access the Serial Console
  2. In the emergency shell: mount -o remount,rw /
  3. Edit /etc/fstab to fix or comment out the bad line
  4. Reboot

💡 Prevention: The nofail Option
Add nofail to fstab entries to prevent boot failures:
UUID=your-uuid /data ext4 defaults,nofail 0 2

14.4.3 Restore Missing Boot Files

📖 Complete Theory: The "Kernel Panic" Scenario

When an EC2 Linux instance loses critical boot files — such as the kernel image (vmlinuz) or the initial RAM disk (initramfs or initrd) — it typically fails to boot with a "Kernel Panic" error.

⚠️ Typical Error Message:
Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)

🧠 Why This Happens:
  • Incomplete kernel update: Insufficient disk space in /boot
  • Corrupted boot files: Unclean shutdown or file system corruption
  • Manual deletion: Accidental deletion of files in /boot
  • GRUB misconfiguration: Bootloader points to a kernel version that no longer exists

🛠️ Recovery Method: Rescue Instance
  1. Stop and detach the root volume
  2. Attach to a rescue instance in the same AZ
  3. Mount the volume and chroot into it
  4. Reinstall the kernel and regenerate boot files
For RPM-based systems (Amazon Linux, RHEL, CentOS):
# Reinstall the kernel package yum reinstall kernel -y # Regenerate initramfs dracut -f -vvvvv # Rebuild GRUB configuration grub2-mkconfig -o /boot/grub2/grub.cfg

For Debian-based systems (Ubuntu):
# Reinstall the kernel apt install --reinstall linux-image-$(uname -r) # Regenerate initramfs update-initramfs -u -vvvvv # Rebuild GRUB configuration update-grub

💡 If Recovery Fails: Create a new AMI from the repaired volume and launch a fresh instance. This method effectively forces placement on a different host while preserving your data.

Key Takeaways

  • Two primary recovery methods exist: EC2 Serial Console (BIOS-level access) and Rescue Instance (attaching the volume to a helper instance). The Rescue Instance method is the universal fallback.

  • chroot is the essential tool for performing system-level repairs on a detached EC2 root volume.

  • Common fixes include: resetting passwords, repairing GRUB, fixing /etc/fstab, removing hardcoded MAC addresses, and restoring critical file permissions.

  • Always exit chroot and properly unmount before detaching the volume to prevent file system damage.

  • Always verify the instance passes both status checks after recovery.

  • The public IP will change after a stop/start cycle unless you use an Elastic IP.

  • nofail in /etc/fstab prevents boot failures from non-critical mounts.

  • Insufficient /boot space is a common root cause of kernel update failures — clean up old kernels regularly.

  • AWSSupport-ResetAccess is a Systems Manager automation runbook that can automate password resets.

  • If recovery fails, create a new AMI from the repaired volume and launch a fresh instance.
