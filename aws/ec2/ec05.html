1.2.3 Machine Learning and AI Workloads on EC2

Machine Learning (ML) and Artificial Intelligence (AI) represent one of the most transformative and demanding use cases for Amazon EC2. Training complex deep learning models and serving them at scale requires massive computational resources that would be prohibitively expensive for most organizations to own and operate on-premises.

EC2 provides the foundational infrastructure for these workloads through specialized instance families, custom silicon, and deep integrations with ML frameworks and services.
🤖 ML/AI 🧠 deep learning ⚡ EC2
🧩

The ML/AI Compute Challenge

Training a modern Large Language Model (LLM) or computer vision system demands thousands of GPU cores working in parallel for weeks or months.

The On-Premises Reality:
  • 💰 Capital Expenditure: A single high-end GPU can cost $10,000-$40,000. Building a 1000-GPU cluster is a multi-million dollar investment
  • ⏰ Procurement Time: Securing these specialized chips often requires months of lead time
  • 📊 Utilization: Most organizations cannot sustain 100% utilization of a GPU cluster, leading to waste
  • 🧠 Technical Expertise: Managing distributed training infrastructure is highly complex

The EC2 Value Proposition:
  • ⚡ On-Demand Access: Launch high-performance GPU instances in minutes
  • 💳 Pay-as-you-go: No upfront hardware investment
  • 📈 Elasticity: Scale clusters up or down based on workload requirements
  • 🎯 Choice: Select from NVIDIA GPUs, AWS custom chips, and various price/performance tiers
🧩 challenge 💰 cost ⚡ EC2 value
⚡

NVIDIA GPU Instances

The P Family — High-Performance Training
The EC2 P family comprises AWS's high-performance GPU instances built for compute-intensive workloads like ML training, large-scale inference, and scientific simulations.

🟦 P4 Instances (NVIDIA A100 GPUs):
  • GPU: NVIDIA A100 Tensor Core GPUs (40 GB memory)
  • Use Cases: Training and inference of large models like BERT, LLaMA, and ResNet
  • Networking: Supports Elastic Fabric Adapter (EFA) for low-latency distributed training
  • Best For: Production-scale AI training, scientific simulations, high-throughput inference

🟪 P5 Instances (NVIDIA H100 GPUs):
  • GPU: NVIDIA H100 GPUs (80 GB high-bandwidth memory)
  • Performance: Delivers up to 400+ TFLOPS (mixed precision)
  • Use Cases: Generative AI applications, LLMs, graphics and video generation
  • Cost: Approximately $113-$118 per hour for the largest size
  • Best For: Extremely demanding workloads requiring maximum compute density

💡 P-family instances are ideal for jobs bottlenecked by GPU throughput or memory bandwidth. They are typically deployed in clusters for high-throughput training and inference pipelines, with support for GPUDirect RDMA to reduce latency in distributed workloads.
⚡ P family 🟦 A100 🟪 H100 🚀 training
🎨

NVIDIA GPU Instances

The G Family — Graphics & Inference
The EC2 G family provides GPU instances optimized for graphics-intensive applications and machine learning inference, balancing performance with cost efficiency.

🟩 G5 Instances (NVIDIA A10G GPUs):
  • GPU: NVIDIA A10G Tensor Core GPUs (24 GB memory per GPU)
  • Benefits: Up to 3x better performance and 40% better price performance than G4dn
  • ML Training: Offers up to 15% lower cost-to-train than P3 instances
  • Networking: Up to 100 Gbps network bandwidth
  • Storage: Up to 7.6 TB of local NVMe SSD storage

G5 instances are ideal for:
  • Graphics-intensive applications (remote workstations, video rendering, gaming)
  • ML inference for natural language processing and computer vision
  • Training moderately complex, single-node ML models

AWS Trainium

Purpose-Built Training Chips
Trainium is AWS's custom silicon designed explicitly for deep learning training while keeping costs low. It represents a strategic investment in vertical integration to optimize price-performance.

🚀 Trainium3 (Latest Generation — Announced 2025):
  • Technology: AWS's first 3nm AI chip
  • Performance: Up to 4.4x more compute performance, 4x greater energy efficiency, and almost 4x more memory bandwidth than Trainium2
  • Scale: Trn3 UltraServers scale to 144 Trainium3 chips, delivering up to 362 FP8 PFLOPs
  • Networking: NeuronSwitch-v1 delivers 2x more bandwidth; enhanced Neuron Fabric networking achieves <10 microsecond latency
  • Cost Savings: Customers report reducing training and inference costs by up to 50%

🟡 Trainium2:
  • Performance: Used in Project Rainier, connecting 500,000+ Trainium2 chips into the world's largest AI compute cluster
  • Customers: Anthropic, Karakuri, Metagenomi, Ricoh, and Splash Music are reducing costs by up to 50%

Use Cases:
  • Natural language processing (NLP)
  • Computer vision training
  • Recommendation and ranking models
  • Generative AI model training
🧠 Trainium 🔬 3nm chip 💰 50% savings

AWS Inferentia

Purpose-Built Inference Chips
Inferentia powers AWS's Inferentia2 chips (Inf2 instances) for deep learning inference tasks, delivering up to 50% better performance over similar EC2 instances with sustainability benefits.

📊 Inf2 Instances:
  • Purpose: Deep learning inference
  • Use Cases: Image and text generation, summarization, speech recognition
  • Available Sizes:
    • ml.inf2.xlarge
    • ml.inf2.8xlarge
    • ml.inf2.24xlarge
    • ml.inf2.48xlarge
  • Price/Performance Benefits: Inf2 provides the price/performance advantage of custom silicon for inference workloads, making it cost-effective for production deployments of Transformer-family models.

AWS Neuron Migration

Cost Optimization Path
For production inference on Transformer-family models, migrating from NVIDIA GPUs to AWS Neuron (Inf2/Trn) can significantly reduce costs.

Migration Workflow:
  • 1. Verify Model Support: Confirm the model architecture is Neuron-supported
  • 2. Pre-Compile Offline: Compile the model offline before task startup to avoid startup latency
  • 3. Canary Deployment: Deploy Inf2 service alongside existing GPU service; shift traffic via capacity-provider strategy weights
  • 4. Validate Output Parity: Run evaluation suite comparing GPU vs Neuron output quality
  • 5. Production Shift: Gradually shift traffic 5% → 100% to the Neuron-based service

⚠️ Risk Callouts:
  • Compilation ramp adds lead time to each new model version
  • Not all Hugging Face models are Neuron-supported
  • Validate output parity before shifting production traffic
🔄 Neuron 💰 cost savings ⚡ Inf2/Trn

💡 When Not to Self-Host GPUs

"A team running their entire estate on ECS Fargate wants to add an LLM feature. No stated need to self-host a model; no GPU expertise; wants to stay on Fargate."

The answer: Keep Fargate, call Amazon Bedrock.

This approach:
  • Keeps the application/orchestrator CPU-only on Fargate
  • Calls a managed foundation model API (Bedrock)
  • Requires zero GPU infrastructure
  • Uses VPC endpoints for secure, private connectivity
  • Stays on Fargate with all its operational advantages

Infrastructure Best Practices

1. GPU Instance Selection
  • Match to Workload: P5 for large-scale training, G5 for inference and graphics, Inf2/Trn for cost-optimized Transformer workloads
  • Right-Sizing: Start small, monitor utilization, scale up if needed
  • Homogeneous ASGs: Use one GPU type per Auto Scaling group to avoid placement issues. Mixed-GPU ASGs can cause problems because managed scaling protects on the smallest instance type

2. Network Architecture
  • EFA for Distributed Training: Use Elastic Fabric Adapter for low-latency, high-throughput inter-node communication
  • Placement Groups: Use cluster placement groups for tightly coupled workloads
  • VPC Endpoints: Keep ML inference traffic off the internet with VPC endpoints (ECR, S3, Bedrock)

3. Storage Optimization
  • S3 for Model Weights: The primary durable store for model artifacts
  • EFS/FSx for Fast I/O: Cache models locally for faster load times
  • Checkpoints to S3: Offload checkpoints every 15-30 minutes to durable storage

4. Observability
  • CloudWatch Agent: Collects host-level metrics (nvidia_smi) for EC2 launch type
  • Container Insights: Agentless DCGM metrics available on Managed Instances
  • Serving-Engine Metrics: Track latency, tokens/second, and error rates

5. Security
  • IAM Roles: Task roles scoped to specific S3 prefixes and Bedrock model IDs
  • Secrets Manager: Store Hugging Face tokens and API keys securely
  • VPC Configuration: Use private subnets with VPC endpoints for all AWS services

Real-World Example

LLM Inference Deployment on EKS Auto Mode
Prerequisites:
  • Hugging Face account with access token
  • GPU quota increase requested through AWS Service Quotas (process can take 24-48 hours)

Architecture:
  • Instance Type: G5, G6, or G6e instances (optimized for ML workloads)
  • Model: Qwen 3 32b fp8 or Deepseek
  • Components: GPU NodePool with NVIDIA taints, Hugging Face secrets, Model Deployment, Web UI, ALB Ingress

Implementation Steps:
  1. Deploy GPU NodePool: Creates GPU nodes with NVIDIA taints to ensure only GPU-compatible workloads schedule
  2. Configure Secrets: Namespace + Hugging Face token as Kubernetes secret
  3. Deploy Model: Use vLLM serving engine with tolerations matching the GPU node taint
  4. Deploy Web UI: Open WebUI for interactive model interaction
  5. Access: Via kubectl port-forward (internal ALB) or public HTTPS via Route53

⚠️ Key Insight: GPU quota availability varies across AWS accounts; many have a default quota of 0 for p* and g* instance types. Request quota increases well in advance of production deployment.

Key Takeaways

  • EC2 provides specialized ML infrastructure through P-family (NVIDIA high-end), G-family (NVIDIA graphics/inference), Inf2 (Inferentia inference), and Trn (Trainium training) instances.

  • Graviton C8g instances can also be used for CPU-based ML inference, offering up to 30% better performance over previous generations.

  • AWS Neuron (Inferentia/Trainium) offers up to 50% cost savings over similar NVIDIA instances for supported Transformer workloads, but requires a compilation ramp.

  • Capacity Blocks for ML provide guaranteed GPU capacity for short-term, critical workloads without long-term commitment.

  • Spot Instances can reduce training costs by up to 90%, but require interruption tolerance and checkpointing.

  • GPU is not supported on AWS Fargate — any GPU/ML workload must run on ECS-on-EC2, EKS, or as self-managed EC2.

  • Container orchestration on EC2 (ECS/EKS) is the modern deployment pattern for ML inference, providing scaling, health checks, and service discovery.

  • Not every ML workload requires self-hosting — for many teams, Amazon Bedrock (managed FMs) or SageMaker (managed platform) is the better path.

  • Mixed-GPU ASGs can cause placement issues; use one homogeneous ASG per GPU type.

  • Observability requires either the CloudWatch Agent (EC2 launch type) or Container Insights enhanced observability (Managed Instances).
