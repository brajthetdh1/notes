3.2 AWS Identity and Access Management (IAM)

3.2.1 Creating IAM Users and Groups
📖 Complete Theory

IAM Users and Groups form the foundational building blocks for managing human access to your AWS account. The relationship between them is simple but powerful:

👤 IAM User: Represents a single person or application that needs to interact with AWS. Each user has a unique identity within your AWS account and can have its own set of security credentials.

👥 IAM Group: A collection of IAM users. Groups allow you to apply the same permissions to multiple users at once, following the best practice of managing permissions at a group level rather than individually.

The central concept is scalable permission management. By adding users to groups, you attach permissions to the group, and all members inherit them.

Why Groups are a Best Practice:
⚡ Operational Efficiency: Granting access through groups reduces the number of policies you need to manage, making it easier to apply the principle of least privilege.
🔄 Simplified Management: When a user's role changes, you simply move them to a different group — they automatically inherit the new permissions.
🔒 Enhanced Security & Visibility: It's much easier to audit who has what permissions by reviewing group memberships than by checking each user's attached policies.
📋 Standardized Permissions: Groups based on job functions help prevent over-privileging by ensuring users have only the permissions they need.

3.2.1.2 IAM Policies

The Language of Permissions
Permissions in AWS are defined using IAM Policies. A policy is a JSON document that explicitly defines what actions are allowed or denied on which AWS resources.

{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": "ec2:Describe*", "Resource": "*" } ] }

Two Types of IAM Policies:
  • 📦 AWS Managed Policies: Pre-built policies created and maintained by AWS. Cover common use cases like ReadOnlyAccess, AdministratorAccess, or AmazonEC2FullAccess.
  • ✏️ Customer Managed Policies: Policies you create and manage yourself to fit specific, custom permission requirements. You can define granular, least-privilege permissions tailored to your organization.

📌 How Policies are Attached: Policies can be attached directly to a user, to a group, or to a role. The recommended best practice is to attach policies to groups, not to individual users.

Creating an IAM Group

Step 1:
Open the IAM Console — Log in to the AWS Management Console and navigate to the IAM service.
Step 2:
Access User Groups — In the navigation pane, select User groups, then click the Create group button.
Step 3:
Name the Group — Enter a descriptive name (e.g., Developers, ReadOnlyUsers). Group names must be unique within your account.
Step 4:
Attach Permission Policies — This is the crucial step. Select the policies that define the permissions members of this group should have.
Step 5:
Add Users (Optional) — You can select existing users to add to the group now, or skip this step and add them later.
Step 6:
Create the Group — Click the Create group button to finish.

Creating an IAM User

Step 1:
Open the IAM Console — Navigate to the IAM service.
Step 2:
Access Users — In the navigation pane, select Users, then click the Add users button.
Step 3:
Set User Details — Enter a unique username.
Step 4:
Select Access Type — Choose the type of access:
  • 💻 Programmatic access: For users who will use the AWS CLI, SDKs, or API
  • 🌐 AWS Management Console access: For users who will log in to the AWS web interface
Step 5:
Set Permissions — Choose the Add user to group option to follow best practices:
  • Select the group(s) you have already created
  • The user will inherit all policies attached to those groups
Step 6:
Review and Create — Review your settings and click Create user.

🎯 Example: Creating a ReadOnly Group and User

Goal: To give a new team member, sanjeev, the ability to view AWS resources but not make any changes.

1. Create a ReadOnly Group: Create an IAM group named ReadOnlyGroup. Attach the AWS-managed policy ReadOnlyAccess.

2. Create a User: Create an IAM user named sanjeev.

3. Add to Group: When setting sanjeev's permissions, select Add user to group and add them to ReadOnlyGroup.

Result: sanjeev can log in and view resources. If their role changes, you simply move them to a different group (e.g., Developers) and they automatically inherit the new permissions.

Managing Group Membership

Adding a User to a Group:
  1. In the IAM console, go to User groups and select the group name
  2. On the Users tab, click Add users
  3. Select the users you want to add and confirm

Removing a User from a Group:
  1. In the IAM console, go to User groups and select the group name
  2. On the Users tab, select the user you want to remove
  3. Click Remove users

💡 Key Insight: When a user's role changes, you simply move them to a different group. This avoids the "permission creep" that often occurs when managing permissions for individual users.

Advanced Concepts

Principle of Least Privilege
The Principle of Least Privilege:
This security principle dictates that a user should be given only the minimal permissions necessary to perform their job. The primary mechanism for enforcing this is by creating specific groups for each job function.

Group-Based vs. Attribute-Based Access Control:
While groups are excellent for defining roles, attributes can provide an additional layer of fine-grained control. Attributes like Department, Project, or Location can be used in policies to further scope permissions.

💡 Example: You could have a Project attribute for users in your WebAppDeveloper group, using it to limit their access to resources associated only with that specific project.

Enhancing Security with Service Control Policies (SCPs):
SCPs are a governance tool available through AWS Organizations. They can enforce group-based permission management across your entire organization.
{ "Version": "2012-10-17", "Statement": [ { "Sid": "DenyDirectUserPolicyAttachment", "Effect": "Deny", "Action": [ "iam:AttachUserPolicy", "iam:DetachUserPolicy", "iam:PutUserPolicy", "iam:DeleteUserPolicy" ], "Resource": "*" } ] }
⚠️ SCP Impact: The above policy, when applied as an SCP, prevents any direct policy attachments to users, forcing administrators to use groups or IAM roles.

Review Questions

Q1: What is the primary purpose of creating IAM user groups?
Answer: The primary purpose of creating IAM user groups is to simplify and centralize permission management. By creating groups that correspond to job functions (e.g., Developers, ReadOnlyUsers), you can attach permission policies to the group. When you add IAM users to the group, they automatically inherit all the permissions you've defined. This makes it much easier to apply the principle of least privilege and manage permissions at scale.
Q2: Why is it a best practice to assign permissions to users only through groups?
Answer: Assigning permissions only through groups is a best practice for several key reasons:
  • 📊 Scalability: Managing permissions for 1,000 users through groups is far more efficient than managing 1,000 individual configurations.
  • ✅ Consistency: It ensures that all users in the same role have the same set of permissions, preventing inconsistencies.
  • 🔄 Operational Efficiency: Role changes are accomplished by simply moving the user between groups.
  • 🔍 Easier Auditing: It's much simpler to understand who has what permissions by reviewing group memberships.
Q3: What is the difference between an AWS managed policy and a customer managed policy?
Answer: The main difference is who creates and maintains the policy:
  • AWS managed policy: Created and maintained by AWS. Designed for common use cases (e.g., ReadOnlyAccess, AmazonEC2FullAccess). A convenient starting point.
  • Customer managed policy: Created and maintained by you. Allows you to define custom, granular permissions that fit your organization's specific security requirements.
Q4: How can I use attributes to further refine access control beyond groups?
Answer: You can use attributes like Department, Project, or Location in conjunction with groups to create a more precise access control model — often called Attribute-Based Access Control (ABAC).

Example: You might have a WebAppDeveloper group. All developers have the same core permissions. However, you could also assign a Project attribute to each user. In your policies, you could add a condition that allows a developer to access a resource only if the PrincipalTag matches the ResourceTag of that resource.
Q5: How does a Service Control Policy (SCP) help enforce group-based permissions?
Answer: A Service Control Policy (SCP) is a governance tool used in AWS Organizations to apply restrictions at an account or organizational unit (OU) level. It acts as a "guardrail" for permissions.

You can use an SCP to deny specific IAM actions that would undermine your group-based permission model. For example, an SCP can prevent:
  • iam:AttachUserPolicy
  • iam:DetachUserPolicy
  • iam:PutUserPolicy
  • iam:DeleteUserPolicy
When applied, any attempt to attach a policy directly to a user (instead of through a group) will be blocked, enforcing the best practice that permissions must be managed through groups.
