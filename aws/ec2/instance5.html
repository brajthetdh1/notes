7.6 Cost Optimization Best Practices

📖 Complete Theory

Effective EC2 cost optimization requires a systematic approach across three dimensions: selecting the right instance for the workload, choosing the optimal purchase model, and continuously mapping usage to actual demand.

The financial impact of these practices is substantial. McKinsey found that effective FinOps practices, including EC2 optimization, can reduce cloud costs by 20-30% based on their review of $3 billion in actual cloud bills.
💰 cost optimization 📊 FinOps ⚡ 20-30% savings

Strategy 1: Right-Sizing Instances

Right-sizing means matching instance capacity to actual workload demand. It remains the fastest path to cutting EC2 spend without commitments or architectural changes.

Key Right-Sizing Metrics:
MetricThresholdAction
Max CPU/Memory UtilizationBelow 40% over 4 weeksDownsize the instance
Max CPU Utilization1% or lessConsider termination (idle)
Target CPU Utilization40-70%Well-utilized instance

📌 AWS Guideline: Any instance with maximum CPU and memory utilization below 40% over a four-week period qualifies for downsizing. Cutting an oversized instance in half saves roughly 50% on that instance with no performance impact.

Tools for Right-Sizing:
  • AWS Compute Optimizer — ML-based rightsizing recommendations (up to 25% cost reduction)
  • AWS Trusted Advisor — Identifies underutilized resources
  • AWS Cost Explorer — Rightsizing engine flags idle instances
  • Amazon Q EC2 Instance Selector — Personalized recommendations

💡 Best Practice: Run right-sizing continuously, not quarterly. Workload patterns shift as applications evolve, and a right-sized instance today can drift into over-provisioned territory within weeks.
📐 right-sizing 📊 up to 25% ⚡ Compute Optimizer

📊 Effective Savings Rate (ESR): The FinOps Foundation recommends evaluating commitment purchases against the ESR, not the headline discount percentage. 💡 Flexibility Rule of Thumb: Be flexible across at least 10 instance types for each workload. Include larger instance types if vertically scalable, and older generation types if horizontally scalable.

Strategy 4: Scheduling & Auto Scaling

Instance Scheduling:
Stop non-production instances during off-hours to eliminate compute charges. You'll still incur EBS storage costs, but the savings are substantial.

Automated Scheduling Approach:
  • Use AWS Lambda + EventBridge to stop instances after hours
  • Use AWS Instance Scheduler (AWS solution) for recurring schedules
  • Use AWS Systems Manager for maintenance windows

Auto Scaling Best Practices:
StrategyImplementationBenefit
Set minimum capacityMaintain baseline On-Demand instancesGuarantee availability
Mixed instances policyCombine On-Demand + SpotCost savings + availability
Scaling policiesCPU-based, request-based, or scheduledMatch capacity to demand
ALB health checksRemove unhealthy instances automaticallyMaintain application health

📊 Production-Ready ASG Configuration:
  • On-Demand Base Capacity: 1-2 instances (guaranteed availability)
  • On-Demand % Above Base: 30-50%
  • Spot Percentage: 50-70%
  • Allocation Strategy: price-capacity-optimized

💡 Key Insight: Even with Spot configured, if capacity is unavailable, Auto Scaling will launch On-Demand instances to maintain desired capacity. This ensures availability but reduces savings.

Strategy 5: Selecting the Right Instance Type

Graviton Instances:
AWS Graviton processors deliver up to 40% better price-performance than comparable non-Graviton instances. Consider migrating workloads to Graviton-based instances (M7g, C7g, R7g) for significant savings.

Graviton Migration Requirements:
  • Recompiling applications for ARM architecture
  • Testing for compatibility
  • Updating AMIs and launch configurations

  • Break-even utilization for EC2 Instance SP vs Compute SP is ~92% — below that, Compute SP delivers equal or better savings.

Review Questions

Q1: What is the most effective first step for reducing EC2 costs?
Answer: Right-sizing. Matching instance capacity to actual workload demand is the fastest path to cutting EC2 spend without commitments or architectural changes. AWS guidelines state that any instance with maximum CPU and memory utilization below 40% over four weeks qualifies for downsizing. Right-sizing can reduce costs by up to 25%.
Q2: What hidden costs should you budget for beyond EC2 instance pricing?
Answer: Ancillary costs can add 40-50% to compute costs. Key hidden costs include:
  • EBS storage: $0.08/GB-month for gp3
  • Data transfer: $0.09/GB after free tier
  • Inter-AZ traffic: $0.01/GB per direction
  • Public IPv4: $0.005/hour (~$3.60/month each)
  • NAT Gateway: $0.045/hour + $0.045/GB processed
Q3: What is the Effective Savings Rate (ESR) and why is it important?
Answer: The Effective Savings Rate measures realized savings minus the cost of unused commitments, divided by On-Demand-equivalent spend. It's important because the headline discount percentage (66-72%) is rarely achieved in practice. The average AWS Compute ESR runs around 26%, well below theoretical maximums, because most organizations carry some unused commitment inventory.
Q4: What are the best practices for using Spot Instances?
Answer: Key Spot best practices include:
  • Be flexible across 10+ instance types
  • Use price-capacity-optimized allocation strategy
  • Enable Capacity Rebalancing
  • Use integrated AWS services (EMR, ECS, Batch, EKS, SageMaker)
  • Use Auto Scaling Groups or EC2 Fleet
  • Avoid deprecated RequestSpotFleet API
Q5: When should you choose EC2 Instance Savings Plans over Compute Savings Plans?
Answer: Choose EC2 Instance SP when your workload is:
  • 100% EC2 (no Fargate or Lambda)
  • Concentrated in one instance family and one region
  • Highly predictable for the commitment term (1-3 years)
  • Utilization will remain above the ~92% break-even point
Choose Compute SP when you need flexibility across families, regions, or services, or when your utilization might drop below the break-even point.
