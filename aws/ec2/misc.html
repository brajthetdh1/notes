Amazon CloudFront

Amazon CloudFront is a Content Delivery Network (CDN) that delivers content globally with low latency and high transfer speeds. It distributes static, dynamic, and streaming content and integrates with S3, EC2, API Gateway, ALB, or any custom origin. CloudFront uses edge locations worldwide to serve content closer to users.

Key Features

  • Global Edge Network: Hundreds of edge locations worldwide route requests to the nearest edge for low latency.
  • Caching: Frequently accessed objects are cached at edge locations to reduce load on origin servers.
  • Dynamic & Static Content: Efficiently serves HTML, CSS, JS, images, and dynamic API responses with optional caching.
  • HTTPS & Security: Supports SSL/TLS encryption, AWS WAF integration, and signed URLs/cookies for private content.
  • Origin Support: Can pull content from S3 buckets, EC2 instances/load balancers, or custom HTTP servers.
  • Lambda@Edge: Run code at edge locations for request/response manipulation, URL rewriting, authentication, or A/B testing.

How CloudFront Works

  1. User Request: User requests content like https://www.example.com/image.png.
  2. Edge Location Check: CloudFront checks if the object is cached at the nearest edge location.
  3. Cache Hit / Miss:
    • Hit: Returns the cached object immediately.
    • Miss: Fetches from the origin (S3/EC2/etc.), caches it, then returns it to the user.
  4. Subsequent Requests: Object is served from the edge cache, reducing latency and origin load.

Example: S3 + CloudFront

  • Origin: S3 bucket hosting a static website.
  • CloudFront Distribution: Domain like d123abc.cloudfront.net, with caching rules and TTL settings.
  • Custom Domain: Map www.example.com to CloudFront using Route 53, with SSL certificate via ACM.

Caching Behavior

  • TTL (Time to Live): Controls how long objects remain in the cache.
  • Invalidation: Manually remove cached objects when content is updated.
  • Cache Based on Headers / Cookies / Query Strings: Fine-grained caching for dynamic or personalized content.

💡 Tech Lead Tip: Always configure CloudFront in front of your S3 static websites for HTTPS, caching, and global low-latency delivery. Combine with Lambda@Edge for advanced request/response manipulation and personalization.

CloudFront with Custom Domain & HTTPS

Serve your CloudFront distribution securely via a custom domain using AWS Route 53 and ACM. This setup ensures global low-latency delivery with SSL/TLS encryption.

1. Prerequisites

  • Existing CloudFront distribution serving content (e.g., S3).
  • Owned domain name (example.com).
  • Route 53 hosted zone for your domain (or any DNS provider).

2. Add Custom Domain to CloudFront

  • CloudFront Console → Select Distribution → Edit General Settings.
  • In Alternate Domain Names (CNAMEs), add: www.example.com

3. Request SSL Certificate (ACM)

  • Use ACM in us-east-1 (required for CloudFront).
  • Request public certificate for www.example.com (optional: add example.com).
  • Validate via DNS (recommended) or Email.

4. Attach Certificate to CloudFront

  • CloudFront → Distribution → Edit → SSL Certificate → Custom SSL Certificate → select ACM certificate.
  • Enable Redirect HTTP to HTTPS.
  • Save changes (~15–20 minutes for propagation).

5. Configure Route 53 DNS

  • Create Record Set:
    • Name: www
    • Type: A – IPv4 address
    • Alias: Yes → Select CloudFront distribution
  • Non-AWS DNS: Use CNAME → www.example.com → d123abc.cloudfront.net

6. Optional: Redirect Root Domain

  • Create S3 bucket example.com → Enable Static Website Hosting → Redirect to www.example.com.
  • Route 53 A record alias points root domain to this S3 bucket endpoint.

7. Summary Flow

User (https://www.example.com)
        ↓
Route 53 DNS resolves
        ↓
CloudFront edge location
        ↓
Origin (S3 bucket / EC2 / ALB)

CloudFront serves content securely via SSL/TLS, with edge caching for low latency.

Key Points & Tech Tips

  • Request ACM certificates in us-east-1 for CloudFront.
  • Enable HTTPS redirection in CloudFront.
  • Use Route 53 alias for low-latency DNS resolution.
  • Invalidate cache if updating SSL or content.
  • Optional: redirect root domain to www for better user experience.

CloudFront + S3 Cross-Region Replication (CRR)

Combining CloudFront CDN with S3 CRR ensures global performance, disaster recovery, and compliance for production-ready applications.

1. Amazon S3 Cross-Region Replication (CRR) Recap

  • Automatically replicates objects from source bucket to destination bucket in another region.
  • Versioning must be enabled on both buckets.
  • Replication is asynchronous (eventual consistency).
  • Supports replication of new objects, metadata, tags, and delete markers (optional).
  • Use Cases: Disaster recovery, compliance, reduced latency for global users.

Example: Source Bucket (us-east-1) → Destination Bucket (us-west-2)

2. Amazon CloudFront Recap

  • Global CDN caching content at edge locations.
  • Works with S3, EC2, ALB, or custom origins.
  • Supports HTTPS, WAF, Lambda@Edge, and caching policies.
  • Can use custom domains with Route 53 and ACM.
  • Improves global performance and reduces latency.

3. Using CloudFront with S3 CRR

  • Source bucket (primary region) stores original objects.
  • CRR replicates objects to a destination bucket in another region (backup/DR).
  • CloudFront distribution uses either:
    • Source bucket as origin (global users)
    • Destination bucket as origin (region-specific performance)
  • Optional Route 53 routing (latency-based / geolocation) for directing users to nearest CloudFront distribution.

4. Why Combine CloudFront with CRR?

  • Global Performance + Redundancy: CloudFront caches content near users, CRR ensures backup in another region.
  • High Availability: Origin failover to secondary bucket in case primary fails.
  • Compliance & Data Residency: Keep copies in multiple regions while serving content globally.

5. Architecture Flow Example

Users (Global)
       ↓
   CloudFront Edge
       ↓
   Origin (S3 Bucket in Region A)
       ↓ (optional failover)
   S3 Bucket in Region B (via CRR)

Write Flow: Upload to Source Bucket → replicated asynchronously to Destination Bucket.
Read Flow: CloudFront edge serves cached content → fetches from origin if cache miss.

6. Considerations / Best Practices

  • CRR + Versioning: Required for replication and disaster recovery.
  • CloudFront Caching: Configure TTL and invalidation to avoid stale content.
  • Origin Failover: Use CloudFront failover to secondary bucket for high availability.
  • Cost: CRR incurs inter-region transfer; CloudFront reduces S3 origin requests.
  • Security: Use Origin Access Identity (OAI) to restrict S3 bucket access to CloudFront only.

💡 Tech Lead Tip

For global static websites, combine S3 CRR for backup and regional redundancy with CloudFront for accelerated delivery. Use Route 53 latency-based routing for multi-CDN or multi-region failover to ensure both performance and resilience.

Using Amazon S3 as a CloudFront Origin

A common architecture for static websites, media delivery, and global caching, where CloudFront caches content from S3 buckets for improved performance.

1. What Does “S3 as a CloudFront Origin” Mean?

The origin is the source of content that CloudFront caches and serves to users. CloudFront fetches objects from your S3 bucket on cache misses, then caches them at edge locations for faster subsequent access.

2. How It Works

  1. User Request: A user requests https://www.example.com/image.png.
  2. Edge Cache Check: Cache hit → return immediately; cache miss → fetch from S3 origin.
  3. Origin Fetch: CloudFront fetches the object from S3, caches it at the edge, and returns to the user.
  4. Subsequent Requests: Served directly from edge cache → low latency, reduced S3 load.

3. Configuration Steps

  • Create S3 Bucket: Store content (HTML, CSS, JS, images, videos). Optional: Enable static website hosting.
  • Create CloudFront Distribution: Select S3 bucket as origin. Prefer REST endpoint for HTTPS support.
  • Origin Access Identity (OAI): Restrict direct S3 access → only CloudFront can fetch content.
  • Set Cache Behavior: Default TTL, optional header/cookie/query caching.
  • Configure HTTPS & Custom Domain: Use ACM for SSL → add CNAME in CloudFront → map in Route 53.

4. Benefits of Using S3 as CloudFront Origin

  • Global Performance: Edge caching reduces latency worldwide.
  • Reduced S3 Load: Only cache misses go to S3 → lower costs.
  • Security: OAI ensures bucket is private, accessible via CloudFront only.
  • HTTPS Support: CloudFront provides SSL termination even if S3 website endpoint doesn’t support HTTPS.
  • Custom Behavior: Cache policies, geo-restriction, signed URLs/cookies for private content.

5. Special Considerations

  • Static vs Dynamic: S3 is ideal for static content; CloudFront can cache dynamic content temporarily if needed.
  • Object Versioning: Enable versioning to avoid stale cache issues; use CloudFront invalidation for updates.
  • Origin Failover: CloudFront can failover to secondary bucket for high availability.
  • Access Permissions: Prefer OAI → restrict bucket policy; do not make the bucket public.

6. Architecture Flow

Users Worldwide
        ↓
CloudFront Edge
   ┌─────────────┐
   │ Edge Cache  │
   └─────────────┘
        ↓ (cache miss)
S3 Origin Bucket (private)
        ↓
Content returned → cached at edge → served to users

Optional: Use S3 Cross-Region Replication (CRR) for multi-region failover → CloudFront can switch origins if needed.

💡 Tech Lead Tip

Always use CloudFront OAI for secure S3 access. Enable HTTPS via ACM for your custom domain. Combine S3 versioning and CloudFront invalidation to manage updates efficiently. Set TTL and cache policies based on content type (static vs dynamic) for optimal performance.
