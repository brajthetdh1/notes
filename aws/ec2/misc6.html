10.5 IAM Roles for EC2

📖 Complete Theory: Secure Credential Management

IAM Roles for EC2 are the secure, AWS-recommended way to grant permissions to applications running on your EC2 instances. Instead of embedding long-term credentials (Access Keys) in your application code or configuration files, you use an IAM role to provide temporary, automatically rotated credentials.

Why Use IAM Roles Instead of Access Keys?

ApproachMethodSecurityMaintenance
IAM User with Access KeysStore Access Key ID + Secret Access Key on the instance❌ High risk if keys are compromised❌ Manual rotation; must update every instance
IAM Role for EC2Attach role to instance; application gets temporary credentials via metadata✅ Temporary credentials auto-rotate; no keys stored✅ Centralized management; update once, all instances inherit

💡 Real-World Example: If your application needs to upload files to S3, you can attach an IAM role with AmazonS3FullAccess to your EC2 instance. The instance automatically receives temporary credentials, and AWS handles credential rotation for you — no keys to store or manage.

🔑 The Core Problem with Access Keys on EC2:

Operational Challenges:
  • ❌ Manual Distribution: You must securely copy keys to every new instance
  • ❌ Credential Rotation: When keys need to be rotated, you must update every instance manually
  • ❌ Incident Response: Rotating keys in use by multiple instances can cause outages
  • ❌ Lack of Centralized Management: Each instance maintains its own credentials

Security Risks:
  • ❌ Exposure in Code: Access keys stored in application code are visible to anyone with read access
  • ❌ Public Exposure: Developers may accidentally push keys to public repositories
  • ❌ Former Employees: Ex-employees may retain access to durable credentials
  • ❌ Long-Term Exposure: Access keys remain valid until manually rotated

Temporary Credentials via Instance Metadata:
When an application runs on an EC2 instance with an IAM role, it obtains temporary security credentials from the EC2 instance metadata service:
  • Credentials represent the IAM role and are valid for a limited time
  • They are automatically updated before they expire
  • Retrievable from: http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name

💡 With some AWS SDKs, a provider manages the temporary credentials transparently. The credentials are automatically updated before they expire.

10.5.1 Why Use IAM Roles Instead of Access Keys?

📖 Complete Theory: The Case for Temporary Credentials

Using IAM roles instead of long-term access keys for EC2 instances is one of the most critical security practices in AWS. It eliminates the operational burden and security risks associated with managing static credentials while enabling a least-privilege security model.

⚖️ IAM Role vs. Access Key: A Direct Comparison
AspectIAM Role (Temporary)Access Keys (Permanent)
Credential LifespanShort-lived, auto-rotatedLong-lived, manual rotation
StorageNot stored — retrieved via IMDSStored on instance
Management OverheadNone — AWS handles rotationManual rotation and distribution
Security PostureHigh — compromised credentials expireLow — compromised keys usable indefinitely
Permission UpdatesUpdate role once; all instances inheritUpdate each instance's key file
Risk of ExposureMinimal — not stored on diskHigh — keys can be exposed in code

💡 The AWS Well-Architected Framework explicitly recommends replacing long-term credentials with temporary credentials wherever possible. For EC2, this means using IAM roles instead of access keys.

✅ Best Practices Summary:
Use IAM roles for EC2: Avoid embedding keys; assign minimal privileges
Enforce IMDSv2: Require session tokens to mitigate SSRF attacks
Update IAM policies regularly: Follow least-privilege principles
Monitor with CloudTrail: Track role assumptions and API calls for auditing
📝 Review Questions
Q1: Why is using IAM roles for EC2 considered more secure than embedding access keys?
IAM roles provide temporary, automatically rotated credentials instead of long-term access keys. This eliminates the risk of keys being exposed in code repositories, configuration files, or via insecure sharing. Even if temporary credentials are compromised, they expire quickly and cannot be used indefinitely.
Q2: What are the operational benefits of using IAM roles instead of access keys?
IAM roles eliminate the operational burden of manually distributing, rotating, and managing credentials across multiple instances. When you update a role's permissions, all attached instances automatically inherit the changes. No manual updates to each instance are required.
Q3: How do applications on an EC2 instance obtain credentials from an IAM role?
Applications retrieve temporary security credentials from the EC2 Instance Metadata Service at http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name. AWS SDKs and the CLI handle this retrieval transparently — no code changes are required.
Q4: What is an instance profile and when is it needed?
An instance profile is a container that holds an IAM role and delivers its temporary credentials to an EC2 instance. When you create an IAM role using the AWS console, the instance profile is created automatically. However, when using the AWS CLI or API, you must create both the role and the instance profile separately.
Q5: What does the AWS Well-Architected Framework recommend regarding access keys?
The AWS Well-Architected Framework recommends avoiding the use of long-term credentials in favor of temporary credentials. For EC2 instances, this means using IAM roles instead of access keys.

10.5.2 Attaching IAM Roles to EC2 Instances

📖 Complete Theory: The Instance Profile Mechanism

Attaching an IAM role to an EC2 instance is the process of assigning a set of temporary, automatically rotating credentials to the instance so it can securely access AWS services without storing long-term access keys.

What is an Instance Profile?
An instance profile is the mechanism that physically delivers the IAM role's permissions to the EC2 instance.

Key Points:
  • An instance profile can contain only one IAM role, but the same role can be attached to many instances
  • When you create a role using the IAM console, the instance profile is automatically created with the same name as the role
  • When using the CLI or API, you must create the role and instance profile as separate steps

🛠️ Methods for Attaching an IAM Role:

Method 1: During Instance Launch (Recommended)
# Launch with existing instance profile aws ec2 run-instances \ --image-id ami-0abcdef1234567890 \ --instance-type t3.micro \ --iam-instance-profile Name="EC2-S3-ReadOnly"

Method 2: Attaching to an Existing Instance
aws ec2 associate-iam-instance-profile \ --instance-id i-1234567890abcdef0 \ --iam-instance-profile Name="EC2-S3-ReadOnly"

Method 3: Replacing an Existing Role
# Get the association ID aws ec2 describe-iam-instance-profile-associations \ --filters Name=instance-id,Values=i-1234567890abcdef0 # Replace the role aws ec2 replace-iam-instance-profile-association \ --association-id iip-assoc-0044d817db6c0a4ba \ --iam-instance-profile Name="New-Role-Name"

Method 4: Detaching an IAM Role
aws ec2 disassociate-iam-instance-profile \ --association-id iip-assoc-0044d817db6c0a4ba

⚙️ Using the CLI to Create and Attach Roles (Manual Steps):
# 1. Create the IAM Role with Trust Policy aws iam create-role \ --role-name EC2-S3-ReadOnly \ --assume-role-policy-document file://ec2-trust-policy.json # 2. Attach a Permissions Policy aws iam attach-role-policy \ --role-name EC2-S3-ReadOnly \ --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess # 3. Create the Instance Profile aws iam create-instance-profile \ --instance-profile-name EC2-S3-ReadOnly # 4. Add the Role to the Instance Profile aws iam add-role-to-instance-profile \ --role-name EC2-S3-ReadOnly \ --instance-profile-name EC2-S3-ReadOnly
📝 Review Questions
Q1: What is an instance profile and how does it relate to an IAM role?
An instance profile is a container that passes an IAM role to an EC2 instance. When you attach a role to an instance, you are actually attaching the instance profile. When using the console, the instance profile is automatically created with the same name as the role; when using the CLI, you must create it separately.
Q2: Can you attach an IAM role to a running EC2 instance?
Yes. You can attach a role to a running instance using the console (Actions → Security → Modify IAM role) or the CLI (associate-iam-instance-profile). You can also attach roles to stopped instances. If the instance already has a role, it will be replaced by the new one.
Q3: How many IAM roles can be attached to a single EC2 instance?
Only one IAM role can be attached to an instance at a time. However, the same role can be attached to many instances. If you need multiple permission sets, you must consolidate them into a single role with the necessary permissions.
Q4: What is the difference between attaching a role via the console vs. the CLI?
When attaching a role via the console, the instance profile is created automatically with the same name as the role. When using the CLI, you must manually create the instance profile and then add the role to it before the role can be attached to an instance.
Q5: How can you verify that an IAM role is correctly attached to an instance?
You can verify in the EC2 console by checking the IAM role field on the instance's Description tab. From within the instance, you can query the Instance Metadata Service at http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name. You can also test permissions using the AWS CLI without providing any access keys.

10.5.3 Common IAM Policies for EC2

S3ReadOnlyAccess & SSMManagedInstanceCore
📖 Complete Theory: Managed Policies for EC2

Two of the most frequently used AWS managed policies for EC2 are AmazonS3ReadOnlyAccess and AmazonSSMManagedInstanceCore. These policies provide essential, pre-defined permissions that allow your EC2 instances to interact with other AWS services and management tools securely.

📦 AmazonS3ReadOnlyAccess
Definition and Purpose:
The AmazonS3ReadOnlyAccess policy grants read-only access to all S3 buckets and objects via the AWS Management Console and API. It is a foundational policy for any application on EC2 that needs to retrieve data from S3 without modifying it.

📜 The Policy Document:
{ "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": [ "s3:Get*", "s3:List*", "s3:Describe*", "s3-object-lambda:Get*", "s3-object-lambda:List*" ], "Resource": "*" } ] }

🔑 Understanding the Permissions:
  • s3:Get* — Allows all S3 actions starting with "Get" (e.g., s3:GetObject to download files)
  • s3:List* — Allows s3:ListBucket to view bucket contents
  • s3:Describe* — Allows descriptive actions on S3 resources

💡 Use Cases for EC2:
  • Web Servers: Serve static content (images, CSS, JavaScript) from S3
  • Data Processing: Read large datasets stored in S3 without write permissions
  • Backup and Restore: Retrieve backup files from S3 for restore operations

⚠️ Important Consideration: The "Resource" : "*" element grants read access to all S3 buckets in your account. For more granular control, create a customer-managed policy that specifies a particular bucket ARN.
⚙️ AmazonSSMManagedInstanceCore

Definition and Purpose:
The AmazonSSMManagedInstanceCore policy enables an EC2 instance to use the core functionality of AWS Systems Manager. It is the standard policy required for an instance to communicate with the Systems Manager service for management tasks.

Use Cases for EC2:
  • ✅ Session Manager: Browser-based shell access without SSH keys or public IPs
  • ✅ Patch Manager: Automated, scheduled OS patching
  • ✅ State Manager: Enforce desired configuration state

💡 Key Insight: The ssmmessages and ec2messages actions are required for Session Manager to establish a secure, bidirectional session without requiring an open inbound port (like port 22 for SSH).

📝 Review Questions
Q1: What is the purpose of the AmazonS3ReadOnlyAccess policy?
It provides read-only access to all S3 buckets and objects, allowing an EC2 instance to retrieve data from S3 without the ability to modify or delete it. Its Action list includes s3:Get*, s3:List*, and s3:Describe*.
Q2: What core functionality does the AmazonSSMManagedInstanceCore policy enable?
It enables an EC2 instance to use the core functionality of AWS Systems Manager. This includes communicating with the SSM service for inventory, patching, and, most importantly, establishing secure sessions via Session Manager.
Q3: Why is AmazonSSMManagedInstanceCore a prerequisite for using Session Manager?
The policy grants permissions for ssmmessages and ec2messages actions. These are the specialized channels required for the SSM Agent and the Systems Manager service to create and manage the secure, interactive session used by Session Manager.
Q4: Is AmazonS3ReadOnlyAccess always secure enough for a production workload?
While it grants read-only access, its "Resource":"*" element allows access to all S3 buckets in the account. For production environments with multiple buckets, it is a best practice to create a custom policy that restricts access to only the specific S3 bucket(s) required by the application.
Q5: Can the AmazonSSMManagedInstanceCore policy alone enable full logging of Session Manager sessions?
No. This policy only provides the core communication permissions. To log sessions to an S3 bucket, you must also attach an additional policy that grants s3:PutObject permissions specifically for that logging bucket.

Key Takeaways

  • IAM Roles provide temporary credentials — no long-term access keys to manage or store on instances.

  • Instance Profile is the container that passes the IAM role to the EC2 instance — one role per instance.

  • Credentials are auto-refreshed before they expire — applications can retrieve new credentials from instance metadata.

  • Least privilege is a best practice — create roles with only the permissions the application needs.

  • Console vs. CLI — console creates instance profiles automatically; CLI/API requires separate creation.

  • AmazonS3ReadOnlyAccess grants read-only access to all S3 buckets — use custom policies for granular control.

  • AmazonSSMManagedInstanceCore enables Session Manager, Patch Manager, and State Manager functionality.

  • SSMManagedInstanceCore is a prerequisite for Session Manager — it enables secure, browser-based shell access without SSH keys.

  • Attach roles during launch (recommended) or to running/stopped instances via Modify IAM role.

  • Verify role attachment using the EC2 console or by querying the Instance Metadata Service.
