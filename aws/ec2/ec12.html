6.1.1 Pending → Running → Stopping → Stopped → Terminated

📖 Complete Theory

The EC2 instance lifecycle is a series of state transitions, each with its own characteristics, behaviors, and implications. Understanding these transitions in detail is essential for effective instance management, cost optimization, and troubleshooting.

Transition 1: Pending → Running

Trigger: Launch Instance (Initial launch) or Start Instance (from Stopped state)

What Happens During Pending:
1. Resource Allocation
AWS reserves physical host with capacity
10-30 seconds
2. AMI Copy
AMI copied to root volume (EBS-backed)
30-120 seconds
3. Instance Initialization
Network settings (VPC, subnet, ENI)
10-20 seconds
4. Boot Process
BIOS → Bootloader → OS Kernel → Services
20-60 seconds
5. User Data Execution
Scripts executed on first boot
Variable
6. Status Checks
System Status Checks and Instance Status Checks
Continuous

💡 Billing Impact: Billing begins when the instance enters the Running state (not during Pending).

✅ You Can: Monitor progress via EC2 console, CloudWatch events, or CLI.
❌ You Cannot: Connect to the instance, attach EBS volumes, or modify instance settings.

🚀 Pending→Running 📋 provisioning 💰 billing starts
⏸️

Transition 2: Running → Stopping → Stopped

Trigger: Stop Instance (user-initiated)

What Happens During Stopping:
1. Shutdown Signal
ACPI shutdown signal sent to OS
Immediate
2. OS Shutdown
Orderly shutdown (systemd or init)
10-60 seconds
3. Process Termination
All running processes terminated
5-20 seconds
4. EBS Sync
All data flushed to EBS volumes
5-15 seconds
5. Instance Deactivation
Instance powered off (vCPU and memory released)
Immediate
6. State Change
Instance transitions to Stopped state
Immediate

💡 Billing Impact: Compute billing stops when the instance enters the Stopping state. EBS storage billing continues.

✅ You Can: Modify instance attributes (type, user data, security groups) while Stopped.
❌ You Cannot: Connect to the instance (it's powered off).

⚠️ Important Notes:
  • If the instance fails to stop (e.g., OS hang), you may need to use Force Stop.
  • Instance store data is lost during stop.
  • Public IP is released; you will get a new public IP when you restart.

Transition 3: Stopped → Pending → Running

Trigger: Start Instance (user-initiated)

What Happens During Start:
1. Resource Re-allocation
AWS finds a new physical host
10-30 seconds
2. EBS Attachment
Root EBS volume attached to new host
10-20 seconds
3. Instance Boot
Instance boots from EBS volume
20-60 seconds
4. OS Initialization
OS services start (SSH, etc.)
10-20 seconds
5. Networking
Instance receives network configuration
5-10 seconds
6. Ready
Instance is operational
-

💡 Billing Impact: Compute billing begins again when the instance enters the Running state.

📌 Important Notes:
  • User data scripts do not execute on start (only on first boot).
  • The instance may be moved to a different physical host.
  • If you changed the instance type while Stopped, it will now launch with the new type.
▶️ Stopped→Running 📋 re-allocation 💰 billing resumes
🔄

Transition 4: Running → Reboot → Running

Trigger: Reboot Instance (user-initiated)

What Happens During Reboot:
1. Shutdown
OS receives reboot signal (ACPI)
10-30 seconds
2. Boot
OS restarts (BIOS → Kernel → OS)
20-60 seconds
3. Services Start
All configured services start
10-30 seconds
4. Status Checks
AWS checks instance health
10-30 seconds

💡 Billing Impact: Billing continues uninterrupted (no break in compute billing).

📌 Important Notes:
  • Reboots are much faster than stop/start (< 5 minutes vs. 5-10 minutes).
  • Instance store data is preserved during reboot (unlike stop/start).
  • Elastic IPs and public IPs remain unchanged.
  • Recommended for applying OS updates and clearing memory state.

Transition 5: Running/Stopped → Terminating → Terminated

Trigger: Terminate Instance (user-initiated)

What Happens During Termination:
1. Shutdown
OS shuts down gracefully (if running)
10-60 seconds
2. Resource Release
vCPU, memory, network resources released
5-10 seconds
3. EBS Volume Deletion
Volumes with DeleteOnTermination=true deleted
10-30 seconds
4. Elastic IP Disassociation
Elastic IPs disassociated (remain in account)
5-10 seconds
5. Instance ID Removal
Instance ID permanently deleted
Immediate
6. State Change
Instance enters Terminated state
Immediate

⚠️ Important Notes:
  • Termination is permanent and irreversible.
  • You can set DeleteOnTermination=false on EBS volumes to preserve them.
  • Elastic IPs are disassociated but remain in your account (you are charged for unused Elastic IPs).
  • Terminated instances disappear from the console after approximately 1 hour.
  • CloudTrail logs the termination event for audit purposes.

Best Practices

⏹️ Stop Before Terminating
Stop first to ensure clean shutdown and preserve EBS data if needed
🔄 Use Reboot for Updates
Reboot for OS updates; faster and preserves instance store data
💾 DeleteOnTermination
Root volume: true; Data volumes: false (preserve important data)
🔗 Lifecycle Hooks
Use Auto Scaling lifecycle hooks to run scripts before termination
📊 Monitor Status Checks
Set CloudWatch alarms for failed status checks
🏷️ Tag Instances
Identify purpose and help with lifecycle management decisions

Key Takeaways

  • Pending → Running: Billing starts when instance reaches Running state. User data executes only on first boot.

  • Running → Stopping → Stopped: Compute billing stops; EBS storage continues. Public IP is released (unless Elastic IP). Instance store data is lost.

  • Stopped → Pending → Running: Instance may move to a different physical host. User data does NOT execute again.

  • Running → Reboot → Running: Fastest state transition. Instance store data preserved. IP addresses unchanged. Billing continues uninterrupted.

  • Running/Stopped → Terminating → Terminated: Permanent and irreversible. EBS volumes deleted unless DeleteOnTermination=false.

  • Always use EBS snapshots before termination to preserve data.

  • CloudTrail logs all state transitions for audit purposes.

Review Questions

Q1: What is the difference between rebooting and stop/start?
Answer: Rebooting preserves the instance's physical host, IP addresses, and instance store data. Stop/start may move the instance to a different physical host, releases the public IP (unless Elastic IP), and loses instance store data. Rebooting is faster (2-5 minutes) and has no billing interruption, while stop/start takes 5-10 minutes with compute billing pausing during the stopped state.
Q2: What happens to Elastic IPs during a stop/start cycle?
Answer: Elastic IPs remain associated with the instance during stop/start cycles. The public IP (non-Elastic) is released when the instance stops and a new one is assigned when it starts. Elastic IPs provide a stable public IP that persists across stop/start cycles.
Q3: What happens to data on the root EBS volume when you terminate an instance?
Answer: The root EBS volume is deleted when you terminate the instance, unless DeleteOnTermination is set to false for the root volume. By default, DeleteOnTermination is true for root volumes.
Q4: How can you preserve EBS volumes when terminating an instance?
Answer: You can set the DeleteOnTermination flag to false on the EBS volume. This can be done when launching the instance (in block device mapping) or after the instance is running (by modifying the volume's attributes). Even with this flag set, the volume will be detached from the instance and persist in your account.
Q5: What are the default billing charges for a stopped instance?
Answer: A stopped instance does not incur compute charges. However, you continue to pay for: EBS storage (root volume and any attached volumes), Elastic IP addresses (if attached), and EBS snapshots (if any). This is why it's important to terminate instances you no longer need.
Q6: How do you handle a failed stop operation (stuck in Stopping state)?
Answer: If an instance is stuck in the Stopping state for an extended period, you can use the "Force Stop" option. This is equivalent to pulling the power plug on the instance. Force stop is available in the EC2 console, CLI (aws ec2 stop-instances --force), and API.
Q7: What is the difference between "Stop" and "Terminate" for Spot Instances?
Answer: Spot Instances cannot be stopped — they can only be rebooted or terminated. When you terminate a Spot Instance, it is permanently deleted. The two-minute warning for Spot Instance interruptions means you should plan for graceful shutdown to avoid data loss.
