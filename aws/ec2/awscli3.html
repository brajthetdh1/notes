3.3.2 Configuring AWS CLI with Access Keys

Once the AWS CLI is installed, the next critical step is configuring it with your credentials. This section covers the complete process of creating IAM access keys, running aws configure, understanding the configuration files, and best practices for secure credential management.

🔑

Prerequisites: Creating IAM Access Keys

Before you can configure the CLI, you need an AWS account and an IAM user with programmatic access. Never use your AWS root user credentials for CLI tasks — always use an IAM user with appropriate permissions.

Step-by-Step: Create Access Keys for an IAM User

1

Choose Command Line Interface

⚠️ Critical Security Warning: This is the only time you can view or download the Secret Access Key. If you close this dialog without saving it, you cannot recover it and must create a new access key.

Your credentials will look like:

Where Credentials Are Stored

The values you provide with aws configure are stored in two separate files within the .aws directory in your user's home folder.

Linux/macOS~/.aws/credentials~/.aws/config
WindowsC:\Users\USERNAME\.aws\credentialsC:\Users\USERNAME\.aws\config

📂 File Contents:
  • Credentials File: Stores aws_access_key_id and aws_secret_access_key.
  • Config File: Stores region and output format settings.

💡 Tip: You can view these files directly using a text editor to confirm your settings.

The Credential Provider Chain

The AWS CLI searches for credentials in a specific order, stopping when it finds a valid set:

🔗 Precedence Order (Highest to Lowest):
  1. Command line options: --region, --output, and --profile parameters
  2. Environment variables: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN
  3. CLI credentials file: ~/.aws/credentials
  4. CLI configuration file: ~/.aws/config
  5. Container credentials: IAM roles for Amazon ECS tasks
  6. Instance profile credentials: IAM roles for Amazon EC2 instances

💡 Key Takeaway: Environment variables take precedence over credentials stored in files. This is useful for temporary overrides.
🔗 provider chain 📋 precedence 🌐 env vars
👥

Working with Multiple Profiles

If you manage multiple AWS accounts or environments, you can configure named profiles.

Creating a Named Profile:
aws configure --profile dev-account

Using a Named Profile:
aws s3 ls --profile dev-account

Setting a Default Profile with Environment Variables:
# Linux/macOS export AWS_PROFILE=dev-account # Windows Command Prompt setx AWS_PROFILE dev-account # Windows PowerShell $Env:AWS_PROFILE="dev-account"

Override a specific setting for a profile:
aws configure set region us-west-2 --profile dev-account
👥 profiles 🔑 multiple accounts 🌍 region override

Verifying Your Configuration

To confirm that your AWS CLI is configured correctly and authenticated, run this command:
aws sts get-caller-identity
Expected Output:
{ "UserId": "AIDA...", "Account": "123456789012", "Arn": "arn:aws:iam::123456789012:user/your-username" }

✅ This confirms:
  • Your credentials are valid
  • You are authenticated as the correct IAM user

Additional Verification Commands:
  • aws s3 ls — test basic S3 permissions
  • aws configure list — view current configuration settings
✅ verify 🔍 sts get-caller-identity 📋 aws configure list

Advanced: Managing Multiple Access Keys

An IAM user can have up to two active access keys at a time. This allows for zero-downtime rotation:

🔄 Rotation Process:
  1. Create a new access key
  2. Update your applications/scripts to use the new key
  3. Verify everything works correctly
  4. Mark the old key as Inactive (not deleted)
  5. Monitor for any issues for a few days
  6. Delete the old key

CLI Commands for Key Rotation:
# Create a new key aws iam create-access-key --user-name my-service-account # Deactivate the old key aws iam update-access-key \ --user-name my-service-account \ --access-key-id AKIAIOSFODNN7OLDKEY \ --status Inactive # After verification, delete the old key aws iam delete-access-key \ --user-name my-service-account \ --access-key-id AKIAIOSFODNN7OLDKEY

Rotation Best Practices:
🟢 General Workloads
Every 90 days
🔵 High-Security Workloads
Every 30-60 days
🔴 Outdated Practice
Every 1 year (too long)

Key Takeaways

  • Never use root user credentials for the AWS CLI — always create an IAM user with programmatic access.

  • Download or copy your Secret Access Key immediately after creation. You cannot view it again.

  • The aws configure command is the fastest way to set up your default profile, storing credentials in ~/.aws/credentials and settings in ~/.aws/config.

  • Use named profiles (aws configure --profile <name>) to manage multiple AWS accounts or environments.

  • The CLI uses a credential provider chain with a specific precedence order — environment variables override file-based credentials.

  • Rotate access keys regularly — 90 days is the recommended maximum for general workloads.

  • Verify your configuration with aws sts get-caller-identity or aws configure list.

Review Questions

Q1: What is the purpose of the aws configure command?
Answer: The aws configure command is the quickest way to set up your AWS CLI installation. It prompts you for your access key ID, secret access key, default region, and default output format. It then stores these values in the ~/.aws/credentials and ~/.aws/config files for the default profile.
Q2: Why should you not use root user access keys with the AWS CLI?
Answer: As a best practice, you should not use the AWS account root user access keys for any task where it's not required. Instead, create a new IAM user with programmatic access. The root user has unrestricted access to all AWS resources, making it a massive security risk if the credentials are compromised. IAM users follow the principle of least privilege.
Q3: What are the four values prompted for by aws configure?
Answer: The four values are:
  • AWS Access Key ID — your IAM access key
  • AWS Secret Access Key — your IAM secret key
  • Default region name — the AWS Region to use by default (e.g., us-east-1)
  • Default output format — how results are formatted (json, text, or table)
Q4: Where are AWS CLI credentials stored after running aws configure?
Answer: The credentials are stored in two files within the .aws directory in your user's home folder:
  • Credentials file (~/.aws/credentials) — stores the access keys
  • Config file (~/.aws/config) — stores region and output format settings
Q5: How can you create and use a named profile for multiple AWS accounts?
Answer: Use aws configure --profile <profile-name> to create a named profile. To use it:
  • Add --profile <profile-name> to each command: aws s3 ls --profile produser
  • Set the AWS_PROFILE environment variable for the current session
Q6: How can you verify that your AWS CLI is configured correctly?
Answer: The most reliable verification method is running aws sts get-caller-identity, which returns your IAM user/role ARN and confirms your credentials are valid. You can also run aws s3 ls (with appropriate permissions) to test basic service access, or aws configure list to see where the CLI found each configuration value.
