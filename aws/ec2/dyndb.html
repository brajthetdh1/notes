What is DynamoDB?

Amazon DynamoDB is a fully managed NoSQL database service that delivers fast and predictable performance with seamless scalability. It uses a key-value and document data model, automatically replicates across multiple Availability Zones, and offers both on-demand and provisioned capacity modes.

Core Characteristics

  • Single-digit millisecond latency for reads and writes.
  • Fully managed with automatic scaling and replication.
  • Flexible primary keys (partition key or partition + sort key).
  • Secondary indexes (GSI and LSI) for additional query flexibility.
  • DynamoDB Streams for change-data capture and event-driven triggers.

Use Cases

DynamoDB is widely used for building applications such as e-commerce product catalogs, user session stores, IoT telemetry ingestion, gaming leaderboards, and serverless backends integrated with AWS Lambda and API Gateway.

Data Organization

1. Partitions (Physical Storage)

DynamoDB stores data across multiple partitions (distributed storage nodes).

The Partition Key decides which partition holds your data.

Good partition key choice = data spread evenly = consistent performance.

Bad partition key choice = hot partition (too many reads/writes on a single partition).

2. Sort Key (for Composite Keys)

If you use a composite primary key (Partition Key + Sort Key):

Partition Key groups related items together.

Sort Key orders them (lexicographically).

This enables range queries: e.g., fetch all orders for a user between two dates.

3. Item Collection

All items with the same partition key value form an item collection.

This is where LSIs (Local Secondary Indexes) operate.

🔹 Indexes in Depth

Local Secondary Index (LSI)

  • Same partition key as the main table, but a different sort key.
  • Created only at table creation.
  • Limited to 5 LSIs per table.
  • Good when you want multiple views on the same group of items.

Global Secondary Index (GSI)

  • Different partition key (and optional sort key) than the main table.
  • Can be created anytime.
  • Up to 20 GSIs per table.
  • Ideal for queries that don’t fit your base table’s primary key.

🔹 Query vs Scan (Important!)

Query

  • Retrieves items based on partition key (and optional sort key conditions).
  • Very efficient, uses indexes.
  • Example: Get all messages for chatId = 123 sorted by timestamp.

Scan

  • Reads the entire table item by item.
  • Much slower, more expensive.
  • Should be avoided for production use unless necessary.

🔹 Capacity & Performance Deep Dive

Read Capacity Units (RCU)

  • 1 RCU = 1 strongly consistent read/sec of up to 4 KB.
  • Or 2 eventually consistent reads/sec of up to 4 KB.

Write Capacity Units (WCU)

  • 1 WCU = 1 write/sec of up to 1 KB.

On-Demand Mode

  • Scales automatically.
  • Pay-per-request.
  • Useful for unpredictable traffic.

Provisioned Mode

  • You set RCUs and WCUs.
  • Cheaper if traffic is predictable.
  • Can enable Auto Scaling to adjust units as traffic changes.

📌 Primary Key in DynamoDB (Detailed Explanation)

A Primary Key in DynamoDB uniquely identifies each item in a table. Unlike SQL databases where you can have multiple unique constraints, DynamoDB requires exactly one primary key per table, and every item must have a unique value for it.

1. Types of Primary Keys

🔹 Simple Primary Key (Partition Key Only)

Consists of a single attribute called the Partition Key.

DynamoDB uses the Partition Key value to determine which physical partition stores the item.

Every item must have a unique partition key value in this model.

👉 Example:

Table: Users
Partition Key: userId
Item:
{
  "userId": "101",
  "name": "Alice",
  "email": "alice@example.com"
}

Here, userId uniquely identifies each user.

📌 Best suited when:

You only need to look up items by one unique ID (like UserID, ProductID).

🔹 Composite Primary Key (Partition Key + Sort Key)

Consists of two attributes:

  • Partition Key: Groups related items together.
  • Sort Key: Orders items within the same partition.

Multiple items can have the same partition key, but each must have a different sort key.

Together, (Partition Key, Sort Key) must be unique.

👉 Example:

Table: Orders
Partition Key: userId
Sort Key: orderDate
Items:
{
  "userId": "101",
  "orderDate": "2025-01-01",
  "amount": 150
}
{
  "userId": "101",
  "orderDate": "2025-02-10",
  "amount": 200
}

Both items have the same userId but different orderDate.

📌 Benefits:

Enables range queries on the Sort Key.

Example: Get all orders for userId=101 where orderDate is between 2025-01-01 and 2025-03-01.

2. How Partition Key Works

The Partition Key value is passed through a hashing function.

The hash decides which physical partition (storage node) stores the item.

If too many items share the same partition key, this causes a hot partition (performance bottleneck).

👉 Example of Good vs Bad Partition Key:

  • Good: userId for a large user base (millions of users → data spreads well).
  • Bad: countryCode (if 90% users are from one country, all requests hit the same partition).

3. Why Sort Key Matters

Without Sort Key → You can only retrieve a single item by Partition Key.

With Sort Key → You can retrieve multiple items sharing the same Partition Key, ordered lexicographically.

👉 Example query:

Get all Orders for userId=101 sorted by orderDate.

4. Real-World Examples

Table Partition Key Sort Key Use Case
Users userId — Lookup users by ID
Orders userId orderDate Fetch user orders in order
Messages chatId timestamp Get messages in a chat by time
Products category productId Fetch all products in a category

5. Key Design Principles

  • Choose a partition key with high cardinality (many distinct values).
  • Distribute traffic evenly across partitions.
  • Use composite keys when you need to model 1-to-many relationships.
  • Consider access patterns first before designing primary keys (DynamoDB schema design is query-driven).

✅ In short:

Simple Primary Key → Unique item lookup.

Composite Primary Key → Grouping + ordering of items.

High Availability & Durability in DynamoDB

DynamoDB is designed to provide continuous uptime and data safety, even in the face of hardware failures, AZ (Availability Zone) outages, or sudden spikes in traffic.

1. Multi-AZ Data Replication (Built-In Redundancy)

DynamoDB is a regional service. When you write data to a DynamoDB table, it is automatically synchronously replicated across multiple Availability Zones (AZs) within the same AWS Region.

  • If one AZ goes down, your table is still available in another AZ.
  • No need for you to manage replication manually.

📌 Analogy: Imagine you save a document — DynamoDB makes 3 copies of it in different “buildings” (AZs) instantly.

2. Automatic Failover

Because the data is spread across multiple AZs: If one AZ experiences hardware/network issues, DynamoDB automatically routes traffic to healthy replicas. This ensures high availability with no downtime for your application.

3. Durability through Replication

Data durability means your data won’t get lost even if hardware fails. DynamoDB achieves durability by:

  • Writing multiple copies of each item across AZs.
  • Using a quorum-based write mechanism (write acknowledged only after data is safely stored in multiple replicas).

4. Consistency Models

To balance availability and performance, DynamoDB offers two read models:

  • Eventually Consistent Reads (default): Reads might not reflect the latest write instantly, but replicas will synchronize quickly. Provides higher availability with lower latency.
  • Strongly Consistent Reads: Guarantees you always read the latest committed value. Reads from the leader replica. Slightly higher latency.

5. Backup & Restore

  • Point-in-Time Recovery (PITR): DynamoDB can restore your table to any second within the last 35 days.
  • On-Demand Backups: Create full table backups at any time without affecting performance.

These features ensure long-term durability against accidental deletion or corruption.

6. Global Tables (Cross-Region Replication)

DynamoDB Global Tables replicate your data across multiple AWS Regions.

  • Disaster recovery (if an entire region goes down).
  • Low-latency reads/writes for globally distributed applications.
  • Provides multi-active replication (you can write in any region, and DynamoDB syncs changes).

7. Auto Scaling & On-Demand Mode

DynamoDB automatically scales capacity (RCUs/WCUs) up and down based on traffic. This prevents service outages due to unexpected spikes, keeping your application always available.

8. SLA (Service Level Agreement)

AWS provides a 99.999% availability SLA for DynamoDB Global Tables and 99.99% availability for standard DynamoDB tables. This level of uptime is achieved through:

  • Redundancy
  • Automated failover
  • Continuous monitoring

✅ Summary

DynamoDB ensures high availability and durability through:

  • Multi-AZ replication within a region.
  • Automatic failover to healthy replicas.
  • Quorum-based writes and replication for durability.
  • Configurable consistency models (eventual vs strong).
  • Point-in-time recovery and backups.
  • Global Tables for cross-region disaster recovery and low-latency access.
  • Auto scaling to handle traffic bursts.

Indexes in DynamoDB (Detailed Explanation)

DynamoDB indexes are data structures that let you query the table using alternative keys (attributes other than your primary key). There are two types: Local Secondary Index (LSI) and Global Secondary Index (GSI).

1. Local Secondary Index (LSI)

🔹 Definition

  • LSI shares the same Partition Key as the base table.
  • Uses a different Sort Key to provide alternate views of the same partition.
  • You must define LSIs at table creation time (cannot add later).
  • Limited to 5 LSIs per table.

🔹 How It Works

Example:

  • Partition Key: userId
  • Sort Key: orderDate

Add an LSI with:

  • Partition Key: userId (same as base table)
  • Sort Key: orderAmount

Now you can query all orders for a user, but sorted by amount instead of date.

🔹 Storage

  • LSIs use the same storage as the base table.
  • Updates to the base table also update LSIs.
  • They count towards the item size limit (400 KB) of the table.

🔹 Use Cases

Multiple ways to query items within the same partition:

  • Orders by date
  • Orders by price
  • Orders by status

2. Global Secondary Index (GSI)

🔹 Definition

  • GSI can have a different Partition Key and an optional Sort Key from the base table.
  • You can create GSIs anytime (not limited to table creation).
  • Each table can have up to 20 GSIs.

🔹 How It Works

Base Table:

  • Partition Key: userId
  • Sort Key: orderDate

Add GSI:

  • Partition Key: productId
  • Sort Key: orderDate

Now you can fetch all orders for a product across users.

🔹 Storage

  • GSIs use separate storage.
  • They maintain their own RCUs (Read Capacity Units) and WCUs (Write Capacity Units).
  • Updates in the base table are automatically propagated to GSIs asynchronously.

🔹 Use Cases

  • Find all orders by productId.
  • Fetch items by status.
  • Enable many-to-many relationships.

3. Key Differences Between LSI and GSI

Feature LSI GSI
Partition Key Same as base table Different from base table
Sort Key Different from base table Optional (can have or not)
Creation Time Only at table creation Anytime
Storage Shares storage with base table Separate storage
Item Size Limit 400 KB (same as base table) Each GSI item also limited to 400 KB
Consistency Supports strongly consistent reads Only eventually consistent reads
Max per Table 5 LSIs 20 GSIs

4. Real-World Example

Table: Orders

  • Partition Key: userId
  • Sort Key: orderDate

LSI:

  • Partition Key: userId
  • Sort Key: orderAmount

Query → Get all orders for a user sorted by amount.

GSI:

  • Partition Key: productId
  • Sort Key: orderDate

Query → Get all orders for a product across all users.

5. Best Practices

Use LSI when:

  • You need multiple query patterns for the same partition.
  • Strongly consistent reads are important.

Use GSI when:

  • You need to query data using completely different attributes.
  • You want more flexibility (since they can be added later).

✅ In Summary

  • LSI → Same Partition Key, different Sort Key, multiple views of the same partition.
  • GSI → Different Partition Key (and optional Sort Key), enables completely new query patterns.

CRUD Operations in DynamoDB (Real-World Example)

Table: Users

userId (PK) name email age
101 Alice Doe alice@example.com 25
102 Bob Smith bob@example.com 30

1. Create (PutItem)

{
  "TableName": "Users",
  "Item": {
    "userId": { "N": "103" },
    "name": { "S": "Charlie Brown" },
    "email": { "S": "charlie@example.com" },
    "age": { "N": "28" }
  }
}

👉 Inserts a new record for Charlie. If userId=103 already exists, it overwrites unless you add a ConditionExpression like attribute_not_exists(userId).

2. Read

a) GetItem – Fetch user by ID

{
  "TableName": "Users",
  "Key": {
    "userId": { "N": "101" }
  }
}

👉 Returns Alice’s full record.

b) Query – Example with Sort Key

Find all users with ID > 100 or query ranges if a Sort Key exists (e.g., createdDate BETWEEN 2023-01-01 AND 2023-12-31).

c) Scan – Fetch all users

{
  "TableName": "Users"
}

👉 Returns every record (Alice, Bob, Charlie, etc.) – but slower & costly.

3. Update (UpdateItem)

{
  "TableName": "Users",
  "Key": {
    "userId": { "N": "101" }
  },
  "UpdateExpression": "SET age = :newAge",
  "ExpressionAttributeValues": {
    ":newAge": { "N": "26" }
  }
}

👉 Updates Alice’s age from 25 → 26. Other fields remain unchanged.

4. Delete (DeleteItem)

{
  "TableName": "Users",
  "Key": {
    "userId": { "N": "102" }
  }
}

👉 Deletes Bob’s record. Optionally, add a condition (e.g., delete only if age=30).

5. Batch Operations

  • BatchWriteItem: Insert Charlie + Delete Bob in one request.
  • BatchGetItem: Retrieve Alice + Charlie in one request.

⚡ Summary

  • Create (PutItem): Add Charlie.
  • Read (GetItem/Query/Scan): Fetch Alice or all users.
  • Update (UpdateItem): Update Alice’s age.
  • Delete (DeleteItem): Delete Bob.
  • Batch: Perform multiple actions at once.

DynamoDB CRUD Operations via AWS CLI

1. Create (PutItem) – Add Charlie

aws dynamodb put-item \
  --table-name Users \
  --item '{
    "userId": {"N": "103"},
    "name": {"S": "Charlie Brown"},
    "email": {"S": "charlie@example.com"},
    "age": {"N": "28"}
  }'

2. Read

a) GetItem – Fetch Alice (userId=101)

aws dynamodb get-item \
  --table-name Users \
  --key '{
    "userId": {"N": "101"}
  }'

b) Scan – Fetch all users

aws dynamodb scan --table-name Users

3. Update (UpdateItem) – Update Alice’s age to 26

aws dynamodb update-item \
  --table-name Users \
  --key '{
    "userId": {"N": "101"}
  }' \
  --update-expression "SET age = :newAge" \
  --expression-attribute-values '{
    ":newAge": {"N": "26"}
  }'

4. Delete (DeleteItem) – Remove Bob (userId=102)

aws dynamodb delete-item \
  --table-name Users \
  --key '{
    "userId": {"N": "102"}
  }'

5. Batch Operations

a) BatchWriteItem – Insert Charlie + Delete Bob

aws dynamodb batch-write-item \
  --request-items '{
    "Users": [
      {
        "PutRequest": {
          "Item": {
            "userId": {"N": "103"},
            "name": {"S": "Charlie Brown"},
            "email": {"S": "charlie@example.com"},
            "age": {"N": "28"}
          }
        }
      },
      {
        "DeleteRequest": {
          "Key": {
            "userId": {"N": "102"}
          }
        }
      }
    ]
  }'

⚡ With these exact AWS CLI commands, you can directly test CRUD operations in DynamoDB.

Advanced DynamoDB AWS CLI Commands

1. Query Items by Partition Key

aws dynamodb query \
  --table-name Users \
  --key-condition-expression "userId = :uid" \
  --expression-attribute-values '{":uid":{"N":"101"}}'

✅ Fetches all items with userId=101.

aws dynamodb query \
  --table-name Orders \
  --key-condition-expression "userId = :uid AND orderDate BETWEEN :start AND :end" \
  --expression-attribute-values '{":uid":{"N":"101"}, ":start":{"S":"2025-01-01"}, ":end":{"S":"2025-12-31"}}'

2. Scan with Filter Expression

aws dynamodb scan \
  --table-name Users \
  --filter-expression "age > :minAge" \
  --expression-attribute-values '{":minAge":{"N":"25"}}'

Returns users older than 25. Useful for ad-hoc queries when keys are unknown.

3. Conditional PutItem (Prevent Overwrite)

aws dynamodb put-item \
  --table-name Users \
  --item '{
    "userId": {"N": "104"},
    "name": {"S": "David Johnson"},
    "email": {"S": "david@example.com"},
    "age": {"N": "29"}
  }' \
  --condition-expression "attribute_not_exists(userId)"

Fails if userId=104 already exists.

4. Update with Conditional Expression

aws dynamodb update-item \
  --table-name Users \
  --key '{"userId":{"N":"103"}}' \
  --update-expression "SET age = :newAge" \
  --condition-expression "age < :maxAge" \
  --expression-attribute-values '{":newAge":{"N":"30"}, ":maxAge":{"N":"30"}}'

5. BatchGetItem

aws dynamodb batch-get-item \
  --request-items '{
    "Users": {
      "Keys": [
        {"userId":{"N":"101"}},
        {"userId":{"N":"103"}}
      ]
    }
  }'

6. BatchWriteItem

aws dynamodb batch-write-item \
  --request-items '{
    "Users": [
      {
        "PutRequest": {
          "Item": {
            "userId":{"N":"105"},
            "name":{"S":"Eve Adams"},
            "email":{"S":"eve@example.com"},
            "age":{"N":"27"}
          }
        }
      },
      {
        "DeleteRequest": {
          "Key": {
            "userId":{"N":"103"}
          }
        }
      }
    ]
  }'

7. Create a Global Secondary Index (GSI)

aws dynamodb update-table \
  --table-name Users \
  --attribute-definitions AttributeName=email,AttributeType=S \
  --global-secondary-index-updates '[
    {
      "Create": {
        "IndexName": "EmailIndex",
        "KeySchema":[
          {"AttributeName":"email","KeyType":"HASH"}
        ],
        "Projection":{"ProjectionType":"ALL"},
        "ProvisionedThroughput":{"ReadCapacityUnits":5,"WriteCapacityUnits":5}
      }
    }
  ]'

Now you can query users by email:

aws dynamodb query \
  --table-name Users \
  --index-name EmailIndex \
  --key-condition-expression "email = :email" \
  --expression-attribute-values '{":email":{"S":"alice@example.com"}}'

8. Update Table Capacity (Provisioned Mode)

aws dynamodb update-table \
  --table-name Users \
  --provisioned-throughput ReadCapacityUnits=10,WriteCapacityUnits=5

✅ Summary of Useful Commands

  • put-item: Insert / create items (with conditional expressions)
  • get-item: Read single item by key
  • query: Efficient multi-item read by Partition + Sort Key
  • scan: Read entire table with filters
  • update-item: Update attributes (with optional conditions)
  • delete-item: Remove items
  • batch-get-item: Fetch multiple items at once
  • batch-write-item: Insert/Delete multiple items
  • update-table: Modify table capacity or add GSI/LSI
