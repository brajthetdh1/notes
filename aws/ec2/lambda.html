AWS Lambda: Serverless Computing

AWS Lambda is a fully managed serverless compute service that lets you run code without provisioning or managing servers. You only pay for the compute time you consume, making it highly scalable and cost-effective.

Key Features

  • Serverless: No server management required.
  • Automatic scaling based on request volume.
  • Supports multiple languages (Node.js, Python, Java, Go, .NET, Ruby).
  • Integrated with AWS ecosystem (S3, DynamoDB, API Gateway, etc.).
  • Event-driven execution triggered by AWS services or HTTP requests.

Concurrency & Performance

Lambda functions can scale to handle thousands of concurrent requests. Key concurrency concepts include:

  • Unreserved Concurrency: Shared pool across region.
  • Reserved Concurrency: Guarantees a fixed number of executions.
  • Provisioned Concurrency: Keeps instances warm to avoid cold start latency.

Use Cases

AWS Lambda is ideal for applications that require scalable, event-driven computing:

  • Data processing from S3, DynamoDB streams, or Kinesis.
  • Backend for web and mobile applications via API Gateway.
  • Real-time file or image transformations.
  • Scheduled tasks using Amazon EventBridge (CloudWatch Events).

AWS EC2 vs AWS Lambda

AWS provides multiple compute services to build and run applications. Two popular options are Amazon EC2 and AWS Lambda. Choosing the right service depends on your workload, scalability, and cost requirements.

Feature Amazon EC2 AWS Lambda
Compute Model Virtual servers you manage; persistent instances. Serverless, event-driven compute; automatically managed by AWS.
Scaling Manual or auto-scaling via Auto Scaling Groups. Automatic scaling with concurrency limits; scales per request.
Pricing Pay per running instance (hourly or per second depending on OS). Pay per execution duration and memory used; no charge when idle.
Use Cases Long-running applications, custom OS or software requirements, databases, legacy apps. Event-driven tasks, microservices, real-time file processing, short-lived jobs.
Management You manage OS updates, patches, scaling, and networking. AWS fully manages runtime, scaling, and infrastructure.
Startup Time Minutes depending on instance type. Milliseconds to seconds; cold starts may add latency.
State Management Persistent storage attached via EBS, local disks. Stateless by design; requires external storage (S3, DynamoDB) for persistent state.

Key Takeaways

  • Use EC2 for full control, persistent workloads, or legacy applications.
  • Use Lambda for event-driven, short-lived tasks and serverless architectures.
  • Lambda reduces operational overhead and scales automatically, but EC2 provides more flexibility and control.
  • Cost depends on usage patterns: Lambda can be cheaper for sporadic workloads, while EC2 may be cost-effective for continuously running servers.

Creating a Lambda Function in Java

Here is a step-by-step explanation of creating an AWS Lambda function in Java without showing code, focusing on concepts and workflow:

1. Set Up Your Java Project

Choose a build tool like Maven or Gradle to manage dependencies. Add AWS Lambda dependencies, primarily:

  • aws-lambda-java-core for the Lambda interfaces.
  • aws-lambda-java-events if your Lambda will handle specific AWS events (like API Gateway, S3, or DynamoDB).
  • Optionally, include logging dependencies for monitoring output in CloudWatch.

2. Implement the Lambda Handler

AWS Lambda requires a handler method that processes incoming events. There are two main approaches:

  • RequestHandler Interface: Accepts input of a specific type (e.g., String, Map) and returns a result.
  • RequestStreamHandler Interface: Works with raw input and output streams; useful for HTTP events or binary data.

The handler contains the business logic of your Lambda function.

3. Configure Project for Deployment

Package your project into a JAR file that contains all dependencies (often called a “fat JAR”). Use a tool like the Maven Shade Plugin or Gradle equivalent to bundle dependencies together. Ensure the fully qualified class name of your handler is known for AWS to invoke it.

4. Deploy Lambda to AWS

You can deploy via:

  • AWS Management Console: Upload the packaged JAR and configure the function.
  • AWS CLI: Use commands to create or update the Lambda function.
  • Infrastructure as Code: Use SAM, CloudFormation, or CDK for automated deployments.

During deployment, specify:

  • Handler name (fully qualified class + method).
  • Memory and timeout settings.
  • Execution role with proper permissions for AWS services your Lambda interacts with.

5. Configure Event Sources

Decide how Lambda is triggered:

  • Direct API calls via API Gateway.
  • Object uploads in S3.
  • Streams like Kinesis or DynamoDB.

Lambda automatically scales and executes in response to these events.

6. Test and Monitor

Test Lambda using console test events or real triggers from configured services. Monitor via CloudWatch logs to check execution, errors, and performance. Optionally, set up X-Ray for tracing and debugging complex workflows.

Key Concepts

  • Lambda is serverless, so AWS handles infrastructure, scaling, and patching.
  • Lambda is stateless, so any persistent state must be stored in external services like S3, DynamoDB, or RDS.
  • Proper configuration of memory, timeout, and concurrency ensures performance and cost efficiency.

AWS Lambda Handlers in Java

Examples of Java Lambda handlers using different interfaces.

1. RequestHandler Interface


import com.amazonaws.services.lambda.runtime.Context;
import com.amazonaws.services.lambda.runtime.RequestHandler;

public class MyLambdaHandler implements RequestHandler<String, String> {

    @Override
    public String handleRequest(String input, Context context) {
        context.getLogger().log("Received input: " + input);
        return "Hello, " + input + "!";
    }
}

This handler takes a String input and returns a String output. The Context object allows logging and accessing runtime information.

2. RequestStreamHandler Interface


import com.amazonaws.services.lambda.runtime.Context;
import com.amazonaws.services.lambda.runtime.RequestStreamHandler;
import java.io.InputStream;
import java.io.OutputStream;
import java.io.IOException;

public class MyStreamLambdaHandler implements RequestStreamHandler {

    @Override
    public void handleRequest(InputStream input, OutputStream output, Context context) throws IOException {
        byte[] buffer = input.readAllBytes();
        String inputString = new String(buffer);
        String response = "Processed: " + inputString;
        output.write(response.getBytes());
    }
}

This handler works with raw input and output streams, useful for HTTP events, API Gateway proxy events, or binary data processing.

Java Lambda Function Triggered via API Gateway

1. Lambda Function in Java

A simple Lambda function that returns a greeting message based on JSON input. 


package com.example.lambda;

import com.amazonaws.services.lambda.runtime.Context;
import com.amazonaws.services.lambda.runtime.RequestHandler;
import java.util.Map;
import java.util.HashMap;

public class GreetingLambda implements RequestHandler<Map<String, String>, Map<String, String>> {

    @Override
    public Map<String, String> handleRequest(Map<String, String> input, Context context) {
        context.getLogger().log("Received input: " + input);
        
        String name = input.getOrDefault("name", "World");
        String message = "Hello, " + name + "!";

        Map<String, String> response = new HashMap<>();
        response.put("message", message);
        return response;
    }
}

Creating a Java Lambda Function and Pointing to JAR

Step 1: Go to AWS Lambda Console

  • Open the AWS Lambda Console.
  • Click Create function → choose Author from scratch.

AWS prepares an environment with a JVM for your Java code execution.

Step 2: Configure Basic Function Settings

  • Function Name: e.g., GreetingLambda
  • Runtime: Select Java 17
  • Execution Role: Attach an IAM role with permissions for required AWS services (CloudWatch logging, S3, DynamoDB, etc.)

At this point, AWS has created an empty function ready to run your Java code.

Step 3: Upload Your Java JAR

  • Scroll to the Code source section.
  • Upload a .jar file containing your compiled Java code and dependencies.
  • Ensure the JAR contains the handler class GreetingLambda implementing RequestHandler.

The uploaded JAR is the **executable code** that Lambda will run.

Step 4: Specify the Handler

In the Handler field, enter:

com.example.lambda.GreetingLambda::handleRequest
  • Class: com.example.lambda.GreetingLambda → Java class inside the JAR.
  • Method: handleRequest → Method AWS will call on each Lambda invocation.

AWS Lambda runtime loads this class into the JVM and executes this method whenever an event triggers the function.

Step 5: Deploy and Test

  • Click Deploy to make the function active.
  • Optionally, create a test event in the console to send JSON input to your Java handler and verify the response.

Handling Multiple Methods in a Java Lambda Class

Lambda Invokes Only the Handler Method

AWS Lambda calls only one method in your Java class, the one specified as the handler (e.g., GreetingLambda::handleRequest). Any other methods in the class are not invoked directly by Lambda.

Option 1: Call Other Methods Internally from the Handler

Use the handler method as the entry point and delegate to other methods based on input: 


public class GreetingLambda implements RequestHandler<Map<String, String>, Map<String, String>> {

    @Override
    public Map<String, String> handleRequest(Map<String, String> input, Context context) {
        String type = input.getOrDefault("type", "greet");
        if ("greet".equals(type)) {
            return greet(input);
        } else if ("farewell".equals(type)) {
            return farewell(input);
        }
        return defaultResponse();
    }

    private Map<String, String> greet(Map<String, String> input) {
        Map<String, String> response = new HashMap<>();
        response.put("message", "Hello, " + input.getOrDefault("name", "World") + "!");
        return response;
    }

    private Map<String, String> farewell(Map<String, String> input) {
        Map<String, String> response = new HashMap<>();
        response.put("message", "Goodbye, " + input.getOrDefault("name", "World") + "!");
        return response;
    }

    private Map<String, String> defaultResponse() {
        Map<String, String> response = new HashMap<>();
        response.put("message", "Unknown type");
        return response;
    }
}

Option 2: Create Separate Lambda Functions

  • If the methods represent completely independent functionality, create separate Lambda functions for each method.
  • Example handler mappings:
    • GreetingLambda::greetHandler
    • GreetingLambda::farewellHandler

Option 3: Dispatcher Pattern

Use a single handler method as a dispatcher that routes requests to different service classes or methods based on an input field like action or type. This is useful for API Gateway endpoints that perform multiple actions.

Key Takeaways

Scenario How Lambda Behaves Recommended Approach
Multiple methods in one class Only the handler method is invoked Use internal calls or dispatcher logic
Independent methods Cannot be invoked automatically Create separate Lambda functions for each handler
Multiple behaviors under one endpoint Handler decides which method to execute based on input Use dispatcher pattern

AWS Lambda and Web Applications

AWS Lambda can be used to power web applications, especially in a serverless architecture. By integrating Lambda with API Gateway, Lambda functions can be exposed as HTTP endpoints that respond to REST or GraphQL requests. This setup works well when the frontend is hosted on a static platform like S3 with CloudFront and the backend consists of small, stateless functions handling business logic, database queries, or event-driven tasks. Lambda provides automatic scaling, pay-per-use pricing, and eliminates the need to manage servers. For microservices-based web applications, combining Lambda, API Gateway, and managed databases such as DynamoDB or Aurora Serverless is often highly efficient.

However, Lambda is not the same as a traditional always-on web server, which introduces some limitations. One major concern is cold starts, particularly with Java Lambdas, where the JVM must initialize before processing the first request, causing latency of hundreds of milliseconds to several seconds. Lambdas are also short-lived, with a maximum execution time of 15 minutes, making them unsuitable for long-running tasks or persistent WebSocket connections. Additionally, Lambda functions are stateless, so any session information or in-memory data must be stored externally in services such as DynamoDB, Redis, or RDS. Handling large file uploads is constrained by memory and temporary storage limits, and complex Java frameworks like Spring Boot may increase cold-start times, impacting responsiveness.

Because of these characteristics, Lambda is best suited for API-driven backends, event-driven processing, and serverless microservices, rather than traditional monolithic web applications requiring persistent sessions or long-running processes. For high-traffic Java web apps that require always-on servers and persistent connections, EC2, Fargate, or containerized Spring Boot applications are typically a better fit. A hybrid approach can also be effective: the frontend is fully serverless using S3 and CloudFront, while Lambda handles lightweight API endpoints and heavier or stateful services run on traditional servers or containers.

In summary, AWS Lambda is a powerful tool for web applications that are stateless, event-driven, and modular, but it requires careful consideration of cold starts, execution limits, and external state management. For full-featured, traditional Java web applications, other compute options are usually more appropriate.

Handling Multiple APIs with AWS Lambda

You do not always need a separate Lambda function for each API endpoint. The design depends on traffic patterns, performance, and maintainability requirements.

Single Lambda for Multiple APIs (Dispatcher Pattern)

A single Lambda function can handle multiple API endpoints by implementing a dispatcher in the handler. The Lambda inspects the incoming event (from API Gateway) to determine which internal method or service to execute.

For example, both /greet and /farewell API requests can be routed to the same Lambda function. The handler checks a field like action or path in the event, then calls greet() or farewell() internally.

Advantages: Fewer Lambda deployments, shared initialization, and easier code maintenance.
Considerations: Cold start affects all endpoints, and heavy traffic on one API may impact others.

Separate Lambda per API

Alternatively, each API endpoint can have its own Lambda function. For example:

  • GreetingLambda::greetHandler → /greet
  • GreetingLambda::farewellHandler → /farewell

Advantages: Independent scaling per API, better isolation, and easier monitoring and logging.
Considerations: More Lambda functions to manage, potential code duplication unless shared via Lambda layers.

Best Practices

Use a single Lambda when APIs are lightweight, related, or share initialization logic. Use multiple Lambdas when APIs are heavy, independent, or have distinct scaling needs. Lambda layers can help share common code between functions.

In summary, whether you create one Lambda or many depends on your app design, traffic patterns, and performance requirements. The dispatcher pattern is often a practical compromise for multiple related endpoints.

AWS Lambda and Microservices

AWS Lambda is well-suited for building microservices, especially in a serverless architecture. Each Lambda function can act as an independent service responsible for a single piece of business logic. This aligns perfectly with the microservices principle of single responsibility. For example, separate Lambda functions can handle order processing, inventory updates, sending notifications, or authentication, allowing each service to scale and deploy independently.

Lambda integrates seamlessly with other AWS services to enable a fully event-driven microservices ecosystem. An S3 upload can trigger a Lambda to process files, messages in an SQS queue can trigger order processing, and DynamoDB streams or EventBridge events can trigger other Lambda functions. This enables asynchronous communication between services, ensuring that high load or failures in one microservice do not directly impact others.

One of Lambda's major benefits for microservices is automatic scaling. Each function scales independently based on incoming events or API requests, eliminating the need to provision servers. Combined with API Gateway, Lambda can expose HTTP endpoints, providing a fully serverless API layer for your microservices.

Lambda also supports modular and reusable code through Lambda layers. Shared libraries or utilities can be included as layers, allowing multiple microservices to reuse the same code without duplication. This supports the microservices principle of independent deployability while maintaining shared standards.

In summary, AWS Lambda supports microservices by providing small, focused, independently deployable functions that can be triggered by events or HTTP requests, scale automatically, integrate with other AWS services, and allow asynchronous communication. This makes Lambda ideal for building cost-efficient, scalable, and decoupled serverless microservices architectures.

Managing Multiple APIs in Java Lambda

Using separate Lambda functions for each API endpoint with different JARs can quickly become bulky. Each function needs its own JAR containing compiled classes and dependencies. If your project has many APIs, this leads to multiple JARs with overlapping code, increasing storage, deployment complexity, and maintenance effort.

Another challenge is cold start overhead. Each Java Lambda function requires its own JVM initialization. Heavy frameworks like Spring Boot amplify this delay, and having many separate functions can result in multiple cold starts affecting application responsiveness, especially for low-latency APIs.

Additionally, managing dozens of Lambda functions increases operational complexity. Each function requires its own IAM roles, environment variables, monitoring, and logging configuration. While Lambda layers can help share code, managing a large number of functions remains cumbersome.

Alternative Approaches

  • Single JAR with Dispatcher Pattern: One Lambda function handles multiple APIs by routing requests internally based on input fields. This reduces JAR duplication, simplifies deployment, and keeps initialization consistent.
  • Hybrid Approach: Use multiple Lambdas only for APIs with very different scaling, latency, or resource requirements, while grouping related APIs into a single function with a shared JAR.

In summary, separate functions for each API provide isolation and independent scaling but can become bulky in Java projects. Grouping related APIs into one function with a dispatcher or using a hybrid approach is often more efficient and maintainable.

Handling Environment Variables in Java Lambda

Environment variables in AWS Lambda allow you to configure your function without hardcoding values in Java code. They can be set directly in the AWS Lambda console, via AWS CLI, or using CloudFormation. Common examples include database connection strings, API keys, or environment identifiers like ENV=dev or ENV=prod.

In Java, environment variables can be accessed at runtime using System.getenv(). For example: 


String dbUrl = System.getenv("DB_URL");
String apiKey = System.getenv("API_KEY");
String environment = System.getenv("ENV");

Best practices:

  • Do not hardcode sensitive information; use environment variables or AWS Secrets Manager.
  • Use different variables for different stages (dev, test, prod).
  • Leverage Lambda layers for shared configuration across multiple functions.
  • Handle missing variables gracefully, providing defaults or meaningful error messages.

For example, if a Lambda function needs to connect to a database, storing the connection string and credentials in environment variables allows the same function code to run across multiple environments simply by changing the environment variable values.

In summary, environment variables are the standard way to configure Java Lambda functions, manage secrets securely, and enable easy promotion across environments without changing code.
