The "Stop/Start" Recovery Method

📖 Complete Theory: Why Stop/Start Works

When an EC2 instance becomes unresponsive or fails its status checks, the "Stop/Start" method is one of the most powerful and effective recovery techniques. Unlike a simple reboot, which keeps the instance on the same underlying physical host, stopping and starting an instance typically migrates it to new hardware, resolving many host-level issues.

The Core Principle: Hardware Migration
When you stop an EBS-backed EC2 instance, AWS releases the physical resources (vCPU, memory) and network interfaces back to the pool. When you start it again, AWS allocates new underlying hardware for the instance. This often results in the instance being moved to a new, healthy physical host.

When to Use Stop/Start:
  • System Status Check Failures: StatusCheckFailed_System indicates infrastructure issues
  • Unresponsive Instances: Completely unresponsive or stuck in a "hung" state
  • Host-Level Issues: Problems at the hypervisor level rather than OS configuration

💡 Key Insight: Stop/Start migrates your instance to new hardware, while a reboot keeps it on the same host. Use Stop/Start for System Status Check failures, not for Instance Status Check failures.

Stop/Start Procedure

🛠️ Step-by-Step Stop/Start Procedure:

Step 1: Stop the Instance
# AWS CLI aws ec2 stop-instances --instance-ids i-1234567890abcdef0 # Boto3 ec2.stop_instances(InstanceIds=['i-1234567890abcdef0'])

Step 2: Wait for the Stop to Complete
The instance state will transition to stopping and then stopped. During this time, compute charges stop.

Step 3: Start the Instance
# AWS CLI aws ec2 start-instances --instance-ids i-1234567890abcdef0 # Boto3 ec2.start_instances(InstanceIds=['i-1234567890abcdef0'])

📝 Review Questions
Q1: What is the difference between a reboot and a Stop/Start operation?
A reboot restarts the operating system while keeping the instance on the same physical host. A Stop/Start operation stops the instance, releases its underlying resources, and then starts it again — typically on new hardware.
Q2: When should you use Stop/Start instead of a reboot?
Use Stop/Start when the instance is failing the System Status Check (StatusCheckFailed_System), indicating a problem with the underlying AWS infrastructure.
Q3: What happens to the public IP address when you stop and start an EC2 instance?
The public IPv4 address is released and a new one is assigned. If an Elastic IP is attached, it persists.
Q4: What data is lost when you stop and start an EC2 instance?
Data stored in RAM and on Instance Store volumes is lost. Data stored on EBS volumes persists.

14.3.1 Detaching Root Volume

📖 Complete Theory: Why You Must Stop First

The most important rule to remember is that you cannot detach the root volume while the instance is running. This is a critical safeguard to prevent data corruption and system crashes. The root volume is actively being used by the operating system; forcefully pulling it out would be like yanking a computer's hard drive while it's on.

To detach the root volume, the instance must be stopped.

🛠️ Step-by-Step: Detaching the Root Volume
# Step 1: Stop the instance aws ec2 stop-instances --instance-ids i-1234567890abcdef0 # Step 2: Detach the volume aws ec2 detach-volume --volume-id vol-1234567890abcdef0 # Boto3 ec2_client.detach_volume(VolumeId='vol-1234567890abcdef0')

⚠️ Critical Warning: The --force Flag
The detach-volume command has a --force option. This should only be used as an absolute last resort.

Why it's dangerous: A forced detach does not allow the operating system to flush any remaining data from its cache or file system metadata to the disk. This can lead to data loss or file system corruption.

When to use it: Only use it if the instance is completely unresponsive and you cannot unmount the volume normally.

🔧 Unmounting vs. Detaching:
  • Unmounting is an OS-level operation that flushes pending writes and makes the file system ready for removal
  • Detaching is an AWS API call that removes the volume from the instance
  • When an instance is stopped, all its volumes are automatically unmounted
📝 Review Questions
Q1: Why must you stop an instance before detaching its root volume?
The root volume is the instance's operating system disk. If an EBS volume is the root device, it cannot be detached while the instance is running. The instance must be stopped first to ensure data consistency and prevent system crashes.
Q2: What is the risk of using the --force flag when detaching a volume?
The --force option can lead to data loss or file system corruption because the instance doesn't have an opportunity to flush file system caches or metadata before the volume is removed. It should only be used as a last resort on a failed instance.

14.3.2 Attaching to a Rescue Instance

📖 Complete Theory: Why This Method Works

The rescue instance method works because EBS volumes are persistent and can be detached from one EC2 instance and attached to another. By attaching the problematic volume to a healthy instance, you can mount its file system, examine logs, edit configuration files, and resolve the issue — all without needing to connect to the broken instance itself.

# Step 1: Stop the problem instance aws ec2 stop-instances --instance-ids i-1234567890abcdef0 # Step 2: Detach the root volume aws ec2 detach-volume --volume-id vol-1234567890abcdef0 # Step 3: Attach to rescue instance aws ec2 attach-volume \ --volume-id vol-1234567890abcdef0 \ --instance-id i-rescue-instance-id \ --device /dev/sdf # Step 4: SSH into rescue instance and mount ssh -i your-key.pem ec2-user@<rescue-public-ip> sudo lsblk sudo mkdir /mnt/rescue sudo mount /dev/xvdf1 /mnt/rescue

🧰 Common Fixes:
Bad SSH config → Edit /mnt/rescue/etc/ssh/sshd_config
Bad fstab entry → Edit /mnt/rescue/etc/fstab
Lost root password → chroot /mnt/rescue; passwd root
SELinux issues → semodule -B inside chroot
Full root volume → xfs_growfs or resize2fs
GRUB corruption → grub-install /dev/xvdf

💡 Key Insight: The rescue instance method is the most versatile troubleshooting approach for unreachable EC2 instances. The rescue instance and the problem instance must be in the same Availability Zone.

14.3.3 Mounting and Fixing Issues (chroot)

📖 Complete Theory: The Power of chroot

When you use the rescue instance method, simply attaching and mounting the broken volume isn't enough. To fix OS-level problems — such as resetting passwords, repairing SSH configurations, reinstalling bootloaders, or fixing system-wide permissions — you need to operate inside the broken instance's file system as if you were that instance. This is where chroot comes in.

💡 Analogy: Think of the rescue instance as a "repair workshop." The broken instance's hard drive is a patient brought into the workshop. chroot is the tool that lets you, as the doctor, step inside the patient's body to perform surgery, rather than treating it from outside.

🛠️ Step-by-Step: Mounting and Using chroot
# Step 1: Identify the device sudo lsblk # Step 2: Mount the volume sudo mkdir /mnt/recovery sudo mount /dev/xvdf1 /mnt/recovery # Step 3: Mount special filesystems sudo mount -o bind /dev /mnt/recovery/dev sudo mount -o bind /proc /mnt/recovery/proc sudo mount -o bind /sys /mnt/recovery/sys # Step 4: chroot into the broken system sudo chroot /mnt/recovery

🧰 Common Fixes Using chroot:
  • Reset Root Password: passwd root (or passwd ubuntu for Ubuntu)
  • Fix SSH Config: Edit /etc/ssh/sshd_config
  • Fix fstab: Edit /etc/fstab
  • Reinstall GRUB: grub-install /dev/xvdf
  • Fix Permissions: chmod 700 /home/ec2-user/.ssh
  • File System Check: fsck

⚠️ Important: Always exit chroot and properly unmount (umount) before detaching the volume to prevent file system damage.
📝 Review Questions
Q1: What is the purpose of the chroot command when using a rescue instance?
chroot changes the root directory for the current process to the mounted volume. This allows you to run system commands as if you were operating directly on the problematic instance's file system, simplifying configuration changes and password resets.
Q2: What special filesystems should you mount before chroot?
Mount /dev, /proc, and /sys using mount -o bind to ensure the chroot environment behaves like a full operating system.

14.3.4 Re-attaching and Rebooting

📖 Complete Theory: The Final Step

The final stage of the rescue instance recovery process is reattaching the fixed volume to the original instance and verifying that it boots successfully. This step is critical because even if you fixed the root cause, a small mistake in reattachment can leave the instance in the same broken state.

# Step 1: Exit chroot and unmount exit sudo umount /mnt/recovery/dev sudo umount /mnt/recovery/proc sudo umount /mnt/recovery/sys sudo umount /mnt/recovery # Step 2: Detach from rescue instance aws ec2 detach-volume --volume-id vol-1234567890abcdef0 # Step 3: Reattach to original instance as root aws ec2 attach-volume \ --volume-id vol-1234567890abcdef0 \ --instance-id i-1234567890abcdef0 \ --device /dev/xvda # Step 4: Start the original instance aws ec2 start-instances --instance-ids i-1234567890abcdef0 # Step 5: Monitor status checks aws ec2 describe-instance-status --instance-ids i-1234567890abcdef0

⚠️ Important: If any umount command fails with target is busy, it means some process is still using the mount point. Close any terminal sessions inside the mount directory, or use sudo lsof /mnt/recovery to find and kill the offending process.
📝 Review Questions
Q1: What is the correct order for unmounting file systems after using a chroot environment?
Unmount in reverse order. First unmount the special file systems (/dev, /proc, /sys), then unmount the main volume (/mnt/recovery).
Q2: What can cause the umount command to fail with "target is busy"?
This occurs when there is still a process using the mount point. Common causes: you are still inside the mount directory, another terminal session is using /mnt/recovery, or you forgot to exit the chroot environment.
Q3: What device name should you use when reattaching the volume to the original instance?
Reattach with the correct device name that the original instance expects for its root volume. Usually this is /dev/xvda for Nitro instances or /dev/sda1 for older (Xen) instances.

Key Takeaways

  • Stop/Start migrates your instance to new hardware — use it for System Status Check failures.

  • Reboot keeps the instance on the same physical host — use it for transient OS issues.

  • You cannot detach the root volume while the instance is running — it must be stopped first.

  • The --force flag is a last resort that can cause data loss or file system corruption.

  • The rescue instance method is the most versatile troubleshooting approach — the rescue instance and problem instance must be in the same Availability Zone.

  • chroot allows you to operate inside the broken instance's file system — mount /dev, /proc, and /sys before chroot.

  • Unmount in reverse order — special filesystems first, then the main volume.

  • Public IP changes on stop/start unless using an Elastic IP.

  • Instance Store data is lost on stop — only use Stop/Start on EBS-backed instances.

  • Verify status checks after recovery — 2/2 checks passed means the instance is healthy.
