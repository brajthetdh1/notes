Q1: What is the difference between EBS and Instance Store?

📝 Answer:
EBS is a persistent, network-attached block storage that exists independently of the instance, while Instance Store is ephemeral storage physically attached to the host computer.
🔍 Detailed Explanation:
FeatureInstance StoreEBS (Elastic Block Store)
Storage TypeEphemeral (temporary)Persistent block storage
LocationPhysically attached to hostNetwork-attached storage
Data PersistenceLost on stop/terminationPersists independently
PerformanceVery high, low latencyLower than instance store
AttachmentMust be specified at launchCan attach/detach anytime
CostIncluded with instanceCharged separately

💡 Best Use Cases:
  • Instance Store: Temporary data, caching, high I/O tasks where persistence is not required
  • EBS: Boot volumes, databases, applications needing reliable, persistent storage

Q4: What happens to EBS volumes when you terminate an EC2 instance?

📝 Answer:
The behavior depends on the volume type and the DeleteOnTermination flag:
  • Root EBS volumes: Deleted by default (DeleteOnTermination = true)
  • Additional EBS data volumes: Preserved by default (DeleteOnTermination = false)
🔍 Detailed Explanation:

Root volumes are deleted by default to prevent accumulating unused volumes that incur charges. You can change this behavior by explicitly setting DeleteOnTermination = false.

Data volumes (non-root) are preserved by default, aligning with EBS's purpose as persistent storage.

⚠️ Important: If you want to preserve root volumes after instance termination, you must explicitly set DeleteOnTermination = false at launch or modify it on a running/stopped instance.

Q5: What is an EBS Snapshot and how do you use it for disaster recovery?

📝 Answer:
An EBS Snapshot is a point-in-time backup of an EBS volume. For disaster recovery, you use snapshots to restore volumes in the same or different Regions after a failure.
🔍 Detailed Explanation:

Snapshots are incremental backups stored in Amazon S3, capturing the entire state of the volume.

To recover:
  1. Create a snapshot of your critical volumes (boot + data)
  2. After a disaster, create new volumes from the snapshots
  3. Attach the restored volumes to a new EC2 instance
  4. For cross-Region DR, copy snapshots to another Region

💡 Key Insight: Snapshots are incremental — only changed blocks are stored after the first snapshot, making them cost-effective for frequent backups.

Q6: Can you take a snapshot of a volume while it is attached to a running instance?

📝 Answer:
Yes, you can take a snapshot of a volume while it is attached to a running instance. However, it may not be application-consistent if the application has data in memory that hasn't been written to disk.
🔍 Detailed Explanation:

Snapshot creation from a running instance captures data already written to the volume. For application consistency:
  • Unmount the volume to ensure all file system caches are flushed
  • Stop the instance before creating a snapshot of the root volume
  • Use a clustered file system with snapshot support for databases
  • Use SnapByCgroup.sh script to freeze file systems before taking snapshots

⚠️ Important: Snapshots of in-use volumes only capture data that has already been written to the volume. Any data in application or OS caches may be excluded.

Q7: What is the difference between EBS and EFS?

📝 Answer:
EBS is a block storage volume attached to a single EC2 instance, while EFS is a shared file system that can be mounted by thousands of instances simultaneously.
🔍 Detailed Comparison:
FeatureEBSEFS
Storage TypeBlock storageFile storage (NFS)
AccessSingle EC2 instanceThousands of instances concurrently
ScopeSingle Availability ZoneRegional (multi-AZ)
LatencyLowest, consistentSmall latency overhead
Use CasesBoot volumes, databasesShared file access, content management

💡 Key Insight: EBS is for single-instance, block-level storage, while EFS is for shared, file-level access across multiple instances.

Q8: What is an EFS Lifecycle Policy?

📝 Answer:
An EFS Lifecycle Policy is a set of rules that automates the movement of files between EFS storage classes (Standard, Infrequent Access, Archive) based on access patterns.
🔍 Detailed Explanation:

Each lifecycle policy object has a single transition. The three transitions are:

  • TransitionToIA: Moves files to IA after a period of no access (e.g., AFTER_30_DAYS)
  • TransitionToArchive: Moves files to Archive after a longer period
  • TransitionToPrimaryStorageClass: Moves files back to Standard when accessed in IA/Archive (Intelligent-Tiering)

💡 Important: Metadata operations like ls do not count as file access events. Only actual data reads/writes reset the timer.

Q9: How can you increase the size of an EBS volume without downtime?

📝 Answer:
Use EBS Elastic Volumes to increase the volume size online. After modifying the volume, you must extend the partition (if used) and filesystem from within the instance.
🔍 Detailed Explanation:

Step 1: Modify the volume (no downtime)
aws ec2 modify-volume --volume-id vol-xxx --size 200

Step 2: Extend the partition (if applicable)
sudo growpart /dev/nvme0n1 1

Step 3: Extend the filesystem
# For XFS (Amazon Linux) sudo xfs_growfs / # For ext4 (Ubuntu) sudo resize2fs /dev/nvme0n1p1

💡 Important Notes:
  • You can start filesystem expansion as soon as the volume enters the optimizing state
  • AWS allows up to four modifications per volume in a rolling 24-hour period

Q10: What is the maximum IOPS for an io2 EBS volume?

📝 Answer:
The maximum IOPS for an io2 EBS volume is 256,000 (io2 Block Express). The standard io2 volume supports up to 64,000 IOPS.
🔍 Detailed Comparison:

⚠️ Note: To achieve the maximum IOPS, the volume must be attached to a Nitro System EC2 instance. io2 is priced identically to io1 but offers significantly higher performance.
