📚 Relational Database Service

AWS Relational Database Service (RDS)

AWS Relational Database Service (RDS) is a fully managed service that makes it easy to set up, operate, and scale a relational database in the cloud. It handles common database administration tasks such as provisioning, patching, backup, recovery, and scaling, allowing developers to focus on building applications.

Supported Database Engines

  • Amazon Aurora: High-performance, MySQL- and PostgreSQL-compatible.
  • MySQL: Popular open-source relational database.
  • PostgreSQL: Advanced open-source relational database.
  • MariaDB: Open-source fork of MySQL.
  • Oracle: Enterprise-grade commercial database.
  • Microsoft SQL Server: Widely used commercial RDBMS.

Key Features

  • Automated backups: Daily backups with point-in-time recovery.
  • Multi-AZ deployment: High availability and failover support.
  • Read replicas: Scale read-heavy workloads.
  • Automatic software patching: Keep your database secure and up-to-date.
  • Monitoring & metrics: Integrated with Amazon CloudWatch.
  • Encryption: At-rest and in-transit encryption for enhanced security.
  • Scalability: Easily scale compute and storage resources.

Advantages of AWS RDS

  • Fully managed: No need for manual database administration.
  • Reliable: Automated backups, snapshots, and Multi-AZ deployments.
  • Secure: Supports VPC, IAM, KMS encryption, and network isolation.
  • Cost-effective: Pay only for what you use, with reserved instances for long-term savings.
  • Highly available: Failover across Availability Zones ensures minimal downtime.
  • Compatible: Supports popular relational database engines and tools.

Use Cases

  • Web and mobile applications requiring a relational database backend.
  • E-commerce applications with transactional workloads.
  • Analytics applications using read replicas for reporting.
  • Enterprise applications needing high availability and disaster recovery.
  • Migration of on-premises databases to the cloud.

Pricing Model

AWS RDS pricing depends on:

  • Database engine and edition (e.g., MySQL, PostgreSQL, Aurora, Oracle).
  • Instance type (CPU, RAM) and storage size.
  • Deployment option (Single-AZ or Multi-AZ).
  • Provisioned IOPS for high-performance workloads.
  • Data transfer costs (outside AWS region).

Limitations of AWS RDS

While AWS RDS is a powerful managed relational database service, it does have certain limitations that users should be aware of before designing applications.

1. Limited Control Over Database Engine

Unlike self-managed databases, RDS restricts access to certain OS-level configurations and advanced database parameters. You cannot install custom extensions or software that require administrative privileges on the host machine.

2. No SSH / OS-Level Access

You cannot log in to the underlying server via SSH. All access is through the database endpoint using standard protocols (MySQL, PostgreSQL, SQL Server, etc.). This means:

  • You cannot install custom software or database extensions.
  • You cannot directly inspect OS-level logs or metrics beyond what RDS provides.
  • All maintenance tasks (patching, backups, security hardening) are fully managed by AWS.

2. Storage Scaling Constraints

  • Maximum storage limits vary by engine (e.g., MySQL, PostgreSQL, Oracle, SQL Server).
  • Increasing storage beyond certain thresholds might require downtime or instance modification.

3. Limited Customization of Instance Types

Users can choose from predefined instance types (CPU, RAM), but fine-grained custom hardware configurations are not possible. This can be restrictive for specialized workloads requiring specific resources.

4. Multi-AZ Limitations

  • Failover between Availability Zones can cause a short downtime (~1–2 minutes).
  • Read replicas do not automatically failover, and manual promotion is required.

5. Version and Engine Restrictions

AWS RDS supports only specific versions of each database engine. Upgrading to a newer version may require downtime, and certain older versions may eventually be deprecated.

6. Backup and Restore Limitations

  • Point-in-time recovery is limited to the backup retention period (maximum 35 days).
  • Cross-region restore or replication adds complexity and may incur additional costs.

7. Cost Considerations

While RDS is convenient, long-term running instances, Multi-AZ deployments, provisioned IOPS, and snapshots can significantly increase costs compared to self-managed databases on EC2.

8. Scaling Limitations

  • Horizontal scaling is limited; read replicas can scale read-heavy workloads, but write scaling requires sharding at the application level.
  • Auto-scaling options are more limited than some NoSQL or distributed database services.

AWS RDS Read Replicas & Read Scalability

Read replicas allow you to create one or more read-only copies of your primary RDS database instance. They are primarily used to:

  • Offload read traffic from the primary database to improve overall performance.
  • Increase read throughput and handle read-heavy workloads.
  • Enable disaster recovery and reporting without impacting the primary instance.

How Read Replicas Work

Read replicas use asynchronous replication from the primary database. Changes made to the primary instance are replicated to replicas, typically with a small lag. Applications can then direct read queries to replicas while the primary handles writes.

Read Scalability with Replicas

  • You can create up to 15 read replicas for a single RDS primary instance (varies by database engine).
  • Read traffic can be distributed among replicas to reduce load on the primary.
  • Replicas can be promoted to become standalone primary instances for failover scenarios.
  • Supports cross-region replicas for global read scalability and disaster recovery.
  • Ideal for read-heavy workloads like reporting, analytics, and web applications.

Conditions to Apply Read Replicas

Use read replicas under these conditions:

  • High read traffic on the primary instance causing CPU or memory bottlenecks.
  • Applications require horizontal read scalability.
  • Need to offload reporting or analytics queries without affecting primary writes.
  • Disaster recovery planning or cross-region data replication is required.
  • Replication lag is within acceptable limits for your application (asynchronous replication).

Diagram: RDS Read Replica Architecture

Primary DB handles writes; up to 15 read replicas handle read traffic.

Key Considerations

  • Replication is asynchronous, so replicas may lag behind the primary.
  • Read replicas do not reduce write load; they only improve read scalability.
  • Monitor replication lag using CloudWatch to ensure read consistency.
  • Backups and maintenance operations on primary affect replicas.
  • Cross-region replicas may incur additional latency and cost.

AWS RDS Read Replica Cost

While read replicas improve read scalability and reliability, they also incur additional costs. Understanding pricing is important for budgeting and architecture planning.

Cost Components

  • Compute (Instance Hours): Each read replica is billed like a standard RDS instance based on its instance type (vCPU, memory) and region.
  • Storage: You are charged for storage used by each replica. Storage costs are identical to the primary instance.
  • IO Requests: Read/write requests to the replica may incur I/O costs depending on the storage type (e.g., General Purpose SSD, Provisioned IOPS).
  • Data Transfer: Cross-region replication incurs data transfer charges. Data transferred within the same region is usually free.
  • Backups & Snapshots: Backups are taken from the primary instance. Snapshots of replicas are charged separately if created.

Cost Considerations

  • Each read replica effectively doubles (or more) your RDS compute and storage costs.
  • Cross-region replicas are more expensive due to network transfer fees.
  • Scaling up read replicas to handle traffic spikes increases costs proportionally.
  • Deleting unused read replicas can significantly reduce ongoing costs.

Example Cost Scenario

Suppose you have a primary RDS db.m6g.large instance with 100GB General Purpose SSD storage in the US East (N. Virginia) region:

  • Primary instance: $0.077/hr → ~$55/month
  • 100GB storage: ~$10/month
  • 1 read replica of the same type: additional $55 (compute) + $10 (storage) = ~$65/month
  • Cross-region replica may add $0.02/GB for data transfer.

Tips to Optimize Cost

  • Only deploy read replicas if read traffic justifies the cost.
  • Consider smaller instance types for replicas if traffic is moderate.
  • Use cross-region replicas only for disaster recovery, not routine read scaling.
  • Monitor usage with CloudWatch to identify underutilized replicas.
  • Delete unnecessary replicas promptly to avoid idle charges.

Amazon ElastiCache Solution Architecture

Amazon ElastiCache provides a highly available, low-latency, in-memory caching layer that sits between your application and backend databases. It improves performance by reducing database load and accelerating data retrieval for frequently accessed data.

Core Components

  • Client/Application: Web or mobile app accessing data via Redis or Memcached endpoints.
  • ElastiCache Nodes: In-memory nodes for storing cache data.
  • Primary Node & Replicas: Redis supports a primary node for writes and multiple read replicas for scaling reads.
  • Shards (Redis Cluster Mode): Partition data across multiple shards to increase memory capacity and throughput.
  • Multi-AZ Deployment: Provides automatic failover in case of node or Availability Zone failure.
  • VPC & Security Groups: Network isolation and access control.
  • Monitoring & Metrics: CloudWatch integration for latency, memory usage, cache hits/misses, and CPU utilization.

Solution Flow

  1. Application queries for data → first checks ElastiCache.
  2. If cache hit → data returned instantly from memory (sub-millisecond latency).
  3. If cache miss → fetch data from backend database (e.g., RDS, Aurora), then populate the cache for future requests.
  4. Read-heavy applications can utilize Redis read replicas to distribute load and improve performance.
  5. In cluster mode, data is sharded for horizontal scaling; adding more shards increases capacity and throughput.
  6. Automatic failover ensures continuous availability if a primary node fails in Multi-AZ deployments.

High Availability & Disaster Recovery

  • Redis supports Multi-AZ with automatic failover to replica nodes in case of primary failure.
  • Memcached nodes are stateless; clients handle node failures and replacement.
  • Snapshots can be used for backup and restore operations.

Performance & Scaling

  • Sub-millisecond latency for in-memory data access.
  • Horizontal scaling via sharding or adding/removing nodes dynamically.
  • Read replicas improve read throughput without impacting write performance.

Security

  • VPC for network isolation.
  • IAM policies for access control.
  • Encryption in transit and at rest (Redis).
  • Security groups control inbound/outbound traffic.

Amazon ElastiCache

Amazon ElastiCache is a fully managed, in-memory data store and cache service. It supports Redis and Memcached, enabling high-performance, low-latency data access for applications. ElastiCache is widely used to improve application performance by offloading read-heavy workloads from databases.

Key Features

  • In-Memory Caching: Stores data in memory for sub-millisecond latency.
  • Fully Managed: AWS handles setup, patching, monitoring, scaling, and backups.
  • Support for Redis & Memcached: Offers flexibility for different caching requirements.
  • High Availability: Multi-AZ with automatic failover for Redis.
  • Scalability: Supports cluster mode to scale horizontally for Redis and sharding for Memcached.
  • Monitoring: Integration with Amazon CloudWatch for metrics and alarms.

Use Cases

  • Database Caching: Reduce load on RDS or DynamoDB for read-heavy workloads.
  • Session Management: Store session state for web applications for fast retrieval.
  • Leaderboards & Gaming: Real-time ranking updates and fast queries.
  • Message Queues: Implement pub/sub or simple queue systems using Redis.
  • Real-Time Analytics: Fast aggregation and retrieval of frequently accessed data.

High Availability & Replication

  • Redis supports replication with a primary node and multiple read replicas.
  • Automatic failover ensures minimal downtime in Multi-AZ deployments.
  • Memcached supports node replacement but does not provide native replication; client handles failover.

Scalability

  • Vertical Scaling: Increase node type to get more memory or CPU.
  • Horizontal Scaling: Cluster mode for Redis allows adding shards to distribute data.
  • Memcached can scale by adding/removing nodes dynamically without downtime.

Security

  • Supports VPC for network isolation.
  • Integration with AWS IAM for access control.
  • Supports encryption at rest and in transit.

Amazon ElastiCache Strategies

Amazon ElastiCache can be used with multiple caching strategies depending on your application requirements. Choosing the right caching strategy is crucial for achieving optimal performance and cost efficiency.

1. Cache-aside (Lazy Loading)

In this approach, the application is responsible for reading and writing from the cache:

  • On a cache miss, fetch data from the database, store it in the cache, then return to the application.
  • On a cache hit, return data directly from the cache.
  • Pros: Flexible, only caches frequently used data, reduces memory usage.
  • Cons: Application complexity increases, cache consistency must be managed.

2. Read-through

The cache sits transparently in front of the database. When the application requests data:

  • If data exists in cache, it is returned.
  • If not, the cache loads the data from the database and returns it automatically.
  • Pros: Simplifies application code, automatic loading.
  • Cons: Slightly higher latency on cache misses, memory may grow quickly.

3. Write-through

Every write operation goes to both the cache and the database simultaneously:

  • Ensures cache is always up-to-date.
  • Pros: Simplifies read operations, cache consistency guaranteed.
  • Cons: Writes are slower because they update both cache and database.

4. Write-behind / Write-back

Writes go only to the cache initially, and the cache asynchronously updates the database:

  • Reduces database write latency.
  • Pros: High write throughput, database load reduced.
  • Cons: Risk of data loss if cache fails before write-back, more complex failure handling.

5. Eviction Policies

To manage memory efficiently, ElastiCache supports multiple eviction policies:

  • LRU (Least Recently Used): Evict least recently accessed items first.
  • LFU (Least Frequently Used): Evict items accessed least frequently.
  • No eviction / AllKeys-LRU / Random: Depending on Redis or Memcached configuration.

6. Sharding / Partitioning Strategy

For large datasets exceeding a single node's memory:

  • Redis Cluster mode partitions data across multiple shards.
  • Each shard can have a primary node and multiple replicas for read scaling.
  • Ensures horizontal scalability and fault tolerance.

7. Read Replicas for Scaling

Read-heavy applications can leverage Redis read replicas:

  • Primary node handles writes, replicas handle read requests.
  • Reduces load on the primary node and improves read throughput.
  • Automatic failover ensures availability if primary fails.

8. TTL (Time-to-Live) Strategy

Each cached item can have a TTL to automatically expire after a certain period:

  • Prevents stale data accumulation.
  • Ensures cache refreshes periodically from the backend.
  • TTL values can be uniform or variable based on data criticality.

9. Monitoring & Scaling Strategy

  • Monitor cache metrics like memory usage, CPU utilization, cache hits/misses.
  • Scale horizontally by adding shards or replicas when memory utilization is high.
  • Scale vertically by moving to larger node types if needed.

AWS RDS Proxy

RDS Proxy is a fully managed, highly available database proxy for Amazon RDS and Amazon Aurora. It improves application scalability, resiliency, and security by pooling and sharing database connections. RDS Proxy is particularly useful for serverless applications, microservices, and applications with unpredictable workloads.

Key Features

  • Connection Pooling: Reduces the overhead of opening and closing database connections, allowing thousands of concurrent client connections with a smaller number of database connections.
  • Automatic Failover: Works with Multi-AZ RDS or Aurora instances, automatically routing connections to a healthy instance during failover.
  • IAM Authentication: Supports AWS Identity and Access Management (IAM) for secure, passwordless database access.
  • Security Integration: Works with Amazon VPC, AWS Secrets Manager for credentials, and supports TLS encryption.
  • Serverless-Friendly: Ideal for Lambda functions or other serverless architectures where connections open and close frequently.

How RDS Proxy Works

  1. Clients connect to the RDS Proxy endpoint instead of directly connecting to the database.
  2. RDS Proxy maintains a pool of established database connections.
  3. When a client request arrives, RDS Proxy reuses an existing connection from the pool.
  4. During database failover, RDS Proxy automatically reestablishes connections to the new primary, minimizing disruption.

Benefits

  • Scalability: Supports thousands of concurrent application connections without overloading the database.
  • High Availability: Automatically handles database failover and connection retries.
  • Improved Application Performance: Connection pooling reduces latency caused by frequent connection creation.
  • Enhanced Security: IAM authentication, TLS encryption, and Secrets Manager integration.
  • Cost Efficiency: Reduces the need for over-provisioning database instances just to handle connection spikes.

Use Cases

  • Serverless applications (e.g., AWS Lambda) with high connection churn.
  • Microservices architectures where multiple services access the same database.
  • Applications that require seamless Multi-AZ failover support.
  • High-throughput applications needing efficient connection management.

AWS RDS Multi-AZ Deployment & Disaster Recovery

Amazon RDS Multi-AZ (Availability Zone) deployments provide high availability and automatic failover support for your relational databases. By replicating the primary database to a standby instance in a different Availability Zone, RDS ensures your database remains resilient against infrastructure failures.

How Multi-AZ Works

  • RDS automatically provisions and maintains a **synchronous standby replica** in a different AZ from the primary instance.
  • Writes to the primary database are **synchronously replicated** to the standby to ensure durability.
  • In case of failure (e.g., hardware, network, or AZ outage), RDS performs an **automatic failover** to the standby instance, minimizing downtime.
  • The **endpoint of the RDS instance remains the same**, so applications do not need configuration changes.

Disaster Recovery Benefits

  • **Automatic Failover:** Minimizes downtime without manual intervention.
  • **Synchronous Replication:** Ensures no data loss between primary and standby.
  • **High Availability:** Protects against infrastructure failures, AZ outages, and maintenance events.
  • **Seamless Endpoint Switching:** Your application reconnects automatically to the standby.

Architecture Diagram

Primary DB in AZ1 is synchronously replicated to standby in AZ2. Failover happens automatically.

Key Features & Considerations

  • Supported for most RDS engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, and Aurora.
  • **Read traffic** cannot be served from the standby in standard RDS; use Read Replicas for scaling reads.
  • Failover typically completes in **60–120 seconds**, depending on engine and workload.
  • Backups are taken from the standby instance, reducing performance impact on the primary.
  • Multi-AZ increases **costs** because standby instances incur full instance pricing.

When to Use Multi-AZ

  • Applications requiring **high availability** and minimal downtime.
  • Databases where **data durability** is critical.
  • For workloads sensitive to **AZ-level outages**.
  • When combined with Read Replicas, you can achieve both **high availability** and **read scalability**.

Cost Considerations

  • Multi-AZ doubles the compute and storage costs, as a full standby instance is maintained.
  • IO and backup costs remain similar to single-AZ deployments.
  • It’s recommended for **production-critical databases**; for dev/test environments, single-AZ may be sufficient.

RDS Standby Replica vs Read Replica

Amazon RDS provides two key mechanisms for enhancing **availability** and **scalability**: Standby Replicas (Multi-AZ) and Read Replicas. Understanding their differences is essential for designing high-performance, resilient database architectures.

Standby Replica (Multi-AZ)

  • Purpose: High availability & disaster recovery.
  • Replication: Synchronous replication to a standby instance in a different Availability Zone.
  • Read Traffic: Cannot serve read traffic; only the primary instance handles requests.
  • Failover: Automatic failover in case of primary instance or AZ failure; endpoint remains the same.
  • Cost: Full cost of an additional instance; doubles compute and storage costs.
  • Use Case: Critical production workloads requiring minimal downtime and zero data loss.

Read Replica

  • Purpose: Read scalability & offloading queries.
  • Replication: Asynchronous replication from the primary database.
  • Read Traffic: Can serve read queries, reducing load on the primary.
  • Failover: Does not provide automatic failover. Can be promoted to standalone DB manually.
  • Cost: Each replica incurs full instance cost but allows better read throughput.
  • Use Case: Reporting, analytics, or read-heavy applications where read scaling is needed.

Comparison Table

Feature Standby Replica (Multi-AZ) Read Replica
Purpose High availability & disaster recovery Read scalability & offloading queries
Replication Type Synchronous Asynchronous
Read Traffic No Yes
Automatic Failover Yes No (manual promotion possible)
Cost High (full standby instance) Medium (each replica is a full instance)
Use Case Mission-critical production DB Read-heavy workloads, analytics, reporting

Summary

Standby Replicas focus on **availability and durability**, while Read Replicas focus on **scalability and read performance**. For a production-grade RDS architecture, you can combine both: use Multi-AZ for high availability and deploy multiple Read Replicas to scale reads across regions or AZs.

Amazon Aurora – High-Performance Relational Database

Amazon Aurora is a fully managed relational database engine provided by AWS, compatible with both MySQL and PostgreSQL. It is designed for **high performance, scalability, and availability**, combining the speed and reliability of commercial databases with the simplicity and cost-effectiveness of open-source databases.

Key Features

  • High Performance: Up to 5x faster than standard MySQL and 3x faster than standard PostgreSQL.
  • Fully Managed: Automated backups, patching, monitoring, and scaling.
  • High Availability: Multi-AZ deployments with automatic failover to standby replicas.
  • Read Scalability: Up to 15 read replicas with low-latency reads for read-heavy workloads.
  • Storage Auto-Scaling: Storage automatically scales from 10 GB up to 128 TB.
  • Security: Encryption at rest and in transit, IAM integration, and VPC support.

Aurora Architecture

Amazon Aurora separates compute and storage layers. The storage layer is distributed across multiple Availability Zones and automatically replicates six copies of your data. The compute layer can scale independently to handle read/write workloads.

Deployment Options

  • Single-AZ Deployment: Suitable for dev/test workloads.
  • Multi-AZ Deployment: Provides high availability with automatic failover.
  • Cross-Region Read Replicas: For disaster recovery and global read scaling.

Read Replicas & Scalability

  • Up to 15 low-latency read replicas.
  • Replicas can be promoted to standalone instances if needed.
  • Supports both MySQL and PostgreSQL compatibility.

High Availability & Disaster Recovery

  • Automatic failover in Multi-AZ setup within 30 seconds.
  • Continuous backups to Amazon S3.
  • Point-in-time recovery for data protection.

Cost Considerations

  • Compute is billed per instance-hour.
  • Storage is billed per GB-month consumed.
  • Additional cost for I/O operations, backups, and read replicas.
  • Multi-AZ and read replicas increase overall costs but enhance reliability and scalability.

When to Use Amazon Aurora

  • Applications requiring high throughput and low latency.
  • Production workloads needing automated failover and disaster recovery.
  • Applications with unpredictable or growing storage needs.
  • Read-heavy applications that need multiple read replicas.

Amazon Aurora is ideal for businesses that want **enterprise-level database performance** without the operational overhead of managing hardware or complex configurations.

Amazon Aurora – High Availability & Read Scaling

Amazon Aurora is designed for enterprise-grade availability and scalability. It separates the compute and storage layers, allowing high performance and fault tolerance. High availability ensures that applications remain operational even in the event of infrastructure failure, while read scaling enables multiple concurrent read queries without affecting the primary writer instance.

High Availability (Multi-AZ)

  • Amazon Aurora automatically replicates your data across six copies in three Availability Zones (AZs).
  • In a Multi-AZ setup, Aurora maintains a primary writer instance and a standby instance in another AZ.
  • If the primary fails, Aurora automatically performs a failover to the standby instance within ~30 seconds, ensuring minimal downtime.
  • Storage is continuously backed up to Amazon S3, providing point-in-time recovery and disaster protection.

Read Scaling (Read Replicas)

  • Amazon Aurora allows up to 15 low-latency read replicas for MySQL-compatible and PostgreSQL-compatible editions.
  • Read replicas share the same distributed storage as the primary instance, providing near real-time replication.
  • Applications can offload read-heavy workloads to these replicas without affecting write performance on the primary instance.
  • Replicas can be promoted to a primary instance in case of failure or planned maintenance.
  • Supports cross-region read replicas for global applications and disaster recovery.

Key Benefits

  • Minimal Downtime: Automatic failover ensures your database remains available.
  • High Throughput: Offload read operations to replicas, improving application responsiveness.
  • Scalable: Add replicas dynamically based on read demand without affecting primary performance.
  • Disaster Recovery: Multi-AZ and cross-region replication protect against infrastructure failures.

Use Cases

  • Applications with high availability requirements, e.g., e-commerce, finance.
  • Read-intensive workloads that require scaling horizontally.
  • Global applications using cross-region read replicas for low-latency access.
  • Critical production databases needing automatic failover and minimal downtime.

AWS RDS Storage Auto Scaling

Amazon RDS Storage Auto Scaling automatically adjusts your database storage size as your application requirements grow. It helps prevent downtime caused by running out of storage and ensures that your database can handle increasing workloads without manual intervention.

How It Works

  • You define a maximum storage limit when enabling auto scaling for your RDS instance.
  • RDS monitors available storage and automatically increases it when free space falls below a certain threshold.
  • Storage increases occur without downtime, allowing applications to continue operating normally.

Supported Storage Types

Storage auto scaling is available for the following RDS storage types:

  • General Purpose SSD (gp2/gp3)
  • Provisioned IOPS SSD (io1/io2)
  • Magnetic storage (not commonly used; limited support)

Benefits

  • Reduces the risk of database downtime due to storage exhaustion.
  • Eliminates the need for manual storage adjustments.
  • Supports growing workloads seamlessly, especially for unpredictable usage patterns.
  • Integrates with Amazon CloudWatch to provide metrics and alerts on storage usage.

Considerations / Limitations

  • Auto scaling only increases storage; it does not decrease it.
  • Maximum storage limit must be defined during instance creation or modification; RDS will not exceed this limit.
  • There may be a slight performance impact during storage expansion, but RDS handles it transparently.
  • Auto scaling is not a substitute for proper monitoring — it should complement CloudWatch alerts and database performance tuning.

When to Modify Storage Settings

Although storage auto scaling handles increases automatically, there are situations where you may need to manually modify your RDS storage settings:

  • Projected Growth: If your application usage is expected to grow rapidly, preemptively increase storage limits to avoid hitting the maximum threshold.
  • Performance Requirements: Certain workloads benefit from higher IOPS or larger storage allocations; modify storage to ensure optimal performance.
  • Cost Optimization: You might want to increase storage gradually to balance cost versus performance.
  • Maintenance Windows: Major modifications (like changing storage type) require planning during maintenance windows to minimize disruption.
  • Monitoring Alerts: If CloudWatch indicates frequent near-capacity storage usage, consider adjusting limits before hitting the maximum.

Practical Conditions to Trigger Auto Scaling

Storage auto scaling can be applied automatically when certain usage thresholds are met. Examples of common triggers:

  • Low Free Storage Threshold: When free storage falls below a certain percentage, e.g., 10% of allocated storage.
  • Persistent Low Storage: When storage remains below a threshold for a continuous duration, e.g., free storage < 10% for 5 minutes.
  • Approaching Max IOPS or Throughput: If storage usage affects performance metrics, scaling may be applied to support workload growth.
  • Monitoring Alerts: Based on CloudWatch alarms for low available storage, high read/write latency, or other resource constraints.
  • Growth Trends: Auto scaling can proactively add storage if historical metrics show consistent growth over days or weeks.

How to Enable

  1. Go to the RDS console and select your database instance.
  2. Click Modify.
  3. Under Storage, enable Storage Auto Scaling.
  4. Set a maximum storage threshold (e.g., 2 TB).
  5. Apply the changes immediately or during the next maintenance window.
