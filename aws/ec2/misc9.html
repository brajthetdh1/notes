Q1: What is the Shared Responsibility Model in AWS?

📝 Answer:
The AWS Shared Responsibility Model is a security framework that defines the division of security responsibilities between AWS and its customers. AWS secures the infrastructure that runs all services in the AWS Cloud (Security of the Cloud), while you are responsible for securing your use of those services (Security in the Cloud).
🔍 Detailed Explanation:
AWS SHARED RESPONSIBILITY MODEL ┌─────────────────────────────────────────────────────────────────────────────────────┐ │ AWS SHARED RESPONSIBILITY MODEL │ ├─────────────────────────────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────────────────────────────────────┐│ │ │ CUSTOMER RESPONSIBILITY – Security "IN" the Cloud ││ │ │ ┌─────────────────────────────────────────────────────────────────────────┐ ││ │ │ │ • Customer Data │ ││ │ │ │ • Platform, Applications, Identity & Access Management (IAM) │ ││ │ │ │ • Operating System (patching, updates) │ ││ │ │ │ • Network & Firewall Configuration │ ││ │ │ │ • Client-side Data Encryption & Data Integrity │ ││ │ │ │ • Server-side Encryption (File System and/or Data) │ ││ │ │ │ • Networking Traffic Protection │ ││ │ │ └─────────────────────────────────────────────────────────────────────────┘ ││ │ └─────────────────────────────────────────────────────────────────────────────────┘│ │ │ │ ┌─────────────────────────────────────────────────────────────────────────────────┐│ │ │ AWS RESPONSIBILITY – Security "OF" the Cloud ││ │ │ ┌─────────────────────────────────────────────────────────────────────────┐ ││ │ │ │ • AWS Global Infrastructure │ ││ │ │ │ └─ Regions, Availability Zones, Edge Locations │ ││ │ │ │ • Hardware (Servers, Storage Devices) │ ││ │ │ │ • Software Infrastructure (Compute, Storage, Database, Networking) │ ││ │ │ │ • Host Operating System & Virtualization Layer │ ││ │ │ │ • Physical Security of Data Centers │ ││ │ │ └─────────────────────────────────────────────────────────────────────────┘ ││ │ └─────────────────────────────────────────────────────────────────────────────────┘│ │ │ └─────────────────────────────────────────────────────────────────────────────────────┘

Key AWS Responsibilities (Security OF the Cloud):
  • Physical data center security (guards, biometric access, surveillance)
  • Hardware lifecycle (servers, storage, networking equipment)
  • Host operating system and virtualization layer (Nitro Hypervisor)
  • Global network infrastructure (Regions, AZs, Edge Locations)
  • Software infrastructure (compute, storage, database, networking services)

Key Customer Responsibilities (Security IN the Cloud):
  • Data Protection: Encrypt sensitive data, manage encryption keys
  • Identity & Access Management (IAM): Create users, groups, roles, policies
  • Operating System: Patch and update the guest OS on EC2 instances
  • Network Configuration: Configure Security Groups, NACLs, route tables
  • Application Security: Secure application code, implement input validation
  • Compliance: Meet applicable regulatory requirements

Q2: What is the difference between a Security Group and a NACL?

📝 Answer:
A Security Group is a stateful firewall that operates at the instance/ENI level, controlling traffic with allow-only rules. A Network ACL (NACL) is a stateless firewall that operates at the subnet level, supporting both allow and deny rules with numbered priority order.
🔍 Detailed Comparison:
FeatureSecurity Group (SG)Network ACL (NACL)
ScopeInstance/ENI levelSubnet level
StatefulnessStatefulStateless
Rule TypesAllow onlyAllow and Deny
Rule EvaluationAll rules evaluated togetherNumerical order (first match wins)
Default BehaviorDeny all inbound, Allow all outboundAllow all (default) or Deny all (custom)
Ephemeral PortsAutomatically handledMust be explicitly configured
Attach PointsUp to 5 per ENIOne per subnet
Rule Limits60 per SG (soft)20 per NACL (soft)

When to Use Each:
Use CaseSecurity GroupNACL
Instance-level access control✅ Primary tool❌ Not applicable
Deny specific traffic at subnet level❌ Not possible✅ Use DENY rules
Multi-tier application security✅ Create separate SGs per tier✅ Secondary layer
Block malicious IPs❌ Not possible✅ Add DENY rule
Emergency lockdown❌ Limited✅ Add high-priority DENY
Dynamic references✅ Reference other SGs❌ IP addresses only

Q3: Are Security Groups stateful or stateless? What about NACLs?

📝 Answer:
Security Groups are stateful. NACLs are stateless.
🔍 Detailed Explanation:

Security Groups (Stateful):
A stateful firewall remembers the state of connections. When you allow an inbound request, the corresponding outbound response is automatically allowed, regardless of outbound rules.

STATEFUL vs STATELESS COMPARISON ┌─────────────────────────────────────────────────────────────────────────────────────┐ │ STATEFUL vs STATELESS COMPARISON │ ├─────────────────────────────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────────────────────────────────────┐│ │ │ SECURITY GROUP (Stateful) ││ │ │ ┌─────────────────────────────────────────────────────────────────────────┐ ││ │ │ │ Inbound: Allow SSH from 203.0.113.0/24 on port 22 │ ││ │ │ │ Outbound: (No rule needed for SSH response) │ ││ │ │ │ ✅ The response is automatically allowed │ ││ │ │ └─────────────────────────────────────────────────────────────────────────┘ ││ │ └─────────────────────────────────────────────────────────────────────────────────┘│ │ │ │ ┌─────────────────────────────────────────────────────────────────────────────────┐│ │ │ NETWORK ACL (Stateless) ││ │ │ ┌─────────────────────────────────────────────────────────────────────────┐ ││ │ │ │ Inbound: Allow SSH from 203.0.113.0/24 on port 22 │ ││ │ │ │ Outbound: Must also allow response traffic from instance │ ││ │ │ │ ❌ The response is NOT automatically allowed │ ││ │ │ │ Required outbound rule: Allow TCP from ephemeral ports (1024-65535) │ ││ │ │ └─────────────────────────────────────────────────────────────────────────┘ ││ │ └─────────────────────────────────────────────────────────────────────────────────┘│ │ │ └─────────────────────────────────────────────────────────────────────────────────────┘

NACLs (Stateless):
A stateless firewall does not remember the state of connections. If you allow an inbound request, the corresponding outbound response is NOT automatically allowed. You must explicitly configure both inbound and outbound rules to permit return traffic.

Why This Matters:
AspectSecurity GroupNACL
Configuration ComplexitySimpler (stateful)More complex (must handle both directions)
Ephemeral PortsAutomatically handledMust be explicitly configured
Rule CountFewer rules neededMore rules needed (inbound + outbound)

Q4: What is the default rule of a Security Group?

📝 Answer:
A newly created Security Group has the following default rules:
  • Inbound: Deny all traffic (no inbound rules)
  • Outbound: Allow all traffic (all outbound traffic is permitted)
🔍 Detailed Explanation:

New Security Group (Custom):
DirectionDefault Rule
Inbound❌ Deny all (no rules)
Outbound✅ Allow all (0.0.0.0/0 on all ports)

Default VPC Security Group:
The default security group that comes with your VPC has slightly different rules:
  • Inbound: Allows instances in the same security group to communicate with each other
  • Outbound: Allow all outbound traffic

⚠️ Important Notes:
  • Security groups operate on an allow-list basis — all traffic is implicitly denied unless explicitly allowed
  • You cannot create DENY rules in Security Groups (only ALLOW)
  • The outbound "allow all" rule can be modified or removed for additional security

Example: Creating a New Security Group
# Create a new security group aws ec2 create-security-group \ --group-name my-sg \ --description "My custom security group" \ --vpc-id vpc-12345678 # Result: Inbound: Deny all (no rules) # Outbound: Allow all (0.0.0.0/0 on all ports)

Q5: Why use IAM Roles instead of Access Keys on EC2?

📝 Answer:
Using IAM Roles for EC2 instances is better than storing Access Keys because roles provide temporary, automatically rotated credentials instead of long-term static keys. This eliminates the security risk of key exposure, reduces operational overhead, and enables centralized permission management.
🔍 Detailed Explanation:
AspectIAM Role (Temporary)Access Keys (Permanent)
Credential LifespanShort-lived, auto-rotatedLong-lived, manual rotation
StorageNot stored — retrieved via IMDSStored on instance
Management OverheadNone — AWS handles rotationManual rotation and distribution
Security PostureHigh — compromised credentials expireLow — compromised keys usable indefinitely
Permission UpdatesUpdate role once; all instances inheritUpdate each instance's key file
ComplianceAligns with best practicesConsidered an anti-pattern

Operational Challenges with Access Keys:
ChallengeDescription
Manual DistributionMust securely copy keys to every new instance
Credential RotationMust update every instance when keys are rotated
Incident ResponseCompromised keys require immediate rotation across all instances
Lack of Centralized ManagementEach instance maintains its own credentials

Security Risks with Access Keys:
  • Exposure in Code: Keys visible to anyone with read access to the repository
  • Public Exposure: Keys accidentally pushed to public repositories
  • Former Employees: Ex-employees may retain access to durable credentials
  • Long-Term Exposure: Keys remain valid until manually rotated

💡 AWS Well-Architected Framework Recommendation:
The AWS Well-Architected Framework explicitly recommends replacing long-term credentials with temporary credentials wherever possible. For EC2, this means using IAM roles instead of access keys.

Q6: What is SSM Session Manager and why is it more secure than SSH?

📝 Answer:
AWS Systems Manager Session Manager is a fully managed service that provides secure, interactive shell access to EC2 instances and other managed nodes without the need to open inbound ports, manage SSH keys, or maintain bastion hosts. It is more secure than SSH because it eliminates the attack surface of open ports, uses IAM-based authentication, and provides automatic auditing.

Q7: Can Security Groups reference other Security Groups?

📝 Answer:
Yes, Security Groups can reference other Security Groups as sources (for inbound rules) or destinations (for outbound rules). This is one of the most powerful features of Security Groups, enabling dynamic, logical firewall rules based on application tiers.
🔍 Detailed Explanation:

How Security Group References Work:
When you reference a Security Group in a rule, you are allowing traffic based on the logical grouping of resources, not their individual IP addresses. The rule affects all instances (or ENIs) associated with the referenced Security Group.

WEB → APP → DB REFERENCE Web SG (sg-web) ←── Inbound: HTTP(S) from 0.0.0.0/0 │ ▼ (reference: sg-web) App SG (sg-app) ←── Inbound: HTTP/HTTPS from sg-web │ ▼ (reference: sg-app) DB SG (sg-db) ←── Inbound: MySQL from sg-app

Benefits of Security Group References:
BenefitDescription
Simplified ManagementNo rule updates needed when scaling up/down
Self-DocumentingRules clearly express logical architecture
Dynamic ScalingRules cover thousands of instances with a single entry
Logical OrganizationAligns with application tiers rather than IP management

Where Security Group References Are Supported:
ScenarioSupportRequirements
Same VPC✅ YesSimple group-to-group reference
VPC Peering (same region)✅ YesPeering connection must be active
VPC Peering (cross-account)✅ YesFormat: 123456789012/sg-1a2b3c4d
VPC Peering (cross-region)❌ NoMust use CIDR blocks
Transit Gateway✅ YesMust enable feature on TGW
Self-Reference✅ YesA security group can reference itself
Public IP Communication❌ NoReferences only work for private IPs

Creating a Security Group Reference (CLI):
# Allow inbound MySQL access from instances in sg-app aws ec2 authorize-security-group-ingress \ --group-id sg-db \ --protocol tcp \ --port 3306 \ --source-group sg-app

Q8: What is an Ephemeral Port and why is it important for NACLs?

📝 Answer:
An ephemeral port (also called a temporary or dynamic port) is a high-numbered TCP or UDP port (typically in the range 1024-65535) that the operating system assigns to a client-side application for temporary communication. It is important for NACLs because NACLs are stateless and require explicit rules for both inbound and outbound traffic, including these ephemeral ports for return traffic.
🔍 Detailed Explanation:

What Are Ephemeral Ports?
When a client initiates a connection to a server (e.g., browsing a website), the client's operating system assigns a random high-numbered port from the ephemeral port range (usually 1024-65535). This port is used for the duration of the connection and then released.

💡 Example: Web Browsing Connection
Client (Ephemeral Port 34567) → Server (Port 80)
Server (Port 80) → Client (Ephemeral Port 34567) ← Response traffic

Why Ephemeral Ports Matter for NACLs:
Because NACLs are stateless, they do not automatically allow return traffic. For the response from the server to reach the client, you must explicitly allow traffic from the server to the ephemeral port range on the client.

NACL Configuration Example (Stateless):
DirectionRuleProtocolPortCIDRAction
InboundAllow HTTPTCP800.0.0.0/0ALLOW
OutboundAllow responseTCP1024-655350.0.0.0/0ALLOW

Common Ephemeral Port Ranges:
Operating SystemEphemeral Port Range
Linux (default)32768-60999
Windows (default)49152-65535
AWS Recommended for NACLs1024-65535

⚠️ What Happens If You Don't Allow Ephemeral Ports:
If you allow inbound HTTP (port 80) in a NACL but don't allow outbound traffic on ephemeral ports, the response traffic from your web server will be blocked. The client will never receive the response, effectively breaking the connection.

Q9: How do you restrict an instance to only allow traffic from a specific load balancer?

📝 Answer:
To restrict an EC2 instance to only allow traffic from a specific load balancer, you configure the instance's Security Group to allow inbound traffic only from the load balancer's Security Group (for ALB/NLB) or only from the load balancer's IP addresses (for Classic Load Balancer). The recommended approach is to use Security Group references, which automatically adapt as instances are added or removed.
🔍 Detailed Explanation:

Method 1: Using Security Group References (Recommended for ALB/NLB)
This is the recommended approach because it is dynamic and automatically adapts to scaling.

Step 1: Create a Security Group for the Load Balancer (ALB SG)
SG_ALB=$(aws ec2 create-security-group \ --group-name alb-sg \ --description "Security group for ALB" \ --vpc-id $VPC_ID \ --query 'GroupId' --output text) # Allow HTTP/HTTPS from the internet on the ALB aws ec2 authorize-security-group-ingress --group-id $SG_ALB --protocol tcp --port 80 --cidr 0.0.0.0/0 aws ec2 authorize-security-group-ingress --group-id $SG_ALB --protocol tcp --port 443 --cidr 0.0.0.0/0

Step 2: Create a Security Group for the Web Servers
SG_WEB=$(aws ec2 create-security-group \ --group-name web-sg \ --description "Web server SG - only allow from ALB" \ --vpc-id $VPC_ID \ --query 'GroupId' --output text) # Allow HTTP/HTTPS ONLY from the ALB Security Group aws ec2 authorize-security-group-ingress \ --group-id $SG_WEB \ --protocol tcp --port 80 \ --source-group $SG_ALB aws ec2 authorize-security-group-ingress \ --group-id $SG_WEB \ --protocol tcp --port 443 \ --source-group $SG_ALB

Method 2: Using IP Addresses (For Classic Load Balancer)
For Classic Load Balancers, you must use IP addresses because they don't support Security Group references.

ARCHITECTURE DIAGRAM Internet │ ▼ ┌─────────────────────────────────────────────────────────────────────────────────────┐ │ ALB Security Group (sg-alb) │ │ └─ Inbound: HTTP/HTTPS from 0.0.0.0/0 │ └─────────────────────────────────────────────────────────────────────────────────────┘ │ Reference (source = sg-alb) ▼ ┌─────────────────────────────────────────────────────────────────────────────────────┐ │ Web Server Security Group (sg-web) │ │ └─ Inbound: HTTP/HTTPS from sg-alb ONLY │ │ └─ No direct internet access │ └─────────────────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────────────────────────┐ │ EC2 Instances (Web Servers) │ │ └─ Only accept traffic from the ALB │ └─────────────────────────────────────────────────────────────────────────────────────┘

Benefits of Security Group References:
  • Dynamic: New instances automatically get access — no rule updates needed
  • Self-Documenting: Rules clearly express "allow traffic from ALB"
  • Scales Automatically: Works with Auto Scaling Groups without manual intervention
  • More Secure: No need to maintain IP lists

💡 Additional Security Layer: NACL
For defense-in-depth, you can also add a NACL rule to allow traffic only from the load balancer's IP range at the subnet level:
aws ec2 create-network-acl-entry \ --network-acl-id $NACL_ID \ --rule-number 100 \ --protocol tcp \ --port-range From=80,To=80 \ --cidr-block 10.0.0.0/8 \ --rule-action allow \ --ingress

Key Takeaways

  • Shared Responsibility Model: AWS secures the cloud (infrastructure, hardware, virtualization). You secure in the cloud (data, IAM, OS, network config).

  • Security Groups are stateful, instance-level firewalls with allow-only rules. Return traffic is automatically allowed.

  • NACLs are stateless, subnet-level firewalls with allow and deny rules. Rules evaluated in numerical order.

  • Default SG rules: Deny all inbound, Allow all outbound. Operates on an allow-list basis.

  • IAM Roles provide temporary, auto-rotated credentials — more secure than long-term access keys.

  • SSM Session Manager eliminates open inbound ports, SSH keys, and bastion hosts — IAM-based access control.

  • Security Group References enable dynamic, logical rules — reference other SGs instead of IP addresses.

  • Ephemeral ports (1024-65535) must be explicitly allowed in NACLs for return traffic because NACLs are stateless.

  • Restrict traffic to load balancers using Security Group references (ALB/NLB) — the recommended approach.

  • Defense-in-depth uses multiple layers: IAM (least privilege) + Security Groups + NACLs + AWS Config.
