P9.1.1 Create gp3 20GB Volume

Attach to Instance
📖 Theory: Creating and Attaching EBS Volumes
EBS volumes must be created in the same Availability Zone as the EC2 instance they will be attached to. You can create a volume from the AWS Console or CLI and attach it to a running or stopped instance.

Step 1: Identify the Instance and Availability Zone
INSTANCE_ID=$(aws ec2 describe-instances \ --filters "Name=tag:Name,Values=Golden-AMI-Builder" \ --query 'Reservations[0].Instances[0].InstanceId' \ --output text) AZ=$(aws ec2 describe-instances \ --instance-ids $INSTANCE_ID \ --query 'Reservations[0].Instances[0].Placement.AvailabilityZone' \ --output text) echo "Instance ID: $INSTANCE_ID" echo "Availability Zone: $AZ"

Step 2: Create the EBS Volume
VOLUME_ID=$(aws ec2 create-volume \ --volume-type gp3 \ --size 20 \ --availability-zone $AZ \ --tag-specifications 'ResourceType=volume,Tags=[{Key=Name,Value=data-volume}]' \ --query 'VolumeId' \ --output text) echo "Volume ID: $VOLUME_ID" aws ec2 wait volume-available --volume-ids $VOLUME_ID

Step 3: Attach the Volume to the Instance
aws ec2 attach-volume \ --volume-id $VOLUME_ID \ --instance-id $INSTANCE_ID \ --device /dev/xvdf

✅ Verification Checklist:
□ Volume created with gp3 type and 20 GB size
□ Volume is in the same AZ as the instance
□ Volume attached to the instance
📦 P9.1.1 💾 create volume 🔗 attach

P9.1.2 Partition with parted

Format as XFS
📖 Theory: Partitioning and File System Creation
Before using a new EBS volume, it must be partitioned and formatted with a file system. parted is a powerful partitioning tool, and XFS is a high-performance file system recommended for large volumes.

Step 1: Identify the New Disk
lsblk # Expected: xvdf 202:80 0 20G 0 disk ← New volume

Step 2: Partition the Disk Using parted
sudo parted /dev/xvdf mklabel gpt sudo parted /dev/xvdf mkpart primary 0% 100%

Step 3: Verify the Partition
lsblk # Expected: xvdf1 202:81 0 20G 0 part

Step 4: Format the Partition with XFS
sudo mkfs.xfs /dev/xvdf1

💡 Why XFS? XFS is a high-performance 64-bit journaling file system that handles large files and large volumes efficiently. It is the default file system on Amazon Linux 2 and AL2023.

✅ Verification Checklist:
□ Disk partitioned with GPT partition table
□ Partition created using 0% to 100%
□ Partition formatted with XFS file system
□ No errors during format
🔧 P9.1.2 📊 parted 📁 XFS format

P9.1.3 Mount to /data

Configure /etc/fstab
📖 Theory: Mounting and Auto-Mounting
Mounting attaches the file system to a directory. Configuring /etc/fstab ensures the volume is automatically mounted after a reboot.

Step 1: Create a Mount Point
sudo mkdir -p /data

Step 2: Mount the Partition
sudo mount /dev/xvdf1 /data

Step 3: Verify the Mount
df -h /data # Expected: /dev/xvdf1 20G 112M 20G 1% /data

Step 4: Get the UUID of the Partition
sudo blkid /dev/xvdf1 # Expected: UUID="a1b2c3d4-e5f6-7890-abcd-ef1234567890" TYPE="xfs"

Step 5: Add an Entry to /etc/fstab
sudo cp /etc/fstab /etc/fstab.backup echo "UUID=a1b2c3d4-e5f6-7890-abcd-ef1234567890 /data xfs defaults,nofail 0 0" | sudo tee -a /etc/fstab

💡 Why Use UUID? UUID is preferred over device names because device names can change between reboots or on different instance types. nofail prevents boot failures if the volume is not available.

Step 6: Test the Fstab Entry
sudo mount -a

✅ Verification Checklist:
□ Volume mounted to /data
□ df -h shows the volume mounted
□ UUID added to /etc/fstab
□ mount -a completes without errors
📁 P9.1.3 📊 mount 📋 fstab

P9.1.4 Detach and Attach to Second Instance

Verify Data Persistence
📖 Theory: EBS Volume Migration
EBS volumes can be detached from one instance and attached to another in the same Availability Zone. Data persists across instances, demonstrating the power of EBS as persistent storage.

Step 1: Create a Test File
echo "EBS data persistence test - $(date)" | sudo tee /data/testfile.txt

Step 2: Unmount the Volume
sudo umount /data df -h | grep /data # Should show nothing
⚠️ Always unmount before detaching — failing to unmount can cause data corruption.

Step 3: Detach the Volume
ATTACHMENT_ID=$(aws ec2 describe-volumes \ --volume-ids $VOLUME_ID \ --query 'Volumes[0].Attachments[0].AttachmentId' \ --output text) aws ec2 detach-volume --volume-id $VOLUME_ID aws ec2 wait volume-available --volume-ids $VOLUME_ID

Step 4: Launch a Second Instance
SECOND_INSTANCE_ID=$(aws ec2 run-instances \ --image-id ami-0abcdef1234567890 \ --instance-type t3.micro \ --subnet-id $(aws ec2 describe-instances --instance-ids $INSTANCE_ID --query 'Reservations[0].Instances[0].SubnetId' --output text) \ --key-name MyKeyPair \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=Second-Instance}]' \ --query 'Instances[0].InstanceId' \ --output text) aws ec2 wait instance-running --instance-ids $SECOND_INSTANCE_ID
Step 5: Attach the Volume to the Second Instance
aws ec2 attach-volume \ --volume-id $VOLUME_ID \ --instance-id $SECOND_INSTANCE_ID \ --device /dev/xvdf

Step 6: Verify Data Persistence
# On the second instance sudo mkdir -p /data sudo mount /dev/xvdf1 /data cat /data/testfile.txt # Expected: EBS data persistence test - Tue Aug 03 10:30:15 UTC 2026

💡 Key Insight: The test file created on the first instance is still present on the second instance. This demonstrates that EBS data persists even when detached and reattached to a different instance.

Step 7: Clean Up
sudo umount /data aws ec2 terminate-instances --instance-ids $INSTANCE_ID $SECOND_INSTANCE_ID aws ec2 delete-volume --volume-id $VOLUME_ID

✅ Verification Checklist:
□ Test file created on first instance
□ Volume unmounted before detach
□ Volume detached successfully
□ Second instance launched in same AZ
□ Volume attached to second instance
□ Test file content verified on second instance
🔄 P9.1.4 🔀 detach/attach ✅ data persistence

Key Takeaways

  • EBS volumes must be in the same Availability Zone as the EC2 instance they are attached to.

  • New EBS volumes must be partitioned and formatted before use. parted and mkfs.xfs are essential tools.

  • UUID in /etc/fstab is preferred over device names because device names can change between reboots or on different instance types.

  • The nofail option in /etc/fstab prevents boot failures if the volume is not available.

  • Data persists on EBS volumes even when detached and reattached to different instances.

  • Always unmount before detaching to prevent data corruption.

  • XFS is the default file system on Amazon Linux 2 and AL2023 — it handles large files and large volumes efficiently.

  • lsblk is used to identify new disks and partitions.

  • blkid retrieves the UUID of a partition for fstab entries.

  • mount -a tests fstab entries without rebooting.
