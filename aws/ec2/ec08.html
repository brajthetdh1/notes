4.4 Creating and Managing Custom AMIs

4.4.1 Overview of Creating EBS-Backed AMIs
A custom Amazon Machine Image (AMI) is a pre-configured template that contains your specific operating system, applications, and configurations. Creating custom AMIs enables consistent deployments, faster scaling, and reduced manual setup.

This section covers the complete process of creating and managing custom EBS-backed AMIs.
🔧 custom AMIs 📋 EBS-backed 🔄 lifecycle
📖

Why Create Custom AMIs?

Custom AMIs are a cornerstone of production-grade infrastructure. They allow you to:

1. ✅ Consistency
Every instance launched from your custom AMI starts with the exact same configuration, eliminating configuration drift.
2. ⚡ Speed
Instances launch faster because they are ready to serve traffic immediately — no manual installation required.
3. 🏆 Golden AMI Strategy
A hardened, pre-configured AMI that serves as the single source of truth for your infrastructure.
4. 🔒 Security
Bake security hardening directly into the image — OS patches, disabled services, SSH hardening.
5. 🔄 Disaster Recovery
Quickly rebuild infrastructure in another region or account — the entire server configuration is captured in a reusable template.

Creating an AMI from an Instance

The most common method for creating a custom AMI is to start from a running EC2 instance, customize it, and then create an image.

Step-by-Step Process:
1
Launch Base
Start with a trusted base AMI
2
Connect & Customize
SSH/RDP, install software, apply patches
3
Harden
Security updates, SSH config, firewall
4
Clean Up
Remove temp files, package caches
5
Create AMI
Console or CLI → create-image

Hardening Example (Linux):
# Update system packages sudo apt update && sudo apt upgrade -y # Ubuntu/Debian # OR sudo dnf update -y # Amazon Linux # Create a dedicated application user sudo adduser appuser sudo usermod -aG sudo appuser # Harden SSH Configuration sudo nano /etc/ssh/sshd_config # Set: PermitRootLogin no, PasswordAuthentication no, UsePAM yes sudo systemctl restart ssh # Configure Firewall (UFW example) sudo ufw allow OpenSSH sudo ufw allow 80 sudo ufw allow 443 sudo ufw enable # Install common packages sudo apt install -y curl wget git net-tools unzip nginx

Clean Up Before AMI Creation:
# Remove package caches sudo apt clean # Ubuntu/Debian sudo dnf clean all # Amazon Linux # Remove temporary files sudo rm -rf /tmp/* # Clear shell history history -c # Remove SSH host keys (will be regenerated on boot) sudo rm -rf /etc/ssh/ssh_host_*

Creating the AMI

Using the AWS Management Console:
  1. Navigate to EC2 → Instances
  2. Select your running instance
  3. Choose Actions → Image and templates → Create image
  4. Enter a unique name and description
  5. (Optional) Modify block device mapping or add additional EBS volumes
  6. Choose No reboot if you want to avoid downtime (filesystem consistency not guaranteed)
  7. Click Create image

Using the AWS CLI:
aws ec2 create-image \ --instance-id i-1234567890abcdef0 \ --name "My-Custom-AMI-v1.0" \ --description "Hardened web server AMI" \ --no-reboot

📋 What Happens During AMI Creation:
  • Consistency Check: EC2 powers down the instance (unless --no-reboot) to ensure data consistency
  • Snapshot Creation: EC2 creates snapshots of the root volume and any other EBS volumes
  • Registration: EC2 registers the new AMI (state: pending)
  • Availability: After completion, state changes to available

⚠️ Important: You are billed for both the AMI and the underlying EBS snapshots. Costs continue until you deregister the AMI and delete the associated snapshots.

Managing AMI Lifecycle

EC2 Image Builder — Automated AMI Management
EC2 Image Builder is a fully managed AWS service that automates the creation, management, and deployment of customized, secure, and up-to-date server images.

Key Components:
  • Image Recipe: Defines the base image and components to apply
  • Image Pipeline: Automation framework for building, validating, and testing images on a schedule
  • Components: Individual build steps (install packages, run scripts, apply configurations)
  • Distribution: Automatically shares and copies AMIs to other regions and accounts

Deregistering AMIs and Cleaning Up Resources

When an AMI is no longer needed, you should deregister it to prevent unauthorized launches and reduce costs.

Using the AWS Console:
  1. Navigate to EC2 → AMIs
  2. Select your AMI (Owned by me)
  3. Choose Actions → Deregister AMI
  4. (Optional) Select Delete associated snapshots

Using the AWS CLI:
# Deregister AMI only (snapshots remain) aws ec2 deregister-image --image-id ami-1234567890abcdef0 # Deregister AMI and delete associated snapshots aws ec2 deregister-image \ --image-id ami-1234567890abcdef0 \ --delete-associated-snapshots

⚠️ Important: If a snapshot is associated with multiple AMIs, it will not be deleted even if you specify --delete-associated-snapshots. The AMI will still be deregistered.

📌 Considerations When Deregistering:
  • Deregistering an AMI does not affect any instances launched from that AMI
  • You will continue to incur storage costs for any snapshots not deleted
  • You can still view some high-level information about the AMI for instances launched from it
  • You cannot deregister an AMI managed by AWS Backup (use AWS Backup instead)

Key Takeaways

  • Custom AMIs are essential for consistent, secure, and efficient EC2 deployments. They enable faster scaling and simplified disaster recovery.

  • The "Golden AMI" strategy involves creating a hardened, pre-configured AMI that serves as the single source of truth for your infrastructure.

  • EC2 Image Builder provides a fully managed, automated solution for building, patching, and distributing custom AMIs.

  • Always harden your instances before creating AMIs — security patches, disable password authentication, configure firewalls.

  • Clean up before creating an AMI to reduce image size and improve launch speed — remove temporary files, package caches, and shell history.

  • Manage AMI lifecycle proactively with Amazon Data Lifecycle Manager to automate creation, sharing, and cleanup.

  • When deregistering an AMI, you can automatically delete associated snapshots using --delete-associated-snapshots, simplifying cleanup and reducing costs.

  • Deregistering an AMI has no impact on running instances that were launched from it. You must terminate those instances separately to stop costs.

Review Questions

Q1: What is a Golden AMI and why is it important?
Answer: A Golden AMI is a hardened, pre-configured AMI that serves as a single source of truth for your infrastructure. It is important because it ensures consistency across all launched instances, improves security by baking hardening into the image, accelerates deployment speed, and simplifies scaling and disaster recovery.
Q2: What steps are involved in creating a custom EBS-backed AMI from an instance?
Answer: The process involves:
  • Launching a base instance from a trusted AMI
  • Connecting and customizing (installing software, applying patches, configuring settings)
  • Hardening the instance (security updates, SSH configuration, firewall rules)
  • Cleaning up unnecessary files (temporary files, package caches, shell history)
  • Creating the AMI using the EC2 console or CLI (aws ec2 create-image)
Q3: How does EC2 Image Builder help automate AMI management?
Answer: EC2 Image Builder is a fully managed service that automates AMI creation and management. It provides:
  • Image Recipes — define base image and components
  • Image Pipelines — automate build, validation, and distribution on a schedule
  • Components — install packages, run scripts, apply configurations
  • Distribution — copy AMIs to multiple regions and accounts
  • Versionless ARN — automatically use the latest parent image
Q4: How can you deregister an AMI and delete its associated snapshots?
Answer: You can deregister an AMI and delete its associated snapshots using the AWS CLI with the --delete-associated-snapshots parameter:
aws ec2 deregister-image --image-id ami-1234567890abcdef0 --delete-associated-snapshots
In the AWS Console, when selecting the AMI and choosing "Deregister AMI", you can check the "Delete associated snapshots" checkbox.
Q5: What happens to instances launched from an AMI after you deregister it?
Answer: Deregistering an AMI has no effect on any instances that were launched from the AMI. You can continue to use these instances normally. However, you cannot use the deregistered AMI to launch new instances. You should consider terminating any instances that you no longer need to avoid continued costs.
