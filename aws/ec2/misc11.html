14.1 Common EC2 Issues

📖 Complete Theory: Troubleshooting EC2

When an EC2 instance becomes unreachable or fails to boot, it's rarely a single cause. Most issues fall into one of two categories: problems with the AWS infrastructure hosting your instance, or problems with the operating system and configuration inside your instance. Understanding this distinction is the first step toward effective troubleshooting.

Two Types of Status Check Failures

EC2 runs two independent health checks on every running instance:

Status CheckWhat It VerifiesWho Owns the Problem
System Status CheckAWS infrastructure — physical host hardware, network connectivity at hypervisor level, powerAWS (but you must take action)
Instance Status CheckYour operating system — boot process, network config, file system integrity, kernel stateYou

System Status Check Failure:
The hardware your instance runs on has a problem — network issues at the hypervisor, power loss, or physical host degradation. You cannot fix the underlying hardware, but you can move your instance to healthy hardware by stopping and starting the instance (not rebooting).

Instance Status Check Failure:
Your OS isn't booting properly or is misconfigured. Common causes include:
  • Kernel panic or failed kernel update
  • Corrupted file system
  • Bad /etc/fstab entry preventing boot
  • Full root volume
  • Incorrect network configuration
  • Insufficient CPU or memory resources

14.1.1 SSH Connection Failures

Timeout, Permission Denied
📖 Complete Theory: SSH Connection Failures

SSH connection failures to an EC2 instance typically fall into two main categories: Connection Timeout and Permission Denied (publickey). Each indicates a different type of problem with different troubleshooting paths.

🌐 Connection Timeout
A "Connection timed out" error means your SSH packets are not reaching the instance, or the instance's responses are not making it back to you. This is almost always a networking configuration issue.

Troubleshooting Checklist:
  • Security Group: Verify inbound rules allow SSH (port 22) from your IP address
  • Network ACL: NACLs are stateless — allow traffic in both directions (inbound: port 22, outbound: ephemeral ports 1024-65535)
  • Route Table: Ensure public subnet has route to IGW (0.0.0.0/0 → igw-xxxxxxxx)
  • Public IP: Verify instance has a public IP or Elastic IP associated
  • Instance Health: Confirm instance is running and has passed both status checks

❌ Permission Denied (publickey)
A "Permission denied (publickey)" error means your SSH request reached the instance, but the authentication failed. The instance did not find a matching public key for the private key you presented.

Troubleshooting Checklist:
  • Verify the Default Username: Amazon Linux: ec2-user, Ubuntu: ubuntu, Debian: admin
  • Correct Key Pair: Check instance details and ensure you're using the matching private key
  • File Permissions: chmod 400 /path/to/your-key.pem
  • Check .ssh/authorized_keys: File permissions should be 700 for .ssh and 600 for authorized_keys
Recovery Options for Lost Keys:
  • EC2 Instance Connect: Browser-based SSH that bypasses key pair requirement
  • SSM Session Manager: Access a shell without SSH altogether
  • Rescue Instance: Stop instance, detach root volume, attach to temporary instance, edit authorized_keys

💡 Key Insight: NACLs are stateless — you must allow traffic in both directions. For SSH to work, ensure outbound rules permit ephemeral ports (1024-65535) for response traffic.

14.1.2 Instance Unreachable

📖 Complete Theory: Instance Unreachable

When an EC2 instance is unreachable, it means you cannot connect to it via SSH, RDP, or other standard protocols. This often indicates a more severe problem than a simple SSH configuration error, and the instance may fail its Instance Status Check.

⚠️ Critical Warning: Don't Reboot a Failing Instance
If your instance is failing its status checks or is unreachable, do not use aws ec2 reboot-instances. Rebooting a failed instance will keep it on the same physical host, and if the host is the problem, it won't resolve the issue. Instead, the correct action is to stop and start the instance.

🛠️ Troubleshooting Checklist for Unreachable Instances:

1. Check Instance Status Checks:
  • System Status Check Failure: AWS infrastructure problem — stop and start the instance
  • Instance Status Check Failure: OS problem — requires investigation (Serial Console or Rescue Instance)

2. Recover from System Status Check Failure:
  • Stop the instance → Start the instance
  • Moves instance to new underlying hardware
  • New public IP (unless Elastic IP assigned)
  • EBS data persists; Instance Store data is lost

3. Recover from Instance Status Check Failure:
  • EC2 Serial Console: Text-based access even when OS isn't fully booted
  • Rescue Instance: Universal workaround — move root volume to temporary instance
Step-by-Step Rescue Process:
  1. Stop the problem instance
  2. Detach the root volume
  3. Launch a temporary rescue instance (same AZ, same AMI family)
  4. Attach the volume to the rescue instance as a secondary device
  5. Mount the volume and fix the issue (e.g., edit /etc/fstab)
  6. Unmount, detach, reattach to the original instance
  7. Start the original instance

💡 The Stop/Start workflow is the primary recovery method because it forces the instance to move to a new, healthy physical host. When you stop and start an EBS-backed instance, AWS releases the physical resources and reallocates them, often resolving issues caused by host-level degradation.

14.1.3 Status Check Failures

System vs. Instance
📖 Complete Theory: Status Check Failures

Amazon EC2 performs automated, minute-by-minute health checks on every running instance to identify problems. The results determine the overall status: OK (all checks pass) or impaired (one or more checks fail).

🖥️ System Status Checks (AWS Infrastructure):
  • What They Monitor: Physical host, network, power
  • Who Owns the Problem: AWS
  • Resolution: Stop and start the instance (EBS-backed)
  • CloudWatch Metric: StatusCheckFailed_System

💻 Instance Status Checks (Your OS and Software):
  • What They Monitor: Guest OS, applications, network configuration
  • Who Owns the Problem: You
  • Resolution: Troubleshoot the OS — Serial Console, Rescue Instance, or EC2Rescue
  • CloudWatch Metric: StatusCheckFailed_Instance

🔌 Attached EBS Status Checks (Volume Health):
  • What They Monitor: EBS volume reachability and I/O operations
  • Who Owns the Problem: Shared (AWS & customer)
  • Resolution: Stop and start the instance or replace the EBS volume
  • CloudWatch Metric: StatusCheckFailed_AttachedEBS

FeatureSystem Status CheckInstance Status CheckAttached EBS Status Check
What It MonitorsAWS InfrastructureYour OS & softwareEBS reachability & I/O
Who Owns the ProblemAWSYouShared
Primary ResolutionStop and startSerial Console / Rescue InstanceStop and start / Replace volume
CloudWatch MetricStatusCheckFailed_SystemStatusCheckFailed_InstanceStatusCheckFailed_AttachedEBS

💡 Why Stop/Start Works (and Reboot Doesn't):
A simple reboot keeps your instance on the same physical host. If a system status check fails, the issue is with that underlying host, and a reboot will not resolve it. When you stop and start an EBS-backed instance, AWS releases the physical resources and allocates a new set, often migrating the instance to a new, healthy host.

14.1.4 Boot Failures

Corrupted OS, Kernel Panic
📖 Complete Theory: Boot Failures

Boot failures are among the most critical EC2 issues. When your instance fails to boot, it fails the Instance Status Check, rendering it unreachable via SSH or RDP.

🔍 The "Instance Unreachable" Scenario:
The root cause is often a problem at the OS level:
  • Network or startup configuration errors (e.g., a bad /etc/fstab entry)
  • File system corruption (e.g., unmountable /sysroot or XFS metadata errors)
  • Incompatible Kernel or kernel panic (often after a failed update)

🛠️ The Three Primary Recovery Methods:

1. EC2 Serial Console
Text-based access even when OS isn't fully booted
Requires Nitro-based instance type
Fixes: bad fstab, broken SSH config, network issues
2. Rescue Instance
Universal workaround — move root volume
Works for all instance types
Stop → Detach → Rescue → Fix → Reattach → Start
3. EC2Rescue
AWS tool automates diagnostics
Command-line tool
Automates manual rescue instance steps

💡 Common Fix via Serial Console:
Bad fstab entry: Boot drops to emergency shell. Log in, remount root as read-write (mount -o remount,rw /), edit /etc/fstab to fix the entry, and reboot.
🧠 Critical Insights:
  • Public IP changes on stop/start: Unless using an Elastic IP
  • Stop/Start vs. Reboot: Stop/start moves to new hardware; reboot keeps same host
  • Instance Store data is lost on stop
  • Linux boot process: BIOS/UEFI → Bootloader → Kernel → initramfs → systemd

🔍 Review Questions
Q1: What is the main difference between a System Status Check and an Instance Status Check failure?
A System Status Check failure indicates a problem with the AWS infrastructure (the physical host), which is an AWS issue, and you should stop and start the instance to move it to new hardware. An Instance Status Check failure indicates a problem with your operating system, which you are responsible for troubleshooting.
Q2: What are the three primary methods for troubleshooting an EC2 boot failure?
The three primary methods are: (1) EC2 Serial Console — text-based access even when OS isn't fully booted; (2) Rescue Instance — stop, detach, attach to temporary instance, fix, reattach; (3) EC2Rescue — an AWS tool that automates diagnostics and troubleshooting.
Q3: How can you fix a bad fstab entry using a rescue instance?
Stop the problematic instance, detach its root volume, attach it to a rescue instance, and mount it. Then, edit the /etc/fstab file on the mounted volume and comment out or fix the bad entry (e.g., add the nofail option).
Q4: What happens to the public IP address when you stop and start an EC2 instance?
If the instance has a standard public IP (not an Elastic IP), it will be released when the instance is stopped. When the instance is started again, it will receive a new public IP address. The private IP address remains the same.

Key Takeaways

  • Two types of status checks: System (AWS infrastructure) and Instance (your OS). Stop/start fixes System failures; OS troubleshooting fixes Instance failures.

  • Don't reboot a failing instance: Reboot keeps you on the same bad host. Stop and start moves you to a new, healthy host.

  • SSH Connection Timeout: Check Security Groups, NACLs (stateless — check both directions!), route tables, public IP, and instance health.

  • SSH Permission Denied: Verify username, key pair, file permissions (chmod 400), and ~/.ssh/authorized_keys.

  • NACLs are stateless: You must allow traffic in both directions — inbound SSH (port 22) and outbound ephemeral ports (1024-65535).

  • Three recovery methods for boot failures: EC2 Serial Console (preferred), Rescue Instance (universal), EC2Rescue (automated).

  • Public IP changes on stop/start: Unless you're using an Elastic IP, the public IP will change after a stop/start cycle.

  • Instance Store data is lost on stop: Data on Instance Store volumes is erased permanently when you stop an instance.

  • Recovery options for lost keys: EC2 Instance Connect, SSM Session Manager, or Rescue Instance.

  • Check system logs: EC2 console → Actions → Monitor and troubleshoot → Get system log. This output can reveal kernel panics, missing boot files, and file system corruption errors.
