8.1 Auto Scaling Groups (ASGs)

📖 Complete Theory

An Auto Scaling Group (ASG) is a core AWS service that manages a collection of EC2 instances as a single, logical unit for the purposes of automatic scaling and management. Its primary role is to ensure that you have the correct number of instances available to handle the load for your application.

Instead of manually launching and terminating instances, you define an ASG with a minimum, maximum, and desired capacity. The ASG continuously works to maintain the desired number of healthy instances.

The Logical Unit of Scalability

The core purpose of an ASG is threefold:

  • ✅ Maintain a Fixed Number of Instances: Ensures a specified number of instances are always running and healthy

  • 📈 Enable Automatic Scaling: Dynamically adjusts instance count based on demand using scaling policies

  • 🌍 Distribute Instances Across AZs: Provides fault tolerance and high availability

Core Components of an ASG

1. Launch Template (or Launch Configuration)
An ASG uses a Launch Template (recommended) as a blueprint for EC2 instances, defining: AMI, Instance Type, Security Groups, Key Pair, IAM Role, and User Data.

⚠️ Best Practice: AWS strongly recommends using a launch template over a launch configuration. Launch templates provide significantly more flexibility and features, including multiple versions, support for mixed instance types (Spot and On-Demand), and advanced parameters.

2. Desired, Minimum, and Maximum Capacity
🎯 Desired Capacity
The exact number of instances the ASG tries to maintain
Example: 2
📉 Minimum Capacity
The lowest number of instances the ASG will ever have
Example: 1
📈 Maximum Capacity
The highest number of instances the ASG will ever have
Example: 5
3. Scaling Policies
✋ Manual
You adjust Desired Capacity manually
📊 Simple
Single alarm triggers single action
📈 Step
Multiple alarms, different actions
🎯 Target Tracking
Maintains target metric value (e.g., 50% CPU)
📅 Scheduled
Scaling on a schedule (e.g., every Monday 9 AM)

4. Health Checks
The ASG automatically monitors instance health using:
  • EC2 Status Checks: System status + Instance status
  • ELB Health Checks: Application-level health checks
  • Custom Health Checks: Application-specific checks

Integration with Load Balancers

ASGs integrate seamlessly with Elastic Load Balancers (ELBs) to distribute traffic across healthy instances. When instances are launched, they are automatically registered with the load balancer; when they are terminated, they are deregistered.

Application Load Balancer (ALB) Integration
The recommended integration is with an Application Load Balancer (ALB), which operates at Layer 7 and can route traffic based on the request path. The ASG registers and deregisters instances with the ALB's Target Group.

Advantages of Auto Scaling Groups

  • 📈 Dynamic Scaling: Automatically adjusts capacity based on real-time load, ensuring optimal performance and cost.

  • 💰 Cost Efficiency: By matching resources to demand, ASGs help you avoid over-provisioning and only pay for what you use.

  • 🛡️ High Availability & Fault Tolerance: Distributes instances across Availability Zones and automatically replaces unhealthy ones.

  • ⚡ Automated Performance Management: Maintains consistent application performance by dynamically responding to workload changes.

  • 🔗 Integration with Other AWS Services: Integrates with ELB, CloudWatch, and other services for a comprehensive scaling solution.

8.1.2 Launch Templates vs. Launch Configurations

📖 Complete Theory: The Blueprint Evolution

Both Launch Templates and Launch Configurations serve as blueprints that define how new EC2 instances should be provisioned. However, Launch Templates are the modern, feature-rich replacement for the older Launch Configurations.

⚠️ Critical Deprecation Notice: AWS began phasing out launch configurations starting October 1, 2024. New AWS accounts can no longer create launch configurations, and existing ones are encouraged to migrate to launch templates.

Key Takeaways

  • ASG is a logical grouping of EC2 instances for scaling and management.

  • Uses a Launch Template as a blueprint for instances — Launch Configurations are deprecated.

  • Maintains Desired Capacity between Min and Max limits.

  • Supports Multiple Scaling Policies for dynamic or scheduled scaling.

  • Integrates with Load Balancers to distribute traffic and ensure availability.

  • Launch Templates offer versioning, mixed instance types, and support for all current and future EC2 features.

  • October 1, 2024: Launch Configurations phased out for new accounts.

Review Questions

Q1: What is the primary purpose of an Auto Scaling Group?
Answer: The primary purpose of an ASG is to ensure that you have the correct number of healthy EC2 instances available to handle the load for your application. It manages instances as a logical unit, automatically scaling capacity and replacing unhealthy instances.
Q2: What is the difference between a launch template and a launch configuration?
Answer: A launch template is the modern, recommended way to define instance configuration for an ASG. It offers greater flexibility than a launch configuration, including multiple versions, support for mixed instance types (Spot and On-Demand), and more detailed configuration options. Launch Configurations are deprecated as of October 2024.
Q3: What are the three capacity parameters for an Auto Scaling Group?
Answer: The three parameters are Min Size (the smallest number of instances the group can have), Max Size (the largest number of instances the group can have), and Desired Capacity (the exact number of instances the group tries to maintain). Scaling policies adjust the desired capacity within the Min and Max limits.
Q4: How does an Auto Scaling Group handle instances that become unhealthy?
Answer: The ASG performs periodic health checks using EC2 status checks and (if attached) ELB health checks. If an instance fails a health check, the ASG terminates it and automatically launches a new instance to replace it and maintain the desired capacity.
Q5: What is the Target Tracking scaling policy?
Answer: A Target Tracking scaling policy allows you to set a target metric value (e.g., 50% average CPU utilization). The ASG then automatically adjusts the desired capacity (launching or terminating instances) to keep the metric at or close to the target, handling the scaling logic for you.
