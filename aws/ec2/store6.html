P9.2.1 Take Snapshot of Boot Volume

📖 Theory: The First Step in Disaster Recovery
Taking a snapshot of the root volume is the prerequisite for rebuilding an instance. The root volume contains the operating system, applications, and configurations that define your instance's state.

Step 1: Identify the Root Volume
INSTANCE_ID=$(aws ec2 describe-instances \ --filters "Name=tag:Name,Values=Golden-AMI-Builder" \ --query 'Reservations[0].Instances[0].InstanceId' \ --output text) ROOT_VOLUME_ID=$(aws ec2 describe-instances \ --instance-ids $INSTANCE_ID \ --query 'Reservations[0].Instances[0].BlockDeviceMappings[?DeviceName==`/dev/xvda`].Ebs.VolumeId' \ --output text) echo "Instance ID: $INSTANCE_ID" echo "Root Volume ID: $ROOT_VOLUME_ID"

Step 2: Create a Snapshot
SNAPSHOT_ID=$(aws ec2 create-snapshot \ --volume-id $ROOT_VOLUME_ID \ --description "Disaster recovery snapshot before terminating instance" \ --tag-specifications 'ResourceType=snapshot,Tags=[{Key=Name,Value=root-volume-backup-pre-disaster}]' \ --query 'SnapshotId' \ --output text) echo "Snapshot ID: $SNAPSHOT_ID" aws ec2 wait snapshot-completed --snapshot-ids $SNAPSHOT_ID

💡 Incremental Snapshots: Because snapshots are incremental, the first snapshot is a full copy, and subsequent ones only store the changed blocks. This makes them cost-effective for frequent backups.

✅ Verification Checklist:
□ Snapshot created from the root volume
□ Snapshot is in a completed state
📸 P9.2.1 💾 root volume 📸 snapshot

P9.2.2 Delete Original Instance

Simulate Disaster
📖 Theory: The Disaster Simulation
Terminating the original instance simulates a catastrophic failure where the instance is lost. The EBS root volume may be deleted as well, but you have the snapshot you created in the previous step.

⚠️ If DeleteOnTermination is true for the root volume, the volume itself will be deleted when the instance is terminated. This is why having a snapshot is critical.

Step 1: Verify the Snapshot Exists
aws ec2 describe-snapshots --snapshot-ids $SNAPSHOT_ID

Step 2: Terminate the Original Instance
aws ec2 terminate-instances --instance-ids $INSTANCE_ID aws ec2 wait instance-terminated --instance-ids $INSTANCE_ID

✅ Verification Checklist:
□ Original instance terminated
□ Snapshot is still available
💥 P9.2.2 🔥 disaster simulation 💾 snapshot survives

P9.2.3 Create AMI from Snapshot

The Recovery Process
📖 Theory: The AMI Recovery Process
You cannot launch an instance directly from a snapshot. The proper recovery method is to create an AMI from the snapshot, and then launch a new instance from that AMI.

Step 1: Create an AMI from the Snapshot
AMI_ID=$(aws ec2 register-image \ --name "recovered-instance-ami-v1" \ --description "AMI created from snapshot for disaster recovery" \ --architecture x86_64 \ --root-device-name /dev/xvda \ --block-device-mappings "DeviceName=/dev/xvda,Ebs={SnapshotId=$SNAPSHOT_ID,VolumeType=gp3,DeleteOnTermination=true}" \ --virtualization-type hvm \ --query 'ImageId' \ --output text) echo "AMI ID: $AMI_ID" aws ec2 wait image-available --image-ids $AMI_ID

💡 Why Register an AMI? When registering an AMI from a snapshot, you must specify architecture, root device name, and virtualization type. This metadata is what makes the AMI launchable.

Step 2: Launch a New Instance
NEW_INSTANCE_ID=$(aws ec2 run-instances \ --image-id $AMI_ID \ --instance-type t3.micro \ --key-name MyKeyPair \ --subnet-id $(aws ec2 describe-subnets --filters "Name=tag:Name,Values=public-subnet-a" --query 'Subnets[0].SubnetId' --output text) \ --security-group-ids $(aws ec2 describe-security-groups --filters "Name=group-name,Values=web-server-sg" --query 'SecurityGroups[0].GroupId' --output text) \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=Recovered-Instance}]' \ --query 'Instances[0].InstanceId' \ --output text) echo "Recovered Instance ID: $NEW_INSTANCE_ID" aws ec2 wait instance-running --instance-ids $NEW_INSTANCE_ID

✅ Verification Checklist:
□ AMI created from snapshot
□ AMI is in an available state
□ New instance launched from the AMI
□ New instance is in a running state
🔄 P9.2.3 📋 create AMI 🚀 launch instance
✅

P9.2.4 Verify Configuration and Data Recovery

📖 Theory: Post-Recovery Validation
Validation confirms that the recovery was successful. Key checks include OS version, installed applications, configuration files, and any custom data stored on the root volume.

Step 1: Connect to the Recovered Instance
PUBLIC_IP=$(aws ec2 describe-instances \ --instance-ids $NEW_INSTANCE_ID \ --query 'Reservations[0].Instances[0].PublicIpAddress' \ --output text) echo "Recovered Instance Public IP: $PUBLIC_IP" ssh -i MyKeyPair.pem ec2-user@$PUBLIC_IP

Step 2: Verify OS and Configuration
# Check OS version cat /etc/os-release # Check kernel version uname -r # Verify installed packages rpm -qa | head -20 # Check Apache status sudo systemctl status httpd

Step 3: Verify Custom Data
ls -la /var/www/html cat /var/www/html/index.html

💡 Key Insight: The recovered instance should be identical to the original instance as of the snapshot creation time. This includes OS version, installed packages, and custom data.

✅ Verification Checklist:
□ Successfully connected to the recovered instance
□ OS version matches the original
□ Apache is running
□ Custom web page is accessible
✅ P9.2.4 📊 verification 🔄 recovery success

Key Takeaways

  • A snapshot is a point-in-time backup of a single volume, not a launchable instance.

  • You cannot launch an instance directly from a snapshot — you must create an AMI first.

  • When registering an AMI from a snapshot, you must specify architecture, root device name, and virtualization type.

  • An AMI contains one or more snapshots plus instance metadata (architecture, kernel ID, virtualization type).

  • Snapshots are incremental — the first snapshot is a full copy, subsequent ones only store changed blocks.

  • DeleteOnTermination determines whether the root volume is deleted when the instance is terminated.

  • aws ec2 register-image creates an AMI from a snapshot.

  • aws ec2 wait image-available ensures the AMI is ready before launching.

  • Post-recovery validation is essential — verify OS version, installed packages, and custom data.

  • Disaster recovery is not complete until you've tested the recovery process.

Cleanup

# Terminate the recovered instance aws ec2 terminate-instances --instance-ids $NEW_INSTANCE_ID # Deregister the recovered AMI aws ec2 deregister-image --image-id $AMI_ID # Delete the snapshot aws ec2 delete-snapshot --snapshot-id $SNAPSHOT_ID

💡 Remember: Deregistering an AMI does not automatically delete the underlying snapshots. You must delete them separately to avoid ongoing storage costs.
