P7.1 Create Three Subnets

DMZ, App, DB
📖 Theory: Subnet Segmentation
Creating multiple subnets allows you to segment your network for different purposes:
  • DMZ (Demilitarized Zone): Public-facing resources (load balancers, bastion hosts)
  • App: Application servers (internal communication)
  • DB: Database tier (most restricted)

Step 1: Create the VPC
# Create VPC VPC_ID=$(aws ec2 create-vpc \ --cidr-block 10.0.0.0/16 \ --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=multi-nic-vpc}]' \ --query 'Vpc.VpcId' --output text) echo "VPC ID: $VPC_ID" # Enable DNS hostnames aws ec2 modify-vpc-attribute --vpc-id $VPC_ID --enable-dns-hostnames

Step 2: Create Internet Gateway
IGW_ID=$(aws ec2 create-internet-gateway \ --tag-specifications 'ResourceType=internet-gateway,Tags=[{Key=Name,Value=multi-nic-igw}]' \ --query 'InternetGateway.InternetGatewayId' --output text) aws ec2 attach-internet-gateway --internet-gateway-id $IGW_ID --vpc-id $VPC_ID

Step 3: Create the Three Subnets
# DMZ Subnet (Public) SUBNET_DMZ=$(aws ec2 create-subnet \ --vpc-id $VPC_ID \ --cidr-block 10.0.1.0/24 \ --availability-zone us-east-1a \ --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=dmz-subnet}]' \ --query 'Subnet.SubnetId' --output text) # App Subnet (Private) SUBNET_APP=$(aws ec2 create-subnet \ --vpc-id $VPC_ID \ --cidr-block 10.0.2.0/24 \ --availability-zone us-east-1a \ --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=app-subnet}]' \ --query 'Subnet.SubnetId' --output text) # DB Subnet (Private) SUBNET_DB=$(aws ec2 create-subnet \ --vpc-id $VPC_ID \ --cidr-block 10.0.3.0/24 \ --availability-zone us-east-1a \ --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=db-subnet}]' \ --query 'Subnet.SubnetId' --output text)

Step 4: Create Route Tables
# DMZ Route Table (Public) RT_DMZ=$(aws ec2 create-route-table \ --vpc-id $VPC_ID \ --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=rt-dmz}]' \ --query 'RouteTable.RouteTableId' --output text) aws ec2 create-route --route-table-id $RT_DMZ --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW_ID # App Route Table (Private) RT_APP=$(aws ec2 create-route-table --vpc-id $VPC_ID --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=rt-app}]' --query 'RouteTable.RouteTableId' --output text) # DB Route Table (Private) RT_DB=$(aws ec2 create-route-table --vpc-id $VPC_ID --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=rt-db}]' --query 'RouteTable.RouteTableId' --output text)

Step 5: Associate Subnets with Route Tables
aws ec2 associate-route-table --route-table-id $RT_DMZ --subnet-id $SUBNET_DMZ aws ec2 associate-route-table --route-table-id $RT_APP --subnet-id $SUBNET_APP aws ec2 associate-route-table --route-table-id $RT_DB --subnet-id $SUBNET_DB # Enable auto-assign public IP for DMZ subnet only aws ec2 modify-subnet-attribute --subnet-id $SUBNET_DMZ --map-public-ip-on-launch
✅ Verification Checklist:
□ VPC created with CIDR 10.0.0.0/16
□ 3 subnets created (DMZ, App, DB)
□ Internet Gateway created and attached
□ Route tables created and associated
🌐 P7.1 🧱 subnets 📊 DMZ/App/DB

P7.2 Create Three ENIs

In Different Subnets
📖 Theory: Elastic Network Interfaces
ENIs decouple network configuration from compute instances. Each ENI gets its own IP address, security group, and can be independently attached/detached from instances.

Step 1: Create Security Group
SG_ID=$(aws ec2 create-security-group \ --group-name multi-nic-sg \ --description "Security group for multi-NIC instance" \ --vpc-id $VPC_ID \ --tag-specifications 'ResourceType=security-group,Tags=[{Key=Name,Value=multi-nic-sg}]' \ --query 'GroupId' --output text) # Allow SSH from anywhere aws ec2 authorize-security-group-ingress --group-id $SG_ID --protocol tcp --port 22 --cidr 0.0.0.0/0 # Allow all traffic within the security group aws ec2 authorize-security-group-ingress --group-id $SG_ID --protocol all --source-group $SG_ID

Step 2: Create Three ENIs
# ENI 1: DMZ Subnet ENI_DMZ=$(aws ec2 create-network-interface \ --subnet-id $SUBNET_DMZ \ --description "DMZ ENI" \ --groups $SG_ID \ --private-ip-address 10.0.1.10 \ --tag-specifications 'ResourceType=network-interface,Tags=[{Key=Name,Value=eni-dmz}]' \ --query 'NetworkInterface.NetworkInterfaceId' --output text) # ENI 2: App Subnet ENI_APP=$(aws ec2 create-network-interface \ --subnet-id $SUBNET_APP \ --description "App ENI" \ --groups $SG_ID \ --private-ip-address 10.0.2.10 \ --tag-specifications 'ResourceType=network-interface,Tags=[{Key=Name,Value=eni-app}]' \ --query 'NetworkInterface.NetworkInterfaceId' --output text) # ENI 3: DB Subnet ENI_DB=$(aws ec2 create-network-interface \ --subnet-id $SUBNET_DB \ --description "DB ENI" \ --groups $SG_ID \ --private-ip-address 10.0.3.10 \ --tag-specifications 'ResourceType=network-interface,Tags=[{Key=Name,Value=eni-db}]' \ --query 'NetworkInterface.NetworkInterfaceId' --output text)

✅ Verification Checklist:
□ Security group created with SSH access
□ 3 ENIs created in different subnets
□ Each ENI has a static private IP address

P7.3 Attach All Three ENIs

To a Single Instance
📖 Theory: ENI Attachment
An EC2 instance can have multiple ENIs, but the number is limited by the instance type. The primary ENI (eth0) is attached at launch; secondary ENIs can be attached to running or stopped instances.

Step 1: Launch the Instance
INSTANCE_ID=$(aws ec2 run-instances \ --image-id ami-0abcdef1234567890 \ --instance-type t3.medium \ --key-name MyKeyPair \ --network-interfaces "DeviceIndex=0,NetworkInterfaceId=$ENI_DMZ" \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=multi-nic-instance}]' \ --query 'Instances[0].InstanceId' --output text) aws ec2 wait instance-running --instance-ids $INSTANCE_ID

Step 2: Attach Secondary ENIs
# Attach App ENI (device index 1) aws ec2 attach-network-interface \ --network-interface-id $ENI_APP \ --instance-id $INSTANCE_ID \ --device-index 1 # Attach DB ENI (device index 2) aws ec2 attach-network-interface \ --network-interface-id $ENI_DB \ --instance-id $INSTANCE_ID \ --device-index 2

Step 3: Verify Attachment
aws ec2 describe-instances \ --instance-ids $INSTANCE_ID \ --query 'Reservations[0].Instances[0].NetworkInterfaces[*].[NetworkInterfaceId,PrivateIpAddress,Status]' \ --output table

✅ Verification Checklist:
□ Instance launched with DMZ ENI as primary
□ App and DB ENIs attached as secondary interfaces
□ All three ENIs show "in-use" status
🔗 P7.3 🖥️ t3.medium 🔌 3 ENIs

P7.4 Configure Policy-Based Routing

Inside the Instance
📖 Theory: Policy-Based Routing
When an instance has multiple ENIs, the Linux kernel uses the source IP address to determine which route table to use for outgoing traffic. This is called policy-based routing and requires creating separate routing tables for each interface.

Step 1: Connect to the Instance
PUBLIC_IP=$(aws ec2 describe-instances --instance-ids $INSTANCE_ID --query 'Reservations[0].Instances[0].PublicIpAddress' --output text) ssh -i MyKeyPair.pem ec2-user@$PUBLIC_IP

Step 2: Identify Network Interfaces
ip addr # Expected: eth0: 10.0.1.10, eth1: 10.0.2.10, eth2: 10.0.3.10

Step 3: Create Custom Route Tables
echo "100 dmz-table" | sudo tee -a /etc/iproute2/rt_tables echo "200 app-table" | sudo tee -a /etc/iproute2/rt_tables echo "300 db-table" | sudo tee -a /etc/iproute2/rt_tables

Step 4: Add Routes to Each Table
# DMZ routes sudo ip route add default via 10.0.1.1 dev eth0 table dmz-table sudo ip route add 10.0.0.0/16 dev eth0 table dmz-table # App routes sudo ip route add default via 10.0.2.1 dev eth1 table app-table sudo ip route add 10.0.0.0/16 dev eth1 table app-table # DB routes sudo ip route add default via 10.0.3.1 dev eth2 table db-table sudo ip route add 10.0.0.0/16 dev eth2 table db-table

Step 5: Add Source-Based Routing Rules
sudo ip rule add from 10.0.1.10 table dmz-table sudo ip rule add from 10.0.2.10 table app-table sudo ip rule add from 10.0.3.10 table db-table

Step 6: Configure ARP Filtering
echo "net.ipv4.conf.all.arp_filter = 0" | sudo tee -a /etc/sysctl.conf echo "net.ipv4.conf.all.arp_announce = 2" | sudo tee -a /etc/sysctl.conf sudo sysctl -p

⚠️ Important: ARP filtering must be configured correctly to ensure proper ARP responses for all interfaces. The primary ENI cannot be detached — only secondary ENIs can be migrated.
✅ Verification Checklist:
□ Custom route tables created
□ Routes added for each interface
□ Rules configured for source-based routing
□ ARP filtering configured
□ Persistence script created

P7.5 Test Connectivity

From Each Interface
📖 Theory: Testing Multi-NIC Connectivity
To verify that traffic from each interface follows the correct routing path, use curl with the --interface option to bind to a specific source IP.

Step 1: Test DMZ Interface (eth0)
curl --interface 10.0.1.10 https://api.ipify.org -w "\n" ip route get 8.8.8.8 from 10.0.1.10

Step 2: Test App Interface (eth1)
curl --interface 10.0.2.10 https://api.ipify.org -w "\n" --connect-timeout 5 ip route get 8.8.8.8 from 10.0.2.10

Step 3: Test DB Interface (eth2)
curl --interface 10.0.3.10 https://api.ipify.org -w "\n" --connect-timeout 5 ip route get 8.8.8.8 from 10.0.3.10

Step 4: View Routing Tables
ip rule show ip route show table dmz-table ip route show table app-table ip route show table db-table

Step 5: Test Internal Connectivity
ping -I eth0 -c 2 10.0.1.1 ping -I eth1 -c 2 10.0.2.1 ping -I eth2 -c 2 10.0.3.1

✅ Verification Checklist:
□ DMZ interface (eth0) can reach the internet
□ App interface (eth1) can reach the internet (if NAT configured)
□ DB interface (eth2) can reach the internet (if NAT configured)
□ All interfaces can ping their gateways

P7.6 Live ENI Migration

Detach and Attach to Another Instance
📖 Theory: Live ENI Migration
ENI migration is the process of detaching a secondary ENI from one instance and attaching it to another. Because the ENI carries its IP address, security groups, and MAC address with it, traffic is automatically redirected to the new instance without DNS changes.

Step 1: Create a Second Instance
INSTANCE_2=$(aws ec2 run-instances \ --image-id ami-0abcdef1234567890 \ --instance-type t3.medium \ --key-name MyKeyPair \ --subnet-id $SUBNET_DMZ \ --associate-public-ip-address \ --security-group-ids $SG_ID \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=migration-target}]' \ --query 'Instances[0].InstanceId' --output text) aws ec2 wait instance-running --instance-ids $INSTANCE_2

Step 2: Identify the Attachment ID
ATTACHMENT_ID=$(aws ec2 describe-network-interfaces \ --network-interface-ids $ENI_APP \ --query 'NetworkInterfaces[0].Attachment.AttachmentId' --output text)

Step 3: Detach the ENI
aws ec2 detach-network-interface --attachment-id $ATTACHMENT_ID aws ec2 wait network-interface-available --network-interface-ids $ENI_APP

Step 4: Attach to the Second Instance
aws ec2 attach-network-interface \ --network-interface-id $ENI_APP \ --instance-id $INSTANCE_2 \ --device-index 1

Step 5: Verify the Migration
aws ec2 describe-network-interfaces \ --network-interface-ids $ENI_APP \ --query 'NetworkInterfaces[0].[NetworkInterfaceId,PrivateIpAddress,Status,Attachment.InstanceId]' \ --output table PUBLIC_IP_2=$(aws ec2 describe-instances --instance-ids $INSTANCE_2 --query 'Reservations[0].Instances[0].PublicIpAddress' --output text) echo "Second Instance Public IP: $PUBLIC_IP_2"

💡 Key Insight: The primary ENI (eth0) cannot be detached — only secondary ENIs can be migrated. Both instances must be in the same Availability Zone and same VPC as the ENI.
✅ Verification Checklist:
□ Second instance launched successfully
□ ENI detached from first instance
□ ENI attached to second instance
□ IP address and configuration preserved
□ Connectivity verified after migration
🔄 P7.6 🔀 live migration ⚡ high availability

Key Takeaways

  • ENIs decouple networking from compute — you can move network configurations between instances without changing IP addresses.

  • Policy-based routing uses source IP addresses to determine which route table to use, enabling traffic from different ENIs to use different paths.

  • Live migration of ENIs allows for high availability without DNS changes or route table updates.

  • ARP filtering must be configured correctly to ensure proper ARP responses for all interfaces.

  • Security groups can be applied per ENI, providing fine-grained access control.

  • ENI limits depend on the instance type; larger instances support more ENIs.

  • The primary ENI cannot be detached — only secondary ENIs can be migrated.

  • Both instances must be in the same Availability Zone and same VPC for ENI migration.

  • Source/destination check must be disabled for NAT, routing, and firewall instances.

  • Automation: ENI migration can be automated within ASG lifecycle hooks for zero-downtime deployments.
