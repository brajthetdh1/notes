2.4 Local Zones and Wavelength Zones

2.4.1 AWS Local Zones
📖 What are AWS Local Zones?

AWS Local Zones are an extension of an AWS Region that place compute, storage, database, and other select AWS resources closer to large population and industrial centers. They are designed to run workloads that require single-digit millisecond latency to end users.

Think of a Local Zone as a satellite edge location of an AWS Region, located in a major metropolitan area, but still connected to the parent Region via a secure, high-bandwidth private network.
📡 Local Zones ⚡ single-digit ms 🌐 edge

When to Use Local Zones

Local Zones are ideal for workloads that require single-digit millisecond latency to users in a specific metropolitan area.

Common Use Cases:
  • 🎮 Real-time Gaming: Game servers that require low-latency connections for multiplayer experiences
  • 📹 Live Streaming: Video encoding and delivery for platforms like Twitch or YouTube
  • 🥽 AR/VR Applications: Augmented and virtual reality experiences that are latency-sensitive
  • 🖥️ Virtual Workstations: Graphics-intensive applications like CAD, video editing, and 3D rendering
  • 📊 ISV Application Acceleration: Independent Software Vendor applications requiring low-latency performance
  • 🔒 Data Residency: Meeting local data residency requirements for regulated industries like healthcare, finance, and government
  • ☁️ Hybrid Cloud Migrations: Gradually migrating traditional on-premises applications with low-latency dependencies
🎯 use cases 🎮 gaming 📹 streaming 🥽 AR/VR

Working with Local Zones

1. Enable the Local Zone
Local Zones must be opted in before use.
# Enable a Local Zone for your account aws ec2 modify-availability-zone-group \ --group-name us-west-2-lax-1 \ --opt-in-status opted-in

2. Create a Subnet
After opting in, create a subnet in the Local Zone within your VPC.
# Create subnet in Local Zone aws ec2 create-subnet \ --vpc-id vpc-12345678 \ --cidr-block 10.0.5.0/24 \ --availability-zone us-west-2-lax-1a

3. Launch Resources
Launch EC2 instances, EBS volumes, and other supported services in the Local Zone subnet.
# Launch EC2 instance in Local Zone aws ec2 run-instances \ --image-id ami-12345678 \ --instance-type t3.medium \ --subnet-id subnet-12345678 \ --key-name my-key

4. Network Border Groups
You allocate IP addresses from a Network Border Group when using Local Zones. A Network Border Group is a unique set of Availability Zones, Local Zones, or Wavelength Zones from which AWS advertises IP addresses.

⚠️ Key Rule: IP addresses cannot be moved between Network Border Groups.
Example: us-west-2-lax-1 is the Network Border Group for Los Angeles Local Zones.

AWS Wavelength Zones

2.4.2 AWS Wavelength Zones
What are AWS Wavelength Zones?

AWS Wavelength Zones enable developers to build applications that deliver ultra-low latency to 5G devices and end users. Wavelength deploys standard AWS compute and storage services inside telecommunications carriers' 5G networks.

This is a significant architectural shift: instead of data traveling from a 5G device all the way to the cloud region (which can take 50-100 ms), compute resources are placed at the edge of the 5G network — effectively inside the cellular tower's network.

When to Use Wavelength Zones

Wavelength Zones are designed for applications that require ultra-low latency to 5G devices and cannot tolerate the latency of a regional data center:

  • 🌐 IoT Devices: Real-time sensor data processing and control
  • 🎮 Game Streaming: Cloud gaming applications where latency is critical for user experience
  • 🚗 Autonomous Vehicles: Processing data from connected vehicles in real-time
  • 📹 Live Media Production: High-quality video processing and distribution
  • 🥽 Augmented Reality: AR experiences requiring immediate data processing
  • 🏭 Industrial Automation: Real-time control of manufacturing processes
  • 🔄 Edge Resiliency: Applications that require consistent data rates from mobile devices
🎯 use cases 🚗 autonomous 🎮 gaming
🏗️

Wavelength Architecture Best Practices

AWS recommends a hub-and-spoke model when using Wavelength Zones:

📍 In the Wavelength Zone (Spoke/Edge):
  • Run application components that need low latency and higher bandwidth over mobile networks
  • These are the latency-sensitive parts of your application

📍 In the Parent Region (Hub):
  • Components that are less latency-sensitive
  • Components that need to be shared across Zones (shared services)
  • Components that need to persist state, such as databases

⚠️ Important: State management should remain in the Region due to Wavelength Zones' ephemeral nature.
🏗️ hub-and-spoke 🔗 edge 🗄️ state
🔧

Working with Wavelength Zones

1. Opt In to the Zone
Wavelength Zones require opt-in.
# Opt in to a Wavelength Zone aws ec2 modify-availability-zone-group \ --group-name us-east-1-wl1-bos-wlz-1 \ --opt-in-status opted-in

2. Create a Subnet
After opting in, create a subnet in the Wavelength Zone within your VPC.
# Create subnet in Wavelength Zone aws ec2 create-subnet \ --vpc-id vpc-12345678 \ --cidr-block 10.0.100.0/24 \ --availability-zone us-east-1-wl1-bos-wlz-1

3. Create a Carrier Gateway
Unlike standard subnets, Wavelength Zones require a Carrier Gateway to enable inbound traffic from the carrier network and outbound traffic to the internet.
# Create carrier gateway for Wavelength Zone aws ec2 create-carrier-gateway \ --vpc-id vpc-12345678 \ --tag-specifications 'ResourceType=carrier-gateway,Tags=[{Key=Name,Value=wavelength-cgw}]'

4. Allocate Carrier IP Addresses
Allocate Carrier IP Addresses from the Network Border Group for your Wavelength Zone.
# Allocate carrier IP address aws ec2 allocate-address \ --domain vpc \ --network-border-group us-east-1-wl1-bos-wlz-1

5. Launch Resources
Launch EC2 instances, EBS volumes, and other supported resources in the Wavelength subnet.
# Launch EC2 instance in Wavelength Zone aws ec2 run-instances \ --image-id ami-12345678 \ --instance-type t3.medium \ --subnet-id subnet-12345678 \ --key-name my-key

Wavelength Considerations

  • 🌐 Network Access: Most Wavelength Zones have network access specific to a telecommunication carrier and location. You may need multiple Wavelength Zones to meet latency requirements.

  • 🔒 Compliance: Services in Wavelength Zones may have different compliance certifications than those in the parent Region.

  • 📦 Limited Service Availability: Not all AWS services are available in Wavelength Zones.

Key Takeaways

  • Local Zones extend AWS Regions closer to metropolitan areas for single-digit millisecond latency to local users.

  • Wavelength Zones place AWS infrastructure inside 5G carrier networks for ultra-low latency to 5G mobile devices.

  • Network Border Groups define IP address allocation boundaries; IPs cannot be moved between groups.

  • Enable before use: Both Local and Wavelength Zones require explicit opt-in before use.

  • Choose the right edge service:
    • Local Zones: Low-latency applications for metropolitan users (gaming, streaming, AR/VR, virtual workstations)
    • Wavelength: Ultra-low latency to 5G devices (autonomous vehicles, industrial IoT)
    • Outposts: Workloads that must remain on-premises

  • Wavelength requires a Carrier Gateway — unlike standard subnets, Wavelength subnets need a carrier gateway for inbound/outbound traffic.

  • Hub-and-spoke architecture is recommended for Wavelength — latency-sensitive components at the edge, stateful components in the Region.

Review Questions

Q1: What is the primary difference between an Availability Zone and a Local Zone?
Answer: A Local Zone is an AWS infrastructure extension that places compute and storage resources in geographic proximity to large metropolitan areas. While an Availability Zone provides full AWS services with <5 ms latency between zones, a Local Zone is designed for single-digit millisecond latency to local users and provides a subset of core AWS services. A Local Zone is managed by AWS and connected to the parent Region via a high-bandwidth private network.
Q2: What types of applications are best suited for AWS Local Zones?
Answer: AWS Local Zones are ideal for workloads requiring single-digit millisecond latency to end users. Common use cases include:
  • Real-time gaming servers
  • Live streaming and media processing
  • AR/VR applications
  • Virtual workstations (CAD, video editing, 3D rendering)
  • Applications requiring local data residency
Q3: What makes AWS Wavelength Zones different from Local Zones?
Answer: AWS Wavelength Zones are specifically designed for ultra-low latency to 5G devices. While Local Zones place AWS infrastructure in metropolitan data centers, Wavelength Zones place AWS infrastructure inside telecommunications carriers' 5G networks at the edge. This allows data to travel from the 5G device to the compute resource in under 10 milliseconds, enabling applications like autonomous vehicles, IoT devices, game streaming, and live media production.
Q4: What is a Carrier Gateway in Wavelength?
Answer: A Carrier Gateway serves two purposes in AWS Wavelength:
  • Allows inbound traffic from a carrier (telecom) network in a specific location
  • Allows outbound traffic to the carrier network and internet
It is a required component for Wavelength subnets to enable connectivity between the 5G network and your resources in the Wavelength Zone.
Q5: When should you use AWS Outposts instead of Local Zones?
Answer: AWS Outposts is designed for workloads that need to remain on-premises due to latency, data residency, or local data processing requirements, where a customer wants the workload to run seamlessly with the rest of their workloads in AWS. Outposts provides native AWS services on customer-owned infrastructure, while Local Zones are fully AWS-managed in AWS-owned facilities.
Q6: What is a Network Border Group and why is it important?
Answer: A Network Border Group is a unique set of Availability Zones, Local Zones, or Wavelength Zones from which AWS advertises public IP addresses. It defines the geographical boundary for IP address allocation:
  • Example: us-west-2-lax-1 is the Network Border Group for Los Angeles Local Zones
  • Key Rule: Once allocated, IP addresses cannot be moved between Network Border Groups
Q7: What is the recommended architecture pattern for Wavelength applications?
Answer: AWS recommends a hub-and-spoke architecture for Wavelength applications:
  • In the Wavelength Zone (Spoke/Edge): Latency-sensitive application components needing low latency and high bandwidth over mobile networks
  • In the Parent Region (Hub): Less latency-sensitive components, components that need to be shared across zones, and components that need to persist state (databases, etc.)
Key reason: State management should remain in the Region due to Wavelength Zones' ephemeral nature.
