Part A — Primary & Alternate Keys Identity: what makes a row a row

1

How do you choose a primary key?

Short Answer

A good primary key is unique, immutable, narrow, opaque, and generated outside the business domain. It is not a label for the business object — it is the physical address of the row and the anchor for every foreign key and index in the schema. Choose it for stability and width first, and for readability never.

Primary key selection is the highest-leverage decision in a schema, because it propagates. Every foreign key that references the table inherits the type and width. In MySQL/InnoDB, every secondary index physically embeds the primary key value, so a 36-byte UUID primary key inflates every index on the table by roughly 28 bytes per entry compared to an 8-byte integer. That is not a micro-optimisation; on a table with four secondary indexes and a billion rows it is tens of gigabytes of extra I/O.

The four properties that matter

  • Unique and non-null. Trivial, but the enforcement matters: a primary key constraint is the only way to guarantee a stable row identity, so it must be declared as a real constraint, not merely assumed unique in the application.
  • Immutable. If a key can change, every foreign key referencing it must cascade an update, and any cached or logged copy of the value becomes stale. The classic mistake is using an email address as the key: users change emails, and now a simple profile edit rewrites rows across half the schema.
  • Narrow and fixed-width. Width multiplies. An INTEGER (4 bytes) or BIGINT (8 bytes) is ideal. A VARCHAR(255) key is a design smell that will surface as index bloat and slower joins months later.
  • Opaque to the business. If the key carries meaning — an incrementing counter that reveals order volume, a region prefix that must change on migration — the business will eventually want to change it, and you cannot.

Storage-engine reality check

In InnoDB, the primary key is the clustered index: rows are physically stored in primary key order, and secondary indexes store the PK value as the row pointer. This has two consequences. First, inserting random UUIDs causes page splits throughout the B-tree, fragmenting the table and reducing fill factor. Second, wide keys blow up every index. In PostgreSQL, the heap is unordered and secondary indexes store the physical tuple ID (TID), so PK width matters far less for secondary index size — but the primary key index itself, and any join on it, still pays for width. In wide-column stores such as Cassandra, the partition key is the storage layout, so key choice determines query capability, not just performance.

What to avoid

  • Email, phone, SSN, or username as the primary key. All mutable, all personal data, all prone to duplicates and reformatting. Keep them as UNIQUE alternate keys.
  • Wide composite keys on entity tables. A junction table with two 8-byte FKs is fine. A five-column composite primary key on orders is not.
  • Using auto-increment values in public URLs. Sequential IDs enable enumeration: /orders/1001, /orders/1002. Use a separate opaque public identifier or a signed token for anything exposed to clients.
  • Assuming sequences are gapless. Sequences allocate outside the transaction, so rollbacks and crashes leave holes. Gaps are normal; invoice numbers are a business concern that needs its own transactional counter.
Interview Tip

When you declare a primary key in an interview, immediately justify the type: “I'll use an 8-byte surrogate here because this table is referenced by four other tables and I want the foreign keys narrow.” That single sentence demonstrates you understand PK propagation.

When do you use a natural key vs a surrogate key?

Short Answer

Use a surrogate key when the natural identifier is mutable, wide, personal, or externally assigned. Use a natural key when it is short, immutable, universally unique, and genuinely owned by the domain. In practice the right answer is almost always both: surrogate primary key plus a UNIQUE constraint on the natural key.

Definitions

A natural key is an attribute that exists in the business domain and happens to uniquely identify the entity: ISBN for a book, ISO 4217 code for a currency, IATA code for an airport, VAT number for a company. A surrogate key is a system-generated value with no business meaning: an auto-increment integer, a UUID, or a Snowflake ID.

When a natural key is the right call

  • Small, fixed reference data. A currencies table keyed on CHAR(3) ISO code is better than adding an integer surrogate — the code is what every query, report, and API already uses, and it will never change.
  • Standards-body identifiers with guaranteed immutability. ISO country codes, ISO currency codes, IATA airport codes are stable enough that the join is not a risk.
  • Junction tables. A composite natural key of the two participating foreign keys is idiomatic and adds no cost.
  • External identifiers you must look up by anyway. If every integration looks up a record by its external reference, storing that reference as the key removes an index and a join.

When a natural key is a trap

  • Mutable attributes. Email, phone number, username, company name, address. Any change forces cascading updates across every foreign key, and any forgotten copy — a cache, an event payload, a log — becomes silently stale.
  • Wide attributes. An email can be 254 characters. A URL can be longer. Every referencing table and every secondary index pays that width forever.
  • Personal data. Using an email or national ID as the key means the key itself is regulated PII. A GDPR erasure request forces you to rewrite a primary key, which is close to impossible at scale.
  • Externally assigned identifiers. A vendor's customer number is unique in the vendor's system but may collide with a second vendor's numbering, may be recycled, and may change when the integration changes. Treat it as an attribute with a unique index, not as the identity.
  • Identifiers that are not actually unique. SSNs have been reused; phone numbers get recycled; company registration numbers collide across jurisdictions.

The default pattern: surrogate PK + natural unique index

For entity tables, the standard design is:

ColumnRolePurpose
id BIGINTPrimary keyNarrow, immutable anchor for foreign keys
email VARCHARUnique alternate keyEnforces the business rule, used for lookups

This gives you narrow joins and stable references, while still enforcing the business invariant at the database layer. The only cost is an extra unique index on email, which you would need for login lookups anyway.

Trade-off

Surrogate keys hide business meaning, which is usually a feature but occasionally a problem: a report that joins eight tables to recover a human-readable name is annoying. The mitigation is to keep natural keys as unique alternate keys so they are always joinable — you lose nothing but one index.

Common Pitfall

Using a surrogate key instead of a unique constraint rather than in addition to it. If email is not declared UNIQUE, the application layer will eventually create two accounts with the same address under concurrent signup, and no amount of retry logic will fix it.

What are the trade-offs of auto-increment IDs vs UUIDs vs ULIDs/Snowflake IDs in distributed systems?

Short Answer

Auto-increment is compact and perfectly sequential but requires a single writer and cannot be generated client-side. UUIDv4 is coordination-free but random, which destroys B-tree locality and doubles key width. Time-ordered IDs — UUIDv7, ULID, Snowflake — give you coordination-free generation and sequential locality, and are the right default for distributed systems in 2025.

SchemeWidthOrdered?CoordinationMain Risk
Auto-increment4 / 8 BYes, perfectlyCentral sequenceSingle writer; enumeration leak
UUIDv416 BNo — randomNonePage splits, index bloat
UUIDv716 BYes, by timeNoneClock skew; still 16 B
ULID16 BYes, by timeNoneLexical order is case-sensitive in base32
Snowflake8 BYes, by timeMachine ID assignmentClock skew; 41-bit time horizon (~69 yrs)

Auto-increment: the locality champion

An INTEGER/BIGINT identity column is the cheapest possible key: 4–8 bytes, always increasing, so inserts always land at the right edge of the B-tree, filling pages sequentially and keeping the index dense. The cost is architectural. Generation requires a single authority — one sequence per database — so sharding requires per-shard offsets or composite keys, and client-side generation before the round trip is impossible. It also leaks volume: a competitor can infer your order volume from an order ID.

UUIDv4: coordination-free, locality-hostile

Random 128-bit values can be generated anywhere, including the browser, with zero coordination. The problem is that random inserts scatter across the entire B-tree. On InnoDB a million random inserts into a fresh table can produce a table 2–4× larger than the same data inserted sequentially, because page splits leave pages half-full and the working set no longer fits in the buffer pool. The WAL also grows faster because every scattered insert dirties a different page.

Time-ordered IDs: the modern default

UUIDv7 (RFC 9562) puts a 48-bit Unix millisecond timestamp in the high bits, followed by random bits. Sortable, index-friendly, generatable anywhere, no coordination. ULID is the same idea in Crockford base32, which makes it shorter when rendered as text. Snowflake (Twitter's design, and the basis of Instagram's and Discord's variants) packs a 41-bit timestamp, 10 bits of machine identity, and 12 bits of per-millisecond sequence into a 64-bit integer — half the width of a UUID and fully sortable.

How to choose

  • Single database, modest scale: auto-increment is still the best choice — simplest, narrowest, fastest.
  • Distributed, client-generated, no coordination needed: UUIDv7 or ULID. This is the default recommendation for new microservice schemas.
  • Compactness matters (high-volume indexes, embedded storage, binary protocols): Snowflake-style 64-bit IDs, accepting the machine-ID assignment burden.
  • Never: UUIDv4 as a clustered primary key on a write-heavy InnoDB table.
Trade-off

Sortable IDs leak creation time. A UUIDv7 or Snowflake ID embedded in a public URL reveals when the record was created and roughly how many records preceded it. If that is sensitive, keep an internal sortable key and expose a separate random public token.

How do you generate unique IDs across shards and regions?

Short Answer

Either eliminate coordination entirely (UUIDv7, ULID, or a composite of shard ID plus local sequence), or make coordination rare (block/segment allocation, Snowflake machine IDs). Never call a central authority on every insert — that reintroduces the single writer you sharded to escape.

Option 1 — No coordination at all

UUIDv7, ULID, and their relatives need no coordination because uniqueness is probabilistic across 74–122 bits of randomness. The probability of a collision with UUIDv7 is negligible at any realistic scale: you would need roughly 1018 IDs generated within the same millisecond for a meaningful chance. The trade-off is width (16 bytes) and the fact that ordering is only per-millisecond, not globally strict.

Option 2 — Composite key: shard ID + local sequence

If you already shard by a key, prefix it. A user in shard 7 gets ID (7, 100045). Uniqueness is structural, generation is local and cheap, and IDs are 12 bytes as a composite or 8 bytes packed as shard_id << 48 | local_id. The cost is that the consumer must know or be told the shard to look up the row — which is usually fine if the shard key is also the user ID, but painful if you need to fetch by ID alone.

Option 3 — Block / segment allocation

A central allocator hands out ranges rather than individual values. Each node requests 10,000 IDs, serves them from memory, and requests a new block when it runs low. This reduces coordination by four orders of magnitude and survives allocator outages for as long as the pre-allocated block lasts. The trade-off is that IDs are not globally ordered across nodes — node A might be issuing 10,000–19,999 while node B issues 20,000–29,999 — and a node restart wastes whatever remained in its block. Implementations: a database sequence with allocationSize (JPA/Hibernate default), Flickr's ticket server, or a table with UPDATE ... SET next = next + 10000 RETURNING.

Option 4 — Snowflake-style bit packing

A 64-bit value composed of timestamp(41) | datacenter(5) | machine(5) | sequence(12). Each node generates IDs independently, and uniqueness comes from the machine ID. This is the best compactness you can get with local generation. The complications are real:

  • Machine ID assignment must be coordinated — via config, environment variable, or a ZooKeeper/etcd lease. Duplicate machine IDs cause silent collisions, which are the worst kind of bug.
  • Clock skew breaks monotonicity. If a node's clock jumps backwards, it must refuse to generate until time catches up, or you get duplicates. Production implementations detect this and either wait or borrow the sequence field.
  • Time horizon. 41 bits of milliseconds is about 69 years from the epoch — fine, but worth documenting.

Multi-region specifics

Across regions, a central allocator adds cross-region latency to the write path, which is usually unacceptable. Two workable patterns: regional allocators (each region has its own sequence with a region prefix or a disjoint range), or coordination-free IDs (UUIDv7), which is why UUIDv7 is increasingly the default in multi-region services. If you need short human-friendly IDs across regions, a regional prefix plus a local sequence — EU-0001234 — is the pragmatic answer.

Common Pitfall

Confusing unique with monotonic. Global strict ordering requires coordination (or hybrid logical clocks) and is almost never needed. What applications actually need is per-entity ordering — messages in a conversation, events in an aggregate — which you get by using the entity's partition key plus a local sequence.

How do you design composite keys, and when are they better than surrogate keys?

Short Answer

Use a composite key when the natural identity of the row is the combination of its parts — junction tables, weak entities, multi-tenant tables, and time-series partitions. Use a surrogate key when the composite would be wide, mutable, or referenced by many other tables.

Where composite keys are the right answer

  • Junction tables. enrollments(student_id, course_id) with a composite primary key is correct and adds nothing. A surrogate enrollment_id here buys you almost nothing and costs an index.
  • Weak entities. order_lines(order_id, line_no) — the line is meaningless without its order, and the composite naturally expresses that dependency and enforces cascade deletion.
  • Multi-tenant tables. (tenant_id, id) makes tenant isolation structural and gives the query planner an obvious partition-pruning predicate on every query.
  • Time-series and wide-column stores. (device_id, bucket_time, sequence) — the first column is the partition key, the rest are clustering columns. This is the only way to query these systems efficiently.

Where composite keys hurt

  • Width propagation. In InnoDB, secondary indexes embed the primary key. A composite PK of two 16-byte UUIDs makes every secondary index 32 bytes wider per entry.
  • Foreign key ergonomics. Referencing a composite PK requires repeating all its columns in the child table. One FK becomes three columns. Two levels of nesting becomes six.
  • Application and ORM friction. Most ORMs handle single-column surrogate keys far more gracefully than composite keys, and composite-key handling often means custom repository code.
  • Mutation. A composite key cannot be partially updated without effectively deleting and reinserting the row.

Column order matters

For a B-tree composite index, order columns by equality filters first, then the range or sort column. For a composite primary key on a junction table, either order works for uniqueness, but the order determines which single-column prefix queries can use the index. For wide-column stores the order is semantic: the first column is the partition key and everything after is a clustering column. Getting this backwards is the single most common Cassandra data-modelling error.

The pragmatic hybrid

A defensible pattern for entity tables that need composite uniqueness: surrogate primary key for referential convenience, plus a composite UNIQUE constraint expressing the natural identity. For example, memberships with id BIGSERIAL PRIMARY KEY and UNIQUE(user_id, organization_id). You get narrow foreign keys and the invariant is enforced. The cost is one extra index — worth it if the table is referenced elsewhere.

Trade-off

The rule of thumb: composite PK when the row is a relationship or a dependent; surrogate PK when the row is an entity with an independent lifecycle. Junction tables and weak entities are the former. Customers and orders are the latter.

Part B — Uniqueness Under Adversity When the constraint has to hold across shards, deletes, and NULLs

How do you enforce uniqueness across shards?

Short Answer

A UNIQUE index is local to one node, so a hash-sharded table cannot enforce a global unique constraint on its own. The two reliable patterns are shard by the unique key (uniqueness becomes local) or maintain a dedicated lookup table sharded by that key. Everything else is a variation on those two.

The core problem

Suppose you shard users by user_id and need email to be globally unique. A unique index on (user_id, email) enforces nothing useful, because the uniqueness you need is on email alone. Checking with a SELECT before inserting is not safe: two concurrent signups for the same email both see zero rows, both insert, and you now have duplicates. This is the classic distributed uniqueness problem, and it is not solvable with application-level checks alone.

Pattern 1 — Shard by the unique key

If the only uniqueness requirement is email, shard the users table by a hash of the email. Now all rows with the same email land on the same shard, and a local UNIQUE(email) constraint is globally correct. This is the simplest and most robust solution, and it is what you should reach for first. Its limitation is obvious: you can only shard by one key. The moment you need uniqueness on both email and username, this pattern breaks.

Pattern 2 — Dedicated lookup tables

This is the standard answer to the two-unique-keys problem. Keep the main users table sharded by user_id, and add two small lookup tables:

TableShard keySchema
email_lookuphash(email)UNIQUE(email), user_id
username_lookuphash(username)UNIQUE(username), user_id

Because each lookup table is sharded by its own key, its unique constraint is globally valid. Signup becomes a sequence: reserve in email_lookup, reserve in username_lookup, then insert the user. Each reservation is an atomic insert that fails on conflict, so concurrent duplicates are impossible.

Pattern 3 — Conditional writes / lightweight transactions

Stores that support compare-and-set — DynamoDB's ConditionExpression, Cassandra's INSERT ... IF NOT EXISTS (implemented with Paxos), or a Redis SET NX — can enforce uniqueness on a single-key partition. These are effectively Pattern 1 plus an atomic primitive: the unique value becomes the partition key, and the conditional write is the constraint. Be aware that Cassandra LWTs are roughly four times slower than normal writes because they run a Paxos round, so they are fine for low-volume uniqueness checks (usernames) and wrong for high-volume counters.

Handling partial failures

With Pattern 2, a crash between the first reservation and the user insert leaves an orphaned reservation that permanently blocks that email. The standard mitigation is a reservation with a TTL: store a reserved_until timestamp, and have a background reaper delete expired reservations. Similarly, if the second reservation fails after the first succeeded, the transaction must compensate by deleting the first — the saga pattern, which Part 3 covers in detail.

What NewSQL buys you

CockroachDB, Spanner, and YugabyteDB implement distributed transactions underneath a normal UNIQUE constraint, so the problem simply disappears. The cost is latency: a cross-shard unique check in Spanner typically requires a round trip to a Paxos leader in a nearby region. That is often acceptable for a signup flow and never acceptable for a high-volume event stream.

Interview Tip

When the prompt has two unique attributes, immediately say “shard by one, maintain a lookup table for the other” and draw both. Candidates who try to enforce two unique constraints on one sharded table are usually stuck for the rest of the interview.

How do you design soft-delete uniqueness constraints?

Short Answer

A plain UNIQUE(email) plus soft deletes means a user can never re-register a deleted email. The clean fix is a partial (filtered) unique index restricted to live rows. Where partial indexes are unavailable — notably MySQL — emulate them with a generated column that is NULL for deleted rows, since multiple NULLs are permitted in a unique index.

Why teams soft delete

Soft delete replaces DELETE with UPDATE ... SET deleted_at = now(). Teams do it for undo windows, audit requirements, foreign-key preservation, and moderation workflows. It is a legitimate pattern, but it interacts badly with constraints because the row physically still exists — and a unique index sees it.

Solution 1 — Partial unique index (PostgreSQL, SQL Server)

Restrict the constraint to live rows:

EngineSyntax
PostgreSQLCREATE UNIQUE INDEX ON users(email) WHERE deleted_at IS NULL;
SQL ServerCREATE UNIQUE INDEX ix ON users(email) WHERE deleted_at IS NULL;
SQLiteCREATE UNIQUE INDEX ix ON users(email) WHERE deleted_at IS NULL;

This is the correct design when the engine supports it: the index is smaller, the intent is explicit, and re-registration works naturally.

Solution 2 — Generated column with NULLs (MySQL)

MySQL has no partial indexes, but it treats multiple NULLs as distinct in a unique index. So make the indexed value NULL whenever the row is deleted:

StepDDL
Add generated columnactive_email VARCHAR(255) AS (IF(deleted_at IS NULL, email, NULL)) STORED
Unique indexUNIQUE KEY ux_active_email (active_email)

Live rows carry the real email and collide correctly. Deleted rows all carry NULL, and any number of NULLs coexist. The cost is a stored generated column (extra disk) and the fact that restoring a soft-deleted row can now fail if the email was re-registered in the meantime — which is usually the correct behaviour, but should be surfaced as a real error in the UI.

Solution 3 — Mutate the value on delete

On soft delete, rewrite the unique column to something like deleted+{id}@invalid.local. This works on every engine and requires no schema change beyond the delete logic, but it destroys the original value unless you copy it to an archive column, and it makes restore non-trivial. It also breaks any audit requirement to preserve the exact prior state.

Solution 4 — Archive table on delete

Move the row to users_archive and delete it from the live table. The live unique constraint is then trivially correct and small, and the archive can be queried separately. This is the cleanest design conceptually, but it complicates every read path that needs to consider deleted users (support tools, audit, foreign keys pointing at the row).

The hidden cost of soft delete

Whatever uniqueness approach you choose, soft delete imposes a tax on every query: each one must remember WHERE deleted_at IS NULL. One forgotten predicate leaks deleted rows into a UI or a report. The mitigations are a database view exposing only live rows, row-level security policies that filter automatically, or — best — an ORM-layer default scope that makes the filter opt-out rather than opt-in.

Compliance Note

Soft delete is not a substitute for erasure. A GDPR "right to be forgotten" request generally requires actually deleting the personal data, and keeping it in a deleted_at row may itself be a violation. Design a hard-delete path for erasure requests, distinct from the user-facing soft delete.

How do you handle NULL semantics in unique constraints and indexes?

Short Answer

In SQL, NULL means "unknown", so NULL = NULL is unknown, not true. Most engines therefore allow unlimited duplicate NULLs in a unique index — silently defeating the constraint you thought you had. SQL Server is the notable exception: it permits exactly one NULL. Know which engine you are on, and prefer NOT NULL with explicit sentinels.

The rules, per engine

EngineNULLs in a UNIQUE indexNotes
PostgreSQLMultiple allowedUNIQUE NULLS NOT DISTINCT since PG 15
MySQL / MariaDBMultiple allowedNo partial indexes; use generated columns
OracleMultiple allowedNullable-column workarounds common before 23c
SQL ServerExactly oneFiltered indexes are the standard workaround
SQLiteMultiple allowedMatches the standard

The bug this causes

Consider UNIQUE(tenant_id, email) where tenant_id is nullable for platform-level accounts. Three rows with (NULL, 'a@b.com') all pass, because each comparison involves an unknown. The constraint looks correct in the DDL and silently fails in production. The same thing happens with a nullable external_id in an idempotency table: duplicate webhook deliveries insert duplicates because the deduplication key contains a NULL.

The fixes

  • Make the columns NOT NULL. The overwhelmingly correct answer. A nullable column in a unique key is almost always a modelling error — "tenant unknown" should be an explicit sentinel row, not NULL.
  • UNIQUE NULLS NOT DISTINCT (PostgreSQL 15+) makes NULL behave like an ordinary value for uniqueness purposes. Clean, but not portable.
  • Expression index with COALESCE: CREATE UNIQUE INDEX ON t (tenant_id, COALESCE(email,'')). Portable across most engines; costs an expression index.
  • Filtered index on the NOT NULL subset when the semantics genuinely allow many unknowns: CREATE UNIQUE INDEX ON t(id) WHERE id IS NOT NULL.
  • Sentinel values instead of NULL — 0 for a numeric FK, '' for a string. This is what SQL Server forces on you by allowing only one NULL. Document the sentinel loudly; it is a footgun if anyone writes real data equal to it.

NULLs elsewhere in the schema

  • Foreign keys. A NULL FK is not checked — it represents an optional relationship. That is usually what you want, but it means an optional FK cannot be used to guarantee referential integrity of a required relationship.
  • NOT IN with a NULL. x NOT IN (1, 2, NULL) evaluates to unknown for every row, so the query returns zero rows. This is one of the most common silent SQL bugs; use NOT EXISTS instead.
  • Aggregates. COUNT(col) skips NULLs while COUNT(*) does not; SUM, AVG, and MIN ignore them. A report that averages a nullable column silently excludes incomplete records.
  • DISTINCT and GROUP BY treat all NULLs as a single group, even though they are not equal under =. This inconsistency is a standards quirk, not a bug, and it is worth knowing.
  • Sort order. PostgreSQL sorts NULLs last by default for ASC; Oracle sorts them first. Pagination logic that assumes an order breaks on the boundary.
Design Guidance

Default to NOT NULL everywhere, with an explicit default or sentinel where "not yet known" is a genuine state. Reserve true NULL for optional relationships and genuinely absent optional attributes. When a nullable column participates in a unique key, treat it as a bug until proven otherwise — and write a test that inserts two rows with NULL and asserts the constraint fires.
