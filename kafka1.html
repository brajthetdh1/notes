Q1: What is Apache Kafka?

Basics
What is Apache Kafka, and what are its key components?

Apache Kafka is a distributed, partitioned, replicated commit log service. It provides a unified, high-throughput, low-latency platform for handling real-time data feeds.

Key Components:

  • Broker: A Kafka server that stores data and serves client requests.
  • Topic: A logical channel where messages are published.
  • Partition: A physical division of a topic for parallel processing.
  • Producer: A client that publishes messages to topics.
  • Consumer: A client that reads messages from topics.
  • Consumer Group: A group of consumers that work together to consume from a topic.
  • ZooKeeper (legacy): Coordination service for brokers.
  • KRaft (new): Kafka's internal consensus protocol replacing ZooKeeper.

Kafka is not just a message queue: It's a distributed streaming platform for building real-time data pipelines and applications.

Q2: Kafka Use Cases

Basics
What are the main use cases for Apache Kafka?
  • Event Streaming & Analytics: Real-time processing of events (clickstreams, IoT data).
  • Messaging System: Decoupling microservices with reliable messaging.
  • Log Aggregation: Collecting logs from multiple services into a central location.
  • Stream Processing: Real-time transformations, aggregations (Kafka Streams).
  • Change Data Capture (CDC): Capturing database changes and propagating them.
  • Data Integration: Building data pipelines between systems (Kafka Connect).
  • Asynchronous Communication: Reliable, fault-tolerant communication between services.
  • Event Sourcing: Storing state changes as a sequence of events.

Key benefit: Kafka's durability, scalability, and high throughput make it suitable for these use cases.

Q4: Key Features of Kafka

Basics
What are the key features of Kafka that make it suitable for real-time data processing?
  • High Throughput: Can handle millions of messages per second.
  • Low Latency: Sub-second message delivery.
  • Scalability: Horizontally scalable by adding more brokers.

Q5: Kafka Broker

Basics
What is a Kafka Broker and what is its role in the cluster?

A Kafka Broker is a server that runs Kafka and stores data. Brokers are the building blocks of a Kafka cluster.

Roles of a Broker:

  • Data Storage: Stores partitions and their replicas on disk.
  • Message Handling: Receives messages from producers and serves consumers.
  • Partition Leadership: One broker is the leader for each partition.
  • Replication: Maintains replicas of partitions for fault tolerance.
  • Metadata Management: Maintains cluster metadata (topics, partitions, etc.).
  • Coordination: Works with ZooKeeper/KRaft for cluster coordination.

Cluster: Multiple brokers work together to provide scalability and fault tolerance.

# Typical broker configuration
broker.id=1
listeners=PLAINTEXT://:9092
log.dirs=/var/lib/kafka/data
default.replication.factor=2

Q6: Kafka Topic

Basics
What is a Kafka Topic and how does it work?

A Topic is a logical channel in Kafka where messages are published. It is analogous to a table in a database or a folder in a file system.

How it works:

  • Topics are divided into partitions for parallel processing.
  • Each message has a key and a value.
  • Messages are appended to partitions in order.
  • Topics are replicated across brokers for fault tolerance.
  • Topics can have retention policies (time or size-based).
# Create a topic
bin/kafka-topics.sh --create \
  --topic orders \
  --partitions 3 \
  --replication-factor 2 \
  --bootstrap-server localhost:9092

Naming convention: Use descriptive names like user-events, order-created.

Q7: Partitions

Basics
What is the role of Partitions in Kafka?

Partitions are the physical divisions of a topic. They enable parallel processing and scalability.

Key roles:

  • Parallelism: Multiple consumers can read from different partitions simultaneously.
  • Scalability: Partitions can be distributed across brokers.
  • Ordering: Messages within a partition are strictly ordered.
  • Load Balancing: Partitions are distributed across brokers for even load.
// Partition assignment
// Topic: orders (3 partitions)
// Partition-0: messages 0, 3, 6, ...
// Partition-1: messages 1, 4, 7, ...
// Partition-2: messages 2, 5, 8, ...

Important: The number of partitions determines the maximum parallelism of consumers.

Best practice: Choose the number of partitions based on expected throughput and consumer count.

Q8: Offset

Basics
What is an Offset in Kafka and why is it important?

An offset is a unique identifier assigned to each message within a partition. It represents the position of a message in the partition.

Why it's important:

  • Consumer Position: Consumers use offsets to track which messages they've consumed.
  • Replayability: Consumers can reset offsets to re-read messages.
  • Ordering: Offsets ensure the order of messages within a partition.
  • Durability: Offsets are stored in __consumer_offsets topic.
// Offset example
// Partition 0: [msg0: offset0, msg1: offset1, msg2: offset2]
// Consumer commits offset after processing message 1 → commits offset 2

Offset types:

  • Current offset: The last committed offset for a consumer.
  • High-water mark: The offset of the last message available.
  • Log end offset: The next offset to be written.

Q11: Kafka Architecture

Architecture
Explain the overall architecture of Kafka with all its components.

Kafka Architecture consists of:

  • Brokers: Kafka servers that store data and serve requests.
  • Topics: Logical channels for messages.
  • Partitions: Physical divisions of topics.
  • Producers: Publish messages to topics.
  • Consumers: Read messages from topics.
  • Consumer Groups: Groups of consumers that share load.
  • ZooKeeper/KRaft: Coordination and metadata management.
  • Storage: Messages are persisted to disk in log segments.
  • Replication: Partitions are replicated across brokers.
// Architecture flow
Producer → Broker (Leader) → Partition → Replication → ISR
Consumer ← Broker (Leader or Follower) ← Partition

Key design: Kafka is designed as a distributed commit log where messages are appended sequentially to partitions.

Q12: ZooKeeper

Architecture
What is the role of ZooKeeper in a Kafka cluster?

ZooKeeper (legacy) is a distributed coordination service used by Kafka for cluster management.

Roles:

  • Broker Metadata: Maintains the list of brokers in the cluster.
  • Topic Metadata: Stores topic configurations and partition information.
  • Leader Election: Elects leaders for partitions.
  • Controller Election: Elects the controller broker.
  • Consumer Offsets: Previously stored consumer offsets (now in __consumer_offsets topic).
  • Cluster Health: Monitors broker health via heartbeats.
# ZooKeeper ensemble
zookeeper.connect=zk1:2181,zk2:2181,zk3:2181

Important: Kafka 2.8+ introduced KRaft to replace ZooKeeper, removing the external dependency.

Q13: KRaft

Architecture
Can Kafka run without ZooKeeper? What is KRaft?

Yes, Kafka can run without ZooKeeper using KRaft (Kafka Raft).

KRaft (Kafka Raft):

  • An internal consensus protocol that replaces ZooKeeper.
  • Built on the Raft algorithm for distributed consensus.
  • Simplifies cluster management by removing the external dependency.
  • Moves metadata management inside Kafka.
  • Improves scalability and reduces operational overhead.
# KRaft configuration (no ZooKeeper)
process.roles=broker,controller
node.id=1
controller.quorum.voters=1@localhost:9093
log.dirs=/var/lib/kafka/data

Benefits: Simpler deployment, better performance, and easier management.

Status: KRaft is production-ready in Kafka 3.x versions.

Q14: Consumer Group

Architecture
What is a Consumer Group and how does it work?

A Consumer Group is a set of consumers that work together to consume messages from a topic. Each consumer in the group reads from a subset of partitions.

How it works:

  • Each partition is assigned to exactly one consumer in the group.
  • If there are more consumers than partitions, some consumers will be idle.
  • Consumer groups enable parallel processing of messages.
  • Offsets are committed per partition within the group.
// Consumer group configuration
props.put("group.id", "order-processors");
props.put("auto.offset.reset", "earliest");

Benefits:

  • Scalable consumption across multiple instances.
  • Fault tolerance (if a consumer fails, partitions are reassigned).
  • Exactly-once processing within the group.

Q15: Message Ordering

Architecture
How does Kafka ensure message ordering within a partition?

Kafka guarantees that messages within a single partition are delivered in the exact order they were produced.

How it works:

  • Messages are appended to the partition log in sequential order.
  • Each message gets a monotonically increasing offset.
  • Consumers read messages in offset order.
  • If a consumer processes multiple partitions, order is not guaranteed across partitions.
// To ensure order for related messages
// Use the same key for messages that need to be ordered
producer.send(new ProducerRecord<>("topic", "orderId123", "msg1"));
producer.send(new ProducerRecord<>("topic", "orderId123", "msg2"));
// Both messages will go to the same partition

Key point: To preserve order across messages, use the same key or single partition.

Q16: Leader & Follower

Architecture
Explain the concept of Leader and Follower in Kafka partitions.

In Kafka, each partition has a Leader and one or more Followers.

  • Leader: Handles all read and write requests for the partition.
  • Followers: Replicate the leader's data asynchronously.
  • Followers do not serve client requests (they act as backups).
  • If the leader fails, a follower becomes the new leader (leader election).
// Partition leadership
// Partition 0: Broker 1 (Leader), Broker 2 (Follower), Broker 3 (Follower)
// All writes go to Broker 1, replicated to Broker 2 & 3

Advantages:

  • Fault Tolerance: Data is replicated across multiple brokers.
  • High Availability: If a broker fails, a follower takes over.
  • Load Balancing: Leaders are distributed across brokers.

Q17: ISR (In-Sync Replica)

Architecture
What is an ISR (In-Sync Replica) and why is it important?

ISR (In-Sync Replica) is the set of followers that are fully caught up with the leader in terms of replication.

Why it's important:

  • Only ISR members can become the new leader.
  • Producers can choose to wait for acknowledgments from ISR members (acks=all).
  • ISR ensures data durability and consistency.
  • If a follower falls behind, it is removed from the ISR.
// ISR configuration
// Broker 1: Leader (in ISR)
// Broker 2: Follower (in ISR) - caught up
// Broker 3: Follower (not in ISR) - lagging

Key parameters:

  • replica.lag.time.max.ms – maximum time a follower can lag.
  • min.insync.replicas – minimum number of ISR replicas for write acknowledgment.

Q18: Leader Election

Architecture
How does leader election work in Kafka?

Leader election is the process of selecting a new leader for a partition when the current leader fails.

Process:

  • The Controller broker detects leader failure via ZooKeeper/KRaft.
  • The controller selects a new leader from the ISR (In-Sync Replicas).
  • If no ISR replicas are available, the controller may choose any replica (with unclean.leader.election.enable=true).
  • The new leader is elected and notified to all brokers.
// Leader election flow
1. Broker 1 (leader) fails
2. Controller detects failure
3. Controller selects Broker 2 (in ISR) as new leader
4. Broker 2 becomes the new leader for the partition

Important: If unclean.leader.election.enable=false, the partition remains unavailable until an ISR broker is available.

Q19: Replication Factor

Architecture
What is the replication factor and how does it affect fault tolerance?

The replication factor is the number of copies of each partition across different brokers in the cluster.

Effects:

  • Fault Tolerance: Higher replication factor means better fault tolerance. If RF = 3, up to 2 brokers can fail.
  • Availability: With min.insync.replicas = 2, at least 2 replicas must be available for writes.
  • Storage: Higher RF increases storage requirements (RF× data size).
  • Performance: Higher RF increases network traffic and latency due to replication.
# Recommended settings
default.replication.factor=3 # For production
min.insync.replicas=2 # For data durability

Best practice: Use RF=3 for production and RF=1 for development.

Q20: Partition Distribution

Architecture
How does Kafka distribute partitions across brokers?

Kafka distributes partitions using a round-robin strategy with rack awareness.

Distribution algorithm:

  • Partitions are distributed evenly across brokers.
  • Replicas are placed on different brokers and different racks (if configured).
  • The Controller manages partition assignment.
// Example: 3 brokers, 6 partitions, RF=2
// Broker 1: Partition 0 (Leader), Partition 3 (Follower)
// Broker 2: Partition 1 (Leader), Partition 4 (Follower)
// Broker 3: Partition 2 (Leader), Partition 5 (Follower)
// Replicas: Partition 0 (Broker 1, Broker 2), Partition 1 (Broker 2, Broker 3), etc.

Rack awareness: Kafka can distribute replicas across different racks for better fault tolerance.

Q21: Kafka Producer

Producers
What is a Kafka Producer and how does it work?

A Kafka Producer is a client that publishes messages to Kafka topics.

How it works:

  • Create Record: Build a ProducerRecord with topic, key, value, and optionally partition.
  • Partition Assignment: The producer determines the partition (by key or round-robin).
  • Serialization: Serializes key and value (with configured serializers).
  • Buffering: Messages are batched for efficiency (batch.size and linger.ms).
  • Send: Messages are sent asynchronously to the broker.
  • Acknowledgment: Producer waits for acknowledgment (acks configuration).
// Producer configuration
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("acks", "all");
props.put("retries", 3);

Q22: Partition Assignment

Producers
How is a partition determined for a message?

The partition for a message is determined using the following order:

  1. If partition is specified: Uses that partition.
  2. If a key is provided: Uses hash(key) % numPartitions.
  3. If no key and no partition: Uses round-robin or sticky partitioner.
// Partition assignment
// Same key → same partition → ordered messages
producer.send(new ProducerRecord<>("topic", "user123", "msg1"));
producer.send(new ProducerRecord<>("topic", "user123", "msg2"));
// Both messages go to the same partition

Partitioner: Kafka uses DefaultPartitioner (sticky partitioning) or custom partitioners.

Sticky Partitioner: Batches messages to the same partition for efficiency.

Q23: Custom Partitioner

Producers
What is a custom partitioner and when would you use one?

A custom partitioner allows you to define your own logic for determining the partition of a message.

When to use:

  • Data Locality: Route messages to specific partitions for processing.
  • Custom Routing: Based on domain-specific logic.
  • Load Balancing: More advanced load balancing than default hash.
class CustomPartitioner implements Partitioner {
    public int partition(String topic, Object key, byte[] keyBytes,
        Object value, byte[] valueBytes, Cluster cluster) {
        // Custom logic based on key or value
        String keyStr = (String) key;
        if (keyStr.startsWith("high_priority")) {
            return 0; // dedicated partition
        }
        return Math.abs(key.hashCode()) % numPartitions;
    }
}

Implementation: Implement the Partitioner interface and set partitioner.class.

Q24: Producer Acknowledgments

Producers
What are producer acknowledgments (acks) and what are the different levels?

Producer acknowledgments (acks) define how many replicas must acknowledge the write before the producer considers it successful.

ValueDescriptionDurability
acks=0No acknowledgment (fire-and-forget)Lowest (data loss possible)
acks=1Leader acknowledgesMedium (data loss if leader fails)
acks=allAll ISR replicas acknowledgeHighest (no data loss)
// acks configuration
props.put("acks", "all"); // Strongest durability
props.put("acks", "1"); // Leader acknowledgment
props.put("acks", "0"); // Fire-and-forget

Trade-offs:

  • Performance: acks=0 is fastest, acks=all is slowest.
  • Data Loss: acks=0 has the highest risk, acks=all has the lowest.
  • Latency: acks=all has higher latency due to replication.

Q26: Delivery Semantics

Producers
What are the different delivery semantics in Kafka?
  • At-most-once (acks=0): Messages may be lost, but are never delivered more than once. Fastest, least reliable.
  • At-least-once (acks=1/all): Messages are never lost, but may be delivered more than once. Most common, requires idempotent processing.
  • Exactly-once: Messages are delivered exactly once. Requires idempotent producers and transactions.
SemanticLossDuplicatesUse Case
At-most-oncePossibleNot possibleLogs, metrics
At-least-onceNot possiblePossibleMost use cases
Exactly-onceNot possibleNot possibleFinancial transactions

Choice depends on: Business requirements, performance needs, and processing idempotence.

Q27: Exactly-Once Semantics

Producers
How do you achieve exactly-once semantics in Kafka?

Exactly-once semantics require a combination of features:

  • 1. Idempotent Producer: Ensures no duplicates in the same producer session.
  • 2. Transactions: Atomic writes across multiple partitions and topics.
  • 3. Consumer Isolation: Consumers read only committed messages.
// Producer configuration for exactly-once
props.put("enable.idempotence", true);
props.put("acks", "all");
props.put("max.in.flight.requests.per.connection", 1);
props.put("transactional.id", "my-transactional-id");

Consumer side:

  • Set isolation.level=read_committed to read only committed messages.
  • Use transactional APIs for produce-consume operations.

Note: Exactly-once adds overhead but guarantees data integrity.

Q28: Idempotent Producer

Producers
What is an idempotent producer and how does it work?

An idempotent producer ensures that messages are delivered exactly once, even if retries occur.

How it works:

  • Each message has a unique sequence number per partition.
  • The broker tracks the last sequence number for each producer.
  • If a duplicate message is received (same sequence number), the broker ignores it.
  • This prevents duplicates from retries.
// Enable idempotence
props.put("enable.idempotence", true); // Automatically sets acks=all and retries

Requirements:

  • acks=all (must be set).
  • max.in.flight.requests.per.connection ≤ 5 (default).
  • retries > 0 (default is Integer.MAX_VALUE).

Benefits: Simpler exactly-once processing without manual deduplication.

Q29: Transactional API

Producers
What is the transactional API in Kafka?

The Transactional API allows producers to send messages atomically across multiple partitions and topics.

Features:

  • Messages are atomic – all or nothing.
  • Enables exactly-once semantics.
  • Supports consume-transform-produce patterns.
  • Consumers can read only committed messages (read_committed).
// Transactional producer
producer.initTransactions();
producer.beginTransaction();
try {
    producer.send(record1);
    producer.send(record2);
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}

Key components:

  • transactional.id – unique producer ID for transaction coordination.
  • initTransactions() – initialize the producer.
  • beginTransaction() – start a transaction.
  • commitTransaction() – commit the transaction.
  • abortTransaction() – abort the transaction.

Q30: linger.ms & batch.size

Producers
What is linger.ms and batch.size in producer configuration?

These are producer performance tuning parameters:

  • batch.size: Maximum size of a batch in bytes. When a batch reaches this size, it is sent immediately.
  • linger.ms: Maximum time to wait before sending a batch. The producer waits for more messages to fill the batch.
props.put("batch.size", 16384); // 16 KB
props.put("linger.ms", 5); // 5 ms

Impact:

  • Higher batch.size: Better throughput, but more memory usage.
  • Higher linger.ms: More batching, lower throughput, higher latency.
  • Trade-off: Latency vs. throughput.
// Scenario: High throughput with acceptable latency
// batch.size = 64KB, linger.ms = 10ms

Q31: Kafka Consumer

Consumers
What is a Kafka Consumer and how does it work?

A Kafka Consumer is a client that reads messages from Kafka topics.

How it works:

  • Subscribe: Consumer subscribes to one or more topics.
  • Poll: Consumer polls for messages (poll() method).
  • Deserialize: Deserializes key and value with configured deserializers.
  • Process: Processes the received records.
  • Commit: Commits offsets to track progress.
// Consumer configuration
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "my-group");
props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
props.put("auto.offset.reset", "earliest");

Q32: Offset Commit

Consumers
How do consumers commit offsets? What is the difference between commitSync() and commitAsync()?

Offset commit is the process of storing the consumer's position in a partition.

  • commitSync(): Synchronous commit. Waits for the broker to acknowledge. Retries on failure.
  • commitAsync(): Asynchronous commit. Non-blocking. Provides a callback on completion.
// commitSync() – blocking
consumer.commitSync();

// commitAsync() – non-blocking
consumer.commitAsync((offsets, exception) -> {
    if (exception != null) {
        System.out.println("Commit failed: " + exception);
    }
});

Best practice: Use commitSync() in the final commit (e.g., before shutdown) and commitAsync() for regular commits.

Important: Offsets are stored in the __consumer_offsets topic.

Q33: auto.offset.reset

Consumers
What is auto.offset.reset and what are its possible values?

auto.offset.reset determines what a consumer does when there is no committed offset (first start) or when the offset is invalid.

Possible values:

  • earliest: Start from the beginning of the partition (oldest messages).
  • latest: Start from the end of the partition (newest messages).
  • none: Throw an exception if no offset is available.
props.put("auto.offset.reset", "earliest"); // replay all messages
props.put("auto.offset.reset", "latest"); // skip older messages

Use cases:

  • earliest: When you want to process all historical data.
  • latest: When you only care about new messages.
  • none: When you want to be explicit about offset management.

Important: The consumer can also manually seek to specific offsets using seek().

Q34: Consumer Lag

Consumers
What is consumer lag and how do you monitor it?

Consumer lag is the difference between the latest offset in a partition and the consumer's current committed offset. It represents the backlog of messages waiting to be consumed.

How to monitor:

  • Kafka CLI: kafka-consumer-groups.sh --describe --group my-group
  • Metrics: JMX metrics (e.g., kafka.consumer:type=consumer-fetch-manager-metrics).
  • Tools: Burrow, Confluent Control Center, Prometheus + Grafana.
# Check consumer lag
bin/kafka-consumer-groups.sh --describe --group my-group --bootstrap-server localhost:9092

# Example output:
# TOPIC PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG
# topic1 0 100 150 50

Why monitor lag?

  • Detect consumer issues (slow processing, failures).
  • Ensure timely processing of messages.
  • Scale consumers when lag grows.

Q35: Rebalancing

Consumers
How does rebalancing work in consumer groups?

Rebalancing is the process of reassigning partitions among consumers in a group when membership changes.

When rebalancing occurs:

  • A new consumer joins the group.
  • A consumer leaves the group (failure or shutdown).
  • The topic partition count changes.

Rebalancing process:

  • Revocation: Partitions are revoked from existing consumers.
  • Assignment: The group coordinator re-assigns partitions.
  • Partition Assignment Strategy: Range, RoundRobin, Sticky, Cooperative.
// Partition assignment strategies
props.put("partition.assignment.strategy", "org.apache.kafka.clients.consumer.RangeAssignor");

Impact:

  • During rebalancing, consumers may pause processing (stop-the-world).
  • Use Cooperative Sticky strategy for incremental rebalancing (less disruption).

Q36: Consumer Failure

Consumers
What happens when a consumer fails while processing a message?

When a consumer fails:

  • The consumer stops sending heartbeats to the group coordinator.
  • The coordinator detects the failure (session timeout).
  • A rebalance is triggered.
  • Partitions are reassigned to other consumers in the group.

Message processing state:

  • If the failure occurs after processing but before offset commit, the message may be reprocessed (at-least-once).
  • If the failure occurs before processing, the message will be assigned to another consumer.
// Session timeout configuration
props.put("session.timeout.ms", 30000); // 30 seconds
props.put("heartbeat.interval.ms", 3000); // 3 seconds

Best practices:

  • Use idempotent processing to handle duplicate messages.
  • Implement proper error handling and retries.
  • Consider using dead letter queues for unrecoverable failures.

Q37: Message Ordering with Consumers

Consumers
How do you ensure that messages are processed in the order they were produced?

To maintain order:

  • Same Partition: All related messages must go to the same partition (using the same key).
  • Single Consumer: Only one consumer processes that partition.
  • Sequential Processing: The consumer processes messages in offset order within the partition.
// Ensure order for a user's events
// Producer: use user_id as key
producer.send(new ProducerRecord<>("events", "user123", "event1"));
producer.send(new ProducerRecord<>("events", "user123", "event2"));
// Both messages go to the same partition
// Consumer processes them in order

Challenges:

  • Parallel Processing: Multiple consumers processing different partitions don't preserve order across partitions.
  • Consumer Rebalancing: Order is preserved within the partition, but partition reassignment may cause gaps.

Solution: Use Single Partition or Key-based partitioning for ordered processing.

Q38: Reprocess Historical Messages

Consumers
How can consumers reprocess historical messages?

Consumers can reprocess historical messages by resetting offsets.

Methods:

  • 1. auto.offset.reset: Set to earliest for new consumers to start from the beginning.
  • 2. seek() method: Programmatically set the offset for a partition.
  • 3. Command-line: kafka-consumer-groups.sh --to-earliest or --to-offset.
// Using seek()
consumer.assign(Arrays.asList(partition));
consumer.seekToBeginning(partition);
// or
consumer.seek(partition, 0); // start from offset 0
# Command-line reset
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group my-group --topic my-topic --to-earliest --execute

Important: Resetting offsets affects all consumers in the group.

Q39: Partitions vs Consumers

Consumers
What is the relationship between the number of partitions and the number of consumers in a group?

Rule: Each partition is assigned to exactly one consumer in a group.

  • Consumers ≤ Partitions: All consumers are active, processing partitions.
  • Consumers > Partitions: Extra consumers are idle.
// Examples
// 3 partitions, 3 consumers → each consumer gets 1 partition
// 3 partitions, 2 consumers → one consumer gets 2 partitions, other gets 1
// 3 partitions, 5 consumers → 2 consumers are idle

To scale consumption:

  • Increase the number of partitions to match the desired parallelism.
  • Add more consumers (up to the number of partitions).

Best practice: Plan for future growth by setting partitions higher than the initial consumer count.

Q40: Backpressure

Consumers
How would you handle backpressure in a Kafka consumer application?

Backpressure occurs when consumers are unable to keep up with the rate of incoming messages.

Strategies:

  • 1. Poll Throttling: Control poll() frequency.
  • 2. Consumer Lag Monitoring: Detect and alert when lag grows.
  • 3. Scale Out: Add more consumers (if partitions allow).
  • 4. Increase Partition Count: More partitions = more parallelism.
  • 5. Batch Processing: Process messages in batches to reduce overhead.
  • 6. Async Processing: Offload processing to a separate thread pool.
  • 7. Flow Control: Pause partitions (pause()) when lag is high.
// Async processing with bounded queue
ExecutorService executor = Executors.newFixedThreadPool(10);
while (true) {
    ConsumerRecords records = consumer.poll(Duration.ofMillis(100));
    records.forEach(record -> {
        executor.submit(() -> process(record));
    });
}

Best practice: Monitor lag and autoscale consumers based on load.

Q41: Kafka Storage

Storage
How does Kafka store messages on disk?

Kafka stores messages in log segments on disk. Each partition is a sequence of log segments.

Storage structure:

  • Log Directory: /var/lib/kafka/data/topic-partition/
  • Segments: Files with .log (messages), .index (offset indexing), .timeindex (time indexing).
  • Log Rolling: New segments are created when size or time limits are reached.
  • Message Format: Records are stored with timestamp, offset, key, value, headers.
// Log segment files
/var/lib/kafka/data/my-topic-0/
  00000000000000000000.log
  00000000000000000000.index
  00000000000000000000.timeindex
  00000000000000001024.log
  00000000000000001024.index

Key features:

  • Append-only: Writes are sequential.
  • Memory-mapped: Fast reads with OS page cache.
  • Zero-copy: Direct transfer from disk to network (no CPU copying).

Q42: Retention Policy

Storage
What is the retention policy and how does it work?

Retention policy determines how long messages are kept in Kafka before they are deleted.

Types of retention:

  • Time-based: log.retention.hours (default 168 hours = 7 days).
  • Size-based: log.retention.bytes (default is unlimited).
  • Compaction: Keeps only the latest value for each key.
# Topic-level retention
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name my-topic \
  --alter --add-config retention.ms=86400000 # 1 day

How it works:

  • Background threads clean up old segments.
  • Segments are deleted when they exceed the retention policy.
  • Segments are removed in order (oldest first).

Important: Retention applies to segments, not individual messages.

Q43: Log Compaction

Storage
What is log compaction and what is its primary purpose?

Log compaction is a retention policy that retains only the latest value for each message key.

Purpose:

  • Maintain a snapshot of the latest state per key.
  • Reduce storage for topics where only the latest value matters (e.g., database change logs).
  • Enable stateful applications to rebuild state from the compacted log.
// Enable compaction for a topic
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic user-profiles \
  --config cleanup.policy=compact

How it works:

  • A background thread removes older messages with the same key.
  • Only the latest message for each key is kept.
  • The log maintains the tail (latest values) and may have a compact segment.

Q44: Compaction Performance

Storage
How does log compaction impact consumer performance?

Log compaction has both positive and negative impacts on consumers.

  • Positive:
    • Reduced storage space, especially for topics with frequent updates.
    • Faster reads when only the latest value is needed.
  • Negative:
    • Consumers cannot replay older versions of a key.
    • Processing logic must handle null values (tombstones).
    • Compaction adds CPU and I/O overhead for the broker.
// Consumer with compaction-aware processing
if (record.value() == null) {
    // Tombstone – key has been deleted
    handleDeletion(record.key());
} else {
    process(record.key(), record.value());
}

Best practice: Design consumers to handle tombstone messages (null values) for deleted keys.

Q45: High-Water Mark (HW)

Storage
What is the high-water mark (HW) in Kafka?

The high-water mark is the offset of the last message that has been replicated to all ISR replicas.

Why it's important:

  • Consumers can only read messages up to the high-water mark.
  • Messages beyond the HW are not visible to consumers (they are not fully replicated).
  • The HW ensures consistency – consumers see the same data across brokers.
// HW vs LEO (Log End Offset)
// LEO = 50 (last message written)
// HW = 48 (last message replicated to all replicas)
// Consumers can read up to offset 48

When HW updates:

  • When all replicas have acknowledged a message (for acks=all).
  • Followers update their HW after replicating messages.

Note: The HW is also known as the committed offset.

Q46: Cluster Sizing

Storage
What factors should be considered when determining the appropriate size for a Kafka cluster?

Key factors for cluster sizing:

  • Throughput: Expected messages per second (producer and consumer).
  • Data Retention: How long to keep data (retention period).
  • Replication Factor: RF=3 requires 3x storage.
  • Partition Count: Total number of partitions across all topics.
  • Message Size: Average and maximum message size.
  • Peak Load: Peak throughput vs. average.
  • Fault Tolerance: Number of brokers that can fail.
  • Compression: Use compression (e.g., Snappy, GZIP) to reduce storage.
// Storage calculation
// Daily data = messages/sec × message_size × 86400
// Total storage = daily_data × retention_days × replication_factor

Example:

  • 1,000 msgs/sec, 1KB per msg, 7 days retention, RF=3.
  • Daily: 1000 × 1KB × 86400 = 86.4 GB/day.
  • Total: 86.4 GB × 7 × 3 = 1.8 TB storage.

Q47: Reduce Disk Usage

Storage
How do you reduce Kafka's disk usage?

Strategies to reduce disk usage:

  • 1. Reduce Retention: Shorten retention period (log.retention.hours).
  • 2. Use Compression: Enable compression (Snappy, GZIP, LZ4, ZSTD).
  • 3. Log Compaction: Use compaction for keyed topics.
  • 4. Increase Segment Size: Larger segments reduce file overhead.
  • 5. Delete Old Topics: Remove unused topics.
  • 6. Clean Up Logs: Use kafka-log-dirs.sh to clean up.
  • 7. Tiered Storage: Move older data to cheaper storage (Confluent Tiered Storage).
# Enable compression for a topic
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name my-topic \
  --alter --add-config compression.type=snappy

Compression comparison:

  • Snappy: Good balance of speed and compression.
  • LZ4: Fastest, moderate compression.
  • ZSTD: Best compression ratio, slightly slower.
  • GZIP: Good compression, slower.

Q48: Max Message Size

Storage
What is the maximum size of a message that Kafka can receive?

The maximum message size is determined by the broker configuration:

  • message.max.bytes – Broker-level maximum (default 1MB).
  • max.request.size – Producer-level maximum (default 1MB).
  • fetch.max.bytes – Consumer-level maximum (default 50MB).
# Increase message size (broker)
message.max.bytes=10485760 # 10 MB

# Increase for producer
props.put("max.request.size", 10485760); # 10 MB

Important considerations:

  • Large messages impact performance, memory, and replication.
  • Must adjust replica.fetch.max.bytes (default 1MB) for replication.
  • Large messages are not recommended – use external storage for very large data.

Best practice: Keep messages under 1MB for optimal performance.

Q49: Kafka Streams

Streams & Connect
What is Kafka Streams and how does it differ from a regular consumer?

Kafka Streams is a client library for building real-time stream processing applications on top of Kafka.

Key differences from a regular consumer:

  • Stateful Processing: Supports stateful operations (aggregations, joins, windowing).
  • Exactly-Once Semantics: Built-in exactly-once processing.
  • Fault Tolerance: Automatic recovery with state stores.
  • DSL & Processor API: High-level DSL and low-level Processor API.
  • Scalability: Automatic partition rebalancing.
// Kafka Streams example
StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> stream = builder.stream("input-topic");
stream.mapValues(value -> value.toUpperCase())
    .to("output-topic");
KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();

When to use: Real-time transformations, aggregations, joins, event-time processing.

Q50: Kafka Connect

Streams & Connect
What is Kafka Connect and when would you use it?

Kafka Connect is a framework for building and running scalable, reliable data pipelines between Kafka and other systems.

Key features:

  • Source Connectors: Pull data from external systems (databases, files, APIs).
  • Sink Connectors: Push data to external systems (databases, S3, Elasticsearch).
  • Automatic: Handles schema evolution, offset management, and fault tolerance.
  • Distributed: Runs in a distributed mode for scalability.
// Example: JDBC Source Connector
{
  "name": "mysql-source",
  "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
  "tasks.max": 1,
  "connection.url": "jdbc:mysql://localhost:3306/mydb",
  "table.whitelist": "orders",
  "topic.prefix": "mysql-"
}

When to use:

  • Building data pipelines between Kafka and other systems.
  • CDC (Change Data Capture) from databases.
  • Integrating with cloud storage (S3, GCS, Azure).
