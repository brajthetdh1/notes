What is a distributed system, and what are its defining characteristics?

Short Answer

A distributed system is a collection of independent computers that appears to its users as a single coherent system. It communicates only by passing messages over an unreliable network, has no shared memory and no global clock, and can suffer partial failure — some components working while others fail — which is the property that makes it fundamentally different from a single-machine program.

The formal definition and its consequences

Leslie Lamport's often-quoted framing is that a distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable. That is a joke with a serious point: the defining feature is not “multiple machines” but the inability to know the global state. Each node has only a local view, updated by messages that may arrive late, out of order, duplicated, or not at all. From this single fact — the absence of shared memory and a shared clock — every hard problem in the field follows.

Characteristic 1 — Concurrency with no shared clock

Nodes execute in parallel, and there is no reliable way to say that event A on node 1 happened before event B on node 2 using wall-clock time, because clocks drift. Distributed systems therefore reason about ordering with logical clocks, causal relationships, and happens-before graphs rather than timestamps. Any design that assumes “the timestamp is the truth” will eventually fail during a clock skew incident.

Characteristic 2 — Communication only by message passing

There is no shared variable to lock. Coordination must be built on messages, and message passing introduces latency, bandwidth limits, and the inability to distinguish a slow node from a dead one. This is why the failure detector is a first-class concept: the network can only ever tell you “no reply yet”, never “definitely dead”.

Characteristic 3 — Partial failure

On one machine, a failure is usually total: the process crashes, the machine dies. In a distributed system, a component can fail while everything else continues. The database replica is down but the API is up; one shard is unreachable while the other 99 serve traffic. Partial failure is what makes error handling combinatorial — every remote call can fail independently, and the system must decide, per call, whether to retry, degrade, or abort.

Characteristic 4 — Independent failure domains and autonomous components

Each node has its own hardware, OS, and lifecycle. Nodes can be upgraded, rebooted, and replaced independently. This is the source of the scalability benefit — you can add capacity by adding nodes — and the source of operational complexity, because there is no single place to look when things go wrong.

Why build one at all

  • Scale beyond a single machine. CPU, memory, and disk are finite; some workloads (search indexes, chat history, event streams) simply exceed them.
  • Geographic latency. A user in Singapore cannot be served in 10 ms from Virginia, because light takes time to travel.
  • Fault tolerance. Redundancy across machines, racks, and regions is the only way to survive hardware failure.
  • Organisational scaling. Independent services let independent teams ship without coordinating every release.
Interview Framing

Open with: “This is a distributed system, so I'm assuming partial failure, message passing with no shared clock, and eventual consistency unless we design otherwise.” That single sentence signals you understand the actual difficulty and not just the diagram.

What are the main challenges of building distributed systems?

Short Answer

The challenges reduce to six families: partial failure, unreliable networks, absence of a global clock, coordination and consistency, observability, and operational complexity. Every one of them is a consequence of the system being physically spread out, and every one of them has a standard set of mitigations that interviewers expect you to name.

Challenge 1 — Partial failure and ambiguity

A call that times out may mean the server never received it, received it and failed, or received it and succeeded but the response was lost. The caller cannot tell. This ambiguity is why idempotency is the central design discipline of distributed systems: every operation that might be retried must be safe to retry. Retrying a payment without an idempotency key is how companies create double charges.

Challenge 2 — Unreliable network and cascading failure

Networks drop packets, reorder messages, and partition. More dangerously, they degrade: latency rises before connectivity fails, and a slow dependency is often worse than a dead one because it holds resources. Slow downstream services are the leading cause of cascading failures — thread pools exhaust, queues fill, and the whole system collapses from one overloaded component. Mitigations: timeouts, circuit breakers, bulkheads, backpressure, and load shedding.

Challenge 3 — No global clock

Clocks on different machines disagree by milliseconds to seconds. Ordering events by wall-clock time produces impossible histories — a message that appears to be acknowledged before it was sent. Mitigations: logical clocks, Lamport timestamps, hybrid logical clocks, and bounded-uncertainty clocks like Spanner's TrueTime.

Challenge 4 — Coordination and consistency

Agreeing on a value across nodes requires consensus, and consensus is provably expensive: it needs a majority quorum, at least one round trip (often more), and it is impossible to guarantee in a fully asynchronous network with even one crash failure (the FLP result). Every consistency guarantee you ask for is paid for in latency and availability, which is exactly what the CAP and PACELC theorems formalise.

Challenge 5 — Observability and debugging

There is no debugger for a thousand processes. Bugs manifest as emergent behaviour: a latency spike, a slowly diverging replica, a rare duplicate record. Debugging requires distributed tracing with propagated correlation IDs, structured logs, high-cardinality metrics, and the discipline to ask “which component introduced this behaviour?” rather than “which line of code is wrong?”.

Challenge 6 — Testing and reproducing failures

Many distributed bugs only appear under specific interleavings of failure, timing, and load. They cannot be reproduced in a unit test. The industry's answer is chaos engineering: inject node kills, latency, and partitions continuously in staging, and verify that the system degrades gracefully rather than catastrophically.

Challenge 7 — Operational and organisational complexity

Deployment, rolling upgrades, schema migrations across services, certificate rotation, capacity planning, and on-call rotation all multiply with the number of moving parts. A distributed system has an operational cost that scales superlinearly with the number of independent services, which is why “start with a monolith” is now mainstream advice.

Challenge 8 — Security surface

Every service-to-service call is an opportunity for interception or impersonation. Identity must be established per service (mTLS, SPIFFE), secrets rotated, and the blast radius of a compromised component limited. In a monolith, the trust boundary is the process; in a distributed system, it is every link.

The Meta-Challenge

All of these challenges are tradable. You can buy consistency with latency, availability with simplicity, observability with overhead, and fault tolerance with cost. The senior skill is not eliminating the challenges but choosing consciously which ones to pay for — and writing that choice down.

What is the difference between a distributed system and a parallel system?

Short Answer

A parallel system uses many processors sharing memory and a clock, tightly coupled, to finish one computation faster — the goal is performance, and a failure usually kills the whole job. A distributed system uses independent computers communicating by messages to provide a service — the goal is scale, fault tolerance, and geographic reach, and failures are partial. The line blurs in clusters, which are both.

The classical distinction

DimensionParallel systemDistributed system
MemoryShared address spacePrivate memory, message passing
CouplingTight — threads, locks, barriersLoose — RPC, queues, events
ClockOne clock, synchronizedNo global clock
Primary goalSpeed: finish one job fasterScale, availability, fault tolerance
Failure modeWhole job failsPartial failure
Typical hardwareMulti-core CPU, GPU, HPC clusterServers across racks, DCs, regions
Programming modelOpenMP, CUDA, MPIREST, gRPC, Kafka, actor systems
Scaling axisAmdahl's Law boundAlso bounded by coordination cost

Why the distinction matters in practice

Parallelism assumes that all processors are present and healthy for the duration of the computation. That assumption lets you use barriers, shared locks, and deterministic reductions. Distribution cannot assume that, which forces entirely different primitives: quorums instead of barriers, leases instead of mutexes, and idempotency instead of exactly-once execution. If you try to apply parallel-programming intuition to a distributed system — “just take a global lock” — you will build something that deadlocks on the first network partition.

Where the categories overlap

A modern datacenter is both. A machine with 128 cores running a multi-threaded service is a parallel system. A thousand such machines behind a load balancer, sharding a dataset, is a distributed system. MapReduce and Spark sit deliberately in the middle: they distribute work across machines (distribution) but each node also parallelises within itself (parallelism), and the framework hides the difference.

The shared-memory vs shared-nothing axis

The cleanest way to keep them apart is the memory model. Shared memory means threads see each other's writes directly, and synchronisation is via hardware primitives. Shared disk means separate compute nodes attach to the same storage (traditional Oracle RAC). Shared nothing means each node has its own CPU, memory, and disk, and communicates only by messages — this is the architecture of essentially every horizontally scalable database and is the definition of distributed in the modern sense. Shared-nothing scales furthest because there is no contention on a shared resource, but it makes cross-node queries and joins dramatically harder.

How this shows up in interviews

When an interviewer asks you to design a system that processes a billion records, the first clarifying question is whether the work is parallelisable within a node or must be distributed. If a single machine with 64 cores and 512 GB of RAM can do the job in the time budget, the correct answer is one machine — not a cluster. Reaching for distribution when parallelism suffices is a common and expensive mistake, because you inherit every distributed challenge (partial failure, coordination, observability) without needing any of the distributed benefit.

Common Misconception

“Distributed is just parallel across machines.” No — a distributed computation must tolerate the possibility that half its participants vanish mid-computation, which a parallel computation never has to consider. That single requirement changes the algorithm, not just the deployment.

What are the Fallacies of Distributed Computing, and how do they break naive designs?

Short Answer

Eight assumptions that engineers new to distribution make and that are all false: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology doesn't change, there is one administrator, transport cost is zero, and the network is homogeneous. Each fallacy maps to a concrete class of production outage.

The eight fallacies, with their failure modes

FallacyWhat breaksMitigation
The network is reliable Unhandled packet loss, dropped connections, and silent message loss corrupt state Retries with idempotency, timeouts, acknowledgements, dead-letter queues
Latency is zero Chatty APIs, N+1 remote calls, synchronous fan-out to 20 services in one request Batching, caching, async pipelines, co-location, aggressive API consolidation
Bandwidth is infinite Serialising whole objects, sending full documents on every update, image payloads in JSON Compression, field masks, pagination, CDNs, protobuf instead of JSON where it matters
The network is secure Plaintext service-to-service traffic, unauthenticated internal endpoints, SSRF mTLS, zero-trust, service identity, encryption in transit everywhere, including “internal”
Topology doesn't change Hardcoded IPs, static host lists, configs that rot when a node is replaced Service discovery, DNS with short TTLs, dynamic membership, config as code
There is one administrator Firewall rules nobody knows about, inconsistent time zones, undocumented policy Explicit contracts, infrastructure as code, cross-team observability
Transport cost is zero Assuming serialisation and marshalling are free; CPU and memory blow up under load Measure serialisation cost, use binary formats on hot paths, cap payload sizes
The network is homogeneous MTU mismatches, IPv6 gaps, different TLS versions, vendor-specific middleboxes Conservative protocols, capability negotiation, contract tests across environments

Why “latency is zero” is the most expensive fallacy

It hides in designs that look perfectly reasonable on a whiteboard. A page load that calls five services sequentially, each of which calls three more, is 15 network hops. At 2 ms per hop that is 30 ms — fine. At the p99, where each hop occasionally takes 200 ms, that same page load takes seconds, because tail latencies add. This is why fan-out amplification is a standard interview follow-up: “you've added 20 services in the request path; what's your p99?” The correct instinct is to collapse synchronous fan-out into parallel calls, cache aggressively, or move work to an async pipeline.

Why “the network is reliable” is the most dangerous

Unreliability is not binary. A network that drops 0.01% of packets looks reliable in testing and causes mysterious, intermittent data corruption in production — because the code path that handles a dropped connection was never exercised. Fallacy-driven bugs are hard to reproduce precisely because they only manifest at scale, under load, or during a routine failover. The only defence is to design as though every message may be lost, duplicated, or reordered, and then test that assumption with fault injection.

How to use the fallacies in an interview

Name them explicitly when you justify a design decision. “I'm adding an idempotency key here because the network is not reliable and this call may be retried.” “I'm batching these lookups because latency is not zero and 40 sequential calls would blow the p99 budget.” This demonstrates that your design choices come from first principles rather than from copying a reference architecture.

Interview Framing

The fallacies are a checklist for the “what can go wrong” phase of any design. Walking through three or four of them against your own diagram — and naming the mitigation — is one of the strongest signals of production experience you can give.

What is the difference between horizontal and vertical scaling?

Short Answer

Vertical scaling (scale up) means making one machine bigger — more CPU, RAM, faster disk. Horizontal scaling (scale out) means adding more machines and distributing the work. Vertical is simpler and requires no code change but hits a hard ceiling; horizontal is theoretically unbounded but requires the application to be partitioned, stateless, and coordination-aware.

AspectVertical (scale up)Horizontal (scale out)
MechanismBigger instanceMore instances
CeilingHard — largest available machinePractically none
Code changeNoneRequires statelessness, sharding, or partitioning
Failure domainOne big machine — failure is totalMany small — failure is partial
Cost curveSuperlinear at the top endLinear, but with coordination overhead
ComplexityLowHigh — load balancing, discovery, consistency
Best forDatabases, stateful systems, legacy appsStateless web/API tiers, workers

Why vertical scaling hits a wall

There is a maximum size of machine you can buy — currently on the order of hundreds of cores and multiple terabytes of RAM. Beyond that, you must partition. But the wall arrives earlier than the hardware limit for two reasons. First, cost is superlinear: doubling RAM often more than doubles price. Second, the failure domain becomes unacceptable — a single machine holding 4 TB of data is a single point of failure, and the time to restore or fail over a machine that large is measured in minutes to hours.

Why horizontal scaling is not free

Adding machines introduces a set of problems that do not exist on one machine:

  • State placement. Where does a user's session live? Which node owns which shard?
  • Coordination overhead. Cross-node operations need consensus, and consensus costs round trips. This is why scaling is not linear: Amdahl's Law applies to any shared serial section, and the Universal Scalability Law adds a contention term that can make throughput decrease past a certain node count.
  • Load distribution. Requests are not uniform; without careful key design you get hot nodes and idle nodes.
  • Operational surface. More nodes means more failures per day and more to monitor.

The practical strategy: scale up first, then out

For most systems the pragmatic sequence is: (1) build it on one machine, (2) scale vertically until it is expensive or fragile, (3) make the stateless tier horizontally scalable so the bulk of traffic scales out, (4) only then shard the stateful layer. Jumping straight to sharding for a workload that one well-sized database could serve is a common over-engineering mistake that costs months of complexity for no benefit.

Hybrid and the “scale in” dimension

Modern systems combine both: a few large database primaries (vertical) fronted by many small stateless API pods (horizontal). There is also scaling in — reducing capacity when demand falls, which matters for cost and is what elasticity is about. And there is diagonal scaling, where you increase both instance size and count together to keep the ratio of work per node constant while the total fleet grows.

Trade-off

Horizontal scaling trades operational and architectural complexity for unbounded capacity and smaller failure domains. Vertical scaling trades a hard ceiling and a large failure domain for simplicity. The correct answer in an interview depends on the workload: a relational database with strong transactional requirements is often better scaled up; a stateless API tier is always better scaled out.

What is a node, and what is a cluster?

Short Answer

A node is a single participating machine (or process) in a distributed system. A cluster is a set of nodes that cooperate to present a single logical service, share membership knowledge, and coordinate through a protocol. The cluster — not the node — is the unit of availability and the unit of failure domain in most designs.

What makes a node a node

A node has its own CPU, memory, disk, network interface, operating system, and clock. It has a unique identity within the cluster — a node ID, a hostname, or an IP — and it advertises its health through heartbeats. Crucially, a node is the smallest unit you can independently fail, restart, replace, or upgrade. That makes it the natural unit of redundancy: if you need to survive a node failure, you need at least two.

What makes a cluster a cluster

A cluster is more than a list of machines. It has three additional properties:

  • Membership. Every node knows which other nodes are currently participating. Membership must be maintained dynamically and must itself be consistent — otherwise two halves of a cluster can each believe they are the whole, which is the split-brain problem.
  • Coordination. Nodes agree on leadership, shard ownership, and configuration through a protocol (Raft, Paxos, gossip).
  • A shared abstraction. Clients interact with the cluster as one entity — one connection string, one virtual IP, one logical database — while the cluster hides which node served the request.

Types of clusters by purpose

Cluster typePurposeExample
High-availability clusterFailover — one active, others standbyDatabase primary/replica pair
Load-balancing clusterDistribute traffic across identical nodesWeb server fleet behind an LB
Storage clusterReplicate and shard data across nodesCassandra, Ceph, HDFS
Compute clusterParallel job executionSpark, Kubernetes workers
Consensus clusterMaintain strongly consistent configurationZooKeeper, etcd ensemble

Quorum and the size of a cluster

Most consensus-based clusters require a majority quorum to make progress: 3 nodes tolerate 1 failure, 5 tolerate 2, 7 tolerate 3. This gives the familiar guidance to use odd numbers, because an even number (say 4) tolerates the same number of failures as the next lower odd number (3) while costing more. It also explains why large consensus clusters are rare: a 9-node ensemble requires 5 nodes to agree on every write, and cross-region consensus latency grows with the size of the quorum.

Cluster as failure domain

When you design for availability you must identify the failure domain you are protecting against. A node cluster protects against node failure. A rack-aware cluster protects against rack failure (a top-of-rack switch dying). A multi-AZ cluster protects against datacenter failure. A multi-region deployment protects against regional failure. The general rule is that redundancy must be orthogonal to the failure you expect — replicating three copies onto the same rack protects against nothing.

Common Pitfall

Confusing “a cluster of three nodes” with “three replicas”. If all three nodes sit in the same availability zone, the cluster survives a node failure but not a zone failure. Topology matters as much as count.

What is a single point of failure, and how do you eliminate it?

Short Answer

A single point of failure (SPOF) is any component whose failure makes the entire system unavailable. You eliminate it by redundancy plus automatic failover plus a mechanism to detect the failure — all three are required. Redundancy without detection is just idle hardware; detection without failover is just alerting.

Where SPOFs hide

  • The database. One primary with no replica, or a replica that has never been failed over to in production.
  • The load balancer. Ironically, the component added to remove SPOFs is often itself a SPOF unless deployed in a redundant pair with a floating IP.
  • DNS. One DNS provider, one zone, one record with no health check.
  • Configuration and secrets. A single config service that every service reads on startup.
  • The identity provider. If auth is down, every request fails, including ones that should have been cacheable.
  • Shared network devices. One top-of-rack switch, one NAT gateway, one VPN concentrator.
  • Build and deploy. One CI system that cannot deploy a hotfix if it is down.
  • People. Exactly one engineer who understands the billing pipeline.

The three pillars of elimination

  1. Redundancy. At least two instances of the component, placed in different failure domains. Active-active (both serving) or active-passive (one standby) both work; active-active also gives you capacity, active-passive is simpler but wastes a machine.
  2. Detection. A health check that actually reflects the component's ability to serve. A liveness probe that only checks whether the process is running will happily report healthy on a service whose database connection pool is exhausted.
  3. Failover. An automated mechanism to shift traffic or promote a replica. Manual failover is a SPOF because it depends on a human being awake.

Degradation as an alternative to elimination

Not every SPOF can be made redundant — some dependencies are inherently singular (a third-party payment processor, a legacy mainframe). For those, the strategy shifts from elimination to graceful degradation: cache aggressively so reads survive an outage, queue writes so they replay when the dependency returns, and disable non-critical features (recommendations, avatars) while keeping the core purchase flow working. The question to ask is not “how do I make this redundant?” but “what does the system do when this is down?” — and the answer must be deliberate.

Finding SPOFs systematically

The most reliable technique is a game day or fault-injection exercise: deliberately kill each component in staging, one at a time, and observe what breaks. Automated chaos engineering makes this continuous. A complementary technique is to draw the request path end to end and mark every hop that has exactly one instance — that list is your SPOF inventory. Repeating the exercise for the deployment pipeline, the monitoring stack, and the on-call process usually produces uncomfortable findings.

Trade-off

Eliminating every SPOF is impossible and would be ruinously expensive — the redundancy must itself be redundant, recursively. The practical approach is to enumerate SPOFs, rank them by blast radius and likelihood, and eliminate the ones on the critical revenue path while accepting the rest with an explicit degradation plan.

What is the difference between high availability and fault tolerance?

Short Answer

High availability minimises downtime: the system recovers quickly, possibly with degraded service or a brief interruption. Fault tolerance means the system continues operating correctly and without interruption while components fail — no dropped requests, no data loss, no recovery window. Fault tolerance is strictly stronger and strictly more expensive.

DimensionHigh availabilityFault tolerance
Behaviour during failureBrief interruption, then recoveryNo interruption at all
Typical mechanismHealth checks + failover + retriesFull redundancy + instantaneous switchover + replicated state
Data lossPossible (async replication)None by design (sync replication, quorum)
Redundancy levelN+1N+2 or more, often dual-active
CostModerateSubstantially higher
Typical target99.9% – 99.99%99.999%+ (five nines)
ExampleWeb tier behind a load balancer; database fails over in 30 sAircraft fly-by-wire; telecom switches; stock exchanges

The “nines” arithmetic

The difference is most visible in the numbers. 99.9% availability allows 43 minutes of downtime per month. 99.99% allows 4.3 minutes. 99.999% allows 26 seconds. A failover that takes 30 seconds — perfectly acceptable for a highly available system — is a violation of five nines. This is why fault tolerance is not “better HA”; it is a different engineering regime, requiring hot standby, synchronous replication, and failover mechanisms measured in milliseconds.

What high availability actually requires

  • Redundant components in separate failure domains.
  • Health checks that reflect true serviceability, not merely process liveness.
  • Automatic failover with a bounded, measured recovery time.
  • Retry with idempotency so clients survive the brief interruption.
  • Load balancers and DNS that remove unhealthy targets quickly.
  • Regular, tested failover drills — an untested failover is not a mechanism, it is a hope.

What fault tolerance adds on top

  • Synchronous replication or quorum writes, so no committed data is lost during switchover.
  • Active-active processing, so the remaining nodes already have the capacity and state to absorb the failed node's load instantly.
  • Deterministic, sub-second failure detection, often via hardware watchdogs or tight heartbeats.
  • Isolation mechanisms (bulkheads) so the failure of one component cannot slow the others.
  • Extensive formal verification or exhaustive fault-injection testing, because the failure paths must be correct on the first attempt.

Choosing between them

Almost every commercial system targets high availability, not fault tolerance, because the cost curve is steep and the marginal benefit is small. A payment API that fails over in 20 seconds is commercially fine; a trading engine that drops a single order is not. The decision should be driven by the cost of a brief interruption: if a 30-second outage costs thousands, HA is sufficient; if it costs millions or endangers safety, fault tolerance is mandatory.

The hidden third option: graceful degradation

Between HA and FT sits a cheaper strategy — accept the failure, but fail partially. Disable the recommendation widget, serve cached search results, queue the write for later. Users perceive the core product as available even though a component is down. Many “five nines” systems are actually three-nines systems with excellent degradation, and this is frequently the better engineering trade.

Interview Framing

When asked for “high availability”, quantify it: “I'll target 99.99%, which is about four minutes of downtime a month, so failover must be under 30 seconds and I'll accept async replication.” Naming the number and the mechanism together is far stronger than saying “I'll add replicas”.

What is the difference between scalability and elasticity?

Short Answer

Scalability is the ability to handle increased load by adding resources — a capacity property. Elasticity is the ability to add and remove resources automatically and rapidly as demand fluctuates — a responsiveness and cost property. A system can be scalable without being elastic (you can add servers, but only manually and slowly). It cannot be elastic without being scalable.

Scalability in more detail

Scalability answers: “if load doubles, can the system serve it by adding resources, and at what cost?” It is measured by how throughput and latency behave as resources are added. Perfect linear scaling is impossible — Amdahl's Law caps speedup at the serial fraction, and contention for shared resources (databases, locks, network) causes throughput to flatten and eventually decline. A system is described as scalable if the efficiency loss is acceptable: doubling the fleet yields, say, 1.8× throughput.

Elasticity in more detail

Elasticity answers: “when demand spikes at 9 a.m. and falls at 9 p.m., does the system provision and de-provision capacity on its own?” It requires three things beyond scalability:

  • Rapid provisioning. New instances must be able to start and become productive in seconds, not hours — which is why containers and pre-baked images matter.
  • Automated decision-making. Metrics-driven autoscaling policies with sensible thresholds, cooldowns, and hysteresis to prevent thrashing.
  • Fast, safe de-provisioning. Draining connections, finishing in-flight requests, and releasing state cleanly.

Why elasticity depends on statelessness

You can only kill an instance instantly if it holds no irreplaceable state. An elastic tier therefore must externalise session data, cache, and in-flight work to shared stores or durable queues. A stateful service can still be elastic, but scaling it requires data rebalancing — moving partitions between nodes — which is slow and risky. This is why the standard architecture is a highly elastic stateless tier in front of a more static, carefully scaled stateful tier.

Cost implications

Scalability without elasticity means you provision for peak and pay for peak 24/7. For a workload with a 10× daily peak-to-trough ratio, that is roughly 90% waste. Elasticity converts a fixed capital cost into a variable operating cost, which is the entire economic argument for cloud computing. The counter-argument is that autoscaling adds unpredictability — a traffic spike can outrun the scaling policy, and a misconfigured policy can scale the fleet to zero or to bankruptcy.

The failure modes of each

PropertyFailure mode
Scalable, not elasticOver-provisioned, expensive, but stable
Elastic, not scalableDoesn't exist — elasticity presupposes scalability
Poorly elasticThrashing (scale up/down loops), cold-start latency, connection storms when new instances register
Over-elasticScaling on the wrong metric; scaling into a downstream bottleneck (more app servers, same saturated database)

The critical insight: scale on the right signal

Autoscaling on CPU is the default and frequently wrong. A service that is I/O-bound will queue requests while its CPU sits at 15%. The correct signal is usually a leading indicator of user-visible pain — request queue depth, in-flight request count, or p99 latency relative to SLO — combined with a hard cap so a runaway policy cannot exhaust the budget. Equally important is scaling the bottleneck: adding app servers in front of a single saturated database produces no additional throughput, only more contention.

Trade-off

Elasticity trades predictability for cost efficiency. Reserved capacity is cheaper per unit and immune to autoscaling misfires; on-demand elasticity is more expensive per unit but matches spend to demand. Most mature systems use a baseline of reserved capacity plus an elastic burst layer — the hybrid is the pragmatic answer.

What is the difference between latency and throughput?

Short Answer

Latency is how long one operation takes, measured in time. Throughput is how many operations complete per unit time, measured in rate. They are related by Little's Law: concurrency = throughput × latency. They often trade against each other — batching raises throughput and worsens latency — and optimising one blindly can destroy the other.

Little's Law and why it matters

Little's Law states that the average number of items in a system (L) equals the arrival rate (λ) multiplied by the average time each item spends in the system (W): L = λ × W. In a server context: concurrent requests = requests per second × average latency. This is the single most useful capacity formula in system design. If you need to serve 10,000 requests per second at 100 ms latency, you need 1,000 concurrent requests in flight. If latency degrades to 1 second under load, the same 1,000 concurrency slots now only deliver 1,000 requests per second — throughput collapsed because latency grew. This is the mechanism behind most “the system fell over” incidents: a service slows down, requests pile up, thread pools and connection pools exhaust, and throughput goes to zero.

Why they trade off

  • Batching. Grouping 1,000 writes into one disk flush dramatically raises throughput and adds up to the batch window's latency to each individual write.
  • Pipelining. Sending many requests before waiting for responses raises throughput and leaves the tail latency of individual requests uncertain.
  • Caching. Improves both — for hits. It reduces latency and increases effective throughput by absorbing load.
  • Connection reuse. Eliminates handshake latency and raises throughput simultaneously.
  • Buffering. Absorbs bursts and raises sustained throughput while increasing worst-case latency — buffers that are full are just queues with latency.

Tail latency is the real metric

Average latency is a lie. If a page issues 100 backend calls, the user's page load is governed by the slowest of those calls, not the average. With 100 calls, if 1% of calls are slow, the probability that at least one is slow is 1 − 0.99¹⁰⁰ ≈ 63%. This is why services publish p50, p95, p99, and p999 rather than means, and why fan-out amplifies tail latency — a fact that kills many microservice decompositions that look fine on average.

Coordinated omission

A subtle measurement trap: if your load generator waits for each response before issuing the next request, it stops generating load precisely when the system is slow, so the slow responses are never measured at the rate they would occur in production. The result is a latency report that looks far better than reality. Correct benchmarks use open-loop load generation with fixed arrival rates and measure latency from the intended send time, not the actual one.

Practical targets

Latency budgetTypical technique
p99 < 10 msIn-memory data, local cache, no network hop, single index seek
p99 < 100 msOne or two network hops, cached reads, simple query
p99 < 500 msParallel fan-out, database query with indexes, small joins
p99 < 2 sMultiple sequential dependencies, heavier computation
p99 > 2 sMove to async: return 202 Accepted, process in background, notify
Common Pitfall

Reporting throughput without the corresponding latency. “We handle 50,000 requests per second” means nothing if the p99 at that rate is four seconds. Throughput and latency must always be quoted together, at a specified load level.

What is the difference between a stateless and a stateful service, and why does statelessness matter for scaling?

Short Answer

A stateless service keeps no data between requests — every request carries everything needed to process it, and any instance can serve any request. A stateful service retains data across requests (sessions, caches, connections, shards), so requests are bound to specific instances. Statelessness is the property that makes horizontal scaling and elasticity trivial.

What “stateless” really means

No service is truly stateless — it runs on a machine with memory and open sockets. The practical definition is: the service holds no state whose loss would break correctness for a client. An HTTP API that authenticates each request with a signed token and reads its data from a database is stateless: kill any instance mid-traffic and the next request from the same user lands on a different instance and works identically. A WebSocket server holding live connections is stateful: killing it disconnects those users.

Why statelessness enables scaling

  • Any instance serves any request. The load balancer can use the simplest possible algorithm — round robin — with no affinity tracking.
  • Instances are disposable. Autoscaling can kill one at any moment, which is a prerequisite for elasticity.
  • Deployment is trivial. Rolling updates replace instances one at a time with no migration or draining of session data.
  • Failure is cheap. A crashed instance affects only in-flight requests, which can be retried on another instance.
  • Caching is simpler. No need to worry about which instance holds which cached value.

Where state actually goes

Statelessness is not the elimination of state — it is the externalisation of it. The three standard destinations are:

State typeDestinationExample
User sessionSigned token (JWT) or shared session store (Redis)Auth cookies, cart contents
Application dataDatabaseOrders, profiles
Ephemeral/short-livedDistributed cacheRate-limit counters, computed views
Long-running workDurable queueVideo transcoding jobs, email sends
Large binaryObject storeUploaded images

Sticky sessions and why they are a smell

The alternative to externalising state is session affinity: the load balancer routes all requests from a given user to the same instance. It works, and it is widely supported, but it reintroduces every problem statelessness solves. An instance going down now logs out its users. Autoscaling is asymmetric — you cannot easily remove a busy instance. Load is uneven because some sessions are heavier than others. Sticky sessions are acceptable as a migration step, not as a target architecture.

When statefulness is unavoidable

Databases, message brokers, caches with non-trivial state, WebSocket gateways, and stream processors are inherently stateful. The goal for these is not statelessness but controlled statefulness: a small number of instances, explicit partitioning, replication for durability, and a well-defined protocol for moving ownership of a partition from one node to another. The architectural pattern is always the same — a thin, elastic stateless tier in front of a smaller, more carefully managed stateful tier.

Interview Framing

Say: “I'll make the API tier stateless so it can scale horizontally and be replaced freely; session data goes into a signed token or Redis, and the only stateful components are the database and the queue, which I'll design separately.” This single sentence resolves half the scaling questions an interviewer might ask.

What is service discovery, and why is it needed?

Short Answer

Service discovery is the mechanism by which a client finds the current network locations of the instances of a service. It exists because in a distributed system instance addresses change constantly — deploys, autoscaling, and failures replace nodes — so hardcoded IPs and static config files rot immediately. A registry tracks live instances; clients query it (or are pushed updates) to get a fresh list.

The problem it solves

In a static world, orders.internal:8080 resolves to one machine and everyone hardcodes it. In a dynamic world, that service has fifteen instances across three availability zones, each with an ephemeral IP that changes on every deployment, and the count changes hourly with autoscaling. A client that keeps a static list will eventually send traffic to a dead IP and fail. Service discovery replaces the static list with a live view.

The three components

  • Registration. An instance announces itself to the registry on startup and deregisters on shutdown. Registration is usually automatic — a sidecar agent, a Kubernetes controller, or a client library — because manual registration is forgotten during incidents.
  • Health checking. The registry must remove instances that are dead or unhealthy. This requires a health endpoint that reflects real serviceability, and a policy for how many consecutive failures constitute death. False positives remove healthy instances; false negatives route traffic to broken ones. Both are production incidents, so health-check design is not a formality.
  • Lookup. Clients resolve a service name to a set of addresses, either by querying the registry on demand or by receiving pushed updates when the set changes.

Client-side vs server-side discovery

ModelHow it worksTrade-off
Client-side Client queries the registry, chooses an instance, and load-balances itself Fewer hops and smarter balancing, but every language needs a discovery library
Server-side Client hits a stable endpoint (LB, gateway, virtual IP); infrastructure does the lookup Language-agnostic and simple for clients, but adds a hop and a potential bottleneck

Common implementations

Consul provides a registry with health checks and DNS/HTTP interfaces. etcd is a strongly consistent key-value store commonly used as the backing store for discovery, popular in Kubernetes-adjacent systems. ZooKeeper is the older, battle-tested option with ephemeral nodes that disappear automatically when a session dies — an elegant built-in deregistration. Kubernetes provides discovery natively through Services and DNS, which is why many teams no longer run a separate registry. Eureka is the Netflix-era JVM solution. AWS Cloud Map and cloud load balancers offer managed variants.

The consistency problem

A discovery registry is itself a distributed system with an availability/consistency trade-off. If it is strongly consistent, a partition may make it unavailable and clients cannot discover anything — a discovery outage becomes a total outage. If it is eventually consistent, a client may briefly see a stale address and fail. The industry's pragmatic answer is to favour availability, keep a client-side cache of the last known good list, and make the failure mode “route to a possibly-stale instance” rather than “cannot resolve at all”. DNS with short TTLs and local caching is the same trade-off in a simpler form.

Discovery in a service mesh

In a service mesh, discovery and load balancing move out of the application and into the sidecar proxy. The application addresses orders by name; the sidecar resolves it, load-balances across healthy instances, and applies retries, timeouts, and circuit breaking. This is attractive because it is language-agnostic and centrally configurable, at the cost of an extra hop and additional operational complexity. It is the direction most large-scale platforms have converged on.

Common Pitfall

Treating discovery as a solved infrastructure problem and forgetting the cold-start case: a newly started instance registers before its connection pools and caches are warm, so it receives traffic while it is slow, and its slow responses trigger health-check failures, causing a restart loop. The fix is a readiness gate distinct from liveness, held closed until warm-up completes.
