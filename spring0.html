Spring Boot: Advantages & Disadvantages

Advantages

  • Rapid Development & Less Boilerplate: Spring Boot eliminates much of the boilerplate code that traditional Spring requires. Developers can quickly set up projects with minimal configuration, speeding up development cycles.
  • Microservices Ready: It integrates seamlessly with Spring Cloud and other tools, making it easy to build microservices architectures with features like service discovery, configuration management, and distributed tracing.
  • Embedded Servers: Spring Boot comes with embedded servers like Tomcat, Jetty, and Undertow. This means you can run applications as standalone JARs without deploying to an external application server.
  • Production-Ready Features: Built-in Actuator endpoints provide monitoring, health checks, metrics, and application insights, making Spring Boot applications easy to manage in production environments.
  • Large Ecosystem & Community Support: Spring Boot has a rich ecosystem of starter dependencies, plugins, and integrations, backed by a large community that provides tutorials, support, and ready-made solutions.
  • Convention over Configuration: Sensible defaults allow developers to focus on business logic rather than low-level configuration, while still allowing customization when needed.
  • Testability: Spring Boot supports comprehensive testing capabilities with annotations like @SpringBootTest, @WebMvcTest, and @DataJpaTest, making unit and integration testing simpler.
  • Security Integration: Easily integrates with Spring Security to implement authentication and authorization, including support for JWT, OAuth2, and SAML.

Disadvantages

  • Higher Memory Usage & Startup Time: Due to auto-configuration and dependency scanning, Spring Boot applications can consume more memory and have slower startup times compared to lightweight frameworks like Micronaut or Quarkus.
  • Hidden Complexity: Auto-configuration is convenient but can be opaque. Developers may find it difficult to debug or understand what is happening behind the scenes when configurations don’t work as expected.
  • Overkill for Small Applications: For very simple CRUD apps, Spring Boot’s features may be unnecessary overhead, making lightweight frameworks more efficient.
  • Opinionated Defaults: While defaults simplify setup, customizing them often requires a deeper understanding of Spring internals, which can increase the learning curve.
  • Fat JARs: Spring Boot applications are packaged as large JAR files containing all dependencies, which can increase deployment size and startup time.
  • Steep Learning Curve: Beginners may struggle to understand the interplay between Spring Boot, Spring Core, dependency injection, and auto-configuration.
  • Version Compatibility: Spring Boot is tightly coupled with certain Spring and Spring Cloud versions. Upgrading to a newer version may require significant refactoring due to breaking changes.

Spring IoC Container

The IoC container is a core concept in Spring that manages the lifecycle and configuration of application objects (beans).

1️⃣ Definition

The IoC container manages the creation, configuration, and lifecycle of beans. Instead of your code creating objects manually, Spring handles it automatically. This is the essence of Inversion of Control (IoC): control of object creation is "inverted" from your code to the container.

2️⃣ Responsibilities of IoC Container

  • Bean Creation – Instantiates your classes as beans.
  • Dependency Injection – Injects required dependencies into beans automatically.
  • Bean Lifecycle Management – Initializes and destroys beans according to configuration.
  • Configuration Management – Reads configuration from annotations, XML, or Java-based config.

3️⃣ Types of IoC Containers in Spring

Container Description Use Case
BeanFactory Basic container that provides lazy-loading of beans. Lightweight, minimal features.
ApplicationContext Advanced container that extends BeanFactory. Provides eager-loading, internationalization, event propagation, and integration with Spring AOP. Recommended for most Spring applications. Types include:
- ClassPathXmlApplicationContext
- AnnotationConfigApplicationContext
- WebApplicationContext

How to Configure Custom Init and Destroy Methods for Spring Beans

Spring allows you to specify custom initialization and destruction logic for beans. This is useful for performing setup tasks when a bean is created or cleanup tasks before a bean is destroyed.

1. Using XML Configuration

In XML, you can use init-method and destroy-method attributes. 

<bean id="myBean" class="com.example.MyBean"
      init-method="customInit"
      destroy-method="customDestroy"/>

public class MyBean {
    public void customInit() {
        System.out.println("Bean is initializing...");
    }

    public void customDestroy() {
        System.out.println("Bean is being destroyed...");
    }
}

2. Using Annotations (@PostConstruct and @PreDestroy)

You can annotate methods with @PostConstruct for initialization and @PreDestroy for destruction. Spring automatically calls these methods during bean lifecycle. 

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.stereotype.Component;

@Component
public class MyBean {

    @PostConstruct
    public void init() {
        System.out.println("Bean initialized using @PostConstruct");
    }

    @PreDestroy
    public void cleanup() {
        System.out.println("Bean destroyed using @PreDestroy");
    }
}

3. Using Java Config with @Bean

When defining beans via @Bean in a @Configuration class, you can specify initMethod and destroyMethod. 

@Configuration
public class AppConfig {

    @Bean(initMethod = "customInit", destroyMethod = "customDestroy")
    public MyBean myBean() {
        return new MyBean();
    }
}

4. Key Points

  • @PostConstruct and @PreDestroy require JSR-250 annotations (Jakarta EE).
  • For prototype-scoped beans, Spring does not call the destroy method automatically.
  • Custom init/destroy methods are useful for resource allocation, connection setup, or cleanup tasks.
  • Order of invocation: constructor → dependency injection → init method → bean ready → destruction (when context closes).

⚡ Use Cases

Common use cases include opening and closing database connections, starting background threads, loading caches, or releasing file handles.

How to Create a Bean Dynamically at Runtime Using the IoC Container

Spring IoC container usually manages beans defined via @Component, @Bean, or XML configuration. However, sometimes you need to register a bean dynamically at runtime, for example when its type or properties are only known during execution.

1. Using ConfigurableApplicationContext

You can cast the application context to ConfigurableApplicationContext and use its BeanDefinitionRegistry to register beans dynamically. 

import org.springframework.beans.factory.support.BeanDefinitionRegistry;
import org.springframework.beans.factory.support.GenericBeanDefinition;
import org.springframework.context.ApplicationContext;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.stereotype.Component;

@Component
public class DynamicBeanRegistrar {

    private final ApplicationContext context;

    public DynamicBeanRegistrar(ApplicationContext context) {
        this.context = context;
    }

    public void registerBean(String beanName, Class<?> beanClass) {
        ConfigurableApplicationContext configurableContext = (ConfigurableApplicationContext) context;
        BeanDefinitionRegistry registry = (BeanDefinitionRegistry) configurableContext.getBeanFactory();

        GenericBeanDefinition beanDefinition = new GenericBeanDefinition();
        beanDefinition.setBeanClass(beanClass);

        registry.registerBeanDefinition(beanName, beanDefinition);
        System.out.println("Bean " + beanName + " registered dynamically!");
    }
}

2. Using ApplicationContext.getBean()

Once the bean is registered dynamically, you can retrieve it like any other bean: 

MyBean myBean = (MyBean) context.getBean("myDynamicBean");
myBean.doSomething();

3. Key Points

  • Dynamic registration is done via BeanDefinitionRegistry.
  • Useful when the bean type or configuration is not known at compile-time.
  • After registration, Spring manages the bean lifecycle like any other.
  • Careful with scope: you can define singleton, prototype, or custom scopes during registration.

⚡ Use Cases

Common scenarios include plugin systems, dynamic service registration, feature toggles, or runtime configuration-driven beans.

How to Access the IoC Container Programmatically in Spring

Sometimes you need direct access to the Spring IoC container to fetch beans or metadata at runtime. Spring provides two main interfaces for this purpose: ApplicationContextAware and BeanFactoryAware.

1. Using ApplicationContextAware

Implementing ApplicationContextAware allows a bean to obtain a reference to the ApplicationContext. 

import org.springframework.context.ApplicationContext;
import org.springframework.context.ApplicationContextAware;
import org.springframework.stereotype.Component;

@Component
public class MyBean implements ApplicationContextAware {

    private ApplicationContext applicationContext;

    @Override
    public void setApplicationContext(ApplicationContext applicationContext) {
        this.applicationContext = applicationContext;
    }

    public void doSomething() {
        AnotherBean bean = applicationContext.getBean(AnotherBean.class);
        bean.performAction();
    }
}

2. Using BeanFactoryAware

For lightweight access, you can implement BeanFactoryAware to get the BeanFactory reference. This is especially useful if you don’t need full ApplicationContext features. 

import org.springframework.beans.BeansException;
import org.springframework.beans.factory.BeanFactory;
import org.springframework.beans.factory.BeanFactoryAware;
import org.springframework.stereotype.Component;

@Component
public class MyBean implements BeanFactoryAware {

    private BeanFactory beanFactory;

    @Override
    public void setBeanFactory(BeanFactory beanFactory) throws BeansException {
        this.beanFactory = beanFactory;
    }

    public void execute() {
        AnotherBean bean = beanFactory.getBean(AnotherBean.class);
        bean.performAction();
    }
}

3. Key Points

  • ApplicationContextAware provides the full ApplicationContext with all features.
  • BeanFactoryAware provides a lightweight access to beans and bean metadata.
  • Use these only when necessary. Direct container access is generally discouraged; prefer constructor/setter injection.
  • Both interfaces are automatically called by the Spring container during bean initialization.

⚡ Use Cases

Useful for dynamically fetching beans, resolving circular dependencies, implementing plugin systems, or when you need access to container metadata.

Differences Between BeanFactory, ApplicationContext, WebApplicationContext, and ConfigurableApplicationContext

Spring provides multiple IoC container interfaces, each with specific features and use cases. Understanding their differences is crucial for designing Spring applications.

1. BeanFactory

  • Core container interface for Spring IoC.
  • Provides basic dependency injection functionalities.
  • Lazy initialization by default (beans created only when requested).
  • Lightweight and suitable for memory-constrained environments.
  • Example classes: XmlBeanFactory, DefaultListableBeanFactory.

2. ApplicationContext

  • Extends BeanFactory and adds more enterprise features.
  • Pre-instantiates singleton beans by default (eager initialization).
  • Supports internationalization (i18n), event propagation, and resource loading.
  • Common implementations: ClassPathXmlApplicationContext, AnnotationConfigApplicationContext.
  • Preferred choice for most Spring applications.

3. WebApplicationContext

  • Specialized ApplicationContext for web applications.
  • Integrates with the ServletContext for web-specific beans.
  • Supports web-aware features such as session, request, and application scopes.
  • Typical implementation: XmlWebApplicationContext, AnnotationConfigWebApplicationContext.

4. ConfigurableApplicationContext

  • Extends ApplicationContext with lifecycle management methods.
  • Allows programmatic control: refresh(), close(), registerShutdownHook().
  • Useful for managing the container’s lifecycle manually in non-web applications or for testing.
  • Example: GenericApplicationContext, AnnotationConfigApplicationContext.

5. Summary Table

Interface Features Use Case
BeanFactory Basic DI, lazy initialization Lightweight apps, low memory
ApplicationContext DI + i18n + events + resource loading, eager singletons Most Spring apps
WebApplicationContext Web-aware DI, session/request scopes Spring MVC / web apps
ConfigurableApplicationContext Lifecycle control (refresh, close, shutdown hook) Programmatic lifecycle management

How Spring Implements Inversion of Control (IoC) Internally

Spring’s Inversion of Control (IoC) allows the framework to manage object creation, configuration, and lifecycle, rather than the application code. Internally, Spring uses a combination of design patterns and core components to achieve this.

1. Core Components Behind IoC

  • BeanFactory: The fundamental IoC container responsible for instantiating, configuring, and managing beans.
  • ApplicationContext: Extends BeanFactory to provide additional features like event propagation, resource loading, and internationalization.
  • BeanDefinition: Metadata object that holds information about a bean, such as class type, scope, constructor arguments, property values, and lifecycle callbacks.
  • Dependency Injection (DI): Spring reads BeanDefinitions and injects dependencies either via constructor injection, setter injection, or field injection.

2. Bean Lifecycle & IoC

  • Spring parses configuration (XML, annotations, or JavaConfig) and registers BeanDefinitions in the container.
  • During startup, the container instantiates singleton beans (eager initialization) or waits for request (lazy initialization).
  • Dependencies are resolved recursively: if a bean depends on another bean, Spring first instantiates the dependency and injects it.
  • BeanPostProcessors allow hooks before and after initialization for custom processing.
  • Lifecycle methods (@PostConstruct, InitializingBean, custom init-method) are invoked automatically.

3. Internal Mechanisms

  • Reflection: Spring uses Java Reflection to instantiate beans and inject dependencies dynamically.
  • Proxies: Spring can create proxies (JDK dynamic proxy or CGLIB) for features like AOP or lazy injection.
  • Dependency Resolution: The container maintains a graph of bean dependencies and resolves them in order, throwing exceptions for circular dependencies unless handled.
  • Scopes: Bean scope (singleton, prototype, request, session) is handled internally by the container during instantiation and retrieval.

4. Summary

Internally, Spring implements IoC by maintaining a registry of bean definitions, resolving dependencies automatically, and using reflection and lifecycle hooks to manage bean creation, injection, and destruction. This decouples the application code from object instantiation and promotes modular, testable, and maintainable design.

Eager Loading vs Lazy Loading in Spring IoC

Spring IoC container manages the instantiation of beans, and this can be done either eagerly or lazily depending on the configuration and use case.

1. Eager Loading

  • The container creates singleton beans as soon as the context is initialized.
  • All dependencies are resolved immediately during startup.
  • Helps catch configuration or dependency issues early.
  • Annotation / XML: Default behavior for singleton beans in Spring.
  • Pros: Fast access at runtime, all beans ready immediately.
  • Cons: Longer startup time, unnecessary resource usage if some beans are never used.

2. Lazy Loading

  • The container delays bean creation until it is first requested.
  • Dependencies are injected at the time of first access.
  • Helps improve startup time and reduce memory usage.
  • Annotation: @Lazy on bean or @Configuration class.
  • Pros: Faster startup, efficient resource usage.
  • Cons: Slight delay at first access, potential runtime surprises if dependencies fail.

3. Example in Java

@Configuration
public class AppConfig {

    @Bean
    public EagerBean eagerBean() {
        return new EagerBean();
    }

    @Bean
    @Lazy
    public LazyBean lazyBean() {
        return new LazyBean();
    }
}

In this example, eagerBean is instantiated at context startup, while lazyBean is created only when requested for the first time.

4. Summary

Eager Loading: Instantiated at startup, suitable for beans always needed.
Lazy Loading: Instantiated on first request, suitable for optional or heavy beans to improve startup performance.

Replacing a Spring-Managed Bean at Runtime

By default, Spring beans are singleton-scoped and initialized at startup. However, it is possible to replace a bean at runtime using dynamic registration or refreshing the ApplicationContext. This is often needed in plugin systems, dynamic feature loading, or testing scenarios.

1. Using BeanDefinitionRegistry

You can register or replace beans dynamically using BeanDefinitionRegistry. 

@Configuration
public class DynamicBeanConfig implements ApplicationContextAware {

    private ApplicationContext context;

    @Override
    public void setApplicationContext(ApplicationContext applicationContext) {
        this.context = applicationContext;
    }

    public void replaceBean(String beanName, Object newBeanInstance) {
        ConfigurableApplicationContext configurableContext = (ConfigurableApplicationContext) context;
        BeanDefinitionRegistry registry = (BeanDefinitionRegistry) configurableContext.getBeanFactory();

        if (registry.containsBeanDefinition(beanName)) {
            registry.removeBeanDefinition(beanName);
        }

        GenericBeanDefinition beanDefinition = new GenericBeanDefinition();
        beanDefinition.setBeanClass(newBeanInstance.getClass());
        beanDefinition.setInstanceSupplier(() -> newBeanInstance);

        registry.registerBeanDefinition(beanName, beanDefinition);
    }
}

2. Using @RefreshScope (Spring Cloud)

In Spring Cloud, beans annotated with @RefreshScope can be refreshed at runtime using the /actuator/refresh endpoint. This allows configuration properties and beans to be updated without restarting the application.

3. Key Considerations

  • Replacing a singleton bean at runtime may affect other beans that already hold references to the old instance.
  • Prototype beans are easier to replace because each injection point gets a new instance.
  • Dynamic replacement is advanced and should be used carefully to avoid inconsistent state.

4. Summary

Spring allows runtime replacement of beans via BeanDefinitionRegistry or @RefreshScope. This can be useful for dynamic behavior, plugin architectures, or updating configurations without restarting the application. Proper management of references is crucial to avoid runtime issues.

Accessing the Spring IoC Container Programmatically

While Spring typically manages beans via dependency injection, there are cases where you need direct programmatic access to the IoC container. Spring provides two key interfaces for this: ApplicationContextAware and BeanFactoryAware.

1. Using ApplicationContextAware

Implementing ApplicationContextAware allows a bean to receive a reference to the ApplicationContext. This gives access to all Spring-managed beans and environment information. 

@Component
public class MyBean implements ApplicationContextAware {

    private ApplicationContext applicationContext;

    @Override
    public void setApplicationContext(ApplicationContext applicationContext) throws BeansException {
        this.applicationContext = applicationContext;
    }

    public void useBean() {
        MyOtherBean otherBean = applicationContext.getBean(MyOtherBean.class);
        otherBean.performTask();
    }
}

2. Using BeanFactoryAware

BeanFactoryAware is a lower-level approach, giving access only to the BeanFactory. This is useful for lightweight scenarios where full ApplicationContext features are not needed. 

@Component
public class MyBean implements BeanFactoryAware {

    private BeanFactory beanFactory;

    @Override
    public void setBeanFactory(BeanFactory beanFactory) throws BeansException {
        this.beanFactory = beanFactory;
    }

    public void useBean() {
        MyOtherBean otherBean = beanFactory.getBean(MyOtherBean.class);
        otherBean.performTask();
    }
}

3. Key Points

  • ApplicationContext is more powerful than BeanFactory (supports events, internationalization, AOP, etc.).
  • BeanFactoryAware is more lightweight but limited in features.
  • Programmatic access should be used sparingly; dependency injection is preferred for cleaner design.

4. Summary

By implementing ApplicationContextAware or BeanFactoryAware, a Spring bean can gain programmatic access to the IoC container and retrieve other beans at runtime. This provides flexibility but should be used judiciously to avoid tight coupling.

Differentiating Singleton Beans in Different ApplicationContexts

In Spring, a singleton bean means one instance per ApplicationContext, not per JVM. When multiple ApplicationContexts exist, each context maintains its own registry of singleton beans. Therefore, the same bean class can have separate instances in different contexts.

1. Example Scenario

Consider a parent-child context hierarchy (common in web applications: root context + servlet context): 

ApplicationContext parentContext = new AnnotationConfigApplicationContext(ParentConfig.class);
ApplicationContext childContext = new AnnotationConfigWebApplicationContext();
((AnnotationConfigWebApplicationContext) childContext).setParent(parentContext);
childContext.register(ChildConfig.class);
childContext.refresh();

MyBean parentBean = parentContext.getBean(MyBean.class);
MyBean childBean = childContext.getBean(MyBean.class);

System.out.println(parentBean == childBean); // false

2. Key Points

  • Singleton scope is per ApplicationContext. Each context maintains its own bean instances.
  • If a child context does not define a bean, it inherits from the parent context.
  • If the child context defines a bean with the same name as the parent, the child’s bean overrides the parent’s bean in that context.
  • This allows isolation between modules or web layers while still sharing common beans through parent contexts.

3. Summary

Spring differentiates singleton beans by ApplicationContext boundaries. Each ApplicationContext maintains its own singleton instances, even for the same bean class, enabling modular design and parent-child context hierarchies without instance conflicts.

How Spring Handles Bean Initialization Order

Spring initializes beans based on dependency relationships and configuration. Understanding the order is important when certain beans depend on others.

1. Default Initialization Order

By default, Spring resolves dependencies and initializes beans in an order that satisfies all dependencies. If bean A depends on bean B, Spring ensures B is initialized before A. For beans without dependencies, the order is not guaranteed unless explicitly specified.

2. Using @DependsOn

You can explicitly control the initialization order using @DependsOn. This ensures that specified beans are initialized before the annotated bean. 

@Component
@DependsOn({"beanB", "beanC"})
public class BeanA {
    // BeanA will be initialized after beanB and beanC
}

3. Initialization with @PostConstruct

Beans can define a method annotated with @PostConstruct to run initialization logic after dependencies are injected and before the bean is available for use. 

@Component
public class BeanB {
    @PostConstruct
    public void init() {
        System.out.println("BeanB initialized");
    }
}

4. Initialization with init-method in XML or @Bean

When using Java-based @Bean or XML configuration, you can specify an init-method to run custom initialization logic. 

@Bean(initMethod = "customInit")
public MyBean myBean() {
    return new MyBean();
}

public class MyBean {
    public void customInit() {
        System.out.println("Custom initialization logic");
    }
}

5. Summary

  • Spring initializes beans in dependency order automatically.
  • Use @DependsOn to explicitly control initialization order.
  • @PostConstruct and init-method allow custom initialization logic.
  • Proper ordering is crucial when beans interact or depend on each other at startup.

How Does Spring Handle Post-Processor Ordering?

In Spring, BeanPostProcessor and BeanFactoryPostProcessor are powerful extension points that allow modifying bean definitions and bean instances during the container lifecycle. When multiple post-processors exist, the order of execution matters, and Spring provides mechanisms to control it.

1. Default Behavior

By default, Spring does not guarantee the order of post-processor execution. If ordering is not specified, Spring may invoke them in the order of discovery, which can vary based on classpath scanning and configuration.

2. Using PriorityOrdered and Ordered

  • PriorityOrdered – Post-processors that implement this interface are executed first.
  • Ordered – Post-processors that implement this interface are executed next, sorted by their getOrder() value (lower values run earlier).
  • Post-processors that implement neither are executed last, with no guaranteed order. 
@Component
public class CustomPostProcessor implements BeanPostProcessor, Ordered {
    @Override
    public int getOrder() {
        return 1; // lower means higher priority
    }
}

3. Execution Order

  1. All BeanFactoryPostProcessors are executed before any BeanPostProcessor.
  2. Within each category, PriorityOrdered beans are executed first.
  3. Then Ordered beans are executed by ascending order value.
  4. Finally, unordered beans are executed with no guarantee of order.

4. Practical Implications

  • Use PriorityOrdered for critical infrastructure post-processors (e.g., PropertySourcesPlaceholderConfigurer).
  • Use Ordered when relative execution sequence is needed.
  • Avoid relying on unordered execution to ensure predictable behavior.

5. Summary

Spring controls post-processor execution using PriorityOrdered, Ordered, and natural discovery order. For consistent, maintainable behavior, always implement ordering when multiple post-processors are present.

Difference Between refresh() and close() in ApplicationContext

The ApplicationContext in Spring is the central interface for managing the IoC container. It provides lifecycle methods to manage beans. Two important lifecycle methods are refresh() and close().

1. refresh()

  • Reinitializes the ApplicationContext by clearing the current bean definitions and reloading them.
  • Destroys all existing singleton beans and recreates them.
  • Useful when you want to reload configuration without restarting the application.
  • Common in scenarios like dynamic reloading of configuration files (e.g., XML or property files).
ConfigurableApplicationContext context = 
        new ClassPathXmlApplicationContext("appConfig.xml");

// Refresh the context to reload bean definitions
context.refresh();

After refresh(), all beans are re-instantiated and re-wired, and the context lifecycle callbacks (like BeanFactoryPostProcessor, BeanPostProcessor) are re-executed.

2. close()

  • Shuts down the ApplicationContext and releases all resources.
  • Calls destroy methods (@PreDestroy, DisposableBean, custom destroy-methods).
  • Singleton beans are destroyed, and the IoC container becomes unusable after calling close().
  • Typically used at application shutdown.
ConfigurableApplicationContext context = 
        new ClassPathXmlApplicationContext("appConfig.xml");

// Close the context gracefully
context.close();

Once close() is called, the context cannot be used again. To restart, you would need to create a new context instance.

3. Key Differences

Aspect refresh() close()
Purpose Reinitialize and reload the context Shutdown and release resources
Effect on Beans Recreates all beans Destroys all beans
Reusability Context can still be used Context cannot be reused
Typical Use Case Reloading configurations at runtime Graceful shutdown of application

Spring Bean Scopes

In Spring, a bean scope defines the lifecycle and visibility of a bean—how many instances exist and how long they live. By default, Spring beans are singleton, but other scopes are available for specific use cases.

}

Explain @DependsOn and How It Affects Bean Initialization

In Spring, the @DependsOn annotation is used to declare that a bean must be initialized only after certain other beans have been created. By default, Spring manages bean initialization order based on dependency requirements, but in some cases, you may need explicit control.

1. How It Works

When you annotate a bean with @DependsOn("otherBean"), Spring ensures that otherBean is fully created and initialized before the annotated bean is initialized. 

@Component("beanA")
@DependsOn("beanB")
public class BeanA {
    public BeanA() {
        System.out.println("BeanA initialized after BeanB");
    }
}

@Component("beanB")
public class BeanB {
    public BeanB() {
        System.out.println("BeanB initialized first");
    }
}

In the above example, even though BeanA does not directly depend on BeanB, Spring will still initialize BeanB first because of @DependsOn.

2. Use Cases

  • When a bean indirectly depends on another bean (e.g., logging setup, cache initialization).
  • When you need to guarantee startup order for infrastructure beans like schedulers or message listeners.
  • When beans have side effects during initialization that must occur in sequence.

3. Limitations

  • @DependsOn only affects initialization order, not destruction order.
  • It should be used sparingly; prefer natural dependency injection when possible.
  • Excessive use can make the configuration harder to maintain.

4. Summary

@DependsOn is a way to enforce bean initialization order beyond what Spring’s dependency graph dictates. It’s useful for infrastructure or indirect dependencies but should be avoided for general service wiring where constructor or setter injection is a cleaner approach.

Difference Between BeanPostProcessor vs InitializingBean vs @PostConstruct

In Spring, beans go through multiple lifecycle phases. Developers can hook into these phases using BeanPostProcessor, InitializingBean, and @PostConstruct. While they may look similar, they serve different purposes and are invoked at different points.

1. BeanPostProcessor

  • An interface that allows custom logic before and after bean initialization.
  • Applies to all beans in the context, not just one bean.
  • Useful for framework-level concerns (e.g., proxies, annotation processing).
  • Methods:
    • postProcessBeforeInitialization(Object bean, String beanName)
    • postProcessAfterInitialization(Object bean, String beanName)
@Component
public class CustomBeanPostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessBeforeInitialization(Object bean, String name) {
        System.out.println("Before Init: " + name);
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        System.out.println("After Init: " + name);
        return bean;
    }
}

2. InitializingBean

  • An interface implemented by beans that need to perform custom logic after their properties are set.
  • Method: afterPropertiesSet().
  • Applies to the specific bean only.
  • Considered less flexible because it ties code to Spring API.
@Component
public class MyBean implements InitializingBean {
    @Override
    public void afterPropertiesSet() {
        System.out.println("Properties set, custom init logic here...");
    }
}

3. @PostConstruct

  • Annotation from javax.annotation (JSR-250).
  • Marks a method to be executed once after dependency injection is complete.
  • Preferred over InitializingBean because it is decoupled from Spring-specific APIs.
  • Executed only once per bean instance.
@Component
public class AnotherBean {
    @PostConstruct
    public void init() {
        System.out.println("@PostConstruct init logic...");
    }
}

4. Execution Order

  1. BeanPostProcessor.postProcessBeforeInitialization()
  2. @PostConstruct or InitializingBean.afterPropertiesSet() (custom init phase)
  3. BeanPostProcessor.postProcessAfterInitialization()

5. Summary

Coupling Spring-specific Spring-specific Standard Java annotation
Typical Use Framework extensions, proxies Custom bean init logic Custom bean init logic (preferred)

Difference Between Programmatic and Declarative Bean Wiring

In Spring, bean wiring refers to how dependencies between beans are defined and injected. There are two main approaches: programmatic wiring and declarative wiring. Both achieve the same goal but differ in how configuration is expressed and managed.

1. Programmatic Wiring

  • Dependencies are wired directly in Java code.
  • Gives full control but tightly couples beans to configuration logic.
  • Commonly used with @Configuration and @Bean methods.
  • Best when fine-grained logic is required (e.g., conditional wiring).
@Configuration
public class AppConfig {
    @Bean
    public Service service(Repository repository) {
        return new Service(repository); // Programmatic wiring
    }

    @Bean
    public Repository repository() {
        return new Repository();
    }
}

2. Declarative Wiring

  • Dependencies are defined using metadata rather than explicit code.
  • Spring handles the wiring automatically via annotations or XML configuration.
  • More concise, less boilerplate.
  • Best when dependencies follow a straightforward relationship.
@Component
public class Service {
    private final Repository repository;

    @Autowired
    public Service(Repository repository) {
        this.repository = repository; // Declarative wiring with @Autowired
    }
}

@Repository
public class Repository {}

3. Key Differences

Aspect Programmatic Wiring Declarative Wiring
Configuration Style Explicit Java code Annotations/XML metadata
Flexibility Very high (custom logic possible) Simpler, but less fine-grained
Coupling Tighter coupling to config class Looser, relies on framework
Use Case Complex conditions, dynamic beans Straightforward dependency injection

4. Summary

Use programmatic wiring when you need full control over bean creation logic, such as conditional beans or runtime decisions. Use declarative wiring when your goal is simplicity, readability, and minimal boilerplate code for standard dependencies.

What is Method Injection in Spring? (With Example)

Method Injection in Spring is a special form of dependency injection used when you need a new instance of a bean every time a method is called, even if the dependent bean is scoped as a prototype while the parent bean is a singleton.

Why is it Needed?

  • Normally, injecting a prototype bean into a singleton bean causes Spring to inject only one instance at startup.
  • If you need a fresh instance every time, constructor/setter injection is insufficient.
  • Method Injection ensures a new bean is retrieved from the container on every call.

1. Using @Lookup Annotation

// Prototype bean
@Component
@Scope("prototype")
public class Task {
    public void execute() {
        System.out.println("Executing task: " + this);
    }
}

// Singleton bean using @Lookup for method injection
@Component
public abstract class TaskService {
    
    public void runTask() {
        Task task = createTask();  // Gets a new Task each time
        task.execute();
    }

    @Lookup
    protected abstract Task createTask();
}

Here, Spring overrides the createTask() method at runtime to fetch a fresh Task instance from the ApplicationContext whenever called.

2. Using ObjectFactory / Provider

@Component
@Scope("prototype")
public class Report {
    public void generate() {
        System.out.println("Generating report: " + this);
    }
}

@Component
public class ReportService {

    @Autowired
    private ObjectFactory<Report> reportFactory;

    public void processReport() {
        Report report = reportFactory.getObject(); // Always new instance
        report.generate();
    }
}

3. Key Points

  • @Lookup is the simplest way for method injection.
  • ObjectFactory<T> and Provider<T> give more control and work without abstract methods.
  • Method Injection is mainly used for injecting prototype beans into singleton beans.

4. Summary

Method Injection allows Spring to dynamically provide new bean instances when required. It solves the problem of prototype beans inside singleton beans and is often implemented using @Lookup or ObjectFactory.

Explain Scoped Proxies and When They Are Necessary

In Spring, most beans are singleton scoped by default. However, when you inject a prototype or request/session-scoped bean into a singleton bean, you may face issues because the singleton bean will hold onto a single reference created at startup. This breaks the intended lifecycle of the shorter-lived bean.

1. What is a Scoped Proxy?

A scoped proxy is a proxy object created by Spring to stand in place of a bean with a shorter scope (prototype, request, session). Instead of directly injecting the target bean, Spring injects a proxy that knows how to fetch the correct instance at runtime, based on the current context.

2. Example Without Scoped Proxy (Problem)

@Component
@Scope("request")
public class UserRequestBean {
    private final String id = UUID.randomUUID().toString();
    public String getId() { return id; }
}

@Component
public class SingletonService {
    @Autowired
    private UserRequestBean userRequestBean;

    public void printUserId() {
        System.out.println(userRequestBean.getId());
    }
}

Here, SingletonService will always use the same UserRequestBean created at startup — even across different requests. This is incorrect for request scope.

3. Solution: Scoped Proxy

@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)
public class UserRequestBean {
    private final String id = UUID.randomUUID().toString();
    public String getId() { return id; }
}

Now, Spring injects a proxy object into the singleton. Each time a method on the proxy is called, Spring fetches the correct UserRequestBean for the current HTTP request.

4. When Are Scoped Proxies Necessary?

  • When injecting a request or session-scoped bean into a singleton bean.
  • When a prototype bean must be injected into a singleton, but you need a fresh instance every time.
  • When lifecycle scopes mismatch and direct injection would cause stale or shared references.

5. Proxy Types

  • ScopedProxyMode.INTERFACES → Creates a JDK dynamic proxy (for interfaces).
  • ScopedProxyMode.TARGET_CLASS → Creates a CGLIB subclass proxy (for classes).

6. Summary

Scoped proxies solve the problem of injecting shorter-lived beans into longer-lived beans by injecting a proxy instead of the actual object. This ensures that each method call fetches the correct instance according to the current scope (e.g., request, session, or prototype).

Difference Between @Configuration(proxyBeanMethods = true) and false

The @Configuration annotation is used to mark a class as a source of bean definitions. It has an attribute proxyBeanMethods (default: true) that determines how Spring handles method calls between @Bean methods within the same configuration class.

1. proxyBeanMethods = true (Full Mode)

  • Spring uses CGLIB to create a subclass proxy of the configuration class.
  • Calls to @Bean methods within the class go through the proxy.
  • This ensures that beans defined in the configuration class are always singletons (even if you call the @Bean method multiple times).
  • Provides **inter-bean method call management**.
@Configuration(proxyBeanMethods = true)
public class AppConfig {
    @Bean
    public ServiceA serviceA() {
        return new ServiceA(serviceB());
    }

    @Bean
    public ServiceB serviceB() {
        return new ServiceB();
    }
}

Here, even though serviceB() is called explicitly inside serviceA(), Spring intercepts the call and returns the managed singleton instance of ServiceB. Without proxying, you would get a new instance each time.

2. proxyBeanMethods = false (Lite Mode)

  • Spring does not proxy the configuration class.
  • Direct method calls between @Bean methods are treated as normal Java method calls.
  • This means a new instance may be created instead of returning the managed singleton from the container.
  • Faster startup because no CGLIB subclassing is used.
@Configuration(proxyBeanMethods = false)
public class AppConfig {
    @Bean
    public ServiceA serviceA() {
        return new ServiceA(serviceB()); // Direct call, creates a new ServiceB()
    }

    @Bean
    public ServiceB serviceB() {
        return new ServiceB();
    }
}

In this case, serviceA() gets a new instance of ServiceB every time the method is called directly. If you want container-managed singleton behavior, you must rely on Spring to inject dependencies instead of calling @Bean methods manually.

3. When to Use Which?

  • Use proxyBeanMethods = true (default) When you have interdependent @Bean methods and want Spring to manage them as singletons.
  • Use proxyBeanMethods = false When your configuration class is simple, contains independent beans, and you want faster startup (e.g., in microservices with many configurations).

4. Summary

proxyBeanMethods = true ensures that Spring proxies inter-bean calls and preserves singleton semantics, while false skips proxying for performance but may break inter-bean dependency resolution if methods call each other.

Bean Destruction in Spring: Prototype vs Singleton

In Spring, the way bean destruction is handled depends on the bean's scope. While singleton beans are managed completely by the Spring IoC container (including their destruction), prototype beans are treated differently.

1. Singleton Beans

  • Default scope in Spring.
  • Only one instance is created per ApplicationContext.
  • Spring manages the entire lifecycle: instantiation → dependency injection → destruction.
  • At shutdown (context.close()), Spring calls:
    • @PreDestroy methods
    • DisposableBean.destroy() implementation
    • Custom destroy-method defined in XML/Java config
@Component
@Scope("singleton")
public class SingletonBean {
    @PreDestroy
    public void cleanup() {
        System.out.println("Singleton bean destroyed by Spring");
    }
}

✅ Spring takes full responsibility for destroying singleton beans.

2. Prototype Beans

  • A new bean instance is created every time it is requested from the container.
  • Spring manages only instantiation and dependency injection.
  • Spring does not call destroy callbacks (@PreDestroy, DisposableBean, custom destroy-methods) for prototype beans.
  • It is the developer's responsibility to destroy prototype beans manually if needed.
@Component
@Scope("prototype")
public class PrototypeBean {
    @PreDestroy
    public void cleanup() {
        System.out.println("Prototype bean cleanup (not called by Spring!)");
    }
}

✅ To clean up resources for prototype beans, you must manage destruction manually.

3. Key Differences

Aspect Singleton Prototype

Destroy Callbacks Invoked automatically at shutdown Not invoked by Spring
Responsibility Spring cleans up Developer must clean up manually

4. Practical Example

// Singleton cleanup is automatic
context.close(); // triggers @PreDestroy for singletons

// Prototype cleanup must be manual

Core Components for Dependency Injection in Spring

Spring uses BeanFactory and ApplicationContext as the core containers for managing beans.

BeanFactory

  • The simplest container, responsible for creating and managing beans.
  • Lazily instantiates beans (only when requested).

ApplicationContext

  • A more advanced container, extending BeanFactory.
  • Eagerly instantiates singleton beans by default.
  • Provides additional features like event publishing, internationalization (i18n), and AOP integration.

Beans are simply objects managed by Spring. Each bean has a definition (class, scope, dependencies) stored in the container.

How Spring Resolves Dependencies at Runtime

Spring resolves bean dependencies automatically at runtime by following these steps:

  • Bean Definition: Spring scans the application context for beans, i.e., classes annotated with @Component, @Service, @Repository, or beans declared in @Configuration via @Bean.
  • Dependency Graph: Spring builds a graph of all beans and their dependencies.
  • Injection: When a bean is created, Spring automatically injects the required dependencies from the context using constructor, setter, or field injection.
  • Lifecycle Management: Spring manages the bean lifecycle, including initialization and destruction callbacks.

Different Ways to Inject Beans in Spring

Spring provides multiple ways to inject dependencies (beans) into your components. Choosing the right method improves readability, testability, and maintainability.

1️⃣ Field Injection

Directly inject a bean into a class field using @Autowired. Simple but less testable. 

@Component
public class OrderService {

    @Autowired
    private PaymentService paymentService;

    public void processOrder() {
        paymentService.pay();
    }
}

⚠️ Field injection is discouraged in large projects because it hides dependencies and makes unit testing harder.

2️⃣ Constructor Injection

Inject beans via the class constructor. Preferred for immutability and testability. 

@Component
public class OrderService {

    private final PaymentService paymentService;

    @Autowired
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void processOrder() {
        paymentService.pay();
    }
}

✅ Recommended method for most Spring applications. Dependencies are explicit and easy to test.

3️⃣ Setter Injection

Inject beans via a setter method. Useful when dependencies are optional or need to be changed after object creation. 

@Component
public class OrderService {

    private PaymentService paymentService;

    @Autowired
    public void setPaymentService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void processOrder() {
        paymentService.pay();
    }
}

⚠️ Setter injection allows mutability but is less preferred for mandatory dependencies.

4️⃣ Using @Qualifier with Any Injection Type

When multiple beans of the same type exist, use @Qualifier to specify which bean to inject. 

@Autowired
@Qualifier("stripePaymentService")
private PaymentService paymentService;

Works with field, constructor, or setter injection to explicitly select the desired bean.

5️⃣ @Resource and @Inject (JSR-250 / JSR-330)

  • @Resource(name="beanName") – Injects by bean name (JSR-250 standard).
  • @Inject – Equivalent to @Autowired (JSR-330 standard), can be combined with @Named for selection. 
@Resource(name="stripePaymentService")
private PaymentService paymentService;

Useful when working with standard Java EE annotations or migrating legacy code.

By default constructor

By annotated constructor (@Autowired constructor)

For each dependency:

Setter injection

Field injection (Reflection)

Constructor injection: circular dependencies will fail (because the bean must be fully constructed first).

postProcessAfterInitialization()

@Autowired injection

@Value property injection

@Transactional proxy creation

Singleton beans are now fully ready for use.

Bean is returned whenever getBean() is called from the container.

Dependencies are already injected.

When to Use Each Type of Dependency Injection in Spring

1. Constructor Injection – “The Safe Choice”

  • When to use: Dependency is mandatory, you want immutable dependencies (final fields), and easy unit testing.
  • When not to use: Circular dependencies exist (A → B → A), constructor injection will fail.
  • Example: 
    @Service
public class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

2. Setter Injection – “Flexible & Optional”

  • When to use: Dependency is optional, allows circular dependencies, or may change after bean creation.
  • When not to use: Mandatory dependencies (can cause runtime errors if setter is not called).
  • Example: 
    @Service
public class ReportService {
    private EmailService emailService;

    @Autowired
    public void setEmailService(EmailService emailService) {
        this.emailService = emailService;
    }
}

3. Field Injection – “Quick & Dirty”

  • When to use: Prototyping or very small apps; minimal boilerplate code.
  • When not to use: Production code; testable, maintainable, or immutable code.
  • Example: 
    @Service
public class UserService {
    @Autowired
    private UserRepository userRepository;
}

Constructor vs Field Injection in Spring

1. Constructor Injection – Why It’s Preferred

  • Guarantees Mandatory Dependencies: Dependencies are declared in the constructor, so Spring must provide them. 
    @Service
public class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
  • Immutable Dependencies: Fields can be declared final, ensuring they cannot change after creation.
  • Better for Testing: You can pass mocks directly without Spring context: 
    OrderService service = new OrderService(new MockPaymentService());
  • Detects Circular Dependencies Early: Constructor injection fails at context startup if a circular dependency exists, forcing better design.

2. Field Injection – Why It’s Less Preferred

  • Hidden Dependencies: Injected directly into fields with @Autowired, making dependencies less obvious.
  • Harder to Test: Cannot pass mocks easily without reflection or Spring’s test context.
  • Mutable Dependencies: Fields are not final and can be accidentally reassigned.
  • Circular Dependencies Hidden: Circular dependencies may appear at runtime, causing hard-to-debug issues.

Boilerplate Moderate Very low

Key Takeaway: Constructor injection is preferred because it creates safe, testable, maintainable, and immutable code. Field injection is easier but less safe, mostly suitable for small prototypes or legacy code.

Performance Implications: Constructor Injection vs Setter Injection

Both constructor injection and setter injection are ways Spring resolves dependencies, but they have subtle differences in performance, design, and lifecycle behavior.

🔹 Constructor Injection

  • Eager Initialization: All dependencies must be provided at object creation.
  • Performance: Slightly faster at runtime since dependencies are fully initialized during construction (no extra setter calls).
  • Thread Safety: Better immutability guarantees — once constructed, dependencies cannot change.
  • Downside: For beans with many dependencies, constructors can become very large (“constructor bloat”).

🔹 Setter Injection

  • Lazy Flexibility: Dependencies can be injected after object creation.
  • Performance: Involves extra setter calls after instantiation, but overhead is negligible in most applications.
  • Mutability: Dependencies can be changed later, which may lead to runtime inconsistencies.
  • Optional Dependencies: Useful when some beans are not mandatory.

📊 Performance Comparison

Aspect Constructor Injection Setter Injection
Initialization At object creation (eager) After creation (lazy)
Runtime Performance Slightly faster (no setter overhead) Negligible overhead due to setter calls
Immutability Strong — dependencies cannot change Weaker — dependencies can be modified
Use Case Mandatory dependencies Optional dependencies

🔑 Key Points

  • Performance difference is negligible in practice — both are efficient.
  • Constructor injection is preferred for mandatory dependencies and immutability.
  • Setter injection is better for optional or late-bound dependencies.
  • Best practice: use constructor injection by default, setter injection only when necessary.

Required vs Optional Dependencies in Spring DI

In Spring Dependency Injection, dependencies can be required or optional. Understanding the difference helps in designing safe and flexible beans.

1. Required Dependencies

  • Must be provided for the bean to function correctly.
  • Spring will throw an exception at startup if the dependency is missing.
  • Best injected via constructor injection to ensure immutability and mandatory enforcement.

    @Service

}

  • Not required for the bean to function; the bean can operate without it.

  • Best injected via setter injection or field injection if flexibility is desired.

        this.emailService = emailService;
    }
}

✅ Key takeaway: Use required dependencies for critical beans that cannot function without them, and optional dependencies for features that are not always needed.

Can Spring Inject Dependencies into a Final Class or Method?

In Spring, dependency injection is often achieved using CGLIB proxies or Java dynamic proxies. The behavior depends on whether the target class or method is marked as final.

🔹 Final Class

  • CGLIB proxies subclass the target class to inject dependencies.
  • If the class is final, subclassing is not possible.
  • Result: Spring cannot use CGLIB to inject proxies into a final class.
  • Solution: Use interface-based injection with Java dynamic proxies or avoid marking the class as final.

🔹 Final Method

  • CGLIB cannot override final methods.
  • If a dependency is injected via a final method (setter or bean initialization), proxy-based behavior (like AOP) will not work for that method.
  • Field injection still works because Spring can directly set the field via reflection.

🔑 Key Points

  • Spring cannot inject dependencies via proxy into final classes or final methods.
  • Field injection (@Autowired) works even for final methods or final classes.
  • For AOP (method interception), avoid final classes and final methods.

Example

@Component
public final class FinalService {  // ❌ Spring cannot create a proxy
    @Autowired
    private Dependency dep; // ✅ Field injection works
}

@Component
public class MyService {
    @Autowired
    public final void setDep(Dependency dep) { // ❌ Proxy-based injection or AOP won't work
        this.dep = dep;
    }
}

Can Spring Inject a Dependency into a Static Field?

No, Spring cannot inject dependencies directly into static fields because dependency injection in Spring is based on object instances. Static fields belong to the class itself, not to an instance of the class. Since Spring manages beans as instances within the ApplicationContext, it cannot inject into static fields using the usual @Autowired mechanism.

🔹 Why Not?

  • Instance vs Class: Spring creates and manages bean instances, but static fields are tied to the class, not an instance.
  • Lifecycle Management: Spring’s lifecycle management does not apply to static members.
  • Testing & Flexibility: Static injection reduces flexibility and makes unit testing harder.

🔹 Workarounds

Although not recommended, you can indirectly assign dependencies to static fields: 

@Component
public class MyService {
    private static Dependency dependency;

    @Autowired
    public void setDependency(Dependency dep) {
        MyService.dependency = dep; // Assigning to static field via setter
    }

    public static void useDependency() {
        dependency.doSomething();
    }
}

🔑 Key Points

  • Spring does not support direct injection into static fields.
  • Use setter injection to assign values to static fields if absolutely necessary.
  • Avoid static dependency injection for better design, testability, and maintainability.

How does Spring resolve ambiguity when multiple beans of the same type are available, and neither @Primary nor @Qualifier is specified?

When multiple beans of the same type exist in the Spring ApplicationContext and no @Primary or @Qualifier is specified, Spring faces ambiguity because it cannot decide which bean to inject. In such cases:

  • At startup, Spring throws a NoUniqueBeanDefinitionException.
  • The exception message lists all candidate beans of that type.

This ensures that injection is explicit and avoids accidental selection of the wrong bean.

🔹 Example

@Component
class ServiceA implements MyService {}

@Component
class ServiceB implements MyService {}

@Component
class Client {
    @Autowired
    private MyService myService; // ❌ Ambiguity: Which one to inject?
}

👉 This will fail with NoUniqueBeanDefinitionException because both ServiceA and ServiceB implement MyService.

✅ Solutions

  • Use @Primary on one bean to mark it as the default.
  • Use @Qualifier to specify which bean to inject.
  • Inject a List<MyService> or Map<String, MyService> if multiple beans are expected.

What strategies would you use to break a circular dependency in Spring?

A circular dependency occurs when two or more beans depend on each other, directly or indirectly, creating a loop that Spring cannot resolve during dependency injection.

🔹 Example of Circular Dependency

@Component
class ServiceA {
    @Autowired
    private ServiceB serviceB;
}

@Component
class ServiceB {
    @Autowired
    private ServiceA serviceA;
}

👉 Here, ServiceA depends on ServiceB, and ServiceB depends on ServiceA. Spring will fail to initialize these beans due to a circular reference.

✅ Strategies to Break Circular Dependencies

  • @Lazy Injection: Delay the creation of one dependency until it is actually needed. 
    @Component
class ServiceA {
    @Autowired
    @Lazy
    private ServiceB serviceB;
}
    This defers initialization of ServiceB until it is accessed.
  • Use Setter Injection: Instead of constructor injection, use setter injection for one of the beans to allow Spring to instantiate objects before setting dependencies. 
    @Component
class ServiceA {
    private ServiceB serviceB;

    @Autowired
    public void setServiceB(ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}
  • Refactor the Design: Often, circular dependencies indicate a poor design. Extract common functionality into a third bean that both services can depend on.
  • Use Interfaces + Event Listeners: Instead of direct dependencies, decouple the beans with an interface or use ApplicationEventPublisher to communicate between them.
  • Provider / ObjectFactory Injection: Use ObjectFactory<T> or Provider<T> to lazily resolve dependencies at runtime. 
    @Component
class ServiceA {
    @Autowired
    private ObjectFactory<ServiceB> serviceBFactory;

    public void call() {
        ServiceB serviceB = serviceBFactory.getObject();
        serviceB.doSomething();
    }
}

⚡ Key Takeaway

Circular dependencies can sometimes be solved with Spring features like @Lazy or ObjectFactory, but the best long-term solution is often a design refactor to remove the cyclic relationship.

How does Spring manage dependency injection for beans with different lifecycle scopes (singleton, prototype, request, session)?

Spring provides multiple bean scopes that define how long a bean instance lives within the container. Dependency Injection (DI) behavior changes based on the scope of both the dependent bean and the dependency itself.

🔹 Bean Scopes in Spring

  • Singleton (default): One shared instance per Spring container.
  • Prototype: A new instance is created every time it is requested.
  • Request: One instance per HTTP request (web-aware context only).
  • Session: One instance per HTTP session (web-aware context only).

✅ How DI Works with Different Scopes

  • Singleton → Singleton: Spring creates a single instance of the dependency and injects it into all singleton beans.
  • Singleton → Prototype: Only one prototype bean is injected at context initialization. Subsequent calls on the singleton will still use that same instance.
    ⚠️ To truly get a new prototype instance each time, use:
    • @Lookup method injection
    • ObjectFactory<T> or Provider<T>
    • ScopedProxyMode.TARGET_CLASS
  • Singleton → Request / Session: By default, not allowed, because a singleton is created outside the HTTP context. To inject request/session beans into a singleton, Spring uses scoped proxies, which act as placeholders and resolve the correct instance at runtime.
  • Prototype → Prototype: Each dependency is a fresh object when injected.
  • Request / Session → Request / Session: Spring provides one instance per HTTP scope and wires them correctly into the beans within the same scope.

🔧 Example: Singleton with Prototype

@Component
class SingletonService {
    @Autowired
    private ObjectFactory<PrototypeService> prototypeFactory;

    public void process() {
        PrototypeService prototype = prototypeFactory.getObject();
        prototype.doWork();
    }
}

Here, every call to process() fetches a new prototype instance.

⚡ Key Takeaways

  • Singleton is efficient but may cache dependencies unintentionally.
  • Prototype beans need special handling when injected into singletons.
  • Request and Session scopes require web-aware context and usually use proxies.
  • Choosing the right scope ensures correct lifecycle management and avoids memory leaks.

If you inject a prototype bean into a singleton bean, what issues can arise and how do you solve them?

By default, Spring creates singleton beans at container startup and injects all required dependencies eagerly. If one of those dependencies is a prototype bean, Spring resolves it only once during injection. As a result, the singleton bean will always use the same prototype instance, which defeats the purpose of the prototype scope.

⚠️ Problem

  • The prototype bean is instantiated only once when injected into the singleton.
  • Every method call on the singleton uses the same prototype instance.
  • This breaks the expectation that a prototype bean should be a new instance per usage.

🔧 Solutions

Spring provides multiple strategies to solve this issue:

  1. Use ObjectFactory<T>: This allows the singleton to request a fresh prototype instance each time. 
    @Component
class SingletonService {
    @Autowired
    private ObjectFactory<PrototypeService> prototypeFactory;

    public void process() {
        PrototypeService prototype = prototypeFactory.getObject();
        prototype.doWork();
    }
}
  2. Use Provider<T> (JSR-330): Similar to ObjectFactory but with a cleaner API. 
    @Component
class SingletonService {
    @Autowired
    private Provider<PrototypeService> prototypeProvider;

    public void process() {
        PrototypeService prototype = prototypeProvider.get();
        prototype.doWork();
    }
}
  3. Use @Lookup Method Injection: Spring overrides the annotated method at runtime to return a fresh prototype. 
    @Component
class SingletonService {
    public void process() {
        PrototypeService prototype = getPrototypeService();
        prototype.doWork();
    }

    @Lookup
    protected PrototypeService getPrototypeService() {
        return null; // overridden by Spring
    }
}
  4. Use Scoped Proxy: Spring creates a proxy for the prototype bean. Each method call on the proxy delegates to a new prototype instance. 
    @Component
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
class PrototypeService {
    public void doWork() {
        System.out.println("Working with: " + this);
    }
}

    When injected, the proxy ensures that each call resolves a new PrototypeService.

⚡ Key Takeaways

  • Direct injection of prototype beans into singletons does not work as expected.
  • Use ObjectFactory, Provider, or @Lookup for on-demand lookups.
  • Use ScopedProxyMode when working with request/session scoped beans.
  • Choosing the right strategy depends on performance needs and code readability.

How does Spring handle dependency injection when using Java-based configuration (@Configuration + @Bean) vs Component scanning (@Component, @Service, etc.)?

Spring supports two primary ways of registering beans in the ApplicationContext: Java-based configuration using @Configuration and @Bean, and Component scanning using stereotypes like @Component, @Service, @Repository, and @Controller.

1. Java-based Configuration (@Configuration + @Bean)

In this approach, beans are explicitly declared in a @Configuration class using @Bean methods. Spring calls these methods to instantiate and wire beans. 

@Configuration
public class AppConfig {
    @Bean
    public UserService userService() {
        return new UserService(orderService());
    }

    @Bean
    public OrderService orderService() {
        return new OrderService();
    }
}

✅ Explicit control over bean creation, lifecycle, and dependencies. ✅ Good for integrating third-party classes (not annotated with Spring stereotypes). ❌ More boilerplate compared to scanning.

2. Component Scanning (@Component, @Service, etc.)

In this approach, classes are annotated with stereotypes and automatically detected during classpath scanning. Spring instantiates these beans and wires dependencies using @Autowired, @Inject, or constructor injection. 

@Service
public class UserService {
    private final OrderService orderService;

    @Autowired
    public UserService(OrderService orderService) {
        this.orderService = orderService;
    }
}

@Repository
public class OrderService { }

✅ Less boilerplate (automatic scanning and wiring). ✅ Better suited for large projects with many beans. ❌ Less explicit; may cause ambiguity when multiple beans of the same type exist.

3. Key Differences

Aspect Java-based Config Component Scanning
Bean Declaration Explicit via @Bean methods Automatic via annotations
Control Full control over instantiation Limited; mostly automated
Best Use Case Third-party libraries, fine-grained control Large-scale applications with many beans
Ambiguity Low – beans are explicitly defined Possible if multiple beans of same type exist

⚡ Key Takeaway

Use @Configuration + @Bean when you need explicit control or work with external libraries. Use @Component scanning for most application beans to reduce boilerplate. In real-world applications, both approaches are often combined.

How does DI behave with @Lazy beans in Spring? What is a real-world use case for using @Lazy?

By default, Spring eagerly initializes singleton beans at application startup. When you annotate a bean with @Lazy, Spring defers its instantiation until it is actually requested for the first time. For dependency injection, this means that instead of creating the actual bean at startup, Spring injects a lightweight proxy. When the bean’s method is invoked, the proxy triggers initialization of the real bean.

1. Basic Example

@Component
class HeavyService {
    public HeavyService() {
        System.out.println("HeavyService initialized!");
    }
}

@Component
class ClientService {
    private final HeavyService heavyService;

    public ClientService(@Lazy HeavyService heavyService) {
        this.heavyService = heavyService;
    }

    public void run() {
        System.out.println("Running ClientService");
        heavyService.toString(); // HeavyService gets created here
    }
}

👉 Without @Lazy, HeavyService would be created at startup. 👉 With @Lazy, it is created only when heavyService is first accessed.

2. Bean-Level vs Dependency-Level

  • @Lazy on a @Bean or @Component → whole bean is lazily initialized.
  • @Lazy on a constructor/setter/field → only that dependency is lazily injected, not the entire bean.

3. Real-World Use Cases

  • Breaking Circular Dependencies – If two beans depend on each other, annotating one with @Lazy allows Spring to inject a proxy instead of failing.
  • Optimizing Startup Time – For beans that are expensive to create (e.g., connecting to a third-party API, loading a huge dataset), @Lazy ensures they are only initialized when actually needed.
  • Rarely Used Services – For example, an admin-only reporting module doesn’t need to load at startup, saving resources until requested.

⚡ Key Takeaway

- @Lazy beans are created on demand, not at startup. - DI injects a proxy first, then resolves the real bean only when needed. - Best for breaking circular dependencies, improving startup performance, and delaying costly initializations.

Explain the role of BeanPostProcessor and BeanFactoryPostProcessor in Dependency Injection

Spring provides two important extension points to customize the behavior of beans during the Dependency Injection lifecycle: BeanPostProcessor and BeanFactoryPostProcessor. Both are part of the Spring container lifecycle, but they work at different stages.

1. BeanFactoryPostProcessor

A BeanFactoryPostProcessor runs before any beans are created. It allows you to modify the BeanDefinition metadata (like scope, property values, etc.) that the container uses to instantiate beans. 

@Component
class MyBeanFactoryPostProcessor implements BeanFactoryPostProcessor {
    @Override
    public void postProcessBeanFactory(ConfigurableListableBeanFactory beanFactory) {
        BeanDefinition bd = beanFactory.getBeanDefinition("myService");
        bd.setScope(BeanDefinition.SCOPE_PROTOTYPE); // change scope dynamically
    }
}

👉 Used to change bean definitions before beans are instantiated. 👉 Typical use cases: property overrides, scope modifications, conditional configurations.

2. BeanPostProcessor

A BeanPostProcessor runs after beans are instantiated but before they are returned for use. It allows you to modify or wrap bean instances (e.g., creating proxies, applying decorators). 

@Component
class MyBeanPostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        if (bean instanceof MyService) {
            System.out.println("Before init: " + beanName);
        }
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if (bean instanceof MyService) {
            System.out.println("After init: " + beanName);
        }
        return bean;
    }
}

👉 Used to apply custom logic before and after bean initialization. 👉 Typical use cases: AOP proxy creation, annotation handling (like @Autowired, @Transactional), or wrapping beans with decorators.

How does DI interact with Spring AOP proxies? Can you face issues when injecting beans that are wrapped in proxies?

In Spring, when a bean is advised by an AOP aspect, it is not injected directly. Instead, Spring creates a proxy object that wraps the original bean and injects the proxy into the dependent beans. This proxy intercepts method calls and applies cross-cutting concerns like logging, transactions, or security.

1. How DI Works with Proxies

  • Proxy Creation: Spring creates a proxy (JDK dynamic proxy or CGLIB subclass) instead of injecting the actual target bean.
  • Dependency Injection: When another bean requires this dependency, Spring injects the proxy reference.
  • Method Interception: Calls on the proxy are intercepted and advice (e.g., @Transactional, @Cacheable) is applied.

2. Potential Issues

  • Self-invocation Problem: If a bean calls its own method internally, the call bypasses the proxy, so the advice (like @Transactional) is not applied.
  • Casting Errors: JDK proxies can only proxy interfaces. If you inject a proxy and cast it to a concrete class, you get ClassCastException.
  • Equals / HashCode: Proxies may not behave identically to the original bean in terms of identity checks.
  • Serialization Issues: Proxies may not be serializable even if the target class is.

3. Example

@Service
public class PaymentService {
    @Transactional
    public void processPayment() {
        // transaction will apply
        validate();
    }

    public void validate() {
        // if called internally, proxy is bypassed -> no transaction advice
    }
}

Here, calling validate() from within processPayment() does not go through the proxy, so transactional advice is skipped.

4. Solutions

  • Use AopContext.currentProxy() 
    ((PaymentService) AopContext.currentProxy()).validate();
    Requires exposeProxy=true in @EnableAspectJAutoProxy.
  • Refactor into Separate Bean: Move the advised method into another bean, so DI injects the proxy properly.
  • Force CGLIB Proxies: Use @EnableAspectJAutoProxy(proxyTargetClass = true) to avoid interface-only proxies.
  • Use Interfaces for Proxies: Prefer coding against interfaces to avoid casting issues.

⚡ Key Takeaway

Spring DI injects proxy objects when beans are wrapped with AOP. The main issue arises in self-invocation and casting. Solutions include using AopContext, refactoring into multiple beans, or forcing class-based proxies.

Can dependency injection fail because of classloader issues in modular applications? If yes, how do you debug it?

Yes, dependency injection can fail due to classloader issues in modular applications (like Java 9+ modules, OSGi, or microservices with isolated classpaths). Spring relies on reflection to discover and inject beans. If a class is not visible to the application’s classloader, DI can break.

1. Why Classloader Issues Occur?

  • Multiple Classloaders: Different modules/jars loaded by separate classloaders.
  • Module Restrictions: In Java 9+, packages must be explicitly exported using module-info.java.
  • OSGi / Containers: Bundles may not share classes across boundaries.
  • Duplicate Classes: Same class name loaded by different classloaders (causing ClassCastException).

2. Common Symptoms

  • NoSuchBeanDefinitionException → Spring cannot find the bean definition.
  • ClassNotFoundException → Required class is missing from classpath.
  • NoClassDefFoundError → Class was present at compile time but not at runtime.
  • ClassCastException → Bean is loaded by a different classloader than expected.

3. Debugging Steps

  1. Enable Debug Logs: 
    logging.level.org.springframework=DEBUG
logging.level.org.springframework.beans.factory=TRACE
  2. Print Classloaders: Log which classloader loaded a class. 
    System.out.println(MyService.class.getClassLoader());
  3. Check Module Declarations: In module-info.java, ensure required packages are exported: 
    module my.app {
    requires spring.context;
    exports com.myapp.service;
}
  4. Verify Dependencies: Ensure no duplicate jars in classpath or modulepath.
  5. Use Context ClassLoader: In multi-threaded environments, set the correct classloader: 
    Thread.currentThread().setContextClassLoader(this.getClass().getClassLoader());

4. Best Practices to Avoid Issues

  • Use Spring Boot fat jars (isolates classpath management).
  • For Java modules, export required packages in module-info.java.
  • Avoid class duplication across modules.
  • Use @ComponentScan only in packages where classes are accessible.
  • In OSGi, ensure bundles import/export packages correctly.

⚡ Key Takeaway

Dependency Injection can fail if Spring cannot see or load a class due to classloader boundaries. Debugging involves inspecting logs, checking class visibility, and ensuring proper module/package exports. Correct configuration of module-info.java, classpath, and Spring scanning prevents most issues.

What happens if a bean required via DI is not available in the ApplicationContext at runtime?

In Spring, when a bean is requested for dependency injection, the container must find it in the ApplicationContext. If the bean is missing, the behavior depends on @Autowired configuration, the DI style, and Spring’s fail-fast policy.

1. Default Behavior

  • By default, @Autowired is required = true. If the bean is missing, Spring throws a NoSuchBeanDefinitionException during context startup.
  • This is part of Spring’s fail-fast mechanism to avoid running with broken dependencies.

  • @Autowired(required = false) → Injection is skipped if the bean is not found.
  • Optional<T> → Allows injection of an Optional.empty() when bean is missing.

    private EmailService emailService;

    @Autowired(required = false)

    @Autowired
    private Optional pushService;
}

4. Real-World Use Case

In microservices, some beans (like messaging or caching) may only be needed in certain environments. Using Optional or @ConditionalOnProperty ensures flexibility without breaking startup in environments where those beans aren’t defined.

By default, Spring fails fast if a required bean is missing. To handle optional dependencies, use @Autowired(required = false), Optional<T>, or @Nullable, and for environment-specific beans, use @Conditional or @Profile.

How do you inject dependencies in a record class (Java 16+)? Is there any limitation compared to normal classes?

In Java 16+, record classes are immutable data carriers. Since they provide a canonical constructor automatically, Spring can use that constructor for constructor-based dependency injection. This makes record classes suitable for DI, but with some important limitations.

1. How Injection Works with Records

  • Spring detects the canonical constructor of the record.
  • Dependencies are injected through that constructor.
  • Since fields in a record are final and automatically set, no field injection or setter injection is possible.

2. Example

@Service
public record OrderService(PaymentService paymentService, 
                           InventoryService inventoryService) {

    public void placeOrder(String productId) {
        if (inventoryService.isAvailable(productId)) {
            paymentService.charge(productId);
        }
    }
}

Here, OrderService is a record, and Spring automatically injects PaymentService and InventoryService into its constructor.

3. Limitations Compared to Normal Classes

  • No field/setter injection → Only constructor injection is possible.
  • Immutability → Once dependencies are injected, they cannot be changed (unlike normal beans with setters).
  • No custom constructors alongside canonical constructor → If you want custom initialization logic, you must use a compact constructor inside the record.
  • Proxies and AOP → Records are final, which means CGLIB proxying may fail if Spring needs to subclass them. Only JDK dynamic proxies (interfaces) are safe for AOP.

4. Real-World Use Case

Records are well-suited for stateless services, DTOs, and configuration property holders. For example, using @ConfigurationProperties with a record provides immutable, type-safe configuration binding in Spring Boot.

⚡ Key Takeaway

You can inject dependencies into record classes using their canonical constructor, but only constructor injection is supported. Records are great for immutability and clean DI, but they cannot be proxied easily and don’t support mutable patterns like setter injection.

How does Spring support optional dependencies? When would you prefer Optional<T> vs @Autowired(required=false)?

In Spring, not all dependencies are mandatory. Sometimes you want a bean to be injected only if it exists in the ApplicationContext. Spring supports this requirement through different mechanisms: @Autowired(required = false), @Nullable, and Optional<T>.

1. Using @Autowired(required = false)

@Service
public class NotificationService {

    @Autowired(required = false)
    private EmailService emailService;

    public void notifyUser(String msg) {
        if (emailService != null) {
            emailService.send(msg);
        } else {
            System.out.println("Email service not available.");
        }
    }
}

Here, if EmailService bean is not defined, the field will simply remain null. This is straightforward but requires null checks.

2. Using @Nullable

@Service
public class NotificationService {

    private final EmailService emailService;

    public NotificationService(@Nullable EmailService emailService) {
        this.emailService = emailService;
    }
}

With @Nullable, Spring can inject null if the dependency is missing. This works well with constructor injection.

3. Using Optional<T>

@Service
public class NotificationService {

    private final Optional<EmailService> emailService;

    public NotificationService(Optional<EmailService> emailService) {
        this.emailService = emailService;
    }

    public void notifyUser(String msg) {
        emailService.ifPresent(service -> service.send(msg));
    }
}

Using Optional is more expressive and eliminates explicit null checks. It clearly conveys that the dependency may or may not exist.

4. When to use what?

  • @Autowired(required = false): Simple cases, especially for field injection. But may lead to hidden null pointer issues.
  • @Nullable: Preferable with constructor injection for clarity, but still relies on null.
  • Optional<T>: Best when you want explicit semantics that a dependency is optional and avoid null checks. It works well with modern Java practices.

⚡ Key Takeaway

Use Optional<T> whenever possible for readability and to clearly indicate optionality. @Autowired(required = false) and @Nullable are legacy-friendly but rely on null handling, which is less safe.

How does Spring’s DI differ from Jakarta CDI (Contexts and Dependency Injection)?

Both Spring Dependency Injection (DI) and Jakarta CDI (Contexts and Dependency Injection) provide dependency management and lifecycle handling, but they have different philosophies, specifications, and ecosystems.

  • Spring: singleton, prototype, request, session, application, websocket.
  • CDI: @ApplicationScoped, @RequestScoped, @SessionScoped, @Dependent (default), @ConversationScoped.

4. Ecosystem

  • Spring: Rich ecosystem (Spring Boot, Spring Data, Spring Security, Spring Cloud) and widely used in microservices and standalone apps.
  • CDI: Primarily used in Jakarta EE / Java EE applications, often integrated with JPA, JSF, JAX-RS, etc.

5. Bean Discovery

  • Spring: Component scanning and Java-based configuration (@Configuration + @Bean) or XML.
  • CDI: Bean discovery is automatic if beans.xml is present. Producers (@Produces) are used for custom beans.

6. Integration & Portability

  • Spring: Independent of application server; runs anywhere (Tomcat, Jetty, standalone, cloud).
  • CDI: Tightly integrated with Jakarta EE servers (WildFly, Payara, GlassFish).

    @Autowired
    private PaymentService paymentService;
}

CDI

    private PaymentService paymentService;

How can you inject a collection of beans into a single bean?

In Spring, sometimes you want a single bean to work with multiple implementations of an interface or multiple beans of the same type. Spring allows injecting collections such as List, Set, or Map of beans automatically.

Spring will inject all beans of the specified type into a List in the order they are defined in the context. 

public interface PaymentProcessor {

}

What is a Proxy in Spring?

In Spring, a proxy is a wrapper object around a real bean. It intercepts method calls to add extra behavior before or after the actual method executes. This allows Spring to provide additional features transparently.

Common Uses of Proxies:

  • @Transactional - managing transactions
  • @Cacheable - caching method results
  • @Async - executing methods asynchronously
  • Lazy-initialized beans

Key point: When Spring injects a bean into another bean, it may inject a proxy instead of the real object. This allows Spring to add additional logic transparently without changing your code.

Two Types of Proxies in Spring

a) Java Dynamic Proxy

Uses Java’s built-in java.lang.reflect.Proxy. Requirement: Bean must implement at least one interface.

How it works:

  • Proxy implements the same interface(s) as the original bean.
  • Method calls on the proxy are intercepted by an InvocationHandler.
  • The handler can execute additional logic before/after delegating to the real bean.

Example:

  • Interface: UserService
  • Real Bean: UserServiceImpl
  • Proxy: UserServiceImplProxy implements UserService
  • @Transactional on an interface method → proxy starts transaction before calling the real method and commits/rolls back after.

b) CGLIB Proxy

Uses CGLIB (Code Generation Library) to create a subclass of the bean at runtime. Requirement: The bean does not need an interface.

How it works:

  • Creates a subclass of the original bean.
  • Overrides methods to insert extra logic.
  • Calls the original method from the overridden method.
  • Can intercept any non-final method.

Example:

  • Original class: UserService
  • Proxy class: UserService$$EnhancerByCGLIB
  • Often used when the bean does not implement an interface or when proxyTargetClass=true.

How Proxies Work with Dependency Injection

During bean creation, Spring detects if a bean needs proxying (e.g., has @Transactional).

Spring creates a proxy object instead of the actual bean:

  • Java dynamic proxy (for interface-based beans)
  • CGLIB proxy (for class-based beans)

Dependency Injection: When another bean needs this bean:

@Autowired
private UserService userService;

Spring injects the proxy instead of the real object. When a method is called on the proxy:

  1. Pre-processing: e.g., start transaction
  2. Original method execution: call the real bean method
  3. Post-processing: e.g., commit/rollback transaction

How Dependency Injection and Proxies Work Together

During dependency injection, Spring injects the proxy object into dependent beans instead of the real object. This allows Spring to intercept method calls and apply AOP features transparently.

Example:

@Service
public class UserService {
    @Transactional
    public void saveUser(User user) { ... }
}

@Service
public class AdminService {
    @Autowired
    private UserService userService; // actually a proxy
}

When AdminService calls userService.saveUser(), the call is intercepted by the proxy, and transaction management is applied automatically.

Managing Bean Scopes in a Large Multi-Threaded Spring System

1️⃣ Spring Bean Scopes Overview

Spring provides different bean scopes to control lifecycle and visibility:

Scope Description Typical Use
Singleton One shared instance per Spring context (default) Stateless services, utilities
Prototype New instance every time it is requested Stateful temporary objects
Request One instance per HTTP request (web apps) Web controllers, request-specific data
Session One instance per HTTP session (web apps) User session-specific data
Application One instance per ServletContext Global web application state

2️⃣ Challenges in Multi-Threaded Environments

  • Singleton beans are shared → must be stateless or thread-safe.
  • Prototype beans → careful injection when used inside singletons.
  • Request/Session beans → only valid in web-aware threads, not in background tasks.
  • Shared mutable state → risk of race conditions and inconsistent behavior.

3️⃣ Best Practices

a) Keep Singletons Stateless

All shared beans should avoid mutable state. Use local variables or ThreadLocal for per-thread data.

b) Use Prototype Beans Carefully


@Component
public class SingletonService {
    
    @Autowired
    private ObjectProvider<PrototypeBean> prototypeBeanProvider;

    public void performTask() {
        PrototypeBean bean = prototypeBeanProvider.getObject(); // New instance
        bean.doSomething();
    }
}

c) Thread-Local for Per-Thread State


private static ThreadLocal<UserContext> threadUserContext = ThreadLocal.withInitial(() -> null);

Clear ThreadLocal after use to avoid memory leaks.

d) Request/Session Scope in Web Applications

Use @Scope("request") or @Scope("session") for web request/session-specific beans. In async tasks, use RequestContextListener to propagate attributes.

e) Use Immutable Objects

Prefer immutable objects for shared state to avoid concurrency issues.

4️⃣ Tools & Techniques

  • Spring Proxy Mode for prototype-in-singleton beans: @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
  • Synchronized methods, locks, or atomic variables for shared mutable state.
  • Use TaskExecutor or @Async for background threads, ensure thread-safe bean usage.

5️⃣ Summary

  • Singleton beans → stateless and thread-safe.
  • Prototype beans → use ObjectProvider or proxy mode when injected into singletons.
  • Request/Session beans → safe in web threads only.
  • Always prefer immutable objects or proper synchronization for shared state.
  • Async tasks → ensure proper scope and thread safety.

Response Content Handling in Spring (JSON & XML)

In Spring Boot / Spring MVC, response formats such as JSON, XML, or plain text are handled using Content Negotiation and HttpMessageConverter. This mechanism automatically converts Java objects into the correct response type based on the client request.

1️⃣ Content Negotiation

Spring decides which format (JSON, XML, HTML, etc.) to return based on the following:

  • Accept Header: Accept: application/json or Accept: application/xml
  • URL Extension (optional): /user.json or /user.xml
  • Query Parameter (optional): /user?format=json

2️⃣ HttpMessageConverter

Spring uses HttpMessageConverter to convert Java objects into the correct response format:

  • MappingJackson2HttpMessageConverter → JSON
  • MappingJackson2XmlHttpMessageConverter → XML
  • StringHttpMessageConverter → Plain Text
  • FormHttpMessageConverter → Form Data

3️⃣ Example: JSON & XML Response

public class User {
    private int id;
    private String name;
    // getters and setters
}

// Controller
@RestController
@RequestMapping("/users")
public class UserController {
    @GetMapping("/{id}")
    public User getUser(@PathVariable int id) {
        User user = new User();
        user.setId(id);
        user.setName("Alice");
        return user;
    }
}

Why You Shouldn’t Mix Roles in Spring

Each Spring stereotype annotation (@Component, @Service, @Controller, @Repository) has a specific role. Mixing roles can lead to semantic confusion, unexpected behavior, and testing difficulties.

1️⃣ Concept of Role Separation

  • Controller Layer – Handles HTTP requests and maps URLs.
  • Service Layer – Contains business logic.
  • Repository Layer – Handles persistence and database access.
  • Component / Utility Layer – Provides helper methods and common logic.

Each layer has a clear responsibility. Annotations are semantic and functional, influencing Spring features like proxies, transaction management, and MVC mapping.

2️⃣ Practical Consequences of Misusing Annotations

a) @Controller on a non-HTTP class

@Controller
public class OrderUtils {
    public String generateOrderId() {
        return UUID.randomUUID().toString();
    }
}

Problems: Semantic confusion, unnecessary MVC processing, and potential proxy issues.

b) @Service for a controller

@Service
public class UserController {
    @GetMapping("/users")
    public List getAllUsers() { ... }
}

Problems: Misleading role, potential unintended proxies, and confusion for developers.

c) @Repository on a utility class

@Repository
public class FileUtils {
    public void writeFile(String data) { ... }
}

Problems: Unnecessary exception translation, overhead, and potential errors.

3️⃣ Best Practices

  • One role per class (Controller → HTTP handling, Service → business logic, Component → utilities, Repository → data access).
  • Use @Component for generic utilities.
  • Keep layers clean to maintain readability, testability, and framework compatibility.

4️⃣ Correct Usage Examples

@Component
public class UUIDGenerator {
    public String generate() { return UUID.randomUUID().toString(); }
}

@Service
public class OrderService {
    public void processOrder() { ... }
}

@RestController
@RequestMapping("/orders")
public class OrderController {
    @Autowired
    private OrderService orderService;

    @GetMapping
    public List getOrders() { ... }
}

Each class has one clear role and uses the correct stereotype annotation.

5️⃣ Key Takeaways

  • Do not mix roles; use the correct stereotype annotation for each layer.
  • Annotations are semantic and functional; misusing them causes confusion and unintended behavior.
  • Following layered architecture improves maintainability, testability, readability, and proper Spring behavior.

Spring MVC

Spring MVC (Model-View-Controller) is a design pattern for building web applications. It separates the application into three layers: Model, View, and Controller, enabling decoupled and maintainable code.

Components of Spring MVC

  • DispatcherServlet: Front controller that receives all HTTP requests and delegates them to controllers.
  • Controller: Handles user requests, annotated with @Controller or @RestController.
  • Model: Holds application data, passed from controller to view.
  • View: Responsible for rendering the response (JSP, Thymeleaf, FreeMarker, or JSON).
  • HandlerMapping: Maps incoming requests to appropriate controller methods.
  • ViewResolver: Resolves logical view names to actual view templates.

Request Flow

  1. Client sends HTTP request → hits DispatcherServlet.
  2. DispatcherServlet uses HandlerMapping to find the appropriate controller method.
  3. Controller executes business logic and adds data to Model.
  4. Controller returns a view name.
  5. ViewResolver resolves the view template.
  6. Response is rendered and sent back to the client.

Example: Simple Spring MVC Application


@Controller
public class HelloController {

    @GetMapping("/hello")
    public String hello(Model model) {
        model.addAttribute("message", "Hello, Spring MVC!");
        return "hello"; // hello.html or hello.jsp
    }
}

    

<!DOCTYPE html>


    <title>Hello</title>


    <h1 th:text="${message}"></h1>

Key Annotations

Annotation Use
@Controller Marks a class as a Spring MVC controller
@RestController @Controller + @ResponseBody for JSON responses
@RequestMapping Maps HTTP requests to controller methods
@GetMapping / @PostMapping Shortcuts for specific HTTP methods
@PathVariable Extracts values from URI
@RequestParam Extracts query parameters from request
@ModelAttribute Binds request parameters to model attributes
@ResponseBody Sends method return directly as response (JSON, text)

Advantages

  • Clean separation of Model, View, and Controller.
  • Highly configurable and extensible.
  • Supports multiple view technologies (Thymeleaf, JSP, etc.).
  • Supports REST APIs using @RestController.
  • Integrated with other Spring features (DI, AOP, Security, Validation).

DispatcherServlet in Spring MVC

What is DispatcherServlet?

DispatcherServlet is the front controller in the Spring MVC framework. It intercepts all incoming HTTP requests, determines the appropriate controller to handle them, and manages the complete flow from request to response.

Responsibilities

  • Receive Request: Intercepts client HTTP requests.
  • Find Handler: Uses HandlerMapping to locate the controller.
  • Call Controller: Executes the mapped controller method.
  • Prepare Model: Collects model data returned by the controller.
  • Resolve View: Uses ViewResolver to find the actual view (Thymeleaf, JSP, etc.).
  • Render Response: Combines model and view, then sends response to the client.

Request Flow

Client → DispatcherServlet → HandlerMapping → Controller 
       → ModelAndView → ViewResolver → Response

Example in Spring Boot

In Spring Boot, DispatcherServlet is auto-configured. You don’t need web.xml. 


@SpringBootApplication
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}

Custom URL mapping for DispatcherServlet:


@Bean
public ServletRegistrationBean<DispatcherServlet> dispatcherRegistration(DispatcherServlet dispatcherServlet) {
    ServletRegistrationBean<DispatcherServlet> registration = new ServletRegistrationBean<>(dispatcherServlet);
    registration.setLoadOnStartup(1);
    registration.addUrlMappings("/api/*");
    return registration;
}

Key Points

  • Single entry point for all Spring MVC requests.
  • Manages controllers, interceptors, and exception handling.
  • Auto-configured in Spring Boot.
  • Ensures separation of concerns between request handling and view rendering.

Forward vs Redirect in Spring MVC

In Spring MVC, Forward and Redirect are two common ways to navigate between controllers and views. Both serve different purposes depending on whether you want to keep the same request or trigger a new one.

🔹 Forward

Forward happens on the server-side. The request is internally passed to another controller or view, and the URL in the browser does not change. 

@Controller
public class ForwardController {
    
    @GetMapping("/start")
    public String forwardExample() {
        return "forward:/next"; // forward internally
    }

    @GetMapping("/next")
    public String nextPage(Model model) {
        model.addAttribute("msg", "Forwarded successfully!");
        return "success"; // Renders success.html
    }
}

👉 Example: User hits /start → request is forwarded internally to /next but browser URL stays /start.

🔹 Redirect

Redirect tells the browser to make a new HTTP request. This changes the URL in the browser and involves two requests (original + redirected). 

@Controller
public class RedirectController {

    @PostMapping("/submitForm")
    public String submitForm() {
        return "redirect:/success"; // Redirect to new URL
    }

    @GetMapping("/success")
    public String successPage(Model model) {
        model.addAttribute("msg", "Form submitted successfully!");
        return "success"; // Renders success.html
    }
}

👉 Example: User posts to /submitForm → server responds with redirect → browser loads /success as a new URL.

🔑 Key Differences

Aspect Forward Redirect
Where it happens Server-side (internal) Client-side (browser re-request)
URL in browser Does not change Changes
HTTP Requests Single request Two requests
Performance Faster (no extra round-trip) Slightly slower (extra HTTP call)
Use Case Pass control internally Avoid duplicate form submission

Model, ModelAndView, and ViewResolver in Spring MVC

In Spring MVC, Model, ModelAndView, and ViewResolver work together to pass data from the controller to the view and render templates dynamically.

🔹 Model

Model is used to pass data from the controller to the view. Attributes added to the model can be accessed in the view template. 

@Controller
public class UserController {

    @GetMapping("/user")
    public String getUser(Model model) {
        model.addAttribute("name", "John Doe");
        model.addAttribute("age", 30);
        return "user"; // user.html or user.jsp
    }
}

🔹 ModelAndView

ModelAndView combines both the view name and model data in a single object. 

@Controller
public class UserController {

    @GetMapping("/userDetails")
    public ModelAndView getUserDetails() {
        ModelAndView mav = new ModelAndView("userDetails"); // view name
        mav.addObject("name", "Jane Doe");
        mav.addObject("age", 28);
        return mav;
    }
}

🔹 ViewResolver

ViewResolver maps the logical view name returned by the controller to an actual template file. 

@Bean
public SpringResourceTemplateResolver templateResolver() {
    SpringResourceTemplateResolver resolver = new SpringResourceTemplateResolver();
    resolver.setPrefix("classpath:/templates/");
    resolver.setSuffix(".html");
    return resolver;
}

Logical view name "user" → resolved to "classpath:/templates/user.html"

🔑 Summary

Concept Purpose Example
Model Pass data from controller to view model.addAttribute("name", "John")
ModelAndView Combine view + data in a single object new ModelAndView("user").addObject("name", "Jane")
ViewResolver Map logical view name → actual template file "user" → /templates/user.html

Using Model, ModelAndView, DTO, and ViewResolver in Spring MVC

In Spring MVC, using a DTO (Data Transfer Object) allows you to pass only the required data from the controller to the view. This keeps your domain entities safe, flexible, and maintainable. Model, ModelAndView, and ViewResolver work seamlessly with DTOs.

🔹 DTO (Data Transfer Object)

A DTO is a simple POJO that contains only the data you want to expose to the view. 

public class UserDTO {
    private String name;
    private int age;

    public UserDTO(String name, int age) {
        this.name = name;
        this.age = age;
    }
    // getters and setters
}

🔹 Using DTO with Model

Add the DTO object to the model and access its properties in the view. 

@Controller
public class UserController {

    @GetMapping("/user")
    public String getUser(Model model) {
        UserDTO userDto = new UserDTO("John Doe", 30);
        model.addAttribute("user", userDto);
        return "user"; // maps to user.html
    }
}

In Thymeleaf: ${user.name} and ${user.age}

🔹 Using DTO with ModelAndView

@GetMapping("/userDetails")
public ModelAndView getUserDetails() {
    UserDTO userDto = new UserDTO("Jane Doe", 28);
    ModelAndView mav = new ModelAndView("userDetails");
    mav.addObject("user", userDto);
    return mav;
}

Thymeleaf can render DTO properties using: ${user.name} and ${user.age}

🔹 ViewResolver

ViewResolver maps logical view names returned by the controller to actual template files. 

@Bean
public SpringResourceTemplateResolver templateResolver() {
    SpringResourceTemplateResolver resolver = new SpringResourceTemplateResolver();
    resolver.setPrefix("classpath:/templates/");
    resolver.setSuffix(".html");
    return resolver;
}

Logical view name "user" → resolved to "classpath:/templates/user.html"

🔹 Full Flow with DTO

Client Request → Controller
     │
Controller creates DTO → Adds to Model / ModelAndView
     │
Return logical view name
     │
ViewResolver maps name → template (Thymeleaf/JSP)
     │
Template engine renders view using DTO properties
     │
Response sent to client

🔹 Key Points

  • DTO decouples your domain entities from the view.
  • Model is used for simple data passing; ModelAndView combines view + data.
  • ViewResolver maps logical view names to actual template files.
  • Using DTO with Model or ModelAndView ensures cleaner, safer, and maintainable code.
