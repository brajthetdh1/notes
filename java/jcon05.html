Section 5.1: Deadlock – The Classic Thread Tragedy

Deadlock is the most famous liveness hazard. It occurs when two or more threads are blocked forever, each waiting for a resource held by another.

Subsection 5.1.1: The Four Conditions for Deadlock (Coffman Conditions)

For a deadlock to occur, all four of these conditions must be present simultaneously:

ConditionDescriptionExample
1. Mutual ExclusionResources cannot be shared. Only one thread can hold a resource at a time.A synchronized lock on an object.
2. Hold and WaitA thread holds at least one resource while waiting for another.Thread A holds lock X, waiting for lock Y.
3. No PreemptionResources cannot be forcibly taken away from a thread.A thread holds a lock until it voluntarily releases it.
4. Circular WaitA cycle of threads, each waiting for a resource held by the next.Thread A waits for lock Y held by Thread B; Thread B waits for lock X held by Thread A.

Do all four conditions need to be present? Yes. If any one condition is broken, deadlock cannot occur.

Subsection 5.1.2: Classic Deadlock Example – The Bank Transfer

This is the most famous deadlock scenario in Java concurrency.

public class BankAccount {
            private int balance;
            
            public void transfer(BankAccount target, int amount) {
                synchronized (this) {
                    synchronized (target) {
                        this.balance -= amount;
                        target.balance += amount;
                    }
                }
            }
        }

The Deadlock Scenario:

TimeThread A (transfer X→Y)Thread B (transfer Y→X)
T1synchronized(accountX) – locks Xsynchronized(accountY) – locks Y
T2synchronized(accountY) – BLOCKS (waiting for Y)synchronized(accountX) – BLOCKS (waiting for X)
T3DEADLOCK!

What if I call transfer() with the same account as source and target? synchronized is reentrant, so no deadlock. But it's still a bug (transferring to yourself).

Subsection 5.1.4: Preventing Deadlock – Breaking the Conditions

Strategy 1: Lock Ordering (Break Circular Wait)

The most common and effective prevention. Always acquire locks in a consistent global order.

public class BankAccount {
            private final int id;  // Unique ID
            
            public void transfer(BankAccount target, int amount) {
                BankAccount first = this.id < target.id ? this : target;
                BankAccount second = this.id < target.id ? target : this;
                
                synchronized (first) {
                    synchronized (second) {
                        this.balance -= amount;
                        target.balance += amount;
                    }
                }
            }
        }

Strategy 2: Use tryLock() with Timeout (Break Hold and Wait)

if (this.lock.tryLock(1, TimeUnit.SECONDS)) {
            try {
                if (target.lock.tryLock(1, TimeUnit.SECONDS)) {
                    // Critical section
                }
            } finally { this.lock.unlock(); }
        }

Strategy 3: Avoid Nested Locks (Break Hold and Wait)

Restructure code to avoid holding multiple locks simultaneously. Use a transaction log or queue to process transfers atomically.

Strategy 4: Use Higher-Level Abstractions

  • ConcurrentHashMap (no explicit locks needed)
  • BlockingQueue (handles producer-consumer without deadlock risk)
  • AtomicReference (lock-free)

Can deadlock occur with a single thread? No. A single thread cannot deadlock because it holds all locks it acquires (reentrant). Exception: Thread.currentThread().join(); (self-deadlock).

Can deadlock occur with synchronized and ReentrantLock mixed? Yes! Always acquire locks in the same order, regardless of whether they are intrinsic or explicit.

Section 5.2: Starvation – The Forgotten Thread

Starvation occurs when a thread is unable to gain regular access to shared resources and is unable to make progress.

Subsection 5.2.1: What is Starvation?

Definition: A thread is perpetually denied access to resources, causing it to never make progress.

Causes of Starvation:

  • Priority Inversion: High-priority threads consume all CPU time, starving low-priority threads.
  • Resource Hoarding: A thread holds a resource for a very long time.
  • Poorly Designed Thread Pools: A single long-running task occupies a thread.

Is starvation a problem on modern OSes? Modern OS schedulers use dynamic priority adjustments (they boost threads that have waited a long time). Starvation is rare but can still happen in poorly designed applications.

Subsection 5.2.2: Example of Starvation

Thread low = new Thread(() -> {
            while (true) {
                System.out.println("Low priority thread running");
            }
        });
        low.setPriority(Thread.MIN_PRIORITY);
        
        Thread high = new Thread(() -> {
            while (true) {
                // CPU hog, never yields
            }
        });
        high.setPriority(Thread.MAX_PRIORITY);

The low-priority thread may never print anything because the high-priority thread consumes all CPU time.

6 / 50

Subsection 5.2.3: Preventing Starvation

  • Use thread pools – Executors.newFixedThreadPool() limits the number of threads.
  • Avoid setting priorities – Let the OS scheduler handle it.
  • Use fair locks – new ReentrantLock(true) ensures threads get locks in order.
  • Use timeouts – Prevent indefinite waiting.
  • Design with cooperative scheduling – Use yield() or sleep() periodically.

Should I use thread priorities? Avoid them. Thread priorities are OS-dependent and can cause starvation. In most applications, the default priority (NORM_PRIORITY) is the right choice.

Section 5.3: Livelock – The False Progress

Livelock occurs when threads are not blocked but constantly change state in response to each other, making no progress.

Subsection 5.3.1: What is Livelock?

Definition: Threads are active (not blocked) but their actions are ineffective, and they cannot make progress.

Analogy: Two people trying to pass each other in a narrow corridor. Both step left, then both step right, then both step left again, never passing each other.

Subsection 5.3.2: The tryLock() Retry Loop

public void methodA() {
            while (true) {
                if (lock1.tryLock()) {
                    try {
                        if (lock2.tryLock()) {
                            try { /* Do work */ return; }
                            finally { lock2.unlock(); }
                        }
                    } finally { lock1.unlock(); }
                }
                // Retry immediately
            }
        }

Subsection 5.3.3: Preventing Livelock

Strategy 1: Exponential Backoff with Jitter

int retries = 0;
        while (retries < MAX_RETRIES) {
            if (lock1.tryLock()) {
                try {
                    if (lock2.tryLock()) {
                        try { /* Do work */ return; }
                        finally { lock2.unlock(); }
                    }
                } finally { lock1.unlock(); }
            }
            retries++;
            long delay = BASE_DELAY_MS * (long) Math.pow(2, retries);  // Exponential
            delay += ThreadLocalRandom.current().nextLong(0, delay / 2);  // Jitter
            Thread.sleep(delay);
        }

Strategy 2: Use Lock Ordering – If both threads acquire locks in the same order, livelock cannot occur.

Strategy 3: Use a Random Delay – Even a small random delay can break the symmetry that causes livelock.

Section 5.4: Thread Starvation (Resource Starvation)

Thread starvation occurs when a thread cannot get enough resources (CPU, memory, I/O) to make progress.

  • CPU Starvation: Too many threads competing for CPU time.
  • Memory Starvation: OutOfMemoryError due to excessive thread creation.
  • I/O Starvation: A slow database connection causes threads to block.

Subsection 5.4.2: Example of Thread Exhaustion

while (true) {
            new Thread(() -> {
                try { Thread.sleep(Long.MAX_VALUE); }
                catch (InterruptedException e) {}
            }).start();
        }

This will eventually throw OutOfMemoryError or hit the OS thread limit.

What is the OS thread limit?

  • Linux: Usually 32768 (default) but can be increased.
  • Windows: Usually 2048 (per process).
  • macOS: Usually 2048.

Part A: Conceptual Deep-Dive

Q1: What are the four conditions required for deadlock?

A: The four Coffman conditions: (1) Mutual Exclusion, (2) Hold and Wait, (3) No Preemption, (4) Circular Wait. All four must be present for deadlock to occur.

Q2: Can deadlock occur with just one lock?

A: No. A single lock cannot cause deadlock because there is no circular wait. However, a single thread can deadlock itself with Thread.currentThread().join() (self-deadlock).

Q3: What is the difference between deadlock and a "hung" thread?

A: Deadlock = two or more threads blocked forever, each waiting for a resource held by another. Hung thread = a single thread stuck indefinitely (infinite loop, blocking I/O with no timeout).

Q4: Can deadlock occur with ReentrantLock? Can it occur with synchronized?

A: Yes to both. Deadlock is a logic error, not a lock-specific issue. Both can deadlock if threads acquire locks in different orders. ReentrantLock actually provides tools to prevent deadlock (tryLock(), lockInterruptibly()).

Q5: What is the difference between deadlock and livelock?

A: Deadlock = threads are BLOCKED, minimal CPU usage. Livelock = threads are RUNNABLE, high CPU usage (spinning). Livelock is harder to detect because threads appear to be running.

Q6: How do you detect deadlock in a running Java application?

A: (1) Thread dumps (kill -3, jstack), (2) Programmatic detection (ThreadMXBean.findDeadlockedThreads()), (3) VisualVM / JConsole, (4) JFR (Java Flight Recorder).

Q7: What does findDeadlockedThreads() detect that findMonitorDeadlockedThreads() doesn't?

A: findMonitorDeadlockedThreads() detects deadlocks caused by synchronized locks only. findDeadlockedThreads() detects deadlocks caused by both synchronized and ReentrantLock. Always use findDeadlockedThreads().

Q8: What are the main strategies for preventing deadlock?

A: (1) Lock ordering (break circular wait), (2) tryLock() with timeout (break hold and wait), (3) Avoid nested locks, (4) Use higher-level abstractions (ConcurrentHashMap, BlockingQueue).

Q9: How does lock ordering prevent deadlock?

A: Lock ordering ensures all threads acquire locks in the same order, breaking the circular wait condition. Example: always lock by account ID.

Q10: How does tryLock() with timeout prevent deadlock?

A: A thread attempts to acquire all locks. If it can't acquire all within the timeout, it releases any locks it has and retries later. This breaks the "Hold and Wait" condition.

A: Thread starvation occurs when a thread cannot make progress because it cannot acquire necessary resources. Causes: priority inversion, resource hoarding, poor thread pool design.

Q12: What is the difference between starvation and deadlock?

A: Starvation = thread is RUNNABLE but not making progress (resources available but not scheduled). Deadlock = thread is BLOCKED (resources held by others).

Q16: What is "spinning" and how does it relate to livelock?

A: Spinning is when a thread repeatedly checks a condition in a loop without yielding CPU time. Spinning can cause livelock if two threads spin and never meet the condition. Fix: use Thread.sleep() or LockSupport.parkNanos().

Q17: What is thread exhaustion? What causes it?

A: Thread exhaustion occurs when an application creates too many threads, consuming all available memory or reaching the OS thread limit. Causes: creating a new thread for every request, thread leaks.

Q18: How can you prevent thread exhaustion?

A: Use thread pools (Executors.newFixedThreadPool()), use bounded thread pools, monitor thread count, use Virtual Threads (Java 21+).

Q19: What is "priority inversion" and how does it relate to starvation?

A: Priority inversion occurs when a low-priority thread holds a resource needed by a high-priority thread. The high-priority thread blocks, causing starvation. Fix: use priority inheritance (not available in Java). Avoid thread priorities.

Q20: What is the "dining philosophers" problem and how does it relate to deadlock?

A: Five philosophers sit at a round table with forks. Each needs two forks to eat. If all pick up the left fork simultaneously, all wait for the right fork → deadlock. Solutions: lock ordering, mutex, lazy pickup.

Q21: What is the "readers-writers" problem and how does it relate to liveness?

A: Readers-writers involves multiple threads accessing a shared resource: readers can read concurrently, writers need exclusive access. Liveness issues: writer starvation (if readers keep coming) and reader starvation (if writers keep coming). Solution: ReentrantReadWriteLock with fair policy.

Q22: What is "lock ordering" and why is it the most effective deadlock prevention?

A: Lock ordering is acquiring locks in a consistent global order. It breaks the circular wait condition. It's simple, has no runtime overhead, and prevents deadlock by design.

Q23: What is "fairness" in locks and how does it affect liveness?

A: Fairness determines whether threads acquire locks in the order they requested. Fair locks prevent starvation but reduce throughput. Unfair locks have higher throughput but can cause starvation. Use fair locks rarely.

Q24: What is the difference between deadlock and a "blocked" thread?

A: A blocked thread is waiting for a lock held by another thread. Deadlock is a cycle of blocked threads. A blocked thread may become unblocked; deadlock is permanent.

Q25: What is the difference between deadlock and "resource exhaustion"?

A: Deadlock = circular wait causing threads to block. Resource exhaustion = too many threads consuming memory, causing OutOfMemoryError or OS thread limit.

Q26: What is the difference between deadlock and "thread starvation" in a thread pool?

A: Deadlock in thread pool = tasks waiting for each other's results (circular dependency). Thread starvation in thread pool = not enough threads to process tasks (tasks wait indefinitely).

Q27: What is the difference between "livelock" and "priority inversion"?

A: Livelock = threads actively retrying but making no progress (symmetric retry logic). Priority inversion = high-priority thread waits for low-priority thread holding a resource.

Q28: What is the "dining philosophers" problem and what are the solutions?

A: Solutions: (1) Lock ordering (pick up fork with lower ID first), (2) Mutex (single lock controls all forks), (3) Lazy pickup (only pick up if both forks available).

Q29: What is tryLock() and how does it help with deadlock prevention?

A: tryLock() attempts to acquire a lock without blocking indefinitely. It returns true if successful, false otherwise. If any lock acquisition fails, the thread releases any locks it has and retries.

Q30: What is the difference between deadlock and a TimeoutException?

A: Deadlock = threads block indefinitely. TimeoutException = threads block for a limited time, then recover. Always use timeouts to prevent indefinite blocking.

Q36: Write a method that transfers money between two accounts without deadlock.

A: Use lock ordering by account ID.

public class BankAccount {
            private final int id;
            private int balance;
            private final Lock lock = new ReentrantLock();
            
            public boolean transfer(BankAccount target, int amount) {
                BankAccount first = this.id < target.id ? this : target;
                BankAccount second = this.id < target.id ? target : this;
                first.lock.lock();
                try {
                    second.lock.lock();
                    try {
                        if (this.balance < amount) return false;
                        this.balance -= amount;
                        target.balance += amount;
                        return true;
                    } finally { second.lock.unlock(); }
                } finally { first.lock.unlock(); }
            }
        }

A: Use ReentrantReadWriteLock.

public class ReadWriteExample {
            private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();
            private final Lock readLock = lock.readLock();
            private final Lock writeLock = lock.writeLock();
            private int data = 0;
            
            public int read() {
                readLock.lock();
                try { return data; }
                finally { readLock.unlock(); }
            }
            
            public void write(int value) {
                writeLock.lock();
                try { data = value; }
                finally { writeLock.unlock(); }
            }
        }
