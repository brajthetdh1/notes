Happens-Before Relationship

The happens-before relationship is a fundamental concept in the Java Memory Model that guarantees memory visibility and ordering constraints between operations, ensuring that if one action happens-before another, then the first action is visible to and ordered before the second action across all threads.

Key Guarantees:

Memory Visibility

Changes made by one thread are guaranteed to be visible to another thread

Operation Ordering

Ensures proper sequencing of operations across threads

Predictable Behavior

Prevents counter-intuitive reordering by compiler/CPU

Why It Matters:

1 Without happens-before, threads might see stale or inconsistent data
2 Compiler and CPU optimizations could reorder instructions unexpectedly
3 Provides formal guarantees for correct concurrent programming
4 Enables reasoning about multi-threaded program behavior

Happens-Before Rules in Java

Program Order Rule

Each action in a thread happens-before every subsequent action in the same thread

x = 1; // happens-before
y = 2; // this assignment
Monitor Lock Rule

An unlock on a monitor happens-before every subsequent lock on that same monitor

synchronized(obj) {
  // unlock happens-before next lock }
Volatile Variable Rule

A write to a volatile field happens-before every subsequent read of that same field

volatile boolean flag;
flag = true; // happens-before
if(flag) { } // this read
Thread Start/Join Rules

Thread.start() happens-before any action in started thread. Thread.join() happens-before any action after join

thread.start(); // happens-before
// run() method actions
thread.join(); // happens-before code after join

Without Happens-Before

// Thread 1
resource = new Resource(); // May not be visible
ready = true; // Reordered with above?

// Thread 2
while(!ready) { } // May see ready=true but
resource.doSomething(); // stale resource value!
No visibility guarantees between threads
Compiler/CPU may reorder instructions
Thread 2 might see inconsistent state

With Happens-Before

// Thread 1
resource = new Resource();
ready = true; // volatile - creates happens-before

// Thread 2
while(!ready) { }
resource.doSomething(); // Guaranteed to see initialized resource
Volatile write establishes happens-before
All writes before volatile write are visible
Thread 2 sees consistent, initialized state

Key Takeaways

Establishes ordering guarantees between operations

Ensures memory visibility across threads

Prevents harmful compiler/CPU reordering

ThreadLocal Variables

What is ThreadLocal?

ThreadLocal is a Java class that provides thread-local variables where each thread accessing a ThreadLocal variable has its own, independently initialized copy of the variable, ensuring thread isolation and preventing shared state conflicts without requiring synchronization.

private static final ThreadLocal<SimpleDateFormat> dateFormat =
  ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

How It Works

1 Each thread gets its own isolated copy of the variable
2 Variables are stored in thread-specific memory areas
3 No synchronization needed - no shared state
4 Automatically cleaned up when thread terminates

When to Use ThreadLocal

Per-thread Resources

Non-thread-safe objects like SimpleDateFormat, Random, or database connections that are expensive to create.

User Context

Storing user-specific data like authentication context, user preferences, or transaction context in web applications.

Thread-specific State

Maintaining state that should not be shared between threads, like performance metrics or debugging information.

Common Examples:

Web application user sessions
Database connection per thread
Date formatters in multi-threaded environments
Transaction context in Spring
Request-scoped data in servlets

Practical Example

Without ThreadLocal

// Shared SimpleDateFormat - NOT thread-safe!
private SimpleDateFormat format = new SimpleDateFormat("yyyy-MM-dd");

public String formatDate(Date date) {
  return format.format(date); // Race condition!
}
Multiple threads can corrupt internal state

With ThreadLocal

// Thread-safe per-thread formatter
private ThreadLocal<SimpleDateFormat> format =
  ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

public String formatDate(Date date) {
  return format.get().format(date); // Thread-safe!
}
Each thread gets its own formatter instance

Important Considerations

Memory Leaks

Always call remove() in web applications to prevent memory leaks when using thread pools

Memory Overhead

Each thread maintains its own copy, increasing memory usage

Not for Shared State

ThreadLocal is designed for isolation, not for sharing data between threads

Proper Cleanup

Use try-finally blocks to ensure remove() is called even during exceptions

ThreadGroup Class

What is ThreadGroup?

ThreadGroup is a legacy Java class that represents a group of threads and provides a mechanism to organize threads into hierarchical structures, allowing bulk operations like interruption, suspension, or setting maximum priority across multiple threads simultaneously.

// Creating and using ThreadGroup
ThreadGroup group = new ThreadGroup("WorkerThreads");
Thread t1 = new Thread(group, new Worker());
Thread t2 = new Thread(group, new Worker());
group.interrupt(); // Interrupts all threads in group

Why Rarely Used Now?

Deprecated Methods

Critical methods like suspend(), resume(), and stop() are deprecated due to deadlock risks

Modern Alternatives

ExecutorService and ForkJoinPool provide better thread management with improved performance

Security Limitations

Security manager restrictions limit ThreadGroup's usefulness in modern applications

Modern Alternatives to ThreadGroup

ExecutorService

ExecutorService executor = Executors.newFixedThreadPool(5);
executor.submit(() -> System.out.println("Task"));
executor.shutdown();
  • Thread pooling and reuse
  • Better resource management
  • Future-based result handling

ForkJoinPool

ForkJoinPool pool = ForkJoinPool.commonPool();
pool.invoke(new RecursiveTask());
// Work-stealing algorithm
  • Work-stealing for better utilization
  • Ideal for recursive tasks
  • Automatic load balancing

ThreadGroup vs Modern Approaches

Aspect ThreadGroup (Legacy) Modern Approaches
Thread Management Manual thread creation Automatic pooling
Safety Deprecated unsafe methods Safe interruption patterns
Performance Basic grouping Optimized work distribution
Use Case Legacy applications Modern concurrent programming

Current Status: Legacy Feature

While ThreadGroup still exists for backward compatibility, modern Java applications should use Executor framework, CompletableFuture, or Reactive Streams for better concurrency control.

CountDownLatch & CyclicBarrier

CountDownLatch

A synchronization aid that allows one or more threads to wait until a set of operations being performed in other threads completes, using a countdown mechanism that cannot be reset.

CountDownLatch latch = new CountDownLatch(3);

// Worker threads
latch.countDown(); // Decrement count

// Main thread
latch.await(); // Wait until count reaches 0

Characteristics:

  • One-time use
  • Multiple threads can wait
  • Countdown only (no reset)

Use Cases:

  • Start signal
  • Completion signal
  • Wait for initialization

CyclicBarrier

A synchronization aid that allows a set of threads to all wait for each other to reach a common barrier point, with the ability to reset and reuse the barrier for multiple synchronization points.

CyclicBarrier barrier = new CyclicBarrier(3);

// Worker threads
barrier.await(); // Wait for all parties

// Barrier action runs when all threads arrive

Characteristics:

  • Reusable (cyclic)
  • All threads meet at barrier
  • Optional barrier action

Use Cases:

  • Parallel computations
  • Multiplayer games
  • Simulation synchronization

CountDownLatch vs CyclicBarrier

Aspect CountDownLatch CyclicBarrier
Reusability ❌ One-time use ✅ Reusable
Reset Capability ❌ Cannot reset ✅ Automatically resets
Thread Role Different roles Same role
Counting Counts down Waits for fixed number
Use Case Start/Stop signals Multi-phase tasks
Semaphore

A Semaphore is a synchronization primitive that maintains a set of permits, controlling access to a shared resource by limiting the number of threads that can access it simultaneously, making it ideal for resource pooling and rate limiting scenarios.

How Semaphore Works:

1
Initialization

Semaphore created with fixed number of permits

2
Acquire

Thread acquires permit (blocks if none available)

3
Release

Thread releases permit back to semaphore

Semaphore semaphore = new Semaphore(3); // 3 permits

// Thread acquiring permit
semaphore.acquire();
try {
  // Access shared resource
} finally {
  semaphore.release(); // Always release!
}

Types & Use Cases:

Binary Semaphore (Mutex)

Single permit semaphore acting as mutual exclusion lock

Semaphore mutex = new Semaphore(1); // Binary semaphore
Counting Semaphore

Multiple permits for limited resource access

Semaphore pool = new Semaphore(5); // 5 database connections
Fair Semaphore

Guarantees FIFO ordering for waiting threads

Semaphore fairSem = new Semaphore(3, true); // Fair ordering

Connection Pool

Limit database connections to prevent overload

Rate Limiting

Control API call frequency and throughput

Resource Pool

Manage limited resources like printers, files

Key Semaphore Methods

acquire()

Acquire permit (blocks if needed)

release()

Release permit back

tryAcquire()

Non-blocking acquire attempt

availablePermits()

Get current available permits

ReentrantLock & ReentrantReadWriteLock

ReentrantLock

A reentrant mutual exclusion Lock with the same basic behavior as synchronized methods and statements, but with extended capabilities like timed lock waits, interruptible lock waits, and fair locking.

Key Features:

Same thread can acquire lock multiple times
Try-lock with timeout capability
Interruptible lock acquisition
Fair locking option (prevents starvation)
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
  // critical section
} finally {
  lock.unlock();
}

ReentrantReadWriteLock

A lock implementation that supports both read and write locks, allowing multiple readers to access simultaneously while ensuring exclusive access for writers, improving performance in read-heavy scenarios.

Lock Types:

Read Lock: Shared - multiple threads can hold simultaneously
Write Lock: Exclusive - only one thread can hold
Write lock cannot be acquired while read locks are held
Ideal for read-heavy, write-rarely scenarios
ReadWriteLock rwLock = new ReentrantReadWriteLock();
Lock readLock = rwLock.readLock();
Lock writeLock = rwLock.writeLock();

Performance Benefits

Multiple Readers

Many threads can read simultaneously

Single Writer

Exclusive access for write operations

High Concurrency

Better throughput for read-heavy workloads

Synchronized vs ReentrantLock

Synchronized

  • Built-in language feature
  • Automatic lock release
  • Simpler syntax and usage
  • JVM optimized
  • No timeout support
  • Not interruptible while waiting
  • No fair locking option
public synchronized void method() {
  // automatic locking/unlocking
}

ReentrantLock

  • Try-lock with timeout support
  • Interruptible lock acquisition
  • Fair locking option available
  • More flexible and feature-rich
  • Manual lock management required
  • More complex syntax
  • Risk of forgetting to unlock
lock.lock();
try {
  // critical section
} finally {
  lock.unlock(); // manual unlock required
}

Thread-Safe Bank Account System

BankAccount Class

public class BankAccount {
  private final String accountId;
  private double balance;
  private final Object lock = new Object();

  public BankAccount(String accountId, double initialBalance) {
    this.accountId = accountId;
    this.balance = initialBalance;
  }

  public void deposit(double amount) {
    synchronized(lock) {
      if (amount > 0) {
        balance += amount;
      }
    }
  }

  public boolean withdraw(double amount) {
    synchronized(lock) {
      if (amount > 0 && balance >= amount) {
        balance -= amount;
        return true;
      }
      return false;
    }
  }

  public double getBalance() {
    synchronized(lock) {
      return balance;
    }
  }
  public String getAccountId() {
    return accountId;
  }
}

Transfer Service

public class TransferService {
  // Deadlock-free transfer using ordered locking
  public static boolean transfer(
      BankAccount from,
      BankAccount to,
      double amount) {

    if (from == to || amount <= 0) {
      return false;
    }

    // Determine lock order to prevent deadlocks
    BankAccount firstLock = from;
    BankAccount secondLock = to;

    // Always lock in consistent order
    if (from.getAccountId().compareTo(to.getAccountId()) > 0) {
      firstLock = to;
      secondLock = from;
    }

    synchronized(firstLock) {
      synchronized(secondLock) {
        if (from.withdraw(amount)) {
          to.deposit(amount);
          return true;
        }
        return false;
      }
    }
  }
}

Deadlock Prevention Strategy

1
Ordered Locking

Always acquire locks in consistent order (by account ID)

2
Fine-grained Locking

Use separate lock objects per account

3
Atomic Operations

Withdraw and deposit happen atomically within same lock scope

4
Validation

Check for sufficient funds before transferring

Usage Example

// Create accounts
BankAccount account1 = new BankAccount("ACC001", 1000.0);
BankAccount account2 = new BankAccount("ACC002", 500.0);

// Perform thread-safe transfer
boolean success = TransferService.transfer(account1, account2, 200.0);

// Multiple concurrent transfers (thread-safe)
ExecutorService executor = Executors.newFixedThreadPool(4);
for (int i = 0; i < 10; i++) {
  executor.submit(() -> {
    TransferService.transfer(account1, account2, 50.0);
  });
}
executor.shutdown();

ThreadSafeCache Interface

public interface ThreadSafeCache<K, V> {
  V get(K key);
  void put(K key, V value);
  V getOrDefault(K key, V defaultValue);
  boolean containsKey(K key);
  void remove(K key);
  void clear();
  int size();
}

Core Implementation

public class ConcurrentLRUCache<K, V> {
  private final Map<K, V> cache;
  private final ReadWriteLock lock = new ReentrantReadWriteLock();
  private final int maxSize;
  private final LinkedHashMap<K, Long> accessOrder;
}

Key Thread-Safe Methods

Read Operation (get)
public V get(K key) {
  lock.readLock().lock();
  try {
    V value = cache.get(key);
    if (value != null) updateAccessOrder(key);
    return value;
  } finally {
    lock.readLock().unlock();
  }
}
Multiple threads can read concurrently
Write Operation (put)
public void put(K key, V value) {
  lock.writeLock().lock();
  try {
    if (cache.size() >= maxSize) {
      evictLRU();
    }
    cache.put(key, value);
    updateAccessOrder(key);
  } finally {
    lock.writeLock().unlock();
  }
}
Exclusive lock ensures data consistency

Performance Optimizations

LRU eviction for memory management
Time-based entry expiration
Atomic operations for consistency
