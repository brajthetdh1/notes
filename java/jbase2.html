SOLID Principles in Java

SOLID is an acronym for five design principles intended to make software designs more understandable, flexible, and maintainable.

S

Single Responsibility Principle

Definition

A class should have only one reason to change, meaning it should have only one job or responsibility.

Violation Example

class UserService {
  public void createUser(String user) { ... }
  public void sendEmail(String user) { ... }
  public void generateReport() { ... }
  public void saveToDatabase(User user) { ... }
}

Correct Implementation

class UserService {
  public void createUser(String user) { ... }
}

class EmailService {
  public void sendEmail(String user) { ... }
}

class ReportService {
  public void generateReport() { ... }
}

class UserRepository {
  public void save(User user) { ... }
}
Benefits:
  • • Easier to understand and maintain
  • • Reduced coupling between functionalities
  • • Easier testing and debugging
O

Open/Closed Principle

Definition

Software entities should be open for extension but closed for modification.

Violation Example

class AreaCalculator {
  public double calculateArea(Object shape) {
    if (shape instanceof Rectangle) {
      return calculateRectangleArea((Rectangle) shape);
    } else if (shape instanceof Circle) {
      return calculateCircleArea((Circle) shape);
    }
    // Need to modify when adding new shapes
  }
}

Correct Implementation

interface Shape {
  double calculateArea();
}

class Rectangle implements Shape {
  public double calculateArea() { ... }
}

class Circle implements Shape {
  public double calculateArea() { ... }
}

class AreaCalculator {
  public double calculateArea(Shape shape) {
    return shape.calculateArea();
  }
}
Benefits:
  • • Easy to extend with new functionality
  • • No risk of breaking existing code
  • • Promotes polymorphism and abstraction
L

Liskov Substitution Principle

Definition

Objects of a superclass should be replaceable with objects of its subclasses without breaking the application.

Violation Example

class Rectangle {
  protected int width, height;
  public void setWidth(int w) { width = w; }
  public void setHeight(int h) { height = h; }
}

class Square extends Rectangle {
  public void setWidth(int w) {
    width = w; height = w; // Violates LSP!
  }
}

Correct Implementation

interface Shape {
  int getArea();
}

class Rectangle implements Shape {
  private int width, height;
  public int getArea() { return width * height; }
}

class Square implements Shape {
  private int side;
  public int getArea() { return side * side; }
}
Key Rules:
  • • Don't implement stricter validation rules in subclass
  • • Don't throw new exceptions in subclass methods
  • • Maintain all superclass invariants
I

Interface Segregation Principle

Definition

Clients should not be forced to depend on interfaces they do not use. Many client-specific interfaces are better than one general-purpose interface.

Violation Example

interface Worker {
  void work();
  void eat();
  void sleep();
}

class Robot implements Worker {
  public void work() { ... }
  public void eat() { throw new Exception(); } // Forced!
  public void sleep() { throw new Exception(); } // Forced!
}

Correct Implementation

interface Workable {
  void work();
}

interface Eatable {
  void eat();
}

interface Sleepable {
  void sleep();
}

class Human implements Workable, Eatable, Sleepable {
  public void work() { ... }
  public void eat() { ... }
  public void sleep() { ... }
}

class Robot implements Workable {
  public void work() { ... }
}
Benefits:
  • • No forced implementation of unused methods
  • • Reduced side effects from interface changes
  • • Better cohesion and less coupling
D

Dependency Inversion Principle

Definition

High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details. Details should depend on abstractions.

Violation Example

class EmailService {
  public void sendEmail() { ... }
}

class Notification {
  private EmailService emailService; // Direct dependency
  public Notification() {
    this.emailService = new EmailService();
  }
  public void send() {
    emailService.sendEmail();
  }
}

Correct Implementation

interface MessageService {
  void sendMessage();
}

class EmailService implements MessageService {
  public void sendMessage() { ... }
}

class SMSService implements MessageService {
  public void sendMessage() { ... }
}

class Notification {
  private MessageService messageService;
  public Notification(MessageService service) { // Dependency injection
    this.messageService = service;
  }
  public void send() {
    messageService.sendMessage();
  }
}
Benefits:
  • • Loose coupling between modules
  • • Easier testing with mock dependencies
  • • More flexible and maintainable code

Following SOLID principles leads to code that is more maintainable, testable, scalable, and resilient to change.

Interface Segregation Principle (ISP)

Definition

The Interface Segregation Principle states that clients should not be forced to depend on interfaces they do not use. Instead of one large, general-purpose interface, many smaller, client-specific interfaces are preferred, ensuring that implementing classes only need to be concerned with the methods that are relevant to them.

Core Concept

❌ Violation - Fat Interface

interface Worker {
  void work();
  void eat();
  void sleep();
  void code();
  void design();
  void test();
}

Robot class forced to implement eat() and sleep()

✅ Following ISP

interface Workable {
  void work();
}
interface Eatable {
  void eat();
}
interface Codeable {
  void code();
}

Classes implement only relevant interfaces

Problems ISP Solves

Eliminates "Dummy" Methods

No more throwing UnsupportedOperationException or empty method implementations

Reduces Coupling

Clients depend only on methods they actually use

Improves Maintainability

Changes to one interface don't affect unrelated clients

Enhances Testability

Easier to mock and test focused interfaces

Real-World Example

❌ Without ISP

interface Printer {
  void print(Document d);
  void scan(Document d);
  void fax(Document d);
}

class OldPrinter implements Printer {
  // Forced to implement scan() and fax()!
}

✅ With ISP

interface Printer {
  void print(Document d);
}
interface Scanner {
  void scan(Document d);
}
interface Fax {
  void fax(Document d);
}

class OldPrinter implements Printer { }
class MultiFunction implements Printer, Scanner, Fax { }

Key Benefits

Focused Interfaces

Each interface has single, clear responsibility

Reduced Side Effects

Changes don't propagate to unrelated code

Flexible Composition

Mix and match interfaces as needed

Dependency Inversion Principle (DIP)

Definition

The Dependency Inversion Principle states that high-level modules should not depend on low-level modules. Both should depend on abstractions. Additionally, abstractions should not depend on details. Details should depend on abstractions. This principle inverts the traditional dependency hierarchy and enables loose coupling between software components.

The Two Rules of DIP

1

Abstractions Over Implementations

High-level modules and low-level modules should both depend on the same abstractions (interfaces or abstract classes), rather than high-level modules depending directly on low-level implementations.

2

Details Depend on Abstractions

Concrete implementations (details) should depend on and implement abstractions, not the other way around. This ensures that the core architecture drives the implementation details.

Traditional vs DIP Architecture

❌ Traditional Dependency

High-Level
↓ depends on ↓
Low-Level
↓ depends on ↓
Details
// High-level depends on low-level
class BusinessLogic {
  private MySQLDatabase db;
  public void saveData() {
    db.save(); // Direct dependency
  }
}

✅ With DIP

High-Level
↓ depends on ↓
Abstraction
↑ depends on ↑
Low-Level
// Both depend on abstraction
class BusinessLogic {
  private Database db; // Interface
  public void saveData() {
    db.save();
  }
}
class MySQLDatabase implements Database { }

Real-World Example: Data Access

Abstraction Layer

// Abstraction that both depend on
interface UserRepository {
  User findById(Long id);
  void save(User user);
  void delete(Long id);
}

Implementation Flexibility

// Different implementations
class MySQLUserRepository
  implements UserRepository { ... }

class MongoDBUserRepository
  implements UserRepository { ... }

class InMemoryUserRepository
  implements UserRepository { ... }

Dependency Injection & DIP

Dependency Injection is the primary mechanism for implementing DIP, where dependencies are provided to a class from the outside rather than being created internally. This allows high-level modules to work with abstractions while the concrete implementations are injected at runtime, typically through constructors, setters, or framework containers.

// Without DI - violates DIP
class OrderService {
  private EmailNotifier notifier =
    new EmailNotifier(); // Hard dependency
}
// With DI - follows DIP
class OrderService {
  private Notifier notifier; // Abstraction
  public OrderService(Notifier n) {
    this.notifier = n; // Injected
  }
}

Benefits of Dependency Inversion

Loose Coupling

Components depend on abstractions, not concrete implementations

Testability

Easy to mock dependencies for unit testing

Flexibility

Easy to swap implementations without changing core logic

Maintainability

Changes to implementations don't affect high-level modules

Liskov Substitution Principle

What is the Liskov Substitution Principle?

The Liskov Substitution Principle (LSP) states that objects of a superclass should be replaceable with objects of its subclasses without breaking the application's correctness, meaning that subclasses must maintain the behavioral contracts established by their parent classes and not violate any expectations that clients have when working with the base class.

// Should work without issues:
BaseClass obj = new SubClass();
obj.doSomething(); // Should behave as expected

Core Concept

IS-A Relationship

A subclass should truly be a specialized version of its parent

Behavioral Contract

Subclasses must honor all parent class contracts

Key Rules of LSP

Method Signatures

  • Parameters should be the same or more general
  • Return types should be the same or more specific
  • Exceptions should be the same or subtypes

Behavioral Contracts

  • Preconditions cannot be strengthened
  • Postconditions cannot be weakened
  • Invariants must be preserved

Good Example - LSP Compliant

class Bird {
  public void eat() { /* all birds eat */ }
}

class FlyingBird extends Bird {
  public void fly() { /* only flying birds fly */ }
}

class Sparrow extends FlyingBird {
  // Can use both eat() and fly()
}

class Penguin extends Bird {
  // Can use eat(), no fly() method
}

✅ All subclasses can substitute their parent classes without breaking functionality

Common Violation - Square/Rectangle Problem

class Rectangle {
  protected int width, height;
  public void setWidth(int w) { width = w; }
  public void setHeight(int h) { height = h; }
}

class Square extends Rectangle {
  public void setWidth(int w) {
    width = w; height = w; // Violates LSP!
  }
  public void setHeight(int h) {
    height = h; width = h; // Violates LSP!
  }
}

// This breaks client expectations:
void test(Rectangle r) {
  r.setWidth(5);
  r.setHeight(4);
  assert r.width == 5; // Fails for Square!
}

❌ Square changes the behavior expected from Rectangle, breaking substitution

Benefits of Following LSP

Reliable Inheritance

Predictable behavior across hierarchy

Fewer Bugs

Reduces unexpected behavior

Better Extensibility

Easy to add new subtypes

How to Detect and Fix LSP Violations

Detection Signs

  • Type checking with instanceof in client code
  • Overridden methods that do nothing or throw exceptions
  • Subclasses with empty implementations

Fixes

  • Use composition over inheritance
  • Extract common interfaces
  • Apply strategy or state patterns
IS-A vs HAS-A Relationship

IS-A Relationship (Inheritance)

Represents an inheritance relationship where one class is a subtype of another, established using the extends keyword.

class Animal { }
class Dog extends Animal { } // Dog IS-A Animal
  • Represents inheritance hierarchy
  • Uses "extends" keyword
  • Supports polymorphism

HAS-A Relationship (Composition)

Represents composition or aggregation where one class contains a reference to another class as an instance variable.

class Engine { }
class Car {
  private Engine engine; // Car HAS-A Engine
}
  • Represents composition/aggregation
  • Uses instance variables
  • More flexible than inheritance
Constructor Calling in Inheritance

How constructor calling works in inheritance hierarchy?

When creating an object of a subclass, the constructor calling follows a top-down approach where the constructor of the superclass is always called before the constructor of the subclass, either implicitly by the compiler calling the default superclass constructor or explicitly using the super() keyword to call a specific superclass constructor.

Order of constructor execution in multilevel inheritance

In multilevel inheritance, constructors are executed in the order from the topmost superclass down to the most specific subclass, following the hierarchy chain where each constructor completes before the next one in the inheritance chain begins execution.

Execution Order Example:

1 Object class constructor (implicit)
2 Grandparent class constructor
3 Parent class constructor
4 Child class constructor

Code Example:

class A { A() { System.out.println("A"); } }
class B extends A { B() { System.out.println("B"); } }
class C extends B { C() { System.out.println("C"); } }

new C(); // Output: A → B → C
Static Methods & Method Hiding

Can we override static methods? Why or why not?

No, static methods cannot be overridden in Java because static methods are bound at compile-time based on the reference type (static binding), whereas instance method overriding uses runtime polymorphism (dynamic binding) where the actual object type determines which method is called.

What is method hiding in Java?

Method hiding occurs when a subclass defines a static method with the same signature as a static method in its superclass, where the method called is determined by the reference type at compile-time rather than the actual object type at runtime, which is different from true method overriding that uses dynamic polymorphism.

class Parent {
  static void method() { System.out.println("Parent"); }
}
class Child extends Parent {
  static void method() { System.out.println("Child"); } // Hiding
}

Parent p = new Child();
p.method(); // Output: "Parent" (not "Child")

How to prevent a class from being inherited?

You can prevent a class from being inherited by declaring it as final, which makes the class immutable and prevents any other class from extending it, ensuring that the class implementation cannot be modified through inheritance.

public final class CannotBeExtended {
  // This class cannot be inherited
  // Compilation error if any class tries to extend it
}
Method Overloading vs Overriding

Method Overloading

  • Same method name, different parameters
  • Compile-time polymorphism
  • Within same class
  • Return type can be different
class Calculator {
  int add(int a, int b) { }
  double add(double a, double b) { } // Overloaded
}

Method Overriding

  • Same method signature in subclass
  • Runtime polymorphism
  • Between superclass and subclass
  • Return type must be compatible
class Animal {
  void sound() { }
}
class Dog extends Animal {
  void sound() { } // Overridden
}
Return Types in Method Overriding

Can we change the return type in method overriding?

Prior to Java 5, the return type in method overriding had to be exactly the same as the superclass method, but since Java 5, you can change the return type to a subtype of the original return type using covariant return types, which allows more specific return types in overridden methods.

What is covariant return type?

Covariant return type allows an overriding method to return a subtype of the return type declared in the superclass method, providing more specific type information while maintaining type safety and enabling more precise API design in inheritance hierarchies.

class Animal {
  Animal reproduce() { return new Animal(); }
}
class Dog extends Animal {
  @Override
  Dog reproduce() { return new Dog(); } // Covariant return
}

Why no multiple inheritance in Java classes?

Java does not support multiple inheritance through classes to avoid the "diamond problem" where ambiguity arises when a class inherits from two classes that have methods with the same signature, which could lead to confusion about which parent class method should be called and complicate the language design and compiler implementation.

Diamond Problem Example:

class A { void method() { } }
class B extends A { }
class C extends A { }
// class D extends B, C { } // Not allowed!
// Which method() should be called?

Solution:

Java uses interfaces for multiple inheritance, which only declare methods without implementation, avoiding the diamond problem while still allowing multiple type inheritance.

Runtime Polymorphism

What is runtime polymorphism? How is it achieved?

Runtime polymorphism (dynamic polymorphism) is a mechanism where the method call is resolved at runtime based on the actual object type rather than the reference type. It is achieved through method overriding in Java, where a subclass provides a specific implementation of a method that is already defined in its parent class.

Example:

Animal myAnimal = new Dog();
myAnimal.sound(); // Calls Dog's sound()
// Resolved at runtime

Key Points:

  • • Achieved through method overriding
  • • Resolved at runtime (JVM)
  • • Uses inheritance hierarchy
  • • Also called dynamic binding
Compile-time Polymorphism

What is compile-time polymorphism? How is it achieved?

Compile-time polymorphism (static polymorphism) is a mechanism where the method call is resolved during compilation based on the reference type. It is achieved through method overloading in Java, where multiple methods have the same name but different parameters (type, number, or order).

Example:

class Calculator {
  int add(int a, int b) { ... }
  double add(double a, double b) { ... }
}
// Resolved at compile time

Key Points:

  • • Achieved through method overloading
  • • Resolved at compile time (compiler)
  • • Same class, different signatures
  • • Also called static binding
Dynamic Method Dispatch

What is dynamic method dispatch?

Dynamic method dispatch is the mechanism that enables runtime polymorphism in Java, where the JVM determines which version of an overridden method to execute based on the actual object type at runtime, not the reference type. This allows a superclass reference to call subclass methods.

How It Works:

1 Superclass reference points to subclass object
2 Method call made through superclass reference
3 JVM checks actual object type at runtime
4 Subclass's overridden method is executed

Example:

class Animal {
  void sound() { System.out.println("Animal sound"); }
}
class Dog extends Animal {
  void sound() { System.out.println("Bark"); }
}

Animal a = new Dog();
a.sound(); // Output: "Bark"
Method Overriding Rules

What are the rules for method overriding?

Method name must be same
Parameter list must be identical
Return type should be same or covariant
Access modifier can't be more restrictive
Can't override final methods
Can't override static methods
Can't override private methods
Can throw same, subclass, or no exception

Can we override private methods?

No, private methods cannot be overridden because they are not visible to subclasses. A subclass can define a method with the same signature as a private method in the parent class, but this is method hiding, not overriding.

class Parent {
  private void show() { } // Not visible to Child
}
class Child extends Parent {
  void show() { } // This is a new method, not override
}

Can we override final methods?

No, final methods cannot be overridden. The final keyword prevents method overriding, ensuring that the method implementation remains unchanged in subclasses. Attempting to override a final method will result in a compilation error.

class Parent {
  public final void show() { } // Cannot be overridden
}
class Child extends Parent {
  // public void show() { } // COMPILATION ERROR
}

Can we override static methods?

No, static methods cannot be overridden. They are bound at compile time (static binding). A subclass can define a static method with the same signature, but this is method hiding, not overriding. The method called depends on the reference type, not the object type.

class Parent {
  static void show() { System.out.println("Parent"); }
}
class Child extends Parent {
  static void show() { System.out.println("Child"); }
}

Parent p = new Child();
p.show(); // Output: "Parent" (not "Child")

Can we override main method?

No, the main method cannot be overridden because it is a static method. A subclass can define its own main method, but this is method hiding, not overriding. When running the program, JVM always calls the main method of the class specified in the command line.

class Parent {
  public static void main(String[] args) {
    System.out.println("Parent main");
  }
}
class Child extends Parent {
  public static void main(String[] args) {
    System.out.println("Child main");
  }
}
// java Child → "Child main"
// java Parent → "Parent main"

Can we change access modifier while overriding?

Yes, but only to make it less restrictive. You can't make it more restrictive. For example, a protected method can be overridden as public, but a public method cannot be overridden as protected or private. This ensures the Liskov Substitution Principle.

class Parent {
  protected void show() { }
}
class Child extends Parent {
  public void show() { } // ✅ Allowed
  // protected/private void show() { } // ❌ Not allowed
}

How does polymorphism work with static methods?

Static methods don't support runtime polymorphism. They use compile-time binding (static binding). The method called is determined by the reference type, not the actual object type. This is why static method "overriding" is actually method hiding.

class Animal {
  static void sound() { System.out.println("Animal"); }
}
class Dog extends Animal {
  static void sound() { System.out.println("Dog"); }
}

Animal a = new Dog();
a.sound(); // "Animal" (reference type matters)
Dog.sound(); // "Dog" (class name matters)
Abstract Class vs Concrete Class

Abstract Class

  • Cannot be instantiated directly
  • Can have abstract methods (without implementation)
  • Can have constructors, instance variables
  • Supports access modifiers (private, protected)
  • Used for creating inheritance hierarchies
abstract class Animal {
  abstract void makeSound();
  void sleep() { /* implementation */ }
}

Concrete Class

  • Can be instantiated with 'new' keyword
  • All methods have complete implementations
  • Can have constructors, instance variables
  • Supports access modifiers
  • Used for creating actual objects
class Dog extends Animal {
  void makeSound() {
    System.out.println("Woof!");
  }
}
Abstract Class Constructor

Yes, abstract classes can have constructors, and they are used to initialize the state of the abstract class and perform common initialization logic that concrete subclasses will inherit, even though you cannot directly instantiate an abstract class, its constructor gets called when concrete subclasses are instantiated.

Why Have Constructors?

  • 1 Initialize instance variables of abstract class
  • 2 Perform common initialization for all subclasses
  • 3 Enforce constructor chaining in inheritance hierarchy

Example

abstract class Shape {
  private String color;
  // Constructor in abstract class
  public Shape(String color) {
    this.color = color;
  }
}

class Circle extends Shape {
  public Circle(String color) {
    super(color); // Calls abstract class constructor
  }
}
Abstract Method Restrictions

Private Abstract Methods?

❌ NOT ALLOWED

Abstract methods cannot be declared as private because they must be accessible to subclasses for implementation. Private methods are not visible to subclasses, which contradicts the purpose of abstract methods that need to be overridden.

// COMPILATION ERROR
abstract class Example {
  private abstract void method(); // Invalid!
}

Static Abstract Methods?

❌ NOT ALLOWED

Abstract methods cannot be static because static methods belong to the class rather than instances and cannot be overridden (only hidden), while abstract methods require implementation in subclasses through overriding.

// COMPILATION ERROR
abstract class Example {
  static abstract void method(); // Invalid!
}
Abstract Class Instantiation

No, you cannot directly create an object of an abstract class using the 'new' operator because abstract classes are incomplete by design - they may contain abstract methods without implementations. However, you can create anonymous subclasses or use concrete subclasses that provide implementations for all abstract methods.

Invalid Direct Instantiation

abstract class Animal {
  abstract void makeSound();
}

// COMPILATION ERROR
Animal animal = new Animal(); // Invalid!

This fails because Animal has abstract methods without implementations.

Valid Alternatives

// Using concrete subclass
Animal dog = new Dog();

// Anonymous subclass
Animal animal = new Animal() {
  void makeSound() {
    System.out.println("Some sound");
  }
};
Marker Interfaces

Marker interfaces are special interfaces that contain no methods or constants, serving only as markers to indicate that a class implementing them has certain capabilities or should be treated in a special way by the Java runtime or frameworks.

Common Examples

Serializable

Marks classes that can be serialized

class MyClass implements Serializable { }
Cloneable

Allows Object.clone() to work

class MyClass implements Cloneable { }
Remote

Marks RMI remote objects

class MyClass implements Remote { }

Purpose & Usage

Provide metadata about class capabilities
Enable runtime type checking
Used by Java API and frameworks
Largely replaced by annotations in modern Java
Default Methods in Interfaces

Purpose of Default Methods

Default methods were introduced in Java 8 to allow adding new methods to interfaces without breaking existing implementations. They provide backward compatibility when evolving APIs.

interface Vehicle {
  void start(); // traditional abstract method
  
  // Default method with implementation
  default void honk() {
    System.out.println("Beep beep!");
  }
}

Overriding Default Methods

Yes, implementing classes can override default methods to provide their own specific implementation, or they can choose to inherit the default implementation as-is.

class Car implements Vehicle {
  public void start() {
    System.out.println("Car started");
  }
  
  // Override default method
  @Override
  public void honk() {
    System.out.println("Car horn: Honk honk!");
  }
}
Diamond Problem & Solution

What is Diamond Problem?

The diamond problem occurs when a class inherits from two classes that have a common ancestor, creating ambiguity about which method implementation to use. This is a classic multiple inheritance problem.

Class A
Class B
↘
Class C
↙
Class D

Java's Solution

Java solves the diamond problem by:

  • Not allowing multiple inheritance of classes
  • Allowing multiple inheritance of interfaces
  • Requiring explicit overriding for conflicting default methods
interface A { default void method() { } }
interface B { default void method() { } }

class C implements A, B {
  // Must override to resolve conflict
  public void method() {
    A.super.method(); // Choose one explicitly
  }
}
Interface Multiple Inheritance

✅ Yes, an interface can extend multiple interfaces in Java. This is one of the key features that distinguishes interfaces from classes and enables true multiple inheritance of type (but not implementation until default methods).

Syntax Example

interface Walkable {
  void walk();
}

interface Swimmable {
  void swim();
}

// Interface extending multiple interfaces
interface Amphibious extends Walkable, Swimmable {
  void breathe();
}

class Frog implements Amphibious {
  // Must implement all methods from all interfaces
  public void walk() { }
  public void swim() { }
  public void breathe() { }
}

Key Points

No limit on number of interfaces extended
All abstract methods must be implemented
Default method conflicts must be resolved
Enables rich type hierarchies
Encapsulation vs Data Hiding

Encapsulation

Encapsulation is the broader OOP concept of bundling data and methods that operate on that data within a single unit (class), while restricting direct access to some of the object's components and exposing a controlled interface.

  • Bundling data and behavior together
  • Controlling access through methods
  • Hiding implementation details

Data Hiding

Data hiding is a specific technique of making class fields private and providing public getter/setter methods to access and modify them, preventing direct access to the internal data representation.

  • Making fields private/protected
  • Using accessor methods
  • Part of encapsulation implementation

Key Relationship

Data hiding is the implementation technique used to achieve encapsulation, which is the broader design principle.

Achieving Immutability in Java

Immutability in Java is achieved by creating classes whose instances cannot be modified after construction, providing thread safety, predictability, and simplified reasoning about code behavior.

Rules for Immutable Classes

  • 1 Declare class as final to prevent inheritance
  • 2 Make all fields private and final
  • 3 Don't provide setter methods
  • 4 Initialize all fields via constructor
  • 5 Perform deep copy for mutable objects

Immutable Class Example

public final class ImmutablePerson {
  private final String name;
  private final int age;
  private final List<String> hobbies;

  public ImmutablePerson(String name, int age,
    List<String> hobbies) {
    this.name = name;
    this.age = age;
    this.hobbies = Collections.unmodifiableList(
      new ArrayList<>(hobbies));
  }

Shallow Copy vs Deep Copy

Shallow Copy

Creates a new object but shares references to the same nested objects as the original. Changes to nested objects in the copy affect the original.

class Person {
  String name;
  Address address; // Shared reference
}

// Shallow copy:
Person copy = new Person();
copy.name = original.name;
copy.address = original.address; // Same object!
  • Faster and uses less memory
  • Nested objects are shared
  • Default Object.clone() behavior

Deep Copy

Creates a completely independent copy, including all nested objects. No shared references between original and copy.

class Person {
  String name;
  Address address;

  public Person deepCopy() {
    Person copy = new Person();
    copy.name = this.name;
    copy.address = this.address.copy();
    return copy;
  }
}
  • Slower and uses more memory
  • Complete independence
  • Must be implemented manually
Implementing Cloning in Java

Cloneable Interface & clone()

  • 1 Implement Cloneable marker interface
  • 2 Override protected Object.clone() method
  • 3 Call super.clone() to create shallow copy
  • 4 Handle CloneNotSupportedException
  • 5 Make method public for accessibility

Cloning Implementation

public class Employee implements Cloneable {
  private String name;
  private int age;
  private Address address; // Mutable object

  @Override
  public Object clone() throws
    CloneNotSupportedException {
    // Shallow copy
    Employee clone = (Employee) super.clone();
    // Deep copy for mutable fields
    clone.address = (Address) address.clone();
    return clone;
  }
}

// Usage:
Employee original = new Employee();
Employee copy = (Employee) original.clone();

Note: clone() has design issues. Consider copy constructors or factory methods instead for better design.

  }
}
Memory & Serialization

Memory Implications of Inner Classes

Inner classes maintain an implicit reference to their enclosing outer class instance, which can prevent garbage collection of the outer class even when it's no longer needed, potentially causing memory leaks in long-lived applications if inner class instances outlive their outer class instances.

Memory Impact

  • Each inner instance holds outer class reference
  • Prevents outer instance garbage collection
  • Can cause memory leaks in certain scenarios

Best Practices

  • Use static nested classes when possible
  • Clear references when no longer needed
  • Avoid long-lived inner class references

How do you serialize inner classes?

Serializing inner classes is generally not recommended because they contain implicit references to their outer class instances, which would also need to be serialized. If serialization is necessary, the inner class should be declared as static, or the outer class should implement Serializable and carefully manage the serialization process.

Problematic Approach

class Outer {
  class Inner implements Serializable {
    // Will try to serialize Outer.this
    // May cause NotSerializableException
  }
}

Recommended Approach

class Outer {
  static class StaticInner implements Serializable {
    // No outer reference - safe to serialize
  }
}

Fragile Base Class Problem

What is the "fragile base class" problem?

  • Document extension points clearly

Virtual Method Invocation

How does Java handle virtual method invocation?

Java uses virtual method tables (vtables) where each class has a table of method pointers, and object references contain a pointer to their class's vtable; when a virtual method is called, the JVM looks up the actual method implementation in the vtable based on the object's runtime type rather than the reference type, enabling polymorphic behavior.

VTable Structure

class Animal {
  void speak() { } // vtable[0]
}
class Dog extends Animal {
  void speak() { } // vtable[0] - overridden
}
// dog.speak() → vtable[0] → Dog.speak()

Performance Impact

  • One extra indirection vs direct calls
  • JIT can often devirtualize and inline
  • Modern JVMs make cost negligible

Diamond Problem in Java 8+

How to handle the "diamond problem" with default methods?

Java resolves the diamond problem with default methods using compile-time rules: if a class inherits multiple default methods with the same signature, it must override the method itself, and the compiler requires explicit disambiguation using InterfaceName.super.methodName() syntax when calling a specific inherited default implementation.

Diamond Problem Example

interface A { default void foo() { } }
interface B extends A { }
interface C extends A { default void foo() { } }
class D implements B, C {
  // Must override foo() due to conflict
  public void foo() {
    C.super.foo(); // Explicit disambiguation
  }
}

Resolution Rules

  • 1 Class implementations win over interface defaults
  • 2 Most specific interface wins
  • 3 Explicit override required for ambiguity
Polymorphism vs Double Dispatch

Dynamic polymorphism vs double dispatch

Dynamic polymorphism (single dispatch) determines the method to call based only on the receiver object's runtime type, while double dispatch determines the method based on both the receiver's type and the argument's type, requiring explicit design patterns like Visitor to simulate in single-dispatch languages like Java.

Dynamic Polymorphism

Single dispatch - Based on receiver type only
Built-in - Native Java feature
Example: animal.speak()

Double Dispatch

Double dispatch - Based on receiver + argument
Pattern-based - Visitor pattern implementation
Example: element.accept(visitor)

Java doesn't natively support multiple dispatch, but you can simulate it using the Visitor pattern for double dispatch, manual type checking with instanceof for ad-hoc multiple dispatch, or external libraries that use reflection or code generation to provide multiple dispatch capabilities beyond the language's built-in single dispatch mechanism.

Visitor Pattern Approach

}

void collide(Entity a, Entity b) {
  if (a instanceof Ship && b instanceof Asteroid) {
    shipVsAsteroid((Ship)a, (Asteroid)b);

Immutable Class Design

Designing Immutable Classes with Complex Object Graphs

To design truly immutable classes with complex object graphs, you must ensure that all fields are final, constructors fully initialize the object graph, no methods modify internal state, and all mutable components are defensively copied both during construction and when returned from getters, while using immutable collections and ensuring that referenced objects are also immutable or safely encapsulated.

public final class ImmutablePerson {
  private final String name;
  private final List<String> addresses; // Immutable list
  private final Date birthDate; // Mutable - needs defensive copy

  public ImmutablePerson(String name, List<String> addresses, Date birthDate) {
    this.name = name;
    this.addresses = Collections.unmodifiableList(new ArrayList<>(addresses));
    this.birthDate = new Date(birthDate.getTime()); // Defensive copy
  }
}

  • Entire object graph is immutable
  • Higher memory overhead from copying
  • Slower object creation
  • Maximum thread safety

Shallow Immutability

  • Only top-level object is immutable
  • Better performance and memory usage

Handling Circular References

Circular references in immutable objects can be handled using multi-step construction patterns like builders that resolve dependencies after all components are created, employing lazy initialization with immutable holders, or using object IDs/references that can be resolved later, while ensuring that the circular dependency doesn't violate the immutability contract during construction.

// Using builder pattern for circular dependencies
ImmutableNode parent = ImmutableNode.builder()
  .name("parent")
  .build();
ImmutableNode child = ImmutableNode.builder()
  .name("child")
  .parent(parent)
  .build();
parent = parent.withChild(child); // Create new parent with child reference

Defensive Copying Strategy

Defensive copying is necessary when dealing with mutable parameters or return values in immutable classes, requiring you to create copies of mutable objects passed into constructors to prevent external modification, and return copies of internal mutable state from getters to maintain encapsulation, ensuring that the immutable object's state cannot be changed through external references.

Constructor Copying
public ImmutableClass(List<String> items) {
  this.items = new ArrayList<>(items); // Defensive copy
}
Getter Copying
public List<String> getItems() {
  return new ArrayList<>(items); // Defensive copy
}

Advanced Patterns & Benefits

Copy-on-Write Patterns

Copy-on-write patterns optimize immutable object updates by sharing internal state between instances until a modification is needed, at which point a copy is made, allowing for efficient memory usage when objects are frequently read but rarely modified, commonly implemented using persistent data structures or structural sharing techniques.

Basic Implementation
public class CopyOnWriteList {
  private volatile List items = new ArrayList<>();

  public void add(T item) {
    synchronized(this) {
      List newItems = new ArrayList<>(items);
      newItems.add(item);
      items = newItems; // Atomic reference update
    }
  }
}
Benefits
  • Readers never block
  • Consistent snapshots for readers
  • Efficient for read-heavy workloads
  • Memory overhead for writes

High Cost

Deep inheritance, I/O resources, Complex DI

Inner Classes vs Static Nested Classes

Memory implications of inner classes vs static nested classes

Inner classes maintain an implicit reference to their enclosing instance, creating a strong reference chain that can prevent garbage collection of the outer class and lead to memory leaks, while static nested classes are independent and don't hold references to enclosing instances, making them more memory-efficient and suitable for long-lived objects or scenarios where the nested class outlives the outer class.

Inner Classes

Implicit reference to outer instance
Potential memory leaks
Heavier memory footprint

Static Nested Classes

No reference to outer instance
Memory safe
Lighter memory footprint
Memory Leaks Detection & Prevention

How to detect and prevent memory leaks?

Memory leaks can be detected through profiling tools that monitor heap usage over time, analyzing GC logs for increasing old generation occupancy, and using memory analyzers to identify reference chains preventing garbage collection, while prevention involves using weak references for caches, properly closing resources, avoiding static collections holding object references, and being cautious with inner classes and event listeners that may outlive their intended scope.

Detection Methods

  • Heap analysis with VisualVM, YourKit, Eclipse MAT
  • GC log analysis for growing memory patterns
  • Memory pressure monitoring in production

Prevention Strategies

  • Use WeakReference for cache implementations
  • Proper resource cleanup in finally blocks
  • Nullify references in long-lived objects
Finalizers Impact

Impact of finalizers on garbage collection

Finalizers severely impact garbage collection by requiring objects to undergo multiple GC cycles before being reclaimed, delaying memory release and increasing heap pressure, while also consuming additional CPU resources for finalizer thread execution and creating unpredictable performance characteristics that can lead to OutOfMemoryErrors even when objects are technically eligible for collection but stuck in finalization queues.

Finalizer Problems & Alternatives

Problems:
  • Delayed object reclamation
  • No execution guarantees
  • Performance overhead
Alternatives:
  • Explicit cleanup methods
  • try-with-resources (AutoCloseable)
  • PhantomReference with ReferenceQueue
Efficient Garbage Collection Design

How to design objects for efficient garbage collection?

Objects should be designed for efficient garbage collection by minimizing object sizes, preferring short-lived objects that die young and get collected quickly in minor GC cycles, avoiding deep object graphs that require extensive tracing, using primitive fields instead of wrapper objects when possible, and ensuring objects become unreachable as soon as they're no longer needed through proper scope management and nullification of references in long-lived containers.

Good Practices

  • Use primitives instead of wrappers
  • Prefer local scope over instance fields
  • Flatten object hierarchies
  • Use arrays for homogeneous data

Avoid These

  • Long-lived object references
  • Complex object graphs
  • Static collections growing unbounded
  • Objects with finalizers
Object Pools

What are "object pools" and when should they be used?

Object pools are caching mechanisms that maintain a collection of pre-initialized reusable objects ready for use, eliminating the overhead of object creation and initialization while controlling memory usage through bounded allocation, making them suitable for scenarios where object creation is expensive, such as database connections, thread creation, or complex domain objects with heavy initialization logic in high-throughput applications.

When to Use Object Pools

Expensive resource creation (DB connections, threads)
High-frequency object creation requirements
Memory-constrained environments

When to Avoid Object Pools

Simple, lightweight object creation
Objects with mutable, request-specific state
Modern GC-efficient environments
Cache Performance

How does object size affect cache performance?

Object size directly impacts cache performance by determining how many objects can fit in CPU cache lines, with smaller objects allowing better cache utilization and locality, while large objects cause cache pollution, increase cache misses, and reduce performance due to frequent memory access, making compact object layouts with field alignment and primitive-focused designs crucial for high-performance applications.

Cache Optimization Strategies

Object Splitting

Separate hot/cold fields into different objects

Field Packing

Group frequently accessed fields together

Array-based Storage

Use arrays for better cache locality

Flyweight Pattern

What is the flyweight pattern and how does it reduce memory?

The Flyweight pattern minimizes memory usage by sharing common state across multiple objects instead of storing identical data in each instance, separating intrinsic state (shared, immutable) from extrinsic state (context-specific), dramatically reducing memory footprint in scenarios with many similar objects, such as character rendering in text editors, graphical objects in UI toolkits, or fine-grained objects in game development where object count would otherwise be prohibitive.

Intrinsic State (Shared)

  • Immutable and shared across instances
  • Stored in flyweight factory cache
  • Example: Character glyphs, Tree species

Extrinsic State (Context)

  • Varies with each usage context
  • Passed to flyweight methods
  • Example: Position, Color, Size
Object Creation Measurement

How to measure object creation overhead?

Object creation overhead can be measured using microbenchmarking frameworks like JMH that account for JVM warmup and optimization effects, profiling tools that track allocation rates and GC pressure, memory allocation tracking to identify hot allocation paths, and custom instrumentation using System.nanoTime() for specific object creation code paths, while considering factors like JIT compilation, escape analysis, and GC behavior that significantly impact real-world performance.

Measurement Techniques

Tools & Frameworks:
  • JMH for reliable microbenchmarks
  • VisualVM, YourKit for allocation profiling
  • JFR for production allocation analysis
Key Metrics:
  • Allocation rate (objects/second)
  • GC frequency and pause times
  • Memory footprint per operation
Object Reuse vs Recreation

Best practices for object reuse vs recreation

Object reuse should be preferred when object creation is expensive, objects are large, or allocation rates are extremely high, while recreation is better for simple objects, when object pooling adds complexity, or when objects have request-specific state that makes resetting error-prone, with the decision balancing between reduced GC pressure and potential memory leaks versus simpler code and better scalability in modern garbage collectors optimized for short-lived objects.

Reuse Objects When:

Object creation is computationally expensive
Objects hold scarce resources (DB connections)
Memory-constrained environments

Recreate Objects When:

Objects are simple and cheap to create
Objects have request-specific mutable state
Modern GC environments with efficient allocation
