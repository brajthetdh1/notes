Topic 4.1: Visibility

Q1 visibility What is the visibility problem in Java? Can you give a real-world example?

A: The visibility problem occurs when changes made by one thread are not visible to other threads because of CPU caching, compiler optimizations, or instruction reordering.

Real-World Example: A web server has a running flag that controls whether a background thread continues processing requests.

public class WebServer { private boolean running = true; // No volatile! public void start() { new Thread(() -> { while (running) { // Process requests } }).start(); } public void shutdown() { running = false; // May never be seen by the background thread! } }

The background thread may run forever because the JIT compiler optimizes while (running) by caching the value of running in a register. The shutdown() call never takes effect.

The Fix: Make running volatile.

4 min read visibility volatile

Q2 visibility What does volatile guarantee about visibility? Does it guarantee that all writes are flushed to main memory?

A: Yes. A write to a volatile variable:

  • Flushes all previous writes from the thread's local cache to main memory.
  • Invalidates the cache lines of other threads that contain the variable.
  • Inserts memory barriers to prevent reordering.

A read from a volatile variable:

  • Invalidates the thread's local cache and forces a reload from main memory.
  • Inserts memory barriers to prevent reordering.
The "Doubt Clarifier" – Does volatile flush all writes or just the volatile write?
It flushes all writes that occurred before the volatile write. This is the key to the happens-before rule: all writes before the volatile write are visible to any thread that reads the volatile variable.

Example:
private volatile boolean ready; private int data; // Thread A data = 42; // Normal write ready = true; // Volatile write // Thread B if (ready) { // Volatile read int x = data; // Guaranteed to see 42! }
The ready = true write flushes data = 42 to main memory, so Thread B sees both.

Q3 visibility Can a thread see a stale value indefinitely? Or will it eventually see the correct value?

A: Without proper synchronization, a thread can see a stale value indefinitely. The JVM is allowed to cache the value forever (e.g., in a CPU register or by hoisting the read out of a loop). There is no guarantee of eventual visibility.

Example:

private boolean running = true; public void run() { while (running) { // May be hoisted to if (!running) while(true) // Do work } }

The JIT compiler can transform this into:

if (running) { while (true) { // Do work } }

Now the thread never reads running again. The change will never be seen.

The Fix: Make running volatile.

Q5 visibility What is "instruction reordering" and how does it affect visibility?

A: Instruction reordering is when the JVM, JIT compiler, or CPU changes the order of instructions for performance.

Example:

// Without reordering int a = 1; int b = 2; // With reordering (allowed) int b = 2; int a = 1;

In a single-threaded program, this is safe because the result is the same. In a multi-threaded program, it can cause visibility issues.

Example of Reordering Breakage:

private boolean ready; private Config config; // Thread A config = loadConfig(); // Write 1 ready = true; // Write 2 (may be reordered before Write 1) // Thread B if (ready) { useConfig(config); // May see partially loaded config! }

The JVM/CPU may reorder config = loadConfig() and ready = true, so Thread B sees ready == true but config is null or partially constructed.

The Fix: Use volatile or synchronized. They insert memory barriers that prevent reordering.

4 min read reordering JMM volatile

Q6 visibility What is the "happens-before" rule for volatile? Can you explain it with an example?

A: The JMM defines that a write to a volatile variable happens-before any subsequent read of that same variable.

Example:

private volatile boolean flag; private int counter; // Thread A counter = 10; // Write 1 flag = true; // Volatile write // Thread B if (flag) { // Volatile read int x = counter; // Guaranteed to see 10! }

Why:

  • counter = 10 happens-before flag = true (program order rule).
  • flag = true happens-before if (flag) (volatile rule).
  • Therefore, counter = 10 happens-before int x = counter (transitivity).
Interview Tip: Always mention transitivity when explaining volatile visibility.

Q8 visibility If I use volatile, do I also need to use synchronized?

A: It depends. If you have multiple operations that must be performed atomically together, volatile is not enough.

Example (volatile is not enough):

private volatile int count; public void increment() { count++; // NOT atomic! Even with volatile. }

Example (volatile is enough):

private volatile boolean running; public void setRunning(boolean value) { running = value; // Atomic write, volatile is enough. }
Rule of thumb: Use volatile for simple get/set operations. Use synchronized or AtomicInteger for compound operations.

Q10 escape What are the ways an object can escape?

Common escape scenarios:

1. Publishing this in the constructor:

public class EscapeExample { public EscapeExample() { new Thread(() -> System.out.println(this.hashCode())).start(); // Escapes! } }

2. Passing this to another method in the constructor:

public class EscapeExample { public EscapeExample() { Registry.register(this); // Escapes! } }

3. Inner class holding a reference:

public class EscapeExample { public EscapeExample() { new Inner(); // Inner class has reference to outer 'this' } private class Inner { Inner() { System.out.println(EscapeExample.this.hashCode()); } } }

4. Returning a mutable object from a getter (indirect escape):

public class Mutable { private Date birthDate; public Date getBirthDate() { return birthDate; // Returns mutable object; caller can modify it! } }

Q11 escape Why is escaping this dangerous?

A: Because other threads may see the object in a partially constructed state. Non-final fields may still have default values (0, null, false), and final fields may not yet be assigned.

Example:

public class Escapes { private final int value; public Escapes() { new Thread(() -> System.out.println(value)).start(); // May print 0! this.value = 42; } }

If the thread runs before value = 42, it prints 0. The object has escaped before construction is complete.

The Fix: Never start threads or publish this inside a constructor. Use a factory method or a start() method that is called after construction.

3 min read escape danger constructor

Q12 escape How can you prevent escape?

A:

  • Don't publish this in the constructor.
  • Use a factory method that constructs the object and then safely publishes it.
  • Use a separate start() method for threads.
  • Make defensive copies for mutable fields.
  • Use immutable objects (they can't be mutated, so escape is less dangerous, though still problematic).

Example of Safe Construction:

public class Safe { private final int value; private Safe(int value) { this.value = value; } public static Safe create() { Safe obj = new Safe(42); // Safe to publish after construction return obj; } }
3 min read escape prevention factory

Topic 4.3: Thread Confinement

Q14 confinement What is thread confinement and why is it useful?

A: Thread confinement means an object is accessible only from a single thread. This eliminates all synchronization requirements because there are no race conditions.

Benefits:

  • No synchronization needed (no locks, no volatile).
  • Maximum performance (no blocking, no cache flushes).
  • Simpler code (no concurrency bugs).

Example: Local variables in a method are automatically thread-confined.

public void method() { List<String> list = new ArrayList<>(); // Only this thread can access it // ... use list }

Q17 ThreadLocal What is the memory leak problem with ThreadLocal? How do you fix it?

A: In thread pools, threads are reused. If you set a ThreadLocal value but never call remove(), the value remains attached to the thread forever, preventing garbage collection.

The Leak:

public void doWork() { threadLocal.set(new BigObject()); // Attached to thread // ... use threadLocal // No remove()! }

After doWork() returns, the BigObject is still referenced by the thread's ThreadLocalMap. If the thread is reused, the object stays in memory. Over time, this causes a memory leak.

The Fix:

public void doWork() { try { threadLocal.set(new BigObject()); // ... use threadLocal } finally { threadLocal.remove(); // Critical! } }
Interview Tip: This is a very common interview question. Always mention remove().
3 min read ThreadLocal memory-leak remove

Q18 ThreadLocal What is InheritableThreadLocal and when would you use it?

A: InheritableThreadLocal propagates values from a parent thread to child threads.

Example:

public class Context { private static InheritableThreadLocal<String> userId = new InheritableThreadLocal<>(); public static void main(String[] args) { userId.set("user-123"); new Thread(() -> { System.out.println(userId.get()); // Prints "user-123" }).start(); } }

Use Cases:

  • Propagating user context to child threads.
  • Passing configuration or transaction IDs.

Risks:

  • Values can leak unexpectedly.
  • Child threads may modify the value, affecting the parent (if the object is mutable).
Java 21+ Alternative: Use ScopedValue (more flexible and safer).

Topic 4.4: Immutability

Q19 immutability What is an immutable object? What are the benefits?

A: An immutable object is an object whose state cannot be changed after it is created.

Benefits:

  • Thread-safe: No synchronization needed for sharing.
  • Caching-friendly: Can be safely cached and reused.
  • No defensive copies: No need to copy when returning from getters.
  • Simpler reasoning: No need to worry about unexpected changes.

Examples in JDK:

  • String
  • Integer, Long, Double
  • LocalDate, LocalDateTime
  • BigDecimal, BigInteger
3 min read immutability benefits examples

Q20 immutability How do you create an immutable class?

A: Follow these steps:

  1. Make the class final (prevent subclassing).
  2. Make all fields final (set in constructor).
  3. Make all fields private (encapsulation).
  4. No setter methods.
  5. Defensive copy for mutable fields (both input and output).
  6. Ensure constructor does not leak this.

Example:

public final class ImmutablePerson { private final String name; private final Date birthDate; // Mutable! public ImmutablePerson(String name, Date birthDate) { this.name = name; this.birthDate = new Date(birthDate.getTime()); // Defensive copy } public String getName() { return name; } public Date getBirthDate() { return new Date(birthDate.getTime()); // Defensive copy } }
5 min read immutability steps defensive-copy

Q21 immutability Is this class immutable? If not, why?

public final class Person { private final String name; private final List<String> hobbies; public Person(String name, List<String> hobbies) { this.name = name; this.hobbies = hobbies; } public List<String> getHobbies() { return hobbies; } }

A: No! It's not fully immutable because:

  • hobbies is a final reference to a mutable List.
  • The caller can modify the list (e.g., person.getHobbies().add("swimming")).
  • The list is not defensively copied.

The Fix:

public final class Person { private final String name; private final List<String> hobbies; public Person(String name, List<String> hobbies) { this.name = name; this.hobbies = List.copyOf(hobbies); // Defensive copy } public List<String> getHobbies() { return hobbies; // List.copyOf() returns an immutable list } }

Q23 immutability What is "defensive copying" and why is it used?

A: Defensive copying is creating a copy of a mutable object to protect the original from accidental or malicious modification.

When to use defensive copying:

When accepting mutable objects in the constructor:

public ImmutablePerson(Date birthDate) { this.birthDate = new Date(birthDate.getTime()); // Copy input }

When returning mutable objects from a getter:

public Date getBirthDate() { return new Date(birthDate.getTime()); // Copy output }
The "Doubt Clarifier" – Is defensive copying always necessary?
Only for mutable fields. For immutable fields (like String, LocalDate), no copying is needed.

Topic 4.5: Safe Publication

Q26 safe-publication What is safe publication and why is it important?

A: Safe publication is ensuring that an object reference is visible to other threads after the object is fully constructed.

Why it's important: Without safe publication, other threads may see:

  • null (the reference hasn't been written yet).
  • A stale reference (an old object).
  • A partially constructed object (fields not yet initialized).
The "Doubt Clarifier" – Is safe publication the same as thread safety?
No. Thread safety is about the object's behavior when accessed by multiple threads. Safe publication is about ensuring the object is visible in the first place.

Q28 safe-publication Why is static initialization safe?

A: The JVM guarantees that static initializers are executed in a thread-safe manner. When a class is loaded, the static initializer runs once, and the result is visible to all threads.

Example:

public class Registry { public static final MyService SERVICE = new MyService(); // Safe! }
The "Doubt Clarifier" – What about static initializers that throw exceptions?
If a static initializer throws an exception, the class fails to load, and NoClassDefFoundError is thrown. This is safe (fail-fast) but may cause application startup failures.
2 min read static-initialization thread-safe JVM

Q29 safe-publication Why does volatile work for safe publication?

A: When a thread writes to a volatile field, all previous writes are flushed to main memory. When another thread reads the volatile field, it sees all those writes.

Example:

private volatile MyObject obj; public void publish(MyObject o) { obj = o; // Volatile write } public MyObject get() { return obj; // Volatile read }

The volatile write guarantees that the constructor of MyObject completed before the reference was assigned, and the volatile read guarantees that the reading thread sees the fully constructed object.

3 min read volatile safe-publication visibility

Q30 safe-publication What is the "final field" safe publication guarantee?

A: The JMM guarantees that final fields are visible to all threads after the constructor completes, even without synchronization.

Example:

public class Immutable { private final int value; // Guaranteed visible public Immutable(int value) { this.value = value; } }

If Thread A creates an Immutable and publishes it (e.g., via a volatile reference), Thread B is guaranteed to see value correctly.

The "Doubt Clarifier" – Does this apply to non-final fields?
No! Non-final fields are not guaranteed to be visible without synchronization.
3 min read final safe-publication JMM

Q31 safe-publication What is the difference between safe publication and safe initialization?

TermDefinition
Safe PublicationMaking a reference visible to other threads after construction.
Safe InitializationEnsuring the object is fully constructed before the constructor returns.

Safe publication is about visibility. Safe initialization is about construction. A constructor should never leak this, and final fields must be assigned before the constructor returns.

3 min read safe-publication safe-initialization constructor

Q32 safe-publication What is the "final" field reordering problem?

A: The JVM guarantees that writes to final fields are not reordered with the write that publishes the reference. This is part of the initialization safety guarantee.

Example:

public class FinalExample { private final int value; public FinalExample(int value) { this.value = value; } }

The JVM ensures that the write to value happens before the reference to the object becomes visible to other threads.

The "Doubt Clarifier" – What if I have a non-final field?
Non-final fields can be reordered. The reference may become visible before the field is assigned.

Topic 4.6: Advanced JMM Concepts

Q33 JMM What is the "happens-before" relationship? Explain the rules.

A: Happens-before is a JMM rule that defines when one action is guaranteed to be visible to another.

The 8 Happens-Before Rules:

RuleDescription
1. Program OrderWithin a single thread, actions happen-before subsequent actions.
2. Monitor LockAn unlock on a lock happens-before any subsequent lock on that same lock.
3. VolatileA write to a volatile field happens-before any subsequent read of that same field.
4. Thread StartThread.start() happens-before any action in the started thread.
5. Thread TerminationAny action in a thread happens-before Thread.join() returns.
6. InterruptionThread.interrupt() happens-before detection of the interrupt.
7. FinalizerThe end of a constructor happens-before the finalize() method starts.
8. TransitivityIf A happens-before B, and B happens-before C, then A happens-before C.
5 min read JMM happens-before rules

Q34 JMM What is a "data race" and how does it relate to happens-before?

A: A data race occurs when:

  • Two or more threads access the same variable.
  • At least one access is a write.
  • There is no happens-before relationship between the accesses.

Example:

private int x; // Thread A x = 5; // Write // Thread B int y = x; // Read (no happens-before relationship)

There is a data race because there is no happens-before relationship between the write and the read.

The "Doubt Clarifier" – Does a data race always cause problems?
No. Sometimes the threads happen to see the correct value. But the JVM is allowed to produce incorrect results due to reordering, caching, etc. Data races are bugs waiting to happen.
3 min read data-race JMM happens-before

Q35 JMM What is "sequential consistency" and does Java guarantee it?

A: Sequential consistency is a memory model where:

  • All operations appear to happen in a global order.
  • That order is consistent with the program order in each thread.

Does Java guarantee sequential consistency? No! The JMM is weaker than sequential consistency to allow compiler/hardware optimizations.

However: volatile and synchronized provide sequential consistency on the specific variables/locks, but the program as a whole is not sequentially consistent.
3 min read JMM sequential-consistency memory-model

Q36 JMM What is "out-of-thin-air" safety?

A: Out-of-thin-air safety is a JMM guarantee that a thread cannot read a value that was never written.

Example: Without out-of-thin-air safety, a thread could read x = 42 even if no thread ever wrote 42. This is forbidden by the JMM.

The "Doubt Clarifier" – Is out-of-thin-air safety guaranteed for all variables?
Yes, for all variables. However, without synchronization, a thread may read a stale value (an old valid value), but it will never read a completely arbitrary value.
2 min read JMM out-of-thin-air safety
