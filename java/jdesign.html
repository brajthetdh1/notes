Singleton Design Pattern

What is Singleton Pattern?

The Singleton pattern is a creational design pattern that ensures a class has only one instance and provides a global point of access to that instance throughout the application lifecycle.

Problem Solved

Singleton solves the problem of controlling access to shared resources, ensuring that only one instance of a class exists to manage global state, configuration, or expensive resources.

When to Use Singleton Pattern:

Managing database connections
Configuration management
Logging services
Caching mechanisms

Key Characteristics:

Single Instance

Global Access

Controlled Instantiation

Pros & Cons

Advantages

  • Controlled access to single instance
  • Reduced memory footprint
  • Lazy or eager initialization options
  • Easy to implement and understand

Disadvantages

  • Violates Single Responsibility Principle
  • Can be difficult to unit test
  • Hidden dependencies in code
  • Potential for becoming a global state
Basic Implementation

Eager Initialization

public class EagerSingleton {
  private static final EagerSingleton
    INSTANCE = new EagerSingleton();
  private EagerSingleton() {}
  public static EagerSingleton getInstance() {
    return INSTANCE;
  }
}
Created when class is loaded - thread-safe but not lazy

Lazy Initialization

public class LazySingleton {
  private static LazySingleton instance;
  private LazySingleton() {}
  public static LazySingleton getInstance() {
    if (instance == null) {
      instance = new LazySingleton();
    }
    return instance;
  }
}
Created when first requested - NOT thread-safe

Thread Safety ✅ Built-in ❌ Requires sync
Thread Safety

Synchronized Method

public class ThreadSafeSingleton {
  private static ThreadSafeSingleton instance;
  private ThreadSafeSingleton() {}
  public static synchronized
    ThreadSafeSingleton getInstance() {
    if (instance == null) {
      instance = new ThreadSafeSingleton();
    }
    return instance;
  }
}
Thread-safe but performance overhead

Double-Checked Locking

public class DCLSingleton {
  private static volatile DCLSingleton instance;
  private DCLSingleton() {}
  public static DCLSingleton getInstance() {
    if (instance == null) {
      synchronized (DCLSingleton.class) {
        if (instance == null) {
          instance = new DCLSingleton();
        }
      }
    }
    return instance;
  }
}
Performance optimized with volatile keyword

Why Volatile in Double-Checked Locking?

1 Prevents instruction reordering by compiler/JVM
2 Ensures visibility of fully constructed object to all threads
3 Without volatile, threads might see partially constructed object

Static Inner Class

public class InnerClassSingleton {
  private InnerClassSingleton() {}

    private static final InnerClassSingleton

Factory Pattern Overview

What is Factory Pattern?

The Factory Pattern is a creational design pattern that provides an interface for creating objects in a superclass, but allows subclasses to alter the type of objects that will be created, promoting loose coupling by eliminating the need to bind application-specific classes into the code.

Problem it Solves

It solves the problem of tight coupling between client code and concrete classes, making it difficult to extend or modify the system without changing existing code, and eliminates complex object creation logic scattered throughout the application.

Main Benefits:

Loose coupling between client and products
Single Responsibility Principle
Open/Closed Principle compliance
Centralized object creation logic
Easy to extend with new product types
Simplified client code

Factory Pattern vs Direct Creation

Factory Pattern: Decoupled, extensible, follows SOLID principles
Direct Creation: Tightly coupled, hard to test and extend

When to Use Factory Pattern

  • When object creation logic is complex
  • When you need to support multiple product variants
  • When you want to decouple client from concrete classes
Factory Pattern Types

Simple Factory

Static method that creates objects based on parameters

ProductFactory.createProduct(type)

Factory Method

Subclasses decide which class to instantiate

abstract Product createProduct()

Abstract Factory

Creates families of related objects

interface Factory {
  createA(); createB();
}
Simple Factory Pattern

What is Simple Factory?

Simple Factory is a programming idiom rather than a full-fledged design pattern that uses a single static method to create objects based on a parameter, encapsulating the object creation logic in one place.

Implementation Example:

public class VehicleFactory {
  public static Vehicle createVehicle(String type) {
    switch(type) {
      case "car": return new Car();
      case "bike": return new Bike();
      default: throw new IllegalArgumentException();
    }
  }
}

Limitations

  • Violates Open/Closed Principle when adding new types
  • Static method makes testing difficult
  • Not extensible without modifying factory

When to Use Simple Factory

Small applications with few product types
When product types rarely change
Use Factory Method for extensible systems
Factory Method Pattern

What is Factory Method?

Factory Method defines an interface for creating an object, but lets subclasses decide which class to instantiate, allowing a class to defer instantiation to subclasses while maintaining loose coupling.

vs Simple Factory

Factory Method uses inheritance, Simple Factory uses composition
Factory Method is more extensible and follows OCP

Creator Class Role

  • 1 Declares the factory method that returns Product objects
  • 2 May provide default implementation of factory method
  • 3 Can call factory method to create products

Product Interface Role

  • 1 Defines the interface of objects the factory method creates
  • 2 All products must implement this common interface
  • 3 Enables polymorphism and interchangeability

Open/Closed Principle Support

Factory Method supports the Open/Closed Principle by allowing you to introduce new product types without modifying existing client code - you simply create new creator subclasses that implement the factory method to produce the new product types, keeping the system open for extension but closed for modification.

Abstract Factory Pattern

What is Abstract Factory?

Abstract Factory provides an interface for creating families of related or dependent objects without specifying their concrete classes, ensuring that created objects are compatible and work well together.

Problem it Solves

Abstract Factory solves the problem of creating entire families of related products that need to work together, which Factory Method cannot handle since it only creates single products without ensuring compatibility between different product types.

Abstract Factory vs Factory Method

Abstract Factory creates families of products
Factory Method creates single products
Abstract Factory uses composition
Factory Method uses inheritance

When to Choose Abstract Factory

  • When system needs multiple product families
  • When products from same family must be used together
  • When you want to hide product creation and ensure compatibility

Families of Related Products

In Abstract Factory, "families of related products" refer to groups of objects that are designed to work together and are conceptually related. For example, in a UI framework, a "Modern" family might include ModernButton, ModernTextBox, and ModernCheckbox, while a "Classic" family includes ClassicButton, ClassicTextBox, and ClassicCheckbox - each family has compatible components that share the same visual style and behavior.

What is the Prototype Design Pattern?

The Prototype pattern is a creational design pattern that allows creating new objects by copying existing objects (prototypes) rather than creating them from scratch, enabling object creation without depending on their concrete classes.

What Problem Does the Prototype Pattern Solve?

It solves the problem of expensive object creation when object initialization is costly in terms of resources or time, and when the system should be independent of how its objects are created, composed, and represented.

When Should You Use the Prototype Pattern?

When object creation is expensive or complex
When you want to avoid subclassing for object creation
When objects have numerous shared configurations
When you need to create objects at runtime

Key Participants in the Prototype Pattern

Prototype Interface

Declares the clone method

Concrete Prototype

Implements the cloning operation

Client

Creates new objects by cloning prototypes

Prototype Registry

Stores frequently used prototypes

Implementation Details

Shallow Copy

// Copies primitive fields
// Shares reference fields
public Object clone() {
  return super.clone();
}
  • Copies primitive values directly
  • Object references are shared
  • Faster but can cause side effects

Deep Copy

// Copies all fields recursively
public Object clone() {
  DeepCopy obj = (DeepCopy)super.clone();
  obj.referenceField = referenceField.clone();
  return obj;
}
  • Creates copies of referenced objects
  • No shared references
  • Slower but completely independent

Implementing Cloneable Interface

public class Document implements Cloneable {
  private String title;
  private List content;

  @Override
  public Document clone() {
    try {
      Document doc = (Document) super.clone();
      doc.content = new ArrayList<>(this.content);
      return doc;
    } catch (CloneNotSupportedException e) {
      throw new AssertionError();
    }
  }
}

Object.clone()

Native method, requires Cloneable interface, provides shallow copy by default

Copy Constructor

Explicit constructor that takes same type object, more flexible than clone()

Serialization

Serialize and deserialize object, creates complete deep copy automatically

What is the Adapter Pattern?

The Adapter Pattern is a structural design pattern that allows objects with incompatible interfaces to collaborate by converting the interface of one class into another interface that clients expect, acting as a bridge between two incompatible interfaces.

Problem it Solves

It solves the problem of integrating new components or third-party libraries with existing systems that have different interfaces, preventing the need to modify existing code while enabling seamless integration between incompatible systems.

Key Participants

Target

The interface that clients expect and understand

Adaptee

The existing interface that needs adapting

Adapter

The class that implements the Target interface and wraps the Adaptee

Client

The class that interacts with the Target interface

GoF Intent

According to the Gang of Four, the intent of the Adapter Pattern is to "convert the interface of a class into another interface clients expect, allowing classes to work together that couldn't otherwise because of incompatible interfaces."

Real-world Applications

Legacy system integration with modern applications
Third-party library integration with custom interfaces
Database driver adapters for different database systems
API wrappers for different service providers
Implementation & Technical Details

Class Adapter

// Using inheritance
public class ClassAdapter extends Adaptee implements Target {
  public void request() {
    specificRequest(); // Adapts the method
  }
}
  • Uses multiple inheritance (extends Adaptee)
  • Can override Adaptee behavior
  • Limited to one Adaptee class

Object Adapter

// Using composition
public class ObjectAdapter implements Target {
  private Adaptee adaptee;

  public ObjectAdapter(Adaptee adaptee) {
    this.adaptee = adaptee;
  }

  public void request() {
    adaptee.specificRequest(); // Delegates to adaptee
  }
}
  • Uses composition (has-a relationship)
  • More flexible - can adapt multiple adaptees
  • Works with any Adaptee subclass

Advantages of Object Adapter

More flexible - can adapt entire class hierarchies
Can adapt multiple adaptees simultaneously
Doesn't break encapsulation
Works with classes that can't be subclassed

What is the Decorator Design Pattern?

The Decorator pattern is a structural design pattern that allows behavior to be added to individual objects dynamically, without affecting the behavior of other objects from the same class, by wrapping them in special wrapper objects that contain the behaviors.

Intent of Decorator Pattern:

To attach additional responsibilities to an object dynamically while keeping the same interface. Decorators provide a flexible alternative to subclassing for extending functionality.

Key Participants:

  • C Component - Interface for objects that can have responsibilities added
  • D ConcreteComponent - Defines object to which additional responsibilities are added
  • D Decorator - Maintains reference to Component and conforms to Component interface
  • C ConcreteDecorator - Adds responsibilities to the component

Decorator vs Inheritance:

Runtime flexibility vs compile-time binding
Multiple decorators can be combined vs single inheritance
Avoids class explosion from multiple combinations

Problem Solved by Decorator Pattern:

The Decorator pattern solves the problem of needing to extend an object's functionality without creating numerous subclasses for every possible combination of features, providing a more flexible and maintainable approach to adding responsibilities to objects while following the Open/Closed Principle.

Structure & Implementation

UML Diagram Structure:

«interface»

+operation()
ConcreteComponent
+operation()

+operation()
-component: Component
ConcreteDecoratorA
+operation()

Component Interface Role:

The Component interface defines the common interface for both concrete components and decorators, ensuring that decorators can be used interchangeably with concrete components.

interface Coffee {
  double getCost();
  String getDescription();
}

Why Decorator is Abstract:

The Decorator class is abstract to prevent direct instantiation and to enforce the pattern structure, while maintaining the component reference and delegating operations to the wrapped component.

abstract class CoffeeDecorator implements Coffee {
  protected Coffee decoratedCoffee;
  public CoffeeDecorator(Coffee coffee) {
    this.decoratedCoffee = coffee;
  }
}

Arbitrary Composition:

Decorators can be composed arbitrarily because they all implement the same Component interface, allowing multiple decorators to wrap each other in any order while maintaining compatibility.

super.operation() Purpose:

The super.operation() call delegates to the wrapped component, ensuring the base functionality is preserved while allowing the decorator to add behavior before or after the delegation.

Basic Implementation

Basic Java Implementation:

// Component interface
interface Text { String format(); }

// Concrete component
class PlainText implements Text {
  private String content;
  public String format() { return content; }
}

// Abstract decorator
abstract class TextDecorator implements Text {
  protected Text text;
  public TextDecorator(Text text) { this.text = text; }
}

Adding New Functionality:

class BoldDecorator extends TextDecorator {
  public String format() {
    return "<b>" + text.format() + "</b>";
  }
}

class ItalicDecorator extends TextDecorator {
  public String format() {
    return "<i>" + text.format() + "</i>";
  }
}

Chaining Multiple Decorators:

Text text = new PlainText("Hello");
text = new BoldDecorator(text);
text = new ItalicDecorator(text);
// Result: <i><b>Hello</b></i>

Forgetting super.operation():

If you forget to call the wrapped object's method, the decorator breaks the chain and the base functionality is lost, effectively replacing rather than enhancing the behavior.

Order Control:

Decorator execution order is controlled by the wrapping sequence - the last decorator added is the first to execute, with inner decorators processing before outer ones in the method chain.

Comparisons with Other Patterns

Decorator vs Proxy:

Decorator adds responsibilities dynamically
Proxy controls access to the object
Decorators can be stacked infinitely
Proxy typically has one-to-one relationship

Decorator vs Adapter:

Decorator enhances interface without changing it
Adapter converts one interface to another
Decorator is transparent to clients
Adapter changes the interface for compatibility

vs Composite:

Decorator adds responsibilities to individual objects, while Composite treats individual objects and compositions uniformly. Decorator has exactly one component, Composite has zero-to-many children.

vs Strategy:

Choose Decorator when you need to add multiple responsibilities dynamically. Choose Strategy when you need to change the entire algorithm or behavior of an object.

vs Subclassing:

Decorator provides runtime flexibility and avoids class explosion. Subclassing is compile-time bound and can lead to combinatorial explosion of classes.

What is the Facade pattern?

The Facade pattern is a structural design pattern that provides a simplified interface to a complex subsystem, hiding its complexities and making it easier to use while promoting loose coupling between clients and subsystem components.

Main Intent

The primary intent behind the Facade pattern is to provide a unified, higher-level interface that makes a subsystem easier to use by wrapping a complicated subsystem with a simpler interface, thereby reducing complexity and dependencies.

Key Participants

1 Facade - Provides simplified interface to complex subsystem
2 Subsystem Classes - Implement subsystem functionality
3 Client - Uses facade instead of subsystem directly

Loose Coupling

The Facade pattern promotes loose coupling by acting as a mediator between clients and complex subsystems, allowing the subsystem to change without affecting clients and making the system more modular and maintainable.

Programming Principle

The Facade pattern primarily supports the Principle of Least Knowledge (Law of Demeter) by reducing the number of objects that clients need to interact with directly, and also supports Separation of Concerns by isolating complexity.

Simple Analogy

Think of a building facade - it presents a clean, simple exterior while hiding the complex internal systems (plumbing, electrical, structural) from outside viewers.

Implementation & Structure

Main Components

Facade Class - Single entry point with simplified methods
Subsystem Classes - Multiple specialized classes
Client Code - Interacts only with facade

Facade Implementation

public class ComputerFacade {
  private CPU cpu;
  private Memory memory;
  private HardDrive hardDrive;

  public void startComputer() {
    cpu.freeze();
    memory.load();
    hardDrive.read();
    cpu.jump();
    cpu.execute();
  }
}

Facade-Subsystem Relationship

The Facade has a composition relationship with subsystem classes - it knows about and delegates to multiple subsystem components, coordinating their work while hiding the complex interactions from clients.

Internal Knowledge

A Facade typically has knowledge of the subsystem's internal workings to properly coordinate between components, but it should abstract this complexity and present a clean, simple API to clients.

Subsystem Visibility

The Facade should hide most subsystem classes from clients, but it doesn't necessarily prevent direct access to subsystem classes when specialized functionality is needed beyond the facade's simplified interface.

Advantages & Benefits

Simplified Client Code

Clients interact with one simple interface instead of multiple complex subsystems

Improved Maintainability

Changes to subsystem only affect facade, not all client code

Reduced Dependencies

Clients depend only on facade, not on multiple subsystem classes

Easier Testing

Mock the facade instead of multiple subsystem components

Better Encapsulation

Hides implementation details and complex workflows

Clean Architecture

Promotes separation between high-level and low-level modules

Advanced Concepts

Stateful vs Stateless

Facades can be either stateful or stateless. Stateless facades are simpler and thread-safe. Stateful facades can maintain context between calls but require careful design to avoid threading issues and becoming too complex.

Preventing "God Object"

Best Practice Summary

Keep facades focused, use them to hide complexity not to create it, and remember that they should make life easier for clients while allowing subsystem evolution.

What is the Composite design pattern?

The Composite pattern is a structural design pattern that allows you to compose objects into tree structures to represent part-whole hierarchies, letting clients treat individual objects and compositions of objects uniformly through a common interface.

Key Participants in Composite Pattern

Component

Declares common interface for all objects in composition

Leaf

Represents leaf objects with no children

Composite

Stores child components and implements child-related operations

What problem does Composite pattern solve?

It solves the problem of treating individual objects and compositions differently, which leads to complex client code filled with type checks and conditionals when working with tree-like structures, by providing a unified interface for both.

When should you use Composite pattern?

Use Composite pattern when you need to represent part-whole hierarchies of objects, when you want clients to ignore differences between individual objects and compositions, or when you're dealing with tree-structured data where nodes can be either leaves or containers.

Main Benefits of Composite Pattern

Simplified Client Code

Clients can treat simple and complex elements uniformly

Easy to Add New Types

New element types can be added without changing existing code

Flexible Structure

Makes complex tree structures easier to work with

Recursive Composition

Enables recursive algorithms over object structures

Role of Component Interface

The Component interface declares common operations for both simple and complex elements, providing a unified way to access and manipulate objects in the composition, and defines the contract that all concrete classes must follow.

Intermediate Questions

Design Considerations

Child Management in Component Interface

The Component interface can declare child management operations (transparent design) for uniform treatment but may throw exceptions in leaves, or these operations can be only in Composite (safe design) but require client type checking. Transparent design is more common as it provides true uniformity at the cost of potential runtime errors.

Safe vs Transparent Design Trade-offs

Transparent Design
  • True uniformity - same interface for all
  • Runtime errors for invalid operations
  • Simpler client code
Safe Design
  • Compile-time type safety
  • Client must check types explicitly
  • More complex client code

Type Safety in Composite Pattern

Type safety is challenging in Composite pattern because the common interface treats leaves and composites uniformly. Solutions include using the safe design (separate interfaces), runtime type checks, or accepting that some operations may throw exceptions when called on inappropriate node types.

Child Management Problem

The child management problem refers to the dilemma of whether to include child management operations in the Component interface. Including them provides transparency but may lead to runtime errors; excluding them provides safety but loses uniformity and requires clients to distinguish between leaf and composite nodes.

Preventing Cyclic References

To prevent adding a Composite to itself and creating cycles, implementations should check for identity in add() methods, maintain parent references to detect cycles during traversal, or use visitor patterns with cycle detection logic to avoid infinite recursion during operations.

What is the Bridge design pattern?

The Bridge pattern is a structural design pattern that decouples an abstraction from its implementation, allowing both to vary independently by separating the abstraction hierarchy from the implementation hierarchy through composition.

What problem does the Bridge pattern solve?

The Bridge pattern solves the problem of permanent binding between an abstraction and its implementation, which leads to a combinatorial explosion of subclasses when you have multiple dimensions of variation, by allowing abstraction and implementation to be developed and extended independently.

How does Bridge pattern promote loose coupling?

The Bridge pattern promotes loose coupling by separating the abstraction hierarchy from the implementation hierarchy, allowing changes in the implementation to not affect the abstraction and vice versa, and enabling runtime binding of implementations to abstractions through composition rather than inheritance.

What is the main intent behind the Bridge pattern?

The main intent of the Bridge pattern is to decouple an abstraction from its implementation so that the two can vary independently, avoiding a permanent binding between them and providing flexibility to extend both hierarchies without affecting each other.

What is the Flyweight pattern?

The Flyweight pattern is a structural design pattern that minimizes memory usage by sharing as much data as possible with similar objects, storing common data externally and passing it to the objects when needed, effectively allowing thousands of fine-grained objects to be represented by a much smaller number of shared objects.

What problem does it solve?

The Flyweight pattern addresses the problem of excessive memory consumption when an application needs to create a very large number of similar objects, particularly in scenarios like document editors with thousands of characters, game development with numerous entities, or graphical applications with many repeated elements, by separating intrinsic state that can be shared from extrinsic state that varies.

Extrinsic State

Variable, context-specific data passed to flyweight (e.g., position, size)

When to use Flyweight pattern?

You should consider using the Flyweight pattern when your application needs to create a massive number of similar objects that would otherwise consume excessive memory, when most object state can be made extrinsic, when you can identify groups of objects that share common immutable characteristics, and when the application doesn't depend on object identity since shared flyweight objects may be used in multiple contexts.

Core Concepts Deep Dive

Object Sharing Concept

Object sharing in the Flyweight pattern refers to the practice of reusing the same object instance across multiple contexts instead of creating new instances for each occurrence, where the shared object contains only the intrinsic state while the extrinsic state is passed in during operations.

How Flyweight Reduces Memory

The Flyweight pattern dramatically reduces memory usage by storing shared intrinsic state once rather than duplicating it across thousands of objects, while extrinsic state is either computed when needed or stored in a separate lightweight structure, effectively transforming what would be O(n) memory usage into O(1) for shared components plus O(n) for unique extrinsic data.

What is the role of the Command interface?

The Command interface declares the execute() method that all concrete commands must implement, providing a common contract for executing operations and enabling polymorphic treatment of different commands by the invoker.

What is the role of the Invoker in Command pattern?

The Invoker holds a command and at some point asks the command to carry out the request by calling its execute() method. It doesn't know anything about the concrete command or receiver - it only works with the Command interface.

What is the role of the Receiver in Command pattern?

The Receiver knows how to perform the operations associated with carrying out a request. Any class can act as a Receiver, and it contains the actual business logic that gets executed when a command's execute() method is called.

What is the role of the Client in Command pattern?

The Client creates ConcreteCommand objects and sets their receivers. It knows which commands to create and which receiver objects to pass to them, effectively configuring the command objects with the specific operations they should perform.

How do you implement undo/redo functionality using Command pattern?

Implement undo by adding an undo() method to the Command interface and storing the previous state in concrete commands. Maintain two stacks: one for executed commands (for undo) and one for undone commands (for redo).

Implementation Steps:

  1. 1 Add undo() method to Command interface
  2. 2 Store state needed for undo in ConcreteCommand
  3. 3 Maintain history stack for executed commands
  4. 4 Maintain redo stack for undone commands
interface Command {
  void execute();
  void undo();
}

class LightOnCommand implements Command {
  private Light light;
  private boolean previousState;
  public void execute() {
    previousState = light.isOn();
    light.turnOn();
  }
  public void undo() {
    if (!previousState) light.turnOff();
  }
}

What is a Composite Command (Macro Command)?

A Composite Command is a command that contains and executes multiple other commands, treating them as a single unit. It implements the same Command interface but delegates execution to its child commands.

class MacroCommand implements Command {
  private List commands = new ArrayList<>();
  public void addCommand(Command cmd) { commands.add(cmd); }
  public void execute() {
    for (Command cmd : commands) {
      cmd.execute();
    }
  }
  public void undo() {
    // Reverse order for undo
    for (int i = commands.size()-1; i >= 0; i--) {
      commands.get(i).undo();
    }
  }
}

How do you implement command history?

Implement command history by maintaining a stack (for undo) and optionally a separate stack (for redo). Each executed command is pushed onto the undo stack, and when undo is called, the command is popped and its undo() method is executed, then pushed to the redo stack.

What is the State design pattern?

The State pattern is a behavioral design pattern that allows an object to alter its behavior when its internal state changes, making it appear as if the object changed its class by encapsulating state-specific behavior into separate state objects and delegating state-dependent behavior to the current state object.

What problem does the State pattern solve?

The State pattern solves the problem of objects having complex, state-dependent behavior that typically leads to lengthy conditional statements (if/else or switch) scattered throughout the code, which becomes difficult to maintain, extend, and understand as new states are added or behavior changes.

What are the key participants in the State pattern?

Context

Maintains reference to current state object and delegates state-specific behavior

State Interface

Defines common interface for all concrete state classes

Concrete States

Implement state-specific behavior and handle state transitions

How does State pattern differ from conditional statements?

Conditional Statements

  • Complex conditional logic scattered throughout code
  • Difficult to add new states
  • Violates Open/Closed Principle

State Pattern

  • Clean separation of state-specific behavior
  • Easy to add new states
  • Follows Open/Closed Principle

What are the main benefits of using State pattern?

Eliminates complex conditional logic

Easy to add new states without modifying existing code

Improves code readability and maintainability

Basic Implementation

What is the basic structure of State pattern?

// State Interface
interface State { void handle(); }

// Concrete States

  public void handle() { /* state A behavior */ }
}

// Context
class Context {
  private State currentState;
  public void setState(State state) { this.currentState = state; }
  public void request() { currentState.handle(); }
}

How do you define the State interface?

The State interface defines a common contract that all concrete state classes must implement, typically containing methods that represent state-dependent behaviors, allowing the context to work with any state object through this uniform interface without knowing the concrete state class.

What is the role of the Context class?

The Context class maintains a reference to the current state object, delegates state-specific behavior to the current state, and provides methods for clients to trigger state transitions while remaining decoupled from the concrete state implementations.

How do concrete state classes interact with the context?

Concrete state classes interact with the context by either receiving a reference to the context through their methods or by the context passing itself as a parameter, enabling state objects to trigger state transitions by calling context's state-changing methods while implementing state-specific behavior.

How does state transition happen in State pattern?

State transitions occur when concrete state objects, during the execution of their state-specific behavior, determine that the context should change to a different state and call the context's state-setting method, which updates the current state reference and effectively changes the context's behavior.

  • Used for stateful objects with lifecycle

When to choose State pattern over Strategy?

Choose the State pattern when an object's behavior needs to change dynamically based on its internal state, and state transitions follow a defined lifecycle, whereas choose Strategy pattern when you need to provide different algorithms that can be selected by the client and used interchangeably without automatic transitions.

State vs Template Method pattern

The State pattern changes an object's behavior by changing its state object at runtime, while the Template Method pattern defines the skeleton of an algorithm in a base class and lets subclasses override specific steps, providing compile-time flexibility through inheritance rather than runtime flexibility through composition.

How to handle state transitions?

State transitions can be handled either by the context object, where it decides the next state based on current state and action, or by the state objects themselves, where each state knows which state should come next, with the latter approach being more common as it keeps transition logic encapsulated within state classes.

How to avoid circular dependencies?

Circular dependencies between Context and State can be avoided by having the Context provide a method for state transitions that States can call, rather than States directly instantiating other States, and by using interfaces or abstract classes to break direct dependencies between concrete classes.

The starting state is typically initialized in the Context's constructor by creating an instance of the initial concrete state class, ensuring the context begins in a valid state and is ready to handle requests immediately after instantiation.

How to handle illegal state transitions?

Illegal state transitions can be handled by having state objects throw specific exceptions when an operation is not allowed in the current state, or by implementing a default behavior that does nothing or returns an error, with the choice depending on whether illegal operations should be considered programming errors or expected scenarios.

What is Chain of Responsibility?

The Chain of Responsibility is a behavioral design pattern that allows passing requests along a chain of handlers, where each handler decides either to process the request or to pass it to the next handler in the chain, promoting loose coupling between senders and receivers.

Problem it Solves

This pattern solves the problem of hard-coded request-handler relationships by allowing multiple objects to handle a request without the sender needing to know which object will ultimately process it, enabling dynamic handler configuration and avoiding coupling between request senders and specific receivers.

C ConcreteHandler - Implements the handler interface
C Client - Initiates requests to the chain

  • • Reduces coupling between senders and receivers
  • • Allows dynamic chain configuration
  • • Simplifies object responsibilities

Drawbacks:

  • • Requests may go unhandled
  • • Debugging can be difficult
  • • Performance overhead

Handler Interface Role

The handler interface defines the contract for handling requests and typically includes methods for setting the next handler and processing requests, establishing a common protocol that all concrete handlers must follow.

Successor Reference

The "next" reference maintains the chain linkage, allowing each handler to delegate requests it cannot process to the subsequent handler, creating the sequential flow that characterizes the pattern.

Processing Decision

Handlers use business logic to determine if they can process a request, typically based on request type, content, or handler capability, and may either handle it entirely or pass it along the chain.

Can handlers process AND pass?

Yes, handlers can perform partial processing and then pass the request to the next handler, which is common in middleware scenarios where each handler adds value while allowing subsequent handlers to continue processing.

What is the Memento Design Pattern?

The Memento design pattern is a behavioral pattern that provides the ability to capture and externalize an object's internal state without violating encapsulation, so that the object can be restored to this state later, enabling undo/redo functionality and state snapshots.

Three Main Components of Memento Pattern

Originator

Creates and restores mementos containing its state

Memento

Stores the internal state of the Originator

Caretaker

Manages and stores mementos without modifying them

What Problem Does Memento Pattern Solve?

The Memento pattern addresses the challenge of saving and restoring an object's state without exposing its internal implementation details, maintaining encapsulation while providing state persistence and history management capabilities.

When to Use Memento Pattern

When you need undo/redo functionality
For taking state snapshots
When state restoration is needed
To maintain encapsulation boundaries

Key Benefits of Memento Pattern

Preserves encapsulation boundaries
Simplifies originator implementation
Easy state management and restoration
Separation of state persistence concerns
Core Components & Structure

Role of the Originator

The Originator is the object whose state needs to be saved and restored, responsible for creating mementos containing snapshots of its current state and using mementos to restore its previous state while maintaining complete control over its internal data.

Responsibility of Memento Object

The Memento object acts as a secure container that stores the Originator's internal state at a specific point in time, providing controlled access to this state while preventing external objects from directly modifying or inspecting the stored data.

Role of the Caretaker

The Caretaker manages the lifecycle of memento objects by storing them in a history stack or collection, requesting state snapshots from the Originator when needed, and providing stored mementos back to the Originator for state restoration operations.

Component Interaction Flow

1 Caretaker requests a memento from Originator to save state
2 Originator creates memento with current state and returns it
3 Caretaker stores memento without accessing its contents
4 When restoration needed, Caretaker provides memento to Originator
5 Originator restores its state from the memento

Why Memento Objects Are Typically Immutable

Memento objects are designed as immutable to ensure state integrity and prevent accidental or malicious modification of saved states, guaranteeing that historical snapshots remain consistent and reliable for restoration operations throughout the application lifecycle.

Implementation Details

Originator-Only Access to Memento State

To ensure only the Originator can access the Memento's state, the Memento class is typically implemented as an inner class of the Originator or uses package-private visibility, allowing the Originator direct access while restricting other classes from viewing or modifying the stored state.

Narrow Interface vs Wide Interface

Narrow Interface

  • Limited access for Caretaker
  • No state inspection methods
  • Prevents state manipulation

Wide Interface

  • Full access for Originator
  • State retrieval methods
  • Allows state restoration

Implementing Undo/Redo with Memento

Undo/redo functionality is implemented by maintaining two stacks in the Caretaker - one for undo history and one for redo history, where each state change creates a memento pushed to undo stack, undo operations move mementos to redo stack, and redo operations move them back while the Originator restores states accordingly.

Memory Considerations

Large state objects can consume significant memory in history stacks
Implement cleanup strategies for old mementos
Consider incremental mementos for large state changes

Deep Copy vs Shallow Copy in Memento

Memento implementations must carefully choose between deep and shallow copying based on state complexity and reference sharing requirements, where deep copying ensures complete state isolation but impacts performance, while shallow copying is efficient but requires careful handling of mutable shared objects to prevent unintended side effects during state restoration.

Comparison with Other Patterns

Memento vs Command Pattern

While both patterns support undo functionality, the Command pattern stores operations and their reversal logic, focusing on action history, whereas the Memento pattern stores object state snapshots, focusing on state history without requiring knowledge of how state changes occurred or how to reverse them.

Memento vs Prototype Pattern

The Prototype pattern focuses on creating new objects by cloning existing instances for object creation optimization, while the Memento pattern specifically addresses state capture and restoration for a single object over time, serving different purposes despite both involving object copying mechanisms.

Memento vs State Pattern

The State pattern manages an object's behavior changes based on its internal state transitions, while the Memento pattern captures and restores the object's state at specific points in time; Memento is chosen when you need historical state tracking, whereas State is used for dynamic behavior based on current state.

Memento and Iterator Relationship

The Iterator pattern can use Memento to capture iteration state, allowing iterators to save their position and resume later, creating a complementary relationship where Memento provides state persistence capabilities that enhance Iterator functionality with bookmarking and resumption features.

Memento vs Serialization for State Saving

While serialization provides general-purpose object persistence, Memento offers controlled, encapsulated state saving with selective data exposure and restoration logic; Memento is preferred for in-memory state history with encapsulation requirements, whereas serialization suits long-term storage and data transfer scenarios.

Fundamental Concepts

What is the Visitor design pattern?

The Visitor pattern is a behavioral design pattern that allows you to separate algorithms from the objects on which they operate, enabling you to add new operations to existing object structures without modifying the classes of the elements.

What problem does the Visitor pattern solve?

The Visitor pattern solves the problem of needing to perform various operations on elements of an object structure without polluting their classes with numerous unrelated methods, and allows adding new operations without changing the element classes when the object structure is stable but operations need frequent additions.

What are the key components of the Visitor pattern?

Visitor Interface

Declares visit methods for each concrete element type

Concrete Visitors

Implement the operations to be performed on elements

Element Interface

Declares accept method that takes a visitor

Concrete Elements

Implement accept method to call visitor's visit method

When should you consider using the Visitor pattern?

You should consider using the Visitor pattern when you have a complex object structure with many classes and want to perform unrelated operations on them, when the object structure is stable but you frequently need to add new operations, or when you want to keep related operations together in one class rather than spreading them across multiple element classes.

Advantages and Disadvantages

Advantages

  • Open/Closed Principle: Easy to add new operations
  • Single Responsibility: Related operations stay together
  • Accumulate state while visiting elements

Disadvantages

  • Hard to add new element types
  • Violates encapsulation of element classes
  • Can lead to complex code structure
Core Implementation

What is the role of the Visitor interface?

The Visitor interface declares a set of visiting methods that can take concrete elements as arguments, with each method typically named "visit" and accepting a different concrete element type, allowing the visitor to perform operations specific to each element type while maintaining type safety.

interface Visitor {
  void visit(ConcreteElementA element);
  void visit(ConcreteElementB element);
}

What is the role of the Element interface?

The Element interface declares the accept method that takes a visitor as an argument, serving as the entry point for the visitor to access the element and enabling the double dispatch mechanism by allowing the element to call the appropriate visit method on the visitor based on its concrete type.

interface Element {
  void accept(Visitor visitor);
}

How does double dispatch work?

Double dispatch is a mechanism where the operation executed depends on both the runtime type of the visitor and the runtime type of the element being visited, achieved through the element's accept method calling the visitor's visit method with itself as an argument, effectively performing two virtual method calls to determine the exact operation to execute.

// Element calls visitor
element.accept(visitor);

// Which calls back to specific visit method
visitor.visit(this);

First dispatch: Which accept method? (Based on element type)
Second dispatch: Which visit method? (Based on visitor type)

What is the accept() method?

The accept method is the gateway that allows a visitor to access an element, implemented by each concrete element to call the appropriate visit method on the visitor passing itself as an argument, thereby enabling the double dispatch mechanism that determines both the element type and visitor type at runtime.

class ConcreteElement implements Element {
  public void accept(Visitor visitor) {
    visitor.visit(this); // Key to double dispatch
  }
}

How to add new operations?

You can add new operations without modifying existing classes by creating a new concrete visitor class that implements the visitor interface and provides implementations for all the visit methods, allowing you to extend functionality while keeping the element classes unchanged and maintaining the open/closed principle.

class NewOperationVisitor implements Visitor {
  public void visit(ConcreteElementA element) {
    // New operation for ElementA
  }
  public void visit(ConcreteElementB element) {
    // New operation for ElementB
  }
}
Advanced Concepts

Single vs Double Dispatch

Single Dispatch

  • Runtime type of one object determines method
  • Standard virtual method calls in Java
  • Only receiver type matters

Double Dispatch

  • Runtime types of TWO objects determine method
  • Achieved via Visitor pattern in Java
  • Both receiver and argument types matter

How Visitor violates encapsulation?

The Visitor pattern violates encapsulation because concrete visitors often need to access the internal state of element objects through public getter methods, breaking the principle of information hiding and creating tight coupling between visitors and the internal representation of elements, which can make the system more fragile to changes in element implementations.

Cyclic Dependency Issue

The Visitor pattern creates a cyclic dependency where the visitor interface depends on all concrete element types by declaring visit methods for each of them, and simultaneously all concrete elements depend on the visitor interface through their accept methods, making it difficult to add new element types as it requires modifying the visitor interface and all existing visitors.

Adding New Element Types

Adding new element types to an existing visitor hierarchy is challenging because it requires modifying the visitor interface to add a new visit method, which in turn requires updating all existing concrete visitor implementations to handle the new element type, making this pattern unsuitable for situations where the element hierarchy is expected to change frequently.

Acyclic Visitor Pattern

The Acyclic Visitor pattern is a variation that breaks the cyclic dependency by using parameterized visit methods and runtime type checking, allowing visitors to handle only specific element types they're interested in without requiring changes to the base visitor interface when new element types are added, at the cost of losing compile-time type safety and requiring explicit type checks.

interface Visitor { } // Marker interface
interface Element {
  void accept(Visitor visitor);
}
// Concrete visitors check types at runtime
