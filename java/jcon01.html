Section 2.1: What is a Thread?

Before we create threads, we must understand what they are at both the JVM level and the OS level.

The "Doubt Clarifier" – What is ThreadLocalMap?

Each thread has its own ThreadLocalMap that stores values for ThreadLocal variables. When you call ThreadLocal.get(), it retrieves the value from the current thread's map. This is how ThreadLocal provides thread-isolated storage.

The "Doubt Clarifier" – What is parkBlocker?

When a thread is blocked by LockSupport.park(), the parkBlocker field stores the object that caused the blocking. This is used by diagnostic tools to identify why a thread is blocked.

Example:

// Internal implementation of LockSupport
        public static void park(Object blocker) {
            Thread t = Thread.currentThread();
            setBlocker(t, blocker);  // Stores blocker in t.parkBlocker
            UNSAFE.park(false, 0L);
            setBlocker(t, null);
        }

Subsection 2.1.2: The Native Thread – The OS-Level Reality

Every Java thread (platform thread) maps 1:1 to an OS thread. This is called the Native Thread Model.

2 / 23

What happens when you call new Thread().start()?

  1. JVM allocates memory: The JVM allocates a Thread object on the Java heap.
  2. JVM calls native method: Thread.start() calls the native method start0().
  3. OS thread creation: The JVM asks the OS to create a new native thread (via pthread_create on Linux, CreateThread on Windows).
  4. OS allocates resources: The OS allocates:
    • A thread control block (TCB) in kernel space.
    • A stack (typically 1 MB, configurable via -Xss).
    • A program counter (PC) and register set.
  5. JVM attaches: The JVM attaches the new native thread to the Java Thread object.
  6. Thread begins execution: The OS scheduler schedules the thread, and it begins executing the run() method.

The "Doubt Clarifier" – What is the stack size?

The stack stores method frames (local variables, parameters, return addresses). Each frame has a fixed size determined by the compiler. The stack size is configurable:

java -Xss1m MyClass   # 1 MB stack (default)
        java -Xss512k MyClass # 512 KB stack (for many threads)
        java -Xss2m MyClass   # 2 MB stack (for deep recursion)
3 / 23

The "Doubt Clarifier" – What happens if you exceed the stack size?

You get a StackOverflowError. This often happens with deep recursion or infinite recursion.

Example:

public static void recursive() {
            recursive();  // Infinite recursion
        }

Each call adds a new frame to the stack. When the stack overflows, the JVM throws StackOverflowError.

The "Doubt Clarifier" – What is ThreadGroup?

ThreadGroup is a way to group threads for bulk operations. You can interrupt all threads in a group or set their priority.

Example:

ThreadGroup group = new ThreadGroup("Workers");
        Thread t1 = new Thread(group, () -> { /* work */ }, "Worker-1");
        Thread t2 = new Thread(group, () -> { /* work */ }, "Worker-2");
        group.interrupt();  // Interrupts both t1 and t2

But note: ThreadGroup is largely obsolete. Modern practice uses ExecutorService for thread management. ThreadGroup is still used by the JVM for internal purposes.

Subsection 2.1.4: The "Doubt Clarifier" – Why does Thread implement Runnable?

Look at the Thread class signature:

public class Thread implements Runnable {
            // ...
            @Override
            public void run() {
                if (target != null) {
                    target.run();
                }
            }
        }

Thread implements Runnable. This means you can pass a Thread instance to another Thread (though this is almost never done).

Why? Historical reasons. The designers wanted Thread to be a valid Runnable so that you could override run() directly when extending Thread.

But the better practice is to implement Runnable separately, as we'll see in Section 2.2.

Section 2.2: Creating a Thread – The Two Primary Ways

There are two fundamental ways to create a thread in Java. Let's explore both in extreme detail.

Subsection 2.2.1: Method 1 – Extending the Thread Class

Syntax:

public class MyThread extends Thread {
            @Override
            public void run() {
                System.out.println("Thread is running: " + Thread.currentThread().getName());
            }
        }
        
        // Usage        MyThread t = new MyThread();
        t.start();

What happens internally:

  • You create a subclass of Thread.
  • You override run() (which is public void).
  • When you call start(), the JVM creates a native thread and invokes your run() method.

Pros: Simple and straightforward. You can access Thread methods directly (getName(), setPriority(), etc.).

Cons: Single inheritance limitation. Tight coupling. Not flexible.

6 / 23

The "Doubt Clarifier" – Can I call run() directly instead of start()?

Yes, but do not do it.

MyThread t = new MyThread();
        t.run();  // This runs in the current thread, NOT a new thread!

run() is just a regular method. Calling it directly doesn't create a new thread. The start() method is what creates the new thread and schedules it.

If you call run() directly, it executes in the calling thread, not in a separate thread.

Subsection 2.2.2: Method 2 – Implementing the Runnable Interface

Syntax:

public class MyRunnable implements Runnable {
            @Override
            public void run() {
                System.out.println("Runnable running: " + Thread.currentThread().getName());
            }
        }
        
        // Usage
        MyRunnable task = new MyRunnable();
        Thread t = new Thread(task);
        t.start();

Pros: Flexible (can extend another class). Reusable (same Runnable can be submitted to a thread pool). Separation of concerns.

Cons: Slightly more verbose.

7 / 23

Subsection 2.2.3: Method 3 – Using Lambda Expressions (Java 8+)

Because Runnable is a functional interface, you can use lambdas:

// Lambda expression
        Thread t = new Thread(() -> {
            System.out.println("Lambda running: " + Thread.currentThread().getName());
        });
        t.start();

Even shorter (method reference):

Runnable task = System.out::println;
        Thread t = new Thread(task);
        t.start();

The "Doubt Clarifier" – What does "effectively final" mean?

A variable is effectively final if it is not reassigned after initialization. Lambdas can only capture effectively final variables.

int x = 10;
        Runnable r = () -> System.out.println(x);  // OK (x is effectively final)
        
        int y = 20;
        y = 30;  // y is reassigned, NOT effectively final
        Runnable r2 = () -> System.out.println(y);  // COMPILE ERROR!

Subsection 2.2.4: Method 4 – Using ExecutorService (The Real-World Standard)

In production code, you rarely create Thread objects directly. You use thread pools.

ExecutorService executor = Executors.newFixedThreadPool(10);
        executor.execute(() -> {
            System.out.println("Task running on thread pool");
        });
        executor.shutdown();

Subsection 2.2.5: The "Doubt Clarifier" – Which method should I use?

ScenarioRecommended Approach
Learning/experimentingExtend Thread or implement Runnable
Simple one-off tasksLambda with Runnable
Production code (task execution)ExecutorService (thread pools)
Production code (async results)CompletableFuture
Java 21+ (massive concurrency)Virtual Threads (Executors.newVirtualThreadPerTaskExecutor())

Never extend Thread in production code. It's an anti-pattern.

Subsection 2.2.6: The "Doubt Clarifier" – Can I create threads without a Runnable?

Yes, by overriding run() in a subclass of Thread:

class MyThread extends Thread {
            @Override
            public void run() {
                System.out.println("No Runnable needed");
            }
        }

But this is just Method 1 (extending Thread). The target (Runnable) is null, so Thread.run() executes the overridden method.

Section 2.3: The Thread Lifecycle (States)

A thread in Java can be in one of six states (as defined by the Thread.State enum). Understanding these states is critical for debugging, performance tuning, and preventing liveness issues.

Subsection 2.3.1: The Six States – Complete Breakdown

StateDescription
NEWThread object created but not started
RUNNABLEThread is ready to run, or is currently running on a CPU core
BLOCKEDThread is blocked, waiting to acquire a monitor lock
WAITINGThread is waiting indefinitely for another thread to perform an action
TIMED_WAITINGThread is waiting for a specified amount of time
TERMINATEDThread has completed execution

The "Doubt Clarifier" – Is RUNNABLE the same as "running"?

No! RUNNABLE means the thread is ready to run. It may be waiting for the OS scheduler to assign CPU time. In a busy system with more threads than cores, many RUNNABLE threads are actually waiting for CPU.

The "Doubt Clarifier" – What's the difference between WAITING and BLOCKED?

  • BLOCKED: Waiting for a monitor lock (synchronized). The thread is competing with other threads for the lock.
  • WAITING: Waiting for notification or termination. The thread is not competing for a lock; it's passively waiting for an external signal.

Subsection 2.3.2: Visualizing State Transitions

    NEW
         |
         v
     RUNNABLE  <---->  BLOCKED
         |             (acquires lock)
         | (wait)
         v
      WAITING  <---->  TIMED_WAITING

Subsection 2.3.3: Code Examples – Observing Thread States

Example 1: NEW and RUNNABLE

public class StateDemo {
            public static void main(String[] args) throws InterruptedException {
                Thread t = new Thread(() -> {
                    for (int i = 0; i < 100_000_000; i++) { /* busy loop */ }
                });
                System.out.println("After creation: " + t.getState());  // NEW
                t.start();
                System.out.println("After start: " + t.getState());     // RUNNABLE
                t.join();
                System.out.println("After join: " + t.getState());      // TERMINATED
            }
        }
11 / 23

Example 2: WAITING

public class WaitDemo {
            public static void main(String[] args) throws InterruptedException {
                Object lock = new Object();
                Thread t = new Thread(() -> {
                    synchronized (lock) {
                        try {
                            System.out.println("Thread waiting...");
                            lock.wait();  // Releases lock and waits
                            System.out.println("Thread notified!");
                        } catch (InterruptedException e) {
                            Thread.currentThread().interrupt();
                        }
                    }
                });
                t.start();
                Thread.sleep(100);
                System.out.println("Thread state: " + t.getState());  // WAITING
                synchronized (lock) { lock.notify(); }
                t.join();
                System.out.println("Thread state: " + t.getState());  // TERMINATED
            }
        }

The "Doubt Clarifier" – Why does wait() release the lock?

Because if it didn't, no other thread could enter the synchronized block to call notify(). The thread must give up the lock so that other threads can signal it.

Example 3: TIMED_WAITING

Thread t = new Thread(() -> {
            try { Thread.sleep(5000); } catch (InterruptedException e) {}
        });
        t.start();
        Thread.sleep(100);
        System.out.println(t.getState());  // TIMED_WAITING

Example 4: BLOCKED

public class BlockedDemo {
            private static final Object lock = new Object();
            public static void main(String[] args) throws InterruptedException {
                Thread t1 = new Thread(() -> {
                    synchronized (lock) {
                        try { Thread.sleep(10000); } catch (InterruptedException e) {}
                    }
                });
                Thread t2 = new Thread(() -> {
                    synchronized (lock) {
                        System.out.println("Acquired lock!");
                    }
                });
                t1.start();
                Thread.sleep(100);
                t2.start();
                Thread.sleep(100);
                System.out.println("t2 state: " + t2.getState());  // BLOCKED
                t1.join();
                t2.join();
            }
        }

The "Doubt Clarifier" – Why is t2 in BLOCKED and not WAITING?

Because t2 is trying to acquire the intrinsic lock (synchronized). It's not waiting for a notification; it's waiting for the lock to be released. That's the definition of BLOCKED.

Section 2.4: Important Thread Methods

Let's explore the most commonly used methods of the Thread class, their semantics, and their pitfalls.

Subsection 2.4.1: start() – The Only Way to Begin

Signature: public void start()

What it does:

  • Checks that the thread is in NEW state. If not, throws IllegalThreadStateException.
  • Allocates a native thread (OS thread).
  • Schedules the native thread to run.
  • The OS scheduler eventually invokes the thread's run() method.

The "Doubt Clarifier" – Why is start() synchronized?

Internally, start() is synchronized to prevent two threads from calling start() on the same Thread object simultaneously.

Can I call start() twice on the same thread? No. It will throw IllegalThreadStateException.

Subsection 2.4.2: run() – The Task Entry Point

Signature: public void run()

What it does: Contains the code executed by the thread.

14 / 23

Subsection 2.4.3: join() – Waiting for Thread Termination

Signature:

  • public void join() throws InterruptedException – Wait indefinitely.
  • public void join(long millis) throws InterruptedException – Wait with timeout.
  • public void join(long millis, int nanos) throws InterruptedException – Fine-grained timeout.

What it does: The calling thread waits for the specified thread to terminate.

Thread t = new Thread(() -> {
            try { Thread.sleep(2000); } catch (InterruptedException ignored) {}
        });
        t.start();
        t.join();  // Main thread waits here until t finishes
        System.out.println("t has finished");

Does join() release locks? No. The calling thread holds its locks while waiting. This can cause deadlock.

Subsection 2.4.4: sleep() – Pausing the Current Thread

Signature:

  • public static void sleep(long millis) throws InterruptedException
  • public static void sleep(long millis, int nanos) throws InterruptedException

What it does: The current thread pauses for the specified time. It does not release any locks.

15 / 23

The "Doubt Clarifier" – Why is sleep() static?

Because it always operates on the current thread. You cannot make another thread sleep.

Thread.sleep(1000);  // Current thread sleeps for 1 second

What is the minimum sleep time? The JVM's thread scheduler has a certain granularity (typically 1-10 ms on most systems). sleep(1) might actually sleep 1-10 ms depending on the OS.

Is sleep() interrupted? Yes. If another thread interrupts the sleeping thread, sleep() throws InterruptedException.

try {
            Thread.sleep(10000);
        } catch (InterruptedException e) {
            System.out.println("Woken up early!");
            Thread.currentThread().interrupt();  // Re-interrupt
        }

Subsection 2.4.5: yield() – Yielding the CPU

Signature: public static void yield()

What it does: A hint to the JVM scheduler that the current thread is willing to give up its CPU time.

Does yield() guarantee anything? No. It's just a hint. The scheduler may ignore it. Almost never use it.

Subsection 2.4.6: interrupt() – Interrupting a Thread

Signature: public void interrupt()

What it does: Sets the thread's interrupt flag and, if the thread is blocked in certain methods, wakes it up.

What methods throw InterruptedException?

  • Thread.sleep()
  • Object.wait()
  • Thread.join()
  • BlockingQueue.take()
  • Lock.lockInterruptibly()
  • Future.get()

What does interrupt() do to a thread that's not blocked? It just sets the interrupt flag.

How do I handle InterruptedException properly?

Good: Propagate it or restore the interrupt flag.

public void myMethod() throws InterruptedException {
            Thread.sleep(1000);  // Propagate
        }
public void myMethod() {
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();  // Restore flag
            }
        }

Bad (swallow):

public void myMethod() {
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                // Swallow silently! BAD!
            }
        }
17 / 23

What's the difference between interrupted() and isInterrupted()?

  • interrupted(): Static method. Returns the interrupt flag and clears it.
  • isInterrupted(): Instance method. Returns the interrupt flag and does not clear it.
Thread t = Thread.currentThread();
        t.interrupt();
        boolean flag1 = t.isInterrupted();  // true
        boolean flag2 = Thread.interrupted(); // true (clears flag)
        boolean flag3 = t.isInterrupted();  // false (flag was cleared)

Subsection 2.4.7: setDaemon() and isDaemon() – Daemon Threads

What happens when all non-daemon threads finish? The JVM exits, even if daemon threads are still running.

Thread daemon = new Thread(() -> {
            while (true) { /* Infinite loop */ }
        });
        daemon.setDaemon(true);
        daemon.start();
        // Main thread ends, JVM exits. Daemon thread is killed.

Use cases for daemon threads: Garbage collection (GC threads), background health checks, monitoring.

Can you call setDaemon() after start()? No. It throws IllegalThreadStateException.

Section 2.5: Callable and Future – Tasks That Return Results

Runnable is great, but it has a limitation: it cannot return a result or throw checked exceptions. This is where Callable comes in.

Subsection 2.5.1: The Callable Interface

Signature:

@FunctionalInterface
        public interface Callable<V> {
            V call() throws Exception;
        }

Comparison with Runnable:

FeatureRunnableCallable
Returns a valueNo (void)Yes (V)
Throws checked exceptionsNoYes (throws Exception)
Functional interfaceYesYes
Executed byThread, ExecutorExecutorService only

Subsection 2.5.2: The Future Interface

public interface Future<V> {
            boolean cancel(boolean mayInterruptIfRunning);
            boolean isCancelled();
            boolean isDone();
            V get() throws InterruptedException, ExecutionException;
            V get(long timeout, TimeUnit unit) throws InterruptedException, ExecutionException, TimeoutException;
        }

Methods Explained:

MethodDescription
cancel()Attempts to cancel the task.
isCancelled()Returns true if the task was cancelled.
isDone()Returns true if the task completed (normally, exceptionally, or cancelled).
get()Blocks until the task completes and returns the result.
get(timeout)Blocks for a limited time. Throws TimeoutException.

Subsection 2.5.3: Using Callable and Future with ExecutorService

ExecutorService executor = Executors.newSingleThreadExecutor();
        
        Future<Integer> future = executor.submit(() -> {
            Thread.sleep(2000);
            return 42;
        });
        
        try {
            Integer result = future.get();
            System.out.println("Result: " + result);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } catch (ExecutionException e) {
            Throwable cause = e.getCause();
            System.out.println("Task failed: " + cause.getMessage());
        }
        
        executor.shutdown();

The "Doubt Clarifier" – What is ExecutionException?

It's a wrapper for any exception thrown by the task. You can call getCause() to get the underlying exception.

Can I cancel a running task?

Yes, but it requires cooperation from the task.

Future<Integer> future = executor.submit(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                // Do work...
                if (Thread.currentThread().isInterrupted()) {
                    return -1;  // Clean up and exit
                }
            }
            return 0;
        });
        
        future.cancel(true);  // Interrupts the thread

What does cancel(true) do?

  • Sets the interrupt flag on the thread.
  • If the thread is blocked, it wakes it up (throws InterruptedException).
  • The task must check the interrupt flag to actually stop.

cancel(false) sets the interrupt flag but does not interrupt the thread.

Subsection 2.5.4: The "Doubt Clarifier" – Future vs. CompletableFuture

Future is limited: You can't chain operations, combine multiple futures, and get() is blocking. CompletableFuture solves these limitations.

Section 2.6: Common Pitfalls with Thread Creation

Let's list the most common mistakes developers make when creating threads.

Pitfall 1: Calling run() Instead of start()

Thread t = new Thread(() -> System.out.println("Hello"));
        t.run();  // Runs on the main thread, NOT a new thread!

Fix: Always call start().

Pitfall 2: Starting a Thread Twice

Thread t = new Thread(() -> {});
        t.start();
        t.start();  // Throws IllegalThreadStateException

Fix: Create a new thread if you need to run the task again.

Pitfall 3: Forgetting to Handle InterruptedException

try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            // Ignored! BAD!
        }

Fix: Always propagate or restore the interrupt flag.

22 / 23

Pitfall 4: Using Thread.stop(), suspend(), or resume()

These are deprecated. They are unsafe and can leave objects in inconsistent states.

Fix: Use interrupt() for cooperative cancellation.

Pitfall 5: Not Using Thread Pools

Creating a new thread for every request is expensive and can exhaust system resources.

Fix: Use Executors.newFixedThreadPool() or Executors.newCachedThreadPool().
