Chapter 0.1: The Human Cognitive Barrier to Concurrency

Section 0.1.1: Why Your Brain Lies to You About Concurrency

The Sequential Fallacy

From the moment you learned to code, you were trained to think sequentially. Step 1: Do this. Step 2: Do that. Step 3: Return the result.

Your brain has a mental execution model that looks like this:

int x = 5; // Step 1 x = x + 1; // Step 2 System.out.println(x); // Step 3 (Outputs 6)

This is deterministic. Given the same input, you always get the same output. Your brain loves this. It feels safe.

The Concurrent Reality

When multiple threads are involved, your brain's sequential model becomes a liability. The JVM does not execute your code in a nice, predictable order. It interleaves instructions from different threads at the bytecode level, and the OS scheduler decides which thread runs on which CPU core at which millisecond.

Consider this seemingly innocent code:

public class Counter { private int count = 0; public void increment() { count++; // Looks like one step, but it's THREE bytecode instructions } }

If two threads call increment() simultaneously, your brain says: "Well, count starts at 0, both threads add 1, so it ends at 2."

Wrong.

The bytecode for count++ actually looks like this:

getfield count – Read the current value from memory into the stack. iconst_1 – Push the number 1 onto the stack. iadd – Add them together. putfield count – Write the new value back to memory.
The Interleaving Nightmare
Here is what actually happens when Thread A and Thread B race:
TimeThread AThread Bcount in memory
T1Read count (0)–0
T2–Read count (0)0
T3Add 0+1 = 1–0
T4–Add 0+1 = 10
T5Write count = 1–1
T6–Write count = 11

Result: count is 1, not 2. You lost an increment. This is a race condition.

Subsection 0.1.1.1: The "Doubt Clarifier" – But I ran it 100 times and it worked!

This is the most dangerous statement in concurrency.

Why does it work sometimes? Because thread interleaving is probabilistic. The OS scheduler might not interrupt the threads at exactly the wrong moment during your test runs.

Why does it fail later? Under heavy load, with many cores, or on a different JVM version, the scheduler behavior changes. The bug appears in production at 3 AM on a Saturday.

The Golden Rule of Concurrency: If it can break, it will break, given enough time and the right scheduling conditions. You must write code that is provably correct, not just "works on my machine."

Section 0.1.2: Retraining Your Brain – The Interleaving Mindset

How to Think Concurrently

When you read concurrent code, you must actively abandon sequential thinking. Instead, you must adopt the Interleaving Mindset:

  • Assume every line of code can be paused at any time. After reading a variable, before writing it, inside a loop, anywhere.
  • Assume any number of other threads can execute arbitrary code during that pause.
  • Mentally execute all possible interleavings.

For the count++ example, you need to see the four-instruction sequence and realize that the read from Thread B can happen between the read and write of Thread A.

The Mental Exercise

Take this code:

if (cache.containsKey(key)) { return cache.get(key); } else { Value v = computeValue(key); cache.put(key, v); return v; }

Sequential brain: "Check if it's in the cache. If yes, return it. If not, compute it, store it, return it."

Concurrent brain (interleaving mindset):

  • What if Thread A checks containsKey (returns false) and pauses right before computeValue.
  • Thread B comes in, checks containsKey (also false), computes the value, and puts it in the cache.
  • Thread A resumes, computes the value again, and overwrites Thread B's work. Wasted computation.
  • Worse: What if computeValue is expensive (database call, network request)? You just did it twice.
  • Even worse: What if the cache is a HashMap (not thread-safe) and both threads call put simultaneously, causing an infinite loop or corrupted internal structure?

Your new job as a concurrent programmer: Identify every point where threads can interleave and design guards (synchronization, locks, atomic operations) to prevent unsafe outcomes.

Section 0.1.3: The Two Pillars of Thread Safety

To conquer concurrency, you must internalize these two concepts. Everything else is a tool to achieve them.

Pillar 1: Atomicity (The "All or Nothing" Property)

An operation is atomic if it appears to happen instantaneously. No other thread can see it in a partially completed state.

  • count++ is not atomic (read-modify-write).
  • x = 5 is atomic (a simple write to a 32-bit primitive).
  • synchronized blocks are atomic – once a thread enters, no other thread can enter until it exits.
  • AtomicInteger.incrementAndGet() is atomic – it uses hardware-level Compare-And-Swap (CAS) instructions.

Pillar 2: Visibility (The "See My Changes" Property)

Even if one thread modifies a variable atomically, another thread might never see that change.

Why? CPU caches. Each core has its own L1/L2 cache. Thread A running on Core 1 writes x = 5 to Core 1's cache. Thread B running on Core 2 reads x from Core 2's cache. If Core 2's cache hasn't been updated yet, Thread B sees the old value (say, 0). This is a visibility problem.

  • volatile forces visibility: every write to a volatile variable is flushed directly to main memory, and every read is read directly from main memory, bypassing caches.
  • synchronized also guarantees visibility: when you exit a synchronized block, all your writes are flushed to main memory; when you enter, you invalidate your cache and reload from main memory.
The Critical Insight: You need both atomicity and visibility for thread safety. Many beginners think volatile makes everything safe. It only solves visibility. For count++, you need atomicity too.

Section 0.1.4: The "Doubt Clarifier" – What is Thread Safety, Actually?

Let's define this precisely so there is zero ambiguity.

Formal Definition (from Java Concurrency in Practice):

A class is thread-safe if it behaves correctly when accessed from multiple threads, regardless of the scheduling or interleaving of the execution of those threads, and with no additional synchronization or other coordination on the part of the calling code.

Break it down:

  • "Behaves correctly" – It maintains its invariant (e.g., a Counter class always has count >= 0).
  • "Regardless of scheduling" – No matter how the OS scheduler interleaves threads, the invariants hold.
  • "No additional coordination" – The caller doesn't need to wrap every method call in synchronized blocks. The class protects itself.

Example: java.util.concurrent.ConcurrentHashMap is thread-safe. You can call put and get from 100 threads simultaneously, and the map will never become corrupted.

Example: java.util.HashMap is not thread-safe. If you call put from multiple threads without external synchronization, the internal linked lists can become corrupted, leading to infinite loops, lost entries, or NullPointerException.

Section 0.2.2: The Cache Coherency Problem and MESI

The Problem:

  • Core 1 reads variable x from RAM (value = 0) and stores it in L1 cache.
  • Core 2 reads variable x from RAM (value = 0) and stores it in L1 cache.
  • Core 1 writes x = 5 to its L1 cache.
  • Core 2 reads x from its L1 cache. It sees 0, not 5. Data is inconsistent.

The Solution: MESI Protocol

MESI is a cache coherency protocol used by most modern CPUs. Every cache line (typically 64 bytes) has one of four states:

  • M (Modified): The cache line is dirty (modified) in this cache only. Main memory is stale.
  • E (Exclusive): The cache line is clean and present only in this cache. Main memory is up-to-date.
  • S (Shared): The cache line is clean and present in multiple caches. Main memory is up-to-date.
  • I (Invalid): This cache line is invalid. The CPU must read from main memory or another cache.

How it works for the visibility problem:

  • Core 1 reads x -> Sets state to E (Exclusive).
  • Core 2 reads x -> Core 1 sees a "read request" on the bus, changes its state to S (Shared). Core 2 also sets S.
  • Core 1 writes x = 5 -> Core 1 sends an "invalidate" message to all other cores. Core 2's cache line goes to I (Invalid). Core 1's cache line goes to M (Modified).
  • Core 2 tries to read x -> Since its cache line is I, it must fetch from main memory. Core 1, seeing a "read request" for an M line, must first flush the value (5) back to main memory and transition to S (Shared) before Core 2 can read it.
The "Doubt Clarifier" – Does Java guarantee MESI is used? No. Java does not care about the specific hardware protocol. The JVM compiles your bytecode to machine code that uses the appropriate memory barrier instructions (mfence, lfence, sfence on x86) to ensure visibility. But understanding MESI helps you understand why volatile is needed and why it has a performance cost (flushing caches and invalidating other cores is expensive).

Section 0.2.3: Out-of-Order Execution (OoOE)

Modern CPUs do not execute instructions in the order you wrote them. They reorder them to maximize pipeline utilization.

Example:

LOAD r1, [addr1] // Load from memory (takes 100 ns) ADD r2, r1, #1 // Add 1 to r1 (can't execute until LOAD finishes) STORE [addr2], r2 // Store result LOAD r3, [addr3] // This load is independent of the previous instructions

A smart CPU will reorder this:

LOAD r1, [addr1] // Start slow load LOAD r3, [addr3] // Start slow load (while waiting for addr1) ADD r2, r1, #1 // Now both loads are in progress STORE [addr2], r2 // Store result

This is great for performance. But it destroys the illusion of sequential execution.

The JVM and the Compiler:

The JVM's Just-In-Time (JIT) compiler also reorders bytecode instructions during optimization. For example, it might rewrite:

a = 1; b = 2;

as

b = 2; a = 1;

if it detects that a and b have no dependencies. This is perfectly safe in a single-threaded program.

In a multi-threaded environment, reordering can cause catastrophic failures.

Example of Reordering Breakage:

// Thread A config = loadConfig(); // Step 1 (expensive I/O) ready = true; // Step 2 // Thread B if (ready) { useConfig(config); // Step 3 }

Without memory barriers, the JVM/CPU might reorder Step 1 and Step 2, setting ready = true before config is fully loaded. Thread B sees ready == true, reads config, and gets a partially constructed object or null. Catastrophe.

This is why you need volatile or synchronized – they insert memory barriers that prevent reordering across critical boundaries.

Section 0.2.4: The "Doubt Clarifier" – Does the JVM reorder differently on different CPUs?

Yes! The x86 architecture has a relatively strict memory model (Total Store Order - TSO). It does not reorder writes, and reads are not reordered before older writes.

However, ARM and PowerPC have much weaker memory models. They can reorder almost everything.

The Java Memory Model (JMM) acts as a portability shield. It defines a minimal set of guarantees that all JVMs on all architectures must provide. If you write code that follows the JMM rules (e.g., using volatile, synchronized, java.util.concurrent classes), your code will work correctly on x86, ARM, PowerPC, and any other architecture.

If you ignore the JMM and rely on "it works on my Intel laptop," your code will crash and burn in production on an ARM-based AWS Graviton instance.

Section 0.2.5: The Cost of Context Switching

A context switch occurs when the OS scheduler preempts a running thread and switches to another thread.

What happens during a context switch?

  • The OS saves the current thread's CPU registers, program counter, and stack pointer.
  • It flushes the CPU pipeline.
  • It loads the next thread's saved state into the CPU.
  • It resumes execution.

The Cost:

  • Direct overhead: ~1-10 microseconds. That's thousands of CPU cycles.
  • Indirect cost: Cache pollution. The new thread's working set is different, so it evicts the previous thread's data from L1/L2 caches. When the first thread resumes, it has to reload its data from L3 or main memory, incurring hundreds of nanoseconds per cache miss.

Why this matters for pool sizing:

If you create 10,000 threads and the CPU only has 8 cores, the OS will constantly context-switch between them. The threads spend more time context-switching than doing actual work. Throughput plummets.

The Solution: Use thread pools (Executors.newFixedThreadPool). Limit the number of threads to roughly the number of CPU cores for CPU-bound tasks, or slightly more (e.g., 2x cores) for I/O-bound tasks (since threads often block on I/O, allowing others to run).

Section 0.2.6: The Memory Barrier (Fence) Instructions

We've mentioned memory barriers. Let's define them precisely.

A memory barrier is a CPU instruction that prevents reordering of memory operations across the barrier and ensures visibility.

  • StoreStore barrier: All writes before the barrier must complete before any write after the barrier.
  • StoreLoad barrier: All writes before the barrier must complete before any read after the barrier. This is the most expensive barrier because it forces the CPU to flush the store buffer and invalidate caches.
  • LoadLoad barrier: All reads before the barrier must complete before any read after the barrier.
  • LoadStore barrier: All reads before the barrier must complete before any write after the barrier.

How Java uses them:

  • volatile write: Inserts a StoreStore barrier before the write (preventing previous writes from being reordered after) and a StoreLoad barrier after the write (ensuring visibility to other cores).
  • volatile read: Inserts a LoadLoad barrier after the read (preventing subsequent reads from being reordered before) and a LoadStore barrier after the read (preventing subsequent writes from being reordered before).
  • synchronized block entry: Implies a LoadLoad and LoadStore barrier (flush cache).
  • synchronized block exit: Implies a StoreStore and StoreLoad barrier (flush to main memory).
The "Doubt Clarifier" – Why is synchronized more expensive than volatile?
volatile only needs barriers around the single variable access. synchronized needs barriers around the entire critical section, plus the overhead of acquiring and releasing the OS-level mutex (heavyweight lock). synchronized is much more expensive.

Section 1.1: A Brief History of Concurrency in Java

Understanding the evolution of concurrency in Java is not just academic trivia—it explains why certain APIs exist, why some are deprecated, and why modern Java looks the way it does.

Subsection 1.1.1: The Beginning (JDK 1.0 - 1996)

The Original Vision

When Java was first released in 1996, concurrency was baked into the language from day one. This was revolutionary. Most languages at the time (C, C++) treated threading as an external library concern. Java made it a first-class citizen.

What existed:

  • The Thread class – You could extend it and override run().
  • The Runnable interface – You could implement it and pass it to a Thread.
  • The synchronized keyword – Used on methods or blocks to provide mutual exclusion.
  • The Object methods – wait(), notify(), notifyAll() for inter-thread communication.
  • Thread.stop(), Thread.suspend(), Thread.resume() – These existed but were deeply flawed.

The Problems:

  • Low-level and error-prone: wait()/notify() required careful coordination. Getting it wrong meant missed notifications or spurious wakeups.
  • No high-level utilities: There were no thread pools, no concurrent collections, no atomic variables. You had to build everything from scratch.
  • Thread.stop() was dangerous: It forcibly terminated a thread, releasing all locks it held. This could leave shared objects in an inconsistent state. Deprecated in JDK 1.2.
  • Thread.suspend() and resume() were deadlock-prone: If a suspended thread held a lock, no other thread could acquire it. Deprecated in JDK 1.2.
The "Doubt Clarifier" – Why was Thread.stop() so dangerous?
Imagine this scenario:
public class BankAccount { private int balance = 100; public synchronized void transfer(BankAccount target, int amount) { this.balance -= amount; // Step 1 target.balance += amount; // Step 2 } }
If Thread A calls transfer() and is stop()ped after Step 1 but before Step 2, the source account has lost money, but the target account hasn't gained it. Money has vanished from the system. Because stop() releases all locks, no other thread can enter the transfer() method to fix the inconsistency. The object is permanently corrupted.

Lesson: Never use Thread.stop(). Use interruption for cooperative cancellation.

Subsection 1.1.2: The Java 5 Revolution (2004) – java.util.concurrent

This was the single most important event in Java concurrency history. Doug Lea's util.concurrent library was formally adopted into the JDK as java.util.concurrent (JSR-166).

What was added:

  • The Executor Framework (java.util.concurrent.Executor, ExecutorService, ThreadPoolExecutor). Finally, a standard way to manage thread pools instead of creating threads manually.
  • Concurrent Collections (ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue, etc.). Thread-safe, highly scalable data structures. No more wrapping HashMap with Collections.synchronizedMap() (which was a bottleneck).
  • Synchronizers (CountDownLatch, CyclicBarrier, Semaphore, Exchanger). High-level coordination tools that replaced error-prone wait()/notify().
  • Atomic Variables (AtomicInteger, AtomicLong, AtomicReference, etc.). Lock-free, thread-safe operations using hardware Compare-And-Swap (CAS). Far more scalable than synchronized for simple counters.
  • Lock Interface and ReentrantLock. More flexible than synchronized (try-lock, timed-lock, interruptible-lock). Multiple condition variables per lock.
  • Future and Callable. Tasks that return results and can be canceled.
  • The java.util.concurrent.atomic package (mentioned above).
  • ThreadLocalRandom – A thread-safe random number generator (much faster than Math.random() with its global lock).
Why this mattered: Before Java 5, writing correct, high-performance concurrent code was a dark art reserved for experts. Java 5 democratized concurrency by providing battle-tested building blocks.

Subsection 1.1.3: Java 7 (2011) – The Fork/Join Framework

What was added:

  • ForkJoinPool – A special thread pool designed for work-stealing.
  • RecursiveTask and RecursiveAction – For tasks that can be recursively divided (divide-and-conquer).
  • Phaser – A more flexible synchronizer that supports dynamic party registration.

Why Fork/Join was important:

It enabled parallel processing of large datasets without manual thread management. If you had an array of 10 million items, you could fork tasks until the problem size was small enough to process sequentially, then join the results.

Example: Parallel sorting (like Arrays.parallelSort()) and parallel streams (Collection.parallelStream()) use Fork/Join under the hood.

What is work-stealing? In a traditional thread pool, each thread has its own queue of tasks. If Thread A finishes its tasks while Thread B has a backlog, Thread A sits idle. In a work-stealing pool, idle threads "steal" tasks from the back of other threads' queues. This improves CPU utilization and load balancing.

Subsection 1.1.4: Java 8 (2014) – CompletableFuture and Parallel Streams

What was added:

  • CompletableFuture – A revolutionary API for asynchronous programming. Non-blocking. You can chain operations (thenApply, thenCompose, thenCombine). Exception handling (exceptionally, handle, whenComplete). Combine multiple futures (allOf, anyOf). Timeouts and cancellation.
  • Parallel Streams – collection.parallelStream(). Automatically uses the Fork/Join common pool to process streams in parallel. Simplifies parallel processing of collections but comes with caveats (don't use for blocking I/O, don't use if order matters, etc.).

The "Doubt Clarifier" – What's the difference between thenApply and thenCompose?
thenApply: Takes a function that returns a plain value. Wraps it in a CompletableFuture.
Example: future.thenApply(s -> s.length()) (returns CompletableFuture<Integer>).
thenCompose: Takes a function that returns a CompletableFuture. Flattens the nested futures (like flatMap in streams).
Example: future.thenCompose(s -> fetchDataFromDb(s)) (returns CompletableFuture<Data>, not CompletableFuture<CompletableFuture<Data>>).

Subsection 1.1.7: Java 21 LTS (2023) – The Concurrency Revolution (Project Loom)

This is the biggest change to Java concurrency since Java 5.

What was added:

  • Virtual Threads (JEP 444) – Lightweight threads managed by the JVM, not the OS. You can create millions of virtual threads without exhausting system resources. Ideal for I/O-bound applications (web servers, microservices). Thread.startVirtualThread() or Executors.newVirtualThreadPerTaskExecutor().
  • Structured Concurrency (JEP 453 – Preview in 21, Final in 22) – A new API for managing groups of related tasks. StructuredTaskScope ensures all subtasks complete before the parent task continues. Eliminates thread leaks and simplifies cancellation.
  • Scoped Values (JEP 446) – A modern replacement for ThreadLocal. Immutable and inheritable. More efficient and less error-prone than ThreadLocal.
  • Foreign Function & Memory API (JEP 442) – Finalized. Allows calling native code and managing off-heap memory safely.
  • ReentrantLock now supports Virtual Threads better (pinning detection).
Why Virtual Threads change everything:
Platform Threads: Each thread maps 1:1 to an OS thread. Creating a thread is expensive (~1 MB of stack memory, OS kernel overhead). Creating more than a few thousand threads is impractical. Thread pools are necessary to reuse threads.

Virtual Threads: Many-to-many mapping: Many virtual threads share a small number of OS threads (carrier threads). Creating a virtual thread is cheap (~a few hundred bytes of memory). When a virtual thread blocks on I/O, it is "unmounted" from the carrier, and the carrier runs another virtual thread. You can create 100,000 virtual threads without breaking a sweat.
The "Doubt Clarifier" – Is Virtual Thread faster?
For CPU-bound tasks, Virtual Threads are slightly slower than platform threads because of the overhead of mounting/unmounting. For I/O-bound tasks (network calls, database queries, file reads), Virtual Threads are dramatically faster because they allow massive concurrency without wasting threads on blocking operations.

Example: A web server handling 10,000 concurrent requests.
Platform threads: Need a thread pool of 200 threads (due to OS limits). Requests may queue.
Virtual threads: Create a new virtual thread per request (10,000 threads). Each blocks on I/O without wasting carrier threads. Throughput is orders of magnitude higher.
The "Doubt Clarifier" – Will Virtual Threads replace CompletableFuture?
No, but they complement each other.
CompletableFuture is for asynchronous, non-blocking code. It's callback-driven and requires a mental shift (thinking in stages).
Virtual Threads allow you to write synchronous, blocking code that looks like simple imperative code, but the blocking is handled efficiently by the JVM.

Which to choose?
For existing codebases, migrating to Virtual Threads is often as simple as replacing Executors.newFixedThreadPool() with Executors.newVirtualThreadPerTaskExecutor().
For complex asynchronous pipelines (e.g., aggregating results from multiple external services with timeouts and retries), CompletableFuture is still cleaner.
In Java 21+, you can mix both: use Virtual Threads for the blocking parts and CompletableFuture for the composition.

Section 1.2: Why Threads? The Benefits of Concurrency

Now that we've seen the history, let's examine why we bother with this complexity. What's the payoff?

Subsection 1.2.1: Improved Responsiveness

The Problem: The Unresponsive UI

Before concurrency, graphical applications were single-threaded. If a user clicked a button that triggered a long-running operation (like loading a file or making a network request), the UI would "freeze" until the operation completed. The user couldn't click anything else, minimize the window, or scroll.

The Solution: The Event Dispatch Thread (EDT) Pattern

In Swing and JavaFX, there is a dedicated thread for handling UI events (clicks, keypresses). Long-running tasks are dispatched to background threads. When the background thread completes, it posts the result back to the EDT to update the UI.

button.addActionListener(e -> { // This runs on the EDT setBusyCursor(true); new Thread(() -> { // This runs on a background thread Data result = fetchDataFromDatabase(); // Takes 5 seconds // Update UI back on the EDT SwingUtilities.invokeLater(() -> { displayResult(result); setBusyCursor(false); }); }).start(); });

Without concurrency, this would hang the UI for 5 seconds.

Beyond UI: Web Applications

The same principle applies to web servers. A servlet container (like Tomcat) handles each HTTP request on a separate thread. If a request takes 2 seconds to process (e.g., a database query), that thread is occupied for 2 seconds.

Without concurrency (single-threaded server), the server would handle one request at a time. 10 concurrent users would wait 20 seconds.

With concurrency (thread per request), 10 concurrent users get responses in ~2 seconds (assuming enough CPU and database capacity).

Subsection 1.2.2: Better Resource Utilization

The Problem: Wasted CPU Cycles

A single-threaded program that performs I/O operations is constantly idle.

  • CPU Speed: 3 GHz (3 billion cycles per second).
  • I/O Speed (Network): ~100 ms for a database query (300 million CPU cycles wasted).
  • I/O Speed (Disk): ~10 ms for an SSD read (30 million CPU cycles wasted).

During those 100 ms, the CPU core is doing nothing. It could have been running other code, but the single-threaded program is blocked.

The Solution: Keep the CPU Busy

With concurrency, while Thread A is blocked waiting for a database query, the OS scheduler can run Thread B (another request) or Thread C (background processing). The CPU is always doing useful work.

The Math:
Single-threaded web server: Handles 50 requests/second (each request takes 20 ms of CPU + 980 ms of I/O).
Multi-threaded web server with 100 threads: Can handle 100 concurrent requests. The CPU is kept busy context-switching between threads. Throughput increases to ~1000 requests/second (limited by CPU, not I/O).
The "Doubt Clarifier" – Is there a limit?
Yes. You cannot keep increasing threads indefinitely. Context switching overhead, cache thrashing, and memory consumption will eventually degrade performance. This is why thread pools exist (Part III, Chapter 9). You tune the number of threads based on the workload (CPU-bound vs I/O-bound).

Subsection 1.2.3: Simplified Modeling of Complex Systems

The Problem: Simulating the Real World

Many real-world systems are naturally concurrent:

  • A traffic management system has multiple cars, traffic lights, and pedestrians interacting simultaneously.
  • A banking system has multiple accounts, transactions, and ATMs.
  • A multiplayer game has multiple players, NPCs, and physics updates.

The Solution: Model Each Entity as a Thread

  • Each car is a thread.
  • Each traffic light is a thread.
  • Each bank account is a thread.

This makes the code map naturally to the problem domain. It's easier to reason about.

Example: Simulating a toll plaza

  • Each car arrives at random intervals (one thread per car).
  • Each toll booth processes cars (a thread pool).
  • Communication between threads (queue for cars waiting in line).
The "Doubt Clarifier" – Is modeling everything as a thread a good idea for production systems?
Often, no. Creating thousands of threads for thousands of "entities" is impractical (high overhead). Instead, modern systems use:
Event-driven architecture: One thread processes events from many sources.
Actor model (Akka): Lightweight actors that communicate via messages.
Virtual Threads (Java 21+): Now you actually can create thousands of threads for entities without overhead!

Subsection 1.2.4: Parallelism (Getting Things Done Faster)

The Problem: The Need for Speed

Moore's Law is slowing down. Clock speeds haven't increased significantly in years. Instead, we get more cores per chip. A modern server might have 64, 128, or even 256 cores.

The Solution: Parallelism

If you have a compute-intensive task, you can split it across multiple cores.

Example: Image Processing

You have 1 million pixels to apply a filter to.

  • Single thread: Process pixels sequentially. Takes 10 seconds.
  • 8 threads on 8 cores: Each thread processes 125,000 pixels. Takes ~1.25 seconds (plus overhead).

Example: Sorting Large Datasets

Arrays.parallelSort() uses the Fork/Join pool to sort large arrays in parallel. It's significantly faster than Arrays.sort() for arrays over a few thousand elements.

The "Doubt Clarifier" – What's the difference between Concurrency and Parallelism?
This is a crucial distinction:
Concurrency: Dealing with multiple tasks at the same time (interleaved execution). It's about structure.
Parallelism: Executing multiple tasks literally at the same time (simultaneous execution). It's about performance.

A single CPU core can be concurrent (switching between threads) but cannot be parallel. Multiple cores enable parallelism.

Amdahl's Law (We'll cover this in depth in Part V):
If 80% of your program is parallelizable, the maximum speedup with infinite cores is 1 / (1 - 0.8) = 5x. The 20% that must run sequentially will always dominate. This is why identifying the "hot path" is critical.

Section 1.3: The Risks of Threads

With great power comes great responsibility. Threads introduce a host of problems that don't exist in single-threaded code.

Subsection 1.3.1: Thread Safety (Data Corruption)

The Core Risk: When multiple threads access shared, mutable state without proper synchronization, the state becomes corrupted.

Example: The Bank Account Transfer (Revisited)

public class BankAccount { private int balance; public void transfer(BankAccount target, int amount) { this.balance -= amount; // Step 1 target.balance += amount; // Step 2 } }

Without synchronization, if two threads transfer money simultaneously, balances can become negative, or money can be duplicated. We explored this with the count++ example earlier.

The "Doubt Clarifier" – Is corruption always obvious?
No. Sometimes the corruption is subtle. For example, a linked list's internal pointers might be corrupted, causing an infinite loop when traversed. The program hangs, and you get a thread dump showing a thread stuck in an endless loop. Debugging these issues is a nightmare.
How does synchronized fix this?
synchronized ensures that only one thread can execute the critical section at a time. The operations become atomic (from the perspective of other threads).
public synchronized void transfer(BankAccount target, int amount) { this.balance -= amount; target.balance += amount; }
Now, Thread A's entire transfer happens before Thread B starts, or vice versa. No interleaving, no corruption.

But wait: synchronized locks on this. What if Thread A transfers from Account X to Account Y, and Thread B transfers from Account Y to Account X? This can deadlock (Section 1.3.2). We'll cover deadlocks in detail later.

Subsection 1.3.2: Liveness Hazards (The Program Hangs)

Liveness means "making progress." A liveness hazard is a situation where a thread stops making progress.

Type 1: Deadlock

Definition: Two or more threads are blocked forever, each waiting for a resource held by the other.

Classic Example:

// Thread A synchronized(accountX) { synchronized(accountY) { transfer(X, Y); } } // Thread B synchronized(accountY) { synchronized(accountX) { transfer(Y, X); } }
  • Thread A locks X, then tries to lock Y.
  • Thread B locks Y, then tries to lock X.
  • Neither can proceed. Deadlock.
How to detect deadlock?
Thread Dumps (jstack, kill -3): The JVM detects deadlocks and prints them explicitly:
Found one Java-level deadlock: ============================= "Thread B": waiting for lock on accountX (held by "Thread A") "Thread A": waiting for lock on accountY (held by "Thread B")
VisualVM / JConsole: Shows deadlock detection.
ThreadMXBean.findDeadlockedThreads(): Programmatic detection.
How to prevent deadlock:
Lock ordering: Always acquire locks in the same order (e.g., by account ID). Thread A and Thread B both lock the lower ID first.
Try-lock with timeout: lock.tryLock(1, TimeUnit.SECONDS) instead of synchronized.
Avoid nested locks: Minimize holding multiple locks simultaneously.

Type 2: Starvation

Definition: A thread never gets enough CPU time to make progress because higher-priority threads consume all the resources.

Example: Thread A has priority 1 (low). Thread B has priority 10 (high). Thread B runs in an infinite loop, never yielding. Thread A never gets scheduled.

The "Doubt Clarifier" – Does Java priorities actually cause starvation?
In practice, most modern OS schedulers use dynamic priority adjustments (they boost low-priority threads that have waited a long time). Starvation is rare on modern systems. However, poorly designed thread pools (e.g., one huge task hogging the pool) can cause starvation of other tasks.

Prevention: Use Thread.yield() or Thread.sleep() in long-running tasks to give other threads a chance. Use fair locks (new ReentrantLock(true)) to ensure threads get locks in order.

Type 3: Livelock

Definition: Threads are not blocked, but they keep changing state in response to each other and make no progress. It's like two people trying to pass each other in a narrow corridor—they both step left, then both step right, never getting past.

Example:

while (resourceInUse) { releaseResources(); waitRandomTime(); tryAcquireResources(); }

If two threads constantly release and reacquire resources at the same time, they never make progress.

Prevention: Add randomness to retry intervals (exponential backoff). Use priorities (one thread backs off, the other proceeds).

Type 4: Thread Starvation (Resource Starvation)

Definition: A thread holds a resource for too long, causing other threads to wait indefinitely.

Example: In a thread pool, if one task blocks indefinitely (e.g., reading from a socket that never sends data), it occupies a thread from the pool, reducing the number of threads available for other tasks. If all pool threads are blocked, the application freezes.

Prevention: Use timeouts. Use Future.get(5, TimeUnit.SECONDS). Use CompletableFuture.orTimeout(). Always handle cancellation and interruption.

Subsection 1.3.3: Performance Issues (Overhead)

Concurrency doesn't come for free. It introduces overhead that can hurt performance if not managed carefully.

Overhead 1: Thread Creation and Destruction

  • Creating a platform thread is expensive: ~1 MB of stack memory allocated, OS kernel structures set up.
  • Destroying a thread also costs.

The Solution: Thread pools (Executors.newFixedThreadPool). Reuse threads instead of creating new ones.

Overhead 2: Context Switching

We covered this in Part 0. Each context switch costs microseconds and pollutes caches.

The Solution: Don't over-subscribe threads. For CPU-bound tasks, thread count = number of CPU cores. For I/O-bound, a bit more (e.g., 2x cores).

Overhead 3: Synchronization

  • synchronized and locks require memory barriers, which flush caches and invalidate other cores' caches.
  • volatile reads/writes bypass caches, causing memory access latency.

The Solution:

  • Use lock-free algorithms (AtomicInteger, ConcurrentHashMap).
  • Reduce the scope of synchronization (only synchronize the critical section, not the whole method).
  • Use read-write locks for read-heavy workloads.

Overhead 4: Memory Consumption

  • Each thread has its own stack (typically 1 MB). 1,000 threads = 1 GB of stack memory.
  • On 32-bit systems, the address space is limited (4 GB), so you can only create ~4,000 threads.
The Solution (Pre-Java 21): Use thread pools. Limit thread count.
The Solution (Java 21+): Virtual Threads. Their stack is dynamically sized (small) and they don't consume OS thread resources.

Section 1.4: Threads Are Everywhere

Concurrency is not something you can "opt out of." Even if you don't explicitly create threads, you're living in a multi-threaded world.

Subsection 1.4.1: The JVM Itself Is Multi-Threaded

  • Garbage Collector (GC): Runs on background threads. It pauses your application threads (stop-the-world events). Understanding GC is critical for concurrent performance.
  • Finalizer Thread: Runs finalize() methods (deprecated, but still exists).
  • Reference Handler Thread: Handles WeakReference, SoftReference, PhantomReference.
  • Signal Dispatcher: Handles OS signals.
  • Compiler Threads: JIT compilation happens on background threads.
The "Doubt Clarifier" – Do these threads affect my code?
Yes. For example, the GC can pause your threads at any time (unless you use a low-latency GC like ZGC). If you're measuring performance, you must account for GC pauses.

Subsection 1.4.2: Application Servers / Frameworks

  • Spring Boot / Tomcat: Each HTTP request is handled on a separate thread (or Virtual Thread in Java 21). You don't create these threads; the container does.
  • Quartz Scheduler: Runs jobs on background threads.
  • Message Queues (RabbitMQ, Kafka): Consumers run on threads.
  • Database Connection Pools: Connections are managed across threads.
The "Doubt Clarifier" – Why does this matter?
Because you might write code that assumes single-threaded execution, but it's actually invoked concurrently by the container. For example:
@RestController public class MyController { private int counter = 0; // DANGER! Shared mutable state @GetMapping("/count") public int count() { return counter++; // Race condition! } }
Spring Boot handles each request on a thread. Multiple concurrent requests will corrupt counter.

The Fix: Don't store mutable state in Spring components. Use request-scoped beans, or use AtomicInteger.

Subsection 1.4.3: Modern UI Frameworks (Swing, JavaFX, Android)

We covered this briefly. Every UI framework has an Event Dispatch Thread (EDT). You must never block the EDT. You must use background threads for long-running tasks.

The "Doubt Clarifier" – So, what's the bottom line?
If you write code that runs in a JVM (application, web server, Android app), you are writing concurrent code. You cannot avoid it. You must understand concurrency principles to write correct, performant applications. Ignorance is not bliss; it's a bug waiting to happen.

Before we create threads, we must understand what they are at both the JVM level and the OS level.

The "Doubt Clarifier" – What is ThreadLocalMap?
Each thread has its own ThreadLocalMap that stores values for ThreadLocal variables. When you call ThreadLocal.get(), it retrieves the value from the current thread's map. This is how ThreadLocal provides thread-isolated storage.

When a thread is blocked by LockSupport.park(), the parkBlocker field stores the object that caused the blocking. This is used by diagnostic tools to identify why a thread is blocked.

Subsection 2.1.2: The Native Thread – The OS-Level Reality

Every Java thread (platform thread) maps 1:1 to an OS thread. This is called the Native Thread Model.

What happens when you call new Thread().start()?

  1. JVM allocates memory: The JVM allocates a Thread object on the Java heap.
  2. JVM calls native method: Thread.start() calls the native method start0().
  3. OS thread creation: The JVM asks the OS to create a new native thread (via pthread_create on Linux, CreateThread on Windows).
  4. OS allocates resources: The OS allocates:
    • A thread control block (TCB) in kernel space.
    • A stack (typically 1 MB, configurable via -Xss).
    • A program counter (PC) and register set.
  5. JVM attaches: The JVM attaches the new native thread to the Java Thread object.
  6. Thread begins execution: The OS scheduler schedules the thread, and it begins executing the run() method.
The "Doubt Clarifier" – What is the stack size?
The stack stores method frames (local variables, parameters, return addresses). Each frame has a fixed size determined by the compiler. The stack size is configurable:
java -Xss1m MyClass # 1 MB stack (default) java -Xss512k MyClass # 512 KB stack (for many threads) java -Xss2m MyClass # 2 MB stack (for deep recursion)
The "Doubt Clarifier" – What happens if you exceed the stack size?
You get a StackOverflowError. This often happens with deep recursion or infinite recursion.
public static void recursive() { recursive(); // Infinite recursion }
Each call adds a new frame to the stack. When the stack overflows, the JVM throws StackOverflowError.

Subsection 2.1.3: The Thread Class – Constructors

The Thread class has several constructors. Here's the complete list:

// 1. Default: Creates a new thread with a generated name Thread() // 2. With a Runnable target Thread(Runnable target) // 3. With a name Thread(String name) // 4. With a target and name Thread(Runnable target, String name) // 5. With a ThreadGroup Thread(ThreadGroup group, Runnable target) // 6. With a ThreadGroup and name Thread(ThreadGroup group, String name) // 7. With a ThreadGroup, target, and name Thread(ThreadGroup group, Runnable target, String name) // 8. The "Doubt Clarifier" – What is ThreadGroup?
ThreadGroup is a way to group threads for bulk operations. You can interrupt all threads in a group or set their priority.
ThreadGroup group = new ThreadGroup("Workers"); Thread t1 = new Thread(group, () -> { /* work */ }, "Worker-1"); Thread t2 = new Thread(group, () -> { /* work */ }, "Worker-2"); group.interrupt(); // Interrupts both t1 and t2
But note: ThreadGroup is largely obsolete. Modern practice uses ExecutorService for thread management. ThreadGroup is still used by the JVM for internal purposes.

Subsection 2.1.4: The "Doubt Clarifier" – Why does Thread implement Runnable?

Look at the Thread class signature:

public class Thread implements Runnable { // ... @Override public void run() { if (target != null) { target.run(); } } }

Thread implements Runnable. This means you can pass a Thread instance to another Thread (though this is almost never done).

Why? Historical reasons. The designers wanted Thread to be a valid Runnable so that you could override run() directly when extending Thread.

But the better practice is to implement Runnable separately, as we'll see in Section 2.2.

Section 2.2: Creating a Thread – The Two Primary Ways

There are two fundamental ways to create a thread in Java. Let's explore both in extreme detail.

Subsection 2.2.1: Method 1 – Extending the Thread Class

Syntax:

public class MyThread extends Thread { @Override public void run() { System.out.println("Thread is running: " + Thread.currentThread().getName()); } } // Usage MyThread t = new MyThread(); t.start();

What happens internally:

  • You create a subclass of Thread.
  • You override run() (which is public void).
  • When you call start(), the JVM creates a native thread and invokes your run() method.

Pros:

  • Simple and straightforward.
  • You can access Thread methods directly (getName(), setPriority(), etc.).

Cons:

  • Single inheritance limitation: You cannot extend any other class.
  • Tight coupling: The task is baked into the thread class. You can't reuse the task with other execution mechanisms (e.g., thread pools).
  • Not flexible: You can't pass parameters to run() easily.
The "Doubt Clarifier" – Can I call run() directly instead of start()?
Yes, but do not do it.
MyThread t = new MyThread(); t.run(); // This runs in the current thread, NOT a new thread!
run() is just a regular method. Calling it directly doesn't create a new thread. The start() method is what creates the new thread and schedules it.

If you call run() directly, it executes in the calling thread, not in a separate thread.

Subsection 2.2.2: Method 2 – Implementing the Runnable Interface

Syntax:

public class MyRunnable implements Runnable { @Override public void run() { System.out.println("Runnable running: " + Thread.currentThread().getName()); } } // Usage MyRunnable task = new MyRunnable(); Thread t = new Thread(task); t.start();

What happens internally:

  • You create a class that implements Runnable.
  • You implement run().
  • You create a Thread instance and pass the Runnable to it.
  • When you call start(), the JVM creates a native thread and invokes target.run() (where target is your Runnable).

Pros:

  • Flexible: You can extend another class (since you're only implementing an interface).
  • Reusable: The same Runnable can be submitted to a thread pool (ExecutorService).
  • Separation of concerns: The task (what to do) is separate from the execution mechanism (how to run it).

Cons:

  • Slightly more verbose (you need to create a Thread explicitly).
The "Doubt Clarifier" – What is the Runnable functional interface?
@FunctionalInterface public interface Runnable { void run(); }
It's a functional interface, meaning you can use lambda expressions.

Subsection 2.2.3: Method 3 – Using Lambda Expressions (Java 8+)

Because Runnable is a functional interface, you can use lambdas:

// Lambda expression Thread t = new Thread(() -> { System.out.println("Lambda running: " + Thread.currentThread().getName()); }); t.start(); // Even shorter (method reference) Runnable task = System.out::println; Thread t2 = new Thread(task); t2.start();

Pros:

  • Very concise.
  • Captures local variables (effectively final).
The "Doubt Clarifier" – What does "effectively final" mean?
A variable is effectively final if it is not reassigned after initialization. Lambdas can only capture effectively final variables.
int x = 10; Runnable r = () -> System.out.println(x); // OK (x is effectively final) int y = 20; y = 30; // y is reassigned, NOT effectively final Runnable r2 = () -> System.out.println(y); // COMPILE ERROR!
Why this restriction? The lambda is executed on a different thread. To ensure consistency, the captured variables are copied (or reference is captured). If the variable could change, the copy would be stale.

Subsection 2.2.4: Method 4 – Using ExecutorService (The Real-World Standard)

In production code, you rarely create Thread objects directly. You use thread pools.

ExecutorService executor = Executors.newFixedThreadPool(10); // Submit a Runnable executor.execute(() -> { System.out.println("Task running on thread pool"); }); // Submit a Callable (returns a result) Future<Integer> future = executor.submit(() -> { Thread.sleep(1000); return 42; }); executor.shutdown();

We'll cover ExecutorService in depth in Part IV. For now, just know that it's the preferred way to run tasks.

Subsection 2.2.5: The "Doubt Clarifier" – Which method should I use?

ScenarioRecommended Approach
Learning/experimentingExtend Thread or implement Runnable
Simple one-off tasksLambda with Runnable
Production code (task execution)ExecutorService (thread pools)
Production code (async results)CompletableFuture

Never extend Thread in production code. It's an anti-pattern.

Section 2.3: The Thread Lifecycle (States)

A thread in Java can be in one of six states (as defined by the Thread.State enum). Understanding these states is critical for debugging, performance tuning, and preventing liveness issues.

Subsection 2.3.1: The Six States – Complete Breakdown

StateDescriptionWhen Does It Enter This State?When Does It Leave?
NEWThread object created but not startednew Thread()thread.start() is called
RUNNABLEThread is ready to run, or is currently running on a CPU corethread.start() is calledThread scheduler assigns CPU time
BLOCKEDThread is blocked, waiting to acquire a monitor locksynchronized block/method, but lock is held by another threadLock is released by the holding thread
WAITINGThread is waiting indefinitely for another thread to perform an actionObject.wait() (no timeout), Thread.join() (no timeout), LockSupport.park()notify()/notifyAll() called, thread terminates, or unpark() called
TIMED_WAITINGThread is waiting for a specified amount of timeThread.sleep(), Object.wait(timeout), Thread.join(timeout), LockSupport.parkNanos(), LockSupport.parkUntil()Timeout expires, notification, or unpark

Subsection 2.3.2: Visualizing State Transitions

NEW | v RUNNABLE <----> BLOCKED | (acquires lock) | (wait) v WAITING <----> TIMED_WAITING | (timeout) | (notify) v TERMINATED
The "Doubt Clarifier" – Is RUNNABLE the same as "running"?
No! RUNNABLE means the thread is ready to run. It may be waiting for the OS scheduler to assign CPU time. In a busy system with more threads than cores, many RUNNABLE threads are actually waiting for CPU.
The "Doubt Clarifier" – What's the difference between WAITING and BLOCKED?
BLOCKED: Waiting for a monitor lock (synchronized). The thread is competing with other threads for the lock.
WAITING: Waiting for notification or termination. The thread is not competing for a lock; it's passively waiting for an external signal.

Subsection 2.3.3: Code Examples – Observing Thread States

Example 1: NEW and RUNNABLE

public class StateDemo { public static void main(String[] args) throws InterruptedException { Thread t = new Thread(() -> { for (int i = 0; i < 100_000_000; i++) { // Busy loop to keep thread RUNNABLE } }); System.out.println("After creation: " + t.getState()); // NEW t.start(); System.out.println("After start: " + t.getState()); // RUNNABLE (likely) t.join(); // Wait for it to finish System.out.println("After join: " + t.getState()); // TERMINATED } }

Output:

After creation: NEW After start: RUNNABLE After join: TERMINATED

Example 2: WAITING

public class WaitDemo { public static void main(String[] args) throws InterruptedException { Object lock = new Object(); Thread t = new Thread(() -> { synchronized (lock) { try { System.out.println("Thread waiting..."); lock.wait(); // Releases lock and waits System.out.println("Thread notified!"); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } } }); t.start(); Thread.sleep(100); // Give t time to enter WAITING state System.out.println("Thread state: " + t.getState()); // WAITING synchronized (lock) { lock.notify(); // Wake up t } t.join(); System.out.println("Thread state: " + t.getState()); // TERMINATED } }

Output:

Thread waiting... Thread state: WAITING Thread notified! Thread state: TERMINATED
The "Doubt Clarifier" – Why does wait() release the lock?
Because if it didn't, no other thread could enter the synchronized block to call notify(). The thread must give up the lock so that other threads can signal it.

Example 3: TIMED_WAITING

Thread t = new Thread(() -> { try { Thread.sleep(5000); // Sleep for 5 seconds } catch (InterruptedException e) { Thread.currentThread().interrupt(); } }); t.start(); Thread.sleep(100); // Give t time to enter sleep System.out.println(t.getState()); // TIMED_WAITING

Example 4: BLOCKED

public class BlockedDemo { private static final Object lock = new Object(); public static void main(String[] args) throws InterruptedException { Thread t1 = new Thread(() -> { synchronized (lock) { try { Thread.sleep(10000); // Hold lock for 10 seconds } catch (InterruptedException e) { Thread.currentThread().interrupt(); } } }); Thread t2 = new Thread(() -> { synchronized (lock) { System.out.println("Acquired lock!"); } }); t1.start(); Thread.sleep(100); // Give t1 time to acquire lock t2.start(); Thread.sleep(100); // Give t2 time to try to acquire lock System.out.println("t2 state: " + t2.getState()); // BLOCKED t1.join(); t2.join(); } }

Output:

t2 state: BLOCKED
The "Doubt Clarifier" – Why is t2 in BLOCKED and not WAITING?
Because t2 is trying to acquire the intrinsic lock (synchronized). It's not waiting for a notification; it's waiting for the lock to be released. That's the definition of BLOCKED.

Section 2.4: Important Thread Methods

Let's explore the most commonly used methods of the Thread class, their semantics, and their pitfalls.

start() – The Only Way to Begin

Signature: public void start()

What it does:

  • Checks that the thread is in NEW state. If not, throws IllegalThreadStateException.
  • Allocates a native thread (OS thread).
  • Schedules the native thread to run.
  • The OS scheduler eventually invokes the thread's run() method.
The "Doubt Clarifier" – Why is start() synchronized?
Internally, start() is synchronized to prevent two threads from calling start() on the same Thread object simultaneously.
The "Doubt Clarifier" – Can I call start() twice on the same thread?
No. It will throw IllegalThreadStateException.
Thread t = new Thread(() -> {}); t.start(); t.start(); // Throws IllegalThreadStateException

run() – The Task Entry Point

Signature: public void run()

What it does: Contains the code executed by the thread.

The "Doubt Clarifier" – If I override run(), should I call super.run()?
Only if you want the default behavior (which runs the target Runnable). If you're extending Thread and overriding run(), you usually don't call super.run().
The "Doubt Clarifier" – What's the difference between start() and run()?
start() creates a new thread and calls run() on that thread.
run() is just a regular method call on the current thread.

join() – Waiting for Thread Termination

Signature:

  • public void join() throws InterruptedException – Wait indefinitely.
  • public void join(long millis) throws InterruptedException – Wait with timeout.
  • public void join(long millis, int nanos) throws InterruptedException – Fine-grained timeout.

What it does: The calling thread waits for the specified thread to terminate.

Example:

Thread t = new Thread(() -> { // Do some work try { Thread.sleep(2000); } catch (InterruptedException ignored) {} }); t.start(); t.join(); // Main thread waits here until t finishes System.out.println("t has finished");
The "Doubt Clarifier" – What happens if the thread is already terminated?
join() returns immediately.
The "Doubt Clarifier" – What if I call join(0)?
It means "wait forever" (same as join() with no timeout).
The "Doubt Clarifier" – Does join() release locks?
No. The calling thread holds its locks while waiting. This can cause deadlock if the other thread is waiting for one of those locks.

sleep() – Pausing the Current Thread

Signature:

  • public static void sleep(long millis) throws InterruptedException
  • public static void sleep(long millis, int nanos) throws InterruptedException

What it does: The current thread pauses for the specified time. It does not release any locks.

The "Doubt Clarifier" – Why is sleep() static?
Because it always operates on the current thread. You cannot make another thread sleep.
Thread.sleep(1000); // Current thread sleeps for 1 second
The "Doubt Clarifier" – What is the minimum sleep time?
The JVM's thread scheduler has a certain granularity (typically 1-10 ms on most systems). sleep(1) might actually sleep 1-10 ms depending on the OS.
The "Doubt Clarifier" – Is sleep() interrupted?
Yes. If another thread interrupts the sleeping thread, sleep() throws InterruptedException.
try { Thread.sleep(10000); } catch (InterruptedException e) { System.out.println("Woken up early!"); Thread.currentThread().interrupt(); // Re-interrupt }

yield() – Yielding the CPU

Signature: public static void yield()

What it does: A hint to the JVM scheduler that the current thread is willing to give up its CPU time.

The "Doubt Clarifier" – Does yield() guarantee anything?
No. It's just a hint. The scheduler may ignore it.
The "Doubt Clarifier" – When should I use yield()?
Almost never. It's a legacy method. In modern applications, you should not rely on yield() for any correctness or performance guarantees.

interrupt() – Interrupting a Thread

Signature: public void interrupt()

What it does: Sets the thread's interrupt flag and, if the thread is blocked in certain methods, wakes it up.

The "Doubt Clarifier" – What methods throw InterruptedException?
  • Thread.sleep()
  • Object.wait()
  • Thread.join()
  • BlockingQueue.take()
  • Lock.lockInterruptibly()
  • Future.get()
The "Doubt Clarifier" – What does interrupt() do to a thread that's not blocked?
It just sets the interrupt flag. The thread can check it later with Thread.interrupted() or Thread.currentThread().isInterrupted().
The "Doubt Clarifier" – How do I handle InterruptedException properly?
Always propagate it or restore the interrupt flag.

Good:
public void myMethod() throws InterruptedException { Thread.sleep(1000); // Propagate }
Good:
public void myMethod() { try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); // Restore flag } }
Bad (swallow):
public void myMethod() { try { Thread.sleep(1000); } catch (InterruptedException e) { // Swallow silently! BAD! } }
The "Doubt Clarifier" – What's the difference between interrupted() and isInterrupted()?
interrupted(): Static method. Returns the interrupt flag and clears it.
isInterrupted(): Instance method. Returns the interrupt flag and does not clear it.
Thread t = Thread.currentThread(); t.interrupt(); boolean flag1 = t.isInterrupted(); // true boolean flag2 = Thread.interrupted(); // true (clears flag) boolean flag3 = t.isInterrupted(); // false (flag was cleared)

setDaemon() and isDaemon() – Daemon Threads

Signature:

  • public void setDaemon(boolean on)
  • public boolean isDaemon()

What it does: Marks a thread as a daemon thread.

The "Doubt Clarifier" – What happens when all non-daemon threads finish?
The JVM exits, even if daemon threads are still running.
Thread daemon = new Thread(() -> { while (true) { // Infinite loop } }); daemon.setDaemon(true); daemon.start(); // Main thread ends, JVM exits. Daemon thread is killed.
Use cases for daemon threads:
  • Garbage collection (GC threads).
  • Background health checks.
  • Monitoring and logging.
The "Doubt Clarifier" – Can you call setDaemon() after start()?
No. It throws IllegalThreadStateException.
Thread t = new Thread(); t.start(); t.setDaemon(true); // Throws IllegalThreadStateException

Section 2.5: Callable and Future – Tasks That Return Results

Runnable is great, but it has a limitation: it cannot return a result or throw checked exceptions. This is where Callable comes in.

Subsection 2.5.1: The Callable Interface

Signature:

@FunctionalInterface public interface Callable<V> { V call() throws Exception; }

Comparison with Runnable:

FeatureRunnableCallable
Returns a valueNo (void)Yes (V)
Throws checked exceptionsNoYes (throws Exception)
Functional interfaceYesYes
Executed byThread, ExecutorExecutorService only
The "Doubt Clarifier" – Why can't I submit a Callable to a Thread?
Because Thread only accepts Runnable. You need to use ExecutorService.submit().

Subsection 2.5.2: The Future Interface

Signature:

public interface Future<V> { boolean cancel(boolean mayInterruptIfRunning); boolean isCancelled(); boolean isDone(); V get() throws InterruptedException, ExecutionException; V get(long timeout, TimeUnit unit) throws InterruptedException, ExecutionException, TimeoutException; }

Methods Explained:

MethodDescription
cancel()Attempts to cancel the task.
isCancelled()Returns true if the task was cancelled.
isDone()Returns true if the task completed (normally, exceptionally, or cancelled).
get()Blocks until the task completes and returns the result.
get(timeout)Blocks for a limited time. Throws TimeoutException if the task doesn't complete.

Subsection 2.5.3: Using Callable and Future with ExecutorService

ExecutorService executor = Executors.newSingleThreadExecutor(); // Submit a Callable Future<Integer> future = executor.submit(() -> { Thread.sleep(2000); return 42; }); // Do other work while the task runs... try { // Block and wait for the result Integer result = future.get(); System.out.println("Result: " + result); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } catch (ExecutionException e) { // The task threw an exception Throwable cause = e.getCause(); System.out.println("Task failed: " + cause.getMessage()); } executor.shutdown();
The "Doubt Clarifier" – What is ExecutionException?
It's a wrapper for any exception thrown by the task. You can call getCause() to get the underlying exception.
The "Doubt Clarifier" – Can I cancel a running task?
Yes, but it requires cooperation from the task.
Future<Integer> future = executor.submit(() -> { while (!Thread.currentThread().isInterrupted()) { // Do work... if (Thread.currentThread().isInterrupted()) { return -1; // Clean up and exit } } return 0; }); future.cancel(true); // Interrupts the thread
The "Doubt Clarifier" – What does cancel(true) do?
  • Sets the interrupt flag on the thread.
  • If the thread is blocked, it wakes it up (throws InterruptedException).
  • The task must check the interrupt flag to actually stop.
What does cancel(false) do?
  • Sets the interrupt flag but does not interrupt the thread.
  • The task must check isInterrupted() on its own.

Subsection 2.5.4: The "Doubt Clarifier" – Future vs. CompletableFuture

Future is limited:

  • You can't chain operations.
  • You can't combine multiple futures.
  • get() is blocking.

CompletableFuture solves these limitations. We'll cover it in depth in Part IV.

Section 2.6: Common Pitfalls with Thread Creation

Let's list the most common mistakes developers make when creating threads.

Pitfall 1: Calling run() Instead of start()

Thread t = new Thread(() -> System.out.println("Hello")); t.run(); // Runs on the main thread, NOT a new thread!

Fix: Always call start().

Pitfall 2: Starting a Thread Twice

Thread t = new Thread(() -> {}); t.start(); t.start(); // Throws IllegalThreadStateException

Fix: Create a new thread if you need to run the task again.

Pitfall 3: Forgetting to Handle InterruptedException

try { Thread.sleep(1000); } catch (InterruptedException e) { // Ignored! BAD! }

Fix: Always propagate or restore the interrupt flag.

Pitfall 4: Using Thread.stop(), suspend(), or resume()

These are deprecated. They are unsafe and can leave objects in inconsistent states.

Fix: Use interrupt() for cooperative cancellation.

Pitfall 5: Not Using Thread Pools

Creating a new thread for every request is expensive and can exhaust system resources.

Fix: Use Executors.newFixedThreadPool() or Executors.newCachedThreadPool().
