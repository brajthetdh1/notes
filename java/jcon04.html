📦 Chapter 4: Sharing Objects

Section 4.1: Visibility – The "Seeing Is Believing" Problem

Visibility is about ensuring that changes made by one thread are visible to other threads.

Subsection 4.1.1: The Visibility Problem – Why It Happens

The Hardware Reality (Recap): Each CPU core has its own cache (L1, L2). When a thread writes to a variable, it writes to its core's cache. Unless that cache line is flushed to main memory (or invalidated in other cores), other threads may not see the change.

The JVM Reality: The JVM and JIT compiler also reorder instructions for performance. Without proper synchronization, a thread may see operations in an order that violates program order.

The "Doubt Clarifier" – Can a thread never see a change, or just see it later?

It can never see it if the variable is not properly synchronized. The JVM is allowed to cache the value indefinitely (e.g., in a CPU register) and never reload it from memory.

1 / 50

Example: The Infinite Loop Bug

public class VisibilityBug {
            private static boolean running = true;
            
            public static void main(String[] args) throws InterruptedException {
                Thread t = new Thread(() -> {
                    while (running) { /* Do nothing */ }
                    System.out.println("Thread finished");
                });
                t.start();
                Thread.sleep(1000);
                running = false;  // Main thread sets to false
                System.out.println("Set running to false");
                t.join();  // May never finish!
            }
        }

What happens: The JIT compiler optimizes while (running) by hoisting the read of running out of the loop. The loop runs forever.

The Fix: Make running volatile.

Subsection 4.1.2: The "Doubt Clarifier" – Why doesn't System.out.println() fix visibility?

System.out.println() is synchronized. Synchronization forces the thread to reload variables from main memory, which makes the change visible. But this is a terrible hack! You cannot rely on it for correctness. Always use proper synchronization.

Subsection 4.1.3: The "Doubt Clarifier" – What does it mean for a variable to be "stale"?

A stale value is an old value that is still visible in a thread's cache. The JVM guarantees that a read will see some value that was written to the variable (not a completely arbitrary value). But it may be an old value.

Subsection 4.1.4: Visibility Guarantees – What the JMM Promises

Synchronization MechanismVisibility Guarantee
No synchronizationNo guarantee. Threads may see stale values indefinitely.
volatileWrites to volatile are immediately visible to all threads.
synchronizedWrites before synchronized exit are visible to threads entering synchronized on the same lock.

Subsection 4.1.5: The "Doubt Clarifier" – Is volatile enough for a boolean flag used in a loop?

Yes. volatile guarantees that the reading thread will see the latest value. The loop will terminate when the flag is set to false.

private volatile boolean running = true;
        public void run() { while (running) { /* work */ } }
        public void stop() { running = false; }

Subsection 4.1.6: The "Doubt Clarifier" – What is the "happens-before" rule for volatile?

Formal Rule: A write to a volatile field happens-before every subsequent read of that same volatile field.

Example:

private volatile boolean ready;
        private int data;
        
        // Thread A
        data = 42;       // Normal write
        ready = true;    // Volatile write
        
        // Thread B
        if (ready) {     // Volatile read
            int x = data;  // Guaranteed to see 42!
        }

Because data = 42 happens-before ready = true (program order), and ready = true happens-before if (ready) (volatile rule), data = 42 happens-before if (ready) (transitivity).

Section 4.2: Publication and Escape

Publication is making an object available to other threads. Escape is when an object is published before it's fully constructed.

Subsection 4.2.1: What is "Publication"?

Methods of Publication:

  • Storing the reference in a public static field.
  • Returning the reference from a method.
  • Passing the reference as an argument to another method that stores it.
  • Adding the object to a collection that is accessible to other threads.

Subsection 4.2.2: What is "Escape"?

Escape occurs when an object reference is published before the object is fully constructed.

Common Escape Scenarios:

  • Publishing this in the constructor: new Thread(() -> System.out.println(value)).start();
  • Passing this to another method: DangerousClass.register(this);
  • Inner class holding a reference: Inner class has reference to outer this.
5 / 50

Subsection 4.2.3: The "Doubt Clarifier" – Why is escape dangerous?

Because it violates the JMM's initialization safety. Other threads may see:

  • Default values (0, null, false) for non-final fields.
  • Inconsistent values (some fields assigned, others not).
  • The object in an invalid state (invariant broken).

Subsection 4.2.4: Preventing Escape – The "Dangerous Publication" Patterns

Dangerous Pattern 1: Publishing from a static initializer – This is actually safe because static initializers are thread-safe.

Dangerous Pattern 2: Publishing from a non-synchronized method:

private Object shared;
        public void publish(Object obj) { this.shared = obj; }  // Unsafe!

Fix: Use volatile: private volatile Object shared;

Dangerous Pattern 3: Publishing via a HashMap without synchronization:

private Map<String, Object> map = new HashMap<>();
        public void publish(String key, Object obj) { map.put(key, obj); }  // Unsafe!

Fix: Use ConcurrentHashMap.

Section 4.3: Thread Confinement – The "Don't Share" Strategy

Thread confinement is the simplest way to achieve thread safety: don't share mutable objects across threads.

Subsection 4.3.1: Stack Confinement

Local variables are inherently thread-safe because each thread has its own stack.

public int add(int a, int b) {
            int result = a + b;  // Stack-confined. Safe.
            return result;
        }

Are local variables always safe? Yes, as long as the reference does not escape. If you store a local object in a static field, it escapes and is no longer confined.

Subsection 4.3.2: ThreadLocal Confinement

ThreadLocal provides a way to store values that are local to each thread.

public class ConnectionManager {
            private static ThreadLocal<Connection> connectionHolder = 
                ThreadLocal.withInitial(() -> DriverManager.getConnection("jdbc:mysql://..."));
            
            public static Connection getConnection() {
                return connectionHolder.get();
            }
        }
7 / 50

Subsection 4.3.3: Ad-Hoc Thread Confinement

Ad-hoc confinement is when a thread owns an object but doesn't explicitly enforce it (e.g., by convention).

public void run() {
            List<String> list = new ArrayList<>();  // Thread-confined by convention
            processList(list);  // Safe if processList() is only called from this thread
        }

Is ad-hoc confinement reliable? No. It relies on developer discipline. Use ThreadLocal or explicit synchronization instead.

Subsection 4.3.4: The "Doubt Clarifier" – When should I use thread confinement vs. synchronization?

FactorThread ConfinementSynchronization
ComplexitySimple (no locks)Complex (race conditions, deadlocks)
PerformanceExcellent (no overhead)Can be expensive (blocking)
ScalabilityExcellent (no contention)Can be poor (contention)
Use casePer-thread state (e.g., user session)Shared state across threads

Rule of thumb: If you can confine an object to a single thread, do it. It's simpler and faster.

Section 4.4: Immutability – The Ultimate Thread Safety

Subsection 4.4.1: Building an Immutable Class – Step by Step

Step 1: Make the class final (prevent subclassing).

Step 2: Make all fields final (set in constructor).

Step 3: Make all fields private (encapsulation).

Step 4: No setter methods.

Step 5: Defensive copy for mutable fields (input and output).

Step 6: Ensure the constructor does not leak this.

Example:

public final class ImmutablePerson {
            private final String name;
            private final Date birthDate;  // Mutable!
            
            public ImmutablePerson(String name, Date birthDate) {
                this.name = name;
                this.birthDate = new Date(birthDate.getTime());  // Defensive copy
            }
            
            public Date getBirthDate() {
                return new Date(birthDate.getTime());  // Defensive copy
            }
        }
9 / 50

Subsection 4.4.2: The "Doubt Clarifier" – Are final fields always safe?

Yes, but only if the object is safely published. If you publish an immutable object unsafely, the reference may be stale, even if the fields are final.

Subsection 4.4.3: The "Doubt Clarifier" – What is the difference between immutability and final fields?

Immutability: The object's state cannot change after construction.
final fields: A field that cannot be reassigned after construction. It's a building block of immutability.

An object can have final fields but still be mutable if those fields refer to mutable objects.

Subsection 4.4.4: The "Doubt Clarifier" – Are all immutable objects thread-safe?

Yes, trivially. No synchronization is needed because no thread can modify the object. All threads see the same state (assuming safe publication).

Examples of Immutable Classes in the JDK:

  • String
  • Integer, Long, Double
  • LocalDate, LocalDateTime
  • BigDecimal, BigInteger
  • Collections.unmodifiableList()

Subsection 4.5.2: The "Doubt Clarifier" – Why does static initialization work?

The JVM guarantees that static initializers are executed in a thread-safe manner. When the class is loaded, the static initializer runs once, and the result is visible to all threads.

11 / 50

Subsection 4.5.3: The "Doubt Clarifier" – Why does volatile work for safe publication?

When a thread writes to a volatile field, all writes that happened before that volatile write are also flushed to main memory. When another thread reads the volatile field, it sees all those writes.

private volatile MyObject obj;
        public void publish(MyObject o) { obj = o; }  // Volatile write
        public MyObject get() { return obj; }         // Volatile read

Subsection 4.5.4: The "Doubt Clarifier" – What is the "final" safe publication guarantee?

The JMM guarantees that final fields are visible to all threads after the constructor completes, without synchronization. This is called initialization safety.

Does this apply to non-final fields? No! Non-final fields are not guaranteed to be visible without synchronization.

Subsection 4.5.5: The "Doubt Clarifier" – What is the "null" publication problem?

If a reference is not safely published, threads may see null even after the object has been set.

Subsection 4.5.6: The "Doubt Clarifier" – What is the "partially constructed object" problem?

When an object is published unsafely, a thread may see a reference to the object but with some fields not yet initialized.

Example (Double-Checked Locking broken):

private static MyObject instance;
        public static MyObject getInstance() {
            if (instance == null) {
                synchronized (MyObject.class) {
                    if (instance == null) {
                        instance = new MyObject();  // May be reordered!
                    }
                }
            }
            return instance;
        }

Fix: Make instance volatile.
