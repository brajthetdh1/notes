Q151: API Gateway

Microservices
What is an API gateway and what are its responsibilities?

An API Gateway is a single entry point for all client requests to a microservices architecture. It acts as a reverse proxy that routes requests to the appropriate services.

Responsibilities:

  • Request Routing: Routes client requests to the appropriate microservice.
  • Authentication & Authorization: Validates tokens, API keys, and permissions.
  • Rate Limiting: Prevents abuse by limiting request frequency.
  • Load Balancing: Distributes requests across service instances.
  • Request/Response Transformation: Modifies requests/responses as needed.
  • Caching: Caches responses to improve performance.
  • Logging & Monitoring: Centralized logging of all API calls.
  • Circuit Breaking: Prevents cascading failures.

Examples: Netflix Zuul, Spring Cloud Gateway, Kong, AWS API Gateway.

Q152: Service Discovery

Microservices
What is service discovery in microservices?

Service discovery is a mechanism that allows services to find and communicate with each other in a dynamic microservices environment.

How it works:

  • Services register themselves with a service registry at startup.
  • Services query the registry to find the network location of other services.
  • When a service instance changes (scale up/down), the registry is updated.

Key components:

  • Service Registry: A database of service instances and their locations.
  • Service Provider: A service that registers itself.
  • Service Consumer: A service that queries the registry.

Examples: Eureka (Netflix), Consul (HashiCorp), ZooKeeper.

Benefits: Enables dynamic scaling, fault tolerance, and loose coupling.

Q154: Service Registry

Microservices
What is a service registry? How does it work?

A service registry is a database that stores information about available service instances, including their network locations and health status.

How it works:

  • Registration: Services register themselves at startup (or through sidecars).
  • Heartbeat: Services send periodic heartbeats to indicate they are healthy.
  • Query: Clients query the registry to find services.
  • De-registration: Services unregister when shutting down.
  • Health Checks: Registry removes unhealthy instances.

Key features:

  • Consistent and distributed (using consensus protocols).
  • Provides service discovery and load balancing.
  • Supports dynamic scaling.

Examples: Eureka (Netflix), Consul, ZooKeeper, etcd.

Q155: API Versioning

Microservices
What is API versioning and how do you implement it?

API versioning is the practice of managing changes to an API while maintaining backward compatibility for existing clients.

Common implementation strategies:

  • URI Path Versioning: Include version in the URL path.
    GET /api/v1/users
    GET /api/v2/users
  • Query Parameter Versioning: Use a query parameter.
    GET /api/users?version=1
    GET /api/users?version=2
  • Header Versioning: Use custom headers.
    GET /api/users
    Accept-Version: v1
    Accept-Version: v2
  • Content Negotiation: Use media type.
    GET /api/users
    Accept: application/vnd.myapi.v1+json
    Accept: application/vnd.myapi.v2+json

Best practices: Use semantic versioning, deprecate old versions gracefully, and maintain backward compatibility.

Q158: OpenAPI vs Swagger

Microservices
What is the difference between OpenAPI and Swagger?

OpenAPI is a specification for describing REST APIs in a standard, machine-readable format. Swagger is a suite of tools built around the OpenAPI specification.

Key difference:

  • OpenAPI is the specification (formerly known as Swagger Specification).
  • Swagger is a toolset that implements the OpenAPI spec.

Swagger tools include:

  • Swagger Editor: Online editor for OpenAPI definitions.
  • Swagger UI: Interactive API documentation.
  • Swagger Codegen: Generates client/server code from OpenAPI definitions.

Current naming: The spec is now called OpenAPI (v3+), while Swagger refers to the tooling ecosystem.

Q159: API Rate Limiting

Microservices
What is API rate limiting and how do you implement it?

Rate limiting controls the amount of incoming traffic to an API by restricting the number of requests a client can make in a given time window.

Common algorithms:

  • Token Bucket: Clients are given tokens that refill at a fixed rate. Each request consumes a token.
  • Leaky Bucket: Requests are queued and processed at a fixed rate.
  • Fixed Window: Limits requests per time window (e.g., 100 requests per minute).
  • Sliding Window: Counts requests in a rolling time window.

Implementation approaches:

  • API Gateway: Centralized rate limiting (e.g., Kong, AWS API Gateway).
  • Redis: Distributed rate limiting using Redis counters with TTL.
  • Client-side: Respect rate limit headers (Retry-After).
// Redis-based rate limiting (pseudo-code)
key = clientId + ":api:v1"
count = redis.incr(key)
if (count == 1) redis.expire(key, 60)
if (count > 100) return 429 (Too Many Requests)

Q162: Webhooks

Microservices
What is a webhook and when would you use it?

A webhook is a callback mechanism that allows one system to send real-time notifications to another system via HTTP.

How it works:

  • System A registers a URL (callback endpoint) with System B.
  • When an event occurs, System B sends an HTTP POST request to the registered URL.
  • System A processes the event (asynchronously).

When to use webhooks:

  • Event-driven architectures
  • Real-time notifications
  • Third-party integrations (e.g., Stripe payment confirmations)
  • CI/CD pipelines (e.g., GitHub webhooks to trigger builds)

Examples:

  • GitHub → Jenkins (trigger build on push)
  • Stripe → Your server (payment confirmation)
  • Slack → Your app (incoming messages)

Q164: GraphQL

Microservices
What is GraphQL? What are its advantages over REST?

GraphQL is a query language and runtime for APIs developed by Facebook. It allows clients to request exactly the data they need.

Advantages over REST:

  • Exact Data Fetching: Clients request only the fields they need (no over/under-fetching).
  • Single Endpoint: All operations go to a single GraphQL endpoint.
  • Strongly Typed: Uses a schema definition language (SDL) for type safety.
  • Batch Requests: Can fetch multiple resources in a single request.
  • Versionless: No need for API versioning (can deprecate fields).
  • Real-time: Supports subscriptions for real-time updates.
// GraphQL query
{
  user(id: "123") {
    name
    email
    posts {
      title
      content
    }
  }
}

Note: GraphQL is not always better – it has a learning curve and can be overkill for simple APIs.

Q165: GraphQL Resolvers

Microservices
What are GraphQL resolvers and how do they work?

GraphQL resolvers are functions that handle the logic for fetching the data requested in a GraphQL query. Each field in a GraphQL schema has a corresponding resolver.

How they work:

  • The GraphQL engine receives a query and parses it into an Abstract Syntax Tree (AST).
  • For each field, the corresponding resolver function is called.
  • Resolvers fetch data from databases, APIs, or any other source.
  • Resolvers can be asynchronous and nested.
// GraphQL resolver example (Node.js)
const resolvers = {
  Query: {
    user: (parent, args) => {
      return db.getUserById(args.id);
    }
  },
  User: {
    posts: (user) => {
      return db.getPostsByUserId(user.id);
    }
  }
};

Key points:

  • Resolvers are field-level functions.
  • They receive parent (parent object), args (arguments), context, and info.
  • Resolvers enable N+1 query prevention (DataLoader).

Q167: Kubernetes

Deployment
What is Kubernetes and what are its key components?

Kubernetes (K8s) is an open-source container orchestration platform that automates deployment, scaling, and management of containerized applications.

Key components:

  • Pod: Smallest deployable unit (one or more containers).
  • Node: A worker machine (physical or virtual) where pods run.
  • Cluster: A set of nodes managed by Kubernetes.
  • Control Plane: Manages the cluster (API Server, Scheduler, Controller Manager, etcd).
  • Service: Abstraction that defines a logical set of pods and a policy to access them.
  • Deployment: Manages the desired state of pods (replicas, updates).
  • Ingress: Manages external access to services.
  • ConfigMap/Secret: Configuration and sensitive data management.

Why Kubernetes? Fault tolerance, auto-scaling, rolling updates, service discovery.

Q168: Pod in Kubernetes

Deployment
What is a pod in Kubernetes?

A pod is the smallest deployable unit in Kubernetes. It represents one or more containers that share:

  • Network namespace: They share the same IP address and port space.
  • Storage volumes: They can share mounted volumes.
  • Lifecycle: They are scheduled and terminated together.

Key characteristics:

  • Pods are ephemeral – they can be created and destroyed.
  • Containers in a pod can communicate via localhost.
  • Each pod has a unique IP address within the cluster.
  • Pods are managed by higher-level controllers (Deployments, StatefulSets).
// Simple pod definition
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
  - name: nginx
    image: nginx:latest

Note: In production, use Deployments to manage pods, not direct pod definitions.

Q170: Service in Kubernetes

Deployment
What is a service in Kubernetes? What are its types?

A Service in Kubernetes is an abstraction that defines a logical set of pods and a policy for accessing them. It provides stable networking for dynamic pods.

Types of Services:

  • ClusterIP: Internal IP only (accessible within the cluster). Default type.
  • NodePort: Exposes the service on each node's IP at a static port (30000-32767).
  • LoadBalancer: Exposes the service externally using a cloud provider's load balancer.
  • ExternalName: Maps the service to an external DNS name (no proxying).
// Service example (ClusterIP)
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  selector:
    app: web
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080

Key concept: Services enable service discovery and load balancing for pods.

Q171: Ingress Controller

Deployment
What is an ingress controller in Kubernetes?

An Ingress Controller is a Kubernetes component that manages external access to services in a cluster, typically HTTP/HTTPS traffic. It acts as a reverse proxy and load balancer.

Key features:

  • Routing: Routes traffic to different services based on hostnames and paths.
  • SSL/TLS Termination: Manages SSL certificates for secure connections.
  • Load Balancing: Distributes traffic across multiple services.
  • Name-based Virtual Hosting: Hosts multiple domains on a single IP.
// Ingress resource example
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  rules:
  - host: example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80

Popular controllers: NGINX Ingress, Traefik, AWS ALB Ingress Controller.

Q173: Infrastructure as Code (IaC)

Deployment
What is infrastructure as code (IaC)?

Infrastructure as Code (IaC) is the practice of managing and provisioning infrastructure using code (configuration files) rather than manual processes.

Key principles:

  • Declarative: Define the desired state of infrastructure in code.
  • Version Controlled: Infrastructure changes are tracked in Git.
  • Automated: Infrastructure is provisioned automatically.
  • Consistent: Same configuration produces the same environment.

Benefits:

  • Consistency: Eliminates manual errors and configuration drift.
  • Repeatability: Can recreate environments easily.
  • Auditability: Changes are tracked and auditable.
  • Collaboration: Teams can work on infrastructure together.

Examples: Terraform (HashiCorp), AWS CloudFormation, Azure ARM, Ansible.

Q175: CI/CD Pipeline

Deployment
What is a CI/CD pipeline? What are its stages?

A CI/CD pipeline is an automated process that moves software from code commit to production deployment.

Stages:

  • 1. Source: Code is committed to version control (Git).
  • 2. Build: Code is compiled, dependencies are resolved, artifacts are created.
  • 3. Test: Automated tests (unit, integration, e2e) are executed.
  • 4. Deploy (Staging): Artifacts are deployed to a staging environment.
  • 5. Deploy (Production): Artifacts are deployed to production (after approval).
// Example: GitHub Actions workflow
name: CI/CD
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    - name: Build
      run: mvn package
    - name: Deploy
      run: ./deploy.sh

Tools: Jenkins, GitLab CI, GitHub Actions, CircleCI, Azure DevOps.

Q178: A/B Testing

Deployment
What is A/B testing in deployment?

A/B testing (split testing) is an experiment where two or more versions of a feature are shown to different user groups to determine which performs better.

How it works:

  • Version A (Control): The current version (baseline).
  • Version B (Treatment): The new version with a change.
  • Users are randomly assigned to groups (A or B).
  • Metrics (conversion, engagement, revenue) are compared.
  • The winning version is rolled out to all users.

In deployment:

  • Feature flags are used to enable/disable versions.
  • Traffic splitting routes users to different versions.
  • Real-time monitoring measures performance.

Example: Testing two button colors (red vs blue) to see which gets more clicks.

Q179: Feature Flagging

Deployment
What is feature flagging and when would you use it?

Feature flagging (toggling) is a technique that allows developers to enable or disable features without deploying new code.

When to use feature flags:

  • Canary Releases: Gradually roll out features to a subset of users.
  • A/B Testing: Test different variations with user groups.
  • Kill Switch: Quickly disable a problematic feature without rolling back.
  • Decoupled Deployment: Merge code without releasing it (trunk-based development).
  • Beta Testing: Give early access to select users.
// Feature flag example
if (isFeatureEnabled("new-checkout")) {
  // new checkout flow
} else {
  // old checkout flow
}

Tools: LaunchDarkly, Flagsmith, Split.io, custom Redis-based solutions.

Q183: Amazon S3

Storage
What is Amazon S3 and how does it work?

Amazon S3 (Simple Storage Service) is a scalable object storage service provided by AWS. It stores data as objects in buckets.

Key concepts:

  • Bucket: Container for objects (like a folder). Globally unique name.
  • Object: Data (file) + metadata + unique key.
  • Region: Geographic location of the data.
  • Key: Unique identifier for the object in a bucket.

How it works:

  • Upload objects using PUT requests (REST API).
  • Objects are stored across multiple availability zones for durability.
  • Retrieve objects using GET requests.
  • Supports versioning, lifecycle policies, and encryption.
// Upload to S3 (AWS CLI)
aws s3 cp myfile.txt s3://mybucket/myfile.txt

// Download from S3
aws s3 cp s3://mybucket/myfile.txt .

Q185: Distributed File System

Storage
What is a distributed file system?

A distributed file system (DFS) is a file system that allows multiple clients to access files across multiple servers, presenting them as a single, unified file system.

Key features:

  • Transparent Access: Clients see a single file system view.
  • Fault Tolerance: Data is replicated across multiple nodes.
  • Scalability: Can handle petabytes of data and thousands of clients.
  • Data Locality: Moves computation to where data resides.

Examples:

  • Hadoop HDFS: Designed for big data processing.
  • GlusterFS: Open-source scalable file system.
  • Google File System (GFS): Google's internal file system.
  • Amazon EFS: Managed file system for AWS.

Use cases: Big data, enterprise storage, cloud-native applications.

Q186: Hadoop HDFS

Storage
What is Hadoop HDFS and how does it work?

HDFS (Hadoop Distributed File System) is a distributed file system designed to store and process large datasets (petabytes) across commodity hardware.

Key components:

  • NameNode: Manages metadata (file system namespace, block locations).
  • DataNode: Stores the actual data blocks.
  • Secondary NameNode: Provides checkpointing for the NameNode.

How it works:

  • Files are split into blocks (default: 128 MB).
  • Each block is replicated across multiple DataNodes (default: 3 replicas).
  • NameNode tracks which DataNodes have each block.
  • Data is written once, read many times (WORM model).
// HDFS commands
hdfs dfs -mkdir /user/data
hdfs dfs -put file.txt /user/data/
hdfs dfs -get /user/data/file.txt .

Use cases: Big data processing with MapReduce, Spark, and other analytics frameworks.

Q188: Data Replication

Storage
What is data replication in distributed storage?

Data replication is the process of maintaining multiple copies of data across different nodes to ensure:

  • Fault Tolerance: If one node fails, data is still available.
  • High Availability: Data can be accessed even during node failures.
  • Performance: Reads can be distributed across replicas.

Common strategies:

  • Synchronous Replication: Data is written to all replicas before confirming (strong consistency).
  • Asynchronous Replication: Data is written to primary first, then propagated (eventual consistency).
  • Semi-synchronous: Primary waits for at least one replica.

Trade-offs:

  • Cost: More replicas = more storage cost.
  • Consistency: More replicas = more consistency overhead.
  • Availability: More replicas = higher availability.

Q189: Erasure Coding vs Replication

Storage
What is erasure coding and how does it differ from replication?

Erasure coding is a data protection technique that breaks data into fragments, encodes them with redundant parity data, and distributes them across nodes.

AspectReplicationErasure Coding
Storage OverheadHigh (3x for 3 replicas)Low (e.g., 1.5x for 6+3)
RecoveryRead from another replicaReconstruct from fragments + parity
PerformanceFast readsCPU overhead for encoding/decoding
Use CaseHigh-read workloadsCold storage, archival

Erasure coding (6+3): Split data into 6 fragments + 3 parity fragments = 9 fragments. Can tolerate 3 failures.

Key difference: Replication duplicates whole objects; erasure coding encodes data with parity fragments for more efficient storage.

Q194: Auto-Scaling

Performance
What is auto-scaling and how does it work?

Auto-scaling is the automatic adjustment of computing resources (instances, pods) based on demand.

How it works:

  • Metrics Collection: Monitors CPU, memory, request rate, etc.
  • Policy Definition: Defines scaling rules (min, max, scaling triggers).
  • Scaling Action: Automatically adds or removes resources when thresholds are met.

Types:

  • Horizontal Pod Autoscaling (HPA): Kubernetes, scales pods based on metrics.
  • Vertical Pod Autoscaling (VPA): Adjusts resource requests/limits for pods.
  • Cluster Autoscaler: Adds/removes nodes in a cluster.
  • AWS Auto Scaling: EC2 instances scaling based on policies.

Benefits:

  • Cost Optimization: Pay only for what you need.
  • Availability: Scale up during spikes, down during low demand.

Q198: Backpressure

Performance
What is backpressure in distributed systems?

Backpressure is a mechanism that prevents a system from being overwhelmed by too much data. It allows a downstream system to signal upstream that it is overloaded.

How it works:

  • Consumer signals producer to slow down or stop sending data.
  • Prevents buffer overflow and resource exhaustion.
  • Promotes resilience and stability.

Examples:

  • TCP Flow Control: Receiver window size signals sender to slow down.
  • Message Queues: RabbitMQ can apply backpressure when consumers are slow.
  • Reactive Streams: Publisher-subscriber model with backpressure support.

Strategies:

  • Buffer: Temporarily store data (with overflow handling).
  • Drop: Drop excess data (when processing is slow).
  • Throttle: Reduce the rate of data production.
