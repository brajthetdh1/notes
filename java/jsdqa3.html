Q101: Database Normalization

Database Design
What is database normalization? What are the normal forms?

Normalization is the process of organizing database tables to reduce data redundancy and improve data integrity.

Normal Forms:

  • 1NF (First Normal Form): Each column contains atomic, indivisible values. No repeating groups.
  • 2NF: In 1NF and every non-key column is fully dependent on the entire primary key.
  • 3NF: In 2NF and no transitive dependency (non-key columns don't depend on other non-key columns).
  • BCNF (Boyce-Codd Normal Form): Stronger version of 3NF where every determinant is a candidate key.
  • 4NF: No multi-valued dependencies.
  • 5NF: No join dependencies (project-join normal form).

Benefits: Reduces redundancy, avoids anomalies, improves data consistency.

Trade-off: Over-normalization can lead to complex queries and performance issues.

Q102: Denormalization

Database Design
What is denormalization and when would you use it?

Denormalization is the process of adding redundant data to a database to improve read performance by reducing the number of joins.

When to use:

  • Read-heavy workloads: When queries involve many joins across multiple tables.
  • Analytics and reporting: Pre-computed aggregates for faster querying.
  • Data warehouses: Star and snowflake schemas use denormalized tables.
  • When read performance is critical: Even at the cost of increased storage and write complexity.

Trade-offs:

  • +: Faster reads, simpler queries.
  • -: Increased storage, more complex writes, data inconsistency risk.

Best practice: Start normalized, denormalize only when necessary.

Q104: Composite Index

Database Design
What is a composite index? When would you use it?

A composite index is an index created on multiple columns in a table.

When to use:

  • Queries that filter on multiple columns.
  • Queries that use the columns in the WHERE, ORDER BY, or GROUP BY clauses.
  • When columns are frequently used together in queries.

Important rules:

  • Leftmost Prefix Rule: The index can only be used if the query includes the leftmost column(s).
  • Order of columns matters: place the most selective (distinct) column first.
-- Composite index on last_name and first_name
CREATE INDEX idx_name ON users (last_name, first_name);

-- This query can use the index
SELECT * FROM users WHERE last_name = 'Smith' AND first_name = 'John';

-- This can also use the index (leftmost prefix)
SELECT * FROM users WHERE last_name = 'Smith';

-- This cannot use the index efficiently
SELECT * FROM users WHERE first_name = 'John';

Q106: Connection Pooling

Database Design
What is database connection pooling and why is it used?

Database connection pooling is a technique of maintaining a pool of database connections that can be reused across multiple requests.

Why it's used:

  • Performance: Creating a database connection is expensive (TCP handshake, authentication).
  • Resource Management: Limits the maximum number of connections to prevent database overload.
  • Scalability: Reusing connections reduces overhead and improves throughput.
  • Latency Reduction: Eliminates connection establishment time for each request.
// HikariCP configuration example
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:mysql://localhost:3306/db");
config.setMaximumPoolSize(20);
config.setMinimumIdle(5);
config.setConnectionTimeout(30000);
HikariDataSource ds = new HikariDataSource(config);

Common pools: HikariCP, Apache DBCP, C3P0.

Q108: Materialized View

Database Design
What is a materialized view and when is it used?

A materialized view is a physical table that stores the result of a query. Unlike a standard view, it persists data on disk.

When to use:

  • Pre-computed aggregates: For dashboards and reports.
  • Frequent queries: When the same complex query is run repeatedly.
  • Data warehousing: For ETL and analytics.
  • Read-heavy workloads: When data changes infrequently.

Key characteristics:

  • Data is physically stored (takes disk space).
  • Can be refreshed (on-demand or scheduled).
  • Can be indexed for faster queries.
  • Trade-off: Storage vs query performance.
-- Create a materialized view
CREATE MATERIALIZED VIEW sales_summary AS
SELECT product_id, SUM(amount) as total_sales
FROM orders GROUP BY product_id;

Q109: Database Deadlock

Database Design
What is database deadlock? How do you resolve it?

Deadlock occurs when two or more transactions are waiting for each other to release locks, causing all to wait indefinitely.

Example:

  • Transaction A locks Table 1 and waits for Table 2.
  • Transaction B locks Table 2 and waits for Table 1.
  • Neither can proceed → deadlock.

Resolution strategies:

  • Deadlock Detection: Database detects deadlocks and aborts one transaction.
  • Wait-Die / Wound-Wait: Older transactions have priority.
  • Timeout: Set a timeout; if transaction waits too long, it's aborted.
  • Lock Ordering: Always acquire locks in a fixed order.

Prevention tips:

  • Keep transactions short.
  • Access tables in the same order.
  • Use row-level locks where possible.
  • Use optimistic locking.

Q111: ACID Transactions

Database Design
What is an ACID transaction? Explain each property.

ACID is a set of properties that guarantee database transactions are processed reliably.

  • Atomicity: All operations in a transaction succeed or none do. (All-or-nothing.)
  • Consistency: Transaction brings database from one valid state to another. Maintains all constraints (foreign keys, unique, etc.).
  • Isolation: Concurrent transactions are isolated from each other. Intermediate states are not visible to other transactions.
  • Durability: Once a transaction is committed, it persists even in the event of a system failure.
-- ACID example: Bank transfer
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT; -- Both succeed or both fail

Why it matters: ACID ensures data integrity and reliability in transactional systems.

Q114: Dirty Read, Non-Repeatable Read, Phantom Read

Database Design
What is the difference between dirty read, non-repeatable read, and phantom read?
  • Dirty Read: Reading uncommitted data from another transaction. If the other transaction rolls back, the read data is invalid.
  • Non-Repeatable Read: Reading the same row twice within a transaction yields different results because another transaction updated it.
  • Phantom Read: A query returns different rows when executed twice because another transaction inserted or deleted rows that match the query criteria.
AnomalyDescriptionExample
Dirty ReadRead uncommitted dataT1 updates, T2 reads before T1 commits
Non-Repeatable ReadSame row returns different valuesT1 reads, T2 updates, T1 reads again
Phantom ReadDifferent rows returnedT1 reads all rows, T2 inserts, T1 reads again

Isolation levels prevent these anomalies: Higher isolation levels prevent more anomalies.

Q115: Database Migration

Database Design
What is a database migration and how do you handle it?

A database migration is the process of changing the database schema (DDL) as the application evolves.

Types of migrations:

  • Schema changes: Add/remove columns, tables, indexes.
  • Data migration: Move data from one format to another, backfill data.
  • Rollback: Reverting a migration if something goes wrong.

Handling migrations:

  • Version-controlled migration scripts: Tools like Flyway, Liquibase.
  • Backward-compatible changes: Avoid breaking changes (add columns, deprecate, delete later).
  • Zero-downtime migrations: Use patterns like:
    • Expand and Contract: Add new columns, dual-write, switch, drop old.
    • Blue-Green: Migrate the new version while old version runs.
  • Testing: Run migrations on a staging environment first.
-- Flyway migration example
V1__create_users_table.sql
V2__add_email_column.sql
V3__add_index_on_email.sql

Q116: Cache-Aside Pattern

Caching
What is a cache-aside pattern?

Cache-aside (also called lazy loading) is a caching strategy where the application is responsible for loading data into and reading data from the cache.

How it works:

  • Read: Check cache first. If found, return it (cache hit). If not, read from database, store in cache, return (cache miss).
  • Write: Write to database, then invalidate (or update) the cache.
// Cache-aside read pattern
public User getUser(Long id) {
    User user = cache.get(id);
    if (user == null) {
        user = db.findById(id);
        cache.put(id, user);
    }
    return user;
}

Advantages: Simple, works with any cache, only loads requested data.

Disadvantages: Cache miss penalty, stale data if not invalidated properly.

Q117: Read-Through Cache

Caching
What is read-through cache?

Read-through is a caching pattern where the cache acts as the primary source of data and is responsible for loading data from the database on cache misses.

How it works:

  • The application only talks to the cache.
  • On a cache miss, the cache loads the data from the database, stores it, and returns it.
  • This is often implemented by the caching library/framework.
// Read-through with cache library
User user = cache.get("user:123");
// Cache library handles the miss and loads from DB

Advantages: Application is decoupled from the database, simpler code.

Disadvantages: Cache becomes a single point of failure, more complex implementation.

Difference from cache-aside: In cache-aside, the application manages the cache; in read-through, the cache manages the database interaction.

Q118: Write-Through Cache

Caching
What is write-through cache?

Write-through is a caching strategy where data is written to both the cache and the database simultaneously (synchronously).

How it works:

  • Application writes to cache.
  • Cache writes to database (or a library handles both).
  • The write is not considered complete until both are updated.
// Write-through pattern
public void updateUser(User user) {
    db.update(user);
    cache.put(user.getId(), user);
}
// Application code is simpler

Advantages: Cache is always consistent with the database (strong consistency).

Disadvantages: Higher latency (writes are slower), can degrade performance.

Q119: Write-Behind Cache

Caching
What is write-behind (write-back) cache?

Write-behind (or write-back) is a caching strategy where data is written to the cache first, and the database is updated asynchronously (in the background).

How it works:

  • Application writes to cache (fast).
  • Cache writes are batched and written to the database later (eventually).
  • Writes can be delayed, batched, or coalesced.

Advantages: Very fast writes, reduces load on the database, better performance.

Disadvantages: Risk of data loss if cache fails, eventual consistency, more complex implementation.

Use cases: High-throughput systems, analytics, logging.

// Write-behind with a buffer
cache.put(key, value); // Immediate
// Background worker periodically flushes to DB
worker.flushToDatabase();

Q120: Cache Invalidation

Caching
What is cache invalidation and what are the strategies?

Cache invalidation is the process of removing or updating cached data when the underlying data changes to maintain consistency.

Invalidation strategies:

  • Time-to-Live (TTL): Data expires after a set time. Simple and effective.
  • Write Invalidation: When data is updated, remove the cache entry.
  • Write Update: When data is updated, update the cache entry as well.
  • Lease-based: Cache holds a lease on the data; when data changes, lease is revoked.
  • Version-based: Use version numbers; cache checks for newer versions.
  • Manual Invalidation: Application explicitly invalidates cache.

Challenges:

  • Cache Stampede: Multiple requests trying to refresh expired cache simultaneously.
  • Stale Data: Data inconsistency between cache and database.

Best practice: Use TTL combined with proactive refreshing for hot data.

Q121: Cache Stampede vs Avalanche

Caching
What is the difference between cache stampede and cache avalanche?
  • Cache Stampede (Cache Miss Storm): Many requests try to refresh the same expired cache key simultaneously, causing a spike in database load.
  • Cache Avalanche: A large number of cache keys expire at the same time (e.g., due to TTL), causing a massive spike in database traffic.
AspectCache StampedeCache Avalanche
ScopeSingle keyMany keys
CauseCache miss for a hot keyMassive cache expiration
ImpactSpike in DB load for one keySpike in DB load for many keys

Prevention strategies:

  • For stampede: Use mutex locks, re-cache before expiration (stale-while-revalidate).
  • For avalanche: Stagger TTLs, use jitter, add randomization to expiration times.
// Stale-while-revalidate pattern
String value = cache.get(key);
if (value == null || isExpired(value)) {
    value = db.load(key);
    cache.put(key, value, newTTL);
}

Q122: Redis – Data Structures

Caching
What is Redis? What are its data structures?

Redis (Remote Dictionary Server) is an open-source, in-memory data structure store used as a database, cache, and message broker.

Key features:

  • In-memory storage (persistence optional).
  • Rich data structures.
  • Atomic operations.
  • Pub/Sub messaging.
  • Replication and clustering.

  • Sorted Sets: Sets with scores (ranked).
  • Hashes: Key-value pairs (like objects).
  • Bitmaps: Bit operations.
  • HyperLogLog: Cardinality estimation.
  • Streams: Log data structure for message streaming.

Q124: Cache Warming

Caching
What is cache warming and why is it important?

Cache warming is the practice of preloading the cache with frequently accessed data before it's needed (typically after a cache restart or during application startup).

Why it's important:

  • Performance: Avoids cache misses on the first requests after startup.
  • User Experience: Provides fast response times immediately.
  • Prevents Stampede: Prevents a large number of requests from causing a cache stampede.
  • Load Reduction: Reduces load on the database during startup.

Implementation approaches:

  • Pre-population: Load all data from the database.
  • Lazy Warming: Load data on the first request after startup.
  • Scheduled Warming: Warm cache periodically.
  • Smart Warming: Use usage patterns to predict hot data.

Best practice: Warm the cache with the top N most frequently accessed items.

Q125: Distributed Cache

Caching
What is a distributed cache and how does it work?

A distributed cache is a cache that is spread across multiple servers, providing scalability and high availability.

Key features:

  • Scalability: Add more nodes to increase capacity.
  • High Availability: Data is replicated across nodes.
  • Performance: Requests are distributed across nodes.
  • Fault Tolerance: System continues to work if nodes fail.

How it works:

  • Data Distribution: Data is partitioned across nodes using consistent hashing.
  • Client Requests: Client calculates which node holds the key and connects to that node.
  • Replication: Data can be replicated to multiple nodes for fault tolerance.
  • Consistency: Eventual consistency or strong consistency, depending on configuration.

Examples: Redis Cluster, Hazelcast, Apache Ignite.

Consistent Hashing: Minimizes rehashing when nodes are added/removed.

Q127: Kafka Topic and Partition

Message Queues
What is a Kafka topic and partition?
  • Topic: A logical category to which messages are published. Think of it as a stream or queue name.
  • Partition: A physical, ordered, immutable sequence of messages within a topic. Topics are split into partitions for scalability.

Key concepts:

  • Partitioning: Data is distributed across partitions for parallel consumption.
  • Ordering: Messages are ordered only within a partition, not across partitions.
  • Key: Producers can specify a key; messages with the same key go to the same partition (ensuring order).
  • Replication: Partitions can be replicated across brokers for fault tolerance.
// Topic with 3 partitions

Partition 0: [msg1, msg4, msg7]
Partition 1: [msg2, msg5, msg8]
Partition 2: [msg3, msg6, msg9]

Why partitions? Parallelism, scalability, and throughput.

Q130: Exactly-Once Delivery

Message Queues
What is exactly-once delivery in messaging systems?

Exactly-once delivery guarantees that each message is delivered to the consumer exactly once, with no duplicates and no losses.

How it's achieved:

  • Idempotent Producers: Producers assign unique IDs to messages; brokers deduplicate.
  • Transaction Boundaries: Atomic writes to both the consumer's state and the broker's offset.
  • Atomic Reads & Writes: Consumer reads and processes messages within a transaction.

Example (Kafka):

  • Kafka supports exactly-once semantics with idempotent producers and transactional APIs.
  • Messages are written atomically to the topic, and offsets are committed in the same transaction.
// Kafka exactly-once
producer.initTransactions();
producer.beginTransaction();
producer.send(record);
producer.commitTransaction();

Trade-off: Exactly-once has higher overhead (latency, complexity).

Q131: At-Least-Once vs At-Most-Once

Message Queues
What is at-least-once delivery and at-most-once delivery?
  • At-Least-Once Delivery: Each message is delivered at least once. No messages are lost, but duplicates are possible.
  • At-Most-Once Delivery: Each message is delivered at most once. No duplicates, but messages may be lost.
  • Exactly-Once: The ideal combination of both (no loss, no duplicates).
TypeDuplicateLossUse Case
At-Most-Once✅ No⚠️ PossibleReal-time analytics, monitoring
At-Least-Once⚠️ Possible✅ NoFinancial, order processing
Exactly-Once✅ No✅ NoCritical systems (banking)

How they work:

  • At-Most-Once: Send and forget (no retries).
  • At-Least-Once: Ack required; retry on failure.
  • Exactly-Once: Idempotent operations + transaction.

Idempotency: Operations that can be applied multiple times without changing the result (e.g., "set status to paid" is idempotent; "add $10" is not).

Q132: Dead Letter Queue

Message Queues
What is a dead letter queue and why is it used?

A Dead Letter Queue (DLQ) is a special queue where messages are sent when they cannot be processed successfully (e.g., after too many retries, invalid format, or expiration).

Why it's used:

  • Fault Tolerance: Prevents messages from being lost forever.
  • Debugging: Allows developers to inspect failed messages.
  • Monitoring: Tracks message failures and system health.
  • Recovery: Messages can be reprocessed after fixing the issue.

Common scenarios:

  • Message exceeds retry count.
  • Message format is invalid.
  • Destination service is unavailable.
  • Business logic fails.

Q133: Message Ordering

Message Queues
What is message ordering in distributed systems?

Message ordering refers to the guarantee that messages are delivered to consumers in the order they were produced.

Challenges in distributed systems:

  • Messages can arrive out of order due to network delays.
  • Multiple consumers can process messages in parallel.
  • Retries can cause messages to be processed out of order.

How to achieve ordering:

  • Single Partition/Queue: All messages go to one partition (Kafka) or one queue (RabbitMQ).
  • Key-based Partitioning: Messages with the same key go to the same partition, preserving order for that key.
  • Sequence Numbers: Include sequence numbers; consumers handle reordering.
  • Idempotent Processing: Handle messages idempotently if ordering is not guaranteed.
// Kafka: Same key → same partition → ordering preserved
producer.send(new ProducerRecord("topic", key, message));
// All messages with same key are in order

Trade-off: Ordering limits parallelism (more ordering = less parallelism).

Q137: OAuth 2.0

Security
What is OAuth 2.0 and how does it work?

OAuth 2.0 is an authorization framework that enables applications to obtain limited access to user accounts on an HTTP service.

Key roles:

  • Resource Owner: The user who owns the data.
  • Client: The application requesting access.
  • Authorization Server: Issues access tokens.
  • Resource Server: Hosts the protected resources.

Grant types:

  • Authorization Code: Most secure, used by web apps.
  • Client Credentials: Server-to-server communication.
  • Resource Owner Password: Deprecated, not recommended.
  • Implicit: Deprecated, use Authorization Code with PKCE instead.
// Authorization Code flow
1. User logs in → Authorization Server
2. Authorization Server redirects with code
3. Client exchanges code for access token
4. Client accesses Resource Server with token

Q138: JWT (JSON Web Token)

Security
What is JWT (JSON Web Token) and how is it used?

JWT (JSON Web Token) is a compact, URL-safe token format for transmitting claims between parties. It is signed (and optionally encrypted) for security.

Structure:

  • Header: Algorithm and type (e.g., {"alg": "HS256", "typ": "JWT"}).
  • Payload: Claims (user data, expiration, etc.).
  • Signature: Cryptographic signature to verify integrity.
// JWT format
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4iLCJpYXQiOjE1MTYyMzkwMjJ9.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Use cases:

  • Stateless authentication (no server-side session).
  • Information exchange between parties.
  • Single Sign-On (SSO).

Important: JWTs are signed (to verify issuer) and can be encrypted (to keep contents confidential).

Q140: SSL/TLS

Security
What is SSL/TLS and why is it important?

SSL (Secure Sockets Layer) and TLS (Transport Layer Security) are cryptographic protocols that provide secure communication over a network.

Why it's important:

  • Encryption: Data is encrypted in transit (no eavesdropping).
  • Authentication: Verifies the identity of the server (and optionally the client).
  • Integrity: Ensures data is not altered in transit.
  • Trust: Builds user trust (HTTPS padlock).

How it works (handshake):

  • Client sends "hello" with supported TLS versions.
  • Server responds with certificate and public key.
  • Client verifies certificate.
  • Both exchange symmetric session keys.
  • Encrypted communication begins.

Note: TLS is the successor to SSL; SSL is now deprecated.

Q142: HTTPS

Security
What is HTTPS and how does it work?

HTTPS (Hypertext Transfer Protocol Secure) is the secure version of HTTP that uses SSL/TLS for encryption.

How it works:

  • Client connects: Browser sends HTTPS request to server.
  • TLS Handshake: Server responds with SSL/TLS certificate and public key.
  • Verification: Client verifies the certificate with a trusted CA.
  • Key Exchange: Both agree on a symmetric session key using asymmetric encryption.
  • Encrypted Data: All subsequent data is encrypted with the session key.

Benefits:

  • Privacy: Data is encrypted (no eavesdropping).
  • Integrity: Data cannot be modified in transit.
  • Authentication: Server identity is verified.

Note: HTTPS uses port 443 by default.

Q143: DDoS Attack

Security
What is a DDoS attack and how do you prevent it?

DDoS (Distributed Denial of Service) is an attack where multiple compromised systems flood a target with traffic, making it unavailable to legitimate users.

Types:

  • Volumetric: Floods network bandwidth (e.g., UDP floods).
  • Protocol: Exploits protocol weaknesses (e.g., SYN floods).
  • Application Layer: Targets specific applications (e.g., HTTP floods).

Prevention strategies:

  • Rate Limiting: Limit requests from a single IP.
  • Web Application Firewall (WAF): Filter malicious traffic.
  • CDN: Distribute traffic across multiple servers (Cloudflare, Akamai).
  • Anycast: Route traffic to the nearest data center.
  • Auto-scaling: Scale up resources during attacks.
  • Traffic Analysis: Identify and block attack patterns.

Best practice: Use a layered defense approach (network + application + operational).

Q144: RBAC

Security
What is role-based access control (RBAC)?

Role-Based Access Control (RBAC) is a security model where access permissions are assigned to roles, and users are assigned to roles.

Key concepts:

  • Users: Individuals accessing the system.
  • Roles: Job functions or responsibilities (e.g., Admin, Editor, Viewer).
  • Permissions: Actions allowed (e.g., read, write, delete).
  • Role Assignment: Users are assigned roles.

Benefits:

  • Simplified Management: Permissions are managed at the role level.
  • Least Privilege: Users only get permissions they need.
  • Auditability: Clear separation of duties.
  • Scalability: Easy to add new users with existing roles.
// Example roles
ADMIN: read, write, delete, manage_users
EDITOR: read, write
VIEWER: read

Note: RBAC is often implemented with ABAC (Attribute-Based Access Control) for more granular control.

Q145: Principle of Least Privilege

Security
What is the principle of least privilege in security?

The principle of least privilege states that a system should give users and processes only the minimum permissions necessary to perform their tasks.

Why it matters:

  • Reduces Attack Surface: Limits what an attacker can do if they compromise an account.
  • Limits Damage: Contains the impact of security breaches.
  • Improves Accountability: Easier to audit actions.
  • Reduces Insider Threats: Prevents misuse of privileges.

Implementation:

  • Role-Based Access Control (RBAC): Assign only necessary roles.
  • Minimal Permissions: Use read-only access where possible.
  • Time-Bound Access: Temporary access for specific tasks.
  • Just-In-Time (JIT) Access: Grant access only when needed.

Examples:

  • A developer should not have production database admin rights.
  • A read-only user should not be able to write data.
  • Applications should run with non-root user permissions.

Q147: Three Pillars of Observability

Observability
What are the three pillars of observability?

The three pillars are the fundamental data types needed for observability:

  • 1. Logs: Immutable, timestamped records of events. Provide detailed information about what happened.
  • 2. Metrics: Numerical data points measured over time. Provide high-level system health (CPU, memory, request rate).
  • 3. Traces: Records of a request's journey through a distributed system. Show how requests flow through services.

Why three pillars? Together, they provide a complete picture of system behavior.

Q149: Distributed Tracing

Observability
What is distributed tracing? How does it work?

Distributed tracing is a method of tracking a request as it flows through a distributed system, showing the path and timing of each service call.

Key concepts:

  • Trace: The entire journey of a request across multiple services.
  • Span: A single operation within a trace (e.g., a database query, an HTTP call).
  • Trace ID: Unique identifier for the entire trace.
  • Span ID: Unique identifier for a single span.
  • Parent Span ID: ID of the parent span (for hierarchy).
// Trace example
Trace ID: abc123
  Span: API Gateway (duration: 100ms)
    Span: Auth Service (duration: 30ms)
    Span: Order Service (duration: 60ms)
      Span: DB Query (duration: 20ms)

How it works:

  • Each service propagates trace context (trace ID, span ID) via HTTP headers.
  • Services create spans for operations.
  • Spans are sent to a tracing backend (Jaeger, Zipkin).
  • Tracing backend visualizes the trace.
