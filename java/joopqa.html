Q1: What is OOP?

Basic OOPs
What is Object-Oriented Programming (OOP)?

Object-Oriented Programming (OOP) is a programming paradigm that organizes software design around objects rather than functions and logic. An object is a real-world entity that has state (attributes) and behavior (methods).

OOP models real-world entities and their relationships, making code more modular, reusable, and maintainable. Java is a fully object-oriented programming language.

Key concepts:

  • Objects: Instances of classes
  • Classes: Blueprints for creating objects
  • Encapsulation: Bundling data and methods
  • Inheritance: Creating new classes from existing ones
  • Polymorphism: One interface, multiple implementations
  • Abstraction: Hiding implementation details
// Class and Object in Java
class Car {
    String brand; // state
    void start() { System.out.println("Car started"); } // behavior
}

Car myCar = new Car(); // object
myCar.brand = "Tesla";
myCar.start();

Q2: Four Pillars of OOP

Basic OOPs
What are the four main pillars of OOP?

The four main pillars of Object-Oriented Programming are:

  • 1. Encapsulation: Bundling data and methods that operate on that data, hiding internal state from outside access. Achieved using access modifiers like private and protected.
  • 2. Inheritance: Creating new classes based on existing ones, inheriting properties and behaviors. Promotes code reuse.
  • 3. Polymorphism: The ability of objects to take many forms. Allows one interface to be used for a general class of actions.
  • 4. Abstraction: Hiding complex implementation details and showing only essential features. Achieved using abstract classes and interfaces.
// Example demonstrating all four pillars
// Abstraction: Abstract class
abstract class Vehicle { abstract void start(); }

// Inheritance: Car extends Vehicle
class Car extends Vehicle {
    // Encapsulation: private field
    private String model;
    public String getModel() { return model; }
    // Polymorphism: override
    @Override
    void start() { System.out.println("Car starting..."); }
}

Q3: Object in Java

Basic OOPs
What is an Object in Java?

An object in Java is a runtime entity that has:

  • State: Represented by attributes (fields/variables)
  • Behavior: Represented by methods (functions)
  • Identity: A unique identity that distinguishes it from other objects

Objects are created from classes using the new keyword. They are stored in heap memory and are referenced by variables.

Examples of objects: a specific car, a particular person, a bank account, etc.

// Creating an object
Person p1 = new Person(); // p1 is an object of Person class
p1.name = "John"; // Setting state
p1.age = 25; // Setting state
p1.sayHello(); // Calling behavior

Key points:

  • Objects are created at runtime
  • Multiple objects can be created from the same class
  • Each object has its own copy of instance variables
  • Objects communicate by calling each other's methods

Q4: Class in Java

Basic OOPs
What is a Class in Java?

A class in Java is a blueprint or template for creating objects. It defines the structure (fields) and behavior (methods) that all objects of that class will have.

A class is a logical construct that exists at compile-time, while objects are physical entities that exist at runtime.

Components of a class:

  • Fields: Variables that hold the state of the object
  • Methods: Functions that define the behavior of the object
  • Constructors: Special methods used to initialize objects
  • Nested classes: Classes defined within another class
// Class definition
class Employee {
    // Fields
    String name;
    int id;
    double salary;

    // Constructor
    Employee(String name, int id) {
        this.name = name;
        this.id = id;
    }

    // Method
    void display() {
        System.out.println(name + " - " + id);
    }
}

Q7: Advantages of OOP

Basic OOPs
What are the advantages of OOP?

Advantages of Object-Oriented Programming:

  • Reusability: Inheritance allows code reuse, reducing redundancy.
  • Modularity: Code is organized into classes, making it easier to manage.
  • Maintainability: Changes can be made in one place without affecting other parts.
  • Security: Data hiding prevents unauthorized access to internal state.
  • Scalability: Easier to extend and scale large applications.

Q8: Disadvantages of OOP

Basic OOPs
What are the disadvantages of OOP?

Disadvantages of Object-Oriented Programming:

  • Complexity: OOP can be more complex for simple programs.
  • Overhead: Extra memory and performance overhead compared to procedural code.
  • Learning curve: Requires understanding of new concepts (inheritance, polymorphism, etc.).
  • Not suitable for all problems: Some problems are better solved with procedural or functional approaches.

Note: Despite these disadvantages, OOP remains the dominant paradigm for large-scale software development due to its benefits in managing complexity.

Q9: Constructor

Basic OOPs
What is a constructor in Java?

A constructor is a special method that is automatically called when an object is instantiated. It is used to initialize the object's state.

Characteristics of constructors:

  • Has the same name as the class
  • Has no return type (not even void)
  • Can be overloaded (multiple constructors with different parameters)
  • Can have access modifiers (public, private, protected, default)
  • If no constructor is defined, Java provides a default constructor (no-arg)
// Constructor example
class Student {
    String name;
    int rollNo;

    // No-arg constructor
    Student() {
        name = "Unknown";
        rollNo = 0;
    }

    // Parameterized constructor
    Student(String name, int rollNo) {
        this.name = name;
        this.rollNo = rollNo;
    }
}

Note: Constructors are called when you use new keyword: Student s = new Student("John", 101);

Q11: What is Encapsulation?

Encapsulation
What is Encapsulation in Java?

Encapsulation is the mechanism of wrapping data (variables) and code (methods) together as a single unit. It restricts direct access to an object's internal state and provides controlled access through public methods.

Key principles:

  • Keep instance variables private (or protected)
  • Provide public getter and setter methods to access/modify data
  • Data hiding – internal implementation is hidden from outside
// Encapsulated class
class BankAccount {
    private double balance; // private field

    public double getBalance() { // getter
        return balance;
    }

    public void deposit(double amount) { // setter with logic
        if (amount > 0) {
            balance += amount;
        }
    }
}

Benefits: Security, control over data, maintainability, flexibility.

Q12: Achieving Encapsulation

Encapsulation
How do you achieve Encapsulation in Java?

Encapsulation in Java is achieved through:

  • 1. Access Modifiers: Use private for fields to prevent direct access.
  • 2. Getters and Setters: Provide public methods to read and update fields.
  • 3. Business Logic in Setters: Add validation logic inside setter methods.
  • 4. Internal Implementation Hiding: Keep implementation details hidden from users.
// Encapsulation example
class Person {
    private String name;
    private int age;

    public String getName() { return name; }
    public void setName(String name) {
        this.name = name;
    }
    public int getAge() { return age; }
    public void setAge(int age) {
        if (age > 0) { // validation logic
            this.age = age;
        }
    }
}

Note: Encapsulation is not just about making fields private. It's about controlling access and adding validation logic.

Q16: Getters and Setters

Encapsulation
What is a getter and setter method?

Getter and setter methods are public methods that provide controlled access to private fields.

  • Getter: Returns the value of a private field. Naming convention: getFieldName()
  • Setter: Sets the value of a private field. Naming convention: setFieldName(value)

Purpose:

  • Enable encapsulation by keeping fields private
  • Add validation logic in setters
  • Add transformation logic in getters
  • Provide read-only or write-only access
class Product {
    private String name;
    private double price;

    // Getter
    public String getName() { return name; }
    public double getPrice() { return price; }

    // Setter with validation
    public void setPrice(double price) {
        if (price >= 0) {
            this.price = price;
        }
    }
}

Note: Modern IDEs can generate getters and setters automatically.

Q17: Why Getters/Setters?

Encapsulation
Why should we use getters and setters instead of public fields?

Reasons to use getters and setters over public fields:

  • 1. Validation: Setters allow adding validation logic before setting values.
  • 2. Read-only / Write-only: Getters and setters can be selectively provided.
  • 3. Transformation: Getters can transform data before returning.
  • 4. Encapsulation: Internal representation can change without affecting external code.
  • 5. Debugging: Can add logging or debugging code in getters/setters.
  • 6. Thread safety: Can add synchronization logic.
  • 7. Future flexibility: Easy to change implementation later.
// Public field (bad practice)
class User { public String name; }

// Encapsulated (good practice)
class User {
    private String name;
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
}

Best practice: Always use getters and setters for fields that need to be accessed from outside the class.

Q20: Encapsulation without Getters/Setters?

Encapsulation
Can encapsulation be achieved without getters and setters?

Yes! Encapsulation can be achieved without getters and setters. Encapsulation is about hiding implementation details and bundling data and methods.

Examples of encapsulation without getters/setters:

  • Behavioral methods: A class provides methods that perform operations, not just getters/setters.
  • Package-private classes: Classes with default access for internal use.
  • Immutable objects: Objects that cannot be modified after creation (like String).
  • Factory methods: Methods that create objects without exposing fields.
// Encapsulation without getters/setters
class BankAccount {
    private double balance;

    // Only behavior methods, no getters
    public void deposit(double amount) {
        if (amount > 0) balance += amount;
    }
    public boolean withdraw(double amount) {
        if (balance >= amount) {
            balance -= amount;
            return true;
        }
        return false;
    }
// No getBalance() method – but still encapsulated
}

Best practice: Encapsulation is about hiding implementation, not necessarily about providing getters and setters. Getters/setters are just one way to achieve it.

Q21: What is Inheritance?

Inheritance
What is Inheritance in Java?

Inheritance is a mechanism in Java where one class acquires the properties (fields) and behaviors (methods) of another class. It represents an "is-a" relationship.

Key concepts:

  • Parent Class (Superclass): The class being inherited from.
  • Child Class (Subclass): The class that inherits from the parent.
  • Use the extends keyword to create a subclass.
  • Inheritance promotes code reuse and polymorphism.
// Superclass
class Animal {
    void eat() { System.out.println("Eating..."); }
}

// Subclass
class Dog extends Animal {
    void bark() { System.out.println("Barking..."); }
}

// Usage
Dog dog = new Dog();
dog.eat(); // inherited method
dog.bark(); // own method

Benefits: Code reuse, extensibility, method overriding, and polymorphism.

Q22: Types of Inheritance

Inheritance
What are the types of inheritance in Java?

Java supports the following types of inheritance:

  • 1. Single Inheritance: One subclass inherits from one superclass.
  • 2. Multi-level Inheritance: A class inherits from another class, which in turn inherits from another class.
  • 3. Hierarchical Inheritance: Multiple subclasses inherit from a single superclass.

Java does NOT support:

  • Multiple Inheritance: A class inheriting from multiple classes (not supported).
  • Hybrid Inheritance: Combination of multiple and hierarchical inheritance (not supported).
// Single inheritance
class A { }
class B extends A { }

// Multi-level inheritance
class A { }
class B extends A { }
class C extends B { }

// Hierarchical inheritance
class A { }
class B extends A { }
class C extends A { }

Note: Multiple inheritance is achieved through interfaces in Java.

Q23: Multiple Inheritance?

Inheritance
Does Java support multiple inheritance?

No, Java does not support multiple inheritance with classes (i.e., a class cannot extend more than one class).

Why not?

  • Diamond Problem: Ambiguity when two parent classes have the same method or field.
  • Complexity: Multiple inheritance makes the language complex and can lead to confusion.

Solution in Java:

  • Interfaces: A class can implement multiple interfaces.
  • Default methods: Interfaces can have default methods to provide implementation.
// Class cannot extend multiple classes
// class C extends A, B { } // ERROR

// But can implement multiple interfaces
interface I1 { void method1(); }
interface I2 { void method2(); }
class C implements I1, I2 {
    public void method1() { }
    public void method2() { }
}

Note: Java 8 introduced default methods in interfaces, which can lead to conflicts if two interfaces provide default methods with the same signature. However, this is resolved by the implementing class.

Q26: 'extends' Keyword

Inheritance
What is the 'extends' keyword used for?

The extends keyword is used to create a subclass that inherits from a superclass.

Syntax: class Subclass extends Superclass { ... }

Key points:

  • extends establishes an "is-a" relationship.
  • A class can extend only one class (single inheritance).
  • The subclass inherits all public and protected members.
  • extends is used for classes, while implements is used for interfaces.
// Superclass
class Shape {

}

// Subclass using extends
class Circle extends Shape {

// The 'is-a' relationship
Shape s = new Circle(); // Circle IS-A Shape

Note: Every class in Java implicitly extends Object class (the root of the class hierarchy).

Q27: 'super' Keyword

Inheritance
What is the 'super' keyword in Java?

The super keyword is a reference variable used to refer to the immediate parent class object. It is used in the context of inheritance.

Uses of super:

  • Access parent class fields: super.field
  • Call parent class methods: super.method()
  • Call parent class constructor: super(parameters) – must be the first statement in constructor
class Animal {
    String name = "Animal";
    Animal() { System.out.println("Animal constructor"); }
    void eat() { System.out.println("Animal eating"); }
}

class Dog extends Animal {
    String name = "Dog";
    Dog() {
        super(); // call parent constructor
        System.out.println("Dog constructor");
    }
    void display() {
        System.out.println(super.name); // "Animal"
        System.out.println(this.name); // "Dog"
        super.eat(); // "Animal eating"
    }
}

Important: super() must be the first statement in a constructor.

Q29: Method Overriding

Inheritance
What is method overriding in Java?

Method overriding occurs when a subclass provides a specific implementation of a method that is already defined in its superclass.

Rules for overriding:

  • Same method name and parameters (signature)
  • Same or more accessible access modifier (can't be more restrictive)
  • Return type can be covariant (subtype of parent's return type)
  • final methods cannot be overridden
  • static methods cannot be overridden (they are hidden)
  • private methods cannot be overridden
class Animal {
    void sound() { System.out.println("Animal makes sound"); }
}

class Cat extends Animal {
    @Override
    void sound() { System.out.println("Meow"); } // overriding
}

// Usage
Animal a = new Cat();
a.sound(); // "Meow" (runtime polymorphism)

Benefits: Enables runtime polymorphism, supports the Open/Closed principle, and allows extension of behavior.

Q31: Overriding Rules

Inheritance
What are the rules for method overriding in Java?

Rules for method overriding:

  • 1. Same signature: Method name and parameter list must be the same.
  • 2. IS-A relationship: Must be in a subclass.
  • 3. Access modifier: Cannot be more restrictive (can be less restrictive).
  • 4. Return type: Must be the same or a subtype (covariant return).
  • 5. Exceptions: Cannot throw broader checked exceptions (can throw narrower or fewer).
  • 6. final methods: Cannot be overridden.
  • 7. static methods: Cannot be overridden (method hiding).
  • 8. private methods: Cannot be overridden.
  • 9. Constructors: Cannot be overridden.
  • 10. @Override annotation: Not required but recommended for compiler validation.
class Parent {
    protected Number getValue() throws Exception {
        return 10;
    }
}

class Child extends Parent {
    @Override
    public Integer getValue() throws NullPointerException {
        return 20; // covariant return, broader access, narrower exception
    }
}

Note: The @Override annotation helps catch errors at compile-time.

Q32: @Override Annotation

Inheritance
What is the '@Override' annotation and why is it used?

@Override is a marker annotation used to indicate that a method is intended to override a method in a superclass.

Why use it?

  • Compiler verification: Ensures the method actually overrides a superclass method. If not, compiler shows an error.
  • Readability: Makes the code easier to understand and maintain.
  • Prevents errors: Catches typos or signature mismatches.
class Parent {
    void display() { }
}

class Child extends Parent {
    @Override
    void display() { } // ✓ Correct override

    // @Override
    // void display(String s) { } // Compiler error
}

Note: @Override is optional but strongly recommended. It helps catch subtle bugs and improves code quality.

Q33: Override Static Methods?

Inheritance
Can we override static methods in Java?

No, static methods cannot be overridden in Java. They can be hidden but not overridden.

Why not?

  • Static methods are associated with the class, not with the object.
  • Overriding is a runtime concept, while static methods are resolved at compile-time.
  • Method resolution for static methods is based on the reference type, not the object type.
class Parent {
    static void display() { System.out.println("Parent static"); }
}

class Child extends Parent {
    // This is method hiding, not overriding
    static void display() { System.out.println("Child static"); }
}

// Usage
Parent p = new Child();
p.display(); // "Parent static" (compile-time resolution)
Child c = new Child();
c.display(); // "Child static"

Key point: Static methods are hidden in subclasses, not overridden. This is called "method hiding".

Q34: Override Private Methods?

Inheritance
Can we override private methods in Java?

No, private methods cannot be overridden in Java.

Why not?

  • Private methods are not inherited by subclasses.
  • They are only accessible within the same class.
  • Subclasses cannot see or override private methods.

Note: A subclass can define a method with the same name and signature, but it's a new method, not an override.

  • Performance-critical methods
  • Methods that should not be modified

Q36: Constructors in Inheritance

// Parent: Hello
// Child constructor

Important: super() or super(parameters) must be the first statement in a constructor.

Q38: Liskov Substitution Principle

Inheritance
What is the Liskov Substitution Principle?

The Liskov Substitution Principle (LSP) is a SOLID principle that states:

"Subtypes must be substitutable for their base types."

In simpler terms: A subclass should extend the behavior of the superclass without changing its fundamental behavior.

Key points:

  • Subclasses should not violate the expectations of the superclass.
  • Subclasses should not remove or weaken the behavior of the superclass.
  • Subclasses should not throw more exceptions than the superclass.
  • Subclasses should not weaken preconditions or strengthen postconditions.
// Violation of LSP
class Rectangle {
    int width, height;
    void setWidth(int w) { width = w; }
    void setHeight(int h) { height = h; }
}

class Square extends Rectangle {
    @Override
    void setWidth(int w) { super.setWidth(w); super.setHeight(w); }
    @Override
    void setHeight(int h) { super.setWidth(h); super.setHeight(h); }
}

// This violates LSP because Square changes Rectangle behavior

Solution: Use composition instead of inheritance when the subclass is not truly substitutable.

  • Supports the Open/Closed Principle
  • Allows for family of related classes

Q44: Method Overloading

What is method overloading?

Method overloading is a feature that allows a class to have multiple methods with the same name but different parameters (different number, type, or order).

Characteristics:

  • Methods must have different parameter lists (number, type, or order).
  • Return type can be different but doesn't contribute to overloading.

p.print(5.5); // double: 5.5

Benefits: Cleaner API, intuitive method names, flexibility.

Q45: Overloading Rules

Polymorphism
What are the rules for method overloading?

Rules for method overloading:

  • 1. Different parameter lists: Methods must have different number, type, or order of parameters.
  • 2. Same method name: All overloaded methods must have the same name.
  • 3. Return type: Can be different but doesn't contribute to overloading (can't overload based on return type alone).
  • 4. Access modifiers: Can be different.
  • 5. Exceptions: Can throw different exceptions.
  • 6. Static methods: Can be overloaded.
  • 7. Constructors: Can be overloaded.
class OverloadExample {
    // Different number of parameters
    void m(int a) { }
    void m(int a, int b) { }

    // Different type of parameters
    void m(int a) { }
    void m(double a) { }

    // Different order of parameters
    void m(int a, double b) { }
    void m(double a, int b) { }

    // Can't overload based on return type alone
    // int m() { }
    // void m() { } // ERROR
}

Note: Overloading is resolved at compile-time based on the method signature.

Q53: What is Abstraction?

Q57: Abstract Class vs Interface – When to Use

When would you use an abstract class vs an interface?

Use an abstract class when:

  • You want to provide default implementations for some methods.

  • You want to have constructors.
  • You want to restrict a class hierarchy (template pattern).

Q94: equals() & hashCode() Contract

Advanced OOPs
What is the contract between equals() and hashCode()?

The contract between equals() and hashCode() is defined in the Object class and must be followed:

  • 1. Consistency: If two objects are equal according to equals(), they must have the same hash code.
  • 2. Consistency: The hash code should not change as long as the object's state doesn't change (with respect to equality).
  • 3. Not Required: If two objects have the same hash code, they may or may not be equal.
// Violation of the contract
class BadPerson {
    String name;
    @Override
    public boolean equals(Object obj) {
        return name.equals(((BadPerson)obj).name);
    }
    // No hashCode() override – violation!
}

// Correct implementation
class GoodPerson {
    String name;
    @Override
    public boolean equals(Object obj) {
        return name.equals(((GoodPerson)obj).name);
    }
    @Override
    public int hashCode() {
        return name.hashCode();
    }
}

Why it matters: Violating the contract breaks HashMap, HashSet, and other hash-based collections.

Difference between shallow copy and deep copy in context of clone?
  • Shallow Copy (default clone): Copies only the object's fields. If the object contains references to other objects, only the references are copied (not the nested objects).
  • Deep Copy: Copies the object and all nested objects, creating completely independent copies.
class Address { String city; }
class Person implements Cloneable {
    String name;
    Address address;

    @Override
    protected Object clone() throws CloneNotSupportedException {
        Person p = (Person) super.clone(); // shallow copy
        // For deep copy, also clone address
        p.address = new Address();
        p.address.city = this.address.city;
        return p;
    }
}

Q97: SOLID Principles

Design Principles
What are SOLID principles in OOP?

SOLID is an acronym for five design principles that help create maintainable, flexible, and scalable object-oriented software.

  • S – Single Responsibility Principle: A class should have one and only one reason to change.
  • O – Open/Closed Principle: Classes should be open for extension, closed for modification.
  • L – Liskov Substitution Principle: Subtypes must be substitutable for their base types.
  • I – Interface Segregation Principle: Clients should not be forced to depend on interfaces they don't use.
  • D – Dependency Inversion Principle: Depend on abstractions, not on concrete implementations.
// Single Responsibility – Good
class Employee { }
class EmployeeRepository { }
class EmployeeReport { }

// Open/Closed – Good
interface Shape { double area(); }
class Circle implements Shape { }
class Rectangle implements Shape { }

Benefits: Better code quality, easier maintenance, improved testability, reduced technical debt.

Q98: Single Responsibility Principle

Design Principles
What is the Single Responsibility Principle?

The Single Responsibility Principle (SRP) states that a class should have only one reason to change, meaning it should have only one responsibility.

Key points:

  • Each class should focus on one thing.
  • Separate concerns into different classes.
  • Improves cohesion and reduces coupling.
  • Makes code easier to understand and maintain.
// ❌ Violates SRP – multiple responsibilities
class Employee {
    void calculateSalary() { }
    void saveToDatabase() { }
    void generateReport() { }
}

// ✅ Follows SRP – each class has one responsibility
class Employee {
    void calculateSalary() { }
}
class EmployeeRepository { void save() { } }
class EmployeeReport { void generate() { } }

Benefits: Easier to test, maintain, and extend. Changes to one responsibility don't affect others.

Q99: Open/Closed Principle

Design Principles
What is the Open/Closed Principle?

The Open/Closed Principle (OCP) states that classes should be open for extension but closed for modification.

Key points:

  • You should be able to add new functionality without changing existing code.
  • Use abstraction (interfaces, abstract classes) to enable extension.
  • Avoid modifying existing code when adding new features.
// ❌ Violates OCP – need to modify when adding new shape
class AreaCalculator {
    double calculateArea(Object shape) {
        if (shape instanceof Circle) { ... }
        if (shape instanceof Rectangle) { ... }
    }
}

// ✅ Follows OCP – extendable
interface Shape { double area(); }
class Circle implements Shape { double area() { ... } }
class Rectangle implements Shape { double area() { ... } }
class AreaCalculator {
    double calculateArea(Shape shape) { return shape.area(); }
}

Benefits: Code is more flexible, easier to extend, and less likely to introduce bugs.

Q100: Dependency Inversion Principle

Design Principles
What is the Dependency Inversion Principle?

The Dependency Inversion Principle (DIP) states that:

  • High-level modules should not depend on low-level modules. Both should depend on abstractions.
  • Abstractions should not depend on details. Details should depend on abstractions.

Key points:

  • Depend on interfaces/abstract classes, not concrete classes.
  • This reduces coupling and increases flexibility.
  • Makes code more testable (easy to mock dependencies).
// ❌ Violates DIP – High-level depends on low-level
class EmailService { void send() { } }
class Notification {
    EmailService email = new EmailService();
    void notify() { email.send(); }
}

// ✅ Follows DIP – depends on abstraction
interface MessageService { void send(); }
class EmailService implements MessageService {
    void send() { }
}
class SmsService implements MessageService {
    void send() { }
}
class Notification {
    MessageService service;
    Notification(MessageService service) { this.service = service; }
    void notify() { service.send(); }
}

Benefits: Loose coupling, better testability, easier to swap implementations.
