Section 4.1: Visibility – The "Seeing Is Believing" Problem

Visibility is about ensuring that changes made by one thread are visible to other threads. We touched on this in Chapter 3, but now we go deep.

Subsection 4.1.1: The Visibility Problem – Why It Happens

The Hardware Reality (Recap):

Each CPU core has its own cache (L1, L2). When a thread writes to a variable, it writes to its core's cache. Unless that cache line is flushed to main memory (or invalidated in other cores), other threads may not see the change.

The JVM Reality:

The JVM and JIT compiler also reorder instructions for performance. Without proper synchronization, a thread may see operations in an order that violates program order.

The "Doubt Clarifier" – Can a thread never see a change, or just see it later?
It can never see it if the variable is not properly synchronized. The JVM is allowed to cache the value indefinitely (e.g., in a CPU register) and never reload it from memory. This is not a "delay"; it's a permanent staleness.

Example: The Infinite Loop Bug

public class VisibilityBug { private static boolean running = true; public static void main(String[] args) throws InterruptedException { Thread t = new Thread(() -> { while (running) { // Do nothing } System.out.println("Thread finished"); }); t.start(); Thread.sleep(1000); running = false; // Main thread sets to false System.out.println("Set running to false"); t.join(); // May never finish! } }

What happens: The JIT compiler optimizes while (running) by hoisting the read of running out of the loop:

if (!running) { // Loop never executes } else { while (true) { // Infinite loop } }

Because running is not volatile, the JIT assumes it won't change. The loop runs forever.

The Fix: Make running volatile.

Subsection 4.1.2: The "Doubt Clarifier" – Why doesn't System.out.println() fix visibility?

Some developers notice that adding a System.out.println() inside the loop "fixes" the bug. Why?

System.out.println() is synchronized (it uses PrintStream which has synchronized methods). Synchronization forces the thread to reload variables from main memory, which makes the change to running visible.

But this is a terrible hack! You cannot rely on println() for correctness. It may not work on all JVMs, and it's slow. Always use proper synchronization (volatile, synchronized, or Atomic).

Subsection 4.1.3: The "Doubt Clarifier" – What does it mean for a variable to be "stale"?

A stale value is an old value that is still visible in a thread's cache. For example:

  • Thread A writes x = 5.
  • Thread B reads x and gets 0 (the initial value) because Thread B's cache hasn't been invalidated.

Stale values are not random; they are previous values. The JVM guarantees that a read will see some value that was written to the variable (not a completely arbitrary value). But it may be an old value.

Subsection 4.1.5: The "Doubt Clarifier" – Is volatile enough for a boolean flag used in a loop?

Yes. volatile guarantees that the reading thread will see the latest value. The loop will terminate when the flag is set to false.

Example:

private volatile boolean running = true; public void run() { while (running) { // Do work } } public void stop() { running = false; // Volatile write; immediately visible }
The "Doubt Clarifier" – What if the flag is a boolean but I use AtomicBoolean instead?
AtomicBoolean is more flexible if you need CAS operations (e.g., compareAndSet). For simple get/set, volatile is sufficient and slightly faster.

Subsection 4.1.6: The "Doubt Clarifier" – What is the "happens-before" rule for volatile?

The JMM defines a happens-before relationship between a write to a volatile variable and any subsequent read of that same variable.

Formal Rule:

A write to a volatile field happens-before every subsequent read of that same volatile field.

Consequences:

  • All writes that happened before the volatile write are also visible to the reading thread.
  • All reads that happen after the volatile read will also see those writes.

Example:

private volatile boolean ready; private int data; // Thread A data = 42; // Normal write ready = true; // Volatile write // Thread B if (ready) { // Volatile read int x = data; // Guaranteed to see 42! }

Because ready = true happens-before if (ready), and data = 42 happens-before ready = true (program order), data = 42 also happens-before if (ready). Thread B is guaranteed to see data = 42.

Section 4.2: Publication and Escape

Publication is making an object available to other threads. Escape is when an object is published before it's fully constructed.

Subsection 4.2.1: What is "Publication"?

Publishing an object means making its reference available to code outside its current scope.

Methods of Publication:

  • Storing the reference in a public static field.
  • Returning the reference from a method.
  • Passing the reference as an argument to another method that stores it.
  • Adding the object to a collection that is accessible to other threads.
  • Safe Publication: Publishing an object in a way that ensures it is fully constructed and visible to other threads.
  • Unsafe Publication: Publishing an object without proper synchronization.
4 min read publication safe-publication

Subsection 4.2.2: What is "Escape"?

Escape occurs when an object reference is published before the object is fully constructed. This allows other threads to see a partially constructed object.

Common Escape Scenarios:

Scenario 1: Publishing this in the constructor

public class EscapeExample { private final int value; public EscapeExample() { new Thread(() -> System.out.println(value)).start(); // 'this' escapes! this.value = 42; } }

The thread may see value = 0 (default) if it runs before this.value = 42.

Scenario 2: Passing this to another method

public class EscapeExample { public EscapeExample() { DangerousClass.register(this); // 'this' escapes! // ... rest of constructor } }

Scenario 3: Inner class holding a reference

public class EscapeExample { private final int value; public EscapeExample() { this.value = 42; new Inner(); // Inner class has reference to outer 'this' } private class Inner { Inner() { System.out.println(EscapeExample.this.value); // Safe? Not if the constructor is called before 'value' is assigned! } } }
5 min read escape this constructor

Subsection 4.2.3: The "Doubt Clarifier" – Why is escape dangerous?

Because it violates the JMM's initialization safety. The JMM guarantees that final fields are visible after the constructor completes. But if the object escapes before the constructor completes, there is no guarantee.

Consequences:

  • Other threads may see default values (0, null, false).
  • Other threads may see inconsistent values (some final fields assigned, others not).
  • The object may be in an invalid state (invariant broken).
3 min read escape danger initialization-safety

Subsection 4.2.4: Preventing Escape – The "Dangerous Publication" Patterns

Dangerous Pattern 1: Publishing from a static initializer

public class Dangerous { public static final Object shared = new Object(); // Safe! }

This is actually safe because static initializers are thread-safe (the JVM guarantees it).

Dangerous Pattern 2: Publishing from a non-synchronized method

private Object shared; public void publish(Object obj) { this.shared = obj; // Unsafe! No visibility guarantee. }

Fix: Use volatile:

private volatile Object shared;

Dangerous Pattern 3: Publishing via a HashMap without synchronization

private Map<String, Object> map = new HashMap<>(); public void publish(String key, Object obj) { map.put(key, obj); // Unsafe! HashMap is not thread-safe. }

Fix: Use ConcurrentHashMap.

Section 4.3: Thread Confinement – The "Don't Share" Strategy

Thread confinement is the simplest way to achieve thread safety: don't share mutable objects across threads.

Subsection 4.3.1: Stack Confinement

Local variables are inherently thread-safe because each thread has its own stack.

Example:

public int add(int a, int b) { int result = a + b; // Stack-confined. Safe. return result; }
The "Doubt Clarifier" – Are local variables always safe?
Yes, as long as the reference does not escape. If you store a local object in a static field, it escapes and is no longer confined.
private static Object escaped; public void method() { Object obj = new Object(); // Stack-confined escaped = obj; // Escapes! Now shared. }
3 min read stack-confinement local-variables

Subsection 4.3.2: ThreadLocal Confinement

We covered ThreadLocal in Chapter 3. It provides a way to store values that are local to each thread.

Use Case: Database Connections

public class ConnectionManager { private static ThreadLocal<Connection> connectionHolder = ThreadLocal.withInitial(() -> DriverManager.getConnection("jdbc:mysql://localhost:3306/mydb") ); public static Connection getConnection() { return connectionHolder.get(); } }

Each thread gets its own connection. No synchronization needed.

The "Doubt Clarifier" – Is ThreadLocal the same as a local variable?
No. A local variable is confined to a single method call. ThreadLocal is confined to a thread across multiple method calls. It persists for the lifetime of the thread.
4 min read ThreadLocal confinement connection

Subsection 4.3.3: Ad-Hoc Thread Confinement

Ad-hoc confinement is when a thread owns an object but doesn't explicitly enforce it (e.g., by convention).

Example: A thread creates an object and passes it to other methods within the same thread, but never to other threads.

public void run() { List<String> list = new ArrayList<>(); // Thread-confined by convention processList(list); // Safe if processList() is only called from this thread }
The "Doubt Clarifier" – Is ad-hoc confinement reliable?
No. It relies on developer discipline and documentation. There is no compiler enforcement. It's better to use ThreadLocal or explicit synchronization.

Subsection 4.3.4: The "Doubt Clarifier" – When should I use thread confinement vs. synchronization?

Rule of thumb: If you can confine an object to a single thread, do it. It's simpler and faster.

Section 4.4: Immutability – The Ultimate Thread Safety

We covered the basics in Chapter 3. Now we go deeper into practical implementation.

Subsection 4.4.1: Building an Immutable Class – Step by Step

Step 1: Make the class final (prevent subclassing).

public final class ImmutablePerson { // ... }

Step 2: Make all fields final (set in constructor).

private final String name; private final int age;

Step 3: Make all fields private (encapsulation).

private final Date birthDate;

Step 4: No setters.

// No setter methods!

Step 5: Defensive copy for mutable fields (input and output).

public ImmutablePerson(Date birthDate) { this.birthDate = new Date(birthDate.getTime()); // Defensive copy on input } public Date getBirthDate() { return new Date(birthDate.getTime()); // Defensive copy on output }

Step 6: Ensure the constructor does not leak this.

// No starting threads or passing 'this' to other classes in the constructor.

Subsection 4.4.2: The "Doubt Clarifier" – Are final fields always safe?

Yes, but only if the object is safely published. If you publish an immutable object unsafely, the reference may be stale, even if the fields are final.

Example:

private ImmutablePerson person; // Not volatile! public void setPerson(ImmutablePerson p) { this.person = p; // Unsafe publication! }

Thread B may see null or a stale reference. Even immutable objects must be safely published.

3 min read final safe-publication

Subsection 4.4.3: The "Doubt Clarifier" – What is the difference between immutability and final fields?

  • Immutability: The object's state cannot change after construction.
  • final fields: A field that cannot be reassigned after construction. It's a building block of immutability.

An object can have final fields but still be mutable if those fields refer to mutable objects.

public final class MutablePerson { private final Date birthDate; // final, but Date is mutable! public MutablePerson(Date birthDate) { this.birthDate = birthDate; } public Date getBirthDate() { return birthDate; // BAD! Caller can modify the Date. } }

Fix: Use LocalDate (immutable) or defensive copy.

4 min read immutability final mutable-fields

Subsection 4.4.4: The "Doubt Clarifier" – Are all immutable objects thread-safe?

Yes, trivially. No synchronization is needed because no thread can modify the object. All threads see the same state (assuming safe publication).

Examples of Immutable Classes in the JDK:

  • String
  • Integer, Long, Double (all primitive wrappers)
  • LocalDate, LocalDateTime
  • BigDecimal, BigInteger
  • java.util.Collections.unmodifiableList() (read-only view)
3 min read immutability thread-safe examples

Subsection 4.4.5: The "Doubt Clarifier" – What about StringBuilder vs. StringBuffer?

  • StringBuilder is mutable and not thread-safe.
  • StringBuffer is mutable and thread-safe (all methods are synchronized).
  • String is immutable and thread-safe.
Use StringBuilder for single-threaded code (faster). Use StringBuffer for multi-threaded code (or better, use String if you don't need mutation).

Safe publication is ensuring that an object is fully constructed and visible to other threads.

Subsection 4.5.2: The "Doubt Clarifier" – Why does static initialization work?

The JVM guarantees that static initializers are executed in a thread-safe manner. When the class is loaded, the static initializer runs once, and the result is visible to all threads.

Example:

public class Configuration { public static final Config CONFIG = loadConfig(); // Safe! }
2 min read static-initialization thread-safe

Subsection 4.5.3: The "Doubt Clarifier" – Why does volatile work for safe publication?

When a thread writes to a volatile field, all writes that happened before that volatile write are also flushed to main memory. When another thread reads the volatile field, it sees all those writes.

Example:

private volatile MyObject obj; public void publish(MyObject o) { obj = o; // Volatile write; all previous writes are visible } public MyObject get() { return obj; // Volatile read; sees all previous writes }
3 min read volatile safe-publication

Subsection 4.5.4: The "Doubt Clarifier" – What is the "final" safe publication guarantee?

The JMM guarantees that final fields are visible to all threads after the constructor completes, without synchronization. This is called "initialization safety."

Example:

public class Immutable { private final int value; public Immutable(int value) { this.value = value; } }

If Thread A creates an Immutable and publishes it (e.g., via a volatile reference), Thread B is guaranteed to see the value correctly.

The "Doubt Clarifier" – Does this apply to non-final fields?
No. Non-final fields are not guaranteed to be visible without synchronization. Always use final for fields that are set in the constructor.
4 min read final initialization-safety JMM

Subsection 4.5.5: The "Doubt Clarifier" – What is the "null" publication problem?

If a reference is not safely published, threads may see null even after the object has been set.

Example:

private Object obj; // Not volatile public void set(Object o) { obj = o; // Write } public Object get() { return obj; // May return null! }

Thread A calls set(new Object()). Thread B calls get() and may see null because the write to obj is not visible.

Fix: Make obj volatile or synchronize the setter and getter.

3 min read null publication visibility

Subsection 4.5.6: The "Doubt Clarifier" – What is the "partially constructed object" problem?

When an object is published unsafely, a thread may see a reference to the object but with some fields not yet initialized.

Example (Double-Checked Locking broken):

private static MyObject instance; public static MyObject getInstance() { if (instance == null) { synchronized (MyObject.class) { if (instance == null) { instance = new MyObject(); // May be reordered! } } } return instance; }

The instance = new MyObject() can be reordered so that the reference is assigned before the constructor completes. Thread B sees instance != null and uses a partially constructed object.

Fix: Make instance volatile.
