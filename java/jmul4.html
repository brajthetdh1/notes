Section 3.1: What is Thread Safety? – The Formal Definition

Let's start with an absolutely precise definition, then break it down word by word.

Subsection 3.1.1: The Definitive Definition

A class is thread-safe if it behaves correctly when accessed from multiple threads, regardless of the scheduling or interleaving of the execution of those threads, and with no additional synchronization or other coordination on the part of the calling code.

Let's dissect this:

PhraseMeaning
"behaves correctly"The class maintains its invariants (e.g., a BankAccount never has a negative balance; a Counter never loses increments).
"regardless of scheduling"No matter how the OS scheduler interleaves thread instructions, the invariants hold.
"with no additional synchronization"The caller doesn't need to wrap every method call in synchronized. The class protects itself.
The "Doubt Clarifier" – What is an invariant?
An invariant is a condition that must always be true for an object to be in a valid state.

Example: For a Counter class:
public class Counter { private int count = 0; // Invariant: count >= 0 always public void increment() { count++; } public int get() { return count; } }
The invariant is count >= 0. In a single-threaded environment, this always holds. In a multi-threaded environment without synchronization, the invariant can break (e.g., count might become negative due to race conditions, or you might lose increments).

Subsection 3.1.2: The Three Pillars of Thread Safety

Thread safety rests on three fundamental properties. You must understand all three:

PillarDefinitionExample of Failure
AtomicityOperations appear to happen instantaneously; no other thread sees an intermediate state.count++ (read-modify-write) is not atomic.
VisibilityChanges made by one thread are guaranteed to be seen by other threads.Without volatile, a thread may never see a value written by another thread.
OrderingInstructions are not reordered in ways that violate program semantics.Without synchronized, the JVM/CPU can reorder ready = true before config = loadConfig().
The "Doubt Clarifier" – Are these three properties independent?
Yes and no.

  • synchronized provides all three (atomicity, visibility, ordering) for the critical section.
  • volatile provides visibility and ordering, but not atomicity for compound actions.
  • AtomicInteger provides atomicity and visibility, but ordering is handled by the CAS (Compare-And-Swap) hardware instruction.
You must choose the right tool for the right problem.

Subsection 3.1.3: Thread-Safe Classes – Examples

Thread-Safe (Built-in):

  • java.util.concurrent.ConcurrentHashMap
  • java.util.concurrent.CopyOnWriteArrayList
  • java.util.concurrent.atomic.AtomicInteger
  • java.lang.String (immutable)
  • java.lang.Integer (immutable)

Not Thread-Safe:

  • java.util.HashMap
  • java.util.ArrayList
  • java.lang.StringBuilder
  • java.text.SimpleDateFormat (not thread-safe; use ThreadLocal or DateTimeFormatter)
The "Doubt Clarifier" – Why is SimpleDateFormat not thread-safe?
SimpleDateFormat maintains internal state (like a calendar) that is mutated during formatting and parsing. If multiple threads call format() simultaneously, they corrupt each other's state. Use DateTimeFormatter (Java 8+), which is immutable and thread-safe.

Section 3.2: Atomicity – The First Pillar

Atomicity is about operations that appear indivisible. Let's dive deep.

Subsection 3.2.1: Atomic Operations – What the JVM Guarantees

The JVM guarantees that the following operations are atomic:

  • Reads and writes to volatile variables (including long and double).
  • Reads and writes to all primitive types except long and double (on 32-bit JVMs, long/double are not atomic unless volatile).
  • Reads and writes to reference variables (the reference itself, not the object).
  • All operations in a synchronized block (the block as a whole is atomic).
The "Doubt Clarifier" – What about x = y? Is that atomic?
If x and y are int (32-bit), the read of y and the write to x are each atomic individually, but the combination (read y, write x) is not atomic. Another thread could change y between the read and the write.
5 min read atomicity JVM

Subsection 3.2.2: The "Check-Then-Act" Race Condition

This is the most common race condition in Java.

Example: Lazy Initialization (Broken)

public class LazySingleton { private static ExpensiveObject instance = null; public static ExpensiveObject getInstance() { if (instance == null) { // CHECK instance = new ExpensiveObject(); // ACT } return instance; } }

Why it's broken:

  • Thread A checks instance == null (true), pauses just before creating the object.
  • Thread B checks instance == null (true), creates the object, returns it.
  • Thread A resumes, creates a second object, overwriting Thread B's work.

This is a check-then-act race. It's not just about performance (creating two objects); it's about correctness (if the object has side effects or you need exactly one instance).

The Fix:

public static synchronized ExpensiveObject getInstance() { if (instance == null) { instance = new ExpensiveObject(); } return instance; }

Subsection 3.2.3: The "Read-Modify-Write" Race Condition

This is the classic count++ problem.

Example: Counter (Broken)

public class Counter { private int count = 0; public void increment() { count++; // NOT atomic } public int get() { return count; // NOT atomic (though read is atomic, it may see stale value) } }

The Interleaving (100% sure to lose increments):

  • Thread A reads count (0).
  • Thread B reads count (0).
  • Thread A adds 1 (1) and writes back.
  • Thread B adds 1 (1) and writes back.

Result: count = 1. We lost an increment.

The Fix (Option 1 – synchronized):

public class Counter { private int count = 0; public synchronized void increment() { count++; } public synchronized int get() { return count; } }

The Fix (Option 2 – AtomicInteger):

import java.util.concurrent.atomic.AtomicInteger; public class Counter { private AtomicInteger count = new AtomicInteger(0); public void increment() { count.incrementAndGet(); // Atomic CAS operation } public int get() { return count.get(); // Volatile read } }
The "Doubt Clarifier" – Which fix is better?
AspectsynchronizedAtomicInteger
PerformanceHigh contention -> slowLow to moderate contention -> fast
SimplicityEasy to understandSlightly more complex (new API)
ScalabilityPoor (all threads block)Excellent (no blocking, CAS loops)
Use caseComplex operations (multiple variables)Simple counters or single-variable updates
Rule of thumb: Use AtomicInteger for counters, flags, and simple accumulators. Use synchronized or ReentrantLock for complex operations that involve multiple variables.

Subsection 3.2.4: The "Put-If-Absent" Race Condition

Example: Cache (Broken)

public class Cache { private Map<String, Object> map = new HashMap<>(); public Object getOrCompute(String key) { if (!map.containsKey(key)) { // CHECK Object value = compute(key); // EXPENSIVE map.put(key, value); // ACT } return map.get(key); } }

Why it's broken:

  • Thread A checks !map.containsKey("x") (true), pauses before computing.
  • Thread B checks !map.containsKey("x") (true), computes the value, and inserts it.
  • Thread A computes the value again and overwrites Thread B's work.

The Fix (Option 1 – synchronized):

public synchronized Object getOrCompute(String key) { // ... same code }

The Fix (Option 2 – ConcurrentHashMap's atomic methods):

private ConcurrentHashMap<String, Object> map = new ConcurrentHashMap<>(); public Object getOrCompute(String key) { return map.computeIfAbsent(key, this::compute); // Atomic! }

computeIfAbsent() ensures that the computation happens at most once per key, even under high concurrency.

6 min read race-condition put-if-absent

Subsection 3.2.5: The "Doubt Clarifier" – Is synchronized always enough for atomicity?

Yes, synchronized provides atomicity for the entire critical section. However, you must ensure that all access to the shared state is synchronized.

Counterexample (Broken):

public class BrokenCounter { private int count = 0; public synchronized void increment() { count++; // Synchronized } public int get() { return count; // NOT synchronized! BAD! } }

Thread A calls increment() (sync), writes count = 5. Thread B calls get() (no sync) and may see 0 due to visibility issues. All access must be synchronized, not just writes.

The Fix:

public synchronized int get() { return count; }

Section 3.3: The synchronized Keyword – Deep Internal Mechanics

synchronized is the most fundamental concurrency control mechanism in Java. Let's understand it completely.

Subsection 3.3.1: The Monitor – Every Object Has One

Every Java object has an implicit monitor (also called an intrinsic lock). A thread can acquire the monitor by entering a synchronized method or block on that object. Only one thread can hold the monitor at a time.

Visualization:

Object lock = new Object(); +-------------------+ | Object Header | <- Contains Mark Word (lock state) | Monitor (Lock) | <- Intrinsic lock +-------------------+
The "Doubt Clarifier" – Where is the lock stored?
In the object header (specifically, the "Mark Word"). The JVM stores lock information directly in the object's memory layout. This is why every object can be a lock—no separate lock object is allocated.
5 min read synchronized monitor

Subsection 3.3.2: synchronized Methods vs. Blocks

Synchronized Instance Method:

public synchronized void method() { // Lock acquired on 'this' }

Equivalent to:

public void method() { synchronized (this) { // Lock acquired on 'this' } }

Synchronized Static Method:

public static synchronized void staticMethod() { // Lock acquired on 'Class.class' }

Equivalent to:

public static void staticMethod() { synchronized (MyClass.class) { // Lock acquired on 'MyClass.class' } }

Synchronized Block (Custom Object):

private final Object lock = new Object(); public void method() { synchronized (lock) { // Lock acquired on 'lock' object } }
The "Doubt Clarifier" – Why use a custom lock object instead of this?
  • Encapsulation: The lock is private; no external code can lock on your object and cause contention or deadlocks.
  • Fine-grained locking: You can have multiple locks for different parts of your object.
The "Doubt Clarifier" – Can I synchronize on a null object?
No. synchronized (null) throws NullPointerException.
6 min read synchronized methods blocks

Subsection 3.3.3: Lock Granularity – Coarse vs. Fine

Coarse-Grained Locking (Bad for Performance):

public synchronized void transfer(BankAccount target, int amount) { this.balance -= amount; // Only this.balance needs locking target.balance += amount; // Only target.balance needs locking }

This locks the entire this object, preventing other unrelated operations on the same account.

Fine-Grained Locking (Better):

public void transfer(BankAccount target, int amount) { synchronized (this) { this.balance -= amount; } synchronized (target) { target.balance += amount; } }

But this introduces a deadlock risk (see Chapter 5). The best solution is to use ReentrantLock with tryLock().

The "Doubt Clarifier" – What is lock striping?
Lock striping is using multiple locks to protect different parts of a data structure. For example, ConcurrentHashMap uses 16 locks (by default) to protect different segments of the map. Multiple threads can operate on different segments concurrently.
5 min read lock-granularity striping

Subsection 3.3.4: The Lock Reentrancy – What It Means

synchronized locks are reentrant. If a thread already holds a lock, it can re-enter the same lock without blocking.

Example:

public class ReentrantExample { public synchronized void outer() { inner(); // Thread already holds the lock, so it can enter inner() } public synchronized void inner() { // Do something } }

If locks were not reentrant, outer() calling inner() would deadlock (the thread would wait for its own lock). Reentrancy prevents this.

The "Doubt Clarifier" – How does the JVM track reentrancy?
Each lock has a counter. When a thread acquires the lock, the counter increments. When it releases the lock, the counter decrements. Only when the counter reaches 0 is the lock released for other threads.
4 min read reentrancy lock

Subsection 3.3.5: Bias Locking, Lightweight Locking, Heavyweight Locking

The JVM uses three levels of locking optimization, depending on contention:

LevelDescriptionWhen Used
Biased LockingThe lock "biases" toward the first thread that acquires it. The thread can enter the lock with almost zero overhead (no atomic operations).When a lock is always acquired by the same thread (e.g., single-threaded code, but the object is still synchronized).
Lightweight LockingUses CAS operations in the object header to acquire the lock without involving the OS.When contention is low (brief contention).
Heavyweight LockingUses the OS mutex. Involves context switching and blocking.When contention is high (long waits).
The "Doubt Clarifier" – Can I disable biased locking?
Yes, using JVM flags:
-XX:-UseBiasedLocking # Disable biased locking (helps reduce latency in some cases) -XX:+UseHeavyMonitors # Force heavyweight locking (rarely used)
In Java 15+, biased locking is deprecated and disabled by default in Java 17+.
6 min read locking JVM-optimization

Subsection 3.3.6: The "Doubt Clarifier" – Does synchronized block on String literals?

Yes, but don't do it!

synchronized ("LOCK") { // Bad! // ... }

String literals are interned by the JVM. "LOCK" is the same object across your entire application. Locking on a string literal is global locking—it will cause contention across unrelated parts of your code. Always use a dedicated lock object.

Section 3.4: The volatile Keyword – Complete Semantics

volatile is often misunderstood. Let's clarify it once and for all.

Subsection 3.4.1: What volatile Guarantees

  • Visibility: Every write to a volatile variable is immediately flushed to main memory. Every read reads from main memory. No thread-local caching.
  • Ordering: The JVM and CPU cannot reorder volatile reads/writes with other volatile reads/writes (or with normal reads/writes in a way that violates the JMM).

What volatile Does NOT Guarantee:

  • Atomicity: volatile does not make count++ atomic. It only makes the individual read and individual write atomic.
5 min read volatile visibility ordering

Subsection 3.4.2: When to Use volatile

Use Case 1: Flags (State Variables)

private volatile boolean running = true; public void run() { while (running) { // Do work } } public void stop() { running = false; // Write to volatile; immediately visible to run() thread }

Use Case 2: Configuration Reloading

private volatile Config config = loadConfig(); public void reloadConfig() { config = loadConfig(); // New config published safely } public void useConfig() { config.doSomething(); // Always sees latest config }

Use Case 3: Lightweight Status Tracking

private volatile int status; public void setStatus(int s) { status = s; } public int getStatus() { return status; }
5 min read volatile use-cases

Subsection 3.4.3: When NOT to Use volatile

Case 1: Compound Actions

private volatile int count = 0; public void increment() { count++; // BAD! Not atomic! }

Case 2: Accumulators

private volatile int total = 0; public void add(int value) { total += value; // BAD! Not atomic! }

Case 3: Dependencies Between Variables

private volatile boolean ready; private Config config; public void publish() { config = loadConfig(); // Normal write (could be reordered!) ready = true; // Volatile write } public void consume() { if (ready) { config.doSomething(); // Could see config before it's ready! } }

The JVM can reorder config = loadConfig() and ready = true, so the volatile write doesn't guarantee the normal write is visible. This is why you need synchronized for multi-variable invariants.

6 min read volatile pitfalls

Subsection 3.4.4: The volatile and long/double Special Case

As mentioned earlier, without volatile, long and double writes are not atomic on 32-bit JVMs. With volatile, they are atomic.

private volatile long timestamp = 0; // Atomic read/write on all JVMs
3 min read volatile long double

Subsection 3.4.5: The "Doubt Clarifier" – Why is volatile cheaper than synchronized?

volatile does not acquire a lock. It only adds memory barriers (fences) to ensure visibility and ordering. There is no OS mutex, no context switching, no blocking. For simple flags and state variables, volatile is much faster than synchronized.

3 min read volatile performance

Subsection 3.4.6: The "Doubt Clarifier" – Is AtomicBoolean better than volatile boolean?

AtomicBoolean provides compareAndSet(), getAndSet(), and other atomic operations. If you only need simple get/set, volatile is sufficient. If you need CAS (e.g., "set to true if it's false"), AtomicBoolean is necessary.

Section 3.5: The final Keyword in Concurrency

final is often overlooked in concurrency, but it's a powerful tool for thread safety.

Subsection 3.5.1: Initialization Safety

The JMM guarantees that a final field's value is visible to all threads after the constructor completes, even without synchronization.

Example:

public class ImmutablePerson { private final String name; private final int age; public ImmutablePerson(String name, int age) { this.name = name; this.age = age; } public String getName() { return name; } public int getAge() { return age; } }

If Thread A creates an ImmutablePerson and publishes it (e.g., stores it in a static field), Thread B will always see the correct name and age, even without volatile or synchronized. This is initialization safety.

The "Doubt Clarifier" – Does final guarantee visibility of non-final fields?
No! Only final fields are guaranteed. If you have a non-final field in an otherwise immutable object, it may not be visible to other threads. Always make fields final if they are set in the constructor and never changed.
6 min read final initialization-safety

Subsection 3.5.2: The "Safe Publication" Problem

Even with final fields, the object itself must be safely published. If you publish the object incorrectly, the other thread might see the final fields correctly (due to JMM guarantees) but the reference might be null or a stale reference.

Safe Publication Options:

  • Static initialization: public static final ImmutablePerson person = new ImmutablePerson(...)
  • Volatile reference: private volatile ImmutablePerson person;
  • AtomicReference: private AtomicReference<ImmutablePerson> person;
  • Proper synchronization: synchronized block when publishing.
The "Doubt Clarifier" – What is the "unsafe publication" problem?
// BAD! public class UnsafePublishing { private ImmutablePerson person; public void setPerson(ImmutablePerson p) { this.person = p; // No synchronization! } public ImmutablePerson getPerson() { return person; // No synchronization! } }
Thread A calls setPerson() with a new ImmutablePerson. Thread B calls getPerson() and may see null or a partially constructed object. Even though the ImmutablePerson has final fields, the reference to it is not safely published.

Fix:
private volatile ImmutablePerson person; // Volatile guarantees visibility
6 min read safe-publication final

Subsection 3.5.3: The "Doubt Clarifier" – Can I use final with volatile?

No! final and volatile are mutually exclusive in Java. final means the field is immutable; volatile means the field can change (but changes are visible). You can't have both. If you have a mutable reference that points to an immutable object, the reference itself must be volatile (or use AtomicReference) for safe publication.

Section 3.6: Thread Confinement and ThreadLocal

Sometimes the safest approach is to avoid sharing altogether.

Subsection 3.6.1: What is Thread Confinement?

Thread confinement means that an object is only accessed by a single thread. If no other thread can touch it, there are no race conditions, visibility issues, or synchronization needs.

Types of Thread Confinement:

  • Stack Confinement: Local variables in a method. Each thread has its own stack, so local variables are inherently thread-confined.
    public void method() { int local = 0; // Safe: only current thread can see it // ... }
  • ThreadLocal Confinement: Using ThreadLocal to store values per thread.
5 min read thread-confinement ThreadLocal

Subsection 3.6.2: The ThreadLocal Class

Signature: public class ThreadLocal<T>

How it works: Each thread has its own ThreadLocalMap. When you call set(), the value is stored in the current thread's map. When you call get(), the value is retrieved from the current thread's map.

Usage:

private static ThreadLocal<DateFormat> dateFormat = ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd") ); public String formatDate(Date date) { return dateFormat.get().format(date); // Each thread gets its own SimpleDateFormat }
The "Doubt Clarifier" – Why is ThreadLocal useful for SimpleDateFormat?
Because SimpleDateFormat is not thread-safe. By using ThreadLocal, each thread has its own instance, eliminating the need for synchronization.
5 min read ThreadLocal SimpleDateFormat

Subsection 3.6.3: ThreadLocal – The Memory Leak Problem

ThreadLocal can cause memory leaks in web applications. If a thread (from a thread pool) is reused, the ThreadLocal value from a previous request may still be attached to the thread. If you don't clean it up, the value stays in memory until the thread is destroyed (which might be never for long-lived thread pools).

The Fix: Always call ThreadLocal.remove() after the request is complete.

try { dateFormat.get(); // Use ThreadLocal } finally { dateFormat.remove(); // Clean up! }
The "Doubt Clarifier" – Why does ThreadLocal cause memory leaks?
The ThreadLocalMap stores the value in an Entry that uses the ThreadLocal object as a weak key. However, the value is strongly referenced. If the ThreadLocal is garbage collected, the entry is cleaned. But if you keep the ThreadLocal reference alive, the value remains. In web apps, the thread's ThreadLocalMap can grow indefinitely if you don't call remove().
5 min read ThreadLocal memory-leak

Subsection 3.6.4: InheritableThreadLocal – Passing Values to Child Threads

InheritableThreadLocal passes its value from the parent thread to any child threads created.

Example:

private static InheritableThreadLocal<String> context = new InheritableThreadLocal<>(); public static void main(String[] args) { context.set("Parent"); new Thread(() -> { System.out.println(context.get()); // Prints "Parent" }).start(); }
The "Doubt Clarifier" – When should I use InheritableThreadLocal?
Rarely. It can lead to hard-to-debug state leakage. Use it only when you need to propagate context (like a user ID) to child threads. In Java 21+, ScopedValue is a better alternative.

Section 3.7: Immutability – The Ultimate Thread Safety

If an object's state cannot be changed, it is automatically thread-safe. No synchronization is needed.

Subsection 3.7.1: The Rules of Immutability

An object is immutable if:

  • All fields are final. (Or effectively final—set in constructor and never changed.)
  • The object is not published before construction is complete. (No escaping this reference.)
  • Any mutable fields are not exposed to the caller. (If you have a Date field, return a copy, not the reference.)

Example:

public final class ImmutablePerson { private final String name; private final LocalDate birthDate; // LocalDate is immutable public ImmutablePerson(String name, LocalDate birthDate) { this.name = name; this.birthDate = birthDate; } public String getName() { return name; } public LocalDate getBirthDate() { return birthDate; } // Safe }

If you have a mutable field:

private final Date birthDate; // Date is mutable public Date getBirthDate() { return new Date(birthDate.getTime()); // Defensive copy! }
6 min read immutability defensive-copy

Subsection 3.7.2: The "Doubt Clarifier" – Are all final objects immutable?

No. A final reference to a mutable object means the reference cannot change, but the object's internal state can change.

private final List<String> list = new ArrayList<>(); // The reference is final public void add(String s) { list.add(s); // Mutating the list! The object is NOT immutable. }

To make it immutable, use Collections.unmodifiableList() or List.copyOf().

4 min read immutability final

Subsection 3.7.3: The Benefits of Immutability

  • No synchronization needed. Threads can read freely.
  • No race conditions. No writes = no races.
  • Safe to share. Multiple threads can access the same instance.
  • Caching-friendly. Immutable objects can be safely cached.
The "Doubt Clarifier" – What is the performance cost of immutability?
Immutable objects often require copying (e.g., creating a new list when adding an element). This can be expensive for large objects. However, for small to medium objects, the performance cost is often outweighed by the elimination of synchronization.

Section 3.8: Safe Publication – The Final Piece

Even if an object is thread-safe (e.g., immutable), you must publish it safely.

Subsection 3.8.2: The "Doubt Clarifier" – What if I publish an object in a constructor?

DANGER! Publishing this in a constructor can let other threads see a partially constructed object.

public class BadPublication { private final int value; public BadPublication() { this.value = 42; new Thread(() -> System.out.println(value)).start(); // Publishing this! } }

The thread may see value = 0 (default) if it reads before the constructor finishes.

The Fix: Never start threads or publish this inside a constructor. Use a factory method or start() method after construction.
