Q1: What is System Design?

Fundamentals
What is system design and why is it important?

System design is the process of defining the architecture, components, modules, interfaces, and data flow of a system to meet specific requirements. It translates business requirements into a technical blueprint.

Why it's important:

  • Scalability: Ensures the system can handle growth in users, data, and traffic.
  • Reliability: Design for fault tolerance and high availability.
  • Performance: Optimize for low latency and high throughput.
  • Maintainability: Makes the system easier to understand, modify, and extend.
  • Cost efficiency: Balances performance with infrastructure costs.
  • Team alignment: Provides a shared understanding for development teams.

Key activities:

  • Requirements gathering and analysis
  • High-level architecture design
  • Component and module design
  • Data modeling and storage decisions
  • API and interface design
  • Performance and scalability planning

Q3: Key Principles of System Design

Fundamentals
What are the key principles of system design?
  • Scalability: Ability to handle growth in users, data, and traffic.
  • Availability: System uptime and ability to serve requests.
  • Reliability: System continues to function correctly.
  • Performance: Low latency, high throughput.
  • Consistency: Data is the same across all nodes.
  • Maintainability: Easy to modify and extend.
  • Security: Protection against threats and vulnerabilities.
  • Cost-effectiveness: Optimal use of resources.
  • Simplicity: Avoid unnecessary complexity.
  • Separation of concerns: Divide into independent modules.
  • Fault tolerance: Graceful handling of failures.
  • Observability: Monitoring, logging, and tracing.

Trade-offs: Often need to balance these principles (e.g., consistency vs availability).

Q4: Scalability

Fundamentals
What is scalability and how do you achieve it?

Scalability is the ability of a system to handle increased load by adding resources (hardware, instances, or nodes) while maintaining acceptable performance.

Types of scalability:

  • Vertical scaling: Adding more power to existing machine (CPU, RAM).
  • Horizontal scaling: Adding more machines/instances.

How to achieve scalability:

  • Database scaling: Sharding, replication, caching.
  • Load balancing: Distribute traffic across multiple servers.
  • Caching: Store frequently accessed data in memory (Redis, Memcached).
  • Asynchronous processing: Use message queues (Kafka, RabbitMQ).
  • Stateless design: Each request can be handled by any server.
  • Microservices: Decompose application into smaller, scalable services.
  • CDN: Serve static content from edge locations.

Key metric: Scalability is measured by how performance degrades as load increases.

Q8: CAP Theorem

Fundamentals
What is the CAP Theorem? Explain its components.

The CAP Theorem (Brewer's Theorem) states that a distributed data store can provide at most two out of three guarantees:

  • C – Consistency: All nodes see the same data at the same time. A read returns the most recent write.
  • A – Availability: Every request receives a response (success or failure). The system is always operational.
  • P – Partition Tolerance: The system continues to function despite network partitions (messages lost or delayed between nodes).

Trade-offs:

  • CP (Consistency + Partition Tolerance): Sacrifice availability during network partitions (e.g., HBase, MongoDB).
  • AP (Availability + Partition Tolerance): Sacrifice consistency during partitions (e.g., Cassandra, DynamoDB).
  • CA (Consistency + Availability): Sacrifice partition tolerance (not possible in distributed systems).

Real-world choices:

  • Banking systems: Prefer CP (consistency over availability).
  • Social media: Prefer AP (availability over consistency).

Q10: Latency and Throughput

Fundamentals
What is latency and throughput? How are they related?
  • Latency: The time it takes for a single request to be processed. Measured in milliseconds or seconds. Lower latency is better.
  • Throughput: The number of requests processed per unit of time. Measured in requests per second (RPS) or transactions per second (TPS). Higher throughput is better.

Relationship:

  • Latency and throughput are inversely related in many cases.
  • Increasing throughput often increases latency (queueing delays).
  • Optimizing one can sometimes hurt the other.

Little's Law: Throughput = (Concurrency) / (Latency)

Example:

  • A system with 100ms latency and 10 concurrent requests has throughput = 10 / 0.1 = 100 RPS.
  • To improve throughput, you can increase concurrency or reduce latency.

Key trade-off: Optimize for the metric that matters most for your use case.

Q11: Single Responsibility Principle

Principles
What is the Single Responsibility Principle in system design?

The Single Responsibility Principle (SRP) states that every module, class, or function should have one and only one reason to change. It should have a single, well-defined responsibility.

In system design:

  • Each service should have a single, well-defined purpose.
  • Components should be cohesive and focused.
  • Changes to one responsibility shouldn't affect others.

Example:

  • Bad: A monolithic service that handles user auth, payment processing, and notifications.
  • Good: Separate services for Auth, Payments, and Notifications.

Benefits:

  • Easier to maintain and understand
  • Easier to test
  • Easier to scale independently
  • Reduces coupling

Q12: Separation of Concerns

Principles
What is the Separation of Concerns principle?

Separation of Concerns (SoC) is a design principle that advocates dividing a system into distinct sections, each addressing a specific concern or aspect of the system.

Key concepts:

  • Each module handles a specific concern.
  • Cross-cutting concerns (logging, security, etc.) are handled separately.
  • Reduces complexity by isolating different parts.

Examples in system design:

  • Layered architecture: Presentation layer, business logic layer, data access layer.
  • Microservices: Each service handles a specific business capability.
  • MVC pattern: Model (data), View (UI), Controller (logic).

Benefits:

  • Improves maintainability
  • Enables parallel development
  • Makes debugging easier
  • Increases reusability

Q13: DRY Principle

Principles
What is DRY (Don't Repeat Yourself) in system design?

DRY (Don't Repeat Yourself) is a principle that states that every piece of knowledge or logic should have a single, unambiguous representation within a system.

In system design:

  • Avoid duplicating code, configurations, or business logic.
  • Use shared libraries, services, and configurations.
  • Centralize common functionality.

Examples:

  • Bad: Same validation logic in multiple services.
  • Good: A shared validation library or service.
  • Bad: Hard-coded configuration in multiple places.
  • Good: Centralized configuration service.

Benefits:

  • Reduces code size and complexity
  • Easier to maintain and update
  • Reduces bugs caused by inconsistencies
  • Promotes reusability

Note: DRY also applies to data – avoid storing the same data in multiple places without synchronization.

Q14: Law of Demeter

Principles
What is the Principle of Least Knowledge (Law of Demeter)?

The Law of Demeter (or Principle of Least Knowledge) states that an object should have limited knowledge of other objects and should only communicate with its immediate friends.

In practice:

  • Don't chain method calls (a.b.c.d()).
  • Each component should only know about its direct dependencies.
  • Reduce coupling between components.

In system design:

  • Services should only communicate with their immediate dependencies.
  • Avoid cascading calls (Service A calls Service B, which calls Service C).
  • Use APIs and abstractions to hide implementation details.

Example:

  • Bad: order.getCustomer().getAddress().getCity()
  • Good: order.getCustomerCity() – the order handles the chain.

Benefits: Reduces coupling, improves maintainability, and makes testing easier.

Q16: Idempotency

Principles
What is idempotency and why is it important?

Idempotency is the property of an operation that can be applied multiple times without changing the result beyond the first application.

In system design:

  • Idempotent operations produce the same result regardless of how many times they are called.
  • Critical for distributed systems where network failures can cause duplicate requests.

Examples:

  • Idempotent: GET requests, PUT requests (update with same data), DELETE requests
  • Not idempotent: POST requests (creating resources), increment operations

Why it's important:

  • Prevents duplicate processing (e.g., duplicate payments)
  • Allows safe retries after failures
  • Improves system reliability

How to implement:

  • Use idempotency keys (unique request IDs)
  • Check if operation was already performed
  • Design APIs with idempotency in mind

Q20: Microservices Pros & Cons

Principles
What are the advantages and disadvantages of microservices?

Advantages:

  • Independent deployment: Services can be deployed independently.
  • Scalability: Scale individual services based on demand.
  • Technology diversity: Use different technology stacks for different services.
  • Fault isolation: Failure in one service doesn't affect others.
  • Team autonomy: Teams can work independently.
  • Better maintainability: Smaller codebases are easier to understand.
  • Reusability: Services can be reused across applications.

Disadvantages:

  • Increased complexity: More moving parts, network calls.
  • Network latency: Communication overhead between services.
  • Data consistency: Harder to maintain transactions across services.
  • Debugging: Harder to trace requests across services.
  • Operations overhead: Need for service discovery, orchestration, monitoring.
  • Testing: Integration and end-to-end testing is more complex.
  • Configuration management: Managing configurations across services.

Best practice: Start monolithic, evolve to microservices when needed.

Q22: SQL vs NoSQL – When to Use

Data Storage
When would you use a SQL database vs a NoSQL database?

Use SQL when:

  • Data structure is well-defined and doesn't change often.
  • ACID transactions are required (banking, e-commerce).
  • Complex queries and relationships are needed.
  • Integrity and consistency are critical.
  • You need strong schema enforcement.
  • You're building traditional applications (ERP, CRM).

Use NoSQL when:

  • Data structure is flexible or unknown.
  • High scalability and performance are required.
  • You need horizontal scaling across many nodes.
  • Data is unstructured (JSON, documents).
  • You're working with big data or real-time analytics.
  • You need fast read/write operations.
  • CAP theorem trade-off favors availability over consistency.

NoSQL sub-types:

  • Document: MongoDB, CouchDB (JSON documents)
  • Key-Value: Redis, DynamoDB (fast lookups)
  • Column-Family: Cassandra, HBase (large-scale data)
  • Graph: Neo4j, Amazon Neptune (relationships)

Q23: Database Sharding

Data Storage
What is database sharding? When would you use it?

Database sharding is a technique of partitioning data across multiple database instances (shards) based on a shard key. Each shard holds a subset of the data.

When to use sharding:

  • When a single database can't handle the data volume.
  • When write throughput exceeds a single database's capacity.
  • When you need to scale horizontally.
  • When geographical distribution of data is needed.

Sharding strategies:

  • Range-based sharding: Data split by ranges (e.g., user_id 1-1000, 1001-2000).
  • Hash-based sharding: Consistent hashing, distribute uniformly.
  • Directory-based sharding: Lookup service maps keys to shards.
  • Geographical sharding: Data stored based on location.

Challenges:

  • Complex queries across shards
  • Resharding (adding/removing shards)
  • Transaction management across shards

Q24: Database Replication

Data Storage
What is database replication? What are its types?

Database replication is the process of copying data from one database (master) to one or more other databases (replicas) to improve availability, reliability, and performance.

Types of replication:

  • Master-Slave: One master (write), multiple slaves (read). Writes go to master, replicas for reads.
  • Master-Master: Multiple masters can accept writes. Conflict resolution required.
  • Asynchronous: Writes are replicated after commit (higher performance, possible data loss).
  • Synchronous: Writes are replicated before commit (lower performance, guaranteed consistency).

Benefits:

  • High availability: Failover if master fails.
  • Scalability: Read load distributed across replicas.
  • Disaster recovery: Data backed up on replicas.
  • Performance: Reads offloaded from master.

Challenges:

  • Replication lag (async)
  • Conflict resolution (master-master)
  • Increased storage costs

Q26: Distributed Cache

Data Storage
What is a distributed cache? Why is it used?

A distributed cache is a cache that spans multiple servers to provide high performance, scalability, and fault tolerance. It stores frequently accessed data in memory across a cluster of nodes.

Why use it:

  • Performance: Reduce latency by serving data from memory.
  • Scalability: Reduce load on databases.
  • Cost efficiency: Reduce database resources.
  • Geographic distribution: Cache data closer to users.
  • High availability: Data replicated across nodes.

Popular distributed caches:

  • Redis: In-memory data store, supports persistence.
  • Memcached: Simple key-value cache, high performance.
  • Hazelcast: In-memory data grid.
  • Amazon ElastiCache: Managed Redis/Memcached.

Use cases:

  • Database query caching
  • Session storage
  • API response caching
  • Rate limiting counters
  • Distributed locks

Q28: CDN

Data Storage
What is a CDN? How does it work?

A Content Delivery Network (CDN) is a network of geographically distributed servers that cache and deliver content (static and dynamic) to users based on their location.

How it works:

  • Content is stored on origin servers (your infrastructure).
  • CDN caches content at edge locations (PoPs – Points of Presence).
  • Users request content from the nearest edge location.
  • If content is available at edge, it's served immediately (cache hit).
  • If not, the edge fetches from origin (cache miss) and caches it.

Benefits:

  • Low latency: Content served from nearby servers.
  • High availability: Multiple edge locations.
  • Scalability: Handles traffic spikes.
  • Cost reduction: Reduced origin server load.
  • Security: DDoS protection, SSL/TLS.

Use cases:

  • Static assets (images, CSS, JS)
  • Video streaming
  • Software downloads
  • APIs (dynamic content)

Q29: Data Partitioning

Data Storage
What is data partitioning? What are the different strategies?

Data partitioning is the process of dividing a large dataset into smaller, manageable pieces (partitions) distributed across multiple nodes.

Strategies:

  • Range Partitioning: Data split based on value ranges (e.g., dates, IDs).
  • Hash Partitioning: Consistent hashing to distribute data uniformly.
  • List Partitioning: Data assigned to partitions based on a list of values.
  • Composite Partitioning: Combination of multiple strategies.
  • Directory Partitioning: Lookup service maps keys to partitions.
  • Geographical Partitioning: Data based on geographic location.

Considerations:

  • Partition key: Choose carefully to avoid hotspots.
  • Data distribution: Aim for even distribution.
  • Query patterns: Ensure efficient query execution.
  • Rebalancing: Handle when nodes are added/removed.

Benefits: Scalability, performance, fault tolerance.

Q31: REST API

Communication & API
What is REST API? What are its principles?

REST (Representational State Transfer) is an architectural style for designing networked applications. REST APIs use HTTP and are stateless, cacheable, and uniform.

Principles:

  • Stateless: Each request contains all necessary information. No client state stored on server.
  • Client-Server: Separation of concerns between client and server.
  • Cacheable: Responses should explicitly indicate cacheability.
  • Uniform Interface: Consistent API design (URLs, HTTP methods, status codes).
  • Layered System: Client can't tell if it's connected to the end server or an intermediary.
  • Code on Demand (optional): Server can extend client functionality.

HTTP methods:

  • GET: Retrieve resource
  • POST: Create resource
  • PUT: Update/replace resource
  • PATCH: Partial update
  • DELETE: Remove resource

Statelessness: Each request contains all context. No sessions.

Q33: gRPC

Communication & API
What is gRPC and how is it different from REST?

gRPC (gRPC Remote Procedure Call) is a high-performance, open-source RPC framework developed by Google. It uses Protocol Buffers (protobuf) for serialization.

Key features:

  • Protocol Buffers: Binary serialization (smaller, faster than JSON).
  • HTTP/2: Multiplexing, streaming, header compression.
  • Multiple languages: Support for many languages.
  • Streaming: Unary, server-streaming, client-streaming, bidirectional.

REST vs gRPC:

  • REST: Text-based (JSON), HTTP/1.1, client-server, easier to debug.
  • gRPC: Binary (protobuf), HTTP/2, multiple streaming patterns, better performance.

When to use gRPC:

  • Low-latency, high-throughput systems
  • Microservices communication
  • Real-time applications (streaming)
  • Polyglot environments

Q34: GraphQL

Communication & API
What is GraphQL and when would you use it?

GraphQL is a query language and runtime for APIs developed by Facebook. It allows clients to request exactly the data they need.

Key features:

  • Fetch exactly what you need: No over-fetching or under-fetching.
  • Single endpoint: All queries go to one endpoint.
  • Strongly typed: Schema defines available types and operations.
  • Real-time: Subscriptions for live data.
  • Flexible: Clients can aggregate data from multiple sources.

When to use GraphQL:

  • Complex frontends with multiple data needs
  • Mobile apps (bandwidth-sensitive)
  • When you need to aggregate data from multiple sources
  • When you have a well-defined data schema

GraphQL vs REST:

  • REST: Multiple endpoints, can over/under-fetch.
  • GraphQL: Single endpoint, client controls data.

Q36: Message Queue

Communication & API
What is a message queue? When would you use it?

A message queue is a communication mechanism that enables asynchronous communication between services by storing messages until they are processed.

How it works:

  • Producer sends messages to the queue.
  • Consumer retrieves and processes messages.
  • Messages are stored until they're consumed.

When to use:

  • Decouple services (loose coupling)
  • Handle spikes in traffic (buffering)
  • Background processing (email, notifications)
  • Event-driven architectures
  • Reliable communication (guaranteed delivery)
  • Distributed systems

Popular message queues:

  • RabbitMQ: AMQP-based, reliable
  • Apache Kafka: Distributed streaming platform
  • Amazon SQS: Managed queue service
  • ActiveMQ: Open-source, multi-protocol

Q38: Pub-Sub Pattern

Communication & API
What is pub-sub (Publish-Subscribe) pattern?

The Publish-Subscribe (Pub-Sub) pattern is a messaging pattern where publishers send messages to a topic, and subscribers receive messages from topics they are interested in.

Components:

  • Publisher: Sends messages to a topic.
  • Subscriber: Receives messages from a topic.
  • Topic: Logical channel for messages.
  • Broker: Manages topics and message distribution.

Key characteristics:

  • Publishers and subscribers are decoupled.
  • Multiple subscribers can receive the same message.
  • Subscribers receive only messages from topics they subscribe to.
  • Asynchronous communication.

Examples:

  • Event-driven systems: New user registration triggers email, analytics, and notifications.
  • Real-time updates: Stock price updates sent to multiple clients.
  • Social media: New post notifications to followers.

Implementation: Kafka, RabbitMQ (with exchanges), Redis Pub/Sub, AWS SNS.

Q40: Event-Driven Architecture

Communication & API
What is an event-driven architecture?

Event-driven architecture (EDA) is a software architecture pattern where components communicate by producing and responding to events (state changes).

Key components:

  • Event producers: Generate events (services, applications).
  • Event consumers: React to events (other services, applications).
  • Event channel: Transport for events (message queues, streams).
  • Event bus: Central hub for event distribution.

Characteristics:

  • Asynchronous: Events are processed asynchronously.
  • Decoupled: Producers and consumers are independent.

Benefits:

  • Loose coupling
  • Scalability
  • Flexibility
  • Real-time processing

Challenges:

  • Complexity
  • Event ordering

Q42: Cache Eviction Policies

Performance
What are cache eviction policies? Explain LRU, LFU, and FIFO.

Cache eviction policies determine which items to remove from cache when it reaches capacity.

  • LRU (Least Recently Used): Removes the item that hasn't been accessed for the longest time. Most common, good for temporal locality.
  • LFU (Least Frequently Used): Removes the item with the lowest access frequency. Good for items accessed frequently over time.
  • FIFO (First In, First Out): Removes the oldest items regardless of access pattern. Simple but less efficient.

Other policies:

  • MRU (Most Recently Used): Removes the most recently used item.
  • Random: Removes a random item.
  • TTL (Time To Live): Items expire after a fixed time.
// LRU Implementation (simplified)
class LRUCache {
    private LinkedHashMap<Integer, Integer> cache;
    public LRUCache(int capacity) {
        cache = new LinkedHashMap<>(capacity, 0.75f, true) {
            protected boolean removeEldestEntry(Map.Entry eldest) {
                return size() > capacity;
            }
        };
    }
}

Choose based on: Access patterns, cost of cache misses, item size.

Q45: Load Balancing Algorithms

Performance
What are load balancing algorithms? Explain round-robin and least-connections.
  • Round-Robin: Requests are distributed sequentially across servers in a cyclic order. Simple and fair.
  • Least-Connections: Requests are sent to the server with the fewest active connections. Best for long-lived connections.

Other algorithms:

  • Weighted Round-Robin: Servers with higher weight get more requests.
  • Weighted Least-Connections: Combines weights and connections.
  • IP Hash: Consistent hashing based on client IP.
  • Random: Random distribution.
  • Least Response Time: Server with fastest response time.
  • Consistent Hashing: Used in distributed caching.

Round-Robin:

  • Simple, easy to implement
  • Assumes all servers have similar capacity
  • If servers have different capacities, use weighted

Least-Connections:

  • More adaptive to varying load
  • Better for long-lived connections
  • May need to track connection counts

Q46: Rate Limiting

Performance
What is rate limiting and why is it important?

Rate limiting is a technique that controls the amount of traffic a system receives within a certain time period.

Why it's important:

  • Prevent abuse: Protect against DDoS attacks and malicious requests.
  • Fair usage: Ensure all users get a fair share of resources.
  • Cost control: Reduce costs for third-party APIs.
  • System stability: Prevent overload and service degradation.
  • API monetization: Tiered pricing based on usage.

Algorithms:

  • Token Bucket: Tokens added at a fixed rate, consumed per request.
  • Leaky Bucket: Requests queued and processed at a fixed rate.
  • Sliding Window: Count requests in a time window.
  • Fixed Window: Count requests in a fixed time interval.

Implementation:

  • API Gateway (Kong, AWS API Gateway)
  • Middleware (nginx, custom code)
  • Redis for distributed rate limiting

Q47: Circuit Breaker Pattern

Performance
What is a circuit breaker pattern in system design?

The Circuit Breaker pattern prevents a system from repeatedly trying to execute an operation that's likely to fail, allowing the system to fail fast and recover gracefully.

States:

  • Closed: Normal operation. Requests are allowed.
  • Open: Failure threshold exceeded. Requests fail immediately without trying.
  • Half-Open: After a timeout, a limited number of requests are allowed to test if the service has recovered.

Benefits:

  • Prevents cascading failures
  • Reduces load on failing services
  • Allows graceful degradation
  • Enables faster recovery
// Circuit Breaker example (Resilience4j)
CircuitBreaker circuitBreaker = CircuitBreaker
    .ofDefaults("service");
Supplier<String> decorated = CircuitBreaker
    .decorateSupplier(circuitBreaker, () -> {
        return callExternalService();
    });
String result = Try.ofSupplier(decorated)
    .recover(throwable -> "fallback result");

Implementation: Resilience4j, Hystrix (Netflix), custom implementation.

Q48: Retry vs Exponential Backoff

Performance
What is the difference between retry and exponential backoff?
  • Retry: Re-executing a failed operation immediately or after a fixed delay.
  • Exponential Backoff: Increasing the delay between retries exponentially (e.g., 1s, 2s, 4s, 8s).

Retry:

  • Simple, straightforward
  • Can cause cascading failures
  • May overwhelm the service

Exponential Backoff:

  • Reduces load during recovery
  • Allows service time to recover
  • Often combined with jitter (random variance)
// Exponential backoff with jitter
int maxAttempts = 5;
for (int i = 0; i < maxAttempts; i++) {
    try {
        return callService();
    } catch (Exception e) {
        long delay = Math.min(2^i * 100, 30000);
        Thread.sleep(delay + (long)(Math.random() * 1000));
    }
}

Best practice: Use exponential backoff with jitter for distributed systems.
