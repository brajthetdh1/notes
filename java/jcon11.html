Section 10.1: Task Cancellation – The Art of Stopping Gracefully

Cancellation is one of the most misunderstood aspects of concurrency. Java does not provide a safe way to forcibly stop a thread. Instead, it provides a cooperative interruption mechanism.

Subsection 10.1.1: The Interruption Mechanism

Key Methods:

MethodDescription
Thread.interrupt()Sets the interrupt flag and wakes the thread if it's blocked.
Thread.isInterrupted()Returns the interrupt flag (does not clear it).
Thread.interrupted()Returns the interrupt flag and clears it (static method).

Does interrupt() stop the thread? No! interrupt() only sets a flag. The thread must cooperate by checking the flag and exiting gracefully.

while (!Thread.currentThread().isInterrupted()) {
            // Do work
        }

Subsection 10.1.2: Cancellation with Future

Future.cancel() provides a standardized way to cancel a task.

public interface Future<V> {
            boolean cancel(boolean mayInterruptIfRunning);
            boolean isCancelled();
            boolean isDone();
            V get() throws InterruptedException, ExecutionException;
            V get(long timeout, TimeUnit unit) throws InterruptedException, ExecutionException, TimeoutException;
        }

cancel(true) vs cancel(false): true interrupts the thread if running. false marks as cancelled but does not interrupt.

Future<Integer> future = executor.submit(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                // Do work
            }
            return 42;
        });
        future.cancel(true);  // Interrupts the thread

Subsection 10.1.3: Handling InterruptedException

Correct pattern: Propagate it or restore the interrupt flag.

// Propagate
        public void myMethod() throws InterruptedException {
            Thread.sleep(1000);
        }
        
        // Restore flag
        public void myMethod() {
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();  // Restore flag
                // Handle cleanup
            }
        }

Subsection 10.2.4: Exception Handling

MethodDescription
exceptionally(fn)Provides a fallback value on error.
handle(fn)Handles both success and error.
whenComplete(action)Runs an action on completion (success or error).
// exceptionally - fallback on error
        CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
            if (true) throw new RuntimeException("Error!");
            return 42;
        })
        .exceptionally(t -> {
            System.out.println("Error: " + t.getMessage());
            return -1;  // Fallback
        });
        
        // handle - handles both success and error
        future.handle((result, throwable) -> {
            if (throwable != null) {
                System.out.println("Error: " + throwable.getMessage());
                return -2;
            }
            return result * 2;
        });

orTimeout() vs completeOnTimeout(): orTimeout() throws TimeoutException. completeOnTimeout() returns a fallback value.

CompletionService allows you to process completed tasks as soon as they finish, regardless of submission order.

Subsection 10.3.1: What is CompletionService?

public interface CompletionService<V> {
            Future<V> submit(Callable<V> task);
            Future<V> submit(Runnable task, V result);
            Future<V> take() throws InterruptedException;
            Future<V> poll();
            Future<V> poll(long timeout, TimeUnit unit) throws InterruptedException;
        }

Subsection 10.3.2: Example – Processing Results as They Arrive

CompletionService<Integer> service = new ExecutorCompletionService<>(executor);
        
        // Submit 10 tasks
        for (int i = 0; i < 10; i++) {
            final int taskId = i;
            service.submit(() -> {
                Thread.sleep(ThreadLocalRandom.current().nextInt(1000, 5000));
                return taskId * 10;
            });
        }
        
        // Process results as they complete
        for (int i = 0; i < 10; i++) {
            Future<Integer> future = service.take();  // Blocks until a task completes
            System.out.println("Task completed: " + future.get());
        }

Section 10.5: Thread Pool Tuning and Monitoring

Subsection 10.5.1: Sizing Thread Pools

CPU-bound tasks:

Thread count = Number of CPU cores + 1

I/O-bound tasks:

Thread count = Number of CPU cores * (1 + Wait time / Service time)

Example: CPU cores: 8, Service time: 100 ms, Wait time: 900 ms → Thread count = 8 * (1 + 900/100) = 80

Subsection 10.6.2: Virtual Threads and ThreadLocal

Virtual threads support ThreadLocal, but use with caution. Virtual threads are created in large numbers, and ThreadLocal memory can accumulate quickly.

Better alternative: Use ScopedValue (Java 21+) for context propagation.

// ThreadLocal (memory risk)
        private static final ThreadLocal<String> context = new ThreadLocal<>();
        
        // ScopedValue (safer)
        private static final ScopedValue<String> context = ScopedValue.newInstance();
        ScopedValue.where(context, "user-123")
            .run(() -> {
                System.out.println(context.get());  // "user-123"
            });

Q1: How does thread interruption work in Java?

A: Thread interruption is a cooperative mechanism. interrupt() sets the flag. If blocked in wait(), sleep(), join(), or Lock.lockInterruptibly(), it throws InterruptedException. The thread must check isInterrupted() to know if it should stop. One-liner: "interrupt() only sets a flag. The thread must cooperate by checking the flag."

Q2: What is the difference between Thread.interrupted() and Thread.isInterrupted()?

A: isInterrupted() returns the flag without clearing it. interrupted() returns the flag and clears it. Use isInterrupted() for checking without clearing.

Q3: What is the difference between Future.cancel(true) and Future.cancel(false)?

A: true interrupts the thread if running. false marks as cancelled but does not interrupt the thread.

Part A: Conceptual Deep-Dive

Q4: What happens to the interrupt flag when InterruptedException is thrown?

A: The interrupt flag is cleared (set to false). You must restore it if you can't propagate the exception: Thread.currentThread().interrupt();

Q5: How do you cancel a task that doesn't check the interrupt flag?

A: If a task doesn't check isInterrupted(), cancel(true) will not stop it. Ensure the task checks the flag regularly or uses interruptible methods.

Q6: What is the difference between shutdown() and shutdownNow() in ExecutorService?

A: shutdown() completes existing tasks. shutdownNow() attempts to interrupt running tasks and discards queued tasks (returns them).

Q7: What is CompletableFuture and how does it differ from Future?

A: CompletableFuture supports non-blocking composition, chaining, and exception handling. Future only supports blocking get() and manual cancellation.

Q8: What is the difference between thenApply, thenAccept, and thenRun?

A: thenApply transforms the result. thenAccept consumes the result (no return). thenRun runs an action without using the result.

Q9: What is the difference between thenApply and thenCompose?

A: thenApply expects a function that returns a plain value. thenCompose expects a function that returns a CompletableFuture (flattens nested futures). Analogy: map() vs flatMap().

Q10: What is the difference between thenCombine and thenCompose?

A: thenCombine combines two independent futures (parallel). thenCompose chains dependent futures (sequential). Analogy: zip vs flatMap.

Q11: What is the difference between exceptionally and handle?

A: exceptionally is called only on exception. handle is called on both success and failure. handle can change the return type.

Q12: What is the difference between orTimeout() and completeOnTimeout()?

A: orTimeout() throws TimeoutException on timeout. completeOnTimeout() returns a fallback value on timeout.

Q13: What is the difference between allOf() and anyOf()?

A: allOf() completes when all futures complete. anyOf() completes when any future completes. Use anyOf() for race conditions (fastest response).

Q14: What is the difference between get() and join() in CompletableFuture?

A: get() throws checked exceptions (InterruptedException, ExecutionException). join() throws CompletionException (unchecked).

Q15: What is the difference between supplyAsync() and runAsync()?

A: supplyAsync() returns a result. runAsync() does not return a result.

Q16: What is CompletionService and when would you use it?

A: CompletionService processes completed tasks in order of completion. Use it when you need results as they complete or when tasks have varying execution times.

Q17: What is the difference between CompletionService and CompletableFuture?

A: CompletionService = process results in order of completion. CompletableFuture = compose and chain asynchronous operations.

Q18: What is the difference between take() and poll() in CompletionService?

A: take() blocks until a task completes. poll() returns immediately (non-blocking).

Q19: How do you size a thread pool?

A: CPU-bound: cores + 1. I/O-bound: cores * (1 + waitTime/serviceTime). Example: 8 cores, 100ms service, 900ms wait → 80 threads.

Q20: What metrics should you monitor in a thread pool?

A: Pool size, active count, queue size, completed tasks, rejected tasks.

Q21: What are Virtual Threads and how do they differ from Platform Threads?

A: Virtual Threads are lightweight, JVM-managed threads (cheap, scalable to millions). Platform Threads are 1:1 with OS threads (expensive, limited to thousands).

Q22: What is "pinning" in Virtual Threads?

A: Pinning occurs when a virtual thread enters a synchronized block and cannot be unmounted. Fix: use ReentrantLock instead of synchronized.

Q23: When should you use Virtual Threads vs. Platform Threads?

A: I/O-bound → Virtual Threads. CPU-bound → Platform Threads. Task count > 10,000 → Virtual Threads.
