Section 7.1: ReentrantLock – The Flexible Alternative to synchronized

ReentrantLock is the most commonly used explicit lock. It provides the same mutual exclusion as synchronized but with additional features like try-lock, timed lock, interruptible lock, and fairness.

        }

What does "reentrant" mean? A lock is reentrant if a thread that already holds the lock can acquire it again without blocking. The lock maintains a hold count that increments on each lock and decrements on each unlock.

Subsection 7.1.7: The "Doubt Clarifier" – Can I mix synchronized and ReentrantLock on the same object?

Yes, but they are different locks! synchronized uses the intrinsic lock (monitor) of the object. ReentrantLock is a separate lock object.

private final Object monitor = new Object();
        private final ReentrantLock lock = new ReentrantLock();
        
        // Thread A
        synchronized (monitor) {
            lock.lock();  // Holds both locks
            try { /* Critical section */ } finally { lock.unlock(); }
        }
        
        // Thread B - Deadlock risk!
        lock.lock();
        try {
            synchronized (monitor) { /* Critical section */ }
        } finally { lock.unlock(); }

Which should I use? Simple mutual exclusion → synchronized. Need try-lock, timed lock, interruptible lock, multiple conditions, or fairness → ReentrantLock.

Section 7.2: ReadWriteLock – Optimizing for Read-Heavy Workloads

ReadWriteLock allows multiple readers to hold the lock simultaneously, but only one writer.

Subsection 7.2.1: What is ReadWriteLock?

public interface ReadWriteLock {
            Lock readLock();
            Lock writeLock();
        }

Rules:

  • If no thread holds the write lock, any thread can acquire the read lock.
  • If any thread holds the read lock, a thread attempting to acquire the write lock blocks.
  • If a thread holds the write lock, all other threads block for both read and write locks.

Subsection 7.2.2: Basic Usage Pattern

public class Cache {
            private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
            private final Lock readLock = rwLock.readLock();
            private final Lock writeLock = rwLock.writeLock();
            private final Map<String, Object> cache = new HashMap<>();
            
            public Object get(String key) {
                readLock.lock();
                try { return cache.get(key); }
                finally { readLock.unlock(); }
            }
            
            public void put(String key, Object value) {
                writeLock.lock();
                try { cache.put(key, value); }
                finally { writeLock.unlock(); }
            }
        }

Subsection 7.2.3: The "Doubt Clarifier" – What is the risk of writer starvation?

If many readers keep acquiring the read lock, writers may be starved.

Solution 1: Use a fair lock new ReentrantReadWriteLock(true).

Solution 2: Use StampedLock (Java 8+) for optimistic reads.

Subsection 7.2.4: The "Doubt Clarifier" – Can a thread holding the read lock upgrade to a write lock?

No. If a thread holds the read lock and tries to acquire the write lock, it will deadlock.

readLock.lock();
        try {
            writeLock.lock();  // DEADLOCK! Waiting for read lock to be released
            try { /* write */ } finally { writeLock.unlock(); }
        } finally { readLock.unlock(); }

The Fix: Release the read lock before acquiring the write lock.

readLock.lock();
        try { int value = data; } finally { readLock.unlock(); }
        writeLock.lock();
        try { data = value + 1; } finally { writeLock.unlock(); }

Section 7.3: StampedLock – Optimistic Locking for Maximum Performance

StampedLock (Java 8+) provides optimistic locking for even better performance in read-heavy workloads.

Subsection 7.3.1: What is StampedLock?

            public StampedLock();

What is a "stamp"? A stamp is a long value returned by lock acquisition methods. It serves as a "ticket" that must be passed back to unlock methods.

Subsection 7.3.2: Optimistic Read – The Game Changer

Optimistic read is a special read operation that does not acquire a lock. It reads the data and then validates that no write occurred during the read.

public class StampedLockExample {
            private final StampedLock lock = new StampedLock();
            private int x = 0;
            private int y = 0;
            
            public int read() {
                long stamp = lock.tryOptimisticRead();  // No blocking!
                int currentX = x;
                int currentY = y;
                
                if (!lock.validate(stamp)) {
                    // A write occurred during the read! Fall back to regular read lock.
                    stamp = lock.readLock();
                    try {
                        currentX = x;
                        currentY = y;
                    } finally {
                        lock.unlockRead(stamp);
                    }
                }
                return currentX + currentY;
            }
        }

Why is optimistic read faster? No blocking, no cache invalidation, no contention. If a write occurs, you retry with a regular read lock.

Subsection 7.4.2: Basic Usage Pattern

public class BoundedQueue<T> {
            private final Lock lock = new ReentrantLock();
            private final Condition notFull = lock.newCondition();
            private final Condition notEmpty = lock.newCondition();
            private final Queue<T> queue = new LinkedList<>();
            private final int capacity;
            
            public void put(T item) throws InterruptedException {
                lock.lock();
                try {
                    while (queue.size() == capacity) {
                        notFull.await();  // Wait until queue is not full
                    }
                    queue.offer(item);
                    notEmpty.signal();  // Signal that queue is not empty
                } finally { lock.unlock(); }
            }
            
            public T take() throws InterruptedException {
                lock.lock();
                try {
                    while (queue.isEmpty()) {
                        notEmpty.await();  // Wait until queue is not empty
                    }
                    T item = queue.poll();
                    notFull.signal();  // Signal that queue is not full
                    return item;
                } finally { lock.unlock(); }
            }
        }

Why use while instead of if? Always use while to handle spurious wakeups. A thread can wake up from await() without a signal() being called.

Section 7.5: Performance Considerations

Subsection 7.5.1: Lock Contention

Lock contention occurs when multiple threads compete for the same lock. High contention reduces performance.

How to reduce contention:

  • Narrow the critical section: Hold the lock for as short as possible.
  • Use read-write locks: For read-heavy workloads.
  • Use StampedLock: For even better read performance.
  • Use lock striping: Multiple locks for different parts of the data structure.
  • Use lock-free algorithms: AtomicInteger, ConcurrentLinkedQueue.

Subsection 7.5.2: Fairness

Fair locks new ReentrantLock(true) ensure threads acquire the lock in FIFO order. This prevents starvation but reduces throughput.
