Q51: Distributed System

Distributed Systems
What is a distributed system? What are its characteristics?

A distributed system is a collection of independent computers that appear to users as a single coherent system. They communicate and coordinate their actions by passing messages.

Key characteristics:

  • Scalability: Ability to grow by adding more nodes.
  • Fault Tolerance: Can continue operating despite failures.
  • Concurrency: Multiple components run simultaneously.
  • Heterogeneity: Different hardware, OS, and networks.
  • Openness: Extensible with new services.
  • Transparency: Hides internal complexity from users.
  • Message Passing: Communication via network.
  • No Global Clock: Each node has its own clock.

Examples: Google's search infrastructure, AWS, banking systems.

Q52: Distributed Systems Challenges

Distributed Systems
What are the challenges in designing distributed systems?
  • Network Failures: Messages can be lost, delayed, or reordered.
  • Partial Failures: Some nodes can fail while others continue.
  • No Global Clock: Synchronizing time across nodes is difficult.
  • Consistency: Maintaining data consistency across replicas.
  • Concurrency: Coordinating concurrent access to shared resources.
  • Scalability: Adding nodes without performance degradation.
  • Security: Securing communication between nodes.
  • Latency: Network communication introduces delays.
  • Fault Tolerance: Designing for failures.
  • Distributed Consensus: Getting nodes to agree on a value.

Common solutions: CAP theorem, Paxos, Raft, distributed transactions, and retry mechanisms.

Q54: Distributed Consensus

Distributed Systems
What is a distributed consensus algorithm? Why is it needed?

A distributed consensus algorithm allows multiple nodes in a distributed system to agree on a single value even in the presence of failures.

Why it's needed:

  • Maintaining consistency in replicated databases.
  • Leader election in distributed systems.
  • Coordinating transactions across nodes.
  • Implementing distributed lock managers.
  • Agreement on configuration changes.

Key properties:

  • Agreement: All correct nodes agree on the same value.
  • Validity: The agreed value was proposed by some node.
  • Termination: The algorithm eventually terminates.

Well-known algorithms: Paxos, Raft, PBFT.

Q55: Paxos Algorithm

Distributed Systems
What is the Paxos algorithm?

Paxos is a distributed consensus algorithm that solves the problem of reaching agreement in an asynchronous, message-passing system with faults.

Key components:

  • Proposers: Propose values to be agreed upon.
  • Acceptors: Vote on proposals.
  • Learners: Learn the final agreed value.

Phases:

  • Phase 1 (Prepare): Proposer sends a prepare request with a proposal number.
  • Phase 2 (Accept): Proposer sends an accept request.
  • Phase 3 (Learn): Learners are informed of the chosen value.

Important properties:

  • Safety: Only one value is chosen.
  • Liveness: Some value is eventually chosen.
  • Fault Tolerance: Works with up to f failures (requires 2f+1 acceptors).

Drawback: Paxos is notoriously difficult to understand and implement correctly.

Q56: Raft Consensus

Distributed Systems
What is the Raft consensus algorithm?

Raft is a distributed consensus algorithm designed to be understandable and implementable. It was created as a more approachable alternative to Paxos.

Key components:

  • Leader: Handles all client requests and coordinates log replication.
  • Follower: Responds to leader's requests.
  • Candidate: Runs for election when no leader is detected.

Key phases:

  • Leader Election: A leader is elected using a heartbeat mechanism.
  • Log Replication: The leader replicates client requests to followers.
  • Commitment: Once a majority of followers have acknowledged, the entry is committed.

Features:

  • Strong Leader: Single leader makes decisions.
  • Heartbeat: Prevents timeouts.
  • Log Indexing: Tracks committed entries.

Use cases: etcd, Consul, CockroachDB.

Q58: Distributed Transactions

Distributed Systems
What is a distributed transaction? What are the challenges?

A distributed transaction is a transaction that involves multiple databases or services across different nodes.

Challenges:

  • Network Failures: Nodes may become unreachable.
  • Partial Failures: Some nodes may fail while others succeed.
  • Consistency: Maintaining ACID properties across multiple systems.
  • Latency: Coordinating across nodes adds overhead.
  • Concurrency: Handling concurrent transactions.

Solutions:

  • Two-Phase Commit (2PC): Coordinated commit protocol.
  • Saga Pattern: Compensating transactions.
  • Eventual Consistency: Accepting temporary inconsistency.
  • Distributed ACID: Using distributed databases (e.g., Spanner).

Q59: Two-Phase Commit (2PC)

Distributed Systems
What is the Two-Phase Commit (2PC) protocol?

Two-Phase Commit (2PC) is a distributed algorithm used to ensure all nodes in a distributed system either commit or abort a transaction.

Phases:

  • Phase 1 – Prepare (Voting):
    • Coordinator sends a "prepare" request to all participants.
    • Each participant responds with "ready" or "abort".
  • Phase 2 – Commit/Abort:
    • If all participants vote "ready", coordinator sends "commit".
    • If any participant votes "abort", coordinator sends "abort".
    • Participants execute the command.

Drawbacks:

  • Blocking: Participants may wait indefinitely if coordinator fails.
  • Single Point of Failure: Coordinator is a single point of failure.
  • Performance: Requires two rounds of communication.

Better alternatives: 3PC (Three-Phase Commit), Saga pattern.

Q60: Saga Pattern

Distributed Systems
What is the Saga pattern in distributed transactions?

The Saga pattern is a way to manage distributed transactions by breaking them into a sequence of smaller, independent transactions. Each transaction has a compensating action to undo it if needed.

Characteristics:

  • Eventual Consistency: The system will eventually become consistent.
  • Compensating Transactions: Each step has a compensating action.
  • No 2PC Needed: Avoids the blocking issue of 2PC.
  • Resilience: Handles failures gracefully.

Implementation approaches:

  • Choreography: Each service publishes events; others react.
  • Orchestration: A central coordinator manages the saga.
// Example: Order processing saga
// Step 1: Create Order
// Step 2: Reserve Payment
// Step 3: Ship Order
// If Step 3 fails, compensate: cancel payment, delete order

Use cases: E-commerce, banking, microservices transactions.

Q62: Distributed Lock

Distributed Systems
What is a distributed lock? When is it used?

A distributed lock is a lock that is shared across multiple nodes in a distributed system, ensuring that only one node can access a shared resource at a time.

When it's used:

  • Coordinating access to shared resources (e.g., database records).
  • Preventing duplicate processing.
  • Ensuring idempotency in distributed systems.
  • Leader election.
  • Rate limiting across nodes.

Common implementations:

  • Redis: Using SETNX or Redlock.
  • ZooKeeper: Using ephemeral nodes.
  • Database: Using SELECT ... FOR UPDATE.
  • etcd: Using leases and keys.
// Redis distributed lock example
// Acquire lock
SET lock_key unique_id NX PX 30000
// Release lock
IF GET lock_key == unique_id THEN DEL lock_key

Challenges: Network issues, split-brain, and timeouts.

Q63: Distributed ID Generator

Distributed Systems
What is a distributed ID generator? How does it work?

A distributed ID generator is a system that generates unique IDs across multiple nodes without central coordination.

Requirements:

  • Uniqueness: No two nodes generate the same ID.
  • Scalability: Must work at high throughput.
  • Availability: Should be available even if nodes fail.

Common approaches:

  • Snowflake (Twitter): Uses timestamp, machine ID, and sequence number.
  • UUID: Universally unique identifiers.
  • Database Sequences: Centralized sequence (bottleneck).
  • ZooKeeper: Sequential nodes.
// Snowflake ID structure (64-bit)
// [41-bit timestamp][10-bit machine ID][12-bit sequence]
// Example: 1493261979578_1_1

Key features:

  • Monotonically increasing (for sorting).
  • No central coordination.
  • High throughput (millions per second).

Q65: Vector Clock

Distributed Systems
What is vector clock and why is it used?

A vector clock is a distributed algorithm used to determine the causal ordering of events in a distributed system. Each node maintains a vector of counters, one for each node in the system.

How it works:

  • Each node has a vector with its own counter and others' counters.
  • When a node processes an event, it increments its own counter.
  • When a node sends a message, it includes its vector.
  • The receiver merges the vector (max of each component).
// Example with 3 nodes A, B, C
// A's vector: [1, 0, 0]
// B's vector after receiving from A: [1, 1, 0]

Why it's used:

  • To determine causal relationships between events.
  • To detect conflicts in distributed systems.
  • Used in version control and databases (e.g., Riak).

Comparison with Lamport timestamps: Vector clocks can detect causality, while Lamport timestamps can only order events.

Q67: Deadlock

Concurrency
What is a deadlock? How can it be prevented?

A deadlock occurs when two or more threads are blocked forever, each waiting for the other to release a resource.

Four necessary conditions (Coffman conditions):

  • 1. Mutual Exclusion: Resources are held exclusively.
  • 2. Hold and Wait: Holding resources while waiting for others.
  • 3. No Preemption: Resources cannot be forcibly taken.
  • 4. Circular Wait: A cycle of waiting.

Prevention strategies:

  • 1. Resource Ordering: Acquire locks in a fixed order.
  • 2. Timeout: Release locks if not acquired within a time limit.
  • 3. Deadlock Detection: Detect and recover (e.g., using wait-for graphs).
  • 4. Avoidance: Use Banker's algorithm.
// Deadlock example
Thread 1: lock(A); lock(B);
Thread 2: lock(B); lock(A);
// Both threads wait indefinitely

Q68: Race Condition

Concurrency
What is a race condition? How can it be prevented?

A race condition occurs when multiple threads access shared data concurrently, and the final outcome depends on the timing of the operations.

// Race condition example
int counter = 0;
// Thread 1: counter++
// Thread 2: counter++
// Result could be 1 instead of 2

Prevention strategies:

  • Synchronization: Using synchronized blocks or methods.
  • Atomic Operations: Using AtomicInteger, AtomicLong.
  • Locks: Using ReentrantLock or ReadWriteLock.
  • Immutable Objects: Avoid shared mutable state.
  • Thread-local Storage: Each thread has its own copy.
// Using synchronized
synchronized void increment() { counter++; }

// Using AtomicInteger
AtomicInteger counter = new AtomicInteger();
counter.incrementAndGet();

Q70: Thread Safety

Concurrency
What is thread safety? How do you achieve it?

Thread safety means that a class or method behaves correctly when accessed by multiple threads simultaneously, without requiring external synchronization.

Ways to achieve thread safety:

  • 1. Immutability: Make objects immutable (e.g., String).
  • 2. Synchronization: Use synchronized blocks/methods.
  • 3. Atomic Classes: Use AtomicInteger, AtomicReference.
  • 4. Locks: Use ReentrantLock, ReadWriteLock.
  • 5. Thread-local Storage: Use ThreadLocal.
  • 6. Concurrent Collections: Use ConcurrentHashMap, CopyOnWriteArrayList.
  • 7. Volatile: Use volatile for visibility.
// Thread-safe counter using AtomicInteger
class Counter {
    private AtomicInteger count = new AtomicInteger(0);
    public void increment() { count.incrementAndGet(); }
    public int get() { return count.get(); }
}

// Thread-safe with synchronized
class Counter {
    private int count = 0;
    public synchronized void increment() { count++; }
}

Q72: Context Switching

Concurrency
What is context switching in operating systems?

Context switching is the process of storing the state of a running process or thread and loading the state of another process or thread so that the CPU can execute multiple tasks efficiently.

What's stored (context):

  • CPU registers
  • Program counter
  • Memory management info
  • Stack pointer
  • Other process-specific data

Why it's needed:

  • Time-sharing (multitasking).
  • Interrupt handling.
  • Priority-based scheduling.

Cost: Context switching has overhead (saving/restoring state, cache misses, TLB misses).

Optimization: Minimize context switching by using multi-core CPUs and efficient scheduling algorithms.

Q74: Thread Pool

Concurrency
What is a thread pool and why is it used?

A thread pool is a collection of pre-created threads that can be reused to execute tasks. It manages a pool of worker threads.

Why it's used:

  • Performance: Avoids the overhead of creating/destroying threads for each task.
  • Resource Management: Limits the number of concurrent threads.
  • Task Queuing: Queues tasks when all threads are busy.
  • Load Management: Prevents system overload.
// Java ExecutorService (thread pool)
ExecutorService executor = Executors.newFixedThreadPool(10);
for (int i = 0; i < 100; i++) {
    executor.execute(() -> {
        // Task logic
    });
}
executor.shutdown();

Benefits: Better performance, controlled resource usage, and improved system stability.

Q76: Repository Pattern

Design Patterns
What is the Repository Pattern in system design?

The Repository Pattern is a design pattern that mediates between the domain and data mapping layers, providing a collection-like interface for accessing domain objects.

Key concepts:

  • Repository: Acts like a collection of objects.
  • Data Access: Encapsulates data access logic.
  • Abstraction: Hides the underlying data source.
  • Query Methods: Provides methods like find(), save(), delete().
// Repository interface
interface UserRepository {
    User findById(Long id);
    List<User> findAll();
    void save(User user);
    void delete(Long id);
}

// Implementation (e.g., JPA, MongoDB)
class UserRepositoryImpl implements UserRepository {
    // Implementation using database
}

Benefits: Decouples domain logic from data access, improves testability, and centralizes data access logic.

Q77: Factory Pattern

Design Patterns
What is the Factory Pattern and when would you use it?

The Factory Pattern is a creational design pattern that provides an interface for creating objects in a superclass, but allows subclasses to alter the type of objects that will be created.

When to use:

  • When the creation logic is complex.
  • When you want to create different types of objects.
  • When you want to centralize object creation.
  • When you need to decouple client code from concrete classes.
// Factory interface
interface DocumentFactory {
    Document createDocument(String type);
}

// Concrete factory
class PdfFactory implements DocumentFactory {
    public Document createDocument(String type) {
        return new PdfDocument();
    }
}

Benefits: Loose coupling, centralized creation logic, and easier maintenance.

Q78: Observer Pattern

Design Patterns
What is the Observer Pattern and how is it used?

The Observer Pattern is a behavioral design pattern that defines a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

Key components:

  • Subject: Maintains a list of observers and notifies them.
  • Observer: Defines an update method.
  • Concrete Subject: Stores the state and notifies observers.
  • Concrete Observer: Responds to updates.
// Observer interface
interface Observer {
    void update(String message);
}

// Subject
class NewsAgency {
    List<Observer> observers = new ArrayList<>();
    void addObserver(Observer o) { observers.add(o); }
    void notifyObservers(String news) {
        observers.forEach(o -> o.update(news));
    }
}

Use cases: Event handling, publish-subscribe systems, GUI frameworks.

Q79: Strategy Pattern

Design Patterns
What is the Strategy Pattern and when would you use it?

The Strategy Pattern is a behavioral design pattern that enables selecting an algorithm's behavior at runtime.

Key components:

  • Strategy: Interface for algorithms.
  • Concrete Strategy: Implements the algorithm.
  • Context: Uses a strategy object.
// Strategy interface
interface PaymentStrategy {
    void pay(int amount);
}

// Concrete strategies
class CreditCardPayment implements PaymentStrategy { ... }
class PaypalPayment implements PaymentStrategy { ... }

// Context
class ShoppingCart {
    void processPayment(PaymentStrategy strategy) {
        strategy.pay(total);
    }
}

When to use:

  • When you have multiple algorithms.
  • When you want to avoid conditional statements.
  • When algorithms are likely to change.

Q80: Decorator Pattern

Design Patterns
What is the Decorator Pattern and when would you use it?

The Decorator Pattern is a structural design pattern that allows adding behavior to objects dynamically without affecting other objects of the same class.

Key components:

  • Component: Interface defining the object.
  • Concrete Component: The original object.
  • Decorator: Abstract class implementing the component.
  • Concrete Decorator: Adds extra behavior.
// Component
interface Coffee {
    String getDescription();
    double getCost();
}

// Concrete Component
class PlainCoffee implements Coffee { ... }

// Decorator
abstract class CoffeeDecorator implements Coffee {
    protected Coffee coffee;
    CoffeeDecorator(Coffee c) { this.coffee = c; }
}

// Concrete Decorator
class MilkDecorator extends CoffeeDecorator {
    MilkDecorator(Coffee c) { super(c); }
    public String getDescription() {
        return coffee.getDescription() + ", Milk";
    }
}

When to use: When you want to add responsibilities dynamically, without subclassing.

Q81: Proxy Pattern

Design Patterns
What is the Proxy Pattern and when would you use it?

The Proxy Pattern is a structural design pattern that provides a surrogate or placeholder for another object to control access to it.

Types of proxies:

  • Virtual Proxy: Lazy initialization.
  • Protection Proxy: Access control.
  • Remote Proxy: Represents remote objects.
  • Logging Proxy: Logs method calls.
// Subject
interface Image {
    void display();
}

// Real Subject
class RealImage implements Image {
    RealImage(String filename) { loadFromDisk(); }
    void display() { ... }
}

// Proxy
class ProxyImage implements Image {
    RealImage realImage;
    void display() {
        if (realImage == null) {
            realImage = new RealImage(filename);
        }
        realImage.display();
    }
}

When to use: When you need to control or enhance access to an object.

Q83: MVC Pattern

Design Patterns
What is the MVC (Model-View-Controller) pattern?

MVC (Model-View-Controller) is an architectural pattern that separates an application into three interconnected components:

  • Model: Manages data and business logic.
  • View: Displays the UI (visual representation).
  • Controller: Handles user input and updates the model.

Flow:

  • User interacts with the view.
  • Controller processes the request and updates the model.
  • Model notifies the view of changes.
  • View updates the display.
// MVC components
// Model: User (data)
// View: UserView (HTML/UI)
// Controller: UserController (logic)

Benefits: Separation of concerns, better maintainability, and easier testing.

Q85: Event Sourcing

Design Patterns
What is the Event Sourcing pattern?

Event Sourcing is an architectural pattern where state changes are stored as a sequence of events, rather than storing only the current state.

Key concepts:

  • Events: Immutable records of state changes.
  • Event Store: Database for storing events.
  • Current State: Derived by replaying events.
  • Replay: Can rebuild state from events.
// Event Sourcing example
// Events:
// 1. AccountCreated(customerId, initialBalance)
// 2. MoneyDeposited(amount)
// 3. MoneyWithdrawn(amount)
// Current balance = sum of all events

Benefits:

  • Complete audit trail.
  • Ability to rebuild state.
  • Event replay for debugging.
  • Temporal queries (history).

Challenges: Eventual consistency, complexity, and event schema evolution.

Q86: CQRS Pattern

Design Patterns
What is the CQRS (Command Query Responsibility Segregation) pattern?

CQRS (Command Query Responsibility Segregation) is an architectural pattern that separates read and write operations into different models.

Key concepts:

  • Command: Write operations (updates, creates).
  • Query: Read operations.
  • Separate Models: Different data models for reads and writes.
  • Eventual Consistency: Write model may be updated asynchronously.
// CQRS example
// Command: PlaceOrder(command)
// Query: GetOrder(id) – may use a different database

When to use:

  • Complex systems with different read/write requirements.
  • High-performance systems.
  • Collaborative domains.

Benefits: Scalability, optimized reads, and flexible data models.

Q87: URL Shortener Design

Real-World Applications
How would you design a URL shortening service like TinyURL?

Requirements:

  • Shorten long URLs to unique short codes.
  • Redirect short URLs to original URLs.
  • Handle millions of requests.

Key components:

  • ID Generator: Generates unique IDs (e.g., Snowflake).
  • Short Code: Base62 encoding of ID.
  • Cache: Redis for frequently accessed URLs.
  • Database: Stores mapping (short_code → original_url).
  • Load Balancer: Distributes traffic.
// Short code generation
// ID: 123456 → base62 → "b8p"
// URL: https://tinyurl.com/b8p

Scaling considerations:

  • Read-heavy workload → caching.
  • Write-heavy → database sharding.
  • High availability → multiple replicas.

Q89: Social Media Feed Design

Real-World Applications
How would you design a social media feed like Facebook/Twitter?

Requirements:

  • Display posts from friends/followers.
  • Personalized ranking/relevance.
  • Real-time updates.
  • Infinite scrolling.

Key components:

  • Feed Service: Generates and serves feeds.
  • Ranking Service: Determines post order (ML model).
  • Cache: Redis for feed storage.
  • Database: Stores posts and user relationships.
  • Event Bus: Notifies followers about new posts.

Q98: Serverless Architecture

Advanced Trends
What is serverless architecture? What are its pros and cons?

Serverless architecture is a cloud computing model where the cloud provider manages the infrastructure, and users only deploy code (functions) that run in response to events.

Key features:

  • No server management: Infrastructure is abstracted.
  • Event-driven: Functions are triggered by events.
  • Auto-scaling: Automatically scales based on demand.
  • Pay-per-use: Only pay for execution time.

Pros:

  • Reduced operational overhead.
  • Cost-effective for intermittent workloads.
  • Elastic scalability.

Cons:

  • Cold start latency.
  • Vendor lock-in.
  • Limited execution time.
  • Debugging is harder.

Examples: AWS Lambda, Google Cloud Functions, Azure Functions.

Q99: DevOps

Advanced Trends
What is DevOps? How does it relate to system design?

DevOps is a set of practices that combines software development (Dev) and IT operations (Ops) to shorten the development lifecycle and deliver high-quality software continuously.

Key principles:

  • Collaboration: Breaking down silos between teams.

  • Design for Deployability: Systems should be designed for easy deployment.

  • Design for Resilience: Systems should handle failures gracefully.
  • Infrastructure as Code: Using tools like Terraform, Ansible.

Q100: CI vs CD

Advanced Trends
What is the difference between continuous integration and continuous deployment?
  • Continuous Integration (CI): The practice of automatically building and testing code changes frequently (every commit). The goal is to detect integration issues early.
  • Continuous Delivery (CD): The practice of automatically preparing code changes for production release. The software is always in a deployable state.
  • Continuous Deployment (also CD): The practice of automatically deploying every change that passes the CI pipeline to production.
