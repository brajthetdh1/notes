Section 8.1: Overview of Concurrent Collections

Before diving into specific collections, let's understand the landscape and why we need specialized concurrent collections.

Subsection 8.1.1: The Problem with Traditional Collections

Traditional collections (HashMap, ArrayList, LinkedList, etc.) are not thread-safe. If multiple threads access them concurrently, they can:

  • Corrupt internal state: Linked lists can become circular; hash maps can lose entries.
  • Throw exceptions: ConcurrentModificationException during iteration.
  • Produce incorrect results: Lost updates, stale reads.

Why can't I just use Collections.synchronizedMap()?

You can, but it has severe limitations: poor performance under high contention, manual iteration synchronization, and no atomic compound operations.

Section 8.2: ConcurrentHashMap – The Workhorse

ConcurrentHashMap is the most widely used concurrent collection. It provides thread-safe, highly scalable map operations.

Subsection 8.2.1: What is ConcurrentHashMap?

public class ConcurrentHashMap<K,V> extends AbstractMap<K,V>
            implements ConcurrentMap<K,V>, Serializable {
            
            // Atomic operations
            public V putIfAbsent(K key, V value);
            public boolean remove(Object key, Object value);
            public boolean replace(K key, V oldValue, V newValue);
            public V replace(K key, V value);
            
            // Compute operations (Java 8+)
            public V computeIfAbsent(K key, Function<? super K, ? extends V> mappingFunction);
            public V computeIfPresent(K key, BiFunction<? super K, ? super V, ? extends V> remappingFunction);
            public V compute(K key, BiFunction<? super K, ? super V, ? extends V> remappingFunction);
            public V merge(K key, V value, BiFunction<? super V, ? super V, ? extends V> remappingFunction);
        }

What is concurrencyLevel? The concurrencyLevel parameter (deprecated in Java 8+) controlled the number of segments. In Java 8+, it uses a Node array + CAS approach.

Subsection 8.2.2: Key Features of ConcurrentHashMap

  • Thread-safe: All operations are thread-safe.
  • High scalability: Uses lock striping (or CAS in Java 8+) to allow concurrent reads and writes.
  • No blocking for reads: Reads are non-blocking (no locks).
  • Atomic operations: putIfAbsent(), remove(key, value), replace(key, oldValue, newValue).
  • Compute operations: computeIfAbsent(), computeIfPresent(), compute(), merge().
  • No null keys or values: Unlike HashMap, ConcurrentHashMap does not allow null keys or values.
  • Iteration is weakly consistent: Iterators reflect the state at creation time.

Subsection 8.2.3: Internal Structure (Java 8+)

  • Node array: Similar to HashMap, but nodes are volatile.
  • CAS (Compare-And-Swap): Used for non-blocking updates.
  • TreeBin: When collisions exceed 8, linked lists convert to red-black trees for O(log n) performance.
  • Size counter: Uses LongAdder for scalable size tracking.

Subsection 8.2.5: Iteration – Weakly Consistent

ConcurrentHashMap iterators are weakly consistent: They reflect the state at creation time and may not see subsequent modifications.

Section 8.3: Blocking Queues – The Producer-Consumer Pattern

Blocking queues are the backbone of producer-consumer patterns. They provide thread-safe operations that block when the queue is empty (take) or full (put).

Subsection 8.3.1: The BlockingQueue Interface

public interface BlockingQueue<E> extends Queue<E> {
            // Throws exception
            boolean add(E e);       // Throws IllegalStateException if full
            E remove();             // Throws NoSuchElementException if empty
            
            // Returns special value
            boolean offer(E e);     // Returns false if full
            E poll();               // Returns null if empty
            
            // Blocks
            void put(E e) throws InterruptedException;   // Blocks if full
            E take() throws InterruptedException;        // Blocks if empty
            
            // Blocks with timeout
            boolean offer(E e, long timeout, TimeUnit unit) throws InterruptedException;
            E poll(long timeout, TimeUnit unit) throws InterruptedException;
        }

Operation Groups: Throws Exception, Returns Special Value, Blocks, Blocks with Timeout.

Section 8.4: CopyOnWriteArrayList – Read-Heavy, Write-Rarely

CopyOnWriteArrayList is optimized for scenarios where reads are far more frequent than writes.

Subsection 8.4.1: What is CopyOnWriteArrayList?

public class CopyOnWriteArrayList<E> implements List<E>, RandomAccess {
            // Read operations (no locking)
            public E get(int index);
            public int size();
            
            // Write operations (copy-on-write)
            public boolean add(E e);
            public E set(int index, E element);
            public boolean remove(Object o);
        }

How it works:

  • Reads: No locking. Fast and non-blocking.
  • Writes: Creates a new copy of the entire array, modifies it, and sets it as the new array.

Why is it called "copy-on-write"? Every write operation creates a new copy of the entire array. This is expensive but makes reads lock-free.

13 / 40

Subsection 8.4.2: Use Case – Event Listeners

public class EventSource {
            private final CopyOnWriteArrayList<Listener> listeners = new CopyOnWriteArrayList<>();
            
            public void addListener(Listener listener) {
                listeners.add(listener);  // Copy-on-write
            }
            
            public void removeListener(Listener listener) {
                listeners.remove(listener);  // Copy-on-write
            }
            
            public void fireEvent(Event event) {
                for (Listener listener : listeners) {
                    listener.onEvent(event);  // Reads are lock-free
                }
            }
        }

Is CopyOnWriteArrayList good for frequent writes? No! Every write creates a new array copy, which is O(n). Use it only when writes are rare and reads are frequent.

Section 8.5: Non-Blocking Queues

Non-blocking queues use CAS (Compare-And-Swap) for lock-free, high-performance operations.

Subsection 8.5.1: ConcurrentLinkedQueue – Unbounded, Lock-Free

ConcurrentLinkedQueue<String> queue = new ConcurrentLinkedQueue<>();
        queue.offer("Item");  // Non-blocking
        String item = queue.poll();  // Returns null if empty
        String peek = queue.peek();  // Returns null if empty

Why is size() O(n) for ConcurrentLinkedQueue? The queue is lock-free, so the size changes constantly. size() must traverse the entire list to count elements, which is O(n). Use isEmpty() instead for O(1).

Q1: What is ConcurrentHashMap and how does it differ from HashMap?

A: ConcurrentHashMap is a thread-safe, highly scalable map. HashMap is not thread-safe. ConcurrentHashMap provides atomic operations, weakly consistent iteration, and non-blocking reads. Q2: Why does ConcurrentHashMap not allow null keys or values?

A: To avoid ambiguity between "key not found" and "key maps to null" in a concurrent environment. Also, it follows the convention of Hashtable.

Q3: What is the difference between ConcurrentHashMap and Collections.synchronizedMap()?

A: ConcurrentHashMap has better performance, non-blocking reads, weakly consistent iteration, and atomic operations. synchronizedMap() uses a single lock and requires manual synchronization for atomic operations and iteration.

Q4: What is the internal structure of ConcurrentHashMap (Java 8+)?

A: Uses a Node array (volatile), CAS for non-blocking updates, synchronized on the first node for updates within a bin, TreeBin for red-black trees when collisions exceed 8, and LongAdder for size tracking.

A: putIfAbsent() takes a pre-computed value. computeIfAbsent() computes lazily only if the key is missing. computeIfAbsent() is preferred for expensive computations. One-liner: "computeIfAbsent() avoids wasted computation when the key already exists."
