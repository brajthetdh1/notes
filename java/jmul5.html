Topic 3.1: Fundamentals of Thread Safety

Q1 fundamentals If I have a class with no mutable state (no fields), is it thread-safe?

A: Yes, trivially. Stateless objects are always thread-safe because there is nothing to corrupt. Example: a utility class with only static methods that operate on local variables.

public class MathUtils { public static int add(int a, int b) { return a + b; // No shared state } }

The local variables a, b, and the return value live on the stack, which is thread-confined. Multiple threads can call add() simultaneously without any synchronization.

2 min read stateless thread-safe

Q2 fundamentals What is the difference between "thread-safe" and "thread-compatible"?

A:

TermMeaningExample
Thread-SafeThe class behaves correctly without external synchronization.ConcurrentHashMap
Thread-CompatibleThe class is safe if the caller uses external synchronization.HashMap (you can wrap it with Collections.synchronizedMap())
Thread-HostileThe class is not safe even with synchronization (e.g., due to static state).Rare, but possible with poorly designed singletons.
Interview Tip: When asked "Is HashMap thread-safe?" answer: "No, it's thread-compatible. You can make it thread-safe by wrapping it with Collections.synchronizedMap() or using ConcurrentHashMap."
3 min read thread-compatible terminology

Q3 fundamentals What is an "invariant" and how does it relate to thread safety?

A: An invariant is a condition that must always be true for an object to be in a valid state.

Example: A BankAccount class has the invariant balance >= 0. If a race condition causes the balance to become negative, the invariant is broken, and the object is in an invalid state.

Why this matters in interviews: Interviewers often ask you to identify invariants in a given class and explain how synchronization preserves them.
3 min read invariant correctness

Q4 fundamentals What is the relationship between thread safety and synchronized? Can you be thread-safe without synchronized?

A: Yes! You can be thread-safe without synchronized by:

  • Immutability: If the object is immutable, no synchronization is needed (String, Integer).
  • Atomic Variables: Using AtomicInteger, AtomicReference, etc. (lock-free via CAS).
  • Thread Confinement: If the object is only accessed by one thread, no synchronization is needed (local variables, ThreadLocal).
  • Concurrent Collections: Using ConcurrentHashMap, ConcurrentLinkedQueue, etc.

synchronized is just one tool, not the only one.

Topic 3.2: Atomicity

Q5 atomicity What is the difference between a race condition and a data race?

A: This is a common trick question. They are related but distinct:

TermDefinitionExample
Race ConditionA correctness failure due to timing. The outcome depends on the interleaving of threads.if (x == 0) { x = 1; } – Two threads both see x == 0 and both set it to 1.
Data RaceA specific type of race condition caused by a lack of visibility. A thread reads a stale value because another thread's write was not made visible.Thread A writes x = 5; Thread B reads x and sees 0 (stale value) because x is not volatile or synchronized.
Key Insight: All data races are race conditions, but not all race conditions are data races. A race condition can occur even with visibility (e.g., check-then-act with volatile).
4 min read race-condition data-race

Q6 atomicity Is i++ atomic in Java? Why or why not?

A: No. i++ is a read-modify-write operation. The bytecode is:

getfield i // Read iconst_1 // Push 1 iadd // Add putfield i // Write

Each of these four instructions is atomic individually, but the sequence is not atomic. Two threads can interleave between these instructions, causing lost updates.

The Fix: Use synchronized, AtomicInteger.incrementAndGet(), or LongAdder.

3 min read i++ read-modify-write

Q7 atomicity Is x = 5 atomic? What about long x = 5L?

A:

  • x = 5 (32-bit primitive) is atomic.
  • long x = 5L (64-bit) is not atomic on 32-bit JVMs (it's split into two 32-bit writes).
  • On 64-bit JVMs, long writes are atomic.
  • Guaranteed Atomic: Reads/writes to volatile long are atomic on all JVMs.
Interview Tip: If they ask about double, the same rules apply (not atomic unless volatile).
3 min read atomic long double

Q8 atomicity What is the "check-then-act" problem? Give an example.

A: Check-then-act is a race condition where you check a condition, and between the check and the action, another thread changes the state.

Example: Lazy initialization (broken):

if (instance == null) { // CHECK instance = new MyObject(); // ACT }

Thread A and Thread B both see instance == null. Thread A creates the object. Thread B creates a second object, overwriting A's work.

Fix: Use synchronized or ConcurrentHashMap.computeIfAbsent().

3 min read check-then-act lazy-init

Q9 atomicity What is the "put-if-absent" race condition and how do you fix it?

A: This is a specific check-then-act with a Map.

Broken:

if (!map.containsKey(key)) { map.put(key, computeValue(key)); }

Fixes:

  • synchronized around the whole block.
  • ConcurrentHashMap.putIfAbsent() (atomic).
  • ConcurrentHashMap.computeIfAbsent() (atomic, computes at most once).
Interview Expectation: Mention ConcurrentHashMap as the preferred solution for high concurrency.
3 min read put-if-absent ConcurrentHashMap

Q10 atomicity Is HashMap thread-safe? What happens if two threads modify it concurrently?

A: No. HashMap is not thread-safe. If two threads modify a HashMap concurrently (e.g., both calling put()), the following can happen:

  • Lost updates: One put overwrites the other.
  • Corrupted internal structure: The hash table's linked lists can become circular, causing infinite loops during iteration.
  • NullPointerException or ArrayIndexOutOfBoundsException when the internal array is resized and corrupted.

The Fix: Use ConcurrentHashMap or wrap with Collections.synchronizedMap(new HashMap<>()).

Topic 3.3: synchronized Deep Dive

Q12 synchronized What does a thread do when it enters a synchronized block?

A: It attempts to acquire the monitor (intrinsic lock) of the object.

  • If the lock is free, the thread acquires it and enters the block.
  • If the lock is held by another thread, the current thread enters the BLOCKED state and waits.
  • When the holding thread exits the synchronized block, the JVM selects one waiting thread to acquire the lock (not necessarily the first one; it's up to the OS scheduler).
The "Doubt Clarifier" – What happens if the lock is held by the same thread?
The lock is reentrant. The thread can re-enter the synchronized block without blocking (the lock count increments). This is why synchronized is called a "reentrant" lock.

Q14 synchronized Can you synchronized on a null reference?

A: No. It throws NullPointerException.

Q15 synchronized What is the difference between synchronized static method and instance method?

A:

  • Instance method: synchronized locks on this (the instance).
  • Static method: synchronized locks on Class.class (the class object).
public synchronized void instanceMethod() { } // Lock: this public static synchronized void staticMethod() { } // Lock: MyClass.class
The "Doubt Clarifier" – Can I have a synchronized static method and a synchronized instance method running concurrently?
Yes! Because they lock on different objects (Class vs this). They do not block each other. This can be a source of confusion and bugs.
3 min read static instance lock

Q16 synchronized What is a "monitor" in Java?

A: A monitor is a synchronization mechanism that provides:

  • Mutual exclusion: Only one thread can enter the monitor at a time.
  • Condition waiting: Threads can wait on the monitor and be notified when conditions change.

In Java, every object has a built-in monitor (intrinsic lock). synchronized acquires the monitor, and Object.wait() / notify() interact with the monitor's condition queue.

3 min read monitor intrinsic-lock

Q17 synchronized What is "lock coarsening" and "lock elision"?

A: These are JIT compiler optimizations:

OptimizationDescriptionExample
Lock CoarseningMerging adjacent synchronized blocks on the same object into one block.Two separate synchronized blocks back-to-back are merged into one to reduce overhead.
Lock ElisionRemoving a synchronized block entirely if the JIT detects that the lock is never contended (e.g., the object is thread-confined).A synchronized method called only from a single thread becomes a normal method.
Interview Tip: Mention these to show you understand that synchronized is not always slow; the JVM optimizes it heavily.

Topic 3.4: volatile Deep Dive

Q18 volatile What does volatile guarantee?

A: Two things:

  1. Visibility: Writes to a volatile variable are immediately visible to all threads. Reads from volatile read from main memory, not the CPU cache.
  2. Ordering (Happens-Before): A write to a volatile variable happens-before any subsequent read of that same variable. This prevents instruction reordering.

What it does NOT guarantee: Atomicity for compound actions (count++ is still broken).

3 min read volatile visibility ordering

Q19 volatile When should you use volatile?

A: Use volatile when:

  • You have a simple flag (e.g., running, shutdown).
  • You have a single variable that is written by one thread and read by others.
  • You have a configuration object that is published safely.

Example:

private volatile boolean shutdown; public void shutdown() { shutdown = true; // Write } public void run() { while (!shutdown) { // Read // Do work } }
3 min read volatile use-cases

Q20 volatile When should you NOT use volatile?

A:

  • Compound actions: count++ or total += x.
  • Dependent variables: If two variables must be updated together, volatile on one is not enough.
  • Long running computations with internal state: Use AtomicReference or synchronized.
2 min read volatile pitfalls

Q22 volatile Can you make long and double atomic without synchronized?

A: Yes, by using volatile. On 32-bit JVMs, long and double writes are split into two 32-bit writes. volatile ensures the write is atomic (the JVM uses lock prefix on x86 or equivalent memory barriers).

2 min read volatile long double

Q23 volatile What is the "Double-Checked Locking" pattern and why is it broken? How was it fixed?

A: This is one of the most famous concurrency pitfalls.

Broken Version:

public class Singleton { private static Singleton instance; public static Singleton getInstance() { if (instance == null) { // Check 1 synchronized (Singleton.class) { if (instance == null) { // Check 2 instance = new Singleton(); // Constructor } } } return instance; } }

Why it's broken: Due to instruction reordering, instance = new Singleton() can be reordered such that instance is assigned (and visible to other threads) before the constructor completes. Thread B sees instance != null and uses a partially constructed object.

The Fix (Java 5+): Make instance volatile.

private static volatile Singleton instance;

Even Better Fix: Use the static inner class pattern (no volatile needed):

public class Singleton { private Singleton() {} private static class Holder { private static final Singleton INSTANCE = new Singleton(); } public static Singleton getInstance() { return Holder.INSTANCE; } }
Interview Tip: If you mention double-checked locking, immediately explain the fix and why volatile solves it (happens-before relationship between the volatile write and subsequent reads).
5 min read double-checked-locking singleton volatile

Topic 3.5: final and Immutability

Q24 final How does final help with thread safety?

A:

  • Initialization Safety: final fields are guaranteed to be fully initialized before the constructor completes, and their values are visible to all threads after the constructor finishes, even without synchronization.
  • Immutability: final is a prerequisite for immutability. If all fields are final, the object cannot be modified after construction.

Example:

public class ImmutablePerson { private final String name; // Guaranteed visible to all threads private final int age; public ImmutablePerson(String name, int age) { this.name = name; this.age = age; } }
3 min read final initialization-safety

Q25 final What is "safe publication" and how does final help?

A: Safe publication is the process of making an object visible to other threads in a way that doesn't violate the JMM.

Safe Publication Mechanisms:

  • Static initialization: public static final MyClass obj = new MyClass();
  • volatile field: private volatile MyClass obj;
  • AtomicReference: private AtomicReference<MyClass> ref;
  • Synchronized blocks: synchronized block when setting the reference.

How final helps: The JMM guarantees that final fields are visible to all threads after the constructor completes, even without explicit synchronization. So if you safely publish the reference (e.g., via volatile), the final fields are guaranteed to be correct.

4 min read safe-publication final

Q26 immutability Can a class with mutable fields be thread-safe?

A: Yes, if you synchronize access to those fields. Example: java.util.Vector (all methods are synchronized). However, synchronization on every method is expensive, so modern concurrent classes avoid this (ConcurrentHashMap uses lock striping).

2 min read mutable thread-safe

Q27 immutability What is the difference between immutable and effectively immutable?

TermDefinitionExample
ImmutableObject cannot be changed after construction. All fields are final and no methods modify state.String, LocalDate, Integer
Effectively ImmutableObject is mutable but is never mutated after being safely published. It is treated as immutable.A List that is loaded once and never modified; Collections.unmodifiableList()
Interview Tip: Effectively immutable objects can be shared safely, but you must ensure they are never mutated after publication.
3 min read immutable effectively-immutable

Q28 immutability What is a "defensive copy" and why is it used?

A: A defensive copy is a copy of a mutable object that is returned to the caller, preventing the caller from modifying the original object.

Example:

public class ImmutablePerson { private final Date birthDate; // Date is mutable! public ImmutablePerson(Date birthDate) { this.birthDate = new Date(birthDate.getTime()); // Defensive copy on input } public Date getBirthDate() { return new Date(birthDate.getTime()); // Defensive copy on output } }

Without defensive copies, the caller could modify the Date object passed in or returned, breaking immutability.

Topic 3.6: ThreadLocal

Q29 ThreadLocal What is ThreadLocal and when should you use it?

A: ThreadLocal provides thread-local variables. Each thread has its own, independent copy of the variable.

Use cases:

  • Non-thread-safe objects: SimpleDateFormat, Random (use ThreadLocalRandom instead).
  • Per-thread context: User ID, transaction ID, request ID.
  • Database connections per thread: Each thread gets its own connection.

Example:

private static ThreadLocal<SimpleDateFormat> dateFormat = ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
3 min read ThreadLocal use-cases

Q30 ThreadLocal What is the memory leak problem with ThreadLocal?

A: In thread pools, threads are reused. If you don't call remove() on your ThreadLocal, the value remains attached to the thread forever, preventing garbage collection. This can cause memory leaks.

The Fix: Always call remove() in a finally block.

try { dateFormat.get().format(date); } finally { dateFormat.remove(); // Critical! }
Interview Tip: This is a very common interview question. Always mention the remove() method.
3 min read ThreadLocal memory-leak remove

Topic 3.7: Safe Publication

Q32 safe-publication What is the "safe publication" problem? Give an example.

A: Safe publication is ensuring that a reference to an object is visible to other threads after the object is fully constructed.

Unsafe Publication:

public class Unsafe { private MyObject obj; public void setObj(MyObject o) { this.obj = o; // No synchronization! } public MyObject getObj() { return this.obj; // No synchronization! } }

Thread A calls setObj(new MyObject()). Thread B calls getObj() and may see null or a partially constructed object because the write to obj is not visible.

Safe Publication:

private volatile MyObject obj; // Volatile ensures visibility
4 min read safe-publication visibility

Q33 safe-publication What are the safe publication patterns?

A:

  • Static Initialization: public static final MyClass obj = new MyClass();
  • Volatile Field: private volatile MyClass obj;
  • AtomicReference: private AtomicReference<MyClass> ref;
  • Synchronized Block: synchronized (this) { this.obj = new MyClass(); }
  • Concurrent Collections: ConcurrentHashMap.putIfAbsent(), ConcurrentMap.put().
Interview Tip: If you mention the volatile pattern, explain why it works: the write to the volatile field happens-before any subsequent read, ensuring the object's final fields are visible.
4 min read safe-publication patterns

Q34 safe-publication Why is it dangerous to publish this in a constructor?

A: Because the object is only partially constructed. If another thread sees the reference before the constructor completes, it will see default values for non-final fields (0, null, false) instead of the initialized values.

public class Bad { private final int value; public Bad() { new Thread(() -> System.out.println(value)).start(); // Dangerous! this.value = 42; } }

The thread may print 0 if it runs before value = 42.

The Fix: Never start threads or publish this inside a constructor. Use a factory method or call start() after construction.

Topic 3.8: Immutability

Q35 immutability What are the rules for creating an immutable class?

A:

  1. Make the class final (prevents subclassing).
  2. Make all fields final.
  3. Make all fields private (encapsulation).
  4. Do not provide setter methods.
  5. Do not expose mutable fields (return defensive copies).
  6. Ensure the constructor does not leak this.
3 min read immutability rules

Q36 immutability Why is String immutable? What are the benefits?

A:

Benefits of immutability:

  • Thread-safe: No synchronization needed when sharing String instances.
  • Caching: String literals are interned (cached) to save memory.
  • Security: You can pass String to sensitive methods (e.g., file paths, SQL queries) without worrying about the caller modifying it.
  • HashCode caching: The hash code is calculated once and cached, improving HashMap performance.
3 min read String immutability benefits

Q37 immutability Can you make a List immutable?

A:

  • Collections.unmodifiableList(list) – Creates a read-only view. The original list is still mutable.
  • List.copyOf(list) (Java 10+) – Creates a truly immutable copy. The original list can be mutated, but the copy is immutable.
  • List.of(...) (Java 9+) – Creates an immutable list.
Interview Tip: Mention that Collections.unmodifiableList() is not a "deep" immutability; if the list contains mutable objects, those objects can still be mutated.

Topic 3.9: Advanced JMM

Q38 JMM What is the "happens-before" relationship?

A: Happens-before is a JMM rule that defines when one action is guaranteed to be visible to another. If Action A happens-before Action B, then all changes made by A are visible to B.

Key Happens-Before Rules:

  • Program Order Rule: Within a single thread, actions happen-before subsequent actions.
  • Monitor Lock Rule: An unlock on a lock happens-before any subsequent lock on that same lock.
  • Volatile Rule: A write to a volatile field happens-before any subsequent read of that same field.
  • Thread Start Rule: Thread.start() happens-before any action in the started thread.
  • Thread Termination Rule: Any action in a thread happens-before Thread.join() returns.
  • Interruption Rule: Thread.interrupt() happens-before detection of the interrupt.
  • Finalizer Rule: The end of a constructor happens-before the finalize() method starts.
  • Transitivity: If A happens-before B, and B happens-before C, then A happens-before C.
5 min read JMM happens-before visibility

Q39 JMM What is the difference between "happens-before" and "synchronizes-with"?

A:

  • Synchronizes-with: A specific action (like unlocking a monitor or writing to a volatile) that establishes a happens-before relationship with another action.
  • Happens-before: The resulting ordering guarantee. For example, unlocking a monitor synchronizes-with a subsequent lock, and the unlock happens-before the lock.
Interview Tip: Don't overcomplicate this. Just know that volatile writes synchronize-with subsequent volatile reads, and synchronized unlock synchronizes-with subsequent locks.
3 min read JMM synchronizes-with happens-before

Q40 JMM What is "sequential consistency" and does Java guarantee it?

A: Sequential consistency is a memory model where:

  • All operations appear to happen in a global order.
  • That order is consistent with the program order in each thread.

Does Java guarantee sequential consistency? No! The JMM is weaker than sequential consistency to allow compiler/hardware optimizations. However, the JMM's happens-before rules provide enough guarantees for correct programming.

Interview Tip: If you mention this, emphasize that volatile and synchronized provide sequential consistency on the specific variables/locks, but the program as a whole is not sequentially consistent.
4 min read JMM sequential-consistency memory-model

Q41 interview Write a thread-safe singleton in Java.

Expected Answer (Static Inner Class – Best):

public class Singleton { private Singleton() {} private static class Holder { private static final Singleton INSTANCE = new Singleton(); } public static Singleton getInstance() { return Holder.INSTANCE; } }

Why it's thread-safe: The static inner class is loaded lazily (only when getInstance() is called). The JVM guarantees that class loading and initialization are thread-safe.

Alternative (Enum – Most Robust):

public enum Singleton { INSTANCE; }

Why enum is better: It handles serialization and reflection attacks automatically. It's the most robust singleton pattern.
