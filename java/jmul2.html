Subsection 2.1.2: The Native Thread – The OS-Level Reality

Every Java thread (platform thread) maps 1:1 to an OS thread. This is called the Native Thread Model.

What happens when you call new Thread().start()?

  1. JVM allocates memory: The JVM allocates a Thread object on the Java heap.
  2. JVM calls native method: Thread.start() calls the native method start0().
  3. OS thread creation: The JVM asks the OS to create a new native thread (via pthread_create on Linux, CreateThread on Windows).
  4. OS allocates resources: The OS allocates:
    • A thread control block (TCB) in kernel space.
    • A stack (typically 1 MB, configurable via -Xss).
    • A program counter (PC) and register set.
  5. JVM attaches: The JVM attaches the new native thread to the Java Thread object.
  6. Thread begins execution: The OS scheduler schedules the thread, and it begins executing the run() method.
The "Doubt Clarifier" – What is the stack size?
The stack stores method frames (local variables, parameters, return addresses). Each frame has a fixed size determined by the compiler. The stack size is configurable:
java -Xss1m MyClass # 1 MB stack (default) java -Xss512k MyClass # 512 KB stack (for many threads) java -Xss2m MyClass # 2 MB stack (for deep recursion)
The "Doubt Clarifier" – What happens if you exceed the stack size?
You get a StackOverflowError. This often happens with deep recursion or infinite recursion.
public static void recursive() { recursive(); // Infinite recursion }
Each call adds a new frame to the stack. When the stack overflows, the JVM throws StackOverflowError.

Subsection 2.1.4: The "Doubt Clarifier" – Why does Thread implement Runnable?

Look at the Thread class signature:

public class Thread implements Runnable { // ... @Override public void run() { if (target != null) { target.run(); } } }

Thread implements Runnable. This means you can pass a Thread instance to another Thread (though this is almost never done).

Why? Historical reasons. The designers wanted Thread to be a valid Runnable so that you could override run() directly when extending Thread.

But the better practice is to implement Runnable separately, as we'll see in Section 2.2.

Section 2.2: Creating a Thread – The Two Primary Ways

There are two fundamental ways to create a thread in Java. Let's explore both in extreme detail.

Subsection 2.2.1: Method 1 – Extending the Thread Class

Syntax:

public class MyThread extends Thread { @Override public void run() { System.out.println("Thread is running: " + Thread.currentThread().getName()); } } // Usage MyThread t = new MyThread(); t.start();

What happens internally:

  • You create a subclass of Thread.
  • You override run() (which is public void).
  • When you call start(), the JVM creates a native thread and invokes your run() method.

Pros:

  • Simple and straightforward.
  • You can access Thread methods directly (getName(), setPriority(), etc.).

Cons:

  • Single inheritance limitation: You cannot extend any other class.
  • Tight coupling: The task is baked into the thread class. You can't reuse the task with other execution mechanisms (e.g., thread pools).
  • Not flexible: You can't pass parameters to run() easily.
The "Doubt Clarifier" – Can I call run() directly instead of start()?
Yes, but do not do it.
MyThread t = new MyThread(); t.run(); // This runs in the current thread, NOT a new thread!
run() is just a regular method. Calling it directly doesn't create a new thread. The start() method is what creates the new thread and schedules it.

If you call run() directly, it executes in the calling thread, not in a separate thread.

Subsection 2.2.2: Method 2 – Implementing the Runnable Interface

Syntax:

public class MyRunnable implements Runnable { @Override public void run() { System.out.println("Runnable running: " + Thread.currentThread().getName()); } } // Usage MyRunnable task = new MyRunnable(); Thread t = new Thread(task); t.start();

What happens internally:

  • You create a class that implements Runnable.
  • You implement run().
  • You create a Thread instance and pass the Runnable to it.
  • When you call start(), the JVM creates a native thread and invokes target.run() (where target is your Runnable).

Pros:

  • Flexible: You can extend another class (since you're only implementing an interface).
  • Reusable: The same Runnable can be submitted to a thread pool (ExecutorService).
  • Separation of concerns: The task (what to do) is separate from the execution mechanism (how to run it).

Cons:

  • Slightly more verbose (you need to create a Thread explicitly).
The "Doubt Clarifier" – What is the Runnable functional interface?
@FunctionalInterface public interface Runnable { void run(); }
It's a functional interface, meaning you can use lambda expressions.

Subsection 2.2.3: Method 3 – Using Lambda Expressions (Java 8+)

Because Runnable is a functional interface, you can use lambdas:

// Lambda expression Thread t = new Thread(() -> { System.out.println("Lambda running: " + Thread.currentThread().getName()); }); t.start(); // Even shorter (method reference) Runnable task = System.out::println; Thread t2 = new Thread(task); t2.start();

Pros:

  • Very concise.
  • Captures local variables (effectively final).
The "Doubt Clarifier" – What does "effectively final" mean?
A variable is effectively final if it is not reassigned after initialization. Lambdas can only capture effectively final variables.
int x = 10; Runnable r = () -> System.out.println(x); // OK (x is effectively final) int y = 20; y = 30; // y is reassigned, NOT effectively final Runnable r2 = () -> System.out.println(y); // COMPILE ERROR!
Why this restriction? The lambda is executed on a different thread. To ensure consistency, the captured variables are copied (or reference is captured). If the variable could change, the copy would be stale.

Section 2.3: The Thread Lifecycle (States)

A thread in Java can be in one of six states (as defined by the Thread.State enum). Understanding these states is critical for debugging, performance tuning, and preventing liveness issues.

Subsection 2.3.1: The Six States – Complete Breakdown

NEWThread object created but not startednew Thread()thread.start() is called
RUNNABLEThread is ready to run, or is currently running on a CPU corethread.start() is calledThread scheduler assigns CPU time
BLOCKEDThread is blocked, waiting to acquire a monitor locksynchronized block/method, but lock is held by another threadLock is released by the holding thread

Subsection 2.3.2: Visualizing State Transitions

NEW | v RUNNABLE <----> BLOCKED | (acquires lock) | (wait) v WAITING <----> TIMED_WAITING | (timeout) | (notify) v TERMINATED
The "Doubt Clarifier" – Is RUNNABLE the same as "running"?
No! RUNNABLE means the thread is ready to run. It may be waiting for the OS scheduler to assign CPU time. In a busy system with more threads than cores, many RUNNABLE threads are actually waiting for CPU.
The "Doubt Clarifier" – What's the difference between WAITING and BLOCKED?
BLOCKED: Waiting for a monitor lock (synchronized). The thread is competing with other threads for the lock.
WAITING: Waiting for notification or termination. The thread is not competing for a lock; it's passively waiting for an external signal.

Subsection 2.3.3: Code Examples – Observing Thread States

Example 1: NEW and RUNNABLE

public class StateDemo { public static void main(String[] args) throws InterruptedException { Thread t = new Thread(() -> { for (int i = 0; i < 100_000_000; i++) { // Busy loop to keep thread RUNNABLE } }); System.out.println("After creation: " + t.getState()); // NEW t.start(); System.out.println("After start: " + t.getState()); // RUNNABLE (likely) t.join(); // Wait for it to finish System.out.println("After join: " + t.getState()); // TERMINATED } }

Output:

After creation: NEW After start: RUNNABLE After join: TERMINATED

Example 2: WAITING

public class WaitDemo { public static void main(String[] args) throws InterruptedException { Object lock = new Object(); Thread t = new Thread(() -> { synchronized (lock) { try { System.out.println("Thread waiting..."); lock.wait(); // Releases lock and waits System.out.println("Thread notified!"); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } } }); t.start(); Thread.sleep(100); // Give t time to enter WAITING state System.out.println("Thread state: " + t.getState()); // WAITING synchronized (lock) { lock.notify(); // Wake up t } t.join(); System.out.println("Thread state: " + t.getState()); // TERMINATED } }

Output:

Thread waiting... Thread state: WAITING Thread notified! Thread state: TERMINATED
The "Doubt Clarifier" – Why does wait() release the lock?
Because if it didn't, no other thread could enter the synchronized block to call notify(). The thread must give up the lock so that other threads can signal it.

Example 3: TIMED_WAITING

Thread t = new Thread(() -> { try { Thread.sleep(5000); // Sleep for 5 seconds } catch (InterruptedException e) { Thread.currentThread().interrupt(); } }); t.start(); Thread.sleep(100); // Give t time to enter sleep System.out.println(t.getState()); // TIMED_WAITING

Output:

TIMED_WAITING

Example 4: BLOCKED

public class BlockedDemo { private static final Object lock = new Object(); public static void main(String[] args) throws InterruptedException { Thread t1 = new Thread(() -> { synchronized (lock) { try { Thread.sleep(10000); // Hold lock for 10 seconds } catch (InterruptedException e) { Thread.currentThread().interrupt(); } } }); Thread t2 = new Thread(() -> { synchronized (lock) { System.out.println("Acquired lock!"); } }); t1.start(); Thread.sleep(100); // Give t1 time to acquire lock t2.start(); Thread.sleep(100); // Give t2 time to try to acquire lock System.out.println("t2 state: " + t2.getState()); // BLOCKED t1.join(); t2.join(); } }

Output:

t2 state: BLOCKED
The "Doubt Clarifier" – Why is t2 in BLOCKED and not WAITING?
Because t2 is trying to acquire the intrinsic lock (synchronized). It's not waiting for a notification; it's waiting for the lock to be released. That's the definition of BLOCKED.

Subsection 2.3.4: The "Doubt Clarifier" – Can a thread be in multiple states?

No. A thread is in exactly one state at any given time. The state transitions are mutually exclusive.

The "Doubt Clarifier" – Can a thread enter WAITING without owning a lock?
No! Object.wait() must be called from within a synchronized block. If you call wait() without owning the lock, you get IllegalMonitorStateException.
Object lock = new Object(); lock.wait(); // Throws IllegalMonitorStateException (not synchronized)

Section 2.4: Important Thread Methods

Let's explore the most commonly used methods of the Thread class, their semantics, and their pitfalls.

start() – The Only Way to Begin

Signature: public void start()

What it does:

  • Checks that the thread is in NEW state. If not, throws IllegalThreadStateException.
  • Allocates a native thread (OS thread).
  • Schedules the native thread to run.
  • The OS scheduler eventually invokes the thread's run() method.
The "Doubt Clarifier" – Why is start() synchronized?
Internally, start() is synchronized to prevent two threads from calling start() on the same Thread object simultaneously.
The "Doubt Clarifier" – Can I call start() twice on the same thread?
No. It will throw IllegalThreadStateException.
Thread t = new Thread(() -> {}); t.start(); t.start(); // Throws IllegalThreadStateException

run() – The Task Entry Point

Signature: public void run()

What it does: Contains the code executed by the thread.

The "Doubt Clarifier" – If I override run(), should I call super.run()?
Only if you want the default behavior (which runs the target Runnable). If you're extending Thread and overriding run(), you usually don't call super.run().
The "Doubt Clarifier" – What's the difference between start() and run()?
start() creates a new thread and calls run() on that thread.
run() is just a regular method call on the current thread.

join() – Waiting for Thread Termination

Signature:

  • public void join() throws InterruptedException – Wait indefinitely.
  • public void join(long millis) throws InterruptedException – Wait with timeout.
  • public void join(long millis, int nanos) throws InterruptedException – Fine-grained timeout.

What it does: The calling thread waits for the specified thread to terminate.

Example:

Thread t = new Thread(() -> { // Do some work try { Thread.sleep(2000); } catch (InterruptedException ignored) {} }); t.start(); t.join(); // Main thread waits here until t finishes System.out.println("t has finished");
The "Doubt Clarifier" – What happens if the thread is already terminated?
join() returns immediately.
The "Doubt Clarifier" – What if I call join(0)?
It means "wait forever" (same as join() with no timeout).
The "Doubt Clarifier" – Does join() release locks?
No. The calling thread holds its locks while waiting. This can cause deadlock if the other thread is waiting for one of those locks.

sleep() – Pausing the Current Thread

Signature:

  • public static void sleep(long millis) throws InterruptedException
  • public static void sleep(long millis, int nanos) throws InterruptedException

What it does: The current thread pauses for the specified time. It does not release any locks.

The "Doubt Clarifier" – Why is sleep() static?
Because it always operates on the current thread. You cannot make another thread sleep.
Thread.sleep(1000); // Current thread sleeps for 1 second
The "Doubt Clarifier" – What is the minimum sleep time?
The JVM's thread scheduler has a certain granularity (typically 1-10 ms on most systems). sleep(1) might actually sleep 1-10 ms depending on the OS.
The "Doubt Clarifier" – Is sleep() interrupted?
Yes. If another thread interrupts the sleeping thread, sleep() throws InterruptedException.
try { Thread.sleep(10000); } catch (InterruptedException e) { System.out.println("Woken up early!"); Thread.currentThread().interrupt(); // Re-interrupt }

yield() – Yielding the CPU

Signature: public static void yield()

What it does: A hint to the JVM scheduler that the current thread is willing to give up its CPU time.

The "Doubt Clarifier" – Does yield() guarantee anything?
No. It's just a hint. The scheduler may ignore it.
The "Doubt Clarifier" – When should I use yield()?
Almost never. It's a legacy method. In modern applications, you should not rely on yield() for any correctness or performance guarantees.

interrupt() – Interrupting a Thread

Signature: public void interrupt()

What it does: Sets the thread's interrupt flag and, if the thread is blocked in certain methods, wakes it up.

The "Doubt Clarifier" – What methods throw InterruptedException?
  • Thread.sleep()
  • Object.wait()
  • Thread.join()
  • BlockingQueue.take()
  • Lock.lockInterruptibly()
  • Future.get()
The "Doubt Clarifier" – What does interrupt() do to a thread that's not blocked?
It just sets the interrupt flag. The thread can check it later with Thread.interrupted() or Thread.currentThread().isInterrupted().
The "Doubt Clarifier" – How do I handle InterruptedException properly?
Always propagate it or restore the interrupt flag.

Good:
public void myMethod() throws InterruptedException { Thread.sleep(1000); // Propagate }
Good:
public void myMethod() { try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); // Restore flag } }
Bad (swallow):
public void myMethod() { try { Thread.sleep(1000); } catch (InterruptedException e) { // Swallow silently! BAD! } }
The "Doubt Clarifier" – What's the difference between interrupted() and isInterrupted()?
interrupted(): Static method. Returns the interrupt flag and clears it.
isInterrupted(): Instance method. Returns the interrupt flag and does not clear it.
Thread t = Thread.currentThread(); t.interrupt(); boolean flag1 = t.isInterrupted(); // true boolean flag2 = Thread.interrupted(); // true (clears flag) boolean flag3 = t.isInterrupted(); // false (flag was cleared)

setDaemon() and isDaemon() – Daemon Threads

Signature:

  • public void setDaemon(boolean on)
  • public boolean isDaemon()

What it does: Marks a thread as a daemon thread.

The "Doubt Clarifier" – What happens when all non-daemon threads finish?
The JVM exits, even if daemon threads are still running.
Thread daemon = new Thread(() -> { while (true) { // Infinite loop } }); daemon.setDaemon(true); daemon.start(); // Main thread ends, JVM exits. Daemon thread is killed.
Use cases for daemon threads:
  • Garbage collection (GC threads).
  • Background health checks.
  • Monitoring and logging.
The "Doubt Clarifier" – Can you call setDaemon() after start()?
No. It throws IllegalThreadStateException.
Thread t = new Thread(); t.start(); t.setDaemon(true); // Throws IllegalThreadStateException

Subsection 2.5.3: Using Callable and Future with ExecutorService

ExecutorService executor = Executors.newSingleThreadExecutor(); // Submit a Callable Future<Integer> future = executor.submit(() -> { Thread.sleep(2000); return 42; }); // Do other work while the task runs... try { // Block and wait for the result Integer result = future.get(); System.out.println("Result: " + result); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } catch (ExecutionException e) { // The task threw an exception Throwable cause = e.getCause(); System.out.println("Task failed: " + cause.getMessage()); } executor.shutdown();
The "Doubt Clarifier" – What is ExecutionException?
It's a wrapper for any exception thrown by the task. You can call getCause() to get the underlying exception.
The "Doubt Clarifier" – Can I cancel a running task?
Yes, but it requires cooperation from the task.
Future<Integer> future = executor.submit(() -> { while (!Thread.currentThread().isInterrupted()) { // Do work... if (Thread.currentThread().isInterrupted()) { return -1; // Clean up and exit } } return 0; }); future.cancel(true); // Interrupts the thread
The "Doubt Clarifier" – What does cancel(true) do?
  • Sets the interrupt flag on the thread.
  • If the thread is blocked, it wakes it up (throws InterruptedException).
  • The task must check the interrupt flag to actually stop.
What does cancel(false) do?
  • Sets the interrupt flag but does not interrupt the thread.
  • The task must check isInterrupted() on its own.

Section 2.6: Common Pitfalls with Thread Creation

Let's list the most common mistakes developers make when creating threads.

Pitfall 1: Calling run() Instead of start()

Thread t = new Thread(() -> System.out.println("Hello")); t.run(); // Runs on the main thread, NOT a new thread!

Fix: Always call start().

Pitfall 2: Starting a Thread Twice

Thread t = new Thread(() -> {}); t.start(); t.start(); // Throws IllegalThreadStateException

Fix: Create a new thread if you need to run the task again.

Pitfall 3: Forgetting to Handle InterruptedException

try { Thread.sleep(1000); } catch (InterruptedException e) { // Ignored! BAD! }

Fix: Always propagate or restore the interrupt flag.

Pitfall 4: Using Thread.stop(), suspend(), or resume()

These are deprecated. They are unsafe and can leave objects in inconsistent states.

Fix: Use interrupt() for cooperative cancellation.

Pitfall 5: Not Using Thread Pools

Creating a new thread for every request is expensive and can exhaust system resources.

Fix: Use Executors.newFixedThreadPool() or Executors.newCachedThreadPool().
