🧠 Category A: Mental Model & Hardware

Q1: I get that count++ isn't atomic, but what about count = count + 1? Is that any different?

A: No. Absolutely zero difference. The bytecode is identical. The compiler generates the same getfield, iconst_1, iadd, putfield sequence. Both are non-atomic. The only way to make it atomic is to use synchronized, AtomicInteger, or LongAdder.

Q2: You said x = 5 is atomic for 32-bit primitives. What about long and double? They are 64-bit.

A: Excellent catch. On 32-bit JVMs, writing a 64-bit long or double is not atomic by default. The JVM splits it into two 32-bit writes. If you don't use volatile, Thread A might write the high 32 bits, Thread B reads the variable and gets a garbage value (half of the old value, half of the new). If you use volatile, the JVM guarantees the read/write is atomic (even on 32-bit systems). This is explicitly defined in the JMM. Always use volatile for long/double that are shared across threads if you need atomic writes.

🧠 Category A: Mental Model & Hardware

Q3: Why doesn't the CPU just always read from main memory and avoid the visibility problem?

A: Because it would be catastrophically slow. Main memory (RAM) operates at ~50-100 nanoseconds per access. The CPU operates at ~0.3 nanoseconds per cycle. If the CPU went to main memory for every single variable access, it would be hundreds of times slower. Caches (L1/L2) are absolutely essential for performance. We accept the complexity of cache coherency to get 100x speedups.

Q4: The JVM can reorder instructions. Does that mean the order of lines in my source code is completely meaningless?

A: In a single-threaded program, reordering is safe because the JVM guarantees as-if-serial semantics. The program's output appears as if it ran in the order you wrote, even if the JVM or CPU reordered things. In a multi-threaded program, this guarantee is broken for threads that don't synchronize. The JMM defines exactly where reordering is allowed and where it is forbidden (via happens-before rules). Without those rules, the order is indeed arbitrary.

🧠 Category A: Mental Model & Hardware

Q5: What is a "happens-before" relationship? I keep hearing that term.

A: It's the JMM's formal way of defining when one action is guaranteed to be visible to another. If Action A happens-before Action B, then all changes made by A are visible to B. There are specific rules:

  • Program order rule: Within a thread, code order.
  • Monitor lock rule: Unlock of a monitor happens-before any subsequent lock of that same monitor.
  • Volatile rule: Writing to a volatile variable happens-before any subsequent read of that variable.
  • Thread start rule: Thread.start() happens-before any action in the started thread.
  • Thread join rule: Thread.join() happens-before any action after the join returns.

If two actions do not have a happens-before relationship, the JVM is allowed to reorder them, and visibility is not guaranteed.

🧵 Category B: Thread Creation & Lifecycle

Q6: If I extend Thread and override run(), do I still need to pass a Runnable?

A: No. If you override run(), the Thread's internal target field (the Runnable) is ignored. Your overridden run() runs instead. However, extending Thread is strongly discouraged. Implement Runnable and use composition.

Q7: What if my Runnable throws an unhandled exception? The thread just dies?

A: Yes. If an exception escapes run(), the thread terminates and transitions to TERMINATED. The exception does not propagate to the parent thread. To handle it: use Thread.setDefaultUncaughtExceptionHandler() or provide a custom handler via Thread.setUncaughtExceptionHandler().

Thread t = new Thread(() -> { throw new RuntimeException("Boom!"); });
        t.setUncaughtExceptionHandler((thread, ex) -> {
            System.out.println("Thread " + thread.getName() + " crashed: " + ex);
        });
        t.start();

🧵 Category B: Thread Creation & Lifecycle

Q8: When a thread is in BLOCKED state, does it consume CPU cycles?

A: No. BLOCKED means the thread is waiting for a lock. It is not scheduled for CPU time. It's parked in the OS's wait queue. Once the lock is released, the OS moves it back to RUNNABLE. This is why BLOCKED threads don't spin-wait and don't waste CPU cycles.

Q9: What is the difference between WAITING and TIMED_WAITING in practice?

A: WAITING waits indefinitely until someone explicitly notifies it (Object.notify()) or interrupts it. It will wait forever if the notification never comes — dangerous if you don't have a fail-safe. TIMED_WAITING has a timeout. It will automatically wake up after the timeout, even without a notification. Always prefer timed waits over indefinite waits in production code to prevent deadlocks.

🧵 Category B: Thread Creation & Lifecycle

Q10: Can I restart a TERMINATED thread?

A: No. A thread in TERMINATED state cannot be restarted. start() will throw IllegalThreadStateException. You must create a new Thread object if you want to run the same task again.

Q11: What does Thread.yield() actually do? Should I ever use it?

A: It tells the OS scheduler: "I'm done with my current time slice, give another thread a chance." The scheduler may ignore it entirely. Almost never use it. In modern applications, yield() is a relic. The OS scheduler does a much better job of load-balancing. Using yield() can actually hurt performance. The only niche use is in tight spin-loops, but even then, Thread.sleep(0) or LockSupport.parkNanos(1) is preferred.

🧵 Category B: Thread Creation & Lifecycle

Q12: If I call thread.interrupt(), does the thread stop immediately?

A: Absolutely not. interrupt() does not stop the thread. It does two things: (1) Sets the thread's internal interrupt flag to true. (2) If the thread is blocked in a method that throws InterruptedException (like sleep() or wait()), it wakes it up and throws the exception. The thread must cooperate by checking Thread.interrupted() or catching InterruptedException and gracefully shutting down. Java does not have a safe way to forcibly stop a thread (Thread.stop() is deprecated and unsafe).

Q13: If I swallow InterruptedException, what happens to the interrupt flag?

A: If you catch InterruptedException, the interrupt flag is automatically cleared (set to false). If you swallow the exception without re-interrupting, your thread loses the signal that it was interrupted. This is a huge bug. Correct pattern:

try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // Restore the flag
            return; // or handle gracefully
        }

Or better: public void myMethod() throws InterruptedException { Thread.sleep(1000); }

🧵 Category B: Thread Creation & Lifecycle

Q14: If I call future.cancel(true), does the thread stop?

A: No. cancel(true) calls interrupt() on the thread executing the task. If the task is blocked in a method that throws InterruptedException, it will wake up and throw the exception. If the task is running CPU-bound code, interrupt() just sets the flag. The task must explicitly check Thread.currentThread().isInterrupted() to stop.

Future<Integer> future = executor.submit(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                // Do heavy computation
            }
            return -1; // Cancelled
        });
        future.cancel(true);

Q15: Why can't I use Future with a plain Thread? I have to use ExecutorService.

A: Exactly. Future is tied to the ExecutorService API. A plain Thread doesn't know how to return a result or handle exceptions. The ExecutorService acts as a framework that manages task lifecycles. If you want a result from a plain thread, you'd have to use shared mutable state and synchronized/volatile, which is error-prone. That's why Callable and Future were introduced alongside ExecutorService.

🛑 Category C: Daemon Threads & JVM Shutdown

Q16: If the JVM exits while a daemon thread is running, what happens to the daemon thread?

A: The JVM simply stops the daemon thread abruptly. It does not call any cleanup or finally blocks. The thread is killed at the native level. This is why daemon threads should only be used for non-critical background tasks (like monitoring or caching). If your thread holds important resources (database connections, file handles), do not make it a daemon thread.

Q17: If I have a non-daemon thread stuck in an infinite loop, will the JVM shut down?

A: No. The JVM will wait indefinitely for all non-daemon threads to finish. If your main thread exits but a non-daemon thread is stuck, the JVM will hang forever. You'll need to kill the process externally (kill -9). This is why you should always design threads to respond to interrupts or have timeouts.

🛑 Category C: Daemon Threads & JVM Shutdown

Q18: Can I turn a running thread into a daemon?

A: No. setDaemon(true) must be called before start(). Once a thread is running, you cannot change its daemon status. Attempting to do so throws IllegalThreadStateException.

📌 Category C Summary

  • Daemon threads are killed abruptly on JVM shutdown — no cleanup.
  • Non-daemon threads prevent JVM shutdown.
  • Daemon status must be set before start().

🚀 Category D: Advanced Nuisance Questions

Q19: What is a "spurious wakeup"?

A: In Object.wait(), a thread can wake up without notify() or notifyAll() being called. This is a spurious wakeup. It's a rare but real phenomenon on some operating systems. The fix: always call wait() in a loop, checking the condition.

synchronized (lock) {
            while (!condition) {
                lock.wait();  // Spurious wakeup: loop checks condition again
            }
            // Proceed with condition true
        }

Never use if (!condition) wait(); because spurious wakeup will break it.

Q20: What is "pinning" in Virtual Threads? (Preview for Java 21)

A: When a virtual thread is running and enters a synchronized block or calls native code (JNI), it cannot be unmounted from the underlying carrier thread (OS thread). It becomes "pinned." If many virtual threads get pinned simultaneously, you lose the benefits of virtual threads. The workaround: use ReentrantLock instead of synchronized in code that will run on virtual threads.

🚀 Category D: Advanced Nuisance Questions

Q21: If I have 1000 threads, is the JVM going to crash?

A: On modern hardware, 1000 threads is usually fine, but it depends on your stack size. Each thread consumes ~1 MB of native memory (stack). 1000 threads = 1 GB of native memory, which might be fine for a server with 16 GB RAM. 10,000 threads = 10 GB of native memory, which will likely exhaust memory and crash. This is exactly why Virtual Threads (Java 21+) were created – they allow millions of threads with minimal memory overhead.

Q22: What is the difference between Thread.sleep(0) and Thread.yield()?

A: Thread.sleep(0) forces the current thread to relinquish the CPU and enter a temporary TIMED_WAITING state (though the timeout is 0, it still yields). It is more forceful and will cause a context switch. Thread.yield() is a hint and may be ignored. It does not guarantee a context switch. In practice, Thread.sleep(0) is often used in spin-wait loops to reduce CPU usage.

🚀 Category D: Advanced Nuisance Questions

Q23: What is the "Double-Checked Locking" pattern, and why is it broken (and how was it fixed)?

A: Double-checked locking was a performance optimization to reduce synchronization overhead in singleton initialization.

Broken version:

public class Singleton {
            private static Singleton instance;
            public static Singleton getInstance() {
                if (instance == null) {           // Check 1 (no sync)
                    synchronized (Singleton.class) {
                        if (instance == null) {   // Check 2 (sync)
                            instance = new Singleton();
                        }
                    }
                }
                return instance;
            }
        }

Why broken? Due to instruction reordering, instance = new Singleton() can be reordered such that instance is assigned (and visible to other threads) before the constructor completes. Thread B sees instance != null and uses a partially constructed object.

The fix (Java 5+): Use volatile for instance. volatile ensures the constructor completes before the reference becomes visible to other threads.

private static volatile Singleton instance;

Better fix: Use the static inner class pattern or an enum singleton.

🚀 Category D: Advanced Nuisance Questions

Q24: Can I use synchronized with Integer, Boolean, or other wrapper classes?

A: Technically yes, but do not do this. Wrapper objects (like Integer) are immutable and may be interned by the JVM. Synchronizing on Integer.valueOf(1) might lock the same object across different parts of your code unexpectedly, causing deadlocks. Always synchronize on a dedicated lock object:

private final Object lock = new Object();
        synchronized (lock) {
            // critical section
        }

Q25: What is a "thread leak"?

A: A thread leak occurs when you create threads but never clean them up. For example, if you create a new Thread for every request and don't call join() or properly manage the thread pool, threads pile up in memory. Eventually, you run out of native memory (stack space) or hit OS thread limits. Prevention: Always use thread pools (ExecutorService) and ensure you call executor.shutdown() when the application stops.

🚀 Category D: Advanced Nuisance Questions

Q26: What is "Escape Analysis" and how does it affect concurrency?

A: Escape Analysis is a JIT compiler optimization. It determines if an object "escapes" the scope of a method (i.e., is returned, passed to another thread, or stored in a global field). If an object does not escape, the JIT can allocate it on the stack (not the heap) and eliminate synchronization entirely (lock elision). If you write synchronized on a method that only ever runs in a single thread, the JIT can remove the lock entirely because it detects that the lock object doesn't escape. This is a performance optimization that happens at runtime.

Q27: Why are wait() and notify() defined in Object, not Thread?

A: Because they operate on monitors (intrinsic locks), which are associated with every Java object, not just threads. Any object can be used as a lock. wait() releases the lock of that specific object and waits for a notification on that same object. This design allows any object to serve as a synchronization point. If wait() were in Thread, you'd be limited to locking on thread objects, which is a terrible idea.

🚀 Category D: Advanced Nuisance Questions

Q28: Can I call notify() without owning the lock?

A: No. It throws IllegalMonitorStateException. You must be in a synchronized block on the same object. Object lock = new Object(); lock.notify(); throws IllegalMonitorStateException.

Q29: What is the difference between notify() and notifyAll()?

A: notify() wakes up one arbitrary thread that is waiting on the monitor. The scheduler chooses which one. notifyAll() wakes up all threads waiting on the monitor. They then compete for the lock. Only one will acquire it; the others will go back to BLOCKED. Rule of thumb: Always use notifyAll() unless you have a very specific reason to use notify(). notify() can lead to "lost notifications" if the wrong thread wakes up. notifyAll() is safer, though slightly more expensive.

🚀 Category D: Advanced Nuisance Questions

Q30: What is a "thread dump" and how do I get one?

A: A thread dump shows the stack traces of all running threads, along with their states and locks. It's the single most important tool for debugging deadlocks and hangs. How to get one:

  • Linux/Unix: kill -3 <pid> (prints to stdout of the JVM process).
  • Windows: Press Ctrl+Break in the console.
  • jstack: jstack <pid> (prints to stdout).
  • JVisualVM / JConsole: GUI tools.
  • Programmatically: Thread.getAllStackTraces().

Q31: What is a "deadlock" exactly? Can you give me a real-world analogy?

A: Real-world analogy: Two people at a dinner table. Person A has a fork and needs a knife. Person B has a knife and needs a fork. Neither will give up their utensil. They sit there forever. That's deadlock. In Java: Thread A holds lock X, needs lock Y. Thread B holds lock Y, needs lock X. Neither releases. Both block forever. The fix: Always acquire locks in a consistent global order. Or use tryLock() with a timeout.

🚀 Category D: Advanced Nuisance Questions

Q32: What is "livelock" then?

A: Two people trying to pass each other in a narrow hallway. Both step left, then both step right, then both step left again, never making progress. They're not blocked (they're moving), but they're also not making any useful progress. In Java, livelock often happens when threads keep retrying failed operations but fail in the exact same way every time. Fix: Add exponential backoff with random jitter. Thread A waits a random amount of time before retrying; Thread B waits a different random amount. Eventually, one succeeds.

Q33: Why do we have both ThreadLocal and ScopedValue (Java 21+)?

A: ThreadLocal is mutable and inheritable (via InheritableThreadLocal). It's error-prone because child threads can inherit values, leading to unexpected state leaks and memory leaks (if you don't call remove()). ScopedValue is immutable and not inheritable by default. It's designed for structured concurrency. You set a value for a specific scope, and all threads running within that scope see the value. Once the scope ends, the value is gone. It's safer and more memory-efficient.

🚀 Category D: Advanced Nuisance Questions

Q34: If I use ExecutorService, do I still need to worry about volatile or synchronized inside my tasks?

A: Yes! The ExecutorService only manages the execution of tasks on threads. It does not protect shared mutable state. If multiple tasks (running on different threads) access the same shared variable, you still need volatile or synchronized to ensure visibility and atomicity. The ExecutorService is about execution, not synchronization.

Q35: Does Java have a "thread-safe random number generator"?

A: Yes. java.util.concurrent.ThreadLocalRandom is the preferred random generator for concurrent applications. It avoids contention on a shared Random instance. Usage: ThreadLocalRandom.current().nextInt(100);

📋 Quick Reference – Key Takeaways

🔹 Atomicity

Use AtomicInteger, synchronized, or LongAdder. count++ is NOT atomic.

🔸 Visibility

Use volatile or synchronized. Without it, changes may not be seen by other threads.

🔹 Interrupts

interrupt() sets a flag. Thread must check it. Never swallow InterruptedException.

🔸 Thread Pools

Always use ExecutorService in production. Never create raw Thread objects.

🔹 Deadlocks

Always acquire locks in consistent order. Use tryLock() with timeouts.

🔸 Wait/Notify

Always use wait() in a loop (spurious wakeups). Prefer notifyAll() over notify().

⚠️ Most Common Mistakes

  • Calling run() instead of start() – Runs on current thread, not new one.
  • Swallowing InterruptedException – Loses the interrupt signal. Always re-interrupt or propagate.
  • Using Thread.stop() – Deprecated and unsafe. Leaves objects in inconsistent state.
  • Not using thread pools – Creates memory leaks and performance issues.
  • Synchronizing on wrapper objects – Can cause unexpected deadlocks.
  • Double-checked locking without volatile – Broken on Java < 5. Use volatile or static inner class.
  • Not handling spurious wakeups – Always use while loop with wait().

💡 Remember: Concurrency bugs are probabilistic. They'll show up in production at 3 AM.
