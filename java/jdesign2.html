Singleton in Java – Eager vs Lazy Initialization

In Java, the Singleton Design Pattern ensures that only one instance of a class exists in the JVM and provides a global access point to that instance. Below we explain two common approaches: Eager Initialization and Lazy Initialization.

1️⃣ Eager Initialization

In this approach, the instance is created as soon as the class is loaded into memory. 


public class SingletonEager {
    private static final SingletonEager instance = new SingletonEager();

    private SingletonEager() {}

    public static SingletonEager getInstance() {
        return instance;
    }
}
  • ✅ Advantages: Simple and inherently thread-safe.
  • ❌ Disadvantages: Instance is created even if never used, which can waste memory if it’s a heavy object.

2️⃣ Lazy Initialization

Here, the instance is created only when it’s needed for the first time. This can save resources but requires extra care in multithreaded environments. 


public class SingletonLazy {
    private static SingletonLazy instance;

    private SingletonLazy() {}

    public static SingletonLazy getInstance() {
        if (instance == null) {
            instance = new SingletonLazy();
        }
        return instance;
    }
}
  • ✅ Advantages: Saves memory because the instance is created only when required.
  • ❌ Disadvantages: Not thread-safe by default. Multiple threads can create multiple instances simultaneously.

🔍 Reflection and Singleton

The Singleton Design Pattern ensures that only one instance of a class is created throughout the lifecycle of an application. However, Java Reflection can break the Singleton property by allowing access to the class's private constructor and creating multiple instances.

⚠️ How Reflection Breaks Singleton

Reflection provides the ability to inspect and manipulate classes, methods, and constructors at runtime. Using getDeclaredConstructor(), it can bypass access modifiers and invoke the private constructor, which allows creation of multiple instances. 

// Singleton Class
class Singleton {
    private static Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

// Breaking Singleton using Reflection
Constructor constructor = Singleton.class.getDeclaredConstructor();
constructor.setAccessible(true);
Singleton s1 = constructor.newInstance();
Singleton s2 = constructor.newInstance();
System.out.println(s1 == s2); // false 🚨

In this example, Reflection bypasses the private constructor and creates two separate instances, violating the Singleton principle.

✅ Prevention

To prevent Reflection from breaking Singleton, add a check inside the constructor. If an instance already exists, throw an exception to block further creation. 

class Singleton {
    private static Singleton instance;

    private Singleton() {
        if (instance != null) {
            throw new IllegalStateException("Instance already created");
        }
    }

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

Now, even if Reflection tries to call the constructor again, it will throw an IllegalStateException.

🔒 Alternatives to Ensure Singleton Safety

  • Enum-based Singleton: Using enum is the most secure way to implement Singleton in Java. It prevents reflection, serialization, and cloning issues.
  • Bill Pugh Singleton: Use an inner static helper class to ensure thread-safe and lazy initialization. 
// Enum Singleton (Reflection Proof)
enum SingletonEnum {
    INSTANCE;
}

📌 Summary

  • Reflection can break Singleton by invoking private constructors.
  • Prevention: Add a constructor check to throw an exception if instance exists.
  • Best practice: Use Enum Singleton for guaranteed safety.

💾 Serialization and Singleton

The Singleton Pattern ensures that only one instance of a class exists. However, when a Singleton class implements Serializable, the process of serialization and deserialization can break this guarantee by creating a new object instance.

⚠️ How Serialization Breaks Singleton

During serialization, the Singleton object is converted into a byte stream and stored. When deserialized, a new object is created from that stream, instead of returning the already existing instance. 

// Singleton Class with Serialization
class Singleton implements Serializable {
    private static Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

// Breaking Singleton with Deserialization
ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("file.obj"));
out.writeObject(Singleton.getInstance());

ObjectInputStream in = new ObjectInputStream(new FileInputStream("file.obj"));
Singleton s2 = (Singleton) in.readObject();

System.out.println(Singleton.getInstance() == s2); // false 🚨

Here, the deserialized object s2 is not the same as the original Singleton instance.

✅ Prevention

To prevent multiple instances during deserialization, implement the readResolve() method in your Singleton class. The readResolve() method ensures that the deserialized object resolves to the existing Singleton instance. 

class Singleton implements Serializable {
    private static Singleton instance;

    private Singleton() {
        if (instance != null) {
            throw new IllegalStateException("Instance already created");
        }
    }

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }

    // Fix for Serialization issue
    protected Object readResolve() {
        return getInstance();
    }
}

Now, deserialization will not create a new instance. Instead, it will return the same Singleton object.

🔒 Safer Alternatives

  • Enum-based Singleton: Enums automatically handle serialization by JVM, ensuring a single instance always.
  • Bill Pugh Singleton: Works well with serialization if readResolve() is implemented. 
// Enum Singleton (Serialization Proof)
enum SingletonEnum {
    INSTANCE;
}

📌 Summary

  • Serialization creates a new object during deserialization, breaking Singleton.
  • Fix: Implement readResolve() to return the existing instance.
  • Best practice: Use Enum Singleton for built-in serialization safety.

🧬 Cloning and Singleton

The Singleton Pattern ensures that only one instance of a class exists throughout the application. However, if the Singleton class implements Cloneable, the clone() method can be used to create a new object, thereby breaking the Singleton contract.

⚠️ How Cloning Breaks Singleton

When clone() is invoked on a Singleton instance, it returns a new instance of the object instead of reusing the existing one. 

// Singleton with Cloneable
class Singleton implements Cloneable {
    private static Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

Singleton s1 = Singleton.getInstance();
Singleton s2 = (Singleton) s1.clone();

System.out.println(s1 == s2); // false 🚨

Here, s2 is a completely new instance created by clone(), violating the Singleton rule.

✅ Prevention

To prevent cloning from breaking Singleton, you can override the clone() method and throw a CloneNotSupportedException. 

class Singleton implements Cloneable {
    private static Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }

    @Override
    protected Object clone() throws CloneNotSupportedException {
        throw new CloneNotSupportedException();
    }
}

Now, any attempt to clone the Singleton will fail with an exception, preserving the single instance guarantee.

🔒 Safer Alternatives

  • Do not implement Cloneable: By default, objects that don’t implement Cloneable cannot be cloned.
  • Enum Singleton: Enum-based Singleton is inherently safe from cloning, as Enums cannot be cloned by design.

📌 Summary

  • Cloning creates a new object, breaking Singleton.
  • Fix: Override clone() to throw CloneNotSupportedException.
  • Best practice: Avoid Cloneable altogether, or use Enum Singleton for safety.

⚡ Multi-threading and Singleton

In a multi-threaded environment, improper implementation of Singleton can result in the creation of multiple instances. This happens when multiple threads simultaneously enter the critical section where the instance is initialized.

🚨 The Problem

If the getInstance() method is not synchronized, two threads can pass the instance == null check at the same time and both create new instances. 

class Singleton {
    private static Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton(); // ❌ not thread-safe
        }
        return instance;
    }
}

In this case, multiple threads can create multiple Singleton objects, breaking the Singleton rule.

✅ Prevention Techniques

There are several ways to make Singleton thread-safe:

  1. Synchronized Method

    Simple but slower due to method-level lock.

    public static synchronized Singleton getInstance() {
    if (instance == null) {
        instance = new Singleton();
    }
    return instance;
}
  2. Double-Checked Locking

    Efficient, synchronizes only the first initialization.

    public static Singleton getInstance() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) {
                instance = new Singleton();
            }
        }
    }
    return instance;
}
  3. Bill Pugh Singleton (Static Inner Class)

    Relies on JVM class loading, thread-safe and lazy-loaded.

    class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
  4. Enum Singleton

    Best practice — thread-safe, prevents reflection, serialization, and cloning issues.

    enum Singleton {
    INSTANCE;
}

📌 Summary

  • Without synchronization, multiple threads can create multiple Singleton objects.
  • Solutions: Synchronized method (simple), Double-checked locking (efficient), Bill Pugh (best lazy-loading), or Enum Singleton (most robust).
  • Enum Singleton is recommended for production due to built-in safety against reflection, serialization, cloning, and concurrency issues.

Double-Checked Locking (Singleton)

Thread-safe lazy initialization with minimal synchronization overhead.

What it solves

Avoids synchronizing every access to a Singleton by locking only during the first initialization, while remaining thread-safe.

How it works

  • First check without a lock to skip synchronization after initialization.
  • Synchronized block only if the instance is not created.
  • Second check inside the lock to prevent duplicate construction.

Key requirement

volatile on the instance field to prevent instruction reordering and ensure visibility across threads.

Java implementation

final class Logger {
    private static volatile Logger instance;

    private Logger() { }

    static Logger getInstance() {
        if (instance == null) {
            synchronized (Logger.class) {
                if (instance == null) {
                    instance = new Logger();
                }
            }
        }
        return instance;
    }

    void log(String message) {
        System.out.println(message);
    }
}

When to use

  • Singleton needs lazy initialization.
  • High read frequency, low initialization frequency.
  • You need to minimize contention after startup.

Alternatives

  • Initialization-on-demand holder (Bill Pugh).
  • Enum-based Singleton.
  • Eager initialization if startup cost is acceptable.

Bill Pugh Singleton

A simple, thread-safe, and efficient way to implement Singleton using a static inner helper class.

How it works

  • A private static inner class holds the Singleton instance.
  • The inner class is loaded only when getInstance() is called.
  • JVM guarantees thread-safe class loading, so no explicit synchronization is required.

Java Implementation

final class Logger {
    private Logger() { }

    private static class Holder {
        private static final Logger INSTANCE = new Logger();
    }

    static Logger getInstance() {
        return Holder.INSTANCE;
    }

    void log(String message) {
        System.out.println(message);
    }
}

Advantages

  • Lazy initialization – instance created only when needed.
  • Thread-safe without synchronization.
  • No need for volatile or double-checked locking.
  • Simple and easy to read.

Advanced Singleton Implementations in Java

Beyond basic Eager and Lazy Initialization, Java developers often use Bill Pugh Singleton and Enum Singleton for more robust, efficient, and thread-safe implementations.

5️⃣ Bill Pugh Singleton (Inner Static Helper Class)

This method uses a static inner helper class to hold the Singleton instance. The instance is created only when the inner class is loaded, ensuring both lazy loading and thread safety without synchronization overhead. 


public class SingletonBillPugh {
    private SingletonBillPugh() {}

    private static class Holder {
        private static final SingletonBillPugh INSTANCE = new SingletonBillPugh();
    }

    public static SingletonBillPugh getInstance() {
        return Holder.INSTANCE;
    }
}
  • ✅ Advantages: Thread-safe, lazy-loaded, no synchronization cost.
  • ❌ Disadvantages: Slightly less intuitive for beginners.

6️⃣ Enum Singleton

The simplest and most robust Singleton implementation uses enum. Java ensures that enums have only one instance, making it inherently thread-safe and serialization-safe. 


public enum SingletonEnum {
    INSTANCE;

    public void doSomething() {
        System.out.println("Doing work...");
    }
}
  • ✅ Advantages: Simple, thread-safe, serialization-safe, recommended by Joshua Bloch in Effective Java.
  • ❌ Disadvantages: Cannot extend other classes since enums already extend java.lang.Enum.

🔥 Which Singleton Should You Use?

Bill Pugh Singleton → Best when you want lazy loading and thread safety with no performance cost.
Enum Singleton → Best when you want the simplest, safest, and most recommended solution.

Enum Singleton in Java

The Enum Singleton is widely regarded as the most robust and recommended way to implement the Singleton Design Pattern in Java. Unlike other approaches, it is thread-safe, serialization-safe, and protected against reflection attacks by default.

6️⃣ Enum Singleton Implementation

In Java, enums guarantee that only one instance of each enum constant exists. This makes enums naturally suited for implementing singletons with minimal code. 


public enum SingletonEnum {
    INSTANCE;

    public void doSomething() {
        System.out.println("Doing work...");
    }
}

Usage:
SingletonEnum.INSTANCE.doSomething();

  • ✅ Advantages: Simple, thread-safe, serialization-safe, reflection-safe.
  • ✅ Recommended by Joshua Bloch in Effective Java.
  • ❌ Disadvantages: Cannot extend other classes since enums already extend java.lang.Enum.

⚙️ Enum Singleton with State and Methods

An Enum Singleton can maintain state and expose methods, just like a regular class. This makes it powerful for managing global configuration or shared resources. 


public enum ConfigManager {
    INSTANCE;

    private String configValue;

    ConfigManager() {
        this.configValue = "default-config";
    }

    public String getConfigValue() {
        return configValue;
    }

    public void setConfigValue(String value) {
        this.configValue = value;
    }
}

Usage:
ConfigManager.INSTANCE.setConfigValue("production");
System.out.println(ConfigManager.INSTANCE.getConfigValue());

🔒 Thread Safety in Enum Singleton

Enum singletons are inherently thread-safe because the enum instance is created once and managed by the JVM. However, if your singleton contains mutable state, you should still use synchronization techniques or thread-safe classes like ConcurrentHashMap and AtomicInteger to ensure safe access.

Payment Gateway Integration using Factory Pattern

The Factory Pattern allows us to decide which payment object (Credit Card, UPI, PayPal, NetBanking) should be created at runtime based on user input, without exposing the creation logic to the client.

Why Factory Pattern?

  • Encapsulates object creation in one place.
  • Supports multiple payment types without cluttered if-else logic in business code.
  • Open/Closed Principle → easy to add new payment methods like ApplePay or Crypto.
  • Runtime flexibility → user decides payment method dynamically.

Step 1: Define Payment Interface

interface Payment {
    void pay(double amount);
}

Step 2: Implement Concrete Payment Methods

class CreditCardPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paid " + amount + " using Credit Card");
    }
}

class UPIPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paid " + amount + " using UPI");
    }
}

class PayPalPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paid " + amount + " using PayPal");
    }
}

class NetBankingPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paid " + amount + " using NetBanking");
    }
}

Step 3: Create Payment Factory

class PaymentFactory {
    static Payment getPaymentMethod(String type) {
        if (type.equalsIgnoreCase("CREDIT")) {
            return new CreditCardPayment();
        } else if (type.equalsIgnoreCase("UPI")) {
            return new UPIPayment();
        } else if (type.equalsIgnoreCase("PAYPAL")) {
            return new PayPalPayment();
        } else if (type.equalsIgnoreCase("NETBANKING")) {
            return new NetBankingPayment();
        }
        throw new IllegalArgumentException("Invalid payment type: " + type);
    }
}

Step 4: Client Usage

public class Main {
    public static void main(String[] args) {
        Payment payment1 = PaymentFactory.getPaymentMethod("UPI");
        payment1.pay(2500.0);

        Payment payment2 = PaymentFactory.getPaymentMethod("PAYPAL");
        payment2.pay(5000.0);
    }
}

Output

Paid 2500.0 using UPI
Paid 5000.0 using PayPal

When to Use

  • You have multiple payment methods (Credit, UPI, PayPal, NetBanking).
  • The exact payment type should be decided at runtime.
  • You want to follow clean architecture principles (Open/Closed, Single Responsibility).

Abstract Factory Pattern in Payment Gateway

The Abstract Factory Pattern allows creating a family of related objects without specifying their concrete classes. In a payment gateway system, each payment type (Credit Card, UPI, PayPal, NetBanking) may require a combination of components: Payment, Validator, and TransactionHandler.

Problem

A payment gateway must support multiple payment types. Each type is not just a single object, but a family of related components. For example, Credit Card payments need:

  • A validator for card details
  • A payment processor
  • A transaction handler for confirmations and errors

Creating these objects separately using if-else or switch-case logic spreads creation code throughout the system and violates the Open/Closed Principle.

Solution: Abstract Factory

Use an Abstract Factory interface with methods to create each related component. Then implement a Concrete Factory for each payment type (CreditCardFactory, UPIFactory, etc.). This ensures consistency among related components and centralizes creation logic. 

interface PaymentFactory {
    Payment createPayment();
    Validator createValidator();
    TransactionHandler createTransactionHandler();
}

class CreditCardFactory implements PaymentFactory {
    public Payment createPayment() { return new CreditCardPayment(); }
    public Validator createValidator() { return new CreditCardValidator(); }
    public TransactionHandler createTransactionHandler() { return new CreditCardTransactionHandler(); }
}

class UPIFactory implements PaymentFactory {
    public Payment createPayment() { return new UPIPayment(); }
    public Validator createValidator() { return new UPIValidator(); }
    public TransactionHandler createTransactionHandler() { return new UPITransactionHandler(); }
}

Concrete Products

// Credit Card Components
class CreditCardPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paid " + amount + " using Credit Card");
    }
}
class CreditCardValidator implements Validator {
    public boolean validate(String details) {
        System.out.println("Validating Credit Card details");
        return true;
    }
}
class CreditCardTransactionHandler implements TransactionHandler {
    public void handle(String transactionId) {
        System.out.println("Handling Credit Card transaction " + transactionId);
    }
}

// UPI Components
class UPIPayment implements Payment {
    public void pay(double amount) {
        System.out.println("Paid " + amount + " using UPI");
    }
}
class UPIValidator implements Validator {
    public boolean validate(String details) {
        System.out.println("Validating UPI details");
        return true;
    }
}
class UPITransactionHandler implements TransactionHandler {
    public void handle(String transactionId) {
        System.out.println("Handling UPI transaction " + transactionId);
    }
}

Client Usage

public class Main {
    public static void main(String[] args) {
        PaymentFactory factory = new CreditCardFactory();
        
        Payment payment = factory.createPayment();
        Validator validator = factory.createValidator();
        TransactionHandler handler = factory.createTransactionHandler();
        
        if (validator.validate("card details")) {
            payment.pay(5000.0);
            handler.handle("TXN12345");
        }
    }
}

Advantages of Abstract Factory

  • Encapsulates families of related objects for each payment type.
  • Ensures consistency across components (Payment + Validator + Handler).
  • Centralizes creation logic and improves maintainability.
  • Makes it easy to add new payment types without modifying client code.

Factory Patterns: Simple Factory vs Factory Method

Factory patterns allow object creation to be decoupled from client code. While the Simple Factory centralizes object creation, the Factory Method lets subclasses decide which objects to instantiate, promoting extensibility and adherence to the Open/Closed Principle.

1. Simple Factory

Simple Factory centralizes object creation in one class. The client provides input, and the factory decides which concrete object to return. 

interface Payment {
    void pay(double amount);
}

class CreditCardPayment implements Payment {
    public void pay(double amount) { System.out.println("Paid " + amount + " using Credit Card"); }
}

class UPIPayment implements Payment {
    public void pay(double amount) { System.out.println("Paid " + amount + " using UPI"); }
}

class PaymentFactory {
    static Payment getPaymentMethod(String type) {
        if (type.equalsIgnoreCase("CREDIT")) return new CreditCardPayment();
        else if (type.equalsIgnoreCase("UPI")) return new UPIPayment();
        throw new IllegalArgumentException("Unknown payment type");
    }
}

// Client
Payment payment = PaymentFactory.getPaymentMethod("UPI");
payment.pay(500);

Pros: Simple, easy to maintain if few product types.
Cons: Adding new types requires modifying the factory (violates Open/Closed Principle).

2. Factory Method

Factory Method defines an abstract interface for object creation, letting subclasses decide which concrete object to instantiate. 

interface Payment {
    void pay(double amount);
}

class CreditCardPayment implements Payment {
    public void pay(double amount) { System.out.println("Paid " + amount + " using Credit Card"); }

class UPIPayment implements Payment {
    public void pay(double amount) { System.out.println("Paid " + amount + " using UPI"); }

abstract class PaymentFactory {
    abstract Payment createPayment();
}

class CreditCardFactory extends PaymentFactory {
    Payment createPayment() { return new CreditCardPayment(); }
}

class UPIFactory extends PaymentFactory {
    Payment createPayment() { return new UPIPayment(); }
}

// Client
PaymentFactory factory = new CreditCardFactory();
Payment payment = factory.createPayment();
payment.pay(1000);

Pros: Extensible, follows Open/Closed Principle, no modification needed to add new product types.
Cons: More classes, slightly higher complexity.

Understanding Factory Patterns: Simple Factory vs Factory Method vs Abstract Factory

Factory patterns help create objects while hiding the complexity from the client. They are widely used in software to manage object creation, improve flexibility, and maintain clean architecture.

1. Simple Factory

Simple Factory is a single class responsible for creating objects based on input. The client only knows which type it wants and lets the factory create it.

Example: A food delivery app that creates different meal objects. The client requests "Pizza" or "Burger," and the factory returns the right meal object. Another example is a payment system where the factory returns either a Credit Card or UPI payment processor based on user choice.

Simple Factory is easy to implement and works well for small sets of products. However, adding new types requires modifying the factory class.

2. Factory Method

Factory Method defines an interface for creating objects but lets subclasses decide which concrete object to create. It follows the Open/Closed Principle, meaning you can add new types without modifying existing code.

Example: A ride-hailing app where different vehicle types like Car, Bike, or Auto have separate factories. Each factory knows how to create its specific vehicle object. Another example is a notification system with Email, SMS, or Push notifications, each having its own factory.

Factory Method adds flexibility and makes the system more maintainable when product types grow.

3. Abstract Factory

Abstract Factory is used when you need to create families of related objects. It provides an interface for creating multiple products that must work together.

Example: A UI library supporting multiple themes. The factory creates related components like Buttons, TextFields, and Checkboxes that all match the chosen theme. Another example is an e-commerce system: each payment method (Credit Card, PayPal, UPI) has related objects like Validator, TransactionHandler, and Receipt generator. Abstract Factory ensures consistency across all these components.

Abstract Factory is highly extensible and perfect for complex systems where multiple related objects must be created together.

Prototype Pattern: Clone Objects Efficiently

The Prototype Pattern is a creational design pattern that allows you to create **new objects by cloning existing ones**. It is especially useful when creating new objects is **expensive or repetitive**, and you want to **reuse existing instances**.

What is Prototype Pattern?

In the Prototype Pattern, an object provides a method to **clone itself**, creating a new instance with the same properties. Clients can then **modify the cloned object** as needed without altering the original.

Key Components:

  • Prototype: Defines the cloning method (e.g., clone()).
  • Concrete Prototype: Implements the cloning method for specific objects.
  • Client: Uses the prototype to create new objects dynamically.

Java Implementation Example

// Prototype
abstract class Enemy implements Cloneable {
    protected String type;
    protected int health;
    protected int attack;

    public Enemy(String type, int health, int attack) {
        this.type = type;
        this.health = health;
        this.attack = attack;
    }

    public abstract Enemy clone();

    public void display() {
        System.out.println(type + " [Health: " + health + ", Attack: " + attack + "]");
    }
}

// Concrete Prototype
class Orc extends Enemy {
    public Orc(int health, int attack) {
        super("Orc", health, attack);
    }

    @Override
    public Enemy clone() {
        return new Orc(this.health, this.attack);
    }
}

// Concrete Prototype
class Goblin extends Enemy {
    public Goblin(int health, int attack) {
        super("Goblin", health, attack);
    }

    @Override
    public Enemy clone() {
        return new Goblin(this.health, this.attack);
    }
}

// Client
public class PrototypeClient {
    public static void main(String[] args) {
        Enemy orc1 = new Orc(100, 15);
        Enemy orc2 = orc1.clone(); 
        Enemy goblin1 = new Goblin(50, 10);
        Enemy goblin2 = goblin1.clone();

        orc2.display();     // Orc [Health: 100, Attack: 15]
        goblin2.display();  // Goblin [Health: 50, Attack: 10]
    }
}

Here, Orc and Goblin objects are cloned from existing instances. This avoids repetitive initialization and allows creating multiple similar enemies efficiently.

  • Graphic editors: duplicating shapes or layers.
  • Document editors: creating new documents from templates.
  • Caching systems: duplicating frequently used objects instead of recreating them.

  • Reduces repetitive code for object creation.
  • Supports dynamic and runtime object creation.
  • Improves performance when object creation is expensive.
  • Encourages reuse of existing objects.

Disadvantages

  • Requires careful handling of deep vs shallow copies.
  • Can be complex if objects have circular references.
  • Cloning may not always capture all dependencies correctly.

Prototype, Flyweight, and Memento are all creational or state-related design patterns that deal with **object management and memory efficiency**. Understanding the differences helps choose the right pattern for your application.

The Prototype Pattern allows creating new objects by **cloning existing objects** and modifying them independently. It is ideal when many similar objects are needed with minor variations.

Pros: Fast creation, preserves base attributes, reduces duplication. Cons: Cloning complex objects can be tricky.

The Flyweight Pattern reduces memory usage by **sharing objects** with common intrinsic state. Extrinsic state is supplied externally when needed.

Example: In a shooting game, 1000 bullets share the same Bullet object (intrinsic state like shape and damage), while position and trajectory are provided externally.

The Memento Pattern captures and restores the **state of an object** without violating encapsulation. It is commonly used for undo/redo functionality or game checkpoints.

Example: Save the player’s state (health, position, inventory) in a game to allow undo or restore from a checkpoint.

Pros: Preserves object state safely, decouples state storage. Cons: Memory usage grows with many snapshots; not used for creating new objects.

Flyweight Pattern: Efficient Object Sharing

The Flyweight Pattern is a structural design pattern focused on **memory optimization**. It allows sharing objects with **intrinsic state** while supplying **extrinsic state** externally, reducing the overhead of creating many similar objects.

What is Flyweight Pattern?

Flyweight Pattern minimizes memory usage by sharing as much data as possible among similar objects. Intrinsic state (shared) is stored in the flyweight, while extrinsic state (unique per instance) is supplied externally.

It is particularly useful when an application requires **thousands of objects with repetitive data**, such as bullets in a game, letters in a text editor, or trees in a forest.

Java Implementation Example

import java.util.HashMap;
import java.util.Map;

// Flyweight
class Bullet {
    private final String type; // intrinsic state

    public Bullet(String type) {
        this.type = type;
    }

    public void display(int x, int y) { // extrinsic state
        System.out.println("Bullet Type: " + type + " at position (" + x + "," + y + ")");
    }
}

// Flyweight Factory
class BulletFactory {
    private static final Map<String, Bullet> bullets = new HashMap<>();

    public static Bullet getBullet(String type) {
        if (!bullets.containsKey(type)) {
            bullets.put(type, new Bullet(type));
        }
        return bullets.get(type);
    }
}

// Client
public class Game {
    public static void main(String[] args) {
        Bullet b1 = BulletFactory.getBullet("Standard");
        Bullet b2 = BulletFactory.getBullet("Standard");
        Bullet b3 = BulletFactory.getBullet("Explosive");

        b1.display(10, 20);
        b2.display(15, 25);
        b3.display(50, 80);

        System.out.println("b1 == b2? " + (b1 == b2)); // true, same shared object
    }
}

In this example, multiple bullets share the same object (intrinsic state: type), while their positions (extrinsic state) are provided externally. Memory usage is reduced because repeated objects are not recreated.

Real-World Examples

  • Gaming: Thousands of bullets share the same bullet object; position and trajectory are extrinsic.
  • Text Editors: Letters share font and style, but their position in the document is extrinsic.
  • 3D Worlds / Forests: Trees share texture and type, while position is unique.
  • UI Icons: Same icons reused across screens with different positions.

Advantages of Flyweight Pattern

  • Memory efficiency: Reduces redundant object creation.
  • Performance: Less object instantiation overhead.
  • Reusability: Shared objects can be used across multiple contexts.

Disadvantages

  • Complexity: Separating intrinsic and extrinsic state requires careful design.
  • Limited flexibility: Intrinsic state is immutable and shared.
  • Not suitable: Objects with highly dynamic or unique state cannot be shared.

Memento Pattern: Capture and Restore Object State

The Memento Pattern is a behavioral design pattern that allows capturing and restoring an object's internal state without violating encapsulation. It is commonly used for **undo/redo functionality**, **checkpoints**, and **state rollback**.

What is Memento Pattern?

Memento stores a snapshot of an object's internal state externally so that the object can be restored to that state later. This allows the **originator object** to remain encapsulated while providing rollback capabilities.

Key components:

  • Originator: The object whose state needs saving.
  • Memento: Stores the snapshot of the originator's state.
  • Caretaker: Manages mementos (saving/restoring) without accessing their content.

Java Implementation Example

// Memento class
class GameMemento {
    private final int health;
    private final int level;

    public GameMemento(int health, int level) {
        this.health = health;
        this.level = level;
    }

    public int getHealth() { return health; }
    public int getLevel() { return level; }
}

// Originator
class Player {
    private int health;
    private int level;

    public void setState(int health, int level) {
        this.health = health;
        this.level = level;
    }

    public void showState() {
        System.out.println("Player Health: " + health + ", Level: " + level);
    }

    public GameMemento saveState() {
        return new GameMemento(health, level);
    }

    public void restoreState(GameMemento memento) {
        this.health = memento.getHealth();
        this.level = memento.getLevel();
    }
}

// Caretaker
import java.util.Stack;

class GameHistory {
    private final Stack<GameMemento> history = new Stack<>();

    public void save(Player player) {
        history.push(player.saveState());
    }

    public void undo(Player player) {
        if (!history.isEmpty()) {
            player.restoreState(history.pop());
        }
    }
}

// Client code
public class Game {
    public static void main(String[] args) {
        Player player = new Player();
        GameHistory history = new GameHistory();

        player.setState(100, 1);
        player.showState();

        history.save(player);

        player.setState(50, 2);
        player.showState();

        history.save(player);

        player.setState(10, 3);
        player.showState();

        System.out.println("Undoing...");
        history.undo(player);
        player.showState();

        System.out.println("Undoing again...");
        history.undo(player);
        player.showState();
    }
}

In this example, Player is the originator whose state (health and level) is saved in a Memento. GameHistory acts as the caretaker managing the mementos, allowing undo functionality without exposing Player's internal state.

Real-World Examples

  • Text editors: Undo/Redo functionality.
  • Games: Player checkpoint restoration.
  • Financial applications: Transaction rollback.
  • Design software: Revert object modifications.

Advantages of Memento

  • Preserves object state safely without violating encapsulation.
  • Allows undo/redo and state rollback easily.
  • Decouples state storage from the originator object.

Disadvantages

  • Memory overhead can be high if many mementos are stored.
  • Managing large snapshots may impact performance.
  • Not intended for creating new objects, only state restoration.

Adapter Pattern: Bridging Incompatible Interfaces

The Adapter Pattern is a structural design pattern that allows **two incompatible interfaces to work together**. It acts as a bridge, translating calls from your system to a third-party API without changing either side.

What is Adapter Pattern?

Adapter allows an existing class or third-party API (Adaptee) to be used with your system's expected interface (Target) by wrapping it in a translator (Adapter). This ensures **compatibility without modifying** the existing system or API.

Key Components:

  • Target Interface: The interface your system expects.
  • Adaptee: The existing third-party API with an incompatible interface.
  • Adapter: Wraps the Adaptee and implements the Target interface.

Java Implementation Example

// Target interface
interface PaymentProcessor {
    void pay(double amount);
}

// Adaptee: Third-party API
class PayPalAPI {
    public void makePayment(String account, double total) {
        System.out.println("PayPal payment of $" + total + " from account " + account);
    }
}

// Adapter
class PayPalAdapter implements PaymentProcessor {
    private PayPalAPI paypal;

    public PayPalAdapter(PayPalAPI paypal) {
        this.paypal = paypal;
    }

    @Override
    public void pay(double amount) {
        paypal.makePayment("myAccount@example.com", amount); // translate call
    }
}

// Client
public class OnlineStore {
    public static void main(String[] args) {
        PaymentProcessor processor = new PayPalAdapter(new PayPalAPI());
        processor.pay(100.0); // works seamlessly
    }
}

In this example, PayPalAdapter allows the system to use PayPalAPI through the PaymentProcessor interface. Calls to `pay()` are internally translated to `makePayment()`.

Real-World Examples

  • Payment gateways: Integrating PayPal, Stripe, or other APIs using a uniform interface.
  • Logging: Adapting third-party loggers to your application's logging interface.
  • Legacy systems: Converting XML-based responses to JSON expected by modern systems.
  • UI adapters: Wrapping new component libraries to match old component interfaces.

Advantages

  • Allows integration of incompatible interfaces without modifying existing code.
  • Improves **reusability** by decoupling your system from third-party APIs.
  • Makes code more maintainable and flexible for future changes.

Disadvantages

  • Introduces an extra layer, increasing complexity.
  • Too many adapters may clutter the code if multiple APIs change frequently.
  • May slightly impact performance due to additional translation logic.

Facade Pattern: Simplifying Complex Systems

The Facade Pattern is a structural design pattern that provides a **simplified interface** to a complex subsystem of classes. It hides the internal complexity and allows the client to interact with the system using a single, easy-to-use interface.

What is Facade Pattern?

Facade acts as a **unified interface** for a set of interfaces in a subsystem. It makes the subsystem easier to use without exposing its inner workings.

Key Components:

  • Facade: Provides the simplified interface to clients.
  • Subsystem Classes: Complex classes with specific functionalities.
  • Client: Uses the Facade instead of interacting with subsystem classes directly.

// Subsystem classes
class PaymentService {

}

    public void checkStock() {
        System.out.println("Checking inventory...");

class ShippingService {
    public void ship() {
        System.out.println("Shipping product...");
    }

// Facade
class OrderFacade {

    private ShippingService shipping;

    public OrderFacade() {
        payment = new PaymentService();
        inventory = new InventoryService();
        shipping = new ShippingService();
    }

        inventory.checkStock();
        shipping.ship();
        System.out.println("Order placed successfully!");
    }
}

// Client
public class OnlineStore {
    public static void main(String[] args) {
        OrderFacade orderFacade = new OrderFacade();
        orderFacade.placeOrder(); // Simple interface hides complexity
    }
}

In this example, OrderFacade provides a single method `placeOrder()` to the client. Internally, it coordinates multiple subsystem classes like PaymentService, InventoryService, and ShippingService, hiding complexity.

Proxy Pattern: Controlling Access to Objects

The Proxy Pattern is a structural design pattern that provides a **surrogate or placeholder** for another object to control access to it. It is commonly used for **lazy loading, access control, logging, and caching**.

What is Proxy Pattern?

Proxy provides a representative or placeholder for another object. Clients interact with the proxy as if it were the real object. The proxy can control or modify requests before passing them to the real object.

Key Components:

  • Subject: Defines the common interface for RealSubject and Proxy.
  • RealSubject: The actual object the proxy represents.
  • Proxy: Controls access to the RealSubject and may add extra functionality.

Java Implementation Example

// Subject interface
interface Image {
    void display();
}

// RealSubject
class RealImage implements Image {
    private String filename;

    public RealImage(String filename) {
        this.filename = filename;
        loadFromDisk();
    }

    private void loadFromDisk() {
        System.out.println("Loading " + filename + " from disk...");
    }

    public void display() {
        System.out.println("Displaying " + filename);
    }
}

// Proxy
class ProxyImage implements Image {
    private RealImage realImage;
    private String filename;

    public ProxyImage(String filename) {
        this.filename = filename;
    }

    public void display() {
        if (realImage == null) {
            realImage = new RealImage(filename); // Lazy loading
        }
        realImage.display();
    }
}

// Client
public class ImageViewer {
    public static void main(String[] args) {
        Image image1 = new ProxyImage("photo1.jpg");
        Image image2 = new ProxyImage("photo2.jpg");

        // Image is loaded from disk only when display is called
        image1.display(); 
        image1.display(); // Does not load again

        image2.display();
    }
}

In this example, ProxyImage controls access to RealImage and implements **lazy loading**. Images are only loaded from disk when they are actually displayed, improving performance and resource usage.

Decorator Pattern: Extending Functionality Dynamically

The Decorator Pattern is a structural design pattern that allows you to **add new responsibilities to objects dynamically** without modifying existing code. It is ideal when you want to extend behavior in a flexible and reusable way.

What is Decorator Pattern?

Decorator wraps an existing object and provides **additional functionality** while maintaining the same interface. Multiple decorators can be stacked to combine behaviors at runtime.

Key Components:

  • Component: Base interface (e.g., Notification)
  • Concrete Component: Original implementation (e.g., EmailNotification, SMSNotification)
  • Decorator: Abstract class implementing the component and holding a reference to it
  • Concrete Decorator: Adds new behavior (e.g., PriorityNotification, EncryptedNotification)

Java Implementation Example

// Component
interface Notification {

// Concrete Components

    public void send(String message) {

        this.wrappee = wrappee;

}

class PriorityNotification extends NotificationDecorator {
    public PriorityNotification(Notification wrappee) {
        super(wrappee);

    }
}

        super(wrappee);

State Pattern: Changing Behavior Based on Object State

The State Pattern is a behavioral design pattern that allows an object to **change its behavior when its internal state changes**. It helps avoid complex conditional statements and promotes cleaner, more maintainable code.

What is State Pattern?

The State Pattern encapsulates **state-specific behavior into separate classes**. The context object delegates behavior to its current state object, which can change dynamically at runtime.

Key Components:

  • State Interface: Defines common behavior for all states.
  • Concrete States: Implement behavior specific to a state.
  • Context: Maintains a reference to the current state and delegates behavior.

Java Implementation Example

// State Interface
interface TCPState {
    void open(TCPConnection connection);
    void close(TCPConnection connection);
    void acknowledge(TCPConnection connection);
}

// Concrete States
class ClosedState implements TCPState {
    public void open(TCPConnection connection) {
        System.out.println("Opening connection...");
        connection.setState(new EstablishedState());
    }
    public void close(TCPConnection connection) {
        System.out.println("Connection is already closed.");
    }
    public void acknowledge(TCPConnection connection) {
        System.out.println("Cannot acknowledge, connection is closed.");
    }
}

class EstablishedState implements TCPState {
    public void open(TCPConnection connection) {
        System.out.println("Connection is already open.");
    }
    public void close(TCPConnection connection) {
        System.out.println("Closing connection...");
        connection.setState(new ClosedState());
    }
    public void acknowledge(TCPConnection connection) {
        System.out.println("Acknowledging data in established connection.");
    }
}

// Context
class TCPConnection {
    private TCPState state;

    public TCPConnection() {
        this.state = new ClosedState();
    }

    public void setState(TCPState state) {
        this.state = state;
    }

    public void open() {
        state.open(this);
    }

    public void close() {
        state.close(this);
    }

    public void acknowledge() {
        state.acknowledge(this);
    }
}

// Client
public class TCPClient {
    public static void main(String[] args) {
        TCPConnection connection = new TCPConnection();

        connection.acknowledge(); // Closed state behavior
        connection.open();        // Moves to Established state
        connection.acknowledge(); // Established state behavior
        connection.close();       // Back to Closed state
    }
}

In this example, TCPConnection delegates behavior to its current state object. The connection behaves differently depending on whether it is in ClosedState or EstablishedState.

State Pattern: Manage Object Behavior Based on State

The State Pattern allows an object to **change its behavior dynamically when its internal state changes**. Instead of using complex conditional logic, each state is represented by a separate class encapsulating its behavior.

What is State Pattern?

In the State Pattern, a **context object** delegates its behavior to a **state object** representing its current state. Each state implements the same interface but handles actions differently based on the state it represents.

Key Components:

  • State Interface: Defines methods that all concrete states must implement.

    public State getCoinInsertedState() { return coinInsertedState; }

}

What is Template Method Pattern?

  • Encapsulates invariant parts of an algorithm in a base class.

Command Pattern: Encapsulating Operations as Objects

The Command Pattern is a behavioral design pattern that turns **requests or operations into objects**, allowing you to parameterize clients, queue operations, log actions, and support undo/redo functionality.

What is Command Pattern?

In the Command Pattern, an operation is wrapped inside a **command object**. This object contains the method to execute the action and optionally to undo it. It decouples the **invoker** (caller) from the **receiver** (object performing the action).

Key Components:

  • Command Interface: Declares methods like execute() and undo().
  • Concrete Commands: Implements specific operations (TypeCommand, DeleteCommand, FormatCommand).
  • Receiver: The object performing the actual work (TextEditor).
  • Invoker: Calls commands and manages history for undo/redo.

Java Implementation Example

// Command Interface
interface Command {
    void execute();
    void undo();
}

// Receiver
class TextEditor {
    private StringBuilder content = new StringBuilder();

    public void type(String text) { content.append(text); }
    public void delete(int count) {
        if (count <= content.length()) content.delete(content.length() - count, content.length());
    }
    public String getContent() { return content.toString(); }
}

// Concrete Command
class TypeCommand implements Command {
    private TextEditor editor;
    private String text;

    public TypeCommand(TextEditor editor, String text) {
        this.editor = editor;
        this.text = text;
    }

    public void execute() { editor.type(text); }
    public void undo() { editor.delete(text.length()); }
}

// Invoker
import java.util.Stack;

class CommandManager {
    private Stack undoStack = new Stack<>();
    private Stack redoStack = new Stack<>();

    public void executeCommand(Command command) {
        command.execute();
        undoStack.push(command);
        redoStack.clear();
    }

    public void undo() {
        if (!undoStack.isEmpty()) {
            Command command = undoStack.pop();
            command.undo();
            redoStack.push(command);
        }
    }

    public void redo() {
        if (!redoStack.isEmpty()) {
            Command command = redoStack.pop();
            command.execute();
            undoStack.push(command);
        }
    }
}

// Client
public class CommandClient {
    public static void main(String[] args) {
        TextEditor editor = new TextEditor();
        CommandManager manager = new CommandManager();

        Command typeHello = new TypeCommand(editor, "Hello ");
        Command typeWorld = new TypeCommand(editor, "World");

        manager.executeCommand(typeHello);
        manager.executeCommand(typeWorld);

        System.out.println(editor.getContent()); // Hello World

        manager.undo();
        System.out.println(editor.getContent()); // Hello 

        manager.redo();
        System.out.println(editor.getContent()); // Hello World
    }
}

In this example, each typing action is a **command object**. The CommandManager manages the history of executed commands, enabling **undo and redo** operations.

Real-World Examples

  • Undo/Redo in text editors (VS Code, Word, Google Docs)
  • Remote controls for smart home devices
  • Macro recording and playback in applications
  • Transactional systems for reversible operations

Advantages

  • Encapsulates requests as objects.
  • Supports undo/redo by storing command history.
  • Decouples invoker and receiver.
  • Enables queuing, logging, or scheduling operations.

Disadvantages

  • Increases the number of classes (one for each command).
  • May become complex if many commands are required.
  • Command objects may need to store additional state for undo operations.

Command vs Memento

Feature Command Memento
Purpose Encapsulates operations as objects Captures and restores object state
Undo/Redo Implemented by calling command.undo() Implemented by restoring a saved state
History Stores executed command objects Stores snapshots of the originator's state

Composite Pattern: Treat Objects and Compositions Uniformly

The Composite Pattern allows you to **treat individual objects (leaves) and compositions (containers) uniformly**. It is ideal for **tree-like structures**, such as file systems, menus, or organizational hierarchies, where elements can contain other elements recursively.

What is Composite Pattern?

In the Composite Pattern, both **single objects (Leaf)** and **groups of objects (Composite)** implement the same interface, allowing the client to treat them the same way. Each composite can contain multiple leaves or other composites, supporting recursive structures naturally.

Key Components:

  • Component: Declares the interface for all objects in the hierarchy.
  • Leaf: Represents individual objects with no children.
  • Composite: Represents containers that can hold leaves or other composites.
  • Client: Interacts with components uniformly without worrying about their type.

Java Implementation Example

// Component
interface FileSystemComponent {
    void display();
    int getSize();
}

// Leaf
class File implements FileSystemComponent {
    private String name;
    private int size;

    public File(String name, int size) { this.name = name; this.size = size; }

    public void display() { System.out.println("File: " + name + " (" + size + " KB)"); }
    public int getSize() { return size; }
}

// Composite
class Folder implements FileSystemComponent {
    private String name;
    private List<FileSystemComponent> children = new ArrayList<>();

    public Folder(String name) { this.name = name; }

    public void add(FileSystemComponent component) { children.add(component); }
    public void remove(FileSystemComponent component) { children.remove(component); }

    public void display() {
        System.out.println("Folder: " + name);
        for (FileSystemComponent component : children) { component.display(); }
    }

    public int getSize() {
        int totalSize = 0;
        for (FileSystemComponent component : children) { totalSize += component.getSize(); }
        return totalSize;
    }
}

// Client
public class CompositeDemo {
    public static void main(String[] args) {
        File file1 = new File("file1.txt", 10);
        File file2 = new File("file2.txt", 20);
        Folder folder1 = new Folder("Documents");
        folder1.add(file1);
        folder1.add(file2);

        Folder root = new Folder("Root");
        root.add(folder1);
        root.add(new File("readme.md", 5));

        root.display();
        System.out.println("Total Size: " + root.getSize() + " KB");
    }
}

Here, both File and Folder implement the same FileSystemComponent interface. The client can treat single files and nested folders uniformly, and calculate size recursively.

Real-World Examples

  • File systems: folders containing files or other folders.
  • Graphic editors: individual shapes and groups of shapes.
  • Organization hierarchy: employees and managers with subordinates.
  • Menu systems in GUIs: menu items and submenus.

Advantages

  • Clients can treat single objects and composites uniformly.
  • Supports recursive structures naturally.
  • Easy to add new component types without changing client code.

Disadvantages

  • Can make the design more general than needed for simple cases.
  • May increase complexity if there are too many small components.
