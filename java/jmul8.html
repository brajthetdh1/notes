Topic 5.1: Deadlock Fundamentals

Q1 deadlock What are the four conditions required for deadlock? Explain each with a real-world analogy.

A: The four Coffman conditions must all be present for deadlock to occur:

ConditionReal-World AnalogyJava Example
1. Mutual ExclusionA printer can only be used by one person at a time.A synchronized lock on an object.
2. Hold and WaitYou hold a pen while waiting for a paper.Thread holds lock X while waiting for lock Y.
3. No PreemptionYou cannot forcibly take the pen from someone else's hand.A thread holds a lock until it voluntarily releases it.
4. Circular WaitPerson A waits for a paper held by Person B; Person B waits for a pen held by Person A.Thread A waits for lock Y held by Thread B; Thread B waits for lock X held by Thread A.
The "Doubt Clarifier" – If I break just one condition, can deadlock occur?
No. Deadlock requires all four conditions. This is why breaking any one condition is a valid prevention strategy.

Q2 deadlock Can deadlock occur with just one lock?

A: No. A single lock cannot cause deadlock because there is no circular wait. However, a single thread can deadlock itself if it calls Thread.currentThread().join(). This is a self-deadlock, but not a classic deadlock.

Example of Self-Deadlock:

public static void main(String[] args) throws InterruptedException { Thread.currentThread().join(); // Thread waits for itself to finish! }

The thread is waiting for itself to terminate, which will never happen. This is technically a deadlock (or at least a permanent hang), but not a classic multi-threaded deadlock.

Q4 deadlock Can deadlock occur with ReentrantLock? Can it occur with synchronized?

A: Yes to both. Deadlock is a logic error, not a lock-specific issue.

With synchronized:

synchronized (lock1) { synchronized (lock2) { // ... } }

With ReentrantLock:

lock1.lock(); try { lock2.lock(); try { // ... } finally { lock2.unlock(); } } finally { lock1.unlock(); }

Both can deadlock if threads acquire locks in different orders.

The "Doubt Clarifier" – Is ReentrantLock more deadlock-prone than synchronized?
No. ReentrantLock actually provides tools to prevent deadlock (tryLock(), lockInterruptibly()). synchronized offers no such escape hatch.

Q10 prevention How does lock ordering prevent deadlock?

A: Lock ordering ensures that all threads acquire locks in the same order. This breaks the circular wait condition.

Example:

public class BankAccount { private final int id; // Unique ID private int balance; public void transfer(BankAccount target, int amount) { BankAccount first = this.id < target.id ? this : target; BankAccount second = this.id < target.id ? target : this; synchronized (first) { synchronized (second) { this.balance -= amount; target.balance += amount; } } } }

Now Thread A (transfer X→Y) and Thread B (transfer Y→X) both lock the account with the smaller ID first. No circular wait → no deadlock.

The "Doubt Clarifier" – What if two accounts have the same ID?
They shouldn't. Account IDs must be unique. If you can't guarantee uniqueness, use a third lock (e.g., a global ReentrantLock) as a tie-breaker.
4 min read prevention lock-ordering

Q11 prevention How does tryLock() with timeout prevent deadlock?

A: A thread attempts to acquire all locks. If it can't acquire all locks within the timeout, it releases any locks it has acquired and retries later. This breaks the "Hold and Wait" condition.

Example:

public boolean transfer(BankAccount target, int amount) { try { if (this.lock.tryLock(1, TimeUnit.SECONDS)) { try { if (target.lock.tryLock(1, TimeUnit.SECONDS)) { try { this.balance -= amount; target.balance += amount; return true; } finally { target.lock.unlock(); } } } finally { this.lock.unlock(); } } } catch (InterruptedException e) { Thread.currentThread().interrupt(); } return false; // Could not acquire both locks }
The "Doubt Clarifier" – What if both threads keep timing out?
They could livelock. Add random jitter (exponential backoff) to the timeout to break symmetry.

Q13 prevention What is the "Banker's Algorithm" and is it used in Java?

A: The Banker's Algorithm is a deadlock avoidance algorithm used in operating systems. It checks if granting a resource request would lead to a deadlock. If so, the request is denied.

Is it used in Java? No. Java does not implement the Banker's Algorithm. Instead, Java provides prevention strategies (lock ordering, tryLock(), higher-level abstractions).

Topic 5.4: Starvation

Q14 starvation What is thread starvation? What causes it?

A: Thread starvation occurs when a thread is unable to make progress because it cannot acquire necessary resources.

Causes:

  • Priority Inversion: High-priority threads consume all CPU time, starving low-priority threads.
  • Resource Hoarding: A thread holds a resource for a very long time, causing others to wait.
  • Poor Thread Pool Design: A long-running task occupies a thread, causing other tasks to wait.
  • Deadlock (worst form of starvation): Threads wait forever.
The "Doubt Clarifier" – Is starvation a common problem in modern applications?
Modern OS schedulers use dynamic priority adjustments (they boost threads that have waited a long time). Starvation is rare on modern systems but can still happen in poorly designed applications.

Example of Starvation:

Thread low = new Thread(() -> { while (true) { System.out.println("Low priority thread"); } }); low.setPriority(Thread.MIN_PRIORITY); Thread high = new Thread(() -> { while (true) { // CPU hog } }); high.setPriority(Thread.MAX_PRIORITY);

The low-priority thread may never print anything because the high-priority thread consumes all CPU time.

Q16 starvation How can you prevent starvation?

A:

  • Use thread pools (Executors.newFixedThreadPool()) to limit the number of threads.
  • Avoid setting priorities (let the OS scheduler decide).
  • Use fair locks (new ReentrantLock(true)) to ensure threads get locks in order.
  • Use timeouts to prevent indefinite waiting.
  • Design threads with cooperative scheduling (yield or sleep periodically).
The "Doubt Clarifier" – Should I use thread priorities?
Avoid them. Thread priorities are OS-dependent and can cause starvation. In most applications, the default priority (NORM_PRIORITY) is the right choice.

Topic 5.5: Livelock

Q17 livelock What is livelock? Give a real-world example.

A: Livelock occurs when threads are not blocked but constantly change state in response to each other, making no progress.

Real-World Analogy: Two people trying to pass each other in a narrow corridor. Both step left, then both step right, then both step left again, never passing each other.

Java Example:

public class LivelockExample { private final Lock lock1 = new ReentrantLock(); private final Lock lock2 = new ReentrantLock(); public void methodA() { while (true) { if (lock1.tryLock()) { try { if (lock2.tryLock()) { try { // Do work return; } finally { lock2.unlock(); } } } finally { lock1.unlock(); } } // Retry immediately } } public void methodB() { while (true) { if (lock2.tryLock()) { try { if (lock1.tryLock()) { try { // Do work return; } finally { lock1.unlock(); } } } finally { lock2.unlock(); } } // Retry immediately } } }

Thread A acquires lock1, fails to acquire lock2, releases lock1, retries. Thread B acquires lock2, fails to acquire lock1, releases lock2, retries. They keep doing this forever.

Q19 livelock How can you prevent livelock?

A:

Strategy 1: Exponential Backoff with Jitter

Instead of retrying immediately, wait an increasing amount of time.

private static final int MAX_RETRIES = 10; private static final int BASE_DELAY_MS = 100; public void methodA() { int retries = 0; while (retries < MAX_RETRIES) { if (lock1.tryLock()) { try { if (lock2.tryLock()) { try { // Do work return; } finally { lock2.unlock(); } } } finally { lock1.unlock(); } } retries++; long delay = BASE_DELAY_MS * (long) Math.pow(2, retries); // Exponential backoff delay += ThreadLocalRandom.current().nextLong(0, delay / 2); // Jitter try { Thread.sleep(delay); } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; } } }

Strategy 2: Use Lock Ordering – If both threads acquire locks in the same order, livelock cannot occur.

Strategy 3: Use a Random Delay – Even a small random delay can break symmetry.

Thread.sleep(ThreadLocalRandom.current().nextInt(10, 100));

Q20 livelock What is "spinning" and how does it relate to livelock?

A: Spinning is when a thread repeatedly checks a condition in a loop without yielding CPU time.

while (!condition) { // Spin }

Spinning can cause livelock if two threads spin and never meet the condition. It also wastes CPU cycles.

The Fix: Use Thread.sleep() or LockSupport.parkNanos() to yield between checks.

Topic 5.6: Thread Exhaustion

Q21 exhaustion What is thread exhaustion? What causes it?

A: Thread exhaustion occurs when an application creates too many threads, consuming all available memory or reaching the OS thread limit.

Causes:

  • Creating a new thread for every request (without a thread pool).
  • Not properly shutting down threads (thread leaks).
  • Creating many threads for a single operation (e.g., 1000 threads for 1000 database queries).

Consequences:

  • OutOfMemoryError (native memory exhaustion).
  • OS thread limit reached (thousands of threads).
  • Poor performance (excessive context switching).
The "Doubt Clarifier" – What is the OS thread limit?
It varies by OS:
Linux: Usually 32768 (default) but can be increased.
Windows: Usually 2048 (per process).
macOS: Usually 2048.
3 min read exhaustion thread-limit

Q22 exhaustion How can you prevent thread exhaustion?

A:

  • Use thread pools: Executors.newFixedThreadPool() limits the number of threads.
  • Use bounded thread pools: new ThreadPoolExecutor(core, max, timeout, queue).
  • Monitor thread count: Use Thread.activeCount() or JMX.
  • Use Virtual Threads (Java 21+): Millions of threads with minimal overhead.

Example:

// Bad: Creates a new thread for every request new Thread(() -> processRequest()).start(); // Good: Reuses threads from a pool ExecutorService executor = Executors.newFixedThreadPool(100); executor.execute(this::processRequest);

Topic 5.7: Advanced Questions

Q23 advanced What is "priority inversion" and how does it relate to starvation?

A: Priority inversion occurs when a low-priority thread holds a resource needed by a high-priority thread. The high-priority thread blocks, and the low-priority thread runs, causing starvation.

Example:

  • Thread A (High Priority) needs lock X.
  • Thread B (Low Priority) holds lock X and is running.
  • Thread A blocks, waiting for lock X.
  • Thread C (Medium Priority) runs and consumes CPU, preventing Thread B from running and releasing lock X.

Thread A never makes progress. This is priority inversion.

The Fix: Use priority inheritance (the OS temporarily boosts Thread B's priority to Thread A's level).

Java Note: Java does not implement priority inheritance. Avoid using thread priorities.
4 min read priority-inversion starvation

Q24 advanced What is a "deadlock" in a database context?

A: Database deadlocks occur when two transactions each hold locks on resources that the other needs.

Example:

  • Transaction A updates Table X, then tries to update Table Y.
  • Transaction B updates Table Y, then tries to update Table X.

Both transactions block. The database detects the deadlock and rolls back one transaction.

How to handle in Java:

  • Use @Transactional with a retry mechanism.
  • Catch DeadlockLoserDataAccessException (Spring) and retry.

Q26 advanced What is the "dining philosophers" problem and how does it relate to deadlock?

A: The dining philosophers problem is a classic concurrency problem:

  • Five philosophers sit at a round table.
  • Each has a fork on their left and a fork on their right.
  • To eat, a philosopher needs both forks.
  • If each philosopher picks up the left fork simultaneously, all will wait for the right fork → deadlock.

Solutions:

  • Lock Ordering: Philosophers pick up the fork with the lower ID first.
  • Mutex: A single lock controls access to all forks.
  • Lazy Pickup: Wait until both forks are available.

This problem mirrors the bank transfer deadlock (multiple resources, each held by one thread).

Q27 advanced What is the "readers-writers" problem and how does it relate to liveness?

A: The readers-writers problem involves multiple threads accessing a shared resource:

  • Readers: Only read the data (can read concurrently).
  • Writers: Read and write (need exclusive access).

Liveness Issues:

  • Writer Starvation: If readers keep coming, writers may never get a chance to write.
  • Reader Starvation: If writers keep coming, readers may be starved.

Solution: Use ReentrantReadWriteLock with a fair policy.

Q28 advanced What is "lock ordering" and why is it the most effective deadlock prevention?

A: Lock ordering is the practice of acquiring locks in a consistent global order. It breaks the circular wait condition.

Why it's effective:

  • Simple to implement.
  • No runtime overhead (unlike tryLock() which requires retries).
  • Prevents deadlock by design.

Example:

// Always lock by ID BankAccount first = this.id < target.id ? this : target; BankAccount second = this.id < target.id ? target : this; synchronized (first) { synchronized (second) { // ... } }
The "Doubt Clarifier" – What if I can't assign a unique ID?
Use a third lock (e.g., a global ReentrantLock) as a tie-breaker, or use System.identityHashCode().
3 min read lock-ordering prevention

Q29 advanced What is "tryLock" and how does it help with deadlock prevention?

A: tryLock() attempts to acquire a lock without blocking indefinitely. It returns true if successful, false otherwise.

How it helps:

  • A thread can attempt to acquire all locks.
  • If any lock acquisition fails, it releases any locks it has.
  • It retries after a delay.

Example:

if (lock1.tryLock()) { try { if (lock2.tryLock()) { try { // Critical section return true; } finally { lock2.unlock(); } } } finally { lock1.unlock(); } } return false; // Could not acquire both locks
3 min read tryLock prevention

Q30 advanced What is "fairness" in locks and how does it affect liveness?

A: Fairness determines whether threads acquire locks in the order they requested them.

PolicyBehaviorLiveness Impact
Fair Lock (new ReentrantLock(true))Threads get the lock in the order they requested.Prevents starvation but reduces throughput.
Unfair Lock (new ReentrantLock(false))Threads compete for the lock; the OS scheduler decides.Higher throughput but can cause starvation.
The "Doubt Clarifier" – Should I use fair locks?
Rarely. Fair locks are slower because they require more bookkeeping. In most applications, the performance cost outweighs the benefit.

Q31 pitfall What is wrong with this code?

Answer: This is a classic deadlock. Thread A locks lock1 then lock2. Thread B locks lock2 then lock1. If both threads run simultaneously, they will deadlock.

Fix: Make both threads lock in the same order (lock1 then lock2).

Q47 interview What is the difference between deadlock and "thread starvation" in a thread pool?

FeatureDeadlock in Thread PoolThread Starvation in Thread Pool

Example of Thread Pool Deadlock:

ExecutorService pool = Executors.newFixedThreadPool(2); Future<?> f1 = pool.submit(() -> { Future<?> f2 = pool.submit(() -> { // Inner task }); f2.get(); // Waits for inner task }); f1.get(); // Waits for outer task

The outer task waits for the inner task, but both tasks share the same pool of 2 threads. Deadlock!

Q49 interview What is the "dining philosophers" problem and what are the solutions?

A: The dining philosophers problem is a classic concurrency problem.

Problem: Five philosophers sit at a round table. Each has a fork on each side. To eat, a philosopher needs both forks. If all philosophers pick up the left fork simultaneously, all will wait for the right fork → deadlock.

Q50 interview How would you design a system to detect and recover from deadlock?

A:

Detection:

  • Use ThreadMXBean.findDeadlockedThreads() periodically.
  • Monitor lock acquisition times (if a lock takes too long, log a warning).

Recovery:

  • Interrupt deadlocked threads (thread.interrupt()).
  • Log the deadlock details (thread dumps).
  • Restart affected threads or the application.
  • Use a circuit breaker pattern to prevent cascading failures.

Prevention:

  • Use lock ordering.
  • Use tryLock() with timeouts.
  • Use higher-level abstractions (ConcurrentHashMap, BlockingQueue).
