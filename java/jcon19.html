Threads vs Processes in Java

Threads

A thread is the smallest unit of execution within a process - a lightweight sub-process that shares the same memory space and resources as other threads in the same process.

In Java:

Threads are represented by the Thread class or implemented via the Runnable interface, sharing heap memory but having separate stack memory.

Lightweight Shared Memory Faster Context Switching Same Process

Processes

A process is an independent program in execution with its own memory space, resources, and state - completely isolated from other processes running on the system.

In Java:

Each JVM instance runs as a separate process, and you can create new processes using ProcessBuilder or Runtime.exec().

Heavyweight Isolated Memory Slower Context Switching Independent

Key Differences

Memory

Threads share memory, Processes have isolated memory

Creation Cost

Threads are lightweight, Processes are heavyweight

Communication

Threads communicate directly, Processes need IPC

Isolation

Process crashes don't affect others, Thread crashes affect entire process

Java Thread Creation Example 

public class ThreadExample {
    public static void main(String[] args) {
        // Method 1: Extending Thread class
        class MyThread extends Thread {
            public void run() {
                System.out.println("Thread running!");
            }
        }
        
        // Method 2: Implementing Runnable
        class MyRunnable implements Runnable {
            public void run() {
                System.out.println("Runnable running!");
            }
        }
        
        // Start threads
        new MyThread().start();
        new Thread(new MyRunnable()).start();
    }
}

Thread Lifecycle States

NEW

Thread created but not started

RUNNABLE

Ready to run or currently running

BLOCKED

Waiting for monitor lock

WAITING

Waiting indefinitely for another thread

TERMINATED

Execution completed

start() vs run() Methods

start() Method

  • Creates a new thread of execution
  • Calls run() method in new thread
  • Returns immediately to caller
  • Enables true multithreading

run() Method

  • Runs in current thread context
  • No new thread created
  • Blocks until execution completes
  • Equivalent to normal method call

Starting Thread Twice

IllegalThreadStateException

A thread cannot be started twice. Once a thread completes its execution and enters the TERMINATED state, it cannot be restarted. Attempting to call start() on a thread that has already been started will throw an IllegalThreadStateException.

Thread thread = new Thread(() -> System.out.println("Running"));
thread.start(); // ✓ Works fine
thread.start(); // ❌ Throws IllegalThreadStateException

Thread.sleep() Method

Purpose & Behavior

Key Features:

  • Pauses thread execution for specified time
  • Does not release held locks
  • Can be interrupted via interrupt()
  • Throws InterruptedException

Usage Example:

try {
  Thread.sleep(2000); // Sleep for 2 seconds
  System.out.println("Awake!");
} catch (InterruptedException e) {
  Thread.currentThread().interrupt();
}

yield() Method

How yield() Works

Behavior:

  • Hints scheduler to pause current thread
  • Moves thread from RUNNING to RUNNABLE
  • Allows other threads of same priority to run
  • Scheduler may ignore the hint

Important Notes:

  • Not guaranteed to have any effect
  • Use for debugging or testing only
  • Rarely used in production code
What is Thread Safety?

Thread safety refers to the property of code that functions correctly and produces expected results when accessed simultaneously by multiple threads, without requiring additional synchronization or causing race conditions, data corruption, or inconsistent state.

Why Thread Safety is Important:

Prevents race conditions and data corruption
Ensures data consistency across threads
Maintains program predictability
Enables safe concurrent access to shared resources
Synchronized Keyword

The synchronized keyword in Java is a built-in mechanism that provides mutual exclusion and ensures that only one thread can execute a synchronized method or block at a time for a given object monitor, preventing concurrent access to critical sections of code.

How It Works:

  • 1 Thread acquires intrinsic lock (monitor)
  • 2 Executes synchronized code exclusively
  • 3 Automatically releases lock when done
  • 4 Other threads wait for lock release

Example:

public synchronized void increment() {
  count++; // Thread-safe operation
}
Synchronized Method vs Block

Synchronized Method

public synchronized void method() {
  // Entire method is synchronized
}
  • Locks on the entire object (instance method) or class (static method)
  • Simpler syntax and usage
  • Can reduce performance by locking more code than necessary

Synchronized Block

public void method() {
  synchronized(lockObject) {
    // Only this block is synchronized
  }
}
  • Locks on specific object or custom lock
  • Finer-grained control over locking scope
  • Better performance by minimizing locked sections
Object-level vs Class-level Locking

Object-level Locking

// Instance synchronized method
public synchronized void instanceMethod() { }

// Synchronized block on 'this'
synchronized(this) { }
  • Each object instance has its own lock
  • Multiple threads can access different instances simultaneously
  • Used for instance-specific synchronization

Class-level Locking

// Static synchronized method
public static synchronized void staticMethod() { }

// Synchronized block on class
synchronized(MyClass.class) { }
  • Single lock per class (shared across all instances)
  • Only one thread can access any static synchronized method
  • Used for class-level shared resource protection
Race Condition

A race condition occurs when the behavior of software depends on the relative timing of events, such as the order in which threads are scheduled, leading to unpredictable and often incorrect results when multiple threads access and modify shared data without proper synchronization.

Race Condition Example:

public class Counter {
  private int count = 0;

  public void increment() {
    count++; // NOT thread-safe!
  }
}
1 Thread A reads count (value: 0)
2 Thread B reads count (value: 0)
3 Both increment to 1 instead of 2
4 Result: Lost update!

Solution with Synchronization:

public class Counter {
  private int count = 0;

  public synchronized void increment() {
    count++; // Now thread-safe!
  }
}
Only one thread can execute increment() at a time
Prevents concurrent read-modify-write operations
Ensures atomicity of the increment operation
Volatile Keyword

The volatile keyword in Java ensures that reads and writes to a variable are always done directly from and to main memory, preventing thread caching and ensuring visibility of changes across all threads, while also preventing certain instruction reordering optimizations.

When to Use Volatile:

Simple status flags or stop signals
Visibility guarantee without atomicity
Reader-writer scenarios with single writer
NOT for compound operations (like count++)

Volatile Example:

public class TaskRunner {
  private volatile boolean running = true;

  public void stop() {
    running = false; // Immediately visible to all threads
  }

  public void run() {
    while (running) {
      // Do work
    }
  }
}
Changes to 'running' are immediately visible to all threads
Synchronized vs Volatile

Synchronized

  • Provides mutual exclusion (only one thread at a time)
  • Guarantees both visibility AND atomicity
  • Prevents instruction reordering
  • More expensive performance-wise
  • Suitable for compound operations

Volatile

  • No mutual exclusion (multiple threads can access)
  • Guarantees visibility but NOT atomicity
  • Prevents certain instruction reordering
  • Better performance than synchronized
  • Suitable for simple flags and status variables

Wait(), Notify(), and NotifyAll() Methods

wait()

Causes the current thread to wait until another thread invokes notify() or notifyAll() for this object. The thread releases ownership of the monitor and waits until notified.

synchronized(obj) {
  while(!condition) {
    obj.wait();
  }
  // Continue execution
}

notify()

Wakes up a single thread that is waiting on this object's monitor. If multiple threads are waiting, one is arbitrarily chosen to be awakened.

synchronized(obj) {
  condition = true;
  obj.notify();
}

notifyAll()

Wakes up all threads that are waiting on this object's monitor. The threads will compete in the usual manner for the right to synchronize on the object.

synchronized(obj) {
  condition = true;
  obj.notifyAll();
}

Producer-Consumer Example

Producer Thread:
synchronized(sharedQueue) {
  while(sharedQueue.isFull()) {
    sharedQueue.wait();
  }
  sharedQueue.add(item);
  sharedQueue.notifyAll();
}
Consumer Thread:
synchronized(sharedQueue) {
  while(sharedQueue.isEmpty()) {
    sharedQueue.wait();
  }
  Item item = sharedQueue.remove();
  sharedQueue.notifyAll();
}
Why Synchronized Context is Required

The wait(), notify(), and notifyAll() methods must be called from within a synchronized context because they require the calling thread to own the object's monitor, ensuring proper coordination between threads and preventing race conditions and lost notifications.

Technical Reasons

1
Monitor Ownership

wait() releases the monitor, notify() wakes threads waiting for the monitor - both require current ownership

2
Atomic Check-and-Wait

Prevents race conditions between checking condition and waiting

3
Memory Visibility

Synchronization ensures changes are visible to waiting threads

Consequences Without Synchronization

IllegalMonitorStateException

Runtime exception thrown when called without owning monitor

Lost Notifications

Notifications can be missed if condition check and wait aren't atomic

Race Conditions

Threads can act on stale data without proper synchronization

Inconsistent State

Multiple threads can modify shared state simultaneously

Correct Usage

// Thread-safe with synchronization
synchronized(lock) {
  while(!condition) {
    lock.wait();
  }
  // Do work
  lock.notifyAll();
}
Atomic condition check and wait

Incorrect Usage

// NOT thread-safe - throws exception!
if(!condition) {
  lock.wait(); // IllegalMonitorStateException!
}
lock.notify(); // Also throws exception!
Race condition and IllegalMonitorStateException

Key Rule to Remember

Always call wait(), notify(), and notifyAll() from within synchronized blocks or methods, and always use wait() in a loop to handle spurious wakeups and ensure the condition is truly met before proceeding.

wait() Method

// Object class method

  • Releases lock while waiting

What is a Deadlock?

A deadlock is a situation in concurrent programming where two or more threads are blocked forever, each waiting for the other to release a lock or resource, creating a circular dependency that prevents any progress and halts the entire system.

The Four Necessary Conditions for Deadlock:

Mutual Exclusion

Resources cannot be shared

Hold and Wait

Threads hold resources while waiting for others

No Preemption

Resources cannot be forcibly taken

Circular Wait

Circular chain of waiting threads

Deadlock Example:

// Thread 1
synchronized(lockA) {
  synchronized(lockB) {
    // Do work
  }
}

// Thread 2
synchronized(lockB) {
  synchronized(lockA) {
    // Do work
  }
}
1 Thread 1 acquires lockA, wants lockB
2 Thread 2 acquires lockB, wants lockA
3 Both threads wait forever - DEADLOCK!

Visual Representation:

Thread 1
🔒 A → ⏳ B
Thread 2
🔒 B → ⏳ A
💀 DEADLOCK
How to Prevent Deadlocks

Lock Ordering

Always acquire locks in a consistent, predefined order to prevent circular wait conditions.

// Good: Consistent lock order
synchronized(lockA) {
  synchronized(lockB) {
    // Both threads use same order
  }
}

Timeout Mechanism

Use tryLock with timeout to avoid indefinite waiting and implement retry logic.

if (lock.tryLock(5, TimeUnit.SECONDS)) {
  try {
    // Critical section
  } finally {
    lock.unlock();
  }
}

Avoid Nested Locks

Don't acquire multiple locks if possible, or use coarse-grained locking

Resource Hierarchy

Assign numeric values to resources and acquire in ascending order

Deadlock Detection

Use monitoring tools to detect and break deadlocks automatically

Best Practices for Prevention:

Use higher-level concurrency utilities from java.util.concurrent
Minimize lock scope and duration
Design for immutability where possible
Use thread-safe collections instead of manual synchronization
Thread Starvation

Thread starvation occurs when a thread is unable to gain regular access to shared resources and is unable to make progress because other "greedy" threads are constantly holding the locks or resources needed, preventing the starved thread from executing its tasks.

Common Causes

Long-held Locks

Threads holding locks for extended periods

Inappropriate Priorities

High-priority threads dominating CPU time

Infinite Loops

Threads stuck in loops holding resources

Unfair Scheduling

Scheduler favoring certain threads repeatedly

Starvation Example

public class Resource {   public synchronized void longRunningTask() {     // Takes 10 seconds to complete     // Other threads wait indefinitely   } }

// Multiple threads calling longRunningTask() // Low-priority threads may never get access
Thread A acquires lock for 10 seconds
Thread B, C, D queue up waiting
Thread A immediately reacquires lock
Other threads starve indefinitely

Prevention & Solutions

Use fair locks (ReentrantLock(true))
Minimize critical section duration
Use timeouts for lock acquisition
Avoid thread priorities when possible
Livelock

Livelock occurs when two or more threads continuously change their state in response to each other without making any real progress, effectively "being too polite" where each thread repeatedly retries an operation that fails because of the other thread's actions, creating an endless loop of state changes without completion.

Livelock Characteristics

Active but Stuck

Threads are running but not progressing

Endless Retries

Continuous state changes without resolution

Cooperative Deadlock

Threads respond to each other's actions

CPU Utilization

High CPU usage with zero productive work

Classic Example: Polite People

Two people meeting in a hallway:

Person A moves left to let B pass
Person B moves right to let A pass
Now they're still blocking each other
Person A moves right...
Person B moves left...
Cycle repeats indefinitely! 🔄
Both threads constantly adjust their behavior
Each response triggers the same reaction
No thread can complete its intended action

Code Example: Resource Livelock

class Worker {   private boolean busy = false;   private Worker colleague;      public void work() {     while (busy) {       // If I'm busy, check if colleague is busy too       if (colleague.isBusy()) {         Thread.yield(); // Be polite         continue;       }       // Both keep yielding to each other endlessly     }   } }
Worker 1: "You go first" → yields
Worker 2: "No, you go first" → yields
Worker 1: "No, you go first" → yields
Infinite cycle of politeness!

One thread should proceed without yielding
Different code paths for different conditions
Detection & Recovery

Force one thread to take different action

Producer-Consumer Problem

The producer-consumer problem is a classic synchronization challenge where multiple producer threads generate data and place it into a shared buffer, while multiple consumer threads remove and process that data, requiring coordination to prevent race conditions, buffer overflow, or underflow.

Producers

  • Generate data items
  • Add items to shared buffer
  • Wait if buffer is full

Consumers

  • Remove data items from buffer
  • Process consumed items
  • Wait if buffer is empty
Key Challenges

Race Conditions

Multiple threads accessing shared buffer simultaneously causing data corruption

Buffer Overflow

Producers adding data when buffer is already full

Buffer Underflow

Consumers trying to remove data from empty buffer

Solution using wait() and notify()

Producer Implementation

public void produce() throws InterruptedException {
  synchronized (buffer) {
    while (buffer.isFull()) {
      buffer.wait(); // Wait if full
    }
    buffer.add(item);
    buffer.notifyAll(); // Notify consumers
  }
}
Checks buffer capacity before adding
Waits if buffer is full
Notifies waiting consumers after adding

Consumer Implementation

public void consume() throws InterruptedException {
  synchronized (buffer) {
    while (buffer.isEmpty()) {
      buffer.wait(); // Wait if empty
    }
    Item item = buffer.remove();
    buffer.notifyAll(); // Notify producers
  }
  process(item);
}
Checks if buffer has items before removing
Waits if buffer is empty
Notifies waiting producers after removing
Modern Solution with BlockingQueue

Java's BlockingQueue interface provides a thread-safe implementation that handles all synchronization internally, making it the preferred modern solution for producer-consumer scenarios.

Producer with BlockingQueue

public class Producer implements Runnable {
  private final BlockingQueue queue;

  public void run() {
    try {
      while (true) {
        Item item = produceItem();
        queue.put(item); // Blocks if full
      }
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
    }
  }
}

Consumer with BlockingQueue

public class Consumer implements Runnable {
  private final BlockingQueue queue;

  public void run() {
    try {
      while (true) {
        Item item = queue.take(); // Blocks if empty
        processItem(item);
      }
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
    }
  }
}

Benefits of BlockingQueue:

Built-in thread safety
Simpler, cleaner code
Automatic blocking operations
Better performance
Key Implementation Points

Traditional Approach

  • Use synchronized blocks with wait()/notify()
  • Always use while loops for condition checks
  • Call notifyAll() instead of notify()
  • Handle InterruptedException properly

Modern Approach

  • Prefer BlockingQueue implementations
  • Use ArrayBlockingQueue or LinkedBlockingQueue
  • Leverage put() and take() blocking methods
  • Consider capacity bounds for backpressure

Java Memory Model (JMM)

The Java Memory Model (JMM) is a formal specification that defines how threads interact through memory and how changes made by one thread to shared variables become visible to other threads, ensuring predictable behavior in multi-threaded environments while allowing compiler and processor optimizations.

Key JMM Concepts

Main Memory vs Working Memory

Each thread has its own working memory separate from main memory

Visibility Guarantees

Ensures changes to shared variables are visible across threads

Happens-Before Relationship

Defines ordering constraints for memory operations

Instruction Reordering Prevention

Prevents certain compiler and CPU optimizations that could break correctness

Memory Architecture

Thread-local cached copies
Synchronization
Forces memory visibility

Read

Assign
Working Memory
Write

Happens-Before Relationship

The happens-before relationship defines a partial ordering of operations that guarantees if one action happens-before another, then the first is visible to and ordered before the second.

Establishes Happens-Before:
  • Program order within a thread
  • Monitor lock operations (synchronized)
  • volatile variable reads/writes
  • Thread.start() and Thread.join()
Example:
// Thread A
x = 1; // Write
lock.unlock(); // Happens-before edge

// Thread B
lock.lock(); // Synchronizes-with
r1 = x; // Read sees x = 1

Predictable Behavior

Ensures multi-threaded programs behave consistently across different platforms and architectures

Performance Optimization

Allows compilers and processors to optimize while maintaining correctness guarantees

Portability

Provides consistent memory semantics across different JVM implementations and hardware

Hashtable vs HashMap

Hashtable

  • Thread-safe: Synchronized methods
  • No nulls: Neither keys nor values can be null
  • Performance: Slower due to synchronization
  • Legacy: Since Java 1.0
  • Enumeration: Uses Enumeration for iteration

HashMap

  • Not thread-safe: No synchronization
  • Allows nulls: Both keys and values can be null
  • Performance: Faster, no synchronization overhead
  • Modern: Since Java 1.2
  • Iterator: Uses fail-fast Iterator

Example Usage:

// Hashtable - thread-safe
Hashtable<String, Integer> table = new Hashtable<>();
table.put("key", 1);
// table.put(null, 1); // Throws NullPointerException
// HashMap - not thread-safe
HashMap<String, Integer> map = new HashMap<>();
map.put("key", 1);
map.put(null, 1); // Allowed
ConcurrentHashMap

ConcurrentHashMap is a thread-safe implementation of Map that provides better scalability than Hashtable by using fine-grained locking mechanisms and allowing concurrent read operations without locking, while maintaining thread safety for write operations.

Thread Safety Mechanism:

1
Segment Locking

Divides map into segments, locking only the affected segment during writes

2
Lock-free Reads

Read operations don't require locking, allowing concurrent access

3
CAS Operations

Uses Compare-And-Swap for atomic updates without full locking

Key Features:

High concurrency for read operations
Better performance than Hashtable
Doesn't throw ConcurrentModificationException
Null keys/values not allowed

ConcurrentHashMap Example:

ConcurrentHashMap<String, Integer> concurrentMap = new ConcurrentHashMap<>();

// Multiple threads can safely use this map
concurrentMap.put("key1", 100);
concurrentMap.putIfAbsent("key2", 200);

// Concurrent reads without locking
Integer value = concurrentMap.get("key1");

// Atomic operations
concurrentMap.compute("key1", (k, v) -> v + 50);
CopyOnWriteArrayList

CopyOnWriteArrayList is a thread-safe variant of ArrayList where all mutative operations (add, set, remove) create a fresh copy of the underlying array, allowing for safe iteration even while modifications occur, making it ideal for read-heavy scenarios with infrequent writes.

When to Use:

Read-heavy operations

When reads significantly outnumber writes

Listener lists

Event listener management in observer pattern

Snapshot iterations

When you need consistent snapshots during iteration

Pros & Cons:

✅ Advantages:
  • • Thread-safe without explicit synchronization
  • • No ConcurrentModificationException during iteration
  • • Excellent read performance
❌ Disadvantages:
  • • Memory overhead from copying
  • • Poor write performance
  • • Data consistency delays

CopyOnWriteArrayList Example:

CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
list.add("Item1");
list.add("Item2");

// Safe iteration - won't throw ConcurrentModificationException
for (String item : list) {
  System.out.println(item);
  // Can safely modify list during iteration
  list.add("NewItem"); // This creates a new copy
}

// The original iteration continues with the original snapshot

Phaser vs CountDownLatch/CyclicBarrier

Phaser

A reusable synchronization barrier that supports dynamic registration of parties and multiple phases of execution.

Phaser phaser = new Phaser(3);
phaser.arriveAndAwaitAdvance();
phaser.arriveAndDeregister();

CountDownLatch

One-time synchronization point where threads wait until a count reaches zero. Cannot be reset.

CountDownLatch latch = new CountDownLatch(3);
latch.countDown();
latch.await();

CyclicBarrier

Reusable barrier that threads wait at until a fixed number arrives, then all proceed together.

CyclicBarrier barrier = new CyclicBarrier(3);
barrier.await();

Key Differences:

Phaser: Dynamic party registration, multiple phases
CountDownLatch: One-time use, fixed parties
CyclicBarrier: Reusable, fixed parties, single phase
Phaser: Most flexible, supports hierarchical phasing
Exchanger and TransferQueue

Exchanger

A synchronization point where two threads can exchange objects. Both threads must arrive at the exchange point to proceed.

Exchanger<String> exchanger = new Exchanger<>();

// Thread 1:
String received = exchanger.exchange("Data from Thread 1");

// Thread 2:
String received = exchanger.exchange("Data from Thread 2");
Perfect for genetic algorithms, pipeline designs
Both threads block until exchange completes
Only works with exactly two threads

TransferQueue

A BlockingQueue where producers can wait for consumers to receive elements, ensuring handoff coordination.

TransferQueue<String> queue = new LinkedTransferQueue<>();

// Producer waits for consumer
queue.transfer("Important Data");

// Or try without waiting
boolean sent = queue.tryTransfer("Data", 1, TimeUnit.SECONDS);
Handoff semantics - producer waits for consumer
Supports multiple producers and consumers
Useful for message passing with backpressure
CompletableFuture vs Future

Future (Basic)

Represents the result of an asynchronous computation with limited capabilities for completion handling.

Future<String> future = executor.submit(task);

// Blocking call
String result = future.get();

// Check if done
if (future.isDone()) { ... }

// Cancel task
future.cancel(true);
No completion callbacks
No exception handling composition
Manual completion not possible

CompletableFuture

An enhanced Future that can be explicitly completed and supports functional-style transformations and compositions.

CompletableFuture<String> future =
  CompletableFuture.supplyAsync(() -> "Hello")

Visibility in Java Memory Model

Visibility in the Java Memory Model refers to the guarantee that when one thread modifies a shared variable, other threads will see the updated value, preventing scenarios where threads work with stale cached copies of data that can lead to inconsistent application state.

Visibility Problem:

1 Thread A writes to shared variable in CPU cache
2 Thread B reads from its own CPU cache
3 Thread B sees stale, outdated value
4 Result: Inconsistent state across threads

Solutions for Visibility:

volatile keyword
synchronized blocks/methods
Atomic variables from java.util.concurrent.atomic
Final fields (after proper construction)
Reordering in Java Memory Model

Reordering is an optimization technique where the compiler, JVM, or processor may change the order of instruction execution to improve performance, which can cause unexpected behavior in multithreaded code when memory operations appear to execute in a different order than specified in the source code.

Reordering Example:

// Thread 1
x = 1; // Statement A
flag = true; // Statement B

// Thread 2
while (!flag) { }
print(x); // Could print 0 due to reordering!
Statements A and B might be reordered, causing Thread 2 to see flag=true but x=0

Preventing Reordering:

volatile

Creates memory barriers preventing reordering across volatile accesses

synchronized

Ensures operations within synchronized blocks are not reordered

happens-before

JMM guarantees establish ordering constraints

The final keyword in Java provides thread safety guarantees by ensuring that once a final field is set in the constructor, all threads will see the correctly initialized value without synchronization, and the JVM prohibits reordering of operations that could expose partially constructed objects.

No Reordering

JVM prevents reordering that could expose final fields before initialization

Custom Lock Implementation

Implementing a custom lock in Java involves creating a class that implements the Lock interface, typically using low-level synchronization primitives like AtomicInteger and LockSupport to manage thread state transitions, queue management, and efficient waiting/notification mechanisms.

Implementation Strategy:

1
State Management

Use AtomicInteger for lock state (0=unlocked, 1=locked)

2
Queue Management

Maintain waiting threads in a queue (LinkedList or custom)

3
Thread Control

Use LockSupport for efficient thread parking/unparking

4
Fairness

Implement FIFO ordering for fair lock acquisition

Basic Lock Structure:

public class SimpleLock implements Lock {
  private AtomicInteger state = new AtomicInteger(0);
  private Thread owner = null;
  private Queue<Thread> waiters = new LinkedList<>();

  public void lock() {
    while (!state.compareAndSet(0, 1)) {
      // Lock is held, park thread
      waiters.add(Thread.currentThread());
      LockSupport.park();
    }
    owner = Thread.currentThread();
  }
}

Complete Custom Lock Implementation:

public class CustomReentrantLock implements Lock {
  private AtomicInteger state = new AtomicInteger(0);
  private Thread exclusiveOwner = null;
  private final Queue<Thread> waitQueue = new ConcurrentLinkedQueue<>();

  @Override
  public void lock() {
    Thread current = Thread.currentThread();
    if (exclusiveOwner == current) {
      state.incrementAndGet(); // Reentrant
      return;
    }
    waitQueue.offer(current);
    while (waitQueue.peek() != current ||
        !state.compareAndSet(0, 1)) {
      LockSupport.park(this);
    }
    waitQueue.poll();
    exclusiveOwner = current;
  }

  @Override
  public void unlock() {
    if (exclusiveOwner != Thread.currentThread())
      throw new IllegalMonitorStateException();
    int c = state.decrementAndGet();
    if (c == 0) {
      exclusiveOwner = null;
      Thread next = waitQueue.peek();
      if (next != null) LockSupport.unpark(next);
    }
  }
  // Implement other Lock methods...
}

Use CAS operations for thread-safe state changes

Maintain FIFO order for fair lock acquisition

Efficient Parking

Use LockSupport for low-level thread control

ConcurrentHashMap Thread Safety

ConcurrentHashMap achieves thread safety without synchronizing every method by using fine-grained locking mechanisms, specifically segment-based locking or in Java 8+, using synchronized blocks only on individual buckets combined with advanced techniques like volatile variables, CAS operations, and tree bin locking for high concurrency scenarios.

Key Techniques:

  • Segment Locking (Java 7): Divides map into segments with separate locks
  • Bucket Locking (Java 8+): Synchronizes only on individual buckets
  • CAS Operations: Compare-and-swap for lock-free reads
  • Volatile Reads: Ensures memory visibility without locking

Benefits:

Multiple threads can read concurrently without blocking
Writers can operate on different segments simultaneously
Better scalability for high-concurrency applications
ConcurrentHashMap vs SynchronizedMap

ConcurrentHashMap

  • Fine-grained locking at bucket/segment level
  • Multiple threads can read and write concurrently
  • Better performance for high-concurrency scenarios
  • Doesn't throw ConcurrentModificationException
  • Bulk operations are not atomic
Map<String, String> map = new ConcurrentHashMap<>();

Collections.synchronizedMap()

  • Coarse-grained locking on entire map
  • Only one thread can access map at a time
  • Poor performance under high contention
  • Iteration requires external synchronization
  • Bulk operations are atomic when synchronized
Map<String, String> syncMap =
  Collections.synchronizedMap(new HashMap<>());

CopyOnWriteArrayList Iterator Safety

CopyOnWriteArrayList handles iterator safety by creating a snapshot of the underlying array at the time of iterator creation, allowing iteration over this immutable snapshot while modifications to the list create a new copy of the array, ensuring that iterators never throw ConcurrentModificationException and always see the state of the list at their creation time.

How It Works:

1 Iterator created with snapshot of current array
2 Modifications create new copy of underlying array
3 Old iterators continue with their snapshot
4 New iterators get the updated snapshot

Characteristics:

Iterator Behavior Weakly Consistent
ConcurrentModificationException Never Thrown
Write Performance Expensive
Read Performance Excellent

Use Case Example:

// Perfect for listener lists where iteration is frequent
CopyOnWriteArrayList<EventListener> listeners =
  new CopyOnWriteArrayList<>();

// Safe to iterate while others add/remove listeners
for (EventListener listener : listeners) {
  listener.onEvent(event); // Never throws CME
}
