Chapter 3: Thread Safety

Section 3.1: What is Thread Safety? – The Formal Definition

Let's start with an absolutely precise definition, then break it down word by word.

Subsection 3.1.1: The Definitive Definition

A class is thread-safe if it behaves correctly when accessed from multiple threads, regardless of the scheduling or interleaving of the execution of those threads, and with no additional synchronization or other coordination on the part of the calling code.

Let's dissect this:

PhraseMeaning
"behaves correctly"The class maintains its invariants (e.g., a BankAccount never has a negative balance).
"regardless of scheduling"No matter how the OS scheduler interleaves thread instructions, the invariants hold.
"with no additional synchronization"The caller doesn't need to wrap every method call in synchronized.
1 / 50

The "Doubt Clarifier" – What is an invariant?

An invariant is a condition that must always be true for an object to be in a valid state.

Example: For a Counter class, the invariant is count >= 0.

Subsection 3.1.2: The Three Pillars of Thread Safety

Thread safety rests on three fundamental properties. You must understand all three:

PillarDefinitionExample of Failure
AtomicityOperations appear to happen instantaneously; no other thread sees an intermediate state.count++ (read-modify-write) is not atomic.
VisibilityChanges made by one thread are guaranteed to be seen by other threads.Without volatile, a thread may never see a value written by another thread.
OrderingInstructions are not reordered in ways that violate program semantics.Without synchronized, the JVM/CPU can reorder ready = true before config = loadConfig().

Subsection 3.1.3: Thread-Safe Classes – Examples

Thread-Safe (Built-in):

  • java.util.concurrent.ConcurrentHashMap
  • java.util.concurrent.CopyOnWriteArrayList
  • java.util.concurrent.atomic.AtomicInteger
  • java.lang.String (immutable)
  • java.lang.Integer (immutable)

Not Thread-Safe:

  • java.util.HashMap
  • java.util.ArrayList
  • java.lang.StringBuilder
  • java.text.SimpleDateFormat (use DateTimeFormatter instead)

Section 3.2: Atomicity – The First Pillar

Subsection 3.2.1: Atomic Operations – What the JVM Guarantees

The JVM guarantees that the following operations are atomic:

  • Reads and writes to volatile variables (including long and double).
  • Reads and writes to all primitive types except long and double (on 32-bit JVMs).
  • Reads and writes to reference variables (the reference itself, not the object).
  • All operations in a synchronized block (the block as a whole is atomic).
3 / 50

Subsection 3.2.2: The "Check-Then-Act" Race Condition

This is the most common race condition in Java.

Example: Lazy Initialization (Broken)

public class LazySingleton {
            private static ExpensiveObject instance = null;
            
            public static ExpensiveObject getInstance() {
                if (instance == null) {           // CHECK
                    instance = new ExpensiveObject(); // ACT
                }
                return instance;
            }
        }

Why it's broken:

  • Thread A checks instance == null (true), pauses just before creating the object.
  • Thread B checks instance == null (true), creates the object, returns it.
  • Thread A resumes, creates a second object, overwriting Thread B's work.

The Fix:

public static synchronized ExpensiveObject getInstance() {
            if (instance == null) {
                instance = new ExpensiveObject();
            }
            return instance;
        }
4 / 50

Subsection 3.2.3: The "Read-Modify-Write" Race Condition

This is the classic count++ problem.

Example: Counter (Broken)

public class Counter {
            private int count = 0;
            public void increment() {
                count++;  // NOT atomic
            }
        }

The Interleaving:

  • Thread A reads count (0).
  • Thread B reads count (0).
  • Thread A adds 1 (1) and writes back.
  • Thread B adds 1 (1) and writes back.
  • Result: count = 1. We lost an increment.

The Fix (Option 1 – synchronized):

public synchronized void increment() { count++; }

The Fix (Option 2 – AtomicInteger):

private AtomicInteger count = new AtomicInteger(0);
        public void increment() { count.incrementAndGet(); }

Subsection 3.2.4: The "Put-If-Absent" Race Condition

Example: Cache (Broken)

public Object getOrCompute(String key) {
            if (!map.containsKey(key)) {           // CHECK
                Object value = compute(key);       // EXPENSIVE
                map.put(key, value);               // ACT
            }
            return map.get(key);
        }

Fix: Use ConcurrentHashMap.computeIfAbsent() (atomic).

Section 3.3: The synchronized Keyword – Deep Internal Mechanics

Subsection 3.3.1: The Monitor – Every Object Has One

Every Java object has an implicit monitor (intrinsic lock). Only one thread can hold the monitor at a time.

Where is the lock stored? In the object header (the "Mark Word").

6 / 50

Subsection 3.3.2: synchronized Methods vs. Blocks

Synchronized Instance Method:

public synchronized void method() {
            // Lock acquired on 'this'
        }

Equivalent to:

public void method() {
            synchronized (this) { /* ... */ }
        }

Synchronized Static Method:

public static synchronized void staticMethod() {
            // Lock acquired on 'MyClass.class'
        }

Synchronized Block (Custom Object):

private final Object lock = new Object();
        public void method() {
            synchronized (lock) { /* ... */ }
        }

Why use a custom lock object instead of this?

  • Encapsulation: The lock is private; no external code can lock on your object.
  • Fine-grained locking: You can have multiple locks for different parts.
7 / 50

Subsection 3.3.3: Lock Granularity – Coarse vs. Fine

Coarse-Grained (Bad for Performance):

public synchronized void transfer(BankAccount target, int amount) {
            this.balance -= amount;      // Only this.balance needs locking
            target.balance += amount;    // Only target.balance needs locking
        }

Fine-Grained (Better, but deadlock risk):

public void transfer(BankAccount target, int amount) {
            synchronized (this) { this.balance -= amount; }
            synchronized (target) { target.balance += amount; }
        }

Subsection 3.3.4: The Lock Reentrancy – What It Means

synchronized locks are reentrant. If a thread already holds a lock, it can re-enter the same lock without blocking.

public synchronized void outer() {
            inner();  // Thread already holds the lock, so it can enter inner()
        }
        public synchronized void inner() { /* ... */ }

How does the JVM track reentrancy? Each lock has a counter. When a thread acquires the lock, the counter increments. When it releases, the counter decrements. Only when the counter reaches 0 is the lock released.

Subsection 3.3.5: Bias Locking, Lightweight Locking, Heavyweight Locking

LevelDescriptionWhen Used
Biased LockingLock "biases" toward the first thread that acquires it. Almost zero overhead.When a lock is always acquired by the same thread.
Lightweight LockingUses CAS operations in the object header. No OS involvement.When contention is low.
Heavyweight LockingUses OS mutex. Involves context switching and blocking.When contention is high.

Can I disable biased locking? Yes, using -XX:-UseBiasedLocking. In Java 15+, biased locking is deprecated and disabled by default in Java 17+.

Does synchronized block on String literals? Yes, but don't do it! String literals are interned, causing global locking.

Section 3.4: The volatile Keyword – Complete Semantics

Subsection 3.4.1: What volatile Guarantees

  • Visibility: Every write to a volatile variable is immediately flushed to main memory. Every read reads from main memory.
  • Ordering: The JVM and CPU cannot reorder volatile reads/writes with other volatile reads/writes.

What volatile Does NOT Guarantee:

  • Atomicity: volatile does not make count++ atomic.

Subsection 3.4.2: When to Use volatile

Use Case 1: Flags (State Variables)

private volatile boolean running = true;
        public void run() { while (running) { /* work */ } }
        public void stop() { running = false; }

Use Case 2: Configuration Reloading

private volatile Config config = loadConfig();
        public void reloadConfig() { config = loadConfig(); }
10 / 50

Subsection 3.4.3: When NOT to Use volatile

Case 1: Compound Actions

private volatile int count = 0;
        public void increment() { count++; }  // BAD! Not atomic!

Case 2: Accumulators

private volatile int total = 0;
        public void add(int value) { total += value; }  // BAD! Not atomic!

Case 3: Dependencies Between Variables

private volatile boolean ready;
        private Config config;
        public void publish() {
            config = loadConfig();  // Normal write (could be reordered!)
            ready = true;           // Volatile write
        }

Subsection 3.4.5: The "Doubt Clarifier" – Why is volatile cheaper than synchronized?

volatile does not acquire a lock. It only adds memory barriers (fences) to ensure visibility and ordering. There is no OS mutex, no context switching, no blocking.

Section 3.5: The final Keyword in Concurrency

Subsection 3.5.1: Initialization Safety

The JMM guarantees that a final field's value is visible to all threads after the constructor completes, even without synchronization.

public class ImmutablePerson {
            private final String name;
            private final int age;
            public ImmutablePerson(String name, int age) {
                this.name = name;
                this.age = age;
            }
        }

Subsection 3.5.2: The "Safe Publication" Problem

Even with final fields, the object itself must be safely published.

Safe Publication Options:

  • Static initialization: public static final ImmutablePerson person = new ImmutablePerson(...)
  • volatile reference: private volatile ImmutablePerson person;
  • AtomicReference: private AtomicReference<ImmutablePerson> person;
  • Proper synchronization: synchronized block when publishing.

Section 3.6: Thread Confinement and ThreadLocal

Subsection 3.6.1: What is Thread Confinement?

Thread confinement means that an object is only accessed by a single thread.

  • Stack Confinement: Local variables in a method. Each thread has its own stack.
  • ThreadLocal Confinement: Using ThreadLocal to store values per thread.

Subsection 3.6.2: The ThreadLocal Class

private static ThreadLocal<DateFormat> dateFormat = 
            ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
        
        public String formatDate(Date date) {
            return dateFormat.get().format(date);  // Each thread gets its own instance
        }

Why is ThreadLocal useful for SimpleDateFormat? Because SimpleDateFormat is not thread-safe. ThreadLocal gives each thread its own instance.

13 / 50

Subsection 3.6.3: ThreadLocal – The Memory Leak Problem

ThreadLocal can cause memory leaks in web applications. If a thread (from a thread pool) is reused, the ThreadLocal value from a previous request may still be attached.

The Fix: Always call ThreadLocal.remove() after the request is complete.

try {
            dateFormat.get();  // Use ThreadLocal
        } finally {
            dateFormat.remove();  // Clean up!
        }

Why does ThreadLocal cause memory leaks? The ThreadLocalMap stores the value in an Entry that uses the ThreadLocal object as a weak key. However, the value is strongly referenced. If you don't call remove(), the value remains.

Subsection 3.6.4: InheritableThreadLocal – Passing Values to Child Threads

InheritableThreadLocal passes its value from the parent thread to any child threads created.

When should I use InheritableThreadLocal? Rarely. In Java 21+, ScopedValue is a better alternative.

14 / 50

Section 3.7: Immutability – The Ultimate Thread Safety

Subsection 3.7.1: The Rules of Immutability

An object is immutable if:

  1. All fields are final.
  2. The object is not published before construction is complete.
  3. Any mutable fields are not exposed to the caller.

Example:

public final class ImmutablePerson {
            private final String name;
            private final LocalDate birthDate;  // LocalDate is immutable
            
            public ImmutablePerson(String name, LocalDate birthDate) {
                this.name = name;
                this.birthDate = birthDate;
            }
        }

Subsection 3.7.3: The Benefits of Immutability

  • No synchronization needed.
  • No race conditions.
  • Safe to share.
  • Caching-friendly.

Part A: Conceptual Deep-Dive

Q1: If I have a class with no mutable state (no fields), is it thread-safe?

A: Yes, trivially. Stateless objects are always thread-safe because there is nothing to corrupt. Example: a utility class with only static methods that operate on local variables. The local variables live on the stack, which is thread-confined.

Q2: What is the difference between "thread-safe" and "thread-compatible"?

A: Thread-safe = behaves correctly without external synchronization (ConcurrentHashMap). Thread-compatible = safe if the caller uses external synchronization (HashMap wrapped with Collections.synchronizedMap()).

Q3: What is an "invariant" and how does it relate to thread safety?

A: An invariant is a condition that must always be true for an object to be in a valid state. Example: balance >= 0 in a BankAccount. If a race condition breaks the invariant, the object is in an invalid state.

Part A: Conceptual Deep-Dive

Q4: What is the relationship between thread safety and synchronized? Can you be thread-safe without synchronized?

A: Yes! You can be thread-safe without synchronized by: (1) Immutability (String, Integer), (2) Atomic Variables (AtomicInteger), (3) Thread Confinement (local variables, ThreadLocal), (4) Concurrent Collections (ConcurrentHashMap).

Q5: What is the difference between a race condition and a data race?

A: Race condition = correctness failure due to timing (e.g., check-then-act). Data race = a specific race condition caused by lack of visibility (stale values). All data races are race conditions, but not all race conditions are data races.

Q6: Is i++ atomic in Java? Why or why not?

A: No. i++ is a read-modify-write operation. The bytecode is: getfield → iconst_1 → iadd → putfield. Each instruction is atomic individually, but the sequence is not atomic.

Q7: Is x = 5 atomic? What about long x = 5L?

A: x = 5 (32-bit primitive) is atomic. long x = 5L is not atomic on 32-bit JVMs (split into two 32-bit writes). On 64-bit JVMs, long writes are atomic. Guaranteed: reads/writes to volatile long are atomic on all JVMs.

Part A: Conceptual Deep-Dive

Q8: What is the "check-then-act" problem? Give an example.

A: Check-then-act is a race condition where you check a condition, and between the check and the action, another thread changes the state. Example: lazy initialization (if (instance == null) { instance = new MyObject(); }).

Q9: What is the "put-if-absent" race condition and how do you fix it?

A: This is a specific check-then-act with a Map. Fixes: (1) synchronized around the whole block, (2) ConcurrentHashMap.putIfAbsent(), (3) ConcurrentHashMap.computeIfAbsent() (preferred for high concurrency).

Q10: Is HashMap thread-safe? What happens if two threads modify it concurrently?

A: No. Concurrent modifications can cause: (1) lost updates, (2) corrupted internal structure (circular lists → infinite loops), (3) NullPointerException or ArrayIndexOutOfBoundsException.

Q11: What is the difference between synchronized and ReentrantLock?

A: ReentrantLock offers: try-lock, timed-lock, interruptible-lock, multiple condition variables, fairness. synchronized is simpler and often preferred for low contention. Both are reentrant.

Q12: What does a thread do when it enters a synchronized block?

A: It attempts to acquire the monitor. If free, it acquires and enters. If held by another thread, it enters BLOCKED state and waits. If held by the same thread, it re-enters (reentrant).

Q13: What is the difference between locking on this and locking on a private final Object?

A: private final Object provides better encapsulation, lower deadlock risk, and more flexibility (multiple locks). synchronized(this) is less encapsulated (external code can lock on your object).

Q14: Can you synchronized on a null reference?

A: No. It throws NullPointerException.

Q15: What is the difference between synchronized static method and instance method?

A: Instance method locks on this. Static method locks on MyClass.class. They can run concurrently (different locks).

Q16: What is a "monitor" in Java?

A: A monitor is a synchronization mechanism that provides: (1) mutual exclusion (only one thread can enter), (2) condition waiting (wait()/notify()). Every Java object has a built-in monitor.

Q17: What is "lock coarsening" and "lock elision"?

A: JIT optimizations. Lock coarsening = merging adjacent synchronized blocks. Lock elision = removing a synchronized block entirely if the JIT detects the lock is never contended.

Q18: What does volatile guarantee?

A: (1) Visibility: Writes are immediately visible to all threads. (2) Ordering (Happens-Before): A write to a volatile variable happens-before any subsequent read. It does NOT guarantee atomicity for compound actions.

Part A: Conceptual Deep-Dive

Q19: When should you use volatile?

A: (1) Simple flags (running, shutdown), (2) Single variable written by one thread and read by others, (3) Configuration objects that are safely published.

Q20: When should you NOT use volatile?

A: (1) Compound actions (count++), (2) Dependent variables (two variables must be updated together), (3) Long running computations with internal state.

Q21: What is the difference between volatile and synchronized?

A: volatile provides visibility and ordering, but not atomicity. synchronized provides all three. volatile is cheaper (no blocking, no OS mutex).

Q22: Can you make long and double atomic without synchronized?

A: Yes, by using volatile. On 32-bit JVMs, volatile ensures the write is atomic.

A: Double-checked locking was a performance optimization for singleton initialization. Broken because: due to instruction reordering, instance can be assigned before the constructor completes, causing other threads to see a partially constructed object. The fix (Java 5+): make instance volatile.

Q24: How does final help with thread safety?

A: Initialization Safety: final fields are guaranteed to be fully initialized before the constructor completes, and their values are visible to all threads after the constructor finishes, even without synchronization.

Q25: What is "safe publication" and how does final help?

A: Safe publication is making an object visible to other threads without violating the JMM. final helps because the JMM guarantees final fields are visible after the constructor completes.

Q26: Can a class with mutable fields be thread-safe?

A: Yes, if you synchronize access to those fields. Example: java.util.Vector (all methods are synchronized). However, modern concurrent classes use better techniques (lock striping, CAS).

Q27: What is the difference between immutable and effectively immutable?

A: Immutable = cannot be changed after construction (all fields final). Effectively immutable = mutable but never mutated after being safely published (e.g., Collections.unmodifiableList()).

A: A defensive copy is a copy of a mutable object returned to the caller, preventing the caller from modifying the original. Used in immutable classes with mutable fields (e.g., Date).

Q29: What is ThreadLocal and when should you use it?

Q38: What is the "happens-before" relationship?

A: A JMM rule that defines when one action is guaranteed to be visible to another. Key rules: Program order, Monitor lock, Volatile, Thread start, Thread join, Interruption, Finalizer, and Transitivity.

Q39: What is the difference between "happens-before" and "synchronizes-with"?
