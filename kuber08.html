Introduction to Secrets

A Kubernetes Secret is an object that contains a small amount of sensitive data such as passwords, tokens, or keys. Secrets are designed to store confidential information separately from Pod definitions and container images.

Unlike ConfigMaps, Secrets provide additional security protections and are specifically intended for sensitive information that shouldn't be stored in plain text.

Security Note: While Secrets are more secure than ConfigMaps, they are not encrypted by default in etcd. For production environments, consider enabling encryption at rest.

Secret Features

  • Base64 encoding for data storage
  • Multiple secret types for different use cases
  • Automatic mounting as volumes or environment variables
  • Built-in Docker registry integration
  • TLS certificate management
  • Service account token automation

When to Use Secrets vs ConfigMaps

Use Secrets for: Passwords, API keys, TLS certificates, SSH keys, database credentials, OAuth tokens

Use ConfigMaps for: Configuration files, environment settings, command-line arguments, non-sensitive application config

What is a Secret?

Secret Architecture

Secrets are Kubernetes objects that store sensitive data in a base64-encoded format. They can be consumed by Pods as environment variables or mounted as files in volumes.

How Secrets Work

Base64 Encoding

Secrets are stored as base64-encoded strings in etcd

In-Memory Filesystem

When mounted as volumes, secrets use tmpfs (in-memory)

Automatic Updates

Secret volumes are automatically updated when secrets change

Security Considerations:

  • Not encrypted by default in etcd
  • Accessible to users with API permissions
  • Consider external secret solutions for enhanced security

Creating Secrets

Secrets can be created using various methods. It's important to choose the method that provides the best security for your sensitive data.

Warning: Avoid storing secrets in version control. Use secure secret management tools and consider external secret solutions for production.

Creation Methods

Imperative Commands


# Create from literal values
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password=secret123

# Create from file
kubectl create secret generic tls-secret \
  --from-file=tls.crt=./cert.crt \
  --from-file=tls.key=./cert.key

# Create Docker registry secret
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=admin \
  --docker-password=secret \
  --docker-email=admin@example.com

# Create from environment file
kubectl create secret generic app-secret \
  --from-env-file=secrets.env

Declarative YAML


apiVersion: v1
kind: Secret
metadata:
  name: app-secret
  namespace: default
type: Opaque
data:
  # Values must be base64 encoded
  username: YWRtaW4=
  password: c2VjcmV0MTIz
  api-key: YXBpLWtleS1zZWNyZXQ=

# To encode values:
# echo -n "secret123" | base64
# → c2VjcmV0MTIz

# Alternative: use stringData for plain text
stringData:
  database-url: postgresql://user:pass@localhost:5432/db
  # stringData values are automatically
  # base64 encoded when stored

Environment Variables

Using Secrets as Environment Variables

Secrets can be injected as environment variables into containers. This method is convenient but has security implications.

Security Consideration:

Environment variables may be visible in shell history, logs, and debugging tools. Use secret volumes for highly sensitive data.

Best Practices:

  • Use for less sensitive data like API endpoints
  • Avoid for passwords and private keys
  • Consider using secret volumes for certificates
  • Use optional: true for non-critical secrets

Environment Variables Example


apiVersion: v1
kind: Pod
metadata:
  name: app-pod-with-secrets
spec:
  containers:
  - name: app-container
    image: my-app:1.0
    env:
    # Single value from Secret
    - name: DB_USERNAME
      valueFrom:
        secretKeyRef:
          name: database-secret
          key: username
          
    # Another single value
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: database-secret
          key: password
          
    # Optional secret (won't fail if missing)
    - name: API_KEY
      valueFrom:
        secretKeyRef:
          name: api-secret
          key: api-key
          optional: true

    # All key-value pairs from Secret as env vars
    envFrom:
    - secretRef:
        name: app-secret
        optional: false

  # The Secret must exist in the same namespace
  # or be explicitly referenced

envFrom Example


apiVersion: v1
kind: Pod
metadata:
  name: app-pod-envfrom
spec:
  containers:
  - name: app-container
    image: my-app:1.0
    envFrom:
    # Import all key-value pairs from Secret
    - secretRef:
        name: database-secret
      
    # Import from multiple Secrets
    - secretRef:
        name: api-secret
        
    # Optional Secret
    - secretRef:
        name: monitoring-secret
        optional: true
        
    # Additional explicit environment variables
    - name: APP_ENV
      value: "production"

  restartPolicy: Never

envFrom imports all key-value pairs from a Secret as environment variables. Each key becomes an environment variable name.

Secret Volumes

Mounting Secrets as Volumes

Secrets can be mounted as volumes in Pods, providing a more secure way to access sensitive data compared to environment variables.

Security Benefits:

  • • Secrets are stored in tmpfs (in-memory filesystem)
  • • Not written to disk on nodes
  • • Automatic updates when secrets change
  • • Better isolation between containers

Use Cases:

  • TLS certificates and private keys
  • SSH keys and configuration files
  • Any sensitive file-based configuration
  • When hot-reloading of secrets is needed

Secret Volume Example


apiVersion: v1
kind: Pod
metadata:
  name: app-pod-secret-volume
spec:
  containers:
  - name: app-container
    image: my-app:1.0
    volumeMounts:
    - name: secret-volume
      mountPath: /etc/secrets
      readOnly: true
      
    - name: tls-volume
      mountPath: /etc/tls
      readOnly: true
      
    - name: single-secret-volume
      mountPath: /app/database.password
      subPath: password
      readOnly: true

  volumes:
  # Mount entire Secret as files
  - name: secret-volume
    secret:
      secretName: app-secret
      defaultMode: 0400  # Read-only permissions
      
  # Mount TLS Secret
  - name: tls-volume
    secret:
      secretName: tls-secret
      items:
      - key: tls.crt
        path: certificate.crt
      - key: tls.key
        path: private.key
      defaultMode: 0444
      
  # Mount single key from Secret
  - name: single-secret-volume
    secret:
      secretName: database-secret
      items:
      - key: password
        path: password

Hot Reloading Secrets


apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app-container
        image: my-app:1.0
        volumeMounts:
        - name: config-secret
          mountPath: /etc/config
        # Application should watch for file changes
        # or use SIGHUP to reload configuration

      volumes:
      - name: config-secret
        secret:
          secretName: app-config-secret
          # Secret updates are automatically
          # propagated to the volume
          # Kubelet sync period: ~1 minute

      # Optional: Add checksum annotation to
      # force Pod restart on Secret change
      # annotations:
      #   checksum/config: {{ include ( .Files.Get "secret.yaml") | sha256sum }}

Secret volumes automatically update when the underlying Secret changes. Applications should be designed to detect and reload these changes.

Image Pull Secrets

Private Registry Authentication

Image pull secrets are used to authenticate with private container registries when pulling images.

When to Use Image Pull Secrets:

  • • Private Docker Hub repositories
  • • Enterprise container registries
  • • Cloud provider container registries
  • • Any registry requiring authentication

Configuration Methods:

  • Pod-level imagePullSecrets
  • ServiceAccount imagePullSecrets
  • Node-level docker configuration

Image Pull Secret Examples


# Create Docker registry secret
kubectl create secret docker-registry my-registry-secret \
  --docker-server=registry.example.com \
  --docker-username=admin \
  --docker-password=secretpassword \
  --docker-email=admin@example.com

# Use in Pod specification
apiVersion: v1
kind: Pod
metadata:
  name: private-image-pod
spec:
  containers:
  - name: app-container
    image: registry.example.com/my-private-app:1.0
  imagePullSecrets:
  - name: my-registry-secret

# Use in Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-deployment
spec:
  template:
    spec:
      containers:
      - name: app
        image: registry.example.com/app:1.0
      imagePullSecrets:
      - name: my-registry-secret

Service Account Configuration


# Add image pull secret to service account
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-service-account
  namespace: default
imagePullSecrets:
- name: my-registry-secret

# Use the service account in Pods
apiVersion: v1
kind: Pod
metadata:
  name: pod-with-sa
spec:
  serviceAccountName: my-service-account
  containers:
  - name: app
    image: registry.example.com/app:1.0
    # No need for imagePullSecrets in Pod spec
    # when using ServiceAccount with pull secrets

# Benefits:
# - Centralized registry configuration
# - Applies to all Pods using the ServiceAccount
# - No need to specify in each Pod/Deployment

Using ServiceAccounts with image pull secrets is the recommended approach for managing registry authentication across multiple Pods.

Security Considerations

Understanding the security implications of Kubernetes Secrets is crucial for protecting sensitive data in your cluster.

Built-in Security Features

Base64 Encoding

Secrets are stored as base64-encoded strings, providing basic obfuscation.

tmpfs Storage

Secret volumes use in-memory filesystem, not written to disk.

RBAC Protection

Secrets are protected by Kubernetes RBAC system.

Security Limitations

Not Encrypted by Default

Secrets are stored as base64 in etcd without encryption.

Accessible to Admins

Cluster administrators can access all secrets.

Environment Variable Exposure

Secrets in environment variables may appear in logs.

Enhancing Secret Security

Enable Encryption at Rest

Configure etcd encryption for secrets storage.

EncryptionConfiguration

Use External Secret Managers

Integrate with HashiCorp Vault, AWS Secrets Manager, etc.

CSI Secret Store

Implement Network Policies

Restrict access to etcd and API server.

NetworkPolicy

Encryption at Rest Configuration


apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
    - secrets
    providers:
    - aescbc:
        keys:
        - name: key1
          secret: c2VjcmV0IGVuY3J5cHRpb24ga2V5
    - identity: {}  # Fallback: no encryption

# Apply configuration to API server
# --encryption-provider-config=/etc/kubernetes/encryption-config.yaml

# After enabling, recreate secrets to encrypt them:
kubectl get secrets --all-namespaces -o json | \
  kubectl replace -f -

Secret Best Practices

Security Guidelines

Enable Encryption at Rest

Always encrypt secrets in etcd for production clusters.

Use RBAC Effectively

Restrict secret access using Role-Based Access Control.

Prefer Secret Volumes over Environment Variables

Use volumes for sensitive data to avoid exposure in logs.

Operational Practices

Use External Secret Managers

Consider HashiCorp Vault or cloud secret managers for enhanced security.

Rotate Secrets Regularly

Implement secret rotation policies and automate where possible.

Audit Secret Usage

Regularly review which applications are using which secrets.

Pro Tip: External Secret Solutions

For enterprise-grade secret management, consider using external solutions like HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault with the Kubernetes CSI Secret Store driver. These provide advanced features like dynamic secrets, lease management, and detailed audit logs.
