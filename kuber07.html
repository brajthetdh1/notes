Kubernetes Overview

What is Container Orchestration?

Kubernetes is an open-source container orchestration platform originally developed by Google. It automates the deployment, scaling, and management of containerized applications. In today's microservices architecture, applications are broken down into smaller, independent services that run in containers. While Docker provides the containerization technology, Kubernetes manages these containers at scale.

Think of Kubernetes as the operating system for your cloud-native applications. Just as an OS manages processes, memory, and storage on a single machine, Kubernetes manages containers across a cluster of machines, providing:

  • Service Discovery and Load Balancing: Automatically exposes containers using DNS names or IP addresses and distributes network traffic
  • Storage Orchestration: Automatically mounts storage systems of your choice
  • Automated Rollouts and Rollbacks: Gradually updates applications while monitoring health
  • Automatic Bin Packing: Places containers based on resource requirements and constraints
  • Self-healing: Restarts failed containers, replaces and reschedules containers when nodes die
  • Secret and Configuration Management: Stores and manages sensitive information

Evolution of Application Deployment

Traditional Deployment

Applications run directly on physical servers with no isolation, leading to resource conflicts.

Virtualized Deployment

Virtual machines allow multiple applications to run on a single physical server with better isolation.

Container Deployment

Containers provide similar isolation as VMs but are more lightweight and share the OS kernel.

Why Kubernetes for Java Applications?

Java applications, especially those built with Spring Boot, Micronaut, or Quarkus, are perfectly suited for Kubernetes. The JVM's mature ecosystem, combined with Kubernetes' scaling capabilities, allows enterprises to run massive Java workloads efficiently. Kubernetes handles the operational complexity while Java provides the robust application runtime.

Kubernetes Architecture

Cluster Architecture Overview

A Kubernetes cluster consists of a set of nodes (machines) that run containerized applications. The cluster has two main components: the control plane (master nodes) and the worker nodes. The control plane makes global decisions about the cluster and detects and responds to cluster events. Worker nodes host the Pods that are the components of the application workload.

Control Plane Components

API Server

The front-end of the Kubernetes control plane that exposes the Kubernetes API. It's the central management entity that receives all REST requests for modifications, serving as the gateway to the cluster.

All communications between components, as well as external CLI tools like kubectl, go through the API Server. It validates and configures data for API objects such as pods, services, and deployments.

etcd

A consistent and highly-available key-value store used as Kubernetes' backing store for all cluster data. It stores the configuration data, state, and metadata of the cluster.

etcd is designed with distributed systems in mind and uses the Raft consensus algorithm to manage a highly available replicated log. All cluster data, such as pod details, secrets, and configmaps, is stored here.

Scheduler

The component that assigns Pods to Nodes based on resource availability and constraints. It watches for newly created Pods with no assigned node and selects a node for them to run on.

The scheduler considers factors like resource requirements, hardware/policy constraints, affinity and anti-affinity specifications, data locality, and deadlines when making scheduling decisions.

Controller Manager

Runs controller processes that regulate the state of the cluster. Each controller is a separate process but they are compiled into a single binary for simplicity.

Important controllers include the Node Controller (managing node status), Replication Controller (maintaining correct number of pods), Endpoints Controller (populating Endpoints objects), and Service Account & Token Controllers (creating default accounts and API access tokens).

Node Components

Kubelet

An agent that runs on each node in the cluster. It ensures that containers are running in a Pod by taking a set of PodSpecs provided through various mechanisms and ensuring the described containers are running and healthy.

The Kubelet doesn't manage containers that were not created by Kubernetes. It works in terms of a PodSpec, which is a YAML or JSON object that describes a pod. The Kubelet takes these PodSpecs and ensures the containers described in those PodSpecs are running and healthy.

Kube Proxy

A network proxy that runs on each node in the cluster, maintaining network rules on the node. These network rules allow network communication to your Pods from network sessions inside or outside of your cluster.

Kube-proxy uses the operating system packet filtering layer if available, otherwise it forwards the traffic itself. It watches the Kubernetes API for changes to Services and Endpoints and updates the iptables rules accordingly to route traffic to the correct pods.

Container Runtime

The software responsible for running containers. Kubernetes supports several container runtimes: Docker, containerd, CRI-O, and any implementation of the Kubernetes CRI (Container Runtime Interface).

The container runtime is responsible for pulling images from registries, managing container lifecycle, and providing an isolated environment for containers to run. Each pod runs in its own cgroups and namespaces for isolation.

Pod

The smallest deployable unit in Kubernetes, representing a single instance of a running process in the cluster. A Pod encapsulates one or more application containers, storage resources, and a unique network IP.

Containers within a Pod share the same network namespace, meaning they can find each other via localhost, and can share storage volumes. Pods are designed to be ephemeral - when a Pod dies, it's not resurrected; instead, a new Pod is created.

High Availability Considerations

For production environments, the control plane should be set up for high availability. This typically involves running multiple master nodes with load-balanced API servers, a clustered etcd database, and redundant scheduler and controller manager instances. Worker nodes should also be distributed across availability zones for resilience.

Kubernetes Core Concepts

Pods: The Basic Building Blocks

A Pod is the smallest and simplest unit in the Kubernetes object model that you create or deploy. It represents a single instance of a running process in your cluster and contains one or more containers, such as Docker containers. When you create a Pod, you can define how much CPU and memory (RAM) each container needs.

Controllers: Managing Pods

While Pods are the basic deployable units in Kubernetes, you typically don't create them directly. Instead, you use controllers which provide higher-level abstractions to manage the Pod lifecycle. Controllers ensure that the desired state of the cluster matches the observed state.

Deployment

Provides declarative updates for Pods and ReplicaSets. You describe a desired state in a Deployment, and the Deployment Controller changes the actual state to the desired state at a controlled rate.

Deployments are perfect for stateless applications and support rolling updates, rollbacks, and scaling operations. They manage ReplicaSets which in turn manage Pods.

StatefulSet

Manages the deployment and scaling of a set of Pods, and provides guarantees about the ordering and uniqueness of these Pods.

Unlike Deployments, StatefulSets maintain a sticky identity for each of their Pods. These pods are created from the same spec, but are not interchangeable - each has a persistent identifier that it maintains across any rescheduling.

DaemonSet

Ensures that all (or some) Nodes run a copy of a Pod. As nodes are added to the cluster, Pods are added to them. As nodes are removed from the cluster, those Pods are garbage collected.

Useful for cluster-wide services like log collection (Fluentd, Logstash) or monitoring (Prometheus Node Exporter) that need to run on every node.

Job & CronJob

A Job creates one or more Pods and ensures that a specified number of them successfully terminate. As pods successfully complete, the Job tracks the successful completions.

A CronJob creates Jobs on a time-based schedule, similar to the Unix cron utility. It's perfect for periodic tasks like database backups, report generation, or sending notifications.

Services & Networking

Services in Kubernetes provide a stable endpoint to access a group of Pods. Since Pods are ephemeral - they can be created, destroyed, and rescheduled - their IP addresses are not reliable for communication. Services solve this problem by providing a stable IP address and DNS name that load balances traffic to the appropriate Pods.

Service Types

ClusterIP (Default)

Exposes the service on a cluster-internal IP. The service is only reachable from within the cluster. This is the default ServiceType.

NodePort

Exposes the service on each Node's IP at a static port. A ClusterIP service is automatically created, and the NodePort service will route to it.

LoadBalancer

Exposes the service externally using a cloud provider's load balancer. NodePort and ClusterIP services are automatically created.

ExternalName

Maps the service to the contents of the externalName field by returning a CNAME record with its value.

Ingress

An API object that manages external access to the services in a cluster, typically HTTP/HTTPS. Ingress can provide load balancing, SSL termination, and name-based virtual hosting.

While a Service routes traffic within the cluster, Ingress is the entrypoint from outside the cluster. It requires an Ingress Controller to be installed in the cluster.

Network Policies

Specifies how groups of pods are allowed to communicate with each other and other network endpoints. Network Policies use labels to select pods and define rules which specify what traffic is allowed to the selected pods.

Configuration & Storage

ConfigMaps

ConfigMaps allow you to decouple configuration artifacts from image content to keep containerized applications portable. You can store non-confidential data in key-value pairs that pods can consume as environment variables, command-line arguments, or configuration files in a volume.

Secrets

Similar to ConfigMaps but designed to hold sensitive information, such as passwords, OAuth tokens, and SSH keys. Storing this information in a Secret is safer and more flexible than putting it in a Pod definition or container image.

Volumes

A directory containing data, accessible to the containers in a pod. Kubernetes supports many types of volumes, and a pod can use any number of them simultaneously. When a pod is destroyed, the data in ephemeral volumes is destroyed, but data in persistent volumes remains.

Persistent Volumes (PV)

A piece of storage in the cluster that has been provisioned by an administrator or dynamically provisioned using Storage Classes. PVs are cluster resources, just like nodes.

Persistent Volume Claims (PVC)

A request for storage by a user. It is similar to a pod - pods consume node resources and PVCs consume PV resources. Pods can request specific levels of resources (CPU and Memory), while PVCs can request specific size and access modes.

Storage Classes

Allow administrators to describe the "classes" of storage they offer. Different classes might map to quality-of-service levels, backup policies, or arbitrary policies determined by the cluster administrators.

Java Integration with Kubernetes

Containerizing Java Applications

Containerizing Java applications involves packaging your application code, dependencies, and the JVM into a container image. This image can then be deployed consistently across different environments. When containerizing Java applications for Kubernetes, there are several important considerations to ensure optimal performance and resource utilization.

Dockerfile Best Practices for Java

# Multi-stage build for smaller final image
FROM maven:3.8.4-openjdk-11 AS builder
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# Runtime stage
FROM openjdk:11-jre-slim

# Add user for security (don't run as root)
RUN groupadd -r java-user && useradd -r -g java-user java-user

# Install necessary packages
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

# Copy the JAR from the builder stage
COPY --from=builder /app/target/myapp.jar app.jar

# Change to non-root user
USER java-user

# Expose application port
EXPOSE 8080

# JVM options optimized for containers
ENV JAVA_OPTS="-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0 -XX:+UseG1GC"

# Health check
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
    CMD curl -f http://localhost:8080/actuator/health || exit 1

# Run the application
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]

JVM Memory Management in Containers

The JVM traditionally wasn't container-aware, but recent versions have improved significantly. Key considerations:

  • Use -XX:+UseContainerSupport to make the JVM respect container memory limits
  • Set -XX:MaxRAMPercentage instead of fixed -Xmx values for flexibility
  • Consider using the -XX:+UseG1GC garbage collector for better performance
  • Monitor memory usage with tools like VisualVM or JMX

Base Image Selection

Choosing the right base image is crucial for security and performance:

  • openjdk:11-jre-slim: Small footprint, good for production
  • eclipse-temurin:11-jre: Popular alternative to OpenJDK
  • distroless/java: Minimal image with only Java runtime
  • Alpine Linux variants: Very small but may have compatibility issues

Basic Client Usage Example

import io.kubernetes.client.openapi.ApiClient;
import io.kubernetes.client.openapi.Configuration;
import io.kubernetes.client.openapi.apis.CoreV1Api;
import io.kubernetes.client.openapi.models.V1Pod;
import io.kubernetes.client.openapi.models.V1PodList;
import io.kubernetes.client.util.Config;

public class KubernetesClientExample {
    
    public static void main(String[] args) {
        try {
            // Initialize client - automatically detects kubeconfig
            ApiClient client = Config.defaultClient();
            Configuration.setDefaultApiClient(client);
            
            CoreV1Api api = new CoreV1Api();
            
            // List all pods in all namespaces
            V1PodList podList = api.listPodForAllNamespaces(
                null, null, null, null, null, null, null, null, null, null);
            
            System.out.println("Pods in cluster:");
            for (V1Pod pod : podList.getItems()) {
                System.out.printf("Name: %s, Namespace: %s, Status: %s%n",
                    pod.getMetadata().getName(),
                    pod.getMetadata().getNamespace(),
                    pod.getStatus().getPhase());
            }
            
            // Create a new pod using the fluent API
            V1Pod newPod = new CoreV1Api(client).pods()
                .inNamespace("default")
                .create()
                .body(new V1PodBuilder()
                    .withNewMetadata()
                        .withName("test-pod")
                        .addToLabels("app", "test")
                    .endMetadata()
                    .withNewSpec()
                        .addNewContainer()
                            .withName("test-container")
                            .withImage("busybox:latest")
                            .withCommand("sh", "-c", "echo 'Hello Kubernetes'; sleep 3600")
                        .endContainer()
                    .endSpec()
                    .build())
                .execute();
            
            System.out.println("Created pod: " + newPod.getMetadata().getName());
            
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}

Watching Resources

import io.kubernetes.client.openapi.ApiClient;
import io.kubernetes.client.openapi.ApiException;
import io.kubernetes.client.openapi.apis.CoreV1Api;
import io.kubernetes.client.openapi.models.V1Pod;
import io.kubernetes.client.util.Watch;
import okhttp3.Call;

public class PodWatcherExample {
    
    public static void main(String[] args) throws ApiException {
        ApiClient client = Config.defaultClient();
        CoreV1Api api = new CoreV1Api(client);
        
        Call call = api.listPodForAllNamespacesCall(
            null, null, null, null, null, null, null, null, null, true, null);
        
        try (Watch watch = Watch.createWatch(
                client,
                call,
                new TypeToken>(){}.getType())) {
            
            for (Watch.Response item : watch) {
                V1Pod pod = item.object;
                String eventType = item.type;
                
                System.out.printf("Event: %s, Pod: %s/%s, Phase: %s%n",
                    eventType,
                    pod.getMetadata().getNamespace(),
                    pod.getMetadata().getName(),
                    pod.getStatus().getPhase());
                
                // Handle different event types
                switch (eventType) {
                    case "ADDED":
                        System.out.println("New pod added to cluster");
                        break;
                    case "MODIFIED":
                        System.out.println("Pod was modified");
                        break;
                    case "DELETED":
                        System.out.println("Pod was deleted");
                        break;
                }
            }
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}

Database Deployment with StatefulSet

Stateful applications like databases require special handling in Kubernetes. StatefulSets provide stable, unique network identifiers and stable persistent storage.

PostgreSQL StatefulSet

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgresql
  namespace: java-app-production
spec:
  serviceName: postgresql
  replicas: 1
  selector:
    matchLabels:
      app: postgresql
  template:
    metadata:
      labels:
        app: postgresql
    spec:
      containers:
      - name: postgresql
        image: postgres:13
        ports:
        - containerPort: 5432
          name: postgresql
        env:
        - name: POSTGRES_DB
          value: mydb
        - name: POSTGRES_USER
          value: appuser
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef:
              name: java-app-secrets
              key: database-password
        volumeMounts:
        - name: postgresql-data
          mountPath: /var/lib/postgresql/data
        resources:
          requests:
            memory: "256Mi"
            cpu: "100m"
          limits:
            memory: "1Gi"
            cpu: "500m"
        livenessProbe:
          exec:
            command:
            - /bin/sh
            - -c
            - exec pg_isready -U appuser -d mydb
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          exec:
            command:
            - /bin/sh
            - -c
            - exec pg_isready -U appuser -d mydb
          initialDelaySeconds: 5
          periodSeconds: 5
      volumes:
      - name: postgresql-data
        persistentVolumeClaim:
          claimName: postgresql-pvc
  volumeClaimTemplates:
  - metadata:
      name: postgresql-data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "fast-ssd"
      resources:
        requests:
          storage: 10Gi

Best Practices for Java in Kubernetes

JVM Tuning for Containers

Memory Management

  • Use -XX:+UseContainerSupport to make JVM aware of container limits
  • Set -XX:MaxRAMPercentage=75.0 instead of fixed -Xmx values
  • Consider -XX:InitialRAMPercentage=50.0 for faster startup
  • Use -XX:+UseG1GC for better garbage collection performance
  • Set -XX:MaxGCPauseMillis=200 to control GC pauses
  • Use -XX:NativeMemoryTracking=summary for memory analysis

CPU Optimization

  • Set appropriate CPU requests and limits in Kubernetes
  • Use -XX:ActiveProcessorCount to match container CPU limits
  • Consider using -XX:+UseParallelGC for throughput-oriented applications
  • Use -XX:CICompilerCount to control JIT compiler threads

Container-Specific Optimizations

  • Use slim or distroless base images to reduce attack surface
  • Run as non-root user for security
  • Set securityContext in pod specifications
  • Use multi-stage builds to create minimal final images
  • Leverage image layer caching in CI/CD pipelines
  • Regularly update base images for security patches

Startup Performance

  • Use -Dspring.context.lazy-initialization=true for Spring Boot
  • Consider using Spring Boot 2.4+ with layered JARs
  • Explore GraalVM native image for faster startup
  • Use startupProbe for applications with slow startup
  • Set appropriate initialDelaySeconds for probes

Application Design for Kubernetes

Health Checks

Proper health checks are critical for Kubernetes to manage your application lifecycle effectively.

Liveness Probe

Indicates whether the container is running. If failed, the container will be restarted.

Readiness Probe

Indicates whether the container is ready to serve requests. If failed, the container will be removed from service endpoints.

Startup Probe

Indicates whether the application has started. Useful for slow-starting applications.

// Spring Boot Actuator health endpoints
@RestController
public class CustomHealthIndicator 
    implements HealthIndicator {
    
    @Override
    public Health health() {
        // Custom health check logic
        if (isHealthy()) {
            return Health.up()
                .withDetail("database", "connected")
                .build();
        } else {
            return Health.down()
                .withDetail("database", "disconnected")
                .build();
        }
    }
}

Security Best Practices

Container Security

  • Use minimal base images to reduce attack surface
  • Regularly scan images for vulnerabilities
  • Run containers as non-root users
  • Use read-only root filesystems when possible
  • Drop all capabilities and add only required ones
  • Use seccomp, AppArmor, or SELinux profiles

Network Security

  • Implement Network Policies to control traffic between pods
  • Use TLS for all internal and external communication
  • Implement mutual TLS (mTLS) for service-to-service communication
  • Use service meshes like Istio for advanced security features
  • Limit external access using firewalls and security groups

Secrets Management

  • Never store secrets in container images or source code
  • Use Kubernetes Secrets with proper access controls
  • Implement secret rotation policies
  • Consider external secret managers like HashiCorp Vault
  • Encrypt Secrets at rest (enable encryption at rest in Kubernetes)

RBAC & Access Control

  • Implement Role-Based Access Control (RBAC) for Kubernetes
  • Use the principle of least privilege
  • Regularly audit permissions and access
  • Use service accounts with minimal permissions
  • Implement Pod Security Standards
