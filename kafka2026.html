⚠️ ZooKeeper: Removed, Not Deprecated

Apache ZooKeeper is no longer part of Kafka. Kafka 4.0 (released March 2025) eliminated ZooKeeper entirely — no fallback, no compatibility mode, and no security support.

What Changed

  • Kafka 3.9 was the last release to support ZooKeeper.
  • Kafka 4.0+ is KRaft-only. ZooKeeper mode is gone.
  • ZooKeeper security support ended November 2025.

Migration Path (Mandatory)

  • Upgrade to Kafka 3.9 (bridge release).
  • Migrate to KRaft while still on 3.x.
  • Then upgrade to Kafka 4.x.

Why it matters: ZooKeeper required a separate distributed system to operate, monitor, and secure. Removing it simplifies the stack and unlocks features that were difficult or impossible with ZooKeeper — such as 2 million partitions per cluster and dramatically faster controller failovers.

📜 ZooKeeper Setup (Legacy Reference)

Kept for historical context — do not use for new deployments.

Complete guide to setting up ZooKeeper for Kafka, explained step-by-step, from minimal local setup to a production-ready ensemble.

🔹 1. Download & Install ZooKeeper

Option 1: Download binary

wget https://downloads.apache.org/zookeeper/stable/apache-zookeeper-3.9.1-bin.tar.gz
tar -xzf apache-zookeeper-3.9.1-bin.tar.gz
cd apache-zookeeper-3.9.1-bin

Option 2: Use package manager (Linux)

sudo apt-get update
sudo apt-get install zookeeperd

🔹 2. Configure ZooKeeper

Create a zoo.cfg file inside conf/:

tickTime=2000
dataDir=/var/lib/zookeeper
clientPort=2181
initLimit=5
syncLimit=2

Explanation:

tickTime → basic time unit in ms.
dataDir → directory to store ZooKeeper state.
clientPort → port clients (Kafka brokers) will connect to.
initLimit → number of ticks for followers to sync with leader during startup.
syncLimit → number of ticks for followers to sync with leader during operation.

🔹 3. Set myid (For Ensemble)

If running multiple ZooKeeper nodes, each node needs a unique myid:

echo 1 > /var/lib/zookeeper/myid  # Node 1
echo 2 > /var/lib/zookeeper/myid  # Node 2
echo 3 > /var/lib/zookeeper/myid  # Node 3

🔹 4. Configure Ensemble (Multiple Nodes)

Add the following to zoo.cfg on all nodes:

server.1=zk1:2888:3888
server.2=zk2:2888:3888
server.3=zk3:2888:3888

Explanation:

server.X=hostname:leaderPort:electionPort
Each node knows about all other nodes.

🔹 5. Start ZooKeeper

Single-node (dev/test):

bin/zkServer.sh start

Check status:

bin/zkServer.sh status

Multi-node ensemble:
Start ZooKeeper on each node individually.
Ensure all nodes show Mode: leader or Mode: follower.

🔹 6. Connect Kafka to ZooKeeper

In Kafka server.properties:

zookeeper.connect=zk1:2181,zk2:2181,zk3:2181

Kafka brokers will register with ZooKeeper at this address.
ZooKeeper handles metadata, leader election, and broker liveness.

🔹 7. Verify Setup

List brokers registered:

bin/zookeeper-shell.sh zk1:2181
ls /brokers/ids

You should see the broker IDs of all active Kafka brokers.

✅ Minimal interview-safe summary:
Install ZooKeeper.
Configure zoo.cfg with tickTime, dataDir, clientPort.
Set myid for each node.
Add server.X lines for ensemble.
Start ZooKeeper, check status.
Connect Kafka brokers using zookeeper.connect.

⚙️ KRaft: The Only Metadata Mode

🔹 Controller Quorum

A small set of Kafka nodes (typically 3 or 5) run the Raft consensus protocol to manage all cluster metadata. Dedicated controllers are recommended for production.

🔹 Brokers and Controllers

Nodes can be brokers, controllers, or both. process.roles=broker,controller works for small clusters; separate controller nodes isolate metadata load and improve stability.

🔹 Scale Benefits

  • 2 million partitions (vs ~200k with ZooKeeper).
  • Dramatically faster controller failover.
  • Single system to configure and monitor.

🔹 Pre-Vote (KIP-996)

Pre-vote reduces unnecessary leader elections caused by transient network issues, improving metadata stability.

⚠️ Migration Complexity: Not a Routine Bump

Migrating to Kafka 4.0 is a full architectural overhaul, not just a version number change. Organizations that start the migration expecting a simple upgrade discover these realities mid-project:

  • Controller quorum design must be planned — dedicated controllers, rack awareness, and quorum sizing.
  • Tooling and configs must be rewritten: zookeeper.connect, zookeeper.*, and legacy scripts are gone.
  • Deployment automation (Ansible, Terraform, Helm, Strimzi) needs updated templates.
  • Monitoring must be re-plumbed to KRaft metrics (controller quorum state, metadata lag).
  • Rollback is limited — once the bridge migration completes, going back is non-trivial.

📜 KRaft Setup

Step-by-step guide to setting up Kafka in KRaft mode (without ZooKeeper),
from single-node dev setup to a multi-node production-ready cluster:

🔹 1. Download & Install Kafka
wget https://downloads.apache.org/kafka/3.5.0/kafka_2.13-3.5.0.tgz
tar -xzf kafka_2.13-3.5.0.tgz
cd kafka_2.13-3.5.0

You can also use Docker or package managers for simpler setups.

🔹 2. Configure Kafka for KRaft Mode

Edit config/kraft/server.properties (or copy server.properties):

# Node roles: broker, controller, or both
process.roles=broker,controller

# Unique ID for this node
node.id=1

# Controller quorum (ID@host:port)
controller.quorum.voters=1@node1:9093,2@node2:9093,3@node3:9093

# Client and controller listeners
listeners=PLAINTEXT://:9092,CONTROLLER://:9093

# Data storage directory
log.dirs=/var/lib/kafka-logs

# Topic defaults
num.partitions=3
default.replication.factor=3

Explanation:

process.roles → defines if node is broker, controller, or both.
controller.quorum.voters → list of nodes forming the Raft quorum.
listeners → separate ports for clients and controller communication.
log.dirs → where Kafka stores logs (messages and metadata).

🔹 3. Format the Metadata Log (First-time setup)

Before starting KRaft, you need to format the metadata log for the controller quorum:

bin/kafka-storage.sh format -t  -c config/kraft/server.properties

 → generate a unique cluster ID (use uuidgen or kafka-storage.sh random-uuid).

Example:

export KAFKA_CLUSTER_ID=$(bin/kafka-storage.sh random-uuid)
bin/kafka-storage.sh format -t $KAFKA_CLUSTER_ID -c config/kraft/server.properties

🔹 4. Start Kafka Brokers / Controllers
bin/kafka-server-start.sh config/kraft/server.properties

Repeat on all nodes with unique node.id and adjusted listeners.
Controller quorum elects a leader automatically using Raft.

🔹 5. Verify Cluster

Check brokers and metadata:

bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092
bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

All brokers should be registered with the controller quorum.

🔹 6. Create Topics & Test
bin/kafka-topics.sh --create --topic orders \
  --bootstrap-server localhost:9092 \
  --partitions 3 \
  --replication-factor 2

bin/kafka-topics.sh --describe --topic orders --bootstrap-server localhost:9092

Send and consume messages as usual:

bin/kafka-console-producer.sh --topic orders --bootstrap-server localhost:9092
bin/kafka-console-consumer.sh --topic orders --from-beginning --bootstrap-server localhost:9092

Download Kafka.

💾 Tiered Storage (KIP-405, GA since Kafka 3.9)

Tiered storage decouples compute from storage. Recent data stays on broker disks (hot tier), while older segments are offloaded to object storage (cold tier). Clients read historical data with no code changes.

💰 Cost Savings

Object storage costs a fraction of SSD/NVMe. Organizations report 3–9× storage cost reductions.

⚡ Operational Gains

  • 15× faster partition reassignments.
  • 13–115× faster disaster recovery.
  • Independent scaling of compute and storage.

⚠️ Limitations You Must Know

  • Historical read bottleneck (pre-4.2): Only one partition per fetch could pull from remote storage, capping throughput at ~1 MiB by default. Fixed in Kafka 4.2 with multi-partition remote fetch[reference:8].
  • Minimum retention constraints: Low-cost object storage tiers often require a minimum 3-day retention period. Verify policy before setting local.retention.ms.
  • Storage backend support: Only S3-API-compatible stores are certified. Non-certified object stores may not be supported.
  • Operational visibility: Remote read latency and error metrics must be actively monitored — they are separate from broker-local metrics.
  • Migration of existing topics: Enabling tiered storage on existing topics does not retroactively offload data — only new segments are tiered.
# Broker-level enablement
remote.log.storage.system.enable=true
remote.log.metadata.manager.class.name=org.apache.kafka.server.log.remote.metadata.storage.TopicBasedRemoteLogMetadataManager

# Topic-level (example)
kafka-topics.sh --create --topic transactions \
  --config remote.storage.enable=true \
  --config local.retention.ms=86400000 \
  --config retention.ms=2592000000

📬 Share Groups (KIP-932): Queues for Kafka

Share groups bring queue-like semantics to Kafka. Unlike traditional consumer groups where each partition is assigned to exactly one consumer, multiple consumers in a share group can read from the same partition cooperatively, with per-message acknowledgment.

✅ When to Use

  • Point-to-point messaging patterns.
  • Workloads previously on RabbitMQ or SQS.
  • Elastic consumer scaling beyond partition count.

⚠️ Current Status

  • Preview in Kafka 4.1; GA in 4.2.
  • Early-access clusters cannot upgrade to 4.1.

🚨 Critical Trade-offs

  • No per-partition ordering: Records are dispatched independently; share groups do not guarantee message order within a partition. Do not use for ordering-sensitive workloads.
  • Dead-letter queue (DLQ) — now available in 4.4: KIP-1191 adds broker-managed DLQs[reference:9]. Records that exceed max delivery count or are explicitly rejected are routed to a configurable DLQ topic[reference:10]. Requires share.version=2[reference:11].
  • New consumer API: Share groups use KafkaShareConsumer — existing consumer code cannot be reused directly.

⚡ KIP-848: Next-Gen Consumer Rebalance

The classic rebalance protocol causes “stop-the-world” pauses. KIP-848 introduces a server-side, incremental protocol that delivers up to 20× faster rebalances and eliminates full-group synchronization barriers.

How to Enable

group.protocol=consumer

Server-side enabled by default in Kafka 4.0; clients opt in.

Real-World Impact

In one benchmark, rebalance time dropped from 103 seconds to 5 seconds.

⚠️ Adoption Friction

  • Classic protocol is still the default in KafkaConsumer. Adoption is opt-in.
  • No regex subscription support: subscribed_topic_regex is not supported in KIP-848[reference:12]. Regex evaluation moves to the broker using RE2/J, which requires full-topic-name matches and behaves differently from the classic protocol[reference:13].
  • Alternative Kafka implementations (e.g., Redpanda) may not support KIP-848 yet. Verify compatibility.
  • Kafka Streams gained KIP-1071 support in 4.1 — earlier versions cannot use the new protocol with Streams.

🛡️ ISR, ELR and Modern Durability

Core Settings (Still Valid)

  • Replication factor 3 at topic creation.
  • min.insync.replicas=2 — not 3 — leaving headroom for maintenance.
  • acks=all on producers for durability.
  • enable.idempotence=true to prevent duplicates during retries.

🔹 Eligible Leader Replicas (ELR, KIP-966)

ELR is a subset of ISR guaranteed to have complete data up to the high watermark. Only ELR replicas are eligible for leader election, preventing silent data loss even when ISR is non-empty. ELR is available from Kafka 4.0 and enabled by default on new clusters starting 4.1[reference:14].

Why ELR matters — a concrete failure:

  • Leader L receives messages and acknowledges to producers before followers fully replicate.
  • L crashes; a follower with ISR membership but incomplete data becomes leader.
  • Un-replicated messages are permanently lost — producers think they were written.
  • ELR restricts leader eligibility to replicas that provably have all acknowledged data, closing this gap. It provides minISR-1 tolerance to data-loss unclean shutdowns[reference:15].

🚨 NotEnoughReplicasException: Causes & Solutions

Occurs when a producer sends a message but the broker cannot meet the required number of in-sync replicas (ISR) for a partition. This ensures Kafka maintains strong durability and consistency guarantees.

Common Causes

  • Replicas offline: ISR falls below min.insync.replicas.
  • RF > available brokers: Topic has RF 3 but only 2 brokers exist.
  • Under-replicated partitions: Followers lag behind; ISR shrinks.

Fixes

  • Bring offline brokers back online.
  • Ensure replication factor ≤ broker count.
  • Reduce min.insync.replicas (durability trade-off).
  • Set producer acks=1 if full replication is not critical.
  • Monitor under-replicated partitions.

📉 Broker Down & ISR Drops to 0

Causes

  • Broker crash or shutdown.
  • Network partition isolating followers.
  • Disk or hardware failure preventing replication.

Consequences

  • Data loss risk: Unreplicated messages can be lost if a new leader lacks full data.
  • Producers fail: acks=all yields NotEnoughReplicasException.
  • Partitions may be temporarily unavailable.

🛡️ Strong Durability & Replication Consistency

Strong Durability

  • Append-only log: Messages are never overwritten.
  • Replication: Writes replicated to ISR.
  • acks=all + min.insync.replicas ensures messages are acknowledged only when replicated to enough brokers.

Replication Consistency

  • Leader-follower model: All writes go to leader; followers replicate.
  • ISR: Only fully caught-up replicas are eligible for leader election.
  • ELR (KIP-966): Further restricts leader eligibility to prevent silent data loss.

🚀 Producer Throughput & Partition Sizing

✅ Use LZ4 Compression

LZ4 offers the best balance of speed (~594 MB/s compression, ~2,428 MB/s decompression) for high-throughput workloads.

⚠️ Avoid ZSTD

ZSTD has known data-corruption edge cases in certain librdkafka versions. Stick with LZ4 unless validated.

📐 Partition Count Sizing Framework

Rules of thumb (avoid primes, prefer 6/12/24/60, stay under 4,000 partitions per broker) are a starting point. Use this framework for production sizing:

  1. Target consumer throughput: Measure single-consumer rate (e.g., 5–10 MB/s per partition[reference:16]). Total desired throughput ÷ consumer rate = minimum partitions.
  2. Target producer throughput: Ensure broker count × per-broker write capacity ≥ desired write throughput.
  3. Replication overhead: Partition count × RF = total replicas. Keep replicas-per-broker under ~4,000[reference:17].
  4. Controller/metadata load: KRaft supports 2M partitions, but per-broker limits still apply.
  5. Growth headroom: Add 30–50%. Partition count cannot be reduced without topic recreation.
  6. Key cardinality: Ensure key space exceeds partition count to avoid hot partitions.

Example: 300 MB/s write traffic, 5 MB/s consumer rate, RF=3. Minimum partitions = 60 for consumer parallelism. Total replicas = 180. Across 9 brokers = ~20 replicas/broker — comfortable. Add 50% headroom → 90 partitions.

📉 Consumer Lag: Causes & Remedies

  • Slow consumer processing: Processing rate < producer rate → lag grows.
  • Uneven partition assignment: Hot partitions overload some consumers.
  • Network congestion / broker overload: Fetch latency increases.
  • Blocking operations in poll loop: Heartbeat failures trigger rebalances.
  • Rebalance pauses (classic protocol): Migrate to KIP-848 (group.protocol=consumer) for up to 20× faster rebalances.
  • Cascading rebalance storms: When LLM API latency exceeds max.poll.interval.ms, repeated rebalances occur (see AI section).

🔧 Consumer Lag Troubleshooting

  1. Check lag metrics: Use kafka-consumer-groups.sh or dashboards.
  2. Inspect consumer code: Remove blocking operations; use async/parallel processing.
  3. Review partition assignment: Ensure even distribution; use round-robin or sticky assignor.
  4. Optimize batch sizes: Tune fetch.min.bytes, fetch.max.wait.ms, max.poll.records.
  5. Check network/broker load: Rule out bottlenecks.
  6. Enable parallel processing: Process independent messages in parallel threads.
  7. Offset commit strategy: Commit after successful processing; use async commits carefully.

🔁 Duplicate Messages: Causes & Remedies

Consumer Side

  • Offsets not committed properly: Messages re-read after crash/restart.
  • Rebalance before offset commit: Another consumer reprocesses messages.

Producer Side

  • Retries without idempotence: Same message written multiple times.
  • Remedy: enable.idempotence=true or use Kafka transactions.

🧪 Duplicate Message Example Scenario

Setup: Topic orders, 1 partition, consumer group order-processors. Producer sends Order1, Order2, Order3.

  1. Consumer reads Order1 and Order2.
  2. Consumer crashes before committing the offset for Order2.
  3. On restart, Kafka resends from the last committed offset (Order1).
  4. Consumer reads Order2 again → duplicate processing.

Fix: Commit offsets after successful processing; implement idempotent processing logic.

📌 Offset Committing Explained

Automatic vs Manual

  • Automatic (enable.auto.commit=true): Commits at intervals regardless of processing completion. Risk: duplicates or message loss on crash.
  • Manual (enable.auto.commit=false): Commit only after successful processing. Use commitSync() for reliability, commitAsync() for throughput.

Best Practices

  • Commit offsets after successful processing.
  • Handle rebalances with ConsumerRebalanceListener.
  • Implement idempotent processing to safely handle duplicates.
  • Offsets stored in __consumer_offsets topic.

💽 Broker Disk Full: Consequences & Remedies

Stops Accepting Writes

Broker rejects new messages to avoid corrupting log segments. Producers see DiskError or NotEnoughReplicasException.

Partitions Unavailable

If the leader runs out of space, the partition becomes temporarily unavailable for writes.

Replication Fails

Followers cannot replicate; ISR drops; acks=all writes fail.

Remedies: Increase disk capacity, delete old segments, configure retention policies, reassign partitions with kafka-reassign-partitions.sh, and monitor disk usage proactively.

📊 Uneven Partition Traffic

Causes

  • Constant key: All messages use the same key → same partition.
  • Custom partitioner bug: Always returns the same partition.
  • Small partition count: Even round-robin can skew temporarily.

Fixes

  • Use key=null for round-robin if ordering is not needed.
  • Use varied/dynamic keys.
  • Increase partition count.
  • Monitor per-partition bytes-in metrics.

🗂️ Partition Assignment

Producer Side

  • Key-based: hash(key) % numPartitions — order preserved per key.
  • Round-robin: key=null — even distribution.
  • Custom partitioner: Implement logic; ensure even distribution.

Consumer Side

  • Range assignor: Contiguous partitions per consumer.
  • Round-robin assignor: Even distribution.
  • Sticky assignor: Minimizes movement during rebalances.
  • Rebalance: Partitions reassigned when consumers join/leave.

🔢 Message Ordering Guarantee

  • Partition-level ordering: Messages are appended in order within a partition.
  • Key-based ordering: Same key → same partition → order preserved per key.
  • Factors breaking order: Producer retries without idempotence, multiple partitions, consumer concurrency.
  • Best practices: Use keys, enable enable.idempotence=true, design around partition-level ordering.

🔑 Ensuring Ordering per Key

  • Key-based partitioning: All messages with the same key go to the same partition.
  • Single consumer per partition: Each partition is consumed by only one consumer at a time.
  • Partition count planning: Balance throughput and ordering requirements.
  • Avoid unnecessary rebalances: Minimize consumer joins/leaves during critical processing.
  • Idempotent processing: Handle duplicates safely if exactly-once is needed alongside ordering.

⚖️ Broker Load Balancing & Redistribution

Strategies

  • Increase partition count: Allows traffic to spread more evenly.
  • Rebalance partitions: Use kafka-reassign-partitions.sh to move hot partitions.
  • Review key distribution: Avoid skewed keys causing hot partitions.
  • Add brokers: Expand the cluster; trigger rebalance.
  • Monitor and automate: Use Cruise Control for dynamic rebalancing.

Problems

  • Replication delays; high memory usage; increased latency; OutOfMemoryError risk.

🔁 Replication Factor & Broker Failures

A replication factor of 1 means each partition has only one replica. If the broker crashes, data loss and unavailability occur. Redesign strategies:

  • Increase RF to ≥ 2 (recommended 3).
  • Use min.insync.replicas ≥ 2 with acks=all.
  • Distribute replicas across brokers.
  • Monitor ISR and automate failover.

🔄 Consumer Recovery After Microservice Downtime

  • Same group.id: Kafka tracks offsets per group; resumes from last committed offset.
  • Manual commits: enable.auto.commit=false — commit after processing.
  • Retention: log.retention.hours must exceed expected downtime; otherwise data is lost.
  • Offset storage: __consumer_offsets persists offsets.

📡 NetworkProcessorAvgIdlePercent Low

Measures how much time broker network threads are idle. Low value (e.g., < 20%) indicates network I/O bound.

Causes: High client traffic, insufficient num.network.threads, large requests/responses, slow disk/CPU, network bottlenecks.

Fixes: Increase network threads, tune producer configs, add brokers/rebalance partitions, upgrade hardware/network, investigate disk/CPU bottlenecks.

⏭️ Skipping Messages or Out-of-Order After Rebalance

During rebalances, consumers may lose partition ownership. If offsets are committed incorrectly, messages can be skipped or reprocessed out of order.

Causes: Auto-commit too early, long rebalance duration, multiple consumers per partition, manual offset mismanagement.

Fixes: Disable auto-commit, reduce max.poll.records, tune session/heartbeat timeouts, implement idempotent processing, use partition-aware logic.

♾️ Producer Retrying Indefinitely

Infinite retries cause backlog growth, memory pressure, and duplicate risk.

Causes: Broker unavailable, replication issues, misconfigured retries/delivery.timeout.ms, slow brokers, no idempotence.

Fixes: Set retries to 5–10, set delivery.timeout.ms, enable enable.idempotence=true, adjust backoff, ensure sufficient ISR.

🤖 Kafka for AI / GenAI (2025–2026)

Kafka is the real-time data backbone for enterprise AI. It connects operational data with RAG pipelines, vector databases, and LLM-powered assistants. Beyond being an "event backbone," there are specific production inference patterns every architect should know[reference:18].

1. External RPC

Consumer calls OpenAI, Anthropic, or Bedrock APIs via async I/O + backoff. Simplest pattern; latency risk.

2. Embedded Model

Run ONNX or TensorFlow Lite inside the consumer JVM. Low latency, no network hop.

3. Sidecar Inference

GPU serving (Triton, vLLM) runs next to the Kafka processor in the same pod/host.

🚨 Cascading Rebalance Storm (Production Risk)

LLM API latency often exceeds 30 seconds. If a consumer blocks on an LLM call longer than max.poll.interval.ms:

  1. Broker evicts the consumer → rebalance begins.
  2. Another consumer picks up the same records → also blocks on the LLM.
  3. Repeat → the entire consumer group enters a rebalance storm.

Mitigations: Async HTTP clients with bounded timeouts, decouple LLM calls from the poll loop via internal queues, set generous max.poll.interval.ms (5–10 min), or use Kafka Streams async processing.

🔐 Modern Security

OAuth 2.0 / OIDC

Integrates with Okta, Azure AD, Keycloak. Kafka 4.1 adds JWT bearer grant type (KIP-1139) for service-to-service auth without client secrets[reference:19].

mTLS

Strong transport-level security with client certificates. Works well if you already have PKI infrastructure.

Zero-Trust Model

Use strong authentication (mTLS, OAuth, SCRAM-SHA-512) — never rely on IP allowlists alone. Enforce ACLs at the topic level; separate principals for producers and consumers.
