Why Pods Are The Smallest Deployable Unit

Pod

Atomic Unit

A Pod represents a single instance of a running process in your cluster and serves as the atomic unit of deployment because it encapsulates one or more tightly coupled application containers that share the same execution context, including storage, networking, and namespace isolation.

Kubernetes cannot deploy individual containers directly because Pods provide the essential shared environment where co-located containers can communicate through localhost, share volumes, and coordinate their lifecycle management through a single IP address and namespace.

The Pod abstraction enables Kubernetes to schedule, scale, and manage containers as a cohesive unit, ensuring that applications consisting of multiple interdependent containers are always deployed together and can maintain their required communication patterns and resource sharing.

Shared Networking

Containers in a Pod share the same network namespace and IP address

Shared Storage

Volumes are shared between all containers within the same Pod

Lifecycle Coordination

Containers start and stop together as a single deployable unit

YAML Manifest Files in Kubernetes

What is a YAML Manifest File?

A YAML manifest file is a declarative configuration file that describes the desired state of Kubernetes resources using YAML syntax, serving as the primary method for defining, deploying, and managing applications and infrastructure within a Kubernetes cluster through human-readable text documents.

How Kubernetes Uses Manifests

Kubernetes uses these manifest files as blueprints to create and maintain the desired state of resources, where the control plane continuously monitors actual cluster state and reconciles it with the specifications defined in your YAML files to ensure your applications run exactly as declared.

  • Human-readable and machine-parsable format

Kube-Scheduler: The Cluster's Matchmaker

Primary Function

The kube-scheduler is responsible for assigning newly created Pods to optimal worker nodes in the cluster by evaluating resource requirements, constraints, and policies to determine the best possible node for each Pod's execution environment.

Selection Process

It continuously watches the API server for unscheduled Pods, filters available nodes based on feasibility constraints, scores the remaining suitable nodes, and finally binds the Pod to the highest-scoring node through the API server.

Kubelet - The Node Agent

Worker Node

Compute Machine

The kubelet acts as the primary node agent that runs on each worker node and serves as the crucial bridge between the Kubernetes control plane and the container runtime, continuously ensuring that containers are running in a Pod as specified by the cluster's desired state.

It constantly monitors the API server for new or updated Pod specifications and takes immediate action to create, modify, or terminate containers using the container runtime, while also performing regular health checks and reporting back the node and Pod status to the control plane.

The kubelet manages the complete Pod lifecycle including mounting volumes, executing container probes, enforcing resource limits, and collecting metrics, making it responsible for maintaining the node's operational readiness and ensuring workload compliance with the cluster's declared configuration.

Kube-Proxy: Kubernetes Networking

Worker Node

kube-proxy
iptables

Kube-proxy is a network proxy that runs on each node in your Kubernetes cluster, maintaining network rules on the node to allow network communication to your Pods from inside or outside of your cluster using various proxy modes like iptables, IPVS, or userspace.

It watches the Kubernetes API server for changes to Services and Endpoints, and automatically updates the node's networking rules to route traffic to the appropriate backend Pods, implementing the virtual IP abstraction and load balancing across Pod endpoints.

By maintaining these network rules, kube-proxy enables Service discovery and implements the ClusterIP, NodePort, and LoadBalancer Service types, ensuring that traffic destined for a Service is properly load-balanced across all healthy Pods that match the Service's selector.

Proxy Modes

iptables Mode

Uses Linux iptables to redirect traffic to backend Pods with efficient load balancing and better performance than userspace mode

IPVS Mode

Uses Linux IP Virtual Server for better performance with large numbers of Services, supporting multiple load balancing algorithms

Userspace Mode

Legacy mode where kube-proxy directly handles traffic in userspace, less efficient but more compatible with older systems

Service Monitoring

Watches Kubernetes API for Service and Endpoint changes to keep networking rules updated

Load Balancing

Distributes network traffic across multiple Pod endpoints using various load balancing algorithms

What is a Service and Why is it Needed?
Service
Pods

A Service in Kubernetes is a stable networking abstraction that provides a consistent endpoint and load balancing for a dynamic set of Pods, acting as an immutable gateway that decouples frontend clients from backend Pod instances that may be constantly changing, failing, or scaling.

Services are critically needed because Pods are ephemeral and disposable resources that can be rescheduled, scaled, or replaced at any time, each receiving new IP addresses, which would break communication if clients had to track individual Pod IP addresses directly.

By providing a stable virtual IP address, DNS name, and port combination that persists regardless of Pod lifecycle changes, Services enable reliable service discovery and load distribution while maintaining continuous connectivity for applications in a highly dynamic container environment.

Why We Need Services When We Have Pods

The Pod Problem

Pods are ephemeral and dynamic - they can be created, destroyed, and rescheduled frequently by Kubernetes. When a Pod dies and gets recreated, it receives a completely new IP address, making direct Pod-to-Pod communication unreliable and unpredictable for applications.

Dynamic Environment Challenges

In a Kubernetes cluster, Pods are constantly changing due to scaling, failures, or deployments. Without Services, applications would need to continuously discover and track Pod IP addresses, creating complex and fragile networking dependencies.

Service Solution

Services provide a stable, persistent endpoint and DNS name that abstracts away the dynamic nature of Pods. They act as a load balancer that automatically routes traffic to healthy Pods using label selectors, regardless of how many Pods exist or where they're running.

Consistent Access Point

Services maintain a stable virtual IP and DNS name that never changes, allowing other applications to reliably connect to your application without needing to know about the underlying Pod instances or their constantly changing IP addresses.

ClusterIP vs NodePort

ClusterIP

ClusterIP is the default Kubernetes service type that exposes the service on a cluster-internal IP address, making it only accessible from within the cluster.

This service type creates a stable virtual IP inside the cluster that other pods can use to communicate with your application, providing internal load balancing across the pods.

ClusterIP services are ideal for internal microservices communication where you don't need external access, offering better security by keeping the service isolated from outside traffic.

Internal Only Default Type Secure

NodePort

NodePort exposes the service on each node's IP address at a static port, making it accessible from outside the cluster using any node's IP address and the assigned port.

This service type opens the same port on every node in the cluster and routes traffic from that port to the service, which then distributes it to the pods.

NodePort is useful for development, testing, or when you need direct external access to your service without a load balancer, though it exposes your application more broadly.

External Access Static Port Development

Ingress vs LoadBalancer Service

Ingress

An Ingress is an API object that manages external access to services in a cluster, typically HTTP/HTTPS, providing layer 7 routing capabilities with host-based and path-based routing rules.

It acts as a smart router and reverse proxy that can handle SSL termination, load balancing, name-based virtual hosting, and path-based routing to direct traffic to different services based on the request characteristics.

Ingress requires an Ingress Controller to function, which is a pod that watches the API server for Ingress resources and configures the underlying load balancer or proxy accordingly.

Layer 7 Routing SSL Termination Host-based Routing Path-based Routing

LoadBalancer Service

A LoadBalancer Service is a type of Kubernetes service that automatically provisions an external cloud load balancer to expose the service to the internet, operating at layer 4 of the OSI model.

It provides basic TCP/UDP load balancing and distributes incoming traffic across all healthy pods behind the service, with each service typically getting its own external IP address and cloud load balancer instance.

This service type is cloud-provider specific and can be expensive since each service creates a separate load balancer resource in your cloud provider's infrastructure with associated costs.

Layer 4 Load Balancing Cloud Provider Integration External IP TCP/UDP Protocols

Key Differences

OSI Layer

Ingress operates at Layer 7 (Application), while LoadBalancer operates at Layer 4 (Transport)

Cost Efficiency

One Ingress can handle multiple services, while each LoadBalancer service creates separate cloud resources

Routing Capabilities

Ingress supports host/path-based routing, while LoadBalancer does basic round-robin load balancing

Configuration

Ingress requires a controller, LoadBalancer works out-of-the-box with cloud providers

What is a Deployment?

A Deployment is a Kubernetes controller that provides declarative updates for Pods and ReplicaSets, allowing you to describe an application's life cycle including which images to use, the number of pods to run, and how to handle updates and rollbacks.

It manages the creation, scaling, and deletion of Pods through ReplicaSets while ensuring your application maintains the desired state you specify, automatically handling pod failures and distributing traffic across healthy instances.

Deployments enable powerful rollout strategies like rolling updates, blue-green deployments, and canary releases while maintaining application availability throughout the update process and providing instant rollback capabilities if issues are detected.

Rolling Updates

Gradually replace old pods with new ones without downtime

Rollback

Instantly revert to previous version if issues occur

Scaling

Easily scale the number of pod replicas up or down

Self-Healing

Automatically replaces failed or terminated pods

Why Use Deployments Instead of Direct Pods?

Self-Healing Capability

Deployments automatically monitor and maintain the desired state of your application by automatically replacing failed or terminated Pods without manual intervention, ensuring high availability and reliability.

Rolling Updates & Rollbacks

Deployments enable seamless application updates by gradually replacing old Pods with new ones while maintaining service availability, and provide instant rollback capabilities to previous stable versions if issues arise.

Easy Scaling

With simple commands or configuration changes, Deployments allow you to scale your application up or down by adjusting replica counts, automatically managing the creation or termination of Pods to match demand.

Key Takeaway

While you can create Pods directly for testing or debugging purposes, Deployments provide the production-grade orchestration layer that manages Pod lifecycle, ensures application reliability, and enables seamless operations including updates, scaling, and self-healing capabilities that are essential for running applications in production environments.

What Happens When a Pod Gets Deleted?
1

Termination Request

User sends delete command via kubectl or API, marking Pod for deletion with deletionTimestamp

2

PreStop Hook Execution

If defined, PreStop hooks run to gracefully shutdown applications before termination

3

SIGTERM Signal

SIGTERM signal sent to main process, giving containers time to shutdown gracefully (default 30s)

4

Force Termination

After grace period, SIGKILL forces immediate termination of any remaining processes

When a Pod deletion is initiated, Kubernetes immediately marks the Pod with a deletion timestamp and begins a graceful termination process that allows running applications to complete their work and cleanup resources properly before being forcibly removed from the cluster.

The kubelet on the node receives the termination signal and executes any defined PreStop hooks, then sends SIGTERM to the main process in each container, providing a configurable grace period (default 30 seconds) for applications to handle shutdown procedures before escalating to forceful termination with SIGKILL.

Throughout this process, the Pod's status transitions to "Terminating", endpoints are removed from Services, and once all containers have stopped, the Pod object is completely removed from the API server and etcd, freeing up resources for new workload scheduling.

Critical Dependencies

Services stop routing traffic immediately upon deletion signal, so ensure your applications can handle abrupt connection loss during graceful shutdown period.

Configuration Options

Grace period can be customized with terminationGracePeriodSeconds, and PreStop hooks can perform custom cleanup tasks before termination begins.

What is a Rolling Update?
v1.0 Old Version
v2.0 New Version

A rolling update is a deployment strategy where Kubernetes gradually replaces old versions of your application with new versions while maintaining continuous availability and zero downtime throughout the update process.

During a rolling update, the deployment controller incrementally creates new Pods with the updated version while simultaneously terminating old Pods, ensuring that a specified number of Pods remain available and serving traffic at all times.

How Rolling Updates Work

1

New Pods are created with updated version

2

New Pods become ready and start receiving traffic

3

Old Pods are terminated gradually

4

Process continues until all Pods are updated

Zero Downtime

Application remains available throughout the deployment process

Easy Rollback

Simple to revert to previous version if issues occur

Gradual Deployment

Controlled pace reduces risk and allows for monitoring
