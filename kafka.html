Apache Kafka: The Architecture of the Distributed Commit Log

A comprehensive architectural deep-dive — from the commit log and KRaft to tiered storage, share groups, and exactly-once semantics.

To truly understand Apache Kafka, one must completely abandon the traditional paradigm of message queues (like RabbitMQ or ActiveMQ) and relational databases. Kafka is not a queue; it is a distributed, partitioned, replicated commit log.

This document provides a comprehensive architectural deep-dive into Kafka's core components, strictly focusing on the physical and logical structures that allow it to function as a highly scalable, fault-tolerant, distributed system.

Part 1: The Foundational Paradigm — The Commit Log

Before understanding the cluster, brokers, or topics, one must understand the commit log, as every architectural decision in Kafka flows from it.

A commit log is an append-only, totally ordered sequence of records. When a record is written to a log, it is assigned a sequential ID (an offset) and appended to the end of the log. It is immutable; it cannot be modified or deleted (until a retention policy purges it).

Architecturally, this means:

  • Writes are strictly sequential: This maximizes disk I/O performance, as sequential writes are vastly faster than random writes on both HDDs and SSDs.
  • Reads are strictly sequential: Consumers read from a specific offset forward. Because Kafka doesn't delete records upon read, it doesn't need complex pointer manipulation. The disk acts as a simple, high-throughput buffer.
  • Decoupling of Write and Read: Because the log is persistent, the pace of producers (writers) and consumers (readers) is entirely decoupled.

Kafka scales this single-machine concept into a distributed system across a network of machines.

Part 2: The Cluster Topology

A Kafka Cluster is a group of servers working together to provide the distributed commit log. Architecturally, a cluster is designed to be horizontally scalable and fault-tolerant.

2.1 The Controller (The Brain)

Every cluster must have a single source of truth for metadata and state management. In older Kafka versions, this was handled by ZooKeeper. However, in modern Kafka (version 4.0+), the architecture has transitioned to KRaft (Kafka Raft).

The KRaft Controller Quorum:

  • Architecture: KRaft replaces ZooKeeper by using the Raft consensus algorithm internally. The cluster contains a set of Controller nodes (typically 3 or 5 for high availability) that form a quorum.
  • The Active Controller: At any given time, one controller is elected as the Active Controller (the Leader of the Raft quorum). The others are Standby Controllers (Followers).
  • The Metadata Log: The Active Controller manages the cluster metadata (topics, partitions, replicas, configurations) by writing it to an internal metadata log. Standby controllers continuously replicate this log.
  • Duties: The Active Controller monitors the liveness of all brokers. If a broker fails, the Controller is responsible for electing a new leader for the partitions that were hosted on the failed broker. It also handles topic creation, partition reassignment, and broker registration.

2.2 The Broker (The Muscle)

A Broker is a single Kafka server. A cluster is composed of multiple brokers (often 3, 5, 10, or hundreds).

  • Stateless vs. Stateful: Brokers are stateless regarding consumer consumption but highly stateful regarding data storage. Each broker stores a portion of the data (partition replicas) on its local disk.
  • Request Handling: A broker handles two main types of requests:
    • Produce Requests: Receiving data from producers and appending it to the end of the relevant partition log.
    • Fetch Requests: Serving data to consumers reading from a specific offset, and serving replication requests from follower brokers.
  • Network Threads: Each broker has a network thread pool (num.network.threads) that reads incoming requests and writes responses, and an I/O thread pool (num.io.threads) that handles the actual disk I/O and request processing.
  • Zero-Copy Principle: To achieve extreme throughput, brokers use the OS "zero-copy" feature (sendfile). The broker does not copy data from the page cache to application memory and then to the network socket. Instead, the OS sends the data directly from the disk page cache to the network socket, eliminating CPU overhead and memory copies.

Part 3: Logical vs. Physical Data Organization

3.1 Topics (The Logical Abstraction)

A Topic is a named feed to which records are published. It is the logical category of data.

  • Multi-Subscriber: Unlike traditional queues that delete a message once it is read, a topic is a multi-subscriber model. It is an append-only log that multiple consumers can read from independently without affecting each other.
  • Topic Configuration: Topics carry configurations that govern the physical data, such as retention time (e.g., 7 days), retention size (e.g., 100GB), and cleanup policies.

3.2 Partitions (The Physical Unit)

A topic is subdivided into Partitions. A partition is the actual physical unit of storage on a broker's disk.

  • Ordering: Kafka guarantees strict ordering only within a single partition, not across the entire topic.
  • Parallelism: Partitions are the unit of parallelism. If a topic has 10 partitions, it can be processed by up to 10 consumers concurrently (in the same consumer group).
  • Distribution: Partitions are distributed across the brokers in the cluster. A single broker can host multiple partitions from different topics.
  • Disk Layout: On the broker's disk, a partition is a directory containing a set of Segment Files. Kafka does not store the entire log in one massive file. It rolls the log into segments (e.g., 1GB each). Active segments are written to, while older segments are immutable and subject to retention policies.

3.3 Replication Architecture

To ensure fault tolerance, every partition is replicated across multiple brokers.

  • Partition Leader: For any given partition, one broker is designated as the Leader. All producer writes and consumer reads (by default) must go through the Leader to ensure consistency.
  • Partition Followers: The other brokers hosting replicas act as Followers. They continuously send Fetch requests to the Leader to pull the latest records and replicate them to their local disks. Followers do not serve client requests (unless using specific configurations like Consumer Rack Awareness with Local Quorum).
  • In-Sync Replicas (ISR): A Follower is considered "in-sync" if it has fetched all the records up to the Leader's High Watermark (HW) within a specified time frame (replica.lag.time.max.ms). The ISR list is maintained by the Controller.
  • Leader Epochs: To prevent data divergence during leader elections (e.g., a network partition splits the cluster), Kafka uses Leader Epochs. An Epoch is a monotonically increasing number. When a new leader is elected, a new epoch is created. This allows followers to know exactly how much data to truncate if they were out of sync with the old leader.

3.4 Offsets (The Position)

An Offset is a 64-bit integer that uniquely identifies the position of a record within a partition.

  • Immutability: Offsets are strictly monotonically increasing. Once a record is appended, its offset is permanent.
  • Log End Offset (LEO): The offset of the next record that will be written to the partition. If 5 records are written (offsets 0-4), the LEO is 5.
  • High Watermark (HW): The offset up to which data has been successfully replicated to all ISR (In-Sync Replicas). Consumers can only read data up to the High Watermark. This ensures that consumers never read data that might be lost if a leader election occurs.
  • Consumer Offset: The offset maintained by the consumer (or consumer group) dictating where it is currently reading.

Part 4: The Producer Architecture

Producers are client applications that publish records to topics. Architecturally, the producer is highly optimized for throughput and control.

The Record Accumulator: The producer does not send records one by one. It buffers records in memory (the Record Accumulator).

Batching: Records are grouped into batches (per partition) before being sent to the broker. This reduces network overhead.

Partitioner: The producer's partitioner determines which partition a record goes to.

  • Key-Based: If a key is provided, the producer uses a hash of the key modulo the number of partitions to determine the target partition. This guarantees that all records with the same key go to the exact same partition (and thus, maintain strict ordering).
  • Round-Robin/Sticky: If no key is provided, Kafka uses a sticky partitioner (in newer versions) to send batches to one partition until the batch is full or latency thresholds are met, then switches to another partition.

Sender Thread: A background I/O thread pulls batches from the Accumulator and sends them to the appropriate broker (the leader of the target partition).

Acknowledgments (acks):

  • acks=0: Fire and forget.
  • acks=1: The Leader writes to its local log and acknowledges.
  • acks=all (or -1): The Leader waits for the record to be replicated to all ISR before acknowledging. This ensures no data loss.

Part 5: The Consumer Architecture

Consumers are client applications that subscribe to topics.

Pull Model: Consumers pull data from brokers by sending Fetch requests with their current offset. This prevents the broker from being overwhelmed by pushing data to slow consumers.

Consumer Groups: The fundamental scaling mechanism for consumers. Multiple consumers can be grouped together by assigning them the same group.id.

  • The Rule: Each partition of a topic is assigned to exactly one consumer within a consumer group. This prevents duplicate processing.
  • Parallelism: If a topic has 10 partitions, a consumer group can have a maximum of 10 active consumers. If an 11th consumer joins, it will sit idle.

The Group Coordinator: A specific broker in the cluster is designated as the Group Coordinator for a consumer group.

  • It manages group membership, heartbeats, and triggers rebalances.
  • It manages the offset commit log (historically stored in the __consumer_offsets topic).

The Rebalance Protocol: When a consumer joins or leaves a group, or when partitions are added to a topic, a rebalance occurs. The Group Coordinator orchestrates this. The group leader (one of the consumers) calculates the new partition assignment and sends it to the coordinator, which distributes it to all consumers. During a rebalance, the entire group stops consuming (a "stop-the-world" event), which is why modern architectures use Cooperative Sticky Assignors to minimize downtime.

Offset Committing: Consumers commit their offsets back to Kafka. If a consumer crashes, the new consumer assigned to that partition will start reading from the last committed offset, ensuring at-least-once or exactly-once processing guarantees.

Part 6: End-to-End Data Flow

To synthesize the architecture, trace the life cycle of a single record:

  1. A Producer application creates a record and assigns it a key.
  2. The Producer's internal Partitioner hashes the key to determine the target Partition.
  3. The record is buffered in the Producer's Record Accumulator.
  4. The Producer's Sender thread sends a Produce Request to the Broker that acts as the Leader for that partition.
  5. The Leader Broker appends the record to its local Commit Log segment file, assigning it the next Offset (incrementing the LEO).
  6. The Follower Brokers send Fetch requests to the Leader to replicate the record.
  7. Once the record is written to all ISR Followers, the Leader advances the High Watermark (HW).
  8. A Consumer in a Consumer Group sends a Fetch Request to the Leader Broker, asking for records starting from its current committed offset.
  9. The Broker reads from the page cache and sends the record to the Consumer via the network.
  10. The Consumer processes the record and commits the new offset back to the Broker's __consumer_offsets topic.
  11. The KRaft Controller monitors the whole system, ensuring brokers are alive, updating the ISR lists, and triggering leader elections if the Leader Broker fails.

This architecture—built on immutable append-only logs, partition-based parallelism, replication for fault tolerance, and the KRaft consensus protocol—is what allows Kafka to handle millions of messages per second with extreme reliability.

20 Conceptual & Confusing Architecture Questions

These questions address the "why" and "how" of Kafka's internal design, stripping away surface-level definitions to reveal the mechanics of the distributed commit log.

1. Why is Kafka fundamentally a "Commit Log" and not a traditional "Message Queue"?

The Confusion: People often treat Kafka like RabbitMQ, assuming messages are deleted once consumed. Architectural Explanation: A traditional message queue is a destructive read model. When a consumer reads a message, it is removed from the queue. This tightly couples the consumer's speed to the queue's size. Kafka is an immutable, append-only commit log. Data is written to the end of the log and is never altered. Consumers do not "remove" messages; they simply maintain a pointer (an offset) to their position in the log. Because the data is persistent on disk (governed by retention policies, not consumption), a single log can be read concurrently by dozens of independent consumers at their own pace. This fundamentally decouples producers (writers) from consumers (readers).

2. How does Kafka guarantee message ordering, and what is the architectural limitation?

The Confusion: "Kafka guarantees ordered messages." Architectural Explanation: Kafka guarantees ordering only within a single partition, never across an entire topic. When a producer sends a message, it is appended to a specific partition. Because a partition is a single, sequential log file on a broker's disk, records are strictly ordered. However, if a topic has 10 partitions, messages are distributed across those partitions (often round-robin or based on a key). There is no global clock or sequence across those 10 partitions, meaning consumers reading from all 10 partitions will see messages interleaved out of order. Architectural Limitation: To guarantee global ordering, you must use a single partition, which restricts the topic's scalability and parallelism to one CPU core on one broker.

3. What is the exact architectural difference between a Topic and a Partition?

The Confusion: They are often used interchangeably by beginners. Architectural Explanation: A Topic is a purely logical concept. It is a named category (e.g., "user-clicks") that exists in the cluster's metadata (managed by the KRaft controller). It holds no data itself. A Partition is the physical unit of storage. A topic is subdivided into one or more partitions. A partition is an actual directory on a broker's filesystem containing segment files. Partitions are the unit of parallelism: they allow a topic to be scaled horizontally across multiple brokers in a cluster.

4. What is the High Watermark (HW), and why can't consumers read past it?

The Confusion: If a producer writes a message, why isn't it immediately available to consumers? Architectural Explanation: The High Watermark is an architectural safety mechanism for replication. When a producer writes to a Leader partition, the message gets the next Log End Offset (LEO). However, a consumer cannot read that message until the Leader has successfully replicated it to all In-Sync Replicas (ISR). The HW is the offset up to which all ISR followers have successfully replicated. Consumers can only read up to the HW. If a Leader crashes before a message is replicated to the followers, and a follower becomes the new Leader, that message would be lost. By restricting consumer reads to the HW, Kafka guarantees that consumers will never read data that is vulnerable to being lost during a leader election.

5. What happens during a Leader Election, and why is the KRaft Controller essential?

The Confusion: If a broker fails, how does the cluster keep running without losing data? Architectural Explanation: Every partition has one Leader (handles reads/writes) and several Followers (replicate data). If the broker hosting the Leader goes offline, the cluster must elect a new Leader from the ISR. This is where the KRaft Controller Quorum (the cluster's brain) comes in. The Controller continuously monitors the health of all brokers via heartbeats. When it detects a failure, it immediately looks at the ISR list for the affected partitions and elects a new Leader. It then updates the cluster metadata to reflect the new Leader, and informs the remaining brokers and clients (via metadata updates) so they can redirect their traffic.

6. Why did Kafka transition from ZooKeeper to the KRaft consensus protocol?

The Confusion: ZooKeeper worked for years, so why change the core architecture? Architectural Explanation: ZooKeeper was an external system used for metadata management (tracking brokers, partitions, and configurations). This created a "split-brain" architecture (two separate systems to secure and monitor). KRaft (Kafka Raft) internalizes this. The KRaft Controllers use the Raft consensus algorithm to maintain an internal metadata log. This provides massive architectural benefits: Scalability: ZooKeeper was a bottleneck for clusters with hundreds of thousands of partitions. KRaft can handle millions. Faster Failover: Metadata is already inside Kafka; controllers don't have to negotiate with an external system to elect a new leader. Simplified Architecture: Only one system to deploy, secure, and monitor.

7. What exactly is an In-Sync Replica (ISR), and how does a replica get kicked out?

The Confusion: Replicas are just copies of data, so aren't they always in sync? Architectural Explanation: An ISR is a subset of replicas that are fully caught up to the Leader's High Watermark. A replica is dynamically added to or removed from the ISR based on its performance. A Follower broker continuously sends Fetch requests to the Leader to replicate data. If a Follower falls behind (e.g., due to a slow disk, network congestion, or GC pause) and does not fetch up to the Leader's LEO within the replica.lag.time.max.ms configuration, the Leader removes it from the ISR. It is no longer eligible to become a Leader. Once it catches up again, it is re-added to the ISR.

8. How does Kafka achieve extreme throughput using the OS "Zero-Copy" principle?

The Confusion: Kafka writes to disk, which is usually slow. How is it so fast? Architectural Explanation: In traditional applications, reading a file and sending it over a network involves four context switches (User to Kernel space) and multiple memory copies (Disk -> Kernel Page Cache -> User Space -> Socket Buffer -> Network). Kafka uses the Linux sendfile system call. Because Kafka data is immutable and doesn't need to be modified in application memory, Kafka instructs the OS to send data directly from the Page Cache straight to the Network Socket. This "Zero-Copy" approach eliminates CPU overhead and memory copying, allowing Kafka to saturate network interfaces with minimal CPU usage.

9. Why can't a Consumer Group have more consumers than there are partitions?

The Confusion: If I have 10 consumers and 5 partitions, why are 5 consumers idle? Architectural Explanation: The fundamental rule of consumer groups is that a single partition can only be assigned to exactly one consumer within a group at any given time. This guarantees that messages are processed in order and prevents duplicate processing. If you have a topic with 5 partitions, the maximum parallelism for a consumer group is 5. The Group Coordinator (a broker) will assign one partition to each of the 5 consumers. If you spin up an 11th consumer for a 10-partition topic, it will sit idle, acting as a hot standby. It will only start working if one of the active 10 consumers crashes or leaves the group.

10. What is a Consumer Group Rebalance, and why is it a "Stop-the-World" event?

The Confusion: Rebalances sound like a seamless background process. Architectural Explanation: A rebalance occurs when the membership of a consumer group changes (a consumer joins/leaves/crashes, or partitions are added). During a traditional (Eager) rebalance, the Group Coordinator dictates a "Stop-the-World" protocol: All consumers revoke their partitions and stop consuming. The group leader (one of the consumers) calculates a new assignment, sends it to the Coordinator, which then distributes it to the group. During this window, no messages are processed by that group. (Modern Kafka uses Cooperative Sticky Assignors to perform incremental rebalances, which only stop affected consumers rather than the whole group).

11. What is the __consumer_offsets topic, and why is it critical?

The Confusion: Where are consumer read positions actually stored? Architectural Explanation: To track where consumers are in the log, Kafka cannot rely on the consumer to remember (because if the consumer crashes, that state is lost). Instead, Kafka stores this state internally. __consumer_offsets is an internal, highly replicated Kafka topic (usually 50 partitions). When a consumer commits its offset, it produces a message to this internal topic. The Group Coordinator (a broker) manages this topic. When a consumer group initializes, it consumes from this topic to restore its state. This architectural choice means Kafka uses its own commit log to store its own state.

12. What is the difference between acks=1 and acks=all architecturally?

The Confusion: Both mean the message was received, right? Architectural Explanation: acks=1: The Producer requires an acknowledgment from the Leader Broker only. As soon as the Leader writes to its local disk, it responds. This is fast, but if the Leader crashes before Followers replicate the data, the message is lost. acks=all (or -1): The Leader waits for the message to be written to its local disk and replicated to all In-Sync Replicas (ISR). Only when the High Watermark advances does it respond. This guarantees zero data loss (as long as at least one ISR survives), but increases latency because the producer must wait for the slowest Follower.

13. What is the architectural purpose of the Producer's Record Accumulator and Sticky Partitioner?

The Confusion: Producers just send messages to Kafka, right? Architectural Explanation: To achieve high throughput, Producers do not send one message at a time. The Record Accumulator is an in-memory buffer inside the Producer that groups messages destined for the same partition into "Batches". The Sticky Partitioner solves the "small batch" problem. If a producer sends messages with no key, a round-robin partitioner would send message 1 to partition A, message 2 to B, etc. This prevents batches from filling up. Sticky partitioning sends all messages in a batch to a single partition until the batch is full, then switches to another. This drastically improves batching efficiency and reduces latency.

14. What is a Leader Epoch, and what problem does it solve?

The Confusion: Why do we need epochs if we have offsets? Architectural Explanation: Leader Epochs solve the problem of data divergence during network partitions (split-brain). Imagine a Leader crashes, a Follower becomes the new Leader, but the old Leader comes back online and starts accepting writes. Epochs prevent this. Each time a Leader is elected, a new epoch (a monotonically increasing number) is generated. Followers include their epoch in Fetch requests. If a Follower tries to fetch from a Leader with an older epoch, the Leader rejects it and forces the Follower to truncate its log to the last known committed offset of the current epoch. This ensures absolute consistency.

15. What is the difference between Time-Based Retention and Log Compaction?

The Confusion: Doesn't Kafka just delete old messages? Architectural Explanation: Kafka gives you two distinct data lifecycle policies per topic: Retention (delete): Based on time (e.g., keep 7 days) or size (e.g., keep 100GB). When the threshold is met, entire segments of the log are deleted. This is typical for event streams. Log Compaction: Kafka retains the latest value for every key. If a topic is compacted, Kafka runs a background process that scans the log and removes older records if a newer record with the same key exists. This turns a Kafka topic into a changelog or a "table." It is used for restoring state (e.g., Kafka Streams state stores, or database CDC).

16. How does the "Pull" model work architecturally, and why does Kafka use it over a "Push" model?

The Confusion: Message brokers usually push data to consumers. Architectural Explanation: In a Push model, the broker must track the consumption rate of every consumer and throttle data accordingly. If a consumer is slow, a Push model can overwhelm it. Kafka uses a Pull model. Consumers send a FetchRequest with their current offset. The broker returns a chunk of data. This elegantly solves the slow consumer problem: if a consumer is slow, it simply pulls less often. The broker doesn't care. This makes the broker highly scalable, shifting the burden of flow control entirely to the consumer. Long-polling is used to prevent consumers from aggressively busy-waiting when no new data is available.

17. How are offsets committed, and what is the difference between "At-Least-Once" and "Exactly-Once" processing?

The Confusion: Consumers read data, so once they read it, the offset updates. Architectural Explanation: The offset is not automatically committed when read. The consumer application must explicitly commit the offset back to the __consumer_offsets topic. At-Least-Once: The consumer processes the message, then commits the offset. If the consumer crashes between processing and committing, the message will be read again, causing duplicate processing. Exactly-Once (EOS): Kafka achieves this using Transactions. The producer writes data and commits offsets atomically in a single transaction. If the transaction fails, neither the data nor the offset is written.

18. What happens to data if a broker crashes before replication finishes?

The Confusion: The producer got an ack, so the data is safe. Architectural Explanation: If the producer used acks=1 (Leader only), the Leader writes to disk and acknowledges the producer. The Leader crashes immediately before followers fetch the data. The Controller elects a Follower as the new Leader. The new Leader does not have the data. The data is permanently lost. To prevent this, you must use acks=all AND configure min.insync.replicas (e.g., 2). This forces the Leader to wait until at least 2 replicas (including itself) have the data. If the Leader crashes, the surviving ISR replica will have the data and be promoted.

19. What is the architecture of a Kafka Segment File?

The Confusion: Kafka stores everything in one big file. Architectural Explanation: A partition is not a single file. It is a directory containing multiple Segments. A segment consists of two main files: a .log file (containing the actual messages) and a .index file (an offset-to-position index) and a .timeindex (timestamp-to-offset). When a .log file reaches a certain size (e.g., segment.bytes=1GB), Kafka rolls a new segment. This architectural design is crucial for retention: instead of deleting individual messages (which is impossible in an append-only log), Kafka simply deletes entire old segment files, which is an instant, atomic file system operation.

20. How does the KRaft Controller Quorum maintain consistency without ZooKeeper?

The Confusion: Without ZooKeeper, how do controllers agree on the metadata? Architectural Explanation: The KRaft controllers form a Raft quorum (usually 3 or 5 nodes). One node is elected as the Active Controller. The Active Controller writes metadata changes (like "create topic X") to its local __cluster_metadata log. It then replicates this log to the Standby controllers. A majority (quorum) of controllers must acknowledge the write to the log before the change is committed. Once committed, the metadata is pushed to the brokers. This provides strong consistency and allows the cluster to survive the failure of a minority of controller nodes.

Kafka Storage Internals: How Data Lives on Disk

To the client, Kafka appears as a streaming platform. To the operating system, Kafka is a highly optimized file system application. The true genius of Kafka's performance lies in its storage architecture. By treating data as an append-only log and leveraging the operating system's Page Cache, Kafka achieves throughputs that rival in-memory databases while maintaining the durability of disk storage.

This chapter explores the physical reality of Kafka's storage engine, breaking down partitions into log segments, dissecting retention and compaction policies, and examining the background machinery that keeps the disk footprint manageable.

The Anatomy of a Partition (Log Segments)

A Kafka partition is not a single, monolithic file. If a partition were a single file, it would grow infinitely, making it impossible to delete old data efficiently, impossible to search for specific offsets quickly, and prone to file system corruption. Instead, a partition is a directory on the broker's file system containing a set of Log Segments.

The Segment Lifecycle:

When a topic is created, Kafka creates a directory for each partition. Initially, it opens a single active segment file. All incoming producer records are appended to this active segment. As data is written, the segment grows. When it reaches a configured size limit (log.segment.bytes, defaulting to 1GB) or a time limit (log.roll.hours), Kafka "rolls" the segment. It closes the current file, makes it immutable (read-only), and opens a new active segment file for new incoming data.

This architecture is vital for several reasons:

  • Retention: Kafka can delete entire old segments as whole files, bypassing the need to rewrite or modify active data.
  • Searchability: When a consumer requests offset 8,500,000, Kafka doesn't scan from offset 0. It uses file names and indexes to jump directly to the segment containing that offset.
  • File System Limits: It prevents massive file size degradation and allows for efficient memory mapping.

The Triple-File Structure:

Every single segment in a partition consists of three tightly coupled files:

  • The .log File: This contains the actual record batches. It is a raw, binary append-only file.
  • The .index File (Offset Index): This is a sparse index. It does not map every offset to a file position, as that would consume too much memory. Instead, it maps an offset to a physical byte position in the .log file every 4KB (log.index.interval.bytes).
  • The .timeindex File (Timestamp Index): Introduced in Kafka 0.10, this maps timestamps to offsets. It allows consumers to search for messages based on when they were produced (e.g., "give me all messages from 2:00 PM onwards").

Naming Conventions and Base Offsets:

Segment files are named using a 20-character zero-padded string representing the Base Offset (the offset of the very first message written to that segment). For example, a segment file named 00000000000000012345.log contains messages starting from offset 12345. The subsequent messages in this file will be 12346, 12347, etc., up to the last message before the next segment begins (e.g., offset 99999). This naming convention allows Kafka to perform binary searches across the file names to quickly locate the segment that holds a specific offset.

The Read Path: Memory-Mapped Files (mmap):

How does Kafka read from these files so fast? It uses Memory-Mapped Files (mmap). For the .index and .timeindex files, Kafka maps them directly into the OS page cache. When a consumer requests a specific offset, Kafka doesn't execute a disk read. It looks into the memory-mapped index, finds the physical byte position in the .log file, and then reads from the .log file (which is also heavily cached in OS page cache).

The Write Path: Page Cache and Flushing:

Kafka does not flush data to physical disk immediately upon receiving a write. It writes to the OS Page Cache. The OS handles flushing to disk asynchronously. Kafka relies on Replication (ISR) for durability, not on disk flushing. You can force flushing via log.flush.interval.messages and log.flush.interval.ms, but this is generally discouraged as it destroys performance without adding real safety (replication is safer).

Retention Policies (Deleting the Old)

Because Kafka is an append-only log, the disk will eventually fill up. Kafka manages this using Retention Policies. By default, a topic's cleanup policy is delete.

Time-Based Retention (retention.ms):

This is the most common policy. By default, Kafka retains data for 7 days (retention.ms=604800000). A background thread called the Log Manager runs periodically (every log.retention.check.interval.ms, default 5 minutes). It scans the segment files in each partition. If the last modified time of the highest offset in a closed (passive) segment is older than the retention threshold, the segment is marked for deletion.

Size-Based Retention (retention.bytes):

This policy limits the maximum size of a partition (not a topic, but per partition). If retention.bytes=-1 (default), there is no size limit. If set to, for example, 10GB, the Log Manager calculates the total size of all segments in the partition. If it exceeds 10GB, it deletes the oldest segments from the beginning of the log until the size falls below the threshold.

The Golden Rule: Active Segments are Sacred:

A crucial architectural rule: Kafka never deletes the active segment. Even if the active segment has reached the retention.ms limit, it cannot be deleted because producers are actively appending to it. Retention and deletion only apply to closed, passive segments. Data in the active segment is effectively retained until it is rolled into a passive segment.

The Deletion Mechanism:

When a segment is marked for deletion, Kafka does not simply call rm -rf. It renames the file to include a .deleted suffix (e.g., 00000000000000012345.log.deleted). It waits for a configurable delay (file.delete.delay.ms, default 60 seconds) to allow any in-flight read requests to finish. After the delay, the OS file system unlink operation removes the file blocks, freeing up disk space instantly.

Consumer Impact: OffsetOutOfRangeException:

What happens if a consumer is lagging, and the segment containing its current offset is deleted due to retention? When the consumer tries to fetch the next offset, the broker checks its indexes and finds that the requested offset is older than the smallest offset in the partition. The broker throws an OffsetOutOfRangeException. The consumer must then use auto.offset.reset (earliest or latest) to jump to a valid position in the log.

Log Compaction (The Changelog Model)

Retention by deletion is perfect for event streams. But what if you are using Kafka as a State Store? Imagine a stream of updates to user profiles. User1 -> {name: "Alice"}, User2 -> {name: "Bob"}, User1 -> {name: "Alice Smith"} (a correction). If you use standard retention, you will eventually delete the historical data. If a new consumer reads from the beginning, it will process both the old and new value for User1. If you are restoring a microservice's database from this topic, you don't want the old value. Enter Log Compaction.

The Architecture of Compaction:

When you set cleanup.policy=compact, Kafka retains at least the last known value for each message key within a partition. It does not guarantee that there is only one value per key. It guarantees that the latest value is never deleted. The goal is to ensure the log is a "snapshot" of the final state, plus a tail of recent history.

Tombstones (Null Values):

How do you delete a key in a compacted topic? You produce a message with the key and a null value. This is called a Tombstone. Tombstones are special. They are retained for a specific period (delete.retention.ms, default 24 hours) to ensure all consumers can see the deletion, and then they are purged.

The "Head" and "Tail" of a Compacted Log:

  • The Head (Active Segment): Clean, uncompacted. New messages are written here.
  • The Tail (Dirty Segments): Segments that may contain duplicate keys.

Use Cases:

  • Kafka Streams: Internal state stores (RocksDB) are backed by compacted topics. If a Streams application crashes, it rebuilds its state by replaying the compacted topic.
  • Change Data Capture (CDC): Capturing every change to a database table. Compaction ensures the topic doesn't grow infinitely while retaining the latest database row state.

The Log Cleaner (The Engine Room)

Who does the actual work of compaction? The Log Cleaner. This is a pool of background threads (log.cleaner.threads) running on the broker.

The Cleanable Ratio:

The Log Cleaner does not run continuously on every segment. It calculates the Dirty Ratio of a partition. Dirty Ratio = (Size of Dirty Segments) / (Total Size of Partition). A segment is considered "dirty" if it hasn't been compacted yet. The cleaner only triggers on a partition when the Dirty Ratio exceeds min.cleanable.dirty.ratio (default 0.5). This prevents the cleaner from working too hard and stealing CPU/I/O from the broker.

The Copy-and-Swap Algorithm:

The Log Cleaner does not modify files in place. It performs a highly efficient Copy-and-Swap operation: Identify the dirtiest segments to clean. Build a Map of the latest offset for every unique key. Copy: It creates new, temporary segment files. It iterates through the old segments. If a message is the latest occurrence of its key, it copies it to the new segment. If it's an older occurrence, it drops it. Swap: Once the new segment is built and flushed to disk, Kafka seamlessly swaps the file pointers. Readers currently reading the old segment continue to read it (the OS keeps the file handle open until the reader finishes), while new readers are directed to the clean segment. Delete: The old, dirty segment is deleted.

The Cost of Compaction:

Compaction is I/O intensive. The cleaner must read the entire dirty segment and write out a new one. It uses a significant amount of RAM (log.cleaner.dedupe.buffer.size). If a topic has a massive key cardinality (millions of unique keys), the deduplication map can exhaust broker memory.

Transactional Markers:

When using Kafka Transactions (Exactly-Once Semantics), the log cleaner must be aware of transactional markers. It will not clean a segment if there are open, uncommitted transactions in it. It ensures that aborted transactions are completely removed during the compaction process.

Advanced Storage Mechanics & Tuning

  • log.segment.bytes: Default 1GB. Smaller segments = faster deletion/compaction, but more files to manage (more open file handles). Larger segments = less overhead, but slower retention/compaction cycles.
  • log.roll.ms: Forces a segment roll based on time, even if size isn't reached. Crucial for topics with low throughput, ensuring retention policies don't get stuck on a never-ending active segment.
  • log.preallocate: If true, Kafka preallocates the full 1GB file on disk when a segment is created. This reduces file fragmentation on the OS, but uses disk space immediately.
  • JBOD over RAID: Kafka is designed to run on JBOD (Just a Bunch Of Disks) rather than hardware RAID. Kafka's replication provides the redundancy, so RAID 5/10 is unnecessary and can actually hurt performance. Kafka can be configured with log.dirs pointing to multiple disks. It distributes partitions evenly across the disks. If one disk fails, Kafka marks the partitions on that disk as offline and relies on other brokers' replicas.
  • File System Choices: XFS is the recommended file system for Kafka. It handles concurrent I/O well and doesn't suffer from the extreme latency spikes seen in ext4 during large file deletions. ZFS is extremely feature-rich but high memory overhead. Often discouraged for Kafka unless carefully tuned.
  • The __consumer_offsets Topic Architecture: This internal topic is a perfect example of Kafka's self-hosting architecture. It is a topic with cleanup.policy=compact. Keys are (group_id, topic, partition). Values are the committed offsets. When a consumer commits, it writes to this compacted topic. When a consumer starts up, it reads this topic from the beginning (or from the latest snapshot) to reconstruct its state. The Log Cleaner ensures this topic doesn't grow infinitely.
  • Handling Disk Full: If a broker's disk fills up, Kafka enters a critical state. The broker will refuse writes (and possibly reads) to protect itself. To prevent this, Kafka brokers use quotas (replica.quota). If a follower replica is lagging, it might consume too much network bandwidth, starving producers. Quotas ensure fair resource allocation.

20 Conceptual & Confusing Storage Internals Questions

These questions target the exact mechanics of Log Segments, Retention, Compaction, and the Log Cleaner.

1. Why does Kafka split a partition into multiple segment files instead of using one massive file?

If a partition were a single file, two major architectural problems would occur. First, deletion would be impossible. You cannot easily delete the oldest messages at the top of a single file without rewriting the entire terabyte-sized file. By splitting the log into segments, Kafka can delete entire old files instantly. Second, searching would be inefficient. With segments, Kafka can use the segment's base offset (in the filename) and sparse indexes to binary search for a specific offset, rather than scanning a massive file from the beginning.

2. How does Kafka delete a specific, individual message from a standard topic?

In a standard topic (with cleanup.policy=delete), you cannot delete an individual message. Kafka operates on an immutable, append-only log. Data is only deleted at the segment level. When a segment reaches its size limit (log.segment.bytes) or time limit, it is rolled into a passive, read-only file. Only when an entire segment violates the retention policy (retention.ms or retention.bytes) is the whole file deleted from the disk.

3. Can the active segment of a partition be deleted by a retention policy?

No. Kafka never deletes the currently active segment, because producers are actively appending to it. Retention rules only apply to closed, passive segments. If your topic receives very little traffic, an active segment might remain open for days. To prevent data from living on disk indefinitely, you must configure log.roll.ms or log.roll.hours to force Kafka to roll a new segment based on time, even if it hasn't reached its size limit, so the old segment can be made eligible for deletion.

4. What exactly is the difference between retention.bytes and log.segment.bytes?

They operate on completely different scales. log.segment.bytes (default 1GB) dictates the maximum size of a single file (segment) on the disk. When a segment hits this size, it rolls. retention.bytes, on the other hand, dictates the maximum total size of the entire partition (all segments combined). If a partition's total size exceeds retention.bytes, Kafka will start deleting the oldest passive segments until the total size falls below the threshold.

5. If Log Compaction retains the latest value for a key, does it guarantee exactly one message per key exists in the topic?

No. Log compaction guarantees that Kafka will retain at least the last known value for each key. It does not guarantee that older values are deleted immediately. Compaction is a background process (the Log Cleaner) that runs asynchronously. Until the Log Cleaner processes a segment, the log may contain multiple historical values for the same key. The goal of compaction is eventual consistency, not immediate deduplication.

6. How do you actually delete a key entirely from a compacted topic?

You produce a Tombstone. A Tombstone is a message with the specific key you want to delete and a null value. When the Log Cleaner encounters a Tombstone, it knows to eventually remove all previous values for that key. However, the Tombstone itself is not deleted immediately; it is retained for delete.retention.ms (default 24 hours) to ensure that all consumers have time to see the deletion before the marker itself is purged.

7. Why is the .index file described as "sparse"?

If Kafka mapped every single offset to a byte position, the index file would be almost as large as the data file itself, consuming massive amounts of memory (since the index is memory-mapped). Instead, Kafka uses a sparse index. It only maps an offset to a physical position every 4KB (log.index.interval.bytes). When a consumer asks for offset 1005, Kafka binary searches the sparse index to find the closest mapped offset (e.g., 1000), jumps to that byte position in the .log file, and then linearly scans the remaining 5 messages. This balances memory efficiency with fast lookups.

8. What happens to an active consumer if the segment it is reading from gets deleted by retention?

If a consumer is lagging so far behind that the segment containing its current offset is deleted, the consumer's next fetch request will fail. The broker will throw an OffsetOutOfRangeException. The consumer is now in an invalid state and must reset its position based on the auto.offset.reset configuration, either jumping to the earliest available message (earliest) or the newest message (latest).

9. Does Kafka fsync every message to physical disk before acknowledging the producer?

No. By default, Kafka writes to the OS Page Cache (RAM) and relies on the operating system to flush the data to disk asynchronously. Relying on fsync for every message would destroy Kafka's throughput. Kafka achieves durability through replication (ISR), not through immediate disk flushing. As long as the data is in the page cache of multiple brokers, it is considered safe from broker failure (though not safe from a simultaneous power outage across the whole data center).

10. What is the "Dirty Ratio" and why does the Log Cleaner care about it?

If the Log Cleaner constantly ran, it would consume massive CPU and I/O, stealing resources from the brokers handling client traffic. The Dirty Ratio is the percentage of the partition's data that consists of "dirty" (uncompacted) segments. The Log Cleaner only kicks in when this ratio exceeds min.cleanable.dirty.ratio (default 0.5, or 50%). This ensures the cleaner only works when there is enough garbage to justify the performance cost of rewriting segments.

11. How does the Log Cleaner modify segments? Does it rewrite the file in place?

The Log Cleaner never modifies a file in place. It uses a Copy-and-Swap algorithm. It reads the dirty segments, filters out the superseded keys, and writes the surviving messages to a brand new, clean segment file. Once the new file is completely written and flushed, Kafka atomically swaps the file pointers in the partition directory. The old, dirty file is then deleted. This allows readers to continue reading from the old file without interruption until they finish.

12. Why does Kafka recommend JBOD (Just a Bunch Of Disks) instead of RAID for storage?

Kafka already provides redundancy through partition replication across different brokers. Using RAID 5 or RAID 10 is an unnecessary expense and can actually hurt performance due to the RAID controller's write penalties. With JBOD, Kafka is configured to use multiple independent disks (log.dirs). If one disk fails, only the partitions on that specific disk go offline, and Kafka seamlessly fails over to the replicas on other brokers.

13. What is the physical structure of the __consumer_offsets topic?

In a beautiful example of self-hosting, Kafka stores consumer offsets using its own storage engine. The __consumer_offsets topic is a standard Kafka topic with a cleanup.policy=compact. The key is the combination of (group_id, topic, partition), and the value is the committed offset. When a consumer group restarts, it simply replays this compacted topic to rebuild its state.

14. How does a consumer find offset 1,500,000 without scanning the whole disk?

It uses a three-step process. First, Kafka looks at the segment filenames (which are named after their base offset, e.g., 0000000000001500000.log) and does a binary search to find the exact file containing the offset. Second, it looks at the memory-mapped .index file to find the closest physical byte position before the target offset. Finally, it jumps to that byte position in the .log file and scans forward a few messages until it finds the exact offset.

15. Why is XFS recommended over ext4 for Kafka storage?

Kafka is highly sensitive to I/O latency. The ext4 file system is known to suffer from significant latency spikes when performing massive file deletions (which Kafka does constantly via retention policies). XFS handles concurrent I/O and large-scale file deletions much more gracefully, making it the recommended file system for Kafka brokers.

16. What happens if a Tombstone (null value) is deleted before a consumer reads it?

This is a critical edge case in compaction. Tombstones are retained for delete.retention.ms (default 24 hours) specifically to prevent this. However, if a consumer is offline for longer than this period, it will miss the Tombstone entirely. When it comes back online, it will only see the older, un-compacted values (if it reads from the beginning), resulting in stale state. This is why compacted topics are usually paired with strict consumer SLAs or state restoration from a snapshot.

17. What is the difference between a "Clean" segment and a "Dirty" segment?

In the context of compaction, "dirty" does not mean unflushed. A Dirty segment is one that has not yet been processed by the Log Cleaner and may contain multiple historical values for the same key. A Clean segment has been processed by the Log Cleaner, and all superseded keys have been removed. The Log Cleaner continuously groups clean and dirty segments together to optimize the process.

18. Can you use Log Compaction on a topic that has no message keys?

No. Log compaction relies entirely on the message key to identify which records supersede others. If a topic has cleanup.policy=compact but messages are produced with null keys, the Log Cleaner cannot deduplicate them. In fact, Kafka will often reject the topic configuration or the cleaner will simply ignore null-keyed messages in a compacted topic, leaving them to grow indefinitely.

19. Why does Kafka keep a .timeindex file alongside the .index file?

Offsets tell you where a message is in the sequence, but they don't tell you when it arrived. The .timeindex file maps timestamps to offsets. This is crucial for use cases where you need to replay data from a specific time (e.g., "reprocess the last 2 hours of data after a bug fix"). Without the time index, Kafka would have to scan offsets sequentially to find the message with the correct timestamp.

20. How does Kafka protect itself from a disk filling up entirely?

Kafka has several defense mechanisms. First, brokers have a log.dirs config and rely on the OS to throw I/O exceptions if the disk is full. To prevent this, Kafka uses Replication Quotas (replica.quota). If a broker detects that a follower is lagging and consuming too much disk/network bandwidth trying to catch up, the quota throttles the follower. Additionally, administrators monitor the kafka.log:type=Log,name=Size JMX metrics to alert before the disk hits 100%. If the disk does fill, the broker will refuse new writes, but it will typically still serve reads so consumers can drain the backlog.

Replication: Ensuring Durability and Availability

Replication is the mechanism that transforms Kafka from a single-node message log into a fault-tolerant distributed system. Without replication, a broker failure would mean permanent data loss and service unavailability. Kafka's replication model is unique among distributed systems: it does not rely on majority quorum consensus for every write (like Raft or Paxos). Instead, it uses a leader-centric, ISR-based protocol that trades a small amount of consistency for enormous gains in throughput and availability.

This chapter dissects every layer of that protocol—from the follower fetch request to the High Watermark, from unclean leader election to the newly introduced Eligible Leader Replicas (ELR)—and explains the architectural reasoning behind each design decision.

The Leader-Follower Model

At the most fundamental level, Kafka replicates at the partition level. A topic with a replication factor of N has N identical copies of each partition, distributed across different brokers.

The Asymmetry of Roles:

  • The Leader: Handles all client reads and writes. Producers send records directly to the leader's log. Consumers (by default) fetch records from the leader. The leader is the sole authority for the ordering and acceptance of new records for that partition.
  • The Followers: Do not serve client requests (under default configurations). Their sole architectural purpose is to replicate the leader's log by sending Fetch requests—the exact same mechanism consumers use.

This asymmetry is a deliberate performance choice. If every replica could accept writes, Kafka would require complex distributed locking or quorum consensus to order records. By funneling all writes through a single leader, Kafka serializes the log in memory and on disk, eliminating contention.

The Follower Fetch Loop:

  1. The follower issues a FetchRequest to the leader, specifying the offset from which it wants to consume.
  2. The leader responds with a batch of records starting at that offset, along with the current Leader Epoch and the leader's High Watermark.
  3. The follower appends the records to its local log.
  4. The follower immediately issues another fetch request for the next offset.

This loop runs continuously, even when there is no new data, because the follower must also learn about changes to the High Watermark and the ISR from the leader.

The In-Sync Replica Set (ISR)

Not all replicas are equal. The ISR is the subset of replicas that are "caught up" to the leader. The leader is always a member of the ISR.

The Lag Threshold:

A follower remains in the ISR as long as it is actively fetching and keeping pace with the leader. The architectural definition of "in-sync" is governed by replica.lag.time.max.ms (default 30,000 ms). A follower is removed from the ISR if either of two conditions occurs: It has not sent a fetch request to the leader within the lag window. It has not caught up to the leader's Log End Offset (LEO) within the lag window. Once removed, the follower is no longer eligible to become leader. It can only re-enter the ISR after it has fully caught up to the leader's current LEO. The ISR is not static; it shrinks and grows dynamically based on network conditions, disk performance, and broker health.

The UnderReplicatedPartitions Metric:

The most critical operational metric in Kafka is UnderReplicatedPartitions. It counts the number of partitions led by a broker where the ISR size is smaller than the total replica count. In a healthy cluster, this metric is zero. If it remains above zero, the cluster has less durability than the replication factor suggests: a subsequent broker failure could drop the ISR below min.insync.replicas, blocking producers.

The High Watermark (HW)

The High Watermark is the linchpin of Kafka's consistency guarantee for consumers.

Definition and Mechanics:

The HW is the highest offset that every replica in the ISR has successfully replicated. When a producer writes record at offset 100, the leader appends it and its LEO becomes 101. However, the HW does not advance to 101 immediately. The leader tracks the fetch offsets of all ISR followers. If the slowest ISR follower has only fetched up to offset 98, the HW remains at 99 (the next offset to be fetched). Only when all ISR followers have fetched up to 100 does the leader advance the HW to 101.

Consumer Read Visibility:

Consumers can only read up to the High Watermark. This is the core of Kafka's "committed" data guarantee. If a consumer could read up to the leader's LEO, and the leader crashed before followers replicated offset 100, a new leader would be elected without offset 100. The consumer would have seen data that vanished—a catastrophic consistency violation. By restricting reads to the HW, Kafka ensures that any record a consumer has seen is durably replicated across the ISR and will survive a leader election.

HW Propagation Lag:

The follower's HW always lags slightly behind the leader's HW. The leader communicates the HW to followers in the fetch response. This asynchronous propagation means a follower may briefly have a stale HW. This is generally benign for consumers, but it is the root cause of "spurious out-of-range" errors in certain follower-fetching configurations.

Durability Guarantees — acks and min.insync.replicas

Replication alone does not prevent data loss. The producer and topic configurations must be aligned to enforce durability.

Producer Acknowledgments (acks):

  • acks=0: The producer does not wait for any acknowledgment. Data can be lost immediately.
  • acks=1: The leader writes to its local log and responds. If the leader crashes before followers replicate, data is lost.
  • acks=all (or -1): The leader waits until all ISR replicas have acknowledged the write before responding. This is the only setting that provides strong durability.

The min.insync.replicas Safety Net:

acks=all alone is insufficient. If the ISR shrinks to just the leader, acks=all is equivalent to acks=1. Therefore, min.insync.replicas enforces a minimum ISR size for writes to succeed. If min.insync.replicas=2 and the ISR has only one replica, the leader will reject writes with a NotEnoughReplicas exception. The most common production configuration is Replication Factor = 3, min.insync.replicas = 2, acks = all. This tolerates the loss of one broker without data loss and without blocking writes.

The "Stuck Replica" Edge Case:

A subtle architectural flaw: with acks=all, the leader waits for all ISR members. If a follower is in the ISR but becomes "stuck" (e.g., due to a GC pause or network blip) and stops fetching, the leader will wait indefinitely, eventually timing out the producer. The ISR lag timeout will eventually remove the stuck replica, but until then, producer latency spikes.

Leader Election and Failure Handling

When a leader fails, the cluster must elect a new leader without losing committed data.

The KRaft Controller's Role:

In modern Kafka (4.0+), the KRaft Controller Quorum (not ZooKeeper) is responsible for leader election. The active controller monitors broker heartbeats. When it detects a failure, it selects a new leader from the ISR of the affected partition.

Clean Leader Election:

A clean leader election selects a new leader from the ISR. Because every ISR member has replicated all data up to the High Watermark, no committed data is lost. The new leader increments the Leader Epoch and begins accepting writes. The old leader, upon recovery, is fenced and must truncate its log to the last committed offset before rejoining as a follower.

Unclean Leader Election:

What if no ISR replica is alive? The cluster faces a choice between availability and consistency: Wait for an ISR replica to return (preserves consistency but sacrifices availability), or elect a non-ISR replica (an out-of-sync follower) (restores availability but risks silent data loss). By default (unclean.leader.election.enable=false), Kafka chooses consistency over availability. Enabling unclean election is a deliberate trade-off for use cases where uptime is more critical than data integrity.

Leader Epochs and Log Divergence

Before KIP-101, followers truncated their logs based on the High Watermark. This could cause data loss during rapid leader changes because the HW could be stale.

The Leader Epoch Vector:

Kafka now uses Leader Epochs to prevent divergence. Each leader term is assigned a monotonically increasing epoch number. Each replica maintains a vector of (LeaderEpoch, StartOffset) pairs, recording when each leader's term began. When a follower rejoins after a failure, it does not blindly truncate to the HW. Instead, it sends a LeaderEpochRequest to the current leader. The leader returns the end offset of the follower's last known epoch. The follower truncates only the records that do not exist in the leader's log, eliminating the risk of truncating committed data.

The Last-Replica-Standing Problem and Eligible Leader Replicas (ELR)

Even with Leader Epochs, a known edge case remained: the Last-Replica-Standing scenario.

The Problem:

Imagine a partition with an ISR of [A, B] and min.insync.replicas=2. The HW is at offset 100. Broker A (leader) crashes. Broker B is the only ISR member left. Because the ISR size (1) is below minISR (2), the HW cannot advance. Broker B is then shut down uncleanly and loses its unflushed data (say, offsets 90–100). When B restarts, it is no longer in the ISR. But A is also still down. Now no ISR replica is alive. If unclean leader election is enabled, B—which has lost committed data—can be elected leader. The surviving replicas then truncate their logs to match B, causing cluster-wide committed data loss.

The ELR Solution (KIP-966):

Eligible Leader Replicas (ELR) separate the concept of "in-sync" from "safe to lead". The KRaft controller maintains a per-partition ELR set. A replica enters the ELR set if it has fully replicated data up to the HW, even if it has fallen out of the ISR (e.g., because the ISR size dropped below minISR). In the last-replica-standing scenario, B would be in the ELR set (it had replicated up to the HW before falling out). The controller can then elect B as leader without data loss, because B is known to have all committed data.

Leader Selection Order with ELR:

  1. ISR: If the ISR is non-empty, select an unfenced ISR replica.
  2. ELR: If the ISR is empty but the ELR is non-empty, select an unfenced ELR replica.
  3. Last Known Leader: If both are empty, select the last known leader if it is unfenced (this is the unclean election fallback).

Configuration and Operational Impact:

ELR is available from Kafka 4.0 and is enabled by default on new clusters from 4.1. It is controlled by eligible.leader.replicas.version. When ELR is enabled, the cluster-level min.insync.replicas config cannot be removed, and changing it (even to the same value) resets all ELR state. The ELR set is exposed via DescribeTopicPartitions for observability.

Edge Cases and Subtle Behaviors

  • HW Regression on Leader Change: When a new leader is elected, its HW may temporarily be lower than the old leader's HW, because the new leader's HW propagation lagged. During this window, consumers may experience a brief reduction in readable data. This is temporary and self-corrects.
  • Offset Reuse After Unclean Election: After an unclean leader election, the new leader may reuse offsets that a consumer group has already acknowledged. The consumer group will never receive records written at those reused offsets, creating a silent processing gap.
  • Consumer OffsetOutOfRange After Truncation: When a follower truncates its log due to Leader Epoch reconciliation or unclean election, a consumer reading from that follower (in a follower-fetching configuration) may encounter an OffsetOutOfRangeException if its offset was in the truncated region. The consumer must reset its position using auto.offset.reset.

20 Conceptual & Confusing Replication Questions

These target the subtle edge cases, failure modes, and internal mechanics of Kafka's replication architecture.

1. Why does Kafka use a "Pull" model for follower replication instead of the Leader "Pushing" data to followers?

If the Leader pushed data, it would have to maintain complex tracking of every follower's state, network capacity, and processing speed. If a follower was slow, the Leader would either have to block (hurting overall throughput) or drop data (causing inconsistency). By using a Pull model, the followers dictate the pace. A follower sends a FetchRequest with its current offset. The Leader simply responds with data up to a limit. This decouples the Leader's write speed from the follower's replication speed. It also allows the follower to batch requests, maximizing network efficiency, and prevents the Leader from overwhelming slow followers.

2. If a follower broker is fully alive and functioning, can it still be removed from the ISR?

Yes, it can be removed. Being "alive" (sending heartbeats to the KRaft controller) is not the same as being "in-sync." A follower is removed from the ISR if it fails to fetch data up to the Leader's Log End Offset (LEO) within replica.lag.time.max.ms (default 30 seconds). This can happen if the follower is experiencing a massive JVM Garbage Collection pause, a slow disk (I/O bottleneck), or severe network congestion. Even though the process is alive, it is too far behind to be considered a safe candidate for leader election.

3. Why can't consumers read data all the way up to the Leader's Log End Offset (LEO)?

This is the core of Kafka's "ghost read" prevention. The Leader's LEO is the offset of the next message to be written. If a consumer read up to the LEO, and the Leader crashed immediately before replicating that data to the followers, a new Leader would be elected that does not have that data. The consumer would have seen a message that effectively vanished from the system. To prevent this, consumers can only read up to the High Watermark (HW), which is the offset that has been successfully replicated to all members of the ISR.

4. If I set acks=all, am I guaranteed that my data will never be lost?

No. acks=all means the Leader will wait for acknowledgments from all current ISR members. However, if the ISR has shrunk to just the Leader (because followers are lagging), acks=all is functionally identical to acks=1. To guarantee durability, you must combine acks=all with min.insync.replicas (e.g., set to 2). This forces the Leader to reject writes if the ISR size drops below 2. If you don't use min.insync.replicas, a "last-replica-standing" scenario can lead to silent data loss.

5. What is the "Stuck Replica" problem, and how does it impact acks=all?

Because acks=all waits for all ISR members, it is vulnerable to a single slow replica. If a follower is in the ISR but becomes "stuck" (e.g., due to a transient network glitch or a long GC pause) right before a fetch, the Leader will wait for it indefinitely. During this time, producer latency spikes. The ISR lag timeout (replica.lag.time.max.ms) will eventually remove the stuck replica, but until that happens, the partition's write throughput is severely degraded.

6. How can an unclean leader election cause "silent data loss"?

An unclean election occurs when no ISR replica is available, and Kafka elects a replica that was not fully caught up (if unclean.leader.election.enable=true). This new leader is missing the most recent committed records. When the old replicas rejoin, the new leader forces them to truncate their logs to match the new leader's shorter log. The records that were committed (and possibly read by consumers) are permanently wiped out. It is "silent" because the cluster remains online, but data has disappeared.

7. Why did Kafka introduce "Leader Epochs" if we already had the High Watermark?

Before Leader Epochs, followers truncated their logs based on the High Watermark received from the new leader. But HW propagation is asynchronous. A new leader might have a stale HW. If a follower rejoined and truncated based on a stale HW, it could truncate data that was actually committed, or fail to truncate data that was uncommitted. Leader Epochs solve this by attaching a monotonically increasing number to each leader's term. Followers record the epoch and the offset at which it started. When rejoining, the follower asks the new leader for the end offset of its last known epoch, eliminating the ambiguity and ensuring only truly uncommitted data is truncated.

8. What exactly is the "Last-Replica-Standing" problem?

Imagine a partition with RF=3, minISR=2, and acks=all. The HW is at offset 100. Broker A (Leader) crashes. Broker B (ISR) crashes and comes back without its unflushed data (say, offsets 90-100). The ISR shrinks to size 1 (only Broker C). The HW cannot advance because minISR is not met. Now, Broker C crashes. When it recovers, it is no longer in the ISR. No ISR replica exists. If unclean election is enabled, Broker B (which lost offsets 90-100) is elected leader. It forces Broker C to truncate its log to offset 89. Committed data is lost.

9. How do Eligible Leader Replicas (ELR) solve the Last-Replica-Standing problem?

ELR (KIP-966) creates a separate set from the ISR. The ELR set tracks replicas that have fully replicated data up to the High Watermark, even if they fall out of the ISR (e.g., because the ISR size drops below minISR). In the Last-Replica-Standing scenario, Broker B would still be in the ELR set because it had previously replicated to the HW. If the ISR is empty, the KRaft controller will elect a leader from the ELR set rather than an arbitrary out-of-sync replica, guaranteeing zero committed data loss even when the cluster is down to its last safe replica.

10. What is the strict precedence order for leader election when ELR is enabled?

To guarantee safety while maximizing availability, the KRaft controller follows a strict order: ISR: Elect an unfenced ISR replica. ELR: If the ISR is empty, elect an unfenced ELR replica. Last Known Leader: If both ISR and ELR are empty, elect the last known leader (the unclean election fallback). This ensures the cluster only resorts to risking data loss after all known safe replicas (ISR and ELR) are unavailable.

11. How does a consumer's position behave if an unclean leader election occurs?

After an unclean election, the new leader has a shorter log (it lost data). A consumer's committed offset might point to a position that no longer exists (e.g., offset 100, but the new leader's LEO is 90). When the consumer fetches, it gets an OffsetOutOfRangeException and must reset. Even worse, the new leader may start accepting new data at offsets that were previously used (offsets 90-100). The consumer will never receive the original records at those offsets, resulting in a silent gap in data processing.

12. Why is UnderReplicatedPartitions considered the most critical operational metric?

If UnderReplicatedPartitions is greater than zero, it means the ISR size is smaller than the configured replication factor. Your cluster is now operating with reduced redundancy. If min.insync.replicas is 2 and your ISR size drops to 1, producers with acks=all will be blocked from writing. Furthermore, if the last ISR broker fails, you are forced into an unclean election (data loss) or a hard outage. This metric is the canary in the coal mine for both durability and availability.

13. If a follower falls out of the ISR, does it stop replicating data entirely?

No. The follower continues to send FetchRequests and receive data from the leader. Its architectural role changes: it is no longer eligible to be elected Leader, and it is not counted towards acks=all or the High Watermark. However, it continues to chase the leader's LEO. Once it catches up (it has fetched up to the leader's current LEO), the leader will automatically add it back to the ISR.

14. How does a newly elected leader know exactly how much data a rejoining follower needs to truncate?

The new leader does not push a truncation command. When a follower rejoins, it sends an OffsetForLeaderEpochRequest containing the last epoch it remembers and the offset it reached in that epoch. The leader responds with the end offset of that epoch from its own log. The follower compares this to its own log and truncates any data beyond the leader's returned offset. This ensures that the follower only removes uncommitted data, relying on the immutability of the epoch vectors rather than a potentially stale High Watermark.

15. Why does Kafka maintain a vector of (LeaderEpoch, StartOffset) pairs instead of just the latest epoch?

A follower might be offline for a long time, spanning multiple leader elections (e.g., it missed epochs 5, 6, and 7). The vector of pairs allows the follower to tell the new leader exactly where it diverged in the past. The leader can look at the follower's epoch history and say, "For epoch 6, I only have data up to offset 500, so you must truncate to 500." If the follower only had the latest epoch, the leader would not know the historical context of the follower's log.

16. Can a consumer read data that has not yet been replicated to the followers?

Under default configurations, no. Consumers are strictly gated by the High Watermark (HW). Even though the leader has the data locally (up to its LEO), it will not serve it to a consumer until all ISR followers have replicated it. However, Kafka 2.4 introduced replica.fetch.response.max.bytes and configurations for "Follower Fetching" (KIP-392), which allows consumers to read from the closest follower rather than the leader to save network costs. In that specific setup, the follower serves data only up to its own replicated HW, ensuring consistency.

17. What happens if the ISR shrinks below min.insync.replicas while a producer is writing with acks=all?

If the ISR size drops below the min.insync.replicas threshold, the leader will actively reject further produce requests. It throws a NotEnoughReplicas or NotEnoughReplicasAfterAppend exception. This is a deliberate safety mechanism. It is better to block writes (sacrificing availability) than to accept writes that cannot be replicated to the minimum safe number of brokers (sacrificing durability). The producers will retry until the ISR recovers.

18. What is "HW Regression," and why does it matter?

In a perfectly stable system, the HW only advances. But during a leader change, the new leader's HW may briefly be lower than the old leader's HW because HW propagation is asynchronous. During this window, consumers attempting to fetch data at the higher offset will receive an OffsetOutOfRangeException (or get empty responses). This regression is temporary; once the new leader's followers catch up, the HW will advance past its previous high point. It matters because consumers must be robust enough to handle these temporary read failures during failovers.

19. Why is the "Last Known Leader" the final fallback for leader election, even after ELR?

This is the ultimate availability vs. consistency trade-off. If the ISR and ELR are both empty, it means every safe replica is offline. The cluster is facing a choice: stay completely offline (waiting for a safe replica to return) or come online with a risk of data loss (unclean election). If unclean.leader.election.enable is true, the controller will pick the last known leader because it has the highest chance of having the most data, minimizing the potential data loss, even though it is not fully guaranteed to be safe. If the setting is false, the partition simply remains offline.

20. How does OffsetOutOfRangeException happen in a replicated system if data is supposed to be durable?

Durability guarantees that the data exists somewhere in the cluster, but it does not guarantee that a specific consumer's offset remains valid. A consumer will get this exception if: The data it is looking for has been deleted by retention policies (the log segments were purged). An unclean leader election occurred, and the new leader's log is shorter than the consumer's committed offset (the data was truncated). A follower truncation occurred due to Leader Epoch reconciliation. In all these cases, the consumer's offset points to a position that no longer exists in the current active log, forcing the consumer to reset its position.

Producer Theory: Writing Data

The producer is the entry point of the entire Kafka ecosystem. While brokers and storage systems are optimized for reading and retention, the producer is optimized for one thing: moving bytes from an application into the distributed commit log as efficiently and safely as possible. Every architectural decision in the producer—from the in-memory buffer to the sequence-number deduplication protocol—exists to balance three competing forces: throughput, latency, and durability.

The Internal Producer Pipeline

A call to producer.send(record) is deceptively simple. In reality, it traverses a pipeline made of seven distinct stages, split across two threads: the application's main thread and a background daemon called the Sender thread.

The Two-Thread Architecture:

The Kafka producer is fundamentally asynchronous. When the application calls send(), the method returns a Future<RecordMetadata> almost immediately. The actual network transmission happens in the background.

  • The Main (Application) Thread: Handles everything from interceptors to accumulation. It is responsible for serialization, partitioning, and appending the record to an in-memory buffer.
  • The Sender Thread: A daemon thread started when the KafkaProducer is constructed. It continuously polls the buffer, groups records into batches, and handles the network I/O to the brokers.

This decoupling is what allows the producer to achieve high throughput: the application thread never blocks on network I/O (unless the buffer is full).

Stage-by-Stage Breakdown:

  1. Interceptors (ProducerInterceptor): An extension point. The onSend() method runs on the main thread and can modify the record before it is serialized.
  2. Metadata Wait (waitOnMetadata): The producer checks if it has metadata (partition count, leader broker) for the target topic. If not, it blocks (up to max.block.ms) while fetching metadata from the cluster.
  3. Serialization: The key and value are converted to byte arrays using the configured Serializer classes.
  4. Partitioning: The Partitioner determines which partition the record belongs to. If a key is provided, it hashes the key. If no key is provided, it uses a sticky partitioner to fill batches efficiently.
  5. Record Accumulation (RecordAccumulator): The serialized record is appended to an in-memory queue associated with the target partition. This is where records wait to be batched.
  6. Batch Draining (Sender.ready() and drain()): The Sender thread identifies which partitions have accumulated enough data (or waited long enough) and drains those batches from the accumulator.
  7. Network I/O (NetworkClient): The Sender constructs ProduceRequest objects and hands them to the NetworkClient, which performs non-blocking NIO network operations to send the data to the broker.

Acknowledgments and Durability (acks)

The acks configuration is the single most important setting for controlling the durability of your writes. It determines how many replicas must acknowledge a record before the producer considers the send successful.

The Three Acknowledgment Modes:

  • acks=0 (Fire and Forget): The producer considers the record "written successfully" the moment it is sent onto the network. It does not wait for any response from the broker. This offers the lowest possible latency and highest throughput, but provides zero durability guarantees. If the broker is down or the network drops the packet, the data is lost forever.
  • acks=1 (Leader Only): The producer waits for the Leader replica to write the record to its local log and return an acknowledgment. This is faster than waiting for all replicas, but if the Leader crashes before Followers replicate the data, the record is lost.
  • acks=all (or -1): The producer waits for the entire In-Sync Replica (ISR) set to acknowledge the write. This provides the strongest durability guarantee. However, it does not completely eliminate the risk of data loss if the ISR shrinks to just the Leader.

The min.insync.replicas Safety Net:

acks=all alone is insufficient because the ISR is dynamic. If two of three brokers are offline, the ISR shrinks to one. In this state, acks=all is functionally identical to acks=1. The min.insync.replicas (minISR) broker/topic setting closes this gap. It specifies the minimum ISR size required for the broker to accept a write. If the ISR drops below minISR, the broker rejects the produce request with a NotEnoughReplicasException. The most common production configuration is Replication Factor = 3, minISR = 2, acks = all, which tolerates the loss of one broker without data loss and without blocking writes.

The Acknowledgment Flow: The Purgatory:

When a producer sends a batch with acks=all, the broker's I/O thread appends the records to the active log segment. The request then enters a component called the Purgatory—a delayed-operation timer wheel. It waits there until every broker in the current ISR acknowledges the replicated write, or until request.timeout.ms expires.

Idempotent Producers

In distributed systems, network failures can cause a producer to retry a send. Without safeguards, a retry can result in the same record being written twice.

The Deduplication Protocol:

The Idempotent Producer (enable.idempotence=true) solves this by ensuring that retrying a failed send never creates duplicates in the topic.

  • Producer ID (PID): Each producer instance is assigned a unique, broker-generated ID when it starts up.
  • Sequence Numbers: The producer attaches a monotonically increasing sequence number to every record, per topic-partition, starting at 0.
  • Broker-Side Deduplication: When a broker receives a batch, it checks the sequence number. If the sequence is the expected next value, it writes the batch. If the sequence is a duplicate (a retry), the broker discards the batch and sends a success response to the producer. If the sequence is out of order (a gap), the broker throws an OutOfOrderSequenceException.

Configuration Requirements and Defaults:

Idempotence requires specific configurations to be set. In Kafka 3.0+, idempotence is enabled by default. When enabled, the producer automatically enforces: acks=all, retries > 0, max.in.flight.requests.per.connection <= 5.

The Fencing Epoch:

Each PID is paired with an Epoch number. When a new producer instance is created with the same transactional.id, the broker increments the epoch. This fences out the old producer instance, preventing it from writing any more data.

The Limitation: It Only Lasts for One Session:

Idempotence guarantees exactly-once delivery only for the lifetime of a single producer session. If the producer application crashes and restarts, it gets a new PID. The broker cannot detect duplicates from the old PID.

Transactions and Exactly-Once Semantics (EOS)

Idempotence is not sufficient when a producer needs to write to multiple partitions atomically or when the consume-transform-produce pattern is used.

The Core Problem: Atomicity:

Consider a stream processing application that reads from topic A, transforms the data, and writes to topic B. Without transactions, a crash after writing to B but before committing the consumer offset for A results in duplicate writes upon restart.

The Transactional Producer:

Transactions allow a producer to group writes to multiple partitions into a single atomic unit. Either all messages are committed and become visible, or none are.

  • The transactional.id: A user-provided, persistent ID. Unlike the PID, which is ephemeral, the transactional.id survives restarts. It is used to recover or abort unfinished transactions from a previous instance.
  • The Transaction Coordinator: A broker-side component that manages the transaction state. It tracks which partitions are involved, coordinates the two-phase commit protocol, and maintains a transaction log in the internal __transaction_state topic.

The Consume-Transform-Produce Pattern:

The canonical EOS use case combines producer transactions with consumer offset commits: producer.beginTransaction(); for (ConsumerRecord record : consumer.poll(...)) { producer.send(new ProducerRecord<>("output", transform(record.value()))); } producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata()); producer.commitTransaction(); If commitTransaction() succeeds, both the output messages and the consumer offsets are committed atomically.

The Boundary of EOS:

Kafka's exactly-once guarantee is limited to the Kafka cluster. If the output of the transaction is written to an external system (like a database or a microservice), that external system is outside the transactional boundary and is not guaranteed to be atomic with the Kafka transaction.

Batching, Compression, and Throughput Optimization

Kafka's throughput is directly tied to how efficiently the producer can group records and minimize network overhead.

The Record Accumulator and Buffer Management:

The RecordAccumulator is an in-memory buffer (buffer.memory, default 32MB). If the buffer fills up, the send() method blocks for up to max.block.ms (default 60s) before throwing a BufferExhaustedException.

Batching: batch.size and linger.ms:

  • batch.size (default 16KB): The maximum number of bytes accumulated per partition before a batch is sent. Larger batches mean fewer network requests and higher throughput.
  • linger.ms (default 0, or 5ms in newer versions): The maximum time the producer will wait to fill a batch before sending it. This is the primary throughput-vs-latency trade-off. Increasing linger.ms allows more records to accumulate in a batch, improving throughput at the cost of added latency.

Compression:

Compression reduces network traffic and disk storage. The producer compresses the entire batch, not individual records, which is highly efficient. compression.type: Options are none, gzip, snappy, lz4, and zstd. Compression adds CPU overhead in the producer but significantly reduces the size of the request. lz4 is the recommended general-purpose choice. zstd offers the best compression ratio (up to 3x) and is ideal for high-throughput pipelines.

In-Flight Requests and Ordering:

max.in.flight.requests.per.connection controls how many unacknowledged requests can be sent over a single connection. Without idempotence: A value greater than 1 can cause reordering if a batch fails and a subsequent batch succeeds before the retry. With idempotence: The broker enforces ordering up to a value of 5. This is why idempotence allows you to maintain ordering while still having multiple in-flight requests.

20 Conceptual & Confusing Producer Questions

1. If I set acks=all, is my data guaranteed to never be lost?

No. acks=all waits for all current ISR members. If the ISR shrinks to one (the leader), acks=all degrades to acks=1. You must combine it with min.insync.replicas >= 2 to prevent the leader from acknowledging writes when it is the only replica left.

2. Why is idempotence enabled by default in Kafka 3.0+, and what is the cost?

It is enabled by default because the performance overhead is negligible (a few microseconds for PID assignment and sequence tracking), while the reliability benefit is massive. It prevents duplicate writes from network retries without requiring the user to understand the complexities of distributed deduplication.

3. Does an idempotent producer guarantee exactly-once delivery if my application crashes and restarts?

No. Idempotence is tied to a single producer session (a single PID). If the application restarts, it gets a new PID, and the broker cannot detect duplicates from the previous session. For cross-session exactly-once guarantees, you need transactions with a persistent transactional.id.

4. What is the difference between enable.idempotence and transactional.id?

enable.idempotence provides exactly-once guarantees per partition for the lifetime of a single producer session. transactional.id enables atomic writes across multiple partitions and survives producer restarts by allowing a new instance to abort or commit the previous instance's unfinished transactions.

5. If I set linger.ms=0, does that mean the producer sends immediately?

Not exactly. linger.ms=0 means the Sender thread does not wait to fill a batch; it sends whatever is in the accumulator as soon as it is ready. However, due to batching and network scheduling, there is still some microsecond-level batching that occurs. The Sender thread is not infinitely fast, so records can still accumulate briefly.

6. How does compression interact with batch.size?

Compression is applied to the entire batch. A larger batch.size means more data is compressed together, resulting in a better compression ratio and greater network savings. This is why high-throughput configurations pair a large batch.size with a compression codec like lz4 or zstd.

7. Why is max.in.flight.requests.per.connection limited to 5 when idempotence is enabled?

The sequence numbers are attached per batch. If there are too many in-flight requests, and a retry occurs, the broker may receive batches out of order. The limit of 5 ensures that the broker's reordering buffer can handle the window without throwing an OutOfOrderSequenceException.

8. Can I use acks=0 with idempotence?

No. Idempotence requires acks=all. If you explicitly set acks=0 or acks=1, idempotence is silently disabled (or an exception is thrown, depending on the version).

9. What happens if the RecordAccumulator buffer is full?

The send() call will block for up to max.block.ms (default 60s), waiting for space to free up. If space does not become available within that time, it throws a BufferExhaustedException or TimeoutException. This is a backpressure mechanism indicating the producer is sending data faster than the network can drain it.

10. Why does the Sender thread use a separate thread from the application?

If network I/O were done on the application thread, every send() call would block until the broker responded, destroying application performance. The two-thread model allows the application to continue producing records into the in-memory buffer while the Sender thread handles the network operations asynchronously.

11. What is the delivery.timeout.ms and how does it relate to retries?

delivery.timeout.ms is the upper bound on the total time a record can spend in the producer before being considered failed. It includes the time waiting in the accumulator, the time for all retries, and the time for the broker to acknowledge. The producer will fail the record when this timeout is reached, regardless of how many retries remain.

12. How do transactions handle "zombie" producers?

When a new producer instance starts with the same transactional.id, the Transaction Coordinator increments the epoch number. Any request from the old producer (with the old epoch) is rejected with a ProducerFencedException. This prevents a split-brain scenario where two producers are writing under the same identity.

13. What is the role of the __transaction_state topic?

It is an internal, compacted topic that stores the metadata and state of all ongoing and completed transactions. The Transaction Coordinator uses it to recover state after a broker restart. It tracks which partitions are involved in each transaction and whether they were committed or aborted.

14. Can a consumer read uncommitted transactional messages?

Yes, but only if configured to do so. Consumers have an isolation.level setting. read_uncommitted (the default) allows consumers to see all records, including those in ongoing or aborted transactions. read_committed filters out records from aborted or ongoing transactions, ensuring the consumer only sees committed data.

15. Why does the producer need to be restarted to enable idempotence?

Idempotence is a session-level guarantee. The PID is assigned when the producer is created. If you could toggle idempotence on and off mid-session, the sequence numbers would be inconsistent, and the broker's deduplication state would be invalidated. The configuration is therefore fixed at initialization.

16. How does the Sticky Partitioner improve batching?

If no key is provided, a round-robin partitioner would send record 1 to partition A, record 2 to partition B, etc. This prevents batches from filling up. The Sticky Partitioner sends all records in a batch to a single partition until the batch is full, then switches to another partition. This dramatically improves batching efficiency.

17. What is the relationship between buffer.memory and batch.size?

buffer.memory is the total memory available for all batches across all partitions. Each partition has its own batch.size buffer. If you have many active partitions, the total memory required is batch.size * active_partitions * safety_factor. If buffer.memory is too small, producers will block frequently.

18. Why does acks=all sometimes cause higher latency than acks=1?

With acks=1, the leader responds as soon as it writes to its local log. With acks=all, the leader must wait for all ISR followers to fetch and acknowledge the record. This extra round-trip to the followers adds network and disk latency to the acknowledgment path.

19. Can I achieve exactly-once semantics without transactions?

No. Idempotence alone only prevents duplicate writes per partition for a single producer session. If you need to atomically update multiple partitions or commit consumer offsets alongside producer writes, transactions are mandatory. Exactly-once semantics (EOS) in Kafka is built on the foundation of idempotence plus transactions.

20. What happens to a transaction if the producer crashes before committing?

The Transaction Coordinator will eventually time out the transaction (based on transaction.timeout.ms, default 60s) and automatically abort it. When a new producer instance starts with the same transactional.id, it will either recover the transaction or abort it before beginning a new one.

Consumer Theory: Reading Data

The consumer is where the value of the distributed commit log is ultimately realized. While producers and brokers are optimized for durability and throughput, the consumer is optimized for control, scalability, and isolation. It is the only component in the Kafka ecosystem that dictates how fast data is processed, which data is read, and how failures are recovered.

Every architectural decision in the consumer—from the two-thread poll loop to the server-driven rebalance protocol of KIP-848—exists to solve a single fundamental problem: how do you distribute the partitions of an ordered, immutable log across a dynamic group of independent processes without losing data, without duplicating work, and without stopping the world?

The Consumer Group — The Unit of Scalability

A single consumer reading from a topic is limited by the throughput of one process. To scale, Kafka introduces the Consumer Group.

The Partition Ownership Invariant:

Consumers that share the same group.id form a group. The group subscribes to a set of topics. Kafka distributes the partitions of those topics across the consumers in the group. The fundamental invariant is absolute: each partition is assigned to exactly one consumer within the group at any given time. This is what guarantees that records are processed in order and that no two consumers in the same group process the same record. A consumer can be assigned multiple partitions. If a topic has 5 partitions and a group has 3 consumers, the assignment might be [P0, P1], [P2, P3], [P4].

The Scalability Ceiling:

The maximum number of active consumers in a group equals the number of partitions in the subscribed topics. If you have 5 partitions and 7 consumers, 2 consumers will sit idle, acting as hot standbys that only begin working if an active consumer crashes. To increase parallelism, you must increase the partition count (which is a one-way operation for a topic).

Multiple Groups, Independent Progress:

Multiple consumer groups can read from the exact same topic independently. Each group has its own isolated offset ledger. Group A can be 1 million records behind while Group B is fully caught up, and neither affects the other. This is the architectural basis for the "multi-subscriber" model of the commit log.

Offset Management — The Ledger of Progress

Consumers do not "remove" records from Kafka. Instead, each consumer group maintains a committed offset for every partition it owns. This offset is the position of the next record to be read.

The __consumer_offsets Topic:

Offset commits are not stored in an external database. They are written to an internal, compacted Kafka topic called __consumer_offsets. When a consumer commits an offset, it sends an OffsetCommitRequest to the Group Coordinator (a designated broker). The coordinator appends the commit to __consumer_offsets. The commit is only acknowledged to the consumer after it has been replicated to the In-Sync Replicas (ISR) of the offsets topic partition. This ensures that committed offsets survive broker failures.

The Coordinator Cache:

While the durable record lives in the compacted topic, the Group Coordinator also caches offsets in an in-memory table. When a consumer sends an OffsetFetchRequest to resume after a restart, the coordinator serves the offset from this cache, avoiding a disk read. If the coordinator has just taken ownership of the offsets partition (e.g., after a broker failover), it must load the partition into cache; during this window, fetches fail with OffsetsLoadInProgressException, and consumers retry.

Auto-Commit vs. Manual Commit:

  • enable.auto.commit=true: The consumer commits offsets automatically at a fixed interval (auto.commit.interval.ms). This provides at-least-once semantics. If the consumer crashes after processing a batch but before the next auto-commit, the batch will be reprocessed.
  • enable.auto.commit=false: The application explicitly calls commitSync() or commitAsync(). This gives the developer control to implement at-least-once (commit after processing) or at-most-once (commit before processing) semantics.

The auto.offset.reset Safety Net:

What happens when a consumer group has no committed offset (first run) or the committed offset is out of range (the data was deleted by retention, or the log was truncated by an unclean election)? The auto.offset.reset configuration dictates the fallback: earliest: Reset to the beginning of the log. latest: Reset to the end of the log (skipping all existing data). none: Throw an exception. This only applies when there is no valid committed offset. It does not apply if a committed offset exists, even if it is far behind.

The Rebalance Protocol — Redistributing Ownership

A rebalance occurs whenever the membership of a consumer group changes or the set of subscribed partitions changes. During a rebalance, partition ownership is redistributed.

The Classic Eager Protocol (Stop-the-World):

The original rebalance protocol is eager. It operates on a strict, stop-the-world principle: Trigger: A consumer joins, leaves, or times out. Prepare Rebalance: The coordinator notifies all consumers to rejoin the group. Every consumer revokes all its partitions and stops processing. JoinGroup: All consumers send a JoinGroupRequest. The coordinator elects one consumer as the group leader and returns the full member list. SyncGroup: The leader computes the new partition assignment and sends it to the coordinator in a SyncGroupRequest. The coordinator distributes the assignment to all consumers. Resume: Consumers begin processing their new partitions.

The architectural flaw is obvious: a single consumer leaving causes the entire group to stop consuming, even the partitions that are not moving. In large groups, this creates significant processing gaps and latency spikes.

Cooperative Sticky (KIP-429 — Incremental, Client-Driven):

Introduced in Kafka 2.4, the CooperativeStickyAssignor keeps the client-side coordination model of the classic protocol but changes the revocation strategy. Instead of revoking all partitions, the cooperative protocol uses two rebalance rounds: Round 1: Consumers that need to give up partitions revoke only those partitions. They continue processing their remaining partitions. Round 2: The coordinator assigns the revoked partitions to their new owners. This is an incremental rebalance. A consumer that is not involved in the partition shuffle continues processing without interruption. The protocol still relies on a group-wide synchronization barrier, but the scope of that barrier is limited to the moving partitions.

KIP-848: The Next-Generation Server-Driven Protocol:

Available in Kafka 4.0, KIP-848 represents a fundamental architectural shift. It moves the rebalance logic from the clients to the broker's Group Coordinator.

The Problem with Client-Driven Coordination:

The classic protocols (both eager and cooperative) require multiple rounds of network communication: JoinGroup, SyncGroup, and multiple heartbeats. For large groups (thousands of consumers), this coordination overhead becomes the dominant cost of a rebalance. The clients must all agree on a common "generation" or "epoch" before progress can resume.

Server-Side Reconciliation:

KIP-848 eliminates the group-wide synchronization barrier entirely. The protocol works as follows: Continuous Heartbeat: Consumers send a ConsumerGroupHeartbeat request to the coordinator. This single RPC carries the consumer's subscription, its current assignment acknowledgment, and its liveness signal. Target Assignment: The coordinator computes a target assignment for the group using a server-side assignor (pluggable, with range and uniform assignors by default). Current State: The coordinator tracks the current assignment—which partitions each consumer actually owns and is processing. Incremental Reconciliation: On each heartbeat, the coordinator compares the current state to the target state. If they differ, it sends specific revoke or assign commands to individual consumers. There is no global "rebalance" event; the coordinator simply reconciles each consumer toward the target state at its own pace. A consumer pauses processing only for the specific partitions being revoked. All other consumers and all other partitions are completely unaffected.

The Group Epoch and Assignment Epoch:

To maintain consistency without a global barrier, KIP-848 uses two epochs: Group Epoch: Incremented whenever the group's target assignment changes (e.g., a member joins). Assignment Epoch: Included in the heartbeat. A consumer only acknowledges a new assignment if its epoch is current. This prevents stale, out-of-order assignments from being applied.

The Performance Impact:

The elimination of the stop-the-world barrier and the reduction of network rounds leads to dramatically faster rebalances—up to 20x faster in large groups. This makes KIP-848 safe for Kubernetes autoscaling, where pods are constantly joining and leaving, and for rolling restarts that previously triggered rebalance storms.

The Poll Loop and Flow Control

The consumer is fundamentally a pull-based system. The application calls poll() in a loop, and the consumer fetches data from the brokers.

The Two Threads:

  • The Application (Poll) Thread: The thread calling poll(). It handles deserialization, processing, and offset commits.
  • The Heartbeat Thread: A background thread that sends heartbeats to the coordinator to maintain membership in the group. It runs independently of the application thread, so a slow processing loop does not necessarily cause a session timeout (but it can cause a poll interval timeout).

The Two Timeout Guards:

  • session.timeout.ms (default 45s in Kafka 3.0+): The maximum time the coordinator will wait without receiving a heartbeat before declaring the consumer dead. The heartbeat thread must beat within this window (heartbeat.interval.ms should be ≤ 1/3 of this value).
  • max.poll.interval.ms (default 5 minutes): The maximum time between two poll() calls. If the application thread spends too long processing a batch and exceeds this interval, the consumer is considered failed, even if the heartbeat thread is still beating. The consumer will voluntarily leave the group, triggering a rebalance.

This dual-timeout mechanism separates liveness (heartbeat thread) from progress (poll thread). A consumer can be alive but not making progress; max.poll.interval.ms catches this case.

Flow Control: max.poll.records and Fetch Tuning:

  • max.poll.records (default 500): The maximum number of records returned in a single poll() call. If the broker has more data, the consumer holds it in an internal buffer for the next poll.
  • fetch.min.bytes (default 1): The minimum amount of data the broker should return for a fetch request. Increasing this reduces the number of fetch requests (improving throughput) at the cost of latency.
  • fetch.max.wait.ms (default 500): The maximum time the broker will wait to accumulate fetch.min.bytes before responding. This caps the latency introduced by fetch.min.bytes.

Incremental Fetch Sessions (KIP-227):

In a cluster with thousands of partitions, a single fetch request that enumerates every partition would be enormous. KIP-227 introduced fetch sessions: The consumer sends an initial full fetch request listing all partitions. The broker responds with a session ID and an epoch. Subsequent requests are incremental: the consumer sends only the delta—the partitions whose fetch state has changed (e.g., a partition was added or its fetch offset advanced). The broker maintains the session state on its side, merging the delta into the existing set. This reduces the network payload of fetch requests from O(partitions) to O(changes), which is critical for scalability.

Static Membership (KIP-345)

In dynamic environments (Kubernetes, rolling deployments), consumers restart frequently. A restart is a "leave" followed by a "join", which triggers a rebalance even though the consumer is coming right back. Static Membership solves this by assigning each consumer a user-provided group.instance.id. When a static member restarts: It rejoins with the same group.instance.id. The coordinator recognizes the ID and does not trigger a rebalance. The consumer resumes its previous assignment without partition shuffling. The coordinator retains the static member's assignment for a longer period (the session timeout) before declaring it permanently gone. This is the single most effective configuration for reducing churn in containerized environments.

Isolation Levels and Transactional Reads

When reading from topics that receive transactional writes (EOS), consumers must decide what visibility they have into open transactions.

isolation.level=read_uncommitted:

The default. The consumer sees all records, including those written by transactions that are still open or have been aborted. This provides the highest throughput and lowest latency but breaks exactly-once guarantees for the consumer.

isolation.level=read_committed:

The consumer only sees records from transactions that have been successfully committed. Records from aborted or ongoing transactions are filtered out. Architecturally, the consumer cannot read past the Last Stable Offset (LSO). The LSO is the highest offset such that all transactions below it are either committed or aborted. If a transaction is open at offset 100, a read_committed consumer cannot read past offset 99 until that transaction is resolved. This can introduce transactional lag on partitions with long-running transactions.

20 Conceptual & Confusing Consumer Questions

1. Why can't a consumer group have more active consumers than partitions?

Because the fundamental invariant is that a partition can only be assigned to one consumer in a group. Extra consumers are idle because there is no partition left to assign. To increase parallelism, you must add partitions. This is why partition count should be planned for peak future concurrency, not just current throughput.

2. If a consumer commits offset 100, does it mean it has processed record 100?

Not necessarily. If enable.auto.commit=true, the commit happens on a timer, not after processing. The consumer may have fetched up to 150 but processed only 120 when the auto-commit fires. If it crashes, records 121–150 will be reprocessed, resulting in duplicates. This is why at-least-once semantics require idempotent processing.

3. What is the difference between session.timeout.ms and max.poll.interval.ms?

session.timeout.ms is checked by the heartbeat thread. If the broker doesn't hear a heartbeat within this window, the consumer is dead. max.poll.interval.ms is checked by the poll thread. If the application goes too long between poll() calls (even if the heartbeat thread is still alive), the consumer voluntarily leaves the group. The first detects process failure; the second detects processing stalls.

4. Why does a cooperative rebalance still require two rounds?

Round 1 gathers the revocations. Consumers that need to give up partitions revoke only those partitions and report back. Round 2 assigns the freed partitions to their new owners. Without Round 2, the coordinator would not know which partitions are available to assign. The key improvement over eager is that unaffected partitions are never revoked.

5. How does KIP-848 eliminate the group-wide synchronization barrier?

By moving the assignment computation to the broker and making the heartbeat the sole communication channel. Each consumer independently heartbeats. The coordinator compares the current assignment to the target and sends targeted revoke/assign commands to the consumers that need them. There is no "wait for all consumers to join" phase. A consumer that is not affected never knows a rebalance is happening.

6. What happens if a consumer is revoked a partition while it is still processing a batch?

In the classic protocols, the consumer must finish the current poll() batch before it can rejoin or acknowledge revocation. In KIP-848, the coordinator can instruct a consumer to revoke a partition at any time. The consumer will finish processing the in-flight records for that partition, commit the offset, and then release ownership. This is why the max.poll.records and processing-time bounds are critical: they determine how long a revocation can be delayed.

7. What is the OffsetsLoadInProgressException and why does it happen?

When a Group Coordinator is elected for a __consumer_offsets partition for the first time (e.g., after a broker failover), it must load that partition into its in-memory cache. During this load, OffsetFetchRequests fail with OffsetsLoadInProgressException. The consumer retries after a backoff. This is a transient condition and does not indicate data loss.

8. Can a consumer read from a follower replica instead of the leader?

Yes, using Follower Fetching (KIP-392). This allows consumers to read from the replica closest to them (e.g., in the same rack or data center), reducing cross-rack network traffic. The follower serves data only up to its own High Watermark, ensuring that the consumer never reads data that might be lost.

9. Why does a rebalance storm happen, and how do you prevent it?

A rebalance storm occurs when consumers repeatedly join and leave, causing endless rebalance cycles. Common causes: max.poll.interval.ms too low for the processing time. session.timeout.ms too low for the network latency. Pods restarting without static membership. Prevention: use group.instance.id (static membership), tune the poll and session timeouts, and ensure processing completes within the poll interval.

10. What is the __consumer_offsets topic's replication factor, and why does it matter?

It is an internal topic with a replication factor (typically 3). If it loses replicas, offset commits can fail (if acks=all is used for offsets). A failed offset commit means the consumer cannot advance its progress; on restart, it will re-read from the last successful commit. This topic must be treated with the same care as any production topic.

11. How does auto.offset.reset=latest cause data loss?

If a consumer group has no committed offset (or its offset is out of range) and auto.offset.reset=latest, it will start reading from the end of the log, skipping all existing records. This is intentional for real-time-only consumers but catastrophic for batch-processing consumers that expect to process historical data.

12. What is the relationship between the Group Coordinator and the KRaft Controller?

The KRaft Controller manages cluster metadata (topics, partitions, leaders). The Group Coordinator is a broker-side component responsible for a subset of consumer groups. When a consumer looks up its coordinator, it sends a FindCoordinatorRequest to any broker; the broker returns the address of the broker hosting the __consumer_offsets partition for that group. The coordinator operates independently of the controller's metadata management.

13. Can two consumer groups have the same group.id but different subscriptions?

No. The group.id is the identity of the group. All consumers with the same group.id must share the same subscription. If they subscribe to different topics, the coordinator will compute an assignment that covers the union of subscriptions, but a consumer that did not subscribe to a topic will not be assigned its partitions. This is generally an anti-pattern; use distinct group.ids for distinct applications.

14. What happens to offsets when a topic is deleted and recreated?

Offsets are tied to the topic-partition and the group. When a topic is deleted, the __consumer_offsets entries for that topic remain (they are compacted, not deleted synchronously). If the topic is recreated with the same name, the old offsets may still be present, causing consumers to resume from positions that no longer correspond to the new topic's data. This is why auto.offset.reset is a safety net.

15. Why is commitAsync() preferred in some high-throughput consumers?

commitSync() blocks the poll thread until the broker acknowledges the commit, adding latency to every poll cycle. commitAsync() sends the commit and returns immediately, allowing the consumer to continue fetching. The trade-off is that a commit failure is not immediately known; the application must handle retries or fall back to a synchronous commit on shutdown.

16. What is the FetchSession and why does it matter for consumers with many partitions?

A fetch session maintains state on the broker for a specific consumer's fetch requests. Without it, every fetch request must list every partition, creating massive network overhead. With incremental fetch sessions, subsequent requests carry only the deltas. This is essential for consumers subscribed to topics with hundreds or thousands of partitions.

17. How does the consumer know which broker to fetch from for each partition?

The consumer periodically refreshes metadata (metadata.max.age.ms). For each partition, the metadata indicates the leader broker. The consumer sends fetch requests directly to the leader. If the leader changes, the consumer receives a NotLeaderForPartitionException and refreshes metadata.

18. What is the difference between a "generation" in the classic protocol and an "epoch" in KIP-848?

In the classic protocol, the generation is a group-wide number. All consumers must be on the same generation to participate; a new generation starts only after all consumers have rejoined and synced. In KIP-848, the group epoch and assignment epoch are managed by the coordinator. A consumer can be on an older assignment epoch while another consumer is on a newer one; the coordinator reconciles them independently. This is the essence of the incremental, server-driven design.

19. Can a consumer pause and resume partitions?

Yes, using pause(Collection<TopicPartition>) and resume(Collection<TopicPartition>). Pausing a partition tells the consumer to stop fetching from it, but it remains assigned to the consumer. This is useful for backpressure: if a downstream system is slow, the consumer can pause the relevant partitions without triggering a rebalance.

20. What is the maximum parallelism of a consumer group, and how do you exceed it?

The maximum parallelism is the number of partitions. To exceed it, you must either: Add more partitions to the topic (a permanent change). Use Share Groups (KIP-932), a newer feature that allows multiple consumers to cooperatively process records from the same partition, breaking the one-to-one invariant. Share Groups are designed for queue-like workloads where per-record ordering is not required.

Advanced Delivery Semantics

Data processing guarantees define how a system handles records when failures occur. In a distributed system, failures are not exceptional—they are the norm. Networks partition, brokers crash, disks fill, and consumer processes are killed by orchestrators. The delivery semantics you choose determine what happens to your data when these failures inevitably strike.

Kafka offers three fundamental delivery semantic models, each representing a different trade-off between reliability, performance, and implementation complexity: At-Most-Once, At-Least-Once, and Exactly-Once Semantics (EOS). These guarantees are not properties of the broker alone; they are contracts formed by the coordinated configuration of producers, brokers, and consumers.

The Three Delivery Semantics

The Fundamental Problem:

The delivery guarantee is fundamentally about the relationship between three events: The producer writes a record to the broker. The consumer processes the record. The consumer commits its offset. If any of these events fails, or if the system cannot determine whether an event occurred, the delivery guarantee dictates how the system recovers.

At-Most-Once Delivery:

The system processes a record at most once. If a failure occurs, the system will not retry, potentially leading to data loss. At-most-once is the simplest semantic to implement because it requires no coordination or retry logic. It can be configured at either the producer or consumer side.

Producer-Side At-Most-Once: The producer sets acks=0 and disables retries (retries=0). The producer sends the record and does not wait for any acknowledgment from the broker. If the network drops the packet or the broker is down, the record is lost forever. This offers the highest possible throughput and the lowest possible latency because no network round-trip is required for acknowledgment.

Consumer-Side At-Most-Once: The consumer commits its offset before processing the record. If the consumer crashes during processing, on restart it resumes from the already-committed offset and skips the record entirely. The record is lost.

The Architectural Rationale: At-most-once trades reliability for speed. It is appropriate for use cases where occasional data loss is acceptable and performance is critical: high-throughput telemetry, metrics collection, log aggregation, or non-critical monitoring data.

The Danger of Auto-Commit: The most common cause of unintended at-most-once delivery is enable.auto.commit=true (the default). With auto-commit, Kafka commits offsets during poll() at a configured interval (auto.commit.interval.ms, default 5 seconds). The failure scenario is subtle and devastating: Consumer calls poll() and receives messages 100–199. Auto-commit fires and commits offset 200. Consumer crashes while processing message 150. Consumer restarts and fetches from offset 200. Messages 150–199 are lost forever. A platform engineer at an e-commerce company reported losing 10,000 orders because auto-commit was enabled and the consumer crashed between commit and processing. Auto-commit provides at-most-once delivery by default, and if you cannot tolerate message loss, it must be disabled.

At-Least-Once Delivery:

The system guarantees a record will be processed, but failure recovery may cause the record to be processed more than once, leading to data duplication. This is the default setting for most message systems and the most common semantic in production. At-least-once requires the producer to wait for acknowledgment and retry on failure, and the consumer to commit offsets after successful processing.

Producer Configuration: acks=all (or -1): The leader waits for the entire In-Sync Replica (ISR) set to acknowledge the write before responding. retries > 0: The producer retries failed sends, potentially creating duplicates if the original send was actually successful but the acknowledgment was lost.

Consumer Configuration: enable.auto.commit=false: The application controls when offsets are committed. Commit the offset after the record has been successfully processed.

The Duplicate Problem: If the consumer crashes after processing record 150 but before committing the offset, on restart it will re-read record 150 and process it again. This is not a bug; it is the defined behavior of at-least-once. The architecture guarantees no data loss, but it makes no promise about duplicates.

The Mitigation: Idempotent Processing: The burden of duplicates is shifted to the application. The processing logic must be idempotent—processing the same record twice must produce the same result as processing it once. Common strategies include: Unique ID Check (track processed message IDs in a database), Upsert Operations (use insert-or-update logic keyed by an entity ID), Conditional Writes (only write if the record is newer than the existing state). A customer address update is naturally idempotent: writing the same address twice produces the same result. A payment charge is not: charging a customer twice is a critical failure.

When At-Least-Once Is Appropriate: At-least-once is the preferred semantic for most production applications where data loss is unacceptable but duplicates can be managed through idempotent processing or downstream deduplication logic.

Exactly-Once Semantics (EOS):

The system ensures that every record is processed exactly one time, avoiding both data loss and data duplication. Messages are processed precisely once even in the presence of producer retries, broker failures, or consumer crashes.

Why Exactly-Once Is Hard: Exactly-once is the holy grail of distributed messaging because it requires solving two separate problems simultaneously: The producer-side problem: How do you prevent duplicates when a producer retries a send that may or may not have succeeded? The consumer-side problem: How do you atomically update the output data and the consumer offset, so that a crash cannot cause either duplicate processing or data loss? Kafka solves the first problem with idempotent producers and the second with transactions.

The Two Pillars of Kafka EOS: Idempotent Producers: Sequence-number-based deduplication that ensures retries do not create duplicates within a single producer session. Transactions: Atomic multi-partition writes that group records and offset commits into a single unit that either fully succeeds or fully rolls back.

When Exactly-Once Is Required: EOS is mandatory for financial transactions, inventory updates, billing systems, or any operation where duplicates cause incorrect results. Processing a payment twice charges the customer incorrectly; missing a payment fails to record revenue.

The Cost: Exactly-once is not free. It introduces: Slightly higher latency (typically 2–5 ms) due to the additional coordination round-trips. Lower throughput (10–20% reduction) compared to at-least-once. Increased configuration and operational complexity. The requirement for consumers to use isolation.level=read_committed to filter out aborted records.

Idempotent Producers — The First Pillar

The idempotent producer is the foundation of Kafka's exactly-once guarantee. It solves a deceptively simple problem: when a producer sends a record and does not receive an acknowledgment, it does not know whether the record was written or not. If it retries, it may create a duplicate. If it does not retry, it may lose the record.

The Deduplication Protocol:

Kafka assigns each producer a unique Producer ID (PID) during initialization. The producer then tags each record (specifically, each record batch) with a monotonically increasing sequence number, per topic-partition, starting at 0. When a broker receives a batch, it maintains the last sequence number it has seen for that PID and partition. It then applies a simple but powerful rule: If the sequence number is exactly the expected next value, the broker writes the batch and updates its expected sequence. If the sequence number is lower than the expected next value, the broker recognizes it as a duplicate (a retry). It discards the batch and sends a success response to the producer. If the sequence number is higher than the expected next value (a gap), the broker throws an OutOfOrderSequenceException. This protocol ensures that retrying a failed send never creates duplicates, because the broker can identify and discard retries.

The Configuration Requirements:

Enabling idempotence (enable.idempotence=true) triggers automatic validation and enforcement of three related configurations: max.in.flight.requests.per.connection must be ≤ 5. This limits the number of unacknowledged requests that can be in flight on a single connection. The broker's reordering buffer can handle up to 5 out-of-order batches. If batch 2 fails and batch 3 succeeds, the broker holds batch 3 until batch 2 is retried, preserving order. retries must be > 0. Idempotence only matters if the producer actually retries. acks must be all. The broker needs to receive the batch to deduplicate it; acks=0 or 1 is incompatible.

The Fencing Epoch:

The PID alone is not sufficient. If a producer application restarts, it gets a new PID, and the broker cannot correlate it with the old session. To enable cross-session idempotence, Kafka pairs the PID with a Producer Epoch. When a new producer instance initializes with the same transactional.id (for transactional producers), the broker increments the epoch. The old producer instance is fenced—its requests are rejected with a ProducerFencedException. This prevents a "zombie" producer from writing data after a new instance has taken over.

The Limitation: Session Scoped:

Idempotence without transactions guarantees exactly-once delivery only to a single partition, for the lifetime of a single producer session. It does not survive producer restarts, and it does not provide atomicity across multiple partitions.

Transactions — The Second Pillar

Idempotence solves the duplicate problem for a single partition and a single producer session. But modern stream processing requires something more: the ability to read from one topic, transform the data, write to multiple output topics, and commit the consumer offset—all as a single atomic operation.

The Consume-Transform-Produce Pattern:

Consider a stream processing application that reads from topic A, computes an aggregation, and writes to topic B. It must also commit its consumer offset for topic A. Without transactions, a crash between writing to B and committing the offset for A results in duplicate processing on restart: the records in A are re-read, and the output in B is written twice. Transactions solve this by grouping the output writes and the offset commit into a single atomic unit.

The Transactional Producer:

The transactional producer is configured with a transactional.id—a user-provided, persistent identifier. Unlike the PID, which is ephemeral, the transactional.id survives restarts and is used to recover or abort unfinished transactions from a previous instance.

The Transaction Coordinator:

Transactions are coordinated by a broker-side component called the Transaction Coordinator (TC). The TC manages a transaction log in the internal __transaction_state topic and is responsible for driving the transaction through its lifecycle: begin, prepare, commit, or abort. The TC also handles timeout management. If a transaction remains open longer than transaction.timeout.ms (default 60 seconds), the TC will proactively abort it, preventing a stuck producer from blocking read_committed consumers indefinitely.

The Two-Phase Commit Protocol:

Kafka implements a lightweight two-phase commit (2PC) protocol for transactions. It does not use the XA standard; instead, it uses its own internal topics and control messages.

Phase 1: Prepare. The producer calls commitTransaction(). The producer sends an EndTxnRequest (with commit=true) to the TC. The TC writes a PREPARE_COMMIT record to the __transaction_state topic. The TC sends the transaction metadata (the list of involved partitions) to the leaders of those partitions. The partition leaders write a transaction marker (a control record) to their logs.

Phase 2: Commit. Once all partition leaders have acknowledged the prepare phase, the TC writes a COMPLETE_COMMIT record to the __transaction_state topic. The producer receives a success response and can proceed. The transaction markers in the data partitions signal to consumers that the records are now committed. If any step fails, the transaction is aborted. The TC writes an ABORT marker, and the records from the aborted transaction are marked as invisible to read_committed consumers.

How Transactions Handle Offsets:

The critical insight of Kafka's transaction design is that consumer offsets are treated as just another message. When a producer calls sendOffsetsToTransaction(), the offsets are written to the __consumer_offsets topic as part of the same transaction. This means the offset commit and the output records are atomic: either both are committed, or neither is.

The Isolation Level: read_committed:

Transactions are only half of the exactly-once guarantee. The other half is on the consumer side. A consumer configured with isolation.level=read_committed will only see records from transactions that have been successfully committed. Records from aborted or ongoing transactions are filtered out. The architectural mechanism is the Last Stable Offset (LSO). The LSO is the offset just before the oldest open (uncommitted, not yet aborted) transaction in the partition. A read_committed consumer cannot read past the LSO.

The Production Hazard: LSO Lag:

If a transactional producer opens a transaction at offset 100 and takes 30 seconds to commit, all read_committed consumers on that partition are blocked at offset 99 for those 30 seconds, even if records at offset 200 are already in the log. A slow or stuck transactional producer can cause consumer lag to grow rapidly and trigger processing SLA violations. This is why transaction.timeout.ms must be tuned carefully.

The Common Mistake:

If you configure a transactional producer but forget to set isolation.level=read_committed on the consumer, the consumer will happily read records from aborted transactions—seeing data that was supposed to be rolled back. The transactional guarantee on the producer side is useless without the corresponding filter on the consumer side.

EOS Version 2 (KIP-447):

The original transaction design (KIP-98) required one unique transactional.id per producer instance. This made it difficult to scale stream processing applications, because each thread or task needed its own transactional ID. KIP-447 introduced a new threading model where multiple stream processing tasks can share a single transactional producer and a single transactional.id. This mode was originally called exactly_once_beta and was renamed to exactly_once_v2 in Kafka 3.0 (KIP-732). It improves application scalability by allowing more concurrent transactional producers without requiring a globally unique ID per instance. Kafka Streams enables EOS v2 by setting processing.guarantee=exactly_once_v2 (broker version 2.5+ required).

The Boundaries of Exactly-Once

Kafka's exactly-once guarantee is often misunderstood. It is a powerful but bounded guarantee.

Within Kafka, Not Beyond:

Kafka's EOS guarantee covers the Kafka cluster: reading from Kafka topics, processing, and writing back to Kafka topics, including offset commits. If your application writes to an external system—a relational database, a REST API, a file system—that external system is outside the transactional boundary. If a transaction commits in Kafka but the external write fails, you have a consistency violation. The Kafka record exists; the external side effect does not. To achieve atomicity across Kafka and an external system, you must use architectural patterns such as: The Outbox Pattern: Write to the external database and a Kafka topic in the same database transaction. Change Data Capture (CDC): Capture the database changes and stream them to Kafka.

20 Conceptual & Confusing Delivery Semantics Questions

1. If I enable idempotence on the producer, do I get exactly-once semantics?

No. Idempotence guarantees exactly-once delivery to a single partition, for the lifetime of a single producer session. It does not survive producer restarts, and it does not provide atomicity across multiple partitions or between output writes and offset commits. True EOS requires transactions, which build on top of idempotence.

2. Why does acks=all not guarantee exactly-once by itself?

acks=all ensures durability: the leader waits for all ISR replicas to acknowledge the write. But if the producer retries a send because the acknowledgment was lost (even though the write succeeded), a duplicate is created. Durability is not the same as exactly-once. Idempotence is required to prevent the duplicate from the retry.

3. What is the difference between enable.idempotence and transactional.id?

enable.idempotence provides session-scoped, single-partition deduplication. It does not survive restarts and does not coordinate across partitions. transactional.id is a persistent identifier that enables cross-session exactly-once by allowing a new producer instance to recover or abort transactions from a previous instance. transactional.id is the foundation of atomic multi-partition writes.

4. If a consumer uses read_committed, can it still see duplicates?

Yes, in certain failure scenarios. read_committed filters out records from aborted transactions. But if a transaction commits successfully, and the consumer later crashes and re-reads from an earlier offset (due to a rebalance or a manual reset), it will see the same committed records again. read_committed does not prevent duplicates from consumer-side reprocessing; it only prevents visibility of aborted transactional data.

5. What happens if a transactional producer crashes before calling commitTransaction()?

The transaction remains open until it times out. The Transaction Coordinator will eventually abort it after transaction.timeout.ms (default 60 seconds). The records written by the transaction are marked as aborted and are invisible to read_committed consumers. The producer must call initTransactions() on restart to recover or abort the previous transaction before beginning a new one.

6. Why is max.in.flight.requests.per.connection limited to 5 when idempotence is enabled?

The broker's reordering buffer can hold up to 5 out-of-order batches. If batch 2 fails and batch 3 succeeds, the broker holds batch 3 until batch 2 is retried, preserving order. If more than 5 requests were in flight, the broker might not have enough buffer space to hold all the out-of-order batches, and it would have to reject them, causing a producer error.

7. Can I use transactions with acks=1?

No. Transactions require acks=all. The Transaction Coordinator and the partition leaders must have strong durability guarantees to ensure that the transaction markers are not lost. acks=1 would allow a transaction marker to be lost if the leader crashes after writing it but before replicating it.

8. What is the __transaction_state topic, and why does it matter?

It is an internal, compacted Kafka topic that stores the metadata and state of all ongoing and completed transactions. The Transaction Coordinator uses it to recover state after a broker restart. It tracks which partitions are involved in each transaction and whether they were committed or aborted. If this topic is unavailable, no new transactions can be initiated.

9. How does a consumer recover from a ProducerFencedException?

A ProducerFencedException indicates that a new producer instance with the same transactional.id has taken over, and the current producer is a zombie. The correct response is to stop the producer immediately and not attempt to retry. The application should be restarted or a new producer should be created with a different transactional.id. Retrying with a fenced producer will only cause more errors.

10. If I use enable.auto.commit=true, can I ever achieve at-least-once?

Technically, yes, but it is extremely fragile. Auto-commit commits offsets on a timer, independent of processing. If processing is fast enough that it always completes before the next auto-commit, you might achieve at-least-once in practice. But if processing is slow or variable, auto-commit will commit offsets for records that have not been processed, resulting in at-most-once (data loss). There is no configuration of auto-commit that guarantees at-least-once; manual commit is required.

11. What happens to offsets when a transaction is aborted?

The offsets written via sendOffsetsToTransaction() are also part of the transaction. When a transaction is aborted, those offset commits are rolled back. The consumer group's committed offset remains at its previous value, ensuring that the records are re-read and reprocessed in the next transaction.

12. Can a read_committed consumer read past the LSO if the transaction is taking too long?

No. The LSO is a hard boundary. The consumer cannot read past it until the open transaction is resolved (committed or aborted). This is why transaction.timeout.ms is critical: it bounds the maximum time a transaction can block consumers. If a transaction is stuck, the TC will abort it after the timeout, allowing the LSO to advance.

13. How does Kafka Streams achieve exactly-once processing?

Kafka Streams uses the transactional producer under the hood. When processing.guarantee=exactly_once_v2 is configured, Streams manages transactions automatically: it begins a transaction, processes records, writes output, commits offsets, and commits the transaction—all as a single atomic unit. The exactly_once_v2 mode (KIP-447) allows multiple tasks to share a transactional producer, improving scalability.

14. If I retry a failed batch manually (by re-sending it), does idempotence still protect me?

Only if the retry is within the same producer session and uses the same PID and sequence numbers. If you manually re-send a record by calling producer.send() again, it is treated as a new record with a new sequence number, and idempotence will not deduplicate it. Idempotence only protects against the producer's internal retry mechanism, not application-level re-sends.

15. What is the relationship between transactional.id and consumer group offsets?

The transactional.id is associated with the producer, not the consumer. However, when sendOffsetsToTransaction() is called, the offsets for the consumer group are written as part of the transaction. The transactional.id ensures that the producer can recover the transaction state across restarts, and the offsets are atomically committed or aborted along with the output records.

16. Why can't I use EOS with a consumer that is not in a consumer group?

You can use a transactional producer without a consumer group, but the sendOffsetsToTransaction() call requires a ConsumerGroupMetadata object, which is only available if the consumer is part of a group. For manual partition assignment (assign()), you can use sendOffsetsToTransaction(offsets, groupMetadata) if you provide the group metadata manually, but this is uncommon and error-prone.

17. How does the broker handle a transaction that spans multiple partitions?

The Transaction Coordinator sends the transaction metadata to the leaders of all involved partitions. Each leader writes a transaction marker to its log. The commit is only finalized when all partition leaders have acknowledged the marker. If any partition leader fails, the TC retries until the marker is written or the transaction times out and is aborted.

18. What is the difference between read_committed and read_uncommitted in terms of LSO?

read_uncommitted (the default) ignores the LSO entirely. It can read all records, including those from open or aborted transactions. read_committed respects the LSO: it will not read past the offset of the oldest open transaction. This means read_committed consumers may experience transactional lag—they cannot read data that is "behind" an open transaction, even if newer data exists.

19. Can I achieve exactly-once semantics without using Kafka transactions?

Not within Kafka itself. Idempotence alone is insufficient for multi-partition atomicity and offset coordination. You can achieve effectively-once semantics by using at-least-once delivery combined with idempotent processing and a deduplication store (e.g., a database table of processed message IDs). But this is an application-level solution, not a Kafka-level guarantee.

20. How do I monitor whether my transactions are healthy?

Key metrics to watch: TransactionCoordinatorMetrics: Number of ongoing, committed, and aborted transactions. transaction.timeout.ms violations: A rising number of aborted transactions indicates stuck producers. LSO lag: The gap between the LSO and the high watermark. If this grows, read_committed consumers are blocked. Producer record-error-rate: Errors like ProducerFencedException or InvalidProducerEpochException indicate zombie producers or fencing events.

Modern Architecture: KRaft, Tiered Storage, and Share Groups

Apache Kafka is undergoing its most significant architectural transformation since its creation. For over a decade, Kafka's design was constrained by two fundamental assumptions: metadata must be managed by an external system (ZooKeeper), and all data must live on the local disks of the brokers. The modern architecture shatters both assumptions.

The removal of ZooKeeper in Kafka 4.0 (March 2025), the general availability of Tiered Storage in Kafka 3.9 (KIP-405), and the introduction of Share Groups (KIP-932) represent a re-architecture of Kafka's control plane, data plane, and consumption model respectively. These are not incremental features; they are foundational changes that redefine what Kafka can do, how it scales, and what it costs to operate.

KRaft — The Self-Managed Metadata Quorum

For more than a decade, Apache Kafka relied on Apache ZooKeeper as its external metadata store and coordination service. This architecture, while functional, introduced significant operational complexity and scalability limits. KRaft (Kafka Raft) eliminates ZooKeeper entirely, replacing it with a native consensus protocol built directly into Kafka.

The ZooKeeper Problem:

Operational Complexity: Running a production Kafka cluster meant operating two separate distributed systems. Each had its own configuration, monitoring requirements, upgrade cycles, and failure modes. Teams needed expertise in both systems, and troubleshooting issues often required understanding the complex interactions between them. This doubled the operational surface area and created a class of failures that were difficult to diagnose because they spanned two systems.

Scalability Bottleneck: ZooKeeper was not designed for Kafka's specific workload patterns. As Kafka clusters grew to support hundreds of thousands of partitions, ZooKeeper became a bottleneck. The metadata size grew, and operations like partition reassignments or leader elections could take minutes instead of seconds. A concrete example: creating a topic with 1,000 partitions in a ZooKeeper-based cluster could take 10–15 seconds as metadata was written to ZooKeeper and then propagated to all brokers. During this window, producers and consumers could not reliably interact with the new topic. ZooKeeper-based clusters were practically limited to around 200,000 partitions.

Metadata Propagation Delays: In the ZooKeeper model, metadata changes followed a multi-hop path: written to ZooKeeper, then read by the controller, then propagated to other brokers. This multi-hop process introduced latency and created windows where different parts of the cluster had inconsistent views of metadata.

Split-Brain Risk: With two distributed systems, there was always a risk of a "split-brain" scenario where Kafka and ZooKeeper disagreed about the state of the cluster. The controller (a Kafka broker) and ZooKeeper had to be kept in sync, and failures at the boundary between them could lead to inconsistent metadata.

The KRaft Architecture:

KRaft replaces ZooKeeper with a Raft-based quorum controller running within Kafka itself. The name combines "Kafka" and "Raft," the consensus algorithm developed by Diego Ongaro and John Ousterhout at Stanford University. Raft was designed to be more understandable than alternatives like Paxos while providing the same strong consistency guarantees.

The Controller Quorum: In a KRaft cluster, a subset of nodes are designated as controllers. These controllers form a Raft quorum, electing one controller as the active leader. The active controller handles all metadata changes, appending them to a replicated metadata log. The other controllers are hot standbys with fully replicated state, ready to take over instantly if the active controller fails. The quorum size determines fault tolerance: 3 controllers tolerate 1 failure; 5 controllers tolerate 2 failures. Even numbers are discouraged: a 4-controller quorum tolerates the same number of failures as 3, but with more overhead.

The Metadata Log: Metadata lives in an internal Kafka topic called __cluster_metadata. Every change—topic creation, partition reassignment, ACL modification, broker registration—is appended as a record to this log. Brokers track their state using offsets into this log. When a broker reconnects after a failure, it catches up by reading from its last known offset, rather than loading the entire metadata state from scratch. This event-sourced design is the key to KRaft's performance and recovery speed.

How the Metadata Log Works:

The Active Controller: The active controller is the leader of the Raft quorum. It receives all metadata change RPCs from brokers. Before committing a batch of records to the __cluster_metadata log, the active controller first attempts to apply them to its in-memory state. If this application process fails, the active controller process exits, allowing another node to take leadership. This is a critical safety mechanism: a controller that cannot correctly apply a metadata change must not continue to lead.

Replication: The active controller appends records to its local metadata log and replicates them to the follower controllers. A metadata change is only committed once a majority of the quorum has acknowledged it. This is the Raft consensus guarantee: no committed metadata is lost unless a majority of controllers fail simultaneously.

Snapshots: The metadata log cannot grow indefinitely. Periodically, the controllers write a snapshot of the in-memory metadata state to disk. This is conceptually similar to log compaction, but state is read from memory rather than re-reading the log from disk. Snapshots allow new or recovering controllers to load the current state without replaying the entire log from the beginning.

Broker Metadata Caching: Brokers do not maintain their own Raft quorum. Instead, they act as followers of the metadata log—they consume the __cluster_metadata topic to stay up to date. Each broker tracks its last consumed offset. When a broker reconnects after a failure, it catches up incrementally by reading from that offset, rather than fetching a full metadata snapshot. This makes metadata propagation far more efficient than the ZooKeeper model.

Controller Failover: Near-Instantaneous:

In the ZooKeeper model, when the controller failed, the new controller had to load all metadata from ZooKeeper. With millions of partitions, this could take minutes. During this window, the cluster could not process metadata changes (topic creation, leader elections for failed partitions), and some operations were blocked. In KRaft, the standby controllers already have the full metadata state in memory. When the active controller fails, a new leader is elected by the Raft quorum almost immediately. The new active controller does not need to load state from an external system; it is already there. The result is near-instantaneous controller failover. A Confluent lab experiment on a cluster with 2 million partitions—ten times the practical maximum for ZooKeeper—showed that controlled shutdown time and recovery time after uncontrolled shutdown are greatly improved with a quorum controller versus ZooKeeper. The KRaft consensus and quorum controller enable Kafka clusters to scale to millions of partitions through improved control plane performance.

Deployment Modes: Separated vs. Combined:

Separated Mode (Recommended for Production): Controllers and brokers run on different nodes. This provides isolation: controller performance is not affected by broker workloads (disk I/O from produce/fetch, network saturation from replication). Controllers can be scaled and rolled independently of brokers. This is the recommended mode for large clusters and critical production deployments.

Combined Mode: A single node runs both controller and broker roles (process.roles=broker,controller). This is simpler to operate for small use cases like development environments. The key disadvantage is that the controller is less isolated from the rest of the system. It is not possible to roll or scale the controllers separately from the brokers in combined mode. Combined mode is not recommended in critical deployment environments.

The Path to KRaft: Migration and the 4.0 Milestone:

The transition to KRaft was a multi-year journey: Kafka 2.8: KRaft released in early access. Kafka 3.0: KRaft released in preview. Kafka 3.3.1: KRaft marked production-ready. Kafka 3.9.x: The last major release supporting both ZooKeeper and KRaft—the bridge version for migrations. March 2025 (Kafka 4.0): ZooKeeper support completely removed. KRaft is the only supported mode for all new and upgraded deployments. For organizations still on ZooKeeper, migration paths exist. Cloud providers like Amazon MSK now support in-place upgrades from ZooKeeper to KRaft metadata mode through the familiar version upgrade workflow. Managed services like Aiven offer automated, zero-downtime migrations triggered during a routine version upgrade from Kafka 3.8 to 3.9, incurring two rolling restarts of the brokers and adding about 15 minutes of overhead for a 32-node cluster.

Tiered Storage (KIP-405) — Decoupling Compute from Storage

Kafka's traditional architecture tightly couples compute and storage. Every byte of data is stored on the local disks of the brokers, and retention is limited by the size of those disks. This model works well for real-time streaming, but it becomes prohibitively expensive when organizations need to retain data for weeks, months, or years for compliance, analytics, or replay. Tiered Storage, introduced in KIP-405 and reaching general availability in Kafka 3.9, breaks this coupling. It introduces two storage tiers: a local (hot) tier on broker disks, and a remote (cold) tier in object storage like Amazon S3, Google Cloud Storage, or Azure Blob Storage. Recent data stays on local disks for low-latency access; older, closed log segments are offloaded to object storage for long-term retention at a fraction of the cost.

The Architecture of Tiered Storage:

The Local Tier (Hot): This is the traditional Kafka storage model. It uses fast SSDs attached to the brokers and holds recent data—typically hours to days of retention. Consumers reading recent data experience the same low latency as in a non-tiered cluster.

The Remote Tier (Cold): This uses external object storage systems. It holds historical data—weeks, months, or years—at a much lower cost per gigabyte than broker-attached SSDs. The remote tier is pluggable: Kafka defines an interface, and vendors or the community provide implementations for specific storage backends.

The Remote Log Manager (RLM): The RLM is the central broker-side component responsible for managing the lifecycle of log segments in remote storage. It runs on every broker and performs two roles: On leader replicas, it persists old log segments to the tiered store and deletes expired data from the tiered store. On leader and follower replicas, it reads the log from the tiered store for consumer fetches.

The Plugin Interfaces: RemoteStorageManager (RSM): The "mover." It handles the physical interaction with remote storage: uploading completed log segments, fetching data when consumers request historical data, and deleting expired segments. Each uploaded segment receives a unique RemoteLogSegmentId that identifies it in the remote storage system. RemoteLogMetadataManager (RLMM): The "catalog." It maintains metadata about which segments exist in remote storage, their offsets, and their locations. This metadata layer requires strong consistency guarantees to ensure consumers can reliably find and read historical data. Kafka provides a default implementation using an internal topic called __remote_log_metadata. Critically, Apache Kafka does not ship with actual storage backend implementations. The community and vendors provide plugins. For example, Aiven offers an open-source RemoteStorageManager supporting S3, GCS, and Azure Blob Storage, and Adobe has a similar implementation.

The Write Path: How Segments Are Offloaded:

The tiering process is asynchronous and designed not to interfere with the producer write path.

Eligibility Criteria: A log segment is eligible for offloading only when two conditions are met: The segment is closed (not the active segment). Active segments are still being written to and cannot be uploaded. The segment's end offset is less than the Last Stable Offset (LSO). Remote storage should only contain committed or acknowledged data, never data from open transactions.

The Upload Trigger: The RLM runs a periodic task controlled by remote.log.manager.task.interval.ms (default 30 seconds). Every interval, it scans for eligible segments and uploads them to remote storage. Only closed, non-active segments are uploaded, once all required index files exist and the LSO has moved past the segment.

The Upload Process: When a segment is selected for offloading, the RLM uses the RemoteStorageManager.copyLogSegmentData method to perform the upload. The segment is typically uploaded as multiple blobs: the chunked segment data, a combined index blob, and a manifest with chunk and compression metadata. Configurable quotas at both the broker and plugin level prevent bursty uploads from straining network bandwidth, disk bandwidth, or CPU during tiering.

Metadata Recording: Once the upload succeeds, the RLM records the segment's metadata (its remote location, offset range, and other attributes) through the RemoteLogMetadataManager. This metadata is written to the __remote_log_metadata topic. Every broker consumes all partitions of this topic on startup to rebuild the latest remote segment state in memory.

Local Copy Retention: The local copy of the segment is not deleted immediately after upload. It is retained until the local retention policy (retention.ms or retention.bytes for the local tier) determines it should be removed. This creates a window where both a local and a remote copy exist, ensuring that recent reads continue to be served from local disk.

The Read Path: How Consumers Fetch Remote Data:

Tiered Storage is designed to be completely transparent to clients. Consumers use the same Kafka consumer API; no code changes are required. When a consumer requests data that is no longer on the local disk, the broker automatically fetches it from remote storage.

The Fetch Decision: When a fetch request arrives, the broker checks whether the requested offset is in the local log or the remote log. If the data is still locally on the broker, the read is served from there. If the data is only in remote storage, the broker routes the fetch to the remote tier.

The Remote Fetch Process: The broker's RLM fetches the required segment from remote storage via the RemoteStorageManager. The plugin (e.g., Aiven's) fetches data in configurable chunks (4 MiB by default) using byte-ranged GETs. Results are cached via a Caffeine LFU cache to avoid duplicate remote reads. Prefetching eagerly fetches upcoming chunks in parallel while serving the current request. Combined with caching, this allows consumers to read from object storage at close to local disk latency.

The Latency Trade-off: Remote reads are inherently slower than local reads. Historical reads hit object-storage latency, so backfills and far-behind consumers are slower than an all-local setup. Remote fetches add IOPS and request cost. When the broker downloads a data segment from remote storage and stores it locally, it imposes additional IOPS on the network and local disk capacity, and it can negatively impact the page cache established for messages closer to the end of the queue. However, the prefetching and caching mechanisms mitigate this for most workloads, especially when consumers are reading sequentially through historical data.

KIP-1002 and KIP-1248: Ongoing improvements target the fetch path. KIP-1002 addresses the fact that each segment index is fetched independently, which can increase latency when fetching across segments because remote fetch round-trips are the most expensive operation. KIP-1248 explores broker support for remote tiered storage fetch directly from the consumer, which would eliminate the double data transfer (broker-to-remote, then broker-to-consumer) and reduce network latency and transfer costs.

Retention and the Decoupling of Storage from Compute:

The most transformative aspect of Tiered Storage is that it decouples retention from broker disk capacity. In the traditional model, the maximum retention was strictly bounded by the total disk capacity of the cluster. Want 30 days of history? Buy bigger disks. This made long retention prohibitively expensive because you were paying SSD prices for cold data. With Tiered Storage, you configure two separate retention policies: Local retention: How long data stays on the fast local disks (e.g., 7 days). Remote retention: How long data stays in object storage (e.g., 2 years). The local tier becomes a hot cache, not the system of record. Your brokers no longer need to be storage servers pretending to be a streaming system. You can retain data for years at object-storage prices, while still serving recent data with local-disk latency. This decoupling also enables faster cluster operations. Brokers can be added or removed without migrating terabytes of historical data, because the historical data lives in the remote tier, accessible to any broker.

Share Groups (KIP-932) — Queue Semantics on a Log

Kafka's consumer group model is built on a strict invariant: one partition, one consumer. This provides ordering and simplicity, but it also imposes a hard scalability ceiling: the maximum parallelism of a consumer group equals the number of partitions. If you have 10 partitions, you can have at most 10 active consumers. To add more processing capacity, you must add more partitions—an operation that is not always desirable or possible. Share Groups, introduced in KIP-932 and production-ready since Kafka 4.2, break this invariant. They introduce queue-like semantics to Kafka: multiple consumers in a share group can cooperatively read from the same partition, with per-record acknowledgment instead of partition-level offset commits. This decouples consumer parallelism from the number of partitions.

The Problem with Consumer Groups for Queue Workloads:

Consumer groups are designed for log workloads: ordered streams where each record must be processed exactly once in order. But many Kafka use cases are actually queue workloads: task distribution, work queues, and point-to-point messaging, where ordering is less important than throughput and per-message failure handling. In a consumer group, if a consumer encounters a "poison message" (a record that always fails processing), the entire partition is blocked. The consumer cannot skip the record without committing past it (which would lose the record for everyone), and it cannot retry indefinitely without stalling the partition. The coarse granularity of offset-based commits means one bad record can halt an entire partition. Share Groups solve this by moving from partition-level ownership to record-level coordination.

The Share Group Model:

A share group is a new consumption model where: Multiple consumers (share consumers) cooperatively read from the same partition. Each record is acquired by a consumer for a time-limited period. Each record must be explicitly acknowledged (ACCEPT, RELEASE, or REJECT). The broker, not the client, coordinates which consumer gets which record.

The Record State Machine:

The heart of a share group is the record state machine managed by the SharePartitionManager. Each record in a share partition transitions through a set of states: Available: The record is eligible for delivery to a consumer. Acquired: The record has been delivered to a consumer and is protected by a time-limited acquisition lock (default 30 seconds). While acquired, it cannot be delivered to another consumer. Acknowledged: The consumer has explicitly ACCEPTed the record. It will never be re-delivered. Archived: The record has been REJECTed or has exceeded its maximum delivery count. It is permanently archived and never re-delivered.

The Acknowledgment Types: ACCEPT: The record was processed successfully. It is acknowledged and never re-delivered. RELEASE: The consumer could not process the record (e.g., a transient failure) and is releasing it back to the share group for immediate redelivery to another consumer. REJECT: The record is permanently unprocessable (a poison message). It is archived and never re-delivered. This is the critical mechanism that allows a share group to move past a poison message without blocking the partition.

Delivery Count: The broker tracks the delivery count for each record—the number of times it has been acquired. If the count exceeds maxDeliveryCount, the record is automatically transitioned to ARCHIVED state, preventing infinite redelivery loops.

The Share-Partition Offset Window: SPSO and SPEO:

Share groups do not use traditional consumer offsets. Instead, each share partition maintains two offsets: Share-Partition Start Offset (SPSO): The earliest eligible record for consumption—the lower bound of the active window. Share-Partition End Offset (SPEO): The boundary of the in-flight records window—the upper bound of records that have been fetched and may be acquired. Records before the SPSO have been acknowledged and purged. Records after the SPEO have not yet been delivered. The window between SPSO and SPEO is the set of records that are in various states (Available, Acquired, Acknowledged, Archived).

The Broker-Side Coordination:

Unlike consumer groups, where the client-side group leader computes the assignment, share groups use server-side coordination only. The broker's SharePartitionManager manages partition state, record acquisition, lock timeouts, and delivery counts. This eliminates the need for the complex client-side rebalancing protocol that consumer groups require and reduces the latency for consumer membership changes. ShareGroupHeartbeat: Share consumers send a ShareGroupHeartbeat request to the broker. This single RPC carries liveness, subscription, and acknowledgment information. The broker responds with records that have been acquired for that consumer. There is no group-wide barrier, no JoinGroup/SyncGroup, and no stop-the-world rebalance. The group states are simplified to EMPTY, STABLE, and DEAD.

Explicit vs. Implicit Acknowledgment:

Explicit (default): The application calls acknowledge() for each record individually. On session rollback, records are RELEASEd back to the share group for immediate redelivery. This provides the finest-grained control over failure handling. Implicit: The broker treats all delivered records as ACCEPTed on the next poll/commit. On rollback, the consumer is closed so the broker's record-acquisition lock can expire and the records become eligible for redelivery. This is simpler but offers less control.

The Use Cases for Share Groups:

Share groups are designed for queue-like workloads where: Multiple consumers need to process items efficiently in parallel from a single or multiple topics. Messages need explicit acknowledgment/release to avoid reprocessing or allow retries. Consumer parallelism should not be limited by the number of partitions. A single poison message must not block the entire partition. Examples include task distribution systems, order processing queues, and any point-to-point messaging pattern where per-message failure handling is essential.

20 Conceptual & Confusing Modern Architecture Questions

1. If KRaft eliminates ZooKeeper, does it also eliminate the need for a separate controller quorum?

No. KRaft replaces ZooKeeper with a Raft-based controller quorum that runs inside Kafka. The controllers are still a separate set of nodes (or a combined role) that form a quorum. What changes is that the metadata management is no longer external; it is handled by Kafka itself using the Raft consensus protocol. You still need a quorum of controllers (3 or 5 for production) to tolerate failures.

2. Why does KRaft use an internal topic (__cluster_metadata) instead of a dedicated consensus database?

Because Kafka is already a replicated log system. The metadata log is conceptually identical to a Kafka topic: an append-only, replicated sequence of records. By storing metadata as records in a Kafka topic, KRaft reuses Kafka's existing replication and log infrastructure. Brokers can consume this topic just like any other topic, tracking their offsets to stay in sync. This is a form of self-hosting: using the system's own primitives to manage the system itself.

3. What happens if a KRaft controller applies a metadata change to its in-memory state but crashes before committing it to the log?

The change is not committed and will be lost. The active controller applies the batch to its in-memory state before appending to the log. If it crashes before the append is replicated to a majority, the change is not durable. When a new controller is elected, it will not have that change in its state. This is safe because the change was never acknowledged to the client. If the in-memory application itself fails (e.g., due to an invalid state transition), the controller exits, allowing another node to take leadership—preventing a controller with corrupt state from continuing to lead.

4. How can KRaft support 2 million partitions when ZooKeeper topped out at 200,000?

The bottleneck was not Kafka's data plane; it was the metadata control plane. ZooKeeper stored metadata as znodes, and every metadata change required a round-trip to ZooKeeper and then propagation to brokers. With millions of partitions, the metadata size and the frequency of changes overwhelmed ZooKeeper's capacity. KRaft stores metadata in a compact, event-sourced log and uses offsets for incremental propagation. Brokers no longer fetch full metadata snapshots; they read the delta from their last offset. The controller failover is near-instantaneous because standby controllers already have the state in memory. This architectural change removes the control-plane bottleneck, allowing the cluster to scale to millions of partitions.

5. Is Tiered Storage a replacement for local disks, or a supplement?

It is a supplement. The local tier remains the primary storage for recent data and the source of low-latency reads. Tiered Storage offloads closed, non-active segments to remote storage for long-term retention. The local disk becomes a hot cache for recent data, not the system of record. If the local disk fails, the broker can recover recent data from replicas and historical data from remote storage, but the local disk is still essential for real-time performance.

6. If a segment is uploaded to remote storage, when is the local copy deleted?

After the local retention policy is satisfied. The local copy is not deleted immediately upon upload. It remains on the local disk until it exceeds the local retention threshold (e.g., retention.ms for the local tier). This creates a window where both a local and a remote copy exist, ensuring that recent reads continue to be served from local disk. The RemoteLogManager deletes the local copy only when the local retention policy dictates it.

7. What happens if a consumer tries to read a segment that is being uploaded to remote storage?

The read is served from the local copy. The upload process is asynchronous, and the local segment remains fully readable until it is deleted by local retention. There is no window during which a segment is "in transit" and unreadable. The RLM only deletes the local copy after the upload is confirmed and the local retention policy allows deletion.

8. How does a read_committed consumer interact with Tiered Storage and the Last Stable Offset (LSO)?

The LSO still gates remote offloading. A segment is only eligible for upload to remote storage when its end offset is less than the LSO. This means remote storage only contains committed data. A read_committed consumer reading from remote storage will only see committed records. If a transaction is open, the segment containing it is not eligible for offloading until the transaction resolves. This preserves the isolation guarantee across tiers.

9. Why does Tiered Storage add latency to historical reads, and how is this mitigated?

Remote storage (object storage) has higher latency than local SSD. A read from S3 or GCS involves a network round-trip and object-storage API overhead, typically in the tens of milliseconds versus sub-millisecond local reads. This is mitigated by: Chunked fetching: Data is fetched in 4 MiB chunks using byte-ranged GETs. Caching: An LFU cache (e.g., Caffeine) stores recently fetched chunks to avoid duplicate remote reads. Prefetching: Upcoming chunks are eagerly fetched in parallel while the current request is served. These mechanisms allow sequential historical reads to approach local-disk latency, though random point lookups in very old segments will still incur remote latency.

10. Can a share group consumer read from a partition that is also being read by a consumer group?

Yes. Share groups and consumer groups are independent consumption models. A partition can have multiple consumer groups (each with its own offset) and multiple share groups (each with its own record state machine) reading from it simultaneously. The broker coordinates record acquisition for share groups, but it does not interfere with consumer group offset management.

11. If a share group consumer crashes while holding an acquisition lock on a record, what happens?

The record becomes eligible for redelivery after the lock expires. The acquisition lock is time-limited (default 30 seconds). If the consumer does not acknowledge the record within the lock duration, the broker releases the lock and returns the record to the Available state. It can then be acquired by another consumer in the share group. The delivery count is incremented, and if it exceeds maxDeliveryCount, the record is archived.

12. How does a share group handle a poison message differently from a consumer group?

A consumer group cannot skip a poison message without committing past it, blocking the entire partition. A share group consumer can REJECT the poison message. The record is archived and never re-delivered, and the rest of the partition continues to flow. This is the fundamental advantage of per-record acknowledgment: one bad record does not block the entire stream.

13. What is the difference between RELEASE and REJECT in a share group?

RELEASE means the consumer could not process the record right now (e.g., a transient failure or resource contention). The record is returned to the Available state and can be re-delivered immediately, potentially to another consumer. REJECT means the record is permanently unprocessable (e.g., malformed data, a business rule violation). The record is Archived and will never be delivered again. REJECT is the mechanism for handling poison messages without blocking the partition.

14. Why do share groups have no rebalance protocol like consumer groups?

Because share groups do not assign partitions to consumers. In a consumer group, the rebalance protocol redistributes partition ownership. In a share group, multiple consumers can read from the same partition simultaneously. The broker's SharePartitionManager dynamically acquires records for available consumers. There is no partition ownership to reassign, so there is no need for a group-wide rebalance. The group states are simplified to EMPTY, STABLE, and DEAD, and membership changes are handled via heartbeats without a stop-the-world barrier.

15. Can a share group consumer exceed the number of partitions?

Yes. This is one of the primary benefits of share groups. Consumer group parallelism is capped at the number of partitions. Share group parallelism is decoupled from the partition count. You can have 100 consumers in a share group reading from a topic with 10 partitions, because the broker coordinates record-level distribution. This eliminates the need for "over-partitioning" just to achieve consumer parallelism.

16. Is the __remote_log_metadata topic replicated and durable like __consumer_offsets?

Yes. The __remote_log_metadata topic is an internal, replicated Kafka topic. It uses the same replication and durability guarantees as any other Kafka topic. The RemoteLogMetadataManager requires strong consistency to ensure consumers can reliably find and read historical data. The metadata about remote segments must survive broker failures, because without it, the cluster would not know which segments exist in remote storage or where they are located.

17. What happens if the remote storage backend (e.g., S3) is unavailable?

Historical reads fail, but recent reads continue to work. The local tier operates independently of the remote tier. If S3 is unavailable, consumers can still read recent data from local disk. However, consumers attempting to read historical data that exists only in remote storage will receive errors until the remote backend recovers. The RemoteLogManager will retry failed uploads and fetches with backoff. This is a critical operational consideration: the availability of your historical data depends on the availability of your object-storage provider.

18. How does KRaft handle a scenario where the active controller and a majority of the quorum are lost simultaneously?

The cluster loses the ability to make metadata changes. Raft requires a majority of the quorum to commit changes. If a majority of controllers are lost (e.g., 2 out of 3), no new metadata can be committed. The cluster can continue to serve produce and fetch requests for existing partitions (the data plane continues), but it cannot create topics, reassign partitions, or elect new leaders for failed partitions. This is a control-plane outage, not a data-plane outage. The cluster recovers when a majority of controllers is restored.

19. Why is combined mode (controller and broker on the same node) not recommended for production?

Because it sacrifices isolation. In combined mode, the controller shares CPU, memory, disk I/O, and network with the broker. A broker experiencing heavy produce/fetch load or replication traffic can starve the controller, delaying metadata operations and failover. Combined mode also prevents independent scaling and rolling upgrades of controllers versus brokers. It is suitable for development and small non-critical clusters, but production deployments should use separated mode for isolation and operational flexibility.

20. If Tiered Storage decouples storage from compute, can I run Kafka without local disks at all?

Not with KIP-405. Tiered Storage still requires local disks for the active segment and for recent data (the hot tier). Active segments are being written to and cannot be uploaded to remote storage. The local tier is essential for low-latency real-time reads and for the write path. The future direction (KIP-1150, "Diskless Topics") explores running brokers that fetch data entirely from object storage without local copies, but this is a separate, more radical architectural shift. KIP-405 is a two-tier model, not a zero-local-disk model.

Security & Operations

A Kafka cluster without security is a liability. Without authentication, any client on the network can produce malicious data or consume confidential information. Without authorization, a well-meaning developer can accidentally delete a critical topic. Without deliberate performance tuning, a cluster that worked in development will collapse under production load.

Security and operations are not afterthoughts; they are architectural layers that must be designed into the cluster from day one.

Authentication — Verifying Identity

Authentication answers the fundamental question: "Who are you?" Before any data flows, Kafka must verify the identity of every client (producer, consumer, admin tool) and, in KRaft mode, every broker and controller in the quorum. Kafka supports two authentication channels: SASL (Simple Authentication and Security Layer) and TLS mutual authentication (mTLS). Each mechanism presents a different trade-off between operational simplicity, credential rotation, and integration with enterprise identity systems.

SASL/PLAIN — The Simplest Mechanism:

SASL/PLAIN transmits a username and password in cleartext. It is the easiest mechanism to configure but offers the weakest security guarantee. It should never be used without TLS encryption, because the credentials are visible on the wire. SASL/PLAIN is appropriate only for development environments or when integrated with an external secret management system that rotates credentials programmatically.

SASL/SCRAM — Challenge-Response Authentication:

SCRAM (Salted Challenge Response Authentication Mechanism) provides stronger security than PLAIN by avoiding cleartext password transmission. Instead of sending the password over the network, SCRAM uses a challenge-response protocol where the client proves knowledge of the password through cryptographic hashing without revealing the password itself. Kafka supports SCRAM-SHA-256 and SCRAM-SHA-512, with SCRAM-SHA-512 recommended for new deployments due to its stronger cryptographic properties. In Kafka 4.0+ with KRaft mode, SCRAM credentials are stored in the cluster's metadata log (__cluster_metadata), not in ZooKeeper. This is a significant architectural shift from the ZooKeeper-based setup that older guides describe.

SASL/GSSAPI (Kerberos) — Enterprise Integration:

SASL/GSSAPI integrates Kafka with an existing Kerberos infrastructure. It is the standard choice for enterprises that already operate a Kerberos Key Distribution Center (KDC) and need Kafka to participate in a centralized identity federation. The Kerberos handshake is more complex than SCRAM: the client requests a ticket-granting ticket (TGT) from the KDC, then requests a service ticket for the Kafka broker, and finally presents the service ticket to the broker for authentication. This provides strong mutual authentication but requires significant operational overhead (KDC management, keytab distribution, ticket renewal).

SASL/OAUTHBEARER — Cloud-Native Identity:

OAUTHBEARER is Kafka's OAuth 2.0 implementation. It enables Kafka to validate OAuth 2.0 bearer tokens, bridging traditional Kafka authentication with modern cloud-native identity providers like Okta, Auth0, or any OIDC-compliant identity provider. How It Works: The client obtains a JWT (JSON Web Token) from an external authorization server. The client presents the token to the Kafka broker during the SASL handshake. The broker validates the token (signature, expiry, audience, issuer) either locally or by introspecting it with the authorization server. OAuth 2.0 with OpenID Connect (OIDC) has become the standard authentication mechanism for cloud-native Kafka deployments. SASL/OAUTHBEARER supports both unsecured JWT tokens (development only) and secured tokens from external identity providers.

SSL/TLS Mutual Authentication (mTLS):

mTLS uses client certificates instead of passwords or tokens. Both the client and the broker present X.509 certificates during the TLS handshake. The broker validates the client certificate against a trusted Certificate Authority (CA), and the client optionally validates the broker's certificate. Architectural Considerations: mTLS is machine-identity authentication. It is ideal for service-to-service communication where each application has its own certificate. Certificate rotation is a significant operational challenge. Short-lived certificates (e.g., 24-hour validity) require automation (e.g., cert-manager in Kubernetes, Vault PKI) to renew without downtime. The SSL user name is derived from the certificate's Distinguished Name (DN), typically CN=writeuser,OU=....

Inter-Broker and Controller Authentication:

Authentication is not limited to clients. In a secure cluster, brokers must authenticate to each other for replication, and brokers must authenticate to the KRaft controllers. In KRaft mode, the controller quorum has its own listener, configured via controller.listener.names (e.g., CONTROLLER). The listener.security.protocol.map must map both the broker listener and the controller listener to secure protocols. It is a requirement that the host and port defined in controller.quorum.bootstrap.servers match the controller listener configuration. The inter-broker SASL mechanism must be configured separately from the client-facing mechanism (sasl.mechanism.inter.broker.protocol), and it must be a mechanism that supports mutual authentication (SCRAM or GSSAPI, not PLAIN).

Authorization — Controlling Access

Authentication establishes identity. Authorization determines what that identity is allowed to do.

The ACL Model:

Kafka's authorization framework is pluggable, configured via authorizer.class.name. For KRaft clusters, the implementation is org.apache.kafka.metadata.authorizer.StandardAuthorizer, which stores ACLs in the cluster's metadata log. An ACL is defined in the general format: Principal {P} is [Allowed|Denied] Operation {O} From Host {H} on any Resource {R} matching ResourcePattern {RP}.

The Components: Principal: The authenticated identity, typically prefixed with User: (e.g., User:producer-app). Operation: The action being controlled (e.g., Read, Write, Create, Delete, Alter, Describe, All). Host: The IP address from which the request originates. This allows ACLs to restrict access to specific network locations. Resource: The target of the operation, identified by its type (Topic, Group, Cluster, TransactionalId, DelegationToken) and name. ResourcePattern: The matching strategy for the resource name: LITERAL (exact match), PREFIX (starts with), or WILDCARD (all resources of that type).

The Authorization Evaluation Path:

When a client sends a request to a broker, the StandardAuthorizer evaluates it against the ACLs stored in memory (loaded from the metadata log). The evaluation follows a specific precedence: Super Users: If the principal is listed in super.users, the request is allowed regardless of ACLs. Super users bypass all authorization checks. Deny ACLs: If an explicit Deny ACL matches the principal, operation, host, and resource, the request is denied immediately. Allow ACLs: If an explicit Allow ACL matches, the request is allowed. Default: If no ACL matches, the request is denied by default. The configuration allow.everyone.if.no.acl.found defaults to false, meaning an empty ACL list provides no access. Setting this to true is a dangerous misconfiguration that grants access to all unconfigured resources.

KRaft Principal Forwarding:

In KRaft clusters, admin requests such as CreateTopics and DeleteTopics are sent by the client to the broker listener. The broker must forward these requests to the active controller for execution. Authorization of these forwarded requests is performed on the controller node. The broker packages the client's request and the client's authenticated principal into an Envelope request. The controller first authenticates the broker (using the broker's principal), then authorizes the underlying request using the forwarded client principal. The Architectural Implication: This forwarding mechanism requires Kafka to serialize and deserialize the client principal. If a custom principal.builder.class is used, it must implement KafkaPrincipalSerde so that the principal can survive the broker-to-controller hop.

ACL Management:

ACLs are managed via the kafka-acls.sh CLI or the Admin API. ACLs are stored in the __cluster_metadata topic. When an ACL is added or removed, the change is appended to the metadata log, replicated by the Raft quorum, and propagated to all brokers. Each broker's StandardAuthorizer updates its in-memory ACL cache from the metadata log, ensuring that authorization decisions are made locally with minimal latency.

Performance Tuning — Maximizing Throughput

Security protects the cluster; performance tuning determines whether it is useful. Kafka's performance is governed by a small set of configurations that trade throughput against latency, and by a set of metrics that reveal when the cluster is approaching its limits.

The Producer Trade-off: batch.size and linger.ms:

The producer's throughput is directly tied to how efficiently it batches records. Two settings control this trade-off: batch.size (default 16KB): The maximum number of bytes accumulated per partition before a batch is sent. Larger batches mean fewer network requests and higher throughput. linger.ms (default 0 or 5ms): The maximum time the producer waits to fill a batch before sending it. Increasing this value allows more records to accumulate, improving throughput at the cost of added latency. For high-throughput pipelines, set batch.size to 32KB–1MB and linger.ms to 5–100ms. A common high-throughput configuration is batch.size=1MB and linger.ms=100ms. The key insight is that Kafka performance tuning is 20% changing configs and 80% understanding your workload. A batch size that is optimal for a low-latency trading system will be catastrophic for a batch analytics pipeline.

Compression:

Compression reduces network traffic and disk storage by compressing the entire batch, not individual records. The choice of codec is a trade-off between CPU overhead and compression ratio: LZ4: The recommended general-purpose choice. Low CPU overhead, good compression ratio. Zstd: The best compression ratio (up to 3x), ideal for high-throughput pipelines where network bandwidth is the bottleneck. Snappy: Similar to LZ4, with a different performance profile. Compression is configured via compression.type on the producer and broker. The broker can also recompress batches if the topic-level compression.type differs from the producer's.

Partition Sizing: The 4,000 Rule:

Partitions are the unit of parallelism. Too few partitions limit throughput; too many increase overhead and reduce cluster efficiency. The Recommended Limits: 4,000 partitions per broker is the general recommendation. 200,000 partitions per cluster was the practical limit for ZooKeeper-based clusters. KRaft can handle significantly more, but the per-broker limit remains a useful operational guardrail. Keep the total number of topics under 7,000 to avoid metadata and controller overhead. Partition counts cannot be reduced without recreating the topic. Start with a number that supports current parallelism and allows for future growth.

Acknowledgments and Durability:

The acks setting controls the durability of writes and has a direct impact on latency: acks=0: The producer does not wait for any acknowledgment. Lowest latency, highest risk of data loss. acks=1: The leader broker acknowledges the write. A balance between latency and durability, but data can be lost if the leader fails before replication. acks=all: The leader waits for the entire ISR to acknowledge. Highest durability, highest latency. For production, acks=all combined with min.insync.replicas=2 and a replication factor of 3 is the standard configuration for durability without sacrificing availability.

Consumer Tuning:

The consumer's throughput is governed by its fetch configuration: fetch.min.bytes (default 1): The minimum amount of data the broker should return. Increasing this reduces the number of fetch requests. fetch.max.wait.ms (default 500): The maximum time the broker waits to accumulate fetch.min.bytes. max.poll.records (default 500): The maximum number of records returned from a single poll() call. A consumer with a low fetch.min.bytes and a low fetch.max.wait.ms will spin in a tight loop, fetching empty responses and wasting CPU. Raising these values forces the broker to long-poll, blocking until data arrives.

Operational Monitoring — The Metrics That Matter

A Kafka cluster emits thousands of metrics. Most are noise. A small set of high-signal metrics reveals the health of the cluster.

Broker Health Metrics:

Under-Replicated Partitions: This is the single most critical operational metric. A partition is under-replicated when its ISR size is smaller than its replication factor. In a healthy cluster, this metric is zero. A non-zero value means the cluster is operating with reduced redundancy. If the ISR drops below min.insync.replicas, acks=all producers will be blocked from writing. ISR Shrink/Expand Rate: A rapidly changing ISR indicates instability—network flapping, GC pauses, or disk I/O bottlenecks. Stable ISRs are a sign of a healthy cluster. Offline Partitions: An offline partition has no leader. It cannot be read or written. This is a critical outage for that partition and requires immediate attention. Network Processor Idle Percentage: This metric reports the fraction of time the broker's network processors are idle. Ideally, this value should be greater than 0.3 (30%). A value below 0.3 indicates the network threads are saturated and cannot keep up with incoming requests. Request Handler Idle Percentage: The fraction of time the request handler threads are idle. When this drops below 20%, the broker is struggling to process requests, and latency will increase.

Consumer Metrics:

Consumer Lag: The difference between the producer's latest offset (Log End Offset) and the consumer's committed offset. Growing lag indicates the consumer cannot keep pace with the producer. Sustained lag threatens ISR stability and can eventually cause the consumer to fall out of retention, resulting in data loss. Commit Latency: The time it takes for an offset commit to be acknowledged. High commit latency can indicate coordinator load or network issues. Rebalance Rate: Frequent rebalances indicate consumer instability—pods restarting without static membership, session timeouts being too low, or processing taking longer than max.poll.interval.ms.

Infrastructure Metrics:

Disk Utilization: Keep disk utilization below 60% to leave headroom for partition rebalancing and to prevent data movement issues during broker failures. Network Throughput: Monitor bytes in/out per second. A saturated network is a bottleneck that no amount of producer tuning can overcome. CPU Usage: Sustained high CPU may indicate undersized brokers, inefficient serialization, or excessive compression overhead. JVM Heap and GC: Long GC pauses cause session timeouts and ISR shrinks. Monitor GC pause times and heap usage.

Security Telemetry:

Security monitoring is often neglected until an incident occurs. Key metrics: Failed Authentication Rate: A spike in failed authentications may indicate a misconfigured client, an expired certificate, or a brute-force attack. Authorization Failures: A spike in AuthorizationException may indicate a misconfigured ACL or an attempt to access unauthorized resources. TLS Handshake Failures: Can indicate certificate expiry, truststore misconfiguration, or protocol version mismatches.

20 Conceptual & Confusing Security & Operations Questions

1. If I use SASL/SCRAM, why do I still need TLS?

SCRAM protects the password from being transmitted in cleartext, but it does not encrypt the data flowing over the connection. Without TLS, records, offsets, and metadata are visible to anyone with network access. SCRAM provides authentication; TLS provides encryption. They are complementary, not substitutes. Always use SASL_SSL, never SASL_PLAINTEXT, in production.

2. What happens if a client connects with a valid certificate but no matching ACL?

Authentication and authorization are separate layers. A valid certificate authenticates the client as a specific principal, but the StandardAuthorizer still evaluates the request against the ACLs. If no Allow ACL matches the principal, operation, and resource, the request is denied (unless allow.everyone.if.no.acl.found=true, which is a dangerous misconfiguration). A certificate is an identity, not a permission.

3. Why is allow.everyone.if.no.acl.found considered a security risk?

When set to true, any resource with no ACL is accessible to every authenticated principal. A single missing ACL on a sensitive topic (e.g., pii-data, payment-events) grants read and write access to every user in the cluster. This violates the principle of least privilege. In production, this setting must be false, and ACLs must be explicitly granted for every resource.

4. How does KRaft Principal Forwarding change the authorization architecture?

In KRaft mode, admin requests (e.g., CreateTopics) are forwarded from the broker to the active controller. The broker wraps the request and the client's principal in an Envelope request. The controller authenticates the broker, then authorizes the request using the forwarded client principal. This means the authorization decision is made on the controller, not the broker. The architectural implication is that custom principal classes must implement KafkaPrincipalSerde to survive the serialization boundary.

5. Why is acks=all not sufficient for durability without min.insync.replicas?

The ISR is dynamic. If two of three brokers are offline, the ISR shrinks to one. In this state, acks=all is functionally identical to acks=1—the leader waits only for itself. min.insync.replicas (set to 2) forces the leader to reject writes when the ISR is below the threshold, preventing the leader from acknowledging writes that are not safely replicated. The two settings must be used together.

6. If I increase batch.size and linger.ms, will my producer always achieve higher throughput?

Only if the bottleneck is network or per-request overhead. If the bottleneck is broker disk I/O, consumer processing speed, or network bandwidth saturation, larger batches will not help. They may even increase latency without improving throughput. Performance tuning requires identifying the actual bottleneck first. As one source notes, it is "20% changing configs and 80% understanding your workload".

7. Why is 4,000 partitions per broker recommended, and what happens if I exceed it?

Each partition consumes memory (for indexes, metadata), file handles (for segment files), and CPU (for replication threads and request handling). Beyond 4,000 partitions per broker, the overhead of managing partitions begins to degrade performance—leader elections take longer, controller metadata becomes larger, and the broker spends more time on housekeeping than on serving clients. The limit is a guideline, not a hard constraint, but exceeding it requires careful monitoring and tuning.

8. What does it mean if the network processor idle percentage drops below 0.3?

The network processors handle all incoming requests—produce, fetch, metadata, admin, and replication. When idle drops below 0.3, the network threads are saturated and cannot keep up with the request rate. Requests queue up, latency increases, and the broker becomes a bottleneck for the entire cluster. This is a sign that you need more brokers, faster network hardware, or both.

9. Why does consumer lag sometimes decrease when consumers are unhealthy?

If a consumer crashes or is removed from the group, it stops committing offsets. The remaining consumers take over its partitions. The group's lag (the maximum lag across all partitions) may temporarily decrease if the crashed consumer was the most lagged. This is a false signal. The correct metric is per-partition lag, not group-level lag. A crashed consumer is a failure, not an improvement.

10. What is the difference between session.timeout.ms and max.poll.interval.ms?

session.timeout.ms is checked by the heartbeat thread. If the coordinator does not receive a heartbeat within this window, the consumer is declared dead. max.poll.interval.ms is checked by the poll thread. If the application goes too long between poll() calls (even if the heartbeat thread is alive), the consumer voluntarily leaves the group. The first detects a crashed process; the second detects a stuck processing loop.

11. Can I use mTLS and SASL simultaneously on the same listener?

A single listener uses one security.protocol (e.g., SSL, SASL_SSL, SASL_PLAINTEXT). You cannot stack mTLS and SASL on the same listener. However, you can run multiple listeners on different ports, each with a different security protocol. For example, CLIENT://:9092 with SASL_SSL for external clients, and INTERNAL://:9093 with SSL (mTLS) for internal services. This allows different client populations to use different authentication mechanisms.

12. How does SCRAM credential rotation work in KRaft mode without downtime?

In KRaft mode, SCRAM credentials are stored in the __cluster_metadata log. You can update a SCRAM credential using the Admin API or kafka-configs.sh. The change is appended to the metadata log, replicated by the controller quorum, and propagated to all brokers. Brokers update their in-memory credential cache without a restart. This is a significant operational improvement over ZooKeeper-based clusters, where SCRAM credentials were stored in ZooKeeper and rotation could be more disruptive.

13. What is the difference between a Deny ACL and the absence of an Allow ACL?

Deny ACLs exist for explicit, targeted revocation. If a principal has been granted Allow on a resource via a PREFIX or WILDCARD ACL, a Deny ACL on a specific resource name overrides the broader Allow. This allows administrators to grant broad access while carving out exceptions. In the evaluation order, Deny takes precedence over Allow.

14. Why is fetch.min.bytes=1 and fetch.max.wait.ms=0 a performance anti-pattern?

With these settings, the consumer sends a fetch request, and if there is no new data, the broker immediately returns an empty response. The consumer immediately sends another fetch. This creates a tight spin loop that consumes CPU, network bandwidth, and broker request-handling capacity for no useful work. Setting fetch.max.wait.ms to a non-zero value (e.g., 500ms) makes the broker long-poll, blocking until data arrives or the timeout expires, eliminating the spin.

15. How does the StandardAuthorizer achieve low-latency authorization decisions?

The StandardAuthorizer loads the ACLs from the __cluster_metadata log into an in-memory cache. Authorization decisions are made against this in-memory structure, not by reading from disk or making a network call. The ACL cache is kept up to date by consuming the metadata log. This design ensures that authorization adds minimal latency to the request path.

16. What happens if the controller quorum is configured with an even number of nodes?

Raft requires a majority to commit changes. A 4-node quorum requires 3 nodes to commit (majority of 4 is 3), tolerating only 1 failure—the same as a 3-node quorum. However, the 4-node quorum has more overhead (more replication traffic, more complex elections) with no increase in fault tolerance. An even number is therefore discouraged; use 3 or 5.

17. Why does a growing consumer lag eventually threaten ISR stability?

If a consumer is far behind, it may be reading old segments. But more critically, a growing lag often indicates that the consumer is overloaded, which can lead to longer processing times. If processing exceeds max.poll.interval.ms, the consumer is removed from the group, triggering a rebalance. During the rebalance, partitions are reassigned, and the new consumer may start from an older offset, further increasing lag. Additionally, if the lag is caused by a broker-side bottleneck (e.g., disk I/O saturation), that same bottleneck can prevent follower replicas from fetching data, causing them to fall out of the ISR and shrinking the ISR.

18. What is the architectural difference between acks=1 and acks=all in terms of the Purgatory?

With acks=1, the broker's I/O thread appends the record to the leader's log and immediately responds to the producer. The request does not enter the Purgatory. With acks=all, the request is placed in the Purgatory (a delayed-operation timer wheel) and waits until every ISR follower has fetched and acknowledged the record. This adds a network round-trip to the followers and a Purgatory wait to the producer's latency. The architectural cost of durability is the Purgatory wait.

19. Why is inter-broker SASL mechanism configuration separate from client SASL mechanism configuration?

Clients and brokers have different security requirements. Clients may use PLAIN (in development) or OAUTHBEARER (with an external IdP), while brokers should use a mechanism that supports mutual authentication, such as SCRAM or GSSAPI. PLAIN does not support mutual authentication and should never be used for inter-broker communication. The separation (sasl.mechanism for clients, sasl.mechanism.inter.broker.protocol for brokers) allows each population to use the appropriate mechanism.

20. If disk utilization is at 80%, why is that considered a risk even if the cluster is functioning?

Disk headroom is required for partition rebalancing and broker failure recovery. When a broker fails, its partitions are reassigned to surviving brokers. The surviving brokers must write the replicated data to their disks. If a broker is already at 80% utilization, it may not have enough space to accept the reassigned partitions, causing the reassignment to fail. The recommended maximum is 60% utilization to leave sufficient headroom for failure scenarios.
