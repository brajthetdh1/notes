Introduction to Volumes

A Kubernetes Volume is a directory containing data accessible to containers in a Pod. Unlike container filesystems, volumes persist across container restarts and can be shared between containers in the same Pod.

Volumes solve the problem of data persistence in containerized applications by providing various storage backends and lifecycle management options.

Key Concept: Volumes decouple storage from Pod lifecycle, enabling data persistence, sharing between containers, and integration with external storage systems.

Volume Features

  • Data persistence across container restarts
  • Sharing data between containers in a Pod
  • Integration with cloud and network storage
  • Dynamic provisioning of storage
  • Support for various storage backends
  • Lifecycle management and cleanup

Container Filesystem Limitations

Container filesystems are ephemeral - data is lost when the container crashes, restarts, or the Pod is rescheduled. Volumes provide the solution for persistent data storage requirements.

Volume Concepts

Volume vs Container Storage:

  • Container Storage: Ephemeral, tied to container lifecycle
  • Volume Storage: Persistent, survives container restarts
  • Shared Access: Multiple containers can access same volume

Ephemeral Volumes

Ephemeral Volume Types

Ephemeral volumes have the same lifetime as the Pod. They are created when the Pod is scheduled and destroyed when the Pod is removed.

When to Use Ephemeral Volumes:

  • • Temporary scratch space
  • • Cache directories
  • • Build artifacts
  • • Temporary file processing
  • • Data that doesn't need persistence

Common Ephemeral Types:

  • emptyDir: Empty directory for Pod lifetime
  • hostPath: Node filesystem directory (with caveats)
  • gitRepo: Git repository checkout (deprecated)

emptyDir Example


apiVersion: v1
kind: Pod
metadata:
  name: emptydir-pod
spec:
  containers:
  - name: writer
    image: busybox
    command: ["/bin/sh"]
    args: ["-c", "while true; do echo $(date) >> /cache/timestamp; sleep 1; done"]
    volumeMounts:
    - name: cache-volume
      mountPath: /cache
      
  - name: reader
    image: busybox
    command: ["/bin/sh"]
    args: ["-c", "tail -f /cache/timestamp"]
    volumeMounts:
    - name: cache-volume
      mountPath: /cache

  volumes:
  - name: cache-volume
    emptyDir: 
      medium: Memory  # Optional: use memory instead of disk
      sizeLimit: 100Mi  # Optional: size limit

# emptyDir is created when Pod is assigned to node
# Survives container restarts but not Pod deletion
# Can be backed by node's disk or memory

hostPath Volume


apiVersion: v1
kind: Pod
metadata:
  name: hostpath-pod
spec:
  containers:
  - name: test-container
    image: busybox
    command: ["/bin/sh"]
    args: ["-c", "while true; do echo $(date) >> /host-data/log.txt; sleep 5; done"]
    volumeMounts:
    - name: hostpath-volume
      mountPath: /host-data

  volumes:
  - name: hostpath-volume
    hostPath:
      # Required: path on the host
      path: /data/pod-storage
      # Optional: type of path
      type: DirectoryOrCreate  # Other options: Directory, File, Socket, etc.

# Security Considerations:
# - Pods can access host filesystem
# - Use only for trusted workloads
# - Consider node affinity for specific nodes
# - Not suitable for multi-node clusters

hostPath volumes mount a file or directory from the host node's filesystem into the Pod. Use with caution due to security implications.

Persistent Volumes

Persistent Volume (PV) Concepts

A PersistentVolume (PV) is a cluster-wide storage resource provisioned by an administrator. PVs have a lifecycle independent of any individual Pod.

PV Characteristics:

  • • Cluster-level resource
  • • Independent of Pod lifecycle
  • • Backed by physical storage
  • • Supports various access modes
  • • Can be statically or dynamically provisioned

Access Modes:

  • ReadWriteOnce (RWO): Read-write by single node
  • ReadOnlyMany (ROX): Read-only by many nodes
  • ReadWriteMany (RWX): Read-write by many nodes
  • ReadWriteOncePod (RWOP): Read-write by single Pod

PersistentVolume Example


apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs
  labels:
    type: nfs
    environment: production
spec:
  capacity:
    storage: 10Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs-storage
  mountOptions:
    - hard
    - nfsvers=4.1
  nfs:
    path: /exports/data
    server: nfs-server.example.com

# PV States:
# - Available: Free and not yet bound
# - Bound: Bound to a PVC
# - Released: PVC deleted but resource not reclaimed
# - Failed: Automatic reclamation failed

# Reclaim Policies:
# - Retain: Manual reclamation
# - Recycle: Basic scrub (rm -rf /volume/*)
# - Delete: Associated storage asset deleted

Different PV Types

Storage Classes

StorageClass Concepts

A StorageClass provides a way to describe the "classes" of storage available. Different classes might map to quality-of-service levels, backup policies, or arbitrary policies determined by cluster administrators.

StorageClass Benefits:

  • • Dynamic volume provisioning
  • • Storage tier abstraction
  • • Policy-based storage selection
  • • Cloud provider integration
  • • Custom parameters for provisioners

Common Provisioners:

  • kubernetes.io/aws-ebs: AWS Elastic Block Store
  • kubernetes.io/gce-pd: Google Persistent Disk
  • kubernetes.io/azure-disk: Azure Disk
  • kubernetes.io/csi: Container Storage Interface
  • kubernetes.io/no-provisioner: Manual provisioning

StorageClass Examples


# AWS EBS StorageClass
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ebs
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
  fsType: ext4
reclaimPolicy: Delete
allowVolumeExpansion: true
mountOptions:
  - debug
volumeBindingMode: WaitForFirstConsumer

# Azure Disk StorageClass
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: managed-premium
provisioner: kubernetes.io/azure-disk
parameters:
  storageaccounttype: Premium_LRS
  kind: Managed
reclaimPolicy: Delete

# GCE PD StorageClass
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard-pd
provisioner: kubernetes.io/gce-pd
parameters:
  type: pd-standard
  replication-type: none
reclaimPolicy: Delete

Volume Binding Modes

Immediate

PV is bound immediately when PVC is created

  • ✓ Fast binding
  • ✗ May bind to wrong topology
  • ✓ Good for single-zone clusters

WaitForFirstConsumer

PV binding is delayed until Pod using PVC is scheduled

  • ✓ Better topology awareness
  • ✗ Slightly slower binding
  • ✓ Recommended for multi-zone clusters

Persistent Volume Claims

PersistentVolumeClaim (PVC) Concepts

A PersistentVolumeClaim (PVC) is a request for storage by a user. It is similar to a Pod - Pods consume node resources while PVCs consume PV resources.

PVC Binding Process:

  1. 1. User creates PVC with specific requirements
  2. 2. Control loop looks for matching PV
  3. 3. If no PV matches, dynamic provisioning may occur
  4. 4. PVC bound to PV
  5. 5. Pod can use PVC via volume mount

PVC States:

  • Pending: Waiting for PV binding
  • Bound: Successfully bound to PV
  • Lost: Bound PV no longer exists

PVC Examples


# Basic PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 8Gi
  storageClassName: fast-ebs

# PVC with Selector
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc-with-selector
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: ""
  selector:
    matchLabels:
      environment: production
    matchExpressions:
    - {key: tier, operator: In, values: [cache]}

# PVC for existing PV
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc-existing
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  volumeName: pv-nfs  # Specific PV name
  storageClassName: ""

Using PVC in Pods


apiVersion: v1
kind: Pod
metadata:
  name: pvc-pod
spec:
  containers:
  - name: app-container
    image: nginx:latest
    volumeMounts:
    - name: data-volume
      mountPath: /usr/share/nginx/html
      
  volumes:
  - name: data-volume
    persistentVolumeClaim:
      claimName: my-pvc
      readOnly: false  # Default

# StatefulSet with PVC Template
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: "nginx"
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "fast-ebs"
      resources:
        requests:
          storage: 1Gi

Volume Mounts

Volume Mount Concepts

Volume mounts connect volumes defined in Pod specifications to container filesystems. They determine where and how volumes are accessible within containers.

Mount Options:

  • • mountPath: Path in container filesystem
  • • subPath: Mount subdirectory of volume
  • • readOnly: Mount as read-only filesystem
  • • mountPropagation: Share mounts with host

Mount Propagation:

  • None: No mounts are propagated (default)
  • HostToContainer: Host mounts propagate to container
  • Bidirectional: Both directions propagation

Volume Mount Examples


apiVersion: v1
kind: Pod
metadata:
  name: volume-mount-pod
spec:
  containers:
  - name: app-container
    image: nginx:latest
    volumeMounts:
    # Basic mount
    - name: config-volume
      mountPath: /etc/nginx/conf.d
      readOnly: true
      
    # SubPath mount
    - name: shared-volume
      mountPath: /app/config
      subPath: app-config
      readOnly: false
      
    # Multiple containers sharing volume
    - name: log-volume
      mountPath: /var/log/app
      readOnly: false

  - name: sidecar-container
    image: busybox:latest
    command: ["/bin/sh", "-c", "tail -f /logs/app.log"]
    volumeMounts:
    - name: log-volume
      mountPath: /logs
      readOnly: true

  volumes:
  - name: config-volume
    configMap:
      name: nginx-config
      
  - name: shared-volume
    persistentVolumeClaim:
      claimName: app-pvc
      
  - name: log-volume
    emptyDir: {}

Advanced Mount Options


apiVersion: v1
kind: Pod
metadata:
  name: advanced-mount-pod
spec:
  containers:
  - name: test-container
    image: busybox:latest
    command: ["/bin/sh", "-c", "sleep 3600"]
    volumeMounts:
    # SubPath with environment expansion
    - name: workdir1
      mountPath: /workdir
      subPath: $(POD_NAME)  # Requires enableServiceLinks: true
      
    # SubPathExpr with downward API
    - name: workdir2
      mountPath: /logs
      subPathExpr: $(POD_NAMESPACE)/$(POD_NAME)
      
    # Mount propagation
    - name: host-mount
      mountPath: /host
      mountPropagation: HostToContainer

  volumes:
  - name: workdir1
    persistentVolumeClaim:
      claimName: work-pvc
      
  - name: workdir2
    persistentVolumeClaim:
      claimName: log-pvc
      
  - name: host-mount
    hostPath:
      path: /data
      type: Directory

# Enable environment variable expansion
enableServiceLinks: true

Volume Best Practices

Storage Design

Choose Appropriate Volume Types

Select volume types based on data persistence requirements and access patterns.

Use StorageClasses for Dynamic Provisioning

Leverage StorageClasses to automate PV creation and management.

Implement Proper Access Modes

Choose access modes that match your application's read/write requirements.

Operational Practices

Monitor Storage Usage

Implement monitoring and alerting for storage capacity and performance.

Implement Backup Strategies

Regularly backup critical data and test restore procedures.

Use Volume Snapshots

Leverage VolumeSnapshot API for point-in-time backups.

Pro Tip: Volume Expansion

Many CSI drivers and cloud providers support online volume expansion. Enable allowVolumeExpansion: true in your StorageClass and use kubectl patch pvc my-pvc -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}' to resize PVCs without downtime.
